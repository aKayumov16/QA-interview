# 🧠 Тема 1: Что такое Cypress?

### 🚀 Коротко о главном
**Cypress** — это современный инструмент для автоматизации тестирования веб-приложений. Он написан на JavaScript и предназначен для проведения **E2E (End-to-End)**, **Component**, **Integration** и **API** тестов. 

В отличие от старого доброго Selenium, который работает «снаружи» браузера через драйвер, Cypress работает **внутри** того же цикла выполнения, что и твое приложение. Это его главная суперсила.

---

### 🛠 Как это работает (Архитектура)
Представь, что Selenium — это водитель, который управляет машиной через пульт дистанционного управления (медленно, есть задержка связи). 
**Cypress — это пассажир, который сидит прямо в салоне.** Он видит всё, что происходит на приборной панели, может нажать на кнопки и чувствует каждое движение машины в реальном времени.

*   **Native Access:** Cypress имеет прямой доступ к объектам `window`, `document` и даже к состоянию твоего приложения (например, Redux или Vuex).
*   **Same-loop execution:** Код теста и код приложения работают в одном процессе. Это минимизирует проблемы с синхронизацией.

---

### ✨ Ключевые фичи (Почему его любят)
1.  **Automatic Waiting (Авто-ожидание):** Тебе больше не нужно писать `sleep(5000)` или мучиться с `WebDriverWait`. Cypress сам ждет, пока элемент появится в DOM, станет видимым и перестанет анимироваться.
2.  **Time Travel (Путешествие во времени):** После прохождения теста ты можешь навести мышку на каждый шаг в логе, и Cypress покажет состояние приложения именно в тот момент (сделает «снимок» DOM).
т3.  **Debuggability (Легкая отладка):** Ты можешь использовать обычные Chrome DevTools прямо внутри Cypress. Можно ставить `debugger` и смотреть переменные.
4.  **Network Control:** С помощью команды `cy.intercept()` ты можешь перехватывать сетевые запросы, подменять ответы сервера (mocking) или имитировать ошибки (например, 500 Internal Server Error).
5.  **Screenshots & Videos:** Автоматическое создание скриншотов при падении теста и запись видео всего прогона.

---

### ⚠️ Нюансы и ограничения (Взгляд Senior-а)
Не всё так идеально. Как опытный инженер, ты должен знать, где Cypress может «споткнуться»:

*   **Ограничение одного домена:** Исторически Cypress было сложно работать с переходом на другой сайт (например, с `mysite.com` на `paypal.com`). Сейчас есть команда `cy.origin()`, но это всё равно требует осторожности.
*   **Только браузеры на движке Chromium и Firefox:** Ты не сможешь протестировать Safari так же глубоко, как в WebKit (хотя поддержка WebKit развивается).
*   **Не для мобильных приложений:** Cypress тестирует только веб-приложения в браузере. Он не предназначен для тестирования нативных iOS/Android приложений.
*   **Одностраничность:** Из-за архитектуры внутри браузера, управление несколькими вкладками одновременно — это боль и костыли.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Чем Cypress лучше Selenium?**
**О:** Скоростью выполнения, отсутствием необходимости в драйверах, встроенным авто-ожиданием и возможностью глубокого доступа к состоянию приложения (DOM, Network, Window).

**В: Можно ли с помощью Cypress тестировать API?**
**О:** Да! С помощью `cy.request()` ты можешь отправлять GET, POST, PUT, DELETE запросы и проверять ответы сервера так же легко, как и UI-тесты.

**В: Что такое Flaky Tests (флакующие тесты) и помогает ли Cypress с ними?**
**О:** Флакующие тесты — это тесты, которые то проходят, то падают без изменения кода. Cypress радикально снижает их количество благодаря автоматическому ожиданию элементов и отсутствию задержек между командой теста и действием в браузере.

**В: Можно ли использовать Cypress для тестирования мобильных сайтов?**
**О:** Да, ты можешь эмулировать размер экрана (viewport) мобильного устройства через конфиг, но это будет именно тестирование веб-версии сайта, а не реального мобильного браузера на смартфоне.

# 🛠 Тема 1: Установка и настройка (Installation & Configuration)

Для начала забудь про установку библиотек глобально в систему. Это путь к «адской зависимости», когда один проект требует одну версию, а другой — другую. Мы работаем профессионально.

### 1. Изоляция окружения (The Golden Rule)
Прежде чем ставить `pytest`, тебе нужно создать **виртуальное окружение**. Это изолированная песочнет для твоего проекта.

*   **Как делать правильно:**
    ```bash
    # Создаем виртуальное окружение (называем его .venv)
    python -m venv .venv

    # Активируем его
    # Для Windows:
    .venv\Scripts\activate
    # Для macOS/Linux:
    source .venv/bin/activate
    ```
*   **Зачем это нужно?** Чтобы зависимости твоего проекта не конфликтовали с системными библиотеками и другими проектами на твоем компьютере.

### 2. Установка Pytest
Теперь, когда мы внутри «песочницы», устанавливаем сам инструмент и необходимые расширения.

*   **Базовая установка:**
    ```bash
    pip install pytest
    ```
*   **Установка зависимостей проекта:** В реальной работе ты не устанавливаешь пакеты по одному. У тебя есть файл `requirements.txt` или `pyproject.toml`. 
    *   Команда: `pip install -r requirements.txt`

### 3. Правила именования (Discovery Mechanism)
Pytest — это «умный» инструмент. Он сам сканирует папки и ищет тесты. Но он делает это только если ты соблюдаешь **магию имен**. Если нарушишь — он просто промолчит и скажет, что тестов 0.

*   **Файлы:** Должны начинаться с `test_*.py` (например, `test_login.py`).
*   **Классы:** Должны начинаться с `Test*` (например, `class TestUserAuth:`).
*   **Функции (тесты):** Должны начинаться с `test_*` (например, `def test_valid_password():`).

### 4. Конфигурационные файлы (Где хранить настройки)
Не нужно каждый раз при запуске писать длинную команду в терминале вроде `pytest --verbose --html=report.html`. Все это нужно вынести в конфиг.

У нас есть три главных игрока:

#### А) `pytest.ini` — Классика
Самый популярный способ. Создай этот файл в корне проекта.
```ini
[pytest]
# Какие папки сканировать (чтобы не тратить время на лишнее)
testpaths = tests

# Автоматические аргументы командной строки (addopts)
# -v: подробный вывод, --tb=short: короткий traceback при ошибках
addopts = -v --tb=short

# Настройка путей Python (чтобы тесты видели твой код)
pythonpath = src
```

####  Б) `pyproject.toml` — Современный стандарт
Сейчас в мире Python все переходят на этот формат для управления всеми инструментами сразу (black, flake8, pytest). 
*Если ты видишь такой файл — не пугайся, настройки pytest живут внутри него в секции `[tool.pytest.ini_options]`.*

#### В) `conftest.py` — Контейнер для фикстур
Это **не** файл конфигурации в плане настроек запуска, но это важнейший файл для *настройки окружения тестов*. 
*   В него мы кладем фикстуры, которые должны быть доступны всем тестам в этой папке.
*   Pytest автоматически подхватывает его при запуске.

### 💡 Senior Tips (Нюансы)

1.  **Проблема `PYTHONPATH`:** Самая частая ошибка новичка — запуск теста, который не может импортировать код из папки `src`. **Решение:** Всегда прописывай `pythonpath = src` в `pytest.ini`.
2.  **`.gitignore`:** Никогда не пушь папку `.venv` и кэши `__pycache__` в Git. Твой `.gitignore` должен быть чистым.
3.  **Зависимости:** Всегда фиксируй версии библиотек в `requirements.txt`. Сегодня `pytest` работает, а завтра вышла новая версия, которая всё сломала.

### ❓ FAQ (Частые вопросы)

**В: Почему Pytest говорит "collected 0 items", хотя я написал тесты?**
**О:** Проверь названия. Твой файл называется `login_test.py` вместо `test_login.py`? Или функция называется `check_login()` вместо `test_login()`? Pytest их просто не видит.

**В: Можно ли использовать `unittest` и `pytest` одновременно?**
**О:** Да, Pytest умеет запускать тесты, написанные на классическом `unittest`. Это удобно при миграции старого проекта на новый фреймворк.

**В: Зачем мне `addopts` в конфиге, если я могу просто писать аргументы в терминале?**
**О:** Терминал — для разовых экспериментов. Конфиг — для стабильности. Твой коллега или CI/CD сервер должен запускать тесты *одинаково* каждый раз без ручного ввода параметров.

# 🛠 Шпаргалка: Конфигурация PyTest

Конфигурация — это то, что превращает набор разрозненных скриптов в профессиональный фреймворк. Хорошая конфигурация позволяет запускать тесты одной командой, не забывая про важные флаги, и избавляет от «шума» в консоли.

### 1. Основные файлы конфигурации
В PyTest есть несколько способов хранить настройки. Выбирай один (лучше всего — современный `pyproject.toml`).

*   **`pytest.ini`**: Классический и самый популярный файл. Идеален, если тебе нужно настроить только PyTest.
*   **`pyproject.toml`**: Современный стандарт Python. Если у тебя проект на Poetry или Flit, все настройки (включая PyTest) живут здесь. Это «единое окно» для всего проекта.
*   **`tox.ini`**: Используется, если ты используешь `tox` для тестирования в разных окружениях (разные версии Python).
*   **`setup.cfg`**: Устаревающий формат, но всё ещё встречается.

### 2. Ключевые параметры (что внутри?)

Вот те настройки, которые ты будешь использовать в 90% случаев:

#### `addopts` (Самый важный параметр)
Это «автоматический ввод» флагов командной строки. Вместо того чтобы каждый раз писать `pytest -v --tb=short`, ты один раз пишешь это в конфиге.
*   **Пример:** `addopts = -v --tb=short --durations=5`
    *   `-v`: подробный вывод (verbose).
    *   `--tb=short`: короткий traceback (чтобы не заваливать экран текстом при падении).
    *   `--durations=5`: показать 5 самых медленных тестов в конце запуска.

#### `testpaths`
Указывает PyTest, где искать тесты. Это критично для больших проектов. Без этого PyTest будет сканировать вообще все папки (включая `venv`), что очень медленно.
*   **Пример:** `testpaths = tests integration_tests`

#### `python_files`
Если твои файлы называются не `test_*.py`, а, например, `check_*.py`, здесь ты это переопределяешь.
*   **Пример:** `python_files = check_*.py`

#### `markers`
Регистрация кастомных маркеров. **Важно:** Если ты используешь `@pytest.mark.slow`, но не зарегистрировал его в конфиге, PyTest выдаст предупреждение (Warning).
*   **Пример:** `markers = slow: marks tests as slow`

#### `filterwarnings`
Помогает убрать «мусор» из логов. Если какая-то библиотека спамит старыми DeprecationWarning, ты можешь их заглушить.
*   **Пример:** `filterwarnings = ignore::DeprecationWarning`

---

### 3. Иерархия (Кто главнее?)
Это нюанс, на котором часто валятся новички. Если настройка задана в двух местах, действует правило **«Последний пришел — первый забрал»**:

1.  **Командная строка (CLI)** — Самый высокий приоритет. Перебивает всё.
2.  **Файл конфигурации (`pytest.ini` / `pyطproject.toml`)**.
3.  **Настройки по умолчанию самого PyTest**.

*Пример: В конфиге прописано `-v`, но ты запустил `pytest -s`. В итоге запустится с `-s`, а `-v` будет проигнорирован.*

---

### 💡 Senior Pro-Tips (Нюансы)

1.  **Используй `pyproject.toml`**: Это стандарт индустрии. Весь современный Python-мир переезжает туда. Твой конфиг будет выглядеть так:
    ```toml
    [tool.pytest.ini_options]
    addopts = "-v"
    testpaths = ["tests"]
    ```
2.  **Не забивай `addopts` слишком сильно**: Не стоит включать туда флаги, которые нужны только иногда (например, `--lf` — запуск только упавших тестов). Оставь там только «базовую гигиену» (verbose, traceback style).
3.  **Следи за `testpaths`**: Если проект разрастается, добавление папки с логами или кэшем в исключения через `testpaths` может ускорить запуск тестов в разы.

### ❓ FAQ (Частые вопросы)

**В: Почему PyTest всё равно выдает Warning про неизвестный маркер, хотя я его добавил?**
**О:** Проверь синтаксис в секции `markers`. Он должен быть в формате `имя_маркера: описание`. Также убедись, что ты не допустил опечатку в названии файла конфигурации.

**В: Можно ли использовать переменные окружения (ENV) в конфиге?**
**О:** Напрямую в `.ini` или `.toml` — нет. Но ты можешь использовать библиотеку `python-dotenv` в своих фикстурах, чтобы подтягивать настройки из `.env` файла.

**В: Что делать, если я хочу запускать тесты с разными настройками (например, для API и для UI)?**
**О:** Не плоди разные файлы конфигурации. Используй `addopts` для базы, а специфичные флаги передавай через CLI при запуске конкретной команды в CI/CD или в терминале.

# 🚀 Тема: Запуск тестов (Running Tests)

Запуск тестов — это не просто нажатие кнопки "Run". Это управление жизненным циклом выполнения, фильтрация нужных проверок и оптимизация времени прохождения пайплайна.

### 1. Базовые команды
*   `pytest` — запуск всех найденных тестов в текущей директории.
*   `pytest tests/test_auth.py` — запуск конкретного файла.
*   `pytest tests/test_auth.py::test_login_success` — запуск одного конкретного теста (по имени функции).
*   `pytest tests/test_auth.py::test_class::test_method` — запуск метода внутри класса.

### 2. Фильтрация тестов (Выбираем только то, что нужно)
Когда тестов тысячи, запускать всё — непозволительная роскошь.
*   **По ключевым словам (`-k`):** Поиск по имени теста или содержимому.
    *   `pytest -k "login"` — запустит все тесты, в названии которых есть "login".
    *   `pytest -k "not slow"` — запустит всё, кроме тестов со словом "slow".
    *   *Senior Tip:* Это самый быстрый способ запустить похожие тесты, не меняя код.
*   **По маркерам (`-m`):** Использование логических операторов для меток.
    *   `pytest -m smoke` — только тесты с `@pytest.mark.smoke`.
    *   `pytest -m "smoke and not regression"` — запуск критических тестов, исключая регрессию.

### 3. Управление процессом (Control Flow)
*   **Остановка при первой ошибке (`-x` или `--exitfirst`):**
    *   Заставляет PyTest прекратить выполнение всей сессии сразу, как только один тест упал.
    *   *Зачем:* Идеально для локальной отладки, чтобы не ждать завершения 100 тестов, если первый же сломал логику.
*   **Запуск только упавших тестов (`--lf` или `--last-failed`):**
    *   Запускает только те тесты, которые провалились в предыдущем прогоне.
    *   *Зачем:* Экономит кучу времени при ретесте багов.
*   **Запуск упавших тестов в начале (`--ff` или `--failed-first`):**
    *   Сначала запускает "проблемные" тесты, а потом всё остальное.
    *   *Зачем:* Позволяет быстро увидеть результат регрессии по багам.

### 4. Режим вывода и отладка (Verbosity & Debugging)
*   **`-v` (Verbose):** Подробный вывод. Вместо точек (`.`) ты увидишь названия тестов и их статус. Обязательно для CI/CD логов.
*   **`-s` (No capture):** Отключает перехват `stdout`. Позволяет видеть обычные `print()` прямо в консоли во время выполнения.
    *   *Senior Tip:* **Никогда не оставляй `-s` в настройках CI/CD!** Это замусоривает логи и делает их нечитаемыми. Используй только локально для дебага.
*   **`--durations=N`:** Показывает `N` самых медленных тестов.
    *   *Зачем:* Твой главный инструмент для борьбы с "раздуванием" времени прогона. Если тест идет 2 минуты — это повод для рефакторинга.

# 🎯 Шпаргалка: Поиск элементов в Cypress

В Cypress поиск элементов — это не просто «найти и кликнуть». Это искусство нахождения стабильных селекторов, которые не сломаются при первом же редизайне сайта.

### 1. Основные инструменты (The Big Two)

*   **`cy.get(selector)`** — Твой главный инструмент. Использует стандартные **CSS-селекторы**.
    *   *Пример:* `cy.get('.btn-submit')`, `cy.get('#login-form input[name="email"]')`.
    *   *Нюанс:* Работает максимально быстро, но ищет по всему дереву DOM.
*   **`cy.contains(text/selector, text)`** — Ищет элемент, содержащий определенный текст.
    *   *Пример:* `cy.contains('Logout')` или `cy.contains('button', 'Submit')`.
    *   *Нюанс:* Очень полезно для тестирования пользовательского опыта (UX), но опасно, если текст на сайте часто меняется (например, при локализации).

### 2. Навигация по DOM (Traversing)
Когда тебе нужно найти элемент относительно другого (например, "кнопку внутри этой строки таблицы").

*   **Вниз по дереву:**
    *   `.find(selector)` — Ищет потомков внутри уже найденного элемента. (`cy.get('.list').find('.item')`).
    *   `.children()` — Выбирает только прямых потомков.
*   **Вверх по дереву:**
    *   `.parent()` — Находит непосредственного родителя.
    *   `.closest(selector)` — **Самый важный метод.** Ищет ближайшего предка, подходящего под селектор (поднимается вверх по дереву). Идеально для работы с карточками или строками таблиц.
*   **В стороны (соседи):**
    *   `.siblings()` — Находит всех «братьев/сестер» в том же контейнере.
    *   `.next()` / `.prev()` — Следующий или предыдущий элемент на том же уровне.

### 3. Ограничение области поиска (`cy.within`)
Если у тебя есть сложный компонент (например, модальное окно), не нужно писать длинные пути. Зайди внутрь него.

*   **`cy.within(callback)`** — Все команды внутри колбэка будут искать элементы **только внутри** указанного контейнера.
    ```javascript
    cy.get('.modal-container').within(() => {
      cy.get('.btn-close').click(); // Ищет кнопку только внутри модалки
    });
    ```

### 4. Золотые правила Senior-разработчика (Best Practices)

1.  **Забудь про XPath (по возможности):** В Cypress CSS-селекторы работают быстрее и читаются лучше. XPath — это крайний случай, когда без него никак.
2.  **Используй `data-cy` или `data-test` атрибуты:** Это «святой грааль». Если разработчики добавят `data-cy="submit-button"`, твой тест не сломается, даже если класс `.btn-blue` изменится на `.btn-red`.
    *   *Плохо:* `cy.get('div > ul > li:nth-child(3) > a')` (Хрупко!)
    *   *Хорошо:* `cy.get('[data-cy="nav-link"]')` (Стабильно!)
3.  **Избегай глубокой вложенности:** Селекторы вроде `div > div > span > b` — это мина замедленного действия.

### 5. Подводные камни и нюансы (Pitfalls)

*   **Detached from DOM:** Самая частая ошибка. Элемент был найден, но в момент клика React/Vue перерисовал компонент, и старый элемент «отвалился» от документа.
    *   *Решение:* Cypress сам умеет делать ретраи (retries), но если не помогает — используй `cy.get()` заново или проверь логику обновления стейта.
*   **Actionability:** Перед кликом Cypress проверяет, виден ли элемент, не перекрыт ли он другим и не заблокирован ли (`disabled`). Если тест падает на поиске — проверь, не крутится ли в этот момент лоадер поверх кнопки.

### ❓ FAQ (Частые вопросы)

**В: В чем разница между `cy.get('.item')` и `cy.contains('.item', 'Hello')`?**
**О:** `cy.get` ищет по CSS-селектору. `cy.contains` ищет элемент, который *подходит* под селектор `.item` И при этом содержит текст "Hello".

**В: Что делать, если элемент есть в DOM, но его не видно на экране?**
**О:** Cypress может найти его через `cy.get()`, но упадет на `.click()`. Если тебе нужно просто проверить наличие (без взаимодействия), используй `.should('exist')`. Если нужно проверить видимость — `.should('be.visible')`.

**В: Как найти элемент, если у него нет уникального ID или класса?**
**О:** Используй метод `.contains()` по тексту или начни поиск от стабильного родителя через `.within()` или `.closest()`. Но лучше всего — попроси разработчиков добавить `data-cy`.

# 🎯 Тема: Специальные селекторы в Cypress

Как Senior QA, скажу сразу: **селектор — это фундамент твоего теста.** Если ты выбираешь элементы через хрупкие CSS-классы или длинные XPath, твой тест «умрет» при первом же редизайне. Хороший селектор — это тот, который не меняется при изменении стилей.

### 1. Базовый инструмент: `cy.get()`
Это твой основной рабочий инструмент. Он использует стандартные **CSS-селекторы**.

*   **Что умеет:** Поиск по тегу, классу, ID, атрибуту.
*   **Пример:** 
    ```javascript
    cy.get('.btn-submit') // По классу
    cy/get('#login-button') // По ID
    cy.get('input[name="email"]') // По атрибуту
    ```
*   **Нюанс:** `cy.get()` всегда ищет элементы **от корня документа**, если ты не ограничил область поиска.

### 2. Текстовый селектор: `cy.contains()`
Самый «человечный» способ поиска. Он ищет элемент, внутри которого есть определенный текст.

*   **Как работает:** Можно передать строку или регулярное выражение.
*   **Пример:**
    ```javascript
    cy.contains('Logout') // Найдет любой элемент с текстом "Logout"
    cy.contains('button', 'Submit') // Ищет именно КНОПКУ, внутри которой есть текст "Submit"
    cy.contains(/^Welcome, .*$/) // Поиск через Regex (сложные условия)
    ```
*   **Нюанс:** Будь осторожен с `cy.contains()`. Если на странице десять кнопок с текстом «OK», он выберет **первую попавшуюся**. Всегда старайся уточнять контекст.

### 3. Поиск внутри контекста: `cy.within()` и `.find()`
Когда страница превращается в «спагетти» из тегов, тебе нужно сузить область поиска.

*   **`cy.within()`**: Переключает фокус на конкретный контейнер. Все команды внутри замыкания будут искать элементы *только внутри* этого контейнера.
    ```javascript
    cy.get('.user-card').within(() => {
      cy.get('.avatar').should('be.visible') // Ищем аватар только внутри карточки пользователя
      cy.contains('Delete').click()         // Ищем кнопку удаления именно в этой карточке
    })
    ```
*   **`.find()`**: Используется после `cy.get()`, чтобы найти потомка.
    ```javascript
    cy.get('.nav-menu').find('.item-active') // Найти активный пункт внутри меню
    ```

### 4. Навигация по дереву (Traversing)
Иногда нужно найти элемент, «оттолкнувшись» от другого.

*   **`.parent()`**: Поднимаемся на один уровень вверх.
*   **`.children()`**: Спускаемся к прямым потомкам.
*   **`.siblings()`**: Ищем «соседей» (элементы на том же уровне).
*   **`.closest()`**: **Самый важный метод.** Ищет ближайшего родителя, подходящего под селектор (вверх по дереву). Это гораздо стабильнее, чем `parent().parent()`.

---

### 👑 Золотое правило Senior-разработчика: `data-cy`
Никогда не используй классы (`.btn-primary`) или структуру DOM для тестов. Классы меняются верстальщиками каждый день. 

**Используй специальные атрибуты для тестирования:**
*   В коде приложения добавь: `<button data-cy="submit-button">Submit</button>`
*   В тесте пиши: `cy.get('[data-cy="submit-button"]')`

Это делает твой тест **неубиваемым** при любом редизайне.

# 🛠 Шпаргалка: Взаимодействие с элементами в Cypress

В Cypress взаимодействие — это не просто «нажать на кнопку». Это процесс, который включает в себя **Actionability Checks** (проверку возможности действия). Cypress перед кликом проверяет: виден ли элемент, не перекрыт ли он другим, не заблокирован ли он.

### 1. Базовые действия (Basic Actions)
Самые часто используемые команды для имитации действий пользователя.

*   `.click()` — Клик по элементу.
    *   `cy.get('button').click()`
*   `.type('text')` — Ввод текста в `input` или `textarea`.
    *   `cy.get('input').type('Hello World{enter}')` (можно передавать спецклавиши).
*   `.clear()` — Очистка поля ввода.
    *   `cy.get('input').clear()`
*   `.check()` / `.uncheck()` — Работа с чекбоксами и радиокнопками.
    *   `cy.get('[type="checkbox"]').check()`
*   `.select('value')` — Выбор значения в стандартном `<select>`.
    *   `cy.get('select').select('option_value')`

### 2. Работа со спецклавишами (Special Keys)
Внутри `.type()` можно имитировать нажатие системных клавиш:
*   `{enter}` — Enter
*   `{esc}` — Escape
*   `{backspace}` — Backspace
*   `{uparrow}`, `{downarrow}` — Стрелки вверх/вниз
*   `\n` — Символ новой строки

### 3. Продвинутые взаимодействия (Advanced)
Когда стандартного `.click()` недостаточно.

*   **Triggering Events:** Если элемент реагирует на `mouseover` или `mousedown`, используй `.trigger()`.
    *   `cy.get('.menu-item').trigger('mouseover')`
*   **Double Click / Right Click:**
    *   `cy.get('.element').dblclick()`
    *   `cy.get('.element').rightclick()`
*   **Drag and Drop:** В Cypress нет нативного крутого Drag & Drop «из коробки». Обычно используют плагин `@4tw/cypress-drag-drop` или имитируют через `.trigger('mousedown')`, `.trigger('mousemove')`, `.trigger('mouseup')`.

### 4. Нюансы и "Подводные камни" (Senior Level) 🧠

#### A. Actionability & `{force: true}`
Если элемент перекрыт прозрачным слоем или находится за пределами видимости, Cypress выдаст ошибку. 
*   **Решение:** Можно использовать `cy.get('button').click({ force: true })`.
*   **⚠️ Senior Advice:** Не злоупотребляй `{force: true}`. Если ты используешь его везде, ты перестаешь тестировать реальное поведение пользователя. Тест может проходить, а настоящий юзер не сможет нажать на кнопку. Используй только если элемент *действительно* скрыт технически (например, это декоративный элемент).

#### B. Проблема "Detached from DOM"
Это самая частая ошибка. Происходит, когда Cypress нашел элемент, но в момент клика React/Vue перерисовал компонент, и старый элемент «отвалился» от дерева DOM.
*   **Решение:** Убедись, что перед взаимодействием ты дождался стабильного состояния (например, через `should('be.visible')` или проверку отсутствия лоадера).

#### C. Выбор элементов (Selectors)
Никогда не используй длинные CSS-пути типа `div > ul > li:nth-child(3)`. Они сломаются при любом изменении верстки.
*   **Best Practice:** Используй атрибуты, специально созданные для тестов: `data-cy`, `data-test` или `data-testid`.
    *   `cy.get('[data-cy="submit-button"]').click()`

# ⌨️ Шпаргалка: События мыши и клавиатуры в Cypress

В Cypress есть два уровня взаимодействия: **Synthetic Events** (синтетические события — имитация через JS) и **Real Events** (настоящие события — как у реального пользователя).

## 1. Клавиатура (Keyboard)

Основной инструмент — команда `.type()`.

*   **Базовый ввод:** `cy.get('#input').type('Hello World')`
*   - **Специальные клавиши:** Используй фигурные скобки `{}`.
    *   `{enter}` — нажатие Enter.
    *   `{esc}` — клавиша Escape.
    *   `{backspace}` — удаление символа.
    *   `{downarrow}`, `{uparrow}`, `{leftarrow}`, `{rightarrow}` — стрелки навигации.
    *   `{space}` — пробел.
    *   `{ctrl}`, `{shift}`, `{alt}` — модификаторы (обычно используются в связке, например: `{ctrl}a` для выделения всего).
*   **Очистка поля:** `.clear()` — лучший способ очистить `input`, прежде чем писать заново.
*   **Имитация человека (Delay):** Чтобы тест не проходил слишком быстро (что иногда ломает логику фронтенка), используй задержку:
    `cy.get('#input').type('Slow typing', { delay: 100 })` — вводит символы с паузой 100мс.

## 2. Мышь (Mouse)

Cypress отлично справляется с кликами, но важно знать нюансы позиционирования.

*   **Основные действия:**
    *   `.click()` — левый клик.
    *   `.dblclick()` — двойной клик.
    *   `.rightclick()` — правый клик (вызов контекстного меню).
*   **Координаты и позиции:** Если нужно кликнуть не в центр элемента, а, например, в верхний угол:
    `cy.get('.menu-item').click('topleft')` или `cy.get('.box').click({ position: 'bottomRight' })`.
*   **Force Click (Опасная зона):** Если элемент перекрыт другим элементом (например, лоадером или прозрачным слоем), `.click()` упадет.
    `cy.get('#hidden-btn').click({ force: true })` — **Senior Warning:** Используй это только в крайнем случае. Если тебе нужно `force: true`, значит, твой тест не проверяет реальную доступность элемента для пользователя.

## 3. Низкоуровневые события (Trigger)

Когда стандартных `.click()` недостаточно (например, нужно вызвать `mouseover` или `mousemove`), используем `.trigger()`.

*   **События наведения:** `cy.get('.dropdown').trigger('mouseover')` — имитация наведения мыши для раскрытия меню.
*   **События нажатия/отпускания:** `mousedown`, `mouseup`.
*   **Специфические события:** `contextmenu` (для вызова меню), `mouseenter`, `mouseleave`.

## 4. Ультимативное решение: `cypress-real-events`

**В чем проблема?** Команды `.click()` и `.trigger()` в Cypress — это "синтетические" события. Они говорят браузеру: *"Эй, выполни JS-функцию клика"*. Но они не создают реального физического взаимодействия на уровне браузера. Это значит, что некоторые сложные CSS-эффекты (например, `:hover`) или проверки безопасности (`isTrusted: true`) могут не сработать.

**Решение:** Плагин [cypress-real-events](https://github.com/dmtrontd/cypress-real-events).
Он использует протокол Chrome DevTools, чтобы имитировать **настоящий** клик или наведение.

*   `cy.get('.btn').realClick()` — настоящий физический клик.
*   `cy.get('.item').realHover()` — настоящее наведение (работает с `:hover` в CSS).

### 💡 Нюансы и советы от Senior

1.  **Проблема "Забытого фокуса":** При использовании `.type()` элемент получает фокус. Если после этого скрипт на странице меняет состояние DOM, твой следующий шаг может упасть. Всегда проверяй, не перекрыл ли новый элемент твою цель.
2.  **События и Bubbling (Всплытие):** Помни, что клик по дочернему элементу (например, по тексту внутри кнопки) вызывает событие на родителе. Если у тебя сложная верстка, `.click()` может сработать не на том слое, который ты ожидал.
3.  **Не злоупотребляй `{force: true}`:** Это главный признак "плохого" автотеста. Хороший тест должен доказывать, что пользователь **может** нажать на кнопку.

**О:** Скорее всего, поле ввода перекрыто другим прозрачным элементом или скрипт на странице моментально очищает поле при потере фокуса. Попробуй использовать `{delay: 50}` или проверь наличие перекрывающих элементов через `cy.get(':visible')`.

**В: Чем `.trigger('mouseover')` отличается от `.realHover()`?**
**О:** `.trigger()` — это программная команда (JS-событие). Оно не активирует CSS-псевдоклассы `:hover`. `.realHover()` — это имитация движения физической мыши, которая активирует и JS, и CSS.

**В: Как нажать на кнопку, которая находится вне зоны видимости (нужно проскроллить)?**
**О:** Cypress по умолчанию делает `scrollIntoView` перед кликом. Но если это не срабатывает, используй `cy.get('selector').scrollIntoView().click()`.

# 📝 Шпаргалка по Cypress: Работа с формами

Работа с формами — это 70% задач в E2E тестах. Твоя цель не просто «вписать текст», а имитировать поведение реального пользователя и проверить логику валидации и отправки данных.

### 1. Основные элементы управления

#### **Текстовые поля (`input[type="text"]`, `textarea`)**
*   `.type('текст')` — базовый ввод.
*   `.clear()` — очистка поля. 
    *   *Senior Tip:* Всегда используй `.clear().type('новое значение')`, если не уверен, что поле пустое. Cypress может дописывать текст к уже существующему, что приведет к падению теста.
*   `{enter}` — нажатие клавиши Enter внутри `.type()`. Пример: `cy.get('#search').type('Cypress{enter}')`.
*   `{backspace}`, `{selectall}` — специальные команды для имитации клавиатуры.

#### **Чекбоксы и Радиокнопки (`checkbox`, `radio`)**
*   `.check()` — поставить галочку/выбрать вариант. Работает даже если элементов несколько (через селектор).
*   `.uncheck()` — снять галочку.
*   `.click()` — можно использовать вместо `.check()`, но `.check()` безопаснее, так как он не «переключает» состояние (toggle), а именно устанавливает его в `true`.

#### **Выпадающие списки (`select`)**
*   `.select('value')` — выбор по атрибуту `value`.
*   `.select('Текст опции')` — выбор по видимому тексту.
*   `.select('option[index=2]')` — выбор по индексу (редко, но полезно).

#### **Загрузка файлов (`input[type="file"]`)**
*   В современных версиях Cypress используй `.selectFile()`.
*   `cy.get('input[type="file"]').selectFile('cypress/fixtures/sample.json')` — загрузка файла из папки fixtures.
*   Можно передавать объект: `{ contents: fileContent, fileName: 'test.txt' }`.

### 2. Проверки (Assertions) — Что мы проверяем?

После заполнения формы недостаточно просто нажать «Submit». Нужно проверить состояние элементов:

*   **Значение поля:** `cy.get('#email').should('have.value', 'test@example.com')`.
*   **Состояние чекбокса:** `cy.get('#agree').should('be.checked')` или `should('not.be.checked')`.
*   **Видимость ошибок:** `cy.get('.error-message').should('be.visible').and('contain', 'Invalid email')`.
*   **Атрибуты (например, disabled):** `cy.get('#submit-btn').should('be.disabled')` (проверка, что кнопка не активна, пока форма не заполнена).

### 3. Продвинутые нюансы (Senior Level)

#### **Обработка асинхронности и API (`cy.intercept`)**
Самая частая ошибка: нажать кнопку «Отправить» и сразу проверить результат, когда запрос еще летит на сервер.
*   **Правильный путь:** Используй `cy.intercept()` для перехвата сетевого запроса.
    ```javascript
    // 1. Начинаем слушать запрос
    cy.intercept('POST', '/api/login').as('loginRequest');

    // 2. Действуем в форме
    cy.get('#login-btn').click();

    // 3. Ждем, пока сервер ответит (ждем завершения сетевого цикла)
    cy.wait('@loginRequest').its('response.statusCode').should('eq', 200);
    ```

#### **Проблема «Перекрытых элементов»**
Иногда всплывающее уведомление или лоадер перекрывают кнопку. Если `.click()` падает с ошибкой `element is being covered by another element`, используй `{ force: true }`. 
*   *Но будь осторожен:* Это «костыль». Если элемент перекрыт, значит, пользователь тоже не сможет на него нажать. Сначала попробуй дождаться исчезновения лоадера.

#### **Работа с динамическими формами**
Если поля появляются только после выбора определенного чекбокса, всегда используй явное ожидание появления элемента или проверку его видимости (`should('be.visible')`), прежде чем взаимодействовать.

# 🧠 Шпаргалка: Chai Library в Cypress

### 📌 Что это такое?
**Chai** — это библиотека утверждений (assertions). Если Cypress — это твои «руки», которые кликают и вводят текст, то Chai — это твой «глаз», который проверяет, всё ли идет по плану.

**Важный нюанс:** Тебе **не нужно** устанавливать Chai отдельно. Он уже встроен в Cypress вместе с библиотекой `expect`, `should` и `assert`.

---

### 🛠 Три стиля написания тестов
В Chai есть три синтаксиса. В Cypress чаще всего используют первые два (BDD-стиль).

1.  **Expect (BDD)** — Самый популярный и читаемый. Мы создаем объект ожидания.
    *   `expect(actual).to.equal(expected);`
2.  **Should (BDD)** — Расширяет прототип объектов. Выглядит очень естественно (как английское предложение).
    *   `actual.should.equal(expected);`
3.  **Assert (TDD)** — Классический стиль (как в Java/C#). Более строгий, но менее «человечный».
    *   `assert.equal(actual, expected);`

---

### 🚀 Основные цепочки проверок (Chains)
Цепочки слов вроде `.to.be`, `.to.have`, `.with` не делают никакой логики — они нужны только для **читаемости**. Смысл несут только методы после них.

#### 1. Работа со строками (Strings)
*   `.to.equal('text')` — точное совпадание.
*   `.to.include('sub')` — содержит подстроку.
*   `.to.have.lengthOf(5)` — длина строки.
*   `.to.match(/regex/)` — проверка через регулярное выражение.

#### 2. Работа с числами (Numbers)
*   `.to.eql(10)` — равенство.
*   `.to.be.gt(5)` — больше чем (Greater Than).
*   `.to.be.lt(15)` — меньше чем (Less Than).
*   `.to.be.closeTo(10, 0.1)` — проверка с погрешностью (важно для float!).

#### 3. Работа с массивами и объектами (Arrays & Objects)
*   `.to.deep.equal([1, 2])` — **Критически важно!** Сравнивает содержимое, а не ссылки в памяти.
*   `.to.have.property('id', 1)` — проверка наличия ключа и его значения.
*   `.to.include(item)` — наличие элемента в массиве.
*   `.to.have.lengthOf(3)` — количество элементов.

#### 4. Работа с DOM-элементами (Специфика Cypress)
Здесь Chai работает в связке с командами Cypress:
*   `cy.get('.btn').should('be.visible')` — элемент виден.
*   `cy.get('input').should('have.value', 'Hello')` — значение инпута.
*   `cy.get('.error').should('have.class', 'active')` — проверка CSS-класса.
*   `cy.get('a').should('have.attr', 'href', '/home')` — проверка атрибута.

---

### ⚠️ Senior Nuances (О чем забывают джуны)

1.  **The Retryability Trap (Ловушка повторных попыток):**
    Это самое важное! Команды Cypress (`cy.get`, `cy.contains`) умеют ждать появления элемента. Если ты используешь `expect` внутри `.then()`, **авто-ретраи (retry) перестают работать**.
    *   ❌ **Плохо:** `cy.get('.loader').then(el => expect(el).to.not.exist)` — если элемент еще в процессе исчезновения, тест упадет мгновенно.
    *   ✅ **Хорошо:** `cy.get('.loader').should('not.exist')` — Cypress будет ждать, пока элемент не исчезнет.

2.  **`equal` vs `deep.equal`:**
    Если ты сравниваешь два объекта `{a: 1}` и `{a: 1}`, обычный `.equal` вернет `false`, потому что это разные объекты в памяти. Всегда используй `.deep.equal` для объектов и массивов.

3.  **`should` vs `expect` с `null/undefined`:**
    Стиль `.should` может упасть с ошибкой "cannot read property of undefined", если объект, который ты проверяешь, равен `null`. В таких случаях безопаснее использовать `expect(obj).to.be.null`.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `.equal` и `.deep.equal`?**
**О:** `.equal` проверяет идентичность (ссылку в памяти или примитивное значение). `.deep.equal` рекурсивно обходит структуру объекта/массива и сравнивает их содержимое.

**В: Почему я не должен использовать `expect` для проверки видимости элемента?**
**О:** Потому что `expect` — это мгновенная проверка. Если элемент появится через 100мс, `expect` уже выдаст ошибку. Команда `.should()` в Cypress интегрирована с механизмом ожидания (retryability) и будет перепроверять условие, пока не выйдет таймаут.

**В: Как проверить, что массив содержит определенный объект?**
**О:** Используй `expect(array).to.deep.include(expectedObject)` или, если это Cypress-команда, `cy.wrap(array).should('deep.include', expectedObject)`.

**В: Можно ли использовать Chai без Cypress?**
**О:** Да, Chai — это самостоятельная библиотека JavaScript. Она может использоваться в Node.js проектах, Jest или любом другом тестовом фреймворке. В Cypress она просто поставляется "из коробки".

# 🧠 Шпаргалка: Типы проверок (Assertions) в PyTest

**Суть:** Проверка (assertion) — это точка принятия решения. Если условие истинно (`True`) — тест идет дальше. Если ложно (`False`) — тест падает, и мы получаем отчет об ошибке. В PyTest стандартный оператор `assert` магически расширен: при провале он выводит значения переменных, что критически важно для дебага.

---

### 1. Базовые проверки (Scalar Assertions)
Самый простой уровень — проверка конкретных значений.

*   **Равенство (`==`, `!=`):** Проверка того, что значение совпадает с ожидаемым.
    ```python
    assert result == 10
    assert status != "error"
    ```
*   **Идентичность (`is`, `is not`):** **Важный нюанс!** Проверяет не равенство значений, а то, что это *один и тот же объект в памяти*. Используй только для `None` или синглтонов.
    ```python
    assert user is None  # Правильно
    assert x is y       # Опасно (может быть True по значению, но False по объекту)
    ```
*   **Принадлежность (`in`, `not in`):** Проверка наличия элемента в списке, строке или словаре.
    ```python
    assert "admin" in user_roles
    assert 404 not in response_codes
    ```

### 2. Проверка исключений (Exception Assertions)
Тест считается успешным, если код **выбросил** ожидаемую ошибку. Если ошибка не возникла — тест упал.

*   **`pytest.raises`:** Основной инструмент.
    ```python
    import pytest

    def test_division_by_zero():
        with pytest.raises(ZeroDivisionError):
s           1 / 0
    ```
*   **Проверка сообщения об ошибке (`match`):** Senior-level подход. Недостаточно знать, *какая* ошибка упала, нужно убедиться, что *текст* ошибки верный (чтобы не поймать другую ошибку того же типа).
    ```python
    with pytest.raises(ValueError, match="Invalid age"):
        process_user_age(-5) # Упадет, если в тексте есть "Invalid age"
    ```

### 3. Проверка коллекций (Collections Assertions)
Когда мы проверяем списки, словари или множества.

*   **Длина коллекции:** Всегда проверяй `len()`, прежде чем лезть внутрь элементов.
    ```python
    assert len(users) == 5
    ```
*   **Содержимое (Deep Comparison):** PyTest умеет сравнивать вложенные структуры (словари в списках и т.д.) «из коробки».
    ```python
    expected = [{"id": 1, "name": "Alice"}, {"id": 2, "name": "Bob"}]
    assert actual_users == expected
    ```

### 4. Проверка чисел с плавающей точкой (Floating Point)
**Золотое правило:** Никогда не используй `==` для `float`. Из-за особенностей двоичной системы представления чисел, `0.1 + 0.2` не будет равно `0.3`.

*   **`pytest.approx`:** Магический инструмент для сравнения чисел с заданной погрешностью.
    ```python
    import pytest

    def test_float_precision():
        assert 0.1 + 0.2 == pytest.approx(0.3)
        # Можно задать допуск (rel или abs)
        assert value == pytest.approx(1.0, rel=1e-5) 
    ```

### 5. Проверка типов и атрибутов (Type & Attribute Checks)
Иногда нужно проверить не значение, а структуру объекта.

*   **`isinstance`:** Проверка типа данных.
    ```python
    assert isinstance(response, dict)
    ```
*   **Проверка наличия атрибута:** 
    ```python
    assert hasattr(user_object, 'email')
    ```

---

### 💡 Советы от Senior (Best Practices)

1.  **Не делай "Assertion Roulette":** Не пиши 20 проверок в одном тесте. Если первая упадет, ты не узнаешь, что происходит с остальными. Один тест — одна логическая проверка (или группа очень связанных проверок).
2.  **Информативность:** Если используешь сложные проверки, добавляй кастомное сообщение через запятую: `assert user.age > 18, f"User age is {user.age}, expected > 18"`. Это сэкономит тебе кучу времени при чтении логов в CI/CD.
3.  **Избегай `try-except` внутри теста:** Если ты пишешь `try: ... except: assert False`, ты делаешь тест грязным. Используй `pytest.raises`.

---

### ❓ FAQ (Частые вопросы)

**В: В чем разница между `assert a == b` и `assert a is b`?**
**О:** `==` проверяет **значение** (содержимое). `is` проверяет **адрес в памяти** (являются ли это буквально одним и тем же объектом). Для чисел и строк это часто работает одинаково, но для списков и словарей — это критическая разница.

**В: Почему мой тест падает на `0.1 + 0.2 == 0.3`, хотя математически это верно?**
**О:** Это проблема точности Float в компьютере. Всегда используй `pytest.approx()` для любых операций с дробными числами.

**В: Как проверить, что в списке есть определенные элементы, но не важен их порядок?**
**О:** Преобразуй списки в множества (set) перед сравнением: `assert set(actual_list) == set(expected_list)`.

**В: Что делать, если я хочу проверить, что ошибка содержит конкретное слово, но не знаю точную фразу?**
**О:** Используй параметр `match` с регулярным выражением в `pytest.raises(Error, match="слово")`.

# 🧠 Шпаргалка: Сложные проверки (Complex Assertions)

В простых тестах мы проверяем `2 + 2 == 4`. В реальных проектах мы проверяем структуру JSON, содержимое логов, наличие ключей в словарях и корректность вычислений с плавающей точкой.

### 1. Проверка исключений (Exception Testing)
Когда тест должен упасть с конкретной ошибкой — это тоже успешный сценарий. Мы используем контекстный менеджер `pytest.raises`.

*   **Базовая проверка:** Проверяем, что тип ошибки именно тот, который мы ждем.
*   **Проверка сообщения (Regex):** Самый важный нюанс. Мало знать, что упал `ValueError`, нужно убедиться, что причина именно та. Используй параметр `match`.

```python
import pytest

def divide(a, b):
    if b == 0:
        raise ValueError("Division by zero is not allowed!")
    return a / b

def test_divide_by_zero():
    # Плохо: просто проверяем тип ошибки
    with pytest.raises(ValueError):
  	    divide(10, 0)

    # Хорошо (Senior level): проверяем и тип, и текст ошибки через Regex
    with pytest.raises(ValueError, match=r"not allowed"):
        divide(10, 0)
```

### 2. Проверка структур данных (Deep Assertions)
Когда ты работаешь с API, ты получаешь сложные JSON (словари со списками и вложенными словарями).

*   **Сравнение подмножеств:** Часто нам не важен весь ответ API, а только конкретные поля.
*   **Порядок элементов:** В списках порядок может иметь значение, а может и нет. Для проверки состава (без учета порядка) используй `set()`.

```python
def test_api_response():
    actual_response = {
        "id": 1,
        "status": "active",
        "tags": ["premium", "new", "verified"]
    }
    
    # Проверка конкретного ключа
    assert actual_response["status"] == "active"
    
    # Проверка наличия элемента в списке (независимо от позиции)
    assert "premium" in actual_response["tags"]
    
    # Если важно, что в списке НЕТ лишнего
    expected_tags = {"premium", "new", "verified"}
    assert set(actual_response["tags"]) == expected_tags
```

### 3. Сравнение чисел с плавающей точкой (Floating Point Precision)
**Золотое правило:** Никогда не сравнивай `float` через прямое `==`. Из-за особенностей двоичной системы, `0.1 + 0.2` не будет равно `0.3`.

Используй `pytest.approx`.

```python
def test_math_precision():
    result = 0.1 + 0.2
    # Ошибка: assert result == 0.3  <-- это упадет!
    
    # Правильно: PyTest сам подберет допустимую погрешность
    assert result == pytest.approx(0.3)
    
    # Можно задать свою точность (rel — относительная, abs — абсолютная)
    assert result == pytest.approx(0.3, rel=1e-5)
```

### 4. Кастомные сообщения об ошибках (Custom Failure Messages)
В больших проектах логи в CI/CD — твой единственный друг. Если тест упал с `AssertionError: False`, ты ничего не поймешь. Всегда добавляй контекст.

```python
def test_user_permissions(user):
    is_admin = user.has_role("admin")
    # Senior tip: всегда пиши, ЧТО именно мы проверяли и какие были данные
    assert is_admin, f"User {user.id} should have admin role, but got roles: {user.roles}"
```

### 💡 Нюансы от Senior-а (Pro Tips)

1.  **Принцип "Fail Fast":** Если проверка сложная, сначала проверяй самые простые и важные условия (например, `assert response.status_code == 200`). Нет смысла проверять структуру JSON, если сам запрос вернул 500 ошибку.
2.  **Не переусложняй Assert:** Если твой `assert` занимает 10 строк — вынеси логику сравнения в отдельную функцию или фикстуру. Тест должен читаться как рассказ.
3.  **Избегай "Assertion Roulette":** Это когда в одном тесте 20 проверок. Если упадет первая, ты не узнаешь, работают ли остальные. Используй `@pytest.mark.parametrize` для разделения логики.

# 🪝 Тема: Pytest Hooks (Хуки)

### Что такое Хуки?
Если коротко: **Хуки — это «крючки»**, за которые ты можешь зацепиться, чтобы изменить поведение Pytest в процессе его работы. 

Представь, что Pytest — это конвейер на заводе. Он идет по строго заданному маршруту: *запуск $\to$ чтение конфига $\to$ поиск тестов $\to$ выполнение каждого теста $\to$ завершение*. Хуки позволяют тебе «вклиниться» в любой этап этого процесса и сказать: «Подожди, на этом этапе я хочу добавить вот этот флаг», «А здесь я хочу пропустить все тесты с пометкой @slow» или «А тут я хочу прикрепить скриншот к отчету».

### Где они живут?
Хуки нельзя просто написать в файле `test_sample.py`. Чтобы они работали глобально, их нужно размещать в:
1. **`conftest.py`** — самый частый вариант для локальных нужд проекта.
2. **Собственных плагинах** — если ты пишешь полноценный инструмент для всей компании.

---

### Основные этапы и ключевые хуки

Я разделил их по жизненному циклу процесса тестирования:

#### 1. Этап конфигурации (Configuration)
Здесь мы настраиваем «входные параметры» перед тем, как Pytest вообще начал искать тесты.
*   **`pytest_addoption(parser)`**: Самый полезный хук для автоматизатора. Позволяет добавить свои кастомные флаги в командную строку (например, `--env=prod` или `--browser=chrome`).
*   **`pytest_configure(config)`**: Вызывается после того, как все настройки прочитаны. Здесь можно программно менять конфигурацию или проверять, правильно ли переданы аргументы.

#### 2. Этап сбора тестов (Collection)
Pytest сканирует файлы и находит функции, начинающиеся с `test_`.
*   **`pytest_collection_modifyitems(items)`**: «Магия» фильтрации. Ты получаешь список всех найденных тестов (`items`) и можешь их изменять: удалять (скипать), менять порядок или вешать на них дополнительные маркеры прямо «на лету».

#### 3. Этап выполнения теста (Execution)
Это то, что происходит внутри каждого конкретного теста.
*   **`pytest_runtest_setup(item)`**: Вызывается перед началом выполнения теста. Идеально для подготовки специфического окружения.
*   **`pytest_runtest_teardown(item)`**: Вызывается после завершения теста (независимо от того, прошел он или упал).
*   **`pytest_runtest_makereport(item, call)`**: **Критически важный хук для отчетности.** Он позволяет перехватить результат выполнения (`passed`, `failed`, `error`) и, например, сделать скриншот именно в тот момент, когда тест упал.

#### лы4. Этап завершения сессии (Session)
*   **`pytest_sessionstart(session)`**: Вызывается один раз при запуске всего процесса. Удобно для инициализации глобальных ресурсов (например, создание подключения к БД).
*   **`pytest_sessionfinish(session)`**: Вызывается в самом конце. Здесь можно закрыть соединения, отправить уведомление в Slack или сгенерировать итоговый кастомный отчет.

---

### 💡 Нюансы от Senior-а (Pro Tips)

1.  **Производительность:** Никогда не пиши тяжелую логику (запросы к БД, сложные вычисления) внутри хуков коллекции (`pytest_collection_modifyitems`). Этот хук вызывается каждый раз при поиске тестов. Если он будет тормозить, весь запуск Pytest станет мучительным.
2.  **Область видимости:** Помни, что `conftest.py` работает как иерархия. Хук в корневом `conftest.py` видит все тесты проекта, а хук в подпапке — только тесты этой папки.
3.  **Использование `makereport`:** Если ты хочешь делать скриншоты при падении, тебе нужно использовать именно этот хук и проверять состояние `report.failed`. Попытка сделать это в `teardown` часто приводит к тому, что ты не можешь получить доступ к текущему состоятию браузера.

# 🧠 Шпаргалка: Управление сессиями (Session Management)

**Суть темы:** Управление сессией — это умение настроить ресурсы так, чтобы они создавались **один раз** в самом начале запуска всех тестов и уничтожались только в самом конце. Это экономит кучу времени, если тебе нужно поднять базу данных, запустить Docker-контейнер или авторизоваться в API.

### 1. Главный инструмент: `scope='session'`
В Pytest всё управляется через область видимости (scope) фикстур. Для сессий мы используем именно этот параметр.

```python
import pytest

@pytest.fixture(scope="session")
def db_connection():
    # SETUP: Выполняется ОДИН раз перед всеми тестами
    print("\n[Setup] Подключаемся к базе данных...")
/connection = "Connected to DB" 
    yield /connection  # Передаем объект в тесты
    
    # TEARDOWN: Выполняется ОДИН раз после всех тестов
    print("\n[Teardown] Закрываем соединение с БД...")
```

### 2. Где хранить? (`conftest.py`)
Фикстуры сессии **обязаны** жить в `conftest.py`. Если ты напишешь их внутри файла с тестом, они не будут доступны другим модулям, и смысл "глобальной сессии" потеряется.

### 3. Золотое правило: "Session = Read-Only"
Это самый важный нюанс для Senior-разработчика.
* **Плохо:** Использовать сессионную фикстуру для изменения данных (например, удалять записи из БД). Если один тест удалит данные, все последующие тесты в этой сессии упадут.
* **Хорошо:** Сессионная фикстура готовит "чистую" среду или предоставляет доступ к неизменяемым объектам (токен, конфиг, соединение).
* **Как делать правильно:** Если нужно менять данные — делай это в фикстуре с `scope="function"`, но используй сессионную фикстуру как фундамент.

### 4. Подводный камень: Параллелизация (`pytest-xdist`)
Если ты запускаешь тесты параллельно (через `-n auto`), помни: **сессия создается отдельно для каждого воркера (процесса)**.
* Если у тебя 4 воркера, то `scope="session"` выполнится **4 раза** (по разу на каждый процесс).
* **Решение:** Если нужно, чтобы база поднялась строго один раз на весь проект, используй специальные механизмы блокировки файлов (file locking) внутри фикстуры.

### 5. Иерархия зависимостей
Сессионная фикстура может зависеть от более мелких.
* `session` (подняли Docker) $\rightarrow$ `module` (создали таблицу) $\rightarrow$ `function` (заполнили данными).

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что будет, если в сессионной фикстуре произойдет ошибка на этапе Setup?**
**О:** Все тесты, которые зависят от этой фикстуры, будут пропущены или помечены как `Error`. Тесты не запустятся, так как фундамент (сессия) не был построен.

**В: Можно ли в сессионной фикстуре использовать `yield`?**
**О:** Да, и это **обязательно**, если тебе нужно очистить ресурсы (закрыть браузер, остановить контейнер). Без `yield` ты не сможешь прописать логику Teardown.

**В: Чем `scope="session"` отличается от `scope="package"`?**
**О:** `session` живет всё время, пока работает команда `pytest`. `package` живет только пока тестируются тесты внутри одной папки (пакета). Сессия — это "максимальный" уровень жизни.

**В: Как понять, что я злоупотребляю сессиями?**
**О:** Если твои тесты стали "зависимыми" друг от друга. Если тест А упал, и из-за этого тест Б (который не должен был зависеть от А) тоже упал — значит, ты изменил состояние сессии, и это плохой дизайн.

# 🛠 Custom Commands (Пользовательские команды)

**Custom Commands** — это способ расширить встроенный объект `cy`, создав свои собственные методы. Это "макросы" или сокращения для повторяющихся действий. Вместо того чтобы в каждом тесте писать 10 строк кода для логина, ты пишешь одну команду: `cy.login()`.

### 📍 Где их объявлять?
Все кастомные команды должны жить в файле:  
`cypress/support/commands.js` (или `.ts`, если используешь TypeScript).

### 🏗 Синтаксис
Используется метод `Cypress.Commands.add(name, callback)`.

```javascript
// Базовый шаблон
Cypress.Commands.add('commandName', (arg1, arg2) => {
  // Логика команды
  cy.get('.selector').type(arg1);
});
```

### 🚀 Примеры использования

#### 1. Простой пример: Авторизация
Вместо повторения ввода логина и пароля:
```javascript
Cypress.Commands.add('login', (email, password)- => {
  cy.get('[data-cy="email-input"]').type(email);
  cy.get('[data-cy="password-input"]').type(password);
  cy.get('[data-cy="submit-btn"]').click();
  // Важно: можно добавить проверку, что логин прошел успешно
  cy.url().should('include', '/dashboard');
});

// В тесте используем так:
cy.login('user@example.com', 'password123');
```

#### 2. Более сложный пример: Работа с API + UI
Команда может комбинировать разные уровни взаимодействия.
```javascript
Cypress.Commands.add('createProduct', (productName) => {
  cy.request('POST', '/api/products', { name: productName }).then((response) => {
    // После создания через API, мы можем сразу перейти к проверке в UI
    cy.visit(`/products/${response.body.id}`);
    cy.get('.product-title').should('contain', productName);
  });
});
```

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Не создавай "Команды-Боги" (God Commands):** 
    Самая большая ошибка — делать команду, которая делает *всё сразу* (например, `cy.loginAndNavigateToSettingsAndOpenProfile()`). Если один шаг упадет, ты не сможешь протестировать остальные части. Команда должна быть атомарной (выполнять одну логическую задачу).

2.  **Проблема асинхронности и `.then()`:** 
    Помни, что Cypress — это очередь команд. Если тебе нужно использовать результат выполнения команды внутри другой команды, всегда используй `.then()`.
    *Плохо:* `const val = cy.get('.el').text();` (это не сработает).
    *Хорошо:* `cy.get('.el').then(($el) => { const val = $el.text(); ... });`

3.  **Избегай перегрузки `commands.js`:** 
    Если команд становится больше 10-15, файл `commands.js` превращается в свалку. Разделяй их! Создавай отдельные файлы (например, `auth-commands.js`, `ui-commands.js`) и импортируй их в `support/e2e.js`.

4.  **TypeScript (Важно!):** 
    Если ты используешь TS, Cypress "не узнает" о твоей новой команде и будет ругаться на `cy.login is not a function`. Тебе нужно объявить типы в файле `cypress/support/index.d.ts`:
    ```typescript
    declare namespace Cypress {
      interface Chainable {
        login(email: string, password: string): Chainable<void>;
      }
    }
    ```

5.  **Custom Commands vs Page Objects:** 
    *   **Custom Commands** — для низкоуровневых действий (логин, очистка БД, создание данных через API).
    *   **Page Objects / App Actions** — для высокоуровневой логики страниц и бизнес-сценариев. Не превращай `cy` в библиотеку со всеми селекторами твоего приложения.

# 🛠 Шпаргалка: Pytest Fixtures (Фикстуры)

**Фикстура** — это подготовка окружения перед тестом и уборка после него. Если тест — это приготовление блюда, то фикстура — это нарезка ингредиентов (Setup) и мытье посуды (Teardown).

### 1. Базовый синтаксис: `return` vs `yield`
Это самый важный момент. 
*   **`return`**: Просто дает данные тесту. Тест получает объект и всё, фикстура завершена.
*   **`yield`**: Разделяет процесс на две части. Всё, что **до** `yield`, — это Setup. Всё, что **после** — это Teardown (очистка).

```python
@pytest.fixture
def db_connection():
    # SETUP: Создаем подключение
    conn = create_db_connection()
    yield conn  # Тест получает 'conn' и работает с ним
    # TEARDOWN: Закрываем соединение после теста
    conn.close()
```

### 2. Области видимости (Scopes)
Scope определяет, как часто фикстура будет запускаться. Выбор неправильного scope — главная причина медленных тестов или "грязных" данных.

| Scope | Когда запускается | Для чего использовать |
| :--- | :--- | :--- |
| **`function`** (дефолт) | Перед каждым тестом | Создание записей в БД, временные файлы. |
| **`class`** | Перед началом класса тестов | Настройка общего состояния для группы методов. |
| **`module`** | Один раз на весь `.py` файл | Запуск локального сервера, тяжелые конфигурации. |
| **`session`** | Один раз за весь прогон тестов | Подключение к БД, инициализация драйвера браузера. |

> **Senior Tip:** Никогда не используй `session` scope для данных, которые меняются в тестах (например, удаление пользователя). Если один тест удалит юзера, остальные упадут.

### 3. Зависимости фикстур (Fixture Injection)
Фикстуры могут зависеть друг от друга. Это позволяет строить цепочки подготовки.

```python
@pytest.fixture
def user_id():
    return 42

@pytest.fixture
def user_profile(user_id): # Передаем зависимость
    return fetch_profile(user_id)
```

### 4. Автоматические фикстуры (`autouse`)
Иногда нужно, чтобы фикстура работала "невидимо" (например, для очистки логов или проверки авторизации), не прописывая её в каждый тест.

```python
@pytest.fixture(autouse=True)
def clean_logs():
    yield
    clear_all_logs() # Выполнится после каждого теста автоматически
```
*Осторожно: злоупотребление `autouse` делает тесты "магическими" и сложными в отладке.*

### 5. Файл `conftest.py` — Глобальный склад
Чтобы не копипастить фикстуры из файла в файл, используй `conftest.py`. 
*   Все фикстуры в этом файле видны всем тестам в этой и подпапках.
*   Это позволяет разделять логику: в корне проекта — общие фикстуры (БД), в папке `/api` — специфичные для API.

### 6. Fixture Factories (Продвинутый уровень)
Иногда тесту нужно передать параметр в фикстуру. Но фикстуры не принимают аргументы напрямую из теста. Решение — **возвращать функцию**.

```python
@pytest.fixture
def create_user():
    def _make_user(name): # Внутренняя функция-завод
        return User(name=name)
    return _make_user

def test_user_name(create_user):
    user = create_user("Alice") # Передаем параметр прямо в тесте
    assert user.name == "Alice"
```

### ⚠️ Нюансы и Антипаттерны (Senior Insights)

1.  **Side Effects (Побочные эффекты):** Если фикстура с `session` scope меняет состояние системы, она может "отравить" другие тесты. Старайся делать фикстуры максимально изолированными.
2.  **God Fixture:** Не делай одну гигантскую фикстуру, которая создает БД, пользователя, сессию и загружает конфиг. Разбей её на мелкие части. Маленькие фикстуры легче переиспользовать.
3.  **Overuse of `autouse`:** Если ты не можешь найти, откуда взялся объект в тесте — проверь `autouse`. Это плохой тон для командной разработки.

### ❓ FAQ (Частые вопросы)

**В: Чем отличается фикстура от обычного Setup/Teardown из unittest?**
**О:** Фикстуры Pytest гораздо гибче. Они поддерживают внедрение зависимостей (dependency injection), имеют разные scopes и позволяют строить сложные графы зависимостей, в то время как `setUp` в `unittest` работает только на уровне класса/метода.

**В: Что произойдет, если фикстура упадет на этапе Setup?**
**О:** Тест, использующий эту фикстуру, будет помечен как `Error` (не `Fail`). Код после `yield` выполнен не будет.

**В: Как переопределить фикстуру из `conftest.py` для конкретного файла?**
**О:** Просто объяви фикстуру с тем же именем в самом тестовом файле. Pytest найдет более "близкую" по области видимости фикстуру и использует её.

**В: Можно ли использовать фикстуры внутри других фикстур?**
**О:** Да, это стандартная практика для построения цепочек подготовки данных.

# 🚀 Cypress Cheat Sheet: Intercepting (`cy.intercept`)

**Intercepting** — это «режим Бога» в Cypress. Это инструмент, который позволяет тебе перехватывать сетевые запросы (XHR/Fetch), которые делает твое приложение, и управлять ими. Ты можешь либо просто подсматривать за ними (**Spying**), либо подменять их ответы на свои собственные (**Stubbing/Mocking**).

### 1. Три режима работы
1.  **Spying (Наблюдение):** Ты не меняешь запрос, а просто ждешь его появления и проверяешь, что в нем пришло (статус, тело, заголовки).
2.  **Stubbing (Подмена):** Ты перехватываешь запрос и возвращаешь заранее подготовленный «фейковый» ответ (например, чтобы протестировать пустой список или ошибку 500).
3.  **Modifying (Изменение):** Ты позволяешь запросу уйти на сервер, но «на лету» меняешь его ответ перед тем, как он попадет в браузер.

---

### 2. Базовый синтаксис и Matchers
Чтобы перехватить запрос, нужно указать, **что именно** мы ищем.

*   **По URL (простой):** `cy.intercept('/users')` — поймает любой запрос, содержащий `/users`.
*   
*   **По методу и URL:** `cy.intercept('GET', '/api/v1/users')` — более точный поиск.
*   
*   **С использованием Wildcards (масок):** `cy.intercept('POST', '/api/v1/orders/*')` — поймает все POST запросы к заказам с любым ID.
*   
*   **Объектный подход (Самый мощный):**
    ```javascript
    cy.intercept({
      method: 'GET',
      url: '/api/v1/users*',
      query: { id: '123' } // Поймает только если в URL есть ?id=123
    })
    ```

---

### 3. Работа с Alias (Псевдонимы) — Ключ к стабильности
Никогда не надейся, что запрос «успеет» выполниться сам по себе. Всегда используй `.as()`.

```javascript
// 1. Объявляем перехватчик и даем ему имя (alias)
cy.intercept('GET', '/api/users').as('getUsers');

// 2. Выполняем действие в приложении (клик по кнопке, загрузка страницы)
cy.get('#load-button').click();

// 3. Ждем, пока запрос завершится
cy.wait('@getUsers').then((interception) => {
  // Теперь у нас есть доступ к деталям запроса и ответа
  expect(interception.response.statusCode).to.equal(200);
});
```

---

### 4. Stubbing: Подмена данных (Mocking)
Когда бэкенд еще не готов или тебе нужно проверить специфический сценарий (например, огромный список товаров).

```javascript
cy.intercept('GET', '/api/users', {
  statusCode: 200,
  body: [{ id: 1, name: 'John Doe' }], // Возвращаем свой JSON
  headers: { 'x-custom-header': 'hello' }
}).as('getMockUsers');
```

---

### 5. Продвинутый уровень: Изменение ответа (Response Modification)
Ты можешь перехватить реальный ответ от сервера и «подкрутить» его перед тем, как приложение его увидит.

```javascript
cy.intercept('GET', '/api/users', (req) => {
  req.continue((res) => {
    // res — это то, что пришло от реального сервера
    res.body.push({ id: 99, name: 'Hacker' }); // Добавляем юзера в реальный список
    res.statusCode = 201; // Меняем статус на лету
  });
}).as('modifiedUsers');
```

---

### ⚠️ Нюансы и «грабли» (Senior Tips)

1.  **Порядок имеет значение:** Cypress проверяет перехватчики сверху вниз. Если у тебя два `cy.intercept` на один URL, сработает **последний** объявленный.
2.  **Сначала Intercept, потом Action:** Это золотое правило. Сначала опиши `cy.intercept(...).as('alias')`, и только потом делай `cy.click()` или `cy.visit()`. Если запрос уйдет до того, как Cypress его «зарегистрирует», ты его не поймаешь.
3.  **Не злоупотребляй Stubbing:** Если ты подменяешь вообще все запросы, ты тестируешь не свое приложение, а свои фантазии о том, как работает бэкенд. Старайся использовать реальные данные там, где это возможно.
4.  **Spying vs Stubbing для тестов на ошибки:** Чтобы проверить, как UI реагирует на ошибку сервера (например, 500 или 403), `intercept` — твой лучший друг. Не жди, пока бэкенд разработчики сломают сервер специально для тебя.

### ❓ FAQ (Частые вопросы)

**В: Чем `cy.intercept` лучше старого `cy.route`?**
**О:** `cy.route` умел работать только с XHR запросами и был ограничен в возможностях. `cy.intercept` работает с любыми сетевыми запросами (включат Fetch API) и позволяет не только смотреть, но и изменять запрос/ответ.

**В: Что будет, если я сделаю `cy.wait('@alias')`, а запрос так и не придет?**
**О:** Тест упадет по таймауту. Cypress будет ждать указанное время (по умолчанию 5 секунд), прежде чем сказать: «Я не увидел этого запроса».

**В: Можно ли перехватить запрос, который уходит сразу при `cy.visit()`?**
**О:** Да, но это сложно. Чтобы поймать самый первый запрос при загрузке страницы, нужно использовать `cy.intercept` **до** вызова `cy.visit()`.

**В: Как проверить, что в теле запроса (Request Body) ушли правильные данные?**
**О:** Внутри `.wait('@alias')` используй свойство `interception.request.body`.
```javascript
cy.wait('@createUser').then((interception) => {
  expect(interception.request.body).to.have.property('email', 'test@test.com');
});
```

# 🧠 Шпаргалка: Stubbing & Mocking

### 🎯 Суть процесса
Когда мы тестируем конкретный модуль (Unit-тест), мы не хотим, чтобы тест зависел от внешнего мира: базы данных, API сторонних сервисов или даже других сложных модулей твоего проекта. 

**Цель:** Изолировать тестируемый код (SUT — System Under Test), заменив его зависимости «заглушками».

---

### 1. Stub vs Mock: В чем разница?
Это классика собеседований. Не путай их.

*   **Stub (Заглушка):** Это "глупый" объект. Его единственная задача — **ответить на запрос** заранее заготовленным ответом. Он не проверяет, как его вызвали, он просто возвращает данные.
    * *Пример:* «Если спросят про пользователя, всегда отвечай, что его зовут Иван».
*   **Mock (Мок):** Это "умный" объект. Его задача — **проверить поведение**. Он записывает: сколько раз его вызвали, с какими аргументами, в каком порядке.
    * *Пример:* «Проверь, что функция `send_email` была вызвана ровно один раз и именно с адресом `admin@test.com`».

> **Senior Tip:** В современном Python (с библиотекой `unittest.mock`) грань размыта, так как один и тот же объект может работать и как Stub (через `return_value`), и как Mock (чеently через `assert_called_with`).

---

### 2. Инструментарий: `monkeypatch` vs `mocker`

В PyTest есть два основных пути:

#### A. Встроенный `monkeypatch`
Это стандартная фича PyTest. Она идеально подходит для простых вещей.
* **Что умеет:** Менять атрибуты объектов, переменные окружения (`setenv`), пути в `sys.path`.
* **Плюсы:** Не нужно ничего устанавливать.
* **Минусы:** Плохо подходит для сложной логики и проверки вызовов (сложно проверить, сколько раз вызвали функцию).

```python
def test_env_var(monkeypatch):
    monkeypatch.setenv("API_KEY", "secret_123")
    assert os.getenv("API_KEY") == "secret_123"
```

#### B. Библиотека `pytest-mock` (объект `mocker`)
Это обертка над стандартным `unittest.mock`, адаптированная под PyTest. **Рекомендуемый стандарт в индустрии.**
* **Что умеет:** Патчить (подменять) функции, классы и методы; делать Spy; проверять аргументы.
* **Главный плюс:** Автоматический Cleanup. Тебе не нужно вручную возвращать всё как было — `mocker` сам «откатит» изменения после завершения теста.

---

### 3. Основные техники (Patterns)

#### 🔹 Stubbing (Подмена значения)
Используем `return_value`, чтобы имитировать успешный ответ.
```python
def test_get_user_name(mocker):
    # Подменяем функцию так, чтобы она всегда возвращала "John"
    mocker.patch('app.services.get_user_from_db', return_value={"name": "John"})
    
    result = app.get_user_name(1) # Внутри вызывается наш мок
    assert result == "John"
```

#### 🔹 Side Effect (Имитация ошибок или динамики)
Если нужно проверить, как код реагирует на **исключение** или на **последовательность разных ответов**.
```python
def test_api_error(mocker):
    # Имитируем падение API с ошибкой 500
    mocker.patch('app.api.call', side_effect=Exception("Connection Error"))
    
    with pytest.raises(Exception, match="Connection Error"):
        app.do_request()

def test_sequence(mocker):
    # Имитируем очередь ответов: сначала 200, потом 404
    mocker.patch('app.api.call', side_effect=[{"status": 200}, {"status": 404}])
```

#### 🔹 Spying (Слежка)
Мы не подменяем логику функции, а просто «приклеиваемся» к ней, чтобы проверить факт вызова.
```python
def test_spy_example(mocker):
    spy = mocker.spy(real_service, 'process_data')
    
    real_service.process_data("input")
    
    assert spy.call_count == 1  # Проверяем, что метод реально сработал
```

---

### ⚠️ Главная ловушка: "Where to patch?" (Где патчить?)
Это ошибка №1. **Патчить нужно там, где объект ИСПОЛЬЗУЕТСЯ, а не там, где он ОПРЕДЕЛЕН.**

Представь структуру:
`models.py` — здесь лежит функция `get_data`.
`services.py` — здесь мы делаем `from models import get_data`.

Если ты напишешь `mocker.patch('models.get_data')`, тест **НЕ СРАБОТАЕТ**, потому что `services.py` уже импортировал старую функцию в свою область видимости.
**Правильно:** `mocker.patch('services.get_data')`.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем `mocker` лучше, чем ручной `patch` из `unittest.mock`?**
**О:** Автоматическим откатом изменений (cleanup). В `unittest.mock` ты должен использовать контекстный менеджер `with patch(...)` или вручную делать `stop()`. Если тест упадет до того, как ты сделаешь `stop()`, глобальное состояние проекта может испортиться для следующих тестов. `mocker` делает это за тебя.

**В: Можно ли использовать `monkeypatch` для подмены функции?**
**О:** Можно через `monkeypatch.setattr`, но это неудобно для проверки вызовов (ты не узнаешь, сколько раз вызвали функцию). Для функций всегда используй `mocker`.

**В: Что такое `side_effect` и когда его использовать вместо `return_value`?**
**О:** `return_value` — это статичный ответ. `side_effect` нужен, если: 1) Нужно выбросить ошибку (`Exception`). 2) Нужно возвращать разные значения при каждом вызове (передав список). 3) Нужно выполнить дополнительную логику при вызове.

# 🕵️‍♂️ Spying (Шпионаж) в тестировании

Если коротко: **Spying — это наблюдение без вмешательства.**

Когда ты используешь `mock` или `patch`, ты подменяешь реальный объект «пустышкой». Когда ты используешь `spy`, ты оставляешь реальный код работать как обычно, но ставишь на него «скрытую камеру», которая записывает всё: вызывали ли функцию, с какими аргументами и что она вернула.

### 🎯 Главное отличие (The Trinity)
Чтобы не путаться, запомни три кита мокинга:
1.  **Stub (Заглушка):** Подменяет ответ. Ей плевать на вызовы, она просто возвращает `True` или `42`.
2.  **Mock (Мок):** Заменяет логику. Вместо реального тяжелого запроса в БД — пустая функция. Она не выполняет реальный код.
3.  **Spy (Шпион):** **Выполняет реальный код**, но записывает историю вызовов.

### 🛠 Как это работает в `pytest-mock`
В экосистеме `pytest` для этого используется инструмент `mocker.spy(target, 'method_name')`.

**Базовый синтаксис:**
```python
def test_spy_example(mocker):
    # Представим, что у нас есть класс Service
    from my_app import Service
    service = Service()

    # Мы "шпионим" за методом 'do_work' внутри объекта service
    spy = mocker.spy(service, 'do_work')

    # Вызываем реальный метод
    result = service.do_work("input_data")

    # Проверяем, что шпион зафиксировал вызов
    assert spy.call_count == 1
    assert spy.call_args[0][0] == "input_data"
    
    # ВАЖНО: Реальный результат всё еще работает!
    assert result == "Expected Real Result"
```

### 💡 Когда использовать Spy? (Use Cases)
*   **Проверка побочных эффектов:** Тебе нужно убедиться, что метод `send_email` был вызван, но ты не хочешь отключать саму отправку (например, если это логика формирования логов).
*   **Интеграционные тесты:** Когда ты тестируешь цепочку вызовов внутри системы и хочешь убедиться, что компонент А действительно обратился к компоненты Б.
*   **Проверка аргументов:** Когда важно не то, *что* вернул метод, а с какими именно параметрами он был запущен.

### ⚠️ Нюансы и "Подводные камни" (Senior Insights)

1.  **Реальный код выполняется!** Это самая опасная часть. Если ты шпионишь за методом, который удаляет записи из базы данных или отправляет SMS — **он это сделает**. Шпион не защищает от побочных эффектов.
2.  **Spy vs Patch:** Если тебе нужно изолировать тест от внешнего мира (сеть, БД) — используй `patch`. Если тебе нужно просто проверить факт взаимодействия внутри системы — используй `spy`.
3.  **Сложность отладки:** Если шпион "записывает" слишком много данных в больших циклах, это может немного замедлить тест и забить память (хотя на практике это редкость).
4.  **Область видимости:** Шпионить можно только за атрибутами объектов или модулей, которые доступны в текущем контексте.

### ❓ FAQ (Частые вопросы)

**В: Можно ли с помощью Spy изменить возвращаемое значение?**
**О:** Нет. Если ты изменишь результат — это уже будет `mock` или `patch`. Задача шпиона — оставаться незаметным и не менять поведение системы.

**В: Что если я хочу шпионить за встроенной функцией Python, например `print`?**
**О:** С `mocker.spy` это может быть сложно, так как `print` — это встроенная функция (built-in). Для таких случаев лучше использовать `mocker.patch('builtins.print')`. Шпионаж лучше всего работает с твоими собственными классами и методами.

**В: Как проверить, что метод НЕ вызывался?**
**О:** Используй проверку `assert spy.call_count == 0`. Это классический сценарий для проверки условий (например, если ошибка произошла раньше, email не должен был отправиться).

**В: Если я шпионю за методом класса, будет ли шпион работать для всех экземпляров этого класса?**
**О:** Если ты используешь `mocker.spy(MyClass, 'method')`, то да, это затронет класс. Но обычно безопаснее и точнее шпионить за конкретным экземпляром: `mocker.spy(my_instance, 'method')`.

# 🚀 Шпаргалка: API Testing (Integration Layer)

**API Testing** — это проверка того, как компоненты системы общаются друг с другом через интерфейс. В отличие от UI-тестов, здесь мы не видим кнопок, мы работаем с «контрактом»: отправили запрос $\rightarrow$ получили ответ. Если формат ответа совпадает с обещанием (контрактом), значит, API работает.

### 1. Фундамент: HTTP Протокол
Чтобы тестировать API, нужно понимать, что именно ты отправляешь и что ожидаешь получить.

*   **HTTP Methods (Глаголы):**
    *   `GET`: Получение данных. *Свойство: Идемпотентность (повторный вызов не меняет состояние сервера).*
    *   `POST`: Создание нового ресурса. *Не идемпотентен (два раза нажмешь — создашь два юзера).*
    *   `PUT`: Полная замена ресурса. Если пришлешь не все поля, недостающие могут затереться.
    *   `PATCH`: Частичное изменение. Обновляем только конкретное поле (например, только `email`).
    *   `DELETE`: Удаление.
*   **Status Codes (Результаты):**
    *   `2xx (Success)`: `200 OK` (всё супер), `201 Created` (ресурс создан), `204 No Content` (успешно, но ответа в теле нет).
    *   `4xx (Client Error)`: Твоя вина. `400 Bad Request` (кривой JSON), `401 Unauthorized` (забыл токен), `403 Forbidden` (токен есть, но прав нет), `404 Not Found` (неверный URL).
    *   `5xx (Server Error)`: Вина разработчиков. `500 Internal Server Error` (код упал с ошибкой), `503 Service Unavailable` (сервер лег).

### 2. Анатомия запроса и ответа
При написании теста ты манипулируешь этими частями:
*   **Endpoint (URL):** Путь к ресурсу (`/api/v1/users/123`).
*   **Headers:** Метаданные. Самые важные: `Content-тиpe: application/json` и `Authorization: Bearer <token>`.
*   **Params (Query Params):** Параметры в URL после знака `?` (`/users?role=admin`). Используются для фильтрации/сортировки.
*   **Payload (Body):** Тело запроса (обычно JSON). То, что мы передаем при `POST/PUT`.

### 3. Чек-лист: Что именно проверять? (The Senior Way)
Недостаточно просто проверить `status_code == 200`. Хороший тест проверяет:

1.  **Status Code:** Первичная проверка на успех/провал.
2.  **Schema Validation (Контракт):** Проверка структуры JSON. Есть ли поле `id`? Является ли `email` строкой? Это критично. Используй библиотеку `jsonschema` или `pydantic`.
3.  **Data Integrity:** Если мы создали юзера, проверяем, что в ответе пришел именно тот `name`, который мы отправляли.
4.  **Negative Scenarios:** 
    *   Отправка пустых обязательных полей.
    *   Неверный тип данных (строка вместо числа).
    *   Превышение лимитов (слишком длинная строка).
5.  **Headers Check:** Проверка `Content-Type`, наличие необходимых заголовков безопасности.

### 4. Инструментарий в Python
*   **`requests`**: Библиотека №1 для отправки HTTP-запросов.
*   **`pytest`**: Движок для запуска и организации тестов.
*   **`jsonschema`**: Для проверки структуры JSON (чтобы не писать 100 `assert` на каждое поле).

### 5. Senior Nuances (Тонкости)
*   **Idempotency Testing:** Всегда проверяй, что повторный `DELETE` или `PUT` не ломает систему.
*   **Environment Isolation:** Никогда не хардкодь базовый URL (`http://localhost:8080`). Используй фикстуры и переменные окружения (`pytest-dotenv`), чтобы тесты летали между `dev`, `staging` и `prod`.
*   **Auth Fixtures:** Создай одну фикстуру `auth_token`, которая один раз логинится перед сессией и раздает токен всем тестам. Это экономит кучу времени.

# 🧠 Cheat Sheet: Iframe & Shadow DOM in Cypress

В Cypress работа с `iframe` и `Shadow DOM` — это классическая «боль», потому что эти технологии создают **изолированные контексты**. Cypress по умолчанию живет в основном окне (top-level window) и не видит то, что находится за пределами его прямой видимости.

---

## 1. Iframe (Внешний документ)
**Суть:** `iframe` — это фактически еще одна HTML-страница, вставленная в твою. У неё свой `document` и свой `body`. Cypress не может «прострелить» сквозь границы iframe стандартным `.get()`.

### Как работать:
Чтобы протестировать элемент внутри iframe, нужно сначала «достучаться» до его содержимого (`contentDocument`), а затем переключить контекст на его `body`.

**Базовый паттерн (Custom Command):**
```javascript
// В commands.js
Cypress.Commands.add('getIframeBody', (selector) => {
  return cy
    .get(selector) // Находим сам iframe
    .its('0.contentDocument.body') // Добираемся до body внутри него
    .should('not.be.empty') // Ждем, пока он загрузится
    .then(cy.wrap); // Оборачиваем в объект Cypress для дальнейшей работы
});

// Использование в тесте:
cy.getIframeBody('#my-iframe').find('#button-inside').click();
```

### ⚠️ Нюансы (Senior Level):
1.  **Race Condition (Гонка состояний):** Iframe загружается медленнее основного документа. Всегда используй `.should('not.be.empty')` или проверку на видимость, иначе тест упадет, попытавшись найти элемент в еще не загруженном документе.
2.  **Cross-Origin Policy:** Если `iframe` ведет на другой домен (например, `google.com`), браузер заблокирует доступ к его содержимому из соображений безопасности. В Cypress это решается настройкой `chromeWebSecurity: false` в `cypress.config.js`, но помни — это «костыль».
3.  **Плагины:** Для сложных случаев (много вложенных iframe) лучше использовать проверенный плагин `cypress-iframe`. Он делает синтаксис чище.

---

ط## 2. Shadow DOM (Инкапсуляция)
**Суть:** Это стандарт Web Components. Он создает «скрытое» дерево элементов внутри элемента. Элементы внутри Shadow DOM не видны обычному `cy.get()`, так как они находятся в отдельном дереве (Shadow Root).

### Как работать:
Cypress умеет пробиваться сквозь Shadow DOM, если ему об этом сказать.

**Способ А: Глобально (рекомендую)**
Если всё твое приложение построено на Web Components, включи поддержку во всем проекте.
```javascript
// cypress.config.js
const { defineConfig } = require("cypress");

module.exports = defineConfig({
  e2e: {
    includeShadowDom: true, // Теперь cy.get() видит сквозь Shadow DOM везде
  },
});
```

**Способ Б: Локально (точечно)**
Если нужно найти элемент только в одном конкретном месте.
```javascript
// Используем команду .shadow()
cy.get('.host-element').shadow().find('.inner-button').click();
```

### ⚠️ Нюансы (Senior Level):
1.  **Open vs Closed Shadow DOM:** 
    *   `mode: 'open'` — Cypress (и JS) может зайти внутрь. Это то, с чем мы работаем.
    *   `mode: 'closed'` — **Это смерть для автоматизации.** В режиме `closed` доступ к `shadowRoot` через JavaScript программно закрыт. Если разработчики использовали `closed`, стандартными средствами Cypress ты туда не попадешь (придется использовать хаки с переопределением конструктора `HTMLElement`).
2.  **Производительность:** Глобальный `includeShadowDom: true` может немного замедлить поиск элементов в очень тяжелых DOM-деревях, так как Cypress приходится проверять каждый узел на наличие Shadow Root.

## ❓ FAQ (Частые вопросы на собеседовании)

**В: Почему `cy.get('.btn')` не находит кнопку, если она внутри iframe?**
**О:** Потому что `cy.get()` ищет только в текущем документе (`document`). Iframe — это отдельный документ со своим собственным деревом DOM. Тебе нужно явно получить доступ к `contentDocument` этого iframe.

**В: Можно ли протестировать `closed shadow DOM` средствами Cypress?**

**В: В чем разница между `.shadow()` и `includeShadowDom: true`?**
**О:** `.shadow()` — это ручное управление (ты сам указываешь путь). `includeShadowDom: true` — это автоматизация (Cypress сам сканирует дерево на наличие Shadow Roots при каждом поиске).

# 🪟 Работа с окнами и вкладками в Cypress

### ⚠️ Главная проблема (The Elephant in the Room)
**Cypress не умеет переключаться между вкладками.** 
В отличие от Selenium, который управляет браузером извне, Cypress работает *внутри* того же цикла событий, что и ваше приложение. У него нет доступа к другим окнам или вкладкам, которые открыл браузер. Если тест нажмет на ссылку с `target="_blank"`, фокус уйдет в новую вкладку, и Cypress «потеряет» управление.

**Золотое правило Senior-разработчика:** Мы не учимся переключаться между вкладками, мы **запрещаем** им открываться, заставляя контент открываться в текущей вкладке.

---

### 🛠 Основные стратегии решения

#### 1. Удаление атрибута `target="_blank"` (Для обычных ссылок)
Самый частый сценарий: у ссылки есть атрибут, который говорит браузеру «открой это в новом окне». Наша задача — удалить этот атрибут перед кликом.

```javascript
// Находим ссылку и удаляем target, чтобы она открылась в текущем окне
cy.get('a[href="/new-page"]')
  .invoke('removeAttr', 'target') 
  .click();

// Теперь мы проверяем URL в той же вкладке
cy.url().should('include', '/new-page');
```

#### 2. Перехват `window.open` (Для JS-событий)
Иногда открытие окна происходит не через HTML-тег, а через JavaScript-код: `window.open('url')`. Здесь нам нужно использовать **Stub** (заглушку).

```javascript
cy.visit('/', {
  onBeforeLoad(win) {
    // Создаем заглушку для функции window.open
    cyط.stub(win, 'open').as('windowOpen');
  }
});

// Кликаем по кнопке, которая вызывает window.open
cy.get('#open-popup-button').click();

// Проверяем, что функция была вызвата с правильным URL
cy.get('@windowOpen').should('be.calledWith', '/expected-url');
```

#### 3. Использование `cy.request` (Для проверки контента без UI)
Если вам нужно проверить, что по ссылке в новой вкладке находится правильный текст или статус-код, не обязательно «открывать» её визуально. Можно просто сделать запрос к API/URL.

```javascript
cy.get('a#external-link').then(($el) => {
  const url = $el.prop('href'); // Берем URL из ссылки
  
  cy.request(url).then((response) => {
    expect(response.status).to.eq(200);
    expect(response.body).to.contain('Welcome');
  });
});
```

### 🧠 Нюансы и советы (Senior Tips)

1.  **Не пытайтесь использовать плагины для переключения вкладок.** Большинство из них — это костыли, которые ломают стабильность теста. Используйте `invoke('removeAttr', 'target')`.
2.  **Сложные сценарии с Pop-up:** Если клик вызывает всплывающее окно (iframe или сложный модал), работайте не с «окном», а с содержимым внутри текущего DOM. 
3.  **Проблема аутентификации:** Если новая вкладка ведет на сторонний сервис (например, Google Login), `window.open` заглушка — ваш единственный путь. Вы можете перехватить URL и имитировать логин через `cy.request`.

**В: Почему я не могу просто использовать `cy.switchWindow()`?**
**О:** Такого команды не существует в Cypress. Архитектура Cypress привязана к одной вкладке. Любая попытка выйти за пределы текущего окна обрывает связь теста с приложением.

**В: Что делать, если ссылка открывает PDF или скачиваемый файл?**
**О:** Не пытайтесь «открыть» его в браузере через Cypress. Используйте `cy.request()` для загрузки файла и проверьте его содержимое (или заголовки `Content-Type`) программно.

# 📸 Visual Regression Testing (VRT) — Шпаргалка

**Visual Regression Testing** — это метод тестирования, при котором мы проверяем не логику кода (как в функциональных тестах), а то, как интерфейс **выглядит**. Мы сравниваем текущий скриншот приложения с «эталонным» (Baseline/Golden Image). Если разница между ними превышает заданный порог — тест считается провалившимся.

### 🎯 Зачем это нужно?
Функциональные тесты (Cypress/Playwright) проверяют, что кнопка *кликабельна* и *отправляет форму*. Но они не заметят, если:
* Кнопка стала серой вместо синей.
* Текст наехал на картинку.
* Верстка «поплыла» на мобильном разрешении.
* Появился лишний отступ (margin/padding).

### 🛠 Как работает процесс (Workflow)
1.  **Capture:** Автотест открывает страницу и делает скриншот (или снимок конкретного элемента).
2.  **Comparison:** Специальный движок (pixelmatch, Resemble.js или облачные сервисы) накладывает новый скриншот на эталонный.
3.  **Diffing:** Вычисляется разница в пикселях.
4.  **Threshold Check:** Если процент разницы меньше допустимого (например, < 0.1%), тест **Passed**. Если больше — **Failed**.
5.  **Update Baseline:** Если изменения легитимны (дизайнер обновил UI), инженер нажимает кнопку «Approve», и новый скриншот становится новым эталоном.

### ⚠️ Главные проблемы и "Подводные камни" (Nuances)

VRT — это один из самых «хрупких» (flaky) видов тестирования. Вот где все ломается:

1.  **Динамический контент:** Даты, имена пользователей, рекламные баннеры или курсы валют всегда разные.
    *   *Решение:* **Masking** (закрашивание области черным квадратом перед снимком) или **Mocking** (подмена данных через API, чтобы текст всегда был одинаковым).
2.  **Анимации и переходы:** Если скриншот сделан в момент, когда кнопка плавно меняет прозрачность, тест упадет.
    *   *Решение:* Отключать CSS-анимации в тестовой среде или использовать команды ожидания `stable` (когда анимация завершена).
3.  **Рендеринг шрифтов и антиалиасинг:** Один и тот же шрифт может выглядеть чуть иначе на macOS и на Linux (в Docker). Это создаст «шум» из пикселей.
    *   *Решение:* **Запуск тестов строго в Docker-контейнере.** Окружение (ОС, браузер, версия движка) должно быть идентичным везде.
4.  **Разные разрешения (Viewport):** Тест на 1280x720 не равен тесту на 1920x1080.
    *   *Решение:* Всегда жестко задавать `viewport` в конфигурации теста.

### 🚀 Инструментарий
*   **Low-level (библиотеки):** `pixelmatch` (самый популярный движок сравнения), `resemble.js`. Используются, если ты пишешь свой плагин.
*   **Plugin-based (для Cypress/Playwright):** `cypress-image-snapshot`, `playwright-visual-regression`. Работают локально, хранят картинки в твоем репозитории.
*   **SaaS Solutions (Enterprise уровень):** **Percy**, **Applitools**. Самые мощные инструменты. Они сами управляют облачными браузерами, умеют «умное» сравнение (не по пикселям, а по структуре DOM) и имеют удобный UI для ревью изменений.

### 💡 Best Practices (Советы Senior-а)
*   **Не делай скриншот всей страницы:** Скриншоть конкретные компоненты (карточку товара, хедер, футер). Так меньше шансов поймать случайный шум.
*   **Устанавливай Threshold (Порог):** Никогда не ставь 0% разницы. Дай системе микроскопическую погрешность (например, `0.1%`), чтобы избежать ложных срабатываний из-за сглаживания пикселей.
*   **Используй Mock API:** Твой UI должен быть детерминированным. Если данные приходят одни и те же — визуальный тест будет стабильным.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что делать, если тест падает из-за того, что текст в блоке стал чуть длиннее?**
**О:** Если это баг верстки — фиксим код. Если это фича (изменился контент) — делаем ребадлайн (Update Baseline), чтобы новый вариант стал эталоном.

**В: Можно ли использовать VRT для тестирования динамических графиков?**
**О:** Напрямую — очень сложно из-за постоянного движения линий. Лучше всего либо зафиксировать состояние данных через Mock, либо использовать "Masking", чтобы скрыть область графика, если нас интересует только окружение него.

**В: Почему Visual Testing не заменяет функциональный?**
**О:** Потому что VRT не знает, работает ли кнопка. Она видит, что кнопка синяя, но не может проверить, вызывается ли при клике API-запрос. Это дополнение, а не замена.

# 🧩 Cypress Component Testing: Senior Cheat Sheet

**Component Testing (CT)** — это способ тестирования отдельных частей твоего приложения (React, Vue, Angular, Svelte) в изоляции. Если E2E-тесты проверяют «весь замок», то CT проверяет «один кирпич» или «одну дверь». Ты запускаешь компонент внутри реального браузера, а не в виртуальной среде типа JSDOM (как это делает Jest).

### 🚀 Основная концепция
Вместо того чтобы загружать целую страницу через `cy.visit()`, ты используешь команду **`cy.mount()`**. Она берет твой компонент и «вклеивает» его в пустую тестовую страницу.

**Главный профит:** Ты видишь реальный рендеринг, реальные CSS-стили и реальное поведение браузера, но при этом тебе не нужно поднимать бэкенд или базу данных.

---

### 🛠 Ключевые элементы

1.  **`cy.mount(<Component />)`**: Сердце CT. Принимает компонент и его пропсы.
2.  **Props (Входные данные)**: Ты передаешь всё, что нужно компоненту, прямо в момент монтирования.
3.  **Events (События)**: Проверка того, что при клике на кнопку вызывается нужная функция (callback).
4.  **Isolation (Изоляция)**: Компонент не знает о существовании других компонентов, если ты сам их не импортируешь.

---

### 🧠 Нюансы и «подводные камни» (Senior Level)

#### 1. Проблема Context Providers (Самая частая ошибка!)
Если твой компонент использует `useContext`, `Redux`, `React Router` или `ThemeProvider`, обычный `cy.mount(<MyComponent />)` **упадет**. Компонент не найдет контекст.
*   **Решение:** Создай кастомную команду `cy.mountWithProviders`. Оберни в неё свой компонент со всеми необходимыми провайдерами (Theme, Redux, Router).

#### 2. Mocking API (Заглушки)
Хотя мы тестируем компонент, он может делать запросы внутри `useEffect`.
*   **Решение:** Используй `cy.intercept()`. Да, он работает в Component Testing точно так же, как в E2E! Ты перехватываешь запрос и отдаешь фейковый JSON.

#### 3. Стили и Глобальный CSS
В CT компоненты могут выглядеть «сломанными», если ты забыл импортировать глобальные стили (например, Tailwind или Bootstrap) в конфигурационный файл теста.
*   **Решение:** Убедись, что `setupNodeEvents` или основной файл конфигурации импорта тестируемого приложения включает базовые стили.

#### 4. Сравнение с Jest/React Testing Library (RTL)
Почему не использовать привычный Jest?
*   **Jest/RSD:** Работает в Node.js (JSDOM). Это быстро, но это *имитация* браузера. Нельзя проверить реальные Z-index, сложные анимации или специфические баги рендеринга.
*   **Cypress CT:** Работает в **реальном Chrome/Firefox**. Если кнопка перекрыта невидимым слоем — Cypress это увидит, а Jest — нет.

---

### 📋 Шпаргалка по коду (Пример на React)

```javascript
// Тест компонента Button
import MyButton from './MyButton'

describe('MyButton Component', () => {
  it('должен корректно отображать текст и реагировать на клик', () => {
    // 1. Создаем шпиона (spy) для функции
    const onClickSpy = cy.spy().as('onClickSpy')

    // 2. Монтируем компонент с пропсами
    cy.mount(<MyButton label="Click Me" onClick={onClickSpy} />)

    // 3. Проверяем текст (Assertion)
    cy.get('button').should('contains.text', 'Click Me')

    // 4. Имитируем действие и проверяем вызов функции
    cy.get('button').click()
    cy.get('@onClickSpy').should('have.been.called')
  })
})
```

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Чем Component Testing отличается от E2E тестирования?**
**О:** E2E проверяет весь путь пользователя через все слои приложения (UI -> API -> DB). CT проверяет только логику и визуализацию конкретного компонента в изоляции, подменяя внешние зависимости (API) заглушками.

**В: Можно ли тестировать взаимодействие двух компонентов в CT?**
**О:** Можно, но это уже превращается в Integration Testing. Рекомендуется держать фокус на одном компоненте, чтобы тесты оставались быстрыми и точными. Если нужно проверить связь — монтируй родителя.

**В: Как протестировать загрузку данных из API в компоненте?**

**В: Что делать, если компонент использует библиотеку анимаций (например, Framer Motion)?**
**О:** В CT это работает отлично, так как браузер настоящий. Но если анимация слишком долгая и мешает тесту, можно использовать `cy.clock()` для управления временем или отключить анимации в тестовом окружении.

# 🧠 Паттерны проектирования в Test Automation

**Дизайн-паттерны** — это не «волшебные таблетки», а проверенные временем шаблоны решения типичных проблем. В автотестах мы используем их, чтобы код не превратился в «спагетти», который невозможно поддерживать при первом же изменении верстки.

### 1. Page Object Model (POM) — Король паттернов
Самый популярный паттерн. Его суть: **разделение логики теста и структуры страницы.**
*   **Как это работает:** Каждая страница сайта — это отдельный класс. В этом классе описаны локаторы (кнопки, поля ввода) и методы (логика взаимодействия: `login()`, `searchProduct()`).
*   **Зачем:** Если разработчики изменят ID кнопки «Войти», ты поменяешь его только в одном месте (в Page Object), а не в 100 тестах.
*   **⚠️ Нюанс (Senior Tip):** **Никогда не пиши Assertions (проверки) внутри Page Object!** Класс страницы должен только *предоставлять данные* или *выполнять действия*. Проверка того, что текст правильный, должна происходить в самом тесте. Иначе твой POM станет «умным» и неподдерживаемым.

### 2. Page Component / Fragment (Компоненты)
Развитие POM для больших проектов.
*   **Как это работает:** Вместо того чтобы создавать один гигантский класс `DashboardPage`, ты разбиваешь его на маленькие части: `HeaderComponent`, `SidebarComponent`, `FooterComponent`.
*   **Зачем:** Если шапка сайта (Header) есть на всех страницах, тебе не нужно дублировать её код в каждом Page Object. Ты просто подключаешь компонент `Header` в нужные страницы.
*   **Преимущество:** Модульность и высокая переиспользуемость.

### 3. Screenplay Pattern — Продвинутый уровень
Если POM — это «где» (на какой странице), то Screenplay — это «кто» и «что делает». Он фокусируется на **поведении пользователя**.
*   **Как это работает:** В основе лежат 4 сущности:
    1.  **Actor (Актер):** Тот, кто выполняет тест (например, "Admin" или "Guest").
    2.  **Ability (Способность):** Что актер умеет (например, "Browse the web").
    3.  **Task (Задача):** Высокоуровневое действие ("Add item to cart").
    4.  **Interaction (Взаимодействие):** Низкоуровневое действие ("Click button").
*   **Зачем:** В очень сложных проектах POM превращается в «Божественные объекты» (God Objects) — классы на 2000 строк кода. Screenplay разбивает всё на маленькие, атомарные классы-задачи.

### 4. Factory Pattern (Фабрика)
Паттерн для создания объектов без указания конкретного класса.
*   **Как это работает:** Ты создаешь метод `UserFactory.create_user('admin')`, который возвращает объект пользователя с нужными правами и набором данных.
*   **Зачем:** Упрощает создание сложных тестовых данных (например, разных типов пользователей: Admin, Editor, Viewer) в одном месте.

### 5. Fluent Interface (Текучий интерфейс / Method Chaining)
Паттерн для улучшения читаемости тестов.
*   **Как это работает:** Методы класса возвращают `this` (или `self` в Python). Это позволяет выстраивать цепочки действий.
*   **Пример:** `page.login(user).search('laptop').addToCart().verifySuccess();`
*   **Зачем:** Тест читается как человеческое предложение.

### 6. Data-Driven Testing (DDT) — Тестирование на данных
Разделение логики теста и входных данных.
*   **Как это работает:** Один и тот же тест запускается несколько раз с разными наборами данных из внешнего источника (JSON, CSV, Excel).
*   **Зачем:** Чтобы не плодить 10 одинаковых тестов для проверки валидации полей (пустая строка, слишком длинная строка, спецсимволы), ты пишешь один тест и «прогоняешь» его через массив данных.

---

### 🚩 Главные антипаттерны (Чего делать НЕ надо)
1.  **Hardcoded Values:** Зашивать URL, логины и пароли прямо в код теста. Используй конфиги/переменные окружения.
2.  **Logic in Tests:** Тест должен состоять из шагов: *Action -> Action -> Assert*. Если в тесте появились `if-else` или сложные циклы — ты переусложнил. Логику нужно выносить в Page Objects или Tasks.
3.  **God Object:** Создание одного класса, который умеет всё (и логин, и поиск, и оформление заказа). Это смерть для поддержки.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем разница между POM и Screenplay?**
**О:** POM ориентирован на структуру страниц (структурный подход), а Screenplay — на действия пользователя (поведенческий подход). POM проще в освоении, Screenplay лучше масштабируется в огромных проектах.

**В: Можно ли использовать Singleton для управления драйвером (Browser)?**
**О:** Технически можно, но это опасно. Если ты захочешь запустить тесты параллельно (в несколько потоков), Singleton станет «бутылочным горлышком» или приведет к конфликтам между браузерами. Лучше использовать Dependency Injection или передавать экземпляр драйвера через фикстуры/контекст.

**В: Где именно должны находиться Assertions в Page Object?**
**О:** В идеале — нигде. Но если проект небольшой, допустимы "Soft Assertions" (проверки состояния), которые не роняют тест сразу. Однако классический стандарт: Page Object возвращает состояние (например, заголовок страницы), а тест его проверяет.

**В: Как паттерн Factory помогает в тестировании API?**
**О:** С помощью фабрики можно генерировать разные тела запросов (Payloads). Например, `PayloadFactory.get_user_payload(role='admin')` создаст JSON с нужными полями, избавляя тебя от ручного написания словарей в каждом тесте.

# 🧠 Шпаргалка: Page Object Model (POM)

**Page Object Model (POM)** — это паттерн проектирования, цель которого — разделить **логику теста** (что мы проверяем) и **логику взаимодействия с UI** (как мы это делаем). 

Вместо того чтобы писать в тесте `click("#login-btn")`, ты пишешь `LoginPage.click_login()`. Если разработчики изменят ID кнопки на `.submit-button`, тебе нужно будет поправить код только в **одном** месте (в Page Object), а не в сотне тестов.

---

### 🏗 Структура паттерна

Весь проект делится на два уровня:

1.  **Page Objects (Слой страниц/компонентов):**
    *   **Locators (Селекторы):** Хранилище всех ID, Xpath, CSS-селекторов.
    *   **Actions (Методы):** Функции, имитирующие действия пользователя (`login`, `search_product`, `add_to_cart`).
    *   **State/Information (Состояние):** Методы, которые возвращают данные со страницы (например, `get_user_name()`).

2.  **Test Layer (Слой тестов):**
    *   Здесь только **бизнес-логика**.
    *   Здесь происходят **Assertions** (проверки).
    *   Тест не знает про селекторы, он знает только про методы страниц.

---

### 🛠 Золотые правила Senior-уровня (Best Practices)

#### 1. Принцип "No Assertions in Page Objects"
Это самая частая ошибка новичков. **В методах Page Object не должно быть `assert`.**
*   ❌ **Плохо:** Метод `login()` проверяет, что пользователь вошел. Если проверка упадет, ты не поймешь: то ли кнопка не нажалась, то ли логин не сработал.
*   ✅ **Хорошо:** Метод `login()` просто выполняет действия. А тест после вызова `login()` делает проверку `assert page.is_logged_in()`.

#### 2. Компонентный подход (Component Object Model)
Не пытайся запихнуть всю страницу в один огромный класс. Если на сайте есть общая шапка (Header), боковое меню (Sidebar) или футер, вынеси их в **отдельные маленькие классы-компоненты**.
*   *Зачем?* Чтобы не дублировать код поиска элементов меню на каждой странице.

#### 3. Fluent Interface (Цепочки вызовов)
Чтобы тесты читались как текст, возвращай `self` или объект следующей страницы из методов.
*   **Пример:** `LoginPage.enter_credentials(u, p).click_submit().verify_dashboard()` — это превращает тест в понятную историю.

####s 4. Инкапсуляция селекторов
Селекторы должны быть "приватными" (в Python это префикс `_`). Тест не должен иметь прямого доступа к `self._login_button`. Он должен использовать метод `click_login()`.

---

### ⚠️ Нюансы и "Подводные камни"

*   **Проблема "Божественного объекта" (God Object):** Когда класс `HomePage` разрастается до 2000 строк. Решение: Дроби страницу на компоненты (SearchBox, UserMenu, ProductCard).
*   **Ожидания (Waits):** Не делай `time.sleep()` внутри Page Object. Вшивай явные ожидания (`WebDriverWait`) прямо в методы действий. Пользователь не ждет 5 секунд, он ждет появления элемента.
*   **Переходы между страницами:** Метод действия должен возвращать объект той страницы, на которую пользователь попал после клика.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Где должны находиться Assertions?**
**О:** Только в тестовых функциях. Page Object предоставляет данные или состояние (true/false), а тест решает, считать это успехом или провалом.

**В: Что делать, если элемент на странице меняется динамически?**
**О:** Использовать более стабильные атрибуты (например, `data-testid`) и инкапсулировать логику ожидания внутри метода Page Object, чтобы тест даже не знал о сложности процесса.

**В: POM — это всегда про страницы?**
**О:** Нет. Современный подход — это **Component-Based Testing**. Мы создаем объекты для карточки товара, для модального окна, для таблицы. Страница — это просто композиция из этих компонентов.

**В: В чем разница между Page Object и Page Component?**
**О:** Page Object — это целая страница (URL). Page Component — это переиспользуемый кусок интерфейса (например, кнопка "Лайк" или "Поиск"), который встречается на многих страницах.

# 🧠 Паттерн проектирования: App Actions

### Что это такое?
**App Actions** — это альтернатива классическому Page Object Model (POM). Если POM фокусируется на взаимодействии с **интерфейсом** (кликнул, ввел, проверил), то App Actions фокусируется на взаимодействии с **внутренним состоянием приложения** (вызвал функцию, изменил стор, обновил переменную).

Вместо того чтобы имитировать путь пользователя через 10 страниц для создания заказа (что долго и нестабильно), мы напрямую «подсовываем» приложению нужное состояние (например, кладем товар в корзину через Redux/Vuex action).

### Зачем это нужно? (The "Why")
1.  **🚀 Скорость:** Пропуск UI-шагов экономит десятки секунд на каждом тесте. В масштабе 500 тестов это часы сэкономленного времени в CI.
2.  **🛡️ Стабильность (Reliability):** UI-тесты часто падают из-за анимаций, перекрывающих элементы, или медленной загрузки страниц. App Actions работают на уровне логики, где нет «плавающих» элементов.
/3. **🎯 Изоляция:** Ты тестируешь конкретную фичу, а не цепочку всех предыдущих фич.

### Как это работает технически?
Для реализации App Actions разработчики должны «подружиться» с тестировщиком и выставить внутренние методы приложения (Redux actions, Vuex mutations, React Context) в глобальный объект `window`.

**Схема взаимодействия:**
`Cypress` ➔ `cy.window()` ➔ `App Window Object` ➔ `Internal App Logic (Action/Mutation)` ➔ `State Change`

### Пример реализации

**1. Со стороны разработчика (в коде приложения):**
```javascript
// В файле инициализации приложения (например, main.js)
if (window.Cypress) {
  window.store = store; // Выставляем Redux/Vuex стор в window для доступа из Cypress
}
```

**2. Со стороны тестировщика (в Cypress):**
```javascript
// Вместо долгого пути через UI: 
// Login -> Search -> Add to Cart -> Checkout

// Используем App Action:
it('should checkout fast using app actions', () => {
  cy.visit('/');
  
  cy.window().then((win) => {
    // Напрямую вызываем action, который кладет товар в корзину
    win.store.dispatch('cart/addItem', { id: 123, quantity: 1 });
  });

  // Теперь мы сразу на странице чекаута с готовым состоянием
  cy.get('.checkout-button').click();
  cy.get('.total-price').should('contain', '$123');
});
```

### ⚠️ Нюансы и "Подводные камни" (Senior Insights)

*   **Золотое правило:** Используй App Actions **только для подготовки состояния (Setup)**. Сам процесс тестирования целевой фичи (Assertion) должен оставаться через UI. Если ты будешь проверять всё только через App Actions, ты перестанешь быть QA и станешь интеграционным тестом логики.
*   **Риск "Ложной уверенности":** Если ты слишком сильно полагаешься на App Actions, ты можешь пропустить баг в UI-пути (например, кнопка "Добавить в корзину" на самом деле не работает, но твои тесты проходят, потому что они обходят эту кнопку).
*   **Связность (Coupling):** Твои тесты становятся сильно привязаны к внутренней архитектуре приложения. Если разработчики переименуют `addItem` в `addProductToCart`, твои тесты упадут. Это цена за скорость.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем принципиальная разница между Page Object и App Actions?**
**О:** POM имитирует **поведение пользователя** (User Perspective). App Actions используют **внутреннюю логику приложения** (Developer Perspective). POM — это про "что видит юзер", App Actions — про "как работает код".

**В: Можно ли использовать их вместе?**
**О:** Да, и это лучший подход. Используй App Actions для быстрой подготовки данных (логин, создание корзины, заполнение профиля), а POM — для выполнения самого сценария теста и проверок на странице.

**В: А если разработчики не хотят выставлять `window.store`?**
**О:** Это классический конфликт. Твоя задача как Senior — объяснить бизнесу экономию денег (CI/CD время) и стабильность релизов. Если это невозможно, единственным выходом остается использование API-запросов (`cy.request`) для подготовки состояния.

**В: Не делает ли App Actions наши тесты "нереалистичными"?**
**О:** Тесты становятся менее реалистичными в части *подготовки*, но остаются максимально реалистичными в части *проверки*. Мы тестируем не то, как пользователь логинится, а то, как работает корзина. Логин — это не цель нашего теста.

# 🧠 Шпаргалка: Принципы написания тестов

Хороший тест — это не тот, который нашел баг, а тот, который **быстро и надежно** сообщает о поломке именно там, где она появилась.

### 1. Золотой стандарт: Принцип FIRST
Это база, которую должен знать каждый. Тест считается качественным, если он соответствует этим критериям:

*   **F — Fast (Быстрый):** Тесты должны летать. Если автотесты идут 2 часа, разработчики перестанут их запускать. Короткие тесты позволяют получать фидбек мгновенно.
*   **I — Independent (Независимый):** Каждый тест должен быть «островом». Результат теста `A` не должен зависеть от того, прошел или упал тест `B`. Тесты можно (и нужно) запускать в любом порядке и параллельно.
*   **R — Repeatable (Повторяемый):** Тест должен давать один и тот же результат в любой среде (локально, на CI, в Docker). Если тест проходит у тебя, но падает в Jenkins — это плохой тест.
*   **S — Self-validating (Самопроверяемый):** Тесту не нужен человек, чтобы понять, прошел он или нет. Он должен иметь четкий `Assertion` (утверждение). Результат: Pass/Fail.
*   **T — Thorough / Timely (Тщательный / Своевременный):** Тест должен покрывать важные сценарии и писаться вовремя (в идеале — вместе с кодом или до него).

---

### 2. Структура теста: Паттерн AAA
Любой тест (будь то Cypress, PyTest или Playwright) должен иметь четкую структуру. Не смешивай всё в кучу. Используй **AAA**:

1.  **Arrange (Подготовка):** Создаем данные, настраиваем окружение, логинимся, переходим на нужную страницу.
2.  **Act (Действие):** Выполняем целевое действие (клик по кнопке, ввод текста, отправка формы). Это самая короткая часть теста.
3.  **Assert (Проверка):** Проверяем результат. Появился ли текст? Сменился ли статус? Удалилась ли запись?

> **Senior Tip:** Если у тебя в секции `Act` больше 2-3 действий — твой тест превращается в «сценарий», который сложно поддерживать. Разбей его на несколько атомарных тестов.

---

### 3. Ключевые концепции (Deep Dive)

#### **Атомарность (Single Responsibility)**
Один тест = одна проверяемая логика. 
*   ❌ **Плохо:** Тест «Регистрация и покупка товара», где в одном `it()` ты и регистрируешься, и ищешь товар, и кладешь в корзину, и оплачиваешь. Если упадет регистрация, ты даже не узнаешь, работает ли корзина.
*   ✅ **Хорошо:** Отдельные тесты на регистрацию, на добавление в корзину и на оформление заказа.

#### **Тестирование поведения, а не реализации (Black Box)**
Не проверяй, как код работает «под капотом» (например, наличие определенного класса или ID, если это не часть бизнес-логики). Проверяй то, что видит пользователь.
*   ❌ **Плохо:** `cy.get('.btn-blue-large').click()` — если дизайнер поменяет цвет на красный, тест упадет, хотя функционал работает.
*   ✅ **Хорошо:** Использовать семантические атрибуты (например, `data-cy="submit-button"` или `role="button"`).

#### **Борьба с Flakiness (Нестабильностью)**
Главный враг автоматизатора. Тест падает рандомно без изменения кода.
*   **Избегай жестких ожиданий (`sleep/wait`):** Никогда не пиши `cy.wait(5000)`. Это делает тесты медленными и ненадежными.
*   **Используй асинхронность правильно:** Жди появления элемента или завершения сетевого запроса (Cypress делает это автоматически, но важно понимать, *что именно* мы ждем).

---

### 4. Нюансы от Senior-а
*   **Data Management:** Не используй жестко зашитые данные (Hardcoded data) типа `user_123`. Если база данных очистится или изменится, тесты «посыпались». Используй динамическую генерацию данных (библиотеки типа *Faker*).
*   **Clean up (Уборка):** Если твой тест создал пользователя — постарайся его удалить (через `after` или фикстуры). Не оставляй мусор в базе, иначе со временем тесты начнут конфликтовать друг с другом.

---

### ❓ FAQ (Частые вопросы)

**В: Что делать, если тест слишком длинный и проверяет много всего?**
**О:** Разбей его. Длинные тесты сложно дебажить. Если один шаг упал, ты теряешь информацию о том, работали ли остальные шаги. Используй фикстуры для подготовки состояний.

**В: Можно ли использовать `cy.wait(number)`?**
**О:** В 99% случаев — нет. Это «антипаттерн». Если элемент не появился, лучше использовать проверку состояния (assertion), которая будет ждать появления элемента до истечения таймаута.

**В: Как понять, что тест покрывает достаточно?**
**О:** Ориентируйся на риск. Тестируй критические пути (Happy Path) и наиболее вероятные ошибки пользователя. Не пытайся достичь 100% покрытия всего кода — это пустая трата ресурсов.

**В: Почему важно, чтобы тесты были независимыми?**
**О:** Представь, что у тебя 500 тестов. Если тест №1 создает данные, которые нужны тесту №500, то при сбое теста №1 ты получишь «эффект домино» — упадут еще 499 тестов. Это кошмар для отладки.

# 🧠 Шпаргалка: Борьба с Flakiness (Нестабильными тестами)

**Flaky Test** — это тест, который при одном и том же коде и одной и той же среде может то проходить, то падать. Это «ложный сигнал», который подрывает доверие к CI/CD.

---

### 1. Основные причины (Root Causes)
Чтобы победить врага, нужно знать его в лицо. Все флейки делятся на три группы:

*   **Race Conditions (Состояние гонки):** Тест пытается взаимодействовать с объектом (кнопкой, API), который еще не готов/не загрузился. Код выполнился быстрее, чем UI обновился.
*   **Shared State (Загрязнение окружения):** Тесты зависят друг от друга. Тест №2 падает, потому что тест №1 не удалил созданного пользователя или не очистил кэш/базу.
*   **External Dependencies (Внешние факторы):** Зависимость от сторонних API, нестабильной сети, работы Docker-контейнеров или медленного железа в CI.
*   **Non-determinism (Недетерминизм):** Использование случайных чисел (`random`), текущего времени (`datetime.now()`) или данных, которые меняются со временем, без фиксации состояния.

---

### 2. Стратегии исправления (The Fixes)

#### 🚫 Антипаттерн: `time.sleep()`
**Никогда не используй фиксированные задержки.** Если ты ставишь `sleep(5)`, а сервер ответил за 6 секунд — тест упал. Если за 1 секунду — ты зря тратишь 4 секунды. Это делает пайплайн медленным и всё еще не гарантирует успех.

#### ✅ Решение №1: Smart Waits (Умные ожидания)
Используй **Polling** (опрос). Тест должен ждать не «5 секунд», а «появления конкретного условия» в течение таймаута.
*   *Принцип:* Проверяем условие каждые 100мс. Как только условие выполнено — идем дальше. Если не выполнено за 10с — падаем.

#### ✅ Решение №2: Изоляция и Clean Teardown
Каждый тест должен быть «островом».
*   Используй фикстуры с `scope="function"` для подготовки данных.
*   Всегда делай очистку (Cleanup) в блоке `yield` или `teardown`.
*   **Золотое правило:** Тест не должен знать о существовании других тестов.

#### ✅ Решение №3: Детерминизм данных
Если используешь генерацию данных, используй **Seed** (зерно).
*   Вместо просто `random.randint()`, используй `random.seed(42)`. Это сделает последовательность «случайных» чисел одинаковой при каждом запуске.

#### ✅ Решение №4: Мокирование (Mocking)
Если тест падает из-за того, что сторонний сервис (например, платежный шлюз) тормозит — **замокай его**. Тест должен проверщать твою логику, а не доступность чужого API.

---

### 3. Инструменты обнаружения и борьбы
*   **`pytest-rerunfailures`:** Плагин, который перезапускает упавшие тесты. 
    *   *Нюанс:* Это «пластырь», а не лечение. Если тест прошел со второго раза — **он всё равно Flaky**. Его нужно найти и починить, а не просто скрыть.
*   **Анализ логов и артефактов:** Всегда сохраняй скриншоты, видео и логи консоли при падении. Без них дебаг флейков превращается в гадание на кофейной гуще.
*   **Test Quarantine (Карантин):** Если тест стал нестабильным, выноси его из основного пайплайда в отдельный «песочный» запуск, чтобы он не блокировал релиз, пока ты его чинишь.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Что делать, если я вижу, что тест падает только в CI, но проходит локально?**
**О:** Это классический признак Race Condition или нехватки ресурсов. В CI окружение обычно слабее (меньше CPU/RAM), и процессы идут медленнее. Проверь использование `sleep` и замени их на умные ожидания. Также проверь, не зависит ли тест от локальных файлов или БД, которых нет в CI.

**В: Поможет ли добавление ретраев (retries) решить проблему Flakiness?**
**О:** Нет. Ретраи лишь маскируют симптомы. Если ты просто добавишь 3 попытки, ты уменьшишь количество алертов, но увеличишь время выполнения пайплайна и оставишь дыру в надежности. Решение — поиск первопричины (Root Cause Analysis).

**В: Как понять, что тест стал "флейки"?**
**О:** Нужно вести статистику. Если один и тот же тест падает в течение недели с разной периодичностью без изменений в коде — это флейк. Инструменты вроде Allure TestOps или кастомные дашборги в Grafana помогают это отслеживать.

# 🧠 Шпаргалка: Управление тестовыми данными (Test Data Management — TDM)

**Суть темы:** Тестовые данные — это топливо для твоих тестов. Если топливо грязное (непредсказуемое) или его мало (тесты падают из-за нехватки ресурсов), то даже самый идеальный код автотестов бесполезен.

---

### 1. Три уровня зрелости работы с данными

В зависимости от сложности проекта, мы используем разные подходы:

*   **Уровень «Новичок» (Hardcoded):** Данные зашиты прямо в коде теста (`const email = 'test@example.com'`).
    *   *Плюс:* Быстро и просто.
    *   *Минус:* При изменении требований нужно переписывать десятки тестов. Ужасно для поддержки.
*   **Уровень «Middle» (External Files):** Данные вынесены в `JSON`, `CSV` или `YAML`. Тест читает файл.
    *   *Плюс:* Легко менять данные, не трогая код. Можно использовать один файл для разных наборов тестов.
    *   *Минус:* Файлы могут стать огромными и трудночитаемыми. Данные «статичны» (они не меняются в процессе теста).
*   **Уровень «Senior» (Dynamic/API-driven):** Тест сам создает нужные данные перед началом выполнения через API или прямые запросы к БД, а после завершения — удаляет их.
    *   *Плюс:* Полная изоляция тестов. Каждый тест имеет свой уникальный "мир". Нет конфликтов между параллельными запусками.
    *   *Минус:* Требует написания сложной инфраструктуры (запросы к API, фабрики данных).

---

### 2. Основные стратегии генерации

1.  **Static Data (Золотой набор):** Набор заранее подготовленных данных в БД (например, пользователь "Admin", "User_1").
    *   *Нюанс:* Опасно! Если один тест изменит пароль у "Admin", все остальные тесты упадут.
2.  **Dynamic Generation (Faker/Factories):** Использование библиотек (типа `Faker.js`) для генерации случайных имен, email, адресов прямо в коде.
    *   *Нюанс:* Помогает избежать дублей, но может привести к трудновоспроизводимым багам (например, если Faker сгенерирует слишком длинное имя, которое не влезает в UI).
3.  **Data Seeding (Посев):** Использование API-запросов (`cy.request()` в Cypress) для создания нужного состояния системы перед тестом. Это "золотой стандарт".

---

### 3. Главные принципы (Senior Insights)

*   **Изоляция (Isolation):** Тест А не должен зависеть от того, что сделал Тест Б. Каждый тест должен приходить в «чистую» среду или создавать свою собственную.
*   **Атомарность:** Данные должны быть минимально необходимыми для теста. Не создавай "супер-пользователя с 100 заказами", если ты проверяешь только смену аватара.
*   **Cleanup (Очистка):** Всегда думай о том, как удалять данные. Замусоренная база данных — это путь к деградации производительности и ложным срабатываниям тестов.
*   **Traceability (Прослеживаемость):** Если тест упал, ты должен иметь возможность легко найти в БД именно тот объект, который использовался в тесте (используй уникальные префиксы, например `test_user_abc123`).

---

### 4. Тонкие нюансы и "грабли"

*   **PII (Personally Identifiable Information):** Никогда не используй реальные данные клиентов (email, телефоны) в автотестах. Это нарушение GDPR/безопасности. Только синтетика!
*   **Data Aging (Старение данных):** Если ты тестируешь подписку, твои данные должны иметь разные даты истечения. Проблема в том, что "завтра" наступит, и тесты, которые работали вчера, могут упасть сегодня. Решение — динамический расчет дат относительно `new Date()`.
*   **Race Conditions (Состояние гонки):** При параллельном запуске (Cypress Cloud или Jenkins с несколькими узлами) два теста не должны пытаться редактировать одного и того же пользователя.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что лучше: JSON-файл или API-запрос для создания юзера?**
**О:** Если это критически важный объект, от которого зависит весь сценарий — **API**. Это гарантирует, что юзер существует и он "свежий". JSON хорош только для констант (список стран, валют), которые не меняются.

**В: Как бороться с тем, что тесты оставляют за собой мусор в БД?**
**О:** Используй паттерн `Teardown`. В Cypress это может быть выполнение `cy.request('DELETE', ...)` в блоке `after()` или `afterEach()`. Если база позволяет, лучше всего откатывать транзакции или использовать временные схемы/контейнеры (Docker).

**В: Можно ли использовать Faker для всех полей?**
**О:** Можно, но осторожно. Для логики — да. Но для критических проверок (например, валидация формата почты) лучше контролировать часть данных вручную, чтобы не получить "случайный" провал теста из-за странного символа в сгенерированном имени.

# ⏳ Time Travel (Cypress)

**Time Travel** — это одна из самых мощных функций Cypress, которая превращает процесс отладки из «угадывания» в визуальное исследование. Это возможность буквально «перемотать» выполнение теста назад и увидеть, как выглядело ваше приложение в каждый конкретный момент выполнения команд.

### 🛠 Как это работает (Under the hood)
Cypress не просто записывает шаги, он делает **DOM Snapshots**. 
После каждой команды, которая изменяет состояние приложения (например, `.click()`, `.type()`, `.request()`), Cypress сохраняет текущее состояние DOM-дерева. Когда вы взаимодействуете с логом команд, Cypress подменяет текущий DOM в окне браузера на тот самый «снимок», сделанный в нужный момент.

### 🚀 Основные возможности

1.  **Hover (Наведение):** Наведите курсор на любую команду в **Command Log** (левая панель), и в основном окне вы увидите состояние приложения *сразу после* выполнения этой команды.
2.  **Click (Клик по команде):** Если кликнуть на команду, Cypress покажет детали:
    *   Какие элементы были найдены.
    *   Какие события произошли.
    *   **Console Logs:** В консоли браузера появятся логи, относящиеся именно к этому шагу (включая сетевые запросы).
3.  **Network Inspection:** Вы можете увидеть все XHR/Fetch запросы, которые были совершены в рамках конкретной команды. Это позволяет мгновенно понять: «Ага, кнопка не нажалась, потому что API вернул 500».

### 🧠 Senior Nuances (На что обратить внимание)

*   **DOM Snapshot $\neq$ Full App State:** Важно понимать, что Time Travel показывает **состояние DOM**, а не состояние JavaScript-объектов в памяти. Если вы изменили значение переменной внутри компонента, но это не отразилось на верстке — «перемотка» этого не покажет.
*   **Отладка Flaky-тестов:** Это главный инструмент для борьбы с «мигающими» тестами. Если тест падает на `assertion`, вы можете отмотать назад к шагу *перед* ассертом и увидеть, в какой момент элемент исчез или изменился.
*   **Производительность:** При очень длинных тестах (сотни команд) большое количество снимков может нагружать память браузера. 
*   **Связь с консолью:** Senior-разработчик всегда смотрит не только на визуальный снимок, но и в **Console** при клике на команду. Именно там «живут» ошибки сетевых запросов и логгирование, которые не видны на скриншоте.

### ❌ Ограничения
*   Снимки делают только те команды, которые влияют на DOM.
*   Если ваше приложение использует сложные анимации или Canvas (где нет классического DOM-дерева), Time Travel может быть менее информативным.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему при наведении на команду я вижу старую версию страницы?**
**О:** Вы видите состояние *после* выполнения команды. Если вы хотите увидеть, что было *до* клика, вам нужно навести на предыдущую команду в списке.

**В: Поможет ли Time Travel увидеть ошибку в логике API, если визуально всё ок?**
**О:** Да, но только если вы кликнете на команду (например, `cy.request` или `intercept`) и проверите вкладку **Network** в консоли разработчика. Визуальный снимок DOM может не показать тело ответа сервера.

**В: Можно ли использовать Time Travel для автоматического создания скриншотов?**
**О:** Технически — это разные механизмы. Скриншоты (`cy.screenshot()`) — это статические изображения, а Time Travel — это интерактивные DOM-снимки. Но Time Travel — это ваш «живой» инструмент для ручного исследования во время разработки теста.

# 🛠 Инструменты разработчика в Pytest

Когда тесты начинают падать или работать медленно, тебе нужны «глаза» и «уши». Инструменты разработчика — это всё, что помогает заглянуть внутрь процесса выполнения теста, увидеть состояние переменных и понять, где именно произошел сбой.

### 1. CLI Флаги: Твой первичный набор выживания
Запуск тестов через терминал — это база. Но просто `pytest` недостаточно. Тебе нужны флаги управления выводом:

*   `-v` (`--verbose`): **Режим подробности**. Показывает названия каждого теста, а не просто точки. Без него в больших проектах ты не поймешь, какой именно тест упал.
*   `-s` (`--no-capture`): **Разблокировка `print()`**. По умолчанию Pytest перехватывает всё, что выводится в консоль (stdout/stderr), чтобы не засорять отчет. Если ты поставил `print("DEBUG: variable = x")`, ты его не увидишь без этого флага. *Важно: используй только при локальной отладке!*
*   `-x` (`--exitfirst`): **Стоп-кран**. Останавливает выполнение всей сессии сразу после первой ошибки. Незаменимо, когда у тебя 1000 тестов и ты не хочешь ждать завершения всех упавших, чтобы поправить один конкретный.
*   `-k <pattern>`: **Таргетированный удар**. Позволяет запустить только те тесты, чье имя совпадает с паттерном (например, `pytest -k "login"`).
*   `--durations=n`: **Поиск «тормозов»**. Выводит топ-n самых долгих тестов. Если твоя CI/CD пайплайн ползет как улитка — это твой первый шаг к оптимизации.

### 2. Дебаггинг (Debugging): Хирургическое вмешательство
Когда `print` уже не помогает, пора использовать отладчик.

*   **`breakpoint()`**: Встроенная функция Python (начиная с 3.7). Вставь её в любое место кода. При запуске теста выполнение остановится, и ты попадешь в интерактивную консоль (PDB).
    *   *Что можно делать внутри:* смотреть значения переменных (`p my_var`), идти по шагам (`n` — next, `s` — step into), смотреть стек вызовов (`w` — where).
*   **IDE Debugger (PyCharm / VS Code)**: Самый комфортный способ. Ты расставляешь красные точки (breakpoints) мышкой, нажимаешь «Debug» и визуально видишь состояние всей программы в реальном времени. 
    *   *Senior Tip:* Настрой конфигурацию запуска Pytest в IDE, чтобы дебаггер подхватывал твои фикстуры и аргументы командной строки.

### 3. Мониторинг покрытия (Coverage)
Инструмент: `pytest-cov`.
Он показывает, какие строки твоего кода были задействованы во время тестов, а какие — «мертвый груз». 
*   **Зачем:** Если покрытие 20%, ты не тестировщик, а создатель иллюзии безопасности. Тебе нужно видеть «дыры» в тестах.

### 4. Визуализация результатов (Reporting)
Когда нужно показать результат не себе, а менеджеру или коллегам:
*   **`pytest-html`**: Генерирует один красивый HTML-файл со списком всех тестов и ошибками.
*   **Allure Report**: Король отчетности. Он умеет прикреплять скриншоты, логи, видео и строить красивые графики трендов. Это стандарт индустрии для серьезных проектов.

---

### 💡 Нюансы от Senior-а (Pro Tips)

1.  **Не оставляй `breakpoint()` в коде!** Если ты замерджишь код с дебаггером в общую ветку, твоя CI/CD pipeline «зависнет» навсегда, ожидая, пока кто-то нажмет кнопку в консоли сервера.
2.  **`print` vs `logging`**: Для быстрой проверки — `print`. Для серьезного проекта — используй модуль `logging`. Логи можно настроить так, чтобы они писались в файл, имели уровни (INFO, ERROR, DEBUG) и не забивали консоль при каждом запуске.
3.  **Опасность `-s` в CI**: Никогда не включай флаг `-s` в настройках Jenkins/GitLab. Если тестов тысячи, огромные дампы логов с принтами могут «раздуть» размер лог-файла до гигабайт и уронить сервер сборки.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Я добавил `print("Hello")` в тест, но в терминале пусто. Почему?**
**О:** Pytest перехватывает стандартный вывод. Используй флаг `-s`, чтобы увидеть свои принты.

**В: Как быстро найти, какой тест тормозит всю сборку?**
**О:** Запусти тесты с флагом `--durations=5`. Pytest покажет 5 самых медленных тестов в конце выполнения.

**В: Что лучше: `pdb` или дебаггер в PyCharm?**
**О:** Если нужно быстро проверить значение переменной «на лету» — `breakpoint()`. Если нужно изучить сложную логику с переходом по методам и просмотром переменных в таблице — IDE Debugger.

**В: Могу ли я запустить только один конкретный тест из файла?**
**О:** Да, просто укажи путь к файлу и имя теста через `-k`: `pytest tests/test_auth.py -k "test_login_success"`.

# 📸 Шпаргалка: Скриншоты и Видео в Cypress

В автоматизации скриншоты и видео — это твои главные «улики» (evidence). Без них при падении теста в CI/CD ты видишь только текст ошибки, но не видишь, что реально происходило на экране.

## 1. Скриншоты (Screenshots)

### Автоматические скриншоты
По умолчанию Cypress настроен так: **если тест падает, он сам делает скриншот**. Тебе не нужно писать лишний код.
*   **Где искать:** `cypress/screenshots`.
*   **Нюанс:** Скриншот делается в момент возникновения ошибки (assertion failure). Если ошибка произошла внутри `cy.wait()`, скриншот может зафиксировать состояние чуть позже, чем нужно.

### Ручные скриншоты (`cy.screenshot()`)
Используются для визуальной проверки ключевых этапов или создания документации.

*   **Базовое использование:**
    ```javascript
    cy.screenshot('step-name'); // Создаст файл step-name.png
    ```
*   **Скриншот конкретного элемента:**
    Полезно, если нужно проверить только попап или карточку товара, не захватывая весь экран.
    ```javascript
    cy.get('.modal-content').screenshot('modal-only');
    ```
*   **Настройка параметров:**
    Можно передать объект с настройками (например, изменить формат или размер).
    ```javascript
    cy.screenshot('custom-shot', { capture: 'viewport' }); // 'viewport' (стандарт) или 'fullPage'
    ```

### 💡 Senior Tips (Нюансы):
1.  **`fullPage: true` — коварная штука.** Скриншот всей страницы может работать медленно и иногда некорректно «склеивать» части страницы, если есть сложные CSS-эффекты или фиксированные хедеры. Используй осторожно.

## 2. Видео (Video Recording)

Видео — это «черный ящик» твоего теста. Оно бесценно для отладки сложных флоу (например, когда анимация ломает клик).

### Как это работает
*   **`cypress run` (Headless mode):** Видео записывается **автоматически**. Это происходит только при запуске тестов в консоли (в CI/CD или терминале).
*   **`cypress open` (GUI mode):** Видео **не записывается**. В режиме разработчика это экономит ресурсы и время.

### Конфигурация (`cypress.config.js`)
Управление видео происходит через конфиг:

```javascript
const { defineConfig } = require("cypress");

module.exports = defineConfig({
  e2e: {
    video: true, // Включить/выключить запись (по умолчанию true)
    videoCompression: 32, // Качество (0-51). Чем меньше число, тем выше качество и больше вес файла.
    // По умолчанию стоит 32 — золотая середина.
  },
});
```

### 💡 Senior Tips (Нюансы):
1.  **Производительность в CI.** Запись видео — тяжелая операция для процессора. Если твои тесты и так идут долго, запись видео может замедлить выполнение еще на 20-30%. В очень нагруженных проектах `video: false` — нормальная практика, если есть скриншоты.
2.  **Docker & Linux.** При запуске в Docker (например, в Jenkins или GitLab) иногда возникают проблемы с записью видео из-за отсутствия нужных библиотек для кодирования (ffmpeg). Если видео не создается — проверяй наличие `ffmpeg` в образе.
3.  **Артефакты.** Не забывай настраивать свой CI/CD пайплайн так, чтобы папка `cypress/videos` сохранялась как **Artifact**. Иначе после завершения работы раннера видео просто исчезнет.

# 🐳 Тема: Запуск тестов в Docker

### 🎯 Зачем это нужно? (The Why)
Главная проблема автоматизации — фраза *"На моей машине всё работает"*. Docker решает проблему окружения. Мы упаковываем код, зависимости, интерпретатор и системные библиотеки в один неизменяемый образ. Это гарантирует, что тесты пройдут одинаково и на твоем ноутбуке, и в Jenkins/GitHub Actions.

---

### 🛠 1. Подход через Dockerfile (Создание образа)
Мы создаем "слепок" нашего тестового окружения.

**Пример базового `Dockerfile`:**
```dockerfile
# 1. Выбираем легкий образ с Python
FROM python:3.10-slim

# 2. Устанавливаем рабочую директорию внутри контейнера
WORKDIR /tests

# 3. Копируем только файлы зависимостей (это важно для кэширования!)
COPY requirements.txt .

# 4. Устанавливаем зависимости
RUN pip install --no-cache-dir -r requirements.txt

# 5. Копируем весь остальной код тестов в контейнер
COPY . .

# 6. Команда, которая запустится при старте контейнера
CMD ["pytest"]
```

**Senior Tip (Нюанс про кэширование):** Всегда копируй `requirements.txt` и делай `pip install` **ДО** того, как скопируешь весь код (`COPY . .`). Если ты изменишь только один тест, Docker не будет переустанавливать все библиотеки заново, а возьмет готовый слой из кэша. Это экономит минуты при каждой сборке.

---

### 🚀 2. Подход через Docker Compose (Интеграционные тесты)
Если твоим тестам нужна база данных (PostgreSQL), Redis или API-сервис, использовать один Dockerfile мало. Тебе нужен `docker-compose`.

**Пример `docker-compose.yml`:**
```yaml
version: '3.8'

services:
  # Наш сервис с тестами
  test_runner:
    build: .
    volumes:
      - .:/tests  # Монтируем текущую папку, чтобы не пересобирать образ при каждом изменении кода
    environment:
      - DATABASE_URL=postgresql://user:pass@db:5432/test_db
    depends_on:
      - db

  # База данных для тестов
  db:
    image: postgres:13
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: test_db
    ports:
      - "5432:5432"
```

**Senior Tip (Нюанс про Volumes):** В режиме разработки используй `volumes: - .:/tests`. Это позволяет тебе менять код теста на хосте, и изменения мгновенно подхватятся внутри контейнера без пересборки образа. Но **никогда** не делай так в CI/CD — там образ должен быть самодостаточным.

---

### ⚠️ 3. Важные нюансы (The Gotchas)

1.  **`.dockerignore` — это маст-хэв.**
    Создай файл `.dockerignore` рядом с Dockerfile. Добавь туда `__pycache__`, `.venv`, `.git`, `.pytest_cache`. Если ты скопируешь папку `.venv` со своего компьютера в контейнер, возникнет конфликт архитектур (например, если у тебя Mac, а контейнер на Linux), и тесты упадут.
2.  **Exit Codes (Коды завершения).**
    Docker передает код выхода процесса `CMD` наружу. Если PyTest упал, он вернет ненулевой код. Это критично для CI/CD: именно по этому коду Jenkins понимает, что билд "красный".
3.  **Сетевое взаимодействие.**
    Внутри Docker-сети контейнеры видят друг друга по **именам сервисов**. Если твой сервис в compose называется `db`, то в коде тестов адрес базы будет не `localhost:5432`, а `db:5432`.

---

### ❓ FAQ (Частые вопросы)

**В: Как посмотреть логи тестов, если контейнер упал сразу после запуска?**
**О:** Используй команду `docker logs <container_id>`. Также можно запустить контейнер в интерактивном режиме с переопределением команды: `docker run -it <image_name> /bin/bash`, чтобы "зайти" внутрь и потыкать команды руками.

**В: Как прокинуть переменные окружения (например, API_KEY) без пересборки образа?**
**О:** Используй флаг `-e` при запуске `docker run -e API_KEY=secret ...` или секцию `environment` в `docker-compose.yml`.

**В: Почему мои тесты не видят базу данных, хотя она запущена в Compose?**
**О:** Проверь `depends_on`. База может запуститься, но процесс PostgreSQL еще будет инициализироваться (создавать таблицы), а PyTest уже начнет стучаться. В идеале используй скрипт "wait-for-it", который ждет доступности порта базы перед запуском тестов.

# 🚀 Шпаргалка: Интеграция PyTest с GitHub Actions

**GitHub Actions (GHA)** — это инструмент автоматизации (CI/CD). В контексте тестирования его задача: при каждом пуше или Pull Request автоматически поднимать виртуальную машину, устанавливать зависимости, запускать твои тесты и сообщать результат.

### 🏗 Основные понятия
* **Workflow (Воркфлоу)** — весь процесс целиком (описан в `.yml` файле).
* **Event (Событие)** — триггер, который запускает workflow (например, `push` или `pull_request`).
* **Job (Работа)** — группа шагов. По умолчанию все джобы в одном workflow запускаются параллельно.
* **Step (Шаг)** — отдельная команда (скрипт или готовое Action).
* **Runner (Раннер)** — сервер (виртуалка), на котором крутятся тесты (чаще всего `ubuntu-latest`).

---

### 🛠 Анатомия идеального Workflow (`.github/workflows/tests.yml`)

Вот «золотой стандарт» конфига для Python-проекта:

```yaml
name: PyTest Suite # Имя, которое ты увидике в интерфейсе GitHub

on:
  push:
    branches: [ main, develop ] # Запуск при пуше в эти ветки
  pull_request:
    branches: [ main ]         # Запуск при создании PR в main
  workflow_dispatch:           # Позволяет запустить тест вручную кнопкой

jobs:
  test:
    runs-on: ubuntu-latest      # Используем последнюю версию Linux
    
    strategy:
      matrix:                   # МАГИЯ: Запуск тестов на разных версиях Python одновременно
        python-version: ["3.9", "3.10", "3.11"]

    steps:
      - name: Checkout code
        uses: actions/checkout@v4 # Шаг 1: Копируем код репозитория в раннер

      - name: Set up Python ${{ matrix.python-version }}
        uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
          cache: 'pip'           # КРИТИЧНО: Включает кэширование зависимостей (ускоряет CI)

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          if [ -f requirements.txt ]; then pip install -r requirements.txt; fi
          pip install pytest pytest-cov # Установка доп. инструментов

      - name: Run PyTest
        run: |
          pytest --doctest-modules --junitxml=reports/result.xml --cov=src/

      - name: Upload Test Report
        if: always()               # ВАЖНО: Запускать даже если тесты упали!
        uses: actions/upload-artifact@v4
        with:
          name: pytest-report
          path: reports/
```

---

### 💡 Senior Tips (Нюансы и "подводные камни")

1.  **Кэширование (`cache: 'pip'`)**: Если не использовать кэш, GitHub будет скачивать все библиотеки заново при каждом запуске. Это тратит время и деньги. Всегда включай `cache`.
2.  **`if: always()`**: По умолчанию, если шаг с тестами упал (тесты не прошли), все последующие шаги пропускаются. Если ты хочешь сохранить отчет об ошибках (артефакт), обязательно добавь `if: always()`. Без этого ты увидишь "красный крестик", но не увидишь логов, почему именно всё упало.
3.  **Matrix Strategy**: Не тестируй только на одной версии Python. Твой код может работать на 3.11, но сломаться на 3.9 из-за устаревшего синтаксиса или библиотек. Матрица — это дешевый способ обеспечить совместимость.
4.  **Secrets (Секреты)**: Никогда не храни API-ключи в коде или в `.yml`. Используй `Settings -> Secrets and variables -> Actions` в GitHub. В коде вызывай их так: `${{ secrets.MY_API_KEY }}`.
5.  **Artifacts (Артефакты)**: Результаты тестов живут только пока живет раннер. Чтобы "забрать" HTML-отчет или JUnit XML себе на компьютер, используй `actions/upload-artifact`.

### ❓ FAQ (Частые вопросы)

**В: Почему мои тесты запускаются очень долго?**
**О:** Скорее всего, ты не настроил кэширование зависимостей и каждый раз пересобираешь окружение с нуля. Проверь наличие `cache: 'pip'` в `setup-python`. Также проверь, не слишком ли огромная у тебя матрица (много версий Python одновременно).

# 🚀 Шпаргалка: Параллелизация тестов в PyTest

### 💡 Суть темы
Параллелизация — это запуск нескольких тестовых сессий одновременно на разных ядрах процессора (или даже на разных машинах). 
**Главная цель:** Сократить время прохождения Pipeline (CI/CD) с часов до минут.

### 🛠 Основной инструмент: `pytest-xdist`
Стандартный PyTest выполняет тесты последовательно (один за другим). Чтобы включить параллелизм, используется плагин `pytest-xdist`.

**Базовые команды:**
* `pytest -n 4` — запуск в 4 потока (воркера).
* `pytest -n auto` — PyTest сам определит количество ядер процессора и запустит оптимальное число воркеров.

---

### ⚠️ Главные «подводные камни» (Нюансы Senior-уровня)

Параллелизация — это не просто флаг в консоли. Это изменение архитектуры тестов. Если твои тесты не изолированы, параллельный запуск их «убьёт».

#### 1. Состояние гонки (Race Condition) и общие ресурсы
Это самая частая проблема. Если два теста одновременно пытаются:
* Удалить одного и того же пользователя в БД.
* Записать данные в один и тотный файл.
* Изменить одну и ту же глобальную переменную.
**Результат:** Недетерминированные ошибки (Flaky tests), которые то проходят, то падают.

#### 2. Проблема Scope фикстур (`session` scope)
Когда ты используешь `-n auto`, PyTest создает несколько **отдельных процессов** (воркеров). 
* Фикстуры с уровнем `function` и `class` работают предсказуемо.
* Но фикстура с уровнем `session` **выполняется отдельно для каждого воркера**. 
* *Нюанс:* Если твоя `session`-фикстура поднимает Docker-контейнер с БД, то при `-n 4` ты попытаешься поднять 4 контейнера на одном порту. Это вызовет конфликт.

#### 3. Изоляция данных (Database Isolation)
Чтобы тесты не мешали друг другу, каждый воркер должен работать со своей «песочницей».
**Решение:** Использование `worker_id`. Плагин `xdist` передает каждому воркеру уникальный ID (`gw0`, `gw1` и т.д.). Ты можешь использовать этот ID, чтобы создавать разные базы данных или префиксы в именах пользователей.

---

### 🏗 Best Practices (Как делать правильно)

1.  **Принцип Idempotency (Идемпотентность):** Каждый тест должен оставлять систему в том же состоянии, в котором она была до него, ИЛИ быть полностью независимым от состояния системы.
2.  **Использование `worker_id` для динамических ресурсов:**
    ```python
    @pytest.fixture(scope="session")
    def db_engine(worker_id):
        # Создаем уникальную БД для каждого воркера
        db_name = f"test_db_{worker_id}"
        return setup_database(db_name)
    ```
3.  **Сначала почини последовательный запуск:** Никогда не включай параллелизацию, пока твои тесты не проходят стабильно в один поток. Если они падают по очереди — параллелизм только усложнит отладку.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Что делать, если тесты падают только при запуске `-n auto`?**
**О:** Ищи «загрязнение» ресурсов. Скорее всего, два теста обращаются к одному и тому же объекту в БД или файловой системе. Проверь использование `session`-фикстур и наличие глобального состояния.

**В: Можно ли запускать тесты на разных машинах через `xdist`?**
**О:** Да, `xdist` поддерживает работу по SSH (через `execremote`), но в современном мире для этого чаще используют оркестрацию в CI/CD (например, разделение задач на разные Job в GitLab CI или GitHub Actions).

**В: Как ограничить запуск тяжелых тестов в параллельном режиме?**
**О:** Можно использовать маркеры. Сначала запускай тяжелые/критичные тесты последовательно, а затем запускай остальную массу через `-n auto`. Или используй логику внутри фикстур, которая проверяет наличие `worker_id`.

**В: Сколько воркеров ставить? Больше — значит быстрее?**
**О:** Нет. Каждый воркер — это отдельный процесс со своим потреблением RAM и CPU. Если ты выделишь 16 воркеров на 4-ядерном процессоре, возникнет огромная нагрузка на переключение контекста (context switching), и тесты начнут идти **медленнее**. Оптимально: количество ядер или `ядра - 1`.

# 📊 Тема: Отчетность (Reporting)

В автоматизации отчетность — это не просто "прошел/не прошел". Это инструмент **диагностики**. Хороший отчет должен отвечать на три вопроса:
1. Что именно сломалось?
2. Почему это сломалось? (лог, скриншот, traceback)
3. Насколько критичен этот сбой?

### 1. Уровень "Junior": Консольный вывод (Standard Output)
Самый базовый способ. Ты запускаешь тесты и видишь точки (`.`), ошибки (`F`) или пропуски (`s`) в терминале.

*   **`pytest -v` (Verbose):** Показывает названия тестов вместо точек. Маст-хэв для локального запуска.
*   **`pytest -s`:** Позволяет видеть `print()` внутри тестов. 
    *   *Нюанс:* В CI/CD (Jenkins/GitLab) злоупотребление `-s` может раздуть логи сервера до гигабайт. Используй только при отладке.
*   **`--tb=short/long/auto`:** Управление глубиной Traceback (отчета об ошибке). `short` — только суть, `long` — всё дерево вызовов.

### 2. Уровень "Middle": HTML-отчеты (`pytest-html`)
Когда нужно отправить результат коллегам в виде одного файла, который можно открыть в браузере.

*   **Как работает:** Плагин генерирует один `.html` файл со списком тестов, временем выполнения и ошибками.
*   **Главная фишка (Attachments):** Senior-подход заключается не просто в запуске отчета, а в **прикреплении артефактов**. Если тест упал — отчет должен содержать скриншот или лог.
    *   *Как реализовать:* Через хук `pytest_runtest_makereport` в `conftest.py`, чтобы автоматически "подклеивать" скриншоты к HTML-отчету при падении теста.
*   **Минус:** Сложно анализировать историю изменений (тренд) и неудобно смотреть, если тестов тысячи.

### 3. Уровень "Senior": Allure Framework
Это стандарт индустрии для серьезных проектов. Это не просто отчет, это полноценная интерактивная аналитика.

*   **Возможности:**
    *   **Steps (Шаги):** Использование аннотации `@allure.step` превращает тест из "черного ящика" в понятную инструкцию: "Нажал кнопку", "Ввел логин".
    *   **Attachments:** Легкое прикрепление скриншотов, JSON-ответов API, логов сервера.
    *   **Behaviors:** Группировка тестов по фичам (User Stories).
    *   **Severity/Retries:** Пометка критичности теста и отслеживание того, сколько раз тест перепускался перед тем, как пройти.
*   **Нюанс:** Allure требует двух этапов: 1) Генерация сырых данных (`allure generate`) и 2) Запуск веб-сервера для просмотра (`allure serve`). В CI/CD нужно настраивать сохранение именно "сырых" результатов (allure-results), чтобы потом их можно было историзировать.

### 4. Уровень "Architect": Code Coverage (Покрытие кода)
Отчетность о том, **насколько хорошо мы протестировали код**. Используем `pytest-cov`.

*   **Зачем:** Чтобы видеть "белые пятна" — функции или методы, которые вообще не затрагивались тестами.
*   **Метрики:** Процент покрытия строк (Line coverage) и веток (Branch coverage).
*   **Нюанс:** 100% покрытие $\neq$ отсутствие багов. Это лишь показатель того, что код был *выполнен* во время теста.

### 5. Интеграция с CI/CD (JUnit XML)
Для систем вроде Jenkins, GitLab CI или Azure DevOps отчеты в HTML бесполезны для автоматики. Им нужен **XML**.

*   **`--junitxml=report.xml`:** Генерирует стандартный формат, который понимают все CI-системы. Именно на основе этого файла Jenkins рисует свои красивые графики "Pass/Fail" на главной странице билда.

### ❓ FAQ (Частые вопросы)

**В: Почему мой Allure отчет пустой, хотя тесты прошли?**
**О:** Скорее всего, ты смотришь на папку `allure-results`, а не на сгенерированный отчет. Тебе нужно запустить команду `allure serve allure-results`. Также проверь, что плагин `allure-pytest` установлен и корректно работает.

**В: Можно ли прикрепить скриншот к HTML-отчету автоматически?**
**О:** Да, но "из коробки" `pytest-html` это делает плохо. Тебе нужно написать небольшой хук в `conftest.py`, который будет перехватывать статус `Failed` и записывать путь к файлу в отчет.

**В: Что важнее: Coverage или Allure?**
**О:** Это разные вещи. Allure говорит: *"Что произошло с тестами"*. Coverage говорит: *"Чего не хватает в тестах"*. В идеальном проекте должны быть оба.

**В: Как сделать так, чтобы отчеты не пропадали после завершения работы Jenkins?**
**О:** Нужно настроить **Artifacts** (Артефакты) в настройках твоего Pipeline. Укажи путь к папке с результатами (например, `allure-results/`), и Jenkins сохранит их внутри билда навсегда.
