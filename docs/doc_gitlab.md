# 🧠 Шпаргалка: Git Essentials

Git — это **распределенная** система контроля версий. Это значит, что у каждого разработчика на компьютере хранится полная копия всей истории проекта, а не только текущий слепок файлов.

## 🏗 1. Ментальная модель (Три состояния)
Прежде чем писать команды, запомни, где находятся твои файлы. Это ключ к пониманию Git:
1.  **Working Directory** (Рабочая директория): Файлы, которые ты сейчас редактируешь в IDE.
2.  **Staging Area / Index** (Область подготовки): «Черновик» следующего коммита. Сюда попадают файлы после `git add`.
3.  **Local Repository** (Локальный репозиторий): База данных Git на твоем ПК, где хранятся уже зафиксированные изменения (`git commit`).
4.  **Remote Repository** (Удаленный репозиторий): Копия проекта на сервере (GitLab), с которой ты синхронизируешься (`push`/`pull`).

---

## 🚀 2. Начало работы
*   `git init` — превращает текущую папку в Git-репозиторий. Создает скрытую папку `.git`.
*   `git clone <url>` — копирует существующий удаленный репозиторий к тебе на компьютер.

## 📝 3. Ежедневный цикл (Workflow)
1.  `git status` — **Твой лучший друг.** Всегда запускай её, чтобы понять, что происходит: какие файлы изменены, а какие в индексе.
2.  `git add <file>` — переносит файл из Working Directory в Staging Area.
    *   `git add .` — добавить вообще всё (будь осторожен!).
3.  `git commit -m "feat: add login logic"` — делает «снимок» состояния индекса и сохраняет его в локальную историю.
    *   *Senior Tip:* Пиши осмысленные сообщения. Используй префиксы (`feat:`, `fix:`, `docs:`, `refactor:`). Это стандарт индустрии (Conventional Commits).

## 🔄 4. Синхронизация с удаленным сервером
*   `git fetch` — «Сходи на сервер и посмотри, что там нового, но ничего не меняй у себя». Просто обновляет информацию о ветках.
*   `git pull` — `fetch` + `merge`. Скачивает изменения и сразу пытается влить их в твою текумущую ветку.
    *   ⚠️ **Нюанс:** Если ты и твой коллега правили одну и ту же строку, после `pull` возникнет **конфликт**.
*   `git push` — отправляет твои локальные коммиты на сервер GitLab.

## 🌿 5. Ветвление (Branching) — Сердце Git
Ветки позволяют работать над фичами изолированно от основного кода (`main/master`).
*   `git branch <name>` — создает новую ветку.
*   `git switch <name>` (или старый `git checkout <name>`) — переключает тебя на указанную ветку.
*   `git switch -c <name>` — создать новую ветку и сразу на неё перейти (комбо).
*   `git merge <feature-branch>` — вливает изменения из `feature-branch` в твою текущую ветку.

---

## 🛠 6. Продвинутые инструменты (Senior level)
*   **`git rebase`**: Вместо обычного слияния (`merge`), `rebase` берет твои коммиты и «переписывает» их поверх последних коммитов целевой ветки. Это делает историю линейной и красивой.
    *   ⚠️ **Золотое правило:** Никогда не делай `rebase` веток, которые уже запушены в общий репозиторий (public branches). Ты перепишешь историю, и у коллег всё сломается.
*   **`git cherry-pick <commit-hash>`**: Позволяет «выдернуть» один конкретный коммит из другой ветки и применить его к твоей текущей. Полезно, если тебе нужен только один фикс из огромной ветки с фичами.
*   **`git stash`**: "Карман" для временного хранения. Если ты работаешь над задачей, но нужно срочно переключиться на другой баг, не делая «грязный» коммит:
    1. `git stash` — прячет текущие изменения в карман.
    2. Делаешь другие задачи...
    3. `git stash pop` — достает изменения обратно и применяет их.

## 🆘 7. Как всё исправить (Undo)
*   `git checkout -- <file>` — отменить изменения в файле (вернуть к состоянию последнего коммита).
*   `git reset --soft HEAD~1` — отменить последний коммит, но **оставить** все изменения в файлах (они снова будут в Staging Area). Идеально, если забыл что-то добавить.
*   `git reset --hard HEAD~1` — **ОПАСНО.** Удаляет последний коммит и **навсегда** стирает все изменения в файлах.
*   `git revert <commit-hash>` — создает *новый* коммит, который делает всё ровно наоборот тому, что сделал указанный коммит. Это безопасный способ отката в публичных ветках.

## ❓ FAQ (Частые вопросы)

**В: Чем `git fetch` отличается от `git pull`?**
**О:** `fetch` — это просто "посмотреть". Он не трогает твой код. `pull` — это "скачать и попытаться склеить". Если ты боишься конфликтов, делай сначала `fetch`, а потом сам решай, как мержить.

**В: Что такое Merge Conflict и как с ним жить?**
**О:** Это ситуация, когда Git не знает, какую строку оставить (твою или коллеги). Тебе нужно открыть файл, увидеть маркеры (`<<<<<<<`, `=======`, `>>>>>>>`), вручную выбрать правильный код, сохранить файл, сделать `git add` и завершить коммит.

**В: Зачем нужен `.gitignore`?**
**О:** Чтобы не засорять репозиторий мусором: логами, временными файлами IDE, папками зависимостей (`node_modules`) и секретами (паролями). Если файл попал в Git, простое добавление его в `.gitignore` не удалит его из истории.

**В: Что лучше: `merge` или `rebase`?**
**О:** Зависит от политики команды. `merge` — честный и сохраняет историю как она была (со всеми переплетениями). `rebase` — делает историю чистой, прямой линией, но «лжет» о том, когда именно были написаны коммиты. В больших проектах часто требуют `rebase` для чистоты истории перед Merge Request.

# 🧠 Шпаргалка: Структура GitLab (Hierarchy & Organization)

Если вкратце: GitLab — это не просто набор репозиториев, это **иерархическая система контейнеров**. Главный принцип здесь — **наследование**. Всё, что ты настроил наверху, «стекает» вниз.

### 1. Уровни иерархии (Top-Down)

В GitLab всё строится по принципу матрешки:
`User` $\rightarrow$ `Group` $\rightarrow$ `Subgroup` $\rightarrow$ `Project`.

#### **A. User (Пользователь)**
Это конечная точка. У пользователя есть личные репозитории (Personal Projects), но в корпоративной среде мы работаем через группы.

#### **B. Group & Subgroup (Группы и Подгруппы)**
Это логические контейнеры для организации работы.
*   **Зачем нужны:** Чтобы объединять команды, отделы или микросервисы.
*   **Subgroups:** Ты можешь создавать бесконечную вложенность (например: `Company` $\rightarrow$ `Backend-Team` $\rightarrow$ `Payment-Service`).
*   **Главная фишка — Наследование прав:** Если ты добавил разработчика в группу `Backend-Team` с ролью *Developer*, он автоматически станет *Developer* во всех подгруппах и проектах внутри этой ветки.

#### **C. Project (Проект)**
Это «атом» GitLab. Это не просто Git-репозиторий, это комплексная единица, которая включает в себя:
*   **Git Repository:** Сам код.
*   **Issue Tracker:** Задачи и баги.
*   **Merge Requests:** Процесс ревью.
*   **CI/CD Pipelines:** Автоматизация.
*   **Container/Package Registry:** Хранение образов и артефактов.
*   **Wiki & Pages:** Документация.

---

### 2. Visibility Levels (Уровни видимости)

На каждом уровне (Group или Project) ты определяешь, кто может видеть контент:

1.  **Private:** Видят только те, кому явно дали доступ (или кто унаследовал его от группы).
2.  **Internal:** Видят **все**, у кого есть аккаунт в *вашем* экземпляре GitLab. (Очень удобно для обмена кодом между разными командами внутри одной компании).
3.  **Public:** Видит весь интернет (используется для Open Source проектов).

> **⚠️ Важный нюанс (Senior Tip):** Ты не можешь сделать подгруппу «более публичной», чем её родительская группа. Если родительская группа `Private`, то любая подгруппа внутри неё автоматически будет `Private`, даже если ты попытаешься выставить ей `Public`.

---

### 3. Namespace (Пространство имен)

В GitLab путь к проекту — это его **Namespace**.
Пример: `gitlab.com/my-org/dev-team/api-service`
*   `my-org` — Top-level group.
*   `dev-team` — Subgroup.
*   `api-service` — Project.

Это критически важно для настройки CI/CD переменных и прав доступа: ты можешь задать переменную на уровне `dev-team`, и она будет доступна во всех проектах внутри этой папки.

---

### ⚡️ Резюме для быстрого запоминания

| Объект | Что это? | Главная функция |
| :--- | :--- | :--- |
| **Group** | Папка для команд | Управление доступом и общими настройками (Variables, Runners). |
| **Subgroup** | Вложенная папка | Структурирование сложных систем (например, по микросервисам). |
| **Project** | Рабочая единица | Хранение кода, задач, пайплайнов и реестров. |
| **Inheritance** | Наследование | Права и переменные текут сверху вниз (от Group к Project). |

---

### ❓ FAQ (Частые вопросы)

**В: В чем разница между Group и Project?**
**О:** Группа — это контейнер для организации людей и прав. Проект — это место, где живет код и процессы. Ты не можешь «запушить» код в группу, только в проект.

**В: Если я удалю группу, что произойдет с проектами внутри неё?**
**О:** (Senior Warning!) Все проекты, подгруппы и данные внутри этой группы будут **безвозвратно удалены**. Удаление группы — это ядерный удар по всей ветке иерархии.

**В: Можно ли переместить проект из одной группы в другую?**
**О:** Да, через настройки проекта (Transfer Project). Но помни: изменится его `Namespace` (URL), и все старые ссылки на репозиторий или CI/CD переменные, привязанные к старому пути, могут сломаться.

**В: Как лучше всего организовать структуру для 100 микросервисов?**
**О:** Не создавай 100 проектов в одной куче. Создай группы по доменам (например, `billing`, `auth`, `shipping`). Внутри каждой группы — свои подгруппы или проекты. Это позволит тебе управлять правами доступа (например, дать доступ к `billing` только финансовому отделу), не затрагивая остальные части системы.

# 🔐 Шпаргалка: Управление доступом (IAM) в GitLab

**IAM (Identity and Access Management)** в GitLab — это не только про «кто может нажать кнопку Merge». Это про иерархию, наследование прав и соблюдение принципа **Least Privilege** (минимально необходимых прав).

---

### 1. Иерархия объектов: Фундамент доступа
В GitLab доступ всегда строится сверху вниз. Понимание этой структуры критично, чтобы не наплодить лишних доступов.

*   **Instance (Уровень сервера):** Глобальные настройки (для тех, кто админит свой GitLab).
*   **Groups & Subgroups:** Контейнеры для проектов. Здесь мы группируем команды (например, `Team-Backend`).
*   **Projects:** Самый низкий уровень — репозитории, где живет код и пайпляны.

> **⚠️ Нюанс (Наследование):** Если ты добавил пользователя в группу `Engineering` с ролью `Developer`, он автоматически станет `Developer` во всех подгруппах и проектах внутри этой группы. **Права не могут «уменьшаться» при наследовании вниз, но могут уточняться.**

---

### 2. Роли и уровни доступа (Permissions)
В GitLab есть 5 основных ролей. Запомни их по «зонам ответственности»:

| Роль | Что может делать (кратко) | Для кого |
| :--- | :--- | :--- |
| **Guest** | Видит Issue, комментарии, Wiki. **Не видит код** (в приватных проектах). | Менеджеры, заказчики, QA (только для чтения задач). |
| **Reporter** | Видит код, может скачивать артефакты, создавать Issue. Не может пушить. | Тестировщики, аудиторы, аналитики. |
| **Developer** | Основная рабочая лошадка. Создает ветки, делает Merge Requests (MR), запускает пайплайны. | Инженеры, пишущие код. |
| **Maintainer** | «Хозяин» проекта. Управляет защищенными ветками, настройками CI/CD, переменными (Variables). | Team Lead, Senior DevOps. |
| **Owner** | Полный контроль, включая удаление группы/проекта и управление доступом. | Лид команды или админ. |

---

### 3. Механизмы защиты кода (Guardrails)
Мало дать роль, нужно настроить «предохранители», чтобы даже Developer не мог сломать `main`.

*   **Protected Branches:** Самая важная настройка. Позволяет запретить `force push` и прямой пуш в важные ветки (`main`, `production`). Только `Maintainers` могут мержить код.
*   le **Protected Tags:** Запрещает удаление или изменение тегов (например, версий `v1.0.0`), что критично для стабильности релизов.
*   **Code Owners:** С помощью файла `CODEOWNERS` можно настроить так, чтобы при изменении папки `/infra` запрос на ревью автоматически уходил именно DevOps-инженеру.
*   **Merge Request Approvals (Premium):** Требование обязательного одобрения от конкретных людей перед мержем.

---

### 4. Аутентификация и ключи (Как зайти в систему)
Доступ к GitLab осуществляется тремя путями:

1.  **Web UI / HTTPS:** Логин/пароль или SSO (SAML, LDAP, Google Auth).
2.  **SSH Keys:** Для работы с Git через терминал. Самый безопасный и удобный способ для разработчика.
3.  **Personal Access Tokens (PAT):** «Заменитель» пароля для API, скриптов или IDE. 
    *   *Senior Tip:* Всегда ограничивай **Scopes** (права) токена (например, только `read_repository`) и ставь **Expiration Date**. Никогда не используй токены с правами `api` без крайней необходимости.

### 💡 FAQ: Вопросы на собеседовании / В жизни

**В: Пользователь — Developer в группе, но ему нужно только смотреть Issue в подгруппе. Можно ли это сделать?**
**О:** Напрямую «откатить» роль вниз нельзя (наследование работает только вверх). Тебе придется либо создать пользователя отдельно для этой подгруппы с ролью `Guest`, либо использовать внешнюю систему управления доступом (LDAP/SAML), где права управляются вне GitLab.

**В: В чем критическая разница между Developer и Maintainer при работе с веткой `main`?**
**О:** Developer может создавать ветки и делать MR, но если ветка `main` помечена как **Protected**, он не сможет запушить в неё напрямую (только через MR) и не сможет сделать `force push`, который может затереть историю.

**В: Что такое "Least Privilege" и как это применить в GitLab?**
**О:** Это принцип выдачи минимально необходимых прав. Не давай роль `Maintainer` всем подряд. Если человеку нужно только проверять логи — дай `Reporter`. Если нужно писать код — `Developer`. Чем меньше прав, тем меньше риск, что случайная ошибка или украденный токен уничтожат проект.

**В: Можно ли использовать один и тот же SSH-ключ для разных пользователей?**
**О:** Технически можно (если ключ лежит на машине), но это **грубейшее нарушение безопасности**. В логах GitLab будет невозможно понять, кто именно совершил действие — реальный владелец ключа или тот, кто его украл. Каждый должен иметь свой уникальный ключ.

# 🧠 Шпаргалка: GitLab Flow

**GitLab Flow** — это стратегия ветвления, которая является «золотой серединой» между слишком простым *GitHub Flow* (где есть только `main`) и слишком переусложненным *GitFlow* (с кучей вечно живых веток `develop`, `release`, `hotfix`).

Ее главная цель: обеспечить стабильность релизов, не превращая процесс разработки в бюрократический ад.

---

### 🛠 Основные принципы

В основе GitLab Flow лежит концепция **"Upstream First"** (Сначала — в основной источник). Все изменения сначала попадают в `main`, и только потом «спускаются» вниз по цепочке к продакшену.

#### 1. Feature Branches (Ветки функций)
Любая задача (фича, багфикс, рефакторинг) начинается с новой ветки от `main`.
*   Работа идет в изоляции.
*   Завершается созданием **Merge Request (MR)**.
*   После проверки и тестов ветка вливается в `main`.

#### 2. Environment Branches (Ветки окружений) — *Вариант для Web/SaaS*
Если у тебя есть цепочка серверов (Staging $\rightarrow$ Pre-production $\int$ Production), ты создаешь соответствующие ветки.
*   `main` — здесь всегда актуальный, протестированный код.
*   `staging` — ветка, которая развернута на тестовом стенде. Код попадает сюда из `main`.
*   `production` — ветка, отражающая то, что сейчас видит пользователь. Код попадает сюда из `staging`.

#### 3. Release Branches (Ветки релизов) — *Вариант для ПО/Mobile/Embedded*
Если ты выпускаешь версии продукта (например, v1.0, v1.1), которые нужно поддерживать долгое время.
*   Когда в `main` накопилось достаточно фич, создается ветка `1.0`.
*   Все критические баги сначала чинятся в `main`, а затем **cherry-pick** (переносятся) в ветку релиза.

---

### ⚠️ Нюансы и "Подводные камни" (Senior Insights)

1.  **Правило Upstream First (Критически важно!):** Никогда не фикси баг сразу в ветке `production` или `release`. Если ты поправил баг в `production`, но забыл про `main`, то при следующем релизе этот баг вернется (регрессия). **Сначала `main`, потом перенос вниз.**
2.  **Cherry-pick — твой инструмент:** В GitLab Flow для переноса исправлений из `main` в старые ветки релизов используется команда `cherry-pick`. Это позволяет точечно забирать только фиксы, не притаскивая за собой сырые фичи.
s3
3.  **Автоматизация (CI/CD):** GitLab Flow работает только тогда, когда на ветки `main`, `staging` и `production` навешаны автоматические пайплайны. Влитие в `main` должно запускать тесты, а влитие в `production` — автоматический деплой.
4.  **Когда выбирать:** 
    *   Выбирай **Environment Branches**, если у тебя веб-сервис (SaaS), где важна скорость доставки.
    *   Выбирай **Release Branches**, если ты делаешь софт, который люди скачивают (мобильные приложения, десктоп), и тебе нужно поддерживать старые версии.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Чем GitLab Flow отличается от GitHub Flow?**
**О:** В GitHub Flow есть только ветка `main`. Как только код в `main` — он сразу в продакшене. Это круто для маленьких команд, но опасно для крупных проектов, где нужно сначала протестировать код на стейджинге. GitLab Flow добавляет промежуточные этапы (ветки окружений или релизов).

**В: Что делать, если в `production` нашли критический баг?**
**О:** 1. Создаешь ветку от `main`. 2. Исправляешь баг. 3. Делаешь MR в `main`. 4. После апрува и прохождения тестов в `main`, делаешь Merge (или Cherry-pick) в ветку `production` (или `staging`).

**В: Можно ли использовать GitLab Flow, если у нас нет серверов для Staging?**
**О:** Да. В этом случае ты используешь упрощенную версию: работаешь только с `main` и тегами (tags). Код в `main` всегда готов к деплою, а релиз — это просто создание тега.

**В: Не слишком ли много веток создает этот подход?**
**О:** По сравнению с GitFlow — нет. Здесь нет разделения на "develop" и "master". У тебя есть одна точка правды (`main`) и лишь дополнительные ветки для контроля доставки кода в конкретные среды.

# 🛠 Шпаргалка: Code Review & Merge Requests (MR)

**Merge Request (MR)** — это не просто кнопка «влить код». Это процесс проверки изменений, инструмент коммуникации и главный фильтр качества перед тем, как код попадет в основную ветку (`main`/`master`).

### 1. Жизненный цикл MR
Процесс должен быть прозрачным. Хороший тон — это когда каждый понимает статус задачи.

*   **Draft (ранее WIP - Work In Progress):** Если ты еще не закончил, обязательно помечай MR как `Draft:` в заголовке. Это сигнал коллегам: *"Не ревьюйте, я еще ковыряюсь"*. Это избавляет от лишних уведомлений и преждевременных замечаний.
*   / **Reviewing:** Стадия, когда код готов, тесты прошли (CI зеленый), и ты ждешь фидбек.
*   **Approved:** Коллеги проверили код и дали «добро».
*   **Merged:** Код успешно влит в целевую ветку.

### 2. Инструменты контроля качества (Governance)
Senior-подход — это автоматизация правил, чтобы не тратить время людей на проверку очевидных вещей.

*   **Approval Rules:** Настройка правил, кто и сколько человек должны одобрить MR. Например: *"Для изменений в папке `/security` обязательно 2 аппрува от группы Security Team"*.
*   **Code Owners:** Использование файла `CODEOWNERS`. Ты прописываешь в нем, что за какие файлы отвечают конкретные люди/группы. GitLab автоматически добавит их в ревьюеры, если изменены эти файлы. **Это маст-хэв для больших монорепозиториев.**
*   **Merge Request Templates:** Создай шаблон (через `.gitlab/merge_request_templates/`), чтобы автор MR всегда заполнял: *Что сделано? Как протестировать? Какие зависимости затронуты?* Это дисциплинирует команду.

### 3. Искусство ревью (Reviewing Mechanics)
Ревью — это диалог, а не допрос.

*   **Comments & Threads:** Каждое замечание должно быть в отдельном треде (ветке обсуждения). Не забывай нажимать **"Resolve thread"**, когда вопрос закрыт. Если тред висит открытым — значит, работа не закончена.
*   le **Suggestions (Предложения):** Это киллер-фича GitLab. Ревьюер может прямо в комментарии написать исправленный кусок кода, и автор нажмет одну кнопку *"Apply suggestion"*, чтобы автоматически применить правку. Это экономит кучу времени на лишних коммитах.
*   **Review Apps:** Если у тебя настроен CI/CD, GitLab может развернуть временное окружение (ephemeral environment) для каждого MR. Ревьюер может кликнуть на ссылку и потыкать фичу в браузере еще до того, как она попала в `main`.

### 4. Стратегии слияния (Merge Methods)
Выбор стратегии влияет на чистоту истории твоего Git-репозитория.

*   **Merge Commit:** Создает специальный "merge commit". Сохраняет всю историю веток, но превращает граф коммитов в «спагетти», если веток много.
*   **Squash Merge (Рекомендую):** Схлопывает все мелкие коммиты из MR (типа *"fix typo"*, *"oops"*, *"test"*) в один чистый, осмысленный коммит. **Это золотой стандарт для чистого `main`.**
*   **Fast-forward Merge:** Просто перемещает указатель ветки вперед. История линейная и красивая, но требует, чтобы ветка была актуальна относительно `main` (нужно делать rebase).

---

### 💡 Senior Tips (Нюансы)
1.  **Small is Beautiful:** Чем меньше MR, тем быстрее и качественнее ревью. Огромный MR на 50 файлов — это смерть для ревьюера. Он либо пропустит баги из-за усталости, либо затянет процесс на неделю.
2.  **CI is your first reviewer:** Никогда не зови людей на ревью, если пайплайн упал (красный). Ревьюер не должен тратить время на поиск синтаксических ошибок или упавших тестов — это работа автоматики.
3.  **Don't be a jerk:** Критикуй код, а не человека. Вместо *"Ты написал плохой цикл"* пиши *"Этот цикл может вызвать проблемы с производительностью при больших данных"*.

### ❓ FAQ (Частые вопросы)

**В: Что делать, если в MR возникли конфликты?**
**О:** Тебе нужно обновить свою ветку из целевой (`git pull origin main`). Реши конфликты локально, сделай коммит и `push`. GitLab сам увидит изменения и уберет пометку "Conflict".

**В: Чем отличается `Rebase` от `Merge` при обновлении ветки?**
**О:** `Merge` создает новый коммит слияния и сохраняет историю как она есть. `Rebase` переписывает историю твоих коммитов, ставя их «поверх» актуального `main`. Rebase делает историю линейной, но он опасен, если ты уже запушил ветку и с ней работают другие (переписывание истории).

**В: Зачем использовать `Squash Merge`, если я хочу видеть каждый свой шаг?**
**О:** Твои «шаги» — это промежуточный мусор. В истории проекта важен результат (фича), а не то, сколько раз ты исправлял опечатку в процессе разработки. Squash делает историю понятной для всех.

**В: Как закрыть задачу (Issue) автоматически?**
**О:** Напиши в описании MR фразу `Closes #123` или `Fixes #123`. Когда MR будет влит, GitLab сам закроет связанную задачу.

# 🧠 Шпаргалка: Анатомия `.gitlab-ci.yml`

`.gitlab-ci.yml` — это не просто конфиг, это **манифест** твоего пайплайна. Это декларативное описание того, *что* должно произойти, а GitLab сам решит, *как* это запустить на раннерах.

### 1. Глобальные настройки (Global Configuration)
Эти параметры определяют поведение всего файла.

*   **`stages`**: Список этапов пайплайна. Определяет порядок выполнения групп задач. 
    *   *Нюанс:* Задачи внутри одного стейджа выполняются **параллельно** (если есть свободные раннеры). Стейджи идут строго последовательно.
*   **`image`**: Глобальный Docker-образ, в котором будут запускаться все джобы, если не указано иное.
*   **`variables`**: Глобальные переменные, доступные всем джобам. Помогают избежать дублирования (например, `APP_VERSION`).
*   **`workflow`**: Управляет тем, будет ли вообще запущен пайплайн (например, запретить запуски на каждый коммит в черновиках).

### 2. Структура Job (Unit of Work)
Джобы — это ключевые элементы. Каждая джоба — это отдельный процесс в контейнере.

*   **`script`**: **Сердце джобы.** Список команд (bash/shell), которые должны выполни/ниться. Без этого секции джоба невалидна.
*   **`tags`**: Указывает, на каком именно раннере должна запуститься джоба (например, `docker`, `shell`, `gpu`). 
    *   *Нюанс:* Если ты забудешь теги, GitLab попытается отправить джобу на любой свободный раннер, что может привести к ошибке, если там нет нужного софта.
*   **`allow_failure`**: Если `true`, то даже при падении этой джобы пайплайн пойдет дальше (полезно для линтеров или тестов, которые не критичны).

### 3. Логика управления (Control Flow)
Как заставить GitLab быть «умным».

*   **`rules` (Modern Way)**: Самый мощный инструмент. Позволяет запускать джобу при определенных условиях:
    *   `if`: Проверка переменных (например, `$CI_COMMIT_BRANCH == "main"`).
    *   `changes`: Запуск только если изменились файлы в конкретной папке (идеально для монорепозиториев).
    *   `exists`: Проверка наличия файла.
    *   *Senior Tip:* **Забудь про `only/except`**. Они устарели и менее гибкие, чем `rules`.
*   **`needs` (DAG - Directed Acyclic Graph)**: Позволяет джобе начаться сразу после завершения конкретной предыдущей джобы, не дожидаясь окончания всего стейджа. Это **критически важно для ускорения пайплайна**.

### 4. Передача данных (Data Persistence)
Контейнеры эфемерны (умирают после выполнения). Как передать результат?

*   **`artifacts`**: «Результат работы». Файлы, которые нужно сохранить (бинарники, отчеты, собранный фронтенте). 
    *   *Нюанс:* Артефакты передаются между стейджами. Используй `expire_in`, чтобы не забить диск сервера старым мусором.
*   **`cache`**: «Инструментарий». Используется для ускорения (например, папка `node_modules` или `.m2`). 
    *   *Нюанс:* **Cache — это не Artifacts**. Кэш не гарантирует доставку данных между джобами (он может не скачаться), он лишь пытается их подложить.

### 5. DRY & Modularization (Чистый код)
Чтобы `.gitlab-ci.yml` не превратился в «простыню» на 2000 строк.

*   **`extends`**: Позволяет наследовать настройки от другой джобы или шаблона. Избавляет от копипаста.
*   **`include`**: Разделение конфига на части. Можно вынести общие правила в отдельный репозиторий и подключать их везде.

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `cache` и `artifacts`?**
**О:** Если тебе нужно передать собранный `.jar` файл из стадии `build` в стадию `deploy` — это **Artifacts**. Если ты хочешь, чтобы в следующий раз `npm install` прошел быстрее, потому что папка `node_modules` сохранилась — это **Cache**.

**В: Почему моя джоба не запустилась, хотя я запушил код?**
**О:** Проверь секцию `rules`. Скорее всего, там стоит условие (например, проверка ветки или изменения файлов), которое не выполнилось для твоего коммита.

**В: Что такое `needs` и зачем оно мне, если есть `stages`?**
**О:** `stages` заставляют все джобы в стейдже ждать друг друга. `needs` позволяет «прокинуть» путь сквозь стейджи. Если у тебя есть тяжелый тест, который идет 20 минут, а легкий деплой — 1 минуту, с помощью `needs` ты сможешь задеплоить легкую часть сразу, не дожидаясь окончания тестов (если это допустимо).

**В: Как сделать так, чтобы джоба запускалась только при пуше в ветку `main`?**
**О:** Используй современный синтаксис:
```yaml
rules:
  - if: $CI_COMMIT_BRANCH == "main"
```

# 🧠 Шпаргалка: Логика выполнения в GitLab CI/CD

Логика выполнения — это «мозги» твоего пайплайна. Она определяет, **когда** запускается джоба, **при каких условиях** и **в каком порядке**. Если здесь ошибиться, можно получить либо лишние траты ресурсов на ненужные сборки, либо пропустить критически важный деплой.

### 1. Stages (Этапы) — Фундамент
Все джобы распределяются по стадиям (`stages`). 
*   **Суть:** По умолчанию GitLab выполняет стадии строго последовательно: `build` $\to$ `test` $\to$ `deploy`. Пока все джобы в `build` не завершатся успешно, `test` не начнется.
*   **Нюанс:** Если одна джоба в стадии упала, вся стадия считается проваленной, и следующие стадии не запустятся (если не настроено иное).

### 2. Rules (Правила) — Современный стандарт
Забудь про старые `only` и `except`. В современном GitLab всё решают `rules`. Это набор условий, который проверяется сверху вниз. **Первое совпадение побеждает.**

**Основные ключевые слова в `rules`:**
*   `if`: Проверка переменных (например, `$CI_COMMIT_BRANCH == "main"`).
*   `changes`: Запуск джобы только если изменились определенные файлы (например, только если поменялось в папке `frontend/`).
*   `exists`: Запуск, если в репозитории присутствует определенный файл (например, `Dockerfile`).
*   `when`: Что делать, если условие сработало (`on_success`, `manual`, `always`, `never`).

**Пример:**
```yaml
test-job:
  script: npm test
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"  # Только для MR
      when: always
    - changes:
        - src/**/*                                      # Или если изменился код в src
      when: on_success
    - when: never                                       # В остальных случаях — не запускать
```

### 3. Workflow Rules — Уровень пайплайна
`workflow:rules` — это глобальный фильтр. Он определяет, будет ли создан **весь пайплайн целиком** или нет. 
*   **Зачем:** Чтобы избежать дублирования пайплайнов (например, когда одновременно создается пайплайн для ветки и для Merge Request).

### 4. Needs (DAG — Directed Acyclic Graph) — Убийца очередей
Это «секретное оружие» для ускорения CI/CD. По умолчанию джобы ждут завершения всей предыдущей стадии. `needs` позволяет разорвать эту цепочку.
*   **Суть:** Ты говоришь: «Мне не нужно ждать окончания всей стадии `test`, мне нужна только джоба `build-app`». Как только `build-app` готова, `deploy-app` может стартовать, даже если в это время крутятся тесты для других модулей.
*   **Нюанс:** Использование `needs` превращает линейный пайплайн в граф (DAG), что значительно экономит время.

### 5. Управление статусом: When и Allow Failure
*   `when: manual`: Создает «кнопку» в интерфейсе GitLab. Джоба не запустится сама, пока инженер не нажмет Play. Идеально для деплоя на Production.
*   `allow_failure: true`: Помечает джобу как «прошедшую с предупреждением» (оранжевый значок). Если она упадет, пайплайн не остановится и пойдет дальше. Полезно для линтеров или экспериментальных тестов.

---

### ⚠️ Нюансы от Senior-а (на чем все валятся)

1.  **Порядок в `rules` критичен:** Если ты первым поставишь условие, которое всегда истинно (`if: $CI_COMMIT_BRANCH`), то все последующие специфичные правила (например, `changes`) будут проигнорированы.
2.  **Ловушка `changes`:** В GitLab CI правило `changes` работает не совсем так, как кажется. При запуске пайплайна по пушу в ветку, GitLab сравнивает изменения с предыдущим коммитом. Но если ты используешь `rules` в контексте Merge Request, логика может меняться. Всегда тестируй!
3.  **Скрытые переменные:** Часто забывают, что `rules` могут зависеть от переменных окружения (Environment Variables). Если переменная не прокинута в пайплайн, правило `if: $MY_VAR == "true"` просто не сработает без ошибки, а джоба просто «исчезнет».

### ❓ FAQ (Частые вопросы)

**В: Почему моя джоба вообще не появилась в пайплайне?**
**О:** Скорее всего, сработало правило `when: never` или не подошло условие в `workflow:rules`. Проверь глобальные правила пайплайна.

**В: В чем разница между `only/except` и `rules`?**
**О:** `only/except` — это устаревший, ограниченный синтаксис. `rules` гораздо мощнее, так как позволяют использовать сложные логические условия (`if`, `changes`, `exists`) и гибко управлять поведением через `when`. Используй только `rules`.

****В: Как сделать так, чтобы джоба запускалась только при ручном нажатии, но при этом не блокировала остальные стадии?**
**О:** Используй `when: manual` и убедись, что у тебя **не** включена зависимость от этой джобы в других задачах через `needs`. Также добавь `allow_failure: true`, чтобы пайплайн не висел в статусе "Running" вечно, ожидая твоего клика.

**В: Что будет, если я использую `needs` и укажу джобу из еще не завершенной стадии?**
**О:** GitLab выдаст ошибку конфигурации (Linter error). Ты можешь ссылаться только на те джобы, которые либо уже завершены, либо находятся в той же стадии или в стадиях, которые идут раньше.

# 📦 GitLab CI/CD: Artifacts (Артефакты)

**Artifacts** — это файлы или папки, которые создаются в процессе выполнения Job (задачи) и должны быть сохранены, чтобы их можно было использовать в следующих стадиях (stages) того же пайплайна или скачать вручную из интерфейса GitLab.

### 🛠 Основной синтаксис
Все настройки пишутся в блоке `artifacts` внутри конкретной задачи в `.gitlab-ci.yml`.

```yaml
build_job:
  stage: build
  script:
    - npm install
    - npm run build  # Создает папку 'dist'
  artifacts:
    paths:
      - dist/        # Что именно сохраняем
      - build.log    # Отдельный файл
    expire_in: 1 week # Срок жизни артефакта
    when: on_success # Когда сохранять
```

### 🔍 Ключевые параметры (Нюансы)

1.  **`paths`**: Список путей к файлам/директориям. Можно использовать wildcards (`*.log`, `build/**/*.js`).
2.  **`expire_in`**: **Критически важный параметр.** Если его не указать, артефакты будут храниться вечно (или пока не закончится место на сервере). 
    *   *Примеры:* `30 mins`, `2 hours`, `1 day`, `1 week`.
    *   *Senior tip:* Всегда ограничивай время жизни. Мусор в хранилище — враг стабильности GitLab.
3.  **`when`**: Определяет условие загрузки артефактов:
    *   `on_success` (дефолт): только если джоба прошла успешно.
    *   `on_failure`: полезно для сохранения логов ошибок, когда билд упал.
    *   `always`: сохранять в любом случае.
4.  **`reports`**: Это "магический" подтип артефактов. Они не просто лежат файлом, а **интегрируются в UI GitLab**.
    *   `junit`: отчеты о тестах (появляются во вкладке Tests).
    *   `cobertura`: покрытие кода (code coverage) — рисуется прямо в Merge Request.
    *   `dependency_scanning`, `sast`, и др.: результаты сканеров безопасности.

---

### ⚖️ Главное противостояние: Artifacts vs Cache
Это классический вопрос на собеседовании. Не путай их!

| Характеристика | **Artifacts** (Артефакты) | **Cache** (Кэш) |
| :--- | :--- | :--- |
| **Цель** | Передача результатов между стадиями пайплайна. | Ускорение работы джоб за счет повторного использования зависимостей. |
| **Связь** | Между `stages` одного пайплайна. | Между разными запусками (pipelines) или разными ветками. |
| **Надежность** | Гарантированы (если джоба прошла). | "Best effort" — может отсутствовать, если раннер новый. |
| **Пример использования** | Скомпилированный `.jar` файл, собранный Docker-образ. | Папка `node_modules`, `.m2` репозиторий, `pip` кэш. |

---

### 💡 Senior Tips (Тонкие моменты)

*   **Размер имеет значение:** Не пытайся запихнуть в артефакты всё подряд (например, всю папку `node_modules`). Это раздувает размер пайплайна и замедляет его выполнение из-за пересылки данных между раннером и сервером GitLab.
*   **Безопасность:** Никогда не клади в артефакты секреты (`.env` с паролями, приватные ключи). Любой, у кого есть доступ к проекту, сможет их скачать.
*   **Dependency Chain:** Помни, что для того, чтобы следующая джоба увидела артефакт, она должна находиться в более поздней `stage`.

---

### ❓ FAQ (Частые вопросы)

**В: Что будет, если я забуду указать `expire_in`?**
**О:** Артефакт будет храниться бесконечно долго. Это приведет к тому, что диск на сервере GitLab забьется очень быстро, и система может упасть.

**В: Можно ли использовать артефакты из другого пайплайна?**
**О:** Напрямую — нет. Артефакты "живут" внутри одного пайплайна. Но ты можешь скачать их через API GitLab или использовать `needs:project` (в продвинутых сценариях), но это уже выход за рамки базового использования.

**В: Почему мои тесты не отображаются в интерфейсе GitLab, хотя файлы JUnit создались?**
**О:** Проверь, что ты используешь именно секцию `reports: junit:`, а не просто `paths:`. Только `reports` заставляет GitLab парсить XML и строить красивые графики.

**В: Если джоба упала (on_failure), я увижу артефакты?**
**О:** Да, если ты явно указал `when: on_failure` или `when: always`. Это лучший способ увидеть логи, которые привели к падению билда.

# 🧠 Шпаргалка: GitLab CI/CD — Cache (Кэширование)

### 🎯 Что такое Cache?
**Cache** — это механизм для сохранения файлов между разными запусками (pipelines) или даже между разными джобами (jobs). Его единственная цель — **ускорение пайплайна**. Мы кэшируем то, что тяжело скачивать или собирать заново: зависимости (`node_modules`, `vendor`, `.m2`, `pip cache`).

> **Senior Note:** Кэш — это не гарантия. Он может «протухнуть», удалиться или не подтянуться. Твой пайплайн должен уметь работать и без него (всегда делать `npm install` или `pip install`, если кэша нет).

---

### 🛠 Основные параметры (`.gitlab-ci.yml`)

1.  **`paths`**: Список путей (файлов или папок), которые нужно сохранить.
    *   *Пример:* `- node_modules/` или `- vendor/`
2.  **`key`**: Самый важный параметр. Это «идентификатор» кэша. Если `key` совпадает, GitLab подтянет старый кэш.
    *   Если не указать — будет общий кэш для всех веток (плохая идея!).
3.  **`policy`**: Режим работы с кэшем:
    *   `pull-push` (дефолт): Скачивает кэш в начале джобы и загружает обновленный в конце.
    *   `pull`: Только скачивает. Идеально для джоб, которые только тестируют код (не меняя зависимости). Это экономит время на загрузку.
    *    `push`: Только загружает. Используется в джобах сборки.

---

### 🚀 Стратегии использования Key (Уровень: Pro)

Чтобы кэш работал эффективно и не конфликтовал между ветками, используй правильные ключи:

*   **`key: $CI_COMMIT_REF_SLUG`**: Кэш привязан к конкретной ветке. Ветка `feature-1` имеет свой кэш, `master` — свой.
    *   *Плюс:* Изоляция. *Минус:* При создании новой ветки кэш будет пустым (нужно ждать первой сборки).
*   **`key: files: [package-lock.json]`**: **(Best Practice)** Кэш пересобирается только тогда, когда меняется файл зависимостей.
    *   GitLab считает хеш от файла. Если `package-lock.json` не изменился — берем старый кэш. Это максимально эффективно.

---

### ⚠️ Главное отличие: Cache vs Artifacts
Это классический вопрос на собеседовании. Не путай их!

| Характеристика | **Cache** (Кэш) | **Artifacts** (Артефакты) |
| :--- | :--- | :---cr
| **Цель** | Ускорение (Dependencies) | Результат сборки (Build output) |
| **Срок жизни** | Временный, может исчезнуть в любой момент | Гарантированный, передается между стадиями |
| **Зависимость** | Не обязателен для успеха пайплайна | Обязателен для следующих Stage |
| **Пример** | `node_modules`, `.cache/pip` | `dist/`, `build/`, `binary.exe` |

---

### 🚩 Нюансы и «грабли» (Senior Tips)

1.  **Cache Poisoning (Отравление кэша):** Если одна джоба в ветке криво обновила зависимости и закинула их в кэш, все последующие джобы этой ветки упадут.
2.  **Distributed Runners:** Если у тебя много разных Runner-ов на разных машинах, обычный локальный кэш не сработает. Тебе нужно настроить **S3-compatible storage** (например, MinIO) в `config.toml` раннера, чтобы все раннеры видели одну «корзину» с кэшем.
3.  **Размер имеет значение:** Слишком большой кэш (гигабайты) может замедлить пайплайн сильнее, чем отсутствие кэша, из-за времени на его загрузку/выгрузку по сети.
4.  **Используй `policy: pull` для тестов:** В джобах `test` никогда не делай `push`. Тесты только читают зависимости. Это экономит время на этапе завершения джобы.

---

### ❓ FAQ (Частые вопросы)

**В: Почему мой кэш не работает и всегда скачивается с нуля?**
**О:** Проверь `key`. Если ты используешь `key: $CI_COMMIT_REF_SLUG`, то для каждой новой ветки кэш будет пустым. Также проверь, что пути в `paths` указаны верно относительно корня проекта.

**В: Что лучше: кэшировать всю папку `node_modules` или только `package-lock.json`?**
**О:** Кэшировать нужно именно **папку** (содержимое), но использовать **файл** для создания ключа (`key: files: [package-lock.json]`). Это даст тебе и скорость, и автоматическое обновление при изменении библиотек.

**В: Можно ли использовать кэш между разными проектами в GitLab?**
**О:** Напрямую — нет. Кэш привязан к конкретному проекту. Но если ты используешь S3-бэкенд для кэша, можно настроить общие пути, но это архитектурно «грязный» хак.

# 🧠 Шпаргалка: GitLab CI/CD Variables (Переменные)

**Переменные** — это способ передать конфигурацию, секреты или параметры в твой пайплайн без изменения самого кода `.gitlab-ci.yml`. Это «топливо» для гибкости: один и тот же код может деплоиться и на `staging`, и на `production`, просто меняя значения переменных.

---

### 1. Уровни определения (Где живут переменные)

Переменные в GitLab могут быть объявлены в разных местах. Это критически важно для понимания **приоритета (Precedence)**.

1.  **Triggered Variables (Самый высокий приоритет):** Переменные, которые ты передаешь «на лету» через API или при ручном запуске пайплайна (Run Pipeline). Они перекрывают всё остальное.
2.  **Job-level Variables:** Объявлены внутри конкретной `job` в `.gitlab-ci.yml`. Работают только для этой джобы.
3.  **Global YAML Variables:** Объявлены на верхнем уровне `.gitlab-ci.yml`. Доступны всем джобам в этом файле.
4.  **Project/Group Settings (UI):** Переменные, настроенные через интерфейс GitLab (*Settings -> CI/CD -> Variables*). Это основное место для хранения секретов.
5.    **Predefined Variables (Встроенные):** Те, что GitLab дает тебе «бесплатно» (например, `$CI_COMMIT_SHA`, `$CI_JOB_ID`). Их нельзя перезаписать, только использовать.

---

### 2. Типы переменных в UI (Security & Scope)

Когда ты создаешь переменную в интерфейсе проекта, у тебя есть три важнейших рычага управления:

*   **Masked (Маскирование):** 
    *   *Что делает:* Скрывает значение переменной в логах пайплайна (вместо пароля будет `[MASKED]`).
    *   *Нюанс:* Значение должно соответствовать правилам (не слишком короткое, не содержит спецсимволов, которые могут сломать логи). **Всегда используй это для паролей и токенов.**
*   **Protected (Защита):** 
    *   *Что делает:* Переменная будет доступна только в тех пайплайнах, которые запущены на **Protected Branches** (например, `main`) или **Protected Tags**.
    *   *Нюанс:* Это спасает от ситуации, когда разработчик создает ветку `feature/hack-secrets`, меняет скрипт деплоя и пытается украсть пароль из логов.
*   **Environment Scope (Область видимости):** 
    *   *Что делает:* Позволяет иметь разные значения для одной и той же переменной в зависимости от окружения (`production` vs `staging`).
    ке

---

### 3. Тип данных: String vs File

В GitLab есть два способа хранения содержимого:
1.  **Variable (String):** Обычная строка. Удобно для ключей, имен бакетов, версий.
2.  **File:** GitLab не просто сохраняет строку, а записывает её в **временный файл** на раннере, а в саму переменную кладет **путь к этому файлу**.
    *   *Зачем это нужно:* Идеально для `KUBECONFIG`, `SSH_KEY` или `service-account.json`. Вместо того чтобы мучиться с парсингом строки, ты просто делаешь `kubectl --kubeconfig $MY_FILE_VAR`.

---

### 4. Senior Tips (Нюансы и Best Practices)

*   **⚠️ Избегай Hardcode:** Никогда не пиши пароли прямо в `.gitlab-ci.yml`. Это дыра в безопасности. Только через UI/Vault.
*   **Hierarchy Trap:** Помни, что если ты объявил переменную `DB_URL` в UI проекта и такую же в `job` в YAML — джоба возьмет ту, что в YAML. Если хочешь переопределить конфиг из YAML значением из UI, будь осторожен с приоритетами.
*   **Expansion (Развертывание):** GitLab умеет подставлять переменные друг в друга: `DEPLOY_TARGET: $CI_ENVIRONMENT_NAME`. Но будь аккуратен с рекурсией.
*   **Use `.env` files for dynamic values:** Если одна джоба должна передать значение следующей (которая не является child-pipeline), используй `artifacts:reports:dotenv`. Это «легальный» способ прокинуть динамически вычисленную переменную между стадиями.

---

### ❓ FAQ (Частые вопросы)

**В: Я добавил секрет в UI как "Masked", но он всё равно виден в логах. Почему?**
**О:** Скорее всего, значение слишком короткое или содержит символы, которые GitLab не может безопасно замаскировать (например, пробелы в начале/конце или специфические спецсимволы). Проверь требования к Masked variables в документации.

**В: Как мне передать переменную из одной джобы в другую, если они на разных стадиях?**
**О:** Используй механизм `artifacts:reports:dotenv`. В первой джобе запиши `export MY_VAR=hello` в файл `.env`, а во второй подключи этот артефакт. Это гораздо чище, чем пытаться использовать глобальные переменные.

**В: Что лучше: переменная типа "File" или "String" для SSH-ключа?**
**О:** Только **File**. Если ты запишешь ключ как String, тебе придется в пайплайне делать `echo "$SSH_KEY" > ~/.ssh/id_rsa` и возиться с правами доступа (`chmod 600`). С типом File GitLab сделает это за тебя.

**В: Можно ли использовать переменные из Group уровня в проекте?**
**О:** Да! Это мощный инструмент для DRY (Don't Repeat Yourself). Ты можешь определить `COMPANY_REGISTRY` на уровне всей группы, и все 100 твоих проектов будут его видеть автоматически.

# 🚀 Шпаргалка: GitLab Environments & Deployments

### 🧠 Суть концепции
В GitLab **Environments (Окружения)** — это не просто названия серверов. Это логические сущности, которые позволяют GitLab отслеживать, какая версия кода сейчас развернута на конкретном стенде (Staging, Production, Review App). 

**Deployments (Деплои)** — это процесс доставки артефактов в эти окружения, который можно контролировать, откатывать и автоматизировать.

---

### 🛠 Ключевые элементы `.gitlab-ci.yml`

Чтобы GitLab «увидел» деплой, недостаточно просто запустить скрипт. Нужно использовать ключевое слово `environment`.

#### 1. Основные параметры:
*   **`name`**: Идентификатор окружения (например, `production`, `staging`). Часто используют переменные, чтобы имя зависело от ветки: `name: review/$CI_COMMIT_REF_SLUG`.
*   **`url`**: Ссылка на работающее приложение. После успешного деплоя в интерфейсе GitLab появится кнопка «View deployment», ведущая прямо на ваш сайт.
*   **`on_stop`**: **(Важно!)** Имя джобы, которая должна выполниться для «уборки» (например, удалить временный Review App или остановить контейнер).

#### 2. Пример конфигурации:
```yaml
deploy_review:
  stage: deploy
  script:
    - echo "Deploying to temporary environment..."
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    url: https://my-app-$CI_COMMIT_REF_SLUG.example.com
    on_stop: stop_review  # Связка для очистки

stop_review:
  stage: deploy
  script:
    - echo "Destroying temporary environment..."
  when: manual          # Очистка обычно делается вручную или по триггеру
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    action: stop         # Говорит GitLab, что это джоба удаления
```

---

### 🏗 Advanced Patterns (Продвинутые фишки)

#### 1. Review Apps (Динамические окружения)
Это «киллер-фича». Для каждого Merge Request (MR) создается временное окружение. Тестировщик или ревьюер может кликнуть по ссылке в MR и увидеть, как именно работают изменения в реальном браузере, не дожидаясь деплоя в Staging.

#### 2. Deployment Strategy: Manual vs Automatic
*   **Automatic**: Деплой происходит сразу после успешных тестов (подходит для Staging).
*   **Manual (`when: manual`)**: Кнопка в интерфейсе, которую нажимает человек (обязательно для Production, чтобы избежать случайных деплоев).

#### 3. Protected Environments
В настройках GitLab можно указать, что деплой в `production` могут делать только пользователи с ролью `Maintainer`. Это критически важно для безопасности.

#### 4. Rollback (Откат)
Если деплой провалился или принес баги, в интерфейсе GitLab (Deployments -> Environments) есть кнопка **Rollback**. Она перезапускает предыдущую успешную джобу деплоя. 
*Нюанс: Rollback работает только если ваша CI/CD логика позволяет повторный запуск старой джобы.*

---

### ⚠️ Тонкие моменты (Senior Tips)

1.  **Action `prepare` и `start`**: Если ваш деплой сложный (например, сначала нужно создать БД, а потом залить код), вы можете использовать `action: prepare`. Это позволяет GitLab понимать последовательность подготовки окружения.
2.  **Забытый `on_stop`**: Если вы используете Review Apps и не настроили `on_stop`, ваши временные ресурсы (контейнеры в K8s, инстансы в облаке) будут плодиться бесконечно, пока не сожрут весь бюджет компании.
3.  **Идемпотентность**: Ваши джобы деплоя должны быть идемпотентными. Это значит, что если запустить одну и ту же джобу дважды, результат должен быть одинаковым (приложение не должно «сломаться» от повторного деплоя).
4.  **Scoped Variables**: Всегда используйте переменные окружения, ограниченные конкретным `environment` или `branch`, чтобы пароль от Production не утек в Staging-пайплайн.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Чем `environment: name` отличается от простого названия джобы?**
**О:** Название джобы — это просто текст в логах. `environment: name` создает запись в базе данных GitLab, позволяя видеть историю деплоев, управлять ссылками и делать Rollback.

**В: Как сделать так, чтобы Review App удалялся сам после закрытия Merge Request?**
**О:** Нужно настроить джобу с `action: stop` и привязать её через `on_stop`. GitLab умеет триггерить такие джобы при закрытии MR.

**В: Можно ли использовать один и тот же `environment: name` для разных веток?**
**О:** Можно, но тогда история деплоев будет перемешана. Лучше использовать динамические имена (например, с префиксом ветки), чтобы видеть четкую историю для каждой фичи отдельно.

**В: Что делать, если при Rollback база данных изменила структуру (миграции)?**
**О:** Это классическая проблема. GitLab умеет откатывать *код*, но не умеет откатывать *состояние базы*. Senior-подход: всегда делайте миграции обратно совместимыми (Expand/Contract pattern), чтобы старый код мог работать с новой схемой БД.

# 🛠 Шпаргалка: Matrix Builds в GitLab CI/CD

### Что это такое? (The Concept)
**Matrix Builds** — это механизм, который позволяет запускать одну и ту же джобу несколько раз, но с разными комбинациями переменных. 

Представь, что тебе нужно протестировать приложение на трех версиях Node.js (16, 18, 20) и на трех разных операционных системах (ubuntu, alpine, busybox). Вместо того чтобы копипастить три разные джобы, ты пишешь **одну** длоку, а GitLab сам «размножает» её на все возможные комбинации.

В математике это называется *декартово произведение* (Cartesian Product). Если у тебя 3 версии Node и 3 ОС — ты получишь $3 \times 3 = 9$ параллельных джоб.

---

### Синтаксис и примеры

Все магия происходит внутри ключевого слова `parallel: matrix`.

#### 1. Простой пример (один параметр)
Тестируем разные версии языка.
```yaml
test_node_versions:
  stage: test
  image: node:$NODE_VERSION
  parallel:
    matrix:
      - NODE_VERSION: [16, 18, 20]
  script:
    - node -v
    - npm test
```

#### 2. Сложный пример (несколько параметров)
Создаем комбинацию: разные версии Node.js + разные операционные системы.
```yaml
integration_tests:
  stage: test
  parallel:
    matrix:
      - NODE_VERSION: [16, 18]
        OS_TYPE: [ubuntu, alpine]
  image: node:$NODE_VERSION
  script:
    - echo "Running tests on Node $NODE_VERSION in $OS_TYPE environment"
    - npm install
    - npm test
```
*Результат: GitLab создаст 4 джобы (16-ubuntu, 16-alpine, 18-ubuntu, 18-alpine).*

---

### 💡 Нюансы от Senior (На что обратить внимание)

1.  **Взрывной рост количества джоб (Combinatorial Explosion):**
    Будь осторожен! Если ты добавишь третий параметр (например, `DB_TYPE: [postgres, mysql, mongo]`), количество джоб вырастет с 4 до 12. Если параметров станет слишком много, ты забьешь очередь всех своих Runner-ов, и другие важные пайплайны в компании встанут в очередь. **Всегда считай итоговое число джоб.**

2.  **Использование переменных в `image`:**
    Как показано в примерах выше, переменные из матрицы можно (и нужно) использовать прямо в ключе `image`. Это самый мощный кейс для Matrix Builds.

3.  **Взаимодействие с `needs`:**
    Если твоя матричная джоба должна ждать завершения другой джобы (через `needs`), помни, что эта зависимость будет применяться ко **всем** созданным под-джобам.

4.  **Изоляция:**
    Каждая джоба в матрице — это абсолютно независимый процесс. Если одна упадет (например, из-за бага в Node 16), остальные продолжат выполняться. Это круто для локализации ошибок.

5.  **Переопределение переменных:**
    Внутри матрицы ты можешь задавать значения, которые будут перекрывать глобальные переменные проекта, что позволяет гибко настраивать окружение под конкретную комбинацию.

---

### ❓ FAQ (Частые вопросы)

**В: Что если я хочу, чтобы в одной из джоб матрицы был другой параметр?**
**О:** Матрица работает по принципу «все со всеми». Ты не можешь сказать: «Для Node 16 используй только Ubuntu, а для Node 20 — везде». Если тебе нужна такая логика, придется либо использовать `rules` внутри джобы (что усложнит код), либо разбить матрицу на две разные джобы.

**В: Можно ли использовать Matrix Builds вместе с `extends`?**
**О:** Да. Ты можешь создать базовый шаблон (template) с общими скриптами и через `extends` подтягивать его в джобу, где будет объявлена матрица. Это лучший способ держать `.gitlab-ci.yml` чистым.

**В: Как понять, какая именно комбинация упала, если я вижу кучу одинаковых названий джоб?**
**О:** GitLab автоматически добавляет суффикс к имени джобы, содержащий значения переменных из матрицы (например, `integration_tests: [16, ubuntu]`). Всегда смотри на имя джобы в интерфейсе Pipeline.

**В: Можно ли использовать Matrix Builds для запуска тестов в разных браузерах?**
**О:** Да, это классический кейс. Ты создаешь матрицу `BROWSER: [chrome, firefox, safari]` и используешь это в скрипте запуска Selenium/Playwright.

# 🚀 Шпаргалка: Parent-Child Pipelines в GitLab CI/CD

### 💡 Что это такое? (Суть)
Представь, что у тебя огромный проект (Monorepo), где лежит код фронтенда, бэкенда и мобильного приложения. Если ты будешь пихать всё в один `.gitlab-ci.yml`, он превратится в «спагетти» на 2000 строк, который невозможно читать и поддерживать.

**Parent-Child Pipelines** — это механизм, позволяющий одному пайплайну (Родителю) запускать другие, отдельные пайплайны (Дети). У каждого "ребенка" свой собственный `.gitlab-ci.yml`.

### 🛠 Как это работает (Механика)
Основной инструмент здесь — ключевое слово `trigger` в джобе родительского пайплайна.

**Схема работы:**
1. **Parent Pipeline**: Содержит логику определения, что и когда запускать.
2. **Trigger Job**: Специальная джоба, которая говорит: «Эй, запусти вот этот файл!».
3. **Child Pipeline**: Выполняет свою независимую последовательность стадий (stages).

**Пример минимального конфига:**

```yaml
# .gitlab-ci.yml (Parent)
stages:
  - triggers

trigger_backend_pipeline:
  stage: triggers
  trigger:
    include: backend/.gitlab-ci.yml  # Путь к файлу ребенка
    strategy: depend                 # Ключевой нюанс! (см. ниже)
  rules:
    - changes:
        - backend/**/*               # Запускаем только если изменился код в папке backend
```

### 🌟 Когда это использовать? (Use Cases)
1. **Monorepo (Главный кейс):** Чтобы не пересобирать бэкенд, когда ты просто поправил README в папке фронтенда.
2. **Снижение сложности:** Разделение логики на понятные модули (Deploy, Test, Build).
тика
3. **Изоляция ошибок:** Ошибка в пайплайне тестирования микросервиса "А" не должна блокировать выполнение пайплайна микросервиса "Б".

### ⚠️ Нюансы и «Грабли» (Senior Insights)

1.  **`strategy: depend` — это критично!**
    *   По умолчанию, если ты просто используешь `trigger`, родительская джоба пометится как **Success**, даже если дочерний пайплайн упал. Это плохо, так как ты не узнаешь о поломке.
    *   Используй `strategy: depend`, чтобы статус родителя зависел от статуса ребенка. Если ребенок упал — родитель тоже падает.

2.  **Передача переменных (The `dotenv` trick):**
    Переменные из родителя не всегда автоматически «протекают» в ребенка так, как тебе хочется. Если нужно передать динамическое значение (например, версию собранного артефакта) из родителя в ребенка, используй `artifacts: reports: dotenv`. Это создаст файл с переменными, который будет доступен в дочернем пайплайне.

3.  **Область видимости (Scope):**
    Дочерний пайплайн — это отдельная сущность в интерфейсе GitLab. Ты увидишь его как «вложенный» процесс. Но помни: у него свои собственные `stages`.

4.  **Рекурсия:**
    Технически, ребенок может запустить своего ребенка (Grandchild Pipeline). Но не увлекайся, иначе превратишь отладку в ад.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `include` и `trigger`?**
**О:** `include` просто копирует код из другого файла в твой текущий `.gitlab-ci.yml` (мержит их в один большой файл перед запуском). `trigger` запускает **новый, отдельный процесс** пайплайна.

**В: Как запустить дочерний пайплайн только при изменении файлов в определенной папке?**
**О:** Используй секцию `rules: changes` в родительской джобе с триггером. Это база для эффективного Monorepo.

**В: Что произойдет, если я не укажу `strategy: depend` и дочерний пайплайн упадет?**
**О:** Родительская джоба завершится успешно (Success). В логах основного пайплайна ты увидишь зеленую галочку, что может ввести команду в заблуждение.

**В: Можно ли передать артефакты из родителя в ребенка?**
**О:** Напрямую — нет, так как это разные пайплайны. Но ты можешь использовать `dotenv` отчеты для передачи переменных или настроить общие хранилища (S3/Artifactory), откуда оба пайплайна смогут забрать файлы.
</p>

# 🚀 Тема: Dynamic Child Pipelines (Динамические дочерние пайплайны)

### Что это такое? (Простыми словами)
Обычно `.gitlab-ci.yml` — это статичный файл. Ты один раз его написал, и он всегда одинаковый. Но представь, что у тебя **Monorepo** (десяток микросервисов в одном репозитории). Если ты изменил код только в `service-a`, зачем запускать тесты для `service-t`?

**Dynamic Child Pipelines** — это когда один пайплайн (Parent) во время своей работы **генерирует новый YAML-файл** (на основе логики, например, с помощью Python или Bash) и тут же запускает его как отдельный под-процесс (Child).

Это «пайплайн, который создает другие пайплайны».

---

### Как это работает (Архитектура)
Процесс всегда состоит из двух этапов:

1.  **Parent Job (Генератор):** Выполняет скрипт (скрипт-мастер), который анализирует изменения в репозитории и записывает инструкции в новый файл, например `generated-config.yml`. Этот файл **обязательно** должен быть сохранен как `artifact`.
2.  **Trigger Job (Запуск):** Специальная джоба с ключевым словом `trigger`, которая берет этот артефакт и говорит GitLab: «Эй, запусти вот этот новый конфиг!».

---

### Реализация (Пример кода)

**Файл `.gitlab-ci.yml` (Parent Pipeline):**

```yaml
stages:
  - setup
  - trigger

# 1. Шаг генерации
generate-pipeline:
  stage: setup
  script:
    - echo "stages: [test, deploy]" > generated-config.yml
    - echo "test-job:" >> generated-config.yml
    - echo "  script: echo 'Running dynamic tests...'" >> generated-config.yml
    # Здесь может быть сложный Python скрипт, который проверяет git diff
  artifacts:
    paths:
      - generated-config.yml

# 2. Шаг запуска
trigger-child-pipeline:
  stage: trigger
  trigger:
    include:
      - artifact: generated-config.yml # Берем файл из предыдущей джобы
        job: generate-pipeline       # Указываем, откуда его взять
    strategy: depend                  # Ждем завершения дочернего пайплайму (важно!)
```

---

### 💡 Нюансы и "Подводные камни" (Senior Tips)

1.  **`strategy: depend` — это критично:** Если ты не добавишь `strategy: depend`, то Parent Pipeline пометит свою работу как "Success" сразу после того, как запустит Child Pipeline, даже если сам Child упадет с ошибкой. С `depend` родитель будет ждать результата «детей».
2.  **Artifacts — это фундамент:** Если ты забудешь про секцию `artifacts: paths:` в генерирующей джобе, Trigger Job просто не увидит файл и пайплайн упадет с ошибкой "File not found".
3.  **Сложность отладки:** Отлаживать динамические пайплайны сложно, потому что ты не видишь код в репозитории — он создается «в воздухе». 
    *   *Совет:* Всегда делай так, чтобы генератор выводил содержимое итогового файла в лог (`cat generated-config.yml`). Это спасет тебе часы жизни.
4.  **Передача переменных:** Переменные из Parent Pipeline не попадают в Child автоматически (если не настроено иначе). Используй `inherit: variables: true` или явно передавай их через `trigger:variables`.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Зачем использовать это, если есть `rules:changes`?**
**О:** `rules:changes` — это круто для простых случаев (изменился файл -> запусти джобу). Но если у тебя сложная логика (например, нужно построить дерево зависимостей между 50 сервисами или динамически менять количество стадий/stages), `rules` станет нечитаемым монстром. Dynamic Pipelines дают бесконечную гибкость.

**В: Как я увижу результаты дочернего пайплайна в интерфейсе?**
**О:** GitLab создаст отдельную запись в списке Pipeline. В Parent Pipeline ты увидишь иконку "Downstream pipeline", кликнув на которую, попадешь в визуализацию выполнения Child Pipeline.

**В: Можно ли генерировать бесконечное количество пайплайнов?**
**О:** Технически — да, но GitLab имеет лимиты на количество вложенных уровней (обычно до 2-3 уровней вглубь). Не делай рекурсию без крайней необходимости.

**В: Что делать, если генератор упал?**
**О:** Если джоба `generate-pipeline` упала, Trigger Job даже не начнется. Это хорошо, так как это предотвращает запуск "пустых" или некорректных процессов.

# 🚀 Шпаргалка: Auto DevOps

**Auto DevOps** — это не «магия», которая сама пишет код. Это набор предустановленных шаблонов (CI/CD templates) и скриптов, которые GitLab применяет к твоему проекту, чтобы автоматизировать весь жизненный цикл: от сборки до деплоя в Kubernetes. 

Его философия: **Convention over Configuration** (Соглашение важнее конфигурации). Если ты следуешь стандартам GitLab, тебе не нужно писать `.gitlab-ci.yml`.

---

### 🛠 Как это работает (The Core Logic)

Auto DevOps анализирует твой репозиторий и пытается угадать, что там лежит. Для этого используются **Cloud Native Buildpacks**. Они смотрят на файлы (например, `package.json`, `requirements.txt`, `pom.xml`) и понимают: "Ага, это Node.js!" или "Это Python!".

#### 🏗 Основные этапы (Stages) Pipeline:
1.  **Build**: Использует Buildpacks для создания Docker-образа из твоего кода и пушит его в GitLab Container Registry.
2.  **Test**: Запускает Unit-тесты (если они найдены) и проверяет код на ошибки.
3.  **Security**: Самый важный этап для Enterprise. Запускает:
    *   **SAST** (анализ кода).
    *   **Dependency Scanning** (проверка библиотек на уязвимости).
    *   **Container Scanning** (проверка образа на дыры в безопасности).
4.  **Release**: Создает артефакты и готовит версию для деплоя.
5.  **Deploy**: Деплоит приложение в Kubernetes-кластер, используя **Helm charts**.

---

### 🔍 Нюансы и "Подводные камни" (Senior Insights)

1.  **Зависимость от Kubernetes**: Auto DevOps «заточен» под Kubernetes. Если у тебя нет рабочего K8s кластера, интегрированного с GitLab, этап `Deploy` будет бесполезным.
2.  **Сложность кастомизации**: Главная проблема — когда твой проект *не* вписывается в стандарт. Тебе придется переопределять (override) джобы в своем `.gitlab-py.yml`. Постепенно твой конфиг может стать сложнее, чем если бы ты писал CI/CD с нуля.
3.  **Buildpacks vs Dockerfile**: Auto DevOps предпочитает Buildpacks. Если у тебя есть свой специфический `Dockerfile`, тебе нужно настроить пайплайн так, чтобы он использовал его, иначе стандартный процесс может всё испортить.
4.  **Ресурсозатратность**: Эталонный пайплайн очень тяжелый. Он запускает кучу сканеров безопасности, что требует мощных Runner-ов и много времени.

### 💡 Когда использовать?

*   ✅ **ДА**: Для прототипов, микросервисов со стандартным стеком (Node, Python, Go) и новых команд, которым нужно "быстро и по стандартам".
*   ❌ **НЕТ**: Для legacy-монолитов, сложных систем с кастомной инфраструктурой или когда у тебя жесткие требования к специфическим шагам сборки.

### ❓ FAQ (Частые вопросы на собеседованиях)

**Q: Можно ли использовать Auto DevOps, если у меня уже есть свой `.gitlab-ci.yml`?**
**A:** Да. Как только ты создаешь файл `.gitlab-ci.yml` в корне проекта, GitLab понимает, что ты хочешь кастомизацию, и **отключает** стандартный Auto DevOps. Твой файл становится главным.

**Q: Как мне добавить свой шаг в существующий Auto DevOps пайплайн?**
**A:** Ты не "добавляешь" в него, а "расширяешь". Ты используешь ключевое слово `extends` или просто переопределяешь конкретную `job`, которую предоставляет шаблон Auto DevOps.

**Q: Что такое Cloud Native Buildpacks в контексте этой темы?**
**A:** Это технология, которая позволяет собрать Docker-образ без написания `Dockerfile`. Она сама определяет язык программирования, устанавливает зависимости и настраивает среду выполнения. Именно это делает Auto DevOps "умным".

**Q: Где хранятся секреты для деплоя в Auto DevOps?**
**A:** Они должны быть настроены в **CI/CD Variables** твоего проекта или группы (например, `KUBERNETES_SERVICE_HOST`, доступы к кластеру). Без них этап Deploy упадет.

# 🧠 Шпаргалка: Архитектура GitLab Runner

Если коротко: **GitLab Server** — это «мозг» (планировщик), а **GitLab Runner** — это «руки» (исполнитель). Сервер говорит, *что* нужно сделать, а Раннер берет задачу и делает её.

### 1. Модель взаимодействия: Polling (Опрос)
Это критически важный нюанс. В отличие от многих других систем, GitLab Server **не подключается** к Runner-у. 
*   **Как это работает:** Runner сам периодически «стучится» к GitLab Server с вопросом: *«Есть для меня работа?»*.
*   **Почему это круто (Security):** Твой Runner может находиться за NAT или в закрытом контуре без публичного IP. Тебе не нужно открывать входящие порты на сервере с раннерами. Нужен только исходящий доступ к GitLab.

### 2. Основные компоненты
Архитектура состоит из двух уровней:
1.  **Runner Manager (Диспетчер):** Это сам процесс, запущенный на хосте. Он отвечает за регистрацию в GitLab, получение заданий, управление очередью и жизненным цикту задач.
2.  **Executor (Исполнитель):** Это среда, внутри которой физически запускается твой код (скрипт `gitlab-ci.yml`). 

### 3. Типы Executor-ов (Где живет код)
Выбор экзекутора определяет уровень изоляции и безопасности:

*   **Shell:** Код выполняется прямо на хостовой машине, где стоит Runner.
    *   *Плюсы:* Максимальная скорость (нет оверхеда на запуск контейнеров).
    *   *Минусы:* **Zero isolation**. Если один job удалит всё с диска или поднимет процесс-вирус, пострадает весь сервер. Нельзя использовать для публичных проектов.
*   **Docker:** Каждый job запускается в отдельном изолированном контейнере.
    *   *Плюсы:* Чистая среда, предсказуемость, легко масштабировать. Стандарт индустрии.
    *   *Минусы:* Нужно управлять образами и кэшем.
*   **Kubernetes:** Каждый job — это отдельный Pod в кластере.
    *   *Плюсы:* Бесконечное (почти) масштабирование, идеальная интеграция с Cloud Native инфраструктурой.
    *   *Минусы:* Высокая сложность настройки.
*   **VirtualBox / VMware:** Запуск в полноценной виртуальной машине.
    *   *Плюсы:* Максимальная изоляция (уровень гипервизора).
    *   *Минусы:* Очень медленно и ресурсозатратно.

### 4. Конфигурация и управление (`config.toml`)
Все настройки раннера живут в файле `/etc/gitlab-runner/config.toml`. 
**Ключевые параметры, которые нужно знать:**
*   `concurrent`: Сколько **всего** заданий может выполнять один Runner Manager одновременно (суммарно по всем регистрациям). Если поставишь 1, а придет 10 задач — 9 будут ждать в очереди.
*   `limit`: Сколько заданий может выполнять конкретный тип раннера.

*   `tags`: Метки. Позволяют разделять задачи. Например, джобы для Android должны уходить на раннеры с тегом `android`, а не на легкие Docker-раннеры.

### 5. Нюансы и "Подводные камни" (Senior Tips)
*   **Zombie Processes:** При использовании Docker executor, если твой скрипт запускает фоновые процессы, они могут «зависнуть» и превратиться в зомби, забивая память. Используй `--init` в настройках, чтобы корректно убивать процессы.
*   **Cache vs Artifacts:** Раннер не хранит состояние между запусками сам по себе. Если тебе нужно передать файл из Job A в Job B — это **Artifacts**. Если нужно ускорить сборку (например, `node_modules`) — это **Cache**. Но помни: кэш может быть недоступен, если джоба улетела на другой раннер без общего хранилища.
*   **Docker-in-Docker (DinD):** Если тебе нужно собирать Docker-образ внутри CI, тебе придется запускать контейнер в привилегированном режиме (`privileged = true`). Это дыра в безопасности. Всегда старайся использовать **Kaniko** вместо DinD — он безопаснее и не требует root-прав на хосте.

### ❓ FAQ (Частые вопросы)

**В: Можно ли использовать один Runner для разных проектов?**
**О:** Да, это стандартная практика. Ты регистрируешь один Runner на уровне Instance (если у тебя GitLab Self-managed) или на уровне Group, и он будет обслуживать все вложенные проекты.

**В: Что делать, если джобы выполняются слишком медленно?**
**О:** 1. Проверь `concurrent` в `config.toml`. 2. Проверь, не перегружен ли диск (I/O wait). 3. Используй Docker Executor и кэширование зависимостей. 4. Если ресурсов мало — добавь больше раннеров с нужными тегами.

**В: В чем разница между `tags` в GitLab CI и `tags` в настройках Runner?**
**О:** Это две стороны одной медали. В `.gitlab-ci.yml` ты пишешь: *"Мне нужен раннер с тегом `gpu`"*. А в настройках Runner ты говоришь: *"Я — раннер, и у меня есть тег `gpu`"*. Если теги не совпадут — джоба будет висеть в статусе `pending` вечно.

**В: Как обеспечить изоляцию, если я боюсь за безопасность?**
**О:** Забудь про Shell executor. Используй Docker или Kubernetes. И никогда не ставь `privileged = true` без крайней необходимости.

# 🧠 Шпаргалка: GitLab Runner Executors

**Executor (Исполнитель)** — это среда, в которой физически запускаются команды из твоего `.gitlab-ci.yml`. Представь, что Runner — это «дирижер», а Executor — это «инструмент» (скрипка, барабан или пианино), на котором исполняется конкретная нота (job).

---

### 1. Shell Executor
Самый простой и «опасный» тип. Команды запускаются прямо в терминале операционной системы, где установлен Runner.

*   **Как работает:** Runner берет команды из CI и просто вставляет их в `bash` или `powershell` хостовой машины.
*   **Плюсы:** 
    *   Максимальная скорость (нет накладных расходов на запуск контейнеров).
    *   Легко использовать инструменты, уже установленные в системе.
*   **Минусы (Нюансы):** 
    *   **Dirty Environment (Грязная среда):** Если одна джоба создала файл или установила библиотеку, следующая джоба это увидит. Это приводит к «магическим» ошибкам, которые невозможно воспроизвести.
    *   **Безопасность:** Если злоумышленник подсунет вредоносный код в MR, он получит доступ ко всей хостовой машине.
*   **Senior Pro-tip:** Используй Shell **только** для очень простых задач или на изолированных машинах, где ты полностью контролируешь окружение.

### 2. Docker Executor
Золотой стандарт современной разработки. Каждая джоба запускается в отдельном, чистом контейнере.

*   **Как работает:** Runner берет образ (например, `python:3.9`), поднимает контейнер и выполняет команды внутри него.
*   **Плюсы:**
    *   **Изоляция:** Каждая длоба начинается с «чистого листа».
    *   **Воспроизводимость:** Ты точно знаешь, что код соберется одинаково и на ноутбуке разработчика, и в GitLab.
    *   **Гибкость:** В `.gitlab-ci.yml` ты можешь для каждой джобы указать свой `image`.
*   **Минусы (Нюансы):** 
    *   **Docker-in-Docker (DinD):** Если тебе нужно собирать Docker-образы внутри пайплайна, придется настраивать сложную и небезопасную схему DinD.
    *   Нужно следить за очисткой старых образов на хосте, иначе диск забьется очень быстро.
*   **Senior Pro-tip:** Это выбор №1 для 90% задач. Всегда старайся использовать Docker Executor.

### 3. Kubernetes Executor
Вершина эволюции. Runner запускает каждую джобу как отдельный **Pod** в кластере Kubernetes.

*   **Как работает:** Runner общается с API Kubernetes, создает Pod, выполняет работу и удаляет его.
*   **Плюсы:**
    *   **Бесконечное масштабирование:** Если у тебя 100 параллельных джоб, K8s просто поднимет 100 подов (если есть ресурсы в кластере).
    *   **Высокая доступность:** Если упадет один узел (node), джоба может переехать на другой.

*   **Минусы (Нюансы):**
    *   **Сложность:** Требует наличия и глубоких знаний кластера Kubernetes.
    *   Долгий старт (overhead) по сравнению с Docker Executor из-за создания Pod'а.
*   **Senior Pro-tip:** Используй, если у тебя уже есть инфраструктура K8s и тебе нужно обрабатывать огромные объемы параллельных задач.

### 4. VirtualBox / SSH / Virtual Machine Executors
Запуск джоб внутри виртуальных машин.

*   **Как работает:** Runner подключается по SSH к другой машине или управляет гипервизором для запуска VM.
*   **Плюсы:** Максимальная изоляция (на уровне ядра ОС), можно тестировать специфические настройки сети или ядра.
*   **Минусы:** Очень медленно, тяжело масштабировать, потребляет много ресурсов.
*   **Senior Pro-tip:** Применяется крайне редко — только для задач тестирования низкоуровневого ПО или специфического железа.

**В: Что произойдет, если я забуду очистить Docker-образы на Runner с Docker Executor?**
**О:** Твой сервер со временем «умрет» из-за нехватки места (Disk Pressure). Всегда настраивай `cron` задачу для `docker system prune` или используй автоматическую очистку.

**В: Можно ли использовать один и тот же Runner с разными Executor'ами?**
**О:** Нет. Один экземпляр GitLab Runner (процесс) работает с одним конкретным Executor, указанным в `config.toml`. Но ты можешь запустить *несколько разных* инстансов Runner'а на одной машине: один с Shell, другой с Docker.

**В: В чем главная разница между Docker и Kubernetes Executor для разработчика?**
**О:** Для разработчика разницы почти нет (он пишет `image: node:latest`). Разница в **инфраструктуре**: Docker требует наличия Docker Engine на сервере, а K8s Executor требует работающего кластера и прав доступа к нему.

**В: Как передать файлы между джобами, если у нас Docker Executor (где среда чистая)?**
**О:** Используй механизм **Artifacts** (для передачи результатов работы) или **Cache** (для ускорения повторных сборок, например, папки `node_modules`).

# 🚀 Шпаргалка: Регистрация и настройка GitLab Runner

### 1. Суть процесса
Представь, что GitLab — это **Директор**, который раздает задачи. А Runner — это **Рабочий**. Директору не важно, где сидит рабочий (дома, в офисе или на другом сервере), главное, чтобы рабочий сообщил: «Я готов, дай задачу». Регистрация — это процесс знакомства Рабочего с Директором и выдачи ему «пропуска» (токена).

### 2. Типы раннеров (Важно для архитектуры)
Прежде чем регистрировать, нужно понять, чьи это будут рабочие:
*   **Shared Runners (Общие):** Доступны всем проектам в инстансе GitLab. Идеально для мелких задач.
*   / **Group Runners (Групповые):** Доступны только проектам внутри конкретной группы. Золотая середина для больших компаний.
*   **Specific Runners (Проектные):** Привязаны к одному конкретному проекту. Нужны, когда нужны супер-специфичные ресурсы (например, GPU или доступ к закрытой сети).

### 3. Процесс регистрации (`gitlab-runner register`)
Сейчас в GitLab происходит переход от старых *Registration Tokens* к новым *Authentication Tokens*. 

**Алгоритм действий:**
1.  **Получение токена:** В интерфейсе GitLab (в настройках проекта/группы/инстанса) создаешь новый раннер и копируешь полученный токен.
2.  **Запуск команды:** На сервере, где стоит Runner, запускаешь:
    ```bash
    gitlab-runner register
    ```
3.  **Интерактивный опрос (что нужно знать):**
    *   **GitLab URL:** Адрес твоего GitLab.
    *   **Registration Token:** Тот самый «пропуск».
    *   **Executor:** *Самый важный выбор*. (Смотри ниже).
    *   **Description/Tags:** Имя раннера и метки (теги), по которым GitLab поймет, что эта задача подходит именно этому раннеку.

### 4. Выбор Executor (Сердце настройки)
От этого зависит, насколько «чистым» будет твой билд:
*   **`shell`**: Запускает команды прямо в терминале хостовой машины. 
    *   *Нюанс:* **Опасно и грязно.** Если один билд установит библиотеку, она останется для следующего. Легко «замусорить» сервер.
*   **`docker`**: (Industry Standard) Каждый билд запускается в изолированном контейнере. 
    *   *Нюанс:* Самый надежный вариант. После завершения джобы контейнер удаляется, среда всегда чистая.
*   **`kubernetes`**: Запускает каждую джобу как отдельный Pod в кластере. 
    *   *Нюанс:* Идеально для масштабирования, но требует наличия и настройки K8s.

### 5. Конфигурация: Файл `config.toml`
Это «мозг» раннера. Находится обычно в `/etc/gitlab-runner/config.toml`.

**Что там нужно крутить (Senior Tips):**
*   **`concurrent`**: Сколько всего джоб может выполнять один экземпляр раннера одновременно. Если поставишь `1`, задачи будут стоять в очереди. Если много — забьешь CPU/RAM сервера.
*   **`limit`**: Максимум джоб для конкретного сектора (по тегам).
*   **`cache`**: Настройка путей для кэширования (чтобы не качать `node_modules` каждый раз).
*   **`pull_policy`**: Как раннер должен забирать Docker-образ (`always`, `if-not-present`). Ставь `always`, чтобы всегда иметь свежий образ, но это создает трафик.

### 6. Теги (Tags) — Твой навигатор
Если ты зарегистрировал раннер с тегом `python-3.9`, то джоба в `.gitlab-ci.yml` **не запустится** на нем, если в ней не указан этот же тег. Это механизм распределения нагрузки.

### ❓ FAQ (Частые вопросы на собеседованиях/в работе)

**В: Что делать, если раннер зарегистрирован, но джобы не запускаются?**
**О:** Проверь три вещи: 
1. Статус сервиса (`gitlab-runner status`).
2. Совпадают ли `tags` в `.gitlab-ключе` и в настройках раннера.
3. Не забита ли очередь (параметр `concurrent` в `config.toml`).

**В: В чем разница между Registration Token и Authentication Token?**
**О:** Регистрационный токен использовался только для первичного «знакомства». Аутентификационный токен — это постоянный ключ, который раннер использует для работы. GitLab уходит от первого в сторону второго ради безопасности (чтобы нельзя было бесконечно плодить раннеры через один старый токен).

**В: Можно ли использовать один Runner для разных проектов?**
**О:** Да, если это Shared Runner или Group Runner. Но помни про изоляцию: если ты используешь `shell` executor, проекты могут мешать друг другу. Используй `docker`.

**В: Как ускорить пайплайны при регистрации нового раннера?**
**О:** Настрой кэширование (`cache`) в `config.toml` и используй Docker-executor с предварительно скачанными образами (pull_policy: `if-not-present`).

# 🚀 Шпаргалка: Масштабирование в GitLab

Масштабирование — это процесс увеличения возможностей системы при росте количества пользователей, репозиториев или пайплайнов. Мы разделяем его на два уровня: **Runner Scaling** (где бежит код) и **GitLab Instance Scaling** (где живет код).

---

## 1. Масштабирование Runners (Execution Scaling)
*Цель: Чтобы пайплайны не стояли в очереди, а выполнялись параллельно.*

Когда джоб много, один раннер не справится. Нам нужно увеличивать количество «рабочих рук».

### Основные подходы:
1.  **Vertical Scaling (Вертикальное):** Увеличение ресурсов (CPU/RAM) на существующем раннере. 
    *   *Когда:* Если джобы тяжелые (компиляция C++, сборка тяжелых Docker-образов).
2.  **Horizontal Scaling (Горизонтальное):** Добавление новых раннеров.
    *   *Когда:* Если джоб много, но они легкие (тесты, линтеры), и они просто стоят в очереди.

### Технологии масштабирования:
*   **Docker Machine (Legacy/Classic):** Автоматическое создание виртуальных машин (например, в AWS или GCP) под каждую задачу и их удаление после завершения.
*   **Kubernetes Executor (Modern Standard):** Самый мощный способ. GitLab создает **Pod** (временный контейнер) в K8s для каждой джобы. Как только джоба выполнена — Pod удаляется. 
    *   *Плюс:* Бесконечное масштабирование (пока есть ресурсы в кластере).
*   **Concurrency Control:** В файле `config.toml` на раннере параметр `concurrent` определяет, сколько джоб один раннер может запускать одновременно. **Важно:** не ставь слишком много, иначе убьешь CPU/RAM сервера.

### 💡 Нюансы (Senior Tips):
*   **Tags & Labels:** Используй теги, чтобы распределять нагрузку. Например: тяжелые задачи — на мощные раннеры с тегом `high-cpu`, легкие — на дешевые.
*   **Docker Layer Caching:** При масштабировании на разные ноды кэш Docker-слоев теряется. Используй **Distributed Cache** (S3/Minio), чтобы раннеры могли подтягивать кэш друг друга.

---

## 2. Масштабирование GitLab Instance (Infrastructure Scaling)
*Цель: Чтобы сам GitLab не «упал», когда тысячи людей одновременно делают `git push` или смотрят MR.*

### Уровни архитектуры:
1.  **Database (PostgreSQL):** Сердце метаданных. При росте нагрузки переносим БД на отдельный мощный сервер (Managed DB).
2.  **Redis:** Хранит кэш и очереди задач. При масштабировании — выносим на отдельный инстанс.
/3.  **Gitaly (Самое важное!):** Это сервис, который отвечает за работу с Git-репозиториями. 
    *   **Gitaly Cluster:** Если репозиториев тысячи, один сервер Gitaly станет узким местом (I/O bottleneck). Решение — кластер из нескольких нод Gitaly с репликацией. Это устраняет Single Point of Failure (SPOF).
4.  **Object Storage (S3/Minio):** **Золотое правило масштабирования.** Никогда не храни артефакты, LFS и бэкапы на диске сервера GitLab. Выноси их в S3-совместимое хранилище. Это позволяет разгрузить диск сервера и упростить его масштабирование.

### Глобальное масштабирование:
*   **GitLab Geo:** Если у тебя команды в США, Европе и Азии. Позволяет создавать реплики GitLab в разных регионах (Read-only реплики), чтобы разработчики не качали гигабайты кода через океан с задержкой.

---

## 🧠 FAQ: Часто задаваемые вопросы

**В: У меня растет очередь джоб в GitLab, что делать первым делом?**
**О:** Сначала проверь `concurrent` в `config.toml`. Если он уперся в потолок — добавь новый Runner (Horizontal Scaling). Если раннеры есть, но джобы падают по Out of Memory — увеличивай ресурсы раннера (Vertical Scaling).

**В: Что такое "узкое место" (Bottleneck) при масштабировании GitLab?**
**О:** Чаще всего это **Gitaly** (дисковые операции с Git) или **Disk I/O** на сервере с артефактами. Если ты не вынес артефакты в S3, твой сервер «умрет» от переполнения диска очень быстро.

**В: Можно ли масштабировать GitLab, просто добавляя RAM на один сервер?**
**О:** Это называется Vertical Scaling. Это работает до определенного предела (предела физического железа). Для настоящего Enterprise-уровня нужно только Horizontal Scaling (Gitaly Cluster, распределенная БД, S3).

**В: В чем разница между масштабированием Runner и масштабированием GitLab?**
**О:** Масштабирование Runner решает проблему "медленной сборки". Масштабирование GitLab решает проблему "недоступности интерфейса и API". Это разные задачи.

# 🛠 Шпаргалка: Масштабирование через Tags & Labels (GitLab Runners)

В GitLab Runner-ы — это рабочие лошадки. Но если у тебя один раннер на всё, ты быстро упрешься в потолок. Чтобы эффективно масштабироваться, тебе нужно уметь направлять конкретные задачи на конкретные исполнители. Для этого используются **Tags**.

### 1. Основная концепция
Представь, что GitLab — это диспетчерская, а Runner-ы — это парк машин (грузовики, легковые, рефрижераторы).
*   **Runner Tags:** Это «наклейки» на машинах. При регистрации раннера ты говоришь: «Я — грузовик» (`tag: heavy-duty`).
*   **Job Tags:** Это требования в заказе. В `.gitlab-ci.yml` ты пишешь: «Мне нужен `heavy-disptach`».

Если теги в задаче не совпадают с тегами раннера, задача будет висеть в статусе `pending` вечно.

### 2. Как это работает (Механика)
*   **На стороне Runner:** При регистрации (`gitlab-runner register`) ты указываешь список тегов через флаг `--tag-list`. Один раннер может иметь много тегов: `docker, linux, high-cpu`.
*   **На стороне Job:** В файле `.gitlab-ci.yml` ты используешь ключевое слово `tags`.

```yaml
build_job:
  stage: build
  script:
    - echo "Building heavy application..."
  tags:
    - docker  # Задача пойдет только на раннер, у которого есть этот тег
    - high-cpu # И обязательно должен быть еще этот тег
```

### 3. Нюансы и «Подводные камни» (Senior level)

#### ⚠️ Правило пересечения (Intersection)
Если ты указал в задаче **два** тега (`docker` и `linux`), GitLab будет искать раннер, у которого есть **оба** этих тега одновременно. Если у раннера есть только `docker`, задача его не выберет.

#### ⚠️ Ловушка «Безтеговых» раннеров (The Untagged Runner Trap)
Это самая частая причина хаоса. 
*   Если у раннера **нет ни одного тега**, он считается «универсальным солдатом». Он будет подхватывать **любую** задачу, в которой вообще не указаны теги.
*   **Проблема:** Если ты создашь задачу без тегов (забыл написать), она может упасть на слабом раннере, предназначенном для мелких задач, и забить ему очередь или просто упасть по нехватке памяти.
*   **Best Practice:** Всегда вешай теги на свои основные раннеры. Оставляй без тегов только самые базовые, «дежурные» раннеры.

#### ⚠️ Иерархия и масштабирование
При масштабировании (например, в Kubernetes) используй теги для разделения сред:
*   `tags: [production]` — только для деплоя на прод.
*   `tags: [gpu]` — только для задач машинного обучения.
*   `tags: [macos]` — только для сборки iOS приложений.

### 4. Различие: Tags vs Labels
Не путай!
*   **Runner Tags:** Инструмент маршрутизации задач (как мы разобрали).
*   **Issue/MR Labels:** Это метаданные для управления проектом (метки `bug`, `feature`, `priority: high`). Они не влияют на то, *где* выполнится код, но влияют на то, *кто* его будет делать.

---

### ❓ FAQ (Частые вопросы)

**В: Что делать, если джоба висит в статусе `pending` и не запускается?**
**О:** Проверь два момента: 1) Есть ли вообще активный раннер с точно такими же тегами? 2) Не слишком ли много тегов ты указал в задаче (помни, что нужно полное совпадение всех перечисленных тегов)?

**В: Можно ли использовать подстановочные знаки (wildcards), например `docker-*`?**
**О:** Нет. В GitLab Runner tags — это точное строковое соответствие. Никаких `*` или `?`.

**В: Как лучше всего называть теги для масштабирования?**
**О:** Используй семантическую группировку: `[os]-[executor]-[capability]`. 
Пример: `linux-docker-arm64` или `windows-shell-large`. Это позволит тебе очень гибко комбинировать задачи.

**В: Если я добавлю новый тег раннеру через интерфейс GitLab, подхватит ли он старые задачи?**
**О:** Да, как только конфиг раннера обновится (или при следующем перезапуске/обработке джобы), он станет доступен для задач с этим тегом. Но помни: сам процесс добавления тега в UI не меняет `config.toml` на самом сервере мгновенно, но GitLab видит изменения в своей базе.

# 🛠 Шпаргалка: Maintenance (GitLab & Runners)

### 1. Обслуживание GitLab Runners (Execution Layer)
Раннеры — это «рабочие лошадки». Они потребляют ресурсы и со временем превращаются в свалку мусора.

*   **Очистка Docker-мусора (Docker Cleanup):**
    Если ты используешь `docker` executor, каждый билд оставляет за собой слои, остановленные контейнеters и неиспользуемые сети.
    *   *Что делать:* Настрой периодический `docker system prune -f` или используй cron-задачу. 
    *   *Нюанс:* Будь осторожен с `--volumes`, чтобы не удалить кэш, который ускоряет сборку.
*   **Обновление Runner-а:**
    Версия Runner-а должна быть совместима с версией GitLab Server. 
    *   *Правило:* Всегда проверяй **Compatibility Matrix**. Если сервер обновился до мажорной версии (например, с 15.x на 16.x), Runner нужно обновить в первую очередь.
*   **Мониторинг ресурсов:**
    Раннеры могут «съедать» всю CPU и RAM хоста.
    *   *Что делать:* Настрой алерты на использование диска (Disk Usage) и CPU Load. Если диск забьется логами или артефактами — пайплайны встанут.
*   **Управление `config.toml`:**
    Это мозг раннера. 
    *   *Senior Tip:* Храни конфигурацию раннеров в Git (Infrastructure as Code). Не меняй конфиг руками на сервере — если сервер упадет, ты не вспомнишь, какие `tags` или `limits` ты прописал.

---

### 2. Обслуживание GitLab Server (Platform Layer)
Здесь живет вся твоя интеллектуальная собственность. Ошибки здесь стоят очень дорого.

*   **Стратегия Backup & Restore (Самое важное!):**
    Бэкап, который не проверяли на восстановление — это не бэкап, а иллюзия безопасности.
    *   *Что делать:* Настрой `gitlab-rake gitlab:backup:create`. 
    *   *Нюанс:* Бэкап базы данных **не включает** в себя файлы репозиториев (git data) и секреты (`gitlab-secrets.json`). Если ты потеряешь `.json` файл, ты не сможешь расшифровать базу! Всегда копируй `/etc/gitlab/gitlab-secrets.json` отдельно.
*   **Upgrade Path (Путь обновления):**
    В GitLab нельзя просто прыгнуть с версии 14.0 на 16.0. 
    *   *Правило:* Существуют «обязательные промежуточные версии» (upgrade checkpoints). Всегда читай **Official Upgrade Guide**. Пропуск одной важной минорной версии может сломать миграцию базы данных.
*   **Очистка старых артефактов и кэша:**
    GitLab хранит результаты прошлых билдов. Со временем папка `artifacts` раздувается до терабайт.
    *   *Что делать:* Настрой **Expiration Policy** в настройках проекта (например, удалять артефакты старше 30 дней).
*   **Мониторинг здоровья (Health Checks):**
    Используй встроенный Prometheus и Grafana. Следи за метриками: `GitLab.Database.Connections`, `GitLab.Sidekiq.Queue_Size` (если очередь задач растет — сервер не справляется).

### 💡 Senior Nuances (Тонкие моменты)

1.  **Sidekiq Lag:** Если ты видишь, что Merge Request создался, но не пришло уведомление или не запустился пайплайн — проверь **Sidekiq**. Это фоновый обработчик задач. Если его очередь забита, GitLab «тупит».
2.  **Log Rotation:** Логи GitLab (`/var/log/gitlab`) могут съесть весь диск. Убедись, что `logrotate` настроен правильно.
3.  **Database Vacuuming:** Для PostgreSQL (который внутри GitLab) важно следить за тем, чтобы старые данные удалялись и не раздували таблицы (bloat).

### ❓ FAQ (Частые вопросы на собеседованиях/в работе)

**В: Что произойдет, если я обновлю GitLab Server, но забуду обновить Runner?**
**О:** В большинстве случаев всё будет работать, но ты потеряешь доступ к новым фичам CI/CD. Если в новом GitLab изменился формат `.gitlab-ci.yml`, старый Runner просто не поймет синтаксис и упадет с ошибкой парсинга.

**В: Я сделал бэкап базы данных. Достаточно ли этого для полного восстановления?**
**О:** Нет! Тебе критически необходимы три вещи: 1) Бэкап БД, 2) Файлы репозиториев (git data), 3) `gitlab-secrets.json`. Без третьего пункта база будет бесполезна.

**В: Как быстро понять, почему пайплайны не запускаются?**
**О:** Первым делом смотри в **Sidekiq Queue**. Если задачи висят в статусе `pending` — значит, либо нет свободных раннеров, либо Sidekiq перегружен и не может их подхватить.

**В: Как бороться с тем, что Docker-раннер постоянно забивает диск?**
**О:** Настрой `cron` задачу на выполнение `docker system prune -af --volumes` (с осторожностью) или используй специализированные инструменты очистки артефактов GitLab API.

# 🛡️ Шпаргалка: SAST (Static Application Security Testing)

### 💡 Что это такое простыми словами?
**SAST** — это «взгляд в код без его запуска». Представь, что ты проверяешь чертеж здания на наличие ошибок в конструкции еще до того, как начали заливать бетон. Мы сканируем исходный код (текст), ищем опасные паттер deны (например, забытые пароли или функции, позволяющие взломать систему) и выводим отчет.

В GitLab SAST — это часть стратегии **Shift Left** (сдвиг безопасности влево). Мы хотим найти дыру в коде на этапе коммита, а не когда хакер уже взломал наш сервер.

---

### 🛠️ Как это работает в GitLab CI/CD
GitLab не изобретает велосипед, он использует набор готовых анализаторов (Semgrep, Flawfinder, Bandit и др.) под каждый язык программирования.

**Как включить:**
Самый простой способ — подключить официальный шаблон в свой `.gitlab-ci.yml`:

```yaml
include:
  - template: Security/SAST.gitlab-ci.yml
```

После этого GitLab сам определит языки в твоем репозитории и запустит нужные сканеры.

---

### 🔍 Ключевые компоненты
1.  **Analyzers:** Специальные Docker-контейнеры, которые «понимают» конкретный язык (Python, JS, Go, Java и т.д.).
2.  **SAST Report:** Результат сканирования сохраняется в файл `gl-sast-report.json`. Именно его GitLab использует, чтобы отрисовать красивые графики в интерфейсе.
3.  **Vulnerability Report:** Главный дашборд (в версии Ultimate), где видны все найденные уязвимости по всем проектам.

---

### ⚠️ Нюансы и «подводные камни» (Senior Tips)

1.  **False Positives (Ложные срабатывания):** Это главная боль. Инструмент может сказать: *"Эй, тут дыра!"*, а на самом деле это безопасный код. Если ложных срабатываний слишком много, разработчики начнут игнорировать SAST совсем.
    *   *Что делать:* Настраивай исключения (например, через файлы `.semgrepignore`).
2.  **SAST vs SCA (Не путай!):** 
    *   **SAST** проверяет **ТВОЙ** код (то, что ты написал).
    *   **SCA (Dependency Scanning)** проверяет **ЧУЖОЙ** код (библиотеки и пакеты, которые ты скачал через `npm` или `pip`).
3.  **Скорость пайплайна:** Сканирование больших репозиториев может занимать много времени. 
    *   *Совет:* Используй `rules`, чтобы запускать SAST не на каждый коммит, а только при создании Merge Request или при пуше в ветки `main`/`develop`.
4.  **Context Blindness:** SAST не видит «картину целиком». Он может найти уязвимость в коде, но не знать, что этот код защищен внешним WAF (Web Application Firewall) или специфическими настройками сервера.

---

### 🚀 Best Practices
*   **Fail the pipeline:** Настрой пайплайн так, чтобы он падал, если найдены уязвимости уровня `Critical` или `High`. Это заставит команду исправлять ошибки сразу.
*   **Code Owners:** Используй функционал `Code Owners`, чтобы владельцы критических модулей автоматически становились ревьюерами при обнаружении проблем.
*   **Постепенное внедрение:** Не включай все проверки сразу на старый проект — ты утонешь в тысяче алертов. Начни с самых критичных.

# 🛡️ DAST (Dynamic Application Security Testing)

### Что это такое? (Простыми словами)
Если **SAST** — это проверка «чертежей» вашего приложения (анализ исходного кода), то **DAST** — это проверка **уже построенного здания**. 

DAST не смотрит в код. Он имитирует действия хакера: стучится в работающее приложение, подставляет вредоуровневые символы в формы, пытается взломать авторизацию и ищет дыры в протоколах (HTTP/HTTPS). Это **Black-box testing** (тестирование «черного ящика»).

### Как это работает в GitLab CI/CD
В GitLab DAST обычно запускается на этапе, когда приложение уже развернуто (например, на `review-app` или `staging`). 

1.  **Trigger:** Пайплайн доходит до стадии `test`.
2.  **Execution:** Запускается контейнер (обычно на базе OWASP ZAP), который получает URL вашего приложения.
3.  **Attack:** Сканер «простукивает» все доступные эндпоинты, проверяя их на уязвимости (SQL-инъекции, XSS, небезопасные заголовки, ошибки конфигурации).
4.  **Report:** Результаты парсятся и отображаются в GitLab Security Dashboard или прикрепляются к Merge Request.

### Ключевые нюансы (Senior level)

1.  **Зависимость от окружения:** DAST бесполезен, если у вас нет работающего URL. **Главная ошибка новичков:** пытаться запустить DAST до того, как завершился этап `deploy`.
2.  **Проблема авторизации:** Сканер «видит» только то, что доступно публично. Если ваше приложение требует логина, вам нужно передать сканеру учетные данные (через переменные или скрипты аутентентификации), иначе он не протестирует защищенные разделы (личный кабинет, админку).
3.  **Время выполнения:** DAST — это **медленно**. В отличие от SAST, который пролетает код за минуты, DAST может «ползать» по сайту часами. 
    *   *Совет:* Не запускайте полный глубокий сканер на каждый коммит в ветку. Используйте быстрые (baseline) сканы для MR и полные сканы — по расписанию (nightly builds).
4.  **False Positives (Ложные срабатывания):** DAST часто ошибается, принимая странный ответ сервера за атаку. Вам нужно уметь настраивать `ignore` списки или конфигурационные файлы, чтобы не «заспамить» команду разработчиков ложными алертами.
5.  **Влияние на данные:** Будьте осторожны! DAST может отправить запрос на удаление данных или заполнение форм тысячами мусорных записей. **Никогда не запускайте агрессивный DAST на Production-базе.**

### Чек-лист настройки в `.gitlab-ci.yml`
*   [ ] Использовать готовый шаблон GitLab (`Jobs/DAST.gitlab-ci.yml`).
*   [ ] Определить переменную `DAST_URL` (адрес, который нужно атаковать).
*   [ ] Настроить переменные для аутентификации, если приложение закрыто паролем.
*   [ ] Использовать `artifacts`, чтобы видеть отчеты в интерфейсе GitLab.

### ❓ FAQ (Частые вопросы)

**В: В чем фундаментальная разница между SAST и DAST?**
**О:** SAST смотрит на **код** (находит ошибки в логике написания), DAST смотрит на **результат работы** (находит ошибки в конфигурации сервера, SSL-сертификатах и уязвимости, которые проявляются только при взаимодействии).

**В: Можно ли запускать DAST прямо на Production?**
**О:** Технически — да. Но это крайне рискованно. Сканер может вызвать отказ в обслуживании (DoS), забить базу данных мусором или случайно триггернуть критические бизнес-процессы (например, рассылку писем всем клиентам). Лучше всего использовать `Staging` или `Review Apps`.

**В: Почему мой DAST сканер не нашел уязвимость в API?**
**О:** Скорее всего, сканер просто "не увидел" эндпоинты. В отличие от браузера, сканер не знает о существовании скрытых путей `/api/v1/delete-user`. Для работы с API нужно передавать сканеру файл спецификации (например, **Swagger/OpenAPI**).

**В: Как уменьшить время прохождения пайплайна при использовании DAST?**
**О:** Используйте режим `baseline scan` вместо `full scan` для ежедневных проверок. Настройте правила (`rules`), чтобы полный тяжелый сканер запускался только при слиянии (merge) в основную ветку.

# 🛡️ Шпаргалка: Dependency Scanning (SCA)

### 🧠 Что это такое?
**Dependency Scanning** — это процесс проверки сторонних библиотек и пакетов (твоих зависимостей), которые ты используешь в проекте, на наличие известных уязвимостей. 

В мире безопасности это называется **SCA (Software Composition Analysis)**. Если SAST проверяет *твой* код, то Dependency Scanning проверяет *чужой* код, который ты скачал через `npm`, `pip`, `maven` или `go mod`.

### ⚙️ Как это работает в GitLab
1.  **Входные данные:** Сканер ищет файлы манифестов (например, `package-lock.json`, `Gemfile.lock`, `requirements.txt`, `pom.xml`).
2.  **Процесс:** Инструмент (чаще всего **Gemnasium**) анализирует список библиотек и их версий, а затем сверяет их с базой данных известных уязвимостей (**CVE** — Common Vulnerabilities and Exposures).
3.  **Результат:** GitLab генерирует отчет в формате JSON, который превращается в красивую таблицу в интерфейсе Merge Request и Security Dashboard.

### 🚀 Как внедрить (Pipeline)
Самый правильный способ — использовать готовый шаблон GitLab. Не нужно писать свои скрипты, просто добавь это в `.gitlab-ci.yml`:

```yaml
include:
  - template: Security/Dependency-lockfile-scanning.gitlab-ci.yml
  # Или полный набор для всех типов сканирования:
  - template: Security/Dependency-Scanning.gitlab-ci.yml
```

### 🔍 Нюансы и "подводные камни" (Senior Level)

*   **Manifest vs Lockfile:** Это критически важно. Сканирование файла `package.json` (манифест) дает лишь примерное представление, так как версии там могут быть указаны диапазоном (`^1.2.0`). Сканирование **Lock-файла** (`package-lock.json`, `poetry.lock`) — это "золотой стандарт", потому что там зафиксирована конкретная версия, которая реально попадет в продакшн.
*   **Транзитивные зависимости (Transitive Dependencies):** Это зависимости твоих зависимостей. Ты подключил библиотеку `A`, а она внутри себя тянет уязвимую библиотеку `B`. Хороший сканер должен уметь "прокапываться" до самого низа дерева зависимостей.
*   **False Positives (Ложные срабатывания):** Иногда уязвимость есть, но твой код её не использует (unreachable code). В GitLab можно помечать уязвимости как `Dismissed` с комментарием, чтобы они не спамили в отчетах.
*   **Vulnerability Management:** Dependency Scanning — это не разовое действие. Это часть жизненного цикла. Если завтра в популярной библиотеке найдут дыру, твой старый пайплайн должен об этом сообщить.
*   **Security Gate:** Ты можешь настроить пайплайн так, чтобы он **падал (fail)**, если обнаружена уязвимость с уровнем критичности `Critical` или `High`. Это и есть настоящий DevSecOps.

### ❓ FAQ (Часто задаваемые вопросы)

**Q: В чем разница между SAST и Dependency Scanning?**
**A:** SAST смотрит на то, как *ты* пишешь код (например, забыл ли ты очистить ввод пользователя от SQL-инъекции). Dependency Scanning смотрит на то, какие *готовые куски* кода ты притащил в проект.

**Q: Что делать, если сканер нашел уязвимость, но обновить библиотеку нельзя (ломает проект)?**
**A:** Это классическая дилемма. 1) Попробовать найти патч или альтернативную библиотеку. 2) Если никак — использовать механизм `Dismiss` в GitLab, аргументировав это тем, что уязвимый участок кода не вызывается в твоем приложении (но делай это только после проверки!).

**Q: Почему мой сканер ничего не нашел, хотя я точно знаю, что библиотеки старые?**
**A:** Проверь, используешь ли ты **Lock-файлы**. Если у тебя есть только `requirements.txt` без зафиксированных версий, сканер может просто "не увидеть" реальную картину того, что установится при деплое.

**Q: Можно ли сканировать Docker-образы этим инструментом?**
**A:** Нет, для этого существует другой инструмент — **Container Scanning**. Dependency Scanning работает только с текстовыми файлами манифестов внутри репозитория.

# 🛡️ Шпаргалка: Container Scanning в GitLab

### Что это такое?
**Container Scanning** — это процесс автоматического сканирования слоев Docker-образа (или любого OCI-совместимого образа) на наличие известных уязвимостей (CVE — Common Vulnerabilities and Exposures). 

Представь, что ты заказываешь пиццу. **Code Scanning** проверяет рецепт, а **Container Scanning** проверяет не только ингредиенты, но и то, не протухла ли колбаса, которую привезли на склад, и чистые ли руки у повара.

### Как это работает в GitLab
GitLab использует встроенный инструмент (чаще всего это **Trivy**) внутри CI/CD пайплаина. 
1.  **Build:** Ты собираешь образ (`docker build`).
2.  **Push:** Отправляешь его в GitLab Container Registry.
3.  **Scan:** Специальная джоба скачивает этот образ, «разбирает» его на слои и сверяет установленные пакеты (библиотеки, системные утилиты) с огромной базой данных уязвимостей.
4.  **Report:** Результаты записываются в артефакты пайплайна и отображаются в интерфейсе GitLab.

### Основные этапы настройки
Чтобы всё заработало, тебе не нужно писать сложные скрипты, достаточно подключить шаблон:

```yaml
include:
  - template: Security/Container-Scanning.gitlab-ci.yml

container_scanning:
  variables:
    CS_IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
```

### 💡 Нюансы от Senior (на что смотреть)

1.  **Base Image — это фундамент.** Если ты используешь `FROM ubuntu:latest`, сканер найдет сотни уязвимостей, потому что в стандартном образе много лишнего софта. **Совет:** Используй минималистичные образы (`alpine` или `distroless`). Чем меньше мусора в образе, тем чище отчет.
2.  **Severity Threshold (Порог критичности).** Сканер может найти 500 уязвимостей уровня `Low`. Если ты настроишь пайплайн так, чтобы он падал на любой уязвимости, разработка встанет. **Совет:** Настраивай `CS_SEVERITY_THRESHOLD`, чтобы пайплайн падал только на `Critical` или `High`.
3.  **False Positives (Ложные срабатывания).** Иногда сканер говорит, что пакет уязвим, но в твоем контексте это не имеет значения (например, уязвимая функция библиотеки не используется). **Совет:** Научись использовать файлы исключений (`.trivyignore`), чтобы «заглушить» проверенные и безопасные уязвимости.
4.  **Связь с Registry.** Сканер должен иметь доступ к образу. Поэтому Container Scanning должна запускаться **после** того, как образ уже запушен в Registry.
5.  **Интеграция с Merge Requests.** В версии Ultimate результаты сканирования появляются прямо в MR. Это киллер-фича: разработчик видит проблему *до* того, как код попал в основную ветку.

### 🛠️ Ключевые переменные для управления
*   `CS_IMAGE`: Путь к образу, который нужно проверить.
*   `CS_SEVERITY_THRESHOLD`: Уровень (low, medium, high, critical), при котором джоба считается проваленной.
*   `CS_ANALYSIS_MODE`: Режим анализа (например, можно указать только поиск по системным пакетам).

# 🛡️ Тема: Secret Detection (Поиск секретов)

### Что это такое?
**Secret Detection** — это автоматизированный процесс сканирования твоего кода на наличие забытых «паролей»: API-ключей, токенов (AWS, Stripe, GitHub), сертификатов, паролей от БД и других конфиденциальных данных. 

Представь, что разработчик случайно закоммитил `access_token` в репозиторий. Если этот код попадет в публичный доступ или даже просто будет доступен коллегам, злоумышленник может использовать его для взлома инфраструктуры. Secret Detection ловит такие «утечки» до того, как они станут катастрофой.

### Как это работает в GitLab?
GitLab использует под капотом мощные инструменты (чаще всего это **gitleaks**), которые просматривают историю коммитов и содержимое файлов на наличие паттернов (регулярных выражений), похожих на секреты.

В пайплайне это выглядит как отдельная Job, которая запускается в рамках этапа `test` или `security`.

### Как внедрить (Quick Start)
Если ты используешь GitLab Ultimate, достаточно добавить шаблон в свой `.gitlab-ci.yml`:

```yaml
include:
  - template: Security/Secret-Detection.gitlab-ci.xml

stages:
  - test
```

### 💡 Нюансы от Senior'а (То, о чем не пишут в учебниках)

1.  **Проблема "Уже поздно":** Если секрет попал в историю Git — **он скомпрометирован**. Даже если ты удалишь его следующим коммитом, он останется в истории (в предыдущих слоях репозитория). 
    *   *Что делать:* Сначала **аннулируй (rotate)** ключ, а потом уже очищай историю репозитория.

2.  **False Positives (Ложные срабатывания):** Это главная боль. Инструмент может принять за ключ обычную строку или тестовый ID. 
    *   *Решение:* Настройка файлов исключений (`.sast-exclude-paths` или конфигурация gitleaks), чтобы не «спамить» в отчеты.

3.  **Pre-commit Hooks — Твой лучший друг:** Не жди, пока пайплайн в GitLab упадет. Настрой разработчикам `pre-commit` хуки локально на их машинах. Это позволит ловить секреты **до** того, как они вообще покинули компьютер разработчика.

4.  **Сложность очистки истории:** Использование инструментов вроде `git-filter-repo` или `BFG Repo-Cleaner` для удаления секрета из всей истории — это операция, которая может сломать репозиторий всем остальным участникам команды (придется делать hard reset). Поэтому фокус должен быть на **предотвращении**, а не на лечении.

5.  **Security Dashboard:** В GitLab Ultimate результаты сканирования попадают в единую панель управления. Это позволяет Security-инженерам видеть общую картину по всем проектам компании, а не бегать по каждому репозиторию отдельно.

# 📜 Шпаргалка: License Compliance в GitLab

**License Compliance** — это процесс автоматической проверки всех сторонних библиотек и зависимостей, которые ты используешь в проекте, на соответствие юридическим правилам твоей компании. 

Если коротко: это инструмент, который говорит: *"Эй, ты добавил библиотеку с лицензией GPL, а у нас политика — только MIT и Apache. Срочно удаляй, иначе нас засудят!"*

---

### 🛠 Как это работает (Механика)
GitLab не «угадывает» лицензии магическим образом. Процесс строится на базе **Dependency Scanning**:

1.  **Сканирование:** GitLab запускает сканер (например, `gemnasium`), который аналитзирует файлы манифестов (`package-lock.json`, `pom.xml`, `requirements.txt` и т.д.).
2.  **Идентификация:** Сканер находит список всех твоих зависимостей и определяет их лицензии (на основе метаданных пакетов).
3.  **Сверка с политикой (Policy Check):** GitLab берет этот список и сравнивает его с твоим **License Policy** (списком разрешенных и запрещенных лицензий), который ты настроил в интерфейсе GitLab.
4.  **Результат:** Если найдена «запрещенная» лицензия, GitLab создает уязвимость (vulnerability) в отчете и может остановить пайплайн.

---

### ⚙️ Основные компоненты настройки

1.  **License Policy (Политика):**
    *   **Allow List (Белый список):** Список «безопасных» лицензий (например, MIT, Apache 2.0, BSD).
    *   **Deny List (Черный список):** Список «опасных» лицензий (например, GPL v3, AGPL), которые могут обязать тебя открыть исходный код всего проекта.
2.  **Compliance Dashboard:** Единое окно в GitLab (доступно в Ultimate), где видно состояние всех проектов: где всё ок, а где обнаружены нарушения.
3.  **Dependency Scanning Job:** В твоем `.gitlab-ci.yml` должен быть настроен этап сканирования зависимостей. Без него проверку лицензий проводить нечем.

---

### ⚠️ Нюансы и «подводные камни» (Senior Insights)

*   **Транзитивные зависимости (Transitive Dependencies):** Это самая большая головная боль. Ты можешь подключить библиотеку с отличной лицензией MIT, но *внутри* неё может быть зависимость с «ядовитой» GPL. **Всегда проверяй дерево зависимостей**, а не только верхний уровень.
*   **Ложноположительные результаты (False Positives):** Иногда сканер не может определить лицензию или ошибается. В таких случаях тебе придется использовать механизм **Vulnerability Management**, чтобы «закрыть» (dismiss) уязвимость с комментарием, почему это безопасно.
*   **Сложность настройки Policy:** Не пытайся сразу запретить всё. Начни с анализа текущего проекта. Сначала просто собирай отчеты, посмотри, что у тебя уже «сломано», и только потом включай блокировку пайплайна (`fail pipeline`).
*   **Разница между Scan и Compliance:** Сканирование — это технический процесс поиска. Compliance — это бизнес-процесс принятия решения (разрешено или нет).

### ❓ FAQ: Часто задаваемые вопросы

**В: Что будет, если я добавлю библиотеку с запрещенной лицензией?**
**О:** Если в `.gitlab-ci.yml` настроено правило `allow_failure: false`, то пайплайн упадет (статус Failed). Это не даст тебе замержить код, содержащий нарушение.

**В: Где именно настраиваются правила (Allow/Deny list)?**
**О:** В GitLab Ultimate это делается через настройки группы или проекта в разделе *Security & Compliance -> License Compliance*.

**В: Покрывает ли этот инструмент мой собственный код?**
**О:** Нет. Он проверяет только **входящие зависимости** (third-party libraries). Твой собственный код считается «собственностью», если ты не указал иное в файле `LICENSE`.

**В: Можно ли использовать License Compliance для проверки Docker-образов?**
**О:** Напрямую — нет, но косвенно — да. Через **Container Scanning**, который видит пакеты внутри образа, можно получить информацию о лицензиях установленного ПО.

# 🛡️ IaC Scanning: Твой щит перед деплоем

### Что это такое? (The Concept)
**Infrastructure as Code (IaC) Scanning** — это процесс автоматической проверки твоих конфигурационных файлов (Terraform, Kubernetes manifests, Ansible, CloudFormation) на наличие ошибок безопасности и неправильных настроек **до того**, как они попадут в облако.

Если обычный SAST ищет ошибки в логике кода (например, SQL-инъекции), то IaC Scanning ищет "дыры" в архитектуре: открытые порты 22/80 для всего мира, отсутствие шифрования дисков, отсутствие тегов или запуск контейнеров от имени `root`.

**Главная идея — Shift Left:** Найти проблему на этапе написания кода, а не когда админ в панике пытается закрыть дыру в уже работающем AWS/Azure.

---

### Как это работает в GitLab?
GitLab использует встроенные сканеры (часто это обертки над инструментами вроде `Kics`, `Terrascan` или `Checkov`). 

1. **Trigger:** Ты пушишь код или создаешь Merge Request.
2. **Pipeline Stage:** В пайплайне запускается джоба (обычно на этапе `test`).
3. **Analysis:** Сканер читает твои `.tf`, `.yaml` или `.yml` файлы.
4. **Report Generation:** Результат сохраняется в формате JSON/Artifacts.
5. **Visualization:** GitLab парсит этот отчет и красиво рисует его в интерфейсе: в **Vulnerability Report** и прямо в **Merge Request**.

---

### Что именно он проверяет? (Key Checks)
*   **Network Security:** Открытые порты, слишком широкие правила Inbound/Outbound в Security Groups.
*   **Identity & Access (IAM):** Слишком мощные права (Wildcards `*` в политиках), отсутствие MFA.
*   **Storage Security:** Публичный доступ к S3 бакетам, отсутствие шифрования (Encryption at rest).
*   **Compute Security:** Запуск инстансов без необходимых тегов, использование устаревших образов.
*   **Kubernetes Specifics:** Запуск контейнеров с `privileged: true`, отсутствие `resources.limits`, работа под пользователем `root`.

---

### Как внедрить (Implementation)
Самый простой способ — использовать готовый шаблон GitLab. В свой `.gitlab-ci.yml` достаточно добавить:

```yaml
include:
  - template: Security/IaC-Scanning.gitlab-ci.yml

stages:
  - test
# Сканер сам создаст джобу в стейдже 'test'
```

**Нюанс:** Чтобы сканер работал эффективно, он должен запускаться на ранних этапах. Не жди завершения деплоя, чтобы узнать, что твой S3 бакет открыт миру.

---

### Senior Tips & Nuances (О чем не пишут в учебниках)

1.  **False Positives (Ложные срабатывания):** Это главная боль. Сканер может ругаться на открытый порт 80, хотя это веб-сервер, который *должен* быть открыт. 
    *   *Решение:* Научись использовать файлы исключений или аннотации (в зависимости от инструмента), чтобы не "засорять" отчет.
2.  **The "Broken Build" Dilemma:** Нужно ли останавливать пайплайн при нахождении уязвимости? 
    *   *Совет:* Для `Critical` и `High` — **да**, обязательно. Для `Low` — лучше просто уведомлять, иначе разработчики начнут игнорировать все алерты (Alert Fatigue).
3.  **Compliance vs Speed:** Сканирование занимает время. Если у тебя тысячи файлов, это может замедлить CI. 
    *   *Решение:* Используй `rules` в GitLab CI, чтобы запускать сканирование только при изменении файлов в папках `terraform/` или `k8s/`.
4.  **Integration with Terraform Plan:** Самый продвинутый уровень — сканировать не просто статический код, а **план** (Terraform Plan JSON). Это позволяет увидеть изменения, которые произойдут в реальности, а не только то, что написано в коде.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Чем IaC Scanning отличается от SAST?**
**О:** SAST смотрит на *приложение* (Python, Go, Java), чтобы найти баги в логике. IaC Scanning смотрит на *инфраструктуру* (Terraform, K8s), чтобы найти ошибки в конфигурации окружения.

**В: Могу ли я использовать свой собственный сканер вместо GitLab-овского?**
**О:** Да. Главное — выводить результат в формате **SAST Report JSON**, который понимает GitLab. Тогда все уязвимости всё равно появятся в красивом интерфейсе Merge Request.

**В: Что делать, если сканер нашел уязвимость, но мы решили оставить её (это осознанный риск)?**
**О:** Не игнорируй это в коде. Используй механизм `vulnerability dismissal` в GitLab или добавь комментарий/исключение прямо в конфигурацию сканера. Это должно быть документировано.

**В: Покрывает ли IaC Scanning Ansible?**
**О:** Да, если инструмент (например, Checkov) поддерживает анализ Ansible Playbooks. Но фокус обычно смещен на Terraform и Kubernetes.

# 🐳 GitLab Container Registry: Cheat Sheet

**GitLab Container Registry** — это встроенный в GitLab реестр (хранилище) для Docker-образов и других OCI-совместимых артефактов. Вместо того чтобы заводить отдельный Docker Hub или AWS ECR, ты хранишь образы прямо рядом с кодом. Это позволяет использовать единую систему прав доступа (IAM) и максимально упрощает CI/CD пайплайны.

### 🛠 Основные концепции

1.  **Единая точка входа:** Реестр привязан к проекту или группе. Если у тебя есть доступ к репозиторию, у тебя (в зависимости от роли) есть доступ и к образам.
2.  **Путь к образу (Image Path):** Это критически важно. Путь всегда строится по иерархии:
    `registry.gitlab.com/<group>/<project>/<image-name>:<tag>`
3.  **OCI-совместимость:** Ты можешь использовать стандартные команды `docker`, `podman` или `skopeo`.

### 🚀 Работа с реестром (Workflow)

#### 1. Авторизация (Login)
Чтобы пушить или пуллить образы, нужно авторизоваться.
*   **Вручную (локально):** Используй Personal Access Token (PAT) с правами `read_registry` / `write_registry`.
    ```bash
s$ docker login registry.gitlab.com -u <username> -p <token>
    ```
*   **Внутри GitLab CI/CD:** **Никогда не используй свои личные токены в пайплайнах!** Используй встроенную переменную `$CI_JOB_TOKEN`. Она создается автоматически для каждой джобы и имеет права именно того проекта, где идет сборка.

#### 2. Сборка и пуш (Build & Push)
Пример классической джобы в `.gitlab-ci.yml`:
```yaml
build_image:
  image: docker:latest
  services:
    - docker:dind  # Docker-in-Docker для сборки внутри контейнера
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:latest .
    - docker push $CI_REGISTRY_IMAGE:latest
```
*   `$CI_REGISTRY_USER`: автоматический юзер (обычно `gitlab-ci-token`).
*   `$CI_REGISTRY_PASSWORD`: автоматический пароль.
*   `$CI_REGISTRY_IMAGE`: путь к реестру твоего текущего проекта.

### ⚠️ Важные нюансы (Senior Tips)

1.  **Container Registry Cleanup Policy (Очистка):**
    Образы весят много. Если каждый коммит будет создавать новый тег, место на диске закончится мгновенно.
    *   **Решение:** Настрой *Cleanup Policy* в настройках проекта (*Settings -> Packages and Registries -> Container Registry*). Укажи правила: например, удалять все образы, кроме последних 10, или те, что старше 30 дней.

2.    **Безопасность (Scanning):**
    Реестр — это не просто склад, это фильтр. Включи **Container Scanning** в пайплайне. GitLab будет проверять слои твоего образа на наличие известных уязвимостей (CVE) и выдавать отчет прямо в Merge Request.

3.  **Использование тегов:**
    *   Никогда не полагайся только на тег `:latest` в продакшене. Если образ обновится, а ты его не пересоберешь — ты не сможешь откатиться к стабильной версии.
    *   **Best Practice:** Используй Git SHA (хеш коммита) или Semantic Versioning (v1.2.3) в качестве тегов.

4.  **Garbage Collection (GC):**
    Удаление тега в интерфейсе GitLab не удаляет сами слои образа с диска физически. Чтобы реально освободить место, на Self-managed инстансах нужно запускать процесс *Garbage Collection* (но будь осторожен: это требует остановки записи в реестр!).

### ❓ FAQ (Частые вопросы)

**В: Как мне забрать образ из другого проекта GitLab?**
**О:** Тебе нужно либо дать права доступа пользователю/группе, либо использовать Deploy Token. Если проект публичный — просто делай `docker pull`. Если приватный — используй токен с правами `read_registry`.

**В: Почему мой Docker Build падает с ошибкой "Permission Denied"?**

**В: Можно ли хранить в Registry не только Docker-образы?**

# 📦 GitLab Package Registry: Шпаргалка

### Что это такое?
**GitLab Package Registry** — это встроенный в GitLab менеджер артефактов и библиотек. Если Git хранит *исходный код*, то Package Registry хранит *результат его сборки* (скомпилированные библиотеки, модули, пакеты), который можно переиспользовать в других проектах.

Представь это как свой собьественный, приватный **npm registry**, **Maven Central** или **PyPI**, который находится прямо внутри твоего репозитория.

---

### 🚀 Основные возможности
1.  **Поддержка форматов:** GitLab "из коробки" понимает популярные менеджеры пакетов:
    *   **JavaScript/Node.js:** npm, Yarn.
    *   **Java/Kotlin:** Maven, Gradle.
    *   **Python:** PyPI.
    *   **PHP:** Composer.
    *   **.NET:** NuGet.
    *   **Ruby:** RubyGems.
    *   **C/C++:** Conan.
    *   **Generic Packages:** (Важно!) Позволяет загружать *любые* бинарные файлы (exe, zip, tar.gz), к которым нет специального менеджера пакетов.

2.  **Единая точка прав доступа:** Тебе не нужно настраивать отдельные доступы для Artifactory или Nexus. Если у разработчика есть доступ к проекту в GitLab, он (в зависимости от роли) может скачивать пакеты из этого проекта.

3.    **Интеграция с CI/CD:** Пакеты собираются, тестируются и пушатся в Registry автоматически одним пайплайном.

---

### 🔐 Аутентификация (Как к нему подключиться?)
Это самое «узкое» место. Чтобы скачать пакет, нужно представиться.

1.  **`CI_JOB_TOKEN` (Лучший друг в CI/CD):** Внутри GitLab Pipeline тебе **не нужно** создавать пароли. GitLab сам создает временный токен для каждой джобы. Используй его в `.npmrc`, `pip.conf` и т.д.
2.  **Deploy Tokens:** Если нужно скачивать пакеты извне (например, на сервер деплоя или локально), создай Deploy Token в настройках проекта. Он не привязан к конкретному человеку и безопаснее, чем личный пароль.
3.  **Personal Access Token (PAT):** Для локальной разработки. Твой личный токен.

---

### 🛠️ Нюансы и "Подводные камни" (Senior Tips)

*   **⚠️ Generic Packages — это спасение:** Если у тебя есть какой-то кастомный скрипт или бинарник, который не влезает в стандартные форматы, используй Generic Packages. Ты можешь через `curl` загрузить туда любой файл и потом так же легко его забрать.
*   **⚠️ Scope (Область видимости) токена:** Помни, что `CI_JOB_TOKEN` имеет ограниченные права. Если твой пакет лежит в *Проекте А*, а ты пытаешься скачать его из пайплайна *Проекта Б*, тебе нужно настроить разрешение на доступ между проектами (через настройки доступа к репозиториям).
*   **⚠️ Версионирование:** GitLab Registry не мешает тебе перезаписать пакет с той же версией (в зависимости от типа менеджера), но это **смертный грех** в DevOps. Всегда используй семантическое версионирование (SemVer). Если версия перетерта, у всей команды «поплывут» сборки.
*   **⚠️ Очистка (Cleanup):** Пакеты могут раздувать хранилище GitLab (особенно если это Docker-образы или тяжелые бинарники в Generic). Настрой политики удаления старых версий, чтобы не разориться на дисках.

**О:** Это разные вещи. **Container Registry** хранит Docker-образы (слои файловой системы). **Package Registry** хранит библиотеки и файлы (код, скомпилированные артефакты, зависимости).

**В: Можно ли использовать один Package Registry на всю организацию?**
**О:** Да, если ты создашь пакеты в уровне **Group**, а не Project. Тогда все подгруппы и проекты внутри этой группы смогут иметь к ним доступ по единому пути.

**О:** Первым делом проверь права `CI_JOB_TOKEN`. Если пакет находится в другом проекте, убедись, что в настройдеках этого проекта разрешен доступ для других проектов (Settings -> CI/CD -> Token Access).

# 📦 GitLab Generic Packages: Шпаргалка

### Что это такое?
**Generic Package Registry** — это «универсальный склад» внутри GitLab. В отличие от специализированных реестров (npm, Maven, PyPI), где есть строгий протокол и структура, Generic Packages позволяют хранить **любые бинарные файлы**: `.zip`, `.exe`, `.tar.gz`, `.apk`, `.iso` и даже просто текстовые конфиги.

Если у твоего артефакта нет своего пакетного менеджера — используй Generic Packages.

---

### 🛠 Как это работает (Архитектура URL)
Всё общение с реестром идет через **REST API**. Главное, что нужно запомнить — это структура пути (URL). Она всегда выглядит так:

```text
https://<gitlab-domain>/api/v4/projects/<project_id>/packages/generic/<package_name>/<version>/<file_name>
```

*   `<project_id>`: ID твоего проекта (можно найти на главной странице проекта).
*   `<package_name>`: Название твоего «пакета» (логическая группа файлов).
*   `<version>`: Версия (строка, которую ты придумываешь сам).
*   `<file_name>`: Имя самого файла.

---

### 🚀 Основные операции

#### 1. Загрузка файла (Upload)
Загрузка всегда происходит через HTTP метод `PUT`. Самый простой способ — использовать `curl` в твоем `.gitlab-ci.yml`.

```bash
curl --request PUT \
     --form file=@my_artifact.zip \
     --form package_name="my-app" \
     --form version="1.0.5" \
     --header "PRIVATE-TOKEN: <your_access_token>" \
     "https://gitlab.com/api/v4/projects/<project_id>/packages/generic/my-app/1.0.5/my_artifact.zip"
```
*💡 **Senior Tip:** Внутри CI/CD пайплайна вместо `PRIVATE-TOKEN` всегда используй встроенный `${CI_JOB_TOKEN}`. Это безопаснее и не требует настройки лишних прав.*

#### 2. Скачивание файла (Download)
Скачивание — это обычный `GET` запрос.

```bash
curl --header "JOB-TOKEN: ${CI_JOB_TOKEN}" \
     "https://gitlab.com/api/v4/projects/<project_id>/packages/generic/my-app/1.0.5/my_artifact.zip" \
     --output my_artifact.zip
```

---

### ⚠️ Нюансы и «Подводные камни» (Senior Insights)

1.  **Версионирование — это твоя ответственность.** В npm или Maven система сама понимает, что такое `1.2.0`. В Generic Packages нет никакой логики версий. Если ты загрузишь файл с той же версией, он просто перезапишет старый (или создаст дубликат, если не настроено иначе). Ты сам должен следить за семантикой.
2.  **Storage Quota (Место на диске).** Помни, что всё, что ты туда заливаешь, занимает место в квоте твоего GitLab-инстанса/проекта. Если забивать Generic Packages огромными образами без очистки, проект быстро «раздуется».
3.  **Cleanup Policy (Очистка).** В GitLab есть механизмы удаления старых артефактов, но для Generic Packages нужно настраивать правила очистки отдельно или писать свой скрипт через API, чтобы не превратить репозиторий в свалку.
4.  **Безопасность.** Любой, у кого есть доступ к проекту (на уровне Developer и выше), может скачать эти файлы. Если внутри архива лежат секреты — это плохая идея.

### ❓ FAQ: Часто задаваемые вопросы

**В: Можно ли использовать Generic Packages вместо Container Registry для Docker-образов?**
**О:** Технически — да (залить `.tar` со слоями образа), но **нельзя**. Container Registry оптимизирован под Docker (слои, манифесты, pull/push логика). Использовать Generic для Docker — это как возить грузы на велосипеде вместо фуры.

**В: Что использовать для авторизации в CI/CD?**
**О:** Всегда `CI_JOB_TOKEN`. Он создается автоматически для каждой джобы и имеет права текущего проекта. Это избавляет от необходимости хранить `Personal Access Token` в переменных.

**В: Как мне увидеть список всех загруженных пакетов?**
**О:** Можно через UI (раздел *Packages and registries* -> *Generic Packages*) или через API запрос `GET /projects/<id>/packages`.

**В: Можно ли хранить там конфиги для разных окружений?**
**О:** Да, это отличный кейс. Ты можешь создать пакет `config-app` с версиями `prod`, `staging`, `dev`. Это позволяет отделять конфигурацию от кода.

# 📝 Шпаргалка: GitLab Issues

**Issues (Задачи)** — это не просто «баг-репорты». В GitLab Issue — это любая единица работы: баг, фича, исследовательская задача (Spike), технический долг или даже идея для документации. Это фундамент вашего планирования.

### 1. Анатомия Issue (Основные элементы)
Чтобы задача была понятной, она должна содержать:
*   **Title & Description:** Заголовок должен быть кратким, а описание — подробным. Используй **Markdown** (списки, таблицы, блоки кода), чтобы структурировать суть проблемы или требования.
*   **Assignee (Исполнитель):** Тот, кто «несет ответственность». *Нюанс: в одной задаче может быть несколько исполнителей, но фокус должен быть на одном.*
*   **Labels (Метки):** Главный инструмент классификации. Помогают фильтровать задачи по типу (`type::bug`, `type::feature`), приоритету (`priority::high`) или компоненту (`component::ui`).
*   **Milestone (Веха):** Группировка задач по смыслу или времени (например, «Release 1.0» или «Sprint 24»). У вехи есть дата начала и окончания.
*   **Weight (Вес/Сложность):** Оценка сложности задачи (в Story Points или условных единицах). Помогает понять нагрузку на команду.

### 2. Организация работы: Boards & Templates
Если задач много, обычный список превращается в хаос. Тебе нужны инструменты управления:

*   **Issue Boards (Канбан-доски):** Визуализация процесса. Ты создаешь колонки, которые привязаны к определенным меткам (например, колонка `Doing` привязана к метке `status::doing`). Перетаскивание карточки меняет её метку.
*   **Issue Templates (Шаблоны):** **Must-have для Senior уровня.** Чтобы не писать каждый раз «Шаги для воспроизведения» или «Ожидаемый результат», создай шаблоны в папке `.gitlab/issue_templates/`. Это гарантирует, что все задачи будут приходить в едином стандарте.
*   **Scoped Labels (Специфические метки):** Магия GitLab. Метки формата `key::value` (например, `workflow::in-progress` и `workflow::review`). Главная фишка: у одной задачи не может быть двух меток одного ключа. Если ты перетаскиваешь задачу в колонку «Review», старая метка «In Progress» удалится автоматически.

### 3. Автоматизация и Связи
Senior не делает ручную работу там, где можно автоматизировать:

*   **Closing Issues via Commit/MR:** В описании Merge Request или в тексте коммита пиши `Closes #123`. Как только MR будет влит (merged) в основную ветку, задача №123 закроется сама.
*   **Quick Actions:** Прямо в комментариях к задаче можно использовать команды:
    *   `/assign @user` — назначить исполнителя.
    *   `/label ~"bug"` — добавить метку.
    *   `/milestone %"Sprint 1"` — привязать к вехе.
    *   `/close` — закрыть задачу.
*   **Linking:** Всегда связывай Issue с Merge Request. Это создает «прослеживаемость» (traceability): можно увидеть, какой код решил какую задачу.

---

### 💡 Нюансы от Senior'а
1.  **Не путай Milestone и Iteration.** *Milestone* — это долгосрочная цель (релиз). *Iteration* — это короткий цикл (спринт), который обычно повторяется каждые 2 недели. В GitLab есть встроенный механизм для автоматизации Iterations.
2.  **Weight — это не часы.** Никогда не оценивай задачи в часах. Оценивай в сложности (1, 2, 3, 5, 8...). Часы — вещь субъективная и переменная, сложность — более стабильная величина.
3.  **Избегай "Label Hell".** Если у тебя 200 разных меток, никто не будет в них разбираться. Используй иерархию (Scoped Labels), как описано выше.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что делать, если задача слишком большая?**
**О:** Разбей её! Большая задача (Epic) должна быть декомпозирована на несколько маленьких Issues. Огромная Issue — это риск провала планирования.

**В: Можно ли использовать Issues для хранения документации?**
**О:** Можно, но не стоит. Для долгосрочной документации используй **GitLab Wiki** или файлы `.md` прямо в репозитории. Issues — это про «сделал/не сделал».

**В: Как быстро закрыть сразу 10 задач?**
**О:** Используй Bulk Edit. В списке Issue выдели нужные галочками, нажми "Edit" и примени массовое изменение (например, добавь метку или закрой их).

**В: Чем отличается Assignee от Reporter?**
**О:** *Assignee* — тот, кто работает. *Reporter* — тот, кто создал задачу или просто наблюдает за процессом (его можно добавить в комментарии через `@`).

# 📋 Шпаргалка: GitLab Issue Boards

**Issue Boards** — это визуальный инструмент управления задачами (Kanban-доски), который позволяет превратить плоский список задач (Issues) в наглядный процесс. Если Issues — это «что нужно сделать», то Boards — это «на каком этапе сейчас находится работа».

### 🧠 Главная концепция: "Всё есть Label"
Самое важное, что нужно понять Senior-у: **Колонки на доске не существуют сами по себе. Каждая колонка — это просто визуальное представление конкретной метки (Label).**
Если ты хочешь колонку «In Progress», ты должен создать метку `In Progress` и добавить её в конфигурацию доски. Перетаскивание карточки из одной колонки в другую — это автоматическое добавление/удаление соответствующей метки у Issue.

---

### 🛠 Типы досок (Scope)
1.  **Project Boards:** Работают только внутри одного проекта. Идеально для микро-менеджмента конкретной фичи или багфикса.
2.  **Group Boards:** Самый мощный инструмент. Собирают задачи из **всех** проектов внутри группы и всех её подгрупп. Это позволяет видеть общую картину (Roadmap) по всему департаменту или продукту.

---

### 🚀 Ключевые возможности и фишки

*   **Multiple Lists (Несколько списков):** На одной доске можно отобразить разные колонки. Например: `To Do`, `Doing`, `Testing`, `Done`.
*   **Filtering:** Ты можешь создать несколько досок на базе одного и того же набора задач, но с разными фильтрами. 
    * *Пример:* Доска "Bugs" (фильтр по метке `type::bug`) и доска "Features" (фильтр по метке `type::feature`).
*   **Scoped Labels (Специфическая фишка GitLab):** Использование меток формата `status::doing` и `status::done`. При перетаскивании задачи между ними, GitLab сам удалит старую метку и добавит новую. Это предотвращает ситуацию, когда у задачи висят сразу три статуса.
*   **Drag-and-Drop:** Максимально интуитивное перемещение задач между этапами.

---

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Забытые метки:** Если ты удалишь Label в настройках проекта, колонка на доске исчезнет вместе со всеми задачами, которые были в ней. Задачи не пропадут, они просто «выпадут» из визуального поля.
2.  **Сложность конфигурации:** Не пытайся сделать 20 колонок. Это превратит Kanban в хаос. Оптимально: 4–6 этапов жизненного цикла задачи.
3.  **Permissions (Права):** Чтобы двигать карточки, у пользователя должны быть права как минимум `Developer`. `Reporter` может только смотреть.
4.  **Group Board Overload:** Если в группе сотни проектов, Group Board может стать перегруженным. Используй фильтры по подгруппам или меткам, чтобы не утонуть в инфошуме.

### ❓ FAQ (Частые вопросы на собеседованиях/митингах)

**В: Можно ли на одной доске видеть задачи из разных проектов?**
**О:** Да, если ты используешь **Group Board**. Это основной способ агрегации задач для всей команды.

**В: Что произойдет, если я перетащу задачу в колонку, которой нет в списке фильтров текущей доски?**
**О:** Ты не сможешь этого сделать физически через Drag-and-Drop, так как ты перемещаешь задачу между *визуальными списками*, каждый из которых жестко привязан к конкретной метке.

**В: Как автоматизировать переход задачи из "In Progress" в "Review"?**
**О:** Используй **Scoped Labels** (например, `workflow::progress` и `workflow::review`). При перетаскивании GitLab сам позаботится о чистоте меток, удалив старую и применив новую.

**В: В чем разница между фильтром на доске и колонкой на доске?**
**О:** **Колонка** — это то, что ты *видишь* (привязка к Label). **Фильтр** — это то, что *скрывает* лишнее со всей доски (например, фильтр "только задачи исполнителя Иван"). Фильтр применяется ко всем колонкам сразу.

# 🧠 Шпаргалка: Milestones & Epics (Планирование и стратегия)

Если коротко: **Epics** — это про «Что мы хотим построить» (стратегия), а **Milestones** — это про «Когда мы это сделаем» (тактика).

---

## 1. Epics (Эпики) — "Большие цели"
*Доступно в GitLab Premium/Ultimate.*

**Эпик** — это высокоуровневая задача, которую невозможно выполнить за один спринт. Это крупная фича или направление развития продукта.

*   **Иерархия:** Эпики могут иметь под-эпики (Sub-epics). Это позволяет дробить огромные задачи на логические части.
*   **Содержимое:** Внутри эпика живут **Issues** (задачи) и другие **Epics**. 
*   **Scope (Область):** Эпики живут на уровне **Группы (Group)**, а не отдельного проекта. Это позволяет объединять задачи из разных репозиториму под одной стратегической целью.
*   **Roadmaps:** Если у тебя есть эпики с датами, GitLab может построить визуальную дорожную карту (Timeline), чтобы менеджеры видели загрузку на месяцы вперед.

---

## 2. Milestones (Вехи/Милстоуны) — "Сроки и релизы"
*Доступно во всех версиях GitLab.*

**Milestone** — это временной или целевой контейнер для задач. Это инструмент контроля прогресса в конкретный промежуток времени.

*   **Типы использования:**
    1.  **Sprint/Iteration:** Короткий цикл (например, 2 недели) для Agile-команд.
    2.  **Release:** Конкретная версия продукта (например, `v1.2.0`).
    3.  **Bug-fix period:** Период интенсивного исправления багов.
*   **Scope (Область):** 
    *   **Project Milestone:** Виден только внутри одного проекта.
    *   **Group Milestone:** Общий для всей группы и всех подгрупп/проектов в ней. *Это киллер-фича: один милстоун на 10 микросервисов.*
*   **Атрибуты:** Дата начала (Start Date), дата окончания (Due Date) и вес задач (Weight).

---

## 3. Взаимосвязь: Как это работает вместе

Правильная архитектура управления проектом выглядит так:

`Epic (Feature X)` $\rightarrow$ `Milestone (Sprint #5)` $\rightarrow$ `Issue (Task A, Task B)`

1.  **Epic** задает контекст (мы делаем систему оплаты).
2.  **Milestone** задает рамки (мы должны успеть это до 30 сентября).
3.  **Issues** — это конкретная работа (написать API, создать UI-компонент).

---

## 💡 Нюансы и Senior Tips (На что наступают новички)

*   **Не путай Label и Milestone:** 
    *   *Label* — это "категория" или "тип" (например, `type::bug` или `priority::high`). Метка может быть у задачи вечно.
    *   *Milestone* — это "дедлайн". У задачи не может быть двух разных милстоунов одновременно.
*   **Group Milestones — это спасение:** Если у тебя микросервисная архитектура, никогда не делай милстоуны в каждом проекте отдельно. Делай один `Group Milestone` на уровне группы. Так ты увидишь общую картину прогресса по всем сервисам в одном месте.
*   **Burndown Chart:** Всегда следи за графиком сгорания задач в Milestone. Если линия не идет вниз — вы не успеваете к релизу, пора либо расширять сроки, либо выкидывать задачи из этого милстоуна.
*   **Weight (Вес):** Не игнорируй поле `Weight`. Без него твой Milestone — это просто список дел, а с ним — математически обоснованный план нагрузки на команду.

## ❓ FAQ (Частые вопросы)

**В: Я создал Milestone в проекте, но не вижу его в другом проекте этой же группы. Почему?**
О: Потому что ты создал *Project Milestone*. Чтобы он был виден везде, создавай его на уровне *Group*.

**В: Можно ли привязать Issue к нескольному Epics?**
О: В GitLab одна задача (Issue) может принадлежать только одному эпику напрямую. Но она может быть частью цепочки под-эпиков.

**В: Что делать, если мы не успеваем закрыть задачу в рамках Milestone?**
О: Хорошая практика — перенести задачу (re-assign/re-milestone) в следующий Milestone. Не оставляй "хвосты" в старом милстоуне, это портит статистику Burndown Chart и точность планирования.

**В: Эпики доступны в бесплатной версии GitLab?**
О: Нет, Epics — это часть функций уровня Premium и выше. В Free-версии тебе придется имитировать эпики с помощью Labels или Issue Boards.

# 📖 Тема: Wiki & Documentation в GitLab

### Что это такое?
**Wiki** — это встроенный в проект инструмент для ведения долгосрочной документации. Если `README.md` — это «паспорт» конкретного репозитория (кратко: что это, как запустить), то **Wiki** — это «энциклопедия» проекта (подробно: архитектура, регламенты, инструкции по деплою, контакты команды).

### 🧠 Главный секрет (Senior Nuance)
Самое важное, что нужно понимать: **Wiki в GitLab — это отдельный Git-репозиторий**, привязанный к вашему проекту. 
Это значит:
1. Вы можете клонировать Wiki себе на компьютер (`git clone ...`).
2. Вы можете редактировать страницы локально через VS Code и пушить изменения так же, как в основной код.
3. У Wiki есть своя история коммитов. Вы всегда можете откатиться к старой версии документации.

---

### 🛠 Ключевые возможности и инструменты

#### 1. Формат контента
*   **Markdown:** Основной язык разметки. Поддерживает таблицы, списки, ссылки, чек-листы.
*   **Mermaid.js:** (Критически важно!) Позволяет рисовать диаграммы (Flowcharts, Sequence diagrams, Gantt) прямо в тексте с помощью кода. Больше никаких картинок из Visio/draw.io, которые невозможно отредактировать.
*   **LaTeX:** Поддержка математических формул.

#### 2. Структурирование (Навигация)
Если страниц много, они превратятся в кашу. Чтобы этого не случилось, используй:
*   **`_sidebar.md`**: Это «магический» файл. Если ты создашь его в Wiki, GitLab превратит его в боковую панель навигации. В нем ты просто перечисляешь ссылки на другие страницы своей вики. Без него пользователи будут блуждать по списку страниц в алфавитном порядке.

#### 3. Изображения и вложения
*   Можно просто перетаскивать (drag-and-drop) картинки прямо в редактор GitLab. Они загрузятся в специальный репозиторий вложений.
*   **Совет:** Для больших схем лучше использовать Mermaid, а для скриншотов интерфейса — drag-and-drop.

### ⚖️ Сравнение: README vs Wiki vs GitLab Pages

| Инструмент | Для чего использовать? | Жизненный цикл |
| :--- | :--- | :--- |
| **README.md** | Быстрый старт, установка, описание кода. | Меняется вместе с кодом (в том же MR). |

| **GitLab Pages** | Публичный сайт проекта (документация на HTML/React). | Автоматически собирается через CI/CD пайплайн. |

### ⚠️ Нюансы и "подводные камни"

1.  **Права доступа (Permissions):** Права на редактирование Wiki наследуются от прав на проект. Если у пользователя роль `Guest`, он может только читать. Для редактирования нужен уровень `Developer` и выше.
2.  **Синхронизация:** Поскольку это отдельный репозиторий, если ты удалишь проект в GitLab, Wiki удалится вместе с ним.
3.  **Засорение:** Не превращай Wiki в склад мусора. Если информация касается конкретной функции кода — пиши её в `README.md` или в документации внутри папок кода. В Wiki — только то, что касается всего проекта/системы.

# 📝 Тема: GitLab Snippets (Сниппеты)

### Что это такое?
**Snippets** — это «заметки» или «кусочки кода», которые живут отдельно от основных репозиториев. Представь, что это продвинутые *Pastebin* или *GitHub Gists*, встроенные прямо в твой GitLab. 

Если тебе нужно сохранить полезный скрипт на Bash, кусок SQL-запроса или шаблон конфигурации Nginx, и ты **не хочешь** создавать под это отдельный репозиторий (который будет «мусорить» в списке проектов), — используй сниппеты.

---

### 🛠 Типы сниппетов
В GitLab есть два уровня существования сниппетов:

1.  **Personal Snippets (Персональные):** Принадлежат тебе. Их видишь ты. Это твой личный «карман» с полезностями, которые ты используешь в работе.
2.  **Project Snippets (Проектные):** Привязаны к конкретному проекту. Они видны всем, у кого есть доступ к этому проекту. Идеально для командных шаблонов (например, `.gitlab-ci.yml` заготовка или скрипт деплоя), которые должны быть под рукой у всей команды.

---

### 🔒 Уровни видимости (Visibility)
Это критически важный момент для безопасности:
*   **Private:** Видишь только ты (или участники проекта, если сниппет проектный).
*   **Internal:** Видят все, кто авторизован в вашем GitLab (полезно для внутренних инструментов компании).
*   **Public:** Видит весь интернет (если ваш GitLab открыт наружу).

---

### 🚀 Ключевые фишки и возможности
*   **Markdown Support:** Сниппеты — это не просто текст. Ты можешь использовать таблицы, списки, жирный шрифт и, конечно, подсветку синтаксиса для кода.
*   **Versioning (История изменений):** Каждый раз, когда ты редактируешь сниппет, GitLab сохраняет историю. Ты всегда можешь откатиться к предыдущей версии.
*   **Attachments:** В сниппеты можно прикреплять файлы и изображения. Это превращает их в подобие мини-документации.
*   **Git-powered:** Сниппеты — это полноценные Git-репозитории «под капотом». Ты можешь сделать `git clone <url_сниппета>`, чтобы скачать его себе локально, и даже делать `git push` для обновлений.

---

### ⚠️ Нюансы и Best Practices (Советы от Senior)

1.  **⚠️ Секреты — под запретом!** Никогда не вставляй пароли, API-ключи или токены в сниппеты, даже если они `Private`. Если кто-то получит доступ к твоему аккаунту (или к проекту), твои секреты будут скомпрометированы. Для этого есть *GitLab CI/CD Variables*.
2.  **Сниппет vs Файл в репозитории:** 
    *   Если код требует тестирования, запуска CI/CD и живет в рамках жизненного цикла приложения — **клади его в репозиторий**.
    *   Если это «одноразовый» или вспомогательный скрипт, который просто удобно иметь под рукой — **используй сниппет**.
3.  **Именование:** Всегда давай понятное название и описание. Через полгода ты не вспомнишь, что такое `script_v2_final`.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Можно ли клонировать сниппет через терминал?**
**О:** Да! Сниппет в GitLab — это маленький Git-репозиторий. Найди ссылку на Clone (она есть на странице сниппета) и используй стандартный `git clone`.

**В: В чем разница между Project Snippet и файлом в репозитории, если я могу просто создать файл `script.sh` в проекте?**
**О:** Файл в репозитории является частью истории проекта и влияет на его состояние (build, deploy). Сниппет — это *внешний* ресурс. Если ты удалишь проект, проектные сниппеты удалятся вместе с ним, но персональные останутся. Сниппеты удобнее для «инструментария», который не является частью самого продукта.

**В: Можно ли использовать Snippets для хранения документации?**
**О:** Можно, но это плохая практика. Для документации лучше использовать **GitLab Wiki** или файлы `README.md` прямо в репозитории. Сниппеты — это про короткие фрагменты кода и текста, а не про структурированную базу знаний.

# 🛠 Шпаргалка: GitLab Agent for Kubernetes (KUA)

### Что это такое?
**GitLab Agent for Kubernetes** — это way-to-go решение для реализации **GitOps**. Это небольшое приложение (бинарник/pod), которое ты устанавливаешь прямо в свой K8s кластер. Он создает защищенный туннель между твоим кластером и GitLab.

Раньше мы использовали подход **"Push"** (CI-джоба берет `KUBECONFIG` и стучится в кластер). 
Теперь мы используем **"Pull"** (Агент сам следит за изменениями в Git и применяет их в кластере).

---

### 🚀 Главные сценарии использования

1.  **GitOps (Pull-based deployment):** Ты пушишь манифесты (Helm, Kustomize, YAML) в репозиторий $\rightarrow$ Агент видит изменения $\rightarrow$ Агент сам обновляет ресурсы в кластере.
2.  **Secure CI/CD (Push-based via Agent):** Тебе всё еще нужно запустить `helm upgrade` из пайплайна? Ты не хранишь секретный `KUBECONFLIG` в переменных GitLab. Ты просто говоришь джобе: "Используй агент". Агент предоставляет временный доступ к кластеру через API.
3.  **Cluster Monitoring & Security:** Агент может отдавать данные о состоянии кластера обратно в GitLab (например, для анализа безопасности или мониторинга ресурсов).

---

### 🏗 Как это работает (Архитектура)

1.  **Установка:** Ты устанавливаешь агент через **Helm-чарт** в целевой кластер.
2.  **Регистрация:** При установке создается `agent-id`. Ты добавляешь этот ID в GitLab.
3.  **Конфигурация (`config.yaml`):** Это "мозг" агента. В специальном репозитории ты пишешь файл конфигурации, где указываешь: *"Этому проекту (Project A) разрешено управлять этим кластером"*.
4.  **Связь:** Агент сам инициирует соединение с GitLab (outbound connection). Тебе **не нужно** открывать API Kubernetes наружу или иметь публичный IP у кластера.

---

### 💡 Нюансы и "подводные камни" (Senior level)

*   **Безопасность (RBAC):** Агент по умолчанию имеет права, которые ты ему дашь. Не давай ему `cluster-admin`, если это не критично. Используй Kubernetes RBAC, чтобы ограничить его возможности внутри кластера.
*   **Конфигурация через Git:** Помни, что управление агентом — это тоже код. Если ты забыл обновить `config.yaml` в репозитории с конфигурацией агента, новые проекты не смогут подключиться к кластеру.
*   **Pull vs Push:** Хотя агент позволяет делать "Push" (через `kubectl` в CI), настоящая мощь — в "Pull". Если ты используешь только Push, ты просто используешь дорогой и сложный прокси-инструмент вместо обычного секрета.
*   **Multi-cluster:** Один агент = один кластер. Если у тебя 10 кластеров, тебе нужно 10 инстансов агента (но управлять ими можно из одной точки в GitLab).

---

### ❓ FAQ (Частые вопросы на интервью)

**В: В чем принципиальная разница между использованием `KUBECONFIG` в переменных и GitLab Agent?**
**О:** В `KUBECONFIG` ты хранишь супер-секретный ключ, который может украсть любой, кто получит доступ к переменным CI. Если кластер открыт для внешнего мира (Push), он уязвим для атак. Агент работает по принципу Pull: кластер сам "стучится" в GitLab. Внешний мир не видит API Kubernetes вообще.

**В: Нужно ли мне открывать порт 6443 (API K8s) во внешний мир для работы агента?**
**О:** Нет! Это киллер-фича. Агент устанавливает исходящее соединение (outbound) к GitLab. Твой кластер может находиться за NAT или в закрытой приватной сети.

**В: Можно ли использовать GitLab Agent вместе с ArgoCD?**
**О:** Да, это не исключает друг друга. Ты можешь использовать Агента для обеспечения безопасности связи и передачи данных, а ArgoCD — как основной движок деплоя внутри кластера. Но часто Агент сам может заменить ArgoCD для простых задач.

**В: Где хранятся настройки прав доступа агента?**
**О:** В специальном репозитории (обычно называемом `agent-config`), где лежит файл `config.yaml`. Именно там ты прописываешь связи между `project path` и кластером.

# 🛠 Terraform Integration in GitLab: Full Guide

Если кратко: **Terraform Integration** — это превращение GitLab из простого хранилища кода в полноценную платформу для управления инфраструктурой (IaC). Вместо того чтобы запускать `terraform apply` со своего ноутбука, ты делаешь это через пайплинки, а результат проверки видишь прямо в Merge Request.

### 1. Terraform State Management (Backend)
Самое важное в Terraform — это файл **state** (`.tfstate`). Это «память» твоего инфраструктурного кода. Если потерять state или если два человека одновременно его изменят — инфраструктура превратится в тыкву.

GitLab предлагает встроенный **HTTP Backend**. Тебе не нужно настраивать S3 и DynamoDB для блокировок (locks).
*   **Как это работает:** GitLab предоставляет URL-адрес. Terraform отправляет туда свой state.
*   **Преимущества:** 
    *   **State Locking:** GitLab автоматически блокирует state во время выполнения джобы, предотвращая одновременные изменения.
    *   **Security:** Доступ к стейту ограничен теми же правами, что и доступ к репозиторию.
    *   **Versioning:** Можно откатиться к предыдущим версиям стейта.

### 2. Terraform Plan in Merge Requests (Visual Review)
Это «киллер-фича». Когда ты создаешь Merge Request (MR), GitLab запускает пайплайн, который делает `terraform plan`.
*   Результат выполнения (`plan`) не просто логируется в консоль, а **выводится в виде специального виджета прямо в теле MR**.
*   **Зачем это нужно:** Ревьюер (Senior или Lead) видит не только код, но и реальный эффект: *"Ага, этот коммит удалит базу данных и создаст новый инстанс"*. Это позволяет ловить ошибки до того, как они попадут в `main`.

### 3. Workflow: От кода до деплоя
Правильный процесс (Pipeline) выглядит так:
1.  **Stage: Init** — Инициализация бэкенда (подключение к GitLab HTTP backend).
2.  **Stage: Validate/Lint** — Проверка синтаксиса и стандартов (tflint, terraform validate).
3.  **Stage: Plan** — Выполнение `terraform plan`. Результат сохраняется как **Artifact**.
4.  **Stage: Apply** — Выполняется *только* после апрува MR и слияния в ветку `main`. Важно: `apply` должен использовать тот же самый файл плана, который был проверен на этапе Plan (через артефакты).

---

### 💡 Нюансы и "подводные камни" (Senior Tips)

*   **Artifacts are Key:** Никогда не делай `terraform plan > plan.txt` и потом читай его глазами. Сохраняй план как файл: `terraform plan -out=plan.tfplan`. В следующем этапе (Apply) используй именно этот файл: `terraform apply plan.tfplan`. Это гарантирует, что ты применишь именно то, что проверил.
*   **Secret Management:** Никогда не пиши пароли и ключи в `.tf` файлах. Используй **GitLab CI/CD Variables** (тип *Masked* и *Protected*). Для более сложных вещей используй Hashilock Vault, интегрированный с GitLab.
*   **Permissions & Code Owners:** Используй файл `CODEOWNERS`. Настрой его так, чтобы любые изменения в папке `/terraform` требовали обязательного апрува от команды DevOps/SRE. Это защитит инфраструктуру от случайных правок разработчиков.
*   **Environment Separation:** Используй разные файлы стейта (или разные пути в бэкенде) для `staging` и `production`. Ошибка в одном не должна убить другой.

# 🛠 Terraform Plan in Merge Request (MR)

### 💡 Суть концепции
В обычном подходе ты запускаешь `terraform plan` локально или смотришь логи в консоли CI/CD. Это неудобно: ревьюер видит только код (HCL), но не видит, **что именно изменится в реальности** (создастся ли новый сервер или удалится база данных).

**Terraform Plan in MR** — это процесс, при котором результат выполнения команды `terraform plan` автоматически публикуется в виде комментария прямо в Merge Request. Это превращает MR из «просто изменения кода» в «запрос на изменение инфраструктуры с предпросмотром».

---

### 🏗 Как это устроено (Workflow)

1.  **Trigger:** Ты создаешь ветку и пушишь изменения. GitLab CI запускает пайплайн.
2.  **Execution:** Внутри джобы выполняется `terraform plan`.
3.  **Capture:** Результат выполнения (diff) сохраняется в артефакт или переменную.
4.  **Feedback Loop:** С помощью GitLab API (или специальных инструментов) этот текст форматируется и постится как **комментарий к MR**.

---

### 🗝 Ключевые компоненты для реализации

#### 1. GitLab Managed Terraform State (Must Have!)
Забудь про хранение `tfstate` в S3 или локально. Для полноценной интеграции используй встроенный в GitLab бэкенд.
*   **Почему это важно:** GitLab сам управляет блокировками (locking), чтобы два пайплайна не испортити стейт, и предоставляет API для доступа к нему.
*   **Как выглядит в коде:**
    ```hcl
    terraform {
      backend "http" {} # Конфигурация заполняется динамически в CI/CD
    }
    ```

#### 2. Pipeline Configuration (`.gitlab-ci.yml`)
Тебе нужны как минимум две стадии: `validate/plan` и `apply`.
*   **Важный нюанс:** Для джобы `plan` нужно использовать правило `rules: - if: $CI_PIPELINE_SOURCE == "merge_request_event"`. Это гарантирует, что план будет генерироваться именно при открытии/обновлении MR.

#### 3. Commenter (Инструмент публикации)
Есть два пути:
*   **Путь «Сложный/Ручной»:** Написать скрипт на Python/Bash, который парсит вывод `terraform plan` и через `curl` отправляет его в GitLab API (`POST /projects/:id/merge_requests/:mr_id/notes`).
*   **Путь «Senior» (GitLab Native):** Использовать готовые open-source решения (например, [tf-plan-commenter](https://github.com/GitLab/terraform-plan-commenter) или встроенные возможности GitLab в новых версиях), которые делают это "из коробки".

---

### ⚠️ Нюансы и «Подводные камни» (Senior Insights)

1.  **`no-color` — твой лучший друг:** Когда Terraform выводит план в консоль, он использует ANSI-коды для цвета. Если просто закинуть этот текст в комментарий GitLab, ты получишь нечитаемую кашу из символов вроде `^[[0m`. Всегда используй флаг `terraform plan -no-color`.
2.  **Размер комментария:** Если изменение огромное (например, пересоздание 100 ресурсов), комментарий может превысить лимит GitLab по размеру сообщения или просто стать нечитаемым. 
    *   *Совет:* В таких случаях лучше прикреплять `plan` как **артефакт** и давать ссылку на него в комментарии.
3.  **Секреты в планах:** Иногда в `plan` могут попасть значения переменных (например, пароли, если они не помечены как `sensitive`). 
    *   *Совет:* Всегда используй переменные с пометкой `sensitive = true` и убедись, что маскирование переменных работает в GitLab CI.
4.  **Drift Detection:** Plan в MR помогает заметить "дрифт" (когда кто-то изменил инфраструктуру руками через консоль AWS/Azure). Если план показывает неожиданное удаление ресурсов — это красный флаг для ревьюера.

### ❓ FAQ (Частые вопросы)

**В: Можно ли делать `terraform apply` прямо из MR?**
**О:** В классическом GitOps — нет. Применяй код только после слияния (merge) в основную ветку (`main`). MR — это только для **проверки**. Apply должен происходить в пайплайне, который запускается по событию `push` в `main`.

**В: Что делать, если план показывает "Destroy and Recreate"?**
**О:** Это самый критичный момент. Если ревьюер видит `-/+ destroy and create replacement`, он должен проверить, не удаляется ли важная база данных или сетевой шлюз. Если это допустимо — ок, если нет — нужно менять код (например, использовать `lifecycle { prevent_destroy = true }`).

**В: Зачем использовать именно GitLab Managed State, а не S3?**
**О:** ПотомуY что это дает единую точку правды. Тебе не нужно настраивать IAM-роли для доступа к S3, не нужно отдельно настраивать DynamoDB для блокировок. Всё уже внутри GitLab, и права доступа управляются через группы GitLab.

**Г: Как понять, что план устарел?**
**О:** Если пока ты делал ревью, кто-то другой влил свой MR в `main`, твой план стал неактуальным (state изменился). В этом случае пайплайн должен упасть или потребовать перезапуска.

# 🛠 Тема: Installation Types (Типы установки GitLab)

Когда мы говорим об установке GitLab, главный вопрос не «как нажать кнопку», а **«кто будет это обслуживать?»**. В индустрии есть три основных пути: SaaS, Omnibus и Kubernetes.

### 1. GitLab SaaS (GitLab.com)
Это облачная версия. Ты просто регистрируешься, и всё уже работает. Тебе не нужен сервер, не нужно обновлять Linux и не нужно настраивать бэкапы базы данных.

*   **Суть:** Всё управление инфраструктурой лежит на плечах GitLab Inc.
*   **Плюсы:** 
    *   Zero Maintenance (ноль поддержки).
    *   Все обновления безопасности прилетают автоматически.
    *   Идеально для стартапов и небольших команд.
*   **Минусы/Нюансы:**
    *   Меньше контроля над настройками сервера (например, ты не можешь подкрутить конфиг Nginx или изменить системные лимиты).
    *   Данные хранятся на чужих серверах (важно для компаний с жестким комплаенсом).
    *   Цена может расти вместе с количеством пользователей и потреблением ресурсов.

### 2. GitLab Self-Managed: Omnibus (Классика)
Это самый популярный способ «самостоятельной» установки. **Omnibus** — это один большой пакет (архив), который содержит в себе *всё*: веб-сервер Nginx, базу данных PostgreSQL, Redis, Gitaly и т.д.

*   **Суть:** Ты берешь готовый «комбайн», ставишь его на свой Linux-сервер (`apt install` или `yum install`), и он разворачивает всю экосистему внутри себя.
*   **Плюсы:**
    *   Простота: одна команда — и всё работает.
    *   Полный контроль над данными и настройками.
    *   Легко обновлять (просто накатываешь новый пакет).
*   **Минусы/Нюансы:**
    *   **Vertical Scaling Only:** Чтобы GitLab работал быстрее, тебе нужно покупать сервер с *большим* количеством ядер и RAM. Ты не можешь легко «растянуть» один Omnibus-сервер на десять машин.
    *   Вся ответственность за бэкапы, обновления ОС и безопасность — на твоих плечах.

### 3. GitLab Self-Managed: Kubernetes (Helm Chart)
Это уровень «Hardcore». Мы разворачиваем GitLab не как один большой сервер, а как набор маленьких микросервисов (подов) внутри кластера Kubernetes.

*   **Суть:** Использование Helm-чарта для деплоя в K8s. Каждый компонент GitLab (API, Web, Gitaly, Database) превращается в отдельный сервис в кластере.
*   **Плюсы:**
    *   **Horizontal Scaling:** Если у тебя много пользователей, ты просто добавляешь узлы в Kubernetes, и система масштабируется сама.
    *   **High Availability (HA):** Идеально для отказоустойчивых систем. Если один под упал — K8s его перезапустит.
    *   Cloud Native: Идеально вписывается в современную инфраструктуру.
*   **Минусы/Нюансы:**
    *   **Extreme Complexity:** Тебе нужен очень сильный инженер (или команда), который умеет управлять Kubernetes.
    *   Очень дорого и сложно в настройке хранилищ (Persistence) и сетевых политик.

# 🛠 Шпаргалка: GitLab Backup & Restore

Бэкап GitLab — это не только копия репозиториев. Это комплексная задача по сохранению состояния базы данных, секретов и всех связанных артефактов. Если ты сохранишь код, но потеряешь ключи шифрования — твой бэкап будет бесполезным мусором.

## 1. Что входит в стандартный бэкап?
Когда мы запускаем стандартную команду `gitlab-rake gitlab:backup:create`, GitLab упаковывает в один архив (`.tar`):
*   **Базу данных (PostgreSQL):** пользователи, issue, merge requests, настройки проектов и т.д.
*   **Repositories:** сами Git-репозитории.
*   **Uploads:** аватарки, прикрепленные файлы к задачам.
*   **LFS objects:** большие файлы.
*   **Artifacts:** результаты работы CI/CD пайплайнов.
*   **Container Registry (опционально):** если настроено хранение внутри GitLab.

## ❌ Что НЕ входит в стандартный бэкап (КРИТИЧЕСКИ ВАЖНО)
Это то, на чем валятся новички. Эти файлы **нужно копировать отдельно** вручную или через свои скрипты:
1.  **`gitlab-secrets.json`**: Самый важный файл. В нем лежат ключи шифрования базы данных. Без него ты не сможешь расшифровать токены, пароли и переменные в БД.
2.  **`gitlab.rb`**: Конфигурация самого GitLab (настройки SMTP, домены, интеграции).
3.  **SSL Сертификаты**: Твои `.crt` и `.key` файлы для HTTPS.
4.  **Внешние хранилища (S3/MinIO)**: Если артефакты или репозитории лежат в облаке, команда `backup:create` их не скачает. Их нужно бэкапить средствами самого облака.

## 2. Процесс создания (Backup)
**Команда:**
```bash
sudo gitlab-rake gitlab:backup:create
```
*   **Где искать:** По умолчанию в `/var/opt/gitlab/backups`.
*   **Совет Senior'а:** Никогда не храни бэкапы на том же диске, где живет GitLab. Используй S3 или удаленное сетевое хранилиму.

## 3. Процесс восстановления (Restore)
Восстановление — это хирургическая операция. **Главное правило: Версия GitLab должна совпадать один-в-один!** Нельзя восстановить бэкап от версии 15.4 на версию 16.0.

**Алгоритм действий:**
1.  **Подготовка:** Установи ту же самую версию GitLab, с которой был сделан бэкап.
2.  **Копирование конфигов:** Перенеси `gitlab-secrets.json` и `gitlab.rb` на новый сервер (без них — всё!).
3.  **Остановка процессов:**
    ```bash
    sudo gitlab-ctl stop unicorn # или puma
    sudo gitlab-ctl stop sidekiq
    # Останавливаем все, что может писать в БД
    ```
4.  **Запуск восстановления:**
    ```bash
    sudo gitlab-rake gitlab:backup:restore BACKUP=timestamp_of_your_backup
    ```
    *(Примечание: `timestamp` — это часть имени файла без расширения .tar)*
5.  **Пересборка конфигурации:**
    ```bash
    sudo gitlab-ctl reconfigure
    sudo gitlab-ctl restart
    ```

## 4. Нюансы и "Подводные камни" (Senior Tips)

*   **Размер имеет значение:** Если база данных весит терабайты, `gitlab-rake` может упасть по таймауту или забить всё место на диске. В таких случаях нужно смотреть в сторону потоковых бэкапов базы (streaming replication/WAL-G).
*   **Проверка бэкапа (Validation):** Бэкап считается существующим только тогда, когда ты попробовал его развернуть на тестовом стенде. Раз в месяц делай "учебную тревогу".
*   **Permissions:** После восстановления часто «слетают» права на папки. Всегда проверяй `chown` для `/var/opt/gitlab`.
*   **Cleanup:** Не забывай настроить автоматическое удаление старых бэкапов (`backup_keep_time`), иначе диск забьется за неделю.

## ❓ FAQ (Частые вопросы)

**В: Я восстановил репозитории, но не могу войти в систему и вижу ошибки в БД. Что случилось?**
**О:** Скорее всего, ты забыл перенести файл `gitlab-secrets.json`. GitLab не может расшифровать данные в базе, поэтому считает их поврежденными или невалидными.

**В: Можно ли восстановить бэкап на более новую версию GitLab?**
**О:** Официально — нет. Сначала нужно восстановиться на ту же версию, а затем провести процесс Upgrade (обновления) по шагам.

**В: Мой бэкап весит 10 ГБ, но после восстановления репозитории пустые. Почему?**

**В: Как автоматизировать бэкап?**
**О:** Используй `crontab`. Создай скрипт, который запускает `gitlab-rake`, затем архивирует результат вместе с конфигами и отправляет в облако (например, через `aws s3 cp`).

# 🔐 Шпаргалка: Authentication Integration в GitLab

**Суть темы:** Интеграция аутентификации — это способ избавить пользователей от необходимости иметь отдельный логин/пароль именно для GitLab, связав его с уже существующей системой управления пользователями (Identity Provider или IdP). Это основа концепции **SSO (Single Sign-On)**.

---

### 1. Основные протоколы (Чем мы связываемся?)

В мире Enterprise используются три основных игрока:

#### **A. LDAP / Active Directory (Классика)**
Самый старый и распространенный метод. GitLab «спрашивает» у вашего сервера (например, Microsoft AD) вопрос: «Эй, вот этот юзер прислал пароль, он верный?».
*   **Как работает:** GitLab подключается к LDAP-серверу через специальный порт, выполняет поиск пользователя по дереву (DN — Distinguished Name) и проверяет пароль.
*   **Нюанс:** Настройка требует точного знания структуры вашего LDAP (Base DN, Bind DN, Search Filter). Если ошибешься в фильтре — никто не зайдет.

#### **B. SAML 2.0 (Золотой стандарт Enterprise)**
Это протокол на основе XML. Используется в связке с такими гигантами, как Okta, Azure AD (Entra ID), OneLogin.
*   **Как работает:** GitLab выступает как **Service Provider (SP)**, а ваша система (Okta) — как **Identity Provider (IdP)**. Когда юзер жмет «Войти», его перекидывает на страницу Okta, он там логинится, и Okta возвращает в GitLab «подтверждение» (Assertion), подписанное цифровой подписью.
*   **Нюанс:** Здесь критически важны сертификаты. Если срок действия сертификата, которым подписан SAML-ответ, истечет — аутентификация мгновенно «умрет».

#### **C. OAuth2 / OpenID Connect (OIDC) (Современный веб-подход)**
Используется для интеграции с Google, GitHub или собственными микросервисами.
*   **Как работает:** GitLab получает от провайдера не сам пароль, а **Access Token**. С помощью этого токена GitLab может зайти в профиль пользователя и забрать его имя и email.
*   **Нюнкс:** OIDC — это надстройка над OAuth2, которая добавляет слой идентификации (ID Token), что делает процесс более структурированным для логина.

---

### 2. Важные концепции (О чем молчат инструкции)

#### **User Provisioning (Создание пользователей)**
Есть два подхода:
1.  **Just-in-Time (JIT):** Пользователь не существует в GitLab, пока он впервые не нажмет «Войти через SAML». В этот момент GitLab «магически» создает ему аккаунт на основе данных из ответа провайдера.
2.  **Pre-provisioning:** Вы заранее синхронизируете список пользователей (например, через LDAP sync). Это лучше для контроля: вы точно знаете, кто имеет доступ, еще до того, как они зашли в систему.

#### **Group Sync (Синхронизация групп)**
Мало просто пустить пользователя. Нужно, чтобы он сразу попал в нужную группу проекта. Продвинутые настройки позволяют маппить (сопоставлять) группы из LDAP/SAML напрямую на группы в GitLab. Это экономит сотни часов работы админа.

#### **Email Collision (Конфликт почт)**
**Критический нюанс!** Если у пользователя уже есть локальный аккаунт в GitLab (созданный вручную) и он пытается зайти через SAML, но email совпадает — GitLab может либо выдать ошибку, либо попытаться «склеить» их. Нужно заранее продумать стратегию: либо запретить локальные аккаунты, либо настроить автоматическое слияние.

---

### 3. Резюме для архитектора (Checklist)

*   [ ] **Безопасность:** Используй только HTTPS/TLS для всех интеграций.
*   [ ] **Отказоустойчивость:** Всегда оставляй одного "Emergency Admin" с локальным паролем (Local Admin), который не зависит от внешних систем. Если упадет ваш AD или Okta, без этого аккаунта вы потеряете доступ к GitLab навсегда.
*   [ ] **Атрибуты:** Убедись, что ваш IdP передает `email` — это главный ключ для связки аккаунтов.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что делать, если после настройки SAML никто не может войти?**
**О:** Первым делом проверь логи GitLab (`gitlab-ctl tail`). В 90% случаев проблема либо в неверном URL (Entity ID), либо в просроченном сертификате, либо в том, что атрибут `email` приходит под другим именем (например, `mail` или `user_email`).

**В: Можно ли использовать одновременно LDAP и SAML?**
**О:** Технически — да, но это плохая практика для UX. Пользователи запутаются, какой кнопкой пользоваться. Лучше выбрать один основной метод (SAML для SSO), а LDAP оставить как вспомогательный или отказаться от него вовсе в пользу современных протоколов.

**В: Как GitLab узнает, что пользователя нужно удалить из GitLab, если его удалили из Active Directory?**
**О:** «Из коробки» GitLab не удаляет пользователей сам. Он просто перестанет пускать их по LDAP/SAML. Чтобы физически удалять или отключать их, нужно настраивать дополнительные скрипты синхронизации (Group Sync) или использовать API.

**В: В чем разница между OAuth2 и OIDC простыми словами?**
**О:** Представь, что ты в отеле. **OAuth2** — это ключ-карта, которая дает тебе право открывать дверь номера (доступ к ресурсу). **OIDC** — это паспорт, который подтверждает, кто именно ты такой (идентификация личности). OIDC использует механику OAuth2, но добавляет информацию о тебе.

# 🛠 Шпаргалка: Monitoring GitLab

Мониторинг GitLab делится на три уровня: **Infrastructure** (железо), **Application** (внутренние сервисы) и **User Experience** (метрики использования).

## 1. Уровень Инфраструктуры (The Foundation)
Если упало железо — приложение не важно.
* **CPU & RAM:** Следим за перегрузкой. Особое внимание — на пики во время массовых запусков CI/CD пайплайнов.
* **Disk I/O (Самое важное!):** GitLab очень чувствителен к скорости диска. Если `iowait` высокий, Gitaly (сервис работы с Git) начнет тормозить, и все операции с репозиториями «встанут».
* **Disk Space:** 
    * **Gitaly storage:** Рост репозиториев.
    * **Container Registry:** Образы Docker растут экспоненциально.
    * **PostgreSQL/Redis:** Если место кончится — база перейдет в Read-only, и GitLab «умрет».
* **Network Latency:** Проверка связи между GitLab и Runner'ами.

## 2. Уровень Приложения (The Core Services)
GitLab — это не один процесс, а оркестр сервисов. Нужно мониторить каждый:

* **Gitaly (Сердце Git):** Это сервис, который отвечает за все операции с файлами `.git`.
    * *Что смотреть:* RPC latency (задержка запросов), количество активных сессий, ошибки чтения/записи.
* **Sidekiq (Рабочая лошадка):** Выполняет фоновые задачи (отправка email, создание пайплайнов, проверки).
    * *Что смотреть:* **Queue Size** (размер очереди) и **Latency** (как долго задача висит в очереди). Если очередь растет — Sidekiq не справляется.
* **PostgreSQL (Мозг):** Хранит всё: пользователей, Issues, настройки.
    * *Что смотреть:* Количество соединений (Connections), Slow Queries (медленные запросы), объем транзакций.
* **Redis (Память):** Кэш и очереди.
    * *Что смотреть:* Использование памяти (Memory usage) и количество вытесненных ключей (Evictions). Если Redis переполнен, GitLab начнет «забывать» сессии пользователей.
* **Nginx/Puma:** Веб-сервер и сервер приложений.
    * *Что смотреть:* HTTP 5xx ошибки (ошибки сервера) и время ответа на запросы (Response Time).

## 3. Инструментарий (The Stack)
Как мы это видим? Стандарт индустрии для GitLab:
1. **Prometheus:** Собирает метрики со всех сервисов (GitLab поставляется с готовым конфигом под него).
2. **Grafana:** Визуализирует эти цифры в красивые графики.
3. **Alertmanager:** Отправляет алерты (Slack, Email, Telegram), если что-то пошло не так.
4. **Logs (ELK/Loki):** Если метрики говорят «что-то плохо», логи говорят «почему именно». Нужно мониторить `gitlab-rails/production.log` и `gitaly/current`.

---

## 💡 Нюансы от Senior-а
* **Золотое правило:** Не мониторь всё подряд. Фокусируйся на **Golden Signals**: Latency (задержка), Traffic (нагрузка), Errors (ошибки), Saturation (насыщенность ресурсами).
* **Скрытая угроссия — Runners:** Часто GitLab работает идеально, но «тормозит» CI/CD. Проблема почти всегда в мониторинге Runner-ов (нехватка CPU на агентах или переполнение диска с Docker-слоями).
* **Zombie Jobs:** Если Sidekiq забит, задачи могут висеть бесконечно, создавая иллюзию работающей системы, хотя по факту деплои не идут.

## ❓ FAQ (Частые вопросы)

**В: GitLab работает, но интерфейс очень медленный. С чего начать проверку?**
**О:** Первым делом смотри на **Gitaly latency** и **PostgreSQL slow queries**. В 90% случаев тормоза — это либо медленный диск, мешающий Gitaly, либо тяжелые запросы к базе.

**В: Очередь Sidekiq растет, но CPU на сервере низкий. Почему?**
**О:** Скорее всего, у тебя проблема с внешними ресурсами (например, база данных не успевает отвечать или сетевые задержки) либо достигнут лимит подключений к БД. Процессы ждут (I/O Wait), а не вычисляют.

**В: Как понять, что нам пора масштабировать GitLab?**
**О:** Если ты видишь стабильный рост **Sidekiq Queue Latency** и **Gitaly RPC latency** при росте количества пользователей — значит, текущая вертикальная мощь (CPU/RAM) исчерпана.

**В: Можно ли мониторить GitLab SaaS (gitlab.com)?**
**О:** Ты не можешь видеть внутренние метрики их серверов (Gitaly, Postgres), но ты **должен** мониторить свои показатели: время выполнения пайплайнов, ошибки API и доступность твоего репозитория через внешние проверки (Synthetics).

# 🚀 Шпаргалка: GitLab API & Webhooks

Если кратко: **API** — это способ, которым ты (или твой скрипт) спрашиваешь GitLab о чем-то. **Webhooks** — это способ, которым GitLab сам сообщает тебе о событиях. Это две стороны одной медали автоматизации.

---

## 1. GitLab REST API (Классика)
Это стандартный HTTP-интерфейс. Ты отправляешь запрос (GET, POST, PUT, DELETE) на определенный URL и получаешь JSON.

### 🔑 Аутентификация (Как войти?)
Никогда не используй свой основной пароль!
*   **Personal Access Tokens (PAT):** Для личных скриптов. Даешь права только на то, что нужно (Scope: `api`, `read_repository`).
*   **Project/Group Access Tokens:** Идеально для автоматизации конкретного проекта. Не привязаны к человеку (если разработчик уволится, бот не «умрет»).
*   **OAuth2:** Если строишь стороннее приложение для всей компании.

### 🛠 Основные возможности
*   **Управление ресурсами:** Создание веток, удаление Merge Requests, управление Issue, изменение прав доступа.
*   **CI/CD Automation:** Запуск пайплайнов (Trigger API), просмотр статуса джоб.
*   **Инвентаризация:** Выгрузка списка всех пользователей, групп или проектов для аудита.

### ⚠️ Нюансы Senior-уровня:
1.  **Pagination (Пагинация):** Это ловушка №1. Если ты запросишь список из 1000 проектов без указания параметров, GitLab вернет только первые 20–30. Всегда используй параметры `per_int` и `page`.
2.  **Rate Limiting:** Не делай тысячи запросов в секунду. GitLab может временно забанить твой IP или токен. Твой скрипт должен уметь обрабатывать ошибку `429 Too Many Requests`.
3.  **Versioning:** API имеет версии (например, `/api/v4/`). При обновлении GitLab старые версии могут отключить. Всегда проверяй текущую версию.

---

## 2. GitLab GraphQL API (Современный подход)
Если REST — это поход в магазин за конкретным продуктом, то GraphQL — это заказ полноценного обеда по меню.

*   **В чем профит?** В REST ты часто делаешь 5 запросов, чтобы собрать данные о проекте, авторе и коммитах (**Over-fetching**). В GraphQL ты пишешь один запрос и забираешь *только те поля*, которые тебе нужны.
*   **Когда использовать?** Когда нужно построить сложные отчеты или дашборды, где важна глубина связей (например: "Дай мне все Merge Requests, созданные пользователем X в группе Y, с указанием статуса пайплайна").

---

## 3. Webhooks (Слушатель событий)
Это механизм **Push-уведомлений**. Ты даешь GitLab URL своего сервера, и как только что-то происходит — GitLab «стучится» к тебе по HTTP POST.

### 🎯 Типичные триггеры:
*   **Push events:** Кто-то запушил код (идеально для запуска внешних тестов).
*   **Merge Request events:** MR создан, обновлен или закрыт (для уведомлений в Slack/Jira).
*   **Pipeline events:** Пайплайн прошел или упал (для алертинга команды).
*   **Issue events:** Появилась новая задача.

### 🛡 Безопасность Webhooks:
1.  **Secret Token:** При настройке вебхука в GitLab можно указать секретный токен. GitLab будет присылать его в заголовке `X-Gitlab-Token`. **Всегда проверяй его на своей стороне!** Иначе любой злоумышленник сможет слать тебе фейковые уведомления о «прошедших тестах».
2.  **HTTPS:** Твой URL должен работать только через TLS (HTTPS).

### ⚠️ Нюансы Senior-уровня:
1.  **Idempotency (Идемпотентность):** Сеть нестабильна. GitLab может прислать один и тот же вебхук дважды. Твой обработчик должен уметь понимать, что он это уже обрабатывал (например, проверяя ID события).
2.  **Async Processing:** Не делай тяжелую работу прямо внутри обработчика вебхука. Если твой скрипт будет думать 30 секунд, GitLab решит, что запрос не прошел, и начнет слать повторы. 
    *   *Правильный путь:* Получил вебхук $\to$ быстро записал в очередь (RabbitMQ/Redis) $\to$ ответил GitLab `200 OK` $\to$ отдельный воркер обработал задачу.

## ❓ FAQ (Часто задаваемые вопросы)

**В: Что выбрать для простого скрипта: REST или GraphQL?**
**О:** Если тебе нужно просто «удалить ветку» или «создать Issue» — бери **REST**. Это проще и понятнее. Если ты строишь сложный аналитический дашборд с кучей связей — учи **GraphQL**.

**В: Как мне проверить, что мой вебхук работает?**
**О:** Используй сервисы вроде `Webhook.site` или `ngrok`. Они создадут временный URL, на который ты сможешь увидеть структуру JSON-пейлоада (тела запроса), приходящего от GitLab.

**В: Могу ли я использовать Webhooks для запуска CI/CD?**
**О:** Можно, но это «костыль». Для запуска пайплайнов лучше использовать **Pipeline Triggers API**. Вебхуки предназначены для уведомления внешних систем, а не для управления внутренним циклом GitLab.

**В: Мой скрипт на Python/Go падает при обработке большого списка проектов через API. В чем причина?**
**О:** Скорее всего, ты забыл про **Pagination**. Ты пытаешься загрузить всё в память одним махом. Нужно реализовать цикл, который проходит по страницам (`page=1`, `page=2`...) до тех пор, пока не придет пустой ответ.
