# 🧠 Шпаргалка: Введение в Java Collections Framework (JCF)

### 1. Что такое JCF?
**Java Collections Framework (JCF)** — это не просто набор классов, это единая архитектура для хранения и манипулирования группами объектов. 

Представь, что тебе нужно хранить инструменты. Ты можешь использовать коробку, ящик, карман или магнитную планку. JCF — это твой «набор контейнеров», где каждый тип (интерфейс) определяет правила использования, а конкретные классы (реализации) — то, как именно они устроены внутри.

**Три кита JCF:**
1.  **Интерфейсы (Interfaces):** Определяют *что* коллекция может делать (например, `List` умеет добавлять элементы по индексу).
*Это контракт. Если класс реализует `List`, ты точно знаешь, как с ним работать.*
2.  **Реализации (Implementations):** Конкретные классы (например, `ArrayList`). Они определяют *как* данные хранятся в памяти.
3.  **Алгоритмы (Algorithms):** Статические методы класса `Collections` (сортировка, поиск, реверс). Они работают над любыми коллекциями, подходящими под условия.

---

### 2. Иерархия: Кто чей «родитель»?
Важно понимать, что не всё в JCF является `Collection`.

#### Группа `Collection` (Наследники интерфейса `Iterable`)
*   **`List` (Список):** Упорядоченная последовательность. Элементы имеют индекс. Допускает дубликаты. *(Пример: очередь людей в кассу).*
*   **`Set` (Множество):** Коллекция уникальных элементов. Дубликатов быть не может. *(Пример: список ID пользователей, которые не должны повторяться).*
*   **`Queue` (Очередь):** Предназначена для хранения элементов перед обработкой. Обычно работает по принципу FIFO (First In, First Out). *(Пример: задачи в принтере).*

#### Группа `Map` (Отдельная ветка)
*   **`Map` (Словарь/Карта):** **Не является** наследником `Collection`. Работает по принципу «Ключ $\to$ Значение». Ключи уникальны, значения — могут повторяться. *(Пример: номер телефона $\to$ имя человека).*

---

### 3. Нюансы от Senior-а (То, что важно знать)

#### 🗝️ Generics (Обобщения)
Без них JCF был бы кошмаром из `Object` и постоянных приведений типов (casting). Generics позволяют сказать: «Этот список — только для строк (`List<String>`)». Это обеспечивает **Type Safety** (типобезопасность) на этапе компиляции.

#### 🗝️ Complexity (Сложность $O$)
Выбор коллекции зависит от того, какую операцию ты делаешь чаще всего:
*   Нужно быстро доставать по индексу? $\to$ `ArrayList` ($O(1)$).
*   Нужно постоянно проверять наличие элемента в огромном списке? $\to$ `HashSet` ($O(1)$).
*   Нужно постоянно удалять из начала? $\to$ `LinkedList` или `Deque`.

#### 🗝️ Iterator & Fail-Fast
Когда ты идешь по коллекции через `Iterator`, Java следит за тем, чтобы никто не изменил структуру коллекции «втихаря» (не через итератор, а просто вызвав `.remove()`). Если структура изменилась — вылетит `ConcurrentModificationException`. Это называется **Fail-fast** механизм.

### ❓ FAQ: Подготовка к интервью

**В: Почему `Map` не наследуется от интерфейса `Collection`?**
**О:** Потому что у них принципиально разная природа. `Collection` работает с одиночными элементами, а `Map` — с парами «ключ-значение». Если бы `Map` наследовал `Collection`, возникла бы путаница: что именно мы добавляем в коллекцию? Ключ или всю пару?

**В: В чем разница между `Iterable` и `Collection`?**
**О:** `Iterable` — это самый верхний интерфейс. Его единственная задача — позволить объекту использовать цикл `for-each`. `Collection` — это более мощный интерфейс, который расширяет `Iterable` методами для управления данными (`add`, `remove`, `size`, `isEmpty`).

**по: Что такое `Collections` (с буквой 's' на конце)?**
**О:** Это утилитарный класс. В нем лежат статические методы для работы с коллекциями: `Collections.sort()`, `Collections.reverse()`, `Collections.unmodifiableList()` и другие. Не путай его с интерфейсом `Collection`!

**В: Что произойдет, если в `Set` добавить один и тот же объект дважды?**
**О:** Вторая попытка добавления вернет `false`, а размер коллекции не изменится. Это фундаментальное свойство `Set`. Но помни: это работает корректно только если у объекта правильно переопределены `equals()` и `hashCode()`.

# 📑 Шпаргалка: Интерфейс `List`

**Суть:** `List` — это упорядоченная коллекция (последовательность), которая позволяет хранить дубликаты и обращаться к элементам по их индексу (позиции).

### 🛠 Основные реализации

| Характеристика | `ArrayList` | `LinkedList` |
| :--- | :--- | :--- |
| **Структура данных** | Динамический массив | Двусвязный список |
| **Доступ по индексу** | $O(1)$ (мгновенно) | $O(n)$ (нужно перебирать с начала/конца) |
| **Вставка/Удаление** | $O(n)$ (из-за сдвига элементов) | $O(1)$ (если мы уже стоим на нужном узле) |
| **Память** | Экономно (только массив данных) | Дорого (хранит ссылки `prev` и `next`) |
| **Когда использовать** | Почти всегда (основной выбор) | Редко (если много операций в начале/конце) |

---

### 🧠 Глубокое погружение (Senior Level)

#### 1. Внутреннее устройство `ArrayList`
*   **Ресайз (Resizing):** Когда массив заполняется, Java создает новый массив большего размера (обычно в 1.5 раза) и копирует старые данные через `System.arraycopy()`. Это дорогая операция.
*   **Capacity vs Size:** `Size` — сколько элементов реально лежит в списке. `Capacity` — размер внутреннего массива. Если знаешь заранее, сколько будет элементов, используй конструктор `new ArrayList(initialCapacity)`, чтобы избежать лишних ребуild'ов.

#### 2. Нюансы `LinkedList`
*   Не забывай, что `LinkedList` реализует не только `List`, но и `Deque`. Это значит, что его можно использовать как очередь или стек.
*   Хотя вставка в середину по теории $O(1)$, на практике тебе всё равно нужно сначала *найти* это место за $O(n)$. Поэтому "магия" быстрого добавления в середину — это миф.

#### 3. Опасный метод `subList(int fromIndex, int toIndex)`
*   **Это НЕ копия!** Это "view" (представление) оригинального списка.
*   Если ты изменишь элемент в `subList`, он изменится и в основном списке.
*   **Ловушка:** Если ты модифицируешь структуру основного списка (добавишь/удалишь элементы), использование `subList` вызовет `ConcurrentModificationException`.

#### 4. Итерация: `Iterator` vs `ListIterator`
*   `Iterator` — можно только идти вперед.
*   `ListIterator` — специфичен для `List`. Позволяет ходить в обе стороны (`hasPrevious`, `previous`) и даже модифицировать элементы (заменять) прямо во время обхода.

---

### ⚠️ Важные нюансы (Pitfalls)

1.  **ConcurrentModificationException:** Возникает, если ты пытаешься удалить элемент из списка через `list.remove()` прямо внутри цикла `for-each`.
    *   *Как правильно:* Используй `iterator.remove()` или `removeIf()`.
2.  **Сложность поиска:** Поиск элемента по значению (`contains`, `indexOf`) в любом `List` — это всегда $O(n)$, так как нужно проверить каждый элемент. Если нужен быстрый поиск — используй `Set`.

---

### ❓ FAQ (Частые вопросы на интервью)

**В: Что лучше: `ArrayList` или `LinkedList` для частого добавления элементов в конец?**
**О:** `ArrayList`. Добавление в конец (`add`) в среднем занимает $O(1)$ (амортизированная сложность). В `LinkedList` это тоже $O(1)$, но накладные расходы на создание объектов узлов (Node) сделают `ArrayList` быстрее.

**В: Как избежать `ConcurrentModificationException` при удалении элементов?**
**О:** Использовать итератор (`iterator.remove()`) или метод `Collection.removeIf(predicate)`. Нельзя менять структуру коллекции, по которой идет стандартный цикл `for-each`.

**В: Что такое "view" в контексте `subList`?**
**О:** Это значит, что новый объект не содержит новых данных, он просто ссылается на тот же массив/узлы, что и оригинал. Любое структурное изменение оригинала делает `subList` невалидным.

**В: Можно ли в `ArrayList` хранить `null`?**
**О:** Да, `ArrayList` позволяет хранить любое количество `null`. (В отличие от некоторых других коллекций).

# 🚀 ArrayList: Ultimate Cheat Sheet

**ArrayList** — это динамически расширяемая реализация интерфейса `List`, основанная на массиве. Это самая используемая коллекция в Java.

### 🧠 Внутреннее устройство (Under the hood)
*   **Основа:** Внутри живет обычный массив `Object[] elementData`.
*   **Динамическое расширение:** Когда массив заполняется, происходит следующее:
    1. Создается новый массив большего размера.
    2. Старые элементы копируются в новый (через `Arrays.copyOf`).
*   **Коэффициент роста:** В современных JDK новый размер вычисляется как `oldCapacity + (oldCapacity >> 1)`. То есть массив увеличивается примерно на **50%** (умножается на 1.5). Это золотая середина между экономией памяти и частотой переаллокаций.
*   **Initial Capacity:** По умолчанию начальная емкость — **10**. Если ты заранее знаешь, что в списке будет 1000 элементов, **всегда** передавай размер в конструктор `new ArrayList<>(1000)`, чтобы избежать лишних циклов копирования.

### 📊 Сложность операций (Big O)

| Операция | Сложность | Комментарий |
| :--- | :--- | :--- |
| `get(index)` | **$O(1)$** | Мгновенный доступ по индексу (прямой расчет адреса в памяти). |
| `add(element)` | **$O(1)$** *amortized* | В среднем очень быстро. Но если случился ресайз — $O(n)$. |
| `add(index, element)` | **$O(n)$** | Нужно сдвинуть все элементы вправо, чтобы освободить место. |
| `remove(index)` | **$O(n)$** | Нужно сдвинуть все элементы влево, чтобы закрыть дырку. |
| `contains(element)` | **$O(n)$** | Линейный поиск (перебор каждого элемента). |
| `remove(Object)` | **$O(n)$** | Сначала ищем элемент ($O(n)$), потом сдвигаем хвост ($O(n)$). |

### ✅ Плюсы и ❌ Минусы

**Плюсы:**
*   🚀 **Быстрый доступ:** Идеален, если нужно часто читать данные по индексу.
*   📦 **Эффективное использование кэша процессора:** Массив лежит в памяти непрерывным блоком (локальность данных), что очень нравится CPU.

**Минусы:**
*   🐌 **Дорогое удаление/вставка в середину:** Сдвиг элементов убивает производительность на больших списках.
*   📉 **Расход памяти:** Из-за стратегии роста 1.5x, часть массива всегда остается пустой (over-provisioning).

### 💡 Senior Nuances (Нюансы для профи)

1.  **Fail-Fast Behavior:** Итератор `ArrayList` является *fail-fast*. Если ты модифицируешь список (добавляешь или удаляешь элементы) прямо во время итерации через `for-each`, ты получишь `ConcurrentModificationException`. Это отслеживается через внутренний счетчик `modCount`.
2.  **Метод `trimToSize()`:** Если ты заполнил огромный список, а потом удалил из него 90% элементов, массив всё еще занимает старый объем памяти. Вызови `trimToSize()`, чтобы уменьшить емкость массива до фактического количества элементов и освободить RAM.
*   **Memory Leak Risk:** При удалении элементов из массива (внутри `remove`), ссылка на объект в массиве не зануляется автоматически до тех пор, пока не произойдет сдвиг или очистка. Однако в современных реализациях JDK это обрабатывается корректно, чтобы не мешать Garbage Collector'у.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем ArrayList отличается от LinkedList?**
**О:** `ArrayList` — это массив (быстрый доступ $O(1)$, но медленная вставка/удаление). `LinkedList` — это двусвязный список (медленный доступ $O(n)$, но быстрая вставка/удаление, если у тебя уже есть ссылка на узел). В 99% случаев в реальной разработке `ArrayList` выигрывает за счет кэш-локальности.

**В: Что произойдет, если я буду добавлять элементы в ArrayList в цикле без указания начальной емкости?**
**О:** Будет происходить многократное создание новых массивов и копирование данных. Это создаст лишнюю нагрузку на CPU и увеличит работу Garbage Collector'а.

**В: Можно ли использовать ArrayList в многопоточной среде?**
**О:** Нет, он не потокобезопасен. Если несколько потоков одновременно пишут в него, можно получить поврежденное состояние или `ConcurrentModificationException`. Для многопоточности используй `CopyOnWriteArrayList` (если чтений много, а записей мало) или синхронизируй доступ.

**В: Как работает метод `add(index, element)`?**
**О:** Он находит место, создает временный массив (или использует текущий), сдвигает все элементы от указанного индекса до конца вправо на одну позицию и вставляет новый элемент. Сложность $O(n)$.

# 🧠 Шпаргалка: LinkedList (Java Collections)

`LinkedList` — это реализация интерфейса `List`, которая представляет собой **двусвязный список**. В отличие от `ArrayList`, где данные лежат в одном непрерывном массиве, здесь каждый элемент — это отдельный объект (**Node**), который знает о своем значении и о своих «соседях».

### 🏗️ Внутреннее устройство
Каждый элемент списка — это узел (`Node`), состоящий из трех полей:
1.  **`item`**: само значение (данные).
2.  **`next`**: ссылка на следующий узел.
3.  **`prev`**: ссылка на предыдущий узел.

Благодаря наличию ссылок в обе стороны, мы можем эффективно перемещаться как вперед, так и назад.

### 📊 Сложность операций (Big O)

| Операция | Сложность | Комментарий Senior'а |
| :--- | :--- | :--- |
| **`get(index)`** | $O(n)$ | **Плохо.** Чтобы найти 100-й элемент, нужно пройти по цепочке от начала (или конца) через 99 предыдущих. |
| **`add(E e)`** | $O(1)$ | **Отлично.** Просто создаем новый узел и перекидываем ссылки у головы/хвоста. |
| **`add(index, E e)`**| $O(n)$ | Поиск места вставки занимает $O(n)$, хотя сама вставка — $O(1)$. |
| **`remove(index)`** | $O(n)$ | Опять же, поиск узла — самая дорогая часть. |
| **`remove(Object o)`**| $O(n)$ | Нужно перебрать список, пока не найдем нужный объект. |
| **`addFirst` / `addLast`**| $O(1)$ | Идеально для реализации очередей. |

### ✅ Плюсы и ❌ Минусы

**Плюсы:**
*   **Динамичность:** Не нужно перевыделять память и копировать массив при заполнении (как в `ArrayList`).
*   **Быстрая вставка/удаление:** Если у тебя уже есть ссылка на нужный узел (например, при итерации), операция удаления или добавления — это просто перекидывание двух ссылок.
*   **Реализация Deque:** Благодаря двусвязности, он идеально подходит для создания очередей (`Queue`) и двусторонних очередей (`Deque`).

**Минусы:**
*   **Расход памяти (Overhead):** Каждый элемент — это не просто данные, а объект `Node`. На каждую запись тратится память под две дополнительные ссылки (`next` и `prev`). В больших списках это заметно.
*   **Cache Unfriendly:** Это критический момент. Элементы `ArrayList` лежат в памяти рядом (локальность данных), что позволяет процессору эффективно использовать кэш. Узлы `LinkedList` разбросаны по всей куче (Heap), что вызывает постоянные **cache misses**.
*   **Медленный доступ:** Нет возможности мгновенно прыгнуть к элементу по индексу.

### 💡 Когда использовать? (Senior Advice)
В 95% случаев в современной Java-разработке ты будешь использовать `ArrayList`. 
**Используй `LinkedList` только если:**
1. Тебе нужно очень много добавлять/удалять элементы в начало или конец списка (и ты работаешь с ним как с `Queue`/`Deque`).
2. Твой алгоритм подразумевает постоянную итерацию с удалением текущего элемента (через `Iterator`), где поиск позиции не требуется.

### ❓ FAQ: Часто задаваемые вопросы на интервью

**1. Вопрос: Что быстрее: `ArrayList.add(0, element)` или `LinkedList.add(0, element)`?**
*   **Ответ:** `LinkedList` быстрее. В `ArrayList` при добавлении в начало приходится сдвигать (копировать) весь массив вправо ($O(n)$). В `LinkedList` нужно просто создать узел и обновить ссылки головы ($O(1)$).

**2. Вопрос: Почему `LinkedList` считается менее эффективным для кэша процессора?**
*   **Ответ:** Из-за отсутствия локальности данных. Элементы массива лежат последовательно, процессор может предсказывать и подгружать их в кэш заранее (prefetching). Узлы списка разбросаны по памяти хаотично, поэтому процессору приходится каждый раз обращаться к медленной оперативной памяти.

**3. Вопрос: Можно ли использовать `LinkedList` как стек?**
*   **Ответ:** Технически — да, он реализует интерфейс `Deque`. Но на практике для стека лучше использовать `ArrayDeque`, так как он быстрее и потребляет меньше памяти. Класс `Stack` вообще устарел (legacy).

**4. Вопрос: Какова сложность поиска элемента по значению в `LinkedList`?**
*   **Ответ:** $O(n)$. Нам придется пройтись линейно от начала списка до тех пор, пока не встретим совпадение.

# 📜 Шпаргалка: Интерфейс List — Vector и Stack

### 1. Общая характеристика
Оба класса являются **Legacy** (устаревшими). Они появились в самых первых версиях Java и входят в иерархию `List`. Их объединяет одно фундаментальное свойство: **они синхронизированы (Thread-safe)**. Это значит, что каждый метод внутри содержит ключевое слово `synchronized`.

---

### 2. Vector (Вектор)
`Vector` — это динамический массив, который умеет расширяться при заполнении.

*   **Как работает:** Внутри это обычный массив. Когда место заканчивается, `Vector` создает новый массив большего размера и копирует туда старые данные.
*   **Главная фишка (Growth Policy):** В отличие от `ArrayList`, который увеличивается примерно на 50%, `Vector` по умолчанию **удваивает** свой размер (рост на 100%).
*   **Thread-safety:** Полный. Каждый метод (`add`, `get`, `remove`) заблокирован монитором объекта. Если один поток пишет, остальные ждут.

**⚠️ Нюанс Senior-уровня:**
Из-за того, что синхронизация происходит на **каждом** методе, `Vector` крайне неэффективен в многопоточной среде, где потоки работают с разными индексами. Возникает огромная конкуренция за блокировку (lock contention). В современном коде вместо него используют `ArrayList` + `Collections.synchronizedList()` или `CopyOnWriteArrayList`.

---

### 3. Stack (Стек)
`Stack` — это реализация структуры данных **LIFO** (Last In, First Out — «последним пришел, первым ушел»).

*   **Иерархия:** `Stack` **наследуется от `Vector`**. Это его главная архитектурная проблема.
*   **Основные методы:**
    *   `push(E item)` — добавить на вершину.
    *   `pop()` — извлечь и удалить верхний элемент.
    *   `peek()` — посмотреть верхний элемент, не удаляя его.
    *   `empty()` — проверить, пуст ли стек.
    *   `search(Object o)` — найти позицию элемента (возвращает 1-based индекс).

**⚠️ Нюанс Senior-уровля (Design Flaw):**
Наследование `Stack extends Vector` — это классический пример **нарушения принципов ООП**. Так как `Stack` — это `Vector`, ты можешь использовать методы вектора, например, `stack.add(0, element)` или `stack.remove(5)`. Это ломает саму суть стека (LIFO), позволяя вставлять элементы в середину. 
**Решение:** Вместо `Stack` всегда используй **`ArrayDeque`**.

| Характеристика | Vector | ArrayList | Stack |
| :--- | :--- | :--- | :--- |
| **Синхронизация** | Да (Thread-safe) | Нет | Да |
| **Производительность** | Низкая (из-за локов) | Высокая | Низкая |

### ❓ FAQ: Вопросы на собеседовании

**1. Почему `Vector` медленнее, чем `ArrayList`?**
> **Ответ:** Потомут что `Vector` — это синхронизированная коллекция. На каждый вызов метода (даже на простой `get()`) тратится время на захват и освобождение монитора (lock). В однопоточном коде эта операция бессмысленна и создает лишнюю нагрузку.

**2. Можно ли использовать `Stack` в современном Java-приложении?**
> **Ответ:** Технически можно, но это плохой тон. Из-за того, что он наследуется от `Vector`, он не гарантирует соблюдение принципов LIFO (можно лезть в середину). Для реализации стека следует использовать интерфейс `Deque` и реализацию `ArrayDeque`.

**3. Что произойдет, если два потока одновременно вызовут `add()` у `Vector`?**
> **Ответ:** Благодаря синхронизации, данные не повредятся. Один поток захватит монитор, выполнит операцию, а второй подождет своей очереди. Это обеспечит атомарность операции в рамках одного метода.

**4. В чем разница в стратегии роста между `ArrayList` и `Vector`?**
> **Ответ:** `ArrayList` увеличивает емкость примерно на 50% (коэффициент 1.5), что более экономно расходует память. `Vector` удваивает размер (коэффициент 2.0), что может привести к избыточному выделению памяти, но реже вызывает операции копирования массива.

# 🧠 Шпаргалка: Интерфейс `Set`

**Суть:** `Set` — это коллекция, которая **не допускает дубликатов**. Если ты попытаешься добавить элемент, который уже есть в сете, ничего не произойдет (метод `add()` вернет `false`).

### 1. Основные реализации (Твой выбор зависит от задачи)

| Реализация | Упорядоченность | Внутреннее устройство | Сложность (avg) | Когда использовать |
| :--- | :--- | :--- | :--- | :--- |
| **`HashSet`** | **Нет** (хаос) | `HashMap` | $O(1)$ | Когда важна максимальная скорость и порядок не важен. |
| **`LinkedHashSet`**| **По порядку вставки** | `HashMap` + Linked List | $O(1)$ | Когда нужны уникальные элементы, но нужно помнить, в каком порядке они пришли. |
| **`TreeSet`** | **Сортировка** (Natural/Comparator) | Red-Black Tree | $O(\log n)$ | Когда элементы всегда должны быть отсортированы. |

---

### 2. Глубокое погружение: Нюансы и "Подводные камни"

#### ⚠️ Контракт `equals()` и `hashCode()` — Это база!
`Set` (особенно `HashSet` и `LinkedHashSet`) определяет дубликаты, используя методы `hashCode()` и `equals()`.
*   **Если ты переопределил `equals`, но забыл `hashCode`:** Твой `Set` будет считать два "одинаковых" объекта разными, потому что они попадут в разные корзины (buckets) внутри хеш-таблицы. **Дубликаты пролезут.**
*   **Золотое правило:** Если `obj1.equals(obj2) == true`, то `obj1.hashCode() == obj2.hashCode()` **обязано** быть истинным.

#### 🌳 Особенности `TreeSet`
*   Он не использует `hashCode`. Он использует `compareTo()` (из интерфейса `Comparable`) или `compare()` (из `Comparator`).
*   **Важно:** Если `compare(a, b) == 0`, то `TreeSet` будет считать эти объекты дубликатами и **не добавит** второй. Это может привести к странному поведению, если логика сравнения не совпадает с логикой `equals`.
*   Не поддерживает `null` (выбросит `NullPointerException`), так как нельзя сравнить `null` с объектом.

#### 💧 Null-элементы
*   `HashSet` и `LinkedHashSet` позволяют хранить один `null`.
*   `TreeSet` — **запрещает** `null`.

---

### 3. Краткий Cheat Sheet по операциям

*   `add(e)` — добавить элемент (возвращает `false`, если он уже был).
*   `remove(e)` — удалить элемент.
*   `contains(e)` — проверка на наличие ($O(1)$ для Hash-реализаций).
*   `isEmpty()` / `size()` — проверка состояния.
*   **Set Operations (через Stream API или методы других коллекций):**
    *   *Intersection (Пересечение):* Оставить только те, что есть в обоих сетах.
    *   *Union (Объединение):* Слить два сета в один без дублей.
    *   *Difference (Разность):* Найти элементы, которые есть в первом, но нет во втором.

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Что будет, если добавить в `HashSet` объект, у которого изменилось поле, участвующее в `hashCode`?**
**О:** Это катастрофа. Объект "потеряется" внутри коллекции. Его старый хеш-код указывает на одну корзину, а новый — на другую. Ты не сможешь его найти через `contains()`, и он будет занимать память вечно (утечка памяти), пока ты не удалишь его по ссылке.

**В: В чем разница между `HashSet` и `LinkedHashSet` в плане производительности?**
**О:** `LinkedHashSet` чуть медленнее на операциях добавления/удаления, так как ему нужно поддерживать двусвязный список (обновлять ссылки на предыдущий и следующий элементы). Но он выигрывает в предсказуемости обхода.

**В: Можно ли использовать `Set` для хранения объектов с мутабельными (изменяемыми) полями?**
**О:** Можно, но это **плохая практика**. Если поле, влияющее на `hashCode`, изменится после добавления объекта в `Set`, структура коллекции нарушится. Старайся делать ключи/элементы сетов иммутабельными (immutable).

**В: Как быстро проверить, есть ли элементы в `List` или `Set`?**
**О:** В `HashSet` это $O(1)$ — мгновенно. В `ArrayList` это $O(n)$ — нужно перебрать весь список. Если тебе нужно часто делать `contains`, всегда выбирай `Set`.

# 🧠 Шпаргалка: Interface Set $\to$ HashSet

### 1. Что это такое?
**HashSet** — это реализация интерфейса `Set`, которая представляет собой коллекцию, содержащую только **уникальные** элементы. 

*   **Главная фишка:** Гарантирует отсутствие дубликаets.
*   **Порядок:** Не гарантирует никакой порядок элементов (порядок может меняться при добавлении новых элементов).
*   **В основе:** Внутри `HashSet` использует обычный `HashMap`. Когда ты добавляешь элемент в `HashSet`, он на самом деле кладется в `HashMap` как **ключ**, а в качестве значения используется заглушка-константа (dummy object).

### 2. Сложность операций (Big O)
В среднем, благодаря хеш-таблице, операции выполняются за константное время:

| Операция | Средняя сложность | Худший случай (коллизии) |
| :--- | :--- | :--- |
| `add()` | $O(1)$ | $O(n)$ или $O(\log n)$ |
| `remove()` | $O(1)$ | $O(n)$ или $O(\log n)$ |
| `contains()` | $O(1)$ | $O(n)$ или $O(\log n)$ |

*Примечание: С Java 8, если коллизий становится слишком много, структура внутри корзины превращается из связного списка в красно-черное дерево, что улучшает худший случай до $O(\log n)$.*

### 3. Фундамент: Контракт `hashCode()` и `equals()`
Это критически важная часть. Чтобы `HashSet` понял, что элементы одинаковые, он использует два метода:
1.  **`hashCode()`**: Определяет «корзину» (bucket), в которую попадет объект.
2.  **`equals()`**: Если в корзине уже есть объекты, метод проверяет, действительно ли новый объект равен старому.

> **Золотое правило Senior-а:** Если ты переопределяешь `equals()`, ты **обязан** переопределить `hashCode()`. 
> *Если не сделать этого, два «равных» объекта попадут в разные корзины, и `HashSet` позволит добавить дубликат.*

### 4. Нюансы и "подводные камни" (Senior level)

*   **Мутабельность (Изменяемость):** Никогда не меняй поля объекта, которые участвуют в расчете `hashCode`, после того как объект был добавлен в `HashSet`. Если ты изменишь поле $\to$ хеш-код изменится $\to$ объект «потеряется» внутри коллекции. Ты не сможерез его найти или удалить, что приведет к утечке памяти.
*   **Null:** `HashSet` позволяет хранить один `null` элемент.
*   **Потокобезопасность:** `HashSet` **не потокобезопасен**. Если несколько потоков одновременно меняют сет, это приведет к непредсказуемому поведению или `ConcurrentModificationException`. Для многопоточности используй `ConcurrentHashMap.newKeySet()`.
*   **Память:** `HashSet` потребляет больше памяти, чем `ArrayList`, такую как он хранит объекты + накладные расходы на структуру `HashMap` (ноды, ссылки).

---

### ❓ Часто задаваемые вопросы на интервью

**В: Как `HashSet` понимает, что элемент уже есть в коллекции?**
**О:** Сначала он вычисляет `hashCode()` объекта и ищет соответствующую корзину. Если корзина пуста — добавляет. Если не пуста, он перебирает все элементы в этой корзине, вызывая `equals()` для каждого, пока не найдет совпадение или не дойдет до конца списка/дерева.

**В: Что будет, если `hashCode()` всегда возвращает одно и то же число (например, `return 42;`)?**
**О:** Сет всё еще будет работать правильно (дубликаты не пропустит), но его эффективность упадет с $O(1)$ до $O(n)$. Все элементы попадут в одну корзину, превратив хеш-таблицу в обычный связный список. Это называется "катастрофической коллизией".

**В: В чем разница между `HashSet`, `LinkedHashSet` и `TreeSet`?**
**О:** 
1.  `HashSet`: Самый быстрый, но порядок не гарантирован.
2.  `LinkedHashSet`: Сохраняет порядок **вставки** (использует двусвязный список внутри).
3.  `TreeSet`: Хранит элементы в **отсортированном** порядке (на основе `Comparable` или `Comparator`), но операции медленнее — $O(\log n)$.

**В: Можно ли добавить в `HashSet` объект типа `List`?**
**О:** Технически — да. Но это опасно из-за упомянутой выше мутабельности. Если ты изменишь содержимое списка после добавления его в сет, его хеш-код изменится, и ты не сможешь найти этот список в сете.

# 🧠 Шпаргалка: LinkedHashSet

### 📌 Что это такое?
**`LinkedHashSet`** — это реализация интерфейса `Set`, которая сочетает в себе две вещи: магию хеш-таблицы (`HashSet`) и предсказуемость двусвязного списка.

Если коротко: **это `HashSet`, который помнит порядок, в котором ты добавлял элементы.**

### ⚙️ Как он устроен внутри (Under the hood)
Это самый важный момент для понимания. 
`LinkedHashSet` не изобретает велосипед. Внутри него лежит обычный `LinkedHashMap`. 

*   **Хеш-таблица:** Обеспечивает быстрое нахождение элемента по хеш-коду ($O(1)$).
*   **Двусвязный список (Doubly Linked List):** Каждая запись в коллекции имеет ссылки на «предыдущий» и «следующий» элементы. Именно этот список позволяет нам пройтись по элементам ровно в том порядке, в котором они были добавлены.

### 🚀 Сложность операций (Big O)
Здесь всё так же круто, как у `HashSet`:
*   **add()**: $O(1)$
*   **remove()**: $O(1)$
*   **contains()**: $O(1)$
*   **size()**: $O(1)$

*Нюанс:* Операции могут быть чуть-чуть медленнее, чем у `HashSet`, из-за необходимости поддерживать связи в двусвязном списке (обновлять указатели `before` и `after`), но на практике разница ничтожна.

### ⚖️ Сравнение: HashSet vs LinkedHashSet vs TreeSet

| Характеристика | `HashSet` | `LinkedHashSet` | `TreeSet` |
| :--- | :--- | :--- | :--- |
| **Порядок элементов** | Хаотичный (не гарантирован) | **По порядку вставки** | **Сортировка (Natural/Comparator)** |
| **Скорость** | Самая высокая | Высокая | Ниже ($O(\лога n)$) |
| **Структура** | Хеш-таблица | Хеш-таблица + Список | Красно-черное дерево |
| **Null элементы** | Разрешен 1 `null` | Разрешен 1 `null` | **Нельзя** (выдаст NPE при сортировке) |

### ⚠️ Важные нюансы и «подводные камни»

1.  **Память:** `LinkedHashSet` потребляет **больше памяти**, чем `HashSet`. Почему? Потому что нам нужно хранить дополнительные ссылки (`before` и `after`) для каждого узла в списке. Если у тебя миллионы объектов, это может стать заметным.
2.  **Дубликаты:** Как и любой `Set`, он игнорирует дубликаты. Но важно: если ты попытаешься добавить элемент, который уже есть, **порядок не изменится**. Элемент останется на своем старом месте.
3.  **Когда использовать:** 
    *   Когда тебе нужна уникальность.
    *   Когда тебе критически важен порядок (например, история последних действий пользователя или очередь задач, где нельзя менять последовательность).

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем `LinkedHashSet` отличается от `HashSet`?**
**О:** Главное отличие — сохранение порядка вставки. `HashSet` не гарантирует никакой порядок при итерации, а `LinkedHashSet` всегда вернет элементы так, как они заходили в коллекцию.

**В: Что произойдет, если я добавлю элемент, который уже есть в `LinkedHashSet`?**
**О:** Коллекция не изменится. Размер (`size`) останется прежним, и элемент не переместится на «конец» списка. Он сохранит свою исходную позицию.

**В: Какая сложность у итерации (прохода циклом) в `LinkedHashSet`?**
**О:** Она эффективнее, чем в `HashSet`. В `HashSet` итератору приходится обходить все корзины (buckets), включая пустые. В `LinkedHashSet` итератор идет прямо по связному списку, пропуская пустые ячейки хеш-таблицы.

**В: Можно ли использовать `null`?**
**О:** Да, как и в обычном `HashSet`, один `null` разрешен.

# 🌲 Cheat Sheet: TreeSet

`TreeSet` — это реализация интерфейса `NavigableSet` (который расширяет `SortedSet`). Если тебе нужно, чтобы элементы в коллекции всегда были **отсортированы** и при этом были **уникальными**, твой выбор — `TreeSet`.

### 🛠 Основные характеристики
*   **Упорядоченность:** Элементы хранятся в естественном порядке (Natural Ordering) или в порядке, заданном через `Comparator`.
*   **Уникальность:** Дубликаты не допускаются.
*   **Структура данных:** В основе лежит **Красно-черное дерево** (Red-Black Tree) — самобалансирующееся бинарное дерево поиска.
*   **Сложность операций:** $O(\log n)$ для основных операций (`add`, `remove`, `contains`). Это медленнее, чем у `HashSet` ($O(1)$), но зато данные всегда отсортированы.
*   **Null-значения:** **Не допускает `null`**. Попытка добавить `null` приведет к `NullPointerException`, так как дерево должно сравнивать элементы между собой.

---

### 🧭 Ключевые методы (NavigableSet)
`TreeSet` крут не просто сортировкой, а возможностью «навигации» по значениям:

1.  **Поиск границ:**
    *   `first()` / `last()` — получить самый первый/последний элемент.
    *   `lower(e)` — элемент, который **строго меньше** `e`.
    *   `higher(e)` — элемент, который **строго больше** `e`.
    *   `floor(e)` — элемент, который **меньше или равен** `e`.
    *   `ceiling(e)` — элемент, который **больше или равен** `e`.
2.  **Выборки (Views):**
    *   `subSet(from, to)` — подмножество элементов в диапазоне.
    *   `headSet(to)` — все элементы до указанного значения.
    *   `tailSet(from)` — все элементы начиная с указанного значения.

---

### ⚠️ Важные нюансы (Senior Level)

#### 1. Контракт `compareTo` vs `equals`
Это самая частая ловушка. `TreeSet` использует **только** метод `compareTo` (или `compare`) для определения того, является ли элемент дубликатом. Он **не смотрит** на `equals()`.
*   **Риск:** Если твой `compareTo` возвращает `0` для двух разных объектов, `TreeSet` просто не добавит второй объект, даже если `equals()` говорит, что они разные. 
*   **Золотое правило:** Всегда старайся делать так, чтобы `(x.compareTo(y) == 0) == (x.equals(y))`. Это называется *consistent with equals*.

#### 2. Выбор между Comparable и Comparator
*   Если ты контролируешь класс (например, `String` или `Integer`), используй **Comparable** (естественный порядок).
*   Если нужно несколько разных логик сортировки (например, по имени, а потом по возрасту) или ты не можешь менять исходный класс — используй **Comparator**.

#### 3. Производительность
Не используй `TreeSet` там, где тебе нужна просто уникальность без сортировки. В 90% случаев `HashSet` будет быстрее и эффективнее по памяти. Используй `TreeSet` только когда тебе критически важен порядок или поиск диапазона.

### ❓ FAQ (Вопросы на собеседовании)

**В: Что произойдет, если добавить в TreeSet объект, у которого `compareTo` возвращает 0, но `equals` возвращает `false`?**
**О:** В `TreeSet` будет добавлен только первый элемент. Второй будет проигнорирован как дубликат, так как для дерева "равенство" — это результат `compareTo == 0`.

**В: Можно ли использовать TreeSet для хранения объектов, которые могут измениться (mutable)?**
**О:** Это очень опасно. Если ты изменишь поле объекта, которое участвует в расчете `compareTo`, дерево «сломается»: элемент окажется не в той ветке, где он должен быть. Поиск и удаление перестанут работать корректно.

**В: В чем разница между `floor()` и `lower()`?**
**О:** Разница в обработке равенства. `floor(10)` вернет `10` (если он есть), а `lower(10)` вернет ближайшее число, которое строго меньше `10`.

**В: Какая сложность у операции `contains` в TreeSet?**
**О:** $O(\log n)$, так как нам нужно пройти по высоте сбалансированного дерева.

# 🧠 Шпаргалка: Interface Queue & Deque

## 1. Интерфейс `Queue` (Очередь)
**Суть:** Представь обычную очередь в магазине. Кто первый пришел, тот первым обслужился (**FIFO** — *First-In-First-Out*). Это структура данных для управления задачами, которые должны быть обработаны в порядке поступления.

### Главная ловушка: Два набора методов
У `Queue` есть две группы методов для одних и тех же операций. Это критически важно знать. Первая группа **выкидывает исключение**, вторая — **возвращает специальное значение** (`null` или `false`).

| Операция | Бросает Exception (Strict) | Возвращает спец. значение (Safe) | Что делает? |
| :--- | :--- | : (Пример) | :--- |
| **Вставка** | `add(e)` | `offer(e)` | Добавляет в конец. Если очередь полная, `add` упадет, а `offer` вернет `false`. |
| **Удаление** | `remove()` | `poll()` | Извлекает из начала. Если пусто, `remove` упадет, а `poll` вернет `null`. |
| **Просмотр** | `element()` | `peek()` | Смотрит на первый элемент, не удаляя его. Если пусто, `element` упадет, а `peek` вернет `null`. |

> **Senior Tip:** В реальном коде чаще используют `offer`, `poll` и `peek`, чтобы избежать внезапных `NoSuchElementException` и не загромождать код блоками `try-catch`.

---

## 2. Интерфейс `Deque` (Double-Ended Queue)
**Суть:** Это «двусторонняя» очередь. Ты можешь добавлять и удалять элементы как с начала, так и с конца. 
**Зачем это нужно?**
1.  Как **Queue** (FIFO): Работает как обычная очередь.
2.  Как **Stack** (LIFO — *Last-In-First-Out*): Работает как стек (последним пришел — первым ушел).

**Основные методы:**
*   `addFirst(e)` / `addLast(e)`
*   `removeFirst()` / `removeLast()`
*   `peekFirst()` / `peekLast()`

---

## 3. Основные реализации (Что выбрать?)

### 🟢 `PriorityQueue` (Очередь с приоритетом)
*   **Как работает:** Не FIFO. Элементы упорядочены согласно их естественному порядку (`Comparable`) или кастомному `Comparator`. В голове очереди всегда "самый важный" элемент.
*   **Внутрянка:** Двоичная куча (Binary Heap).
*   **Сложность:** `offer` и `poll` — $O(\log n)$.
*   **Нюанс:** Не позволяет вставлять `null`.

### 🟢 `ArrayDeque` (Массивная двусторонняя очередь)
*   **Как работает:** Быстрая, эффективная реализация `Deque` на базе массива.
*   **Когда использовать:** Это **лучшая замена классу `Stack`**. Если тебе нужен стек или обычная очередь и не нужна сортировка — бери `ArrayDeque`.
*   **Сложность:** $O(1)$ для операций с конца.
*   **Нюанс:** Не поддерживает `null`.

### 🟢 `LinkedList` (Связный список)
*   **Как работает:** Реализует и `Queue`, и `Deque`. Каждый элемент — это узел, знающий о следующем и предыдущем.
*   **Когда использовать:** Только если тебе нужно постоянно вставлять элементы в середину списка (но тогда это уже не совсем задача для очереди). Для очередей он медленнее, чем `ArrayDeque` из-за лишних аллокаций памяти под каждый узел.

---

## 🛠 Резюме по выбору
1.  Нужен **Стек**? $\to$ `ArrayDeque`.
2.  Нужна **Очередь (FIFO)**? $\to$ `ArrayDeque` или `LinkedList`.
3.  Нужна **Сортировка/Приоритет**? $\to$ `PriorityQueue`.
4.  Нужна **Многопоточность**? $\to$ Смотри в сторону `BlockingQueue` (но это уже другая тема).

## ❓ FAQ (Вопросы с собеседований)

**В: В чем разница между `poll()` и `remove()`?**
**О:** `remove()` выбросит исключение, если очередь пуста. `poll()` вернет `null`. Это вопрос про устойчивость кода к пустым структурам.

**В: Почему `ArrayDeque` лучше, чем `Stack`?**
**О:** Класс `Stack` наследуется от `Vector`, а значит, все его методы `synchronized`. Это накладывает огромные накладные расходы на производительность даже в однопоточном коде. `ArrayDeque` не синхронизирован и работает значительно быстрее.

**В: Может ли `PriorityQueue` содержать `null`?**
**О:** Нет. При попытке добавить `null` ты получишь `NullPointerException`. Это связано с тем, что алгоритм сравнения элементов (`comparator`) не сможет обработать `null`.

**В: Какая сложность у операций в `PriorityQueue`?**
**О:** Добавление (`offer`) и удаление головы (`poll`) занимают $O(\log n)$, так как нужно перестроить дерево (heapify). Поиск произвольного элемента — $O(n)$.

# 🧠 Шпаргалка: Queue, Deque и PriorityQueue

## 1. Иерархия и суть
В Java `Queue` (очередь) — это структура данных, предназначенная для хранения элементов перед их обработкой. Главный принцип здесь не "список", а **порядок извлечения**.

*   **`Queue`**: Интерфейс для работы по принципу FIFO (First-In-First-Out), но с фокусом на задачи (очередь задач, очередь сообщений).
*   **`Deque` (Double Ended Queue)**: "Двусторонняя очередь". Позволяет добавлять и удалять элементы как с начала, так и с конца. 
    *   *Senior tip:* `Deque` — это современная замена классу `Stack`. Если тебе нужен LIFO (Last-In-First-Out), используй `ArrayDeque`, а не `Stack`.

---

## 2. Методы: Две стороны одной медали
Это критически важный момент. У всех методов в очередях есть "дублеры". Разница — в обработке ошибок.

| Действие | Бросает исключение (Exception) | Возвращает спец. значение (`null`/`false`) | Когда использовать? |
| :--- | :--- | :--- | :--- |
| **Вставка** | `add(e)` | `offer(e)` | `offer` безопаснее, если очередь ограничена. |
| **Удаление** | `remove()` | `poll()` | `poll` вернет `null`, если очередь пуста (не уронит приложение). |
| **Просмотр** | `element()` | `peek()` | `peek` — стандарт де-факто для проверки "а есть ли там что-то?". |

---

## 3. PriorityQueue: Очередь с приоритетом
Это не обычная очередь. Здесь элементы извлекаются не в порядке очереди, а **в порядке их важности** (на основе естественного порядка или `Comparator`).

### Внутреннее устройство
*   В основе лежит **Binary Heap (Бинарная куча)**. По умолчанию — **Min-Heap** (минимальный элемент всегда наверху).
*   Это не отсортированный список! Это дерево, которое гарантирует, что корень — самый "малозначимый" (или "наиболее приоритетный") элемент.

### Сложность операций (Big O)
| Операция | Сложность | Комментарий |
| :--- | :--- | :--- |
| `peek()` | $O(1)$ | Мы всегда знаем, кто наверху. |
| `add(e)` / `offer(e)` | $O(\log n)$ | Нужно "протолкнуть" элемент вверх по дереву (sift-up). |
| `poll()` | $O(\log n)$ | После удаления нужно перестроить кучу (sift-down). |
| `remove(Object)` | $O(n)$ | Приходится искать элемент перебором. |

---

## 4. Подводные камни (Senior Nuances) ⚠️

1.  **`null` запрещен:** В `PriorityQueue` нельзя вставлять `null`. Ты получишь `NullPointerException`. Почему? Потому что куча не сможет сравнить `null` с другими элементами для определения приоритета.
2.  **Итератор — это ловушка:** Если ты пройдешься по `PriorityQueue` через `iterator()` или `forEach`, элементы будут идти в **произвольном порядке**, а не в порядке приоритета! 
    *   *Правило:* Чтобы увидеть элементы в правильном порядке, нужно делать `poll()` до тех пор, пока очередь не опустеет.
3.  **Не потокобезопасна:** `PriorityQueue` — это классический non-thread-safe класс. Если несколько потоков одновременно пишут в неё, всё развалится. Для многопоточности используй `PriorityBlockingQueue`.
4.  **Сравнение (Comparable vs Comparator):** 
    *   Если элементы реализуют `Comparable`, куча использует их внутренний метод `compareTo`.
    *   Если нет — ты **обязан** передать `Comparator` в конструктор, иначе получишь `ClassCastException`.

## ❓ FAQ (Частые вопросы на интервью)

**В: Чем `ArrayDeque` лучше, чем `Stack`?**
**О:** `Stack` наследуется от `Vector`, что делает его синхронизированным (медленным) и нарушает принципы ООП (наследование лишних методов). `ArrayDeque` быстрее, эффективнее использует память и предназначен именно для работы как стек/очередь.

**В: Что произойдет, если в `PriorityQueue` добавить элементы, которые не реализуют `Comparable`, и не передать `Comparator`?**
**О:** Произойдет `ClassCastException` в момент попытки вставки элемента.

**В: Гарантирует ли `PriorityQueue` сортировку элементов внутри массива?**
**О:** Нет. Она гарантирует только то, что самый приоритетный элемент будет первым при извлечении (`poll`). Внутренний массив представляет собой дерево (кучу), и порядок элементов в нем может выглядеть хаотично.

**В: Можно ли использовать `PriorityQueue` для реализации алгоритма Дейкстры?**
**О:** Да, это классический кейс. Мы кладем вершины графа в очередь с приоритетом по весу ребра, что позволяет всегда выбирать кратчайший путь.

# 🧠 Шпаргалка: Queue, Deque и ArrayDeque

### 1. Концептуальный фундамент
Прежде чем лезть в реализацию, нужно понимать разницу в интерфейсах:

*   **`Queue` (Очередь):** Работает по принципу **FIFO** (*First-In-First-Out*). Представь очередь в магазине: кто первый пришел, тот первым обслужен. Основные операции: `offer()` (в конец), `poll()` (из начала), `peek()` (посмотреть начало).
*   **`Deque` (Double-Ended Queue):** Двусторонняя очередь. Работает и как **FIFO**, и как **LIFO** (*Last-In-First-Out* — стек). Можно добавлять и удалять элементы с обоих концов. Представь вагон метро: люди могут заходить и выходить как с передней, так и с задней двери.

### 2. ArrayDeque: «Рабочая лошадка»
`ArrayDeque` — это реализация интерфейса `Deque`, основанная на **динамическом массиве**.

#### Как это устроено внутри (Senior level):
*   **Circular Array (Циклический массив):** Это ключевой момент. Внутри нет просто массива, где мы двигаем элементы. Используются два указателя: `head` (голова) и `tail` (хвост). Когда `tail` доходит до конца массива, он «перепрыгивает» в начало (wrap-around), если там есть пустое место. Это позволяет делать операции добавления/удаления за $O(1)$ без дорогостоящего сдвига всех элементов.
*   **Resizing:** Если массив заполняется, происходит расширение (обычно в 2 раза) и копирование элементов.

#### Главные особенности и нюансы:
1.  **Запрет на `null`:** В `ArrayDeque` **нельзя** класть `null`. Почему? Потому что методы `poll()` и `peek()` возвращают `null`, если очередь пуста. Если бы мы могли положить `null` в саму очередь, мы бы не смогли отличить «очередь пуста» от «в очереди лежит null».
2.  **Не потокобезопасен:** Как и большинство коллекций в JCF, он не защищен от конкурентного доступа. Если работаешь в многопоточности — используй `LinkedBlockingDeque` или внешнюю синхронизацию.
3.  **Эффективность памяти:** В отличие от `LinkedList`, `ArrayDeque` не создает отдельный объект-ноду для каждого элемента. Это экономит кучу памяти и уменьшает нагрузку на Garbage Collector (лучше локальность кэша процессора).

### 3. Сравнение: ArrayDeque vs LinkedList vs Stack

| Характеристика | `ArrayDeque` | `LinkedList` | `Stack` |
| :--- | :--- | :--- | :--- |
| **Структура** | Циклический массив | Двусвязный список | Наследник `Vector` (массив) |
| **Скорость (Head/Tail)** | $O(1)$ — очень быстро | $O(1)$ — чуть медленнее из-за аллокаций | $O(1)$, но с overhead на `synchronized` |
| **Память** | Экономно | Дорого (много объектов-нод) | Экономно |
| **Доступ по индексу**| Нет (только через итератор) | Нет | Да (через наследование от Vector) |
| **Вердикт** | **Лучший выбор для Stack/Queue** | Только если нужны вставки в середину | **Устарел (Legacy)** |

---

### ❓ FAQ: Часто задаваемые вопросы на интервью

**В: Почему `ArrayDeque` лучше, чем `Stack`?**
**О:** `Stack` — это старый класс, который наследуется от `Vector`. Это значит, что все его методы `synchronized`. Даже если ты работаешь в одном потоке, программа тратит ресурсы на захват и освобождение монитора. `ArrayDeque` не имеет этой нагрузки и работает быстрее.

**В: В чем главная проблема `ArrayDeque` по сравнению с `LinkedList`?**
**О:** `ArrayDeque` — это массив. Если тебе нужно вставить элемент в середину очереди (не в начало или конец), `ArrayDeque` придется сдвигать элементы, что даст сложность $O(n)$. `LinkedList` при наличии ссылки на узел сделает это быстрее. Но для задач Queue/Stack `ArrayDeque` почти всегда выигрывает.

**В: Что произойдет, если добавить элемент в `ArrayDeque`, когда массив заполнен?**
**О:** Произойдет ресайз (resizing). Создастся новый массив большего размера, и элементы из старого массива будут скопированы в новый с учетом циклической логики (head и tail пересчитаются).

**В: Можно ли использовать `ArrayDeque` как стек?**
**О:** Да, это рекомендуемый способ. Используй методы `push()` и `pop()`. Это эффективнее, чем использование `Stack`.

# 🧠 Шпаргалка: Queue, Deque и BlockingQueue

В Java работа с очередями строится на принципе "очереди за билетами": кто первый пришел, тот первый обслужен. Но в зависимости от задач (многопоточность, стек или двусторонняя очередь) интерфейсы меняются.

## 1. Queue (Очередь) — Классический FIFO
**Суть:** Интерфейс для работы по принципу **FIFO** (First-In-First-Out). Первый элемент, который мы положили, будет первым, кого мы достанем.

**Главный нюанс Senior-уровня:** У всех методов в `Queue` есть две версии: одна выбрасывает **Exception**, а другая возвращает **special value** (`null` или `false`). Это критично для стабильности кода.

| Действие | Бросает Exception | Возвращает спец. значение (Safe) | Что делает? |
| :--- | :--- | :--- | :--- |
| **Вставка** | `add(e)` | `offer(e)` | Добавляет элемент в конец. |
| **Удаление** | `remove()` | `poll()` | Удаляет и возвращает голову очереди. |
| **Просмотр** | `element()` | `peek()` | Смотрит на голову, не удаляя. |

> **💡 Совет:** В реальном коде почти всегда используй `offer`, `poll` и `peek`. Твой код не упадет с `NoSuchElementException`, если очередь вдруг окажется пустой.

---

## 2. Deque (Double-Ended Queue) — Двусторонняя очередь
**Суть:** Наследник `Queue`, который позволяет добавлять и удалять элементы **с обоих концов**. Это "супер-очередь".

**Зачем это нужно?**
1.  **Как Очередь (FIFO):** Используем методы `addLast` / `removeFirst`.
2.  **Как Стек (LIFO - Last-In-First-Out):** Используем методы `push` / `pop`.

**Основные реализации:**
*   **`ArrayDeque`**: Самая быстрая реализация. Внутри — массив. **Важно:** не поддерживает `null`. Если тебе нужна просто очередь или стек — бери `ArrayDeque`.
*   **`LinkedList`**: Реализует и `List`, и `Deque`. Работает медленнее из-за создания узлов (Node) в памяти, но гибче.

> **⚠️ Важный нюанс:** Забудь про класс `Stack`. Он устарел (legacy) и синхронизирован (медленный). Если нужен стек — используй `ArrayDeque`.

---

## 3. BlockingQueue — Очередь для многопоточности
**Суть:** Это специализированная очередь из пакета `java.util.concurrent`. Она "умная": если очередь пуста, поток, пытающийся взять элемент, **засыпает (блокируется)** и ждет появления данных. Если очередь полна, поток-производитель засыпает, пока не освободится место.

**Это фундамент паттерна Producer-Consumer.**

**Три режима работы методов:**
1.  **Throws Exception:** `add`, `remove`, `element`. (Если не получилось — всё упало).
2.  **Returns Special Value:** `offer`, `poll`, `peek`. (Если не получилось — вернул `null` или `false`).
3.  **Blocks (The Magic):** `put`, `take`. (Если пусто/полно — поток **ждет**).

**Популярные реализации:**
*   **`ArrayBlockingQueue`**: Ограниченная по размеру (bounded) очередь на базе массива. Нужно сразу указать емкость.
*   **`LinkedBlockingQueue`**: Может быть как ограниченной, так и нет. Обычно эффективнее для высокой нагрузки.

---

## 🚀 Итоговое сравнение (Cheat Sheet)

| Характеристика | `Queue` | `Deque` | `BlockingQueue` |
| :--- | :--- | :--- | :--- |
| **Принцип** | FIFO | FIFO + LIFO | FIFO + Blocking |
| **Доступ** | Только в конец (вставка) и из начала (извлечение) | С обоих концов | С одного конца, но с ожиданием |

| **Потокобезопасность** | Нет (по умолчанию) | Нет (по умолчанию) | **Да (Thread-safe)** |
| **Основной кейс** | Простая обработка задач | Стек или двусторонняя очередь | Передача данных между потоками |

## ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `poll()` и `remove()`?**
**О:** `remove()` выбросит исключение, если очередь пуста. `poll()` просто вернет `null`. Для надежности в production-коде лучше использовать `poll()`.

**В: Почему `ArrayDeque` лучше, чем `Stack`?**
**О:** `Stack` наследуется от `Vector`, что делает его синхронизированным (накладные расходы на блокировки даже там, где они не нужны). `ArrayDeque` — это современная, быстрая и несинхронизированная реализация стека.

**В: Что произойдет, если вызвать `put()` в `ArrayBlockingQueue`, когда она заполнена?**
**О:** Поток-вызывающий перейдет в состояние `WAITING` (заблокируется) и будет ждать, пока другой поток не вызовет `take()`, освободив место в очереди.

**В: Можно ли положить `null` в `ArrayDeque`?**
**О:** Нет. Большинство современных коллекций (включая `ArrayDeque`) запрещают `null`, чтобы избежать классической ошибки `NullPointerException` при проверке элементов.

# 🧠 Шпаргалка: Интерфейс Map

**Map** — это не `Collection` (в строгом смысле иерархии), а структура данных, работающая по принципу **«Ключ $\to$ Значение»**. Представь себе словарь: ты ищешь слово (ключ) и получаешь его перевод (значение).

### 📌 Основные правила
1.  **Уникальность ключей:** Ключи не могут дублироваться. Если добавить значение по уже существующему ключу, старое значение будет перезаписано.
2.  **Дублирование значений:** Значения могут повторяться. Разным ключам может соответствовать одно и то же значение.
3.  **Контракт `hashCode()` и `equals()`:** Это «священная корова». Если ты используешь свой объект в качестве ключа, ты **обязан** переопределить эти методы. Без этого `Map` тебя не найдет или будет работать некорректно.

---

### 🛠 Основные реализации

| Реализация | Упорядоченность | Особенности | Сложность (avg) |
| :--- | :--- | :--- | :--- |
| **`HashMap`** | Нет | Самая быстрая, универсальная. Позволяет один `null` ключ. | $O(1)$ |
| **`LinkedHashMap`** | Да (по вставке) | Сохраняет порядок добавления элементов. Идеальна для создания LRU-кэшей. | $O(1)$ |
| **`TreeMap`** | Да (сортировка) | Ключи всегда отсортированы (Natural order или `Comparator`). | $O(\log n)$ |
| **`Hashtable`** | Нет | Устарела (Legacy). Все методы `synchronized`. Медленная. Не любит `null`. | $O(1)$ |

---

### ⚙️ Внутреннее устройство HashMap (Senior Level)
Чтобы понимать, почему `HashMap` работает именно так, нужно знать про **Buckets (Корзины)**:

1.  **Хеширование:** Когда ты делаешь `.put(key, value)`, Java берет `hashCode()` ключа и применяет к нему дополнительную функцию, чтобы вычислить индекс в массиве (корзине).
2.  **Коллизии:** Если два разных ключа попали в одну корзину — это коллизия. 
    *   *Раньше (до Java 8):* Коллизии решались через связный список (**Chaining**). При плохой хеш-функции поиск превращался из $O(1)$ в $O(n)$.
    *   *Сейчас (Java 8+):* Если в одной корзине становится слишком много элементов (порог $\ge 8$), связный список превращается в **Красно-черное дерево**. Это улучшает поиск с $O(n)$ до $O(\log n)$.
3.  **Load Factor (Коэффициент загрузки):** По умолчанию `0.75`. Как только массив заполняется на 75%, происходит **Rehash** — создание нового, большего массива и перераспределение всех элементов. Это дорогая операция.

---

### 🚀 Полезные фишки (Java 8+)
Не пиши громоздкие `if (map.get(key) == null)`. Используй современный синтаксис:

*   `getOrDefault(key, defaultValue)` — вернет значение или дефолтное, если ключа нет. Избавляет от `NullPointerException`.
*   `putIfAbsent(key, value)` — добавит только если ключа еще нет.
*   `computeIfAbsent(key, k -> new ArrayList<>())` — **Маст-хэв!** Вычисляет значение и кладет в мапу, только если ключа нет (удобно для создания групп/списков).
*   `merge(key, value, remappingFunction)` — позволяет легко обновлять значения (например, инкрементировать счетчик).

---

### ❓ FAQ (Частые вопросы на интервью)

**В: Что будет, если `hashCode()` всегда возвращает одно и то же число?**
**О:** Все элементы попадут в одну корзину. `HashMap` превратится в связный список (или дерево), и сложность поиска упадет с $sO(1)$ до $O(n)$ или $O(\log n)$. Это называется "деградация производительности".

**В: Можно ли использовать `null` в качестве ключа?**
**О:** В `HashMap` — да (один ключ). В `TreeMap` — нет (выбросит `NullPointerException`, так как не сможет сравнить `null` с другими ключами при сортировке).

**В: Как эффективно итерироваться по Map?**
**О:** Никогда не используй `keySet()` и потом `get(key)` внутри цикла. Это лишние вычисления хеша. Используй `entrySet()`, так как он дает сразу и ключ, и значение:
```java
for (Map.Entry<String, Integer> entry : map.entrySet()) {
    System.out.println(entry.getKey() + " : " + entry.getValue());
}
```

**В: В чем разница между `HashMap` и `ConcurrentHashMap`?**
**О:** `HashMap` не потокобезопасен (может сломаться при записи из разных потоков). `ConcurrentHashMap` спроектирован для многопоточности: он не блокирует всю мапу целиком, а использует более тонкие механизмы (CAS и сегментированные блокировки), что позволяет многим потокам читать и писать одновременно.

# 🧠 Шпаргалка: HashMap

`HashMap` — это реализация интерфейса `Map`, основанная на хэш-таблице. Она хранит данные в формате **«ключ $\to$ значение»**. Это самая используемая структура данных в Java для быстрого поиска по уникальному идентификатору.

### 1. Основные характеристики
*   **Неупорядоченность:** `HashMap` не гарантирует сохранение порядка элементов (в отличие от `LinkedHashMap`). Порядок может измениться при ресайзе.
*   **Ключи и значения:** Разрешает один `null` ключ и любое количество `null` значений.
*   **Не потокобезопасна:** Если несколько потоков одновременно модифицируют `HashMap`, это приведет к непредсказуемому поведению (вплоть до бесконечного цикла в старых версиях или повреждения структуры).

### 2. Внутреннее устройство (Under the hood)
В основе лежит **массив объектов `Node<K, V>`** (их называют «корзинами» или *buckets*).

Каждый `Node` содержит:
1.  `int hash` — результат хэш-функции.
2.  `K key` — сам ключ.

3.  `V value` — значение.
4.  `Node<K, V> next` — ссылка на следующий элемент (для разрешения коллизий).

#### Как происходит поиск (`get`)?
1.  Вычисляется `hash` ключа.
2.  Вычисляется индекс в массиве: `index = hash & (n - 1)`, где `n` — размер массива.
3.  Переходим в корзину по индексу.
4.  Если в корзине один элемент — проверяем `key.equals(targetKey)`.
5.  Если элементов несколько (коллизия), идем по цепочке (Linked List) и сравниваем каждый узел через `equals()`.

### 3. Коллизии и эволюция Java 8+
**Коллизия** — это когда два разных ключа имеют одинаковый индекс в массиве.

*   **До Java 8:** При коллизиях элементы просто выстраивались в связный список. Если хэш-функция плохая, список становился огромным, и поиск превращался из $O(1)$ в $O(n)$.
*   **Java 8+ (Treeification):** Если количество элементов в одной корзине превышает порог **TREEIFY_THRESHOLD (8)**, связный список превращается в **Красно-черное дерево (Red-Black Tree)**. Это улучшает сложность поиска с $O(n)$ до $O(\log n)$. Обратный процесс (разбиение дерева в список) происходит при уменьшении размера корзины.

### 4. Ресайз (Resizing / Rehashing)
Когда количество элементов в карте достигает определенного порога, массив увеличивается вдвое.
*   **Load Factor (Коэффициент загрузки):** По умолчанию **0.75**. Это баланс между памятью и скоростью.
*   **Threshold (Порог):** `Capacity * Load Factor`. Как только количество элементов превышает этот порог, запускается ресайз.
*   **Процесс:** Создается новый массив в 2 раза больше. Все старые элементы пересчитываются и перекладываются в новые корзины. **Это дорогая операция ($O(n)$)**, поэтому важно заранее задавать `initialCapacity`, если данных много.

### 5. Сложность операций (Big O)

| Операция | Average Case | Worst Case (много коллизий) |
| :--- | :--- | :--- |
| **get()** | $O(1)$ | $O(\log n)$ (с деревом) / $O(n)$ (со списком) |
ert**put()** | $O(1)$ | $O(\log n)$ |
| **remove()** | $O(1)$ | $O(\log n)$ |

---

### ⚠️ Важные нюансы (Senior Tips)

1.  **Контракт `hashCode` и `equals`:** Это фундамент. Если ты переопределил `equals`, **обязан** переопределить `hashCode`. Если два объекта равны по `equals`, их `hashCode` должны быть одинаковыми. Иначе ты просто не найдешь объект в `HashMap`.
2.  **Immutable Keys (Неизменяемые ключи):** В качестве ключа лучше всего использовать неизменяемые объекты (например, `String`, `Integer`). Если поле объекта-ключа изменится после того, как он был положен в Map, его `hashCode` изменится, и ты никогда не достанешь значение по этому ключу.
3.  **Выбор начальной емкости:** Если ты знаешь, что в карте будет 1000 элементов, создай её сразу: `new HashMap<>(1334)`. (Почему 1334? Чтобы при загрузке 0.75 порог не сработал раньше времени).

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что будет, если два разных ключа вернут одинаковый `hashCode`?**
**О:** Произойдет коллизия. Элементы попадут в одну корзину. Java использует цепочку из `Node` или красно-черное дерево, чтобы хранить их вместе. Поиск будет работать через `equals()`.

**В: Почему `String` — идеальный ключ для `HashMap`?**
**О:** 1) Он неизменяем (immutability). 2) У него хорошо распределенная хэш-функция, что минимизирует коллизии.

**В: Чем `HashMap` отличается от `Hashtable`?**
**О:** 
1. `HashMap` позволяет `null` ключи/значения, `Hashtable` — нет.
2. `HashMap` не синхронизирован (быстрее), `Hashtable` — потокобезопасен (устарел).
3. В `Hashtable` все методы `synchronized`.

**В: Что такое "Treeification"?**
**О:** Это процесс преобразования связного списка в красно-черное дерево внутри корзины `HashMap`, когда количество коллизий в одной корзине достигает 8, чтобы избежать деградации производительности.
</p>

# 🧠 Шпаргалка: LinkedHashMap

### 📌 Что это такое?
**`LinkedHashMap`** — это наследник `HashMap`. Если `HashMap` — это просто «мешок с ключами», где порядок элементов не гарантирован, то `LinkedHashMap` — это **«умный мешок»**, который помнит, в каком порядке ты клал элементы (или в каком ты их трогал).

### 🛠 Как он устроен внутри?
Представь себе две структуры наложенные друг на друга:
1.  **Hash Table (как в HashMap):** Обеспечивает быстрый поиск по ключу за $O(1)$.
2.  **Doubly Linked List (Двусвязный список):** Все элементы связаны между собой ссылками `before` и `after`.

Когда ты добавляешь элемент, он попадает в нужную «корзину» (bucket) по хэш-коду, и одновременно с этим прицепляется в конец двусвязного списка.

### ⚙️ Два режима работы
Это критически важный нюанс. Через специальный конструктор можно изменить поведение:
`public LinkedHashMap(int initialCapacity, float loadFactor, boolean accessOrder)`

1.  **Insertion Order (по умолчанию, `accessOrder = false`):** Элементы хранятся в том порядке, в котором они были **вставлены**.
2.  **Access Order (`accessOrder = true`):** Элементы перемещаются в конец списка каждый раз, когда ты к ним обращаешься (через `get()` или `put()`). Это делает «свежие» элементы последними, а «старые» — первыми. **Именно на этом строится механизм LRU-кэша.**

### 📊 Сложность операций (Big O)
| Операция | Complexity | Комментарий |
| :--- | :--- | :--- |
| `get(key)` | $O(1)$ | Поиск по хэш-таблице. |
| `put(key, value)` | $O(1)$ | Добавление в таблицу + обновление ссылок в списке. |
| `remove(key)` | $O(1)$ | Удаление из таблицы + перестроение связей в списке. |
| **Итерация** | $O(N)$ | Проходит по списку, а не по всей емкости массива (это быстрее, чем у `HashMap`, если корзин много, а элементов мало). |

### ⚖️ Сравнение: HashMap vs LinkedHashMap

| Характеристика | HashMap | LinkedHashMap |
| :--- | :--- | :--- |
| **Порядок** | Не гарантирован (хаос) | Предсказуемый (вставка или доступ) |
| **Память** | Меньше (только узлы таблицы) | **Больше** (нужно хранить 2 доп. ссылки на каждый узел) |
| **Скорость итерации** | Зависит от `capacity` | Зависит только от `size` (количества элементов) |

### ⚠️ Нюансы и «подводные камни»
1.  **Потребление памяти:** Из-за хранения ссылок `before` и `after`, каждый узел в `LinkedHashMap` весит больше. Если у тебя миллионы мелких объектов, разница в памяти будет заметна.
2.  **Thread Safety:** Как и `HashMap`, он **не потокобезопасен**. В многопоточной среде используй `Collections.synchronizedMap(new LinkedHashMap<>())`.
3.  **LRU Cache (Pro Tip):** Если тебе нужно сделать кэш, который удаляет старые записи, ты можешь переопределить метод `removeEldestEntry`. Это превращает `LinkedHashMap` в полноценный кэш с вытеснением старых данных.

### ❓ Вопросы на собеседовании (Q&A)

**В: В чем главное отличие LinkedHashMap от HashMap?**
**О:** Главное отличие — сохранение порядка элементов. `HashMap` не гарантирует порядок, а `LinkedHashMap` поддерживает либо порядок вставки, либо порядок последнего обращения к элементу.

**В: Как реализовать простой LRU-кэш с помощью LinkedHashMap?**
**О:** Нужно создать наследника `LinkedHashMap`, вызвать конструктор с параметром `accessOrder = true` и переопределить метод `removeEldestEntry`. В этом методе нужно возвращать `true`, когда размер карты превышает допустимый лимит.

**В: Что происходит со структурой, когда мы вызываем `get()` в режиме `accessOrder = true`?**
**О:** Элемент не просто возвращается; его узел перемещается в конец двусвязного списка. Таким образом, он помечается как «самый свежий».

**В: Почему итерация по LinkedHashMap может быть быстрее, чем по HashMap при большой емкости (capacity) и малом количестве элементов?**
**О:** `HashMap` при итерации должна пройтись по всем корзинам (buckets), даже если они пустые. `LinkedHashMap` идет строго по списку существующих элементов, поэтому его время итерации зависит только от количества реально лежащих в нем объектов ($N$), а не от размера массива корзин.

# 🌲 TreeMap: Сортировка и порядок

`TreeMap` — это реализация интерфейса `Map`, которая хранит ключи в **отсортированном порядке**. Если `HashMap` — это хаотичный мешок с вещами, то `TreeMap` — это аккуратно расставленные по алфавиту книги на полке.

### 🛠 Как это устрое

1.  **Структура данных:** Под капотом используется **Красно-черное дерево** (Red-Black Tree). Это самобалансирующееся бинарное дерево поиска.
2.  **Сложность операций:** Благодаря свойствам дерева, основные операции (`get`, `put`, `remove`) имеют сложность **$O(\log n)$**. Это медленнее, чем $O(1)$ у `HashMap`, но зато порядок гарантирован.
3.  **Сортировка:** Элементы сортируются либо по **Natural Ordering** (естественный порядок: числа по возрастанию, строки по алфавиту), либо по кастомному **`Comparator`**, который ты передаешь в конструктор.

### 🚀 Главные фишки (Интерфейс `NavigableMap`)

`TreeMap` реализует не только `SortedMap`, но и более мощный `NavigableMap`. Это дает тебе методы для «навигации» по ключам:
*   `firstKey()` / `lastKey()` — получить самый первый/последний ключ.
*   `higherKey(key)` / `lowerKey(key)` — найти ближайший ключ, который **строго больше** или **строго меньше** заданного.
*   `ceilingKey(key)` / `floorKey(key)` — найти ближайший ключ, который **больше или равен** или **меньше или равен** заданному.
*   `subMap(fromKey, toKey)` — получить «срез» карты в определенном диапазоне.

### ⚠️ Важные нюансы (Senior Tips)

1.  **Null Keys — Запрещены!** В `TreeMap` нельзя использовать `null` в качестве ключа. Почему? Потому что при добавлении нового элемента дерево должно сравнить его с существующими через `compareTo()`. Попытка вызвать метод у `null` приведет к `NullPointerException`. 
    *(В отличие от HashMap, где один null-ключ разрешен).*
2.  **Контракт `Comparable` и `Comparator`:** Если ты используешь кастомный объект в качестве ключа, ты **обязан** либо реализовать интерфейс `Comparable`, либо передать `Comparator`. Если дерево не сможет понять, как сравнить два объекта, ты получишь ошибку.
3.  **Производительность:** Не используй `TreeMap` там, где тебе нужна просто быстрая вставка/поиск. Если порядок не важен — всегда выбирай `HashMap`. `TreeMap` оправдан только тогда, когда тебе критически важна сортировка или поиск диапанов.

---

### ❓ FAQ (Подготовка к собеседованию)

**В: В чем принципиальная разница между HashMap и TreeMap?**
**О:** Главное отличие в порядке элементов и сложности. `HashMap` не гарантирует порядок и работает за $O(1)$, а `TreeMap` всегда держит ключи отсортированными, но требует $O(\log n)$ на операции из-за необходимости балансировки дерева. Также `HashMap` допускает `null`-ключ, а `TreeMap` — нет.

**В: Что произойдет, если в TreeMap добавить объект, который не реализует Comparable, и не передать Comparator?**
**О:** Произойдет `ClassCastException` в момент попытки вставки (метод `put`), так как дерево не сможет выполнить сравнение для построения структуры.

**В: Можно ли использовать TreeMap для хранения элементов в порядке убывания?**
**О:** Да, это легко сделать двумя способами: либо передать в конструктор `Comparator.reverseOrder()`, либо реализовать метод `compareTo` в самом классе ключа так, чтобы он возвращал обратный результат.

**В: Какая сложность у метода `subMap`?**
**О:** Создание «вида» (view) через `subMap` происходит за $O(1)$, но любая операция с полученной подкартой (например, поиск элемента) будет зависеть от глубины дерева, т.е. $O(\log n)$.

# 🗄️ Тема: Hashtable (Legacy implementation)

**Hashtable** — это "старичок" из Java 1.0. Он появился еще до того, как появилось само понятие *Collections Framework*. Это реализация интерфейса `Map`, которая хранит данные в формате `key-ключ` $\to$ `value-значение`.

### 🚀 Основные характеристики
1.  **Thread-Safe (Потокобезопасность):** Все основные методы (`put`, `get`, `remove` и т.д.) помечены ключевым словом `synchronized`. Это значит, что только один поток может выполнять операцию над таблицей в конкретный момент времени.
2.  **Запрет на Null:** В отличие от `HashMap`, `Hashtable` **категорически не разрешает** ни `null` в качестве ключа, ни `null` в качестве значения. Попытка положить `null` вызовет `NullPointerException`.
3.  **Legacy (Устаревший):** Хотя он всё еще работает, в современном коде его использовать практически не за что.

### ⚙️ Внутреннее устройство (кратко)
Работает по принципу **хэш-таблицы**:
*   Внутри — массив "корзин" (buckets).
*   При добавлении вычисляется `hash` ключа, который определяет индекс в массиве.
*   Если два разных ключа попали в один индекс (**коллизия**), элементы выстраиваются в связный список (а в современных версиях Java — могут превращаться в дерево для ускорения поиска).

### ⚖️ Сравнение: Hashtable vs HashMap vs ConcurrentHashMap

Это "золотой" вопрос на собеседованиях.

| Характеристика | `Hashtable` | `HashMap` | `ConcurrentHashMap` |
| :--- | :--- | :--- | :--- |
| **Потокобезопасность** | **Да** (на уровне методов) | **Нет** | **Да** (на уровне сегментов/узлов) |
| **Разрешены Null** | ❌ Нет | ✅ Да | ❌ Нет |
| **Производительность** | 🐢 Низкая (из-за блокировок) | 🚀 Высокая | ⚡ Высокая (умная блокировка) |
| **Стиль** | Legacy (старый) | Современный стандарт | Стандарт для многопоточности |

> **Senior Note:** Главная проблема `Hashtable` — это "грубая" синхронизация. Представь очередь в кассу, где работает всего один кассир, и пока он обслуживает одного клиента, все остальные стоят и ждут. Это убивает параллелизм.

---

### ⚠️ Нюансы и "подводные камни"
*   **Производительность:** Из-за `synchronized` на каждом методе, при высокой нагрузке потоков `Hashtable` станет узким местом (bottleneck) всей системы.
*   **Iterator:** Итератор в `Hashtable` является **fail-fast**. Если во время обхода коллекции другой поток изменит её структуру, ты получишь `ConcurrentModificationException`.

---

### ❓ FAQ (Частые вопросы на интервью)

**1. Вопрос: Можно ли использовать Hashtable в многопоточном приложении?**
*   **Ответ:** Можно, так как он потокобезопасен. Но **не стоит**. Лучше использовать `ConcurrentHashMap`, так как он позволяет нескольким потокам работать с разными частями таблицы одновременно, не блокируя всю структуру.

**2. Вопрос: Что произойдет, если я сделаю `hashtable.put(null, "value")`?**
*   **Ответ:** Произойдет `NullPointerException`. `Hashtable` не поддерживает null-ключи.

**3. Вопрос: В чем разница между синхронизацией в Hashtable и ConcurrentHashMap?**
*   **Ответ:** `Hashtable` блокирует **весь объект** (всю таблицу) при любой операции. `ConcurrentHashMap` использует более тонкую блокировку (на уровне отдельных корзин/узлов), что позволяет множеству потоков одновременно читать и записывать данные в разные части карты.

**4. Вопрос: Если нам нужна потокобезопасная Map, но мы не хотим использовать ConcurrentHashMap, есть ли альтернатива для Hashtable?**
*   **Ответ:** Можно обернуть обычный `HashMap` с помощью `Collections.synchronizedMap(new HashMap<>())`. Это будет работать почти так же, как `Hashtable`, блокируя всю карту целиком.

# 🌲 Шпаргалка: Сбалансированные бинарные деревья (Balanced BST)

### 1. Проблема «Обычного» Бинарного Дерева поиска (BST)
В идеальном BST поиск, вставка и удаление работают за $O(\log n)$. Но у обычного BST есть фатальный недостаток: **он не гарантирует баланс**.

Если вставлять элементы по порядку (1, 2, 3, 4...), дерево превратится в **линейный список** (выродится). В этом случае сложность упадет с $O(\log n)$ до **$O(n)$**. Смысл дерева теряется.

**Сбалансированное дерево** — это структура, которая автоматически перестраивает себя так, чтобы высота дерева всегда оставалась примерно $\log n$.

---

### 2. Основные типы сбалансированных деревьев

#### A. AVL-дерево (Strict Balance)
Это самое «строгое» дерево. 
*   **Суть:** Для каждого узла разница высот его левого и правого поддеревьев (фактор баланса) не может быть больше **1**.
*   **Плюсы:** Очень быстрый поиск (поиск идет по максимально короткому пути).
*   **Минусы:** Дорогая вставка и удаление. При каждом изменении дерево может начать «рассыпаться», и его придется часто перестраивать (делать повороты).
*   **Когда использовать:** Когда у тебя много операций **чтения** и мало операций **записи**.

#### B. Красно-черное дерево (Red-Black Tree) — *Standard in Java*
Это «мягкое» сбалансированное дерево. Оно не гарантирует идеальную симметрию, но гарантирует, что путь от корня до самого дальнего листа не превысит путь до ближайшего листа более чем в 2 раза.
*   **Суть:** Каждый узел имеет цвет (красный или черный) и соблюдает набор правил (например, корень всегда черный, красный узел не может иметь красного потомка).
*   **Плюсы:** Быстрае вставка и удаление. Оно тратит меньше ресурсов на «ремонт» дерева после изменений по сравнению с AVL.
*   **Минусы:** Поиск чуть медленнее, чем в AVL (путь может быть длиннее).
*   **Где встречается:** Именно эта структура лежит в основе `java.util.TreeMap` и `java.util.TreeSet`.

---

### 3. Механизм самобалансировки: Повороты (Rotations)
Чтобы вернуть дерево в баланс, используются **повороты**. Это перестройка ссылок между узлами без нарушения правила порядка (левый < корень < правый).

1.  **Single Rotation (Одинарный поворот):** Левый или правый поворот вокруг узла.
2.  **Double Rotation (Двойной поворот):** Комбинация двух поворотов (сначала поворот потомка, затем поворот родителя). Используется, когда «перекос» идет зигзагом.

---

### 4. Сводная таблица сложности

| Операция | Обычное BST (Worst case) | Сбалансированное BST (Average/Worst) |
| :--- | :--- | :--- |
| **Search** | $O(n)$ | $O(\log n)$ |
| **Insert** | $O(n)$ | $O(\log n)$ |
| **Delete** | $O(n)$ | $O(\log n)$ |
| **Space** | $O(n)$ | $O(n)$ |

---

### 💡 Нюансы от Senior-а (на что обратить внимание)

1.  **Вырожденное дерево:** Всегда помни термин "Degenerate Tree". Это когда BST превращается в Linked List. Это главный враг производительности.
2.  **Выбор между AVL и Red-Black:** Если на собеседовании спросят: «Что выбрать для высоконагруженной системы с частыми обновлениями?», отвечай — **Red-Black**. Она дешевле в обслуживании (меньше поворотов).
3.  **Память:** Сбалансированные деревья тратят чуть больше памяти на хранение метаданных (в AVL — высота узла, в RBT — цвет узла).

---

### ❓ FAQ (Частые вопросы на интервью)

**В: Что произойдет с поиском в BST, если мы будем добавлять элементы в отсортированном порядке?**
*О: Дерево выродится в список, и сложность поиска увеличится с $O(\log n)$ до $O(n)$.*

**В: Почему Java использует именно Red-Black Tree для `TreeMap`, а не AVL?**
*О: Потому что в реальных приложениях операции записи (insert/delete) происходят очень часто. Red-Black Tree обеспечивает лучший баланс между скоростью поиска и стоимостью перестройки дерева при модификации.*

**В: Можно ли сказать, что все сбалансированные деревья — это BST?**
*О: Да, сбалансированное дерево — это частный случай бинарного дерева поиска, который просто гарантирует ограничение высоты.*

**В: Какая сложность у операции удаления в Red-Black Tree?**
*О: В худшем случае $O(\log n)$, так как нам нужно найти узел, удалить его и затем пройти вверх по дереву, чтобы восстановить правила раскраски и баланса.*

# 🧠 Шпаргалка: Механика Hashing (Хеширование)

### 1. Что такое Хеширование?
Если максимально просто: **Хеширование — это создание «отпечатка пальца» объекта.** 
У нас есть огромный массив данных, и мы не хотим перебирать его целиком (это $O(n)$), чтобы найти нужный элемент. Мы прогоняем объект через функцию и получаем число (`int`) — **hash code**. Это число говорит нам, в какую «корзину» (bucket) положить объект.

**Цель:** Превратить поиск по значению в поиск по индексу массива. Это дает нам магическую сложность **$O(1)$** в идеальных условиях.

---

### 2. Золотой контракт: `equals()` и `hashCode()`
Это база, на которой держится вся Java Collections Framework. Если ты нарушишь этот контракт, твои `HashMap` и `HashSet` превратятся в нерабочий мусор.

**Правила:**
1. **Если `a.equals(b) == true`, то `a.hashCode() == b.hashCode()` ОБЯЗАТЕЛЬНО.** (Если объекты равны, их отпечатки должны совпадать).
2. **Если `a.hashCode() == b.hashCode()`, это НЕ значит, что объекты равны.** Это называется **коллизия**.
3. Если ты переопределил `equals`, ты **обязан** переопределить `hashCode`.

> **Senior Note:** Почему? Если два «равных» объекта получат разные хеши, они попадут в разные корзины. Ты положишь объект в `HashMap` под ключом А, а потом попытаешься достать его по ключу Б (который логически равен А). Результат: `null`. Объект «потерялся» внутри коллекции.

---

ط### 3. Коллизии: Когда всё идет не по плану
Коллизия — это ситуация, когда два разных объекта (с точкирующий `equals() == false`) выдают одинаковый `hashCode` или попадают в один и тот же индекс массива (bucket).

**Как Java решает коллизии (Метод Chaining):**
В современных версиях Java (начиная с 8) используется гибридный подход:

1.  **Связный список (Linked List):** В каждой корзине (bucket) хранится ссылка на первый элемент. Если хеши совпали, новый элемент просто цепляется в конец списка.
    *   *Минус:* При большом количестве коллизий поиск превращается из $O(1)$ в $O(n)$.
2.  **Красно-черное дерево (Red-Black Tree):** Это «киллер-фича» Java 8+. Если в одной корзине становится слишком много элементов (порог `TREEIFY_THRESHOLD = 8`), список превращается в сбалансированное дерево.
    *   *Плюс:* Поиск замедляется не до $O(n)$, а до **$O(\log n)$**. Это защищает коллекцию от деградации производительности при плохой хеш-функции.

---

### 4. Каким должен быть хороший Hash Function?
Хорошая функция хеширования — это баланс между скоростью и качеством распределения.

*   **Скорость:** Вычисление должно быть очень быстрым (нельзя запускать тяжелые алгоритмы).
*   **Равномерность (Uniform Distribution):** Хеш-коды должны распределяться по всем корзинам максимально равномерно, чтобы не создавать «куч» в одной корзине.
*   **Детерминированность:** Для одного и того же объекта в рамках одного запуска программы результат всегда должен быть одинаковым.

---

### 5. Нюансы и "Подводные камни" (Senior Level)

*   **Мутабельность (Mutable objects):** **Никогда не используй поля, которые могут измениться, в расчете `hashCode`!** Если ты положил объект в `HashSet`, а потом изменил его поле, повлиявшее на хеш — объект останется в старой корзине. Ты не сможешь его найти и не сможешь удалить. Это классический Memory Leak.
*   **Маленький диапазон хешей:** Если твоя функция возвращает только 0 или 1, ты фактически убиваешь всю мощь хэш-таблицы, превращая её в обычный список.
*   **Распределение по индексам:** `hashCode()` возвращает огромный `int`. Чтобы понять, в какую корзину массива положить объект, Java делает операцию `(n - 1) & hash` (где $n$ — размер массива). Это быстрая замена операции деления по модулю `%`.

### ❓ FAQ (Вопросы на собеседовании)

**В: Что будет, если `hashCode()` всегда возвращает одно и то же число (например, `return 42;`)?**
**О:** Программа будет работать, но производительность упадет. Все объекты попадут в одну корзину. `HashMap` превратится в обычный связный список (или дерево), и сложность поиска станет $O(n)$ или $O(\log n)$ вместо $O(1)$. Это называется "Hash Flooding attack" в контексте безопасности.

**В: Можно ли переопределить только `hashCode`, не трогая `equals`?**
**О:** Можно, но это нарушит контракт. Ты получишь ситуацию, когда разные объекты имеют одинаковый хеш (коллизия), и это нормально. Но ты не сможешь гарантировать корректную работу логики сравнения объектов в коллекциях.

**В: Почему важно использовать `Objects.hash(field1, field2...)`?**
**О:** Это стандартный утилитарный метод, который минимизирует риск ошибок при реализации распределения хеша и правильно обрабатывает `null`-значения полей. Он использует алгоритм, похожий на тот, что в `String.hashCode()`, обеспечивая хорошее распределение.

**В: В какой момент список в корзине превращается в дерево?**
**О:** Когда количество элементов в одной корзине достигает 8 (`TREEIFY_THRESHOLD`), при условии, что общий размер таблицы достаточно велик (чтобы не было ложного срабатывания из-за ресайза).

# 🧠 Шпаргалка: Механика Hashing (hashCode & equals)

### 1. Суть проблемы
Когда мы работаем с коллекциями типа `HashSet` или `HashMap`, нам нужно быстро отвечать на вопрос: *"Есть ли уже такой объект в коллекции?"*. 
*   Сравнивать каждый новый объект со всеми существующими через `.equals()` — это $O(n)$, что очень медленно.
*   **Hashing** позволяет превратить поиск в $O(1)$ (в идеале), используя числовой «отпечаток» объекта.

---

### 2. Метод `equals(Object obj)`
Это инструмент для определения **логического равенства**.
*   **`==` (Identity):** Проверяет, указывают ли две переменные на одну и ту же область памяти (ссылочное равенство).
*   **`.equals()` (Equality):** Проверяет, равны ли *содержимое* и *состояние* объектов (логическое равенство).
*   **Senior Tip:** Всегда проверяй `null`, проверяй тип (`instanceof`) и сравнивай поля по порядку: от самых простых (примитивы) к самым сложным (объекты).

---

### 3. Метод `hashCode()`
Это метод, который возвращает **целое число (int)**, представляющее «адрес» или «корзину» (bucket) объекта в хеш-таблице.
*   Хороший `hashCode` должен распределять объекты по корзинам максимально равномерно.
*   Если у двух объектов одинаковый хеш — это **коллизия** (это нормально, но плохо для производительности).

---

### 4. Золотой Контракт (The Contract)
Это то, на чем валятся все джуны. Если ты переопределяешь один метод, ты **обязан** переопределить и второй.

1.  **Если `a.equals(b) == true`**, то **`a.hashCode() == b.hashCode()`** (Обязательное правило).
2.  **Если `a.hashCode() == b.hashCode()`**, это **НЕ значит**, что объекты равны (Это коллизия).
3.  **Если `a.hashCode() != b.hashCode()`**, то объекты **точно не равны** (это позволяет быстро отсеивать разные объекты).

> **Почему это критично?** Если ты нарушишь правило №1, ты положишь объект в `HashMap` под одним хешем, а потом не сможешь его найти, потому что при поиске метод `equals` будет работать с другим «отпечатком». Объект станет «призраком» в памяти.

---

### 5. Механика работы в HashMap (Алгоритм)
Когда ты делаешь `map.put(key, value)`:
1.  **Вычисляется `hashCode()` ключа.**
2.  На основе хеша вычисляется **индекс корзины** (bucket index).
3.  **Проверка коллизии:** 
    *   Если корзина пуста — кладем объект.
    le   Если в корзине уже есть элементы (коллизия):
    *   Мы перебираем все элементы в этой корзине и вызываем **`equals()`**.
    *   Если `equals()` вернул `true` — перезаписываем старое значение.
    *   Если `equals()` вернул `false` — добавляем новый элемент в список (или дерево) внутри корзины.

---

### 6. Best Practices (Как писать код)
В современном Java (7+) не нужно вручную считать веса полей. Используй утилиты:

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true; // Ссылка одна и та же? Это точно один объект
    if (o == null || getClass() != o.getClass()) return false; // Проверка на null и тип
    User user = (User) o;
    return id == user.id && 
           Objects.equals(name, user.name); // Используй Objects.equals для безопасности
}

@Override
public int hashCode() {
    // Магия генерации хеша на основе всех значимых полей
    return Objects.hash(id, name); 
}
```

**О:** Программа будет работать, но `HashMap` превратится в обычный `LinkedList`. Поиск станет $O(n)$, так как все объекты попадут в одну корзину, и нам придется перебирать их все через `equals()`. Это "убийство" производительности.

# 🧠 Механика Hashing: Коллизии и способы их разрешения

### Что такое коллизия?
Представь, что у тебя есть массив (корзины/buckets) на 10 ячеек. Ты используешь хеш-функцию, чтобы превратить ключ (например, строку "User1") в индекс массива. Хеш-функция выдает индекс `5`. Но другой ключ ("User2") тоже выдает индекс `5`. 
**Это и есть коллизия.** 

Математически это неизбежно (принцип Дирихле): ключей бесконечно много, а ячеек массива — конечное число. Наша задача — не избежать коллизий (это невозможно), а эффективно ими управлять.

---

### 1. Метод цепочек (Separate Chaining)
Это то, как работает стандартный `java.util.HashMap`.

**Суть:** Каждая ячейка массива — это не просто место для данных, а «голова» списка (или другой структуры). Если возникает коллизия, мы просто добавляем новый элемент в список, привязанный к этой ячейке.

*   **Плюсы:**
    *   **Простота реализации:** Легко добавлять элементы.
    *   **Устойчивость к переполнению:** Ты можешь положить в массив больше элементов, чем в нем есть ячеек (Load Factor может быть $> 1$).
    *   **Удаление:** Удалять элемент из списка — стандартная операция.
*   **Минусы:**
    *   **Расход памяти:** Нужно хранить ссылки (указатели) на следующие элементы в цепочке.
    *   **Cache Misses (Промах кэша):** Элементы списка разбросаны по всей оперативной памяти. Процессору тяжело их предсказывать, что замедляет работу.
cdot **Деградация:** Если хеш-функция плохая и все элементы летят в одну корзину, сложность поиска превращается из $O(1)$ в $O(n)$.

> **Senior Note (Java 8+):** В современной Java, если цепочка в одной корзине становится слишком длинной (больше 8 элементов), `HashMap` превращает её из связного списка в **красно-черное дерево**. Это снижает сложность поиска с $O(n)$ до $O(\log n)$.

---

### 2. Открытая адресация (Open Addressing)
Здесь все элементы хранятся строго внутри самого массива. Никаких внешних списков. Если место занято, мы ищем другое свободное место в этом же массиве.

**Механика поиска нового места (Пробирование/Probing):**
1.  **Линейное пробирование (Linear Probing):** Проверяем следующую ячейку: $i+1, i+2, i+3 \dots$ пока не найдем пустую.
    *   *Проблема:* **Первичная кластеризация**. Возникают «кучи» занятых ячеек. Если одна корзина забилась, она начинает забивать соседние, создавая эффект домино.
2.  **Квадратичное пробирование (Quadratic Probing):** Шаг поиска увеличивается квадратично: $i+1^2, i+2^2 \dots$
    *   *Плюс:* Уменьшает риск кластеризации.
3.  **Двойное хеширование (Double Hashing):** Если произошла коллизия, мы вычисляем *вторую* хеш-функцию, которая определяет размер нашего шага.
    *   *Плюс:* Самый эффективный метод из этой группы, практически исключает кластеры.

*   **Плюсы:**
    *   **Cache Locality (Локальность кэша):** Все данные лежат в одном массиве подряд. Процессор обожает это, так как данные подгружаются в кэш целыми блоками.
    *   **Экономия памяти:** Нет нужды хранить лишние ссылки на узлы списка.
*   **Минусы:**
    *   **Проблема удаления (The Tombstone Problem):** Если ты просто удалишь элемент из середины цепочки, поиск «сломается» (алгоритм решит, что дальше пусто и данных нет). Приходится ставить «метку смерти» (tombstone), что усложняет логику.
    *   **Чувствительность к Load Factor:** Как только массив заполняется на 70-80%, производительность резко падает. Нужно часто делать Rehash (пересоздание массива).

---

### Итоговое сравнение

| Характеристика | Chaining (Цепочки) | Open Addressing (Открытая адресация) |
| :--- | :--- | :--- |
| **Где хранятся данные** | Вне основного массива (в узлах списка/дерева) | Только внутри массива |
| **При переполнении** | Работает стабильно, пока есть память | Скорость падает катастрофически |
| **Использование памяти** | Больше (из-за ссылок) | Меньше (только массив) |
| **Cache Friendly** | Плохо (прыжки по памяти) | Отлично (последовательный доступ) |
| **Сложность удаления** | Легко | Сложно (нужны "метки смерти") |

### ❓ FAQ: Вопросы на собеседовании

**В: Что будет, если `hashCode()` всегда возвращает одно и то же число?**
**О:** В случае с *Chaining*, твоя `HashMap` превратится в связный список. Поиск станет $O(n)$. Если это Java 8+, то дерево поможет держать $O(\log n)$, но это всё равно катастрофически медленнее, чем ожидаемое $O(1)$.

**В: Почему в Java выбрана стратегия Chaining (с деревьями), а не Open Addressing?**
**О:** Chaining более предсказуем при плохих хеш-функциях и легче обрабатывает удаление элементов. В высоконагруженных системах "взрыв" кластеризации в открытой адресации может привести к внезапному отказу системы (latency spikes), что опаснее, чем чуть больший расход памяти на ссылки.

**В: Что такое "Clusterization" (Кластеризация) простыми словами?**
**О:** Это когда пустые места в массиве начинают собираться в огромные непрерывные блоки занятых ячеек. Из-за этого поиск любого нового элемента превращается в долгий пробег по всей этой «пробке» из данных.

# 🧠 Механика Hashing: Capacity, Load Factor, Threshold

Если ты хочешь понимать, как работают `HashMap` или `HashSet`, забудь про магию. Это просто массив (array), и управление его размером — это баланс между **памятью** и **скоростью**.

### 1. Capacity (Емкость)
**Что это:** Это размер внутреннего массива (количество «корзин» или *buckets*). 
*   Когда ты создаешь `new HashMap()`, по умолчанию `capacity` равна **16**.
*   Это не количество элементов в мапе, а количество ячеек, куда мы можем положить элементы.

> **Senior Note:** В Java `capacity` всегда стремится к степени двойки ($2^n$). Это делается для оптимизации вычисления индекса: вместо дорогой операции деления с остатком (`hash % capacity`) используется быстра/математическая операция `hash & (capacity - 1)`.

### 2. Load Factor (Коэффициент загрузки)
**Что это:** Это «уровень тревоги». Число (по умолчанию **0.75**), которое определяет, какой процент заполнения массива считается допустимым, прежде чем мы начнем паниковать и расширяться.
*   Он определяет соотношение между временем поиска и использованием памяти.

> **Senior Note:** Почему именно **0.75**? Это золотая середина (trade-off). 
> *   Если сделать его слишком **маленьким** (например, 0.5) $\to$ мы будем слишком часто расширять массив, тратя ресурсы CPU на перестроение (rehashing), хотя памяти будет много.
> *   Если сделать его слишком **большим** (например, 0.9) $\to$ в корзинах будет слишком много коллизий, и поиск превратится из $O(1)$ в $O(n)$ или $O(\log n)$.

### 3. Threshold (Порог)
**Что это:** Это конкретное число элементов, при достижении которого происходит **Resize** (ресайз).
*   Формула: $\text{Threshold} = \text{Capacity} \times \text{Load Factor}$.
*   При дефолтных значениях ($16 \times 0.75$), как только в мапе станет **12** элементов, сработает триггер на расширение.

---

### 🔄 Процесс Resize (Rehashing)
Когда `size >= threshold`, происходит следующее:
1.  Создается новый массив, размер которого обычно **в 2 раза больше** предыдущего.
2.  **Rehashing:** Все старые элементы из старого массива должны быть пересчитаны и разложены по новым корзинам. 
    *   *Почему нельзя просто скопировать?* Потому что индекс элемента зависит от `capacity` (через маску). При изменении размера индексы меняются!

**Это дорогая операция.** Она требует $O(n)$ времени, так как нужно пройтись по всем элементам.

---

### 💡 Нюансы для профи
*   **Коллизии и Resize:** Даже если `size < threshold`, коллизии могут возникать из-за плохого `hashCode()`. Но именно `threshold` контролирует общую плотность данных, чтобы минимизировать вероятность того, что цепочки в корзинах станут слишком длинными.
*   **Предварительная инициализация:** Если ты заранее знаешь, что в мапе будет 1000 элементов, **всегда** создавай её с указанием емкости: `new HashMap<>(1334)`. (Почему 1334? Чтобы при $0.75$ порог был чуть выше 1000 и не спровоцировал лишний ресайз).

---

### ❓ FAQ (Частые вопросы на интервью)

**В: Что произойдет, если я установлю Load Factor = 1.0?**
**О:** Мапа будет работать до последнего момента, пока массив не заполнится «под завязку». Это сэкономит память, но резко увеличит количество коллизий, и производительность упадет (поиск станет медленным).

**В: Что такое Rehashing и почему это плохо?**
**О:** Это процесс пересчета индексов всех элементов при изменении размера массива. Это плохо тем, что это тяжелая операция $O(n)$, которая может вызвать кратковременный «фриз» приложения, если данных очень много.

**В: Как связаны Capacity и производительность поиска?**
**О:** Чем больше `capacity`, тем меньше вероятность коллизий (элементы распределяются по разным корзинам), что делает поиск ближе к $O(1)$. Но слишком большая `capacity` — это пустая трата оперативной памяти.

**В: Можно ли изменить Load Factor после создания мапы?**
**О:** Напрямую через метод — нет. Его нужно передавать в конструктор при создании объекта.

# 🗂️ Тема: Сортировка и сравнение (Sorting & Comparison)

В Java есть два фундаментальных способа научить объекты стоять в очереди по порядку: **Comparable** (внутренний порядок) и **Comparator** (внешний порядок).

## 1. Comparable — «Естественный порядок»
Интерфейс `Comparable<T>` реализуется **внутри самого класса**. Он определяет, как объект сравнивается с объектом того же типа по умолчанию.

*   **Метод:** `int compareTo(T o)`
*   **Логика возврата:**
    *   `0` — элементы равны.
    *   `> 0` — текущий элемент (`this`) "больше" переданного (`o`) (должен идти позже).
    *   `< 0` — текущий элемент "меньше" переданного (должен идти раньше).
*   **Когда использовать:** Когда у класса есть один логичный стандарт сортировки (например, для `String` — по алфавиту, для `Integer` — по величине).

## 2. Comparator — «Внешний судья»
Интерфейс `Comparator<T>` — это **отдельный объект**, который вы создаете, чтобы реализовать *разные* стратегии сортировки для одного и того же класса.

*   **Метод:** `int compare(T o1, T o2)`
*   **Когда использовать:** Когда нужно сортировать по разным полям (по имени, потом по возрасту), или когда класс, который вы сортируете, принадлежит сторонней библиотеке и вы не можете менять его код.

### Современный стиль (Java 8+)
Забудь про анонимные классы. Senior-разработчик использует лямбды и фабричные методы:
```java (Пример)
// Сортировка по имени (коротко и ясно)
list.sort(Comparator.comparing(User::getName));

// Сложная сортировка: сначала по фамилии, потом по возрасту
list.sort(Comparator.comparing(User::getLastName)
                     .thenComparingInt(User::getAge));

// Сортировка в обратном порядке
list.sort(Comparator.comparing(User::getName).reversed());
```

## 3. Алгоритмы под капотом (Что важно знать)
Java не использует один алгоритм для всего. Выбор зависит от типа данных:

1.  **Для примитивов (`Arrays.sort(int[])` и др.):** Используется **Dual-Pivot Quicksort**. Он очень быстрый, но **нестабильный**.
2.  **Для объектов (`Collections.sort()`, `Arrays.sort(Object[])`):** Используется **Timsort** (гибрид сортировки вставками и сортировки слиянием). 
    *   **Важно:** Timsort — **стабильный** алгоритм.

> **Что такое стабильность (Stability)?** Если у тебя есть два объекта с одинаковым ключом (например, два пользователя с именем "Ivan"), при стабильной сортировке их относительный порядок в списке не изменится. Это критично, если ты делаешь многоуровневую сортировку (сначала по имени, потом по возрасту).

## 4. Нюансы и «подводные камни»
*   **Контракт `equals` и `compareTo`:** Хорошим тоном считается, чтобы `(x.compareTo(y) == 0) == (x.equals(y))`. Если это не соблюдается, коллекции вроде `TreeSet` могут вести себя странно (считать объекты одинаковыми, хотя `equals` говорит обратное).
*   **NullPointerException:** Если ты сравниваешь поле, которое может быть `null`, без проверки — всё упадет. 
    *   *Решение:* Используй `Comparator.nullsFirst()` или `Comparator.nullsLast()`.
*   **Сложность:** В среднем и худшем случае для объектов это **$O(n \log n)$**.

**О:** `Comparable` — это "самостоятельный" объект, он определяет свой естественный порядок. `Comparator` — это внешняя утилита, которая позволяет задавать любые дополнительные правила сортировки, не меняя код самого класса.

**О:** Использовать специальные обертки из интерфейса `Comparator`:

# 🧠 Сортировка и сравнение: Comparable vs Comparator

В Java всё крутится вокруг того, как объекты соотносятся друг с другом. Чтобы отсортировать список или использовать его в `TreeSet`, Java должна знать: "Объект А больше объекта Б или меньше?". Для этого есть два интерфейса.

## 1. Comparable (Естественный порядок)
**Суть:** Это «внутренняя» сортировка. Класс сам знает, как себя сравнивать. Если ты реализуешь `Comparable`, ты определяешь **Natural Ordering** (естественный порядок) для этого класса.

*   **Интерфейс:** `java.lang.Comparable`
*   **Метод:** `int compareTo(T o)`
*   **Где живет:** Внутри того самого класса, который мы сравниваем.
*   **Логика возврата:**
    *   `отрицательное число`: `this < o` (мы меньше)
    *   `ноль`: `this == o` (мы равны)
    *   `положительное число`: `this > o` (мы больше)

**Пример:** Для класса `Student` естественным порядком может быть сортировка по `id`.

```java
public class Student implements Comparable<Student> {
    private int id;
    private String name;

    @Override
    public int compareTo(Student other) {
        return Integer.compare(this.id, other.id); // Сортируем по ID
    }
}
```

---

## 2. Comparator (Внешняя стратегия)
**Суть:** Это «внешняя» сортировка. Если тебе нужно иметь **несколько разных способов** сортировки (например, то по имени, то по возрасту), `Comparable` тебе не поможет. Тебе нужен `Comparator`. Это паттерн «Стратегия».

*   **Инкремент:** `java.util.Comparator`
*   **Метод:** `int compare(T o1, T o2)`
*   **Где живет:** В отдельном классе или (что чаще) в виде лямбда-выражения.
*   **Преимущество:** Ты не меняешь код самого класса `Student`, ты просто пишете новые правила «снаружи».

**Современный подход (Java 8+):** Забудь про громоздкие классы. Используй статические методы в интерфейсе `Comparator`.

```java
// Сортировка по имени
Comparator<Student> nameComparator = Comparator.comparing(Student::getName);

// Сложная сортировка: сначала по имени, а если имена равны — по ID
Comparator<Student> complexComparator = Comparator
    .comparing(Student::getName)
    .thenComparingInt(Student::getId);

// Использование в коде
Collections.sort(studentList, nameComparator); 
// Или через Stream API
studentList.stream().sorted(nameComparator).collect(Collectors.toList());
```

## 📊 Сравнительная таблица

| Характеристика | Comparable | Comparator |
| :---s| :--- | :--- |
| **Тип порядка** | Естественный (Natural) | Пользовательский (Custom) |
| **Количество способов** | Только один (один метод в классе) | Неограниченно (много разных классов/лямбд) |
| **Изменение исходного кода** | Нужно менять сам класс | Класс менять не нужно |
| **Метод** | `compareTo(T o)` | `compare(T o1, T o2)` |
| **Пакет** | `java.lang` (всегда доступен) | `java.util` |

## ⚠️ Нюансы от Senior (На что смотрят на собеседованиях)

1.  **Контракт `equals()` и `compareTo()`:** Это ловушка! В идеале, если `a.compareTo(b) == 0`, то `a.equals(b)` тоже должно быть `true`. Если это не так, то коллекции вроде `TreeSet` будут работать странно (они могут "потерять" объект, считая его дубликатом, хотя `equals` говорит обратное).
2.  **Null Safety:** Метод `compareTo` упадет с `NullPointerException`, если ты попытаешься сравнить объект с `null`. Всегда думай о том, как обрабатывать `null` (в `Comparator` есть удобный метод `Comparator.nullsFirst()` или `nullsLast()`).
3.  **Стабильность:** Сортировка в Java (`TimSort`) является **стабильной**. Это значит, что если два элемента равны по критерию сортировки, их относительный порядок не изменится.

**В: Можно ли реализовать и Comparable, и Comparator для одного класса?**
**О:** Да. `Comparable` будет определять стандартное поведение (например, по ID), а ты сможешь написать сколько угодно `Comparator` для других сценариев (по имени, по дате рождения и т.д.).

**В: Что произойдет, если в `compareTo` я всегда буду возвращать `0`?**

**В: Как эффективно сравнивать строки или числа?**
**О:** Никогда не делай `return this.id - other.id;` (это классическая ошибка, которая может привести к переполнению `int`). Используй статические методы-помощники: `Integer.compare(x, y)` или `String.compareTo(other)`.

**В: В чем преимущество использования `thenComparing`?**
**О:** Это позволяет строить цепочки условий (Chaining). Это делает код читаемым и декларативным, избавляя от вложенных `if-else` внутри метода сравнения.

# 🧠 Шпаргалка: Сортировка в Java (TimSort)

Когда ты вызываешь `Collections.sort()` или `Arrays.sort(Object[])`, ты используешь **TimSort**. Это не просто один алгоритм, а гибридный алгоритм, созданный Тимом Петерсом. Его главная цель — эффективно работать с **реальными данными**, которые в жизни редко бывают полностью случайными (они часто уже частично отсортированы).

### 1. Суть алгоритма: Гибридность
TimSort — это комбинация **Merge Sort** (сортировка слиянием) и **Insertion Sort** (сортировка вставками).

*   **Insertion Sort (Сортировка вставками):** Идеальна для очень маленьких массивов или почти отсортированных данных. У неё низкие накладные расходы.
*   **Merge Sort (Сортировка слиянием):** Мощный алгоритм для больших объемов, но требует работы с памятью и рекурсии.

### 2. Как это работает (пошагово)
1.  **Поиск "Runs" (Полос):** Алгоритм сканирует массив в поисках уже отсортированных подпоследовательностей (назовем их *runs*). Если он находит убывающую последовательность, он просто разворачивает её (это $O(n)$).
2.  **MinRun:** Чтобы не плодить слишком много мелких фрагментов, алгоритм определяет минимальный размер "полосы" (`minrun`). Если найденная полоса меньше `minrun`, алгоритм добирает элементы из следующей части массива и использует **Insertion Sort**, чтобы расширить текущую полосу.
3.  **Слияние (Merging):** Когда массив разбит на достаточно крупные и отсовно отсортированные "полосы", начинается классическое слияние (как в Merge Sort), но с использованием стека для управления этими полосами, чтобы поддерживать баланс и минимизировать копирование.

### 3. Сложность (Big O)
| Случай | Сложность | Примечание |
| :--- | :--- | :--- |
| **Best Case** | $O(n)$ | Если массив уже отсортирован, алгоритм просто один раз пройдет по нему. |
| **Average Case** | $O(n \log n)$ | Стандартная работа при случайных данных. |
| **Worst Case** | $O(n \log n)$ | Даже в худшем сценарии он не деградирует до квадратичной сложности. |
| **Space Complexity** | $O(n)$ | Требуется дополнительная память для временного хранения элементов при слиянии. |

### 4. Ключевые нюансы (Senior Level)

*   **Stability (Стабильность):** Это критически важно. TimSort — **стабильный** алгоритм. Это значит, что если два объекта равны по ключу сортировки, их относительный порядок в массиве *не изменится*. Это позволяет делать многоуровневую сортировку (например: сначала по имени, потом по фамилии).
*   **Почему не QuickSort?** QuickSort в худшем случае может развалиться до $O(n^2)$ и он **нестабилен**. Для объектов (где важна стабильность) TimSort — гораздо более предсказуемый и безопасный выбор.
*   **Применимость:** Важно помнить, что `Arrays.sort()` для **примитивов** (`int[]`, `double[]` и т.д.) использует другой алгоритм (**Dual-Pivot Quicksort**). Почему? Потому что примитивам не нужна стабильность (число `5` не может быть "раньше" или "позже" другого числа `5`), а Dual-Pivot Quicksort быстрее и потребляет меньше памяти.

### ❓ FAQ: Вопросы на собеседовании

**В: Чем отличается сортировка примитивов от сортировки объектов в Java?**
**О:** Для объектов используется **TimSort** (стабильный, $O(n \log n)$), так как важна стабильность. Для примитивов используется **Dual-Pivot Quicksort** (нестабильный, но быстрее и экономичнее по памяти), так как стабильность для примитивов не имеет смысла.

**В: Что такое "стабильная сортировка" и почему это важно?**
**О:** Стабильность — это сохранение исходного порядка равных элементов. Это критично, когда мы сортируем сложные объекты по нескольким полям (например, сначала по дате, а потом по цене). Если сортировка нестабильна, второй проход может разрушить порядок первого.

**В: Какая лучшая сложность у TimSort?**
**О:** $O(n)$. Это происходит, когда массив уже отсортирован или почти отсортирован, так как алгоритм просто находит одну длинную "полосу" (run).

**В: Почему TimSort требует $O(n)$ дополнительной памяти?**
**О:** Потому что в процессе слияния (merging) нам нужно временное хранилище для элементов одной из полос, чтобы не затереть данные в основном массиве при копировании.

# 🧠 Шпаргалка: Итерация по коллекциям (Iteration)

Итерация — это процесс обхода элементов коллекции. В Java есть несколько способов сделать это, и выбор зависит от того, нужно ли тебе только **читать** данные, или ты планируешь их **изменять**.

### 1. Классический цикл `for` (по индексу)
Работает только с индексируемыми коллекциями (например, `List`).

*   **Как это выглядит:** `for (int i = 0; i < list.size(); i++) { ... }`
*   **Плюсы:** Можно обращаться к конкретному индексу, можно идти в обратном порядке.
*   **Минусы/Нюансы:** 
    *   **Опасность на `LinkedList`:** Если ты используешь этот цикл для `LinkedList`, сложность превращается из $O(n)$ в $O(n^2)$, потому что `list.get(i)` каждый раз бежит с начала списка. **Никогда не делай так с LinkedList.**
    *   **Проблема удаления:** Если ты удалишь элемент внутри цикла, индексы «поплывут», и ты либо пропустишь следующий элемент, либо получишь `IndexOutOfBoundsException`.

### 2. Enhanced `for-each` loop (Улучшенный цикл)
Самый популярный и читаемый способ для чтения данных. Работает с любым `Iterable`.

*   **Как это выглядит:** `for (String item : list) { ... }`
*   **Плюсы:** Максимально просто, чисто, работает со всеми коллекциями (`Set`, `List`, `Queue`).
*   **Минусы/Нюансы:** 
    *   **Нельзя удалять элементы:** Если ты попытаешься вызвать `list.remove()` внутри этого цикла, ты мгновенно получишь `ConcurrentModificationException`.

### 3. `Iterator` (Инструмент «старой школы» для модификации)
Единственный безопасный способ **удалять** элементы во время обхода в стандартных коллекциях.

*   **Как это выглядит:** 
    ```java
    Iterator<String> it = list.iterator();
    while (it.hasNext()) {
        String s = it.next();
        if (s.equals("delete_me")) it.remove(); // БЕЗОПАСНО
    }
    ```
*   **Плюсы:** Позволяет безопасно удалять текущий элемент (`it.remove()`).
*   **Нюанс:** Это «Fail-fast» итератор. Если кто-то другой (или ты сам через `list.add()`) изменит коллекцию, пока работает итератор, он тут же выбросит ошибку.

### 4. `ListIterator` (Специализация для списков)
Более мощная версия итератора, доступная только для `List`.

*   **Фишки:** 
    *   **Двунаправленность:** Можно идти назад (`hasPrevious()`, `previous()`).
    *   **Модификация:** Можно не только удалять, но и добавлять элементы (`add()`) или заменять текущий (`set()`).
*   **Когда использовать:** Когда тебе нужно сложное перемещение по списку (например, алгоритм реверсирования или поиск соседей).

### 5. `Iterable.forEach()` (Functional Style / Java 8+)
Современный декларативный подход с использованием лямбда-выражений.

*   **Как это выглядит:** `list.forEach(item -> System.out.println(item));` или `list.forEach(System.out::println);`
*   **Плюсы:** Очень кратко, идеально для простых операций чтения/логирования.
*   **Минусы:** 
    *   **Нельзя использовать `break` или `continue`:** Внутри лямбды ты не можешь прервать цикл (придется выбрасывать исключение, что является плохим тоном).
    *   **Сложность отладки:** Сложнее ставить точки остановки (breakpoints) внутри цепочки вызовов.

---

### ⚠️ Главный подвох: Fail-Fast vs Fail-Safe

Это то, на чем валят на собеседованиях.

1.  **Fail-Fast (Быстрый отказ):** Итераторы стандартных коллекций (`ArrayList`, `HashMap`). Они следят за счет переменной `modCount` (счетчик модификаций). Если `modCount` изменился во время итерации — бам! `ConcurrentModificationException`.
2.  **Fail-Safe / Weakly Consistent:** Итераторы из пакета `java.util.concurrent` (например, для `CopyOnWriteArrayList`). Они работают с **копией** данных или позволяют видеть изменения, но не выбрасывают исключение при модификации.

**В: Что произойдет, если я удалю элемент из `ArrayList` внутри цикла `for-each`?**
**О:** Ты получишь `ConcurrentModificationException`. Это происходит потому, что `for-each` под капотом использует `Iterator`, который замечает несоответствие структуры коллекции и выбрасывает ошибку.

**В: Как безопасно удалить элементы из списка по условию?**

2. (Самый современный) Использовать метод `list.removeIf(element -> condition)`.

**В: В чем разница между `Iterator` и `ListIterator`?**
**О:** `Iterator` — универсален для всех коллекций и умеет только вперед и удаление. `ListIterator` — только для списков, умеет ходить в обе стороны, позволяет добавлять и заменять элементы.

# 🛠 Шпаргалка: Iterator vs ListIterator

Когда нам нужно пройтись по элементам коллекции, у нас есть два основных инструмента. Разница между ними — в **области применения** и **мощности**.

### 1. Iterator (Универсальный солдат)
`Iterator` — это базовый интерфейс для всех коллекций (`Set`, `List`, `Queue`). Его задача — просто дать тебе возможность перебрать элементы один за другим.

*   **Где работает:** В любой реализации интерфейса `Collection`.
*   **Направление:** Только **вперед** (forward-only).
*   **Основные методы:**
    *   `hasNext()` — есть ли следующий элемент?
    *   `next()` — верни следующий элемент и сдвинь курсор.
    *   `remove()` — удали текущий элемент из коллекции (единственная безопасная операция модификации во время итерации).

### 2. ListIterator (Специалист по спискам)
`ListIterator` — это расширенная версия `Iterator`, предназначенная **только для списков** (`List`). Он "умнее" и умеет больше.

*   **Где работает:** Только в реализациях `List` (ArrayList, LinkedList и т.д.).
*   **Направление:** **Двунаправленный** (вперед и назад).
*   **Основные методы (чего нет в Iterator):**
    *   `hasPrevious()` / `previous()` — движение в обратную сторону.
    *   `add(E e)` — можно вставить новый элемент прямо в текущую позицию.
    *   `set(E e)` — можно заменить текущий элемент на новый.
    *   `nextIndex()` / `previousIndex()` — получение индекса элемента.

### ⚠️ Senior Nuances (То, на чем валятся джуны)

1.  **Fail-Fast механизм:** Оба итератора являются *fail-fast*. Это значит, что если ты начнешь модифицировать коллекцию (например, через `list.remove()`) прямо во время обхода итератором, ты мгновенно получишь **`ConcurrentModificationException`**. 
    *   *Правило:* Если нужно удалять элементы во время цикла — используй только `iterator.remove()`.

2.  **Курсор — это не элемент:** Представь, что курсор итератора стоит *между* элементами. Когда ты вызываешь `next()`, ты сначала перепрыгиваешь через элемент и возвращаешь его. Это важно понимать при работе с индексами в `ListIterator`.

3.  **Сложность операции:** В `ArrayList` использование `ListIterator` для удаления или добавления может быть дорогим ($O(n)$), так как при каждом изменении происходит сдвиг массива, несмотря на удобство интерфейса.

**В: Что произойдет, если вызвать `remove()` дважды подряд?**
**О:** Ты получишь `IllegalStateException`. Метод `remove()` можно вызывать только один раз между двумя вызовами `next()`.

**В: Как безопасно удалить элементы из списка по условию?**
**О:** 
1. Старым способом: через `Iterator` и его метод `remove()`.
2. Современным (Java 8+): через метод коллекции `list.removeIf(element -> condition)`. Это чище и короче.

# 🧠 Шпаргалка: Итерация и ConcurrentModificationException

Когда ты идешь циклом по коллекции, ты ожидаешь, что коллекция будет стабильной. Но если в этот момент кто-то (другой поток или даже ты сам через `list.add()`) меняет структуру коллекции — всё может сломаться.

### 1. Суть проблемы: ConcurrentModificationException (CME)
Это **Runtime-исключение**, которое выбрасывается, когда структура коллекции была изменена во время итерации (добавление, удаление элементов), но не через сам объект `Iterator`.

**Как это работает «под капотом»?**
У каждой стандартной коллекции (например, `ArrayList`) есть поле **`modCount`** (modification count). 
1. Когда ты создаешь `Iterator`, он запоминает текущее значение `modCount` (назовем его `expectedModCount`).
2. При каждом вызове `next()` или `hasNext()`, итератор проверяет: `if (modCount != expectedModCount) throw CME`.
3. Если ты вызвал `list.remove(index)` напрямую у списка, `modCount` увеличился, а `expectedModCount` у итератора остался старым. **Бум!**

---

### 2. Fail-Fast vs Fail-Safe (Weakly Consistent)

В Java итераторы делятся на два лагеря по своей стратегии поведения при изменениях.

#### **A. Fail-Fast (Быстрый отказ)**
*   **Принцип:** «Если что-то идет не так — падай немедленно». 
*   - Как только итератор замечает несоответствие счетчиков, он выбрасывает `ConcurrentModificationException`.
*   **Зачем это нужно?** Чтобы ты не продолжил работать с «битыми» или непредсказуемыми данными. Это защита от логических ошибок в коде.
*   **Где встречается:** Почти все классические коллекции: `ArrayList`, `HashMap`, `HashSet`, `LinkedList`.

#### **B. Fail-Safe / Weakly Consistent (Слабая согласованность)**
*   **Принцип:** «Продолжаем работать, даже если данные изменились». 
*   **Как это работает?** 
    1. Либо итератор работает на **копии** данных (Snapshot).
    2. Либо он использует специальные механизмы (например, CAS или сегментированные блокировки), которые позволяют видеть изменения, но не ломают структуру обхода.
*   **Нюанс:** Ты можешь увидеть «старые» данные (stale data), которые уже удалены, но итератор их еще не заметил.
*   **Где встречается:** `CopyOnWriteArrayList`, `ConcurrentHashMap`.

---

### 3. Важные нюансы (Senior Level)

1.  **`iterator.remove()` — это легально!**
    Если ты удаляешь элемент через сам объект `Iterator` (`it.remove()`), итератор **сам обновляет** свой `expectedModCount`. Поэтому `ConcurrentModificationException` не возникнет. Но если ты используешь `list.remove()` внутри цикла `for-each` — ты получишь исключение.

2.  **Структурные vs Неструктурные изменения.**
    `modCount` меняется только при **структурных** изменениях (добавление, удаление). Если ты просто заменил значение по существующему ключу в `HashMap` (перезаписал `value`), это не считается структурным изменением, и `modCount` не изменится. Итератор не упадет.

3.  **CopyOnWriteArrayList — дорогая штука.**
    Его "Fail-Safe" механизм работает за счет того, что при любой записи создается **полная копия** массива. Это очень эффективно для чтения, но катастрофично для производительности, если записей много.

---

### ❓ FAQ (Частые вопросы на интервью)

**В: Можно ли удалять элементы из `ArrayList` во время итерации через `for-each`?**
**О:** Нет, ты получишь `ConcurrentModificationException`, так как `for-each` под капотом использует `Iterator`, а ты вызываешь `list.remove()`, что нарушает контракт `modCount`. Используй `iterator.remove()`.

**В: В чем разница между Fail-Fast и Weakly Consistent в контексте потокобезопасности?**
**О:** Fail-Fast предназначен для обнаружения ошибок в однопоточном коде (ошибки логики). Weakly Consistent (Fail-Safe) — это механизм для многопоточного кода, позволяющий избежать блокировок и исключений ценой возможности увидеть чуть менее актуальные данные.

**В: Что произойдет, если я буду читать `ConcurrentHashMap` и в этот момент другой поток добавит туда элемент?**
**О:** Исключения не будет. Итератор `ConcurrentHashMap` является *weakly consistent*: он может или показать новый элемент, или не показать его (зависит от того, попал ли он в ту же корзину), но процесс обхода не прервется.

**В: Какая сложность у `CopyOnWriteArrayList.add()`?**
**О:** $O(n)$, так как при каждой операции добавления происходит копирование всего внутреннего массива.

# 🧠 Шпаргалка: Синхронизированные коллекции в Java

Когда несколько потоков одновременно пытаются читать или изменять одну и ту же коллекцию, возникает **Race Condition** (состояние гонки). Синхронизированные коллекции — это инструменты, которые предотвращают повреждение данных, обеспечивая атомарность операций.

В Java есть два принципиально разных подхода к синхронизации: **Старый (Wrappers)** и **Современный (Concurrent Collections)**.

---

## 1. Старый подход: `Collections.synchronizedXxx()`
Это "обертки" над обычными коллекциями. Вы берете стандартный `ArrayList` и говорите Java: «Сделай его безопасным».

*   **Как это работает:** Внутри каждого метода (add, remove, get) стоит ключевое слово `synchronized`. Весь объект блокируется целиком на время выполнения операции.
*   **Механика блокировки:** **Coarse-grained locking** (крупнозернистая блокировка). Представь огромный склад, где при входе одного человека закрывается дверь для всех остальных.
*   **Плюсы:** Простота, предсказуемость.
*   **Минусы:** 
    *   **Низкая производительность:** Если 10 потоков хотят только *прочитать* данные, они всё равно будут стоять в очереди друг за другом.
    *   **Узкое место (Bottleneck):** При высокой нагрузке потоки просто ждут освобождения одного общего замка.

⚠️ **Критический нюанс (Ловушка итератора):** 
Синхронизация методов не защищает процесс итерации. Если ты начнешь перебирать `synchronizedList` через `for-each` в одном потоке, а другой поток удалит элемент — ты получишь `ConcurrentModificationException`.
**Правило:** При итерации по оберткам ты **обязан** вручную синхронизироваться на объекте коллекции:
```java
synchronized (list) {
    for (String s : list) { ... }
}
```

---

## 2. Современный подход: `java.util.concurrent`
Это высокопроизводительные коллекции, разработанные специально для многопоточности.

*   **Как это работает:** Вместо того чтобы блокировать всё, они используют умные алгоритмы: **Lock Stripping** (разделение на части), **CAS (Compare-And-Swap)** и **Copy-on-Write**.
*   **Механика блокировки:** **Fine-grained locking** (мелкозернистая блокировка). Представь тот же склад, но разделенный на 16 секторов. Поток в секторе А не мешает потоку в секторе Б.

### Ключевые игроки:
1.  **`ConcurrentHashMap`**: Король производительности. Не блокирует всю карту. Использует CAS для вставки и блокирует только конкретный "бакет" (корзину) при конфликте. Чтение почти всегда неблокирующее.
2.  **`CopyOnWriteArrayList`**: Идеален, когда чтений — миллион, а записей — две. 
    *   **Принцип:** При любой модификации (add/set) создается **полная копия** внутреннего массива.
    *   **Плюс:** Чтение происходит без всяких блокировок, очень быстро.
    *   **Минус:** Очень дорогая операция записи (копирование массива — это нагрузка на CPU и память).
3.  **`BlockingQueue` (напр. `ArrayBlockingQueue`)**: Основа паттерна Producer-Consumer. Позволяет потоку "заснуть", если очередь пуста, или "ждать", если очередь полна.

---

## 3. Сводная таблица для принятия решений

| Характеристика | `Collections.synchronizedList` | `CopyOnWriteArrayList` | `ConcurrentHashMap` |
| :--- | :--- | :--- | :--- |
| **Тип блокировки** | Одна на весь объект (Coarse) | Копирование массива | По сегментам/бакетам (Fine) |
| **Скорость чтения** | Низкая (очередь) | **Очень высокая** | Высокая |
| **Скорость записи** | Средняя | **Очень низкая** | Высокая |
| **Итератор** | Fail-fast (нужна синхронизация) | Fail-safe (работает со снимком) | Weakly consistent (не падает) |

---

## ❓ Часто задаваемые вопросы на интервью

**В: В чем разница между Fail-fast и Fail-safe итераторами?**
**О:** `Fail-fast` (как в `synchronizedList`) выбрасывает `ConcurrentModificationException`, если коллекция изменилась во время обхода. `Fail-safe` (или Weakly Consistent, как в `ConcurrentHashMap`) работает либо с копией данных, либо позволяет видеть изменения, но никогда не выкидывает ошибку при модификации.

**В: Что произойдет, если я буду использовать `CopyOnWriteArrayList` в системе с огромным количеством записей?**
**О:** Система "умрет" от нагрузки на Garbage Collector и CPU. Каждая запись создает новый массив. Если массив большой, это вызовет огромные задержки (latency) и переполнение памяти.

**В: Как `ConcurrentHashMap` позволяет читать данные без блокировок?**
**О:** Он использует `volatile` переменные для видимости изменений и атомарную операцию **CAS** (Compare-And-Swap) на уровне процессора. Чтение происходит напрямую из ячеек памяти, которые всегда содержат актуальную ссылку.

**В: Нужно ли синхронизировать доступ к `ConcurrentHashMap`, если мы используем метод `put()`?**
**О:** Нет, сам метод `put()` уже атомарен и безопасен. Но если тебе нужно сделать "проверить-и-обновить" (например, `if (!map.contains(k)) map.put(k, v)`), то между проверкой и вставкой другой поток может успеть вставить данные. В этом случае используй атомарные методы типа `putIfAbsent()`.

# 🧠 Шпаргалка: Concurrent Collections

**Concurrent Collections** — это коллекции из пакета `java.util.concurrent`, специально спроектированные для работы в многопоточной среде. В отличие от обычных коллекций (которые либо не потокобезопасны, либо используют одну глобальную блокировку), эти структуры минимизируют **contention** (соперничество за ресурс) и позволяют нескольким потокам работать одновременно.

---

## 1. Основные стратегии обеспечения безопасности

Прежде чем смотреть на классы, нужно понять три кита, на которых они стоят:
1.  **Lock Stripping (Сегментация):** Разделение данных на части (бакеты/сегменты) и блокировка каждой части отдельно. Если два потока меняют разные части, они не ждут друг друга.
2.  **CAS (Compare-And-Swap):** Низкоуровневая атомарная операция на уровне процессора. «Обнови значение, только если оно всё еще равно вот этому». Позволяет избежать тяжелых `synchronized`.
3.  **Copy-On-Write:** При любой модификации создается полная копия массива. Читающие потоки работают со старой версией, пишущие — с новой.

---

## 2. Ключевые игроки (Классы)

### 🗺️ Maps (Словари)
*   **`ConcurrentHashMap` (Король всех мап):**
    *   **Как работает:** В Java 8+ использует CAS для вставки в пустые бакеты и `synchronized` только на уровне первой ноды бакета при коллизиях. Это максимально мелкая блокировка.
    *   **Плюсы:** Высочайшая производительность, масштабируемость.
    *   **Нюанс:** Итераторы **weakly consistent** (не выбрасывают `ConcurrentModificationException`, но могут не увидеть изменения, произошедшие прямо во время обхода).
*   **`ConcurrentSkipListMap`:**
    *   **Как работает:** Реализация на основе Skip List (многоуровневый связанный список).
    *   **Когда использовать:** Когда нужна **отсортированная** потокобезопасная мапа. Аналог `TreeMap`, но для многопоточности.

### 📜 Lists & Sets (Списки и Множества)
*   **`CopyOnWriteArrayList`:**
    *   **Как работает:** При каждом `add`, `set` или `remove` создается новый массив.
    *   **Когда использовать:** Когда **чтений очень много**, а **записей крайне мало** (например, список слушателей/listeners).
    *   **Минус:** Очень дорогая операция записи ($O(n)$ + выделение памяти).
*   **`CopyOnWriteArraySet`:**
    *   Просто обертка над `CopyOnWriteArrayList`, гарантирующая уникальность.

### 🚦 Queues (Очереди) — Основа Producer-Consumer
*   **`BlockingQueue` (Интерфейс):** Главный инструмент для передачи данных между потоками. Методы `put()` и `take()` блокируют поток, если очередь полна или пуста.
    *   **`ArrayBlockingQueue`:** Ограниченная по размеру (bounded) очередь на базе массива. Фиксированный размер — это хорошо для контроля памяти.
    *   **`LinkedBlockingQueue`:** Может быть безлимитной. Использует две разные блокировки (одну для вставки, другую для извлечения), что дает больше параллелизма, чем `ArrayBlockingQueue`.
    *   **`PriorityBlockingQueue`:** Очередь с приоритетами (на базе кучи/Heap).
    *   **`SynchronousQueue`:** Очередь без емкости. Каждый `put` должен ждать соответствующего `take`. Идеально для передачи задач между потоками «из рук в руки».

---

## 3. Важные нюансы и "Подводные камни" (Senior level)

1.  **Проблема Check-then-Act:** Даже если ты используешь `ConcurrentHashMap`, код вида:
    ```java
    if (!map.containsKey(key)) { // Шаг 1
        map.put(key, value);     // Шаг 2
    }
    ```
    **НЕ является атомарным!** Между шагом 1 и 2 другой поток может успеть вставить значение.
    **Решение:** Используй атомарные методы: `putIfAbsent()`, `computeIfPresent()`, `merge()`.

2.  **Weakly Consistent Iterators:** Помни, что итераторы в Concurrent-коллекциях не «замораживают» мир. Они видят состояние коллекции на момент создания или в процессе обхода. Ты не получишь `ConcurrentModificationException`, но можешь увидеть «призраков» старых данных.

3.  **Fail-Fast vs Fail-Safe:**
    *   `ArrayList` — **Fail-Fast** (сразу падает при изменении во время итерации).
    *   `CopyOnWriteArrayList` — **Fail-Safe/Weakly Consistent** (продолжает работать со старой копией).

## ❓ FAQ (Частые вопросы на интервью)

**В: Почему `ConcurrentHashMap` лучше, чем `Collections.synchronizedMap(new HashMap())`?**
**О:** `synchronizedMap` использует одну блокировку на весь объект. Если 10 потоков хотят прочитать разные ключи, они будут стоять в очереди друг за другом. `ConcurrentHashMap` позволяет множеству потоков читать и даже писать в разные бакеты одновременно.

**В: Что будет с памятью при использовании `CopyOnWriteArrayList` при частых записях?**
**О:** Произойдет резкий рост нагрузки на Garbage Collector (GC). Каждая запись создает новый массив, что забивает Heap-память временными объектами.

**В: Можно ли использовать `ConcurrentHashMap` для обхода всей мапы и удаления элементов?**
**О:** Да, это безопасно. Но помни про атомарность операций внутри цикла. Если нужно удалить по условию, лучше использовать метод `map.remove(key, value)` или `entrySet().removeIf(...)`.

**В: В чем разница между `ArrayBlockingQueue` и `LinkedBlockingQueue`?**
**О:** 1) `Array` — фиксированный размер (bounded), `Linked` — может быть неограниченным. 2) У `Linked` две блокировки (на вход и на выход), что позволяет потоку-производителю и потоку-потребителю работать почти не мешая друг другу. `Array` использует одну общую блокировку.

# 🧠 Шпаргалка: ConcurrentHashMap

`ConcurrentHashMap` (CHM) — это высокопроизводительная, потокобезопасная реализация интерфейса `Map`. Она создана для того, чтобы минимизировать конфликты между потоками при одновременном чтении и записи.

### 1. Главная проблема: Почему не `Hashtable` или `Collections.synchronizedMap`?
Прежде чем разбирать CHM, нужно понимать, что мы заменяем:
*   **`Hashtable` / `synchronizedMap`**: Используют **один глобальный замок (lock)** на весь объект. Если один поток пишет, все остальные (даже те, кто хочет просто прочитать) стоят в очереди. Это "бутылоке горлышко" (bottleneck) при высокой нагрузке.
*   **`ConcurrentHashMap`**: Использует **механизм мелкозернистых блокировок (fine-grained locking)**. Потоки могут работать с разными частями карты одновременно, не блокируя друг друга.

### 2. Эволюция внутреннего устройства (Важно для Senior!)
Механика работы CHM сильно изменилась в Java 8. На собеседованиях любят спрашивать именно про разницу.

#### **Java 7: Segmented Locking (Lock Stripping)**
Карта была разделена на массив **сегментов** (`Segments`). Каждый сегмент — это фактически отдельный маленький `HashMap`.
*   Когда ты делал `put`, блокировался только тот сегмент, в который попадал ключ.
*   Это позволяло работать $N$ потокам одновременно, если они попадали в разные сегменты.
*   **Минус:** Если сегментов было 16, то максимум 16 потоков могли писать одновременно.

#### **Java 8+: CAS и Synchronized на уровне бакетов (Bins)**
Разработчики отказались от сегментов в пользу еще более тонкой гранулярности. Теперь блокировка происходит не на сегменте, а на **голове конкретного бакета (bin/bucket)**.
*   **CAS (Compare-And-Swap):** Если корзина (bucket) пуста, CHM использует атомарную операцию CAS, чтобы вставить новый узел. Это вообще **безблокировочная** операция (lock-free). Она невероятно быстрая.
*   **`synchronized` на node:** Если в корзине уже есть данные (коллизия), поток блокирует только первый узел этой конкретной корзины с помощью `synchronized`. Остальные корзины остаются доступными для других потоков.

### 3. Ключевые особенности и нюансы
*   **Потокобезопасное чтение (`get`):** Операция `get()` в CHM практически всегда **lock-free**. Она использует модификатор `volatile` для полей узлов, что гарантирует видимость изменений между потоками без использования тяжелых блокировок.
*   **Weakly Consistent Iterators:** Итераторы в CHM не выбрасывают `ConcurrentModificationException`. Они "слабо согласованные": они могут или не увидеть изменения, сделанные другими потоками сразу после начала итерации, но они гарантированно не сломают структуру карты.
*   **Treeification (Деревовидность):** Как и в `HashMap`, если количество элементов в одном бакете превышает порог (8), список превращается в **красно-черное дерево**. Это защищает от деградации производительности при плохой хеш-функции ($O(n) \to O(\log n)$).

### 4. Опасная ловушка: Атомарность составных операций
Это то, на чем валятся все новички. Даже если сама карта потокобезопасна, **твоя логика вокруг неё может не быть**.

**❌ Плохо (Race Condition):**
```java
if (!map.containsKey(key)) { // Шаг 1: Проверка
    map.put(key, value);     // Шаг 2: Действие
}
```
*Между шагом 1 и шагом 2 другой поток может успеть вставить значение!*

**✅ Хорошо (Использование атомарных методов):**
```java
map.putIfAbsent(key, value); 
// или
map.computeIfAbsent(key, k -> new Value()); // Атомарно вычислит и положит
```

### ❓ Часто задаваемые вопросы (Q&A)

**В: Можно ли в `ConcurrentHashMap` использовать `null` в качестве ключа или значения?**
**О:** **Нет.** В отличие от `HashMap`, `null` запрещен. Это сделано намеренно, чтобы избежать неоднозначности при вызове `get(key)`: если вернулся `null`, мы не знаем — это ключ реально отсутствует или значение в ключе было `null`.

**В: Как работает метод `size()`? Он точный?**
**О:** Он **приблизительный**. Поскольку карта постоянно меняется другими потоками, `size()` может не отражать реальное количество элементов на момент завершения вызова. Для точного подсчета в высоконагруженных системах лучше использовать другие подходы или учитывать погрешность.

**В: Что такое "Lock Stripping"?**
**О:** Это стратегия уменьшения конкуренции за блокировку путем разделения данных на части и наложения блокировок на каждую часть отдельно, вместо того чтобы блокировать весь объект целиком.

**В: В чем разница между `put()` и `computeIfAbsent()`?**
**О:** `put()` просто перезаписывает значение. `computeIfAbsent()` проверяет наличие ключа и, если его нет, выполняет функцию вычисления и вставляет результат **атомарно**. Это критично для предотвращения дублирования тяжелых операций (например, создания объекта или запроса к БД).

# 🧠 Шпаргалка: CopyOnWriteArrayList

**CopyOnWriteArrayList** — это потокобезопасная реализация интерфейса `List`. Её главная фишка — стратегия **"Copy-on-Write"** (копирование при записи).

### 🛠 Как это работает (Under the hood)
Представь, что у тебя есть список. Когда ты хочешь его изменить (добавить, удалить или заменить элемент), Java не меняет старый массив. Вместо этого она:
1. Создает **полную копию** существующего массива.
2. Вносит изменения в эту новую копию.
3. Заменяет ссылку на старый массив ссылкой на новый.

Внутри используется `volatile` ссылка на массив, что гарантирует видимость изменений для всех потоков (Visibility). Все операции записи защищены блокировкой (`ReentrantLock` или `synchronized`), чтобы два потока не пытались одновременно создать разные копии.

### ✅ Плюсы
1.  **Thread-safety без блокировок на чтение:** Чтение (методы `get`, `size`, `iterator`) происходит максимально быстро и вообще не ждет блокировок. Это делает его невероятно эффективным в сценариях, где читают постоянно, а пишут редко.
2.  **Иммутабельность итератора (Snapshot):** Итератор работает со «снимком» (snapshot) массива, который был на момент создания итератора. 
3.  **Никаких `ConcurrentModificationException`:** Ты можешь спокойно перебирать список в одном потоке, пока другой поток его модифицирует. Итератор просто будет видеть старую версию данных.

### ❌ Минусы (Цена вопроса)
1.  **Дорогая запись:** Любая операция `add`, `set` или `remove` — это $O(n)$ по времени и памяти, так как нужно скопировать весь массив.
2.  **Расход памяти:** Если список большой, частые записи создадут огромную нагрузку на Garbage Collector (GC) из-за постоянного создания новых массивов.
3.  **Stale Data (Протухшие данные):** Итератор может работать со старой версией данных. Если ты начал обход списка, а в этот момент другой поток удалил элемент — итератор этого не заметит, он дойдет до конца «старого» массива.

### 🚀 Когда использовать?
*   **Read-heavy нагрузки:** Когда чтение происходит в тысячи раз чаще, чем запись.
*   **Списки слушателей (Listeners/Observers):** Классический кейс. Список подписчиков меняется крайне редко (при запуске приложения), но при каждом событии мы пробегаем по нему циклом.
*   **Конфигурации:** Хранение настроек, которые загружаются один раз и только читаются в процессе работы.

---

### ❓ FAQ (Вопросы с собеседований)

**1. Почему `CopyOnWriteArrayList` не выбрасывает `ConcurrentModificationException`?**
> **Ответ:** Потому что итератор работает не с текущим массивом, а с его копией, которая была создана в момент вызова `iterator()`. Изменения в оригинальном списке никак не влияют на массив, который держит итератор.

**2. Что произойдет, если во время итерации по `CopyOnWriteArrayList` другой поток удалит элемент?**
> **Ответ:** Ничего страшного для программы не случится. Итератор продолжит работу со своим «снимком» (snapshot), где этот элемент всё еще есть. Однако данные в итераторе будут "устаревшими" по сравнению с актуальным состоянием списка.

**3. Какова сложность операций `add` и `get`?**
> **Ответ:** 
> *   `get`: $O(1)$ — максимально быстро, без блокировок.
> *   `add`: $O(n)$ — из-за необходимости копирования всего массива.

**4. Можно ли использовать этот класс для высоконагруженного списка транзакций, который постоянно обновляется?**
> **Ответ:** Категорически нет. Это приведет к катастрофическому падению производительности и переполнению памяти (Heap Overflow) из-за бесконечного создания копий массива и высокой нагрузки на GC.

**5. Как обеспечить видимость изменений между потоками в этом классе?**
> **Ответ:** Благодаря ключевому слову `volatile` для внутреннего массива. Когда один поток завершает запись и обновляет ссылку, все остальные потоки сразу видят новую ссылку на новый массив.

# 🧠 Шпаргалка: BlockingQueue

**BlockingQueue** — это интерфейс из пакета `java.util.concurrent`, который расширяет `Queue`. Его главная фишка не просто в хранении элементов, а в **механизме ожидания (блокировки)**. 

Это фундамент паттерна **Producer-Consumer** (Производитель-Потребитель). Он позволяет потокам-производителям и потокам-потребителям работать синхронно, не используя при этом сложные `wait/notify` конструкции вручную.

---

### 🛠 Основные механизмы (Методы)
Все методы `BlockingQueue` можно разделить на три группы по поведению при возникновении проблем (очередь полна или пуста):

1.  **Бросают исключение:** `add()`, `remove()`, `element()`. 
    *   *Senior Note:* Используй их только если уверен в размере очереди. В многопоточной среде это путь к панике.
2.  **Возвращают спец. значение (`null` или `false`):** `offer(e)`, `poll()`, `peek()`.
    *   *Senior Note:* Это "неблокирующие" методы. Если очередь пуста, `poll()` просто вернет `null` и пойдет дальше.
3.  **Блокируют поток (The Magic):** `put(e)`, `take()`.
    *   `put(e)` — если очередь полна, поток "засыпает" и ждет, пока освободится место.
    *   `take()` — если очередь пуста, поток "засыпает" и ждет, пока кто-то положит элемент.
4.  **Тайм-аут (Гибриды):** `offer(e, time, unit)`, `poll(time, unit)`.
    *   Поток ждет указанное время. Если не успел — выходит из ожидания. Это лучший выбор для предотвращения "зависаний" системы.

---

### 🏗 Основные реализации

| Реализация | Особенности | Когда использовать |
| :--- | :--- | :--- |
| **ArrayBlockingQueue** | **Bounded** (фиксированный размер). Внутри — массив. Один замок (lock) на все операции. | Когда нужно жестко ограничить потребление памяти (**Backpressure**). |
| **LinkedBlockingQueue** | **Optionally Bounded**. По умолчанию размер `Integer.MAX_VALUE`. Использует два отдельных замка (на вставку и на извлечение). | Когда важна высокая пропускная способность (throughput). Раздельные замки уменьшают конкуренцию потоков. |
| **SynchronousQueue** | **Zero capacity**. В ней нет элементов, она лишь передает их "из рук в руки". Поток `put` не может завершиться, пока поток `take` не заберет элемент. | Для передачи задач между потоками с минимальной задержкой (как в `CachedThreadPool`). |
*   **PriorityBlockingQueue** | Неограниченная. Элементы извлекаются согласно их приоритету (`Comparable`). | Когда важна обработка "критичных" задач вне очереди. |
*   **DelayQueue** | Элементы могут быть извлечены только тогда, когда истечет их задержка. | Для реализации задач по расписанию (Scheduled tasks). |

---

### ⚠️ Senior Nuances (Подводные камни)

1.  **Backpressure (Обратное давление):** Это важнейшее понятие. Если твои Producer-ы работают быстрее, чем Consumer-ы, и ты используешь `LinkedBlockingQueue` без указания размера, память неизбежно закончится (**OutOfMemoryError**). Всегда старайся ограничивать размер очереди (`capacity`).
2.  **Two-Lock Queue Algorithm:** Помни, что `LinkedBlockingQueue` эффективнее `ArrayBlockingQueue` при высокой нагрузке, потому что у неё разные блокировки для `put` и `take`. В `ArrayBlockingQueue` один поток, пишущий, блокирует и поток, читающий.
3.  **Liveness (Живучесть):** Использование методов с тайм-аутом (`poll(timeout)`) — это признак хорошего тона в production-системах. Это позволяет системе "самоисцеляться" и не висеть вечно в ожидании данных, которые могут никогда не прийти.

### ❓ FAQ (Частые вопросы на интервью)

**В: В чем разница между `put()` и `offer()`?**
**О:** `put()` — блокирующий метод. Если очередь полна, поток будет ждать освобождения места. `offer()` — неблокирующий; если места нет, он просто вернет `false`.

**В: Что такое Backpressure и как BlockingQueue помогает его реализовать?**
**О:** Backpressure — это механизм управления потоком данных, чтобы потребитель не был завален работой. Используя `ArrayBlockingQueue` с фиксированным размером и метод `put()`, мы заставляем Producer-а замедлиться (заблокироваться), как только очередь заполняется.

**В: Можно ли использовать `LinkedBlockingQueue` без указания размера?
**О:** Можно, но это опасно. По умолчанию размер будет `Integer.MAX_VALUE`. Если потребитель не справляется, очередь вырастет до гигантских размеров и уронит JVM с `OutOfMemoryError`.

**В: Как работает `SynchronousQueue`?**
**О:** В ней нет внутреннего буфера для хранения элементов. Каждая операция вставки (`put`) ждет операцию извлечения (`take`) и наоборот. Это своеготкальный "ручной" обмен данными между потоками без промежуточного хранения.

# 🧠 Шпаргалка: ConcurrentSkipListMap & ConcurrentSkipListSet

### 1. Что это такое?
Если `ConcurrentHashMap` — это король скорости для обычных задач, то **`ConcurrentSkipListMap`** (и его брат `Set`) — это король **упорядоченности** в многопоточной среде.

Это потокобезопасные реализации, которые обеспечивают:
1.  **Сортировку:** Ключи всегда отсортированы (натуральный порядок или через `Comparator`).
2.  **Потокобезопасность:** Можно одновременно читать и записывать из множества потоков без использования тяжелых `synchronized` блоков.

### 2. Внутреннее устройство: Skip List (Списки с пропусками)
Это самый важный момент. В отличие от `TreeMap`, который использует **Красно-черное дерево**, здесь используется структура **Skip List**.

*   **Как это работает:** Представь обычный связный список. Чтобы найти элемент, тебе нужно пройти по всем узлам ($O(n)$). Теперь представь, что над этим списком есть «экспресс-слои» — дополнительные уровни, которые позволяют перепрыги락 через целые группы элементов.
*   **Почему это круто для Concurrency:** Перестраивать сбалансированное дерево (как в `TreeMap`) при вставке — это кошмар для многопоточности, так как нужно блокировать целые ветки дерева. В **Skip List** изменения локальны: ты просто меняешь указатели у узлов с помощью атомарных операций (**CAS - Compare-And-Swap**). Это делает структуру **lock-free** (или почти lock-free), что минимизирует задержки.

### 3. Основные характеристики
*   **Сложность операций:** $O(\log n)$ для поиска, вставки и удаления. Это медленнее, чем $O(1)$ у `ConcurrentHashMap`, но предсказуемо и стабильно.
*   **Порядок:** Гарантирует порядок элементов (в отличие от `ConcurrentHashMap`).
*   **Итераторы:** **Weakly consistent** (слабо согласованные). Они не выбрасывают `ConcurrentModificationException`. Это значит, что итератор может не увидеть изменения, произошедшие сразу после его создания, но он гарантированно «пройдет» по элементам, которые существовали в момент начала обхода.

### 4. Когда использовать (Decision Making)

| Ситуация | Что выбрать? | Почему? |
| :--- | :--- | :--- |
| Нужна максимальная скорость, порядок не важен | `ConcurrentHashMap` | $O(1)$ — это быстрее всего. |
| Нужна сортировка + много потоков на чтение/запись | **`ConcurrentSkipListMap`** | Позволяет эффективно работать с диапазонами и порядком. |
| Нужно просто хранить уникальные элементы в порядке | `ConcurrentSkipListSet` | Это надстройка над Map, где значение — заглушка. |
| Мало потоков, важна только сортировка | `TreeMap` | Проще и чуть меньше накладных расходов на структуру уровней. |

### 5. Нюансы (Senior Level)
1.  **Lock-free vs Lock-based:** Основная магия здесь в использовании **CAS**. Это позволяет потокам не «засыпать» в ожидании очереди, а пытаться обновить значение. Если обновление не удалось из-за вмешательства другого потока, цикл просто повторяется.
2.  **Память:** Skip List потребляет больше памяти, чем обычный `LinkedList` или `TreeMap`, из-за хранения дополнительных указателей для «экспресс-слоев».
3.  **Range Queries:** Если тебе нужно достать все ключи в диапазоне от `"A"` до `"F"`, `ConcurrentSkipListMap` сделает это идеально благодаря своей структуре. В `ConcurrentHashMap` тебе пришлось бы перебирать вообще всё.

### ❓ FAQ (Частые вопросы на интервью)

**В: Почему мы не используем `Collections.synchronizedSortedMap(new TreeMap())` вместо `ConcurrentSkipListMap`?**
**О:** `synchronizedSortedMap` использует один глобальный замок (монитор) на всю карту. Если один поток пишет, все остальные потоки (даже те, что просто читают) стоят и ждут. `ConcurrentSkipListMap` позволяет множеству потоков модифицировать разные части списка одновременно, не блокируя друг друга.

**В: Что значит «слабо согласованный итератор» (Weakly Consistent Iterator)?**
**О:** Это значит, что итератор не делает «снимка» (snapshot) коллекции в момент создания. Он идет по живым узлам. Если во время обхода другой поток добавит элемент, итератор может его увидеть или не увидеть — это не ошибка. Главное — он никогда не упадет с `ConcurrentModificationException`.

**В: Какая сложность у операций в Skip List?**
**О:** В среднем $O(\log n)$. Это результат того, что уровни «пропусков» позволяют нам делить пространство поиска пополам на каждом уровне, подобно бинарному поиску.

**В: Можно ли использовать ConcurrentSkipListMap для реализации LRU-кэша?**
**О:** Не совсем эффективно. Для LRU важен порядок *последнего доступа*, а `ConcurrentSkipListMap` хранит элементы в порядке *ключей*. Для LRU лучше смотреть в сторону `LinkedHashMap` (но он не потокобезопасен) или кастомных решений на базе `ConcurrentHashMap`.

# 🌊 Концепция Stream Pipeline (Конвейер потоков)

Представь **Stream Pipeline** как конвейер на заводе. У тебя есть сырье (данные), набор станков (операции трансформации) и финальный упаковщик (результат). Пока ты не нажал кнопку «Старт» на последнем этапе, конвейер даже не начнет двигаться.

Концепция Pipeline состоит из трех строго определенных этапов: **Source $\to$ Intermediate Operations $\to$ Terminal Operation**.

### 1. Source (Источник)
Это точка входа. Откуда текут данные?
*   **Коллекции:** `list.stream()`, `set.stream()`.
*   **Массивы:** `Arrays.stream(arr)`.
*   **Файлы/I/O:** `Files.lines(path)`.
*   **Генераторы:** `Stream.generate()` или `Stream.iterate()`.

> **Senior Note:** Важно понимать, что источник — это не сам поток, а лишь поставщик данных. Сам стрим — это лишь абстрактный способ их обхода.

### 2. Intermediate Operations (Промежуточные операции)
Это «станки» на конвейере. Они принимают один стрим и возвращают **новый** стрим. Именно благодаря этому мы можем строить цепочки (chaining).

*   **Трансформация:** `map()` (меняет тип или значение), `flatMap()` (разворачивает вложенные структуры).
*   **Фильтрация:** `filter()` (пропускает только нужные элементы), `distinct()` (убирает дубликаты).
*   **Сортировка:** `sorted()`.
*   **Ограничение:** `limit(n)`, `skip(n)`.

**Ключевая особенность: Laziness (Ленивость).** 
Промежуточные операции **не выполняются**, пока не будет вызвана терминальная операция. Они просто записывают инструкции в «план работ». Это позволяет Java оптимизировать процесс (например, не обрабатывать лишние элементы, если сработал `limit`).

### 3. Terminal Operation (Терминальная операция)
Это кнопка «Стоп» и упаковщик. Она потребляет все элементы стрима и превращает их в конечный результат или выполняет действие. После её вызова поток **закрывается**.

*   **Сбор данных:** `collect()` (в List, Set, Map), `toArray()`.
*    $\to$ **Агрегация:** `reduce()` (схлопывание в одно значение), `count()`, `min()`, `max()`.
*   **Проверка/Поиск:** `anyMatch()`, `allMatch()`, `findFirst()`, `findAny()`.
*   **Действие:** `forEach()` (просто пройтись и что-то сделать, например, распечатать).

---

### 🛠 Главные нюансы (то, что спрашивают на Middle/Senior)

1.  **Immutability (Неизменяемость):** Stream API **не меняет** исходный источник. Если ты применил `filter` к `ArrayList`, исходный список останется прежним. Стрим создает новый поток данных.
2.  **One-time use (Одноразовость):** Стрим нельзя использовать дважды. Как только терминальная операция завершена, стрим считается «закрытым». Попытка вызвать вторую терминальную операцию на том же объекте вызовет `IllegalStateException`.
3.  **Short-circuiting (Короткое замыкание):** Некоторые операции могут остановить конвейер до того, как будут обработаны все элементы источника. Примеры: `findFirst()`, `limit()`, `anyMatch()`. Это критически важно для производительности на больших данных.
4.  **Pipeline Optimization:** Java может переупорядочивать промежуточные операции. Например, если у тебя идет `filter().map()`, движок может попытаться оптимизировать их так, чтобы минимизировать количество вычислений.

---

### ❓ FAQ (Частые вопросы на интервью)

**В: Что произойдет, если я напишу `list.stream().filter(x -> x > 10);` и не добавлю терминальную операцию?**
**О:** Ничего не произойдет. Программа отработает, но фильтрация не запустится. Стрим будет создан, инструкции записаны, но «конвейер» не был запущен. Вывод в консоль или изменение данных не случится.

**В: В чем разница между `map` и `flatMap`?**
**О:** `map` — это трансформация "один к одному" (из $A$ в $B$). `flatMap` — это трансформация "один ко многим" + "разглаживание" (flattening). Если у тебя стрим списков `Stream<List<String>>`, то `flatMap` превратит его в один плоский `Stream<String>`.

**В: Можно ли использовать Stream для изменения элементов внутри исходной коллекции?**
**О:** Технически, через `forEach` и внешнюю изменяемую переменную — можно, но это **плохая практика**. Это нарушает идеологию функционального программирования и может привести к побочным эффектам (side-effects), которые сложно отлаживать, особенно в параллельных стримах.

**В: Что такое "Short-circuiting" операции?**
**О:** Это операции, которые позволяют завершить обработку стрима без необходимости доходить до конца источника. Например, `findFirst()` прекращает работу, как только найден первый подходящий элемент, даже если в списке еще миллион элементов.

# 🧠 Промежуточные операции (Intermediate Operations) & Lazy Evaluation

### 🛠 Суть процесса
Представь, что **Stream** — это не контейнер с данными (как `List`), а **конвейер на заводе**. 
*   **Источник (Source)** — это сырье (например, куча железа).
*   **Промежуточные операции** — это станки на конвейере. Один станок красит, другой режет, третий шлифует.
*   **Терминальная операция** — это кнопка «Собрать готовый продукт» и упаковать его в коробку.

**Главная фишка:** Пока ты не нажал кнопку «Собрать» (терминальную операцию), станки **не крутятся**. Они просто стоят и ждут инструкций. Это и есть **Lazy Evaluation (Ленивые вычисления)**.

---

### ⚡️ Lazy Evaluation: Почему это важно?
Если у тебя миллион элементов, и ты применил к ним 10 операций `filter` и `map`, Java не будет создавать 10 промежуточных списков в памяти. Она построит **граф (pipeline)** из инструкций.

**Преимущества:**
1.  **Экономия памяти:** Не создаются промежуточные коллекции.
2.  **Short-circuiting (Короткое замыкание):** Если тебе нужно всего 5 элементов (`limit(5)`), стрим остановится сразу, как только найдет их, не обрабатывая оставшиеся 999,995 элементов.
3.  **Оптимизация (Stream Fusion):** Java может объединить несколько операций в одну, чтобы за один проход по данным сделать и `filter`, и `map`.

---

### 📋 Основные операции

#### 1. Stateless (Без сохранения состояния)
Эти операции не «помнят» предыдущие элементы. Они работают с каждым элементом независимо. Это идеально для параллельных стримов.
*   `filter(Predicate)` — пропускает только те, что подходят под условие.
*   `map(Function)` — преобразует элемент из одного типа в другой (например, `String` $\to$ `Integer`).
*   `flatMap(Function)` — «разглаживает» структуру. Если у тебя стрим списков (`Stream<List<String>>`), `flatMap` превратит его в один плоский стрим строк (`Stream<String>`).
*   `peek(Consumer)` — используется для дебага. Позволяет «подсмотреть» на элемент, не меняя его.

#### 2. Stateful (С сохранением состояния)
Эти операции **требуют знания всех элементов** стрима, прежде чем они смогут выдать результат. Это «тяжелые» операции.
*   `distinct()` — требует сравнения каждого элемента с каждым, чтобы убрать дубликаты.
*   `sorted()` — не может отсортировать, пока не увидит последний элемент потока.
*   `limit(n)` — хотя это и «короткая» операция, она должна дождаться появления $n$ элементов.

---

### ⚠️ Нюансы (Senior Level)

1.  **Ловушка "Пустого стрима":** Если ты вызвал `filter().map()`, но не вызвал `.collect()` или `.forEach()`, программа просто завершится, и **ничего не произойдет**. Никакого кода внутри лямбд не выполнится.
2.  **Порядок имеет значение:** Если ты сначала сделаешь `sorted()`, а потом `filter()`, это будет работать медленнее, чем если ты сначала отфильтруешь лишнее, а потом начнешь сортировать оставшееся. **Сначала уменьшай объем данных, потом делай тяжелые операции.**
3.  **Side-effects (Побочные эффекты):** Старайся не менять внешние переменные внутри `map` или `filter`. Стримы должны быть функциональными (вход $\to$ выход). Если ты меняешь состояние вне стрима, это может привести к непредсказуемым багам в параллельных стримах.

---

### ❓ FAQ (Подготовка к интервью)

**В: Что произойдет, если вызвать промежуточную операцию, но не вызвать терминальную?**
**О:** Ничего. Стрим будет построен, но выполнение логики внутри операций не начнется. Это и есть суть Lazy Evaluation.

**В: В чем разница между `map` и `flatMap`?**
**О:** `map` — это трансформация 1 к 1 (один элемент на входе $\to$ один на выходе). `flatMap` — это трансформация 1 к многим (один элемент на входе $\to$ целый поток/коллекция на выходе, которые потом «схлопываются» в один общий поток).

**В: Является ли операция `sorted()` ленивой?**
**О:** Она является промежуточной, но она **не может быть полностью ленивой** в плане выполнения. Чтобы вернуть первый элемент отсортированного стрима, Java обязана прогнать *весь* исходный поток через алгоритм сортировки. Это называется "blocking operation".

**В: Можно ли использовать `peek` для изменения данных в стриме?**
**О:** Технически — можно (если объект мутабельный), но **категорически не рекомендуется**. `peek` предназначен для наблюдения. Изменение состояния внутри `peek` нарушает принцип чистоты функций и может сломать логику при переходе на параллельные стримы.

# 🏁 Терминальные операции (Terminal Operations)

### 💡 Суть простыми словами
Представь конвейер на заводе. **Промежуточные операции** (`filter`, `map`) — это станки, которые стоят вдоль ленты. Они не работают сами по себе, они просто «ждут» деталей. **Терминальная операция** — это рабочий в конце конвейера, который забирает готовую деталь или упаковывает коробку. 

Пока терминальная операция не вызвана — **стрим ничего не делает**. Это и называется **Lazy Evaluation** (ленивые вычисления) для промежуточных этапов. Терминальная же операция запускает процесс и выполняет **Eager Execution** (немедленное выполнение).

---

### 🛠 Основные группы операций

#### 1. Сбор данных (Reduction & Collection)
Эти операции превращают поток элементов в нечто иное: коллекцию, число или один объект.
*   **`collect(Collector...)`**: Самая мощная операция. Использует класс `Collectors` для сборки данных в `List`, `Set`, `Map` или даже в одну строку (`joining`).
*   **`reduce(BinaryOperator<T> accumulator)`**: «Схлопывает» все элементы стрима в один результат (например, сумма всех чисел). Работает по принципу: берем первый элемент, применяем к нему второй, результат применяем к третье/.. и т.д.
*   **`count()`**: Просто возвращает количество элементов.

#### 2. Поиск и проверка (Short-circuiting operations)
Это «короткозамкнутые» операции. Их фишка в том, что они **могут остановиться не доходя до конца стрима**, как только результат найден.
*   **`anyMatch(Predicate)`**: Возвращает `true`, если нашелся *хотя бы один* подходящий элемент. Останавливает стрим сразу после нахождения первого совпадения.
*   **`allMatch(Predicate)`**: Возвращает `true`, только если *все* элементы подходят. Остановится, как только встретит первый «неправильный» элемент.
*   **`noneMatch(Predicate)`**: Возвращает `true`, если *ни один* элемент не подошел.
*   **`findFirst()`**: Возвращает первый попавшийся элемент (в последовательном стриме — первый по порядку).
*   **`findAny()`**: Возвращает любой подходящий элемент. В параллельных стримах это **намного быстрее**, так как не нужно ждать завершения обработки всех веток.

#### 3. Итерация и действия (Iteration)
*   **`forEach(Consumer)`**: Пробегает по всем элементам и выполняет действие (например, `System.out.println`). 
    *   ⚠️ *Нюанс:* Не используй `forEach` для изменения внешних переменных (side-effects), это плохая практика.
*   **`forEachOrdered(Consumer)`**: То же самое, что `forEach`, но гарантирует соблюдение порядка элементов даже в **параллельных** стримах.

---

### ⚠️ Важные нюансы (Senior Level)

1.  **Одноразовость (Stream Consumption):** Как только терминальная операция вызвана, стрим считается **закрытым**. Попытка вызвать вторую терминальную операцию на том же объекте стрима приведет к `IllegalStateException`.
2.  **Short-circuiting (Короткое замыкание):** Это критически важно для производительности. Если ты используешь `anyMatch` на миллионе элементов, и первый элемент подошел — стрим завершится мгновенно. Если вместо него использовать `count()`, стрим будет вынужден просмотреть все миллион элементов.
3.  **Side-effects (Побочные эффекты):** Терминальные операции должны быть максимально «чистыми». Если внутри `collect` или `forEach` ты меняешь состояние внешнего списка или счетчика, это может привести к непредсказуемому поведению в многопоточной среде (`Parallel Streams`).

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что произойдет, если вызвать промежуточную операцию, но забыть про терминальную?**
**О:** Ничего не произойдет. Программа выполнится, но стрим будет пустым, так как цепочка команд не была запущена в работу. Это классическая ошибка новичков.

**В: В чем разница между `findFirst()` и `findAny()` при работе с Parallel Streams?**
**О:** `findFirst()` требует соблюдения порядка (нужно дождаться завершения всех веток, чтобы найти именно первый), что создает накладные расходы. `findAny()` берет тот элемент, который первым «вылетел» из любой из рабочих потоков, что делает его гораздо быстрее в параллельных вычислениях.

**В: Можно ли использовать `reduce` для сборки в `List`?**
**О:** Технически — можно, но это крайне неэффективно и сложно. Для сборки коллекций всегда используй `collect()`. `reduce` предназначен для создания одного значения (числа, строки, объекта) из множества элементов.

**В: Что такое "Eager execution" в контексте терминальных операций?**
**О:** Это означает, что операция начинает немедленно обрабатывать элементы и не позволяет программе двигаться дальше по коду, пока результат операции не будет вычислен (или пока не сработает условие остановки).

# 🚀 Шпаргалка: Java Collectors API

**Collectors** — это утилитарный класс, который содержит реализации интерфейса `Collector`. Если `Stream` — это конвейер, по которому движутся данные, то `Collectors` — это «конечные станции», которые решают, в каком виде эти данные должны быть упакова/собраны в итоге (в список, в строку, в карту или даже в число).

### 1. Базовые сборщики (Превращаем поток в коллекцию)
Самые простые операции: превратить элементы стрима в стандартные структуры данных.

*   `toList()` — собирает элементы в `List`. Самый частый гость. *(В Java 16+ можно использовать `.toList()` прямо у стрима, это короче и возвращает неизменяемый список).*
*   `toSet()` — собирает элементы в `Set` (автоматически удаляя дубликаты).
*   `toCollection(Supplier)` — позволяет выбрать конкретную реализацию. Например, `toCollection(TreeSet::new)`, если тебе нужна сортировка по умолчанию.

### 2. Работа со строками (String Manipulation)
Когда нужно склеить элементы в красивый текст.

*   `joining()` — просто склеивает всё в одну строку.
*   `joining(delimiter)` — склеивает с разделителем (например, `, `).
*   `joining(delimiter, prefix, suffix)` — «магия» для формирования строк. Например: `"[Alice, Bob, Charlie]"`.

### 3. Работа с Map (Превращаем в словарь)
Здесь начинаются нюансы, на которых часто валят.

*   `toMap(keyMapper, valueMapper)` — создает карту, где ключ и значение извлекаются из объекта.
*   **⚠️ Нюанс (Collision):** Если в стриме встретятся два одинаковых ключа, ты получишь `IllegalStateException`. 
    *   *Решение:* Используй перегрузку с **mergeFunction**: 
        `toMap(keyMapper, valueMapper, (oldValue, newValue) -> oldValue)` — это скажет: "Если ключ дублируется, оставь старое значение".
*   `toMap(keyMapper, valueMapper, mergeFunction, mapSupplier)` — позволяет также указать, какую именно реализацию Map использовать (например, `TreeMap`).

### 4. Группировка и разделение (The Heavy Hitters)
Это «мозг» коллекторов. Позволяет делать сложную аналитику данных.

*   **`partitioningBy(Predicate)`** — самый простой вид группировки. Всегда возвращает `Map<Boolean, List<T>>`. Делит мир на "правду" и "ложь".
    *   *Пример:* Разделить список студентов на "прошедших" и "не прошедших" экзамен.
*   **`groupingBy(Classifier)`** — классическая группировка по ключу. Возвращает `Map<K, List<T>>`.
    *   *Пример:* Сгруппировать сотрудников по департаментам.
*   **Downstream Collectors (Вложенные коллекторы)** — это когда внутри `groupingBy` ты запускаешь еще один коллектор. Это уровень Senior.
    *   *Прилоб:* Не просто сгруппировать людей по городам, а сразу посчитать количество людей в каждом городе: 
        `groupingBy(Person::getCity, counting())`.

### 5. Агрегация и статистика (Math & Stats)
Когда нужно быстро получить цифры.

*   `counting()` — просто считает количество элементов.
*   `summingInt/Long/Double` — сумма значений.
*   `averagingInt/Long/Double` — среднее арифметическое.
*   `summarizingInt/Long/Double` — **Топ-инструмент**. Возвращает объект `IntSummaryStatistics`, который содержит сразу всё: `count`, `sum`, `min`, `max` и `average`. Одним вызовом!

---

### 💡 Важные нюансы (Senior Tips)

1.  **Immutability (Неизменяемость):** Помни, что `Collectors.toList()` в старых версиях Java возвращал изменяемый `ArrayList`, а современные методы вроде `Stream.toList()` (Java 16+) возвращают **unmodifiable** список. Если попытаешься сделать `.add()` к результату `Stream.toList()`, получишь ошибку.
2.  **Side Effects (Побочные эффекты):** Никогда не используй `collect` для изменения внешних переменных (например, добавления в уже существующий список вне стрима). Стрим должен быть чистой функцией: *вход $\to$ обработка $\to$ выход*.
3.  **Efficiency:** Если тебе нужно просто посчитать элементы, не делай `.collect(Collectors.toList()).size()`. Используй `.count()`. Это быстрее и не требует выделения памяти под список.

---

### ❓ FAQ (Вопросы на собеседовании)

**В: В чем разница между `partitioningBy` и `groupingBy`?**
**О:** `partitioningBy` — это частный случай группировки, где ключом всегда является `Boolean`. Он работает быстрее и эффективнее, так как всегда создает ровно две корзины (true/false). `groupingBy` более универсален и может использовать любой тип ключа.

**В: Что произойдет, если в `toMap` попадутся дубликаты ключей и не указана функция слияния?**
**О:** Произойдет выброс исключения `java.lang.IllegalStateException: Duplicate key`. Чтобы этого избежать, нужно передать третий аргумент (merge function), который решит, какой из двух элементов оставить.

**В: Как с помощью одного коллектора получить и список объектов, и их среднее значение?**
**О:** Напрямую одним `Collector` — нет, но можно использовать `summarizingInt`, так как он возвращает объект статистики, содержащий в себе и сумму, и количество (из которого можно вычислить среднее), и другие метрики.

# 🧠 Шпаргалка: Collectors (Сбор в List и Set)

Класс `Collectors` — это набор готовых стратегий для терминальной операции `.collect()`. Если `Stream` — это конвейер, то `Collector` — это финальная коробка, в которую мы упаковываем результат.

## 1. Основные инструменты

### 🟢 `toList()` — Самый популярный
Собирает элементы стрима в реализацию `List`. 
*   **Что внутри:** Обычно возвращает `ArrayList`.
*   **Порядок:** Сохраняет порядок элементов, который был в стриме.
*   **Мутабельность:** В текущих реализациях JDK (до 16 версии включительно) возвращаемый список **мутабельный** (его можно менять: `.add()`, `.remove()`).

```java
List<String> list = stream.collect(Collectors.toList());
```

### 🔴 `toSet()` — Для уникальности
Собирает элементы в `Set`. Используется, когда нам нужно избавиться от дубликатов.
*   **Что внутри:** Обычно возвращает `HashSet`.
*   **Порядок:** **Не гарантирует** порядок. Элементы могут перемешаться.
*   **Сложность:** $O(n)$, так как каждый элемент проходит через `hashCode()` и `equals()`.

```java
Set<String> set = stream.collect(Collectors.toSet());
```

### 🛠 `toCollection(Supplier<Collection<T>> collectionFactory)` — Универсальный солдат
Если тебе не подходит стандартный `ArrayList` или `HashSet`, используй этот метод. Ты сам передаешь конструктор коллекции.
*   **Зачем:** Когда нужен конкретный тип (например, `TreeSet` для сортировки или `LinkedList` для специфических операций).

```java
// Собираем в TreeSet, чтобы элементы были отсортированы
TreeSet<String> sortedSet = stream.collect(Collectors.toCollection(TreeSet::new));

// Собираем в LinkedList
LinkedList<String> linkedList = stream.collect(Collectors.toCollection(LinkedList::new));
```

---

## 2. Нюансы и "Подводные камни" (Senior Level)

### ⚠️ Разница между `Stream.toList()` и `Collectors.toList()`
Это любимый вопрос на интервью. Начиная с **Java 16**, появился метод `.toList()` прямо у интерфейса `Stream`.
*   **`Collectors.toList()`**: Возвращает мутабельный (изменяемый) список (обычно `ArrayList`).
*   **`Stream.toList()`**: Возвращает **немодифицируемый (unmodifiable)** список. Попытка сделать `.add()` вызовет `UnsupportedOperationException`.
*   **Совет:** Если тебе не нужно менять список после сбора — используй новый `Stream.toList()`, это чище и эффективнее.

### ⚠️ Порядок в Parallel Streams
При использовании `parallelStream()` порядок элементов в `toList()` будет сохранен (благодаря внутренним механизмам слияния), но это требует больше ресурсов на синхронизацию. В `toSet()` порядок всё равно потеряется, так как `HashSet` не хранит порядок по определению.

### ⚠️ Null-значения
Все эти коллекторы позволяют хранить `null`. Если твой стрим содержит `null`, они попадут в итоговую коллекцию без ошибок. Если это критично — используй `.filter(Objects::nonNull)` перед сбором.

---

## 3. FAQ (Вопросы на собеседовании)

**В: Чем `Collectors.toSet()` отличается от `Collectors.toCollection(HashSet::new)`?**
**О:** Функционально — почти ничем. Но `toSet()` — это более высокоуровневая и читаемая абстракция. Использовать `toCollection` стоит только тогда, когда тебе нужен другой тип сета (например, `TreeSet`).

**В: Что будет, если я попытаюсь добавить элемент в список, полученный через `Stream.toList()`?**
**О:** Ты получишь `UnsupportedOperationException`. Этот метод возвращает неизменяемую view коллекции.

**В: Можно ли с помощью `toCollection` получить `LinkedHashSet`?**
**О:** Да, это стандартный способ сохранить порядок вставки при сборке в Set: 
`stream.collect(Collectors.toCollection(LinkedHashSet::new))`.

**В: Какой из методов самый быстрый для простого сбора элементов?**
**О:** Если тебе нужен неизменяемый список и Java 16+, то `Stream.toList()` — самый быстрый и лаконичный, так как он избегает лишних накладных расходов на создание промежуточных объектов коллектора.

# 🧠 Шпаргалка: Collectors (Группировка данных)

Группировка в Java Streams — это аналог оператора `GROUP BY` в SQL. Мы берем плоский поток элементов и превращаем его в структуру `Map`, где ключи — это критерии группировки, а значения — результат агрегации этих элементов.

## 1. partitioningBy (Специальный случай)
Это "упрощенная" версия группировки, которая работает только с типом `Boolean`. Она делит поток на две группы: те, что подходят под `Predicate`, и те, что нет.

*   **Что возвращает:** `Map<Boolean, List<T>>`
*   **Когда использовать:** Когда у тебя бинарное условие (да/нет, прошел/не прошел, активен/не активен).

```java
// Разделение студентов на прошедших и не прошедших экзамен
Map<Boolean, List<Student>> passingStatus = students.stream()
    .collect(Collectors.partitioningBy(s -> s.getGrade() >= 60));
```

## 2. groupingBy (Основной инструмент)
Здесь три уровня сложности. Чем выше уровень, тем больше контроля над результатом.

### Уровень 1: Базовая группировка
Самый простой вариант. Мы только указываем, по какому полю делить элементы. По умолчанию значениями в Map будут `List`.

*   **Что возвращает:** `Map<K, List<T>>`
*   **Пример:** Группировка сотрудников по департаменту.

```java
Map<String, List<Employee>> byDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment));
```

### Уровень 2: Группировка с "Downstream" (Вложенный коллектор)
Это «киллер-фича». Вметь `groupingBy` ты можешь передать второй аргумент — другой коллектор, который скажет, что делать со списком элементов внутри каждой группы.

*   **Что возвра<i>т:</i>** `Map<K, D>` (где `D` — результат работы вложенного коллектора).
*   **Популярные связки:**
    *   `counting()` — вместо списка считать количество элементов.
    *   `mapping()` — трансформировать элементы внутри группы перед сохранением.
    *   `toSet()` — вместо списка получать уникальные элементы.

```java
// 1. Считаем количество сотрудников в каждом департаменте (Map<String, Long>)
Map<String, Long> countByDept = employees.stream()
    .collect(Collectors.groupingBy(Employee::getDepartment, Collectors.counting()));

// 2. Получаем только имена сотрудников по департаментам (Map<String, Set<String>>)
Map<String, Set<String>> namesByDept = employees.stream()
    .collect(Collectors.groupingBy(
        Employee::getDepartment, 
        Collectors.mapping(Employee::getName, Collectors.toSet())
    ));
```

### Уровень 3: Группировка с кастомной реализацией Map
Иногда тебе не нужен `HashMap`. Тебе может понадобиться `TreeMap` (чтобы ключи были отсортированы) или `LinkedHashMap` (чтобы сохранить порядок вставки).

*   **Что возвращает:** `Map<K, D>` (но тип реализации ты выбираешь сам).

```java
// Группируем в TreeMap, чтобы департаменты шли по алфавиту
TreeMap<String, List<Employee>> sortedByDept = employees.stream()
    .collect(Collectors.groupingBy(
        Employee::getDepartment, 
        TreeMap::new, // Фабрика для создания Map
        Collectors.toList() // Downstream collector
    ));
```

## 💡 Нюансы от Senior'а (Pro Tips)

1.  **Производительность `partitioningBy` vs `groupingBy`:** Если твое условие — это `true/false`, всегда используй `partitioningBy`. Он оптимизирован под две корзины и работает быстрее, чем универсальный `group性by`.
2.  **Осторожно с `mapping` + `reducing`:** Вложенные коллекторы могут сильно нагружать память на огромных стримах. Если ты делаешь глубокую вложенность (группировка -> маппинг -> редукция), следи за тем, что не создаешь гигантские промежуточные объекты.
3.  **Null-ключи:** `groupingBy` использует `HashMap` под капотом. Помни, что `HashMap` позволяет один `null` ключ, но если твоя функция классификации (classifier) вернет `null`, это может привести к неожиданному поведению в других структурах (например, в `TreeMap`).
4.  **Side-effects:** Никогда не пытайся менять состояние внешних объектов внутри `classifier` или `downstream` коллектора. Стримы должны быть чистыми функциями.

**О:** `partitioningBy` — это частный случай `groupingBy`, где предикат всегда возвращает `boolean`. Он эффективнее, так как создает всего две группы (true и false) и работает быстрее.

**В: Как получить средний возраст сотрудников по каждому департаменту одним стримом?**
**О:** Нужно использовать `groupingBy` с downstream-коллектором `averagingInt`:

**В: Можно ли сделать группировку по двум полям сразу?**
**О:** Напрямую — нет, но можно использовать "составной ключ". Например, создать `record` или `Pair` из двух полей и использовать его как ключ в `groupingBy`.

# 🧠 Шпаргалка: Collectors.toMap()

`Collectors.toMap` — это инструмент для трансформации потока объектов (`Stream`) в структуру `Map<K, V>`. Это одна из самых часто используемых, но и самых "опасных" операций из-за риска получить исключение при встрече с дубликатами.

### 1. Базовый вариант (The Basic)
Используется, когда ты на 100% уверен, что ключи в стриме уникальны.

**Сигнатура:** `toMap(Function keyMapper, Function valueMapper)`

```java
List<User> users = List.of(new User(1, "Alice"), new User(2, "Bob"));

// Превращаем список в Map<Integer, String> (ID -> Name)
Map<Integer, String> idToName = users.stream()
    .collect(Collectors.toMap(User::getId, User::getName));
```
⚠️ **Риск:** Если в стриме окажется два пользователя с одинаковым `id`, ты получишь `IllegalStateException: Duplicate key`.

---

### 2. Вариант с разрешением конфликтов (The Merger)
Если ключи могут повторяться, тебе нужно сказать Java, что делать со старым и новым значением. Это "золотой стандарт" для безопасного кода.

**Сигнатура:** `toMap(keyMapper, valueMapper, mergeFunction)`

```java
List<User> users = List.of(new User(1, "Alice"), new User(1, "Bob")); // Дубликат ID!

Map<Integer, String> safeMap = users.stream()
    .collect(Collectors.toMap(
        User::getId, 
        User::getName, 
        (existingValue, newValue) -> existingValue // Оставляем первое встреченное значение
    ));
// Результат: {1="Alice"}
```
*   **Стратегии `mergeFunction`:**
    *   `(oldV, newV) -> oldV` — оставить старое.
    *   `(oldV, new -> newV)` — перезаписать новым (выберем последнее).
    *   `(oldV, newV) -> oldV + ", " + newV` — склеить значения в строку.

---

### 3. Вариант с выбором реализации (The Custom Map)
По умолчанию `toMap` возвращает `HashMap`. Но если тебе нужен порядок вставки (`LinkedHashMap`) или сортировка по ключам (`TreeMap`), используй четвертый аргумент.

**Сигнатура:** `toMap(keyMapper, valueMapper, mergeFunction, mapSupplier)`

```java
// Нам нужна TreeMap, чтобы ключи всегда были отсортированы
TreeMap<Integer, String> sortedMap = users.stream()
    .collect(Collectors.toMap(
        User::getId,
        User::getName,
        (oldV, newV) -> oldV,
        TreeMap::new // Указываем конструктор нужной реализации
    ));
```

---

### 💡 Нюансы и "Подводные камни" (Senior Tips)

1.  **Null Values:** `Collectors.toMap` **не позволяет** класть `null` в качестве *значения* (Value), если используется стандартная реализация через `HashMap`. Ты получишь `NullPointerException`. 
    *   *Решение:* Если нужны null-значения, используй `.forEach` или кастомный коллектор.
2.  **Сложность:** Помни, что `toMap` — это терминальная операция. Весь стрим должен быть обработан, прежде чем ты получишь карту.
3.  **groupingBy vs toMap:** 
    *   Если тебе нужно просто "сгруппировать" (один ключ $\to$ список значений), используй `Collectors.groupingBy`. 
    *   `toMap` — это когда один ключ $\to$ одно конкретное значение.

---

### ❓ FAQ (Частые вопросы на интервью)

**В: Что произойдет, если в `toMap` попадутся два одинаковых ключа?**
**О:** Выбросится `IllegalStateException`. Чтобы этого избежать, нужно использовать перегрузку метода с третьим аргументом (`mergeFunction`).

**В: Можно ли использовать `toMap` для создания `Map<Integer, List<User>>`?**
**О:** Напрямую — нет. `toMap` ожидает, что на один ключ приходится одно значение. Для создания мапы, где значением является список, нужно использовать `Collectors.groupingBy(User::getId)`.

**В: Как сохранить порядок вставки элементов при использовании `toMap`?**
**О:** Нужно использовать четвертый параметр (`mapSupplier`) и передать туда `LinkedHashMap::new`. По умолчанию стрим не гарантирует порядок, а `HashMap` его не хранит.

**В: Почему `Collectors.toMap(keyMapper, valueMapper)` падает с NPE, если значение (value) равно null?**
**О:** Внутри реализации `toMap` используется `Map.merge()`. А метод `Map.merge()` в стандартной `HashMap` выбрасывает `NullPointerException`, если новое значение является `null`.

# 🧠 Шпаргалка: Класс `Collectors` — Агрегация

**Агрегация** в Stream API — это процесс «схлопывания» (reduction) множества элементов стрима в один результат. Если `toList()` или `toSet()` просто собирают элементы «как есть», то агрегаторы выполняют математические или логические операции над ними.

### 1. Основные инструменты (The Heavy Hitters)

Эти методы возвращают не коллекцию, а конкретное числовое значение или объект статистики.

*   **`counting()`**: Считает количество элементов в стриме.
    *   *Результат:* `Long`.
    *   *Пример:* `.collect(Collectors.counting())` $\to$ `5L`.
*   **`summingInt()`, `summingLong()`, `summingDouble()`**: Суммирует значения, извлеченные из объектов.
    *   *Результат:* Примитивный тип (в обертке), соответствующий методу.
    *   *Нюанс:* Работает быстрее, чем ручной `reduce`, так как оптимизирован под примитивы.
*   **`averagingInt()`, `averagingLong()`, `averagingDouble()`**: Вычисляет среднее арифметическое.
    *   *Результат:* Всегда **`Double`**.
    *   *Важно:* Если стрим пустой, вернет `0.0`.

### 2. "Швейцарский нож": `summarizing...`

Это самый мощный инструмент для аналитики. Вместо того чтобы запускать пять разных стримов (один для суммы, другой для минимума и т.д.), ты делаешь всё за **один проход**.

*   **`summarizingInt()`, `summarizingLong()`, `summarizingDouble()`**:
    *   **Что возвращает:** Объект статистики (`IntSummaryStatistics`, `LongSummaryStatistics` или `DoubleSummaryStatistics`).
    *   **Внутри объекта сразу всё:** `count`, `sum`, `min`, `max`, `average`.
    *   *Senior Tip:* Используй это, когда тебе нужно построить отчет. Это экономит $O(n)$ времени, так как не нужно перечитывать данные многократно.

### 3. Поиск экстремумов (Min/Max)

*   **`minBy(Comparator)`** и **`maxBy(Comparator)`**:
    *   Находят минимальный или максимальный элемент на основе заданного компаратора.
    *   *Результат:* **`Optional<T>`**.
    *   *Нюанс:* Это критически важно! Если стрим пустой, ты получишь `Optional.empty()`, а не ошибку. Всегда обрабатывай этот случай (`.orElse(...)`).

---

### 💡 Нюансы и "Подводные камни" (Senior Insights)

1.  **Precision (Точность):** При использовании `summingDouble()` помни о проблемах чисел с плавающей точкой (`double` precision error). Если нужна идеальная финансовая точность, агрегация через стримы — не место для `double`, используй `BigDecimal` внутри `reduce`.
2.  **One-pass vs Multi-pass:** Самая частая ошибка джунов — делать так:
    ```java
    long count = list.stream().count();
    double sum = list.stream().mapToDouble(x -> x).sum(); // Плохо! Два прохода по данным.
    ```
    Правильно использовать `summarizingInt`, чтобы пройтись по списку всего один раз.
3.  **Complexity:** Все агрегаторы имеют сложность **$O(n)$**, так как каждый элемент должен быть посещен.

---

### ❓ FAQ (Вопросы на интервью)

**В: В чем разница между `summingInt()` и `reducing(0, Integer::sum)`?**
**О:** С точки зрения результата — почти ничего. Но `summingInt` специально оптимизирован под работу с примитивами и избавляет от лишнего автобоксинга (boxing/unboxing), что делает его более производительным на больших объемах данных.

**В: Что вернет `averagingDouble()` на пустом стриме?**
**О:** Вернет `0.0`. Это важно помнить, чтобы не ожидать там `Optional` или исключения.

**В: Можно ли использовать агрегацию в параллельных стримах (`parallelStream`)?**
**О:** Да, но помни про стоимость слияния (merging). Агрегаторы вроде `counting()` и `summingInt()` очень эффективно работают в параллели, так как их легко объединить (сложить результаты подпотоков). Однако сложные кастомные агрегации могут замедлить поток из-за накладных расходов на синхронизацию результатов.

**В: Что находится внутри `IntSummaryStatistics`?**
**О:** Набор методов: `getCount()`, `getSum()`, `getMin()`, `getMax()`, `getAverage()`. Это готовый объект для быстрой аналитики.

# 🧠 Шпаргалка: Parallel Streams

**Parallel Streams** — это способ распараллелить обработку данных из стрима, используя несколько ядер процессора. Вместо того чтобы обрабатывать элементы один за другим в одном потоке, Java разбивает задачу на подзадачи и выполняет их одновременно.

### ⚙️ Как это работает (Under the hood)
1.  **Fork/Join Framework:** В основе лежит `ForkJoinPool.commonPool()`. Это общий пул потоков для всего приложения.
2.  **Разделение (Splitting):** Стрим использует `Spliterator`, чтобы разделить источник данных на части (рекурсивно, пока части не станут достаточно маленькими).
3.  **Выполнение (Execution):** Подзадачи распределяются по рабочим потокам (worker threads) внутри `commonPool`.
4.  **Сборка (Merging):** Результаты вычислений объединяются обратно в один итоговый результат.

---

### ✅ Когда ИСПОЛЬЗОВАТЬ (Best Practices)
Чтобы параллелизм приносил пользу, а не вред, соблюдай правило **NQ Model**:
*   **N** — количество элементов.
*   **Q** — сложность обработки одного элемента.
*   **Правило:** Параллелизм эффективен, если $N \times Q$ достаточно велико (много данных И/ЛИ тяжелые вычисления).

**Критерии хорошего кандидата на Parallel Stream:**
1.  **Независимость задач:** Обработка одного элемента никак не влияет на другой (нет side-effects).
2.  **CPU-bound задачи:** Тяжелые математические расчеты, обработка изображений, сложная логика.
3.  **Источник данных легко делится:** Например, `ArrayList` или массивы (они позволяют быстро делить данные пополам).

---

### ❌ Когда НЕ ИСПОЛЬЗОВАТЬ (Anti-patterns)
1.  **Маленькие коллекции:** Накладные расходы на создание задач и управление потоками превысят выгоду от параллелизма.
2.  **I/O-bound задачи:** Чтение файлов, запросы к БД или сетевые вызовы. **Важно:** Если ты заблокируешь поток в `commonPool` долгим ожиданием ответа от сети, ты можешь «затормозить» всё приложение, так как этот пул общий для всех параллельных стримов.
3.  **Зависимость от порядка:** Если тебе критически важно сохранить порядок (например, `limit()` или `findFirst()`), параллельный стрим может работать медленнее из-за затрат на пересортировку.
4.  **Наличие Side-effects:** Если внутри стрима ты меняешь внешнюю переменную или коллекцию (например, добавляешь элементы в общий `ArrayList`). Это приведет к **Race Condition**.

---

### ⚠️ Главные нюансы и "подводные камни"

*   **Common Pool Exhaustion:** Все параллельные стримы в приложении используют один и тот же `ForkJoinPool.commonPool()`. Если одна часть приложения «забьет» этот пул тяжелыми задачами, остальные части (включая другие стримы) будут ждать.
*   **`forEach` vs `forEachOrdered`:** 
    *   `parallelStream().forEach(...)` — порядок элементов не гарантирован.
    *   `parallelStream().forEachOrdered(...)` — принудительно сохраняет порядок, но это убивает часть преимуществ параллелизма.
*   **Сложность разделения (Spliterator):** `ArrayList` делится очень быстро ($O(1)$), а `LinkedList` делится очень медленно ($O(n)$), потому что нужно пройти по списку, чтобы найти середину. Параллельный стрим на `LinkedList` может быть даже медленнее обычного.

---

### ❓ FAQ (Частые вопросы на интервью)

**В: Почему параллельный стрим может работать медленнее обычного?**
**О:** Из-за оверхеда (overhead). На разделение данных, создание задач в ForkJoinPool, переключение контекста между потоками и последующую сборку результатов тратятся ресурсы. Если задача слишком простая или данных мало, эти затраты перекрывают выигрыш от параллельной работы.

**В: Что такое Side-effect в контексте стримов?**
**О:** Это изменение состояния, которое выходит за пределы текущей операции стрима. Например, использование `map(x -> list.add(x))` — это плохой side-effect. В параллельном стриме это приведет к непредставимым результатам из-за конкурентного доступа к `list`.

**В: Можно ли использовать свой пул потоков для Parallel Stream?**
**О:** Напрямую — нет, `parallelStream()` всегда использует `commonPool`. Но можно «обмануть» систему, обернув вызов стрима в задачу, запущенную в своем `ForkJoinPool`, но это считается хаком и требует осторожности.

**В: Чем `ArrayList` лучше для параллельных стримов, чем `LinkedList`?**
**О:** `ArrayList` поддерживает быстрый доступ по индексу, что позволяет `Spliterator` мгновенно разделить массив на части. В `LinkedList` для того, чтобы найти середину, нужно пройтись по всем узлам, что делает процесс разделения очень дорогим.

# 🧠 Parallel Streams & ForkJoinPool: Deep Dive

### 1. Суть Parallel Streams
Parallel Stream — это не магия многопоточности, а **абстракция над ForkJoinPool**. Его задача — разбить одну большую задачу на несколько маленьких (декомпозиция), выполнить их параллельно и собрать результат обратно.

Работа строится по принципу **Divide and Conquer** (Разделяй и влагай):
1.  **Split (Fork):** Исходный поток данных делится на части (используя `Spliterator`).
2.  **Execute:** Каждая часть обрабатывается в отдельном потоке.
3.  **Combine (Join):** Результаты подзадач объединяются в один финальный результат.

### 2. Двигатель: ForkJoinPool и алгоритм Work-Stealing
В основе лежит `ForkJoinPool`. Его главная фишка — **Work-Stealing Algorithm** (алгоритм кражи задач).

*   **Как это работает:** У каждого рабочего потока (Worker Thread) есть своя собственная очередь задач (Deque). 
*   Когда поток выполняет свои задачи, он берет их из своей очереди.
*   **Нюанс (The "Stealing"):** Если у одного потока закончились задачи, он не простаивает. Он идет к другому «занятому» потоку и **крадет** задачу из конца его очереди. 
*   **Зачем это нужно:** Это минимизирует простой CPU и обеспечивает равномерную нагрузку на все ядра процессора.

### 3. Подводные камни (Senior Level)

#### ⚠️ Common Pool — общая ловушка
По умолчанию все параллельные стримы используют **`ForkJoinPool.commonPool()`**. 
*   **Проблема:** Это один и тот же пул для всего приложения. Если ты запустишь в `parallelStream()` тяжелую I/O задачу (например, долгий запрос к БД или чтение файла), ты заблокируешь потоки в этом пуле. 
*   **Результат:** Другие части твоего приложения, использующие параллельные стримы, тоже «встанут» и будут ждать.

#### ⚠️ Накладные расходы (Overhead)
Параллелизм — это не бесплатно. Деление задачи на части, создание объектов задач и их последующее слияние требуют ресурсов CPU и памяти.
*   Если задача слишком простая (например, простое сложение чисел), время на управление потоками может превысить время самой вычисления. Стрим станет **медленнее**, чем обычный `for`.

#### ⚠️ Порядок и состояние (State)
*   **Side Effects:** Никогда не меняй внешние переменные внутри `parallelStream`. Это приведет к Race Condition.
*   **Order-dependent operations:** Операции вроде `limit()`, `findFirst()` или `skip()` в параллельном режиме работают крайне неэффективно, так как им приходится синхронизировать состояние между потоками, чтобы соблюсти порядок.

**В: Что будет, если в параллельном стриме вызвать `Thread.sleep()`?**
**О:** Ты заблокируешь поток из `ForkJoinPool.commonPool()`. Если таких вызовов будет много, все остальные параллельные стримы в приложении начнут тормозить или остановятся, так как свободные потоки закончатся.

**В: В чем разница между `fork()` и `join()`?**
**О:** `fork()` — это запуск задачи асинхронно (мы «отпускаем» задачу в пул), а `join()` — это ожидание завершения задачи и получение её результата (блокирующая операция).

# 🧠 Шпаргалка: Parallel Streams — Скорость vs Overhead

### 1. Суть процесса (Under the hood)
Parallel Stream — это не "магические потоки". Это реализация стратегии **Divide and Conquer** (Разделяй и властвуй). 
В основе лежит фреймворк **ForkJoinPool**, а конкретно — его **commonPool()**.

**Как это работает:**
1.  **Split (Spliterator):** Исходный поток разбивается на части (суб-задачи) с помощью `Spliterator`.
2.  **Fork (Распараллеливание):** Задачи отправляются в `ForkJoinPool.commonPool()`.
3.  **Work-Stealing:** Если один поток освободился, он «крадет» задачу у другого занятого потока. Это минимизирует простой ядер.
4.  **Join (Слияние):** Результаты подзадач собираются и объединяются в один финальный результат.

---

### 2. ✅ Когда параллелизм УСКОРЯЕТ (The Good)

Параллелизм выгоден, когда **вычислительная сложность задачи значительно превышает затраты на управление потоками**.

*   **CPU-bound задачи:** Тяжелые математические вычисления, обработка изображений, сложные трансформации данных. Когда каждое ядро процессора должно "попотеть".
*   erc **Большие объемы данных (Large Datasets):** Чем больше элементов, тем выше потенциальный профит от распределения нагрузки.
*   **Независимые операции:** Каждый элемент обрабатывается изолированно. Нет зависимости между результатом элемента $A$ и элемента $B$.
*   **Эффективные источники (Splittable Sources):** Использование структур, которые легко делятся пополам (`ArrayList`, массивы). У них есть прямой доступ к элементам по индексу.

---

### 3. ❌ Когда параллелизм ЗАМЕДЛЯЕТ (The Overhead/Bad)

Здесь кроется большинство багов производительности. Параллелизм создает **Overhead** (накладные расходы): создание задач, контекстное переключение потоков, синхронизация и слияние результатов.

*   **Малые коллекции:** Если операция над элементом занимает 1 наносекунду, то время на "разрезание" списка и передачу задачи в пул будет в 100 раз больше, чем сама работа.
*   **I/O-bound задачи (Смертельный грех):** Если внутри стрима ты делаешь запросы к БД или API. Все потоки `commonPool` могут заблокироваться в ожидании ответа сети. Это приведет к **Thread Starvation** (голоданию потоков) — всё приложение встанет, так как общий пул занят ожиданием I/O.
*   **Плохие источники (Hard to Split):** Например, `LinkedList`. Чтобы разделить `LinkedList` пополам, Java придется пройтись по списку с начала до середины ($O(n)$). В итоге процесс разделения может занять больше времени, чем сама обработка.
*   **Наличие Side Effects (Побочных эффектов):** Если внутри стрима ты меняешь общую переменную (`shared state`), тебе придется использовать `synchronized` или `Atomic`. Конфликты за блокировку (lock contention) убьют всю параллельность.
*   **Сложные операции слияния:** Если операция `reduce` или `collect` требует очень сложной логики объединения результатов, стоимость "Join" этапа перекроет выгоду от "Fork".

### 💡 Senior's Tip: Формула NQ
Для оценки стоит использовать упрощенную модель **NQ**:
*   **N** — количество элементов.
*   **Q** — сложность обработки одного элемента.
Если $N \times Q$ очень мало, забудь про Parallel Stream.

### ❓ Часто задаваемые вопросы (Interview Prep)

**В: Что такое `ForkJoinPool.commonPool()` и чем он опасен?**
**О:** Это общий пул потоков для всех параллельных стримов в рамках одной JVM. Если ты запустишь тяжелую I/O задачу в parallel stream, ты заблокируешь этот пул. Другие части приложения (или другие стримы) не смогут получить ресурсы, так как поток будет ждать ответа от сети/диска.

**В: Почему `ArrayList` лучше подходит для параллельных стримов, чем `LinkedList`?**
**О:** Из-за механизма `Spliterator`. `ArrayList` можно мгновенно разделить по индексу (деление массива). `LinkedList` требует последовательного обхода для нахождения середины, что превращает параллельную задачу в последовательную с огромными накладными расходами.

**В: Можно ли использовать свой собственный пул потоков для Parallel Stream?**
**О:** Напрямую — нет (API стримов не принимает Executor). Но есть "хак": можно обернуть выполнение стрима в `new ForkJoinPool(parallelism).submit(() -> stream.parallel()...).get()`. Это позволяет изолировать тяжелые задачи от общего пула.

**В: Как понять, что пора переходить на Parallel Stream?**
**О:** Только через **профилирование** (JVisualVM, JProfiler). Никогда не используй параллелизм "на глаз". Сначала замерь время выполнения последовательного стрима и сравни с параллельным на реальных данных.

# 🧠 Шпаргалка: Сложность операций (Big O) в Java Collections

Когда мы говорим о сложности, мы имеем в виду **Time Complexity** (сколько времени занимает операция при росте количества элементов $n$). 

### 📊 Сводная таблица сложности

| Коллекция | Доступ по индексу / ключу | Поиск (contains) | Вставка (в начало/конец) | Удаление (из начала/контента) | Примечание |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **ArrayList** | $O(1)$ | $O(n)$ | $O(1)^*$ / $O(n)$ | $O(n)$ / $O(n)$ | $*$ Амортизированная сложность |
| **LinkedList** | $O(n)$ | $O(n)$ | $O(1)$ / $O(1)$ | $O(1)$ / $O(n)$ | Поиск элемента требует обхода |
| **HashSet** | — | $O(1)$ | $O(1)$ | $O(1)$ | Зависит от `hashCode()` |
| **TreeSet** | — | $O(\log n)$ | $O(\log n)$ | $O(\log n)$ | На базе красно-черного дерева |
| **HashMap** | $O(1)$ | $O(1)$ (по ключу) | $O(1)$ | $O(1)$ | В худшем случае $O(\log n)$ |
| **TreeMap** | — | $O(\log n)$ | $O(\log n)$ | $O(\log n)$ | Всегда упорядочено |
| **ArrayDeque** | — | $O(n)$ | $O(1)$ | $O(1)$ | Идеально как стек или очередь |
| **PriorityQueue**| — | $O(n)$ | $O(\log n)$ | $O(\log n)$ | Поиск (не по ключу) — $O(n)$ |

### 🔍 Разбор нюансов (Senior level)

#### 1. ArrayList: Магия "Амортизации"
Вставка в конец `ArrayList` считается $O(1)$, но это **амортизированная** сложность. 
*   **Нюанс:** Когда массив заполняется, Java создает новый массив большего размера (обычно $oldCapacity \times 1.5$) и копирует туда все элементы. В момент расширения операция стоит $O(n)$. Но так как это происходит редко, в среднем мы считаем это за $O(1)$.

#### 2. HashMap: Когда $O(1)$ превращается в $O(\log n)$
Классика учебников говорит, что `HashMap` — это $O(1)$. Но если у тебя плохая хеш-функция и все ключи попали в одну "корзину" (collision), структура превращается в связный список.
*   **Нюанс:** Начиная с Java 8, если количество элементов в одной корзине превышает порог (TREEIFY_THRESHOLD = 8), список превращается в **красно-черное дерево**. Это спасает нас от $O(n)$ и переводит сложность в $O(\log n)$.

#### 3. LinkedList vs ArrayList: Миф о быстрой вставке
Часто говорят: "Используй `LinkedList`, если нужно много вставок в середину". **Это ловушка.**
*   **Нюанс:** Чтобы вставить элемент в середину `LinkedList`, тебе сначала нужно его *найти*. Поиск занимает $O(n)$. В итоге ты тратишь столько же времени, сколько и в `ArrayList`. `LinkedList` выигрывает только если у тебя уже есть ссылка на узел (Node) в этой позиции.

#### 4. PriorityQueue: Дорогое удаление
В `PriorityQueue` операция `peek()` (взгляд на голову) — это $O(1)$. Но `poll()` (удаление головы) — это $O(\log n)$, потому что после удаления куче (Heap) нужно перестроить структуру, чтобы восстановить свойства приоритета.

### ❓ FAQ (Частые вопросы на интервью)

**В: Почему `ArrayList` обычно быстрее, чем `LinkedList`, даже при операциях вставки?**
**О:** Из-за **Cache Locality** (локальность кэша). Элементы `ArrayList` лежат в памяти плотным непрерывным блоком. Процессор очень эффективно подгружает их в кэш. Элементы `LinkedList` разбросаны по всей куче (heap), что вызывает постоянные Cache Misses (промахи кэша).

**В: Что такое "худший случай" для HashMap?**
**О:** Худший случай — это когда все ключи имеют одинаковый `hashCode()`. В этом случае все элементы попадают в одну корзину, и поиск превращается в линейный обход (или обход дерева), что резко снижает производительность.

**В: Какая сложность у операции `contains` в `TreeSet`?**
**О:** $O(\log n)$. Поскольку `TreeSet` базируется на `TreeMap` (красно-черное дерево), поиск идет путем сравнения элементов по порядку, что соответствует логарифмической сложности.

**В: Когда стоит использовать `ArrayDeque` вместо `Stack`?**
**О:** Всегда, когда не нужна многопоточность. Класс `Stack` устарел (legacy) и избыточен, так как каждая его операция `synchronized`. `ArrayDeque` быстрее, эффективнее по памяти и работает как LIFO/FIFO структура без лишних блокировок.

# 🧠 Best Practices: Java Collections & Streams

### 1. Выбор структуры данных (Performance First)
Главная ошибка — использовать `ArrayList` для всего подряд.
*   **Поиск по значению:** Если тебе нужно часто проверять `contains()`, используй `HashSet`. Поиск в `ArrayList` — $O(n)$, в `HashSet` — $int$ $O(1)$.
*   **Уникальность:** Нужны уникальные элементы? Только `Set`. Не пытайся имитировать это через `if (!list.contains(x)) list.add(x)` — это убивает производительность на больших списках.
*   **Порядок:** Если важен порядок вставки — `LinkedHashSet` или `LinkedHashMap`. Если нужна сортировка — `TreeSet` или `TreeMap`.
*   **Очереди:** Для задач типа "первым пришел — первым ушел" используй `Queue` (например, `ArrayDeque`).

### 2. Управление памятью и ресурсами
*   **Initial Capacity (Начальная емкость):** Если ты заранее знаешь, что в списке будет 1000 элементов, создавай его так: `new ArrayList<>(1000)`. Это предотвратит многократное пересоздание внутреннего массива при расширении (resizing), что экономит CPU и память.
*   **Избегай утечек памяти:** Будь осторожен с `Static` коллекциями. Если ты добавишь объект в `static List`, он никогда не будет удален Garbage Collector-ом, пока жива программа.

### 3. Чистота кода со Streams API
Стримы — это про *что* делать, а не *как*.
*   **Никаких Side Effects (Побочных эффектов):** Внутри `map`, `filter` и других операций **нельзя** менять внешние переменные или модифицировать исходную коллекцию. Стрим должен быть "чистой функцией". 
    *   ❌ *Плохо:* `.forEach(x -> list.add(x))` (это убивает идеологию стримов).
    *   ✅ *Хорошо:* `.collect(Collectors.toList())`.
*   **Не злоупотребляй Parallel Streams:** Параллельные стримы — это не "магическая кнопка ускорения". На маленьких данных накладные расходы на разделение задач (Splitting) и слияжение результатов будут выше, чем выгода. Используй их только для тяжелых вычислений на огромных массивах.
*   **Читаемость vs Сложность:** Если цепочка стримов занимает 20 строк и в ней 5 `flatMap`, лучше разбей её на несколько именованных этапов или вернись к обычному циклу `for`. Код должен быть понятен коллегам.

### 4. Безопасность и неизменяемость (Immutability)
*   **Defensive Copying (Защитное копирование):** Если твой метод возвращает список, который хранится внутри класса, не возвращай саму ссылку на него. Верни `List.copyOf(internalList)` или `Collections.unдерживаемыйList(...)`. Иначе любой клиент твоего кода сможет изменить внутреннее состояние объекта.
*   **Предпочитай Immutable коллекции:** В современном Java (9+) используй `List.of()`, `Set.of()`. Они не только лаконичны, но и защищают от случайных изменений.

### 5. Правила итерации
*   **Никогда не удаляй элементы из коллекции через `for-each`:** Это гарантированный `ConcurrentModificationException`.
    *   ❌ *Плохо:* `for (String s : list) { if (cond) list.remove(s); }`
    *   ✅ *Хорошо:* `list.removeIf(s -> cond);` или используй `Iterator.remove()`.

### ❓ FAQ: Часто задаваемые вопросы на интервью

**В: Можно ли использовать Stream дважды?**
**О:** Нет. Стрим — это одноразовый конвейер. Как только вы вызвали терминальную операцию (например, `.collect()`), стрим "закрывается". Попытка повторного использования вызовет `IllegalStateException`.

**В: В чем разница между `map` и `flatMap`?**
**О:** `map` трансформирует каждый элемент в один новый элемент (1 $\to$ 1). `flatMap` трансформирует каждый элемент в поток (Stream) и "распрямляет" их в один общий поток (1 $\to$ $N$). Используй `flatMap`, когда у тебя внутри объектов лежат другие коллекции.

**В: Почему `HashMap` может работать медленно, если много коллизий?**
**О:** Когда разные ключи имеют одинаковый `hashCode`, они попадают в одну "корзину" (bucket). В старых версиях Java это превращало поиск в линейный перебор списка $O(n)$. В новых (Java 8+) корзина превращается в дерево, что улучшает поиск до $O(\log n)$, но нагрузка на CPU всё равно растет.

**В: Когда стоит использовать `ArrayList` вместо `LinkedList`?**
**О:** Почти всегда. Из-за того, что элементы `ArrayList` лежат в памяти плотно друг к другу, процессор может эффективно использовать кэш (CPU Cache Locality). `LinkedList` разбросан по всей памяти, что создает много "промахов" кэша и замедляет работу.
</p>

# 🚩 Anti-patterns: Java Collections & Streams

Антипаттерны — это решения, которые кажутся простыми или логичными в моменте, но создают «технический долг», баги или убивают производительность.

## 1. Слой Collections (Структуры данных)

### ❌ Модификация коллекции во время итерации
**Суть:** Использование цикла `for-each` или обычного `Iterator` для удаления элементов из той же коллекции, по которой ты идешь.
*   **Результат:** `ConcurrentModificationException`.
*   **Как правильно:** Если нужно удалять — используй `iterator.remove()` или метод `removeIf()`.

### ❌ Игнорирование контракта `equals()` и `hashCode()`
**Суть:** Переопределение только одного из этих методов (обычно `equals`) при использовании объектов в `HashSet` или как ключей в `HashMap`.
*   **Результат:** "Потерянные" объекты. Ты кладешь объект в `Set`, а потом не можешь его найти, хотя он там есть, потому что `hashCode` вычисляет другой индекс корзины (bucket).
*   **Как правильно:** Всегда переопределяй оба метода вместе (используй IDE или Lombok `@EqualsAndHashCode`).

### ❌ Выбор неподходящей реализации (Wrong Tool for the Job)
**Суть:** Использование `LinkedList` везде, где нужно "быстрое добавление".
*   **Нюанс:** Многие думают, что `LinkedList` быстрее для вставок. Но из-за плохой локальности данных (cache misses) и накладных расходов на создание узлов, современный `ArrayList` почти всегда выигрывает даже при вставках в середину.
*   **Как правильно:** По умолчанию используй `ArrayList`. Используй `LinkedList` только если у тебя есть специфические требования к очереди или двусвязному списку.

### ❌ Утечки памяти через Static Collections
**Суть:** Хранение объектов в `static` коллекциях (например, `static List<User> cache`) без механизма очистки.
*   **Результат:** Объекты никогда не будут собраны Garbage Collector-ом, так как ссылка на них живет всё время работы приложения.
*   **Как правильно:** Используй `WeakHashMap` или механизмы кэширования с ограничением размера (LRU cache).

## 2. Слой Streams API (Функциональный стиль)

### ❌ Побочные эффекты в промежуточных операциях (Side Effects)
**Суть:** Использование `.map()` или `.filter()` для изменения состояния переменных вне стрима (например, инкремент внешнего счетчика).
*   **Пример:** `.map(x -> { counter++; return x; })`.
*   **Результат:** Непредсказуемое поведение, особенно в `parallelStream()`. Стрим должен быть **stateless** (не иметь состояния).
*   **Как правильно:** Используй терминальные операции (`collect`, `reduce`) для агрегации данных.

### ❌ Повторное использование стрима
**Суть:** Попытка вызвать вторую терминальную операцию на одном и том же объекте стрима.
*   **Результат:** `IllegalStateException: stream has already been operated upon or closed`. Стрим — это одноразовый конвейер.
*   **Как правильно:** Создавай новый стрим из источника для каждой новой цепочки операций.

### ❌ "Тяжелые" лямбды (Fat Lambdas)
**Суть:** Написание многострочной логики с циклами и `if-else` прямо внутри `.map()` или `.filter()`.
*   **Результат:** Код становится нечитаемым, его невозможно тестировать отдельно.
*   **Как правильно:** Выноси сложную логику в отдельные приватные методы. Стрим должен читаться как высокоуровневый список шагов: "отфильтруй, преобразуй, собери".

### ❌ Злоупотребление Parallel Streams
**Суть:** Использование `.parallelStream()` для всех задач, особенно на маленьких коллекциях или задачах с интенсивным I/O.
*   **Результат:** Вместо ускорения ты получаешь замедление из-за затрат на разделение данных (splitting) и управление потоками в `ForkJoinPool`. Также это может "забить" общий пул потоков всей JVM.
*   **Как правильно:** Используй параллелизм только для вычислительно тяжелых задач (CPU-bound) на очень больших объемах данных.

## 🎓 FAQ: Вопросы с собеседованияний

**В: Что произойдет, если в `HashMap` положить объект, у которого `hashCode()` всегда возвращает `1`?**
**О:** Все объекты попадут в одну и ту же корзину (bucket). Это превратит `HashMap` из структуры с $O(1)$ в связный список с $O(n)$. В Java 8+ это частично спасает переход в красно-черное дерево ($O(\log n)$), но производительность всё равно деградирует.

**В: Можно ли использовать `Stream.map()` для изменения данных внутри объектов в коллекции?**
**О:** Технически — да, это не вызовет ошибку. Но архитектурно — это антипаттерн. Стрим должен трансформировать поток элементов, а не мутировать состояние объектов внутри него. Это нарушает принцип чистоты функций и делает код труднопредсказуемым.

**В: Почему `ArrayList` обычно быстрее, чем `LinkedList`, даже при операциях вставки?**
**О:** Главная причина — **CPU Cache Locality**. Элементы `ArrayList` лежат в памяти плотно друг к другу. Процессор при чтении одного элемента подгружает соседние в кэш. В `LinkedList` узлы разбросаны по всей куче, что заставляет процессор постоянно ждать загрузки данных из RAM (cache misses).
