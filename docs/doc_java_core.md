# ☕️ Архитектура Java: Cheat Sheet

Главная идея Java — концепция **WORA** (*Write Once, Run Anywhere* — «Напиши один раз, запускай везде»). Это достигается за счет того, что ты пишешь код не под конкретный процессор или ОС, а под виртуальную машину (JVM).

### 1. Три кита: JDK, JRE и JVM
Многие их путают, но важно четко разделять уровни абстракции:

*   **JVM (Java Virtual Machine)** — это «сердчик» всей системы. Это виртуальный компьютер, который исполняет байт-код. Именно JVM адаптирует твой код под конкретную ОС (Windows, Linux, macOS).
*   **JRE (Java Runtime Environment)** — это среда для **запуска**. Она включает в себя **JVM + стандартные библиотеки** (java.lang, java.util и т.д.). Если тебе нужно просто запустить готовую программу, тебе достаточно JRE.
*   **JDK (Java Development Kit)** — это набор инструментов для **разработки**. Он включает в себя **JRE + инструменты разработчика** (компилятор `javac`, дебаггер `jdb`, документатор `javadoc` и др.). Если ты пишешь код — тебе нужен JDK.

> **Иерархия:** `JDK ⊃ JRE ⊃ JVM`

---

### 2. Процесс компиляции (Lifecycle of Code)
Твой путь от идеи до работающей программы выглядит так:

1.  **Source Code:** Ты пишешь текст в файле `.java`.
2.  **Compilation:** Ты запускаешь компилятор `javac`. Он проверяет синтаксис и превращает твой читаемый код в **Bytecode** (байт-код) — файл `.class`.
3.  **Bytecode:** Это промежуточный, низкоуровневый язык, который не понимает ни один процессор, но идеально понимает JVM. Он универсален.
4.  **Execution:** JVM считывает байт-код и с помощью **Интерпретатора** и **JIT-компилятора** превращает его в машинный код (нули и единицы), понятный конкретному процессору.

---

### 3. Внутреннее устройство JVM (Runtime Data Areas)
Когда программа запущена, JVM выделяет память под разные нужды:

*   **Method Area:** Хранит структуру классов: имена, методы, поля, статические переменные и константы. Это общая область для всех потоков.
*   **Heap (Куча):** Самая важная часть. Здесь живут **все объекты**, созданные в программе (`new MyObject()`). Именно здесь работает Garbage Collector. Общая область для всех потоков.
    ering
*   **Stack (Стек):** Для каждого нового потока (Thread) создается свой стек. В нем хранятся локальные переменные и фреймы методов. Когда метод вызывается, в стеке создается "фрейм", когда метод завершается — фрейм удаляется. Это очень быстро, но память ограничена.
*   **PC Register (Program Counter):** У каждого потока есть свой счетчик команд. Он хранит адрес текущей инструкции, которую выполняет поток.
*   **Native Method Stack:** Сюст для хранения данных методов, написанных на других языках (C/C++), которые вызываются через JNI (Java Native Interface).

---

### 4. Execution Engine: Двигатель прогресса
Как именно код превращается в действия?

*   **Interpreter:** Читает байт-код построчно и сразу выполняет его. Это быстро в начале, но медленно при повторных циклах.
*   **JIT Compiler (Just-In-Time):** "Умный" компонент. Он следит за кодом и находит "горячие участки" (Hot Spots) — те части кода, которые вызываются очень часто (например, циклы). JIT компилирует эти участки напрямую в машинный код один раз, чтобы потом выполнять их с максимальной скоростью процессора.
*   **Garbage Collector (GC):** Автоматический уборщик. Он ищет объекты в Heap, на которые больше никто не ссылается, и удаляет их, освобождая память.

---

### 💡 Нюансы для Senior-ответа:
1.  **Platform Dependence:** Запомни: **Java — платформонезависима, но JVM — платформозависима**. Ты пишешь один `.class` файл, но скачиваешь разные версии JDK/JRE под Windows и под Linux. Именно JVM берет на себя всю грязную работу по общению с ОС.
2.  **JIT vs Interpreter:** Интерпретатор дает "быстрый старт", а JIT обеспечивает "высокую скорость" в процессе долгой работы программы. Без JIT Java была бы слишком медленной.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между Stack и Heap?**
**О:** Heap — это общая область памяти для всех потоков, где хранятся объекты. Она большая, но управление ею (очистка) требует ресурсов. Stack — индивидуальная память для каждого потока, где хранятся примитивы и ссылки на объекты. Она работает очень быстро, но имеет ограниченный размер.

**В: Что произойдет, если в Stack закончится место?**
**О:** Произойдет ошибка `StackOverflowError` (обычно из-за бесконечной рекурсии).

**В: Что произойдет, если в Heap закончится место?**
**О:** Произойдет `OutOfMemoryError` (когда Garbage Collector уже не может освободить достаточно памяти для новых объектов).

**В: Зачем нужен JIT-компилятор, если есть интерпретатор?**
**О:** Интерпретатор выполняет код медленно, так как каждый раз заново разбирает инструкции. JIT находит часто используемый код и превращает его в нативный машинный код, что позволяет Java приблизиться к скорости C++.

# 🧠 Шпаргалка: Типы данных в Java

В Java всё делится на две большие группы: **Примитивы** (Primitive Types) и **Ссылочные типы** (Reference Types). Это фундаментальное различие определяет, как данные хранятся в памяти и как они ведут себя при передаче в методы.

## 1. Примитивные типы (Primitives)
Это «кирпичики» языка. Они максимально просты, не являются объектами и хранят **само значение** непосредственно в стеке (Stack).

| Тип | Размер | Диапазон (примерно) | Особенность |
| :--- | :--- | :--- | :--- |
| `byte` | 8 бит | -128 ... 127 | Минимальный размер, экономит память в массивах. |
| `short` | 16 бит | -32,768 ... 32,767 | Редко используется. |
| `int` | 32 бита | $\approx \pm 2$ млрд | **Стандарт** для целых чисел. |
| `long` | 64 бита | Очень большой | Нужно добавлять суффикс `L` (например, `10L`). |
| `float` | 32 бита | Числа с плавающей точкой | Нужен суффикс `f` (`3.14f`). Низкая точность. |
| `double` | 64 бита | Очень точные числа | **Стандарт** для дробных чисел. |
| `char` | 16 бит | Unicode символ | Хранит один символ (например, `'A'`). |
| `boolean`| $\approx$ 1 бит | `true` / `false` | Логический тип. Размер в памяти не регламентирован жестко. |

### ⚠️ Нюансы примитивов:
*   **Overflow (Переполнение):** Если ты прибавишь 1 к `Integer.MAX_VALUE`, ты не получишь ошибку, ты получишь `Integer.MIN_ESS_VALUE`. Число «прокрутится» по кругу. Это классическая ловушка.
*   **Default Values:** Поля класса (instance variables) всегда инициализируются значениями по умолчанию (`0`, `false`, `null` для объектов). **Локальные переменные** (внутри методов) — **нет**. Если не инициализировать локальную переменную, код просто не скомпилируется.
*   **Floating Point Precision:** Никогда не используй `float` или `double` для финансовых расчетов! Из-за особенностей двоичной системы представления дробных чисел, `0.1 + 0.2` может не равняться `0.3`. Для денег используй `BigDecimal`.

---

э## 2. Ссылочные типы (Reference Types)
Это сложные структуры: Объекты, Массивы, Строки (`String`). В переменной такого типа хранится не само значение, а **адрес (ссылка)** на место в куче (Heap), где лежат данные.

### ⚠️ Нюансы ссылочных типов:
*   **Nullability:** Ссылочный тип может принимать значение `null` (указатель никуда не ведет). Примитив — никогда. Попытка вызвать метод у `null` приведет к легендарному `NullPointerException`.
*   **Сравнение:**
    *   Для примитивов `==` сравнивает **значения**.
    *   Для ссылочных типов `==` сравнивает **адреса в памяти** (указывают ли две переменные на один и тот же объект). Чтобы сравнить *содержимое* объектов, нужно использовать `.equals()`.

---

## 3. Автоупаковка и Распаковка (Autoboxing & Unboxing)
Java умеет автоматически превращать примитив в его «обертку»-объект (Wrapper class) и обратно.

*   **Пример:** `Integer x = 10;` — здесь `int` (примитив) превратился в `Integer` (объект). Это называется **Autoboxing**.
*   **Зачем это нужно?** Чтобы использовать примитивы там, где требуются объекты (например, в коллекциях, хотя мы их сейчас не обсуждаем, или при работе с Generics).
*   **Опасность:** Постоянная упаковка/распаковка в циклах — это лишняя нагрузка на память и процессор (создание кучи мусорных объектов).

---

## ❓ FAQ: Часто задаваемые вопросы на собеседовании

**В: Чем `int` отличается от `Integer`?**
**О:** `int` — это примитив, он хранит значение в стеке, занимает мало места и не может быть `null`. `Integer` — это объект (обертка), живет в куче, может быть `null` и обладает методами (например, `Integer.parseInt()`).

**В: Что произойдет, если прибавить 1 к `Byte.MAX_VALUE`?**
**О:** Произойдет переполнение (overflow). Значение «перепрыгнет» в начало диапазона, и ты получишь `Byte.MIN_VALUE`.

**В: Можно ли присвоить `null` переменной типа `int`?**
**О:** Нет, примитивы не могут быть `null`. Если попытаться это сделать (например, при распаковке объекта `Integer`, который равен `null`), ты получишь `NullPointerException`.

**$\implies$ Senior Tip:** Всегда помни про разницу между **Стеком** (где живут примитивы и ссылки) и **Кучей** (где живут сами объекты). Понимание этого — ключ к пониманию управления памятью в Java.

# 📌 Шпаргалка: Переменные в Java

**Переменная** — это именованная область памяти, в которой хранится значение определенного типа. Можно представить её как коробку с ярлыком (именем) и содержимым (данными).

## 1. Классификация по области видимости (Scope)

В Java переменные делятся на три основных типа в зависимости от того, где они объявлены:

### A. Локальные переменные (Local Variables)
*   **Где живут:** Внутри метода, конструктора или блока кода `{ ... }`.
*   **Время жизни:** Создаются при входе в блок и уничтожаются при выходе из него.
*   **Нюанс (Важно!):** Java **не инициализирует** локальные переменные автоматически. Если ты попытаешься использовать переменную, не присвоив ей значение, получишь ошибку компиляции (`Variable might not have been initialized`).

### B. Поля экземпляра (Instance Variables / Fields)
*   **Где живут:** Внутри класса, но вне методов. Принадлежат конкретному объекту.
*   **Время жизни:** Создаются вместе с объектом (при `new`) и живут, пока объект доступен для Garbage Collector.
*   **Нюанс:** Java **автоматически инициализирует** их значениями по умолчанию:
    *   Числа (`byte`, `int`, `long` и т.s.) $\to$ `0` или `0.0`.
    *   `boolean` $\to$ `false`.
    *   `char` $\to$ `\u0000` (пустой символ).
    *   Ссылочные типы (объекты, String) $\to$ `null`.

### C. Поля класса (Static Variables / Class Variables)
*   **Где живут:** Помечены ключевым словом `static`. Принадлежат самому классу, а не объектам.
*   **Время жизни:** Создаются при загрузке класса JVM и живут до завершения работы программы (или выгрузки класса).
*   **Нюанс:** Одна копия переменной на все экземпляры класса. Доступны через `ИмяКласса.имяПеременной`.

---

## 2. Ключевые модификаторы для переменных

*   **`final`**: Делает переменную "константой". После того как ей присвоено значение, изменить его нельзя.
    *   Для локальных переменных: значение можно присвоить только один раз.
        s   *   Для полей экземпляра: превращает поле в неизменяемое (immutable) состояние объекта.
*   **`static`**: Привязывает переменную к классу, а не к объекту.

---

## 3. Важные нюансы и "подводные камни"

### Shadowing (Затенение)
Если локальная переменная имеет то же имя, что и поле экземпляра, локальная переменная "затеняет" поле. Чтобы добраться до поля класса в таком случае, нужно использовать ключевое слово `this`.

```java
public class User {
    private String name; // Поле экземпляра

    public void setName(String name) { // 'name' здесь — локальный параметр (затеняет поле)
        this.name = name; // this.name обращается к полю, а просто name — к параметру
    }
}
```

### Инициализация vs Объявление
*   **Объявление:** `int x;` (мы просто зарезервировали место).
*   **Инициализация:** `x = 10;` (мы положили значение в коробку).

---

## ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем отличается инициализация поля класса от локальной переменной?**
**О:** Поля класса инициализируются значениями по умолчанию автоматически (`0`, `null`, `false`). Локальные переменные **не инициализируются** сами — программист обязан присвоить им значение перед использованием, иначе код не скомпилируется.

**В: Что будет, если пометить локальную переменную как `static`?**
**О:** Это приведет к ошибке компиляции. Модификатор `static` применим только к полям класса, так как он определяет принадлежность к классу, а не к методу.

**В: Можно ли изменить значение переменной, помеченной `final`?**
**О:** Для примитивов — нет (значение зафиксировано). Для ссылочных типов (объектов) — **да**, но только содержимое объекта. Сама "ссылка" (адрес в памяти) остается неизменной, но поля внутри этого объекта можно менять (если они не `final`).

**В: Что такое "Shadowing"?**
**О:** Это ситуация, когда переменная в более узкой области видимости (например, локальная в методе) имеет то же имя, что и переменная в более широкой области (поле класса), из-за чего к полевому значению становится сложно обратиться напрямую без `this`.

# 🧠 Шпаргалка: Операторы в Java

Операторы — это инструменты, которые управляют логикой, вычислениями и изменением состояния переменных. В Java они делятся на несколько ключевых групп.

### 1. Арифметические операторы (Arithmetic)
Используются для математических вычислений.
*   `+` — Сложение (также используется для конкатенации строк).
*     `-` — Вычитание.
*   `*` — Умножение.
*   `/` — Деление. **Важно:** если оба операнда — целые числа (`int`, `long`), результат будет целым (дробная часть просто отсекается).
*   `%` — Остаток от деления (Modulo). Полезно для проверки четности или циклов.

**Нюанс:** При работе с отрицательными числами знак результата `%` соответствует знаку делимого (левого числа).

### 2. Инкремент и Декремент (Unary)
Увеличение/уменьшение значения на 1.
*   `++i` (**Префиксный**): Сначала увеличиваем, потом используем значение.
*   `i++` (**Постфиксный**): Сначала используем текущее значение, а потом увеличиваем.

**Нюанс:** Это классический вопрос на собеседовании. Разница проявляется именно в момент присваивания или использования в выражении.

### 3. Операторы сравнения (Relational)
Всегда возвращают `boolean` (`true` или `false`).
*   `==` — Равенство (для примитивов сравнивает значения, для объектов — **ссылки**).
*   `!=` — Неравенство.
*   `>` , `<` , `>=` , `<=` — Больше, меньше, больше или равно, меньше или равно.

### 4. Логические операторы (Logical)
Работают с `boolean` значениями.
*   `&&` (**Short-circuit AND**): Логическое "И". Если левая часть `false`, правая даже не вычисляется (короткое замыкание).
*   `||` (**Short-circuit OR**): Логическое "ИЛИ". Если левая часть `true`, правая не вычисляется.
*   `!` — Логическое "НЕ" (инверсия).

**Нюанс:** Существуют также одиночные `&` и `|`. Они работают так же, но **не имеют** эффекта короткого замыкания (вычисляют обе части в любом случае). Это редко нужно, но важно знать.

### 5. Битовые операторы (Bitwise)
Работают на уровне отдельных битов числа.
*   `&` — Побитовое "И".
*   `|` — Побитовое "ИЛИ".
*   `^` — Побитовое "Исключающее ИЛИ" (XOR).
*   `~` — Побитовое отрицание (инверсия всех бит).
*   `<<` — Сдвиг влево (умножение на $2^n$).
*   `>>` — Сдвиг вправо с сохранением знака (деление на $2^n$).
*   `>>>` — **Беззнаковый** сдвиг вправо (заполняет левые биты нулями, игнорируя знак).

### 6. Операторы присваивания (Assignment)
*   `=` — Простое присваивание.
*   `+=`, `-=`, `*=`, `/=`, `%=` — Комбинированные операторы (например, `a += b` это то же самое, что `a = a + b`).

### 7. Тернарный оператор (Ternary)
Сокращенная форма `if-else`.
*   `условие ? значение_если_true : значение_если_false;`

### 8. Оператор `instanceof` (Java 21 Style)
Проверка, является ли объект экземпляром определенного класса.
*   **Классика:** `if (obj instanceof String) { String s = (String) obj; ... }`
*   **Pattern Matching (Новинка):** В современных версиях Java можно сразу объявлять переменную: `if (obj instanceof String s) { ... }`. Это избавляет от лишнего приведения типов (casting).

### ❓ Часто задаваемые вопросы (FAQ)

**В: В чем разница между `&&` и `&`?**
**О:** Разница в "коротком замыкании". `&&` остановится, если первая часть выражения уже определяет результат. `&` выполнит обе части в любом случае. Это критично, если во второй части стоит вызов метода или проверка на `null`.

**В: Что выведет код `System.out.println(10 / 3);`?**
**О:** Выведет `3`. Поскольку оба числа целые, Java выполняет целочисленное деление и отбрасывает остаток. Чтобы получить `3.33...`, нужно хотя бы одно число сделать `double` (например, `10.0 / 3`).

**В: Что будет в переменной `x` после выполнения `int x = 5; int y = x++;`?**
**О:** `x` станет `6`, но `y` станет `5`. Потому_то постфиксный инкремент сначала возвращает старое значение, а потом увеличивает переменную.

**В: Как работает оператор `>>>` и чем он отличается от `>>`?**
**О:** `>>` сохраняет знаковый бит (если число отрицательное, слева приходят единицы). `>>>` всегда заполняет пустые места нулями, что делает его полезным для работы с беззнаковыми данными.

# 🧠 Шпаргалка: Приведение типов (Type Casting)

**Приведение типов** — это процесс преобразования значения одного типа в другой тип. В Java мы разделяем этот процесс на две большие категории: работу с примитивами и работу со ссылочными типами (объектами).

---

### 1. Приведение примитивных типов
Здесь всё зависит от направления движения: от меньшего к большему или наоборот.

#### **A. Расширение (Widening Casting) — Неявное**
Происходит автоматически, когда мы переносим значение из "маленького" типа в "больший". Данные не теряются.
*   **Цепочка:** `byte` $\to$ `short` $\to$ `char` $\to$ `int` $\to$ `long` $\to$ `float` $\to$ `double`.
*   **Пример:**
    ```java
    int myInt = 100;
    double myDouble = myInt; // Автоматически: 100.0
    ```

#### **B. Сужение (Narrowing Casting) — Явное**
Происходит, когда мы пытаемся впихнуть "большой" тип в "маленький". Java не может быть уверена, что данные влезут, поэтому требует явного указания типа в скобках `(type)`.
*   **Риск:** Потеря точности или переполнение (overflow).
*   **Пример:**
    ```java
    double myDouble = 9.78;
    int myInt = (int) myDouble; // Явное приведение: 9 (дробная часть просто отсекается!)
    ```

> **⚠️ Senior Note (Нюанс):** При сужении `double` $\to$ `int` происходит не округление, а **отбрасывание** дробной части (truncation). Если тебе нужно именно математическое округление, используй `Math.round()`.

---

### 2. Приведение ссылочных типов (Object Casting)
Здесь мы работаем с иерархией классов (наследованием).

#### **A. Upcasting (Восходящее приведение)**
Приведение подкласса к суперклассу.
*   **Безопасность:** Всегда безопасно и происходит автоматически.
*   **Суть:** "Любая Собака — это Животное".
*   **Пример:**
    ```java
    Dog myDog = new Dog();
    Animal myAnimal = myertDog; // Upcasting (автоматически)
    ```

#### **B. Downcasting (Нисходящее приведение)**
Приведение суперкласса к подклассу.
*   **Безопасность:** Опасно! Требует явного указания типа. Если реальный объект в памяти не является тем, к чему ты приводишь, программа упадет с ошибкой `ClassCastException`.
*   **Суть:** "Не каждое Животное — это Собака".
*   **Пример:**
    ```java
    Animal myAnimal = new Dog(); 
    Dog myDog = (Dog) myAnimal; // Downcasting (безопасно, так как объект реально Dog)
    
    Animal catWrapper = new Cat();
    Dog errorDog = (Dog) catWrapper; // КРАШ! ClassCastException
    ```

> **⚠️ Senior Note (Нюанс):** Чтобы не ловить `ClassCastException`, всегда используй оператор **`instanceof`** перед тем, как делать Downcasting. Это твоя страховка.

---

### 🛠 Инструментарий: Оператор `instanceof`
Проверяет, является ли объект экземпляром конкретного класса или интерфейса.

```java
if (myAnimal instanceof Dog) {
    Dog myDog = (Dog) myAnimal; // Теперь приводить безопасно
    myDog.bark();
}
```
*В Java 16+ появился **Pattern Matching for instanceof**, который делает это одной строкой:*
```java
if (myAnimal instanceof Dog myDog) { // Проверил и сразу создал переменную myDog
    myDog.bark();
}
```

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что произойдет, если при приведении `long` к `int` значение слишком велико?**
**О:** Произойдет **overflow** (переполнение). Значение "зациклится" и превратится в совершенно другое число (в пределах диапазона `int`), так как старшие биты просто отсекутся.

**В: Можно ли привести `String` к `Integer` через приведение типов?**
**О:** Нет. Несмотря на то, что строка может содержать цифры `"123"`, это разные ветки иерархии (String — это класс, Integer — другой класс). Для этого нужно использовать парсинг: `Integer.parseInt(str)`.

**В: Всегда ли Upcasting безопасен?**
**О:** Да, с точки зрения типов. Но помни: после Upcasting ты теряешь доступ к методам, которые есть в подклассе, но которых нет в суперклассе (ты видишь объект только через "призму" родителя).

**В: В чем разница между потерей точности и потерей данных при кастинге?**
**О:** При `double` $\to$ `int` мы теряем **точность** (дробную часть). При `long` $\to$ `int` мы можем потерять **значимые части числа** (из-за отсечения старших битов), что полностью меняет значение.

# 🏗️ Тема: Классы и Объекты (Classes & Objects)

### 1. Суть концепции
Представь, что ты архитектор.
*   **Класс** — это **чертеж** дома. На чертеже написано, где будут окна, сколько дверей и какая толщина стен. Но в чертеже нельзя жить. Сам по себе чертеж не является домом, это лишь описание.
*   **Объект** — это **реальный дом**, построенный по этому чертежу. Ты можешь построить 10 разных домов (объектов) по одному и тому же чертежу (классу). У них будут одинаковые планировки, но цвет стен или мебель внутри могут отличаться.

### 2. Анатомия Класса
Класс — это программная структура, которая объединяет:
1.  **Состояние (State):** Это **поля (fields)** или атрибуты класса. Переменные, которые хранят данные объекта (например, `color`, `size`, `model`).
2.  **Поведение (Behavior):** Это **методы (methods)**. Функции, которые определяют, что объект может делать (например, `drive()`, `stop()`, `openDoor()`).
3.  **Конструктор (Constructor):** Специальный метод, который "рождает" объект и инициализирует его начальное состояние.

### 3. Объект: Экземпляр (Instance)
Когда мы пишем `new MyClass()`, происходит магия создания **экземпляра**.
Объект обладает тремя характеристиками:
*   **Состояние:** Значения всех его полей в данный момент.
*   **Поведение:** Доступ к методам, описанным в классе.
*   **Идентичность (Identity):** У каждого объекта есть уникальный адрес в памяти (в Heap), даже если два объекта имеют абсолютно одинаковые поля.

### 4. Нюансы "для Senior" (Важно!)

#### А) Ссылка vs Объект
Это самая частая ошибка новичков.
```java
Car myCar = new Car();
```
Здесь:
*   `myCar` — это **не сам объект**. Это **переменная-ссылка** (reference variable), которая лежит в **Stack** и хранит адрес объекта.
*   `new Car()` — это создание самого объекта в **Heap** (куче).
*   Если ты напишешь `Car anotherCar = myCar;`, ты не создашь второй дом. Ты просто сделаешь вторую копию ключа от того же самого дома. Оба "ключа" указывают на один и тот же объект.

#### Б) Класс vs Статические поля (Static)
*   **Поля экземпляра:** У каждого объекта свои (у каждой машины свой цвет).
*   **Статические поля (`static`):** Принадлежат самому классу, а не объектам. Это "общая память" для всех домов по этому чертежу (например, `totalHousesBuilt`).

#### В) Память: Stack vs Heap
*   **Stack (Стек):** Здесь хранятся локальные переменные и ссылки на объекты. Работает быстро, но память ограничена.
*   **Heap (Куча):** Здесь живут сами объекты. Это огромное пространство, которым управляет Garbage Collector.

### ❓ FAQ: Подготовка к интервью

**В: В чем разница между классом и объектом?**
**О:** Класс — это абстрактный шаблон, тип данных, описывающий структуру. Объект — это конкретный экземпляр этого шаблона, существующий в памяти и имеющий состояние.

**В: Что происходит в памяти при выполнении команды `Car c = new Car();`?**
**О:**
1. В **Stack** создается переменная `c`.
2. В **Heap** выделяется место под новый объект типа `Car`.
3. Вызывается конструктор для инициализации полей объекта.
4. Адрес (ссылка) на этот объект в Heap записывается в переменную `c` в Stack.

**В: Может ли существовать класс без объектов?**
**О:** Да. Например, если класс содержит только статические методы и поля (утилитарные классы, как `java.lang.Math`), мы можем использовать его функции, не создавая экземпляр через `new`.

** $\text{В: Если я присвою } car1 = car2, \text{ создастся ли новый объект?}$**
**О:** Нет. Создастся только новая ссылка, которая будет указывать на тот же самый объект в памяти. Оба имени теперь управляют одним и тем же состоянием.

# 🏛 Четыре столпа ООП

ООП — это не про создание сложных иерархий, а про управление сложностью кода. Эти четыре принципа позволяют писать код, который легко расширять и который трудно сломать.

### 1. Инкапсуляция (Encapsulation)
**Суть:** Это сокрытие внутренней реализации объекта и защита его состояния от прямого вмешательства извне. Мы объединяем данные (поля) и методы (поведение) в один юнит — класс, и ограничиваем доступ к данным.

*   **Как реализуется:** С помощью модификаторов доступа (`private`, `protected`, `public`) и методов доступа (геттеры/сеттеры).
*   **Зачем это нужно:** Чтобы гарантировать **целостность данных**. Если поле `age` публичное, любой может записать туда `-5`. Если поле `private`, а в сеттере есть проверка `if (value > 0)`, мы защитили объект от невалидного состояния.
*   **Нюанс (Senior level):** Инкапсуляция — это не просто "сделать всё приватным". Это про создание **интерфейса взаимодействия**. Твой класс должен показывать *что* он делает, но скрывать *как* он это делает. Если ты возвращаешь из геттера ссылку на мутабельный (изменяемый) объект (например, `Date` или `List`), ты нарушаешь инкапсуляцию, так как внешний код может изменить внутренности твоего объекта.

### 2. Наследование (Inheritance)
**Суть:** Механизм, позволяющий создать новый класс на основе уже существующего. Новый класс (подкласс/наследник) забирает себе свойства и методы родительского класса (суперкласса).

*   **Как реализуется:** Ключевое слово `extends`.
*   **Зачем это нужно:** Повторное использование кода (Code Reuse) и создание иерархии "is-a" (является). Например, `Dog` *is-a* `Animal`.
*   **Нюанс (Senior level):** Избегай глубоких иерархий наследования. Глубокое наследование — это ад для поддержки (изменил в дедушке — всё посыпалось у правнука). В современной разработке предпочитают **композицию** ("has-a") наследованию. Наследование должно использоваться только тогда, когда между классами есть четкая логическая связь "является".

### 3. Полиморфизм (Polymorphism)
**Суть:** Способность программы использовать объекты с одинаковым интерфейсом без информации о конкретном типе этого объекта. Буквально: "один интерфейс — много реализаций".

*   **Виды полиморфизма:**
    1.  **Статический (Compile-time):** Перегрузка методов (**Overloading**). Когда у тебя в одном классе есть методы `print(int i)` и `print(String s)`. Решение принимается на этапе компиляции.
    2.  **Динамический (Runtime):** Переопределение методов (**Overriding**). Когда мы вызываем метод у объекта типа `Animal`, но если там лежит реальный `Dog`, выполнится логика собаки. Решение принимается во время выполнения программы.
*   **Нюанс (Senior level):** Полиморфизм — это основа гибкости. Именно благодаря ему мы можем написать метод `process(Shape s)`, и ему будет всё равно, передадим мы туда `Circle` или `Square`. Ключевой момент здесь — **Upcasting** (приведение вверх по иерархии), когда мы приводим подкласс к типу суперкласса.

### 4. Абстракция (Abstraction)
**Суть:** Выделение только значимых характеристик объекта, отсекая всё второстепенное. Мы создаем модель, которая содержит только те детали, которые важны для текущей задачи.

*   **Как реализуется:** Через абстрактные классы (`abstract class`) и интерфейсы (`interface`).
*   **Зачем это нужно:** Снижение когнитивной нагрузки. Когда ты водишь машину, тебе не нужно знать, как работает впрыск топлива (это детали реализации), тебе достаточно абстракции — руля и педалей.
*   **Нюанс (Senior level):** Не путай абстракцию с инкапсуляцией. Инкапсуляция — это *скрытие* деталей внутри, а абстракция — это *проектирование* только важных деталей снаружи. Интерфейс — это высшая форма абстракции в Java: он говорит "что делать", но вообще не говорит "как".

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем разница между перегрузкой (Overloading) и переопределением (Overriding)?**
**О:** Перегрузка — это создание методов с одинаковым именем, но разными параметрами в одном классе (статический полиморфизм). Переопределение — это изменение логики метода родителя в классе-наследнике (динамический полиморфизм).

**В: Можно ли реализовать множественное наследование в Java?**
**О:** В Java нельзя наследоваться от нескольких *классов* (чтобы избежать "алмаза смерти" — Diamond Problem), но можно реализовывать множество *интерфейсов*. Это позволяет достичь эффекта множественного наследования поведения.

**В: Что важнее: Наследование или Композиция?**
**О:** Как Senior, я скажу: **Композиция**. Наследование создает жесткую связь между классами (сильная связанность). Композиция делает систему гибкой и модульной. Используй наследование только для связи "is-a", в остальных случаях — композицию.

**В: Может ли абстрактный класс иметь реализованные методы?**
**О:** Да, в отличие от интерфейсов (до Java 8), абстрактный класс может содержать как пустые (абстрактные) методы, так и методы с готовой логикой. Это позволяет задать "базовое поведение" для всех наследников.

# 2.1. Инкапсуляция (Encapsulation)

**Инкапсуляция** — это механизм сокрытия внутренней реализации объекта и защиты его состояния от прямого и некорректного вмешательства извне.

Представь капсулу с лекарством: ты знаешь, что она делает (лечит), но тебе не нужно знать химический состав порошка внутри или как именно молекулы взаимодействуют с рецепторами. Тебе доступен только интерфейс — «проглотить капсулу».

### Основные инструменты реализации в Java:

1.  **Модификаторы доступа:** Ограничивают видимость полей и методов.
2.  **Скрытие данных (Data Hiding):** Поля класса помечаются как `private`.
3.  **Публичный интерфейс:** Доступ к данным осуществляется только через специальные методы — **геттеры (getters)** и **сеттеры (setters)**.

### Уровни доступа (Access Modifiers)

| Модификатор | Класс | Пакет (package) | Наследники (subclasses) | Весь мир (world) |
| :--- | :---: | :---: | :---: | :---: |
| `private` | ✅ | ❌ | ❌ | ❌ |
| `default` (по умолчанию) | ✅ | ✅ | ❌ | ❌ |
| `protected` | ✅ | ✅ | ✅ | ❌ |
| `public` | ✅ | ✅ | ✅ | ✅ |

---

### Зачем это нужно на самом деле? (Senior Insights)

Многие думают, что инкапсуляция — это просто «сделать поля приватными». Это заблуждение. Настоящая цель — **контроль инвариантов**.

*   **Инвариант** — это правило, которое всегда должно быть истинным для объекта.
    * *Пример:* Возраст человека не может быть отрицательным. Если поле `age` публичное, любой может записать `-5`. Если есть сеттер `setAge(int age)`, мы можем вставить проверку: `if (age < 0) throw new IllegalArgumentException();`.
*   **Скрытие сложности:** Мы можем изменить внутреннюю логику (например, заменить тип хранения данных с `int` на `long`), не меняя код, который использует наш класс.
*   **Гибкость и поддержка:** Мы можем сделать поле «только для чтения» (ReadOnly), оставив только геттер без сеттера.

### ⚠️ Ловушка: "Утечка" инкапсуляции (Leaky Encapsulation)

Это то, на чем валятся на собеседованиях. Если твой геттер возвращает **ссылку на мутабельный (изменяемый) объект**, ты нарушил инкапмуляцию.

```java
public class User {
    private List<String> roles = new ArrayList<>();

    // ОПАСНО: Мы отдаем прямую ссылку на наш внутренний список!
    // Внешний код может вызвать user.getRoles().clear(), и данные внутри класса пропадут.
    public List<String> getRoles() {
        return roles; 
    }

    // ПРАВИЛЬНО (Defensive Copying): Возвращаем копию или неизменяемую обертку
    public List<String> getRolesSafe() {
        return Collections.unmodifiableList(roles);
    }
}
```

**В: В чем разница между Инкапсуляцией и Абстракцией?**
**О:** Это разные вещи. **Абстракция** — это *что* объект делает (выделение важных характеристик, например, интерфейс `Car`). **Инкапсуляция** — это *как* он это делает и как защищает свои внутренности (скрытие реализации двигателя внутри корпуса).

**В: Можно ли сказать, что инкапсуляция обеспечивает безопасность?**
**О:** В контексте логики программы — да. Она предотвращает повреждение состояния объекта некорректными данными. Но она не защищает от хакеров (через Reflection можно взломать `private`), она защищает от ошибок программиста.

**В: Зачем использовать `protected`, если можно всё сделать `private`?**
**О:** `protected` нужен, когда ты хочешь разрешить наследникам видеть внутренние детали реализации, но запретить их всем остальным. Это инструмент проектирования иерархий.

**В: Что такое "Defensive Copying" (Защитное копирование)?**
**О:** Это практика создания копии объекта при передаче его через геттер или конструктор, чтобы внешняя сторона не могла изменить внутреннее состояние твоего класса, манипулируя ссылками.

# 🧬 Наследование (Inheritance)

**Наследование** — это механизм, позволяющий создать новый класс (подкласс/наследник) на основе уже существующего (суперкласс/родитель). Это фундамент для повторного использования кода и реализации полиморфизма.

### 1. Суть концепции
Главное правило: между классами должна быть связь **"IS-A" (является)**.
*   `Dog IS-A Animal` — Наследование уместно.

*   `Car HAS-A Engine` — Это не наследование, это **композиция** (использование другого объекта).

### 2. Ключевые термины и синтаксис
*   **Superclass (Родитель):** Класс, с которого всё берется.
*   **Subclass (Потомок):** Класс, который расширяет функционал.
*   **`extends`**: Ключевое слово для создания связи.

```java
class Animal { // Суперкласс
    void eat() { System.out.println("Eating..."); }
}

class Dog extends Animal { // Подкласс
    void bark() { System.out.println("Woof!"); }
}
```

### 3. Модификаторы доступа (Важнейший нюанс!)
Наследование работает только с тем, что "видно" потомку:
*   `public`: Видно всем, наследуется без проблем.
*   `protected`: **Золотой стандарт для наследования.** Видно внутри пакета и во всех подклассах (даже если они в других пакетах).
*   `default` (package-private): Видно только внутри своего пакета. Если потомок в другом пакете — он не увидит это поле/метод.
*   `private`: **Не наследуется.** Потомок не имеет прямого доступа к приватным полям родителя. Но он может взаимодействовать с ними через `public/protected` геттеры и сеттеры.

### 4. Ключевые слова: `super` и `final`
*   **`super`**:
    *   `super()` — вызов конструктора родителя (обязательно должен быть первой строкой в конструкторе потомка).
    *   `super.method()` — вызов метода родителя, если ты его переопределил в потомке.
*   **`final`**:
    *   `final class`: Класс **нельзя** наследовать (например, класс `String`).
    *   `final method`: Метод **нельзя** переопределить в подклассах.

### 5. Переопределение методов (Method Overriding)
Это когда потомок меняет логику метода родителя.
**Правила "Senior-уровня":**
1.  **Сигнатура:** Имя, параметры и тип возвращаемого значения должны быть идентичны (или ковариантны — см. ниже).
2.  **Доступность:** Нельзя сужать уровень доступа. Если в родителе метод `protected`, в потомке он не может стать `private`.
    *Ковариантность:* Можно вернуть более специфичный тип (например, если родитель возвращает `Animal`, потомок может вернуть `Dog`).
3.  **Аннотация `@Override`**: Всегда используй её! Она заставит компилятор проверить, что ты действительно переопределяешь метод, а не просто опечатался в названии.

### 6. Ограничения Java (Почему нельзя множественное наследование?)
В Java класс может наследоваться **только от одного** класса (`extends` только один).
**Причина:** Проблема "Ромба" (Diamond Problem). Если бы мы наследовались от двух классов, у которых есть метод `doWork()`, Java не знала бы, какую реализацию выбрать.
*(Решение проблемы в Java — это Интерфейсы, но мы их пока не рассматриваем).*

### 💡 FAQ: Вопросы с собеседований

**В: Можно ли вызвать конструктор родителя из конструктора потомка?**
О: Да, через `super()`. Если ты его не напишешь явно, Java автоматически вставит вызов пустого конструктора родителя `super();` первой строкой. Но если у родителя нет дефолтного (пустого) конструктора, код не скомпилируется — тебе придется вызвать один из существующих через `super(args)`.

**В: В чем разница между Overriding и Overloading?**
О:
*   `Overriding` (Переопределение): Тот же метод, те же параметры, другой класс (наследование). Меняем поведение.
*   `Overloading` (Перегрузка): То же имя, но **другие параметры**, тот же класс. Создаем вариации метода.

**В: Что такое "затенение" (Hiding) статических методов?**
О: Если ты создашь статический метод с такой же сигнатурой в подклассе, это не будет переопределением (Polymorphism не работает со static). Это будет называться *hiding*. Вызов будет зависеть от типа ссылки, а не от реального объекта.

**В: Что лучше: Наследование или Композиция?**
О: Senior всегда ответит: **"Предпочитай композицию наследованию"** (Favor composition over inheritance). Наследование слишком сильно связывает классы (tight coupling). Если ты изменишь родителя, "сломаются" все потомки. Композиция более гибкая и безопасная.

# 🧬 Полиморфизм (Polymorphism)

**Полиморфизм** (от греч. "многоформность") — это способность программы использовать один и тот же интерфейс для работы с разными типами данных. В Java это означает, что мы можем работать с объектом подкласса, используя ссылку на его суперкласс, и при этом получать правильное, специфичное поведение.

В Java полиморфизм делится на два четких типа: **Статический** (Compile-time) и **Дискантинг/Динамический** (Runtime).

---

### 1. Статический полиморфизм (Compile-time Polymorphism)
Реализуется через **Перегрузку методов (Method Overloading)**.

*   **Суть:** В одном классе есть несколько методов с одинаковым именем, но **разными сигнатурами** (разное количество, типы или порядок аргументов).
*   **Как работает:** Решение о том, какой именно метод вызвать, принимает **компилятор** еще на этапе сборки кода. Он смотрит на переданные аргументы и "привязывает" вызов к нужному методу.

**Важные нюансы:**
*   Изменение только типа возвращаемого значения **не является** перегрузкой. Если сигнатуры (имена + параметры) идентичны, компилятор выдаст ошибку.
*   При перегрузке важно учитывать автоматическое приведение типов (например, если передать `int`, может сработать метод, принимающий `long`).

---

### 2. Динамический полиморфизм (Runtime Polymorphism)
Реализуется через **Переопределение методов (Method Overriding)**.

*   **Суть:** Подкласс предоставляет свою реализацию метода, который уже определен в его суперклассе или интерфейсе.
*   **Как работает:** Решение о том, какой метод вызвать, принимает **JVM (виртуальная машина)** во время выполнения программы. Она смотрит на **реальный тип объекта** в куче (Heap), а не на тип ссылки. Это называется *Dynamic Method Dispatch*.

**Пример механики:**
```java
Animal myDog = new Dog(); 
myDog.makeSound(); 
// Ссылка типа Animal, но объект типа Dog. 
// JVM увидит, что объект — Dog, и вызовет метод именно класса Dog.
```

**Важные нюансы (Senior level):**
*   **Upcasting (Восходящее приведение):** Безопасное приведение подкласса к суперклассу (`Animal a = new Dog()`). Происходит автоматически.
*   **Downcasting (Нисходящее приведение):** Приведение суперкласса к подклассу (`Dog d = (Dog) a`). Требует явного указания типа и может выбросить `ClassCastException`, если объект на самом деле не является тем, за кого себя выдает.
*   **Правила переопределения:**
    1.  Метод в подклассе не может быть "более строгим" по модификатору доступа (нельзя превратить `public` в `private`).
    2.  Метод не может иметь более узкого диапазона исключений (Checked Exceptions).
*   **Static/Final методы:** Их **нельзя переопределить**. Если ты напишешь метод с такой же сигнатурой в подклассе, это будет *Method Hiding* (сокрытие метода), а не полиморфизм.

---

### 💡 Резюме для запоминания
| Характеристика | Перегрузка (Overloading) | Переопределение (Overriding) |
| :--- | :--- | :--- |
| **Тип полиморфизма** | Статический (Compile-time) | Динамический (Runtime) |
| **Где происходит** | В одном классе | Между суперклассом и подклассом |
| **Сигнатура** | Должна отличаться | Должна быть идентичной |
| **Что решает** | Компилятор | JVM (в рантайме) |

---

### ❓ FAQ (Частые вопросы на интервью)

**В: В чем разница между Overloading и Overriding?**
**О:** Overloading — это создание нескольких методов с одним именем, но разными параметрами в одном классе (решается компилятором). Overriding — это изменение логики родительского метода в дочернем классе (решается JVM во время работы программы).

**В: Что произойдет, если мы переопределим метод, но сделаем его `private`?**
**О:** Это не будет переопределением. Вы получите ошибку компиляции или "сокрытие" метода, так как `private` методы не видны в подклассах и не могут быть переопределены.

**В: Можно ли переопределить `static` метод?**
**О:** Нет. Статические методы принадлежат классу, а не объекту. Если ты создашь такой же статический метод в подклассе, это называется **Method Hiding**. При вызове через ссылку на суперкласс выполнится метод суперкласса, что нарушает суть динамического полиморфизма.

**В: Зачем вообще нужен полиморфизм?**
**О:** Для гибкости и расширяемости (Open/Closed Principle). Мы можем писать код, работающий с абстрактным `Shape`, и нам будет всё равно, добавим мы завтра `Triangle` или `Hexagon` — старый код продолжит работать без изменений.

# 🧩 Тема: Абстракция (Abstraction)

### Что это такое простыми словами?
**Абстракция** — это процесс выделения самых важных характеристик объекта и отсечение всего лишнего.

Представь, что ты управляешь автомобилем. Тебе важно, что есть руль, педали и рычаг передач (это **интерфейс** управления). Тебе абсолютно не нужно знать, какой именно цикл впрыска топлива происходит в цилиндрах прямо сейчас (это **реализация**).

В программировании абстракция позволяет нам работать с объектом, не погружаясь в дебри того, как он устроен внутри. Мы взаимодействуем только с "публичным лицом" объекта.

---

### Как мы реализуем абстракцию в Java?
У нас есть два главных инструмента: **Абстрактные классы** и **Интерфейсы**.

#### 1. Абстрактный класс (`abstract class`)
Это "полуфабрикат". Это класс, который нельзя использовать для создания объектов (нельзя написать `new MyAbstractClass()`), но он служит шаблоном для других классов.

*   **Зачем:** Когда у тебя есть группа тесно связанных классов, которые имеют общую природу (отношение **is-a** / "является").
*   **Что может содержать:**
    *   Абстрактные методы (без тела, только сигнатура).
    *   Конкретные методы (с готовой логикой).
    *   Поля (состояние объекта).
    *   Конструкторы (да, они нужны для инициализации полей при создании наследника).

#### 2. Интерфейс (`interface`)
Это "контракт" или "способность". Он говорит: "Я не знаю, кто ты, но я гарантирую, что ты умеешь делать вот это".

*   **Зачем:** Когда мы хотим наделить разные, не связанные друг с другом классы общим поведением (отношение **can-do** / "умеет"). Например, и `Car`, и `Person` могут реализовать интерфейс `Movable` (двигаемый).
*   **Что может содержать:**
    *   Абстрактные методы (по умолчанию все методы в интерфейсе — абстрактные, если не указано иное).
    *   `default` методы (появились в Java 8, позволяют добавлять логику, не ломая старый код).
    *   `static` методы (утилитарная логика).
    *   Константы (`public static final`).

---

### ⚠️ Нюансы и "подводные камни" (Senior Level)

1.  **Абстрактный класс vs Интерфейс:** Это классический вопрос. Главное отличие — **состояние**. Абстрактный класс может иметь переменные экземпляра (поля), которые хранят состояние объекта. Интерфейс может содержать только константы.
2.  **Множественное наследование:** Класс может наследоваться только от **одного** абстрактного класса, но реализовывать **сколько угодно** интерфейсов. Это ключевой способ обхода ограничений Java.
3.  **Конструкторы в абстрактном классе:** Многие думают, что раз мы не можем создать объект абстрактного класса, то конструктора там быть не может. Это ошибка. Конструктор есть, и он вызывается через `super()` из конструктора наследника, чтобы инициализировать общие поля.
4.  **Интерфейсы — это не только "пустые методы":** С приходом Java 8 и Java 9, интерфейсы стали мощнее. Теперь в них можно писать `default` методы (с логикой) и даже `private` методы (для внутренней помощи другим методам интерфейса). Но суть остается прежней: интерфейс — это описание поведения.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли объявить метод как `final` в абстрактном классе?**
**О:** Да, можно. И это часто делается специально, чтобы запретить наследникам менять критически важную логику, при этом позволяя им реализовывать другие абстрактные методы.

**В: Может ли абстрактный класс не иметь ни одного абстрактного метода?**
**О:** Да. Вы можете пометить класс как `abstract` просто потому, что не хотите, чтобы кто-то создавал его экземпляры напрямую.

**В: В чем разница между "is-a" и "can-do"?**
**О:**
*   `is-a` (является) — это про иерархию сущностей (Собака *является* Животным $\to$ используем абстрактный класс).
*   `can-do` (умеет) $\to$ это про функциональность (Самолет *умеет* летать, Птица *умеет* летать $\to$ используем интерфейс `Flyable`).

**В: Что произойдет, если класс реализует интерфейс, но не реализует все его методы?**
**О:** Этот класс сам обязан быть объявлен как `abstract`. Если он не `abstract`, компилятор выдаст ошибку.

# 🛠 Тема: Конструкторы (Constructors)

### 1. Что это такое?
**Конструктор** — это специальный блок кода, который вызывается в момент создания объекта (`new MyClass()`). Его единственная цель — **инициализировать** состояние объекта (задать начальные значения полям).

**Главные правила:**
*   Имя конструктора **всегда** совпадает с именем класса.
*   У конструктора **нет типа возвращаемого значения** (даже `void`). Если напишешь `public void MyClass()`, Java решит, что это обычный метод, а не конструктор.

---

### 2. Виды конструкторов

1.  **Конструктор по умолчанию (Default Constructor):**
    Если ты **не написал ни одного** своего конструктора, компилятор Java сам добавит пустой конструктор без параметров. Он просто инициализирует поля значениями по умолчанию (`0`, `null`, `false`).
    *⚠️ Ловушка:* Как только ты написал **хотя бы один** свой конструктор (например, с параметрами), дефолтный исчезает. Если тебе он понадобится — пиши его вручную.

2.  **Конструктор без параметров (No-arg Constructor):**
    Ты написал его сам, но не передаешь в него ничего. Используется для создания "пустого" объекта.

3.  **Конструтор с параметрами (Parameterized Constructor):**
    Позволяет передать данные в объект сразу в момент его рождения. Это делает создание объектов более предсказуемым и безопасным.

---

### 3. Ключевые слова: `this` и `super`

Это база, на которой строится цепочка вызовов (Constructor Chaining).

*   **`this()`**: Вызов другого конструктора **того же самого** класса. Позволяет избежать дублирования кода (DRY).
*   **`super()`**: Вызов конструктора **родительского** класса.

**⚠️ Золотое правило:**
Вызов `this()` или `super()` **обязательно** должен быть самой первой строчкой в теле конструктора. Ты не можешь сначала что-то вычислить, а потом вызвать конструктор. Из-за этого ты не можешь использовать `this()` и `super()` одновременно в одном конструкторе (оба претендуют на первую строчку).

---

### 4. Наследование и конструкторы
Запомни: **Конструкторы не наследуются.**
Когда ты создаешь объект дочернего класса (`Child`), Java сначала идет в родительский класс (`Parent`) и выполняет его конструктор, а уже потом выполняет конструктор `Child`.

Если в родителе нет конструктора без параметров (а ты написал только параметризованный), то в дочернем классе тебе **придется** явно вызвать `super(args)` в первой строке, иначе программа не скомпилируется.

---

### 5. Модификаторы доступа
*   `public`: Конструктор доступен всем.
*   `protected`: Доступен внутри пакета и в подклассах.
*   `private`: Конструктор виден только внутри этого класса. **Это основа паттерна Singleton** (нельзя создать объект извне) и утилитных классов (как `java.lang.Math`).

---

### 💡 Нюансы (Senior Tips)
1.  **Конструктор не может быть `final`, `static` или `abstract`.**
    *   `final` — бессмысленно, так как конструкторы не наследуются.
    *   `static` — конструктор принадлежит объекту, а `static` — классу. Это логический конфликт.
    *   `abstract` — конструктор должен содержать реализацию, иначе объект нельзя будет инициализировать.
2.  **Инициализация полей:** Поля класса инициализируются **до** того, как выполнится код в теле конструктора.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что произойдет, если я создам свой конструктор с параметрами, но забуду написать пустой? А потом попытаюсь вызвать `new MyClass()`?**
**О:** Ошибка компиляции. Как только ты создал свой конструктор, "подарок" от Java в виде дефолтного конструктора аннулируется.

**В: Можно ли вызвать `this()` и `super()` в одном конструкторе?**
**О:** Нет. Оба вызова должны быть первой строкой. Выбор стоит жестко: либо мы вызываем другой конструктор того же класса, либо конструктор родителя.

**В: Зачем делать конструктор `private`?**
**О:** Для контроля над процессом создания объектов. Например, в паттерне *Singleton* (чтобы нельзя было создать вторую копию) или в утилитных классах (чтобы никто не создавал объект из класса, где есть только статические методы).

**В: Что такое "Constructor Chaining"?**
**О:** Это процесс, когда один конструктор вызывает другой (через `this` или `super`), выстраивая цепочку от самого глубокого подкласса до самого базового класса `Object`. Это гарантирует, что каждый уровень иерархии правильно инициализировал свои поля.

# 🧠 Шпаргалка: Ключевые слова в Java (Keywords)

**Ключевые слова** — это зарезервированные слова, которые имеют специальный смысл для компилятора. Ты не можешь использовать их как имена переменных, методов или классов.

Мы разделим их на логические группы по их роли в языке.

### 1. Модификаторы доступа (Access Modifiers)
Определяют «видимость» твоего кода. Это фундамент инкапсуляции.

*   **`public`**: Виден всем: внутри класса, в подклассах и в других пакетах.
*   **`protected`**: Виден внутри своего пакета + наследникам (даже если они в другом пакете).
*   **`private`**: Самый строгий уровень. Виден **только** внутри того же самого класса.
*   **`default` (package-private)**: *Технически это не ключевое слово, а отсутствие модификатора.* Если ты ничего не написал, поле/метод будет доступен только внутри своего пакета.

> **Senior Nuance:** Помни про иерархию. При переопределении метода (`@Override`) ты не можешь понижать уровень доступа (например, из `public` сделать `private`). Это нарушит принцип полиморфизма.

### ary 2. Модификаторы состояния и поведения
Эти слова меняют «свойства» классов, методов или переменных.

*   **`static`**: Привязывает поле или метод к **классу**, а не к объекту. Статические методы можно вызывать без создания экземпляра класса.
*   **`final`**: Слово-«запрет».
    *   Для **переменной**: делает её константой (значение нельзя изменить).
    *   Для **метода**: запрещает его переопределение (`@Override`).
    *   Для **класса**: запрещает наследование от него.
*   **`abstract`**: Используется для создания «чертежей». Абстрактный класс нельзя превратить в объект (нельзя сделать `new`), а абстрактный метод не имеет тела.
*   **`transient`**: Говорит JVM: «Не включай это поле в процесс сериализации». Полезно для хранения временных данных или паролей, которые не должны сохраняться в файл/сеть.

### 3. Управление потоком выполнения (Control Flow)
Инструменты для логики «если — то» и циклов.

*   **Условия**: `if`, `else`, `switch`, `case`, `default`.
    *   *Java 21 Note:* В современном Java `switch` стал мощнее (Switch Expressions), он может возвращать значение.
*   ert **Циклы**: `for`, `while`, `do-while`.
*   **Управление циклом**:
    *   `break`: Полный выход из цикла или блока `switch`.
    *   `continue`: Пропуск текущей итерации и переход к следующей.
*   **Передача управления**: `return` (выход из метода с результатом).

### 4. Работа с объектами и типами
*   **`new`**: Оператор выделения памяти в Heap (куче) под новый объект.
*   **`this`**: Ссылка на «текущий» экземпляр класса (помогает отличить поле класса от параметра метода).
*   **`super`**: Ссылка на родительский класс (вызов конструктора или метода предка).
*   **`instanceof`**: Оператор проверки типа.
    *   *Java 21 Note:* Используй **Pattern Matching for instanceof**. Теперь не нужно делать явное приведение типов: `if (obj instanceof String s) { ... }`.

### 5. Обработка исключений (Exception Handling)
Механизм «предохранителей» в коде.

*   **`try`**: Блок кода, который мы «опасаемся» и за которым следим.
*   **`catch`**: Блок, который сработает, если внутри `try` произошла ошибка.
*   **`finally`**: Блок, который выполнится **всегда**, независимо от того, была ошибка или нет (идеально для закрытия ресурсов).
*   **`throw`**: Команда «выбросить» конкретное исключение прямо сейчас.
*   **`throws`**: Предупреждение в сигнатуре метода: «Внимание, этот метод может быть опасен и выкинуть вот такие ошибки».

### ❓ FAQ (Частые вопросы на собеседованиях)

**1. В чем разница между `final`, `finally` и `finalize`?**
Это классический "троллинг" на интервью.
*   `final`: Модификатор (константа, неизменяемый метод/класс).
*   `finally`: Блок в конструкции `try-catch`.
*   `finalize`: Метод класса `Object`, который вызывается перед удалением объекта сборщиком мусора (сейчас считается **deprecated** и использовать его не стоит).

**2. Можно ли использовать `static` метод в интерфейсе?**
Да, начиная с Java 8. Статические методы в интерфейсах полезны для утилитных функций, которые относятся к интерфейсу, но не требуют реализации конкретным классом.

**3. Что будет, если поле помечено как `final`, но это объект (например, `List`)? Можно ли менять содержимое списка?**
Да, можно. Ключевое слово `final` защищает только **ссылку**. Ты не можешь переназначить переменную на другой список (`list = new ArrayList()`), но ты можешь добавлять или удалять элементы внутри самого списка.

**4. Чем `throw` отличается от `throws`?**
`throw` — это действие (мы кидаем ошибку), а `throws` — это декларация (мы предупреждаем, что ошибка может случиться).

# 🧵 Тема: Класс String

**String** — это, пожалуй, самый используемый класс в Java. Если ты понимаешь, как он устроен, ты понимаешь половину основ управления памятью.

### 1. Главная характеристика: Immutability (Неизменяемость)
Объекты класса `String` являются **immutable**. Это значит, что после того, как строка создана, её содержимое изменить нельзя. Любая операция, которая «меняет» строку (`replace`, `toUpperCase`, `substring`), на самом деле не меняет старую строку, а **создает новую** в памяти.

**Почему это важно (Senior нюансы):**
*   **Безопасность:** Строки часто используются для хранения паролей, URL-адресов и путей к файлам. Если бы строки были изменяемы, злоумышленник мог бы изменить значение переменной в процессе выполнения программы.
*   **String Pool (Кэширование):** Благодаря неизменяемости, Java может экономить память, используя один и тот тот же экземпляр строки для разных переменных.
*   **Thread-safety:** Строки можно безопасно передавать между потоками без синхронизации — они не могут измениться «за спиной» у другого потока.
*   **HashCode:** Поскольку содержимое не меняется, `hashCode` вычисляется один раз при создании и кэшируется. Это делает строки идеальными ключами для `HashMap`.

### 2. Память: String Pool (Пул строк)
В Java есть специальная область в Heap (куче), называемая **String Constant Pool**.

*   Когда ты пишешь `String s = "Java";` (литерал), JVM сначала проверяет, есть ли уже строка `"Java"` в пуле. Если есть — возвращает ссылку на существующую. Если нет — создает новую в путе.
*   Когда ты пишешь `String s = new String("Java");`, ты принудительно создаешь **новый** объект в обычной куче (Heap), даже если такая строка уже есть в пуле.

### 3. Сравнение: `==` vs `.equals()`
Это классика, на которой валятся новички.
*   **`==`** — сравнивает **ссылки** (адреса в памяти). Проверяет, указывают ли две переменные на один и тот же объект.
*   **`.equals()`** — сравнивает **содержимое** (последовательность символов). В классе `String` метод `.equals()` переопределен именно для сравнения текста.

### 4. Альтернативы: StringBuilder и StringBuffer
Если тебе нужно собрать строку из 10 000 частей в цикле, использование `String += "part"` убьет твою производительность (создаст 10 000 объектов в памяти).

*   **`StringBuilder`**: Самый быстрый. Используется для конкатенации строк в одном потоке. Не потокобезопасен.
*   **`StringBuffer`**: Старый, «дедушкин» вариант. Потокобезопасен (все методы `synchronized`), но из-за накладных расходов на синхронизацию работает медленнее.

### 5. Современные нюансы (Java 9+)
Раньше строки хранились как массив `char[]` (2 байта на символ, UTF-16). Начиная с Java 9, ввели **Compact Strings**. Теперь внутри используется `byte[]`. Если строка содержит только символы Latin-1 (английский, цифры), она занимает в два раза меньше памяти. Это крутое оптимизационное улучшение.

### 💡 FAQ (Частые вопросы на интервью)

**В: Что произойдет с памятью, если я буду делать `str += "abc"` в цикле 1000 раз?**
**О:** Произойдет лавинообразное создание объектов. На каждой итерации создается новая строка, а старая становится мусором (garbage), который потом должен будет удалять Garbage Collector. Это приведет к нагрузке на CPU и частым паузам GC. Используй `StringBuilder`.

**В: В чем разница между `isEmpty()` и `isBlank()`? (Java 11+)**
**О:**
*   `isEmpty()` возвращает `true`, если длина строки равна 0 (`""`).
*   `isBlank()` возвращает `true`, если строка пустая ИЛИ состоит только из пробельных символов (`"  "`).

**В: Можно ли сделать String потокобезопасным, если он и так immutable?**
**О:** Да, сам класс `String` уже безопасен. Но важно помнить про ссылку на него. Если переменная `String s` не помечена как `final`, другой поток может переназначить её на другую строку. Сама строка — неизменяема, но ссылка на неё — нет.

**В: Что делает метод `.intern()`?**
**О:** Он принудительно перемещает (или проверяет наличие) строку в String Pool. Если такая строка уже есть в пуле, метод вернет ссылку на неё. Это полезно для экономии памяти при работе с огромным количеством дублирующихся строк.

# 🧵 Тема: Методы класса `String`

Прежде чем перейдем к списку, запомни базу: **`String` — это immutable (неизменяемый) объект**. Любой метод, который якобы "изменяет" строку, на самом деле не меняет старую, а создает и возвращает **новый** объект в памяти. Это критически важно для понимания работы String Pool.

### 1. Поиск и проверка содержимого
Эти методы отвечают на вопросы: «Что внутри?», «Где это находится?» и «Начинается ли строка с...?».

*   `contains(CharSequence s)` — проверяет, есть ли подстрока в строке. Возвращает `boolean`.
*   `startsWith(String prefix)` / `endsWith(String suffix)` — проверка начала или конца строки. Очень полезно при парсинге файлов или протоколов.
*   `indexOf(String str)` / `lastIndexOf(String str)` — возвращают индекс первого/последнего вхождения подстроки. Если не нашли — возвращают `-1`.
    *   *Нюанс:* Можно передавать и `char`, и `String`.
*   `isEmpty()` — проверяет, является ли длина строки равной `0`. (Строка `""` — пустая).
*   `isBlank()` (появился в Java 11) — проверяет, пуста ли строка или состоит **только из пробельных символов** (пробелы, табы, переносы строк).
    *   *Senior Tip:* Всегда используй `isBlank()`, если хочешь проверить, ввел ли пользователь реальный текст, а не просто наставил пробелов.

### 2. Извлечение и трансформация
Методы, которые «режут» или «переделывают» строку. Помни: каждый из них создает новый объект.

*   `substring(int beginIndex, int endIndex)` — вырезает кусок строки.
    *   *Важно:* `beginIndex` включается, а `endIndex` — **нет**. (Принцип $[start, end)$).
*   `toLowerCase()` / `toUpperCase()` — перевод в нижний/верхний регистр. Будь осторожен с локалями (в турецком языке есть нюансы с буквой `i`).
*   `trim()` — удаляет все пробельные символы (ASCII) в начале и в конце строки.
*   `strip()` (Java 11+) — современная замена `trim()`. В отличие от `trim`, он понимает Unicode-пробелы. Если работаешь с международными текстами, используй `strip()`.
*   `replace(char oldChar, char newChar)` / `replace(CharSequence target, CharSequence replacement)` — заменяет старые символы/подстроки на новые.
*   `replaceAll(String regex, String replacement)` — мощный метод, использует **регулярные выражения**. Позволяет делать сложные замены (например, «удалить все цифры»).

### 3. Разделение и соединение
Инструменты для работы со списками строк.

*   `split(String regex)` — разбивает строку на массив `String[]` по разделителю (используется регулярка).
    *   *Нюанс:* Если разделитель — спецсимвол регулярки (например, `.`, `|`, `*`), его нужно экранировать: `split("\\.")`.
*   `String.join(CharSequence delimiter, Iterable elements)` — статический метод. Соединяет элементы (из списка или массива) в одну строку, вставляя разделитель между ними. Очень удобно для формирования CSV-строк.

### 4. Сравнение
Самая частая зона ошибок.

*   `equals(Object obj)` — сравнивает **содержимое** строк. Это то, что тебе нужно в 99% случаев.
*   `equalsIgnoreCase(String another)` — то же самое, но игнорирует регистр.
*   `compareTo(String another)` — лексикографическое сравнение (как в словаре). Возвращает `0`, если строки равны, отрицательное число, если текущая строка "меньше", и положительное, если "больше". Используется для сортировки.

### 🚩 FAQ: Часто задаваемые вопросы на собеседовании

**В: В чем разница между `==` и `.equals()` при работе со строками?**
**О:** `==` сравнивает **ссылки** (адреса в памяти). Он проверяет, указывают ли две переменные на один и тот же объект. `.equals()` сравнивает **значения** (последовательность символов). В Java Core это классический вопрос на понимание работы ссылочных типов.

**В: Что будет, если вызвать `substring(5, 2)`?**
**О:** Выбросится исключение `StringIndexOutOfBoundsException`, так как начальный индекс не может быть больше конечного.

**В: В чем разница между `isEmpty()` и `isBlank()`?**
**О:** Для строки `"  "` (два пробела):
`isEmpty()` вернет `true` (так как длина 2, а не 0), но это не совсем верно... стоп, `isEmpty()` вернет `false`, потому что символы есть.
`isBlank()` вернет `true`, так как внутри только пустота (пробелы).
*Поправка для ясности:* `""` — оба вернут `true`. `" "` — `isEmpty` даст `false`, а `isBlank` даст `true`.

**В: Почему String считается Immutable? И в чем профит?**
**О:** Потому что после создания объект нельзя изменить.
*Профиты:*
1. **Безопасность (Security):** Строки используются как ключи в Map и параметры соединения с БД. Если бы их можно было изменить, злоумышленник мог бы подменить путь к файлу или пароль.
2. **String Pool:** Экономия памяти. Несколько переменных могут ссылаться на один объект в пуле.
3. **Потокобезопасность (Thread-safety):** Строки можно безопасно использовать в многопоточной среде без синхронизации, так как их состояние не изменится.

# 🛠 Шпаргалка: StringBuilder vs StringBuffer

### 1. Суть проблемы (The "Why")
В Java класс `String` является **immutable** (неизменяемым). Любая операция над строкой (`concat`, `replace`, `toUpperCase`) не меняет старую строку, а создает в памяти **новый объект**.

Если ты делаешь конкатенацию в цикле на 10 000 итераций:
```java
String s = "";
for (int i = 0; i < 10000; i++) {
    s += i; // Ужас! Создается 10 000 промежуточных объектов String
}
```
Это создает огромную нагрузку на Heap и Garbage Collector. Для решения этой проблемы существуют **mutable** (изменяемые) классы: `StringBuilder` и `StringBuffer`. Они работают с одним и тем же буфером (массивом символов), просто расширяя его при необходимости.

---

### 2. Сравнение: StringBuilder vs StringBuffer

| Характеристика | `String` | `StringBuilder` | `StringBuffer` |
| :--- | :--- | :--- | :--- |
| **Изменяемость** | Immutable (нельзя менять) | Mutable (можно менять) | Mutable (можно менять) |
| **Потокобезопасность** | Да (за счет immutability) | **Нет** (не синхронизирован) | **Да** (все методы `synchronized`) |
</thead>
| **Производительность** | Низкая (при частых изменениях) | **Максимальная** | Ниже (из-за накладных расходов на sync) |

**Senior Tip:** В 99% современной разработки используется `StringBuilder`. `StringBuffer` — это наследие старых времен, когда многопоточность была повсеместна в манипуляциях со строками. Если у тебя нет конкретной задачи делить один и тот же экземпляр билдера между разными потоками, забудь про `StringBuffer`.

---

### 3. Внутреннее устройство (Under the hood)
Оба класса внутри используют массив (в современных Java это `byte[]` с использованием кодировки Latin1 или UTF-16).

*   **Capacity vs Length:**
    *   `length()` — сколько символов реально в строке сейчас.
    *   `capacity()` — размер выделенного массива в памяти.
*   **Алгоритм расширения:** Когда массив заполняется, Java создает новый массив большего размера (обычно `old_capacity * 2 + 2`) и копирует туда старые данные. Это дорогая операция.
*   **Оптимизация:** Если ты заранее знаешь, что в строке будет 1000 символов, всегда инициализируй билдер с нужным размером: `new StringBuilder(1000)`. Это избавит от лишних пересозданий массива.

---

### 4. Основные методы
*   `.append(value)` — добавляет данные в конец (умеет принимать почти всё: int, double, Object и т.д.).
*   `.insert(offset, value)` — вставляет данные в указанную позицию.
*   `.delete(start, end)` — удаляет диапазон символов.
*   `.reverse()` — разворачивает строку задом наперед (часто спрашивают на собесах).
*   `.setLength(0)` — **Хак:** быстрый способ очистить билдер для повторного использования без создания нового объекта.

### ❓ FAQ (Частые вопросы на интервью)

**В: Что будет, если в цикле использовать `String s += "a"`, а что если `StringBuilder.append("a")`?**
**О:** В первом случае сложность будет $O(n^2)$, так как на каждой итерации происходит копирование всей предыдущей строки. Во втором случае сложность $O(n)$, так как мы просто дописываем элемент в конец существующего массива.

**В: Является ли `StringBuffer` потокобезопасным?**
**О:** Да, его методы помечены ключевым словом `synchronized`. Это значит, что если два потока одновременно вызовут `.append()`, они не испортят внутренний массив. Но это же делает его медленнее.

** **В: Можно ли использовать `StringBuilder` в многопоточной среде?**
**О:** Можно, но опасно. Если один поток читает строку через `.toString()`, а другой в этот момент делает `.append()`, ты можешь получить неконсистентные данные или даже ошибки индексации. Но если билдер создается внутри метода (локальная переменная), он по определению принадлежит только одному потоку, и `StringBuilder` — идеальный выбор.

**В: Как работает `String.concat()`? Это то же самое, что `StringBuilder`?**
**О:** Под капотом `String.concat()` создает новый `String` и копирует туда данные. Для простых операций (склеить две строки) это ок. Для циклов — категорически нет.

# 🧠 Шпаргалка: Класс `Object`

**`java.lang.Object`** — это корень всей иерархии классов в Java. Буквально любой класс, который ты создаешь (если не указано иное), автоматически наследуется от `Object`. Это значит, что каждый объект в Java обладает набором базовых свойств и методов.

---

### 1. Основные методы

#### `toString()`
*   **Что делает:** Возвращает строковое представление объекта.
*   **По умолчанию:** Выводит `ИмяКласса@хэш_код_в_16ричной_системе`.
*   **Нюанс (Senior Tip):** Всегда переопределяй его в своих классах (DTO, Entity). Это сэкономит тебе часы при дебаге и логировании. Хороший `toString()` должен показывать значимые поля объекта.

#### `equals(Object obj)`
*   **Что делает:** Проверяет объекты на «логическое равенство».
*   **`==` vs `.equals()`:**
    *   `==` сравнивает **ссылки** (указывают ли две переменные на одну и ту же область памяти).
    *   `.equals()` проверяет **содержимое** (согласно твоей логике).
*   **Контракт `equals` (Критически важно!):** Если ты переопределяешь `equals`, ты обязан соблюдать правила:
    1.  **Рефлексивность:** `x.equals(x)` всегда `true`.
        те `x.equals(y)` $\implies$ `y.equals(x)`.
    3.  **Транзитивность:** Если `x=y` и `y=z`, то `x=z`.
    4.  **Согласованность:** Результат не должен меняться, если поля объекта не менялись.
    5.  **Проверка на null:** `x.equals(null)` всегда `false`.

#### `hashCode()`
*   **Что делает:** Возвращает целое число (`int`), которое является «цифровым отпечатком» объекта.
*   **Зачем нужен:** Используется в хэш-таблицах (например, `HashMap`, `HashSet`) для быстрого поиска объекта по «корзинам» (buckets).
*   **Связь с `equals` (Золотое правило):**
    > **Если два объекта равны по `equals()`, их `hashCode()` ОБЯЗАН быть одинаковым.**
    Если ты нарушишь это правило, твой объект «потеряется» в `HashMap`: ты положишь его под одним ключом, а найти не сможешь, потому что поиск пойдет в другую корзину.

#### `getClass()`
*   **Что делает:** Возвращает объект типа `Class`, который содержит метаданные о текущем классе (имя, методы, поля). Это база для Reflection API.

#### `clone()`
*   **Что делает:** Создает копию объекта.
*   **Нюанс:** Чтобы метод работал, класс должен реализовывать интерфейс-маркер `Cloneable`. Если не реализовать — получишь `CloneNotSupportedException`.
*   **Shallow vs Deep Copy:**
    *   *Shallow (поверхностное):* Копируются значения полей. Если поле — ссылка на другой объект, скопируется только адрес. Оба объекта будут указывать на один и тот же внутренний объект.
    *   *Deep (глубокое):* Нужно вручную копировать все вложенные объекты.

#### `wait()`, `notify()`, `notifyAll()`
*   **Что делают:** Инструменты для взаимодействия потоков (хотя мы не изучаем Concurrency глубоко, знать их суть надо). Позволяют одному потоку ждать сигнала от другого.
*   **Важно:** Вызывать можно **только** внутри блока `synchronized`.

#### `finalize()` — **DEPRECATED**
*   **Что делает:** Метод, вызываемый перед тем, как GC (Garbage Collector) удалит объект.
*   **Senior Tip:** Забудь про него. Он не гарантирует выполнение, замедляет работу GC и считается плохой практиткой. Используй `try-with-resources` и интерфейс `AutoCloseable`.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что будет, если переопределить `equals()`, но не переопределить `hashCode()`?**
**О:** Это приведет к нарушению контракта. В `HashMap` ты сможешь положить объект, но при попытке достать его по точно такому же объекту (логически равному), ты его не найдешь, так как хэш-коды будут разными и поиск уйдет в другую корзину.

**В: Можно ли добавить новый метод в класс `Object`?**
**О:** Нет, методы класса `Object` определены в JDK и их нельзя изменить или расширить (сам класс `Object` является `final`).

**В: В чем разница между `==` и `equals()` для строк?**
**О:** `==` проверяет, являются ли две переменные ссылками на один и тот же объект в памяти. `.equals()` (в классе `String`) сравнивает последовательность символов внутри строк.

**В: Что такое "Shallow Copy" (поверхностное копирование)?**
**О:** Это когда при копировании объекта создаются новые ячейки для примитивов, но для ссылочных типов (объектов) просто копируются адреса. В итоге и оригинал, и копия смотрят на одни и те же вложенные объекты.

# 🧠 Шпаргалка: Критически важные методы (Object Class)

В Java каждый класс (даже если ты его не писал) является наследником класса `java.lang.Object`. Это значит, что у каждого объекта есть набор базовых методов. Понимание этих методов — это фундамент понимания того, как объекты взаимодействуют друг с другом.

### 1. `equals(Object obj)`
Этот метод отвечает на вопрос: **"Являются ли два объекта логически одинаковыми?"**.

*   **`==` vs `.equals()`:** Это классика. `==` сравнивает **ссылки** (адреса в памяти), а `.equals()` предназначен для сравнения **содержимого** (логики).
*   **Контракт `equals` (обязательно к соблюдению!):**
    1.  **Рефлексивность:** `x.equals(x)` всегда `true`.
    2.  **Симметричность:** Если `x.equals(y)`, то и `y.equals(x)`.
    3.  **Транзитивность:** Если `x.equals(y)` и `y.equals(z)`, то `x.equals(z)`.
    4.  **Согласованность (Consistency):** Результат не должен меняться, если объект не изменился.
    5.  **Проверка на null:** `x.equals(null)` всегда должно быть `false`.

> **Senior Tip:** При переопределении `equals` всегда проверяй тип объекта через `instanceof` или `getClass()`, и первым делом делай проверку на `null`.

### 2. `hashCode()`
Метод возвращает целое число (`int`), которое является "цифровым отпечатком" объекта.

*   **Зачем это нужно:** Для быстрого поиска объектов в хеш-таблицах (хотя мы не разбираем Collections, принцип работы алгоритма зависит именно от этого метода).
*   **Золотое правило (Связь с equals):**
    > **Если `a.equals(b) == true`, то `a.hashCode()` ОБЯЗАТЕЛЬНО должен быть равен `b.hashCode()`.**
*   **Обратное неверно:** Если хэш-коды равны, это НЕ значит, что объекты одинаковы (это называется **коллизия**).

> **Senior Tip:** Никогда не переопределяй `equals` без переопределения `hashCode`. Ты сломаешь логику поиска объектов. Хорошая формула для хэша — использовать поля, участвующие в `equals`, и комбинировать их (например, через `Objects.hash(field1, field2)`).

### 3. `toString()`
Метод возвращает строковое представление объекта.

*   **По умолчанию:** Возвращает `ИмяКласса@hex_hashcode` (например, `User@15db9742`). Это бесполезно для отладки.
*   **Зачем переопределять:** Чтобы при логировании или выводе в консоль ты видел реальные данные объекта (`User{id=1, name='Ivan'}`), а не его адрес в памяти.

### 4. `getClass()`
Возвращает объект типа `Class`, который представляет текущий класс объекта во время выполнения (Runtime).

*   **Суть:** Это способ узнать, "кто ты такой" на самом деле. Позволяет проверить точную принадлежность к классу.

### 5. `clone()`
Метод для создания копии объекта.

*   **Проблема:** Метод считается "проблемным" и часто избегается в современной разработке. Он требует реализации интерфейса `Cloneable`, иначе выкинет `CloneNotSupportedException`.
*   **Поверхностное vs Глубокое копирование (Shallow vs Deep Copy):**
    *   **Shallow Copy:** Копируются только поля. Если поле — это ссылка на другой объект, то в копии будет та же самая ссылка. Изменишь объект внутри копии — изменится и в оригинале.
        s   *   **Deep Copy:** Создаются полные независимые копии всех вложенных объектов.

> **Senior Tip:** Вместо `clone()` лучше использовать **Copy Constructor** (конструктор копирования) — это чище, безопаснее и понятнее.

### ❓ FAQ (Частые вопросы на интервью)

**В: Что будет, если `equals` переопределить, а `hashCode` — нет?**
**О:** Ты нарушишь контракт. Если два объекта "равны" по логике, но имеют разные хэш-коды, системы, использующие хэширование (например, для кэширования), не смогут найти твой объект, даже если он там есть. Это приведет к трудноуловимым багам.

**В: В чем разница между `instanceof` и `getClass() == ...` при проверке типа в `equals`?**
**О:** `instanceof` допускает наследование (вернет `true`, если объект — подкласс). `getClass()` проверяет строгое соответствие классов. Выбор зависит от того, хочешь ли ты, чтобы твои подклассы считались равными базовому классу.

**В: Что такое коллизия хэш-функции?**
**О:** Это ситуация, когда два разных объекта (по результатам `equals`) выдают один и тот же `hashCode`. Это не ошибка, это нормальная ситуация, но чем больше коллизий, тем медленнее работает поиск.

**В: Можно ли сделать `hashCode` константой (всегда возвращать 42)?**
**О:** Технически — да, программа не упадет. Но это убьет производительность всех хеш-структур, превратив поиск из $O(1)$ в $O(n)$, так как все объекты попадут в одну "корзину".

# ⚠️ Типы исключений в Java

Вся иерархия делится на две большие ветви: **Error** и **Exception**.

Это "катастрофы", которые происходят на уровне самой виртуальной машины или ресурсов системы.
*   **Суть:** Их **не нужно** (и практически невозможно) обрабатывать программно. Если случился `Error`, программа обычно просто "умирает".

*   **Нюанс:** Пытаться поймать `Error` в `catch` — это плохой тон и признак непрофессионализма.

### 2. Exception (Исключения уровня приложения)
Это события, которые происходят внутри твоей программы. Их **нужно** обрабатывать или хотя бы знать о них. Эта ветвь делится на две критически важные подгруппы:

#### А) Checked Exceptions (Проверяемые исключения)
Это "контрактные" ошибки. Компилятор Java — строгий надзиратель, и он заставляет тебя обработать их еще на этапе написания кода.
*   **Суть:** Это ситуации, которые зависят от внешних факторов (сеть, файловая система, база данных). Программист не может гарантировать, что файл *обязательно* будет существовать.
*   **Правило:** Если метод выбрасывает `Checked Exception`, ты **обязан** либо обернуть его в `try-catch`, либо объявить этот исключение в сигнатуре метода через ключевое слово `throws`.
*   **Примеры:** `IOException`, `SQLException`, `ClassNotFoundException`.

#### Б) Unchecked Exceptions (Непроверяемые / RuntimeException)
Это ошибки логики программиста. Компилятор на них "закрывает глаза".
*   **Суть:** Это ошибки, которые можно было предотвратить правильным написанием кода (проверкой на `null`, проверкой границ массива и т.д.). Они возникают во время выполнения программы (`Runtime`).
*   **Правило:** Их не нужно объявлять в `throws`. Хороший код должен стараться их избегать через проверки (defensive programming).
*   **Примеры:**
    *   `NullPointerException` (обращение к пустому объекту).
    *   `ArrayIndexOutOfBoundsException` (выход за пределы массива).
    *   `ArithmeticException` (деление на ноль).

2.  **Проблема "загрязнения" кода:** В современных фреймворках (например, Spring) наблюдается тренд на отказ от Checked Exceptions в пользу Unchecked. Почему? Потому что Checked Exceptions раздувают сигнатуры методов и заставляют писать бесконечные `try-catch`, что делает код трудночитаемым.
3.  **Правило обработки:** Никогда не делай "пустой catch" (`catch (Exception e) {}`). Это самая большая ошибка новичка. Ты просто "проглатываешь" ошибку, и программа продолжает работать в сломанном состоянии, что приведет к еще более трудноуловимым багам позже.

# 🛠 Механизмы обработки исключений в Java

Исключение (Exception) — это событие, которое нарушает нормальный ход выполнения программы. Обработка исключений позволяет программе не "падать" при первой же ошибке, а попытаться восстановиться или хотя бы корректно завершить работу.

### 1. Иерархия Throwable
Всё, что может быть выброшено (thrown) в Java, наследуется от класса `Throwable`.
*   **`Error`**: Серьезные проблемы на уровне JVM (например, `OutOfMemoryError`). Их **не нужно** и практически невозможно обрабатывать. Это "фатальные" ошибки.
*   **`Exception`**: То, что мы должны обрабатывать. Делится на две ветки:
    *   **Checked (Проверяемые)**: Проверяются компилятором. Ты *обязан* либо обработать их (`try-catch`), либо объявить в сигнатуре метода (`throws`). Примеры: `IOException`, `SQLException`.
    *   **Unchecked (Непроверяемые / Runtime)**: Наследуются от `RuntimeException`. Компилятор не заставляет тебя их обрабатывать. Обычно это ошибки логики программиста. Примеры: `NullPointerException`, `ArrayIndexOutOfBoundsException`.

### 2. Основные конструкции

#### **Блок `try`**
Здесь мы размещаем "опасный" код, который потенциально может вызвать исключение.

#### **Блок `catch`**
Здесь мы описываем, что делать, если возникла конкретная ошибка.
*   **Важный нюанс (Порядок):** Сначала ловим более специфичные исключения (подклассы), а потом — общие (`Exception`). Если сначала поймать `Exception`, то до `IOException` код никогда не дойдет.
*   **Multi-catch:** Начиная с Java 7, можно ловить несколько исключений в одном блоке через пайп: `catch (IOException | SQLException e)`.

#### **Блок `finally`**
Код, который выполнится **всегда**, независимо от того, было исключение или нет.
*   Используется для очистки ресурсов (закрытие файлов, соединений с БД).
*   **Нюанс:** Если в блоке `try` или `catch` есть оператор `return`, блок `finally` всё равно выполнится перед тем, как метод вернет значение.

### 3. Ключевые слова: `throw` vs `throws`

| Слово | Где используется | Смысл |
| :--- | :--- | :--- |
| **`throw`** | Внутри тела метода | Мы "выстреливаем" исключением (создаем объект и кидаем его). |
le | **`throws`** | В сигнатуре метода. Мы предупреждаем: "Этот метод может быть опасен, будь готов". |

### 4. Try-with-resources (Modern Java)
Это "золотой стандарт" для работы с ресурсами. Если объект реализует интерфейс `AutoCloseable` или `Closeable`, его можно объявить внутри скобок `try`.
*   **Плюс:** Ресурс закроется **автоматически** в конце блока, даже если вылетело исключение. Тебе не нужен явный `finally` для закрытия файла/сокета.
*   **Нюанс (Suppressed Exceptions):** Если во время работы `try` возникла ошибка И при автоматическом закрытии ресурса тоже возникла ошибка — основная ошибка не потеряется, а вторая будет "подавленной" (suppressed) и доступна через метод `e.getSuppressed()`.

### 💡 Senior Nuances (На что обратить внимание)

1.  **Exception Swallowing (Проглатывание исключений):** Никогда не пиши пустой блок `catch {}`. Это самая страшная ошибка. Если ты "проглотил" ошибку, программа продолжит работать в невалидном состоянии, и найти причину бага будет невозможно. Как минимум — логируй ошибку.
2.  **Re-throwing (Переброс):** Иногда полезно поймать низкоуровневое исключение (`SQLException`) и обернуть его в свое высокоуровневое (`DataAccessException`), чтобы не раскрывать детали реализации базы данных выше по стеку.
3.  **Checked vs Unchecked — вечный спор:** Современный тренд (как в Spring Framework) — стремиться к использованию `RuntimeException`. Слишком много Checked-исключений делают код "грязным" и перегруженным `try-catch` блоками.

**В: Можно ли прервать выполнение блока `finally`, если в `try` произошел `return`?**

**В: В каких случаях `finally` может НЕ выполниться?**

**В: В чем разница между `throw` и `throws`?**
**О:** `throw` — это действие (создание и запуск ошибки), а `throws` — это декларация (предупреждение в заголовке метода о том, что ошибка возможна).

# 🚀 Шпаргалка: Проброс исключений (Exception Propagation)

### 1. Что это такое?
**Проброс исключения (Propagation)** — это процесс «всплытия» ошибки вверх по цепочке вызовов методов. Если в методе произошло исключение, и ты его **не обработал** (не обернул в `try-catch`), то JVM начинает искать обработчик в том методе, который вызвал текущий. Этот процесс продолжается до тех пор, пока исключение не будет поймано или пока оно не достигнет самого верха — метода `main()`. Если и в `main()` его никто не поймал, поток (Thread) завершается с ошибкой.

Представь это как эстафету: если бегун споткнулся и уронил палочку, она катится по трассе, пока её кто-нибудь не подберет.

### 2. Инструменты управления
Для работы с пробросом используются два ключевых слова:

*   **`throw`**: Используется **внутри тела метода**, чтобы «выбросить» (активировать) исключение прямо сейчас.
    *   *Пример:* `if (age < 18) throw new IllegalArgumentException("Too young!");`
*   **`throws`**: Используется **в сигнатуре метода**. Это «предупреждающая табличка» для всех, кто будет вызывать этот метод. Она говорит: «Эй, будь осторожен, этот метод может выкинуть вот такую ошибку, приготовь `try-catch`».

### 3. Разница в пробросе (Checked vs Unchecked)
Это критически важный нюанс для понимания компиляции Java:

1.  **Checked Exceptions (Проверяемые):** Это «строгие» исключения (наследники `Exception`, но не `RuntimeException`). Для них проброс **обязателен**. Если ты их не поймал, ты **обязан** прописать их в `throws`. Иначе код просто не скомпилируется.
2.  **Unchecked Exceptions (Непроверяемые/Runtime):** Это «тихие» исключения (наследники `RuntimeException`). Их **не нужно** объявлять в `throws`. Они пробрасываются вверх автоматически и незаметно для компилятора.

### 4. Нюансы и "Подводные камни" (Senior Level)

*   **Потеря контекста (Exception Swallowing):** Самая большая ошибка новичка — пустой блок `catch`.
    ```java
    try {
        doWork();
    } catch (Exception e) {
        // Ничего не делаем (Swallowing)
    }
    ```
    Здесь ты «убил» проброс. Исключение остановилось здесь, и никто в системе не узнает, что что-то пошло не так. Это превращает отладку в ад.

*   **Перехват с перевыбросом (Rethrowing & Wrapping):** Хорошая практика — поймать низкоуровневое исключение и выбросить новое, более осмысленное (высокоуровневое), сохранив при этом причину (Cause).
    ```java
    try {
        database.connect(); 
    } catch (SQLException e) {
        // Оборачиваем техническую ошибку в бизнес-ошибку
        throw new ServiceException("Service unavailable", e); 
    }
    ```
    *Здесь `e` передается как причина, чтобы не потерять Stack Trace.*

*   **Стек вызовов (Stack Trace):** Когда исключение пробрасывается вверх, оно «тащит» за собой всю историю вызовов. Именно поэтому в логах мы видим цепочку: `at methodC -> at methodB -> at methodA -> at main`.

# 🛠 Try-with-resources (TWR)

**Try-with-resources** — это синтаксический сахар, представленный в Java 7, который позволяет автоматически закрывать ресурсы, используемые в блоке `try`.

Раньше (в "старые добрые времена") нам приходилось вручную закрывать каждый файл или сокет в блоке `finally`, что приводило к огромному количеку шаблонного кода («boilerplate») и куче ошибок. TWR делает это за тебя.

### 💎 Суть механизма
Любой объект, который ты объявляешь внутри скобок `try (...)`, должен реализовывать интерфейс **`java.lang.AutoCloseable`** (или его наследника `java.io.Closeable`). Как только выполнение кода выходит из блока `try` (нормально или из-за ошибки), JVM автоматически вызывает метод `.close()` у всех объявленных ресурсов.

### 🚀 Ключевые нюансы (Senior Level)

1.  **Интерфейс-фундамент:** Если твой класс не реализует `AutoCloseable`, ты **не сможешь** использовать его в TWR. Это критически важно при создании своих кастомных ресурсов (например, соединений с БД).
2.  **Порядок закрытия (LIFO):** Ресурсы закрываются в **обратном порядке** их объявления. Если ты открыл `Resource A`, а затем `Resource B`, то сначала закроется `B`, а потом `A`. Это логично: если `B` зависит от `A`, мы должны сначала "убрать" зависимость, пока "фундамент" еще жив.
3.  **Подавленные исключения (Suppressed Exceptions) — Самый важный нюанс!**
    В старом подходе (`try-finally`) если ошибка возникла в блоке `try`, а затем при закрытии ресурса в `finally` вылетела *еще одна* ошибка, то первая ошибка **терялась** (перезаписывалась второй).
    В TWR всё иначе: основное исключение (из блока `try`) сохраняется, а исключения, возникшие при автоматическом закрытии, помечаются как **"подавленные" (suppressed)**. Их можно достать через метод `Throwable.getSuppressed()`. Это позволяет не терять первопричину бага.
4.  **Несколько ресурсов:** В скобках `try` можно объявлять сколько угодно ресурсов, разделяя их точкой с запятой `;`.

### 💻 Код: Было vs Стало

**Как было (Old School - плохой путь):**
```java
BufferedReader reader = null;
try {
    reader = new BufferedReader(new FileReader("test.txt"));
    System.out.println(reader.readLine());
} catch (IOException e) {
    e.printStackTrace();
} finally {
    // Огромный риск забыть закрыть или получить ошибку при закрытии
    if (reader != null) {
        try {
            reader.close();
        } catch (IOException e) {
            e.printStackTrace(); // Вторая ошибка может "затереть" первую!
        }
    }
}
```

**Как сейчас (Modern Java - правильный путь):**
```java
// Ресурсы объявляются прямо в скобках try
try (BufferedReader reader = new BufferedReader(new FileReader("test.txt"));
     BufferedWriter writer = new BufferedWriter(new FileWriter("output.txt"))) {
    
    String line = reader.readLine();
    writer.write(line);
    
} catch (IOException e) {
    // Все ресурсы закроются автоматически ДО того, как мы попадем в этот catch
    System.err.println("Ошибка: " + e.getMessage());
} 
// Никаких finally и ручного close()!
```

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что будет, если в блоке `try` произойдет исключение и одновременно при закрытии ресурса тоже возникнет исключение?**
**О:** Первичная ошибка из блока `try` останется главной. Вторая ошибка (из `.close()`) не пропадет, а будет добавлена в список "подавленных" (suppressed) к первой ошибке. Это позволяет провести полный дебаг.

**В: Можно ли объявлять ресурсы в TWR вне скобок `try`?**
**О:** Нет. Смысл TWR именно в том, что область видимости ресурса ограничена блоком `try`. Если ты объявишь переменную *до* `try`, она не будет автоматически закрыта этим механизмом.

**В: Что такое `AutoCloseable` и чем он отличается от `Closeable`?**
**О:** `Closeable` — это старый интерфейс (наследуется от `AutoCloseable`), предназначенный в основном для работы с потоками ввода-вывода (I/O) и выбрасывающий `IOException`. `AutoCloseable` — более современный и общий, он может выбрасывать любое исключение.

**В: Каков порядок закрытия, если я объявил два ресурса в одной строке?**
**О:** Если ты напишешь `try (Resource a = new Resource(), b = new Resource())`, они закроются в порядке `b`, затем `a`. Всегда соблюдается принцип LIFO (Last In, First Out).

# 🧠 Области памяти в JVM (Memory Management)

В JVM память разделена на две основные части: **Thread-specific** (индивидуальная для каждого потока) и **Shared** (общая для всех потока). Понимание этого — ключ к пониманию того, где возникают ошибки `OutOfMemoryError` и `StackOverflowError`.

## 1. Heap (Куча) — "Общий склад"
Это самая большая область памяти. Она **общая** для всего приложения.

*   **Что там хранится:** Все объекты (`new MyObject()`) и массивы.
*   **Жизненный цикл:** Объекты живут здесь, пока на них есть ссылки. Когда ссылок не остается, их удаляет **Garbage Collector (GC)**.
*   **Нюанс (Generations):** Heap не однороден. Он делится на поколения (Young Gen, Old Gen), чтобы GC работал эффективнее (молодые объекты умирают быстро, старые — живут долго).
*   **Риски:** Если объекты создаются слишком быстро или не удаляются, получаем `java.lang.OutOfMemoryError: Java heap space`.

## 2. Stack (Стек) — "Рабочий стол потока"
У каждого нового потока (Thread) создается свой собственный стек. Он **индивидуален** и изолирован.

*   **Что там хранится:**
    1.  Локальные переменные примитивных типов (`int`, `double`, `boolean` и т.д.).
    2.  **Ссылки** на объекты (сами объекты лежат в Heap, но "адреса" — в Stack).
    3.  Фреймы методов (информация о том, какой метод сейчас вызван и куда вернуться после его завершения).
*   **Принцип работы:** LIFO (Last In, First Out). Вызвали метод $\to$ создали фрейм $\to$ метод завершился $\to$ фрейм удалился.
*   **Риски:** Если вызвать бесконечную рекурсию, стек переполнится: `java.lang.StackOverflowError`.

## 3. Metaspace (Метапространство) — "Библиотека классов"
Пришло на смену *PermGen* в Java 8. Это часть **Native Memory** (память операционной системы, а не Heap).

*   **Что там хранится:** Метаданные классов: структура класса, имена методов, константы, статические переменные (в современных версиях), информация о методах.
*   **Нюанс:** Поскольку это Native Memory, размер Metaspace может динамически расширяться, пока не закончится оперативная память компьютера.
*   **Риски:** Если генерировать слишком много классов на лету (например, через прокси-генераторы), можно получить `java.lang.OutOfMemoryError: Metaspace`.

## 4. PC Register & Native Method Stack (Вспомогательные области)
*   **PC Register (Program Counter):** Маленькая область для каждого потока. Хранит адрес текущей инструкции байт-кода, которую выполняет поток. Если поток "заснул", PC Register сохраняет точку возврата.
*   **Native Method Stack:** Стек для выполнения методов, написанных на других языках (C/C++) через JNI (Java Native Interface).

### 📊 Шпаргалка-сравнение: Stack vs Heap

| Характеристика | Stack (Стек) | Heap (Куча) |
| :--- | :--- | :--- |
| **Доступность** | Только текущим потоком | Всем потокам |
| **Размер** | Маленький, ограниченный | Большой |
| **Скорость** | Очень высокая | Ниже (из-за работы GC) |
| **Что внутри** | Примитивы и ссылки | Объекты и массивы |
| **Ошибка при переполнении** | `StackOverflowError` | `OutOfMemoryError` |

# 🧠 Garbage Collection (GC) — Шпаргалка

**Garbage Collection (GC)** — это автоматический процесс управления памятью в JVM. Его главная задача: найти объекты, которые больше не используются программой, и освободить место в **Heap (Куче)**.

### 1. Фундаментальная идея: Reachability (Достижимость)
GC не ищет «мусор». Он ищет **«живые»** объекты. Объект считается живым, если до него можно добраться по цепочке ссылок, начиная от так называемых **GC Roots**.

**GC Roots — это отправные точки:**
*   Локальные переменные в стеке потоков (Stack).
*   Статические переменные классов (Static fields).
- Ссылки из JNI (Native code).
*   Активные потоки (Thread).

Если цепочка разрывается и объект нельзя «дотронуться» от GC Root — он кандидат на удаление.

### 2. Generational Hypothesis (Гипотеза о поколениях)
Это база, на которой строится вся работа GC. Она гласит: **«Большинство объектов умирают молодыми»**.
Вместо того чтобы проверять всю память целиком (что очень дорого), JVM делит Heap на поколения:

1.  **Young Generation (Молодое поколение):**
    *   Здесь рождаются все новые объекты.
    *   Разделено на: **Eden** (Эдем) и два **Survivor Spaces** (S0 и S1).
    *   Когда память в Eden заполняется, происходит **Minor GC**. Выжившие объекты переходят в Survivor.
2.  **Old Generation (Старое поколение / Tenured):**
    *   Сюда попадают «долгожители» — объекты, которые пережили много циклов Minor GC в Young Gen.
    *   Здесь происходит **Major GC** (или Full GC). Это более тяжелая операция.

### 3. Алгоритм работы (Основные этапы)
Процесс очистки обычно состоит из трех шагов:
1.  **Mark (Маркировка):** GC обходит дерево объектов от GC Roots и помечает все достижимые объекты как «живые».
2.  **Sweep (Очистка):** Все непомеченные объекты удаляются.
3.  **Compact (Уплотнение):** *Важный нюанс!* После удаления объектов в памяти остаются «дыры» (фрагментация). Compact перемещает живые объекты вплотную друг к другу, чтобы память была единым цельным блоком.

### 4. Главный враг: Stop-the-World (STW)
Почти любая фаза GC требует остановки всех прикладных потоков приложения. Это называется **Stop-the-World**.
*   **Проблема:** Во время STW приложение «замирает». Если паузы слишком длинные, пользователь видит лаги или таймауты.
*   **Цель оптимизации Java:** Сделать паузы STW максимально короткими и незаметными.

### 5. Современные сборщики (Краткий обзор)
Как Senior, ты должен знать, что выбор GC зависит от задачи:
*   **Serial GC:** Один поток. Для маленьких программ и микросервисов с малым объемом памяти.
*   **Parallel GC:** Несколько потоков на очистку. Фокус на высокой пропускной способности (throughput), но возможны долгие паузы.
*   **G1 (Garbage First):** Стандарт де-факто в современных Java. Разбивает Heap на регионы. Пытается предсказать время паузы и чистит те регионы, где больше всего мусора («Garbage First»).
*   **ZGC / Shenandoah:** Ультра-низкая задержка (ultra-low latency). Почляют почти нулевые паузы STW даже на огромных объемах памяти (терабайты), выполняя основную работу параллельно с приложением.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли в Java получить Memory Leak (утечку памяти)?**
**О:** Да, конечно. Хотя GC удаляет неиспользуемые объекты, он **не может** удалить те, на которые всё еще есть ссылка. Если ты забудешь очистить статический `List` или закроешь не все ресурсы, ссылки на объекты будут жить вечно, и память будет «утекать».

**В: В чем разница между Minor GC и Full GC?**
**О:** **Minor GC** очищает только Young Generation. Это быстро и часто. **Full GC** очищает весь Heap (Young + Old) и может затрагивать Metaspace. Это тяжелая операция с длительной паузой STW.

**В: Что такое фрагментация памяти?**
**О:** Это ситуация, когда свободная память есть, но она разбита на мелкие кусочки между живыми объектами. Из-за этого ты не можешь выделить место под один большой объект, хотя суммарно свободной памяти достаточно. Решается этапом **Compact**.

**В: Где хранятся метаданные классов?**
**О:** В **Metaspace**. Это часть нативной памяти (вне Heap), которая растет по мере необходимости. Раньше (в Java 7 и ниже) был PermGen, который часто приводил к `OutOfMemoryError`.

# 🧠 Тема: Поколения объектов (Generational Garbage Collection)

В основе работы современных JVM лежит **Generational Hypothesis** (Гипотеза о поколениях). Она гласит: *«Большинство объектов умирают молодыми»*.

Вместо того чтобы каждый раз сканировать всю кучу (Heap) в поисках мусора, JVM делит память на зоны, разделяя объекты по «возрасту». Это позволяет проводить быструю очистку там, где мусора больше всего.

### 🏗 Структура Heap (Кучи)

Вся куча делится на две основные части: **Young Generation** (Молодое поколение) и **Old Generation** (Старое поколение).

#### 1. Young Generation (Молодое поколение)
Здесь рождаются все новые объекты. Это зона, где происходит **Minor GC**. Она состоит из трех частей:
*   **Eden (Эдем):** «Колыбель» объектов. Сюда попадает всё, что ты создаешь через `new`.
*   **Survivor Spaces (S0 и S1):** Две одинаковые области («выжившие»). Они всегда работают в паре, и в конкретный момент времени одна из них **всегда пуста**.

**Как это работает (алгоритм):**
1.  Объекты создаются в **Eden**.
2.  Когда Eden заполняется, запускается **Minor GC**.
3.  Живые объекты из Eden переносятся в один из Survivor-ов (например, в S0).
4.  При следующем Minor GC выжившие объекты из Eden + выжившие из S0 перемещаются в S1.
5.  Этот процесс «перекладывания» продолжается, пока объект не станет «старым».

#### 2. Old Generation (Старое поколение / Tenured)
Сюда попадают объекты, которые пережили достаточное количество циклов Minor GC. Здесь происходит **Major GC** (или Full GC). Эта зона больше по размеру и очищается реже, но её очистка — гораздо более тяжелая операция.

---

### ⚙️ Ключевые механизмы и нюансы

*   **Tenuring Threshold (Порог выживания):** Это счетчик «возраста» объекта. Каждый раз, когда объект переживает Minor GC, его возраст увеличивается на 1. Когда возраст достигает определенного порога (настраивается в JVM), объект **промотируется** (promoted) из Survivor в Old Generation.
*   **Stop-the-world (STW):** Это критический термин. Во время большинства фаз GC выполнение твоего приложения полностью останавливается. Задача инженера — минимизировать длительность STW.
*   **Promotion Failure:** Если в Old Gen нет места, чтобы принять «стареющий» объект из Survivor, это может привести к тяжелому Full GC или даже `OutOfMemoryError`.
*   **Large Object Allocation:** Есть нюанс: очень большие объекты (например, огромные массивы) могут минуя Young Generation и сразу создаваться в Old Generation, чтобы не тратить ресурсы на их постоянное копирование между Survivor-ами.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между Minor GC и Major/Full GC?**
**О:** **Minor GC** очищает только Young Generation. Он быстрый, так как область маленькая, а объектов мало. **Major/Full GC** очищает Old Generation (и часто всю кучу). Это долгая операция, которая может вызвать заметные фризы приложения.

**В: Зачем нам два Survivor-а (S0 и S1), если можно использовать один?**
**О:** Чтобы избежать фрагментации памяти. Используя два пространства и метод копирования (Copying Algorithm), мы просто перекладываем живые объекты в чистое пространство, оставляя старое абсолютно пустым и готовым к новой записи. Если бы был один Survivor, нам пришлось бы «затыкать дыры» в памяти, что гораздо сложнее.

**В: Что такое "Promotion"?**
**О:** Это процесс перемещения объекта из Young Generation в Old Generation по достижении им определенного возраста (Tenuring Threshold).

**В: Почему объекты не могут жить в Eden вечно?**
**О:** Потомут Eden имеет ограниченный размер. Если бы мы не выносили живые объекты в Survivor/Old Gen, нам пришлось бы постоянно искать место для новых объектов, и очистка превратилась бы в бесконечный перебор всей памяти.

# 🧠 Шпаргалка: Типы ссылок (Reference Types)

В Java управление памятью автоматизировано через Garbage Collector (GC), но GC не всегда знает, *когда* именно объект пора удалять. Типы ссылок — это способ для разработчика дать подсказку сборщику мусора о «степени важности» объекта.

Всего существует 4 типа ссылок. Мы пойдем от самой «жесткой» к самой «призрачной».

### 1. Strong Reference (Сильная ссылка)
Это то, с чем мы работаем 99% времени. Любое обычное присваивание: `Object obj = new Object();` — это сильная ссылка.
*   **Как работает:** Пока на объект есть хотя бы одна сильная ссылка, GC **никогда** его не удалит. Объект будет жить в памяти вечно (пока жива эта ссылка).
*   **Риск:** Если ты забудешь занулить ссылку (например, в статическом поле), получишь **Memory Leak** (утечку памяти) и в итоге `OutOfMemoryError`.

### 2. Soft Reference (Мягкая ссылка)
Используется для реализации кэшей.
*   **Как работает:** Объект будет жить до тех пор, пока в JVM хватает оперативной памяти. Если GC видит, что память заканчивается, он начинает принудительно удалять объекты, на которые ведут только *Soft References*.
*   CLUE (Подсказка): «Удали меня, если станет совсем плохо с памятью».
*   **Применение:** Кэширование тяжелых данных (картинки, результаты сложных вычислений).

### 3. Weak Reference (Слабая ссылка)
Более агрессивная версия.
*   **Как работает:** Объект будет удален при **первой же** сборке мусора, как только GC до него доберется. Ему не важно, сколько памяти свободно — если GC запустился и увидел объект только с `WeakReference`, он его уничтожит.
*   **Применение:** `WeakHashMap`. Это идеальный способ хранить дополнительные метаданные об объекте, чтобы эти метаданные не мешали самому объекту удаляться из памяти.

### 4. Phantom Reference (Фантомная ссылка)
Самый странный и низкоуровневый тип.
*   **Как работает:** Ты **не можешь** получить доступ к самому объекту через `.get()` (он всегда будет возвращать `null`). Эта ссылка используется только для того, чтобы узнать, что объект *уже* готов к удалению.
*   **Зачем это нужно:** Для выполнения сложных операций очистки ресурсов (например, освобождение памяти вне кучи — native memory), когда стандартного `finalize()` (который уже deprecated) недостаточно. Работает всегда в паре с `ReferenceQueue`.
*   **CLUE:** «Я просто хочу знать, что объект умер, чтобы прибраться за ним».

---

### 📊 Сводная таблица для быстрого запоминания

| Тип ссылки | Когда удаляется? | Основная цель |
| :--- | :--- | :--- |
| **Strong** | Никогда (пока жива ссылка) | Обычная работа с объектами |
| **Soft** | Только при угрозе `OutOfMemoryError` | Умное кэширование |
| **Weak** | При первой же сборке мусора | Связывание данных без удержания объекта |
| **Phantom** | После того, как объект "умер" | Очистка ресурсов (post-mortem) |

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем ключевая разница между Soft и Weak ссылками?**
**О:** Разница в «настойчивости» сборщика мусора. `SoftReference` — это "ленивый" метод, он ждет критической нехватки памяти. `WeakReference` — это "агрессивный" метод, он удаляет объект сразу, как только увидит его при проходе GC.

**В: Что произойдет, если на объект ведет одновременно и Strong, и Weak ссылка?**
**О:** Объект **не будет** удален. Пока жива хотя бы одна *Strong* ссылка, для GC этот объект считается «живым», и наличие слабой ссылки на него не имеет значения.

**В: Можно ли использовать `PhantomReference` для восстановления данных объекта?**
**О:** Нет. Метод `.get()` у фантомной ссылки всегда возвращает `null`. Она предназначена только для уведомления о завершении жизненного цикла объекта через `ReferenceQueue`.

**В: Как реализовать кэш, который не вызывает OutOfMemoryError?**
**О:** Использовать `SoftReference` для хранения значений кэша. Тогда JVM сама решит, когда очистить кэш, чтобы спасти приложение от падения.

# 📜 Шпаргалка: Enums (Перечисления)

### 1. Что такое Enum на самом деле?
Многие думают, что `enum` — это просто именованный список констант. **Это не так.**
В Java `enum` — это **специальный тип класса**, который максимально упрощает создание фиксированного набора значений. Под капотом каждый ваш `enum` уже наследуется от базового класса `java.lang.Enum`.

### 2. Базовый синтаксис
```java
public enum Status {
    NEW,      // По умолчанию это константы (экземпляры класса)
    IN_PROGRESS,
    DONE,
    ARCHIVED
}
```

### 3. Продвинутый уровень: Состояние и поведение
Поскольку `enum` — это класс, он может иметь **поля**, **конструкторы** и **методы**. Это позволяет привязывать к константе дополнительные данные.

**Пример: HTTP Статусы с кодом и описанием**
```java
public enum HttpStatus {
    OK(200, "Success"),
    NOT_FOUND(404, "Not Found"),
    INTERNAL_SERVER_ERROR(500, "Server Error");

    private final int code; // Поля должны быть final (Immutability)
    private final String description;

    // Конструктор у enum всегда private по умолчанию!
    HttpStatus(int code, String description) {
        this.code = code;
        this.description = description;
    }

    public int getCode() { return code; }
    public String getDescription() { return description; }
}
```

### 4. Ключевые методы (Must Know)
*   **`values()`**: Возвращает массив всех констант в порядке их объявления. Идеально для итерации.
*   **`valueOf(String name)`**: Превращает строку в объект `enum`. Выбросит `IllegalArgumentException`, если такой строки нет.
*   **`name()`**: Возвращает точное имя константы как строку (как оно написано в коде).
*   **`ordinal()`**: Возвращает порядковый номер (индекс) константы (начиная с 0). **⚠️ Опасно!** (см. ниже).
*   **`toString()`**: По умолчанию возвращает то же, что и `name()`, но его можно переопределить для красивого вывода.

### 5. Важные нюансы (Senior Insights)

1.  **Immutability (Неизменяемость):** Всегда делай поля внутри `enum` `private final`. Перечисления созданы для представления стабильных состояний. Если ты изменишь состояние константы во время работы программы, это может привести к непредсказуемым багам.
2.  **Ловушка `ordinal()`:** Никогда не используй `ordinal()` для сохранения данных в базу или передачи между сервисами. Если кто-то добавит новую константу в середину списка, все индексы «поплывут», и твои данные в БД станут невалидными. Используй явное поле (например, `id` или `code`).
3.  **Singleton через Enum:** В книге *Effective Java* Джошуа Блох утверждает, что создание синглтона через `enum` — это самый надежный способ защиты от проблем сериализации и многопоточности.
4.  **Интерфейсы:** `enum` не может наследоваться от другого класса (так как уже наследует `Enum`), но он **может реализовывать интерфейсы**. Это позволяет делать разные константы с разной логикой.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли создать экземпляр enum через `new`?**
**О:** Нет. Конструкторы `enum` всегда приватные, а создание объектов управляется самой JVM в момент загрузки класса.

**В: Что будет, если переопределить `toString()` в enum?**
**О:** Метод `name()` всё равно вернет оригинальное имя константы, но при выводе через `System.out.println` или при использовании в логах будет использоваться твой кастомный `toString()`.

**В: Можно ли использовать enum в операторе `switch`?**
**О:** Да, это основной сценарий использования. Это делает код чистым и читаемым.

**В: Может ли enum иметь методы с разной реализацией для каждой константы?**
**О:** Да! Ты можешь объявить абстрактный метод в самом `enum` и реализовать его внутри каждой константы (это называется *constant-specific class body*). Это очень мощный паттерн.

**В: Чем `name()` отличается от `toString()`?**
**О:** `name()` — это финальный метод, он всегда возвращает имя, объявленное в коде. `toString()` — можно переопределить для кастомизации вывода.

# 📌 Тема: Аннотации (Annotations)

### 💡 Что это такое?
Если максимально просто: **Аннотации — это метаданные**. Это «метки» или «теги», которые мы вешаем на код (классы, методы, переменные).

Сами по себе аннотации **не несут логики** и не меняют выполнение программы. Они лишь предоставляют дополнительную информацию о коде для:
1.  **Компилятора** (чтобы он выдал ошибку или предупреждение).
2.  **Инструментов разработки** (IDE, генераторы кода).
    *Примечаet: В runtime-среде их может считывать фреймворк (например, Spring), но это уже область Reflection, которую мы не разбираем.*

---

### 🛠 1. Встроенные аннотации (Стандартные)
Те, что уже есть в JDK и ты используешь каждый день:

*   `@Override` — **Самая важная.** Говорит компилятору: «Я намеренно переопределить метод родителя». Если ты ошибешься в названии метода или параметрах, компилятор сразу подсветит ошибку.
*   `@Deprecated` — Помечает код как «устаревший». Если кто-то попытается его использовать, IDE покажет зачеркнутый текст и предупреждение. Это сигнал: «Не используй это, скоро удалим!».
*   `@SuppressWarnings` — Команда компилятору: «Я знаю, что здесь есть потенциальная проблема (например, небезопасное приведение типов), просто не спамь мне в логах предупреждениями».
*   `@SafeVarargs` — Используется для подавления предупреждений о «небезопасных» варгаргах (varargs) при работе с дженериками.

---

### 🏗 2. Мета-аннотации (Аннотации над аннотациями)
Когда ты создаешь свою собственную аннотацию, тебе нужно описать её поведение. Для этого используются мета-аннотации:

*   **`@Retention` (Жизненный цикл):** Определяет, как долго живет аннотация.
    *   `SOURCE`: Удаляется сразу после компиляции (как комментарии). Видна только в исходном коде. (Пример: `@Override`).
    *   `CLASS`: Сохраняется в `.class` файле, но не видна при выполнении программы. (Стандартное поведение).
    *   `RUNTIME`: Самая мощная. Аннотация доступна во время работы программы. Именно её используют фреймворки для настройки бинов, маппинга БД и т.д.
*   **`@Target` (Место применения):** Определяет, куда можно «лепить» аннотацию.
    *   `ElementType.TYPE` (на класс/интерфейс).
    *   `ElementType.METHOD` (на метод).
    *   `ElementType/FIELD` (на поле).
    *   `ElementType.PARAMETER` (на аргумент метода).
*   **`@Documented`:** Говорит, что эта аннотация должна быть включена в Javadoc.
*   **`@Inherited`:** Позволяет подклассам наследовать аннотацию от родительского класса.

---

### 🧪 3. Как создать свою аннотацию?
Это делается через ключевое слово `@interface`.

```java
import java.lang.annotation.*;

// Настраиваем поведение нашей аннотации
@Retention(RetentionPolicy.RUNTIME) // Будет видна в рантайме
@Target(ElementType.METHOD)        // Можно вешать только на методы
public @interface MyDebugInfo {
    String author() default "Unknown"; // Элемент с дефолтным значением
    int version() default 1;           // Еще один параметр
}

// Использование:
class Service {
    @MyDebugInfo(author = "Senior Dev", version = 2)
    public void processData() {
        // Логика
    }
}
```

**Нюанс:** В аннотациях можно использовать только определенные типы данных: примитивы, `String`, `Class`, `Enum`, другие аннотации и массивы из этих типов. Никаких списков (`List`) или сложных объектов.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `@Override` и просто написанием метода с таким же именем?**
**О:** Без `@Override` ты можешь случайно создать новый метод вместо переопределения (например, если опечатался в параметрах). Компилятор промолчит, и программа будет работать не так, как ты ожидал. С `@Override` компилятор проверит сигнатуру и выдаст ошибку при первой же опечатке.

**В: Что произойдет, если я поставлю `@Retention(RetentionPolicy.SOURCE)` на аннотацию, которую должен считывать Spring в рантайме?**
**О:** Это будет бесполезно. После компиляции аннотация просто исчезнет из байт-кода, и фреймворк её не увидит.

**В: Можно ли в аннотации передать объект класса `Object`?**
**О:** Нет. Как я упоминал выше, типы данных в аннотациях строго ограничены (примитивы, String, Class и т.д.). Это связано с тем, что значения аннотаций должны быть константами, известными еще на этапе компиляции.

**В: Зачем нужна мета-аннотация `@Inherited`?**
**О:** Если ты пометишь класс `Parent` аннотацией `@MyAnnotation` (и у неё есть `@Inherited`), то класс `Child extends Parent` тоже будет считаться помеченным этой аннотацией. Без неё — нет.

# 🧠 Generics (Обобщения)

**Generics** — это инструмент языка, который позволяет параметризовать типы. Вместо того чтобы писать класс для `String`, класс для `Integer` и так далее, мы пишем один класс `Box<T>`, где `T` — это «заполнитель» (placeholder), который мы подставим позже.

### 1. Зачем они нужны? (The "Why")
До появления Generics (в Java 1.4 и ниже) всё хранилось в `Object`. Это приводило к двум проблемам:
1.  **Необходимость явного приведения типов:** Тебе приходилось постоянно писать `(String) list.get(0)`.
2.  **Опасность `ClassCastException`:** Ты мог положить в список `Integer`, а достать его как `String`. Ошибка вылетала не во время компиляции, а во время работы программы (Runtime), что критично.

**Generics решают это на этапе компиляции.** Если ты сказал, что это `List<String>`, компилятор не даст тебе положить туда `Integer`.

### 2. Type Erasure (Стирание типов) — Важнейший нюанс
Это то, на чем валятся многие. Java — язык с обратной совместимостью. Чтобы старый код (без дженериков) мог работать с новым, разработчики JDK внедрили **Type Erasure**.

**Как это работает:**
Компилятор проверяет твой код на ошибки, но после проверки он **удаляет** всю информацию о типах.
*   `List<String>` превращается в просто `List`.
*   Внутри `List` все элементы становятся типом `Object`.
*   Везде, где были ограничения (например, `<T extends Number>`), компилятор подставляет `Number`.

**Следствие:** В Runtime (во время работы программы) JVM «не знает», что в списке лежат именно строки. Она видит только `Object`. Именно поэтому ты не можешь написать `if (list instanceof List<String>)` — это невозможно проверить в рантайме.

### 3. Wildcards (Маски/Подстановочные знаки)
Иногда нам нужно работать с иерархией типов. Для этого используются знаки вопроса `?`.

*   **Unbounded Wildcard (`<?>`):** «Любой тип». Мы не знаем, что там, но можем безопасно читать объекты как `Object`.
*   **Upper Bounded Wildcard (`<? extends T>`):** «Тип `T` или его наследник».
    *   *Пример:* `List<? extends Number>` может содержать `List<Integer>` или `List<Double>`.
    *   **Важно:** Из такого списка можно только **читать** (мы уверены, что там как минимум `Number`), но нельзя **записывать** (кроме `null`), потому что мы не знаем, какой именно это подтип.
*

*   **Lower Bounded Wildcard (`<? super T>`):** «Тип `T` или его предок».
    *   *Пример:* `List<? super Integer>` может содержать `List<Integer>`, `List<Number>` или `List<Object>`.
    *   **Важно:** В такой список можно **записывать** (мы уверены, что тип подходит под `Integer`), но при чтении мы получим только `Object`.

### 4. Принцип PECS (Producer Extends, Consumer Super)
Это золотое правило для использования Wildcards:
*   Если твой объект **отдает** данные (Producer) — используй `extends`.
*   Если твой объект **принимает/потребляет** данные (Consumer) — используй `super`.

### 🚩 Нюансы и «подводные камни»
1.  **Примитивы нельзя использовать в Generics:** Нельзя написать `List<int>`. Только `List<Integer>`. Почему? Потому что из-за *Type Erasure* всё должно приводиться к `Object`, а `Object` не может содержать примитив.
2.  **Нельзя создать экземпляр типа `T`:** Код `T obj = new T();` не скомпилируется. Компилятор не знает, какой конструктор вызывать, так как в рантайме `T` превращается в `Object`.
3.  **Raw Types (Сырые типы):** Использование `List list = new ArrayList();` (без `<>`) — это зло. Это отключает проверку типов и возвращает нас в эпоху Java 1.4, создавая риск `ClassCastException`.

### ❓ FAQ (Вопросы на собеседовании)

**В: Что такое Type Erasure?**
**О:** Это процесс удаления информации о параметрах типов во время компиляции. Компилятор заменяет generic-типы на их верхнюю границу (обычно `Object`), чтобы обеспечить обратную совместимость с кодом без дженериков.

**В: Можно ли использовать примитивы в Generics?**
**О:** Нет. Дженерики работают только с объектами (Reference types), так как из-за стирания типов все параметры должны быть приведены к `Object`. Для работы с числами используется Autoboxing (`int` $\to$ `Integer`).

**В: В чем разница между `List<? extends Number>` и `List<? super Integer>` при попытке добавить элемент?**
**О:** В `<? extends Number>` ты **не можешь** добавить ничего, кроме `null`, потому что компилятор не знает, какой именно наследник там находится (вдруг там `List<Double>`?). В `<? super Integer>` ты **можешь** без проблем добавлять `Integer` и его подтипы.

**В: Почему нельзя проверить `instanceof List<String>`?**
**О:** Потомут что из-за Type Erasure информация о том, что это именно `String`, стирается после компиляции. В рантайме этот список — просто `List`. Можно проверять только `instanceof List<?>`.

# 🚀 Lambda Expressions & Functional Interfaces

### 1. Суть вещей (The Big Picture)
До Java 8 мы передавали в методы **данные** (объекты, числа). С появлением лямбд мы начали передавать в методы **поведение** (код).

*   **Lambda Expression** — это анонимная функция. У неё нет имени, она не принадлежит конкретному классу (хотя синтаксически привязывается к интерфейсу), и её единственная цель — реализовать один метод интерфейса.
*   **Functional Interface (FI)** — это фундамент. Лямбда не может существовать в вакууме; она всегда является реализацией конкретного интерфейса, у которого есть **ровно один абстрактный метод**.

### 2. Функциональные интерфейсы (The Foundation)
Интерфейс считается функциональным, если у него есть только один `abstract method`.
*   **Аннотация `@FunctionalInterface`**: Не обязательна, но **обязательна в хорошем тоне**. Она заставляет компилятор проверить, что ты случайно не добавил второй абстрактный метод.
*   **Нюанс:** Интерфейс может содержать сколько угодно `default` и `static` методов. Они не считаются абстрактными и не нарушают правило "одного метода".

### le 3. Синтаксис лямбд
У лямбды три части: `(параметры) -> { тело }`.

1.  **Без параметров:** `() -> System.out.println("Hello")`
2.  **Один параметр:** `(x) -> x * x` (можно опустить скобки, если параметр один).
3.  **Несколько параметров:** `(a, b) -> a + b`
4.  **Тело-выражение:** Если в теле одна строка, `return` и `{}` не нужны.
5.  **Блок кода:** Если логика сложная, используем `{}` и обязательный `return` (если метод что-то возвращает).

### 4. Стандартные функциональные интерфейсы (Built-in FI)
В пакете `java.util.function` уже есть всё, что тебе понадобится. Запоминай эту четверку:

| Интерфейс | Метод | Что делает? | Пример |
| :--- | :--- | :---s Принимает $T$, возвращает $boolean$ | `t -> t > 0` (Фильтр) |
| **Predicate\<T\>** | `test(T t)` | Принимает $T$, возвращает $R$ | `t -> t.length() > 5` (Трансформация) |
| **Function\<T, R\>** | `accept(T t)` | Принимает $T$, ничего не возвращает | `t -> System.out.println(t)` (Действие) |
| **Supplier\<T\>** | `get()` | Принимает ничего, возвращает $T$ | `() -> new User()` (Фабрика) |

*Есть также вариации: `BiFunction<T, U, R>` (два входа), `UnaryOperator<T>` (вход и выход одного типа).*

### 5. Method References (Сокращенный синтаксис)
Если лямбда просто вызывает существующий метод, её можно заменить на "ссылку на метод" через `::`. Это делает код еще чище.

*   `s -> System.out.print(s)` $\to$ `System.out::print` (Ссылка на метод экземпляра)
*   `() -> Integer.parseInt(s)` $\to$ `Integer::parseInt` (Ссылка на статический метод)
*   `obj -> obj.getName()` $\to$ `User::getName` (Ссылка на метод конкретного типа)

### 6. Важные нюансы и "подводные камни" (Senior level)

1.  **Variable Capture (Захват переменных):** Лямбда может использовать переменные из внешнего контекста (scope). Но есть жесткое условие: переменная должна быть **effectively final**. Это значит, что после инициализации ты не имеешь права её изменять внутри или снаружи блока, где используется лямбда.
    *   *Почему?* Чтобы избежать проблем с консистентностью данных в многопоточной среде.
2.  **Lambda vs Anonymous Inner Class:**
    *   Лямбда — это не просто "красивая запись" внутреннего класса. У лямбды нет своего `this`. Внутри лямбды `this` ссылается на класс, в котором она написана.
    *   Лямбды легче и эффективнее по памяти (JVM оптимизирует их через `invokedynamic`).
3.  **Читаемость:** Не пиши "лямбда-монстров". Если логика занимает 10 строк — выноси её в отдельный именованный метод и используй *Method Reference*.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли использовать лямбду, если в интерфейсе два абстрактных метода?**
**О:** Нет. Лямбда — это реализация конкретного метода. Если методов два, компилятор не поймет, какой из них ты реализуешь. Это перестанет быть функциональным интерфейсом.

**В: Что такое "effectively final"?**
**О:** Это переменная, которую ты не переназначал после создания. Даже если ты не написал слово `final`, но и не менял значение переменной в коде, Java считает её *effectively final*, и её можно безопасно использовать в лямбде.

**В: В чем разница между `Function` и `UnaryOperator`?**
**О:** С технической точки зрения — никакой. `UnaryOperator<T>` — это просто `Function<T, T>`. Он принимает объект одного типа и возвращает объект того же самого типа. Это просто удобный синтаксический сахар для читаемости.

**В: Могут ли лямбды вызывать методы, которые меняют состояние (side-effects)?**
**О:** Технически — да. Но архитектурно — это плохая практика. Лямбды должны быть максимально "чистыми" (pure functions), чтобы их было легко тестировать и использовать в параллельных потоках без побочных эффектов.
