# 🧠 Java 5: Generics (Обобщения)

**Generics** — это инструмент, который позволяет типам (классам и интерфейсам) быть параметризованными. Простыми словами: это способ сказать компилятору: «Этот список будет работать *только* со строками, и не смей пускать туда ничего другого».

### 🎯 Зачем они нужны? (The "Why")
До Java 5 всё хранилось в `Object`. Это приводило к двум проблемам:
1.  **Постоянное приведение типов (Casting):** Тебе приходилось писать `(String) list.get(0)`.
2.  **Runtime Errors:** Ты мог случайно положить `Integer` в список строк, и программа «падала» только во время работы (`ClassCastException`).

**Generics переносят ошибки с этапа выполнения (Runtime) на этап компиляции (Compile-time).**

---

### 🛠 Основные концепции

#### 1. Generic Classes & Methods
Ты можешь объявить класс, который принимает тип как параметр.
*   `T` — Type (самый частый)
*   `E` — Element (для коллекций)
*   `K`, `V` — Key, Value (для мап)

```java
// Generic Class
public class Box<T> {
    private T content;
    public void set(T content) { this.content = content; }
    public T get() { return content; }
}

// Generic Method (тип определяется при вызове)
public <E> void printArray(E[] array) {
    for (E element : array) System.out.println(element);
}
```

#### 2. Wildcards (Символ `?`) — Самая важная часть
Wildcard представляет собой «неизвестный тип».

*   **`<?>` (Unbounded Wildcard):** «Любой тип». Используй, если тебе всё равно, что внутри, и ты только читаешь данные как `Object`.
*   **`<? extends T>` (Upper Bounded):** «Тип `T` или его наследник». 
    *   *Зачем:* Позволяет **читать** данные из структуры. Ты уверен, что всё, что достанешь, будет как минимум типом `T`.
*   **`<? super T>` (Lower Bounded):** «Титип `T` или его предок». 
    *   *Зачем:* Позволяет **записывать** данные в структуру. Ты уверен, что структура примет тип `T`.

#### 3. Принцип PECS (Producer Extends, Consumer Super)
Это золотое правило для работы с Wildcards:
*   Если твоя структура — **Producer** (ты только достаешь из неё данные), используй `extends`.
*   Если твоя структура — **Consumer** (ты только кладешь в неё данные), используй `super`.

---

### ⚠️ Нюансы и «Подводные камни» (Type Erasure)

Самое важное, что нужно понимать: **Generics существуют только на этапе компиляции.** 
После того как код скомпилирован, JVM «забывает» про все `<T>`. Это называется **Type Erasure (Стирание типов)**.

**Последствия стирания:**
1.  **Нельзя использовать примитивы:** `List<int>` — ошибка. Только `List<Integer>`. Потому-что `int` не является объектом, а в рантайме всё превращается в `Object`.
2.  **Нельзя создать экземпляр типа `T`:** `T obj = new T();` — невозможно, так как в рантайме мы не знаем, что такое `T`.
3.  **Нельзя использовать `instanceof` с дженериками:** `if (list instanceof List<String>)` — ошибка. В рантайме это просто `List`.
4.  **Нельзя создать массив дженериков:** `new T[10]` или `new List<String>[10]` — запрещено.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `List<Object>` и `List<?>`?**
**О:** Это критический момент. 
*   `List<Object>` — это список, в который можно положить *любой* объект. 
*   `List<?>` — это список с *неизвестным* типом. Ты не можешь в него ничего положить (кроме `null`), потому что компилятор не знает, какой там тип. Если там вдруг `List<Integer>`, а ты положишь `String`, всё сломается.

**В: Почему я не могу использовать `instanceof List<String>`?**
**О:** Из-за Type Erasure. В рантайме информация о том, что это был именно `String`, стерта. Проверка `list instanceof List` пройдет успешно, но проверка на конкретный внутренний тип — нет.

**В: Можно ли добавить элемент в `List<? extends Number>`?**
**О:** Нет (кроме `null`). Ты не знаешь, какой именно подтип там лежит (`Integer` или `Double`). Если ты добавишь `Integer`, а там на самом деле список `Double`, произойдет катастрофа. Это и есть принцип **Producer Extends**.

# 📝 Шпаргалка: Java 5 Annotations (Аннотации)

### 💡 Что это такое?
**Аннотация** — это метаданные. Это «записки на полях» вашего кода. Сами по себе аннотации не меняют логику работы программы (они не являются инструкциями для JVM), но они предоставляют информацию, которую могут прочитать **компилятор**, **инструменты сборки** (Maven/Gradle) или **фреймворки** (Spring/Hibernate) во время выполнения.

*Аналогия: Представь, что ты вешаешь на папку с документами ярлык «Срочно». Текст внутри папки не меняется, но человек (или процесс), увидев ярлык, изменит свое поведение.*

---

### 🛠 Основные компоненты (Meta-Annotations)
Когда мы создаем свою аннотацию, мы используем специальные аннотации для управления самой анлотацией. Это называется **Meta-annotations**.

1.  **`@Retention` — Жизненный цикл.** Определяет, как долго «живет» аннотация.
    *   `RetentionPolicy.SOURCE`: Удаляется компилятором. Видна только в исходном коде (например, `@Override`).
    *   `RetentionPolicy.CLASS`: Сохраняется в `.class` файле, но недоступна во время работы программы (Runtime). Это значение по умолчанию.
    *   `RetentionPolicy.RUNTIME`: Самый важный тип для разработчика фреймворков. Аннотация доступна через **Reflection API** во время выполнения программы. Именно так Spring понимает, какой метод пометить как `@RequestMapping`.

2.  **`@Target` — Место применения.** Определяет, куда можно «приклеить» аннотацию.
    *   `ElementType.TYPE`: Классы, интерфейсы, перечисления (Enums).
    *   `ElementType.FIELD`: Поля класса.
    *   `ElementType.METHOD`: Методы.
    *   `ElementType.PARAMETER`: Параметры методов.
    *   `ElementType.CONSTRUCTOR`: Конструкторы.

3.  **`@Documented`** — Если добавлена, то ваша аннотация будет включена в Javadoc (документацию). Без нее аннотацию не будет видно в документации к классу.

4.  **`@Inherited`** — Позволяет подклассам наследовать аннотацию от родительского класса. Если применили к `Parent`, то и у `Child` она будет видна (только для `TYPE`).

---

### 🏗 Как создать свою аннотацию?
Создается через ключевое слово `@interface`. Внутри можно объявлять элементы, которые ведут себя как методы.

```java
@Retention(RetentionPolicy.RUNTIME) // Чтобы мы могли прочитать её через Reflection
@Target(ElementType.METHOD)        // Только для методов
public @interface MyDebugInfo {
    String author();                // Обязательный параметр
    String task() default "No task"; // Параметр со значением по умолчанию
    int priority() default 1;       // Еще один дефолтный параметр
}
```

**Использование:**
```java
public class Service {
    @MyDebugInfo(author = "Senior_Dev", task = "Fix Bug #42")
    public void processData() {
        // логика
    }
}
```

---

### ⚠️ Нюансы и «Подводные камни» (Senior Insights)

1.  **Annotation Processing vs Reflection:**
    *   Не путай **Reflection** (чтение аннотаций в Runtime) и **Annotation Processing** (анализ кода во время компиляции). Инструменты вроде **Lombok** или **MapStruct** работают на этапе компиляции (APT — Annotation Processing Tool), они могут генерировать новый код, основываясь на ваших аннотациях. Рефлексия же просто «читает» то, что уже есть.
2.  **Производительность:** Чтение аннотаций через Reflection — операция дорогая. Если ты пишешь высоконагруженный сервис, не стоит сканировать все методы класса при каждом запросе. **Кэшируй результаты сканирования!**
3.  **Типы данных в элементах:** В аннотациях можно использовать только: примитивы, `String`, `Class`, `Enum`, другие аннотации и массивы из этих типов. Никаких списков (`List`) или сложных объектов.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем `@Override` отличается от обычной аннотации?**
О: `@Override` — это встроенная аннотация с `RetentionPolicy.SOURCE`. Она нужна только компилятору, чтобы проверить, действительно ли вы переопределяете метод. Если вы ошибетесь в названии метода, компилятор выдаст ошибку.

**В: Можно ли изменить значение аннотации во время выполнения программы?**
О: Нет. Аннотации — это статические метаданные. Они зашиты в байт-код. Вы можете прочитать их значение, но не можете перезаписать его «на лету» (в отличие от полей класса).

**В: Что произойдет, если я забуду указать `@Retention`?**
О: По умолчанию будет использовано `RetentionPolicy.CLASS`. Это значит, что через Reflection в коде вы эту аннотацию **не увидите**. Для большинства современных фреймворков это станет проблемой.

**В: Зачем нужен `default` в элементах аннотации?**
О: Чтобы упростить использование. Если у параметра есть `default`, разработчику не обязательно передавать его при использовании аннотации, что делает код чище.

# 🧠 Шпаргалка: Autoboxing & Unboxing

### 📌 Суть (The Concept)
В Java есть два типа данных: **примитивы** (`int`, `double`, `boolean`...) — это просто значения в памяти, и **объекты-обертки** (`Integer`, `Double`, `Boolean`...) — это полноценные объекты в Heap.

*   **Autoboxing (Автоупаковка):** Автоматическое преобразование примитива в объект-обертку.
    *   *Зачем:* Чтобы мы могли использовать примитивы там, где требуются только объекты (например, в `List<Integer>`).
*   **Unboxing (Распаковка):** Автоматическое преобразование объекта-обертки обратно в примитив.

---

### ⚙️ Как это работает «под капотом» (Compiler Magic)
Это не магия JVM, это **синтаксический сахар**, который добавляет компилятор Java при сборке кода.

**Пример Autoboxing:**
```java
Integer number = 10; 
// Компилятор превращает это в:
Integer number = Integer.valueOf(1s0);
```

**Пример Unboxing:**
```java
int primitive = number; 
// Компилятор превращает это в:
int primitive = number.intValue();
```
> **Senior Note:** Обрати внимание на `Integer.valueOf()`. Он использует кэширование (см. ниже), в то время как `new Integer()` — это плохой тон, создающий лишний объект.

---

### ⚠️ Опасные зоны (The Pitfalls)

#### 1. NullPointerException (NPE) — Главный убийца кода
Примитив не может быть `null`, а обертка — может. Если ты попытаешься распаковать `null`, программа упадет.
```java
Integer wrapper = null;
int primitive = wrapper; // 💥 Ошибка! Runtime Exception: NullPointerException
```
**Правило:** Всегда проверяй на `null` перед тем, как присвоить обертку примитиву.

#### 2. Сравнение через `==` (Reference vs Value)
При использовании `==` с объектами-обертками ты сравниваешь **ссылки** (адреса в памяти), а не значения.
```java
Integer a = 1000;
Integer b = 1000;
System.out.println(a == b); // false (разные объекты в куче)

int c = 1000;
int d = 1000;
System.out.println(c == d); // true (сравниваются значения примитивов)
```

#### 3. Производительность (Performance Overhead)
Autoboxing/Unboxing в циклах — это скрытая катастрофа для памяти и CPU. Каждый раз создается новый объект, нагружая Garbage Collector (GC).
```java
// ПЛОХО: создание миллионов объектов Integer
Long sum = 0L; 
for (long i = 0; i < Integer.MAX_VALUE; i++) {
    sum += i; // Здесь происходит Unboxing, сложение и Autoboxing обратно в Long
}

// ХОРОШО: используем примитив для расчетов
long sumPrimitive = 0L;
for (long i = 0; i < Integer.MAX_VALUE; i++) {
    sumPrimitive += i;
}
```

---

### 💎 Секретный уровень: Integer Cache
Чтобы сэкономить память, Java кэширует объекты `Integer` для диапазона от **-128 до 127**.

```java
Integer x = 100;
Integer y = 100;
System.out.println(x == y); // true (взяты из кэша, ссылки одинаковые)

Integer m = 200;
Integer n = 200;
System.out.println(m == n); // false (новые объекты созданы в Heap)
```

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли использовать `int` в `ArrayList<int>`?**
**О:** Нет. Generics работают только с типами, наследуемыми от `Object`. Поэтому нужно писать `ArrayList<Integer>`. При добавлении `int` произойдет Autoboxing.

**В: Что происходит при выполнении `Integer a = 10 + 20;`?**
**О:** Сначала выполняется арифметическая операция с примитивами (результат `30`), затем компилятор применяет `Integer.valueOf(30)` (Autoboxing).

**В: Почему использование `==` для сравнения `Integer` — это плохая практика?**
**О:** Потому_то ты не контролируешь, попадет ли значение в кэш или нет. Для проверки логической равенства чисел всегда используй `.equals()`.

**В: В чем разница между `Integer.valueOf(10)` и `new Integer(10)`?**
**О:** `valueOf()` — это умный метод, который проверяет кэш и возвращает существующий объект. `new Integer()` — принудительное создание нового объекта в памяти, что неэффективно. (Кстати, `new Integer` помечен как *Deprecated* начиная с Java 9).

# 📜 Шпаргалка: Java 6 — Scripting API & String Processing

## 1. Scripting API (JSR 223) — Главная звезда версии
До Java 6, если ты хотел добавить в приложение динамическую логику (например, чтобы пользователь мог писать правила скидок без пересборки всего JAR-файла), тебе приходилось либо писать свой парсер, либо использовать сложные костыли. **JSR 223** принес стандартизированный способ запуска скриптовых языков прямо из Java.

### 🛠 Основные компоненты:
*   **`ScriptEngineManager`**: "Диспетчер". Он ищет в classpath доступные движки (JavaScript, Groovy, Python и т.д.) и управляет ими.
*   **`ScriptEngine`**: "Исполнитель". Сам объект, который принимает код и выполняет его.
*   **`Bindings`**: "Контейнер для данных". Это мост между Java и скриптом. Через него ты прокидыва la Java-объекты в скрипт и забираешь результаты обратно.

### 🚀 Как это работает (Workflow):
1.  Создаем `ScriptEngineManager`.
2.  Запрашиваем нужный движок по имени (например, `"javascript"`).
3.  Подготавливаем `Bindings` (передаем переменные).
4.  Выполняем код через `.eval()`.

### 💡 Пример кода:
```java
import javax.script.*;

public class ScriptingExample {
    public static void main(String[] args) throws Exception {
        ScriptEngineManager manager = new ScriptEngineManager();
        // Ищем движок JavaScript (в Java 6 это был обычно Rhino)
        ScriptEngine engine = manager.getEngineByName("javascript");

        // Создаем "мостик" для данных
        Bindings bindings = engine.createBindings();
        bindings.put("price", 100);
        bindings.put("discount", 0.2);

        // Выполняем скрипт, используя наши переменные
        String script = "price * (1 - discount)";
        Object result = engine.eval(script, bindings);

        System.out.println("Final Price: " + result); // Выведет 80.0
    }
}
```

### ⚠️ Нюансы (Senior Tips):
*   **Зависимость от реализации**: Сам API (`javax.script`) — это только интерфейс. Чтобы он заработал, в `classpath` должен лежать конкретный движок (например, библиотека Rhino). Если движка нет, `getEngineByName` вернет `null`.
*     **Производительность**: Вызов `eval()` — операция дорогая. Если скрипт повторяется часто, его нужно **компилировать** (используя `Compilable` интерфейс), чтобы не парсить текст заново каждый раз.
*   **Безопасность**: Никоmal (никогда!) не запускай непроверенный скрипт от пользователя. Это классическая дыра для выполнения произвольного кода (RCE).

## 2. Улучшения в работе со строками и Regex
В Java 6 не появилось революционных методов вроде `String.join()` (это пришло в Java 8), но произошла важная "внутренняя" работа. Основной упор был сделан на **производительность регулярных выражений (`java.util.regex`)**, которые являются фундаментом всех строковых манипуляций.

### 📈 Что именно улучшилось:
*   **Оптимизация Pattern/Matcher**: Улучшена работа с бэктрекингом (backtracking) в регулярных выражениях. Это сделало поиск по сложным паттернам более предсказуемым и быстрым.
*   **Эффективность памяти**: Были внесены оптимизации в то, как `String` и `StringBuilder` взаимодействуют с регулярными выражениями, чтобы уменьшить количество создаваемых временных объектов (Garbage Collection стало меньше "страдать").

### 🔍 Важный нюанс для работы со строками:
Хотя API не расширилось, важно помнить о **Immutability (неизменяемости)** строк. Любая операция (`replace`, `substring`, `toUpperCase`) в Java 6 (как и сейчас) создает **новый объект** в куче. При массовых манипуляциях в циклах всегда используй `StringBuilder`.

## ❓ FAQ (Часто задаваемые вопросы)

**В: Можно ли через Scripting API вызвать метод моего Java-класса?**
**О:** Да! Если ты положишь экземпляр своего класса в `Bindings`, скриптовый язык сможет вызывать его публичные методы. Это основа создания "плагинной" архитектуры.

**В: Почему мой `getEngineByName("javascript")` возвращает `null`?**
**О:** Скорее всего, в твоем проекте нет библиотеки-движка (например, Rhino или Nashorn). Java предоставляет только API, но не саму реализацию языка. Проверь зависимости в Maven/Gradle.

**В: Есть ли разница между `String.substring()` в Java 5 и Java 6?**
**О:** Да, и это критически важно! В Java 5 `substring` мог вызывать утечки памяти (Memory Leak), так как подстрока хранила ссылку на массив символов всей исходной строки. В Java 6 эту "опасную" оптимизацию убрали: теперь создается новый массив символов, что безопаснее для памяти, хоть и чуть затратнее по CPU.

**В: Что использовать для частой конкатенации строк в Java 6?**
**О:** Только `StringBuilder`. Использование `+` в цикле — это классическая ошибка, которая превращает сложность алгоритма из $O(n)$ в $O(n^2)$.

# 🗂 Шпаргалка: JDBC 4.0 (Java 6)

### 💡 Суть изменений
До Java 6 работа с базами данных была "ручной". Тебе нужно было явно говорить JVM: «Эй, загрузи вот этот драйвер!». JDBC 4.0 принесла концепцию **автоматизации** и сделала процесс подключения к БД гораздо более прозрачным (магическим).

---

### 🚀 Главная фича: Автоматическая загрузка драйверов (SPI)
Это самое важное изменение. Раньше ты обязательно писал:
```java
Class.forName("com/mysql/cj/jdbc/Driver"); // Старый "грязный" способ
```
**Что изменилось:** В JDBC 4.0 была внедрена поддержка **Service Provider Interface (SPI)**.

*   **Как это работает:** Теперь драйвер — это не просто набор классов, а "сервис". Если в JAR-файле драйвера внутри есть специальный файл `META-INF/services/java.sql.Driver`, то `DriverManager` сам найдет его в classpath и зарегистрирует при старте приложения.
*   **Результат:** Тебе больше не нужно знать конкретный класс драйвера в своем коде. Ты просто подключаешься по URL (`jdbc:mysql://...`), а Java сама находит нужный "инструмент".

### 🔍 Улучшение работы с метаданными
JDBC 4.0 расширила возможности `DatabaseMetaData`. Стало проще программно опрашивать базу:
*   Проще получать информацию о типах данных, колонках, индексах и ограничениях (constraints).
*   Улучшена поддержка аннотаций и стандартов XML (что помогало в те времена при работе с конфигурациями).

### 🛠 Что нужно знать (Нюансы)
1.  **Зависимость от Classpath:** Автоматика работает **только** если JAR-файл драйвера лежит в classpath. Если ты забыл добавить библиотеку, `DriverManager` не "магически" её найдет, он просто ничего не увидит.
2.  **Class.forName всё еще работает:** Старый способ не удалили (он не deprecated). Его можно использовать, если у тебя очень старый драйвер, который не поддерживает SPI, или если тебе нужно принудительно инициализировать класс.
3.  **URL — это ключ:** Поскольку мы больше не указываем класс драйвера, критически важно правильно составить `jdbc:subprotocol:subname`. Если в URL ошибка, `DriverManager` просто проигнорирует этот драйвер.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Зачем нам JDBC 4.0, если мы всё равно используем Hibernate/Spring Data?**
**О:** Spring и Hibernate — это надстройки. В конечном итоге они всё равно используют `DriverManager` или `DataSource`. Понимание того, как работает базовый JDBC, критично для отладки проблем с подключением (например, когда драйвер не найден).

**В: Как Java понимает, какой именно драйвер использовать из десяти имеющихся в classpath?**
**О:** Она перебирает все зарегистрированные через SPI драйверы и спрашивает у каждого: *"Ты можешь обработать этот URL (например, jdbc:postgresql://...)?"*. Тот драйвер, который ответит `"Да"`, и забирает соединение.

**В: Если я использую `Class.forName()`, считается ли это плохим тоном в Java 6+?**
**О:** Это не ошибка, но это "legacy-стиль". В современном коде лучше полагаться на автоматику. Использование `Class.forName` делает твой код жестко связанным с конкретной реализацией драйвера, что снижает гибкость.

**В: Что такое SPI в контексте JDBC?**
**О:** Это механизм, позволяющий библиотекам (драйверам) предоставлять реализации интерфейсов (`java.sql.Driver`) так, чтобы основная платформа (Java) могла их обнаружить без явного указания классов в коде.

# 🛠 Java 7: Try-with-resources

### 💡 Суть проблемы (The "Why")
До Java 7 управление ресурсами (файлы, соединения с БД, сокеты) было головной болью. Чтобы не было утечек памяти, нам приходилось писать громоздкие блоки `try-catch-finally`. 

**Проблема старого подхода (`try-finally`):**
1. **Boilerplate:** Слишком много однотипного кода.
2. **Exception Masking (Главная беда):** Если исключение вылетало в блоке `try`, а затем при попытке закрыть ресурс в `finally` вылетало *еще одно* исключение, то первое (основное) — терялось. Мы видели только ошибку закрытия, а реальную причину падения программы — нет.

### ✅ Решение: Try-with-resources
Это синтаксический сахар, который автоматизирует закрытие ресурсов. Теперь Java сама гарантирует вызов метода `.close()` в конце блока.

**Синтаксис:**
```java
try (ResourceType resource = new ResourceType()) {
    // Работаем с ресурсом
} catch (Exception e) {
    // Обработка ошибок
} 
// Ресурс закрыт автоматически ПЕРЕД переходом в catch или завершением блока
```

### 🔑 Ключевое требование: `AutoCloseable`
Чтобы объект мог участвовать в `try-with-resources`, он **обязан** реализовывать интерфейс `java.lang.AutoCloseable` (или его «младшего брата» `java.io.Closeable`). 
*   `Closeable` — расширяет `AutoCloseable`, предназначен специально для I/O операций и всегда выбрасывает `IOException`.

### 🚀 Продвинутые нюансы (Senior Level)

1.  **Порядок закрытия (LIFO):** Если ты объявляешь несколько ресурсов через точку с запятой, они закрываются в **обратном порядке** объявления. Это критично: если ресурс Б зависит от ресурса А, то сначала закроется Б, а потом А.
    ```java
    try (Scanner sc = new Scanner(file); 
         BufferedReader br = new BufferedReader(new FileReader(file))) {
        // Сначала закроется br, затем sc
    }
    ```

2.  **Suppressed Exceptions (Подавленные исключения):** Это "киллер-фича". Если в блоке `try` упало исключение и при закрытии ресурса тоже упало исключение, Java **не потеряет** первое. Оно станет основным, а второе будет прикреплено к нему как «подавленное» (suppressed). Ты можешь достать их через `e.getSuppressed()`.

3.  **Область видимости:** Переменная ресурса доступна **только внутри** блока `try`. За его пределами она уже не существует (она "мертва").

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Что будет, если в блоке `try` произойдет ошибка и в методе `.close()` тоже?**
**О:** Основное исключение из блока `try` сохранится. Исключение из `.close()` будет добавлено в список "suppressed" (подавленных). Это решает проблему потери важного лога ошибки.

**В: В чем разница между `AutoCloseable` и `Closeable`?**
**О:** `Closeable` — это специализированный интерфейс для потоков ввода-вывода (I/O), который всегда работает с `IOException`. `AutoCloseable` — более общий интерфейс, который может выбрасывать любое исключение. Все `Closeable` являются `AutoCloseable`, но не наоборот.

**В: Можно ли объявлять несколько ресурсов в одном `try`?**
**О:** Да, через точку с запячку. Важно помнить про порядок закрытия (обратный — Last In, First Out).

**В: Что если ресурс инициализируется вне блока `try(...)`, но внутри метода?**
**О:** Если ты объявил переменную *до* `try`, а инициализировал её *внутри* скобок `try(...)`, то она будет закрыта, но её область видимости может быть проблемой. Правильный паттерн: объявление и инициализация — прямо в круглых скобках `try`.

# 💎 Java 7: Diamond Operator (`<>`)

### 💡 Суть в двух словах
**Diamond Operator** — это синтаксический сахар, который позволяет не дублировать типы при создании объектов Generic-классов. Если тип переменной слева уже определен, компилятор сам «догадается», какой тип использовать справа.

---

### 📉 До и После

**До Java 7 (Verbose/Многословно):**
Тебе приходилось дважды писать один и тот

```java
// Дублирование типа String
List<String> names = new ArrayList<String>(); 
Map<Integer, String> users = new HashMap<Integer, String>();
```

**С Java 7 (Clean/Чисто):**
Ты используешь пустые угловые скобки `<>`, и компилятор делает **Type Inference** (вывод типа).

```java
// Компилятор смотрит на левую часть и понимает, что внутри String
List<String> names = new ArrayList<>(); 
Map<Integer, String> users = new HashMap<>();
```

---

### 🧠 Как это работает под капотом? (Nuances)

1.  **Type Inference (Вывод типов):** Компилятор анализирует контекст. Он берет тип из объявления переменной (Target Type) и подставляет его в конструктор. Это происходит на этапе компиляции, в рантайме никакой магии нет.
2.  **Сложные типы:** Оператор работает не только для простых типов, но и для сложных структур с несколькими параметрами:
    ```java
    // Работает идеально
    Map<String, List<Integer>> complexMap = new HashMap<>(); 
    ```
3.  **Зависимость от контекста:** Если компилятор не может "догадаться" о типе (например, если нет явного объявления слева), использование `<>` приведет к ошибке или созданию **Raw Type** (сырого типа), что опасно.

---

### ⚠️ Подводные камни и нюансы

*   **Опасность Raw Types:** Если ты напишешь `List list = new ArrayList<>();` (без указания типа слева), компилятор не сможет применить вывод типов, и ты получишь `List` (сырой тип), что убивает всю прелесть Generics и безопасность типов.
*   **Взаимодействие с `var` (Java 10+):** С появлением ключевого слова `var` ситуация усложнилась. 
    ```java
    var list = new ArrayList<>(); // ОПАСНО! 
    ```
    Здесь `var` берет тип из правой части. А справа у нас `<>`, значит `list` станет `ArrayList<Object>`. Это классическая ловушка для новичков. Чтобы сохранить типы, нужно либо писать `var list = new ArrayList<String>();`, либо явно указывать тип слева.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Улучшает ли Diamond Operator производительность программы?**
**О:** Нет. Это чисто синтаксический сахар. После компиляции в байт-код разницы между `new ArrayList<String>()` и `new ArrayList<>()` нет. На скорость выполнения кода это не влияет.

**В: Что произойдет, если я напишу `List<String> list = new ArrayList();` (без скобок вообще)?**
**О:** Ты создашь **Raw Type**. Программа скомпилируется (с предупреждением), но ты потеряешь проверку типов на этапе компиляции. Ты сможешь положить в этот список что угодно, что может привести к `ClassCastException` в рантайме.

**В: Можно ли использовать Diamond Operator при передаче аргумента в метод?**
**О:** Да, если метод ожидает Generic-тип и контекст позволяет его вычислить. 
*Пример:* `Collections.emptyList()` — это не совсем оператор, но принцип вывода типа тот же.

# 📑 Шпаргалка: Java 7 — Strings in `switch`

### 🚀 Суть изменения
До версии Java 7 оператор `switch` умел работать только с примитивами (кроме `long`, `float`, `double`) и `enum`. Если нужно было проверить строку, приходилось городить бесконечные цепочки `if-else` с использованием `.equals()`.

В **Java 7** в `switch` официально разрешили использовать объекты типа `String`. Это сделало код чище, читабельнее и уменьшило количество визуального «шума».

### 🛠 Как это выглядит (Синтаксис)
```java
String command = "START";

switch (command) {
    case "START":
        System.out.println("Запуск процесса...");
        break;
    case "STOP":
        System.out.println("Остановка...");
        break;
    case "PAUSE":
        System.out.println("Пауза...");
        break;
    default:
        System.out.println("Неизвестная команда");
}
```

### 🧠 Что происходит «под капотом» (Senior Level)
Многие думают, что Java просто сравнивает строки через `.equals()`. Это не совсем так. Если бы JVM делала последовательное сравнение каждой строки, производительность `switch` падала бы с ростом количества `case`.

**Внутренняя магия:**
1.  **Хэширование:** При компиляции и выполнении Java использует `hashCode()` для каждой строки в `case`. 
2.  **Поиск по хэшу:** Сначала JVM сравнивает хэш-коды. Это очень быстра de операция (сравнение чисел).
3.  **Проверка коллизий:** Если хэш-коды совпали (а такое бывает — это называется *коллизия*), Java делает «контрольный выстрел» через `.equals()`, чтобы убедиться, что строки действительно идентичны.

**Вывод:** `switch` по строкам работает эффективнее, чем длинный `if-else`, так как поиск идет не линейно, а через прыжок по хэш-таблице.

### ⚠️ Важные нюансы и «грабли»

1.  **🚨 NullPointerException (NPE) — Главная опасность!**
    Если переменная, которую ты передаешь в `switch`, окажется `null`, программа **сразу упадет** с `NullPointerException`. 
    *   *Совет:* Всегда проверяй строку на `null` перед `switch` или используй `Objects.requireNonNull()`.

2.  **Case Sensitivity (Регистрозависимость):**
    `"START"` и `"start"` — это разные кейсы. `switch` не умеет игнорировать регистр сам по себе.
    *   *Совет:* Приводи строку к единому регистру перед проверкой: `switch (command.toUpperCase())`.

3.  **Забытый `break`:**
    Старая добрая проблема "fall-through". Если забыть `break`, выполнение провалится в следующий `case`, даже если условие не совпало.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что будет, если передать `null` в `switch(str)`?**
**О:** Вылетит `NullPointerException`. В `switch` нельзя передавать `null`.

**В: Почему `switch` по строкам быстрее, чем `if-else` с `.equals()`?**
**О:** Потому что `switch` использует хэш-коды строк для быстрого поиска (своеобразную хэш-таблицу), в то время как `if-else` проверяет каждое условие по очереди (линейный поиск).

**В: Работает ли `switch` с `String` так же эффективно, если у нас 1000 разных `case`?**
**О:** Да, благодаря использованию `hashCode()`, сложность поиска будет гораздо ближе к константной, чем при линейном переборе в `if-else`.

**В: Можно ли использовать в `case` переменные или выражения?**
**О:** Нет. Значения в `case` должны быть **константами** (compile-time constants). Ты не можешь написать `case myVariable:`.

# 📝 Шпаргалка: Java 7 — Multi-catch Block

### 💡 Суть изменения
До Java 7, если у тебя было несколько исключений, которые требовали **одинаковой** логики обработки, тебе приходилось либо дублировать один и тот же блок `catch`, либо ловить общий предок (например, `Exception`), что считалось плохой практикой.

**Multi-catch** позволяет перечислить несколько типов исключений через вертикальную черту `|` в одном блоке `catch`. Это делает код чище (меньше boilerplate) и уменьшает вероятность ошибок при обновлении логики.

---

### 🛠 Синтаксис
```java
try {
    // Код, который может выбросить разные исключения
} catch (IOException | SQLException | ParseException e) {
    // Единая логика обработки для всех трех типов
    logger.error("Ошибка при обработке данных", e);
}
```

---

### ⚠️ Важные нюансы (Senior level)

#### 1. Переменная исключения `e` — effectively final
Это самый важный технический нюанс. В мульти-кэтче переменная исключения (в примере выше `e`) является **неявно `final`**. 
*   **Что это значит:** Ты не можешь переназначить переменную `e` внутри блока `catch`.
*   **Пример ошибки:**
    ```java
    catch (IOException | SQLException e) {
        e = new IOException(); // ОШИБКА КОМПИЛЯЦИИ! e нельзя менять.
    }
    ```

#### 2. Запрет на иерархическую связь (No Subclassing)
Ты не можешь указать в одном мульти-кэтче исключения, которые связаны отношением «родитель-потомок». Компилятор выдаст ошибку, так как это делает часть списка бессмысленной.
*   **Пример ошибки:**
    ```java
    // ОШИБКА! FileNotFoundException уже входит в IOException. 
    // Это избыточно (redundant).
    catch (IOException | FileNotFoundException e) { 
        ... 
    }
    ```

#### 3. Чистота кода vs Гибкость
Мульти-кэтч идеален, когда логика обработки **абсолютно идентична**. Если для `IOException` ты хочешь просто залогировать ошибку, а для `SQLException` — сделать ретрай (retry), то тебе всё равно нужно два разных блока `catch`. Не пытайся впихнуть невпихуемое в один блок ради красоты.

---

### ✅ Резюме: Когда использовать?
*   **ДА:** Если логика обработки (логирование, очистка ресурсов, проброс дальше) одинакова для всех перечисленных типов.
*   **НЕТ:** Если типы исключений образуют иерархию (одно является подклассом другого).
*   **НЕТ:** Если обработка требует разных действий для разных ошибок.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что изменилось в модификаторе переменной исключения в Multi-catch?**
**О:** Она стала `final`. Ты не можешь присвоить ей новое значение внутри блока.

**В: Можно ли написать `catch (Exception | IOException e)`?**
**О:** Нет. Это вызовет ошибку компиляции, так как `IOException` является подтипом `Exception`. Компилятор увидит избыточность.

**В: Помогает ли Multi-catch уменьшить количество кода?**
**О:** Да, он убирает дублирование блоков `catch`, которые выполняют идентичные действия, тем самым уменьшая "code smell" (запах кода) и упрощая его поддержку.

**В: Если я поймал несколько исключений в одном блоке, как мне понять, какое именно произошло?**
**О:** Ты можешь использовать оператор `instanceof` внутри блока:
```java
catch (IOException | SQLException e) {
    if (e instanceof SQLException) {
        // специфичная логика для SQL
    }
}
```

# 🧠 Шпаргалка: Java 7 NIO.2 (New I/O)

### 📌 Контекст: Зачем это вообще нужно?
До Java 7 у нас был старый добрый `java.io.File`. Он был ужасен: методы возвращали `boolean` вместо исключений (ты не знал, *почему* файл не удалился), не умел работать с метаданными и плохо поддерживал современные файловые системы.

**NIO.2** — это полностью переосмысленный подход к работе с файловой системой. Его главные столпы: `Path`, `Files` и `WatchService`.

---

### 1. Интерфейс `Path` (Замена `File`)
`Path` — это не сам файл, а **логический путь** к нему. Это объектная абстракция, которая может представлять как относительный, так и абсолютный путь.

*   **Как получить:**
    *   `Paths.get("folder/file.txt")` — классика.
    *   `FileSystems.getDefault().getPath("...")` — более низкоутекающий уровень.
*   **Ключевые фишки (Манипуляции):**
    *   `.resolve()` — «склеивание» путей (аналог `new File(parent, child)`). Если передать абсолютный путь в `resolve`, он просто вернет его.
    *   `.relativize()` — вычисляет разницу между двумя путями (как `../..`).
    *   `.normalize()` — убирает лишние элементы типа `.` и `..`.
    *   `.toAbsolutePath()` / `.toRealPath()` — превращает относительный путь в полный. **Важно:** `toRealPath()` проверяет существование файла на диске и разрешает символьные ссылки (symlinks).

---

### 2. Класс `Files` (Твой главный инструмент)
Если `Path` — это «адрес», то `Files` — это «курьер», который выполняет работу. Почти всё, что ты делаешь с файлами, делается через статические методы этого класса.

*   **Чтение и запись:**
    *   `Files.readAllLines(path)` — читает всё в память (List<String>). **⚠️ Опасно для огромных файлов!**
    *   `Files.write(path, bytes)` — быстрая запись.
    *   `Files.newBufferedReader(path)` — создание потока (Stream-based). **✅ Правильный путь для больших данных.**
*   **Управление файлами:**
    *   `Files.copy(src, dest, options)` — копирование (можно добавить `StandardCopyOption.REPLACE_EXISTING`).
    *   `Files.move(src, dest, options)` — перемещение/переименование.
    *   `Files.delete(path)` — удаляет, но кидает исключение, если файла нет.
    *   `Files.deleteIfExists(path)` — безопасное удаление (вернет `false`, если файла не было).
*   **Поиск и обход:**
    *   `Files.walk(startPath)` — возвращает `Stream<Path>`. Рекурсивно проходит по всем подпапку. **Очень мощно.**
    *   `Files.find(...)` — поиск файлов по критериям (дата, размер, расширение).

---

### 3. Атрибуты файла (`FileAttributes`)
NIO.2 позволяет работать с метаданными на уровне ОС.
*   **`BasicFileAttributes`** — база: размер, время создания, время последнего доступа/модификации.
*   **`PosixFileAttributes`** — (только для Linux/Unix) права доступа (rwxr-xr-x), владелец, группа.
*   **Как читать:** `Files.readAttributes(path, BasicFileAttributes.class)`.

---

### 4. `WatchService` (Слежка за файловой системой)
Это механизм, который позволяет программе «подписаться» на события в папке. Вместо того чтобы бесконечно опрашивать диск в цикле (`polling`), ты используешь системные прерывания.

*   **Что можно отловить:** `ENTRY_CREATE`, `ENTRY_DELETE`, `ENTRYs_MODIFY`.
*   **Как это работает:**
    1. Создаешь `FileSystems.getDefault().newWatchService()`.
    2. Регистрируешь путь: `path.register(watchService, StandardWatchEventKinds.ENTRY_CREATE)`.
    3. В бесконечном цикле вызываешь `watchService.take()` (блокирующий вызов), который «просыпается» только при наступлении события.

---

### ⚠️ Senior Nuances (На что наступишь, если не знаешь)

1.  **Memory Leak & OOM:** Никогда не используй `Files.readAllLines()` для лог-файлов размером в 10 ГБ. Всегда используй `Files.newBufferedReader()` или `Files.lines()`, чтобы обрабатывать файл потоком (Stream).
2.  **Symlinks (Символьные ссылки):** Будь осторожен при рекурсивном обходе (`Files.walk`). Если в папке есть ссылка на другую папку, ты можешь уйти в бесконечную рекурсию или выйти за пределы целевой директории.
3.  **Atomic Operations:** При перемещении файлов используй `StandardCopyOption.ATOMIC_MOVE`. Это гарантирует, что операция либо выполнится полностью, либо не выполнится вовсе (важно для критических данных).
4.  **WatchService не рекурсивен по умолчанию!** Если ты подписался на папку `/A`, события в подпапке `/A/B` ты **не увидишь**. Тебе нужно вручную обходить дерево и регистрировать каждый `Path`.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем фундаментальная разница между `java.io.File` и `java.nio.file.Path`?**
**О:** `File` — это старый, ограниченный класс, который часто возвращает `false` вместо ошибок. `Path` — это часть новой API, которая работает с абстракциями файловых систем, поддерживает более богатые метаданные и лучше интегрирована со Stream API.

**В: Как мне быстро найти все `.log` файлы в дереве папок?**
**О:** Используй `Files.walk(startPath).filter(p -> p.toString().endsWith(".log")).forEach(...)`. Это элегантно и эффективно.

**В: Что делать, если я хочу проверить права доступа к файлу на Linux?**
**О:** Используй `Files.getPosixFilePermissions(path)`. Это вернет набор `PosixFilePermission`, с которыми можно работать как с обычным `Set`.

**В: Можно ли использовать NIO.2 для работы с ZIP-архивами без распаковки на диск?**
**О:** Да! Через `FileSystems.newFileSystem(zipPath, null)`. Ты можешь работать с содержимым ZIP-файла так, будто это обычная папка в твоей системе. Это киллер-фича NIO.2.

# 🧠 Java 7: Integer/Long Caching & String Concatenation

В этой теме мы разберем два механизма, которые напрямую влияют на **память** и **производительность**. Хотя основы заложены давно, именно в эпоху Java 7 понимание этих вещей стало критическим для написания оптимизированного кода.

---

### 1. Integer/Long Caching (Кэширование оберток)

В Java типы-обертки (`Integer`, `Long` и др.) — это объекты. Создание объекта в куче (Heap) — это дорого: нужно выделить память, инициализировать его. Чтобы не плодить тысячи одинаковых объектов для маленьких чисел, JVM использует **кэш**.

**Как это работает:**
При создании `Integer` в диапазоне от **-128 до 127**, Java не создает новый объект, а берет уже существующий из заранее подготовленного массива (кэша).

**Нюансы и грабли:**
*   **Оператор `==` vs `.equals()`:** Это классика. Если ты сравниваешь два `Integer` через `==`, ты проверяешь **ссылки** на объекты, а не их значения.
    *   `Integer a = 100; Integer b = 100; (a == b)` $\to$ `true` (взяты из кэша, ссылки ведут на один объект).
    *   `Integer c = 200; Integer d = 200; (c == d)` $\to$ `false` (созданы разные объекты в Heap, ссылки разные).
*   **Диапазон:** Нижняя граница `-128` фиксирована. Верхнюю (`127`) теоретически можно изменить через флаг JVM `-XX:AutoBoxCacheMax=<size>`, но на практике лучше на это не рассчитывать и всегда использовать `.equals()`.

---

### 2. String Concatenation (Конкатенация строк)

В Java строки — это неизменяемые (`immutable`) объекты. Любая операция по «изменению» строки на самом деле создает новую строку в памяти.

**Как это работает в Java 7:**
Когда ты пишешь `String s = "a" + "b" + "c";`, компилятор не делает три операции сложения. Он переписывает твой код, используя `StringBuilder`.
Твой код: `"a" + "b" + "c"`
Превращается в: `new StringBuilder().append("a").append("b").append("c").toString();`

**Нюансы и грабли:**
*   **Ловушка цикла (The Loop Trap):** Это самая частая ошибка.
    ```java
    // ПЛОХО (Senior скажет: "Уволь!")
    String s = "";
    for (int i = 0; i < 1000; i++) {
        s += i; // На каждой итерации создается НОВЫЙ StringBuilder и НОВАЯ строка
    }
    ```
    В этом цикле ты создашь 1000 объектов `StringBuilder` и 1000 промежуточных строк. Это убивает производительность и забивает Garbage Collector.
    **Как правильно:** Создай один `StringBuilder` *вне* цикла и используй `.append()` внутри.

*   **Конкатенация констант:** Если ты складываешь только литералы (`"a" + "b"`), компилятор сделает это еще на этапе компиляции, и в байт-коде будет просто одна строка `"ab"`. Это максимально эффективно.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Почему нельзя использовать `==` для сравнения `Integer`?**
**О:** Потому что `==` сравнивает адреса в памяти. Из-за кэширования это может работать «случайно» для чисел от -128 до 127, но сломается на любом числе вне этого диапазона. Всегда используй `.equals()`.

**В: Что быстрее: `String + String` или `StringBuilder.append()`?**
**О:** Если это одна строка (однострочное выражение) — разницы почти нет, компилятор сам всё оптимизирует. Но если у тебя цикл — только `StringBuilder`. В цикле `+` превращается в катастрофу для памяти.

**В: Можно ли изменить диапазон кэширования Integer?**
**О:** Да, через аргументы запуска JVM (`-XX:AutoBoxCacheMax`), но это специфическая настройка под очень тяжелые высоконагруженные системы, и она затрагивает только верхнюю границу.

# 🧠 Java 8: Lambda Expressions (Шпаргалка)

### 1. Что это такое?
**Лямбда-выражение** — это, по сути, анонимная функция. Это способ написать блок кода (метод), у которого нет имени, но который можно передавать как объект.

**Зачем они нужны?**
До Java 8, чтобы передать логику в метод, нам приходилось создавать громоздкие "анонимные классы". Лямбды позволяют избавиться от "синтаксического шума" (boilerplate code) и перейти к **функциональному стилю** программирования.

### 2. Синтаксис
Структура максимально простая:
`(параметры) -> { тело_функции }`

*   **Параметры:** могут быть пустыми `()`, один параметр `x`, или несколько `(x, y)`.
*   **Стрелка `->`:** разделяет параметры и логику.
try/catch или несколько строк требуют `{}` и `return`. Если одна строка — `return` можно опустить.
*   **Типы данных:** Java умеет делать **Type Inference** (вывод типов). Тебе не нужно писать `(String s) -> ...`, достаточно `(s) -> ...`, так как компилятор сам поймет тип из контекста.

### 3. Фундамент: Functional Interface
Лямбда-выражение **не может существовать само по себе**. Оно может быть реализовано только там, где ожидается **Функциональный Интерфейс**.

*   **Определение:** Это интерфейс, который содержит ровно **один абстрактный метод**.
*   **Аннотация `@FunctionalInterface`:** Она не обязательна, но крайне рекомендуется. Она заставляет компилятор проверить, что ты случайно не добавил в интерфейс второй метод.

**Стандартные интерфейсы (пакет `java.util.function`):**
Это "джентльменский набор", который нужно знать наизусть:
1.  **`Predicate<T>`**: Принимает `T`, возвращает `boolean`. (Проверка условия).
2.  **`Consumer<T>`**: Принимает `T`, ничего не возвращает (`void`). (Действие над объектом).
3.  **`Function<T, R>`**: Принимает `T`, возвращает `R`. (Трансформация данных).
4.  **`Supplier<T>`**: Не принимает ничего, возвращает `T`. (Создание/генерация объекта).
5.  **`UnaryOperator<T>`**: Наследник `Function`, где вход и выход — один и тот же тип.

### 4. Method References (Ссылки на методы) — "Лямбды на стероидах"
Если лямбда просто вызывает существующий метод, её можно сократить еще сильнее, используя оператор `::`.

*   `s -> System.out.println(s)`  $\rightarrow$  `System.out::println` (Ссылка на метод конкретного объекта).
*   `(s) -> Integer.parseInt(s)` $\rightarrow$ `Integer::parseInt` (Ссылка на статический метод).
*   `(obj, str) -> obj.substring(str)` $\rightarrow$ `String::substring` (Ссылка на метод экземпляра).
*   `() -> new ArrayList<>()` $\rightarrow$ `ArrayList::new` (Ссылка на конструктор).

### 5. Важный нюанс: Замыкания и Variable Capture
Лямбды могут использовать переменные из внешнего контекста (области видимости, где объявлена лямбда). Но есть жесткое правило:

**Переменная должна быть `final` или "effectively final".**
Это значит, что ты можешь использовать переменную в лямбде, только если ты **не меняешь её значение** после инициализации. Если ты попытаешься изменить локальную переменную внутри лямбды или после неё — получишь ошибку компиляции.

*Почему?* Лямбда может выполняться в другом потоке, и Java должна гарантировать, что состояние переменной будет консистентным (неизменяемым).

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем лямбда-выражение отличается от анонимного класса?**
**О:** 
1. **Синтаксис:** Лямбды гораздо лаконичнее.
2. **Scope (Область видимости):** У анонимного класса есть свой `this` (ссылка на сам класс), а у лямбды `this` — это объект внешнего класса.
3. **Функциональность:** Анонимный класс может реализовать интерфейс с множеством методов, а лямбда — только функциональный интерфейс.

**В: Можно ли использовать лямбду для реализации интерфейса с двумя методами?**
**О:** Нет. Лямбда по определению привязывается к одному конкретному абстрактному методу. Если методов два, компилятор не поймет, какой из них ты реализуешь.

**В: Что такое "effectively final"?**
**О:** Это переменная, которая не помечена ключевым словом `final`, но её значение ни разу не переназначалось после инициализации. Для лямбды она ведет себя так же, как `final`.

**В: Влияет ли использование лямбд на производительность?**
**О:** В большинстве случаев — нет, разница незаметна. Но технически под капотом используется инструкция `invokedynamic`, которая работает эффективнее и гибче, чем создание новых классов анонимными классами. Однако, при очень частом создании лямбд в высоконагруженных циклах, нужно следить за созданием объектов в куче (heap).

# 🚀 Шпаргалка: Java 8 Method References (Ссылки на методы)

### 💡 Что это такое?
**Method Reference** — это синтаксический сахар для лямбда-выражений. Если твоя лямбда-функция просто вызывает уже существующий метод и не делает никакой дополнительной логики, вместо громоздкой лямбды ты используешь ссылку на метод.

Это делает код короче, чище и читаемее (принцип *Clean Code*).

**Суть:** Вместо того чтобы писать «Возьми строку, примени к ней метод `toUpperCase`», ты просто говоришь: «Используй `String::toUpperCase`».

---

### 🛠 Четыре типа ссылок на методы

Все ссылки на методы делятся на 4 четкие категории. Запомни их — это база.

#### 1. Ссылка на статический метод (`Static Method Reference`)
Когда у тебя есть статический метод, и ты просто передаешь в него аргументы.
*   **Синтаксис:** `ClassName::staticMethodName`
*   **Эквивалент лямбды:** `(args) -> ClassName.staticMethodName(args)`

```java
// Лямбда
Function<String, Integer> parser = (s) -> Integer.parseInt(s);

// Method Reference
Function<String, Integer> parserRef = Integer::parseInt;
```

#### 2. Ссылка на метод экземпляра конкретного объекта (`Reference to a Particular Object's Method`)
У тебя уже есть готовый объект (например, `System.out`), и ты вызываешь его метод.
*   **Сентяксис:** `instance::methodName`
*   **Эквивалент лямбды:** `(args) -> instance.methodName(args)`

```java
List<String> names = Arrays.asList("Java", "Spring", "Hibernate");

// Лямбда (принято передавать элемент списка в println)
names.forEach(s -> System.out.println(s));

// Method Reference (используем уже существующий объект System.out)
names.forEach(System.out::println);
```

#### 3. Ссылка на метод экземпляра произвольного объекта типа X (`Reference to an Instance Method of an Arbitrary Object of a Particular Type`)
**Это самый коварный тип.** Здесь нет конкретного объекта, но есть тип. Первый аргумент лямбды становится "хозяином" (целью) метода, а остальные — его параметрами.
*   **Синтаксис:** `ClassName::methodName`
*   **Эквивалент лямбды:** `(obj, args) -> obj.methodName(args)`

```java
List<String> names = Arrays.asList("apple", "banana", "cherry");

// Лямбда: берем строку 's' и вызываем у неё метод toUpperCase()
Function<String, String> upper = (s) -> s.toUpperCase();

// Method Reference: тип ClassName — String, метод — toUpperCase
Function<String, String> upperRef = String::toUpperCase;
```

#### 4. Ссылка на конструктор (`Constructor Reference`)
Используется для создания новых объектов.
*   **Синтаксис:** `ClassName::new`
*   **Эквивалент лямбды:** `(args) -> new ClassName(args)`

```java
// Лямбда: создаем новый ArrayList
Supplier<List<String>> listSupplier = () -> new ArrayList<>();

// Method Reference
Supplier<List<String>> listSupplierRef = ArrayList::new;
```

---

### 🧠 Нюансы от Senior'а (На что смотреть)

1.  **Совместимость с Functional Interface:** Ссылка на метод работает **только** если сигнатура метода совпадает с сигнатурой функционального интерфейса (SAM - Single Abstract Method). Если метод принимает два аргумента, а твой интерфейс `Function` (один аргумент), компилятор выдаст ошибку.
2.  **Читаемость vs Избыточность:** Не пытайся использовать ссылки на методы там, где есть хоть капля логики. 
    *   *Плохо:* `list.forEach(s -> System.out.println("Item: " + s))` — здесь нельзя использовать `System.out::println`, потому что ты добавил строку `"Item: "`. Здесь нужна лямбда.
3.  **Типизация:** При использовании `ClassName::methodName` (тип 3) важно, чтобы первый аргумент входящего потока данных соответствовал типу объекта, у которого вызывается метод.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `System.out::println` и `String::toUpperCase`?**
**О:** Это разные типы ссылок. `System.out::println` — это ссылка на метод **конкретного объекта** (объекта `PrintStream`). `String::toUpperCase` — это ссылка на метод **произвольного объекта типа String**. В первом случае объект уже существует, во втором — он будет передан в метод в процессе выполнения.

**В: Можно ли использовать Method Reference, если в лямбде есть дополнительная логика (например, `s -> s.trim().toLowerCase()`)?**
**О:** Нет. Ссылка на метод может заменить только один прямой вызов метода. Если есть цепочка вызовов или дополнительные операции, тебе нужна классическая лямбда.

**В: Улучшает ли Method Reference производительность по сравнению с лямбдой?**
**О:** Существенно — нет. В большинстве случаев это просто синтаксический сахар. Однако в некоторых реалификациях JVM ссылки на методы могут быть чуть более оптимизируемы, но для разработчика важнее чистота кода.

**В: Что произойдет, если я использую `ArrayList::new`, но не передам аргументы в конструктор?**
**О:** Если твой функциональный интерфейс (например, `Supplier`) не принимает аргументов, то всё будет отлично. Но если ты попытаешься использовать это там, где нужны параметры (например, `Function`), возникнет ошибка компиляции, так как сигнатуры не совпадут.

# 🧠 Шпаргалка: Java 8 — Functional Interfaces (FI)

### 1. Что это такое?
**Функциональный интерфейс** — это интерфейс, который имеет **ровно один абстрактный метод**. 

В индустрии их часто называют **SAM-интерфейсами** (Single Abstract Method). Именно наличие одного метода позволяет Java понимать, какую лямбда-выражение или ссылку на метод привязать к этому типу.

### 2. Аннотация `@FunctionalInterface`
*   **Это не обязанность, а контракт.** Интерфейс будет функциональным, даже если нет этой аннотации (главное — один абстрактный метод).
*   **Зачем она нужна?** Она заставляет компилятор проверить, что вы случайно не добавили второй абстрактный метод. Это защита от ошибок при рефакторинге.

### 3. Золотые правила (Нюансы)
Чтобы интерфейс оставался функциональным, важно помнить:
1.  **Default методы:** Вы можете добавлять сколько угодно `default` методов. Они не считаются абстрактными и не нарушают правило SAM.
2.  **Static методы:** Можно добавлять любые `static` методы. Они тоже не влияют на статус FI.
3.  **Методы класса Object:** Если в интерфейсе переопределен метод из `java.lang.Object` (например, `public boolean equals(Object obj)`), он **не считается** вторым абстрактным методом. Это легально.

### 4. Основной набор «Built-in» интерфейсов
В Java 8 появился пакет `java.util.function`, который покрывает 99% задач. Запомни их по ролям:

| Интерфейс | Что принимает (Input) | Что возвращает (Output) | Роль в коде |
| :--- | :--- | :--- | :--- |
| **`Predicate<T>`** | `T` | `boolean` | **Фильтр:** Проверяет условие. |
| **`Function<T, R>`** | `T` | `R` | **Трансформер:** Преобразует один тип в другой. |
| **`Consumer<T>`** | `T` | `void` | **Потребитель:** Выполняет действие (side-effect). |
| **`Supplier<T>`** | *ничего* | `T` | **Фабрика:** Создает/предоставляет объект. |
| **`UnaryOperator<T>`** | `T` | `T` | **Спец-трансформер:** Тот же тип на входе и выходе. |
| **`BinaryOperator<T>`**| `T, T` | `T` | **Агрегатор:** Берет два объекта того же типа и возвращает один. |

### 5. Продвинутый уровень: Примитивные специализации (Performance Matters!)
Это то, на чем валятся Junior-разработчики. 
Если ты используешь `Predicate<Integer>`, Java будет делать **Autoboxing** (превращать `int` в объект `Integer`), что создает лишнюю нагрузку на Garbage Collector.

Для высоконагруженных систем всегда ищи примитивные версии:
*   `IntPredicate`, `LongPredicate`, `DoublePredicate` — работают напрямую с примитивами.
*   `ToIntFunction<T>`, `ToLongConsumer<T>` и т.д.

### 6. Bi-варианты (Два аргумента)
Если нужно передать два параметра, используй префикс **Bi**:
*   `BiPredicate<T, U>`
*   `BiFunction<T, U, R>`
*   `BiConsumer<T, U>`

---

### ❓ FAQ: Вопросы на собеседовании

**В: Можно ли сделать функциональный интерфейс, если в нем есть методы `default`?**
**О:** Да. Количество `default` методов не ограничено. Главное, чтобы остался только один `abstract` метод.

**В: Что произойдет, если я добавлю второй абстрактный метод в интерфейс с `@FunctionalInterface`?**
**О:** Компилятор выдаст ошибку. Это и есть смысл данной аннотации.

**В: В чем разница между `Function<T, R>` и `UnaryOperator<T>`?**
**О:** `UnaryOperator<T>` — это подмножество `Function`. У него тип входного и выходного параметра обязан быть одинаковым (`T -> T`). Это просто более строгая и читаемая форма записи.

**В: Зачем нужны интерфейсы типа `IntPredicate` вместо `Predicate<Integer>`?**
**О:** Для избежания лишнего Autoboxing/Unboxing. Работа с примитивами напрямую гораздо быстрее и не засоряет память объектами-обертками. Это критично в стримах (Streams API) при обработке больших массивов данных.

# 🌊 Java 8: Pipeline Processing (Streams API)

**Pipeline processing** — это концепция конвейера. Представь себе заводскую ленту: на вход подается сырье (данные), по пути стоят рабочие (операции), которые фильтруют, красят или пересобирают детали, а в конце стоит упаковщик, который складывает готовый продукт в коробку.

В Java Stream API всё строится на трех компонентах: **Source** $\rightarrow$ **Intermediate Operations** $\rightarrow$ **Terminal Operation**.

---

### 1. Анатомия конвейера

#### 🏗️ Source (Источник)
Это то, откуда текут данные. Это может быть `Collection` (List, Set), массив или даже бесконечный поток чисел.
*   *Пример:* `list.stream()`, `Stream.of(1, 2, 3)`, `Arrays.stream(arr)`.

#### 🛠️ Intermediate Operations (Промежуточные операции) — "Рабочие"
Это функции, которые трансформируют поток. **Главная фишка: они ленивы (lazy).** Они не делают ничего с данными, пока не придет команда «запускай». Они лишь строят план работ.
*   `filter(Predicate)` — пропускает только те элементы, что подходят под условие.
*   `map(Function)` — превращает один объект в другой (например, из `User` делает `String` с именем).
*   `flatMap(Function)` — «разглаживает» вложенные структуры. Если у тебя поток списков, `flatMap` превратит его в поток одиночных элементов.
*   `distinct()` — удаляет дубликаты.
*   `sorted()` — сортирует (может быть тяжелой операцией!).
*   `peek(Consumer)` — «шпион». Позволяет посмотреть на элемент в процессе прохождения, не меняя его (идеально для дебага).
*   `limit(n)` / `skip(n)` — обрезают поток.

#### 🏁 Terminal Operation (Терминальная операция) — "Упаковщик"
Это точка невозврата. Когда вызывается терминальная операция, конвейер начинает работать, данные потекут по всем промежуточным этапам, и на выходе ты получишь результат или побочный эффект. **После терминальной операции стрим закрывается.**
*   `collect(Collector)` — собирает результат в новую коллекцию (`toList()`, `toSet()), `groupingBy`.
*   `forEach(Consumer)` — просто выполняет действие для каждого элемента (например, `System.out::println`).
*   `reduce(BinaryOperator)` — сводит все элементы к одному (например, сумма всех чисел).
*   `count()` — возвращает количество элементов.
*   `anyMatch`, `allMatch`, `noneMatch` — проверяют условия (возвращают `boolean`).
*   `findFirst`, `findAny` — достают элемент из потока.

---

### 🧠 Нюансы и "подводные камни" (Senior Level)

1.  **Lazy Evaluation (Ленивость):** Если ты напишешь `list.stream().filter(x -> x > 10).map(x -> x * 2);` и не вызовешь терминальную операцию, **в консоли ничего не произойдет**. Программа даже не посмотриму в список. Стрим — это просто инструкция "как делать", а не само действие.
2.  **Short-circuiting (Короткое замыкание):** Некоторые операции могут остановить конвейер до того, как пройдут все элементы. Например, `findFirst()` или `limit(5)`. Если в списке миллион элементов, но мы вызвали `limit(5)`, стрим обработает только первые 5. Это критически важно для производительности.
3.  **Side Effects (Побочные эффекты):** **Золотое правило:** Старайся не менять внешние переменные внутри стрима (особенно в `map` или `filter`). Стрим должен быть функциональным: *вход $\rightarrow$ трансформация $\rightarrow$ выход*. Если ты внутри `forEach` меняешь глобальный `ArrayList`, ты рискуешь получить непредсказуемое поведение, особенно при параллельных стримах.
4.  **Parallel Streams (Параллельные потоки):** `list.parallelStream()` — это магия, которая разбивает задачу на части и выполняет их в `ForkJoinPool`. 
    *   *Когда использовать:* Когда данных очень много И операции тяжелые (CPU-bound).
    *   *Когда НЕ использовать:* На маленьких коллекциях (расходы на разделение потока будут больше, чем польза) или если важен порядок элементов.

---

### ❓ FAQ (Часто задаваемые вопросы)

**Q: В чем разница между `map` и `flatMap`?**
**A:** `map` — это трансформация 1 к 1 (был объект $A$, стал объект $B$). `flatMap` — это трансформация 1 ко многим + развертывание. Если у тебя поток строк, где каждая строка — это список слов, то `map` даст тебе "поток списков", а `flatMap` даст тебе "поток всех слов из всех списков".

**Q: Можно ли использовать один и тот же стрим дважды?**
**A:** Нет. Стрим — это одноразовый конвейер. Как только сработала терминальная операция, поток "исчерпан" (consumed). Попытка вызвать вторую операцию на том же объекте выкинет `IllegalStateException`.

**Q: Что быстрее: обычный `for` или `Stream API`?**
**A:** На простых задачах и маленьких данных обычный `for` почти всегда быстрее из-за отсутствия оверхеда на создание объектов стрима. Stream API стоит использовать ради **читаемости, декларативности и удобства работы со сложными трансформациями**.

**Q: Как отладить (дебажить) стрим?**
**A:** Используй операцию `.peek(e -> System.out.println("Checking: " + e))`. Вставляй её между промежуточными этапами, чтобы видеть, как меняются данные «внутри» конвейера.

# 🧠 Шпаргалка: Java 8 Parallel Streams

### 📌 Суть в двух словах
**Parallel Stream** — это способ заставить Java использовать все доступные ядра процессора для обработки элементов коллекции. Вместо того чтобы идти по списку один за другим (последовательно), поток разбивается на части, каждая часть обрабатывается своим потоком, а потом результаты склеиваются обратно.

В основе лежит **Fork/Join Framework**:
1.  **Fork (Разделение):** Задача рекурсивно делится на мелкие подзадачи.
2.  **Join (Соединение):** Результаты подзадач собираются в один финальный ответ.

---

### 🛠 Как это работает «под капотом»
За разделение данных отвечает **Spliterator** (Split + Iterator). Он умеет эффективно дробить источник (например, `ArrayList`) на части. Если `Spliterator` может быстро разделить данные, параллелизм будет эффективным.

Все параллельные стримы по умолчанию используют один и тот же общий пул потоков — **`ForkJoinPool.commonPool()`**. Это критически важный нюанс!

---

### ✅ Когда ИСПОЛЬЗОВАТЬ (Green Flags)
1.  **Огромные объемы данных:** Когда элементов настолько много, что накладные расходы на создание задач оправданы.
2.  **Тяжелые вычисления (CPU-bound):** Операции, которые сильно нагружают процессор (математика, сложные преобразования строк).
3.  **Независимые элементы:** Обработка одного элемента никак не влияет на другой.
4.  **Легко делимые структуры:** `ArrayList`, `IntStream.range` — их легко разбить пополам.

### ❌ Когда НЕ ИСПОЛЬЗОВАТЬ (Red Flags)
1.  **Маленькие коллекции:** Накладные расходы на менеджмент потоков будут выше, чем польза от параллелизма. Стрим станет **медленнее**.
2.  **Зависимость от порядка (Order-sensitive):** Если тебе важен `limit()`, `findFirst()` или `skip()`, параллелизм может сломать логику или резко замедлить процесс из-за необходимости синхронизации порядка.
3.  **I/O операции (Blocking I/O):** Чтение файлов, запросы в БД или сетевые вызовы. Если ты забьешь `commonPool` ожиданием ответа от сети, **все остальные параллельные стримы в приложении встанут колом**.
4.  **Сложные структуры данных:** `LinkedList` очень плохо делится (нужно перебирать элементы по порядку, чтобы найти середину). Параллелизм здесь будет бесполезен.
5.  **Side-effects (Побочные эффекты):** Если внутри `.forEach()` ты меняешь внешнюю переменную или модифицируешь общую коллекцию — получишь **Race Condition**.

---

### ⚠️ Главные нюансы (Senior Insights)

1.  **Common Pool Starvation:** Поскольку все `parallelStream()` используют один и тот же `ForkJoinPool.commonPool()`, одна "плохая" задача (например, долгий запрос в БД) может парализовать всё приложение.
2.  **Statelessness (Безсостоятельность):** Операции в стриме должны быть чистыми функциями. Не используй внешние переменные, которые могут измениться.
3.  **Cost of Merging:** Помни, что после параллельной обработки Java нужно потратить время на "сборку" (merging) результатов обратно в один список/число. Если операция сборки тяжелая, выигрыша не будет.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что произойдет, если я буду использовать `parallelStream()` для запросов к API?**
**О:** Ты рискуешь "задушить" всё приложение. Все параллельные стримы в твоей JVM будут ждать ответа от API в одном и том же пуле потоков. Это классический пример *Thread Starvation*.

**В: Можно ли использовать `parallelStream()` с `LinkedList` эффективно?**
**О:** Нет. `LinkedList` не поддерживает быстрый случайный доступ. Чтобы разделить его пополам, `Spliterator` придется пройтись по всем элементам от начала до середины. Это убивает весь смысл параллелизма.

**В: В чем разница между `stream().parallel()` и `parallelStream()`?**
**О:** Разницы в работе нет. `parallelStream()` — это просто удобный синтаксический сахар для вызова `.parallel()` у существующего стрима.

**В: Как избежать Race Condition при использовании параллельного стрима?**
**О:** Используй потокобезопасные коллекторы (например, `Collectors.toConcurrentMap()`) или старайся проектировать операции так, чтобы они были *stateless* (не зависели от внешнего состояния).

**В: Всегда ли параллельный стрим быстрее?**
**О:** Нет. Из-за затрат на разделение данных (`split`), создание задач и их последующую сборку (`merge`), на малых данных параллельный стрим почти всегда медленнее последовательного.

# 🧠 Шпаргалка: Java 8 New Date/Time API (`java.time`)

### ❌ Почему старый API (`Date`, `Calendar`) — это зло?
Прежде чем изучать новое, нужно понять, от чего мы бежим:
1.  **Mutable (Изменяемость):** Вызвал `.setTime()`, и объект изменился. Это смерть для многопоточности.
2.  **Thread-unsafe:** Нельзя использовать `SimpleDateFormat` в разных потоках одновременно без `synchronized`.
3.  **Странная логика:** Месяцы начинались с **0** (январь — это 0), что порождало бесконечные баги.
4.  **Плохое разделение ответственности:** `Date` представлял и дату, и время, и часовой пояс в одной куче.

### ✅ Главные принципы нового API
*   **Immutability (Неизменяемость):** Все объекты — `final`. Любая операция (`plusDays`, `withMonth`) возвращает **новый** объект.
*   **Thread-safety:** Благодаря неизменяемости, объекты можно спокойно шарить между потоками.
*   **ISO-8601:** Стандартный формат хранения (YYYY-MM-DD).
*   **Fluent API:** Код читается как предложение: `date.plusDays(5).minusHours(2)`.

---

### 🛠 Основные классы (Твой инструментарий)

#### 1. Без привязки к часовому поясу (Local) — "Только то, что видим на часах"
Используй, если тебе не важно, в каком городе находится пользователь.
*   **`LocalDate`**: Только дата (`2023-10-25`).
*   **`LocalTime`**: Только время (`14:30:05`).
*   **`LocalDateTime`**: Дата + Время (`2023-10-25T14:30:05`). *Внимание: здесь нет информации о часовом поясе!*

#### 2. С привязкой к моменту во времени (Global/Instant)
Используй для логов, системных событий и работы с сервером.
*   **`Instant`**: Точка на временной шкале (UTC). Это "чистое" время в миллисекундах/наносекундах от Epoch. Идеально для хранения `created_at` в БД.
*   **`ZonedDateTime`**: Полный фарш. Дата + Время + Часовой пояс (`Europe/Moscow`). Учитывает переходы на летнее/зимнее время.
*   **`OffsetDateTime`**: Дата + Время + Смещение от UTC (`+03:00`). Похоже на `ZonedDateTime`, но не знает про правила перехода времени (просто число).

#### 3. Измерение промежутков (Intervals)
*   **`Duration`**: Разница во **времени** (часы, минуты, секунды, наносекунды). Работает с `Instant` или `LocalTime`.
*   **`Period`**: Разница в **датах** (годы, месяцы, дни). Работает с `LocalDate`.

---

### ⚙️ Основные операции

**Создание:**
```java
LocalDate date = LocalDate.now(); // Текущая дата
LocalDate specificDate = LocalDate.of(2023, Month.OCTOBER, 25); // Своя дата
Instant now = Instant.now(); // Точка в UTC
```

**Манипуляция (Всегда возвращает НОВЫЙ объект!):**
```java
LocalDate nextWeek = date.plusWeeks(1);
LocalDate lastMonth = date.minusMonths(1);
LocalDateTime updatedTime = dateTime.withHour(10).withMinute(0); // Замена части данных
```

**Форматирование и Парсинг:**
`DateTimeFormatter` — это замена `SimpleDateFormat`. Он **Thread-safe**.
```java
DateTimeFormatter formatter = DateTimeFormatter.ofPattern("dd/MM/yyyy");
String formatted = date.format(formatter); // "25/10/2023"

LocalDate parsed = LocalDate.parse("2023-10-25", formatter); 
```

---

### ⚠️ Нюансы и Senior Tips (На чем валятся)

1.  **Забытая переменная:** Самая частая ошибка — написать `date.plusDays(5);` и не присвоить результат новой переменной. Объект `date` **не изменился**.
2.  **Выбор между ZonedDateTime и OffsetDateTime:** Если ты пишешь логику для календаря встреч (где важно летнее время) — бери `ZonedDateTime`. Если ты просто сохраняешь метку времени из API — бери `Instant` или `OffsetDateTime`.
3.  **Сравнение:** Для сравнения используй `.isBefore()`, `.isAfter()` или `.equals()`. Не используй старые методы сравнения объектов, если не уверен в логике.
4.  **БД и JDBC:** При работе с Hibernate/JPA убедись, что драйвер БД поддерживает `java.time` (современные драйверы — да), иначе придется делать маппинг вручную.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `Duration` и `Period`?**
**О:** `Duration` измеряет время в физических единицах (секунды, наносекунды), а `Period` — в календарных (дни, месяцы, годы). Если ты прибавишь `Period` к дате, результат может отличаться по количеству часов из-за перехода на летнее время.

**В: Можно ли использовать `LocalDate` для хранения времени транзакции?**
**О:** Нет. Для транзакций критически важно точное время (часы/минуты) и часовой пояс (UTC), поэтому используй `Instant`.

**В: Почему `DateTimeFormatter` лучше, чем `SimpleDateFormat`?**
**О:** Главная причина — **потокобезопасность**. `SimpleDateFormat` имеет внутреннее состояние (stateful), что приводит к непредсказуемым результатам при одновременном доступе из разных потоков. `DateTimeFormatter` неизменяем и безопасен.

**В: Что произойдет, если я создам `LocalDateTime` и прибавлю к нему день, когда происходит переход на летнее время?**
**О:** В `LocalDateTime` ничего "не сломается", так как он не знает о часовых поясах. Но если ты конвертируешь его в `ZonedDateTime`, Java автоматически скорректирует смещение (offset) согласно правилам указанного региона.

# 🧠 Java 8: `Optional<T>` — Шпаргалка

### 🎯 Что это такое?
`Optional<T>` — это контейнер (обертка), который может либо содержать один объект, либо быть пустым. 
**Главная цель:** Явно сказать программисту: *"Внимание! Здесь может не быть значения"*. Это способ избежать классического `NullPointerException` (NPE) и избавиться от бесконечных проверок `if (obj != null)`.

---

### 🛠 Как создавать (Factory Methods)
Есть три способа инициализации, и важно понимать разницу:

1.  **`Optional.empty()`** — создает пустой контейнер.
2.  **`Optional.of(value)`** — создает контейнер с конкретным значением. 
    ⚠️ **Нюанс:** Если `value` окажется `null`, ты тут же получишь `NullPointerException`. Используй только тогда, когда уверен на 100%, что значение есть.
3.  **`Optional.ofNullable(value)`** — самый безопасный и часто используемый метод. Если придет `null`, он просто вернет `empty()`.

---

### 🔍 Проверка и извлечение (The Dangerous & The Safe)

#### ❌ Плохой путь (Anti-pattern):
```java
Optional<String> name = ...;
String value = name.get(); // Если внутри пусто — бабах! NoSuchElementException
```
Использование `.get()` без предварительной проверки `.isPresent()` превращает `Optional` в обычный `null`, только еще и с лишним расходом памяти.

#### ✅ Хороший путь (Functional Style):
*   **`ifPresent(Consumer)`** — выполни действие, если значение есть.
    `name.ifPresent(n -> System.out.println(n.length()));`
*   **`orElse(defaultValue)`** — верни дефолтное значение, если пусто. 
    ⚠️ **Нюанс:** `defaultValue` вычисляется **всегда**, даже если `Optional` не пустой (это может быть дорого по ресурсам).
*   **`orElseGet(Supplier)`** — верни результат работы функции, если пусто.
    ✅ **Senior Tip:** Используй `orElseGet`, если создание дефолтного значения требует вычислений или обращения к БД. Он выполнится **только** если нужно.
*   **`orElseThrow()`** — выбросит исключение, если пусто (по умолчанию `NoSuchElementException`).

---

### 🌊 Манипуляция данными (Fluent API)
`Optional` работает в стиле Stream API:

*   **`filter(Predicate)`** — оставляет значение, если оно соответствует условию, иначе возвращает `empty()`.
*   **`map(Function)`** — трансформирует значение внутри. Если было пусто — останется пусто.
*   **`flatMap(Function)`** — то же самое, что `map`, но если твоя функция сама возвращает `Optional`, то `flatMap` "развернет" его, чтобы у тебя не получился `Optional<Optional<String>>`.

---

### 🚫 Золотые правила (Senior Advice)

1.  **Не используй `Optional` как тип поля класса.** Он не сериализуем и добавляет лишнюю нагрузку на память. Поля должны быть обычными типами, а `Optional` — только возвращаемым типом метода.
2.  **Не передавай `Optional` в аргументы методов.** Это заставляет вызывающую сторону создавать лишние объекты. Лучше использовать перегрузку методов или аннотации `@Nullable`.
3.  **`Optional` — это для возврата значений из методов.** Его задача — сигнализировать о "пустоте" результата операции.
4.  **Не злоупотребляй в коллекциях.** `List<Optional<String>>` — это плохой тон. Если списка может не быть, пусть будет пустой список.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `orElse` и `orElseGet`?**
**О:** В жадности. `orElse` вычисляет аргумент всегда (eager evaluation). `orElseGet` вызывает лямбду только тогда, когда это действительно нужно (lazy evaluation). Если создание дефолтного значения — тяжелая операция, используй только `orElseGet`.

**В: Можно ли использовать `Optional` для примитивов?**
**О:** Использовать `Optional<Integer>` — плохая идея из-за лишней упаковки (autoboxing). Для этого в Java 8 появились специальные классы: `OptionalInt`, `OptionalLong`, `OptionalDouble`. Они эффективнее.

**В: Что произойдет, если вызвать `Optional.of(null)`?**
**О:** Мгновенный `NullPointerException`. Этот метод предназначен только для гарантированно не-null значений.

**В: Помогает ли `Optional` полностью избавиться от NPE?**
**О:** Нет. Он лишь помогает избежать их в логике обработки возвращаемых значений. Если ты внутри `map` или `filter` обратишься к методу объекта, который сам по себе может быть `null`, ты всё равно получишь ошибку. Это инструмент для проектирования API, а не магический щит.

# 🧠 Java 8 Cheat Sheet: Default & Static Methods in Interfaces

### 📌 Контекст (Зачем это вообще ввели?)
До Java 8 интерфейсы были "чистыми": только сигнатуры методов, никакого тела. Если ты хотел добавить новый метод в популярный интерфейс (например, в `List`), тебе пришлось бы переписывать **все** существующие реализации (ArrayList, LinkedList и т.д.), иначе код просто не скомпилировался бы. 

**Default methods** решили проблему **обратной совместимости**. Теперь можно расширять интерфейсы, не ломая старый код.

---

### 1. Default Methods (Методы по умолчанию)
Это методы в интерфейсе, которые имеют реализацию.

*   **Ключевое слово:** `default`.
*   **Суть:** Реализация "подмешивается" всем классам, которые реализуют этот интерфейс автоматически.
*   **Зачем использовать:** 
    1.  Добавление нового функционала в существующие интерфейсы (Evolution of APIs).
    2.  Предоставление "опционального" поведения (классу не обязательно переопределять метод, если стандартный его устраивает).

**Пример:**
```java
interface Vehicle {
    void drive(); // Абстрактный метод

    default void honk() {
        System.outary.println("Beep beep!"); // Реализация по умолчанию
    }
}

class Car implements Vehicle {
    @Override
    public void drive() {
        System.out.println("Car is driving");
    }
    // Метод honk() уже есть в Car "из коробки"
}
```

---

### 2. Static Methods in Interfaces (Статические методы)
Это методы, которые принадлежат самому интерфейсу, а не объекту.

*   **Ключевое слово:** `static`.
*   **Суть:** Их нельзя переопределить (override) в классах-наследниках. Они вызываются только через имя интерфейса: `InterfaceName.method()`.
*   **Зачем использовать:** 
    1.  Создание утилит, логически связанных с интерфейсом (вместо создания отдельных классов `Collections`, `CollectionsUtils` и т.д.).
    2.  Группировка вспомогательного кода внутри самого интерфейса для лучшей инкапсуляции.

**Пример:**
```java
interface Validator {
    static boolean isNotEmpty(String s) {
        return s != null && !s.isEmpty();
    }
}

// Вызов:
boolean valid = Validator.isNotEmpty("Hello"); 
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Level)

#### 1. Проблема множественного наследования (The Diamond Problem)
Если класс реализует два интерфейса, и в обоих есть `default` метод с одинаковой сигнатурой, возникнет конфликт. Компилятор не знает, какой метод выбрать, и выдаст ошибку.

**Как решать?** Нужно явно переопределить метод в классе и решить, чью логику использовать.
*   Использовать синтаксис: `InterfaceName.super.methodName();`

```java
interface InterfaceA {
    default void action() { System.out.println("From A"); }
}

interface InterfaceB {
    default void action() { System.out.println("From B"); }
}

class MyClass implements InterfaceA, InterfaceB {
    @Override
    public void action() {
        // Выбираем явно:
        InterfaceA.super.action(); 
    }
}
```

#### 2. Приоритет методов (Rule of Resolution)
При поиске метода JVM следует строгому порядку:
1.  **Класс (Class wins):** Если в самом классе или его суперклассе есть метод с такой же сигнатурой, он всегда побеждает интерфейсные `default` методы.
2.  **Интерфейс (Interface wins):** Если конфликта между классами нет, выбирается наиболее "специфичный" интерфейс.

#### 3. Static vs Default
*   `static` методы **не наследуются** в привычном смысле. Ты не можешь вызвать `myCar.staticMethod()`, только `Vehicle.staticMethod()`.
*   `default` методы **наследуются** и доступны через экземпляр объекта.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли переопределить static метод интерфейса в классе?**
**О:** Нет. Ты можешь создать метод с такой же сигнатурой в классе, но это будет не переопределение (Override), а просто новый метод класса (или скрытие, если бы это был статический метод класса). Аннотация `@Override` здесь не сработает.

**В: В чем разница между default и static методами в интерфейсе?**
**О:** `default` методы доступны через объект (instance) и могут быть переопределены. `static` методы принадлежат интерфейсу, вызываются по имени интерфейса и не могут быть переопределены.

**В: Что произойдет, если класс реализует два интерфейса с одинаковым default методом?**
**О:** Произойдет ошибка компиляции (Conflict). Разработчик обязан вручную переопределить этот метод в классе и явно указать, какую реализацию использовать через `InterfaceName.super.method()`.

**В: Почему нельзя просто использовать обычные статические методы в классах-утилитах вместо static методов в интерфейсах?**
**О:** Можно. Но использование `static` методов в интерфейсе делает API более чистым и связанным (Cohesion). Это логически группирует утилиты прямо там, где они нужны — рядом с контрактом (интерфейсом).

# 📜 Шпаргалка: Java 8 — Nashorn JavaScript Engine

### 💡 Что это такое?
**Nashorn** — это высокопроизводительный движок JavaScript, встроенный в JDK начиная с версии 8. Его главная задача — позволить выполнять JavaScript-код прямо внутри Java-приложения. Это не просто «запуск скриптов», это полноценная интеграция двух миров.

### 🚀 Зачем он нужен? (Use Cases)
1.  **Динамическая логика:** Возможность менять бизнес-правила (скрипты) без пересборки и перезапуска всего Java-приложения.
2.  **Scripting API:** Реализация механизма плагинов, где пользователь пишет скрипт на JS, а ваша система его исполняет.

3.  **Interoperability:** Легкий доступ к Java-классам и методам прямо из JavaScript.

### 🛠 Как это работает (Code Implementation)

Для работы с Nashorn используется стандартный API — `javax.script`.

#### 1. Базовый запуск скрипта
```java
import javax.script.ScriptEngine;
import javax.script.ScriptEngineManager;
import javax.script.ScriptException;

public class NashornExample {
    public static void main(String[] args) throws ScriptException {
        // 1. Создаем менеджер движков
        ScriptEngineManager manager = new ScriptEngineManager();
        // 2. Получаем движок "javascript" (Nashorn)
        ScriptEngine engine = manager.getEngineByName("javascript");

        // 3. Выполняем простой код
        String script = "var x = 10; var y = 20; x + y;";
        Object result = engine.eval(script);

        System.out.println("Result: " + result); // Output: 30
    }
}
```

#### 2. Магия Interoperability (Java $\leftrightarrow$ JS)
Это самая мощная фишка. Вы можете прокинуть Java-объект в контекст скрипта.

**Java side:**
```java
// Создаем Java-объект
StringBuilder sb = new StringBuilder("Hello from Java!");
engine.put("javaSb", sb); // Кладем его в "глобальную переменную" скрипта

// Выполняем JS, который манипулирует Java-объектом
engine.eval("javaSb.append(' and Nashorn!');");

System.out.println(sb.toString()); // Output: Hello from Java! and Nashorn!
```

**JS side (вызов статического метода Java):**
```javascript
// Внутри JS можно обращаться к классам Java напрямую
var Date = Java.type('java.util.Date');
var now = new Date();
print(now); 
```

### ⚠️ Важные нюансы (Senior Level)

1.  **Смерть Nashorn (Deprecation):** Это критически важно! Nashorn был объявлен **deprecated в Java 11** и полностью **удален из JDK в Java 15**. Если ты пишешь современный проект на Java 17+, Nashorn там нет «из коробки». Нужно подключать стороннюю библиотеку (например, GraalVM JavaScript).
2.  **Стандарт ECMAScript:** Nashorn поддерживает стандарт **ES5.1**. Это значит, что современные фишки вроде `const`, `let`, стрелочных функций (`=>`) или `async/await` в нем **не работают** (или работают с огромным трудом через костыли).
3.  **Производительность:** Он очень быстрый для своего времени благодаря JIT-компиляции, но он не сравнится с Google V8. Однако для простых скриптов его хватает за глаза.
4.  **Безопасность (Sandboxing):** Если вы позволяете пользователям загружать свои JS-скрипты, помните: по умолчанию у них есть доступ к `java.lang.System.exit(0)` и другим опасным вещам через Java API. Нужно настраивать `ClassFilter` или использовать другие механизмы ограничения прав.

# 🧠 Шпаргалка: Java 9 Module System (Project Jigsaw)

### 🎯 Суть темы
До Java 9 всё работало через **Classpath**. Это был "хаос": если ты добавил JAR-ник, все его классы были доступны всем. Это приводило к «JAR Hell» (конфликты версий) и невозможности скрыть внутренние API JDK.

**Module System** — это способ группировать пакеты в логические блоки (**модули**) и явно прописывать: что этот модуль отдает наружу, а что использует сам. Теперь у нас есть **Modulepath** вместо одного огромного Classpath.

---

### 🏗 Основные понятия

1.  **Модуль (Module):** Набор пакетов + файл `module-info.java`.
2.  **`module-info.java`:** Сердце модуля. Файл, где прописаны все зависимости и границы доступа.
*   **Strong Encapsulation (Сильная инкапсуляция):** Даже если класс `public`, ты не сможешь его использовать, если пакет, в котором он лежит, не **экспортирован** модулем.

---

### 🛠 Ключевые директивы в `module-info.java`

| Директива | Что делает | Аналогия |
| :--- | :--- | :--- |
| **`requires <mod>`** | Модуль зависит от другого модуля. Без этого не скомпилируется. | "Мне нужен этот инструмент". |
| **`exports <pkg>`** | Открывает пакет для использования другими модулями (только `public` классы). | "Этот отдел открыт для посещений". |
| **`opens <pkg>`** | Разрешает доступ к пакету через **Reflection** (даже к `private` полям). | "В этот отдел можно заглядывать через окно (рефлексия)". |
| **`requires transitive <mod>`** | Если модуль А требует модуль B транзитивно, то любой, кто подключит А, автоматически получит и B. | "Цепная реакция зависимостей". |
| **`provides <service> with <impl>`** | Реализация паттерна Service Provider Interface (SPI). | "Мы предоставляем этот сервис через этот класс". |
| **`uses <service>`** | Объявление того, что модуль ищет реализации сервиса. | "Я умею пользоваться этим инструментом". |

---

### ⚠️ Важные нюансы (Senior Level)

1.  **Exports vs Opens (Критически важно!):**
    *   `exports` — дает доступ к **публичному** коду на этапе компиляции и выполнения. Но ты не можешь через рефлексию достучаться до `private` полей в экспортируемом пакете.
    *   `opens` — позволяет использовать Reflection для доступа к **любому** (включая `private`) контенту пакета. Это нужно для фреймворков вроде Spring или Hibernate.

2.  **Split Packages (Проблема разделенных пакетов):**
    В модульной системе **запрещено**, чтобы один и тот же пакет (`com.example.utils`) находился в двух разных модулях. Это вызывает ошибку при запуске. Раньше в Classpath это было возможно и порождало баги.

3.  **Encapsulation of JDK Internals:**
    До Java 9 можно было через рефлексию "взломать" внутренности самой JVM (например, классы `sun.misc.Unsafe`). В Java 9+ эти внутренние части JDK закрыты по умолчанию. Если очень нужно — придется использовать флаг `--add-opens`.

4.  **jlink:**
    Благодаря модулям, ты можешь собрать **свою собственную облегченную JRE**, включив в неё только те модули, которые нужны твоему приложению. Это уменьшает размер образа (актуально для Docker/Cloud).

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем Modulepath отличается от Classpath?**
**О:** Classpath — это просто список JAR-файлов, где всё доступно всем. Modulepath — это структурированный список модулей с четко прописанными правилами видимости и зависимостей.

**В: Что будет, если я экспортирую пакет (`exports`), но не открою его (`opens`)? Смогу ли я изменить `private` поле через рефлексию?**
**О:** Нет. `exports` позволяет видеть только `public` члены класса. Для доступа к `private` полям через Reflection обязательно нужен `opens`.

**В: Зачем нужен `requires transitive`?**
**О:** Чтобы избежать "каскадного" написания зависимостей. Если твой модуль `API` использует библиотеку `JSON`, и ты хочешь, чтобы все пользователи твоего `API` сразу имели доступ к `JSON` без лишних строк в их конфигах, используй `requires transitive`.

**В: Как решить проблему "Split Package", если я обнаружил один и тот же пакет в двух разных модулях?**
**О:** Единственное правильное решение — объединить эти пакеты в один модуль или переименовать пакеты так, чтобы они не пересекались. Переименование — самый безопасный путь.

# 🐚 Java 9: JShell (REPL)

### Что это такое?
**JShell** — это **REPL** (Read-Eval-Print Loop). Если говорить по-простому: это интерактивная консоль, где ты можешь писать код на Java и сразу получать результат, не создавая проект, не написав `public static void main(String[] args)` и не запуская компиляцию.

До Java 9, чтобы проверить, как работает одна строчка кода (например, регулярное выражение или метод `String.split`), тебе нужно было создать класс, метод, запустить IDE/Maven и только потом увидеть результат. JShell убирает этот «бюрократический» барьер.

### Ключевые возможности
1.  **Инкрементальность:** Ты можешь вводить код по кусочкам. Сначала объявил переменную, следующим шагом — метод, который её использует. Состояние (переменные, методы, классы) сохраняется в рамках одной сессии.
2.  **Отсутствие бойлерплейта:** Тебе не нужно объявлять класс или метод для простых вычислений. Пишешь `x = 10` — и всё, переменная живет в памяти JShell.
3.  **Скриптинг:** Ты можешь записывать свои команды в файлы с расширением `.jsh` и запускать их как скрипты.
4.  **Инспекция текущего состояния:** Внутри JShell есть специальные команды, чтобы посмотреть, что ты уже «напрограммировал» за текущую сессию.

### Основные команды (Slash Commands)
В JShell все системные команды начинаются со слеша `/`.

*   `/list` — показать весь код, который ты ввел в текущей сессии.
*   /vars — список всех объявленных переменных и их текущие значения.
*   `/methods` — список всех методов.
*   `/classes` — список всех классов.
*   `/edit <name>` — открыть встроенный редактор для изменения конкретного метода или класса (очень удобно, если накосячил в длинном коде).
*   `/open <file.jsh>` — запустить скрипт из файла.
*   `/drop <name>` — удалить переменную, метод или класс из памяти.
*   `/exit` — выход из JShell.
*   `/help` — справка по всем командам.

### Нюансы от Senior-а 💡

1.  **Среда выполнения:** Помни, что JShell — это не замена IDE. Это инструмент для **прототипирования** и **обучения**. Не пытайся писать там сложную бизнес-логику с кучей зависимостей.
2.  **Автоматический импорт:** JShell по умолчанию импортирует базовые пакеты (`java.lang.*`, `java.util.*` и др.). Тебе не нужно писать `import java.util.List;`, он уже там. Но если тебе нужен специфичный класс из сторонней библиотеки, придется сделать `import`.
3.  **Скрытая переменная `$JShell$`:** Внутри сессии существует специальный объект `$JShell$`. Через него можно программно управлять текущей сессией (например, через него можно получить доступ к списку всех переменных). Это полезно для продвинутого автоматизированного тестирования кода "на лету".
4.  **Scope (Область видимости):** Все, что ты ввел, имеет глобальную область видимости внутри текущей сессии. Если ты объявил `int a = 5;`, эта переменная доступна во всех последующих методах, которые ты напишешь в этой же сессии.

### FAQ (Часто задаваемые вопросы)

**В: Можно ли использовать JShell для тестирования сторонних библиотек (например, Jackson или Guava)?**
**О:** Да! Тебе нужно просто запустить JShell с указанием classpath этих библиотек. Например: `jshell --class-path my-libs.jar`. Это идеальный способ быстро проверить, как парсится JSON конкретной версией библиотеки.

**В: Что произойдет с моими переменными, если я закрою терминал?**

**В: Я написал метод с ошибкой, как его исправить, не переписывая всё заново?**
**О:** Используй команду `/edit <имя_метода>`. Откроется текстовый редактор. Исправь ошибку, сохрани и закрой редактор — JShell перекомпилирует только этот метод.

**В: Можно ли в JShell использовать циклы `for` или `if` вне методов?**

# 🚀 Java 9: Factory Methods for Collections

До Java 9 создание небольших неизменяемых коллекций было тем еще квестом: нужно было либо использовать `Arrays.asList(...)` (который не совсем то, что вы думаете), либо создавать пустую коллекцию и наполнять её в несколько строк. Java 9 принесла лаконичные **Static Factory Methods**.

### 🛠 Что появилось?
В интерфейсах `List`, `Set` и `Map` появились методы `.of()` (и его вариации):
*   `List.of(e1, e2, ...)`
*   `Set.of(e1, e2, ...)`
*   `Map.of(k1, v1, k2, v2, ...)`
*   `Map.ofEntries(entry(k1, v1), ...)` — для большого количества элементов.

### 💎 Главные особенности (то, что важно знать)

1.  **Immutability (Неизменяемость):** Коллeкции, созданные через `.of()`, являются **unmodifiable**. Вы не можете добавить (`add`), удалить (`remove`) или заменить элемент. Попытка изменить коллекцию приведет к `UnsupportedOperationException`.
2.  **No Nulls (Никаких null!):** Это критически важный момент. Методы `.of()` **запрещают** использование `null` как ключа или значения. Если попытаетесь передать `null`, получите `NullPointerException` сразу при создании коллекции.
3.  **No Duplicates (Для Set и Map):** Если вы попытаетесь создать `Set.of(1, 1, 2)`, Java выбросит `IllegalArgumentException`, так как дубликаты недопустимы на этапе инициализации.
4.  **Memory Efficiency:** Эти методы оптимизированы под капотом. Для маленьких коллекций (0, 1, 2 элемента) Java использует специальные внутренние реализации, которые потребляют гораздо меньше памяти, чем стандартный `ArrayList` или `HashSet`.

---

### ⚠️ Главная ловушка: `List.of()` vs `Arrays.asList()`
Это классический вопрос на собеседовании. Разница принципиальна:

| Характеристика | `Arrays.asList(T... a)` | `List.of(T... elements)` |
| :--- | :--- | :--- |
| **Изменяемость** | **Fixed-size** (размер нельзя менять, но элементы *можно* заменить через `.set()`) | **Truly Unmodifiable** (нельзя ни размер менять, ни элементы заменять) |
| **Null-safety** | Разрешает `null` элементы | **Запрещает** `null` (бросает NPE) |
| **Связь с массивом** | Работает как "обертка" над массивом. Измените массив — изменится список. | Создает независимую копию данных. |

---

### ❓ FAQ (Частые вопросы на интервью)

**В: Можно ли добавить элемент в `List.of("A", "B")`?**
**О:** Нет, это вызовет `UnsupportedOperationException`. Список неизменяем.

**В: Что произойдет, если я передам `null` в `Map.of("key", null)`?**
**О:** Вы получите `NullPointerException` мгновенно. Java 9+ строго следит за тем, чтобы в таких фабричных методах не было «грязных» данных.

**В: Почему стоит использовать `.of()`, если есть `Collections.unmodifiableList()`?**
**О:** `List.of()` — это более современный, лаконичный и производительный способ. Он сразу создает оптимизированную структуру, в то время как `unmodifiableList` — это просто "обертка" над уже существующим (и потенциально изменяемым) списком.

**В: Как создать Map с очень большим количеством элементов?**
**О:** Для большого количества пар лучше использовать `Map.ofEntries(Map.entry(k1, v1), ...)` вместо `Map.of(...)`, так как у `Map.of` есть ограничение на количество аргументов (максимум 10 пар).

# 🧠 Java 10: Local Variable Type Inference (`var`)

### 💡 Суть в двух словах
В Java 10 появился ключевое слово `var`. Оно позволяет компилятору самому догадаться (вывести), какой тип данных у переменной, основываясь на том, что ты присваиваешь ей справа.

**Важнейшее уточнение:** Java **не стала** динамически типизированным языком (как Python или JS). Тип переменной определяется **в момент компиляции** и больше не меняется. Это «синтаксический сахар», который просто избавляет тебя от написания длинных названий классов.

---

### 🛠 Как это работает (Правила игры)

#### 1. Обязательная инициализация
Ты не можешь просто объявить `var x;`. Компилятор должен увидеть значение, чтобы понять тип.
```java
var a = 10;      // OK: int
var b;           // ERROR: Cannot infer type without initializer
```

#### 2. Только локальные переменные
`var` можно использовать **только внутри методов**, блоков кода (`if`, `for`, `try-with-resources`) или в лямбдах.
*   ❌ Нельзя использовать для полей класса (class members).
*   ❌ Нельзя использовать для параметров методов.
*   ❌ Нельзя использовать для возвращаемого типа метода.

#### 3. Тип фиксирован
После того как компилятор определил тип, ты не можешь положить туда что-то другое.
```java
var list = new ArrayList<String>();
list = new LinkedList<String>(); // OK: типы совместимы (List)
list = "Hello";                   // ERROR: String не является List
```

#### 4. Проблема `null`
Ты не можешь инициализировать `var` значением `null`, потому что из `null` нельзя вывести тип.
```java
var x = null; // ERROR: What is x? String? Integer? The compiler is lost.
```

---

### ⚖️ Senior's Guide: Когда использовать, а когда — нет

Это самый важный момент. Использование `var` — это вопрос **читаемости**, а не экономии нажатий клавиш.

#### ✅ Хороший тон (Use it when...)
Когда тип переменной очевиден из правой части выражения. Это убирает «визуальный шум».
```java
// Было (громоздко)
Map<User, List<Order>> userOrders = new HashMap<User, List<Order>>();

// Стало (чисто и понятно)
var userOrders = new HashMap<User, List<Order>>(); 

// Использование с фабричными методами или конструкторами
var stream = Stream.of("A", "B", "C").filter(s -> s.startsWith("A"));
```

#### ❌ Плохой тон (Avoid it when...)
Когда использование `var` скрывает смысл кода и заставляет коллегу лезть в документацию или другие файлы, чтобы понять, что за объект перед ним.
```java
// ПЛОХО: Что такое result? String? Boolean? User?
var result = service.process(); 

// ХОРОШО: Тип виден из названия метода
User processedUser = service.processUser(id);
```

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: `var` делает Java динамически типизированным языком?**
**О:** Нет. Типизация остается статической. Разница лишь в том, что тебе не нужно явно писать имя типа — компилятор делает это за тебя на этапе сборки проекта. В байт-коде всё равно будут четкие типы `int`, `String` и т.д.

**В: Влияет ли использование `var` на производительность приложения?**
**О:** Нет. На работу в Runtime (во время выполнения) это никак не влияет. Весь «магический» процесс происходит только во время компиляции. Итоговый `.class` файл будет содержать те же типы, что и при явном объявлении.

**В: Можно ли использовать `var` в циклах `for-each`?**
**О:** Да, это отличный кейс. 
`for (var user : users) { ... }` — это абсолютно легально и удобно, если тип коллекции понятен.

**В: Что будет, если я напишу `var x = 10.0;`?**
**О:** Компилятор выведет тип `double`. Если ты захочешь потом присвоить туда целое число (int), возникнет ошибка компиляции, так как типы несовместимы без явного приведения.

# 🚀 Шпаргалка: Java 11 HTTP API Evolution

До Java 11 мы использовали старый добрый (но ужасный) `HttpURLConnection`. Он был синхронным, неудобным, не поддерживал современные протоколы «из коробки» и требовал тонны шаблонного кода. 

В Java 11 появился новый пакет **`java.net.http`**, который принес современный, реактивный и удобный API.

### 🏗 Основные компоненты (The Big Three)

Весь процесс строится вокруг трех китов:

1.  **`HttpClient`** — «Движок». Это сам клиент, который управляет соединениями, пулом потоков и протоколами. Его нужно создавать один раз и переиспользовать.
2.  **`HttpRequest`** — «Запрос». Описывает, куда мы идем (URL), какой метод используем (GET, POST), какие заголовки (headers) и тело (body) передаем. Создается через Builder.
3.  **`HttpResponse`** — «Ответ». Содержит статус-код, заголовки ответа и само тело ответа.

---

### 🛠 Ключевые фишки (Почему это круто)

*   **HTTP/2 & HTTP/1.1:** Поддержка современного протокола HTTP/2 (мультиплексирование, сжатие заголовков) по умолчанию.
*   **Асинхронность (Non-blocking):** Встроенная поддержка `CompletableFuture`. Можно отправить запрос и не ждать его завершения, а продолжить работу программы.
*   **Fluent API:** Использование паттерна Builder делает код читаемым, как предложение на английском языке.
*   **WebSocket:** В этот же пакет включена полноценная поддержка веб-сокетов для двусторонней связи.

---

### 💻 Код: Синхронный и Асинхронный подходы

#### 1. Простой GET запрос (Синхронно)
*Используй, когда тебе нужно получить данные прямо сейчас и ты не можешь идти дальше без них.*

```java
HttpClient client = HttpClient.newHttpClient(); // Создаем клиент

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/data"))
        .GET() // По умолчанию GET, но лучше указывать явно
        .build();

// .send() блокирует текущий поток до получения ответа
HttpResponse<String> response = client.send(request, HttpResponse.BodyHandlers.ofString());

System.out.println("Status: " + response.statusCode());
System.out.println("Body: " + response.body());
```

#### 2. Мощный POST запрос (Асинхронно)
*Используй в высоконагруженных системах, чтобы не блокировать потоки приложения.*

```java
HttpClient client = HttpClient.newHttpClient();

String jsonBody = "{\"name\":\"Java11\"}";

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/post"))
        .header("Content-Type", "application/json")
        .POST(HttpRequest.BodyPublishers.ofString(jsonBody)) // Используем Publisher для тела
        .build();

// .sendAsync() возвращает CompletableFuture
client.sendAsync(request, HttpResponse.BodyHandlers.ofString())
        .thenApply(HttpResponse::body) // Извлекаем тело из ответа
        .thenAccept(System.out::println) // Печатаем результат
        .exceptionally(ex -> {           // Обработка ошибок
            System.err.println("Error: " + ex.getMessage());
            return null;
        });
```

---

### ⚠️ Нюансы и Senior-советы (Don't forget!)

1.  **Переиспользование клиента:** **Никогда** не создавай `HttpClient` на каждый запрос. Это дорого! Создай один экземпляр (Singleton или Bean в Spring) и используй его везде. Он эффективно управляет пулом соединений.
2.  **BodyHandlers & BodyPublishers:** 
    *   `BodyHandlers` — это про то, как **читать** ответ (в строку, в байты, в файл или через поток).
    *   `BodyPublishers` — это про то, как **отправлять** данные (из строки, из файла, из массива байт).
3.  **Таймауты (Timeouts):** Всегда устанавливай таймаут на запрос (`.timeout(Duration.ofSeconds(10))`). Без него твой поток может «зависнуть» навсегда, если удаленный сервер не отвечает.
4.  **Обработка ошибок:** В асинхронном режиме ошибки (например, `ConnectException`) не выкинут исключение в текущий поток, они упадут в `CompletableFuture`. Всегда используй `.exceptionally()` или `.handle()`.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем `HttpClient` лучше старого `HttpURLConnection`?**
**О:** Поддержкой HTTP/2, встроенной асинхронностью через `CompletableFuture`, более чистым API (Builder pattern) и удобной работой с потоками данных (BodyHandlers).

**В: Можно ли использовать `HttpClient` для работы только по HTTP/1.1?**
**О:** Да. Ты можешь явно указать версию протокола при создании клиента: `HttpClient.newBuilder().version(HttpClient.Version.HTTP_1_1).build();`.

**В: Является ли `HttpClient` потокобезопасным (Thread-safe)?**
**О:** Да, сам объект `HttpClient` спроектирован так, чтобы его можно было использовать из разных потоков одновременно. Однако каждый конкретный `HttpRequest` — это неизменяемый (immutable) объект, его нельзя «подправить» на лету, можно только создать новый через Builder.

**В: Что произойдет, если я не укажу BodyHandler?**
**О:** Тебе придется указать его при вызове метода `.send()`. API спроектировано так, чтобы ты явно определил, в каком виде ты хочешь получить данные (String, File, InputStream), так как это напрямую влияет на потребление памяти.

# 📝 Шпаргалка: Java 11 — String Improvements

В Java 11 разработчики языка не стали менять внутреннюю структуру `String` (она всё так же неизменяема/immutable), но добавили «синтаксический сахар» и новые утилиты, которые избавляют нас от написания громоздкого шаблонного кода. Основной фокус — на чистоте кода и поддержке Unicode.

### 1. Проверка на пустоту: `isBlank()`
До Java 11 мы часто писали `str.trim().isEmpty()`. Это создавало лишний объект строки в памяти (результат `trim()`).

*   **`isEmpty()`**: Возвращает `true`, только если `length == 0`. Пробелы — это не пустота.
*   **`isBlank()`**: Возвращает `true`, если строка пустая **или** состоит только из пробельных символов (пробел, табуляция, перенос строки и т.д.).

**Пример:**
```java
String str = "   ";
System.out.println(str.isEmpty()); // false
System.out.println(str.isBlank()); // true (красиво и эффективно!)
```

### 2. Новая эра удаления пробелов: `strip()`, `stripLeading()`, `stripTrailing()`
Старый добрый `trim()` — это «динозавр». Он удаляет всё, что меньше или равно символу `U+0020` (пробел). Проблема в том, что он не понимает современные Unicode-пробелы.

*   **`strip()`**: Аналог `trim()`, но **Unicode-aware**. Он использует стандарт `Character.isWhitespace()`, который понимает все типы пробелов из разных языков.
*   **`stripLeading()`**: Удаляет пробелы только в начале строки.
*   **`stripTrailing()`**: Удаляет пробелы только в конце строки.

**Нюанс:** Если ты работаешь с международным текстом (Unicode), всегда используй `strip()`. Это безопаснее и современнее.

### 3. Разрезание на строки: `lines()`
Раньше, чтобы разбить текст по строкам, мы использовали `split("\n")`. Но это создавало массив строк сразу в памяти.

*   **`lines()`**: Возвращает `Stream<String>`. Это ленивая операция. Она не создает массив сразу, а дает тебе поток строк, который можно обрабатывать через Stream API (фильтровать, маппить и т.д.).
*   **Умный разделитель**: Метод корректно обрабатывает разные типы окончаний строк: `\n`, `\r` или `\r\n`.

**Пример:**
```java
String multiLine = "Java\nPython\nC++";
multiLine.lines()
         .filter(s -> s.startsWith("J"))
         .forEach(System.out::println); // Выведет: Java
```

### 4. Повторение строки: `repeat(int count)`
Забудь про циклы `for` для создания строк типа `"***"`.

*   **`repeat(n)`**: Просто берет строку и дублирует её `n` раз.

**Пример:**
```java
String star = "*".repeat(5); 
System.out.println(star); // *****
```
**Нюанс:** Если передать отрицательное число, получишь `IllegalArgumentException`.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем принципиальная разница между `trim()` и `strip()`?**
**О:** `trim()` работает только с ASCII-символами (удаляет всё $\le$ пробела). `strip()` — это Unicode-friendly метод, он понимает современные стандарты кодировок и правильно определяет «пробельность» символов в разных языках.

**В: Почему `isBlank()` лучше, чем `trim().isEmpty()`?**
**О:** С точки зрения производительности. `trim().isEmpty()` создает новый объект строки в куче (heap) после выполнения `trim()`. `isBlank()` просто проходит по существующей строке и проверяет символы, не создавая новых объектов.

**В: Что произойдет, если вызвать `"abc".repeat(-1)`?**
**О:** Программа упадет с исключением `IllegalArgumentException`, так как количество повторений не может быть отрицательным.

**В: Когда стоит использовать `lines()`, а когда `split()`?**
**О:** Если тебе нужно просто разбить строку на массив и ты уверен, что данных мало — `split()` привычнее. Но если текст большой (например, лог-файл) и ты хочешь обрабатывать его поэтапно, не загружая весь массив в память — используй `lines()`, так как он возвращает `Stream`.

# 🧠 Java 12–17: Switch Expressions

До Java 12 `switch` был просто **statement** (инструкцией). Он выполнял блок кода, но не возвращал результат. С выходом новых версий (Java 12/13 — превью, Java 14 — стандарт) `switch` превратился в **expression** (выражение), то есть он может возвращать значение, которое можно сразу присвоить переменной.

### 🚀 Главные изменения

#### 1. Переход от Statement к Expression
Раньше ты писал код, чтобы изменить состояние переменных внутри `switch`. Теперь ты можешь использовать `switch` как часть выражения.

**Было (Old Way):**
```java
String dayType;
switch (day) {
    case MONDAY:
    case FRIDAY:
        dayType = "Work";
        break; // Обязательно, иначе fall-through
    case SATURDAY:
        dayType = "Weekend";
        break;
    default:
        dayType = "Unknown";
}
```

**Стало (New Way):**
```java
String dayType = switch (day) {
    case MONDAY, FRIDAY -> "Work"; // Коротко и ясно
    case SATURDAY -> "Weekend";
    default -> "Unknown";
};
```

#### 2. Стрелочный синтаксис (`->`) вместо двоеточия (`:`)
Это киллер-фича. Использование `->` избавляет нас от необходимости писать `break`. В новом синтаксисе **нет fall-through** (проваливания в следующий case). Если ты выбрал ветку, выполнится только она.

#### 3. Группировка кейсов
Теперь не нужно писать несколько `case` друг под другом через двоеточие. Можно использовать запятую:
`case MONDAY, TUESDAY, WEDNESDAY -> ...`

#### 4. Ключевое слово `yield`
Если тебе нужно выполнить не одну строку кода, а целый блок (логику), ты не можешь просто использовать `->`. Тебе придется использовать фигурные скобки, и в этом случае для возврата значения из `switch` используется `yield`.

```java
int result = switch (input) {
    case "complex" -> {
        // Какая-то сложная логика
        int calculation = performMagic(input);
        yield calculation; // Возвращаем значение из блока
    }
    default -> 0;
};
```

---

### ⚠️ Важные нюансы (Senior Tips)

1.  **Exhaustiveness (Исчерпываемость):** Это самое важное. Поскольку `switch` теперь — это выражение, возвращающее значение, компилятор **обязан** быть уверен, что результат будет получен в любом случае.
    *   Если ты используешь `enum`, и перечислил все его значения — `default` не нужен.
    *   Если ты пропустил хотя бы один `enum` или используешь `String/int` — **обязан** написать `default`. Иначе код просто не скомпилируется.
2.  **Запрет на смешивание:** Ты не можешь использовать в одном и том же `switch` одновременно и старый синтаксис с `:` (с `break`), и новый `->`. Выбирай один стиль.
3.  **Смена парадигмы:** Switch Expressions делают код более "функциональным" и уменьшают количество побочных эффектов (side-effects), так как мы не меняем внешние переменные, а получаем новое значение.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Что такое "fall-through" и как новый switch его решает?**
**О:** Fall-through — это когда выполнение кода "проваливается" из одного `case` в другой из-за отсутствия `break`. В новом синтаксисе с использованием `->` этого не происходит по определению: выполнится только правая часть стрелки.

**В: Можно ли использовать `yield` вместе со стрелочным синтаксисом `->`?**
**О:** Да, но только если после стрелки идет блок кода в фигурных скобках `{ ... }`. Без блока кода `yield` не имеет смысла.

**В: Обязателен ли `default` в новом Switch Expression?**
**О:** Только если компилятор не может гарантировать исчерпываемость всех вариантов (например, для `String`, `int` или неполного списка `enum`). Если ты работаешь с `Sealed Classes` (Java 17) и покрыл все разрешенные подклассы, `default` можно опустить.

**В: В чем разница между `case A: return ...` и `case A -> yield ...`?**
**О:** `return` завершает работу всего метода, а `yield` завершает только выполнение текущего `switch expression`, возвращая значение в переменную или место вызова.

# 🧠 Шпаргалка: Pattern Matching for `instanceof` (Java 14–17)

### 🛑 Проблема: "Старый" способ (до Java 14)
Раньше проверка типа и приведение типов были двумя отдельными, скучными и дублирующими друг друга операциями. Это создавало лишний «шум» в коде (boilerplate) и увеличивало риск ошибок (например, можно было случайно привести к не тому типу).

```java
// Как это выглядело раньше
Object obj = "Hello, World!";

if (obj instanceof String) { // 1. Проверяем тип
    String s = (String) obj; // 2. Принудительно кастим (дублирование!)
    System.out.println(s.length());
}
```

### ✅ Решение: Pattern Matching (Java 14/16+)
Теперь `instanceof` умеет не только проверять, но и сразу объявлять переменную нужного типа. Это называется **Binding Variable** (связывающая переменная).

```java
// Как это выглядит сейчас
Object obj = "Hello, World!";

if (obj instanceof String s) { // Проверка + создание переменной 's' типа String
    System.out.println(s.length()); // 's' уже готова к работе
}
```

---

### 🔍 Глубокие нюансы (то, что спрашивают на собеседованиях)

#### 1. Область видимости (Flow Scoping)
Переменная `s` не живет вечно. Она доступна только в той части кода, где проверка `instanceof` пройдена успешно. Это называется **flow-sensitive scoping**.

```java
if (obj instanceof String s) {
    System.out/println(s); // OK: проверка прошла
} 
// System.out.println(s); // ОШИБКА: компилятор не знает, что 's' существует здесь
```

#### 2. Использование в логических операциях (`&&` и `||`)
Это самый тонкий момент. Java понимает порядок выполнения операций.

*   **С оператором `&&` (AND):** Всё отлично. Если левая часть (`instanceof`) истинна, то правая часть уже «видит» переменную `s`.
    ```java
    if (obj instanceof String s && s.length() > 5) { // OK!
        System.out.println(s);
    }
    ```

*   **С оператором `||` (OR):** **ОПАСНО!** Если левая часть ложна, правая часть может не «видеть» переменную `s`.
    ```java
    // ОШИБКА КОМПИЛЯЦИИ: если obj не String, то 's' не определена для правой части
    if (obj instanceof String s || s.length() > 5) { ... } 
    ```

#### 3. Совместимость с `switch` (Java 17+)
Хотя полноценный Pattern Matching в `switch` стал стандартом чуть позже, концепция заложила фундамент для того, чтобы мы могли делать такие вещи:
```java
// Это уже ближе к Java 17/21, но важно понимать контекст
return switch (obj) {
    case Integer i -> "Это число: " + i;
    case String s   -> "Это строка длиной: " + s.length();
    default         -> "Неизвестный тип";
};
```

1.  **Меньше кода:** Убрали лишнюю строку с кастом.
2.  **Безопасность:** Невозможно забыть сделать каст или ошибиться в типе при касте.
3.  **Читаемость:** Код стал чище и декларативнее.

**В: В какой версии это стало стандартом?**
**О:** Это было в режиме Preview в Java 14, но официально зафиксировано как стандарт в **Java 16**. Если ты работаешь на Java 17 — используй смело.

**В: Можно ли использовать `s` в блоке `else`?**
**О:** Нет. В блоке `else` условие `instanceof` считается ложным, а значит, переменная `s` не была инициализирована и не существует.

**В: Повышает ли это производительность?**

**В: А если я использую `instanceof` с `final` полями?**
**О:** Это работает так же отлично. Pattern matching не конфликтует с модификатором `final`.

# 📑 Шпаргалка: Java Records

### 💡 Что это такое?
**Record** — это специальный тип класса, предназначенный исключительно для **хранения данных**. Если тебе нужно создать класс-контейнер (DTO, POJO, Value Object), который просто держит в себе несколько полей и не содержит сложной бизнес-логики, то Record — твой лучший друг.

До появления рекордов нам приходилось писать тонны шаблонного кода (boilerplate): поля, конструктор, `equals()`, `hashCode()` и `toString()`. Рекорд делает всё это за тебя одной строчкой.

### 🛠 Синтаксис
Вместо классического класса:
```java
// Старый подход (Boilerplate)
public class User {
    private final String name;
    private final int age;

    public User(String name, int age) {
        this.name = name;
        this.age = age;
    }
    // + equals, hashCode, toString... (еще 30 строк кода)
}

// Новый подход (Record)
public record User(String name, int age) {}
```

### 🚀 Что получает тебя "из коробки"?
Когда ты объявляешь `record`, компилятор автоматически генерирует:
1.  **Поля**: Все компоненты заголовка становятся `private final`.
2.  **Канонический конструктор**: Конструктор, который принимает все аргументы и присваивает их полям.
3.  **Методы доступа (Accessors)**: Но внимание! Они называются не `getName()`, а просто `name()`.
4.  **`equals()` и `hashCode()`**: Работают на основе всех полей компонента. Два рекорда с одинаковыми данными будут равны.
5.  **`toString()`**: Выводит красивую строку вида `User[name=Ivan, age=25]`.

### 🔍 Нюансы и продвинутые фишки (Senior Level)

#### 1. Compact Constructor (Компактный конструктор)
Это киллер-фича для валидации данных. Тебе не нужно перечислять все аргументы еще раз. Ты просто пишешь логику проверки:
```java
public record User(String name, int age) {
    public User {
        // Проверка данных (валидация)
        if (age < 0) {
            throw new IllegalArgumentException("Age cannot be negative");
        }
        // Присваивание полей происходит автоматически!
        if (name == null) name = "Unknown"; 
    }
}
```

#### 2. Неизменяемость (Immutability) и Shallow Immutability
Рекорды по определению `final`. Ты не можешь изменить поле после создания.
**Но будь осторожен!** Если внутри рекорда лежит изменяемый объект (например, `List`), то сам список заменить нельзя, но *содержимое* списка изменить можно. Это называется "поверхностная неизменяемость".

#### 3. Ограничения (Что НЕЛЬЗЯ делать)
*   **Наследование**: Рекорды не могут наследоваться от других классов (они уже неявно наследуются от `java.lang.Record`).
*   **Дополнительные поля**: Ты не можешь добавить в рекорд свои *экземплярные* (instance) поля. Все данные должны быть описаны в заголовке. Но ты **можешь** добавить статические (`static`) поля.
*   **Класс всегда `final`**: Ты не можешь создать подкласс рекорда.

#### 4. Что МОЖНО делать
*   Рекорды могут реализовывать интерфейсы.
*   Ты можешь добавлять свои методы (включая статические).
*   Ты можешь переопределять стандартные методы (например, сделать свой `toString`).

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем Record отличается от Lombok `@Value` или `@Data`?**
**О:** Lombok — это внешняя библиотека, которая генерирует код при компиляции. Record — это встроенная фича языка. Рекорды более строгие: они запрещают добавлять неявные поля и нацелены именно на неизменяемые данные (data carriers), в то время как Lombok может имитировать всё что угодно.

**В: Можно ли в рекорде изменить значение поля?**
**О:** Нет. Все компоненты рекорда по умолчанию `final`. Если тебе нужна мутабельность (изменяемость), используй обычный класс.

**В: Как работает `equals()` в рекордах?**
**О:** Он сравнивает значения всех компонентов, указанных в заголовке. Если все поля идентичны — объекты равны. Это делает рекорды идеальными для использования в качестве ключей в `HashMap`.

**В: Можно ли добавить в рекорд логику?**
**О:** Да, ты можешь добавлять методы, но они должны быть связаны с данными рекорда. Рекорд — это не про поведение (behavior), а про состояние (state). Если логики становится слишком много, значит, тебе нужен обычный класс.

# 🔒 Sealed Classes (Java 17) — Шпаргалка

### 💡 Суть концепции
До появления Sealed Classes (запечатанных классов) у нас было всего два экстремума: либо класс `final` (никто не может наследоваться), либо обычный класс (любой может создать наследника). 

**Sealed Classes** — это "золотая середина". Они позволяют тебе четко сказать: *"От этого класса могут наследоваться только вот эти конкретные классы, и никто другой"*. Это инструмент для создания **контролируемой иерархии**.

---

### 🛠 Ключевые слова и синтаксис

1.  **`sealed`**: Помечает класс как "запечатанный".
2.  **`permits`**: Список классов, которым разрешено наследоваться от данного.
3.  **`non-sealed`**: Разрывает цепочку ограничений (делает подкласс снова открытым для всех).
4.  **`final`**: Класс, который нельзя расширять дальше (конец ветки).

#### Пример кода:
```java
// Мы разрешаем наследоваться только Circle и Square
public sealed class Shape permits Circle, Square, OpenShape {
    // ...
}

// Вариант 1: Конечная точка (наследование запрещено)
public final class Circle extends Shape { }

// Вариint 2: Продолжаем контролируемую иерархию
public sealed class Square extends Shape permits TransparentSquare { }

// Вариант 3: "Дыра" в безопасности — этот класс снова открыт для всех
public non-sealed class OpenShape extends Shape { }
```

---

### 📏 Правила игры (Must Know)

Чтобы компилятор не ругался, нужно соблюдать три жестких правила:
1.  **Наследование должно быть явным**: Все классы, указанные в `permits`, должны либо находиться в том же пакете, либо в том же модуле.
2.  **Три состояния наследника**: Любой класс, наследующий `sealed` класс, **обязан** иметь один из трех модификаторов:
    *   `final` (закрыл ветку).
    *   `sealed` (продолжил контролируемую ветку).
    *   `non-sealed` (открыл ветку для всех).
3.  **Связь с Records**: `record` по умолчанию являются `final`. Это делает их идеальными кандидатами на роль наследников в sealed-иерархиях.

---

### 🚀 Зачем это нужно? (The "Senior" Reason)

1.  **Domain Modeling (Точное моделирование)**: Если ты пишешь систему платежей, где есть только `CreditCard`, `PayPal` и `Crypto`, зачем позволять кому-то из другого модуля создать `MagicBeansPayment`? Sealed classes защищают твою бизнес-логику.
2.  **Pattern Matching (Killer Feature)**: Это главная причина. В Java 17+ вместе с `switch` можно использовать проверку типов. Если класс `sealed`, компилятор знает **все** возможные варианты. Тебе **не нужен** блок `default` в `switch`, потому что ты покрыл все случаи!
    ```java
    // Компилятор проверит, что ты обработал Circle, Square и OpenShape
    return switch (shape) {
        case Circle c -> "Round";
        case Square s -> "Boxy";
        case OpenShape o -> "Unknown shape type";
        // default НЕ НУЖЕН, если мы покрыли все permitted классы
    };
    ```

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли не писать `permits`, если все наследники в одном файле?**
**О:** Да. Если все подклассы определены в том же файле, что и базовый `sealed` класс, Java сама поймет, кто является наследником. Это удобно для небольших моделей.

**В: Чем `non-sealed` отличается от простого класса?**
**О:** По сути — ничем. `non-sealed` — это способ сказать: "Я принимаю ограничения родителя, но сам отказываюсь их навязывать своим детям". Он превращает закрытую иерархию обратно в обычную открытую.

**В: В какой версии это стало стабильным?**
**О:** Идея появилась раньше (в превью-версиях), но полноценно, как стабильная фича языка, она зафиксирована в **Java 17**.

**В: Помогают ли Sealed Classes в безопасности?**
**О:** Да. Они предотвращают "подмену" логики через расширение твоих классов злоумышленниками или неосторожными разработчиками в сторонних библиотеках. Это называется *Encapsulation of the hierarchy*.

# 📝 Шпаргалка: Java Text Blocks (Java 15+)
*Примечание: В Java 12-14 это были Preview-функции, начиная с Java 15 — стандарт.*

### 🚀 Проблема
До появления Text Blocks написание многострочных строк (SQL-запросов, JSON, HTML) было сущим адом. Тебе приходилось:
1. Использовать конкатенацию (`+`).
2. Вручную вставлять `\n`.
3. Экранировать кавычки (`\"`).
4. Мучиться с отступами, которые ломали читаемость кода.

**Как это выглядело (Old Way):**
```java
String sql = "SELECT id, name, email\n" +
             "FROM users\n" +
             "WHERE status = 'ACTIVE'\n" +
             "ORDER BY name;";
```

### ✅ Решение: Text Blocks
Text Blocks позволяют писать многострочный текст «как есть», сохраняя структуру и читаемость. Используется тройная кавычка `"""`.

**Как это выглядит (New Way):**
```java
String sql = """
             SELECT id, name, email
             FROM users
             WHERE status = 'ACTIVE'
             ORDER BY name;
             """;
```

---

### 🛠 Ключевые правила и нюансы (Senior Level)

#### 1. Правило первой строки (The Opening Line Rule)
Это самая частая ошибка. **Нельзя** писать текст на той же строке, где стоят открывающие тройные кавычки.
*   ❌ `String bad = """Hello""";` — *Ошибка компиляции.*
*   ✅ `String good = """\nHello""";` — *Работает (но зачем так делать?).*
*   ✅ Текст должен начинаться с новой строки после `"""`.

#### 2. Магия отступов (Incidental Whitespace)
Java автоматически удаляет «лишние» пробелы слева, которые являются общими для всех строк блока. Она определяет "базовый" уровень отступа по положению **закрывающей** труктуры `"""`.

*   **Пример 1:** Если закрывающая кавычка стоит под самым началом строки, Java уберет все отступы, которые есть у каждой строки.
*   **Пример 2 (Важно):** Если ты хочешь оставить пробелы в начале строки внутри блока, тебе нужно выровнять закрывающую кавычку `"""` так, чтобы она была левее нужного отступа.

#### 3. Управляющие символы и экранирование
*   **Экранирование кавычек:** Внутри текстового блока не нужно писать `\"`, если ты используешь тройные кавычки. Обычные двойные кавычки внутри — это ок.
*   **Спецсимволы:** `\n`, `\t` и прочие работают как обычно.
*   **Элемент `\` (Backslash) в конце строки:** Если ты поставишь `\` в конце строки внутри блока, Java поймет это как «продолжить строку на следующей, но без переноса символа». Это полезно, если ты хочешь визуально разбить длинную строку в коде, но в итоговой строке не должно быть `\n`.

#### 4. Особенности переноса строк
Текстовые блоки всегда используют системный разделитель строк (обычно `\n`). Если тебе нужно явно управлять переносами или делать их более сложными, используй метод `.formatted()` (появился вместе с Text Blocks), чтобы вставлять переменные через `%s`.

### ❓ FAQ (Частые вопросы на интервью)

**В: Можно ли использовать Text Block для одной строки?**
**О:** Технически можно, но синтаксис требует переноса строки после `"""`. Если тебе нужна одна строка, обычные `" "` — лучший выбор.

**В: Как Text Blocks влияют на производительность?**
**О:** Практически никак. На уровне байт-кода это всё та же строка. Это "синтаксический сахар", который обрабатывается компилятором.

**В: Что произойдет, если я поставлю закрывающую кавычку `"""` в середине строки?**
**О:** Компилятор воспримет это как конец блока. Все, что идет после — уже не часть текстового блока.

**В: Как убрать лишний перенос строки в самом начале блока (сразу после `"""`)?**
**О:** Используй символ `\` в конце первой пустой строки.
```java
String s = """
           \
           Первая строка без пустого отступа выше
           """;
```

**О:** Они позволяют копировать JSON прямо из редактора/Postman и вставлять в Java без ручного добавления `+` и `\n`, что делает код чистым и поддерживаемым.

# 🧠 Java 12–17: Pattern Matching for `switch`

### 📌 Суть проблемы (The "Old Way")
До появления этой фичи `switch` был очень ограниченным. Он умел работать только с примитивами, их обертками, `enum` и `String`. Если тебе нужно было проверить тип объекта (например, `Object obj`), тебе приходилось писать длинную цепочку `if-else` с использованием `instanceof` и **ручным приведением типов (casting)**.

**Как это выглядело раньше:**
```java
if (obj instanceof String) {
    String s = (String) obj; // Громоздкое приведение типа
    System.out.println("Это строка: " + s);
} else if (obj instanceof Integer) {
    Integer i = (Integer) obj;
    System.out.println("Это число: " + i);
}
```

### 🚀 Что изменилось? (The "New Way")
Pattern Matching для `switch` позволяет проверять объект не только на соответствие значению, но и на **тип**, и — что самое крутое — сразу объявлять переменную этого типа внутри `case`.

**Как это выглядит теперь:**
```java
switch (obj) {
    case String s  -> System.out.println("Строка: " + s); // Тип проверен, переменная 's' уже готова
    case Integer i -> System.out.println("Число: " + i);
    case null      -> System.out.println("Пришел null!"); // Обработка null прямо в switch
    default        -> System.out.println("Неизвестный тип");
}
```

---

### 🛠 Ключевые возможности и изменения

1.  **Type Patterns (Шаблоны типов):** Ты можешь писать `case Type variableName`. Если проверка прошла успешно, переменная `variableName` доступна внутри этого блока. Больше никакого явного кастинга.
2.  **Null Handling:** Раньше, если ты передавал `null` в `switch`, ты получал `NullPointerException`. Теперь можно добавить специальный `case null`, что делает код гораздо чище и безопаснее.
3.  **Exhaustiveness (Исчерпываемость):** Это критически важный момент для Senior-разработчика. Компилятор теперь следит за тем, чтобы ты обработал **все возможные варианты**. Если ты используешь `switch` по иерархии классов и не покрыл все подклассы (или не добавил `default`), компилятор выдаст ошибку. Это защищает от багов при расширении системы.

---

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

*   **Порядок имеет значение!** Это самая частая ошибка. Сначала нужно проверять **самые специфичные** типы, а затем — более общие.
    *   ❌ *Ошибка:* `case Object o` перед `case String s`. Компилятор скажет: "Эй, код `case String s` никогда не выполнится, потому что всё попадет в `Object`".
    *   ✅ *Правильно:* От частного к общему.
*   **Статус Preview:** Важно помнить, что в период Java 12–17 эта фича проходила через стадию **Preview**. Это значит, что синтаксис мог немного меняться от версии к версии (например, использование `&&` для условий вместо ключевого слова `when`, которое появилось позже). В Java 17 она всё еще была в превью-режиме (финализация произошла в Java 21), поэтому при работе с проектами на Java 17 нужно включать флаг `--enable-preview`.
*   **Связь с `instanceof`:** Эта фича — логическое продолжение Pattern Matching для `instanceof`, который стал стандартом в Java 16. Они работают в одной концепции: "Проверил -> Объявил переменную -> Использовал".

### ❓ FAQ (Часто задаваемые вопросы)

**В: Можно ли использовать внутри `case` дополнительные условия?**
**О:** В версиях 12–17 возможности были ограничены. Полноценные "Guarded Patterns" (условия через `when`) стали доступны позже. Но сама идея проверки типа уже дала огромный буст к читаемости.

**В: Что будет, если я забуду про `default`, но все типы перечислил?**
**О:** Если ты работаешь с `enum` или закрытыми иерархиями, компилятор может простить отсутствие `default`. Но если ты проверяешь `Object`, то `default` обязателен, иначе программа не будет знать, что делать с типами, которые не подошли под `case`.

**В: Влияет ли это на производительность?**
**О:** Накладные расходы практически незаметны. Современная JVM очень эффективно оптимизирует такие проверки типов. Главный профит здесь — в **безопасности кода** и **чистоте синтаксиса**.

**В: Можно ли внутри `case` сразу делать кастинг?**
**О:** Смысл фичи именно в том, чтобы *избежать* явного кастинга. Если ты пишешь `case String s`, переменная `s` уже является строкой. Писать `(String) s` внутри — это плохой тон и избыточность.

# 🧵 Java 18 – Java 21: Virtual Threads (Project Loom)

### 🎯 Суть в двух словах
Раньше каждый поток в Java (`java.lang.Thread`) был оберткой над тяжелым потоком операционной системы (**Platform Thread**). Создать 10 000 таких потоков — значит «положить» память и нагрузить планировщик ОС контекстными переключениями.

**Virtual Threads (Виртуальные потоки)** — это легковесные потоки, которыми управляет не ОС, а сама JVM. Они позволяют запускать **миллионы** потоков на небольшом количестве реальных потоков ОС.

---

### 🏗️ Как это работает (Архитектура)
Представь модель **M:N**:
*   **M (Virtual Threads):** Огромное количество твоих задач. Они очень дешевые, хранятся в Heap (куче).
*   **N (Carrier Threads / Platform Threads):** Небольшое количество реальных потоков ОС, которые выполняют работу.

**Магия происходит при блокирующем I/O:**
1. Когда виртуальный поток делает запрос к БД или сетевой вызов, он **не блокирует** поток ОС.
2. Вмека (JVM) «снимает» виртуальный поток с потока-носителя (unmount) и сохраняет его состояние в памяти.
3. Поток-носитель освобождается и берет другой виртуальный поток на работу.
4. Как только данные из БД пришли, JVM «навешивает» виртуальный поток обратно на свободный поток-носитель (remount).

**Итог:** Мы пишем простой, синхронный код (без колбэков и реактивщины), но получаем масштабируемость асинхронного кода.

---

### 🛠️ Как использовать (Code Snippets)

**1. Создание одиночного потока:**
```java
Thread vThread = Thread.ofVirtual().start(() -> {
    System.out.println("Я летаю в памяти, а не в ОС!");
});
```

**2. Правильный способ для задач (ExecutorService):**
Вместо старого `FixedThreadPool`, который ограничивает количество потоков, используй новый подход:
```java
try (var executor = Executors.currentThread().newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> doWork()); // Каждый раз создается новый легкий поток
} // Здесь executor автоматически закроется и дождется завершения всех задач
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Level)

**1. Проблема Pinning (Приклеивание):**
Это самая важная проблема. Виртуальный поток может «прилипнуть» к потоку-носителю и не отпускать его, даже если идет блокировка. Это происходит в двух случаях:
*   Использование ключевого слова `synchronized`.
*   Вызов Native-методов (JNI).
*   **Решение:** Заменяй `synchronized` на `ReentrantLock`.

**2. Не используй Thread Pools для виртуальных потоков!**
Старая привычка — создавать пул из 10 потоков, чтобы не нагружать систему. **Это антипаттерн для Virtual Threads.** Виртуальные потоки настолько дешевы, что их не нужно ограничивать пулом. Тебе нужен `newVirtualThreadPerTaskExecutor`, где на каждую задачу — новый поток.

**3. Осторожно с ThreadLocal:**
Если ты создашь миллион виртуальных потоков и в каждом положишь в `ThreadLocal` объект размером 1 МБ, ты получишь `OutOfMemoryError` мгновенно. Виртуальные потоки делают использование `ThreadLocal` опасным при больших масштабах.

**4. CPU-bound задачи не станут быстрее:**
Виртуальные потоки — это решение для **I/O-bound** задач (сеть, БД, файлы). Если у тебя тяжелые вычисления (математика, видео), виртуальные потоки не помогут, так как им всё равно нужны реальные ядра процессора.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем Virtual Thread отличается от Platform Thread?**
**О:** Platform Thread — это обертка над потоком ОС, он дорогой и ограничен ресурсами системы. Virtual Thread — это объект в Heap, управляемый JVM, который может эффективно переключаться при ожидании I/O.

**В: Поможет ли переход на Virtual Threads избавиться от WebFlux (Reactive)?**
**О:** В большинстве случаев — **да**. Реактивное программирование было нужно, чтобы экономить потоки при блокирующем I/O. Виртуальные потоки решают эту же проблему, но позволяют писать понятный императивный код без сложных цепочек `Mono`/`Flux`.

**В: Что такое "Pinning" и как его избежать?**
**О:** Это ситуация, когда виртуальный поток блокирует поток-носителя (Carrier Thread) из-за использования `synchronized`. Избегаем через использование `java.util.concurrent.locks.ReentrantLock`.

**В: Можно ли использовать Virtual Threads для обработки тяжелой математики?**
**О:** Нет. Для CPU-intensive задач количество потоков должно быть сопоставимо с количеством ядер процессора. Виртуальные потоки созданы для ожидания (I/O), а не для вычислений.

# 🧠 Шпаргалка: Structured Concurrency (Java 18–21+)

### 📌 Суть в одном предложении
**Structured Concurrency** — это подход к многопоточности, который позволяет управлять группой задач как единым целым: если одна подзадача падает с ошибкой, все остальные в этой группе автоматически отменяются, не оставляя «зомби-потоков».

---

### ❌ Проблема: Unstructured Concurrency (Как было раньше)
Раньше мы использовали `ExecutorService` или `CompletableFuture`. Это называется **неструктурированным** подходом.
*   **Проблема "Потерянных задач":** Вы запустили 10 потоков для параллельного запроса к микросервисам. Один поток упал с `Exception`, но остальные 9 продолжают работать в фоне, потребляя ресурсы (CPU, память), хотя их результат уже никому не нужен.
*   **Проблема "Утечки ресурсов":** Трудно гарантировать, что все потоки завершились. Это ведет к утечкам памяти и трудностям в отладке.
*   **Сложность обработки ошибок:** Чтобы правильно обработнуть ошибку одного потока и прервать остальные, нужно писать много шаблонного кода (boilerplate) с ручной проверкой флагов прерывания.

---

### ✅ Решение: Structured Concurrency (Как стало)
Представь это как блок `try-with-resources` для потоков. У задачи есть четкая область видимости (scope).
*   **Иерархия:** Потоки образуют дерево. Родительский поток ждет завершения всех дочерних.
*   **Автоматическая отмена:** Если дочерняя задача выбрасывает исключение, `Scope` сигнализирует всем остальным «братским» задачам: «Эй, мы провалились, прекращайте работу!».
*   **Видимость ошибок:** Ошибки не теряются, они всплывают к родителю.

---

### 🛠 Ключевые компоненты API (на базе `StructuredTaskScope`)

В Java 21 (в режиме Preview) основная магия крутится вокруг класса `StructuredTaskScope`. У него есть два основных режима:

1.  **`ShutdownOnFailure`** (Режим «Все или ничего»):
    *   Если хотя бы одна подзадача завершается с ошибкой, все остальные задачи в этом scope немедленно прерываются.
    *   Идеально для: когда нам нужны результаты *всех* сервисов одновременно.

2.  **`ShutdownOnSuccess`** (Режим «Кто первый»):
    *   Как только первая задача успешно завершается, все остальные задачи отменяются.
    *   Идеально для: запроса к нескольким репликам одного и того же сервиса (берем тот ответ, что пришел быстрее).

---

### 💻 Код: Сравнение подходов

#### Было (Unstructured - CompletableFuture):
```java
// Мы запускаем задачи, но если одна упадет, остальные будут "висеть"
CompletableFuture<String> task1 = CompletableFuture.supplyAsync(() -> callServiceA());
CompletableFuture<String> task2 = CompleintableFuture.supplyAsync(() -> callServiceB());

// Если task1 упадет, task2 продолжит работать в фоне, пока не доделает работу
return CompletableFuture.allOf(task1, task2).join(); 
```

#### Стало (Structured - StructuredTaskScope):
```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    // Запускаем задачи (fork)
    Subtask<String> task1 = scope.fork(() -> callServiceA());
    Subtask<String> task2 = scope.fork(() -> callServiceB());

    scope.join();           // Ждем завершения всех задач
    scope.throwIfFailed();  // Если хоть одна упала — кидаем Exception и отменяем остальные!

    return task1.get() + task2.get();
} // Здесь scope закрывается, все ресурсы очищены
```

---

### ⚠️ Нюансы (Senior Level)

1.  **Связь с Virtual Threads (Project Loom):** Structured Concurrency раскрывает потенциал **Virtual Threads**. Виртуальные потоки дешевые, их можно создавать миллионами. Но без структурированного подхода управлять миллионом "неуправляемых" потоков — это хаос. SC дает им дисциплину.
2.  **Статус API:** На момент Java 21 эта фича находится в **Preview**. Это значит, что синтаксис может измениться, и её нельзя использовать в критически важных production-системах без осторожности (нужно включать `--enable-preview`).
3.  **Scope Closure:** Всегда используй `try-with-resources`. Если не закрыть `scope`, ты получишь те же утечки ресурсов, от которых пытался убежать.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем `StructuredTaskScope` отличается от обычного `ExecutorService`?**
**О:** `ExecutorService` — это просто пул потоков, он не заботится о жизненном цикле задач внутри него. Он может запустить задачу и "забыть" про неё. `StructuredTaskScope` накладывает иерархические ограничения: задача не может жить дольше, чем её родительский scope.

**В: Что произойдет с подзадачами, если родительский поток будет прерван?**
**О:** Благодаря структурированному подходу, прерывание (interruption) распространяется вниз по дереву. Все дочерние задачи получат сигнал о прерывании и должны будут завершиться.

**В: Можно ли использовать `ShutdownOnSuccess` для кэширования?**
**О:** Да, это отличный кейс. Ты можешь одновременно запросить данные из Redis и из основной БД. Кто первый ответит — тот и победил, а второй запрос будет отменен, экономя ресурсы.

# 📑 Шпаргалка: Scoped Values (Java 18–21+)

### 🎯 Что это такое?
**Scoped Values** — это механизм для передачи данных между методами и потоками в рамках определенного «окна» (области видимости). Это современная, безопасная и эффективная альтернатива `ThreadLocal`.

Если коротко: это способ сказать: *"Вот этот объект будет доступен всем методам внутри этого блока кода, но как только блок закончится — данные исчезнут"*.

---

### ❌ Проблема ThreadLocal (Почему Scoped Values появились?)
До появления Scoped Values мы использовали `ThreadLocal`. Но у него есть три «смертельных» греха для высоконагруженных систем (особенно с Virtual Threads):

1.  **Мутабельность (Изменяемость):** Любой метод внутри потока может вызвать `.set()` и изменить значение. Это превращает отладку в ад: ты не знаешь, кто и когда подменил данные.
2.  **Утечки памяти:** Если ты забыл вызвать `.remove()`, данные останутся в потоке навсегда. В пуле потоков это приводит к тому, что старые данные «выживают» и отравляют новые задачи.
3.  **Дороговизна при наследовании:** Когда мы создаем дочерние потоки (например, через `Structured Concurrency`), копирование огромного `ThreadLocalMap` из родительского потока в дочерние — это тяжелая операция для памяти и CPU.

---

### ✅ Как работают Scoped Values
Scoped Value работает по принцитию **неизменяемости** и **автоматической очистки**.

#### Основной синтаксис:
```java
// 1. Создаем само значение (ключ)
public final static ScopedValue<String> USER_CONTEXT = ScopedValue.newInstance();

public void processRequest() {
    // 2. Привязываем значение к конкретному блоку кода
    ScopedValue.where(USER_CONTEXT, "Admin_User").run(() -> {
        // Внутри этого блока USER_CONTEXT доступен и равен "Admin_User"
        doBusinessLogic();
    }); 
    // 3. Как только выполнение вышло из run(), значение стерлось. 
    // Попытка прочитать USER_CONTEXT здесь вернет ошибку или пустоту (зависит от реализации).
}

public void doBusinessLogic() {
    // Мы не передавали строку аргументом, но получили её из контекста!
    System.out.println("Current user: " + USER_CONTEXT.get());
}
```

---

### 💎 Ключевые нюансы (Senior Level)

1.  **Immutability (Неизменяемость):** Ты не можешь вызвать `USER_CONTEXT.set("NewValue")`. Если тебе нужно другое значение, ты должен создать **вложенный** scope. Это гарантирует, что данные в текущем блоке не изменятся «под ногами».
2.  **Эффективность для Virtual Threads:** Scoped Values спроектированы так, чтобы их было очень дешево копировать при создании дочерних потоков. Это критически важно для масштабирования до миллионов потоков (Project Loom).
3.  **Scope Nesting (Вложенность):** Ты можешь накладывать слои друг на друга:
    ```java
    ScopedValue.where(ID, 1).run(() -> {
        ScopedValue.where(NAME, "Ivan").run(() -> {
            // Здесь доступны и ID, и NAME
        });
    });
    ```
4.  **ReadOnly by design:** Значение доступно только для чтения через `.get()`. Это делает архитектуру предсказуемой.

---

### 📊 Сравнение: Scoped Value vs ThreadLocal

| Характеристика | ThreadLocal | Scoped Value |
| :--- | :--- | :---            |
| **Изменяемость** | Можно менять в любой момент (`set`) | Только при создании нового Scope |
| **Жизненный цикл** | Пока не удалишь вручную (риск утечек) | Автоматически ограничен блоком `{ }` |
| **Наследование** | Дорогое копирование карты данных | Очень дешевое для дочерних потоков |
| **Безопасность** | Низкая (любой может подменить) | Высокая (нельзя изменить внутри scope) |

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли использовать Scoped Value, если я не хочу создавать новый Scope?**
**О:** Нет. Смысл Scoped Value именно в привязке к области видимости (`where(...).run(...)`). Без `where` значение не будет иметь контекста.

**В: Что произойдет, если вызвать `.get()`, когда значение не привязано?**
**О:** Будет выброшено исключение `NoSuchElementException`. Это защищает тебя от использования «мусорных» или неопределенных данных.

**В: Scoped Value заменяет ThreadLocal полностью?**
**О:** Не совсем. Если тебе нужно именно *изменять* состояние внутри одного и того же потока в процессе его работы (например, счетчик запросов), `ThreadLocal` всё еще может быть удобнее. Но для передачи контекста (User ID, Transaction ID, Trace ID) — Scoped Value однозначно лучше.

**В: Как это влияет на производительность?**
**О:** В сценариях с огромным количеством Virtual Threads Scoped Value значительно выигрывает за счет отсутствия необходимости копировать тяжелые мапы данных при создании новых потоков.

# 🧠 Шпаргалка: Record Patterns (Java 18 – Java 21)

### 📌 Суть темы
**Record Patterns** — это механизм "деконструкции" объектов типа `record`. Если раньше при проверке типа через `instanceof` тебе приходилось врудеть ручной кастинг и вызов аксессоров (`r.x()`, `r.y()`), то теперь ты можешь «разобрать» рекорл на части прямо в момент проверки.

Это часть большой инициативы **Pattern Matching**, которая превращает Java из языка с кучей шаблонного кода (boilerplate) в более лаконичный и функциональный язык.

---

### 🚀 Как это было vs Как стало

#### 1. Базовый уровень: `instanceof`
Раньше, чтобы достать данные из рекорда после проверки типа, ты делал так:
```java
// Старый подход (Java 16+)
if (obj instanceof Point p) {
    int x = p.x(); // Нужно вызывать метод вручную
    int y = p.y();
}
```

**С Record Patterns (Java 21):**
Ты извлекаешь компоненты прямо в шаблоне:
```java
// Новый подход (Java 21)
if (obj instanceof Point(int x, int y)) {
    System.out.println("X: " + x + ", Y: " + y); // Переменные x и y уже доступны!
}
```

#### 2. Продвинутый уровень: Вложенные паттерны (Nested Patterns)
Это «киллер-фича». Если у тебя есть рекорды внутри рекордов, ты можешь разложить всю структуру за один `if` или `switch`.

```java
record Point(int x, int y) {}
record Shape(Point center, double radius) {}

// Представь, что нам нужно проверить, что центр круга находится в точке (0,0)
if (shape instanceof Shape(Point(0, 0), double r)) {
    System.out.println("Круг с центром в начале координат, радиус: " + r);
}
```
*Заметь: мы не просто проверили `Shape`, мы залезли внутрь `Point` и сразу проверили его координаты.*

#### 3. Использование в `switch` (Pattern Matching for switch)
В Java 21 `switch` стал невероятно мощным инструментом для работы с данными.

```java
public void printShapeInfo(Object obj) {
    switch (obj) {
        case Shape(Point(0, 0), double r) -> System.out.println("Origin circle: " + r);
        case Shape(Point(int x, int y), double r) -> System.out.println("Circle at " + x + "," + y);
        case Point(int x, int y) -> System.out.println("Just a point: " + x + "," + y);
        case null -> System.out.println("It's null!");
        default -> System.out.println("Unknown object");
    }
}
```

---

### ⚠️ Важные нюансы (Senior Tips)

1.  **Только для Records:** Record Patterns работают **только** с рекордами. Ты не можешь деконструировать обычный `class`, потому что у него нет гарантированного набора компонентов и фиксированной структуры, как у рекорда.
2.  **Типизация переменных:** Внутри паттерна ты можешь использовать `var` (например, `Point(var x, var y)`), и Java сама выведет тип. Но если тебе нужно проверить конкретный тип (например, только `int`), пиши его явно.
3.  **Guard Clauses (`when`):** Ты можешь добавлять дополнительные условия прямо в паттерн с помощью ключевого слова `when`.
    *   `case Shape(Point(int x, int y), double r) when r > 10 -> ...` (сработает только если радиус больше 10).
4.  **Порядок имеет значение:** В `switch` всегда ставь более специфичные паттерны (вложенные или с условиями `when`) **выше** более общих. Иначе более общий паттерн «перехватит» выполнение раньше времени.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Можно ли использовать Record Patterns для обычных классов?**
**О:** Нет. Рекорды — это "прозрачные" носители данных. Компилятор точно знает, из чего они состоят. Обычный класс может иметь скрытую логику, и деконструкция была бы небезопасной.

**В: В чем профит для производительности?**
**О:** На самом деле, это не столько про скорость выполнения, сколько про чистоту кода. Но с точки зрения JVM, это упрощает работу JIT-компилятору, так как логика проверки типа и извлечения данных объединена в одну атомарную операцию.

**В: А что если я хочу использовать `instanceof`, но не все поля рекорда мне нужны?**
**О:** Ты можешь использовать `var`. Например, `if (obj instanceof Point(var x, var y))`. Если тебе нужно только `x`, ты всё равно обязан объявить `y` в паттерне, иначе структура не совпадет. Но ты можешь написать `Point(int x, var y)`.

**В: Это уже стабильная фича?**
**О:** В Java 21 — да, это стандартная часть языка (Standard Feature). Можно смело использовать в продакшене.

# 🧠 Шпаргалка: Sequenced Collections (Java 21)

### 📌 Проблема: "Хаос в упорядоченности"
До Java 21 в Java не было единого интерфейса для коллекций, которые имеют **определенный порядок** элементов. 
* Если тебе нужен первый элемент `List`, ты пишешь `list.get(0)`.
* Если тебе нужен первый элемент `Deque`, ты пишешь `deque.getFirst()`.
* Если тебе нужен первый элемент `SortedSet`, ты пишешь `set.first()`.

Это было неудобно, нетипично и приводило к дублированию логики. Пришлось каждый раз вспоминать, какой именно метод подходит для конкретного типа коллекции.

### 🚀 Решение: Единая иерархия
В Java 21 ввели три новых интерфейса, которые объединили все "упорядоченные" коллекции под одним предсказуемым API. Теперь, если коллекция имеет четкое начало и конец, она реализует `SequencedCollection`.

#### 1. `SequencedCollection<E>` (Базовый уровень)
Это основной интерфейс для всех коллекций с последовательностью.
**Ключевые методы:**
*   **Доступ к краям:** `getFirst()`, `getLast()`.
*   **Модификация краев:** `addFirst(e)`, `addLast(e)`, `removeFirst()`, `removeLast()`.
*   **Реверс (View):** `reversed()`. 
    > **Важный нюанс:** `reversed()` возвращает не новую коллекцию, а **представление (view)** исходной. Если ты изменишь оригинал, реверсированная копия тоже изменится.

#### 2. `SequencedSet<E>` (Для множеств с порядком)
Расширяет `SequencedCollection`. Применяется там, где элементы уникальны и имеют порядок (например, `LinkedHashSet` или `TreeSet`).
*   Все методы из `SequencedCollection` + гарантия уникальности.

#### 3. `SequencedMap<K, V>` (Для карт с порядком)
Самое мощное дополнение. Теперь у `LinkedHashMap` и `TreeMap` есть единый способ работать с "головами" и "хвостами".
**Ключевые методы:**
*   **Доступ к ключам/значениям:** `firstKey()`, `lastKey()`, `firstEntry()`, `lastEntry()`.
*   **Модификация:** `putFirst(k, v)`, `putLast(k, v)`.
*   **Удаление:** `pollFirstEntry()`, `pollLastEntry()`.

---

### 🛠 Примеры реализации
| Коллекция | Реализует Sequenced-интерфейс? | Почему? |
| :--- | :---: | :--- |
| `ArrayList` | ✅ Да | Есть четкий индекс 0 и последний элемент. |
| `LinkedHashSet` | ✅ Да | Сохраняет порядок вставки. |
| `TreeSet` | ✅ Да | Элементы всегда отсортированы. |
| `LinkedHashMap` | ✅ Да | Сохраняет порядок вставки/доступа. |
| `HashSet` | ❌ Нет | Порядок элементов не гарантирован (хаос). |

---

### ⚠️ Нюансы и "подводные камни" (Senior Level)

1.  **Complexity (Сложность):** Все новые методы (`getFirst`, `addFirst`) спроектированы так, чтобы работать за **O(1)** там, где это возможно (например, в `ArrayList` или `Deque`). Однако помни: `addFirst` для `ArrayList` всё равно будет вызывать сдвиг элементов ($O(n)$).
2.  **The `reversed()` View:** Это не копия! Если ты сделаешь `var rev = list.reversed()`, а потом удалишь элемент из `list`, в `rev` этот элемент тоже исчезнет. Это экономит память, но может привести к неожиданным побочным эффектам (side-effects).
3.  **Backward Compatibility:** Старые методы (`get(0)`, `first()`) никуда не делись. Новые интерфейсы — это надстройка (layer) поверх старых, чтобы унифицировать API.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли сказать, что `HashSet` теперь является `SequencedCollection`?**
**О:** Нет. `HashSet` не гарантирует порядок элементов. Без порядка невозможно определить "первый" или "последний" элемент стабильно.

**В: В чем разница между `reversed()` и `Collections.reverse(list)`?**
**О:** Это принципиально разные вещи. 
*   `Collections.reverse(list)` — **мутирует** (изменяет) исходный список, переставляя элементы местами.
*   `list.reversed()` — создает **view** (представление). Исходный список не меняется, но ты получаешь интерфейс, который "смотрит" на него задом наперед.

**В: Что произойдет, если вызвать `addFirst()` на `ArrayList`?**
**О:** С точки зрения API — всё пройдет успешно. С точки зрения производительности — это будет дорогая операция $O(n)$, так как Java придется сдвинуть все существующие элементы вправо, чтобы освободить место в нулевой позиции.

**В: Является ли `TreeMap` частью SequencedMap?**
**О:** Да, потому что `TreeMap` всегда отсортирован, а значит, у него всегда есть четко определенный первый и последний ключ.

# 🧠 Java 18–21: Foreign Function & Memory (FFM) API

### 📌 Что это такое?
**Foreign Function & Memory (FFM) API** — это современная замена старому и проблемному **JNI (Java Native Interface)**. Его цель — дать Java безопасный, производительный и простой способ взаимодействовать с кодом на C/C++ и работать с памятью вне кучи (off-heap memory).

В версиях 18–21 этот API проходил путь от ранних превью-стадий до стабилизации. Это часть проекта **Project Panama**.

---



### 🚀 Зачем это нужно? (Проблема JNI)
Раньше, если тебе нужно было вызвать функцию из библиотеки `.so` или `.dll`, ты использовал JNI. У него были три огромных минуса:
1.  **Сложность:** Нужно писать много "прослоечного" кода на C.
2.  **Опасность:** Одна ошибка в C-коде — и у тебя `Segmentation Fault` (всё падает вместе с JVM).
3.  **Производительность:** Переход из Java в Native через JNI очень дорогой (overhead).

**FFM решает это**, позволяя описывать сигнатуры нативных функций прямо в Java-коде.

---

### 🛠 Основные компоненты (Триада FFM)

Чтобы работать с внешним миром, тебе нужны три вещи:

#### 1. `MemorySegment` (Память)
Это замена `ByteBuffer` для работы с внекучевой памятью. 
*   **В чем крутость:** Это не просто кусок байтов, это "умный" сегмент. Он знает свои границы (bounds). Если ты попытаешься выйти за пределы — получишь понятную ошибку в Java, а не краш всей JVM.
*   **Типы:** Может представлять как нативную память, так и часть массива в Java.

#### 2. `Arena` (Управление жизненным циклом) — *Ключевое новшество!*
В старом мире управление памятью было кошмаром: выделил — не забыл освободить. **Arena** вводит детерминированное управление.
*   **`Arena.ofConfined()`**: Память живет, пока жива арена (один поток). Идеально для безопасности.
*   **`Arena.ofShared()`**: Память доступна из разных потоков.
*   **`Arena.ofAuto()`**: Java сама решит, когда очистить (как GC, но для нативной памяти).
*   **Суть:** Ты закрываешь `try-with-resources` арену, и вся память внутри неё мгновенно и безопасно освобождается.

#### 3. `Linker` & `SymbolLookup` (Связь)
*   **`SymbolLookup`**: Позвотель найти "имя" функции в библиотеке (например, найти `printf` в `libc`).
*   **`Linker`**: Это "клей". Он берет описание функции (какие аргументы принимает, что возвращает) и превращает это в `MethodHandle`, который можно вызвать из Java.

---

### 📈 Эволюция (18 $\to$ 21)

*   **Java 18/19:** API был в состоянии **Preview**. Названия классов и методов менялись (эксперименты с удобством).
*   **Java 21:** Это важная веха. Хотя API всё еще может требовать флагов включения, он стал гораздо более зрелым. Появились четкие правила работы с `Arena` и улучшилась производительность `Linker`.

---

### ⚠️ Нюансы и "Подводные камни" (Senior Level)

1.  **Security Flag:** Начиная с Java 17+, доступ к нативной памяти ограничен. Чтобы твой код заработал, нужно запускать JVM с флагом:
    `--enable-native-access=ALL-UNNAMED` (или укажи конкретный модуль). Без этого — `SecurityException`.
2.  **Performance:** Несмотря на то что FFM быстрее JNI, вызов нативного кода всё равно дороже обычного Java-метода. Не вызывай мелкие функции в цикле миллион раз без нужды.
3.  **Memory Safety:** Хотя `MemorySegment` защищает от выхода за границы, он **не защищает** тебя от того, что нативный код может повредить данные внутри сегмента, если ты передал ему неверный указатель.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Чем FFM лучше, чем `ByteBuffer.allocateDirect()`?**
**О:** `DirectByteBuffer` ограничен и сложен в управлении жизненным циклом (зависит от GC). `MemorySegment` с использованием `Arena` дает полный контроль: ты сам решаешь, когда память освободится, и это происходит мгновенно и предсказуемо.

**В: Можно ли использовать FFM для замены JNI в старых проектах?**
**О:** Да, это и есть главная цель. Если у тебя есть готовая C-библиотека, переписать интеграцию с неё на FFM — это лучший способ сделать проект стабильнее.

**В: Что будет, если обратиться к сегменту памяти после закрытия `Arena`?**
**О:** Ты получишь `IllegalStateException`. Это "фишка" API — он предотвращает использование "висячих указателей" (dangling pointers), которые являются главной причиной багов в C++.

# 🧠 Шпаргалка: Java Memory API (Project Panama)
**Период:** Java 18–21+ (Incubator/Preview $\to$ Evolution)

### 🎯 Суть проблемы: Зачем это вообще нужно?
Раньше, если тебе нужно было работать с памятью **вне кучи (off-heap)** — например, передать огромный массив данных в C++ библиотеку или прочитать файл напрямую в память без копирования — у тебя было два плохих пути:
1.  **`ByteBuffer.allocateDirect()`**: Удобно, но неудобно. Ограничен по размеру (нельзя больше 2 ГБ), сложно описывать сложные структуры данных.
2.  **JNI (Java Native Interface)**: Очень мощно, но дико сложно, небезокрепно и медленно из-за накладных расходов на переход между Java и Native кодом.

**Memory API** — это современный, безопасный и быстрый способ работать с "сырой" памятью напрямую, не выходя за рамки безопасности JVM. Это часть **Project Panama**.

---

### 🧱 Три кита Memory API

Чтобы работать с памятью, тебе нужно три компонента: **Arena**, **MemorySegment** и **MemoryLayout**.

#### 1. Arena (Управленец жизненным циклом)
В Java управление памятью обычно делает GC. Но в off-heap памяти нет. Если ты выделил память и забыл её освободить — это утечка. **Arena** решает эту проблему, определяя "время жизни" памяти.

*   **`Arena.ofConfined()`**: Самый строгий режим. Память доступна только в одном потоке. Как только арена закрывается (`arena.close()`), память мгновенно освобождается. Идеально для локальных задач.
*   **`Arena.ofShared()`**: Позволяет нескольким потокам работать с одной и тойтой областью памяти. Безопасно, но чуть медленнее из-за синхронизации.
*   **`Arena.global()`**: Память живет всё время, пока работает JVM. Опасно (можно легко получить утечку), но полезно для глобальных кэшей.

#### 2. MemorySegment (Сам кусок памяти)
Это "окно" в твою память. Это не просто массив байтов, а структурированный сегмент.
*   **Spatial Safety (Пространственная безопасность)**: Ты не можешь выйти за границы сегмента (защита от Buffer Overflow).
*   **Temporal Safety (Временная безопасность)**: Если арена закрылась, попытка обратиться к сегменту вызовет исключение, а не "падение" всей JVM (защита от Use-after-free).

#### 3. MemoryLayout (Схема/Чертеж)
Как нам понять, что по смещению 0 лежит `int`, а по смещению 4 — `long`? **MemoryLayout** описывает структуру данных в памяти (похоже на `struct` в C).
*   Ты описываешь: "Здесь у нас заголовок (byte), затем ID (int), затем вес (double)".

---

### 🛠 Пример кода (Как это выглядит в жизни)

Представь, что мы хотим создать структуру "Сотрудник" прямо в off-heap памяти.

```java
import java.lang.foreign.*;
import java.lang.invoke.VarHandle;

public class MemoryApiExample {
    public static void main(String[] args) {
        // 1. Определяем Layout (схему данных)
        // Сначала byte (id), потом int (age)
        StructLayout employeeLayout = MemoryLayout.structLayout(
            ValueLayout.JAVA_BYTE.withName("id"),
            ValueLayout.JAVA_INT.withName("age")
        );

        // 2. Создаем Арену (управляем временем жизни)
        try (Arena arena = Arena.ofConfined()) {
            
            // 3. Выделяем память под один объект по нашему Layout
            MemorySegment employeeSegment = arena.allocate(employeeLayout);

            // 4. Используем VarHandle для безопасного доступа к полям
            VarHandle ageHandle = employeeLayout.varHandle(MemoryLayout.PathElement.groupElement("age"));

            // Записываем данные
            employeeSegment.set(ValueLayout.JAVA_BYTE, 0, (byte) 1); // ID = 1
            ageHandle.set(employeeSegment, 1, 30);                // Age = 30

            // Читаем данные
            int age = (int) ageHandle.get(employeeSegment);
            System.out.println("Employee age: " + age);

        } // <--- Здесь арена закрывается, память очищается АВТОМАТИЧЕСКИ!
    }
}
```

### ⚠️ Нюансы и "Подводные камни" (Senior Level)

1.  **Performance**: Memory API гораздо быстрее JNI, потому что JVM понимает, что происходит с памятью, и может оптимизировать границы проверок. Но использование `VarHandle` через `Layout` всё равно требует аккуратности, чтобы не убить производительность лишними проверками.
2.  **Bounds Checking**: Каждое обращение к сегменту проверяет границы. Если ты делаешь миллионы мелких обращений, это может быть накладной расценой. Для сверхбыстрых операций используют `MemorySegment.reinterpret`.
3.  **Panama vs JNI**: Если твоя задача — просто вызвать функцию из `.so` или `.dll`, тебе понадобится дополнение к Memory API — **FFI (Foreign Function Interface)**. Memory API работает с *данными*, а FFI — с *кодом*.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем `MemorySegment` лучше `ByteBuffer.allocateDirect()`?**
**О:** `MemorySegment` поддерживает гораздо большие объемы данных (больше 2 ГБ), позволяет описывать сложные структуры через `Layout`, и, самое главное, обеспечивает **Temporal Safety** (защиту от использования памяти после её освобождения) через механизм `Arena`.

**В: Что такое "Spatial Safety" в контексте Memory API?**
**О:** Это гарантия того, что ты никогда не прочитаешь или не запишешь данные за пределами выделенного сегмента. Если ты попытаешься обратиться к индексу вне границ, ты получишь `IndexOutOfBoundsException` в Java-коде, а не сегментацию (Segfault) всей программы.

**В: Можно ли использовать `Arena.ofConfined()` в многопоточной среде?**
**О:** Нет. Как следует из названия, доступ к памяти, выделенной в такой арене, разрешен только тому потоку, который её создал. Для мультипоточности используй `Arena.ofShared()`.

**В: Что произойдет, если я попытаюсь обратиться к сегменту после закрытия `Arena`?**
**О:** Произойдет исключение `IllegalStateException`. Это и есть "Temporal Safety" — предотвращение ошибки использования освобожденной памяти.

# 🧠 Java 18 – Java 21: Value Objects & Memory Optimization

### 🎯 Суть проблемы: "The Object Overhead"
В классической Java каждый объект — это «тяжелая» сущность. У него есть **заголовок (Object Header)** (обычно 12-16 байт), информация о мониторе, метаданные и ссылка на класс. 

Если ты создаешь миллион объектов `Point(int x, int y)`, то на сами данные (8 байт) ты тратишь в 2-3 раза больше памяти на заголовки и ссылки. Это приводит к:
1.  **Memory Bloat:** Огромный расход RAM.
2.  **Pointer Chasing:** Процессор вынужден прыгать по адресам в памяти, что убивает кэш-локальность (L1/L2/L3 cache).

---

### 💎 1. Value Objects & Project Valhalla (Контекст)
*Важное уточнение: Полная реализация Value Objects (как части Project Valhalla) — это всё еще развивающийся процесс, но в версиях 18-21 закладывался фундамент и внедрялись концепты, которые к ним ведут.*

**Что такое Value Object (в идеале)?**
Это объект, у которого **нет identity (личности)**. У него нет `==` (сравнения по адресу), есть только состояние. 
*   **Обычный объект:** Это «коробка» с содержимым. Даже если содержимое одинаковое, коробки разные.
*   **Value Object:** Это само значение (как число `5`). Неважно, какая это «коробка», важно, что внутри `5`.

**Зачем это нужно для памяти?**
Если у объекта нет identity, JVM может **«схлопнуть» (flatten)** его. Вместо того чтобы хранить ссылку на объект в куче, JVM может встроить поля этого объекта прямо в тело другого объекта. 
*   *Результат:* Нет лишних ссылок $\to$ нет лишних заголовков $\to$ меньше работы для GC $\to$ выше скорость за счет кэша процессора.

---

### 📦 2. Records (Java 16+) — Наш текущий инструмент
Хотя `Records` — это не полноценные Value Objects из Valhalla, они являются их «духовными предками» в текущем релизе.

*   **Что это:** Неизменяемые (immutable) носители данных.
*   **Оптимизация:** Поскольку `Record` гарантированно неизменяем, JIT-компилятору гораздо проще проводить оптимизации (например, *Escape Analysis*). Если компилятор видит, что Record не «утекает» из метода, он может разложить его на примитивы прямо в стеке (Scalar Replacement), полностью избегая аллокации в куче.

---

### 🚀 3. Революция в Garbage Collection: Generational ZGC (Java 21)
Оптимизация памяти — это не только про то, сколько мы занимаем, но и про то, как быстро мы чистим. В Java 21 произошло важнейшее событие.

**Generational ZGC (Поколенческий ZGC):**
До этого ZGC был не поколенческим. Он сканировал всю кучу. Это круто для низких задержек (low latency), но плохо для throughput (пропускной способности).
*   **Что изменилось:** Теперь ZGC разделяет объекты на «молодые» и «старые». 
*   **Почему это важно для памяти:** Большинство объектов умирают молодыми. Теперь GC фокусируется на очистке только молодой части, не трогая стабильные старые объекты. Это резко снижает нагрузку на CPU и позволяет эффективнее управлять фрагментацией памяти.

---

### 🛠 Резюме по оптимизации (Cheat Sheet)
| Технология | Что делает | Профит |
| :--- | :--- | :--- |
| **Records** | Убирает шаблонный код, упрощает Escape Analysis. | Меньше мусора, лучше работа JIT. |
| **Generational ZGC** | Разделяет кучу на поколения. | Низкая задержка + высокая пропускная способность. |
| **Pattern Matching** | Позволяет эффективно деструктурировать Records. | Чистый код + эффективная проверка типов без лишних кастов. |

### ❓ FAQ (Частые вопросы на собеседовании)

**Q: Чем `Record` отличается от обычного `Class` в плане памяти?**
**A:** С точки зрения структуры в Heap — почти ничем (заголовок всё еще есть). Но с точки зрения оптимизации — `Record` дает JIT-компилятору сигнал, что данные неизменяемы, что позволяет проводить *Scalar Replacement* (разложение объекта на примитивы в стеке), чего нельзя гарантировать для обычного класса.

**Q: Если я использую ZGC, мне нужно ли настраивать память?**
**A:** ZGC очень умный, но Generational ZGC требует понимания того, что у тебя есть две зоны. Основной профит ты получишь, если твои приложения создают много короткоживущих объектов (что типично для микросервисов).

**Q: Когда Value Objects из Project Valhalla реально появятся?**
**A:** Это ongoing процесс. Мы уже видим элементы (Records, Pattern Matching), но "полное отсутствие заголовка" и "flattening" — это цель будущих релизов (предположительно Java 25+).

**Q: Помогает ли `final` в полях объектов оптимизации памяти?**
**A:** Напрямую — нет, он не уменьшает размер объекта. Но косвенно — да, так как `final` помогает JIT делать более агрессивные предположения о состоянии программы, что ведет к лучшей инлайнизации кода.
