# 🧠 Шпаргалка: Что такое Playwright?

### 📌 Суть в двух словах
**Playwright** — это современный фреймворк от Microsoft для автоматизации тестирования веб-приложений. Он позволяет писать надежные End-to-End (E2E) тесты, которые работают во всех современных браузерах (Chromium, Firefox, WebKit) с использованием единого API.

Если Selenium — это «старый добрый внедорожник», который медленный, но проедет везде, то Playwright — это «тесла» с автопилотом: очень быстрый, умный и умеет общаться с браузером на глубоком уровне.

---

### 🚀 Ключевые отличия от Selenium (Senior Perspective)

Главное отличие не в синтаксисе, а в **архитектуре**:

1.  **Протокол связи:**
    *   *Selenium* использует протокол WebDriver (HTTP-запросы). Каждый шаг — это отдельный запрос «клиент -> драйвер -> браузер». Это создает задержки (latency).
    тест $\rightarrow$ HTTP Request $\rightarrow$ Driver $\rightarrow$ Browser.
    *   *Playwright* использует **WebSocket** (одно постоянное соединение). Тест и браузер общаются в реальном времени. Это дает мгновенную реакцию и позволяет перехватывать события (например, сетевые запросы) «на лету».
2.  **Auto-waiting (Авто-ожидания):**
    В Selenium ты постоянно борешься с `NoSuchElementException` и пишешь кучу `WebDriverWait`. Playwright делает **Actionability checks** автоматически: прежде чем кликнуть, он проверяет, виден ли элемент, не перекрыт ли он другим элементом и не анимируется ли он.
3.  **Browser Contexts (Изоляция):**
    В Playwright ты можешь запускать тесты в разных «контекстах» внутри одного экземпляра браузера. Контекст — это как режим инкогнито. Он создается за миллисекунды, имеет свои куки и кэш, но не требует тяжелого перезапуска всего браузера. Это ключ к сверхбыстрому параллельному запуску.

---

### 🛠 Основные возможности

*   **Multi-browser:** Один код для Chrome, Firefox и Safari (через движок WebKit).
*   **Network Interception:** Ты можешь перехватить API-запрос от фронтенда, подменить его ответ (Mocking) или даже заблокировать загрузку тяжелой картинки, чтобы ускорить тест.
*   **Trace Viewer:** «Черный ящик» для тестов. После падения ты можешь открыть запись теста и буквально по кадрам увидеть, что происходило с DOM, сетью и консолью в момент ошибки.
*   **Codegen:** Генератор кода. Ты кликаешь по сайту — Playwright пишет Java-код за тебя.

---

### ⚠️ Нюансы (О чем не пишут в рекламных буклетах)

1.  **Не заменяет всё:** Playwright — это инструмент для UI/E2E. Если тебе нужно просто проверить API, лучше использовать чистый RestAssured или встроенный в Playwright `APIRequestContext`.
2.  **Сложные анимации:** Несмотря на авто-ожидания, очень сложные CSS-анимации или специфические JS-переходы иногда всё еще могут приводить к «флаканью» (flakiness) тестов. Нужно уметь использовать `waitForSelector` в редких случаях.
3.  **Зависимость от движков:** Playwright использует свои сборки браузеров (Chromium, WebKit). Это не совсем тот же Safari, что стоит у тебя на Mac, хотя разница минимальна для 99% тестов.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли использовать Playwright для тестирования мобильных приложений?**
**О:** Напрямую — нет. Он предназначен для веб-приложений. Но он отлично эмулирует мобильные браузеры (Viewport, User-Agent, Touch события). Для нативных приложений (iOS/Android) используй Appium.

**В: В чем преимущество использования Browser Context перед новым экземпляром Browser?**
**О:** Скорость и ресурсы. Создание `Browser` — тяжелая операция (запуск процесса браузера). Создание `Context` — мгновенная операция (создание новой папки профиля в памяти). Это позволяет запускать сотни тестов параллельно на одной машине.

**В: Как Playwright справляется с iFrames?**
**О:** В отличие от Selenium, где нужно постоянно делать `switchTo().frame()`, в Playwright ты используешь `FrameLocator`. Он позволяет искать элементы внутри фрейма так же естественно, как и на основной странице.

# 🛠 Тема 1: Установка и окружение (Setup & Environment)

Правильная настройка — это фундамент. Если здесь будет хаос (разные версии Java или браузеров у разработчика и на CI/CD), твои тесты будут падать "рандомно", и ты потратишь недели на поиск причин, которых нет в коде.

### 1. Пререквизиты (Что должно быть в системе)
Прежде чем писать первую строчку кода, убедись, что у тебя есть:
*   **JDK (Java Development Kit):** Рекомендую **11 или 17+**. Playwright активно использует современные возможности Java. Проверить: `java -version`.
*   **Build Tool:** **Maven** или **Gradle**. В мире Java это стандарт. Maven проще для начала, Gradle гибче для сложных проектов.
*   **IDE:** **IntelliJ IDEA** (лучший выбор для Java).

### 2. Управление зависимостями (Maven)
Забудь про ручное скачивание `.jar` файлов. Всё управление идет через `pom.xml`. 

Твой минимальный набор в `dependencies`:
```xml
<dependency>
    <groupId>com.microsoft.playwright</groupId>
    <artifactId>playwright</artifactId>
    <version>1.42.0</version> <!-- Всегда проверяй актуальную версию! -->
</dependency>
```
*Senior Tip: Никогда не используй динамические версии (типа `LATEST`). Это приведет к тому, что сегодня тест прошел, а завтра упал, потому что вышла новая версия Playwright с breaking changes.*

### 3. Установка браузеров (The Magic Step)
Playwright — это не Selenium. Он не использует тот Chrome, который ты установил себе на Windows. Он скачивает свои собственные, модифицированные сборки **Chromium, Firefox и WebKit**. Это гарантирует идентичность поведения во всех средах.

**Как установить:**
После добавления зависимости в Maven, тебе нужно запустить команду, которая скачает нужные бинарники браузеров. В Java это делается через выполнение CLI-команды Playwright:

```bash
mvn exec:java -e -Dexec.mainClass="com.microsoft.playwright.CLI" -Dexec.args="install"
```

*Нюанс:* Если ты работаешь в Docker или на Jenkins, этот шаг **обязателен** в пайплайне перед запуском тестов. Без этого браузеры просто не найдутся.

### 4. Режим работы: Headless vs Headed
По умолчанию Playwright запускает браузер в режиме **Headless** (без графического интерфейса). Это быстро и идеально для CI/CD.
Для отладки тебе понадобится **Headed** режим (видимое окно). Это настраивается в коде при создании объекта `BrowserType.LaunchOptions`.

---

### 💡 Важные нюансы от Senior'а

1.  **Версионный синк:** Версия библиотеки Playwright в `pom.xml` и версия браузеров, установленных через `install`, должны совпадать. Если обновил зависимость — сразу запусти `install` заново.
2.  **Зависимости ОС (Linux/Docker):** Если ты запускаешь тесты на Linux (например, в Jenkins или GitHub Actions), одного `playwright install` может быть мало. Системе могут понадобиться системные библиотеки (libgbm, libnss т.д.). В этом случае используй официальные образы Playwright для Docker — там всё уже настроено.
3.  **Изоляция:** Всегда помни, что Playwright по умолчанию старается изолировать контексты, но окружение (переменные среды, прокси) должно быть одинаковым везде.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему мои тесты работают на моем компе, но падают в Jenkins?**
**О:** Скорее всего, на Jenkins не выполнен шаг `playwright install` или в системе не хватает системных библиотек для работы браузеров Linux. Проверь логи установки браузеров.

**В: Можно ли использовать мой установленный Chrome вместо того, что скачал Playwright?**
**О:** Технически — да (через `executablePath`), но **не вздумай**. Твоя цель — воспроизводимость. Если у тебя обновится Chrome, а на сервере останется старый, тесты начнут вести себя непредсказуемо. Используй встроенные браузеры Playwright.

**В: Как быстро обновить Playwright во всем проекте?**
**О:** Измени версию в `pom.xml` и выполни команду `mvn exec:java ... -Dexec.args="install"`. Это обновит и библиотеку, и бинарники браузеров.

**В: Нужно ли мне устанавливать драйверы (как ChromeDriver)?**
**О:** Нет. В этом и есть киллер-фича Playwright. Он сам управляет версиями браузеров и протоколом взаимодействия. Забудь про `WebDriverManager`.

# 🧠 Шпаргалка: Иерархия объектов Playwright

В Playwright всё строится по принципу матрешки. Понимание этой вложенности — ключ к написанию быстрых, стабильных и параллельных тестов. Если ты поймешь разницу между `Browser` и `BrowserContext`, ты решишь 50% проблем с изоляцией данных.

### 🏗 Схема иерархии
**Playwright (Engine) ➔ Browser ➔ BrowserContext ➔ Page ➔ Frame**

---

#### 1. Playwright (Root Object)
Это "движок" или точка входа. Он управляет запуском процесса браузера и связью с драйвером.
*   **Суть:** Создает экземпляр управления всеми остальными объектами.
*   **Нюанс:** Его **обязательно** нужно закрывать (`playwright.close()`) в конце выполнения всех тестов (обычно в `@AfterAll`), иначе процесс браузера может "зависнуть" в памяти системы.

#### 2. Browser (The Application)
Это запущенный экземпляр конкретного браузера: Chromium, Firefox или WebKit.
*   **Суть:** Это тяжелый объект. Запуск `browser.launch()` — самая дорогая операция по времени и ресурсам.
*   **Нэнюс:** В одном тесте (или даже в разных тестах) **не нужно** запускать новый `Browser` для каждого сценария. Один запущенный браузер может обслуживать сотни тестов через разные контексты.

#### 3. BrowserContext (The Session / Incognito)
Самый важный объект для понимания архитектуры Playwright. Это "изолированная сессия". Представь, что ты открыл новое окно в режиме "Инкогнито".
*   **Суть:** У каждого контекста свои Cookies, LocalStorage, кеш и разрешения (геолокация, уведомления).
*   **Нюанс (Senior Tip):** Именно здесь происходит магия параллелизации. Чтобы протестировать два разных пользователя (User A и User B), тебе не нужно запускать два браузера. Тебе достаточно создать два `BrowserContext` внутри одного `Browser`. Это работает мгновенно и потребляет мало памяти.
*   **Фишка:** Здесь настраивается `storageState` (состояние авторизации), чтобы не логиниться в каждом тесте заново.

#### 4. Page (The Tab)
Это одна конкретная вкладка внутри контекста.
*   **Суть:** Почти весь твой код (клики, поиск элементов, ожидания) будет работать именно с объектом `Page`.
*   **Нюанс:** Контекст может содержать несколько страниц (вкладок), но обычно в одном тесте мы работаем с одной.

#### 5. Frame / FrameLocator (The Sub-window)
Это iframe — элемент внутри страницы, который является фактически другой HTML-страницей.
*   **Суть:** Позволяет взаимодействовать с контентом, который "вложен" в основной документ.
*   **Нюанс (Senior Tip):** Никогда не используй старый метод `page.frame()`. Всегда используй **`page.frameLocator()`**. Почему? Потому что `frameLocator` поддерживает **Auto-waiting**. Он будет ждать, пока iframe появится в DOM и станет доступным, в то время как старые методы могут упасть с ошибкой, если iframe еще не прогрузился.

---

### 💡 Резюме для архитектора
*   **Launch Browser once** (один раз на весь запуск тестов).
*   **Create Context per test** (новый контекст для каждого теста — это база изоляции).
*   **Create Page per test/scenario** (страница внутри контекста).

### ❓ FAQ (Частые вопросы на интервью)

**В: В чем главное отличие `Browser` от `BrowserContext`?**
**О:** `Browser` — это запущенный процесс приложения (например, Chrome), он тяжелый. `BrowserContext` — это изолированная сессия внутри этого процесса (как инкогнито-вкладка), она легкая и не имеет общих Cookies с другими контекстами.

**В: Можно ли использовать один `BrowserContext` для нескольких тестов одновременно?**
**О:** Технически — да, но **нельзя**. Это нарушит принцип изоляции. Если один тест изменит Cookie или удалит данные из LocalStorage, это повлияет на другие тесты. Всегда создавай новый контекст для каждого теста.

**В: Что произойдет, если я не вызову `playwright.close()`?**
**О:** Процесс драйвера Playwright может остаться висеть в оперативной памяти (Zombie process), что со временем забьет ресурсы сервера или CI-агента.

**В: Как протестировать взаимодействие между двумя разными пользователями?**
**О:** Нужно создать два разных `BrowserContext` внутри одного теста. В первом контексте ты выполняешь действия от лица Администратора, а во втором — от лица Клиента. Они не будут видеть Cookies друг друга.

# 🏗 Иерархия объектов Playwright

Если ты поймешь эту структуру, ты поймешь всё. Представь, что Playwright — это не просто библиотека для кликов, а иерархическая система управления процессами. В основе всего лежит принцип **«Матрешки»**.

### 🌲 Схема иерарэхии (от корня к ветке)
`Playwright` $\rightarrow$ `BrowserType` $\rightarrow$ `Browser` $\rightarrow$ `BrowserContext` $\rightarrow$ `Page`

---

### 1. Объект `Playwright` (The Root / Двигатель)
Это «точка входа» и самый главный объект. Он управляет запуском драйвера Playwright на твоей машине.
* **Что делает:** Инициализирует процесс связи между твоим Java-кодом и браузерным движком.
* **Жизненный цикл:** Его нужно создать один раз (обычно в `@BeforeAll`) и **обязательно** закрыть (`playwright.close()`) в конце всего прогона тестов.
* **⚠️ Нюанс Senior-уровня:** Если ты забудешь вызвать `.close()`, у тебя в системе могут остаться «зомби-процессы» (зависшие драйверы), которые будут жрать оперативную память. В Java всегда используй `try-with-resources`.

### 2. Объект `BrowserType` (The Factory / Завод)
Это не совсем объект, который ты хранишь, это «фабрика» для создания браузеров.
* **Что делает:** Позволяет выбрать движок: `playwright.chromium()`, `playwright.firefox()` или `playwright (webkit)`.
* **Суть:** Ты просто указываешь, какой тип браузера тебе нужен.

### 3. Объект `Browser` (The Process / Процесс)
Это запущенный экземпляр браузера (например, реальный процесс `chrome.exe`).
* **Что делает:** Это тяжеловесный объект. Он запускает полноценное окно браузера (хоть и без видимого интерфейса, если это headless mode).
* **Жизненный цикл:** Запуск браузера — дорогая операция по времени и ресурсам. В идеале, ты запускаешь один `Browser` на весь тестовый класс или даже на весь запуск тестов.

### 4. Объект `BrowserContext` (The Session / Изоляция)
**Самая важная концепция в Playwright.** Это «инкогнито-сессия» внутри одного браузера.
* **Что делает:** Создает абсолютно изолированную среду. У каждого контекста свои Cookies, LocalStorage, кэш и разрешения.
* **Почему это круто:** Вместо того чтобы перезапускать тяжелый `Browser` (что долго), ты просто создаешь новый `BrowserContext` (что мгновенно). Это позволяет запускать тесты параллельно, не боясь, что логика одного теста (например, авторизация) повлияет на другой.
* **⚠️ Нюанс Senior-уровня:** Именно здесь происходит магия мульти-аккаунтности. Хочешь протестировать чат? Создай `context1` (пользователь А) и `context2` (пользователь Б) внутри одного `Browser`.

### 5. Объект `Page` (The Tab / Вкладка)
Это обычная вкладка в браузере.
* **Что делает:** Именно здесь ты совершаешь все действия: `click()`, `fill()`, `navigate()`.
* **Связь:** Одна вкладка (`Page`) живет внутри контекста (`BrowserContext`). Ты можешь открыть 10 вкладок в одном контексте, но они будут делить одни и те же Cookies.

---

### 💻 Код: Как это выглядит в Java (Best Practice)

```java
import com.microsoft.playwright.*;

public class PlaywrightHierarchyExample {
    public static void main(String[] args) {
        // Используем try-with-resources, чтобы Playwright закрылся сам (защита от зомби-процессов)
        try (Playwright playwright = Playwright.create()) { 
            
            // 1. Выбираем тип браузера (BrowserType) и запускаем его (Browser)
            Browser browser = playwright.chromium().launch(new BrowserType.LaunchOptions().setHeadless(false));

            // 2. Создаем изолированную сессию (BrowserContext)
            // Это супер-быстро! Не нужно перезапускать браузер.
            BrowserContext context = browser.newContext();

            // 3. Открываем вкладку (Page)
            Page page = context.newPage();

            // Работаем с контентом
            page.navigate("https://google.com");
            System.out.println("Title: " + page.title());

            // Завершаем работу (Browser и Context закроются при закрытии Playwright или явно)
            browser.close();
        } 
    }
}
```

### ❓ FAQ (Частые вопросы на собеседовании)

# 🧠 Шпаргалка: Иерархия объектов Playwright — Browser

В Playwright всё строится на строгой иерархии. Если ты поймешь, за что отвечает уровень `Browser`, ты никогда не запутаешься в управлении сессиями и контекстами.

### 📍 Место в иерархии
`Playwright (Factory)` $\to$ **`Browser`** $\to$ `BrowserContext` $\to$ `Page`

---

### 🏗 Что такое Browser?
Если говорить просто: **`Browser` — это запущенный экземпляр браузерного движка.** 

Когда ты вызываешь `.launch()`, Playwright запускает реальный процесс в операционной системе (Chromium, Firefox или WebKit). Это «тяжелый» объект. Он потребляет много ресурсов (CPU, RAM), так как это полноценное приложение.

### 🛠 Основные возможности
1.  **Запуск движка:** Через `BrowserType` (Chromium, Firefox, WebKit) мы создаем экземпляр `Browser`.
2.  **Создание контекстов:** Единственная важная задача браузера в тестах — плодить `BrowserContext` (изолированные сессии).
3.  **Управление конфигурацией:** Здесь задаются глобальные параметры: `headless` режим, аргументы запуска (`args`), задержка (`slowMo`).

### 💻 Код (Java)
```java
import com.microsoft.playwright.*;

public class BrowserExample {
    public static void main(String[] args) {
        // 1. Инициализируем Playwright (наш завод по производству объектов)
        try (Playwright playwright = Playwright.create()) {
            
            // 2. Выбираем тип браузера и запускаем сам Browser
            // Это "тяжелая" операция. Делаем её один раз на запуск тестов.
            Browser browser = playwright.chromium().launch(new BrowserType.LaunchOptions()
                .setHeadless(false) // Видим окно браузера
                .setSlowMo(50));    // Задержка 5s для отладки

            // 3. Создаем контекст (изолированная сессия, как инкогнито)
            BrowserContext context = browser.newContext();

            // 4. Создаем страницу (вкладку)
            Page page = context.newPage();
            page.navigate("https://google.com");

            // 5. Обязательно закрываем браузер, чтобы не плодить процессы в системе
            browser.close();
        }
    }
}
```

### ⚠️ Senior Notes (Нюансы и подводные камни)

1.  **Ресурсная тяжесть:** **Никогда не запускай новый `Browser` для каждого теста.** Это убьет производительность твоего CI/CD. Правильный паттерн: Один `Browser` на весь тестовый прогон $\to$ Новый `BrowserContext` на каждый тест.
2.  **Изоляция:** `Browser` — это общая среда. Если ты упадешь с ошибкой и не закроешь `browser.close()`, в памяти процесса (или в Docker-контейнере) может остаться «зомби-процесс» браузера, который будет жрать память.
3.  **Launch Options:** Все настройки, сделанные на уровне `Browser` (например, `--disable-gpu`), дейдут на **все** вкладки и все контексты этого браузера. Если тебе нужно другое поведение для конкретной страницы — это делается в `BrowserContext`.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `Browser` и `BrowserContext`?**
**О:** `Browser` — это запущенное приложение (процесс в ОС). Он тяжелый. `BrowserContext` — это изолированная сессия внутри этого процесса (как режим инкогнито). Контексты очень легкие, их можно создавать сотнями за секунды. В контекстах разные Cookies и LocalStorage, но движок один и тот же.

**О:** Да, и это стандарт индустрии! Ты запускаешь один экземпляр `Browser`, а затем создаешь для каждого потока (теста) свой собственный `BrowserContext`. Это обеспечивает полную изоляцию данных между тестами при минимальных затратах ресурсов.

**О:** Это запуск браузера без графического интерфейса (в фоне). Он работает быстрее и потребляет меньше ресурсов. В 99% случаев на CI/CD (Jenkins, GitHub Actions) используется именно `headless: true`.

# 🧠 Шпаргалка: BrowserContext в Playwright

### 🎯 Что это такое?
Если `Browser` — это запущенный экземпляр браузера (например, Chrome), то **`BrowserContext`** — это изолированная сессия внутри этого браузера. 

**Простая аналогия:** Представь, что ты открыл Google Chrome. Сам процесс браузера — это `Browser`. А каждое новое окно в режиме **«Инкогнито»** — это `BrowserContext`. У каждого окна своя история посещений, свои куки и свой кэш. Они не знают о существовании друг друга.

---

### 🛠 Ключевые возможности (Зачем он нужен?)

1.  **Абсолютная изоляция:** Каждый тест должен запускаться в своем `BrowserContext`. Это гарантирует, что куки или состояние авторизации из Теста №1 не «протекут» в Тест №

2.  **Легковесность (Performance):** Запуск нового `Browser` — это тяжелая операция (запуск процесса в ОС). Создание нового `BrowserContext` — это мгновенная операция внутри уже запущенного процесса. Это ключ к сверхбыстрым тестам.

3.  **Эмуляция окружения:** Внутри контекста ты можешь подменить:
    *   **Геолокацию** (представиться пользователем из Лондона).
    *   **Permissions** (разрешить или запретить доступ к камере/микрофону).
    *   **Viewport** (размер экрана, мобильный или десктопный).
    *   **User-Agent** (притвориться iPhone или Android).
    *   **Эмуляцию сети** (замедление интернета).

4.  **Multi-session testing:** Ты можешь создать два контекста одновременно: в одном — «Админ», в другом — «Клиент», и проверять их взаимодействие (например, чат) в одном тесте.

---

### 🏗 Иерархия и связь
`Playwright` $\rightarrow$ `Browser` $\rightarrow$ **`BrowserContext`** $\rightarrow$ `Page`

*   В одном `Browser` может быть много `BrowserContext`.
*   В одном `BrowserContext` может быть много `Page` (вкладок).
*   Все вкладки (`Page`) внутри одного контекста **делят между собой** куки, localStorage и сессию.

---

### ⚠️ Нюансы и Best Practices (Советы Senior-а)

*   **❌ Ошибка:** Использовать один `BrowserContext` для всех тестов в прогоне.
    *   *Результат:* Тесты станут зависимыми друг от друга. Если один тест залогинится, второй может упасть, потому что он ожидал «чистый» браузер.
*   **✅ Правило:** Один тест = один `BrowserContext`.
*   **🚀 Оптимизация (Storage State):** Чтобы не проходить процедуру логина в каждом тесте (это долго), используй фичу `storageState`. Ты один раз логинишься в контексте, сохраняешь куки и localStorage в JSON-файл, а потом при создании новых контекстов просто подгружаешь этот файл. Это экономит до 50% времени прогона.
*   **🌍 Тестирование локализации:** Если нужно проверить сайт на французском, не меняй настройки системы. Просто создай `BrowserContext` с переопределенным `locale: 'fr-FR'`.

**В: Чем `BrowserContext` отличается от `Page`?**
**О:** `Page` — это конкретная вкладка. `BrowserContext` — это среда, в которой живут эти вкладки. Если ты закроешь `Page`, контекст останется. Если ты закроешь `BrowserContext`, все вкладки и их данные (куки, кэш) будут уничтожены.

**О:** Да, но тебе нужно создать два разных `BrowserContext`. Один с настройками мобильного эмулятора, другой — стандартный.

**В: Как протестировать доступ к микрофону без реального устройства?**

**О:** Неизмеримо быстрее `BrowserContext`. Именно поэтому в Playwright тесты работают быстрее, чем в классическом Selenium.

# 📄 Шпаргалка: Объект `Page` в Playwright

### 🧠 Суть (The Core)
Если браузер — это приложение, а `BrowserContext` — это режим инкогнито, то **`Page` — это одна конкретная вкладка** в этом режиме. 

`Page` — это основной рабочий инструмент автоматизатора. Именно через него мы взаимодействуем с контентом: кликаем, пишем текст, проверяем URL и перехватываем сетевые запросы.

---

### 🏗 Место в иерархии
Чтобы понимать масштаб, запомни цепочку:
`Playwright` $\rightarrow$ `Browser` $\rightarrow$ `BrowserContext` $\rightarrow$ **`Page`**

*   **Browser**: Один экземпляр браузера (например, Chromium).
*   **BrowserContext**: Изолированная сессия (свои cookies, localStorage, кеш). Представь, что это отдельное окно инкогнито.
*   **Page**: Вкладка внутри этой сессии.

> **Senior Note:** Ты можешь открыть 10 вкладок (`Page`) в одном `BrowserContext`. Все они будут делить одни и те же Cookies и Session Storage. Это критично для тестирования сценариев, где один пользователь открывает несколько страниц.

---

### 🛠 Основные возможности (Capabilities)

#### 1. Навигация (Navigation)
*   `page.navigate(url)` — переход по адресу.
*   `page.waitForLoadState(state)` — ожидание завершения загрузки. 
    *   `load` (полная загрузка), `domcontentloaded` (DOM готов), `networkidle` (сеть затихла — *использовать осторожно!*).

#### 2. Визуальная проверка и отчетность
*   `page.screenshot(options)` — создание скриншота (fullPage: true позволяет снять всю страницу целилостно, а не только видимую часть).
*   `page.pdf(options)` — генерация PDF (только для Chromium).

#### 3. Перехват событий (Event Listeners)
Это "суперсила" `Page`. Ты можешь подписываться на события браузера:
*   `page.onDialog(dialog -> ...)` — обработка алертов, подтверждений и промптов.
*   `page.onConsoleMessage(msg -> ...)` — логирование того, что пишет фронтенд в консоль (помогает дебажить ошибки JS).
*   `page.onResponse(response -> ...)` — мониторинг всех ответов от сервера.

#### 4. Работа с сетевым уровнем (Network Interception)
Хотя `route` часто вызывается на уровне контекста, именно через `Page` мы управляем тем, как вкладка реагирует на запросы (подмена ответов, блокировка картинок).

---

### ⚠️ Нюансы и «Подводные камни» (Senior Tips)

1.  **Race Condition при навигации:** Никогда не делай `page.navigate()` и сразу начинай кликать по элементам без проверки. Хотя Playwright имеет *Auto-waiting*, иногда страница может начать редирект сразу после загрузки. Используй `page.waitForURL()`.
2.  **Смерть страницы:** Если ты закрыл `BrowserContext`, все связанные с ним `Page` мгновенно уничтожаются. Ошибка `Target closed` — классика, когда код пытается взаимодействовать с уже закрытой вкладкой.
3.  **Network Idle — это ловушка:** Использование `networkidle` часто приводит к нестабильным тестам (flakiness). Если на странице висит какой-нибудь аналитический скрипт (Google Analytics), который постоянно шлет запросы, тест будет ждать вечно или упадет по таймауту. Лучше ждать конкретный элемент или сетевой запрос (`waitForResponse`).
4.  **Память:** Если в одном тесте ты открываешь десятки страниц через `context.newPage()`, следи за потреблением RAM. Всегда закрывай ненужные вкладки, если они не нужны для текущего сценария.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Можно ли использовать одну и ту же `Page` для разных пользователей в одном тесте?**
**О:** Технически — да. Но практически — нет. Если тебе нужно протестировать взаимодействие двух пользователей, тебе нужны два разных `BrowserContext`. Только так у них будет разный набор Cookies и сессий.

**В: В чем разница между `page.click()` и `page.locator().click()`?**
**О:** С точки зрения результата — почти никакой. Но архитектурно: `page.click(selector)` — это старый стиль (ElementHandle). Современный стандарт — всегда создавать `Locator` через `page.locator(...)`, так как локаторы обладают встроенной логикой перепроверки (retries) и более стабильны.

**В: Как поймать ошибку в консоли браузера с помощью `Page`?**
**О:** Нужно подписаться на событие: 
`page.onConsoleMessage(msg -> { if (msg.type().equals("error")) { throw new RuntimeException(msg.text()); } });`

# 📑 Шпаргалка: Жизненный цикл теста (Test Lifecycle)

В Playwright Java жизненный цикл — это не только выполнение методов `@Test`, но и управление ресурсами (браузером, контекстом и страницами). Если ты не управляешь ими правильно, твои тесты будут либо тормозить, либо «протекать» (один тест будет влиять на другой).

### 🏗 Иерархия объектов (Сверху вниз)
Чтобы понять жизненный цикл, нужно понимать, что мы создаем и уничтожаем:
1.  **`Playwright`**: Движок. Самый тяжелый объект. Создается один раз на запуск сессии.
2.    **`Browser`**: Инстанс браузера (Chromium/Firefox). Тяжелый процесс. Обычно живет всё время выполнения тестового класса.
3.  **`BrowserContext`**: «Изолированная вкладка» (как режим инкогнито). **Ключевой объект.** Легкий. Создается для каждого теста. В нем свои куки, кэш и localStorage.
4.  **`Page`**: Конкретная вкладка внутри контекста.

---

### 🔄 Этапы жизненного цикла (на примере JUnit 5)

Правильный подход — **Reusing Browser, Recreating Context**. Мы не перезапускаем браузер для каждого теста (это слишком долго), но мы создаем новый чистый контекст.

#### 1. `@BeforeAll` — Подготовка фундамента
Здесь мы инициализируем `Playwright` и запускаем `Browser`. Это происходит **один раз** перед всеми тестами в классе.
*   **Что делаем:** Инициализация драйвера, запуск браузера.

####  2. `@BeforeEach` — Создание чистого листа
Здесь мы создаем `BrowserContext` и `Page`. 
*   **Зачем:** Чтобы каждый тест начинался с «чистого инкогнито» (без старых куки и сессий). Это гарантирует **изоляцию**.
*   **Что делаем:** Создание контекста, создание страницы, переход на базовый URL.

#### 3. `@Test` — Само действие
Выполнение бизнес-логики: клики, проверки, ожидания.

#### 4. `@AfterEach` — Уборка за тестом
Закрываем `Page` и `BrowserContext`. 
*   **Зачем:** Чтобы не плодить висящие процессы и очистить память.

#### 5. `@AfterAll` — Завершение работы
Закрываем `Browser` и сам объект `Playwright`.
*   **Зачем:** Полная очистка ресурсов системы.

---

### 💻 Пример эталонной реализации (Java + JUnit 5)

```java
import com.microsoft.playwright.*;
import org.junit.jupiter.api.*;

public class BaseTest {
    // Статические объекты, которые живут долго (на уровне класса)
    protected static Playwright playwright;
    protected static Browser browser;

    // Динамические объекты (меняются в каждом тесте)
    protected BrowserContext context;
    protected Page page;

    @BeforeAll
    static void launchBrowser() {
        playments = Playwright.create();
        browser = playwright.chromium().launch(new BrowserType.LaunchOptions().setHeadless(false));
    }

    @BeforeEach
    void createContext() {
        // Каждый тест получает свой чистый контекст (как инкогнито)
        context = browser.newContext();
        page = context.newPage();
    }

    @AfterEach
    void closeContext() {
        // Закрываем контекст, очищая куки и кэш этого теста
        if (context != null) {
            context.close();
        }
    }

    @AfterAll
    static void shutdown() {
        // Полная остановка всего движка
        if (browser != null) browser.close();
        if (playwright != null) playwright.close();
    }
}
```

### ⚠️ Нюансы от Senior-а

1.  **Проблема «Утечки контекста»:** Если ты создашь `BrowserContext` в `@BeforeAll`, то все тесты будут использовать одни и те же куки. Если первый тест залогинится, второй тест тоже будет залогинен. Это **плохо**, так как нарушается изоляция. Всегда делай контекст в `@BeforeEach`.
2.  **Параллелизация:** Playwright идеально подходит для параллельного запуска. Если ты используешь один `Browser` для всех тестов, но разные `BrowserContext` для каждого — тесты могут летать в 10 потоков без конфликтов.
3.  **Headless vs Headed:** В `@BeforeAll` важно уметь переключать режим (с видимым браузером или без). В CI/CD всегда используй `setHeadless(true)`.
4.  **Забытый `.close()`:** Если не закрывать `BrowserContext` в `@AfterEach`, со временем память на агенте (в Jenkins/GitHub Actions) закончится, и тесты начнут падать с `OutOfMemoryError`.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Можно ли запускать браузер (`Browser`) в `@BeforeEach`?**
**О:** Технически — можно. Но это очень медленно. Запуск процесса браузера занимает секунды, а создание контекста — миллисекунды. Если у тебя 100 тестов, разница будет в минуты.

**В: Что если тест упал на середине? Выполнится ли `@AfterEach`?**
**О:** Да. В JUnit/TestNG аннотации завершения (`@AfterEach`, `@AfterAll`) гарантированно выполняются даже при провале теста. Это критически важно для очистки ресурсов.

**В: Как передать авторизацию из одного теста в другой, чтобы не логиниться каждый раз?**
**О:** Используй механизм `storageState`. Ты один раз логинишься в специальном тесте, сохраняешь состояние контекста (куки/локальное хранилище) в JSON-файл, а затем в `@BeforeEach` загружаешь этот файл в новый `BrowserContext`. Это "золотой стандарт" скорости в Playwright.

# 🧠 Шпаргалка: Locators vs ElementHandles

### 📌 Короткая суть
Если ты хочешь, чтобы твои тесты не падали при каждом обновлении страницы или рендеринге компонента (что в React/Angular происходит постоянно), **забудь про ElementHandle и используй только Locators.**

---

### 1. ElementHandle (Устаревший подход / "Снимок")
`ElementHandle` — это прямая ссылка на конкретный узел в DOM-дереве в **конкретный момент времени**.

*   **Как это работает:** Ты находишь элемент, Playwright «схватил» его и держит в памяти.
*   **Главная проблема (Stale Element):** Если после того, как ты нашел элемент, страница обновилась (например, прилетел новый JSON по API и React перерисовал компонент), твоя ссылка на элемент становится **мертвой**. Попытка кликнуть по ней вызовет ошибку.
*   **Отсутствие магии:** `ElementHandle` не умеет ждать. Если элемент еще не появился или перекрыт лоадером, тебе придется писать `waitFor...` вручную.

### 2. Locator (Современный подход / "Рецепт")
`Locator` — это не сам элемент, а **инструкция (логика)**, как его найти. Это «рецепт» поиска.

*   **Как это работает:** Когда ты вызываешь `locator.click()`, Playwright берет твой "рецепт", идет в браузер, ищет элемент заново, проверяет, виден ли он, не перекрыт ли он другим элементом, и только потом кликает.
*   try **Auto-waiting:** Локатор автоматически применяет все проверки (actionability checks): видимость, стабильность анимации, доступность.
*   **Устойчивость к рендерингу:** Если страница обновилась, локатор просто выполнит поиск заново по своей инструкции и найдет «новый» элемент. Для теста это выглядит бесшовно.

---

### 📊 Сравнительная таблица

| Характеристика | ElementHandle | Locator |
| :--- | :--- | :--- |
| **Что это?** | Ссылка на конкретный узел DOM | Инструкция по поиску элемента |
| **Auto-waiting** | Нет (нужно писать вручную) | **Да (встроено по умолчанию)** |
| **Реакция на рендер** | Ошибка `Stale Element` | Находит элемент заново (Success) |
| **Надежность** | Низкая (Flaky) | Высокая (Stable) |
| **Использование** | Редко (для очень специфичных задач) | **Основной инструмент** |

---

### 🛠 Пример на Java

**Плохой путь (ElementHandle):**
```java
// Нашли элемент
ElementHandle button = page.querySelector("button#submit"); 

// Представим, что в этот момент страница обновилась (AJAX)
// Следующая строка упадет с ошибкой, так как старая ссылка невалидна
button.click(); 
```

**Правильный путь (Locator):**
```java
// Создали инструкцию (поиск еще не выполнялся!)
Locator button = page.locator("button#submit");

// В момент вызова click(), Playwright:
// 1. Ищет кнопку
// 2. Ждет, пока она станет кликабельной
// 3. Кликает
button.click(); 
```

---

### 💡 Нюансы от Senior'а

1.  **Lazy Evaluation (Ленивые вычисления):** Помни, что создание `Locator` не стоит ресурсов, потому что поиск в DOM происходит только в момент **действия** (`click`, `fill`, `innerText`). Это позволяет тебе инициализировать все локаторы в Page Object при создании класса, не боясь, что они "протухнут".
2.  **Chaining (Цепочки):** Локаторы позволяют строить цепочки: `page.locator(".row").locator(".delete-btn")`. Это создает мощный и читаемый инструмент для работы со сложными структурами данных.
3.  **Когда всё же нужен ElementHandle?** Только в экстремальных случаях, когда тебе нужно работать с низкоуровневым JS-выполнением или когда ты делаешь что-то очень специфическое с объектами браузера, чего не покрывает API локаторов (но 99.9% задач решаются локаторами).

---

### ❓ FAQ (Частые вопросы)

**В: Почему мои тесты на Selenium падали из-за `StaleElementReferenceException`, а в Playwright с Locators — нет?**
**О:** Потому что Selenium работал с "фотографиями" элементов (`ElementHandle`), а Playwright работает с "описаниями" (`Locator`). При перерисовке DOM описание остается верным, а фотография устаревает.

**В: Если я создам 100 локаторов в конструкторе Page Object, не замедлит ли это инициализацию теста?**
**О:** Нет. Создание локатора — это просто создание объекта-инструкции. Реальная работа (поиск в DOM) начнется только при вызове метода действия.

**В: Можно ли использовать CSS/XPath внутри Locator?**
**О:** Да, конечно. `page.locator("xpath=//div")` или `page.locator(".my-class")`. Но Senior рекомендует использовать `getByRole`, `getByText` и т.д., так как они делают тесты устойчивыми к изменениям верстки (пользовательский подход).

# 🧠 Шпаргалка: Встроенные локаторы (Built-in Locators)

### 🎯 Главная философия
Забудь про "хрупкие" пути вроде `//div/div[2]/span`. Это путь к боли. Современный подход в Playwright — **User-facing locators**. Мы ищем элементы так, как их видит пользователь или скринридер (программа для слабовидящих). Если пользователь не может найти кнопку по тексту "Оплатить", то и твой тест не должен искать её по сложному XPath.

---

### 🛠 Список локаторов

#### 1. `getByRole(AriaRole role, Locator options)` — **Король локаторов**
Самый мощный инструмент. Он ищет элемент по его семантической роли в дереве доступности (Accessibility Tree).
*   **Пример:** `page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Submit"));`
*   **Зачем:** Если разработчик изменит `<div>` на `<button>`, твой тест не сломается, так как роль останется прежней.
*   **Популярные роли:** `BUTTON`, `CHECKBOX`, `HEADING`, `LINK`, `TEXT`, `LIST`, `TABLE`.

#### 2. `getByText(String text)` — Поиск по тексту
Ищет элемент, содержащий указанный текст.
*   **Пример:** `page.getByText("Welcome, Admin!");`
*   **Нюанс:** По умолчанию ищет подстроку. Если нужно точное совпадение, используй регулярное выражение или параметр `exact: true`.

#### 3. `getByLabel(String text)` — Для форм
Ищет элемент (обычно `input`), связанный с `<label>`, у которого есть указанный текст.
*   **Пример:** `page.getByLabel("Username");`
*   **Зачем:** Это имитирует поведение человека: "Я вижу надпись 'Email' и ввожу данные в поле рядом".

#### 4. `getByPlaceholder(String text)` — Поиск по плейсхолдеру
Используется для полей ввода, где текст подсказки является единственным ориентиром.
*   **Пример:** `page `page.getByPlaceholder("Enter your password");`

#### 5. `getByAltText(String text)` — Для изображений
Ищет элементы (например, `<img>`), у которых атрибут `alt` содержит нужный текст.
*   **Пример:** `page.getByAltText("Company Logo");`

#### 6. `getByTitle(String text)` — По атрибуту `title`
Ищет элемент, у которого есть всплывающая подсказка (атрибут `title`).
*   **Пример:** `page.getByTitle("Close window");`

#### 7. `getByTestId(String id)` — "План Б" (Escape Hatch)
Если элемент не имеет понятной роли или текста (например, иконка без подписи), используй специальный атрибут для тестов.
*   **Пример:** `page.getByTestId("submit-button");`
*   **Senior Tip:** Договорись с разработчиками, чтобы они вешали `data-testid="..."` на сложные элементы. Это самый стабильный способ автоматизации.

---

### 💡 Важные нюансы (Pro Tips)

1.  **Chaining (Цепочки):** Локаторы можно комбинировать.
    *   `page.getByRole(AriaRole.LISTITEM).filter(new Locator.FilterOptions().setHasText("Apple")).getByRole(AriaRole.BUTTON);`
    *   *(Перевод: Найди элемент списка с текстом "Apple", а внутри него найди кнопку).*
2.  **Exact Match:** Почти во всех методах можно передать `new Page.GetByTextOptions().setExact(true)`. Это критично, если у тебя есть кнопки "Cancel" и "Cancel All". Без `exact: true` локатор может найти обе.
3.  **Regex (Регулярные выражения):** Если текст динамический (например, содержит дату), используй `Pattern`:
    *   `page.getByText(Pattern.compile("Order #\\d+"));`
4.  **Auto-waiting:** Все встроенные локаторы в Playwright "умные". Когда ты вызываешь `.click()`, Playwright не просто ищет элемент, а ждет, пока он станет видимым, перестанет двигаться и перекроваться другими элементами.

### ❓ FAQ (Частые вопросы)

**В: Почему нельзя использовать `page.locator(".css-class")` везде?**
**О:** Классы часто генерируются динамически (например, в React/Styled Components) и меняются при каждом билде. Это главная причина "хрупких" тестов. Встроенные локаторы опираются на смысл (роль, текст), который меняется редко.

**В: Что делать, если `getByRole` не находит кнопку, хотя она есть?**

**О:** Иконки не имеют текста. Используй `getByRole` с проверкой `aria-label` или `getByTestId`.

**В: Можно ли использовать `getByText` вместе с фильтрацией?**
**О:** Да! Это отличный способ сузить поиск: `page.locator('.card').filter(new Locator.FilterOptions().setHasText('Success')).getByRole(AriaRole.BUTTON);`

# 🎯 Тема: Встроенные локаторы — `getByRole`

### 💡 Суть метода
`getByRole` — это самый важный и «правильный» способ поиска элементов в Playwright. Его философия: **«Тестируй так, как это видит пользователь или скринридер (программа для незрячих)»**. 

Вместо того чтобы искать элемент по хрупкому CSS-классу `.btn-primary-v2`, мы ищем его по его **роли** (что это за объект?) и **доступному имени** (как он называется?).

### 🛠 Как это работает
Метод ищет элементы по их ARIA-ролям (Accessible Rich Internet Applications). Если элемент семантически корректен (используется `<button>`, `<a>`, `<h1>`), Playwright легко его найдет.

#### Основные параметры:
1.  **`role`** (String): Тип элемента (`button`, `link`, `checkbox`, `heading`, `textbox`, `listitem` и т.д.).
2.  **`name`** (String/RegExp): «Доступное имя» элемента. Это может быть текст внутри кнопки, текст в `aria-label`, или содержимое тега `<label>`.
3.  **`exact`** (Boolean): Если `true`, то поиск идет по точному совпадению (с учетом регистра). По умолчанию — `false` (частичное совпадение).
4.  **Дополнительные атрибуты**: `checked`, `disabled`, `level` (для заголовков), `pressed`.

---

### 💻 Примеры кода (Java)

```java
// 1. Базовый поиск кнопки по тексту
page.getByRole(AriaRole.BUTTON, new Page.GetByRoleOptions().setName("Submit")).click();

// 2. Поиск ссылки с точным совпадением имени
page.getByRole(AriaRole.LINK, new Page.GetByRoleOptions().setName("Login").setExact(true));

// 3. Поиск заголовка (h1) определенного уровня
page.getByRole(AriaRole.HEADING, new Page.GetByRoleOptions().setLevel(1));

// 4. Поиск чекбокса, который должен быть включен (checked)
page.getByRole(AriaRole.CHECKBOX, new Page.GetByRoleOptions().setName("Subscribe")).check();

// 5. Поиск текстового поля по его label
page.getByRole(AriaRole.TEXTBOX, new Page.GetByRoleOptions().setName("Username")).fill("admin");
```

---

### ⚠️ Нюансы от Senior-а (На что наступишь, если не знать)

1.  **Зависимость от семантики**: Если разработчик сделал кнопку через `<div>` и забыл добавить `role="button"`, `getByRole(AriaRole.BUTTON)` её **не найдет**. Это отличный способ «наказать» разработчиков за плохую доступность (Accessibility) и одновременно сделать тесты качественнее.
2.  **Понятие "Accessible Name"**: Помни, что `name` — это не всегда видимый текст. Если у иконки-кнопки есть атрибут `aria-label="Close"`, то для Playwright её имя — `"Close"`, даже если внутри кнопки нет текста.
3.  **Приоритет над CSS**: Всегда старайся использовать `getByRole` вместо `locator(".my-class")`. Классы меняются при редизайне, а роли и названия (логика приложения) — крайне редко.
4.  **Регулярные выражения**: Если текст динамический (например, "Welcome, Ivan!"), используй `Pattern` (RegExp). 
    *   `setName(Pattern.compile("Welcome, .*"))`.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Почему `getByRole` лучше, чем `getByText`?**
**О:** `getByText` просто ищет строку в DOM. Он может найти текст внутри невидимого элемента или в куске текста, который не является интерактивным. `getByRole` гарантирует, что мы взаимодействуем именно с *интерактивным* элементом (кнопкой, ссылкой), что имитирует реальное поведение пользователя.

**В: Что делать, если я не знаю, какой `role` у элемента?**
**О:** Используй **Playwright Inspector** или вкладку **Accessibility** в Chrome DevTools. Там четко написано, как браузер классифицирует этот элемент. Также можно использовать команду `npx playwright codegen`.

**В: Может ли `getByRole` найти несколько элементов?**
**О:** Да. Если на странице три кнопки "Delete", `getByRole` вернет все три. В этом случае тебе нужно будет либо уточнить поиск через `.filter()`, либо использовать `.first()`, `.last()`, или `.nth(index)`.

**В: Как найти элемент, если у него нет текста, а только иконка?**
**О:** Проверь наличие `aria-label` или `title`. Если их нет — это баг доступности. В идеале ты должен требовать от команды добавить `aria-label`, чтобы твой тест (и пользователи с нарушениями зрения) могли его найти.

# 📍 Шпаргалка: Встроенные локаторы (User-facing Locators)

### 🧠 Философия Senior-подхода
Забудь про длинные XPath и сложные CSS-селекторы типа `div > div > span:nth-child(3)`. Они "хрупкие": изменился один `div` в верстке — тест упал.

Playwright продвигает использование **User-facing locators**. Это локаторы, которые имитируют поведение реального пользователя. Пользователь не ищет элемент по ID или классу; он ищет кнопку с текстом "Войти" или поле с надписью "Email". Если ты используешь эти локаторы, твои тесты становятся **неубиваемыми** при рефакторинге кода.

---

### 1. `getByText(String text, Locator.GetByTextOptions options)`
Ищет элемент по его видимому текстовому содержимому.

*   **Как работает:** Ищет совпадение текста внутри элемента или его дочерних элементов.
*   **Нюанс (Exact match):** По умолчанию поиск идет по **частичному** совпадению и игнорируя регистр. Если ты хочешь точного совпадения, обязательно используй параметр `exact: true`.
*   **Когда использовать:** Для проверки заголовков, сообщений об ошибках, текстов в абзацах (`p`, `span`, `div`).

```java
// Найдет "Hello", "Hello World" и "hello"
page.getByText("Hello").click(); 

// Найдет ТОЛЬКО "Hello" (строгое соответствие)
page.getByText("Hello", new Page.GetByTextOptions().setExact(true)).click();
```

---

### 2. `getByLabel(String text, Locator.GetByLabelOptions options)`
Ищет форму (input, textarea, select) по тексту связанного с ней тега `<label>`.

*   **Как работает:** Он ищет элемент управления, который программно связан с текстом в теге `<label>` (через атрибут `for` или вложение).
*   **Почему это круто:** Это проверка **доступности (Accessibility)**. Если `getByLabel` не находит поле — значит, пользователи со скринридерами (слепые люди) тоже не смогут им воспользоваться. Твой тест здесь выступает как аудитор качества.
*   **Нюанс:** Если разработчик забыл связать `label` и `input`, этот локатор **не сработает**, даже если текст на экране есть.

```java
// Ищет <label>Username</label> <input name="user">
page.getByLabel("Username").fill("admin");

// С точным совпадением
page.getByLabel("Email", new Page.GetByLabelOptions().setExact(true)).fill("test@test.com");
```

---

### 3. `getByPlaceholder(String text, Locator.GetByPlaceholderOptions options)`
Ищет поле ввода по тексту подсказки (атрибут `placeholder`), который виден внутри поля до начала ввода.

*   **Как работает:** Ищет элемент, у которого атрибут `placeholder` совпадает с переданной строкой.
*   **Когда использовать:** Когда нет видимого `<label>` (плохая практика в UI, но часто встречается) или когда нужно взаимодействовать именно с подсказкой.
*   **Нюанс:** Это менее надежный локатор, чем `getByLabel`. Текст плейсхолдера часто меняется при локализации (переводе на другой язык) или редизайне. Используй его как "план Б".

```java
// Ищет <input placeholder="Введите ваш пароль">
page.getByPlaceholder("Введите ваш пароль").fill("12345");
```

### 🚀 Резюме по приоритетам (Best Practices)

При выборе локатора следуй этой иерархии (от лучшего к худшему):
1.  **`getByRole`** (самый надежный, проверяет роль элемента: button, checkbox).
2.  **`getByLabel`** (проверяет связь текста и поля).
3.  **`getByText`** (проверяет видимый контент).
4.  **`getByPlaceholder`** (зависит от атрибута, который может измениться).
5.  **CSS/XPath** (крайний случай, когда ничего другого нет).

**В: Что делать, если `getByText` находит сразу пять элементов с одинаковым текстом?**
**О:** Не используй индекс (`first()`, `nth(2)`), это путь к хрупким тестам. Используй **фильтрацию**. Найди родительский контейнер (например, через `getByRole("listitem")`) и примени `.filter()` к нему, чтобы уточнить поиск.

**В: Почему мой `getByLabel` не работает, хотя текст на экране есть?**
**О:** Проверь HTML-код. Текст должен быть либо внутри тега `<label>`, который оборачивает инпут, либо у тега `<label>` должен быть атрибут `for`, совпадающий с `id` инпута. Если связи нет — Playwright не "видит" их как одно целое.

**В: Можно ли использовать регулярные выражения в этих локаторах?**
**О:** Да! В Java ты можешь передать паттерн. Это очень удобно для динамических строк (например, когда в тексте есть ID или дата):
`page.getByText(Pattern.compile("Order #\\d+")); // Найдет "Order #123"`

# 🛠 Шпаргалка: User-Facing & TestId Locators

В Playwright эти три метода относятся к категории **User-facing locators**. Их главная цель — сделать тесты устойчивыми к изменениям дизайна. Если дизайнер изменит цвет кнопки или переименует класс в CSS, твой тест не упадет, потому что он ищет «смысл», а не «код».

---

### 1. `getByAltText` (Локатор по альтернативному тексту)
Используется для поиска элементов (чаще всего изображений `<img>`), у которых есть атрибут `alt`.

*   **Суть:** Мы имитируем то, как скринридер (программа для слабовидящих) описывает картинку пользователю.
*   **Когда использовать:** Идеально для проверки наличия логотипов, иконок или баннеров.
*   **Пример кода:**
    ```java
    // Найдет <img src="logo.png" alt="Company Logo">
    page.getByAltText("Company Logo").click();
    ```
*   **💡 Senior Pro-Tip:** Если у картинки нет атрибута `alt`, этот локатор её не найдет. При тестировании доступности (Accessibility) это отличный способ убедиться, что разработчики не забыли описать важные изображения.

---

### 2. `getByTitle` (Локатор по атрибуту title)
Ищет элементы, у которых есть атрибут `title` (всплывающая подсказка при наведении).

*   **Суть:** Поиск по тексту, который появляется в "тултипе" (tooltip).
*   **Когда использовать:** Когда текст не виден на самой странице постоянно, но он доступен пользователю через системную подсказку.

*   **Пример кода:**
    ```java
    // Найдет <span title="Close Menu">✖</span>
    page.getByTitle("Close Menu").click();
    ```
*   **⚠️ Нюанс:** Не злоупотребляй этим. Атрибут `title` часто меняется или может быть пустым. Это «второстепенный» локатор по сравнению с `getByRole`.

---

### 3. `getByTestId` (Локатор по техническому ID)
Это твой «план Б» и самый стабильный инструмент. Он ищет элемент по специальному атрибуту (по умолчанию `data-testid`).

*   **Суть:** Мы просим разработчиков добавить в HTML специальный атрибут, который **не меняется** при редизайне.
*   **Когда использовать:** Когда элемент слишком сложный, динамический или не имеет понятного текстового описания (например, кнопка «удалить» без текста, только иконка).
*   **Пример кода:**
    ```java
    // Найдет <button data-testid="submit-button">Submit</button>
    page.getByTestId("submit-button").click();
    ```
*   **💡 Senior Pro-Tip:** 
    1. **Никогда** не используй CSS-классы (`.btn-primary`) или XPath для бизнес-логики. Это хрупко.
    2. Если в твоем проекте вместо `data-testid` используют другой атрибут (например, `data-qa`), ты можешь перенастроить Playwright:
       ```java
       // В конфиге или перед тестом
       context.setTestIdAttribute("data-qa"); 
       ```

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Почему нельзя везде использовать `getByTestId`? Если он самый надежный, зачем нам другие?**
**О:** Потомут что тесты должны проверять пользовательский опыт. Если ты будешь тестировать только по `test-id`, ты можешь пропустить ситуацию, когда кнопка на самом деле исчезла с экрана или её текст стал нечитаемым. Мы используем `getByRole` и `getByText`, чтобы убедиться, что *пользователь* видит то, что должен. `TestId` — это инструмент для сложных случаев, где "человеческого" описания недостаточно.

**В: Что делать, если я нашел элемент через XPath, но хочу перейти на `getByTestId`?**
**О:** Это лучший путь развития фреймворка. Подойди к разработчикам и попроси добавить `data-testid`. Это сделает твои тесты "пуленепробиваемыми" (resilient) и уменьшит количество ложноположительных срабатываний (flaky tests) при обновлении верстки.

**В: В чем разница между `getByAltText` и `getByRole(AriaRole.IMG, ...)`?**
**О:** По сути, они часто нацелены на одно и то же. Но `getByAltText` более специфичен для атрибута `alt`. Использование специализированных локаторов делает код теста более читаемым (self-documenting code).

# 🛠 Шпаргалка: Классические селекторы (CSS & XPath)

Когда современные локаторы (`getByRole`, `getByText`) не справляются (например, когда нужно привязаться к сложному атрибуту или специфическому пути), мы достаем «тяжелую артиллерию» — **CSS** и **XPath**.

> **Senior Tip:** Используй классические селекторы только как **последний рубеж**. Если ты часто используешь XPath, значит, твои тесты слишком хрупкие (brittle). Твоя цель — искать элементы по их *смыслу* (роли, тексту), а не по их *месту в дереве*.

---

## 1. CSS Selectors (Твой основной инструмент)
CSS — это быстро, читаемо и эффективно. Playwright отлично оптимизирован под них.

### Основные типы:
*   **По ID:** `#submit-button` (самый быстрый и стабильный).
*   **По классу:** `.btn-primary` (осторожно: классов может быть много, и они могут меняться).
*   **По атрибуту:** `[name="email"]`, `[type="submit"]`, `[data-testid="login-link"]`.
*   **Вложенность:**
    *   `div p` — все `<p>` внутри `<div>` (любой уровень вложенности).
    *   `div > p` — только прямые потомки (только один уровень вниз).
*   **Поиск по части строки (Wildcards):**
    *   `[class^="btn-"]` — класс *начинается* с "btn-".
    *   `[class*="active"]` — класс *содержит* "active".
    *   `[class$="-large"]` — класс *заканчивается* на "-large".

### Псевдоклассы:
*   `:nth-child(n)` — выбор n-го элемента (опасно, если порядок элементов изменится).
*   `:not(.hidden)` — выбрать все элементы, у которых НЕТ класса `hidden`.

---

## 2. XPath (Тяжелая артиллерия)
XPath позволяет перемещаться не только вниз по дереву, но и **вверх** к родителям, а также искать по тексту (хотя в Playwright есть `getByText`, в XPath это делается иначе).

### Типы путей:
*   **Абсолютный (`/html/body/div[1]/...`):** ❌ **ЗАПРЕЩЕН**. Это самоубийство для автотестов. Любое изменение в верстке сломает тест.
*   **Относительный (`//button`):** ✅ **Используй только его**. Он ищет элемент в любом месте документа.

### Мощные фишки (Axes):
XPath незаменим, когда нужно найти элемент, ориентируясь на «соседа» или «родителя»:
*   `//input[@id='user']//parent::div` — найти родителя для инпута.
*   `//td[text()='John']/following-sibling::td` — найти ячейку с именем "John" и взять следующую ячейку в этой же строке (идеально для таблиц).
*   `//label[contains(., 'Email')]/preceding-sibling::input` — найти инпут, который стоит *перед* лейблом с текстом "Email".

### Поиск по тексту:
*   `//button[contains(text(), 'Login')]` — поиск кнопки, содержащей текст "Login".

---

## ⚖️ Сравнение: CSS vs XPath

| Особенность | CSS Selectors | XPath |
| :--- | :--- | :--- |
| **Скорость** | Очень высокая | Чуть медленнее |
| **Направление поиска** | Только вниз (к потомкам) | Вверх, вниз, в стороны (к предкам/соседям) |
| **Читаемость** | Высокая (лаконично) | Низкая (сложно читать длинные пути) |
| **Поиск по тексту** | Ограничен (в Playwright расширен) | Мощный и гибкий |

---

## 💡 Золотые правила Senior-инженера

1.  **Приоритет №1: `data-testid`**. Если ты можешь попросить разработчиков добавить `data-testid="login-submit"`, сделай это. Это самый стабильный селектор из всех возможных.
2.  **Избегай индексов.** Забудь про `div[5]`. Если завтра в верстке появится новый блок, твой тест упадет.
3.  **Принцип "Минимальной достаточности".** Не пиши путь на 10 уровней вниз. Если ID достаточно уникален — используй только его.
4.  **Используй XPath для таблиц и сложных связей.** Когда нужно найти строку в таблице по значению в одной из ячеек, XPath — твой единственный верный друг.

## ❓ FAQ (Часто задаваемые вопросы)

**В: Почему мой CSS селектор не находит элемент, хотя он есть на странице?**
**О:** Скорее всего, элемент находится внутри `iframe` или внутри `Shadow DOM`. Playwright умеет работать с Shadow DOM автоматически, но для `iframe` тебе нужно сначала переключиться на него через `page.frameLocator()`.

**В: Можно ли использовать CSS для поиска по тексту?**
**О:** В чистом CSS — нет. Но в Playwright Java ты можешь использовать расширенный синтаксис, например `page.locator("text=Login")` или встроенные методы. Если же мы говорим строго о селекторах внутри строки `page.locator(".class:has-text('Login')")`, то это работает через внутренние механизмы Playwright.

**В: Что делать, если класс элемента динамический (например, `button_abc123`)?**
**О:** Не пытайся захватить весь класс. Используй поиск по частичному совпадению в CSS: `[class*="button_"]` или найди элемент по его стабильному родителю/тексту через XPath.

**В: Когда XPath всё-таки лучше, чем CSS?**
**О:** Когда тебе нужно «подняться» вверх по дереву (найти родителя) или когда логика поиска сильно завязана на текстовое содержание соседних элементов (как в сложных таблицах).

# ⛓️ Сложные цепочки (Chaining) в Playwright Java

### 💡 Суть простыми словами
Представь, что ты ищешь ключ в огромном торговом центре. Если ты скажешь: *"Найди мне ключ"*, тебя могут отправить в любой магазин. Но если ты скажешь: *"В магазине 'Техника' -> на полке 'Аксессуары' -> найди синий чехол"*, поиск станет точным.

**Chaining (цепочки)** — это способ сузить область поиска. Вместо того чтобы искать элемент по всей странице (`page`), мы сначала находим "контейнер" (родителя), а затем ищем внутри него "ребенка".

---

### 🛠️ Основной инструмент: `.locator()`
В Playwright Java цепочка строится через последовательный вызов метода `.locator()` у уже найденного локатора.

```java
// Плохо: Поиск по всей странице (риск найти не тот элемент, если их много)
page.locator(".delete-button").click(); 

// Хорошо: Цепочка (ищем кнопку удаления именно внутри конкретной строки таблицы)
Locator row = page.locator("tr").filter(new Locator.FilterOptions().setHasText("User123"));
row.locator(".delete-button").click();
```

---

### 🚀 Продвинутый уровень: Chaining + Filtering
Просто цепочки — это хорошо, но магия начинается, когда ты используешь `.filter()`. Это "золотой стандарт" для работы со списками, таблицами и карточками товаров.

**Сценарии использования:**
1.  **Поиск по тексту в контейнере:** Найти карточку товара с названием "iPhone", а затем нажать кнопку "Купить" *внутри этой же* карточки.
2.  **Изоляция области:** Когда на странице 10 одинаковых кнопок "Edit", но тебе нужна та, что относится к конкретному пользователю.

**Пример кода (Best Practice):**
```java
// 1. Находим контейнер (карточку товара) по тексту
Locator productCard = page.locator(".product-card")
    .filter(new Locator.FilterOptions().setHasText("Samsung Galaxy"));

// 2. Внутри ЭТОЙ карточки ищем кнопку "Add to Cart"
productCard.locator("button.add-to-cart").click();
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Auto-waiting не ломается:** Это самое важное. Playwright не просто находит родителя, он ждет, пока **вся цепочка целиком** станет доступной для действия (visible, stable, enabled). Если родитель появился, а кнопка внутри него еще подгружается — Playwright подождет.
2.  **Избегай "глубоких" цепочек:** Не делай `page.locator("div").locator("div").locator("span").locator("a")`. Это превращает тест в хрупкую конструкцию. Если разработчики обернут `span` в еще один `div`, твой тест упадет. 
    *   *Совет:* Старайся держать цепочку не длиннее 2-3 уровней. Используй селекторы, которые ближе к смыслу (Role, Text, TestId).
3.  **Производительность:** Слишком много фильтраций (`filter`) на огромных списках (тысячи элементов) могут замедлить выполнение. Но для обычных UI-тестов это практически незаметно.
4.  **Локаторы — это ленивые объекты:** Когда ты создаешь `row.locator(".btn")`, Playwright **не ищет** элемент в этот момент. Он запоминает "инструкцию". Поиск произойдет только в момент вызова действия (`click()`, `fill()` и т.д.).

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что будет, если родительский элемент исчезнет из DOM во время выполнения цепочки?**
**О:** Playwright применит механизм ретраев (retries). Он попытается заново найти всю цепочку с самого начала (с `page`), пока не найдет обновленный путь или не выйдет таймаут.

**В: Можно ли использовать XPath внутри цепочки?**
**О:** Да, можно. Но если ты уже используешь `.locator()`, старайся использовать CSS или встроенные методы (`getByRole`). XPath в цепочках часто делает код нечитаемым.

**В: В чем разница между `page.locator(".child")` и `parentLocator.locator(".child")`?**
**О:** Первый ищет элемент по всей странице (глобально). Второй — только внутри области `parentLocator`. Это критично для тестов, где на странице много одинаковых элементов.

**В: Как найти элемент, если я не знаю точного текста, но знаю, что он содержит часть строки?**
**О:** Используй `filter` с регулярным выражением или просто подстроку в `hasText`. 
`page.locator(".item").filter(new Locator.FilterOptions().setHasText(Pattern.compile("part_of_text")));`

# 🧠 Шпаргалка: Фильтрация локаторов (Locator Filtering)

### 🎯 Суть
В Playwright ты редко находишь нужный элемент «с первого раза» по уникальному ID. Чаще всего ты находишь набор похожих элементов (например, все строки в таблице или все кнопки в меню), и твоя задача — **отсеять лишнее**, оставив только тот элемент, который содержит определенный текст или другой под-элемент.

Фильтрация — это способ сузить область поиска, не переписывая базовый локатор.

---

### 🛠 Основные способы фильтрации

#### 1. Фильтрация по тексту (`hasText`)
Самый простой способ. Ты говоришь: «Найди мне этот элемент, но только если внутри него есть вот эта строка».

```java
// Найдем кнопку, которая содержит текст "Submit"
// Это сработает и для <button>Submit</button>, и для <button>Click to Submit</button>
Locator submitBtn = page.getByRole(AriaRole.BUTTON).filter(new Locator.FilterOptions().setHasText("Submit"));
```

#### 2. Фильтрация по наличию под-элемента (`has`)
Это «тяжелая артиллерия». Ты используешь другой локатор как условие. Это незаменимо в сложных структурах типа таблиц, списков или карточек товаров.

**Сценарий:** У нас есть список карточек товара (`.product-card`). Нам нужно найти карточку, внутри которой есть кнопка «Купить» с иконкой корзины.

```java
// Создаем локатор для кнопки внутри карточки
Locator buyIcon = page.locator(".cart-icon");

// Фильтруем все карточки так, чтобы в них была именно эта иконка
Locator productWithCart = page.locator(".product-card")
    .filter(new Locator.FilterOptions().setHas(buyIcon));
```

#### 3. Цепочка локаторов (Chaining)
Это не совсем «фильтрация» в строгом смысле, но это способ сузить поиск через иерархию. Ты идешь сверху вниз по дереву DOM.

```java
// Сначала находим строку таблицы, потом внутри неё — кнопку удаления
Locator deleteBtnInRow = page.locator("tr").filter(new Locator.FilterOptions().setHasText("John Doe")).locator(".delete-btn");
```

---

### ⚠️ Нюансы и Senior Tips (На что смотреть)

1.  **`hasText` vs `Exact Text`**: По умолчанию `hasText` делает поиск по подстроке (substring). Если ты напишешь `.setHasText("Order")`, он найдет и "Order", и "Order #123". Если нужна строгая точность, используй регулярные выражения или проверяй через ассерты.
2.  **Производительность**: Избегай слишком глубокой вложенности фильтров (`filter().filter().filter()`). Каждый уровень фильтрации заставляет Playwright заново обходить дерево элементов. Старайся максимально точно определить «базовый» локатор перед фильтрацией.
3.  **Порядок имеет значение**: Сначала применяй самый широкий (но стабильный) локатор, а затем сужай его. Не пытайся найти элемент через `page.locator("div > div > span")` и потом фильтровать его — это хрупкий код. Иди от `getByRole` $\to$ `filter`.
4.  **Видимость**: Помни, что `hasText` видит текст даже в скрытых элементах (если они есть в DOM). Если тебе нужен только видимый текст, всегда добавляй проверку на видимость или используй `getByText` с правильными настройками.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем разница между `.filter(new FilterOptions().setHasText("..."))` и `.getByText("...")`?**
**О:** `getByText` — это поиск *нового* элемента по тексту. `filter(hasText)` — это поиск *существующего* набора элементов и их фильтрация. Если ты применишь `getByText` к списку, ты получишь сам текстовый узел. Если применишь `filter` к списку — ты получишь родительский элемент (например, `div` или `li`), внутри которого этот текст лежит.

**В: Что произойдет, если после фильтрации локатор найдет 0 элементов?**
**О:** Playwright не упадет мгновенно. Он будет ждать (в рамках таймаута), пока в DOM не появится элемент, подходящий под все условия фильтрации. Если за время ожидания никто не подошел — получишь `TimeoutError`.

****В: Можно ли использовать Regex в фильтрации?**
**О:** Да! В Java ты можешь передать паттерн в `setHasText`, что позволяет делать гибкие проверки, например, игнорируя регистр или проверяя формат ID.

# 🛠 Шпаргалка: Базовые действия (Basic Actions)

В Playwright «базовые действия» — это не просто клики. Это интеллектуальные операции. Главная фишка, которую ты должен запомнить как Senior: **Actionability Checks**. Прежде чем выполнить любое действие, Playwright автоматически проверяет, что элемент виден, не перекрыт другими элементами, стабилен (не двигается) и доступен для взаимодействия. Тебе почти никогда не нужны `Thread.click()` или `sleep()`.

### 1. Взаимодействие с кнопками и ссылками (Clicking)
Самые частые операции.

*   `locator.click()` — Обычный клик левой кнопкой мыши.
*   `locator.dblclick()` — Двойной клик.
*   `locator.click(new Locator.ClickOptions().setClickCount(3))` — Если нужно имитировать тройной клик (например, для выделения текста).

> 💡 **Senior Tip:** Если элемент перекрыт прозрачным слоем (например, лоадером), `click()` будет ждать, пока лоадер исчезнет. Но если ты принудительно используешь `force: true`, Playwright кликнет «сквозь» препятствие, что может привести к невалидному тесту. Используй `force` только в крайнем случае.

### 2. Ввод текста (Inputting Data)
Здесь новички чаще всего ошибаются, выбирая между двумя методами.

*   **`locator.fill("текст")`** — **Твой основной инструмент.** Он очищает поле и мгновенно вставляет текст. Это быстро и эффективно. Работает через изменение значения свойства `value`.
*   **`locator.pressSequentially("текст")`** — Имитирует реальный ввод человека: нажимает каждую клавишу по очереди.

> 💡 **Senior Tip:** Используй `fill()` для 99% случаев (логин, формы, поиск). Используй `pressSequentially()`, только если ты тестируешь функционал, который срабатывает *в процессе* ввода (например, выпадающий список подсказок/autocomplete, который фильтруется после каждой буквы).

### 3. Работа с чекбоксами и радиокнопками (Check/Uncheck)
Не используй `click()` для чекбоксов, это плохой тон.

*   `locator.check()` — Устанавливает галочку. Если она уже стоит, ничего не произойдет (это атомарная операция).
*   `locator.uncheck()` — Снимает галочку.
*   `locator.isChecked()` — Возвращает `boolean` (проверка состояния).

### 4. Клавиатура и спецсимволы (Keyboard)
Когда нужно нажать `Enter`, `Escape` или комбинацию клавиш.

*   `locator.press("Enter")` — Нажать Enter на конкретном элементе.
*   `page.keyboard.press("Control+A")` — Глобальное нажатие (на уровне всей страницы).
*   `locator.press("Backspace")` — Удаление символа.

### 5. Мышь и наведение (Mouse & Hover)
Для сложных UI-компонентов (выпадающие меню, тултипы).

*   `locator.hover()` — Наведение курсора на элемент. Критически важно для тестирования выпадающих списков, которые появляются только при наведении.

---

### 🧠 FAQ (Часто задаваемые вопросы)

**В: В чем разница между `fill()` и `pressSequentially()`?**
**О:** `fill()` — это «магия» подмены значения (быстро, надежно). `pressSequentially()` — это симуляция нажатий клавиш (медленно, имитирует человека). Если тебе нужно проверить, как работает поиск с подсказками, выбирай второй вариант.

**В: Почему мой `click()` не срабатывает, хотя я вижу элемент на экране?**
**О:** Скорее всего, элемент перекрыт другим элементом (например, баннером или модальным окном) или он находится в процессе анимации. Playwright ждет завершения анимации. Проверь, нет ли поверх элемента невидимого `div`.

**В: Нужно ли мне использовать `locator.clear()` перед `fill()`?**
**О:** Нет. Метод `fill()` автоматически очищает поле перед вводом нового текста. Лишний код — лишние баги.

**В: Как нажать на кнопку, если она находится вне зоны видимости (нужно скроллить)?**
**О:** Playwright сделает это за тебя! Он автоматически проскроллит элемент в область видимости перед выполнением `click()`. Тебе не нужно писать команды скроллинга вручную.

# 📝 Шпаргалка: Работа с текстом и вводом в Playwright Java

В Playwright работа с текстовыми полями (`<input>`, `<textarea>`) делится на два подхода: «мгновенная подмена» и «имитация человека». Выбор между ними — это то, что отличает джуна от синьора.

### 1. Основные методы

#### `fill(selector, text)` — Твой основной инструмент
Это самый быстрый и надежный метод. Он не печатает символы один за другим, а сразу устанавливает значение поля.
*   **Что делает:** Очищает поле и вставляет текст.
*   **Когда использовать:** В 95% случаев. Если тебе нужно просто заполнить форму для теста.
*   **Нюанс:** Он не вызывает события `keydown`, `keypress` или `keyup` для каждого символа. Он просто меняет `value`.

#### `pressSequentially(selector, text)` — Имитация печати (замена устаревшему `type`)
Этот метод имитирует нажатие каждой клавиши пользователем.
*   **Что делает:** Вводит текст символ за символом.
*   **Когда использовать:** Когда на сайте есть **автокомплит (search suggestions)**, валидация «на лету» или маски ввода (например, для номера телефона), которые реагируют именно на нажатие клавиш.
*   **Фишка:** Можно передать параметр `delay` (в мс), чтобы сделать паузу между буквами, как будто человек реально печатает.

#### `press(selector, key)` — Управление спецклавишами
Используется для нажатия системных клавиш.
*   **Примеры:** `Enter`, `Tab`, `Backspace`, `ArrowDown`, `Escape`.
*   **Зачем:** Чтобы нажать "Enter" после ввода текста или проскроллить выпадающий список кнопкой `ArrowDown`.

#### `clear(selector)` — Очистка поля
Если тебе нужно именно стереть всё содержимое, не используя `fill("")`.

---

### 2. Senior Nuances (Важные нюансы)

1.  **Выбор метода (Speed vs Realism):** Всегда начинай с `fill()`. Если тест падает, потому что выпадающий список не появился — переходи на `pressSequentially()`. Не используй медленную имитацию там, где она не нужна, это раздувает время выполнения пайплайна.
2.  **Проверка результата (Assertions):** Никогда не проверяй текст через обычный `getText()`, если работаешь с инпутами. Для полей ввода используй **Web-First Assertions**:
    *   `assertThat(locator).hasValue("expected text");` — это правильно, так как Playwright будет ждать появления текста (retry), а не упадет мгновенно.
3.  **Скрытые поля:** Если поле скрыто (например, `display: none`), Playwright не сможет в него ничего ввести и выдаст ошибку. Сначала убедись, что элемент видим (хотя авто-вейтинг сделает это за тебя, если элемент просто перекрыт).
4.  **Очистка перед вводом:** Помни, что `fill()` очищает поле сам. Если ты используешь `pressSequentially()`, старый текст **не удаляется**, а дописывается в конец. Это частая причина багов в тестах.

---

### 3. Пример кода (Java)

```java
import com.microsoft.playwright.*;
import com.microsoft.playwright.assertions.PlaywrightAssertions;
import org.junit.jupiter.api.*;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

public class InputTest {
    // ... setup/teardкун (Browser, Page) ...

    @Test
    void testInputScenarios(Page page) {
        page.navigate("https://example.com/form");

        // 1. Быстрое заполнение (Best Practice)
        page.locator("#username").fill("admin_user");

        // 2. Имитация ввода для поиска с автокомплитом
        // Добавляем задержку 100мс, чтобы JS успел отработать поиск
        page.locator("#search-bar").pressSequentially("Playwright", new Page.PressSequentiallyOptions().setDelay(100));

        // 3. Работа со спецклавишами (Нажать Enter после ввода)
        page.locator("#login-button").press("Enter");

        // 4. Очистка и проверка (Web-First Assertion)
        page.locator("#email").fill("old@mail.com");
        page.locator("#email").clear();
        assertThat(page.locator("#email")).hasValue(""); // Проверяем, что пусто
    }
}
```

### ❓ FAQ (Частые вопросы на интервью)

**В: В чем принципиальная разница между `fill()` и `pressSequentially()`?**
**О:** `fill()` — это быстрая вставка значения (`value = 'text'`), которая не триггерит события клавиатуры. `pressSequentially()` — это эмуляция нажатия каждой клавиши, что вызывает цепочку событий `keydown`, `keypress`, `keyup`.

**В: Что делать, если после `fill()` выпадающий список (dropdown) не открылся?**
**О:** Скорее всего, логика фронтенда завязана на событие `input` или `keyup`. В этом случае замени `fill()` на `pressSequentially()`.

**В: Как проверить, что в поле ввода появился нужный текст?**
**О:** Используй `assertThat(locator).hasValue("текст")`. Не используй `getText()`, так как для элементов `<input>` текст хранится в атрибуте `value`, а не внутри тегов.

**В: Можно ли использовать `press()` для ввода длинного текста?**
**О:** Технически можно, но это крайне неэффективно и медленно. Для текста используй только `fill` или `pressSequentially`. `press()` предназначен для одиночных нажатий (Enter, Tab, Backspace).

# 🖱️ Шпаргалка: События мыши и клавиатуры в Playwright Java

В Playwright есть два уровня взаимодействия: **High-level** (через `Locator`) — когда мы работаем с элементами, и **Low-level** (через `Page.mouse` или `Page.keyboard`) — когда мы имитируем сырые движения «руки» пользователя по координатам или нажатия клавиш без привязки к конкретному селектору.

---

## 1. Мышь: Уровень Locator (Рекомендуемый)
Это твой основной инструмент. Playwright сам выполняет **Actionability Checks** (проверяет, виден ли элемент, не перекрыт ли он другим и не анимируется ли он) перед действием.

*   `.click()` — Обычный клик. Можно передать `ClickOptions` (например, `button: MouseButton.RIGHT`).
*   `.dblclick()` — Двойной клик.
*   `.hover()` — Наведение курсора (важно для выпадающих меню).
*   `.dragTo(targetLocator)` — Перетаскивание одного элемента на другой. Это «умный» метод, который сам вычислит координаты.

**💡 Нюанс:** Если элемент перекрыт прозрачным `div` (например, лоадером), `.click()` будет ждать, пока лоадер исчезнет. Если ты хочешь кликнуть «силой», игнорируя препятствия, это делается через низкоуровневую мышь (см. ниже).

---

## 2. Мышь: Уровень Page (Low-level)
Используется для сложных сценариев: рисование на Canvas, сложные Drag-and-Drop, где нужно имитировать движение по траектории.

*   `page.mouse().move(x, y)` — Переместить курсор в точку.
*   `page,mouse().down()` / `page.mouse().up()` — Зажать и отпустить левую кнопку мыши. Это база для создания своего Drag-and-Drop.
*   `page.mouse().click(x, y)` — Клик по координатам (не по элементу!).
*   `page.mouse().wheel(deltaX, deltaY)` — Прокрутка колесика (скроллинг внутри конкретной области).

**⚠️ Senior Tip:** Никогда не используй координаты (`x, y`), если можешь использовать `Locator`. Координаты ломаются при изменении разрешения экрана или масштаба браузера. Используй `page.mouse` только для Canvas или специфических графических тестов.

---

## 3. Клавиатура: Ввод текста
Здесь новички чаще всего совершают ошибки, путая три разных подхода.

1.  **`locator.fill("text")` — САМЫЙ БЫСТРЫЙ.**
    *   *Как работает:* Полностью очищает поле и вставляет текст за один раз (через API браузера).
    *   *Когда использовать:* В 99% случаев. Это быстро и надежно.
2.  **`locator.pressSequentially("text")` — «ЧЕЛОВЕЧНЫЙ».**
    *   *Как работает:* Имитирует нажатие каждой клавиши с небольшой задержкой (как будто человек печатает).
    *   *Когда использовать:* Если на сайте висит JS-валидация, которая срабатывает только на событие `onKeyPress` или `onKeyUp`.
3.  **`locator.press("Enter")` — ОДИНОЧНОЕ НАЖАТИЕ.**
    *   *Как работает:* Нажимает конкретную спецклавишу (Enter, Escape, Backspace).

---

## 4. Клавиатура: Комбинации клавиш (Modifiers)
Для имитации `Ctrl+C`, `Shift+A` или `Control+V`.

*   **Метод `press` с модификатором:**
    `page.keyboard().press("Control+A");` — Выделить всё.
*   **Низкоуровневый метод (Down/Up):**

    page.keyboard().up("Control"); // Отпустили

**О:** Да. Playwright автоматически проскроллит к элементу перед тем, как выполнить `.click()`. Тебе не нужно писать `scrollToElement`.

# 📝 Шпаргалка: Работа с формами в Playwright Java

Работа с формами — это 70% всей автоматизации UI. Главная цель здесь — имитировать действия реального пользователя, но делать это максимально эффективно и надежно.

### 1. Текстовые поля (`input[type='text']`, `textarea`, `password`)

В Playwright есть два основных способа ввода текста. Это критически важный нюанс.

*   **`locator.fill("текст")`** — **Твой основной инструмент.** Он очищает поле и мгновенно вставляет значение. Это быстро, это имитирует работу автозаполнения браузера.
    *   *Когда использовать:* В 99% случаев.
*   **`locator.pressSequentially("текст")`** (ранее назывался `type`) — Имитирует посимвольный ввод с задержкой.
    *   *Когда использовать:* Если на поле навешан обработчик `onKeyPress` или `onKeyUp` (например, поиск с выпадающим списком/автокомплитом), который реагирует только на нажатие клавиш.

**Нюанс:** Если тебе нужно очистить поле, просто используй `locator.fill("")`.

### 2. Чекбоксы и Радиокнопки (`checkbox`, `radio`)

Забудь про обычный `.click()`, если хочешь стабильный тест.

*   **`locator.check()`** — Устанавливает галочку. Если она уже стоит, Playwright ничего не будет делать (идемпотентность).
*   **`locator.uncheck()`** — Снимает галочку.
*   **`locator.setChecked(true/false)`** — Универсальный метод. Принимает boolean.

**Нюанс:** Использование `.click()` на чекбоксе может привести к тому, что ты "переключишь" состояние (если он был включен, станет выключен). `.check()` гарантирует, что результат будет именно "включено".

### 3. Выпадающие списки (`select`)

Для стандартных HTML-тегов `<select>` Playwright предоставляет мощный метод:

*   **`locator.selectOption(...)`** — Позволяет выбирать элементы по нескольким критериям:
    *   По значению (`value`): `selectOption("v1")`
    *   По тексту (то, что видит юзер): `selectOption("Option 1")`
    *   По индексу: `selectOption(new SelectOption().setIndex(2))`
    *   Несколько значений (для мульти-селекта): `selectOption(Arrays.asList("v1", "v2"))`

**Нюанс:** Если выпадающий список — это не `<select>`, а кастомный компонент на `<div>` или `<ul>` (часто в React/Angular), метод `selectOption` **не сработает**. Тебе придется имитировать клик по списку, а затем клик по нужному элементу внутри него.

### локаторы для форм (Best Practices)
При работе с формами старайся использовать **User-facing locators**. Это делает тесты устойчивыми к изменениям CSS-классов:
*   `page.getByLabel("Имя пользователя")` — идеально для `input`, привязанного к `<label>`.
*   `page.getByPlaceholder("Введите email")` — если нет label, но есть placeholder.
*   `page.getByRole(AriaRole.CHECKBOX, new Page.GetByRoleOptions().setName("Согласен с условиями"))`.

1.  **Actionability Checks:** Playwright автоматически ждет, пока поле станет видимым, перестанет двигаться и станет доступным для ввода (`enabled`). Тебе не нужно писать `Thread.sleep()` или явные ожидания перед `fill()`.
2.  **Проблема перекрытия (Overlay):** Если при клике на чекбокс вылетает какой-то попап или анимация, Playwright может упасть с ошибкой "Element is intercepting pointer events". Решение: убедись, что локатор указывает именно на интерактивный элемент, а не на декоративный слой сверху.

# 🧠 Шпаргалка: Специфические действия (Advanced Actions)

Когда стандартных `click()` и `fill()` недостаточно, в дело вступают низкоуровневые манипуляции. Эти действия нужны для имитации сложного поведения пользователя или обхода ограничений (например, когда сайт защищен от простых скриптов).

### 1. Продвинутая работа с клавиатурой
В Playwright есть критическая разница между «вставкой текста» и «печатью».

*   **`locator.fill("text")`**: Самый быстрый способ. Он очищает поле и мгновенно вставляет значение через внутренний API браузера. 
    *   *Нюанс:* Не вызывает события `keydown`, `keyup` или `keypress`. Если на сайте стоит поиск с автодополнением (autocomplete), `fill()` может не сработать, так как скрипт сайта «не заметит» ввода.
*   **`locator.pressSequentially("text")`**: Имитирует реальный набор текста символ за символом. 
    *   *Когда использовать:* Для полей поиска, где нужно дождаться срабатывания JS-событий.
*   **`locator.press("Enter")` / `locator.press("Control+A")`**: Использование специальных клавиш или комбинаций.
*   **Низкоуровневый API (`page.keyboard`)**: Позволяет зажать клавишу (например, `Shift`) и, не отпуская её, совершить другие действия.
    ```java
    page.keyboard().down("Control");
    page.keyboard().press("a"); // Выделить всё
    page.keyboard().up("Control");
    ```

### 2. Манипуляции с мышью (Mouse API)
Если стандартный `locator.click()` не попадает в цель или элемент перекрыт прозрачным слоем, используем `page.mouse`.

*   **`page.mouse.move(x, y)`**: Перемещение курсора в конкретные координаты.
*   **`page/mouse.down()` / `up()`**: Имитация нажатия и отпускания кнопки мыши (основа для сложных перетаскиваний).
*   **Drag and Drop (Перетаскивание)**:
    *   *Высокоуровневый:* `locatorSource.dragTo(locatorTarget)`. Работает в 90% случаев.
    *   *Низкоуровневый (если Drag & Drop глючит):* Последовательность `move` -> `down` -> `move` (к цели) -> `up`. Это помогает, если нужно имитировать движение по определенной траектории.

### 3. Скроллинг (Scrolling)
Playwright обладает «умным» скроллингом (Auto-scrolling), но иногда контроль нужен вручную.

*   **`locator.scrollIntoViewIfNeeded()`**: Магический метод. Проверяет, виден ли элемент, и если нет — прокручивает к нему. 
    *   *Senior Tip:* Всегда используй его перед действиями с элементами, которые могут быть «за пределами видимости» (off-screen), чтобы избежать ошибок `Element is not clickable`.
*   **`page.mouse.wheel(deltaX, deltaY)`**: Имитация прокрутки колесиком мыши. Полезно для тестирования бесконечных лент (infinite scroll).

### 4. Работа с файлами (Upload & Download)
*   **File Upload**: Вместо того чтобы искать кнопку «Обзор», мы используем `locator.setInputFiles("path/to/file")`. Это работает напрямую с input-элементом.
*   **File Download**: Скачивание в Playwright — это ожидание события.
    ```java
    Download download = page.waitForDownload(() -> {
        page.getByText("Скачать отчет").click();
    });
    String path = download.path(); // Путь, куда файл сохранился во временную папку
    ```

### 5. Check / Uncheck (Чекбоксы и Радиокнопки)
*   **`locator.check()`**: Делает элемент отмеченным. Если он уже отмечен — ничего не произойдет (идемпотентность).
*   **`locator.uncheck()`**: Снимает отметку.
*   **`locator.click()`**: В отличие от `check()`, обычный клик по чекбоксу может его снять, если он был нажат. 
    *   *Senior Tip:* Всегда используй `check/uncheck`, если тебе важен конечный результат (состояние), а не сам факт клика.

### 💡 Нюансы от Senior-а: "Actionability Checks"
Прежде чем выполнить любое действие (`click`, `fill` и т.д.), Playwright выполняет автоматическую проверку **Actionability**. Он ждет, пока элемент станет:
1.  **Attached** (прикреплен к DOM).
2.  **Visible** (виден пользователю).
3.  **Stable** (перестал двигаться/анимироваться).
4.  **Receiving Events** (не перекрыт другими элементами).

Если твой тест падает с ошибкой "Element is intercepting pointer events", значит, какой-то лоадер или попап всё еще висит над элементом. Не используй `Thread.sleep()`, используй `page.waitForSelector(".loader", new Page.WaitForSelectorOptions().setState(WaitForSelectorState.HIDDEN))`.

# 🧠 Cheat Sheet: Auto-waiting in Playwright (Java)

### 🚀 Суть в двух словах
**Auto-waiting** — это «киллер-фича» Playwright, которая избавляет нас от ада `Thread.sleep()` и бесконечных `WebDriverWait`. 

В Selenium ты должен был сам сказать: *"Подожди, пока кнопка станет кликабельной"*. В Playwright, когда ты вызываешь метод `.click()`, фреймворк **автоматически** проверяет элемент по спиму критериев перед тем, как совершить действие. Если условия не соблюдены — он ждет (по умолчанию до 30 секунд).

---

### ✅ Actionability Checks (Проверки на «готовность»)
Перед тем как выполнить действие (например, `click()`), Playwright прогоняет элемент через чек-лист **Actionability Checks**. Чтобы клик сработал, элемент должен быть:

1.  **Attached** — Присутствовать в DOM-дереве.
2.  **Visible** — Видим глазу (не имеет `display: none` или `visibility: hidden` и имеет ненулевой размер).
3.  **Stable** — Стабилен. Playwright проверяет, что элемент не «прыгает» (например, завершилась анимация перемещения).
4.  **Enabled** — Не находится в состоянии `disabled`.
5.  **Receives Events** — Элемент не перекрыт другими элементами (например, прозрачным лоадером или модальным окном).

> **Senior Note:** Если ты кликаешь по кнопке, которая только что появилась, но её еще перекрывает полупрозрачный `div` с анимацией затухания, Playwright будет ждать, пока этот `div` исчезнет.

---

### ⚠️ Когда Auto-waiting НЕ помогает (Нюансы)
Это самый важный момент. Авто-ожидание ждет **состояния элемента**, но оно не знает о твоих **бизнес-целях**.

**Пример ошибки:**
Ты нажал кнопку "Сохранить". Playwright проверил, что кнопка кликабельна $\to$ Кликнул $\to$ Тест пошел дальше. Но данные в базе еще не обновились, и следующий шаг (проверка текста) падает. 

**Что делать?**
В таких случаях нужно использовать **Web-First Assertions** или ручные ожидания:
*   `assertThat(locator).hasText("Success")` — это ассерт, который сам умеет ретраить (повторно проверять) условие в течение таймаута.
*   `page.waitForResponse(...)` — если нужно дождаться завершения сетевого запроса.

---

### 🛠️ Управление таймаутами
Если стандартные 30 секунд тебе не подходят:

```java
// Глобальный таймаут для всех действий на странице
page.setDefaultTimeout(5000); // 5 секунд

// Таймаут только для конкретного действия
page.locator("#submit-button").click(new Locator.ClickOptions().setTimeout(1000));
```

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Чем Auto-waiting в Playwright отличается от Implicit Wait в Selenium?**
**О:** `Implicit Wait` в Selenium — это тупое ожидание появления элемента в DOM. Он не проверяет, виден ли элемент или перекрыт ли он другим. Playwright же делает глубокую проверку **Actionability** (видимость, стабильность, кликабельность).

**В: Что произойдет, если я использую `page.click(".btn")`, а кнопка еще не появилась в DOM?**
**О:** Playwright не упадет мгновенно. Он будет опрашивать DOM (polling) до истечения таймаута (30с), пытаясь найти этот элемент и проверить его по списку Actionability Checks.

**В: Можно ли заставить Playwright кликнуть по элементу, даже если он перекрыт другим?**
**О:** Да, можно использовать `force: true`. Это проигнорирует проверки на "Receives Events" и совершит «жесткий» клик по координатам. Но помни: это плохая практика, так как ты тестируешь не то, что видит пользователь.

**В: Почему `assertThat(locator).isVisible()` — это лучше, чем `assertTrue(locator.isVisible())`?**
**О:** Потому что `isVisible()` возвращает `boolean` мгновенно (true или false прямо сейчас), и если элемент появится через 100мс, тест упадет. А `assertThat(...).isVisible()` — это **Web-First Assertion**, он будет ждать появления элемента в течение таймаута.

# 🧠 Шпаргалка: Web-First Assertions в Playwright Java

### 🌟 Суть темы
В классическом тестировании (например, Selenium + JUnit) ассерты работают по принципу **"Проверь прямо сейчас"**. Если элемент еще не загрузился — тест упал. Это главная причина «флакующих» (нестабильных) тестов.

**Web-First Assertions** в Playwright — это "умные" проверки. Они работают по принципу **"Жди, пока условие не станет истинным"**. Playwright будет многократно перепроверять условие в течение заданного времени (по умолчанию 5 секунд), прежде чем выбросить ошибку.

---

### 🛠 Основной синтаксис
Все Web-First ассерты начинаются с использования статического метода `assertThat`.

**Важный импорт:**
```java
import static comcom.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;
```

**Примеры основных проверок:**
*   `assertThat(locator).isVisible();` — Элемент должен быть виден на экране.
*   `assertThat(locator).isHidden();` — Элемент должен быть скрыт.
*   `assertThat(locator).hasText("Login");` — Текст элемента должен **точно** совпадать с указанным.
*   `assertThat(locator).containsText("Welcome");` — Текст элемента должен **содержать** подстроку.
*   `assertThat(locator).hasAttribute("type", "password");` — Проверка атрибута.
*   `assertThat(locator).isChecked();` — Проверка, что чекбокс/радиокнопка выбрана.
*   `assertThat(locator).isEnabled();` — Элемент должен быть активен (не `disabled`).
*   `assertThat(locator).hasValue("admin");` — Проверка значения в `input`.

---

### ⚠️ Критические нюансы (Senior Tips)

#### 1. Главная ловушка: `assertTrue` vs `assertThat`
Это ошибка №1. 
*   ❌ **Плохо:** `assertTrue(page.locator(".status").isVisible());`
    *   *Почему:* `isVisible()` возвращает `boolean` мгновенно. Если страница еще грузится, ты получишь `false` и тест упадет сразу. Ты используешь стандартный ассерт JUnit, который не умеет ждать.
*   ✅ **Хорошо:** `assertThat(page.locator(".status")).isVisible();`
    ert  *Почему:* Playwright будет "опрашивать" (polling) элемент, пока тот не станет видимым или не выйдет таймаут.

#### 2. Точное совпадение vs Частичное
*   `hasText("Hello")` — упадет, если в элементе написано `"Hello World"`.
*   `containsText("Hello")` — пройдет, если в элементе `"Hello World"`.
Всегда выбирай `containsText`, если не уверен на 100% в полном составе строки (например, там могут быть лишние пробелы).

#### 3. Кастомный таймаут
Если ты знаешь, что тяжелый отчет грузится долго (дольше 5 секунд), не увеличивай глобальный таймаут всего фреймворка. Сделай это точечно для конкретного ассерта:
```java
assertThat(page.locator(".heavy-report"))
    .isVisible(new Locator.IsVisibleOptions().setTimeout(15000)); // Ждем 15 секунд
```

#### 4. Отрицательные проверки (Negation)
Используй методы `.isNotVisible()`, `.hasNotText(...)` и т.д., вместо того чтобы пытаться инвертировать логику через `!`. Это делает отчеты о падении гораздо читаемее.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем фундаментальная разница между `ElementHandle` и `Locator` при использовании ассертов?**
**О:** `Locator` — это описание того, как найти элемент. Он "ленивый". Когда ты используешь `assertThat(locator)`, Playwright заново находит элемент перед каждой проверкой. Это защищает от ситуации `StaleElementReferenceException`, которая постоянно мучает пользователей Selenium.

**В: Что произойдет, если ассерт не прошел за 5 секунд?**
**О:** Тест упадет с ошибкой `TimeoutError`. В логах ты увидишь красивый отчет: что именно ожидалось (например, текст "Success") и что было найдено на самом деле.

**$\text{В: Можно ли использовать Web-First Assertions для проверки API ответов?}$**
**О:** Нет. Данные ассерты (`assertThat`) работают только с `Locator` (DOM-элементами). Для проверки API (JSON, статус-коды) нужно использовать стандартные JUnit/TestNG ассерты (`assertEquals`), так как там нет механизма автоматического ожидания в DOM.

**В: Как проверить, что элемент исчез из DOM?**
**О:** Используй `assertThat(locator).isHidden();` или `assertThat(locator).not().toBeAttached();` (если нужно убедиться, что его вообще нет в дереве элементов).

# 🧠 Шпаргалка: Ручные ожидания (Manual Waiting) в Playwright Java

### 💡 Введение
В Playwright есть **Auto-waiting** (авто-ожидание). Прежде чем кликнуть по элементу, Playwright проверяет его видимость, стабильность и доступность. **Но авто-ожидание не всесильно.** Оно ждет *состояния элемента*, но оно не знает, когда завершится сложный фоновый процесс или когда данные в API обновятся. В таких случаях мы включаем «ручное» управление.

---

### 1. Ожидание селектора (`waitForSelector`)
Используется, когда тебе нужно дождаться появления элемента в DOM или его исчезновения, и стандартного `locator.click()` недостаточно (например, если элемент появляется в DOM, но еще не имеет нужного текста).

*   **Состояния (State):**
    *   `visible`: Элемент есть в DOM и виден пользователю.
    / *Самый частый сценарий.*
    *   `hidden`: Элемент исчез из DOM или стал `display: none`.
    *   `attached`: Элемент просто есть в коде страницы (даже если он прозрачный).

**Пример:**
```java
// Ждем, пока кнопка станет видимой
page.waitForSelector(".success-message", new Page.WaitForSelectorOptions().setState(WaitForSelectorState.VISIBLE));

// Ждем, пока лоадер исчезнет
page.waitForSelector("#spinner", new Page.WaitForSelectorOptions().setState(WaitForSelectorState.HIDDEN));
```

---

### 2. Ожидание состояния страницы (`waitForLoadState`)
Помогает дождаться завершения глобальных процессов загрузки страницы.

*   **`load`**: Полная загрузка (HTML + все ресурсы: картинки, стили).
*   **`domcontentloaded`**: HTML загружен и распарсен, но картинки могут еще грузится.
*   **`networkidle`**: **(Осторожно!)** Ожидание, пока не будет минимум 500 мс без активных сетевых запросов.

**⚠️ Senior Tip:** Не злоупотребляй `networkidle`. Если на странице есть бесконечный опрос (polling) сервера или аналитика, тест может упасть по таймауту, потому что сеть «никогда не затихает».

**Пример:**
```java
page.navigate("https://example.com");
page.waitForLoadState(LoadState.NETWORKIDLE); // Ждем, пока сетевая активность утихнет
```

---

### 3. Ожидание сетевых событий (`waitForResponse` / `waitForRequest`)
Это **самый надежный** способ ожидания в современном вебе. Вместо того чтобы гадать «появится ли кнопка», мы ждем конкретный ответ от бэкенда. Если API ответил `200 OK`, значит, данные точно на месте.

**⚠️ Senior Tip (Critical):** Всегда объявляй ожидание **ДО** действия, которое триггерит запрос. Иначе ты можешь пропустить событие (Race Condition).

**Пример:**
```java
// 1. Подготавливаем "ловушку" для ответа
Response response = page.waitForResponse(responseInfo -> 
    responseInfo.url().contains("/api/v1/user/profile") && responseInfo.status() == 200, 
    () -> {
        // 2. Выполняем действие, которое вызывает этот запрос
        page.getByText("Обновить профиль").click();
    }
);

// Теперь мы на 100% уверены, что данные пришли
String body = response.text();
```

---

### 4. Ожидание по условию (`waitForFunction`)
Когда нужно подождать выполнения произвольной логики на стороне браузера (через JavaScript). Это «тяжелая артиллерия».

**Пример:** Ждем, пока счетчик в JS-переменной станет равен 10.
```java
page.waitForFunction("window.myCounter === 10");
```

---

### 🚫 Антипаттерн: `Thread.sleep()`
**Никогда не используй `Thread.sleep()`!**
*   Если поставишь 5 секунд, а элемент появился за 1 — ты зря потерял 4 секунды (тесты станут медленными).
*   Если поставишь 5 секунд, а элемент грузится 6 — тест упадет (тесты станут нестабильными/flaky).

**Исключение:** Только если ты тестируешь баг, связанный с таймингами, или в отладочных целях «на коленке».

---

### ❓ FAQ (Частые вопросы)

**В: Чем `waitForSelector` отличается от `locator.click()`?**
**О:** `locator.click()` уже включает в себя проверку видимости. Используй `waitForSelector` только если тебе нужно дождаться чего-то, что не является целью клика (например, исчезновения баннера или появления скрытого текста).

**В: Что делать, если я использую `networkidle`, а тест падает по таймауту?**
**О:** Значит, на странице есть фоновые запросы (метрики, чаты, ретраи API). Переходи на стратегию `waitForResponse` для конкретного важного запроса. Это сделает тест быстрее и стабильнее.

**В: Как дождаться, пока текст в элементе изменится?**
**О:** Лучше всего использовать **Web-First Assertions**: 
`assertThat(page.locator(".status")).hasText("Completed");`. 
Playwright сам будет перепроверять это условие (retry) в течение таймаута, пока оно не станет истинным. Это и есть «умное» ожидание.

**В: Можно ли ждать появления элемента через `waitForRequest`?**
**О:** Напрямую — нет. Но ты ждешь *запрос*, который создает этот элемент. Если запрос прошел успешно, значит, логика фронтенда отработала, и элемент появится.

# 🛠 Cheat Sheet: Custom Polling in Playwright Java

### Что это такое?
**Custom Polling** — это механизм повторения проверки какого-либо условия через определенные интервалы времени, пока условие не станет истинным или не выйдет время ожидания (timeout).

**Зачем это нужно?** 
Playwright обладает мощным **Auto-waiting** (он ждет появления элемента, его кликабельность и т. декодирование), но он "не знает" о бизнес-логике, которая происходит *вне* DOM или внутри JS-переменных. Например:
*   Нужно дождаться изменения значения глобальной JS-переменной `window.status`.
*   Нужно дождаться, пока в базе данных (или через API) изменится статус заказа.
*   Нужно дождаться появления файла в папке после загрузки.

---

### 1. Способ №1: `page.waitForFunction()` — Внутри браузера
Это "родной" способ Playwright. Код выполняется **в контексте браузера** (на JavaScript). Это максимально быстро и эффективно, так как нет накладных расходов на общение между Java и браузером на каждой итерации.

**Как использовать:**
Ты передаешь строку с JS-кодом или лямбду.

```java
// Пример 1: Ожидание изменения значения JS-переменной
// Мы ждем, пока window.isProcessing станет false
page.waitForFunction("window.isProcessing === false", 
    new Page.WaitForFunctionOptions().setTimeout(10000));

// Пример 2: Передача аргумента из Java в браузерный JS
String expectedText = "Completed";
page.waitForFunction(
    "arg => document.querySelector('#status').innerText === arg", 
    new Page.WaitForFunctionOptions().setArg("expectedText", expectedText)
);
```

**Нюанс от Senior:** 
Помни, что `waitForFunction` работает внутри браузера. Ты не можешь напрямую обратиться к Java-переменной внутри строки с JS-кодом. Тебе нужно использовать `.setArg()`, чтобы "прокинуть" данные из Java в мир JavaScript.

---

### 2. Способ №2: Библиотека Awaitility — Вне браузера (Java side)
Если тебе нужно ждать что-то, чего Playwright не видит (API, БД, файловая система, состояние Java-объекта), используй библиотеку **Awaitility**. Это стандарт индустрии для Java.

**Зависимость (Maven):**
```xml
<dependency>
    <groupId>org/awaitility</groupId>
    <artifactId>awaitility</artifactId>
    <version>4.2.0</version>
    <scope>test</scope>
</dependency>
```

**Как использовать:**
```java
import static org.awaitility.Awaitility.*;
import static java.util.concurrent.TimeUnit.*;

// Пример: Ожидание появления записи в БД или изменения статуса через API
await()
    .atMost(15, SECONDS)          // Максимальное время ожидания (Timeout)
    .pollInterval(2, SECONDS)    // Как часто делать проверку (Polling interval)
    .until(() -> checkOrderStatusViaApi("ORDER_123") == "DELIVERED"); 
```

**Нюанс от Senior:** 
Никогда не используй `Thread.sleep()`. Это "яд" для автотестов. `Thread.sleep()` заставляет поток спать фиксированное время, даже если условие выполнилось через 100 мс. `Awaitility` же завершит ожидание сразу, как только условие станет истинным, экономя драгоценное время в CI/CD.

---

### ⚠️ Главные ошибки и Best Practices

1.  **Забытый Timeout:** Всегда устанавливай жесткий `timeout`. Без него, если условие никогда не выполнится, твой тест (или весь пайплайн) зависнет "на вечно".
2.  **Слишком частый Polling:** Не ставь интервал в 10 мс. Это создаст огромную нагрузку на CPU и может замедлить работу браузера/теста. Оптимально — от 500 мс до 2 секунд.
3.  **Heavy Logic inside Poll:** Внутри функции, которая проверяется (в `until` или `waitForFunction`), не должно быть тяжелых вычислений. Только проверка условия (`boolean`). Если ты начнешь там парсить огромный JSON, тест будет тормозить.
4.  **Смешивание контекстов:** Не пытайся использовать `page.waitForFunction` для проверки состояния базы данных. Для этого есть только Awaitility.

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `page.waitForSelector()` и `page.waitForFunction()`?**
**О:** `waitForSelector` — это узкоспециализированный инструмент для работы с DOM (поиск по CSS/XPath). `waitForFunction` — это универсальный инструмент, позволяющий проверять любую логику (текст, атрибуты, JS-переменные, сложные вычисления), исполняемую в браузере.

**В: Что делать, если мне нужно дождаться, пока элемент исчезнет?**
**О:** В Playwright для этого есть встроенный `locator.waitFor(new Locator.WaitForOptions().setState(WaitForSelectorState.HIDDEN))`. Но если логика исчезновения сложная (например, атрибут меняется на другой), используй `waitForFunction`.

**В: Можно ли использовать Awaitility вместе с Playwright Assertions?**
**О:** Да! Это мощная комбинация. Ты используешь `Awaitility` для ожидания внешнего события (например, пришел вебхук), а затем внутри `until` вызываешь стандартный `assertThat(locator).hasText(...)`.

**В: Как понять, какой интервал (poll interval) выбрать?**
**О:** Начни с 1 секунды. Если тест падает по таймауту, но ты видишь, что условие "почти" выполняется — увеличь `atMost` (timeout), а не уменьшай `pollInterval`. Интервал должен быть достаточно большим, чтобы не создавать лишнюю нагрузку, но достаточно малым, чтобы не терять время.

# 🌐 Тема: Перехват запросов и ответов (Network Interception)

### 💡 Суть простыми словами
Представь, что ты — «человек посередине» (Man-in-the-middle) между браузером и сервером. Когда браузер отправляет запрос (например, за списком товаров), ты можешь его перехватить и:
1. **Подменить ответ** (вместо реального списка прислать свой «фейковый» JSON).
2. **Испортить ответ** (сделать вид, что сервер упал с ошибкой 500).
3. **Заблокировать запрос** (запретить загрузку тяжелых картинок или рекламы).
4. **Изменить запрос** (подменить ID пользователя в теле запроса).

Это делает тесты **независимыми от бэкенда** и позволяет тестировать сценарии, которые сложно воспроизвести на реальном сервере.

---

### 🛠 Основной инструмент: `page.route()`

В Playwright Java всё крутится вокруг метода `page.route(urlPattern, handler)`.

#### 1. Mocking (Подмена данных / Stubbing)
Самый частый кейс. Мы говорим: «Если видишь запрос к `/api/user`, не иди на сервер, а просто верни вот этот JSON».

```java
// Перехватываем все запросы, содержащие "/api/user"
page.route("**/api/user", route -> {
    // Создаем фейковый ответ
    route.fulfill(new Route.FulfillOptions()
        .setStatus(200)
        .setContentType("application/json")
        .setBody("{\"id\": 1, \"name\": \"Senior Dev\", \"role\": \"Admin\"}")
    );
});

page.navigate("https://myapp.com/profile");
// Теперь на странице всегда будет отображаться "Senior Dev", даже если бэкенд недоступен
```

#### 2. Aborting (Блокировка запросов)
Нужно ускорить тесты или проверить, как ведет себя UI при обрыве связи? Блокируем!

```java
// Блокируем загрузку всех картинок (ускоряет выполнение теста)
page.route("**/*.{png,jpg,jpeg}", route -> route.abort("abort"));

// Блокируем аналитику (Google Analytics и т.д.), чтобы не засорять логи
page.route("**/google-analytics.com/**", route -> route.abort());
```

#### 3. Modifying & Continuing (Изменение и продолжение)
Если ты хочешь пропустить запрос дальше, но что-то в нем подправить (например, добавить заголовок).

```java
page.route("**/api/data", route -> {
    // Мы можем изучить запрос перед тем, как пустить его дальше
    System.out.println("Request URL: " + route.request().url());
    
    // Продолжаем выполнение запроса (как будто ничего не было)
    route.continueWasCalled(); 
});
```

---

### ⚠️ Нюансы и «подводные камни» (Senior Tips)

1.  **Порядок имеет значение:** Если у тебя несколько `page.route`, они применяются в порядке регистрации. Но если паттерны пересекаются, сработает тот, что был определен **последним**.
2.  **Regex vs String:** Используй Glob-паттерны (`**/api/**`) или Regular Expressions для гибкости. Обычная строка `"/api/user"` сработает только на точное совпадение.
3.  **Scope (Область видимости):** 
    *   `page.route` — перехватывает запросы только в этой вкладке.
    *   `browserContext.route` — перехватывает запросы во **всех** вкладках этого контекста (идеально для мульти-вкладных тестов).
4.  **Не забывай про `route.continue()`:** Если ты перехватил запрос через `page.route`, но не вызвал ни `fulfill()`, ни `abort()`, то этот запрос **зависнет навсегда**, и тест упадет по таймауту.
5.  **Сложные зависимости:** Если ты подменяешь API, убедись, что подмененный JSON соответствует структуре, которую ожидает фронтенд (TypeScript интерфейсы или Swagger). Иначе ты тестируешь "свой выдуманный мир", а не реальное приложение.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Как проверить, что фронтенд отправил правильный JSON на сервер?**
**О:** Используй `page.waitForRequest()`.
```java
// Ждем, когда будет отправлен POST запрос с определенным телом
Request request = page.waitForRequest(request -> 
    request.url().contains("/api/login") && request.method().equals("POST")
);
// Далее проверяем payload
String postData = request.postData();
assertTrue(postData.contains("\"username\":\"admin\""));
```

**В: Можно ли подменить статус ответа на 500, чтобы проверить "Error Page"?**
**О:** Да, это классика. Используй `route.fulfill(new Route.FulfillOptions().setStatus(500))`. Это лучший способ протестировать обработку ошибок без реальной поломки сервера.

**В: Как заблокировать только определенные типы запросов (например, только шрифты)?**
**О:** Используй паттерн с расширением файла: `page.route("**/*.woff2", route -> route.abort())`.

**В: Что делать, если я хочу подменить данные, но оставить оригинальный ответ от сервера?**
**О:** В Playwright Java нет прямого метода "изменить тело ответа сервера" (intercept and modify response body) одной командой без повторного запроса. Тебе придется либо использовать `fulfill` с заранее подготовленными данными, либо вручную делать запрос через `APIRequestContext`, забирать данные и отдавать их в `fulfill`.

# 🛠 Шпаргалка: Mocking & Stubbing в Playwright Java

### 💡 Что это такое?
**Mocking (Мокинг)** и **Stubbing (Стаббинг)** — это техника перехвата сетевых запросов браузера. Вместо того чтобы позволять браузеру реально идти на сервер за данными, мы «вклиниваемся» в процесс и подсовываем ему заранее подготовленный ответ.

**Зачем это Senior-инженеру?**
1.  **Изоляция:** Тестируем фронтенд независимо от бэкенда (если бэк упал или еще не готов).
2.  **Скорость:** Тесты не ждут реального ответа от медленного API.
3.  **Edge Cases (Граничные условия):** Легко имитировать ошибки `500 Internal Server Error`, `403 Forbidden` или пустые списки, которые сложно воспроизвести на реальном сервере.
4.  **Стабильность:** Тест не упадет из-за того, что в базе данных изменились данные.

---

### 🚀 Основной инструмент: `page.route()`

В Playwright всё крутится вокруг метода `route(urlPattern, handler)`.

#### 1. Простая подмена (Stubbing)
Мы говорим: «На любой запрос, подходящий под этот URL, верни вот такой JSON».

```java
// Перехватываем запрос к API пользователя и возвращаем статический ответ
page.route("**/api/user/profile", route -> {
    route.fulfill(new Route.FailsOptions() // Ошибка в названии, правильно: FulfillOptions
        .setStatus(200)
        .setContentType("application/json")
        .setBody("{\"id\": 1, \"name\": \"Mocked Admin\"}")
    );
});
```
*Нюанс: Используй `**` (glob pattern), чтобы не зависеть от домена.*

#### 2. Имитация ошибки сервера (Error Simulation)
Проверяем, как фронтенд реагирует на «падение» бэкенда.

```java
// Имитируем критическую ошибку сервера
page.route("**/api/payment", route -> {
    route.fulfill(new Route.FulfillOptions().setStatus(500));
});
```

#### 3. Динамическая модификация (Interception & Modification)
Это «высший пилотаж». Мы не просто подменяем ответ, а **пропускаем запрос к реальному серверу**, получаем настоящий ответ, меняем его «на лету» и отдаем браузеру.

```java
page.route("**/api/products", route -> {
    // 1. Делаем реальный запрос к серверу
    route.fetch().thenAccept(response -> {
        // 2. Читаем оригинальный JSON
        String body = response.text();
        // 3. Модифицируем его (например, добавляем фиктивный товар)
        String modifiedBody = body.replace("]", ", {\"id\": 99, \"name\": \"Fake Product\"}]");
        
        // 4. Отдаем измененный ответ браузеру
        route.fulfill(new Route.FulfillOptions()
            .setStatus(200)
            .setContentType("application/json")
            .setBody(modifiedBody));
    });
});
```

---

### ⚠️ Важные нюансы (Senior Tips)

1.  **Порядок имеет значение:** Если у тебя несколько правил `route`, Playwright применяет их по принципу «кто первый подошел под паттерн». Но лучше всего писать более специфичные URL перед общими.
2.  **Scope (Область видимости):** 
    *   `page.route()` — работает только для одной вкладки.
    *   `browserContext.route()` — работает для всех вкладок в этом контексте (идеально для тестирования мульти-вкладки).
    *   `page.route()` — если ты хочешь подменить данные во всем браузере, используй уровень `context`.
3.  **Не забывай про `route.continue()`:** Если ты перехватил запрос, но не вызвал ни `fulfill()`, ни `continue()`, запрос «зависнет» и браузер будет ждать вечно. Используй `route.continue()` если хочешь просто логировать запрос, не меняя его.
4.  **Очистка:** Если ты настраиваешь мок внутри теста, он будет действовать до конца жизни этой страницы/контекста. В сложных тестах будь осторожен, чтобы моки из одного теста не «отравили» другой.

**В: Можно ли с помощью `route` имитировать медленный интернет?**
**О:** Напрямую — нет (в Playwright нет параметра `delay` в `fulfill`). Но ты можешь использовать `route.fetch()` и добавить искусственную задерку через `Thread.sleep()` перед вызовом `fulfill`.

**В: Как подменить картинку или CSS?**

**В: Что лучше: Mocking или реальные данные?**
**О:** Золотое правило: Используй **реальные данные** для Smoke-тестов (проверка, что всё живое) и **Mocking** для Unit/Integration тестов фронтенда (проверка логики интерфейса при разных состояниях API).

**В: Как перехватить все запросы сразу?**
**О:** Используй паттерн `**/*`. Но будь осторожен: если ты заблокируешь или подменишь все запросы, браузер не загрузит даже сам HTML-код страницы.

# 🛠 Mocking/Stubbing: Изменение статус-кодов (Status Codes)

### 💡 Суть простыми словами
Представь, что ты тестируешь фронтенд, но бэкенд еще не готов или ведет себя «слишком хорошо». **Mocking (Мокинг)** — это когда мы перехватываем запрос от браузера к серверу и подменяем реальный ответ на наш собственный. 

**Stubbing (Стаббинг)** — это конкретный вид мокинга, когда мы жестко прописываем: «На этот URL всегда отвечай кодом 500». Это позволяет нам проверить, как интерфейс упадет в ошибку, не дожидаясь, пока разработчики реально сломают сервер.

### 🚀 Как это работает в Playwright Java
В Playwright за это отвечает метод `page.route(urlPattern, handler)`. Мы перехватываем запрос и вместо того, чтобы позволить ему уйти на сервер (`route.continue()`), мы принудительно возвращаем свой ответ (`route.fulfill()`).

#### Основной синтаксис:
```java
page.route("**/api/user", route -> {
    route.fulfill(new Route.FulfillOptions()
        .setStatus(500) // Вот здесь магия изменения кода
        .setBody("{\"error\": \"Internal Server Error\"}") // И подмена тела
    );
});
```

---

### 🛠 Основные сценарии использования

#### 1. Тестирование ошибки сервера (500 Internal Server Error)
Нужно проверить, появится ли на странице «красный баннер» или бесконечный лоадер, если бэкенд «упал».
```java
// Перехватываем любой запрос к API заказов и имитируем падение сервера
page.route("**/api/orders/**", route -> {
    route.fulfill(new Route.FulfillOptions().setStatus(500));
});

page.navigate("https://myapp.com/orders");
// Assert: Проверяем наличие текста "Ошибка сервера, попробуйте позже"
assertThat(page.locator(".error-message")).isVisible();
```

#### 2. Тестирование отсутствия данных (404 Not Found)
Проверяем, как ведет себя страница, если запрашиваемый ресурс не найден.
```java
page.route("**/api/profile/123", route -> {
    route/fulfill(new Route.FulfillOptions().setStatus(404));
});
```

#### 3. Тестирование прав доступа (401 Unauthorized / 403 Forbidden)
Проверяем, что пользователя выкидывает на страницу логина или показывает плашку «Доступ запрещен».
```java
page.route("**/api/admin/**", route -> {
    route.fulfill(new Route.FulfillOptions().setStatus(403));
});
```

---

### ⚠️ Нюансы (Senior level tips)

1.  **Scope (Область видимости):** 
    *   Если ты вызываешь `page.route(...)`, подмена будет работать **только для этой вкладки**.
    *   Если тебе нужно, чтобы ошибка работала во всех вкладках (например, при открытии нового окна), используй `browserContext.route(...)`.

2.  **Pattern Matching (Шаблоны URL):** 
    *   Используй Glob-паттерны (`**/api/**`) или Regex. Будь осторожен: слишком широкий паттерн (типа `**/*`) может случайно заблокировать загрузку самого JS/CSS, и страница просто не отрисуется.

3.  **Order of Operations (Порядок):** 
    *   Playwright проверяет роуты в порядке их регистрации. Если у тебя есть два `route` на один URL, сработает тот, что был объявлен последним (или наиболее специфичным, зависит от реализации паттерна).

4.  **Continue vs Fulfill:** 
    *   Если ты хочешь не просто изменить статус, а еще и поменять тело ответа, но оставить запрос «живым» (пропустить его на сервер), тебе нужно использовать `route.continue()`. Но для изменения статус-кода на ошибку (4xx/5xx) обычно используют именно `fulfill`, так как нам не важно, что ответит реальный сервер — мы уже всё решили за него.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Можно ли изменить только статус-код, не меняя тело ответа?**
**О:** Технически, ты используешь `fulfill`. Если ты не укажешь `.setBody()`, то телом ответа будет пустая строка. Но в хорошем тесте важно передать валидный JSON (даже с ошибкой), чтобы фронтенд не упал с ошибкой парсинга (`JSON.parse error`), а именно обработал бизнес-ошибку.

**О:** Запрос «зависнет» в состоянии ожидания (pending). Тест, скорее всего, отвалится по таймауту, потому что браузер будет бесконечно ждать ответа от этого перехваченного запроса.

**В: Как протестировать сценарий, когда API отвечает 200 OK, но внутри JSON лежит ошибка?**
**О:** Это тоже часть мокинга! Ты используешь `setStatus(200)`, но в `.setBody()` передаешь JSON с полем `{ "success": false, "message": "Error" }`. Это отличный способ проверить логику обработки бизнес-ошибок.

**В: Можно ли мокать запросы к сторонним ресурсам (например, Google Analytics)?**
**О:** Да! Это отличный способ ускорить тесты и убрать лишний сетевой шум. Просто перехвати паттерн `**/google-analytics.com/**` и верни пустой ответ.

# 🛠 Шпаргалка: Mocking/Stubbing (Подмена JSON-ответа)

### 💡 Суть процесса
**Mocking (Мокинг)** — это когда мы перехватываем сетевой запрос, который идет к реальному бэкенду, и вместо того, чтобы ждать ответа от сервера, отдаем «заготовленный» нами ответ.

**Зачем это нужно Senior-у?**
1.  **Изоляция:** Тест фронтенда не упадет, если бэкек «прилег».
2.  **Скорость:** Тест не ждет реальной обработки данных на сервере.
3.  **Тестирование негативных сценариев:** Легко имитировать `500 Internal Server Error` или `403 Forbidden`.
4.  **Граничные значения:** Можно подсунуть огромный массив данных или пустой список, чтобы проверить, как UI «развалится» (или нет).

---

### 🚀 Основной механизм: `page.route()`

В Playwright за это отвечает метод `page.route(urlPattern, handler)`. Мы перехватываем запрос по паттерну URL и используем `route.fulfill()`, чтобы отправить свой ответ.

#### Базовый пример (Подмена JSON)
Допустим, мы хотим, чтобы при запросе к `/api/user` всегда возвращался пользователь "John Doe".

```java
// Перехватываем любой URL, содержащий /api/user
page.route("**/api/user", route -> {
    // Создаем заготовленный JSON
    String jsonResponse = "{\"id\": 1, \"name\": \"John Doe\", \"role\": \"admin\"}";

    // Отдаем подмененный ответ
    route.fulfill(new Route.FulfillOptions()
        .setStatus(200) // Статус OK
        .setContentType("application/json") // Обязательно указываем тип контента
        .setBody(jsonResponse) // Тело ответа
    );
});

// Теперь, когда страница сделает запрос к /api/user, она получит наш JSON
page.navigate("https://myapp.com/profile");
```

---

### 🧠 Нюансы и "Senior" советы

#### 1. Использование Regex и Glob-паттернов
Не пиши полный URL, если не уверен в нем на 100%. Используй маски:
*   `**/api/v1/**` — перехватит всё, что начинается с `/api/v1/`.
*   `RegExp` — для сложных условий (например, если нужно искать ID в URL).

#### 2. Избегай "String Hell" (Используй Jackson/Gson)
Писать JSON руками в виде строк в Java — это путь к ошибкам с кавычками и запятыми. Используй библиотеку (Jackson или Gson), чтобы превращать POJO-классы в JSON.

```java
// Плохо: String json = "{\"name\":\"" + name + "\"}"; 
// Хорошо:
User user = new User(1, "John");
String json = objectMapper.writeValueAsString(user); // Используем Jackson
route.fulfill(new Route.FURLOptions().setBody(json));
```

#### 3. Тестирование ошибок (Error Injection)
Это самое ценное. Ты можешь проверить, что UI показывает красивое уведомление при ошибке сервера:

```java
page.route("**/api/save-data", route -> {
    route.fulfill(new Route.FulfillOptions()
        .setStatus(500) // Имитируем падение сервера
        .setBody("{\"error\": \"Internal Server Error\"}")
    );
});
```

#### 4. Не забывай про `route.continue()`
Если ты используешь `page.route`, но внутри обработчика **не** вызываешь ни `fulfill()`, ни `abort()`, ни `continue()`, запрос «зависнет». Если тебе нужно только модифицировать запрос (например, добавить заголовок), но оставить его живым — используй `route.continue()`.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что произойдет с реальным запросом, если я вызвал `route.fulfill()`?**
**О:** Реальный запрос к серверу **не уйдет**. Playwright прерывает цепочку и сразу отдает твой ответ. Это и есть суть мокинга.

**В: Как подменить только часть данных в реальном ответе?**
**О:** Это называется *Intercept & Modify*. Тебе нужно сначала дождаться реального ответа через `route.fetch()`, изменить его тело и только потом сделать `fulfill()`.
*Пример:* `Response response = route.fetch();` -> парсим JSON -> меняем поле -> `route.fulfill(response)`.

**В: Почему мой мок не работает, хотя URL совпадает?**
**О:** Проверь два момента:
1.  **Content-Type:** Если ты не указал `application/json`, фронтенд может не распознать данные и упасть с ошибкой парсинга.
2.  **Порядок регистрации:** `page.route` должен быть вызван **ДО** того, как страница совершит запрос (т.е. до `page.navigate()` или действия пользователя).

**В: Можно ли мокать запросы для всех страниц сразу?**
**О:** Да, если ты применишь `page.route` к объекту `BrowserContext`. Тогда все вкладки и все страницы в этом контексте будут использовать этот мок. Это супер-удобно для глобальной настройки окружения.

# 🛰️ Шпаргалка: Мониторинг трафика в Playwright Java

**Мониторинг трафика** — это способность теста «подслушивать» то, что браузер говорит с сервером. Мы не просто смотрим на экран (UI), мы проверяем реальное содержимое сетевых пакетов (API-ответов, заголовков, статусов).

### 🛠 Основные инструменты

В Playwright для этого используются **Event Listeners** (слушатели событий). Они работают асинхронно: ты говоришь браузеру «слушай всё, что происходит», и как только случается событие, срабатывает твой код.

1.  `page.onRequest(request -> ...)` — вызывается, когда браузер **отправляет** запрос (GET, POST и т.д.).
2.  `page.onResponse(response -> ...)` — вызывается, когда браузер **получает** ответ от сервера.
3.  `page.waitForResponse(urlMatcher, ...) ` — (Критически важно!) Ожидание конкретного ответа. Тест встанет на паузу, пока не придет нужный пакет данных.

---

### 💻 Практический пример (Java)

Допустим, нам нужно проверить, что при нажатии на кнопку «Купить» уходит правильный запрос к API и сервер возвращает статус `200 OK`.

```java
import com.microsoft.playwright.*;
import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

public class NetworkTest {

    @Test
    void testApiCallOnButtonClick() {
        try (Playwright playwright = Playwright.create()) {
            Browser browser = playwright.chromium().launch(new BrowserType.LaunchOptions().setHeadless(false));
            Page page = browser.newPage();

            page.navigate("https://example.com/shop");

            // 1. Настраиваем "слушателя" ЗАРАНЕЕ (до действия)
            // Мы хотим логировать все ответы, где в URL есть "/api/cart"
            page.onResponse(response -> {
                if (response.url().contains("/api/cart")) {
                	System.out.println("🚀 Запрос к корзине обнаружен!");
                    System.out.println("Статус: " + response.status());
                }
            });

            // 2. Используем waitForResponse для синхронизации теста с сетью
            // Это предотвращает "гонку условий" (race condition)
            Response response = page.waitForResponse(res -> 
                res.url().contains("/api/cart") && res.request().method().equals("POST"), 
                () -> {
                    // 3. Выполняем действие, которое триггерит запрос
                    page.click("#add-to-cart-button");
                }
            );

            // 4. Ассерты (проверки)
            assertEquals(200, response.status(), "API должен вернуть 200 OK");
            
            // Можно даже проверить тело ответа (JSON)
            String body = response.text();
            assertTrue(body.contains("\"status\":\"success\""), "В ответе должна быть фраза success");

            browser.close();
        }
    }
}
```

---

### ⚠️ Нюансы и «Подводные камни» (Senior Tips)

1.  **Race Condition (Гонка условий):** Это самая частая ошибка. Если ты напишешь `page.click(...)`, а *после* этого `page.waitForResponse(...)`, тест упадет или пропустит запрос. Запрос может улететь за миллисекунды до того, как ты начнешь его ждать. 
    *   **Правило:** Сначала вешаем слушатель/ожидание $\rightarrow$ потом совершаем действие.

2.  **Фильтрация (Noise Reduction):** Браузер генерирует сотни запросов (картинки, шрифты, аналитика). Если ты повесишь `onResponse` без фильтрации по URL, твой лог превратится в мусорку, а тесты будут тормозить. Всегда используй `.contains()` или Regex для проверки URL.

3.  **Сложность с `response.text()`:** Чтение тела ответа — операция тяжелая. Если ты пытаешься прочитать тело слишком большого JSON-файла в цикле, это может замедлить выполнение тестов.

4.  **Мониторинг vs Interception:** Не путай *мониторинг* (просто смотреть) и *interception/routing* (`page.route`). Мониторинг — это `onResponse`. Routing — это когда ты перехватываешь запрос и меняешь его на лету (подменяешь данные).

**В: Как мне проверить, что запрос вообще не ушел?**
О: Тебе нужно использовать флаг-переменную. Создай `boolean requestSent = false;`, в `onRequest` меняй её на `true`. В конце теста проверяй `assertFalse(requestSent)`. Но помни, что это сработает только если ты дашь тесту время (например, через `Thread.sleep` или ожидание другого элемента).

**В: Можно ли мониторить трафик во всех вкладках сразу?**
О: Да, если ты повесишь слушатель на `BrowserContext` (`context.onResponse(...)`), он будет ловить все запросы из всех страниц (вкладок), созданных в этом контексте. Это удобно для тестирования взаимодействия между окнами.

**В: Что делать, если запрос уходит, но я не могу его поймать?**
О: Проверь, не происходит ли редирект. Если страница сразу переходит на другой URL, контекст старой страницы может быть уничтожен до того, как сработает твой ассерт. Используй `waitForURL` или проверяй сетевые события через `BrowserContext`.

# 🚀 Тема: API Testing внутри Playwright (Java)

### 🧠 Суть концепции
Многие новички совершают ошибку, думая, что Playwright — это только про браузер. На самом деле, Playwright включает в себя мощный модуль `APIRequestContext`. 

**Зачем это нужно?**
1. **Подготовка данных (Setup):** Вместо того чтобы кликать по UI для создания пользователя (что долго и нестабильно), ты делаешь один быстрый POST-запуск через API.
2. **Проверка состояния (Validation):** После действия в UI, ты проверяешь результат напрямую в базе/API, чтобы убедиться, что фронтенд не просто «красиво отобразил», а данные реально сохранились.
3. **Интеграционное тестирование:** Проверка связки "UI + API" в рамках одного теста.

---

### 🛠 Основные инструменты

В Playwright Java за работу с API отвечает интерфейс `APIRequestContext`. Ты можешь создать его двумя способами:
1. **Независимый запрос:** `playwright.request().newContext(...)` — для запросов к сторонним сервисам или подготовки данных.
2. **Запрос через контекст браузера:** `browserContext.request()` — это «киллер-фича». Этот запрос **автоматически наследует все Cookies и заголовки** текущей сессии браузера (например, токены авторизации).

---

### 📝 Базовый пример кода

```java
import com.microsoft.playwright.*;
import com.microsoft.playwright.request.*;
import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

public class ApiTest {
    // Используем Playwright для создания контекста запросов
    private APIRequestContext request;
    private Playwright playwright;

    @BeforeAll
    static void setup() {
        // Инициализация (в реальном проекте это будет в BaseTest)
    }

    @BeforeEach
    void createContext() {
        playwright = Playwright.create();
        request = playwright.request().newContext(new APIRequest.NewContextOptions()
            .setBaseURL("https://jsonplaceholder.typicode.com") // Базовый URL
            .setHeader("Content-Type", "application/json")));   // Общие заголовки
    }

    @Test
    void testGetUsers() {
        // Выполняем GET запрос
        APIResponse response = request.get("/users/1");

        // Проверки (Assertions)
        assertEquals(200, response.status());
        
        // Извлекаем тело ответа как строку или JSON
        String body = response.text();
        assertTrue(body.contains("Leanne Graham"));
    }

    @Test
    void testCreatePost() {
        // Подготовка данных (Payload)
        String jsonBody = "{\"title\": \"foo\", \"body\": \"bar\", \"userId\": 1}";

        // Выполняем POST запрос
        APIResponse response = request.post("/posts", new APIRequest.PostOptions()
            .setData(jsonBody));

        assertEquals(201, response.status());
    }

    @AfterEach
    void tearDown() {
        request.dispose();
        playwright.close();
    }
}
```

### 💡 Нюансы от Senior-а (на что смотреть)

1.  **JSON Parsing:** Playwright возвращает тело ответа как `String` или `byte[]`. В Java для удобной работы с JSON **обязательно** используй библиотеку **Jackson** или **Gson**. Не пытайся парсить JSON регулярками — это путь к боли.
2.  **Наследование авторизации:** Если ты залогинился в UI через `page.fill(...)`, а затем вызываешь `browserContext.request().get(...)`, Playwright подтянет куки из браузера. Это позволяет тестировать защищенные эндпоинты без повторной авторизации.
3.  **Слои абстракции:** Не пиши `request.post(...)` прямо в тестах. Создай **API Client Layer** (классы-репозитории для API), где методы будут называться `createUser()`, `deleteOrder()`. Тест должен читать как книга, а не как лог сервера.
4.  **Error Handling:** Всегда проверяй статус-код перед тем, как парсить тело ответа. Если придет 500 ошибка, попытка распарсить JSON упадет с невнятной ошибкой `NullPointerException`, а ты потеряешь контекст того, что именно сломалось.

### ❓ FAQ (Частые вопросы)

**В: Чем `APIRequestContext` отличается от `page.route()`?**
**О:** `page.route()` — это **перехват** (Interception). Ты подменяешь или слушаешь то, что браузер *уже* отправляет. `APIRequestContext` — это **инициация** (Initiation). Ты сам отправляешь запрос «извне» браузера.

**В: Как передать сложные объекты в POST запрос?**
**О:** Создай Java POJO класс $\rightarrow$ Используй Jackson (`objectMapper.writeValueAsString(myObject)`) $\rightarrow$ Передай строку в `.setData()`. Это стандарт индустрии.

**В: Можно ли использовать API запросы для обхода 2FA (двухфакторки)?**
**О:** Да! Это классический кейс. Ты можешь через API получить токен или создать сессию, минуя тяжелые UI-шаги с вводом SMS/кодов, и сразу переходить к тестированию функционала.

**В: Что делать, если API требует динамический Bearer Token?**
**О:** В `@BeforeEach` сделай запрос к эндпоинту `/login`, вытащи токен из ответа и добавь его в `APIRequest.NewContextOptions().setHeader("Authorization", "Bearer " + token)`.

# 🗂 Шпаргалка: Работа с Iframe в Playwright Java

### 🧠 Суть проблемы
**Iframe (Inline Frame)** — это, по сути, еще одна HTML-страница, встроенная внутрь твоей основной страницы. Для браузера это отдельный документ. 
**Главное правило:** Твои обычные локаторы (`page.locator(...)`) **не видят** то, что находится внутри iframe. Они «упираются» в границу фрейма и не могут заглянуть внутрь.

### 🛠 Основной инструмент: `FrameLocator`
В Playwright тебе не нужно «переключаться» между фреймами (как это было в Selenium через `switchTo`). Вместо этого ты создаешь **точку входа** во фрейм.

#### 1. Базовый синтаксис
Если у тебя есть iframe с `id="login-frame"`, и внутри него кнопка `#submit`, код будет таким:

```java
// Мы не ищем кнопку на странице, мы создаем локатор, который "смотрит" внутрь фрейма
FrameLocator loginFrame = page.frameLocator("#login-frame");

// Теперь используем этот локатор для поиска элементов ВНУТРИ фрейма
loginFrame.locator("#submit").click();
```

#### 2. Поиск по другим атрибутам
Если у iframe нет `id`, но есть другие признаки (например, `name` или часть `src`):
```java
// По селектору CSS (например, по атрибуту name)
FrameLocator frameByName = page.frameLocator("iframe[name='content-frame']");

// По части URL (если фрейм динамический)
FrameLocator frameBySrc = page            page.frameLocator("iframe[src*='payment-gateway']");
```

#### 3. Вложенные Iframe (Iframe внутри Iframe)
Это классическая «боль» автоматизаторов. Playwright решает это элегантно через цепочку:
```java
// Сначала заходим во внешний фрейм, затем во внутренний
FrameLocator outerFrame = page.frameLocator("#outer-iframe");
FrameLocator innerFrame = outerFrame.frameLocator("#inner-iframe");

innerFrame.locator("#target-button").click();
```

---

### ⚠️ Нюансы и Senior Tips (На что наступишь, если не знать)

1.  **Забудь про `driver.switchTo()`:** В Playwright нет понятия «текущего фокуса». Ты всегда работаешь либо с `page`, либо с `frameLocator`. Тебе **не нужно** возвращаться обратно к основному контенту (`defaultContent()`), потому что ты не покидал его, ты просто создал новый путь доступа.
2.  **Auto-waiting работает:** `frameLocator` в Playwright очень умный. Когда ты вызываешь `.click()` на элементе внутри фрейма, Playwright сам будет ждать, пока:
    *   Сам iframe появится в DOM.
    *   Iframe загрузится.
    *   Элемент внутри него станет доступным (Actionability checks).
3.  **Проблема динамических ID:** Если `id` у фрейма меняется при каждой перезагрузке (часто в React/Angular), используй поиск по селекторам, которые не зависят от ID: `page.frameLocator("iframe[src*='stable-part-of-url']")`.
4.  **Cross-Origin (Разные домены):** Playwright отлично справляется с фреймами, которые подгружают контент с других сайтов (например, виджеты оплаты или карты), в отличие от старых инструментов. Тебе не нужно настраивать специальные разрешения для доступа к другому домену.

---

### ❓ FAQ: Часто задаваемые вопросы

**В: Почему мой локатор `page.locator("#button-inside-iframe")` не находит элемент, хотя я вижу его в DevTools?**
**О:** Потому что этот элемент находится в другом документе (iframe). Обычный `page` ищет только в корневом документе. Тебе обязательно нужно использовать `page.frameLocator()`.

**В: Что делать, если iframe появляется не сразу, а через пару секунд после загрузки страницы?**
**О:** Playwright сам подождет. Метод `frameLocator` ленивый (lazy). Он начнет искать фрейм только в тот момент, когда ты попытаешься совершить действие (например, `.click()`) над элементом внутри него.

**В: Можно ли найти все iframe на странице сразу?**
**О:** Да, через обычный локатор: `page.locator("iframe").all()`. Это полезно, если нужно просканировать страницу на наличие подозрительных или рекламных фреймов.

**В: Как работает поиск, если у iframe нет ни ID, ни Name?**
**О:** Используй CSS-селекторы по другим атрибутам (`src`, `class`, `title`) или даже через XPath. Главное — найти уникальный признак, который отличает этот фрейм от других.

# 🗂 Шпаргалка: Диалоговые окна (Dialogs) в Playwright Java

### 💡 Суть темы
В браузерах существуют три основных типа системных диалогов:
1.  **Alert** (только уведомление, кнопка "OK").
2.   **Confirm** (вопрос, кнопки "OK" и "Cancel").
3.  **Prompt** (вопрос с полем ввода текста).

**Главная особенность Playwright:** В отличие от Selenium, где диалоговое окно «замораживает» браузер и требует переключения фокуса, Playwright работает через **событийную модель**. 

> **⚠️ Важнейший нюанс (Senior Tip):** По умолчанию Playwright **автоматически закрывает (dismiss)** все диалоговые окна. Если ты не напишешь специальный обработчик, тест просто проскочит мимо алерта, и ты даже не узнаешь, что он был.

---

### 🛠 Основной механизм: `page.onDialog()`
Чтобы взаимодействовать с окном, нужно подписаться на событие **ДО** того, как действие (клик) вызовет это окно.

#### Алгоритм действий:
1.  Подписываемся на обработчик `page.onDialog(dialog -> { ... })`.
2.  Выполняем действие, вызывающее диалог (`click()`).
3.  Внутри обработчика решаем: принять (`accept`), отклонить (`dismiss`) или ввести текст (`type`).

#### Методы объекта `Dialog`:
*   `dialog.accept()` — нажать "OK".
*   `dialog.dismiss()` — нажать "Cancel" (или закрыть окно).
*   `dialog.message()` — получить текст сообщения из окна.
*   `dialog.type(text)` — ввести текст (только для `prompt`).
*   `dialog.defaultValue()` — получить значение по умолчанию (для `prompt`).

---

### 💻 Пример кода (Java)

```java
import com.microsoft.playwright.*;
import org.junit.jupiter.api.*;

import static com.microsoft.playwright.assertions.PlaywrightAssertions.assertThat;

public class DialogTest {
    
    @Test
    void handleDialogsTest() {
        try (Playwright playwright = Playwright.create()) {
            Browser browser = playwright.chromium().launch(new BrowserType.LaunchOptions().setHeadless(false));
            Page page = browser.newPage();
            page.navigate("https://your-website.com/alerts");

            // 1. Обработка ALERT (просто подтверждаем)
            page.onDialog(dialog -> {
                System.out.println("Alert message: " + dialog.message());
                dialog.accept(); 
            });
            page.locator("#alert-button").click();

            // 2. Обработка CONFIRM (выбираем отмену)
            // Важно: если нужно другое поведение, можно использовать page.onceDialog()
            page.onDialog(dialog -> {
                if (dialog.type().equals("confirm")) {
                    dialog.dismiss();
                } else {
                    dialog.accept();
                }
            });
            page.locator("#confirm-button").click();

            // 3. Обработка PROMPT (вводим данные)
            page.onDialog(dialog -> {
                dialog.accept("Senior Developer"); // Вводим текст и жмем OK
            });
            page.locator("#prompt-button").click();
            
            // Проверка результата после диалога
            assertThat(page.locator("#result")).containsText("Senior Developer");

            browser.close();
        }
    }
}
```

---

### ⚠️ Нюансы и "Подводные камкамни" (Senior Level)

1.  **Race Condition (Гонка условий):** Всегда регистрируй `page.onDialog(...)` **ДО** вызова `.click()`. Если клик произойдет быстрее, чем обработчик успеет прикрепиться к странице, Playwright применит свое стандартное поведение (авто-закрытие), и ты потеряешь контроль над тестом.
2.  **`onDialog` vs `onceDialog`:** 
    *   `onDialog` — это постоянная подписка на *все* последующие окна в рамках этой страницы.
    *   `onceDialog` — сработает только один раз. Используй его, если хочешь изолировать логику конкретного шага и не влиять на другие диалоги.
3.  **Множественные диалоги:** Если на странице вылетает цепочка окон (одно за другим), `onDialog` будет ловить каждое. Тебе нужно внутри лямбда-выражения добавить проверку `dialog.message()` или `dialog.type()`, чтобы различать их.
4.  **Сложные проверки:** Если тебе нужно проверить, что текст в алерте правильный, делай это внутри обработчика через `Assertions.assertEquals(...)`.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему мой тест падает с ошибкой, хотя я вижу, что алерт появился на экране?**
**О:** Скорее всего, ты не настроил обработчик. Playwright видит диалог, автоматически его закрывает (чтобы не блокировать поток), и если после этого код ожидает появления какого-то элемента, который зависел от нажатия "OK", тест упадет по таймауту.

**В: Как протестировать негативный сценарий, когда пользователь нажимает "Cancel"?**
**О:** Используй `dialog.dismiss()`. Это самый чистый способ имитировать отказ пользователя.

**Г: А если я хочу просто игнорировать все диалоги и ничего не делать?**
**О:** Тебе ничего не нужно делать! Playwright сделает это за тебя по умолчанию. Но для чистоты логов лучше явно прописать `dialog.dismiss()`, чтобы в консоли было видно, что ты контролируешь процесс.

# 📂 Тема: Загрузка и скачивание файлов (File Upload & Download)

В Playwright работа с файлами отличается от Selenium тем, что нам не нужно пытаться взаимодействовать с системным окном Windows/macOS (которое автоматизировать невозможно). Мы работаем напрямую с протоколом браузера.

## 1. Загрузка файлов (File Upload)

Загрузка в Playwright — это всегда взаимодействие с элементом `<input type="file">`.

### Базовый сценарий
Если на странице есть стандартный `input`, мы используем метод `setInputFiles()`.

```java
// Одиночный файл
page.locator("input[type='file']").setInputFiles("path/to/file.pdf");

// Несколько файлов (передаем массив строк)
page.locator("input[type='file']").setInputFiles(new String[] {"file1.txt", "file2.txt"});

// Очистка выбранных файлов (удаление из input)
page.locator("input[type='file']").setInputFiles(new String[]{});
```

### ⚠️ Нюанс: Скрытый Input (Hidden Input)
В современных фреймворках (React, Angular) часто скрывают настоящий `input`, а вместо него рисуют красивую кнопку. Если ты попытаешься сделать `.click()` по кнопке, откроется системное окно, и тест зависнет.

**Решение от Senior:** Всегда ищи именно `input` (даже если он `display: none`) и используй `setInputFiles`. Playwright умеет «прокидывать» файл в скрытый элемент.

### ⚠️ Нюанс: Drag and Drop
Если на сайте реализован перетаскиваемый интерфейс, `setInputFiles` может не сработать напрямую на контейнере. В этом случае нужно использовать эмуляцию событий или искать скрытый `input`, который отвечает за хранение состояния файла.

## 2. Скачивание файлов (File Download)

Скачивание — это **событийная** операция. Мы не можем просто «нажать и подождать». Нам нужно начать «слушать» браузер на предмет появления события загрузки *до того*, как мы нажлокаем на кнопку.

### Правильный паттерн
Используй метод `page.waitForDownload()`. Он принимает в себя лямбда-выражение с действием, которое триггерит скачивание.

```java
// 1. Начинаем ждать событие загрузки
Download download = page.waitForDownload(() -> {
    // 2. Выполняем действие, которое запускает скачивание
    page.getByText("Download Report").click();
});

// 3. Сохраняем файл из временной папки браузера в нужное нам место
Path downloadPath = Paths.get("downloads/report.pdf");
download.saveAs(downloadPath);

// 4. Проверяем, что файл существует и не пустой
assertTrue(Files.exists(downloadPath));
```

### ⚠️ Нюанс: Жизненный цикл файла
Когда браузер скачивает файл, он кладет его во **временную папку**. Как только сессия браузера закрывается, этот файл может быть удален.
**Золотое правило:** Всегда делай `download.saveAs(path)` внутри теста, чтобы вытащить файл из «песочнет» в рабочую директорию проекта.

## 💡 Senior Tips (Советы профи)

1.  **Пути к файлам:** Никогда не используй абсолютные пути типа `C:\Users\Admin\Desktop\test.txt`. Используй относительные пути от корня проекта (`Paths.get("src/test/resources/file.txt")`). Это спасет тебя, когда тесты запустятся на Linux-агенте в Jenkins или GitHub Actions.
2.  **Очистка (Cleanup):** Если твои тесты скачивают файлы, создай в `@AfterEach` логику очистки папки `downloads/`. Иначе после 100 прогонов твой диск забьется мусором, и ты запутаешься в старых результатах.
3.  **Проверка содержимого:** Скачать файл — это только полдела. Senior проверяет содержимое: `String content = Files.readString(downloadPath);`.

# 📑 Шпаргалка: Мульти-вкладки и Мульти-контексты в Playwright

В Playwright концепция отличается от Selenium. Забудь про `driver.switchTo().window()`. Здесь всё строится на владении объектами.

## 1. BrowserContext: "Изолированные песочницы"
`BrowserContext` — это, по сути, отдельное окно в режиме **Инкогнито**. У каждого контекста свои Cookies, LocalStorage, кэш и сессия.

*   **Зачем это нужно?**
    *   **Изоляция:** Каждый тест запускается в чистом контексте. Тесты не влияют друг на другом (никаких "забытых" куки от предыдущего теста).
    *   **Многопользовательское тестирование:** Ты можешь создать `contextUserA` и `contextUserB` в рамках одного теста, чтобы проверить взаимодействие (например, чат).
    *   **Скорость:** Создание контекста — это мгновенная операция, гораздо быстрее, чем запуск нового браузера.

**Код (Java):**
```java
// Создаем два разных пользователя
BrowserContext contextA = browser.newContext();
BrowserContext contextB = browser.newContext();

Page pageA = contextA.newPage(); // Пользователь А
Page pageB = contextB.newPage(); // Пользователь Б

pageA.navigate("https://example.com/login"); // Логинимся под А
// В contextB мы всё еще не залогинены!
```

---

## 2. Multi-Pages: "Вкладки внутри одного контекста"
`Page` — это одна вкладка. В рамках одного `BrowserContext` может быть много вкладок. Все они **делят** между собой Cookies и LocalStorage.

*   **Зачем это нужно?** Тестирование поведения сайта при открытии ссылок в новых вкладках (например, клик по рекламному баннеру или PDF-документу).

**Код (Java):**
```java
Page mainPage = context.newPage();
mainPage.navigate("https://example.com");

// Клик, который открывает новую вкладку (target="_blank")
mainPage.getByText("Открыть отчет").click();

// Как поймать новую вкладку? Используем waitForPage
Page newTab = context.waitForPage(() -> {
    mainPage.getByText("Открыть отчет").click();
});

newTab.waitFor(); 
System.out.println(newTab.title()); // Работаем с новой вкладкой
```

---

## 💡 Senior Nuances (Нюансы, на которых все валятся)

1.  **Ловушка `waitForPage`:** Никогда не делай клик, который открывает новую вкладку, *вне* лямбда-выражения `waitForPage`. Если ты сначала кликнешь, а потом вызовешь `waitForPage`, новая страница может загрузиться слишком быстро, и Playwright её "пропустит", ожидая вечно.
    *   ❌ **Плохо:** `page.click(...); Page newPage = context.waitForPage(...);`
    
2.  **Переключение — это не переключение:** В Selenium ты "переключал фокус" драйвера. В Playwright ты просто имеешь две переменные: `page1` и `page2`. Ты можешь одновременно выполнять действия на обеих вкладках (если логика теста это позволяет).

3.  **Память при мульти-контекстах:** Если ты создаешь 50 контекстов в одном тесте, не забывай закрывать их (`context.close()`), иначе процесс браузера "съест" всю оперативную память сервера/CI.

4.  **Синхронизация состояний:** Если ты тестируешь чат между `UserA` и `UserB`, помни: действия в `pageA` должны быть завершены (или иметь ассерты), прежде чем ты начнешь проверять результат в `pageB`.

## ❓ FAQ (Частые вопросы на интервью)

**В: Чем `BrowserContext` отличается от `Browser`?**
**О:** `Browser` — это запущенный процесс браузера (Chromium/Firefox). Он тяжелый. `BrowserContext` — это легкая изолированная сессия внутри этого процесса. Один `Browser` может содержать сотни `BrowserContext`.

**В: Как протестировать сценарий, где один пользователь отправляет сообщение, а другой его получает?**
**О:** Нужно создать два разных `BrowserContext`. В первом контексте (User A) выполнить действие `click()` (отправка). Во втором контексте (User B) использовать `page.waitForSelector()` или `assertThat(...)`, чтобы увидеть появившийся элемент.

**В: Как мне "переключиться" на новую вкладку, если я не использовал `waitForPage`?**
**О:** Ты можешь получить все открытые страницы через `context.pages()`. Это вернет список всех активных вкладок в этом контексте. Но `waitForPage` — это гораздо более надежный и "чистый" способ с точки зрения архитектуры.

**В: Если я открою новую вкладку в том же контексте, будут ли там те же куки?**
**О:** Да. Все вкладки внутри одного `BrowserContext` имеют общий доступ к Cookies и LocalStorage. Если ты залогинился в первой вкладке, вторая вкладка будет уже авторизована.

# 🔐 Сохранение состояния (Authentication Reuse)

### 💡 В чем суть?
В классическом подходе каждый тест начинает «с чистого листа»: открывается браузер, вводится логин, пароль, ждется редирект... Если у тебя 100 тестов, ты тратишь колоссальное время на повторение одного и того же действия.

**Authentication Reuse** — это стратегия, при которой мы один раз проходим сценарий авторизации, «фотографируем» состояние браузера (Cookies + LocalStorage) и сохраняем это в JSON-файл. Все последующие тесты просто подгружают этот файл и сразу оказываются в авторизованном состоянии.

---

### 🛠 Как это реализовать (Алгоритм)

Процесс делится на два этапа: **Producer** (создает состояние) и **Consumer** (использует состояние).

#### Шаг 1: Создание файла состояния (The Producer)
Мы создаем отдельный тест или специальный метод в `@BeforeAll`, который выполняет логин и сохраняет `storageState`.

```java
// Пример сохранения состояния
public void saveAuthState(Page page, String filePath) throws IOException {
    // 1. Выполняем шаги логина
    page.navigate("https://example.com/login");
    page.fill("#username", "admin");
    page.fill("#password", "password123");
    page.click("#login-button");

    // 2. Ждем, пока авторизация завершится (например, появления профиля)
    page.waitForSelector(".user-profile");

    // 3. Сохраняем состояние контекста в JSON
    BrowserContext context = page.context();
    context.storageState(new BrowserContext.StorageStateOptions().setPath(Paths.get(filePath)));
}
```

#### Шаг 2: Использование состояния (The Consumer)
При создании нового `BrowserContext` мы указываем путь к нашему JSON-файлу.

```java
// Пример использования в тестах
@Test
void testWithSavedAuth() {{
    BrowserContext context = browser.newContext(new Browser<BrowserContext>.NewContextOptions()
        .setStorageStatePath(Paths.get("auth_state.json"))); // Магия здесь!
    
    Page page = context.newPage();
    page.navigate("https://example.com/dashboard");
    
    // Мы уже залогинены! Проверяем наличие данных профиля
    assertThat(page.locator(".user-name")).hasText("Admin User");
}}
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Проблема «Протухшей сессии» (Session Expiration):**
    JSON-файл — это статичный снимок. Если срок жизни куки истек, все твои тесты упадут с ошибкой авторизации. 
    *   *Решение:* В пайплайне CI/CD первым делом должен запускаться «Setup Task», который проверяет валидность файла или принудительно пересоздает его.

2.  **Разные роли пользователей:**
    Если тебе нужно тестировать функционал Админа и Пользователя, не пытайся запихнуть всё в один файл. Создай два файла: `admin_state.json` и `user_state.json`.

3.  **Безопасность (Security First!):**
    **Никогда** не коммить файлы `auth_state.json` с реальными данными в Git. Добавь их в `.gitignore`. В CI/CD эти файлы должны генерироваться «на лету» из секретных переменных (Secrets).

4.  **LocalStorage vs Cookies:**
    Playwright сохраняет и то, и другое. Но помни: если твое приложение хранит токены (JWT) только в `sessionStorage`, Playwright **не сохранит** их через `storageState` (так как session storage живет только пока открыта вкладка). Старайся использовать приложения, где токены в `localStorage` или `Cookies`.

5.  **Race Condition при генерации:**
    Если ты запускаешь тесты параллельно, может возникнуть ситуация, когда тест-потребитель пытается прочитать файл, который еще не успел записать тест-продюсер. 
    *   *Решение:* Используй четкую оркестрацию в Maven/Gradle: сначала `setup` таск, затем `test` таск.

# 🛠 Playwright Inspector: Твой «Рентген» и «Пульт управления»

**Playwright Inspector** — это графический интерфейс (GUI), который позволяет тебе буквально «залезть под капот» выполняемого теста. Это не просто дебаггер, это среда для интерактивного исследования браузера и генерации локаторов.

### 🚀 Как запустить (Entry Points)

Есть два основных способа «остановить время» и вызвать инспектор:

1.  **`page.pause()` в коде:**
    Самый удобный способ. Ты ставишь эту команду в конкретном месте теста, где всё ломается. Тест дойдет до этой строки, остановится и откроет окно инспектора.
    ```java
    page.navigate("https://example.com");
    page.pause(); // Тест замрет здесь и откроет Inspector
    page.click("#submit");
    ```

2.  **Переменная окружения `PWDEBUG=1`:**
    Если ты хочешь запустить весь тест с самого начала в режиме отладки.
    *   **Linux/macOS:** `PWDEBUG=1 mvn test`
    *   **Windows (PowerShell):** `$env:PWDEBUG=1; mvn test`
    *   **Windows (CMD):** `set PWOBSERVE=1 && mvn test`

---

### 🛠 Основные возможности

#### 1. Step-by-step Execution (Пошаговое выполнение)
Когда инспектор открыт, у тебя есть кнопки управления потоком:
*   **Play:** Продолжить выполнение до следующей паузы или конца теста.
*   **Step Over:** Выполнить текущую строку и перейти к следующей. Это позволяет тебе смотреть, на каком именно действии (click, fill, etc.) тест падает.

#### 2. Locator Explorer (Исследование локаторов) — *Самая киллер-фича*
В окне инспектора есть инструмент **"Explore"**. 
*   Ты кликаешь на элемент в браузере (который открылся вместе с инспектором).
*   Инспектор **мгновенно генерирует и показывает** наиболее подходящий локатор (например, `getByRole` или `getByText`).
*   Это избавляет от необходимости гадать, какой CSS-селектор лучше.

#### 3. Live Code Generation (Связка с Codegen)
Инспектор работает в связке с режимом записи. Ты можешь совершать действия в браузере, и инспектор будет показывать, какой Java-код соответствует твоим кликам.

---

### 🧠 Нюансы от Senior-а (На что важно обратить внимание)

*   **Headless vs Headed:** Инспектор **не работает** в `headless` режиме. Тебе обязательно нужно запускать браузер в `headed` режиме (что происходит автоматически при использовании `PWDEBUG=1`).
*   **Auto-waiting не отключается:** Важно понимать, что инспектор не «отключает» умные ожидания Playwright. Если элемент не готов, тест всё равно будет ждать его появления, даже если ты стоишь на паузе. Инспектор просто дает тебе возможность увидеть этот процесс.
*   **Синхронизация:** Окно браузера и окно инспектора — это две разные сущности, но они синхронизированы по состоянию DOM. Если ты изменишь что-то в консоли браузера, инспектор это «подхватит».
*   **Не оставляй `page.pause()` в коде!** Это классическая ошибка джуна. Если этот код попадет в CI/CD (Jenkins/GitHub Actions), твой пайплайн зависнет навсегда, ожидая, пока кто-то нажмет кнопку в невидимом браузере. Используй это **только локально**.

### ❓ FAQ (Частые вопросы)

**В: Что делать, если я использую `page.pause()`, но браузер не открывается?**
**О:** Проверь, не запущен ли у тебя тест в режиме `--headless`. Инспектор требует визуального окна. Также убедись, что у тебя правильно настроены переменные окружения в IDE (IntelliJ IDEA).

**В: Можно ли использовать Inspector для отладки API-запросов?**
**О:** Напрямую — нет, он заточен под UI. Но так как инспектор позволяет смотреть на сетевую активность через вкладку *Network* в открывшемся браузере, ты можешь анализировать ответы API, которые влияют на состояние страницы.

**В: В чем разница между `PWDEBUG=1` и `page.pause()`?**
**О:** 
- `PWDEBUG=1` запускает тест **с первой секунды** в режиме отладки (ты видишь всё с самого начала).
- `page.pause()` позволяет прогнать тест быстро и остановиться **только в нужной тебе точке**. Для больших тестов второй вариант гораздо эффективнее.

**В: Инспектор помогает найти причимые причины падения (Root Cause)?**

# 🛠 Trace Viewer: Твой "Черный ящик" для тестов

**Trace Viewer** — это не просто инструмент для просмотра скриншотов. Это полноценная среда для **post-mortem анализа** (анализа после случившегося). Если тест упал в CI (Jenkins/GitHub Actions), у тебя нет возможности подключиться к нему через дебаггер. Trace Viewer позволяет «перемотать» выполнение теста назад и вперед, видя состояние DOM, сетевые запросы и консоль в каждый момент времени.

### 🧠 Основные концепции

Когда ты открываeks Trace, ты получаешь доступ к следующим слоям данных:

1.  **Timeline (Временная шкала):** Визуальный скроллер сверху. Позволяет быстро перемещаться по ключевым моментам теста.
2.  **Action List:** Список всех выполненных команд (`click`, `fill`, `goto`). При клике на конкретное действие, Trace Viewer переключает состояние страницы именно на этот момент.
3.  **Snapshots (Снимки состояния):** Это киллер-фича. В отличие от обычного скриншота, Playwright сохраняет **состояние DOM**. Ты можешь использовать DevTools прямо внутри Trace Viewer: инспектировать элементы, смотреть CSS и даже делать запросы к элементам, которые были в момент теста.
    *   *Before:* Состояние до действия.
    *   *Action:* Момент взаимодействия (например, нажатие кнопки).
    *   *After:* Что изменилось после действия.
4.  **Network Tab:** Полный лог всех сетевых запросов (`fetch`, `xhr`, `image`, `script`). Ты видишь статус-коды, заголовки и тело ответа. Это критично для поиска багов типа *"Кнопка не нажалась, потому что API вернуло 500"*.
5.  **Console Logs:** Все логи из браузерной консоли (ошибки JS, `console.log`).
6.  **Source Code:** Привязка действия к конкретной строке твоего Java-кода.

---

### 🚀 Как это использовать в Java (Implementation)

Trace не работает «сам по себе», его нужно включить в коде или конфигурации.

#### Настройка в коде:
Обычно настройка делается на уровне `BrowserContext`.

```java
// Создаем контекст с включенным трейсингом
BrowserContext context = browser.newContext();

// 1. Начинаем запись (важно вызвать ДО начала действий)
context.tracing().start(new Tracing.StartOptions()
    .setScreenshots(true) // Сохранять скриншоты для каждого шага
    .setSnapshots(true)   // Сохранять состояние DOM (обязательно!)
    .setSources(true));   // Привязка к исходному коду

try {
    Page page = context.newPage();
    page.navigate("https://example.com");
    page.click("#submit-button");
    // ... твои тесты
} finally {
    // 2. Остановка и сохранение в файл .zip
    context.tracing().stop(new Tracing.StopOptions()
        .setPath(Paths.get("trace-results/test-trace.zip")));
}
```

#### Режимы работы (Strategies):
Как Senior, я рекомендую не записывать трейсы для *всех* тестов (это замедляет выполнение и забивает диск), а использовать стратегии:
*   `off`: Выключено (для локального прогона здоровых тестов).
*   `on`: Записывать всегда (удобно при разработке нового теста).
*   **`retain-on-failure`**: (Золотой стандарт) Записывать только если тест упал. Это экономит ресурсы CI и дает тебе данные именно там, где они нужны.

---

### ⚠️ Нюансы и "Подводные камни"

1.  **Размер файлов:** Если в тесте очень много переходов по страницам или тяжелая загрузка медиа-контента, `.zip` файл может раздуться до сотен мегабайт. Это может "положить" артефакты в Jenkins.
2.  **Производительность:** Включение `setScreenshots(true)` и `setSnapshots(true)` добавляет оверхед на запись данных. На очень больших тестовых сетах это может увеличить время выполнения на 10-20%.
3.  **Просмотр файлов:** Трейс — это не картинка, это архив. Чтобы его открыть, тебе нужно либо:
    *   Локально запустить: `npx playwright show-trace path/to/trace.zip`.
    *   Использовать [trace.playwright.dev](https://trace.playwright.dev) (онлайн-вьюер, куда можно просто перетащить файл).

# 🚀 Playwright Codegen: Твой автоматический помощник

**Codegen** — это встроенный в Playwright инструмент (рекордер), который записывает твои действия в браузере и на лету генерирует готовый код на выбранном языке (в нашем случае Java). 

Представь, что это твой «умный» видеорегистратор: ты просто едешь по дороге (кликаешь по сайту), а он записывает не только видео, но и подробную инструкцию, как повторить этот маршрут.

### 🛠 Как запустить (для Java-проекта)
Поскольку мы работаем в экосистеме Maven/Gradle, тебе не нужно устанавливать ничего отдельного. Используй команду через терминал в корне проекта:

**Если используешь Maven:**
```bash
mvn exec:java -Dexec.mainClass="com.microsoft.playwright.CLI" -Dexec.args="codegen https://google.com"
```

**Что произойдет:**
1. Откроется полноценный браузер (Chromium по умолчанию).
2. Откроется окно **Playwright Inspector**.
3. Все твои клики, ввод текста и навигация будут мгновенно превращаться в Java-код в окне инспектора.

---

### 💡 Ключевые возможности

1.  **Record (Запись):** Ты взаимодействуешь с сайтом — код пишется сам.
2.  **Locator Picker (Выбор локатора):** Это киллер-фича. Ты можешь нажать кнопку "Pick locator" в инспекторе, кликнуть на любой элемент в браузере, и Playwright выдаст тебе **идеальный** локатор (в приоритете `getByRole`, `getByText` и т.д.).
3.  **Multi-tab/Multi-context:** Он умеет отслеживать переходы между вкладками и даже взаимодействие между разными контекстами (например, если ты открыл две разные сессии).

---

### ⚠️ Нюансы и «Подводные камни» (Senior level)

Как опытный инженер, я предостерегаю тебя: **никогда не копируй код из Codegen напрямую в свои тесты как финальный вариант.** Вот почему:

1.  **Проблема "хрупких" локаторов:** Codegen старается использовать лучшие практики (User-facing locators), но если структура сайта сложная, он может свалиться в тяжеловесный и хрупкий `xpath` или `css selector`. 
    *   *Совет:* Всегда проверяй, что он сгенерировал. Если видишь длинный XPath — перепиши его на `getByRole` или `getByTestId` вручную.
2.  **Отсутствие логики:** Codegen генерирует только **линейный сценарий**. Он не умеет создавать циклы (`for`), условия (`if/else`) или работать с внешними данными (Data-Driven). Он просто «жмет на кнопки».
3.  **Никаких ассертов (Assertions):** Рекордер записывает действия, но он не знает, что ты *хочешь проверить*. Он зафиксирует клик по кнопке "Login", но не добавит проверку `assertThat(page).hasURL(...)`. Проверки нужно добавлять руками.
4.  **Засорение кода:** При долгой записи в код попадает много лишнего: скроллинг, фокус на элементах, движения мыши. Перед тем как вставить код в Page Object, проведи «чистку».

# 📸 Тема: Screenshots & Video (Скриншоты и Видео)

В автоматизации скриншоты и видео — это твои «черные ящики». Они нужны не для красоты, а для **post-mortem анализа**: когда тест упал в 3 часа ночи на Jenkins, ты должен увидеть, что именно пошло не так, без возможности запустить тест повторно.

### 1. Screenshots (Скриншоты)

В Playwright есть три уровня работы со скриншотами: **Viewport** (то, что видно на экране), **Full Page** (вся страница целиком) и **Element** (конкретный объект).

#### Основные методы:
*   `page.screenshot(new Page.ScreenshotOptions().setPath(Paths.get("path.png")))` — базовый скриншот текущего вьюпорта.
*   `setFullPage(true)` — делает скриншот всей страницы, прокручивая её сверху донизу. Полезно для проверки длинных лендингов.
*   `setMask(List<Locator>)` — **Senior Tip:** Если на странице есть динамические данные (цены, таймеры) или персональные данные (PII), используй `mask`. Playwright закрасит эти элементы цветными прямоугольниками. Это делает скриншоты «чистыми» и стабильными.

#### Стратегия использования:
**Никогда не делай скриншоты каждого теста.** Это убьет производительность и забьет диск. 
*   *Правильный подход:* Снимать скриншот только в блоке `tearDown` (после теста), если статус теста == `FAILED`.

---

### 2. Video (Видеозапись)

Видео в Playwright привязывается не к конкретной странице, а к **BrowserContext**. Это значит, что видео записывается для всей сессии (всех вкладок внутри одного контекста).

#### Как настроить:
Настройка происходит на этапе создания контекста (`BrowserContext`).
```java
BrowserContext context = browser.newContext(new Browser.NewContextOptions()
    .setRecordVideoDir(Paths.get("target/videos/")) // Куда сохранять
    .setViewportSize(1280, 720)
);
```

#### Нюансы:
*   **Где файл?** Playwright создает видео с уникальным именем (UUID). Тебе придется программно искать его в папке после завершения теста.
*   **Когда сохраняется?** Видео записывается во временный файл и становится доступным в виде полноценного `.webm` только после вызова `context.close()`. Если тест упал так жестко, что контекст не закрылся — видео может быть битым или отсутствовать.

---

### 💡 Senior Nuances (О чем молчат учебники)

1.  **Performance Overhead:** Запись видео — это тяжелая операция для CPU. На больших параллельных запусках (например, в 20 потоков) видео может замедлить выполнение тестов на 30-50%. Используй видео только при отладке или на определенных стейджах CI.
2.  **Storage Management:** В CI/CD (Jenkins/GitLab) всегда настраивай очистку артефактов. Если не удалять старые скриншоты и видео, через неделю твой агент упадет с ошибтом `No space left on device`.
3.  **Headless Mode:** Скриншоты и видео работают в `headless` режиме (без видимого окна браузера) точно так же, как и в `headed`. Не забудь, что при смене разрешения экрана (`viewport`) меняется и композиция скриншота.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли сделать скриншот только одного элемента?**
**О:** Да. Используй `locator.screenshot(options)`. Это идеально, если нужно проверить состояние конкретной кнопки или карточки товара, не отвлекаясь на остальной интерфейс.

# 📝 Шпаргалка: Логирование в Playwright Java

### 🎯 Зачем это нужно?
Логи — это твой «черный ящик» самолета. Когда тест падает в CI/CD (в headless-режиме), у тебя нет видео или глаза. У тебя есть только лог, который должен ответить на вопросы: *Что делал тест? На каком шаге споткнулся? Что ответил сервер?*

### 🛠 Инструментарий
Забудь про `System.out.println`. В Java-мире стандартом является **SLF4J** (фасад) + **Logback** или **Log4j2** (реализация).
*   **SLF4J:** Позволяет менять библиотеку логирования, не меняя код.
*   **Logback:** Быстрый, гибкий, стандарт для Spring и большинства Java-проектов.

**Что добавить в `pom.xml`:**
```xml
<dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
    <version>2.0.x</version>
</dependency>
<dependency>
    <groupId>ch.qos.logback</groupId>
    <artifactId>logback-classic</artifactId>
    <version>1.4.x</version>
</dependency>
```

### 🚦 Уровни логирования (Levels)
Используй их осознанно, чтобы не превратить лог в мусорку:
1.  **`ERROR`**: Критические ошибки (тест упал, элемент не найден). Сопровождается StackTrace.
2.  **`WARN`**: Что-то пошло не так, но тест идет дальше (например, slow response от API или редирект, который мы не ждали).
3.  **`INFO`**: Высокоуровневые шаги (Business Steps). *"User logs in"*, *"Navigated to Dashboard"*. Это то, что читает менеджер/QA Lead.
4.  **`DEBUG`**: Технические детали. *"Clicked locator: #submit-btn"*, *"Waiting for selector..."*. Нужно для отладки.
5.  **`TRACE`**: Максимальная детализация (заголовки HTTP-запросов, содержимое JSON). Обычно выключено в релизе.

### 🚀 Стратегии логирования в Playwright

#### 1. Уровень Page Object (Business Logic)
Логируй **действие**, а не клик.
*   ❌ *Плохо:* `logger.info("Clicking button login");`
*   ✅ *Хорошо:* `logger.info("Attempting to log in user: {}", username);`

#### 2. Управление сетевым трафиком (Network Interception) — **Senior Level**
Самый мощный способ. Ты можешь «подписаться» на события браузера и автоматически логировать все запросы/ответы без написания лишнего кода в тестах.

```java
// В базовом классе теста или Setup
page.onResponse(response -> {
    if (response.status() >= 400) {
        logger.error("API Error: {} | URL: {}", response.status(), response.url());
    } else {
        logger.debug("API Success: {} | URL: {}", response.status(), response.url());
    }
});

page.onConsoleMessage(msg -> {
    logger.info("[Browser Console] {}", msg.text());
});
```

### ⚠️ Нюансы и "Подводные камни" (Pitfalls)

1.  **Засорение логов (Log Pollution):** Если логировать каждый чих в `DEBUG` на уровне CI, размер лог-файла вырастет до гигабайт. Настраивай уровни через `logback.xml` (в CI — INFO, локально — DEBUG).
2.  **Безопасность (Sensitive Data):** **НИКОГДА** не логируй пароли, токены авторизации или персональные данные пользователей в открытом виде. Используй маскирование: `password: ****`.
3.  **Параллелизация:** Если ты запускаешь тесты в несколько потоков (JUnit 5 parallel), обычный лог превратится в кашу из перемешанных строк.
    *   *Решение:* Используй **MDC (Mapped Diagnostic Context)**. Добавляй `Thread ID` или `Test Name` в каждый лог, чтобы можно было отфильтровать сообщения конкретного теста.
4.  **Контекст:** Лог без контекста бесполезен. Вместо `"Element not found"` пиши `"Failed to find Login Button on LoginPage"`.

### ❓ FAQ (Частые вопросы)

**В: Почему `System.out.println` — это плохо?**
**О:** Он не поддерживает уровни (нельзя выключить в продакшене), он медленный (синхронный), и ты не можешь легко перенаправить его в файл, базу данных или систему сбора логов (ELK/Splunk) без костылей.

**В: Как логировать ошибки так, чтобы было удобно дебажить?**
**О:** Всегда передавай `Exception` последним аргументом: `logger.error("Login failed for user {}", user, exception);`. SLF4J сам распечатает весь StackTrace.

**В: Где лучше всего настраивать логирование: в каждом тесте или в одном месте?**
**О:** В одном месте (BaseTest или Listener). Тесты должны описывать *что* мы проверяем, а инфраструктура (логирование, скриншоты) должна решать, *как* это записывать.

**В: Могу ли я логировать тело API ответа в Playwright?**
**О:** Да, через `page.onResponse`. Но будь осторожен: если ответ огромный (например, список из 1000 объектов), это может сильно замедлить выполнение тестов и раздуть лог. Используй `DEBUG` уровень для этого.

# 🧠 Шпаргалка: Page Object Model (POM) в Playwright Java

### 🎯 Что это такое?
**Page Object Model** — это паттерн проектирования, который создает слой абстракции между вашими тестами и UI-элементами страницы. Вместо того чтобы писать «грязный» код с поиском селекторов прямо в тестах, вы создаете специальные классы (Pages), которые описывают структуру страницы и её поведение.

**Простыми словами:** Тест — это *что* мы проверяем (бизнес-логика). Page Object — это *как* мы это делаем (техническая реализация кликов и ввода текста).

---

### 🚀 Зачем это нужно? (The "Why")
1.  **Reusability (Повторное использование):** Один раз описали локатор кнопки «Login», используете его в 50 тестах.
2.  **Maintainability (Поддерживаемость):** Если разработчик изменил `id` у поля ввода, вы меняете его **в одном месте** (в Page Object), а не во всех теста/тестах.
3.  **Readability (Читаемость):** Тест превращается в читаемый сценарий: `loginPage.login(user, pass)`, вместо набора `page.locator("#user").fill(...)`.
4.  **Separation of Concerns (Разделение ответственности):** Тесты отвечают за проверки (Assertions), а страницы — за взаимодействие с UI.

---

### 🛠️ Как это реализовать правильно (Best Practices)

#### 1. Структура класса Page Object
Каждый класс страницы должен содержать:
*   **Поле `Page`:** Объект Playwright, через который идет всё взаимодействие.
*   **Locators:** Приватные поля с локаторами.
*   **Actions (Methods):** Публичные методы для действий (click, fill, etc.).

#### 2. Пример реализации (Java)

**Класс страницы (`LoginPage.java`):**
```java
import com.microsoft.playwright.Page;
import com.microsoft.playwright.Locator;

public class LoginPage {
    private final Page page;
    // Локаторы объявляем как поля класса
    private final Locator usernameInput;
    private final Locator passwordInput;
    private final Locator loginButton;

    public LoginPage(Page page) {
        this.page = page;
        // Инициализируем локаторы в конструкторе
        this.usernameInput = page.locator("#user-name");
        this.passwordInput = page.locator("#password");
        this.loginButton = page.locator("#login-button");
    }

    // Метод-действие (Action)
    public void login(String user, String pass) {
        usernameInput.fill(user);
        passwordInput.fill(pass);
        loginButton.click();
    }

    // Переход на другую страницу (Fluent Interface)
    public DashboardPage navigateToDashboard() {
        return new DashboardPage(page);
    }
}
```

**Класс теста (`LoginTest.java`):**
```java
import org.junit.jupiter.api.Test;
import static com.microsoft/playwright/assertions.PlaywrightAssertions.assertThat;

public class LoginTest extends BaseTest { // Предположим, Setup в BaseTest
    @Test
    void shouldLoginSuccessfully() {
        LoginPage loginPage = new LoginPage(page);
        
        loginPage.login("standard_user", "secret_sauce");
        
        // Ассерты (проверки) ДОЛЖНЫ быть в тесте, а не в Page Object!
        assertThat(page).hasURL("https://www.saucedemo.com/inventory.html");
    }
}
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Где хранить Assertions?** 
    *   ❌ **Плохо:** Писать `assertThat(...)` внутри методов Page Object. Это делает страницу «умной» и труднотестируемой.
    *   ✅ **Хорошо:** Метод страницы возвращает состояние или объект, а тест проверяет его.
2.  **Fluent Interface (Цепочки вызовов):** 
    Чтобы тесты выглядели еще чище, делайте методы, которые возвращают `this` или следующий Page Object. Это позволяет писать: `loginPage.enterUser(u).enterPass(p).clickLogin();`.
3.  **Не перегружайте страницы:** 
    Если страница становится слишком большой (например, Header с кучей меню), выносите части интерфейса в отдельные компоненты (напр. `HeaderComponent.java`). Это называется **Component-Based Testing**.
4.  **Избегайте логики внутри Page Object:** 
    Страница не должна считать налоги или проверять математические формулы. Она только взаимодействует с DOM.

### ❓ FAQ (Часто задаваемые вопросы)

**Q: Можно ли использовать `ElementHandle` вместо `Locator` в Page Object?**
**A:** Нет! В Playwright всегда используйте `Locator`. Он обладает встроенным механизмом *Auto-waiting*, что избавляет вас от необходимости писать `Thread.sleep()` или ручные ожидания.

**Q: Что делать, если на странице много одинаковых элементов (например, список товаров)?**
**A:** Используйте параметры в методах Page Object. Например: `public ProductPage selectProductByName(String name)`. Внутри используйте `.filter({ hasText: name })`.

**L: Нужно ли инициализировать локаторы в конструкторе или прямо в полях?**
**A:** Лучше всего инициализировать их в конструкторе через `page.locator(...)`. Это гарантирует, что при создании объекта страницы у вас уже есть привязка к текущему контексту браузера.

**Q: Как организовать базовый класс для всех страниц?**
**A:** Создайте `BasePage`, в котором будет поле `protected final Page page;` и конструктор. Все остальные страницы будут наследоваться от него. Это уменьшит дублирование кода.

# 🧠 Тема: Base Test Class (Базовый класс тестов)

### 🛠 Что это такое?
**Base Test Class** — это «скелет» твоего фреймворка. Это родительский класс, от которого наследуются все твои тестовые классы. Его главная задача — инкапсулировать (спрятать) всю грязную работу по настройке инфраструктуры, чтобы в самих тестах ты видел только логику проверки бизнес-требований.

### 🎯 Основные задачи Base Class:
1.  **Управление жизненным циклом:** Запуск и остановка Playwright, браузера, контекста и страниц.
2.  **Изоляция (Isolation):** Гарантия того, что каждый тест начинается с «чистого листа» (без старых куки, кэша или сессий).
3.  **Конфигурация:** Чтение настроек (URL, таймауты, режим headless) из файлов (`.properties`, `.yaml`) или системных переменных.
4.  **DRY (Don't Repeat Yourself):** Чтобы не писать `@BeforeEach` в каждом новом классе.

### 🏗 Правильная архитектура (Senior approach)
Главная ошибка новичка — создавать один `Browser` и использовать его во всех тестах без пересоздания `BrowserContext`. Это приводит к **State Leakage** (утечке состояния), когда куки из Теста №1 влияют на Тест №/2.

**Золотой стандарт:**
*   `@BeforeAll`: Запускаем `Playwright` и `Browser` (это тяжелые операции, делаем один раз на весь прогон).
*   `@BeforeEach`: Создаем новый `BrowserContext` и новую `Page` (это легкие операции, обеспечивают чистоту каждого теста).
*   `@AfterEach`: Закрываем `Page` и `Context`.
*   `@AfterAll`: Закрываем `Browser` и `Playwright`.

### 💻 Пример реализации (Java + JUnit 5)

```java
import com.microsoft.playwright.*;
import org.junit.jupiter.api.*;
import java.util.Properties;

public class BaseTest {
    // Используем Protected, чтобы наследники имели доступ к объектам
    protected Playwright playwright;
    protected Browser browser;
    protected BrowserContext context;
те    protected Page page;

    // Настройки (в реальном проекте читаются из файла)
    private String baseUrl = "https://example.com";
    private boolean headless = true; 

    @BeforeAll
    static void launchBrowser() {
        // В идеале: инициализация Playwright и Browser через Singleton или Factory
        // Для простоты примера:
        Playwright playwrightInstance = Playwright.create();
        Browser browserInstance = playwrightInstance.chromium().launch(
            new BrowserType.LaunchOptions().setHeadless(true)
        );
        // В реальном Senior-коде мы бы сохранили эти объекты в статические поля или через DI (Guice/Spring)
    }

    @BeforeEach
    void setup() {
        // Каждый тест получает свой контекст — это КЛЮЧ к стабильности
        playwright = Playwright.create(); 
        browser = playwright.chromium().launch(new BrowserType.LaunchOptions().setHeadless(headless));
        context = browser.newContext(); // Чистый профиль, новые куки
        page = context.newPage();
        page.navigate(baseUrl);
    }

    @AfterEach
    void tearDown() {
        if (context != null) context.close();
        if (browser !=/ null) browser.close();
        if (playwright != null) playwright.close();
    }
    
    // В реальном проекте @BeforeAll и @AfterAll управляют Browser, 
    // а @BeforeEach/@AfterEach — Context и Page.
}
```

### ⚠️ Нюансы и «подводные камни»

1.  **Thread Safety (Потокобезопасность):** Если ты планируешь запускать тесты параллельно (в JUnit 5 это делается через `junit.jupiter.execution.parallel.enabled`), обычные поля класса не сработают — потоки будут перезаписывать `page` друг друга.
    *   *Решение:* Используй `ThreadLocal<Page>`, `ThreadLocal<BrowserContext>` и т.д.
2.  **Resource Leaks (Утечки ресурсов):** Если тест упадет на середине, а ты не закрыл браузер в `@AfterEach`, процесс Chrome может остаться висеть в памяти сервера. Всегда делай закрытие ресурсов.
3.  **Heavy Setup:** Не пихай в `BaseTest` логику авторизации через UI. Это замедляет тесты. Для авторизации используй `storageState` (сохранение куки один раз и подгрузку их во все новые контексты).

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему нельзя использовать один `BrowserContext` для всех тестов?**
**О:** Потому что если Тест №1 залогинится или удалит товар из корзины, Тест №2 увидит это. Это сделает твои тесты зависимыми друг от друга (Flaky tests), и их будет невозможно запускать параллельно.

**В: Где лучше хранить URL и настройки?**
**О:** Никогда не хардкодь их в `BaseTest`. Используй `.properties` или `.yaml` файлы. Это позволит менять окружение (Dev/Staging/Prod) без перекомпиляции кода.

**В: Что если я хочу использовать Page Object Model (POM)?**
**О:** Твои классы страниц (например, `LoginPage`) будут принимать объект `Page` в конструкторе. В тестах ты будешь делать так: `LoginPage loginPage = new LoginPage(page);`. `BaseTest` предоставляет этот самый `page`.

**В: Как сделать запуск Headless-режима переключаемым?**
**О:** Через системную переменную. В коде: `boolean headless = Boolean.parseBoolean(System.getProperty("headless", "true"));`. При запуске в Maven: `-Dheadless=false`.

# 🧠 Шпаргалка: Data-Driven Testing (DDT) в Playwright Java

### 🎯 Суть метода
**Data-Driven Testing** — это подход, при котором логика теста отделена от данных. Вместо того чтобы писать 10 разных тестов для проверки 10 разных логинов, ты пишешь **один** тест, который прогоняется через **массив/файл с данными**.

**Зачем это Senior-у:**
*   **Масштабируемость:** Добавление нового кейса — это добавление строки в файл, а не написание кода.
*   **Чистота (DRY):** Код теста остается коротким и понятным.
*   **Покрытие:** Легко прогнать один сценарий через сотни комбинаций (граничные значения, спецсимволы, пустые поля).

---

### 🛠 Инструментарий в Java (JUnit 5 + Playwright)

В экосистеме Java основным инструментом для DDT является **JUnit 5**. Мы не используем циклы `for` внутри теста (это плохая практика, так как при падении на втором элементе цикл прервется), мы используем **параметризованные тесты**.

#### 1. Уровень "Junior": `@ValueSource` и `@CsvSource`
Подходит для простых типов (строки, числа) или когда данных мало.

```java
@ParameterizedTest
@CsvSource({
    "admin, password123, true",  // login, pass, expectedResult
    "user_1, wrong_pass, false",
    "'', error_pass, false"       // пустой логин
})
void loginTest(String user, String pass, boolean expected) {
    page.fill("#login", user);
    page.fill("#password", pass);
    page.click("#submit");
    // Проверка...
}
```

#### 2. Уровень "Middle": `@MethodSource` (Золотой стандарт)
Когда данные — это не просто строки, а сложные объекты (например, пользователь с набором прав и адресом). Ты выносишь логику генерации данных в отдельный метод.

```java
@ParameterizedTest
@MethodSource("provideUserCredentials")
void complexLoginTest(UserDto user) { // UserDto — твой кастомный POJO класс
    page.fill("#login", user.getUsername());
    // ...
}

// Метод-поставщик данных
static Stream<Arguments> provideUserCredentials() {
    return Stream.of(
        Arguments.of(new UserDto("admin", "p@ss", true)),
        Arguments.of(new UserDto("guest", "guest123", false))
    );
}
```

#### 3. Уровень "Senior": Внешние источники (JSON/CSV/Excel)
В реальных проектах данных слишком много, чтобы держать их в коде. Мы читаем их из внешних файлов. Для JSON идеально подходит библиотека **Jackson** или **Gson**.

*   **Схема:** Тест $\to$ Parser (Jackson) $\rightarrow$ `Stream<Arguments>`.
*   **Плюс:** Тестировщики (не программисты) могут править `.json` файл, не трогая Java-код.

---

### ⚠️ Нюансы и "Подводные камни" (Senior Insights)

1.  **Атомарность (Atomicity):** Каждый набор данных — это **отдельный тест**. Если упал кейс с `user_invalid`, тест для `user_admin` должен успешно выполниться. Используй именно `@ParameterizedTest`, а не `for`.
2.  **Подготовка данных (Data Setup):** DDT — это не только *чтение* данных, но и их *создание*. Если ты тестируешь удаление пользователя, твой тест должен сначала создать этого пользователя через API (используя `APIRequestContext` в Playwright), а потом уже запускать UI-тест.
3.  **Загрязнение среды (Data Pollution):** Если тесты используют одни и те же данные (например, один и тот же email), они могут конфликтовать при параллельном запуске. 
    *   *Решение:* Генерируй уникальные значения (UUID) или используй разные контексты (`BrowserContext`).
4.  **Слишком много данных:** Не пытайся запихнуть 10,000 строк в один `@ParameterizedTest`. Это превратит отчеты в "помойку". Для огромных объемов лучше использовать отдельные скрипты генерации.

---

### ❓ FAQ (Частые вопросы на интервью)

**В: Что делать, если один из наборов данных в DDT вызвал критическую ошибку (например, вылет браузера)?**
*   **О:** JUnit 5 по умолчанию пометит этот конкретный параметр как `Failed`, но остальные параметры продолжат выполняться. Это главное преимущество параметризации перед циклом `for`.

**В: Где лучше хранить данные: в коде или во внешнем файле?**
*   **О:** Если данных < 5 и они статичны — в коде (`@CsvSource`). Если данные меняются от релиза к релизу или их много — во внешнем JSON/CSV.

**В: Как обеспечить изоляцию данных при параллельном запуте Playwright тестов?**
*   **О:** Используй уникальные префиксы для создаваемых сущностей (например, `test_user_${UUID.randomUUID()}`) и всегда старайся чистить за собой (Cleanup) в методе `@AfterEach`.

**В: Можно ли использовать DDT для тестирования API вместе с UI?**
*   **О:** Да, это отличная практика. Ты можешь через API подготовить состояние системы (создать корзину товаров), а затем через Playwright проверить отображение этой корзины в UI, используя тот же набор данных.

# 🚀 Тема: Интеграция с CI/CD (Continuous Integration / Continuous Deployment)

Интеграция автотестов в CI/CD — это переход от режима «работает на моем компьютере» к режиму «работает в облаке/на сервере». В CI/CD нет монитора, нет мышки, и браузеры не установлены по умолчанию.

### 🛠 1. Главная проблема: Браузеры и зависимости
В отличие от Selenium, Playwright требует наличия своих бинарных файлов браузеров (Chromium, Firefox, WebKit). На чистом сервере (Jenkins, GitHub Actions) их нет.

**Senior Tip:** Никогда не полагайся на то, что браузер уже есть в системе. Твой пайплайн должен уметь устанавливать их сам.
*   **Решение через Maven:** Используй плагин или команду `mvn exec:java -e -Dexec.mainClass="com.microsoft.playwright.CLI" -Dexec.args="install"`. Это скачает нужные браузеры перед запуском тестов.

### 🐳 2. Docker — твой лучший друг
Чтобы избежать ада зависимостей (когда на Windows всё ок, а на Linux тесты падают из-за отсутствия библиотек `libgbm` и прочих), используй **Docker**.
*   **Решение:** Используй официальные образы от Microsoft: `mcr.microsoft.com/playwright/java:v1.xx.x-jammy`. В них уже предустановлены все браузеры и системные зависимости. Это делает твои тесты максимально переносимыми.

### 🖥 3. Headless Mode (Безголовый режим)
В CI/CD нет графического интерфейса (GUI). Тесты должны запускаться в режиме `headless: true`.
*   **Нюанс:** По умолчанию Playwright в Java часто настроен на headless, но всегда проверяй это в своем коде или конфиге. Если запустить `headless: false` на сервере без X11-сервера, тест упадет с ошибкой.

### 📊 4. Артефакты: Глаза инженера
Когда тест падает в Jenkins/GitHub Actions, ты не можешь «посмотреть», что случилось. Тебе нужны **артефакты**.
*   **Что сохранять:**
    1.  **Screenshots:** Скриншот в момент ошибки.
    2.  **Video:** Запись прохождения теста (очень помогает понять логику падения).
    3.  **Playwright Trace:** Самый важный артефакт (`trace.zip`). Это «черный ящик» самолета, где можно пошагово разобрать каждый клик и сетевой запрос.
*   **Как это работает в CI:** После завершения шага тестов в пайплайне должен стоять шаг `upload-artifact` (в GitHub Actions) или `archiveArtifacts` (в Jenkins).

### ⚙️ 5. Параллелизация и Sharding (Разделение)
Если у тебя 1000 тестов, запуск их по очереди в CI займет вечность.
*   **Sharding:** Современные инструменты позволяют разбивать тесты на части (шарды). Например, ты запускаешь 4 одинаковых контейнера, каждый из которых берет свою часть тестов. Это сокращает время выполнения в разы.

### 🔐 6. Конфигурация и Секреты
Никогда не хардкодь пароли, URL или ключи API в коде.
*   **Решение:** Используй переменные окружения (Environment Variables). В CI/CD (GitLab Secrets, GitHub Secrets) храни чувствительные данные и прокидывай их в тесты через `System.getenv("MY_PASSWORD")`.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему мои тесты проходят локально, но падают в Jenkins?**
**О:** Скорее всего, дело в одной из трех причин:
1. Не установлены браузеры (`playwright install` не был выполнен).
2. Не хватает системных библиотек (решение — Docker).
3. Разница в разрешениях экрана или скорости сети (в CI сеть может быть медленнее, используй `Web-First Assertions` для авто-ожидания).

**В: Как мне увидеть Trace Viewer, если тест упал в GitHub Actions?**
**О:** Ты должен настроить пайплайн так, чтобы файл `trace.zip` сохранялся как артефакт. После падения ты скачиваешь его и открываешь локально через команду `npx playwright show-trace path/to/trace.zip`.

**В: Можно ли запускать тесты параллельно на одном агенте?**
**О:** Да, Playwright Java поддерживает параллелизм на уровне потоков (Threads). Однако, если ресурсов (CPU/RAM) мало, это может привести к нестабильности (flaky tests). Лучше использовать масштабирование через разные контейнеры (Sharding).

**В: Как управлять разными окружениями (Dev, QA, Prod) в одном пайплайне?**
**О:** Используй параметры запуска Maven. Например: `mvn test -Denv=qa`. В коде Java считывай этот параметр и подставляй нужный базовый URL.
