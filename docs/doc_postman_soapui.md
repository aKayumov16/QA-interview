# 📑 Шпаргалка: Протокол HTTP/HTTPS

### 1. Что это такое?
**HTTP (HyperText Transfer Protocol)** — это протокол прикладного уровня, по которому клиент (браузер, мобильное приложение, Postman) общается с сервером. Это «язык», на котором стороны просят данные и отдают их.

**HTTPS (HTTP Secure)** — это тот же HTTP, но завернутый в защищенный слой **TLS/SSL**. 
*   **Зачем?** Чтобы никто «по дороге» (Man-in-the-Middle) не мог прочитать твои пароли или подменить данные. Он шифрует трафик и проверяет подлинность сервера через сертификаты.

---

### 2. Модель взаимодействия: Request — Response
Взаимодействие всегда строится по циклу: **Клиент отправил запрос $\rightarrow$ Сервер обработал $\rightarrow$ Клиент получил ответ.**

#### А) Структура Запроса (Request)
1.  **Start Line (Стартовая строка):** Содержит Метод, URL и версию протокола. 
    *   *Пример:* `GET /api/v1/users HTTP/1.1`
2.  **Headers (Заголовки):** Метаданные. Кто мы, что хотим получить, в каком формате.
    *   `Content-Type`: тип данных в теле (например, `application/json`).
    *   `Authorization`: токены для доступа.
    *   `User-Agent`: информация о клиенте.
3.  **Body (Тело):** Сами данные (используется в POST, PUT, PATCH). В GET-запросах тела обычно нет.

#### Б) Структура Ответа (Response)
1.  **Status Line (Стартовая строка):** Версия протокола и **Status Code**.
    *   *Пример:* `HTTP/1.1 200 OK`
2.  **Headers (Заголовки):** Информация о сервере и ответе.
    *   `Server`: какой веб-сервер работает (Nginx, Apache).
    *   `Date`: время ответа.
    *   `Set-Cookie`: команда клиенту сохранить куку.
3.  **Body (Тело):** Данные, которые прислал сервер (JSON, XML, HTML-страница).

---

### 3. HTTP Методы (Глаголы)
*Важный нюанс для Senior: разделяй методы на **Safe** (не меняют состояние сервера) и **Idempotent** (повторный запрос дает тот же результат).*

| Метод | Описание | Safe? | Idempotent? |
| :--- | :--- — | :---: | :---: |
| **GET** | Получение данных. Не должен ничего менять на сервере. | ✅ Да | ✅ Да |
| **POST** | Создание нового ресурса (или отправка формы). | ❌ Нет | ❌ Нет |
| **PUT** | Полная замена ресурса. Если отправить 10 раз — результат будет тем же. | ❌ Нет | ✅ Да |
| **PATCH** | Частичное изменение ресурса (только одно поле). | ❌ Нет | ❌ Нет* |
| **DELETE**| Удаление ресурса. | ❌ Нет | ✅ Да |

*\*Примечание: PATCH технически не всегда идемпотентен, если логика метода подразумевает добавление данных к существующим.*

---

### 4. Коды ответов (Status Codes)
Их нужно знать «на зубок», чтобы мгновенно понимать, где ошибка.

*   **1xx (Informational):** «Подожди, процесс идет». Редко встречаются в тестировании API.
*   **2xx (Success):** «Все круто!».
    *   `200 OK`: Успех.
    *   `201 Created`: Ресурс успешно создан (часто после POST).
    *   `204 No Content`: Все ок, но серверу нечего тебе отправить (часто после DELETE).
*   **3xx (Redirection):** «Иди по другому адресу».
    *   `301 Moved Permanently`: Ресурс переехал навсегда.
    *   `304 Not Modified`: Используй кэш (данные не изменились).
*   **4xx (Client Error):** «Ты накосячил» (ошибка в запросе).
    *   `400 Bad Request`: Неверный синтаксис, ошибка в JSON.
    *   `401 Unauthorized`: Ты не представился (нужен логин/токен).
    *   `403 Forbidden`: Ты представился, но тебе сюда нельзя (нет прав).
    *   **`404 Not Found`**: Такого адреса не существует.
    *   `405 Method Not Allowed`: Метод (например, POST) запрещен для этого URL.
*   **5xx (Server Error):** «Я накосячил» (ошибка на стороне бэкенда).
    *   `500 Internal Server Error`: Общий код ошибки в коде сервера (баг).
    *   `502 Bad Gateway`: Проблема с прокси-сервером или шлюзом.
    *   `503 Service Unavailable`: Сервер перегружен или на техработах.

---

### 💡 Нюансы от Senior'а

1.  **Stateless (Без сохранения состояния):** HTTP — это протокол без памяти. Каждый запрос — как первый раз. Сервер не помнит, что ты делал секунду назад. Чтобы «узнать» пользователя, мы используем **Cookies** или **Tokens (JWT)**.
2.  **Idempotency (Идемпотентность):** Это критически важно для надежности систем. Если сетевой сбой прервал запрос `PUT`, ты можешь безопасно повторить его. Но если ты повторишь `POST` (например, на оплату заказа), ты можешь создать дубликат транзакции.
3.  **Разница между 401 и 403:** Это классика. **401** — «Я не знаю, кто ты» (проблема с аутентификацией). **403** — «Я знаю, кто ты, но тебе сюда нельзя» (проблема с авторизацией/правами).

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Чем отличается GET от POST?**
О: GET передает параметры прямо в URL (видимы всем), а POST передает данные в теле запроса (скрыты от глаз в URL, но доступны в трафике). GET предназначен для чтения, POST — для изменения состояния.

**В: Что такое SSL/TLS Handshake?**
О: Это процесс «рукопожатия» между клиентом и сервером при установке HTTPS-соединения, в ходе которого они договариваются о ключах шифрования и проверяют сертификаты.

**В: Может ли GET-запрос иметь Body?**
О: Технически — да (протокол это не запрещает), но архитектурно — это плохая практика. Многие серверы и прокси просто проигнорируют или отбросят тело в GET-запросе. Всегда используй POST/PUT для передачи данных в теле.

**В: Почему 404 — это ошибка клиента, а не сервера?**
О: Потому что клиент запросил ресурс по адресу, которого не существует. Ошибка в том, что *клиент* указал неверный путь.

# 🚀 Шпаргалка: Методы HTTP

**HTTP-методы (или глаголы)** — это инструкции для сервера, которые говорят ему, какое действие нужно совершить над конкретным ресурсом (URL). 

В основе современной разработки лежит принцип **REST**, где каждый метод имеет строго определенную роль.

### 1. Основные методы (The Big Five)

| Метод | Действие | Безопасный? | Идемпотентный? | Тело запроса (Body) |
| :--- | :--- | :---: | :---: | :---: |
| **GET** | Получение данных | ✅ Да | ✅ Да | ❌ Нет |
| **POST** | Создание нового ресурса | ❌ Нет | ❌ Нет | ✅ Да |
| **PUT** | Полное обновление (замена) | ✅ Да | ✅ Да | ✅ Да |
| **PATCH** | Частичное обновление | ❌ Нет | ❌ Нет | ✅ Да |
| **DELETE** | Удаление ресурса | ✅ Да | ✅ Да | ❌ Редко |

---

### 🔍 Разбор нюансов (Senior Level)

#### 🛡️ Понятие "Безопасный метод" (Safe Methods)
Метод считается **безопасным**, если он **не изменяет состояние сервера**. Он только читает данные. 
*   *Пример:* `GET` не должен менять пароль пользователя или удалять запись в базе. Если твой `GET`-запрос при выполнении меняет что-то в БД — это грубейшая ошибка архитектуры.

#### 🔄 Понятие "Идемпотентность" (Idempotency)
Это критически важная тема. Метод **идемпотентен**, если повторный вызов того же самого запроса дает **тот же результат на сервере**, что и первый вызов.
*   **PUT (Идемпотентный):** Если ты 10 раз отправишь запрос «установи имя пользователя = Иван», результат будет один и тот же — имя будет «Иван».
*   **POST (НЕ идемпотентный):** Если ты 10 раз нажмешь кнопку «Оплатить заказ» (отправив POST), сервер может создать 10 разных транзакций и списать деньги 10 раз. **Это именно то, почему нельзя просто так спамить POST-запросами.**

#### 🛠️ PUT vs PATCH: В чем реальная разница?
*   **PUT** — это **замена**. Ты должен прислать *весь* объект целиком. Если ты отправишь только поле `email` через `PUT`, все остальные поля объекта (имя, фамилия, возраст) могут затереться или стать `null`.
*   **PATCH** — это **косметический ремонт**. Ты присылаешь только то поле, которое хочешь изменить.

#### 🔍 Вспомогательные методы
*   **HEAD:** Почти то же самое, что `GET`, но сервер возвращает **только заголовки (headers)**, без тела. Полезно, чтобы проверить размер файла (`Content-Length`) или живой ли URL, не скачивая сам файл.
*   **OPTIONS:** Спрашивает у сервера: «А какие методы ты поддерживаешь для этого URL?». Незаменим в **CORS** (Cross-Origin Resource Sharing), когда браузер проверяет права доступа перед основным запросом.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Можно ли передавать тело (body) в GET-запросе?**
**О:** Технически — стандарт HTTP не запрещает это жестко, но **практически — нельзя**. Многие прокси-серверы, кэши и даже некоторые библиотеки могут просто отрезать `body` из `GET`-закрепления. Всегда используй Query Parameters для передачи данных в GET.

**В: Является ли метод DELETE идемпотентным?**
**О:** **Да.** Если ты удалил пользователя с ID 1, то первый запрос вернет `204 No Content` (успех), а второй запрос на тот же ID вернет `404 Not Found`. Но *состояние сервера* не изменилось: пользователь всё так же удален. Результат для системы один.

**В: В чем разница между POST и PUT, если оба могут создавать данные?**
**О:** Разница в **контроле над URL**. 
При `POST` ты отправляешь запрос на `/users` (коллекцию), а сервер сам решает, какой ID присвоить новому юзеру. 
При `PUT` ты часто обращаешься к конкретному адресу, например `/users/123`. Если пользователя с таким ID нет, `PUT` может его создать, но именно по этому адресу.

**В: Что такое "Safe" и "Idempotent" простыми словами?**
**О:** 
*   **Safe** = «Я ничего не ломаю и не меняю, я просто смотрю».
*   **Idempotent** = «Сколько бы раз я ни нажимал на кнопку, результат в базе данных будет одинаковым».

# 📑 Шпаргалка: HTTP Status Codes (Коды ответов)

**HTTP Status Code** — это трехзначное число, которое сервер отправляет клиенту (Postman, браузер, мобильное приложение), чтобы сообщить о результате выполнения запроса. 

Первая цифра определяет **класс ответа**. Мы делим их на 5 групп.

---

### 🟢 1xx: Informational (Информационные)
*Сервер принял запрос и продолжает процесс.*
В повседневном тестировании REST API встречаются редко, но полезно знать:
*   **101 Switching Protocols**: Используется при переходе с HTTP на WebSockets.

---

### 🔵 2xx: Success (Успех)
*Все прошло отлично. Запрос обработан правильно.*
*   **200 OK**: Стандарт успеха. Тело ответа содержит запрашиваемые данные.
*   **201 Created**: Успешно! Новый ресурс был создан (идеально для `POST` запросов). В ответе часто приходит ID нового объекта.
*   **204 No Content**: Успех, но **тела ответа нет**. Часто используется для `DELETE` или `PUT`, когда серверу нечего сказать, кроме «Ок, я удалил/обновил».

> **💡 Senior Nuance:** Если ты тестируешь `POST` и получаешь `200` вместо `201` — это не критическая ошибка, но нарушение семантики REST. Хороший API должен возвращать `201`.

---

### 🟡 3xx: Redirection (Перенаправление)
*Клиенту нужно предпринять дополнительные действия, чтобы получить ресурс.*
*   **301 Moved Permanently**: Ресурс навсегда переехал на новый URL.
*   **3://304 Not Modified**: Означает, что ресурс не менялся с момента последнего запроса. Используется для **кэширования**. Если видишь этот код — значит, браузер/клиент использует старую копию данных из кэша.

---

### 🔴 4xx: Client Error (Ошибка клиента)
*Ты (или твой запрос) виноват. Неправильные данные, неверный путь или отсутствие прав.*
*   **400 Bad Request**: «Я тебя не понимаю». Ошибка в синтаксисе JSON, пропущен обязательный параметр или передано неверное значение типа.
*   **401 Unauthorized**: «Предъяви паспорт». Ты не авторизован (не передал токен или токен протух). **Важно:** этот код не значит, что у тебя нет прав, он значит, что система тебя не знает.
*   **403 Forbidden**: «Тебе сюда нельзя». Ты авторизован, но у тебя **нет прав** на это действие (например, обычный пользователь пытается удалить админа).
*   **404 Not Found**: «Этого не существует». Неверный URL или ID ресурса.
*   **405 Method Not Allowed**: Ты пытаешься сделать `POST` там, где разрешен только `GET`.
*   **429 Too Many Requests**: «Притормози!». Слишком много запросов за короткий промежуток времени (Rate Limiting). Критично для тестирования безопасности и нагрузки.

---

### 💀 5xx: Server Error (Ошибка сервера)
*Ты всё сделал правильно, но сервер «сломался».*
*   **500 Internal Server Error**: Универсальная ошибка. В коде бэкенда что-то упало (NullPointerException, ошибка БД и т.д.). Самый плохой код для QA.
*   **502 Bad Gateway**: Проблема в инфраструктуре. Один сервер (например, Nginx) получил некорректный ответ от другого сервера (бэкенда).
*   **503 Service Unavailable**: Сервер временно не может обрабатывать запросы (на техработах или перегружен).
*   **504 Gateway Timeout**: Прокси-сервер слишком долго ждал ответа от бэкенда. Время ожидания истекло.

---

### 🧠 FAQ: Вопросы на собеседовании

**1. В чем разница между 401 и 403?**
*   **Ответ:** 401 (Unauthorized) — это про **аутентификацию** (кто ты?). Сервер не знает, кто ты такой. 403 (Forbidden) — это про **авторизацию** (что тебе можно?). Сервер знает, кто ты, но запрещает это действие.

**2. Что должен вернуть API после успешного удаления ресурса (`DELETE`)?**
*   **Ответ:** В идеале `204 No Content` (если тело не нужно) или `200 OK` с подтверждающим сообщением в JSON.

**3. Если ты видишь 504 Gateway Timeout, на что ты будешь проверять?**
*   **Ответ:** Я буду смотреть на время выполнения запроса (Response Time). Скорее всего, бэкенд выполняет слишком тяжелую операцию (например, сложный SQL-запрос), которая не укладывается в тайм-аут прокси-сервера.

**4. Можно ли использовать 200 OK для ошибки?**
*   **Ответ:** Технически — да, это не нарушит протокол, но это **плохая практика**. Если в теле ответа написано `{"error": "failed"}`, но статус `200`, это затрудняет автоматизацию тестирования и работу систем мониторинга. Правильно — отдавать 4xx.

# 📑 Шпаргалка: Структура HTTP-запроса

Представь, что HTTP-запрос — это **посылка**, которую ты отправляешь по почте. Чтобы она дошла и её правильно обработали, у неё должен быть адрес, описание содержимого и само содержимое.

Любой запрос состоит из трёх основных частей: **Request Line**, **Headers** и **Body**.

---

### 1. Request Line (Первая строка запроса)
Это «заголовок» посылки. Она говорит серверу, что именно мы хотим сделать. Состоит из трех элементов:

*   **HTTP Method (Verb):** Команда. Что мы делаем? (`GET` — дай, `POST` — создай, `DELETE` — удали).
*   **URL / URI (Path):** Куда мы обращаемся? Путь к конкретному ресурсу на сервере.
    *   *Пример:* `/api/v1/users/42`
*   **HTTP Version:** Протокол, по которому общаемся. Сейчас стандарт — `HTTP/1.1`, но уже активно внедряется `HTTP/2`.

> **Пример строки:** `GET /api/v1/users?id=10 HTTP/1.1`

---

### 2. Headers (Заголовки)
Это «метаданные» запроса. Информация о самой посылке, её свойствах и инструкциях для сервера. Это пара **Key: Value**.

**Самые важные заголовки, которые нужно знать:**
*   **`Content-Type`**: Говорит серверу, в каком формате мы прислали данные в Body (например, `application/json` или `application/xml`). *Критически важно для POST/PUT.*
*   **`Accept`**: Говорит серверу: «Я хочу получить ответ именно в этом формате» (например, `application/json`).
*   **`Authorization`**: Твой «паспорт». Здесь передаются токены (`Bearer <token>`) или логин/пароль. Без него тебя не пустят к защищенным данным.
*   **`User-Agent`**: Информация о том, какой клиент делает запрос (браузер, Postman, скрипт на Python). Полезно для аналитики и блокировки ботов.
*   **`Cookie`**: Передача сессионных данных (чтобы сервер «узнал» тебя после логина).

---

### 3. Body (Тело запроса)
Это само «содержимое» посылки. Данные, которые ты передаешь серверу.

*   **Когда есть:** В методах `POST`, `PUT`, `PATCH`. Здесь лежат создаваемые или обновляемые объекты (например, JSON с данными нового пользователя).
*   **Когда нет:** В методах `GET` и `DELETE` тела обычно не бывает (хотя технически стандарт не запрещает GET с телом, на практике это считается плохим тоном и многие серверы его просто проигнорируют).

**Популярные форматы Body:**
1.  **JSON** (самый топ в REST) — `{ "name": "Ivan", "age": 25 }`
2.  **XML** — `<user><name>Ivan</name></user>`
3.  **Form-data** — используется для загрузки файлов или отправки простых форм.

---

### 💡 Senior Nuances (Нюансы, которые важно понимать)

1.  **Path Variables vs Query Parameters**:
    *   **Path Variable** (`/users/42`) — это часть адреса, указывает на конкретный ресурс (ID пользователя).
    *   **Query Parameter** (`/users?role=admin`) — это фильтр или уточнение. Он идет после знака `?`. Используется для поиска, сортировки и фильтрации.
2.  **Content-Type vs Accept**: Не путай! `Content-Type` — что **я** прислал. `Accept` — что **я хочу** получить в ответ. Если ты отправишь JSON, но забудешь указать `Content-Type: application/json`, сервер может выдать ошибку `415 Unsupported Media Type`.
3.  **Идемпотентность (Idempotency)**: Это свойство метода. Метод идемпотентен, если повторный запрос с теми же параметрами дает тот же результат, что и первый, и не меняет состояние сервера дополнительно.
    *   `GET`, `PUT`, `DELETE` — идемпотентны.
    *   `POST` — **не** идемпотентен (каждый новый POST может создавать новую запись в базе).

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Может ли у GET-запроса быть Body?**
**О:** Технически, спецификация HTTP это не запрещает, но на практике — **нет**. Многие прокси-серверы, кэши и даже сами веб-серверы могут просто отрезать тело из GET-запроса. Всегда используй Query Params для передачи данных в GET.

**В: В чем разница между PUT и PATCH?**
**О:** `PUT` — это полная замена ресурса. Ты должен прислать весь объект целиком. Если не пришлешь поле `age`, оно может затереться или стать null. `PATCH` — это частичное обновление (только то, что ты прислал).

****В: Что произойдет, если я не укажу Content-Type при отправке JSON?**
**О:** Сервер получит данные, но не поймет, как их распарсить (прочитать). Скорее всего, он вернет ошибку `415 Unsupported Media Type` или `400 Bad Request`.

# 📦 Шпаргалка: Форматы данных в API

Когда мы отправляем запрос через Postman или SoapUI, формат данных — это **контейнер**, в котором упакована твоя информация. Чтобы сервер понял, как «распаковать» твой пакет, крайне важно правильно указать заголовок `Content-Type`. Если ты отправишь JSON, а скажешь, что это XML — сервер выдаст ошибку (обычно 400 Bad Request или 415 Unsupported Media Type).

---

### 1. JSON (JavaScript Object Notation) — «Король API»
Самый популярный формат в REST. Легкий, быстрый и понятный человеку.

*   **Структура:** Пары `ключ: значение` и массивы `[...]`.
*   **Типы данных:** Строки (в двойных кавычках!), числа, булевы значения (`true`/`false`), объекты, массивы и `null`.
*   **Нюансы для Senior:**
    *   **Строгость к кавычкам:** Только **двойные** кавычки `"`. Одинарные `'` — это синтаксическая ошибка.
    *   **Запятые:** Лишняя запятая в конце последнего элемента (trailing comma) — классическая причина поломки парсеров.
    *   **Комментарии:** В стандартном JSON **нельзя** использовать комментарии. Если добавишь `//`, запрос может упасть.
    *   **Content-Type:** `application/json`.

### 2. XML (eXtensible Markup Language) — «Старая школа»
Основа для SOAP-сервисов. Более тяжеловесный, но очень мощный в плане структуры и проверок.

*   **Структура:** Иерархия тегов `<tag>...</tag>`.
*   **Преимущества:** Поддерживает сложные схемы (XSD), что позволяет проводить строгую валидацию данных на уровне структуры.
*   **Нюансы для Senior:**
    *   **Вес:** XML гораздо «шире» JSON из-за закрывающих тегов. Это увеличивает трафик.
    *   **Сложность парсинга:** Требует больше ресурсов процессора для обработки больших файлов.
    *   **Content-Type:** `application/xml` или `text/xml`.

### 3. Form-data (`application/x-www-form-urlencoded`) — «Классика веб-форм»
Так работают обычные HTML-формы на сайтах.

*   **Структура:** Данные передаются в виде строки `key1=value1&key2=value2`. Все спецсимволы (пробелы, &, =) должны быть заэкранированы (URL-encoded).
*   **Нюансы для Senior:**
    *   **Ограничение по объему:** Не подходит для передачи больших объемов текста или бинарных данных (картинок).
    *   **Безопасность:** Все данные видны в URL/теле запроса как открытый текст.

### 4. Multipart/form-data — «Транспорт для файлов»
Единственный адекватный способ отправить файл вместе с текстовыми полями в одном запросе.

*   **Структура:** Запрос разбивается на части (parts) с помощью специального разделителя — **boundary** (граница). Каждая часть может иметь свой собентственный `Content-Type`.
*   **Нюансы для Senior:**
    *   **Boundary:** В заголовке `Content-Type` обязательно должен быть указан уникальный идентификатор границы, например: `Content-Type: multipart/form-data; boundary=----WebKitFormBoundaryABC123`. Postman делает это автоматически.
    *   **Применение:** Используй этот формат всегда, когда нужно протестировать загрузку аватарок, документов или логов.

---

### 📊 Сводная таблица для быстрого сравнения

| Формат | Content-Type | Когда использовать? | Главный минус |
| :--- | :--- | :--- | :--- |
| **JSON** | `application/json` | Стандарт для REST API | Нет поддержки комментариев |
| **XML** | `application/xml` | SOAP, сложные корпоративные системы | Очень громоздкий (много лишнего текста) |
| **Form-url** | `application/x-www-form-urlencoded` | Простые текстовые поля, логин/пароль | Нельзя передать файлы |
| **Multipart**| `multipart/form-data` | Загрузка файлов + метаданные | Сложно читать «глазами» без инструментов |

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что будет, если я забуду указать Content-Type в Postman при отправке JSON?**
**О:** Сервер получит тело запроса, но не поймет, как его интерпретировать. Скорее всего, ты получишь `415 Unsupported Media Type` или `400 Bad Request`.

**В: В чем разница между `form-data` и `x-www-form-urlencoded`?**
**О:** `x-www-form-urlencoded` — это просто строка параметров (как в URL). `multipart/form-data` — это сложная структура с границами, которая позволяет «вкладывать» внутрь запроса файлы и другие типы данных.

**В: Как проверить валидность JSON в Postman?**
**О:** В разделе **Tests** напиши простую проверку: 
`pm.response.to.be.json;`. 
Если формат ответа не JSON, тест упадет. Для проверки структуры используй `pm.expect(jsonData).to.have.property('id');`.

**В: Почему XML считается менее производительным, чем JSON?**
**О:** Из-за избыточности тегов. Чтобы передать одно слово "Hello", в XML нужно написать `<msg>Hello</msg>` (15 символов), а в JSON — `{"m":"Hello"}` (13 символов). На миллионах запросов эта разница в объеме трафика и нагрузке на CPU становится критичной.

# 🧠 Шпаргалка: Заголовки (HTTP Headers)

### Что это такое?
Если представить HTTP-запрос как посылку, то **Body (тело)** — это сам товар внутри, а **Headers (заголовки)** — это накладная на коробке. В заголовках указано, кто отправил посылку, что внутри, в каком формате это упаковано и кому это можно открывать.

Заголовки передаются в двух направлениях:
1.  **Request Headers** (от клиента к серверу): «Я хочу получить данные в JSON», «Вот мой пароль».
2.  **Response Headers** (от сервера к клиенту): «Я отправил тебе картинку», «Не забудь сохранить этот ID в куки».

---

### 1. Основные Request Headers (Что мы настраиваем в Postman)

*   **`Content-Type`** — **Критически важный.** Говорит серверу, в каком формате пришло тело запроса.
    *   *Примеры:* `application/json`, `application/xml`, `text/plain`, `multipart/form-data`.
    *   *Нюанс:* Если ты отправляешь JSON, но забыл поставить `application/json`, сервер может выдать ошибку `415 Unsupported Media Type`.
*   **`Accept`** — Говорит серверу: «Я понимаю только такие форматы». 
    *   *Пример:* `application/json, text/plain`. Если сервер умеет отдавать и XML, и JSON, он выберет тот, что ты указал в Accept.
*   **`Authorization`** — Твой «пропуск» на сервер.
    *   *Виды:* `Bearer <token>` (самый частый для JWT), `Basic <credentials>` (логин:парокс в base64).
    *   *Нюанс:* Ошибки в одном символе токена приведут к `401 Unauthorized`.
*   **`User-Agent`** — Идентификация клиента. Показывает, кто делает запрос (браузер, Postman, или скрипт на Python). 
    *   *Зачем тестировать:* Иногда серверы блокируют запросы, если `User-Agent` подозрительный или пустой (защита от ботов).
*   **`Cookie`** — Передача сессионных данных. Содержит куки, которые клиент должен отправить обратно серверу для подтверждения сессии.

---

### 2. Основные Response Headers (На что смотрим в ответе)

*   **`Content-Type`** — Ответ сервера. Показывает, чем именно он тебя «угостил» (JSON, HTML, Image).
*   **`Set-Cookie`** — Инструкция от сервера: «Запомни этот ID, он тебе понадобится для следующего запроса». Именно этот заголовок наполняет твой `Cookie Jar` в Postman.
*   **`Server`** — Информация о ПО сервера (например, `nginx/1.18.0`). 
    *   *Нюанс:* С точки зрения безопасности, Senior-разработчики стараются скрывать точную версию сервера, чтобы хакерам было сложнее искать уязвимости.
*   **`Access-Control-Allow-Origin` (CORS)** — **Главная боль фронтенд-разработчиков.** Указывает, каким сайтам разрешено делать запросы к этому API. 
    *   *Нюанс:* Если здесь стоит конкретный домен, а ты стучишься с другого — получишь ошибку CORS в браузере (в Postman её не будет, так как Postman игнорирует политику CORS).
*   **`Cache-Control`** — Инструкция для браузера: «Можешь хранить этот ответ у себя 10 минут» или «Не кэшируй это вообще».

---

### 💡 Нюансы от Senior'а (На чем валятся джуны)

1.  **Регистронезависимость:** Заголовки `Content-Type` и `content-type` — это одно и то же. Но всегда лучше придерживаться стандарта (обычно с заглавными).
2.  **Зависимость от Body:** Никогда не меняй `Content-Type` без изменения формата тела запроса. Если в теле JSON, а в заголовке `text/plain`, парсер сервера может «упасть».
3.  **Скрытые заголовки:** Помни, что Postman сам добавляет некоторые заголовки (например, `Postman-Token`). Это нормально.
4.  **Безопасность:** Никогда не передавай пароли в заголовках, которые могут логироваться (хотя `Authorization` — стандарт, само тело пароля должно быть зашифровано внутри токена).

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `Accept` и `Content-Type`?**
**О:** `Content-Type` описывает формат **того, что ты посылаешь** (в теле запроса). `Accept` описывает формат **того, что ты хочешь получить** в ответ.

**В: Что такое ошибка 415 Unsupported Media Type?**
**О:** Это значит, что сервер получил данные, но не понимает их формат. Скорее всего, ты забыл или неправильно указал заголовок `Content-Type`.

**В: Почему в Postman запрос проходит, а в браузере (через JS) — нет?**
**О:** Скорее всего, дело в **CORS**. Браузер соблюдает политику безопасности и проверяет заголовок `Access-Control-Allow-Origin`. Postman — это инструмент для разработчиков/тестировщиков, он не является браузером и игнорирует эти ограничения.

**В: Как проверить наличие конкретного заголовка в тесте Postman?**
**О:** Используй скрипт в разделе Tests:
```javascript
pm.test("Проверка наличия заголовка Content-Type", function () {
    pm.response.to.have.header("Content-Type");
});
```

# 🛠 Тема: Интерфейс и Collections (Postman)

### 1. Интерфейс Postman: Основные зоны
Представь, что Postman — это твой пульт управления API. Весь экран делится на три ключевые части:

*   **Sidebar (Боковая панель):** Твой навигатор. Здесь живут коллекции, история запросов, окружения (Environments) и настройки. Если ты потерял запрос — ищи его в **History**.
*   **Request Builder (Рабочая область):** «Верстак», где ты собираешь запрос. 
    *   *Строка URL:* Куда летим.
    *   *Метод (GET, POST и т.д.):* Что делаем.
    *   *Вкладки (Tabs):* Самое важное. **Params** (параметры в URL), **Authorization** (права доступа), **Headers** (метаданные), **Body** (тело запроса — JSON/Form-data), **Pre-request Script** (код до запроса), **Tests** (код после запроса).
*   **Response Area (Зона ответа):** То, что прислал сервер. 
    *   Тут ты видишь **Status Code** (200 OK, 404 Not Found и т.д.), **Time** (задержка) и **Size**.
    *   Вкладки внутри ответа: **Pretty** (красивый JSON), **Raw** (сырой текст), **Preview** (рендеринг, если пришел HTML).

---

### 2. Collections (Коллекции): Сердце автоматизации
**Collection** — это не просто «папка с запросами». Это логически связанный набор запросов, который можно запускать целиком, настраивать для него общие правила и документировать.

**Структура коллекции:**
`Collection` $\rightarrow$ `Folders (Папки)` $\rightarrow$ `Requests (Запросы)`.

**Зачем они нужны (Senior level):**
1.  **Организация:** Группировка по фичам (например, «Auth Module», «User Profile», «Payments»).
2.  **Наследование:** Ты можешь прописать авторизацию на уровне всей коллекции, и она автоматически применится ко всем запросам внутри. Не нужно тыкать `Bearer Token` в каждом запросе!
3.  **Автоматизация (Collection Runner):** Ты можешь запустить всю коллекцию одной кнопкой, чтобы проверить, не «отвалилась» ли вся система после нового деплоя.
4.  **Передача знаний:** Коллекцию можно экспортировать в JSON и отдать коллеге или положить в Git вместе с кодом проекта.

---

### 💡 Нюансы (Senior Tips)

*   **Naming Convention (Именование):** Никогда не оставляй запросы типа `New Request 1`. Называй их по смыслу: `[POST] Create User`. Это сэкономит часы жизни твоей команде.
*   **Folders vs Collections:** Не плоди коллекции на каждый чих. Используй коллекции для крупных модулей, а папки — внутри них для разных сценариев (например, папка `Positive` и папка `Negative`).
le
*   **Documentation:** В Postman можно писать описание к каждому запросу и папке (Markdown!). Хороший Senior всегда документирует, что делает запрос и какие поля обязательны. Это превращает коллекцию в живую документацию API.
*   **Order of execution:** Помни, что при запуске коллекции через Runner, запросы идут строго сверху вниз по списку. Если твой второй запрос зависит от первого — они должны стоять в правильном порядке.

# 🚀 Шпаргалка: Работа с запросами (Requests)

Запрос — это основной инструмент коммуникации между клиентом (Postman/SoapUI) и сервером. Чтобы запрос прошел успешно, нужно правильно собрать его «анатомию».

### 1. Анатомия запроса
Любой HTTP-задержис состоит из четырех ключевых частей:

*   **URL (Endpoint):** Адрес, куда мы стучимся.
    *   `Base URL`: Корень API (например, `https://api.example.com`).
    *   `Path`: Конкретный путь к ресурсу (`/v1/users`).
*   **HTTP Method (Глагол):** Что мы хотим сделать с ресурсом.
*   **Headers (Заголовки):** Метаданные запроса (служебная информация).
*   **Body (Тело):** Сами данные, которые мы передаем (используется в POST, PUT, PATCH).

---

### 2. HTTP Методы (Глаголы)
Как Senior, я советую запомнить не только названия, но и понятие **идемпотентности** (способность запроса при многократном повторении давать тот же результат, что и один раз).

| Метод | Действие | Идемпотентный? | Комментарий |
| :--- | :--- | :--- | :--- |
| **GET** | Чтение | ✅ Да | Только получение данных. Не должен менять состояние сервера. |
| **POST** | Создание | ❌ Нет | Создает новый ресурс. При повторном нажатии создаст дубликат. |
| **PUT** | Обновление (замена) | ✅ Да | Заменяет ресурс целиком. Если прислать тот же объект, ничего не изменится. |
| **PATCH**| Частичное обновление| ❌ Нет* | Меняет только конкретные поля. (*Зависит от реализации*) |
‌| **DELETE**| Удаление | ✅ Да | Удаляет ресурс. Повторный запрос вернет ту же суть (ресурса уже нет). |

---

### 3. Параметры запроса (Params)
Различают два типа параметров, которые часто путают:

1.  **Path Variables (Переменные пути):** Часть самого URL. Используются для идентификации конкретного ресурса.
    *   *Пример:* `https://api.com/users/123` (где `12ary` — это ID).
2.  **Query Parameters (Параметры запроса):** Идут после знака `?`. Используются для фильтрации, сортировки или пагинации.
    *   *Пример:* `https://api.com/users?role=admin&sort=desc`

> **💡 Senior Nuance:** Никогда не «зашивай» (hardcode) ID в URL. Всегда используй переменные окружения (`{{userId}}`), иначе при смене стенда (с QA на Dev) тебе придется переписывать все запросы вручную.

---

### 4. Заголовки (Headers)
Это «конверт» вашего письма. Самые важные:
*   **Content-Type:** Говорит серверу, в каком формате лежат данные в Body (`application/json`, `application/xml`, `multipart/form-data`). **Если ошибиться здесь — получишь 415 ошибку.**
*   **Accept:** Говорит серверу, какой формат ответа мы хотим получить.
*   **Authorization:** Токен или логин/пароль для доступа (Bearer Token, Basic Auth).
*   **User-Agent:** Информация о том, кто делает запрос (Postman, Chrome и т.д.).

---

### 5. Тело запроса (Body)
Здесь лежат данные. Основные форматы:
*   **JSON:** Самый популярный сегодня. Структура `key: value`.
*   **XML:** Используется в SOAP. Строгая структура с тегами.
*   **form-data:** Используется для загрузки файлов или передачи данных, как из HTML-форм.
*   **x-www-form-urlencoded:** Простой формат «ключ=значение», часто используется для простых авторизаций.

---

### ⚠️ Подводные камни (Nuances)

1.  **Ошибка 415 Unsupported Media Type:** Ты прислал JSON, но забыл или ошибся в заголовке `Content-Type`. Сервер не понимает, как читать твой Body.
2.  **Разница между PUT и PATCH:** Если ты используешь **PUT** и забудешь прислать поле `email`, сервер может затереть старый email пустым значением (так как PUT — это полная замена). **PATCH** же просто обновит то, что ты прислал.
3.  **Скрытые символы:** При копировании Body из мессенджеров или Word могут прилететь невидимые символы или «кривые» кавычки (`“` вместо `"`). Это сломает JSON-парсер.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между Query Params и Path Variables?**
**О:** Path Variables используются для определения конкретного объекта (сущности), например, `/users/5`. Query Params используются для уточнения выборки: фильтрация (`?status=active`), сортировка или поиск.

**В: Что такое идемпотентность запроса? Почему это важно?**
**О:** Это свойство метода при повторном выполнении давать тот же результат, что и первый раз. Это критично для надежности систем: если из-за сбола сети запрос не дошел, мы можем безопасно его повторить (если метод идемпотентный), не боясь создать дубликат заказа или списать деньги дважды.

**В: Что произойдет, если я отправлю POST запрос с пустым Body, но укажу Content-Type: application/json?**
**О:** Сервер попытается распарсить пустой поток как JSON. В зависимости от реализации, ты получишь либо `400 Bad Request` (ошибка синтаксиса), либо ошибку валидации схемы данных.

# 🧠 Шпаргалка: Variables (Переменные) в Postman

**Переменная** — это именованный контейнер для данных. Вместо того чтобы хардкодить (вписывать вручную) URL, токены или ID пользователя в каждый запрос, мы используем «заполнители». Если завтра URL сервера изменится, тебе нужно будет поменять его **только в одном месте**, а не в сотне запросов.

## 1. Иерархия областей видимости (Scopes)
Это самый важный момент. В Postman переменные имеют разный «радиус действия». Когда ты обращаешься к переменной, Postman ищет её сверху вниз по списку (от самого узкого к самому широкому). Если он нашел совпадение в узком скоупе, он не пойдет смотреть в широкий.

| Уровень (Scope) | Где живет? | Для чего используем? |
| :--- | :--- | :--- |
| **1. Local** | Только внутри одного скрипта (в текущем запросе). | Временные расчеты, промежуточные значения в `pm.variables.set()`. |
| **try 2. Data** | Из внешних файлов (CSV/JSON) при запуске Collection Runner. | Тестирование разных наборов данных (параметризация). |
| **3. Environment** | В выбранном окружении (Dev, QA, Prod). | **Самый важный уровень.** URL базы, токены, ID пользователей для конкретной среды. |
| **4. Collection** | Внутри конкретной коллекции. | Общие настройки, которые одинаковы для всех запросов в этой папке. |
| **5. Global** | Доступны во всем Postman (во всех коллекциях). | Глобальные константы, которые не меняются от среды к среде. |

> **Senior Tip:** Соблюдай принцип **минимальной видимости**. Если переменная нужна только для одного запроса — используй Local или Collection. Не засоряй Global-область, иначе через месяц ты не вспомнишь, откуда взялось то или иное значение.

---

## 2. Как работать с переменными

### В интерфейсе (UI)
Для использования в URL, Headers или Body используется двойная фигурная скобка:
`{{variable_name}}`
*Пример:* `https://{{baseUrl}}/api/v1/users/{{userId}}`

### В скриптах (Pre-request / Tests)
В Postman мы используем объект `pm`. 

```javascript
// Чтение переменной (Postman сам найдет нужную по иерархии)
const baseUrl = pm.variables.get("baseUrl");

// Запись в разные уровни
pm.environment.set("token", "abc_123"); // В окружение (Environment)
pm.collectionVariables.set("userId", 45); // В коллекцию (Collection)
pm.globals.set("api_version", "v1");    // Глобально (Global)

// Локальная переменная (умрет сразу после завершения запроса)
pm.variables.set("tempId", 10); 
```

---

## 3. Важные нюансы (Pro-level)

1.  **Shadowing (Затенение):** Если у тебя есть переменная `url` в *Global* и такая же `url` в *Environment*, Postman возьмет значение из *Environment*. Это полезно: ты можешь переопределить глобальную настройку под конкретную задачу, не меняя её везде.
2.  **Безопасность:** **Никогда** не храни пароли, секретные ключи и токены в `Global` или `Collection` переменных, если планируешь делиться коллекцией с командой через Postman Cloud. Эти данные улетят в облако. Используй `Environment` (и не забудь выключить "Initial Value" для секретов).
3.  **Initial Value vs Current Value:** 
    *   *Initial Value:* Синхронизируется с облаком Postman и виден всем участникам команды.
    *   *Current Value:* Живет только у тебя локально. **Секреты (пароли) всегда клади в Current Value.**
4.  **Динамические переменные:** В Postman есть встроенные переменные, которые генерируют случайные данные: `{{$guid}}`, `{{$timestamp}}`, `{{$randomEmail}}`. Это маст-хэв для создания уникальных данных при каждом запуске теста.

## ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `pm.environment.set()` и `pm.collectionVariables.set()`?**
**О:** Разница в области видимости. Environment доступен только когда выбрано конкретное окружение. Collection Variables доступны всем запросам внутри этой коллекции, независимо от выбранного окружения.

**В: Что произойдет, если я попытаюсь использовать переменную, которой нет ни в одном из скоупов?**
**О:** Postman не выдаст ошибку в консоль, но в самом запросе вместо значения ты увидишь строку `{{variable_name}}` (как текст). Это верный признак того, что переменная не определена.

**Т: Как передать ID из ответа первого запроса во второй?**
**О:** В тесте первого запроса нужно написать: 
`pm.environment.set("newId", pm.response.json().id);`
А во втором запросе использовать `{{newId}}`. Это называется **Request Chaining**.

**В: Можно ли использовать переменные в названиях папок или коллекций?**
**О:** Да, Postman поддерживает использование переменных даже в именовании объектов, что позволяет делать динамические отчеты.

# 🧠 Шпаргалка: Environments (Окружения) в Postman

### 🎯 Что это такое?
**Environments** — это наборы переменных, которые позволяют тебе переключать контекст запросов одним кликом. 

Представь, что у тебя есть один и тот же набор тестов, но они должны бегать на трех разных серверах: `localhost` (твой комп), `dev-server` (разработка) и `production` (живой сайт). Вметь переписывать URL в каждом запросе вручную — это путь к ошибкам и потере времени. **Environments решают эту проблему.**

### 🛠 Как это работает?
Вместо того чтобы писать в поле URL: `https://api.qa-server.com/users`, ты пишешь: `{{baseUrl}}/users`.
*   `{{baseUrl}}` — это переменная.
*   Её значение берется из **активного окружения**.
*   Ты просто выбираешь в выпадающем списке сверху (Environment Selector) нужное окружение (`QA`, `Dev` или `Prod`), и Postman сам подставляет нужный адрес.

### 📂 Уровни переменных (Scope/Область видимости)
Это критически важный момент. Если ты создашь переменную в одном месте, она может "перекрыться" другой. Порядок приоритета (от самого слабого к самому сильному):

1.  **Global Variables:** Доступны всегда, независимо от выбранного окружения. Подходят для всего, что не меняется (например, имя пользователя).
2.  **Collection Variables:** Привязаны к конкретной коллекции. Удобно, если у тебя есть специфические данные только для одного набора тестов.
3.  **Environment Variables:** Самый важный уровень. Значения зависят от того, какое окружение ты выбрал.
4.  **Data Variables:** Приходят из внешних файлов (CSV/JSON) во время запуска через Newman. Имеют высший приоритет.

> **Senior Tip:** Если у тебя переменная `{{token}}` есть и в Global, и в Environment — Postman возьмет ту, что в **Environment**. Это называется *Variable Shadowing*.

### ⚠️ Главный нюанс: Initial Value vs Current Value
В Postman у каждой переменной окружения есть две колонки. На этом валятся все новички.

*   **Initial Value (Начальное значение):** Синхронизируется с облаком Postman и **виден всем твоим коллегам** в команде. 
    *   *Никогда не клади сюда пароли, токены или секретные ключи!*
*   **Current Value (Текущее значение):** Хранится только на твоей локальной машине. Он не улетает в облако.
    *   *Сюда мы пишем реальные токены и секреты.*

### 🚀 Best Practices (Как делать правильно)
1.  **Стандартизация имен:** Всегда называй переменные одинаково во всех окружениях. Если в `Dev` у тебя есть `{{baseUrl}}`, то и в `Prod` она должна называться точно так же, иначе тесты упадут.
2.  **Принцип "Чистого шаблона":** В `Initial Value` держи заглушки (например, `https://api.example.com`), а реальные рабочие данные — в `Current Value`.
*   **Не плоди лишнего:** Не создавай переменные для каждого чиха. Если значение не меняется от сервера к серверу — используй Global или Collection variables.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что произойдет, если я запущу запрос, но забуду выбрать Environment?**
**О:** Postman не найдет переменную `{{baseUrl}}` и подставит её как пустую строку или просто текст. Запрос уйдет на некорректный URL, и ты получишь ошибку (например, `404 Not Found` или `DNS Error`).

**В: Можно ли использовать несколько окружений одновременно?**

**В: Как программно (через скрипт) менять переменные окружения?**

Пример в Pre-request Script:

# 🔐 Тема: Authorization (Авторизация)

Прежде чем мы начнем, запомни золотое правило Senior-разработчика/тестировщика: **Authentication $\neq$ Authorization**.

*   **Authentication (Аутентификация):** «Ты кто такой?» (Проверка твоего паспорта).
*   **Authorization (Авторизация):** «Что тебе можно?» (Проверка твоего билета в VIP-ложу или только в общий зал).

В контексте API мы тестируем именно **второе**: имея валидный токен/пароль, может ли пользователь совершить действие, на которое у него нет прав.

---

### 🛠 Основные типы авторизации в API

#### 1. Basic Auth (Самый простой)
*   **Суть:** Ты передаешь `username` и `password`.
*   **Как работает:** Клиент берет строку `user:password`, кодирует её в **Base64** и отправляет в заголовке: `Authorization: Basic <base64_string>`.
*   **Нюанс:** Base64 — это **не шифрование**, это просто способ кодирования. Его легко декодировать. Использовать *только* через HTTPS!

#### 2. API Key (Ключ доступа)
*   **Суть:** Тебе выдают длинную секретную строку (ключ).
*   **Где передается:** Либо в заголовке (`x-api-key: my-secret-key`), либо в параметрах запроса (`?api_key=my-secret-key`).
*   **Нюанс:** Если ключ передается в URL (Query Params), он может остаться в логах сервера. Это дыра в безопасности. Всегда старайся использовать Headers.

#### 3. Bearer Token (JWT — самый популярный сейчас)
*   **Суть:** Ты один раз логинишься, получаешь "билет" (токен) и прикладываешь его к каждому запросу.
*   **Как работает:** Заголовок выглядит так: `Authorization: Bearint <token>`.
*   **Что такое JWT (JSON Web Token):** Это строка из трех частей (Header, Payload, Signature), разделенных точками. Внутри Payload зашита информация о пользователе и его правах.
*   **Нюанс:** Токен имеет срок жизни (**Expiration Time**). Если он протух — получишь 401.

#### 4. OAuth 2.0 (Сложный, но стандарт индустрии)
*   **Суть:** Протокол делегированной авторизации. Позволяет приложению получить доступ к данным пользователя на другом сервисе (как кнопка «Войти через Google»).
*   **Как работает в Postman:** В Postman есть встроенный помощник. Тебе нужно указать `Grant Type`, `Access Token URL`, `Client ID` и `Client Secret`. Postman сам сделает запрос, заберет токен и подставит его.

---

### 🚀 Как это автоматизировать в Postman (Senior Tips)

Не делай ошибку новичка — не вписывай токены руками в каждый запрос.

1.  **Используй уровни коллекций:** Настрой авторизацию на уровне всей **Collection**. В самих запросах выбери `Inherit auth from parent`. Если токен изменится, ты поменяешь его в одном месте.
2.  **Переменные окружения (Environments):** Храни токены в переменных типа `{{access_token}}`.
3.  **Автоматический Login (Chaining Requests):** 
    *   Создай отдельный запрос `Login`.
    *   В разделе **Tests** напиши скрипт, который вытаскивает токен из ответа и сохраняет его в переменную:
        ```javascript
        const jsonData = pm.response.json();
        pm.environment.set("access_token", jsonData.token);
        ```
    *   Теперь при каждом запуске коллекции тебе не нужно логиниться вручную.

---

### ⚠️ На что смотреть при тестировании (Edge Cases)

1.  **401 Unauthorized:** Проверяй, что происходит, когда токен неверный, отсутствует или истек.
2.  **403 Forbidden:** Это твой главный фокус. Проверяй, что пользователь с ролью `USER` не может вызвать метод `DELETE /admin/users`. Если смог — это баг авторизации.
3.  **Token Leakage:** Проверяй, не передается ли чувствительная информация в теле запроса или незашифрованном виде.
4.  **Scope Validation:** Если используешь OAuth, проверяй, что токен с ограниченным доступом (например, `read-only`) не позволяет делать `POST` запросы.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между кодами 401 и 403?**
**О:** 401 — "Я тебя не знаю" (проблема с аутентификацией/паспортом). 403 — "Я знаю, кто ты, но тебе сюда нельзя" (проблема с правами/визой).

**В: Можно ли передавать API Key в URL? Безопасно ли это?**
**О:** Не рекомендуется. URL сохраняются в истории браузера, в логах веб-серверов (Nginx/Apache) и прокси-серверах. Любой, кто имеет доступ к логам, украдет твой ключ.

**В: Что делать, если токен JWT истек во время прогона большого набора тестов?**
**О:** Нужно реализовать механизм "Refresh Token". В Postman это делается через `Pre-request Script`: скрипт проверяет срок действия (или просто делает запрос на обновление) перед выполнением основного запроса.

**В: Как проверить, что JWT токен не подделан?**
**О:** Проверить валидность подписи (Signature). На бэкенде это делает сервер, используя секретный ключ. В тестах ты можешь убедиться, что структура токена верна и он содержит нужные `claims` (поля).

# 🧠 Scripts (JavaScript) в Postman/SoapUI

Скрипты — это «мозги» твоего запроса. Если без скриптов Postman — это просто продвинутый браузер, то со скриптами — это полноценный инструмент автоматизации. В Postman всё строится на объекте `pm`, который предоставляет доступ к запросу, ответу и переменным.

В Postman есть две зоны для написания кода: **Pre-request Script** и **Tests**.

---

### 1. Pre-request Script (Подготовка)
**Суть:** Код выполняется **ДО** того, как запрос улетит на сервер.
**Зачем это нужно:**
*   Генерация динамических данных (случайные email, UUID, даты).
*   Вычисление подписей (HMAC, SHA) для авторизации.
*   Подготовка заголовков или параметров запроса.
*   Очистка переменных перед использованием.

**Пример:** Генерируем случайный email и сохраняем его в переменную окружения.
```javascript
// Генерируем случайное число
const randomNumber = Math.floor(Math.random() * 1000);

// Создаем строку с email
const dynamicEmail = `testuser_${randomNumber}@example.com`;

// Сохраняем в переменную окружения (Environment), чтобы использовать в Body запроса как {{user_email}}
pm.environment.set("user_email", dynamicEmail);

console.log("Сгенерированный email: " + dynamicEmail); 
```

---

### 2. Tests Script (Проверка)
**Суть:** Код выполняется **ПОСЛЕ** того, как пришел ответ от сервера.
**Зачем это нужно:**
*   Валидация статус-кода.
*   Проверка структуры JSON/XML.
*   Проверка значений в теле ответа (Business Logic).
*   Извлечение данных из ответа для следующего запроса (**Chaining Requests**).

**Структура теста:** Все проверки всегда оборачиваются в функцию `pm.test("Название теста", function() { ... });`. Внутри используется библиотека утверждений `pm.expect`.

**Пример:** Комплексная проверка ответа.
```javascript
// 1. Проверка статус-кода
pm.test("Статус код 200 OK", function () {
    pm.response.to.have.status(200);
});

// 2. Парсим JSON из ответа, чтобы работать с данными
const jsonData = pm.response.json();

// 3. Проверка конкретного поля в теле ответа
pm.test("Поле 'id' должно быть числом", function () {
    pm.expect(jsonData.id).to.be.a('number');
});

// 4. Проверка значения (например, имя пользователя)
pm.test("Имя пользователя совпадает с ожидаемым", function () {
    pm.expect(jsonData.name).to.eql("Admin");
});

// 5. Извлечение токена из ответа и сохранение его для следующих запросов
pm.test("Токен получен успешно", function () {
le  const token = jsonData.access_token;
    pm.collectionVariables.set("auth_token", token);
});
```

---

### 💡 Senior Nuances (Нюансы, о которых молчат в туториалах)

1.  **Scope (Области видимости):** Никогда не используй `pm.globals` для всего подряд. Это «грязный» способ. Если данные нужны только внутри одного набора тестов — используй `pm.collectionVariables`. Если меняются от сервера к серверу — `pm.environment`. Глобальные переменные замусоривают память и могут вызвать конфликты в параллельных запусках (Newman).
2.  **Parsing Error:** Всегда помни, что если сервер вернет не JSON (например, ошибку 502 Bad Gateway с HTML-страницей), то строка `pm.response.json()` **упадет с ошибкой** и прервет выполнение скрипта. Senior всегда добавляет проверку:
    ```javascript
    if (pm.response.code === 200) {
        const jsonData = pm.response.json();
        // ... логика
    }
    ```
3.  **Синхронность:** Скрипты в Postman выполняются последовательно. Ты не можешь запустить асинхронный `fetch` внутри теста и ждать его завершения через `await` (Postman sandbox ограничен).
4.  **Console Log:** Используй `console.log()` для отладки, но **удаляй или комментируй их перед пушем в репозиторий**. Оставлять логи в продакшн-коллекциях — плохой тон.

---

### ❓ FAQ (Частые вопросы на интервью)

**В: В чем разница между `pm.expect(val).to.eql(other)` и `pm.expect(val).to.equal(other)`?**
**О:** `eql` проверяет **глубокое равенство** (содержимое объектов и массивов), а `equal` проверяет строгое соответствие (включая ссылку на объект в памяти). Для JSON-ответов всегда используй `eql`.

**В: Как передать данные из одного запроса в другой?**
**О:** В **Tests** первого запроса мы записываем данные в переменную (`pm.environment.set("key", value)`), а во втором запросе обращаемся к ней через синтаксис двойных фигурных скобок `{{key}}` в URL, Headers или Body.

**В: Можно ли использовать внешние библиотеки в Postman?**
**О:** Да, но только те, что уже встроены в Sandbox (например, `crypto-js` для хеширования, `moment` для дат, `ajv` для валидации JSON Schema). Свою библиотеку через `npm install` подключить нельзя.

**В: Что такое Postman Sandbox?**
**О:** Это изолированная среда выполнения JavaScript внутри Postman. Она похожа на браузерный движок, но с ограниченным набором API (ты не можешь сделать прямой доступ к файловой системе компьютера).

# 🧠 Шпаргалка: Assertions (Проверки) в Postman

**Assertions** — это сердце автоматизации. Без них ты не тестируешь, а просто «смотришь на ответ». Проверка (assertion) — это логическое утверждение, которое должно быть **true**. Если оно **false**, тест считается проваленным (Failed).

В Postman под капотом используется библиотека **Chai.js**, поэтому синтаксис будет очень похож на неё.

---

### 1. Структура теста
Любая проверка в Postman состоит из двух уровней:
1.  `pm.test("Название теста", function () { ... })` — это оболочка, которая создает запись в отчете (Pass/Fail).
2.  `pm.expect(...)` — это сама логика проверки (суть утверждения).

```javascript
// Плохо: Ты не узнаешь, что именно упало в отчете
pm.expect(pm.response.code).to.equal(200); 

// Хорошо: В отчете будет написано "Статус код должен быть 200"
pm.test("Статус код должен быть 200", function () {
    pm.response.to.have.status(200);
});
```

---

### 2. Основные типы проверок

#### А. Статус-коды (Status Codes)
Самое базовое. Проверяем, что сервер ответил именно так, как мы ожидали.
*   `pm.response.to.have.status(200)` — конкретный код.
*   `pm.response.to.be.success` — проверка на любой 2xx код.
*   `pm.response.to.be.unauthorized` — проверка на 401.

#### Б. Время ответа (Response Time)
Критически важно для Performance-тестирования.
*   `pm.expect(pm.response.responseTime).to.be.below(500)` — ответ должен прийти быстрее, чем за 500 мс.

#### В. Тело ответа (JSON Body)
Здесь мы проверяем содержимое данных. Сначала парсим JSON: `const jsonData = pm.response.json();`

*   **Проверка значения:** `pm.expect(jsonData.id).to.eql(10);`
*   **Проверка типа данных:** `pm.expect(jsonData.name).to.be.a('string');` (важно для контрактного тестирования).
*   **Проверка наличия поля:** `pm.expect(jsonData).to.have.property('email');`
*   **Проверка в массиве:** `pm.expect(jsonData.items).to.include('Apple');`

#### Г. Заголовки и Cookies (Headers & Cookies)
*   `pm.response.to.have.header("Content-Type");`
*   `pm.expect(pm.response.headers.get("Content-Type")).to.contain("application/json");`

---

### 3. Senior Level: Продвинутые нюансы (Pro Tips)

#### 💎 JSON Schema Validation (Твой главный инструмент)
Проверять каждое поле по отдельности — это долго и неэффективно. Если API изменит тип данных в одном из 50 полей, ты пропустишь баг. Используй **JSON Schema**. Ты описываешь "шаблон" идеального ответа, и Postman проверяет весь объект целиком.

```javascript
const schema = {
    "type": "object",
    "required": ["id", "name"], // Обязательные поля
    "properties": {
        "id": { "type": "number" },
        "name": { "type": "string" }
    }
};

pm.test("Валидация схемы ответа", function () {
    pm.response.to.have.jsonSchema(schema);
});
```

#### 💎 Глубокое сравнение (`eql` vs `equal`)
*   `.to.equal(10)` — проверяет значение (примитивы).
*   `.to.eql({id: 1})` — **Deep Equality**. Проверяет содержимое объектов и массивов, заходя внутрь каждой вложенности. Если использовать `equal` для объектов, тест может упасть, даже если данные внутри одинаковые, из-за разницы ссылок в памяти.

#### 💎 Тестирование динамических данных (Regex)
Если поле содержит дату или случайный ID, ты не можешь проверить его на точное совпадение. Используй регулярные выражения.
*   `pm.expect(jsonData.email).to.match(/@gmail\.com$/);` — проверка, что почта заканчивается на @gmail.com.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что делать, если тест упал, но я не понимаю почему?**
**О:** Всегда используй `console.log()` перед проверкой. Выводи в консоль (`Ctrl + Alt + C`) то, что ты проверяешь: `console.log(jsonData.user_id);`. Без этого ты слеп.

**В: В чем разница между `to.have.property` и `to.include`?**
**О:** `property` используется для объектов (проверка ключа), а `include` — для массивов или строк (проверка наличия элемента/подстроки внутри).

**В: Можно ли в одном тесте (`pm.test`) написать 10 проверок?**
**О:** Технически — да. Но **Senior-совет**: не делай так. Если упадет первая проверка, остальные 9 даже не запустятся. Делай один `pm.test` на одну логическую проверку. Это сделает отчет чистым и понятным.

**В: Как проверить, что массив не пустой?**
**О:** `pm.expect(jsonData.items).to.not.be.empty;` или `pm.expect(jsonData.items.length).to.be.above(0);`

# 🚀 Cheat Sheet: Postman Dynamic Variables

### 💡 Что это такое?
**Dynamic Variables** — это встроенные в Postman «магические» переменные, которые генерируют случайные данные на лету при каждом нажатии кнопки **Send**. 

Тебе не нужно писать код на JavaScript, чтобы создать случайный email или GUID. Ты просто используешь синтаксис `{{$variableName}}`, и Postman сам подставляет туда новое значение. Это критически важно для создания **идемпотентных** тестов (когда каждый запуск теста создает новые данные, не конфликтуя с предыдущими).

### 🛠 Синтаксис
Все динамические переменные всегда начинаются с символа `$`:
`{{$randomEmail}}`, `{{$guid}}`, `{{$timestamp}}`

---

### 📂 Основные категории переменных

#### 1. Идентификаторы и числа (Identity & Numbers)
Используются, когда нужно создать уникальный объект или проверить обработку числовых диапазонов.
*   `{{$guid}}` — Генерирует уникальный UUID/GUID (идеально для `id` или `transactionId`).
*   `{{$randomInt}}` — Случайное целое число.
*   `{{$randomDecimal}}` — Случайное десятичное число.

#### 2. Персональные данные (Personal Info)
Используются для заполнения форм регистрации, профилей пользователей и т.д.
*   `{{$randomFirstName}}` / `{{$randomLastName}}` — Имя и фамилия.
*   `{{$randomEmail}}` — Валидный формат email.
*   `{{$randomPhoneNumber}}` — Случайный номер телефона.
*   `{{$randomAddress}}` / `{{$randomCity}}` — Адресные данные.
*   `{{$randomPassword}}` — Генерация пароля.

#### 3. Время и даты (Date & Time)
Важны для тестирования логов, сроков действия токенов или фильтров по датам.
*   `{{$timestamp}}` — Текущий Unix Timestamp.
*   `SS` / `MM` / `YYYY` — Можно использовать части текущего времени (в зависимости от версии и настроек).

#### 4. Текст и контент (Text & Content)
Для тестирования длины строк, кодировок или просто заполнения описаний.
*   `{{$randomWord}}` — Одно случайное слово.
*   `{{$randomPhrase}}` — Случайная фраза.
*   `{{$loremIpsum}}` — Классический текст "Lorem Ipsum" (полезно для проверки лимитов символов в БД).

---

### 🧠 Senior Nuances (Нюансы, о которых не пишут в туториалах)

1.  **Где их использовать:**
    *   **Body (JSON/XML):** Самое частое. `{"email": "{{$randomEmail}}"}`.
    *   **Params/Headers:** Если API требует уникальный `X-Request-ID` или `User-Agent`.
2.  **Проблема "Застывшего значения":** 
    Динамические переменные меняются **только в момент отправки запроса**. Если ты один раз записал `{{$randomEmail}}` в переменную окружения (Environment Variable) через скрипт, то значение внутри этой переменной зафиксируется. Чтобы оно обновлялось, нужно обращаться к динамической переменной напрямую в теле запроса.
3.  **Комбинирование:** 
    Ты можешь комбинировать их для создания сложных строк: `user_{{$randomInt}}_@test.com`. Это отличный способ избежать ошибок "Duplicate Entry" в базе данных.
4.  **Pre-request Script vs Dynamic Vars:** 
    Если тебе нужна сложная логика (например, email должен быть не просто случайным, а содержать текущую дату), динамических переменных будет мало. В этом случае используй `pm.variables.set()` в Pre-request Script.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Зачем использовать динамические переменные вместо обычного текста в теле запроса?**
**О:** Для обеспечения уникальности данных. Если ты будешь отправлять один и тот же `email` при каждом тесте, второй запуск упадет с ошибкой `400 Bad Request (Duplicate User)`. Динамические переменные решают проблему конфликта данных.

**В: Можно ли использовать динамические переменные внутри Pre-request Script?**
**О:** Напрямую — нет, ты не можешь обратиться к ним как к объекту JavaScript. Но ты можешь использовать их в строках или через `pm.variables.replaceIn('{{$randomEmail}}')`.

**В: Что делать, если мне нужно протестировать негативный сценарий (например, слишком длинный email)?**
**О:** Динамические переменные не подходят для этого, так как они генерируют "валидные" данные. Для негативных тестов тебе придется использовать либо фиксированные значения, либо писать кастомный скрипт в Pre-request Script, который генерирует строку сверх лимита.

# 🔗 Chaining Requests (Цепочки запросов)

**Chaining Requests** — это процесс использования данных, полученных из ответа одного запроса, в качестве входных данных для следующего запроса. Это «клей», который превращает набор разрозненных запросов в полноценный сквозной (End-to/E2E) тест-сценарий.

### 🛠 Как это работает (Алгоритм)
Процесс всегда состоит из трех шагов:
1.  **Выполнение запроса А:** Получаем ответ от сервера.
2.  **Извлечение и сохранение:** С помощью скрипта в разделе `Tests` достаем нужное значение из JSON/XML и записываем его в **переменную** (Environment или Collection).
3.  **Использование в запросе Б:** В URL, Body или Headers запроса Б подставляем эту переменную через синтаксис `{{variable_name}}`.

---

### 💻 Практический пример: Сценарий "Регистрация и Проверка"

Представь, что нам нужно: **Создать пользователя $\rightarrow$ Получить его ID $\rightarrow$ Удалить его.**

#### Шаг 1: POST `/users` (Создание)
В этом запросе мы создаем юзера. Нам нужно вытащить `id`, который сгенерировал сервер.

**Вкладка `Tests`:**
```javascript
// 1. Парсим JSON ответа
const responseData = pm.response.json();

// 2. Проверяем, что запрос прошел успешно (Best Practice!)
pm.test("Status code is 201", function () {
    pm.response.to.have.status(201);
});

// 3. Извлекаем ID и сохраняем в переменную окружения (Environment)
if (responseData.id) {
    pm.environment.set("new_user_id", responseData.id);
    console.log("ID успешно сохранен: " + responseData.id);
} else {
    console.error("Ошибка: ID не найден в ответе!");
}
```

#### Шаг 2: GET `/users/{{new_user_id}}` (Проверка)
Теперь мы используем переменную прямо в URL. Postman сам подставит значение вместо `{{new_user_id}}`.

#### Шаг 3: DELETE `/users/{{new_user_id}}` (Очистка)
Завершаем сценарий, удаляя созданного пользователя.

---

### ⚠️ Нюансы и Senior-советы (Pro Tips)

1.  **Scope (Область видимости):** 
    *   Используй `pm.environment.set` для данных, зависящих от окружения (URL, токены).
    *   Используй `pm.collectionVariables.set` для данных внутри одного сценария (ID пользователя, временные токены). 
    *   **Избегай `pm.globals.set`**, если это не критично — глобальные переменные засоряют память и могут привести к конфликтам в больших проектах.

2.  **Обработка ошибок (Error Handling):** Всегда проверяй, пришел ли ID. Если ты попытаешься сохранить `undefined`, следующий запрос упадет с невнятной ошибкой. Пиши `if (responseData.id) { ... }`.

3.  **Типы данных:** Помни, что Postman сохраняет все переменные как **строки**. Если тебе нужно использовать ID для математических операций или сравнения с числом, используй `Number()` или `parseInt()`.
    *   *Пример:* `pm.environment.set("id_num", Number(responseData.id));`

4.  **Очистка за собой (Cleanup):** Хороший тон — после завершения цепочки (в последнем запросе) удалять временные переменные, чтобы не оставлять «мусор» в окружении.
    *   `pm.environment.unset("new_user_id");`

5.  **Проверка структуры:** Перед тем как доставать значение, убедись, что путь к нему верный (особенно если JSON глубоко вложенный: `responseData.data.user.attributes.id`).

# 🚀 Шпаргалка: Data-Driven Testing (DDT) в Postman

**Data-Driven Testing (DDT)** — это подход в тестировании, когда один и тот же сценарий (коллекция запросов) запускается многократно, но с разными входными данными. Вместо того чтобы создавать 100 запросов для проверки 100 разных пользователей, ты создаешь **один** запрос и подкладываешь к нему **файл с данными**.

### 🛠 Основная механика
Суть DDT держится на «трех китах»:
1.  **Template (Шаблон):** Твоя коллекция запросов в Postman, где вместо реальных значений стоят переменные вида `{{username}}`.
2.  **Data Source (Источник данных):** Внешний файл (CSV или JSON), содержащий таблицу с данными.
3.  **Runner (Исполнитель):** Инструмент (Collection Runner или Newman), который берет строку из файла $\rightarrow$ подставляет её в шаблон $\rightarrow$ запускает запрос $\rightarrow$ переходит к следующей строке.

---

### 📋 Подготовка данных

#### Вариант А: JSON (Рекомендуемый)
Лучший выбор, если у тебя сложные структуры или массивы.
*   **Структура:** Массив объектов.
*   **Плюс:** Поддерживает вложенность и разные типы данных (числа, булевы значения).

```json
[
  {"id": 1, "user": "admin", "status": "active"},
  {"id": 2, "user": "guest", "status": "inactive"}
]
```

#### Вариант Б: CSV
Идеально для простых плоских таблиц (как Excel).
*   **Структура:** Первая строка — заголовки (это и есть имена твоих переменных в Postman).
*   **Плюс:** Легко редактировать и генерировать из Excel/Google Sheets.

```csv
id,user,status
1,admin,active
2,guest,inactive
```

---

### 🚀 Пошаговый алгоритм реализации

1.  **Создай переменные в запросе:** В URL, Headers или Body используй синтаксис `{{variable_name}}`. Имя должно **строго совпадать** с заголовком в CSV или ключом в JSON.
2.  **Напиши тесты (Assertions):** Тесты должны быть универсальными. Не проверяй `status == "active"`, проверяй `pm.expect(pm.response.json().status).to.eql(pm.iterationData.get("status"))`.
3.  **Запусти Collection Runner:**
    *   Выбери коллекцию.
    *   Нажми кнопку **Select File** и выбери свой CSV/JSON.
    *   **Важно:** Проверь, что Postman правильно определил количество итераций (Iterations).
4.  **Нажми Run.**

---

### 🧠 Нюансы от Senior (то, о чем не пишут в туториалах)

1.  **`pm.iterationData.get()` vs `pm.variables.get()`:**
    *   Когда ты используешь файл, данные попадают в область видимости **Iteration Data**. 
    *   Если ты хочешь обратиться к ним в скриптах (Tests/Pre-request), лучше использовать `pm.iterationData.get("key")`. Это гарантирует, что ты берешь данные именно из файла, а не из окружения (Environment).

2.  **Проблема типов данных в CSV:**
    *   CSV — это всегда текст. Если в файле написано `10`, Postman может прочитать это как строку `"10"`. Если твой API ждет число (`Integer`), запрос упадет. 
    *   *Решение:* В Pre-request Script делай приведение типов: `let userId = Number(pm.iterationData.get("id"));`.

3.  **Отладка (Debugging) при массовом запуске:**
    *   Когда у тебя 500 итераций, найти, на какой именно строке упал тест, — ад.
    *   *Совет:* Используй `console.log` в скриптах. При запуске через Newman или в Runner открывай Console. Также старайся делать максимально информативные сообщения об ошибках в тестах: `pm.expect(res, "Failed on user: " + pm.iterationData.get("user")).to.equal(...)`.

4.  **Кодировка:**
    *   Если в данных есть кириллица, всегда сохраняй CSV в кодировке **UTF-8**. Иначе вместо имен ты получишь «кракозябры» и упавшие тесты.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что лучше использовать: JSON или CSV?**
**О:** Если данные плоские (просто список пользователей/товаров) — **CSV**. Это быстрее и удобнее для коллег-менеджеров. Если нужно передавать сложные объекты, массивы или вложенные структуры — только **JSON**.

**В: Как протестировать сценарий, где один запрос зависит от данных другого запроса, но всё равно использовать DDT?**
**О:** Это называется "Hybrid DDT". Ты используешь файл для базовых параметров (например, `userId`), а в Pre-request Script пишешь логику, которая берет этот `userId`, делает предварительный запрос за токеном и сохраняет его в переменную окружения.

**В: Что делать, если я хочу запустить только часть данных из файла?**
**О:** В Runner есть поле **Iterations**. Если в файле 100 строк, но ты хочешь проверить только первые 5, укажи `5` в поле Iterations. Но помни: Postman начнет с первой строки файла.

**В: Можно ли использовать DDT в Newman (CLI)?**
**О:** Да, это стандарт индустрии для CI/CD. Команда выглядит так:
`newman run my_collection.json -d my_data_file.csv`

# 🚀 Шпаргалка: Newman (Postman CLI)

**Newman** — это мощный инструмент командной строки (CLI), который позволяет запускать коллекции Postman без использования графического интерфейса (GUI). Если Postman — это твой «лабораторный стенд» для ручного тестирования, то Newman — это твой «двигатель» для автоматизации и встраивания тестов в CI/CD пайплайны.

### 🛠 1. Суть и назначение
Зачем нам нужен Newman, если есть Postman?
*   **Headless mode:** Запуск тестов на серверах (Jenkins, GitLab CI, GitHub Actions), где нет монитора и мышки.
*   **Automation:** Автоматический запуск тестов при каждом пуше кода разработчиками.
*   **Speed & Resources:** Работает гораздо быстрее и потребляет в разы меньше оперативной памяти, чем тяжелый десктопный Postman.
*   **Integration:** Легко интегрируется с другими инструментами (генерация отчетов, логирование).

### 🚀 2. Быстрый старт (Installation)
Newman работает на базе **Node.js**. Поэтому первым делом убедись, что Node.js установлен.

```bash
# Установка Newman глобально в систему
npm install -g newman
```

### 🏃‍♂️ 3. Основные команды запуска
Для работы тебе нужно заранее экспортировать из Postman два файла: **Collection** (JSON) и **Environment** (JSON).

*   **Простой запуск коллекции:**
    ```bash
    newman run my_collection.json
    ```
*   **Запуск с использованием окружения (Environment):**
    *Это критически важно, чтобы тесты знали, куда стучаться: на Dev, QA или Prod.*
    ```bash
    newman run my_collection.json -e my_env.json
    ```
*   **Запуск с внешними данными (Data-Driven Testing):**
    *Если у тебя есть CSV или JSON файл со списком пользователей/товаров для проверки.*
    ```bash
    newman run my_collection.json -e my_env.json -d test_data.csv
    ```

### 📊 4. Отчетность (Reporting) — Уровень Senior
Просто смотреть в консоль — это неудобно. Для реальных проектов нужны красивые отчеты, которые можно прикрепить к результатам сборки в CI/CD.

1.  **Стандартный JUnit отчет** (для интеграции с Jenkins/GitLab):
    ```bash
    newman run my_collection.json --reporters cli,junit --reporter-junit-export results.xml
    ```
2.  **Красивый HTML отчет (htmlextra):**
    *Это «золотой стандарт». Он показывает детально каждый запрос, заголовки и ошибки.*
    Нужно сначала установить плагин: `npm install -g newman-reporter-htmlextra`
    ```bash
    newman run my_collection.json -r htmlextra
    ```

### ⚠️ 5. Нюансы и «Подводные камни» (Senior Tips)

*   **Проблема путей:** В CI/CD всегда используй относительные пути к файлам коллекций или проверяй, что файлы экспортированы в ту же папку, где запускается Newman.
*   **Синхронизация данных:** Помни, что Newman **не знает** о том, что ты изменил в Postman Desktop. Если ты добавил новый тест в GUI, тебе нужно заново экспортировать JSON-файл коллекции и обновить его в репозитории (Git).
*   **Зависимость от Node.js:** При настройке Docker-контейнера для тестов всегда фиксируй версию Node.js, чтобы избежать внезапных поломок из-за обновлений библиотек.
*   **Глобальные переменные:** Если твои тесты сильно зависят от *Global Variables*, не забудь их экспортировать (хотя лучше всего переносить всё в *Environment variables* для прозрачности).

# 🧠 Шпаргалка: Postman Interceptor

**Postman Interceptor** — это расширение для браузера (Chrome), которое выступает «мостом» между вашим браузером и десктопным приложением Postman. Его главная цель: **избавить тебя от ручного копирования запросов из DevTools в Postman.**

### 🚀 Зачем он нужен? (Use Cases)
1.  **Быстрый захват трафика:** Ты кликаешь по кнопкам на сайте, а запросы сами прилетают в твою коллекцию Postman.
2.  **Синхронизация Cookies:** Это «киллер-фича». Если ты авторизовался на сайте через веб-интерфейс (ввел логин/пароль), Interceptor подтянет все сессионные куки прямо в Postman. Тебе не нужно вручную искать `session_id` или `token` в Application Tab.
3.  **Тестирование авторизации:** Идеально, когда сложно настроить OAuth или сложные заголовки вручную — просто «перехвати» готовый успешный запрос.

---



### 🛠 Как это работает (Setup)
Чтобы всё заработало, нужны две части:
1.  **Chrome Extension:** Устанавливаешь в браузер.
2.  **Postman Desktop App:** Должен быть запущен.

**Процесс настройки:**
*   В Postman нажимаешь на иконку **Interceptor** (или находишь в настройках).
*   В расширении Chrome включаешь переключатель **Capture Requests**.
*   Включаешь **Capture Cookies** (если нужно прокидывать сессию).

---

### 🔍 Основные возможности
*   **Capture Requests:** Перехватывает URL, Method, Headers и Body запросов, которые проходят через браузер.
*   **Capture Cookies:** Синхронизирует куки между браузером и Postman. Это решает проблему `401 Unauthorized` при тестировании API, защищенного сессиями.
*   **Filtering:** Можно настроить фильтры по доменам (например, перехватывать только `*.api.myapp.com`), чтобы не забивать коллекцию мусорным трафиком от Google Analytics или рекламных трекеров.

---

### ⚠️ Нюансы и «Подводные камни» (Senior Insights)
*   **HTTPS Decryption:** Interceptor работает внутри браузера, поэтому он видит расшифрованный трафик. Но если ты пытаешься анализировать специфические запросы, которые идут в обход стандартного HTTP-стека браузера, может возникнуть затык.
*   **Мусор в коллекции:** Если не настроить **Filtering**, через 5 минут работы у тебя будет коллекция из 500 запросов, где перемешаны API твоего приложения, запросы к Facebook, Google и шрифтам. *Всегда настраивай доменные фильтры сразу.*
*   **Безопасность:** Помни, что Interceptor видит всё. Не используй его для работы с критически важными данными (например, банковскими транзакциями) в открытых сетях, так как расширение технически может «прочитать» содержимое запросов.
*   **Не замена Charles/Fiddler:** Interceptor — это не полноценный HTTP-прокси. Он не умеет подменять ответы (Mocking) или менять структуру запроса на лету (Breakpoints). Он только **копирует**. Если нужно именно *изменить* ответ сервера, используй Charles Proxy или Fiddler.

### ❓ FAQ (Часто задаваемые вопросы на собеседовании)

**В: В чем разница между DevTools (Network tab) и Postman Interceptor?**
**О:** DevTools предназначен для *инспекции* текущего трафика (посмотреть, что ушло). Interceptor предназначен для *переноса* трафика в среду тестирования (Postman), чтобы его можно было автоматизировать, запускать коллекции и писать тесты.

**В: Я авторизовался на сайте, но Postman всё равно выдает 401. Почему?**
**О:** Проверь, включена ли функция **Capture Cookies** в расширении и активен ли режим синхронизации в самом Postman. Также убедись, что домен сайта добавлен в список разрешенных для захвата кук.

**В: Можно ли с помощью Interceptor перехватить POST-запрос с телом (Body)?**
**О:** Да, он умеет захватывать и заголовки, и тело запроса, но при больших объемах данных или сложных форматах (multipart/form-data) иногда может потребоваться ручная проверка целостности данных в Postman.

**В: Поможет ли Interceptor, если API использует Bearer Token в заголовке Authorization?**
**О:** Да, он перехватит заголовок `Authorization`. Но важно помнить: куки синхронизируются автоматически, а вот токены из заголовков часто нужно копировать вручную или через настройку правил захвата.

# 🛠 Postman Interceptor & Mock Servers

Эти два инструмента решают разные задачи, но часто работают в одной связке: **Interceptor** помогает быстро собрать реальные запросы из браузера, а **Mock Server** позволяет имитировать их работу, когда бэкенд еще не готов.

---

## 1. Postman Interceptor (Твой «шпион» в браузере)

**Что это:** Расширение для Chrome + дополнение к десктопному Postman. Его главная задача — перехватывать HTTP-трафик, который идет через твой браузер, и мгновенно отправлять его в Postman.

### 🚀 Зачем он нужен:
*   **Быстрое создание коллекций:** Тебе не нужно вручную копировать каждый запрос из `Network` вкладки DevTools. Interceptor делает это за тебя.
*   **Синхронизация Cookies:** Это киллер-фича. Если ты залогинился на сайте в браузере, Interceptor может «подтянуть» эти куки в Postman. Тебе не нужно мучиться с ручным копированием `Session ID` или `Auth Token`.

### 🔍 Нюансы и Senior-советы:
*   **Cookie Sync:** Чтобы куки работали, расширение должно быть активно, а в десктопном Postman должна быть включена функция синхронизации. Если сессия «отвалилась» в Postman — первым делом проверь Interceptor.
*   **Фильтрация:** Не включай перехват всего подряд. Если не настроить фильтры (по домену), Interceptor завалит твою коллекцию мусорным трафиком от Google Analytics, рекламных трекеров и прочего.
*   **HTTPS/SSL:** Для перехвата HTTPS-трафика иногда требуются дополнительные настройки сертификатов, иначе браузер будет ругаться на небезопасное соединение.

## 2. Mock Servers (Твой «двойник» бэкенда)

**Что это:** Виртуальный сервер в облаке Postman, который имитирует поведение реального API. Он не делает логики, он просто возвращает заранее заготовленные ответы.

### 🚀 Зачем он нужен:
*   **Frontend-first разработка:** Фронтенд-разработчик может начать писать код, даже если бэму (бэкенд) еще в процессе написания. Ты просто создаешь Mock с нужной структурой JSON.
*   **Тестирование негативных сценариев:** Сложно заставить реальный сервер выдать `500 Internal Server Error` или `503 Service Unavailable` по щелчку пальцев. В Mock-сервере ты просто создаешь "Example" с таким статус-кодом.
*   **Изоляция тестов:** Ты не зависишь от нестабильного тестового стенда (который может упасть или тормозить).

### 🔍 Нюансы и Senior-советы:
*   **Магия в "Examples":** Mock-сервер работает на основе **Examples**. Если ты просто создал запрос, но не сохранил для него `Example` (ответ), сервер вернет пустой ответ или ошибку. Каждый сценарий (успех, ошибка 400, ошибка 401) — это отдельный Example в твоей коллекции.
*   **Алгоритм Match (Сопоставление):** Это самое важное. Postman ищет наиболее подходящий `Example` по следующим критериям:
    1.  **URL/Path** (совпадает ли путь).
    2.  **Method** (GET, POST и т.д.).
    3.  **Headers** (если в примере указан специфичный заголовок, запрос должен его содержать).
    4.  **Query Params**.
    *Если ты не передашь нужный заголовок, который прописан в Example, Postman может вернуть не тот ответ или выдать 404.*
*   **Задержка (Latency):** В настройках Mock-сервера можно выставить `Fixed Delay`. Это полезно для проверки того, как твой клиент (фронтенд) ведет себя при медленном интернете.

## ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем отличается Interceptor от простого копирования запроса из Chrome DevTools (Copy as cURL)?**
**О:** `Copy as cURL` — это разовое действие. Тебе нужно вручную импортировать его в Postman. **Interceptor** — это автоматизированный процесс, который умеет синхронизировать Cookies и позволяет «записывать» сессию целиком в реальном времени.

**В: Что произойдет, если я отправлю запрос на Mock-сервер, для которого не создан ни один Example?**
**О:** Postman попытается найти совпадение, но если совпадений нет (или есть только частичные), он вернет стандартный ответ (обычно это статус 404 или дефолтный ответ из коллекции).

**В: Можно ли в Mock-сервере реализовать сложную логику (например, проверять данные в теле запроса и менять ответ)?**
**О:** На уровне базового Mock-сервера — **нет**. Он работает по принципу статических шаблонов (Static Matching). Для динамической логики нужны скрипты (Pre-request/Tests) или использование полноценных инструментов вроде WireMock. Postman Mock — это "заглушка", а не полноценный эмулятор бэкенда.

**В: Как протестировать авторизацию через Mock-сервер?**
**О:** Тебе нужно создать два `Example`: один с правильным токеном в заголовке (возвращает 200 OK), второй — с неправильным или отсутствующим (возвращает 401 Unauthorized). Это позволит проверить логику обработки ошибок на клиенте.

# 📖 Тема: API Documentation (Документация API)

**API Documentation** — это «контракт» между разработчиком бэкенда и всеми, кто будет использовать этот сервис (фронтенд-разработчики, мобильные разработчики, тестировщики, сторонние партнеры). Если документация плохая — проект встает, потому что никто не понимает, как отправить запрос, чтобы получить правильный результат.

### 🏗 Основные компоненты «идеальной» документации

Чтобы документация была рабочей, она должна содержать следующие элементы:

1.  **Endpoints (Эндпоти):** Полный URL-адрес ресурса (например, `/api/v1/users/{id}`).
2.  **HTTP Methods:** Четкое указание метода (`GET`, `POST`, `PUT`, `DELETE` и т.д.).
3.  **Parameters (Параметры):**
    *   **Path Parameters:** Часть URL (например, `{id}`).
    *   **Query Parameters:** Параметры после `?` в URL (например, `?limit=10&sort=desc`).
    *   **Header Parameters:** Заголовки (например, `Authorization` или `X-Api-Key`).
    *   **Request Body:** Структура тела запроса (JSON/XML) с описанием каждого поля.
4.  **Data Types & Constraints:** Тип данных (string, integer, boolean), обязательность поля (`required`/`optional`), формат (email, date-time) и ограничения (min/max length).
5.  **Response Structure:** Пример успешного ответа (`200 OK`) и структура объекта.
6.  **Error Codes & Messages:** Описание того, что значат ошибки `400`, `401`, `403`, `404` именно для этого API (например, «400 — неверный формат даты рождения»).
7.  **Authentication/Authorization:** Инструкция, как получить токен и какой метод использовать (Bearer, OAuth2, Basic).

### 🛠 Стандарты и инструменты

В индустрии не принято писать документацию просто в Word. Используются стандарты:

*   **OpenAPI (ранее Swagger):** Золотой стандарт для **REST**. Это формат описания API, который можно превратить в интерактивную веб-страницу (Swagger UI), где можно сразу нажать кнопку "Try it out" и отправить запрос.
*   **WSDL (Web Services Description Language):** Стандарт для **SOAP**. Это массивный XML-файл, который описывает все методы и типы данных. Инструменты вроде SoapUI читают его и автоматически строят запросы.
/
*   **Postman Collections:** Хорошая коллекция в Postman сама по себе является документацией. Если она настроена правильно (с примерами, описанием параметров и тестами), её можно использовать как "живую" документацию.

### ⚠️ Нюансы (Senior Level Insights)

Как опытный инженер, я советую обращать внимание на эти «подводные камни»:

1.  **Documentation Drift (Рассинхрон):** Самая большая боль. Разработчик изменил поле в коде (например, переименовал `user_id` в `uid`), но забыл обновить Swagger. **Результат:** Тесты падают, фронтенд ломается. 
    *   *Решение:* Использовать подход *Design-First* (сначала пишем спецификацию, потом код) или автоматическую генерацию документации из кода.
2.  **Versioning (Версионирование):** Документация должна четко разделять версии API (`/v1/`, `/v2/`). Нельзя просто удалять старые поля, если ими пользуются клиенты.
3.  **Edge Cases (Граничные случаи):** Плохая документация описывает только "счастливый путь" (Happy Path). Хорошая — описывает, что будет, если прислать пустую строку, слишком длинный текст или неверный тип данных.
4.  **Security Disclosure:** Никогда не включай реальные токены, пароли или персональные данные пользователей в примеры документации! Только заглушки (`<your_token_here>`).

### ❓ FAQ (Часто задаваемые вопросы)

**В: Чем отличается Swagger от OpenAPI?**
**О:** **OpenAPI** — это спецификация (набор правил и формат описания, как "грамматика" языка). **Swagger** — это набор инструментов (интерфейс для визуализации, редактор, генератор кода), которые работают с этой спецификацией.

**В: Что делать тестировщику, если документация не совпадает с реальностью?**
**О:** Это критический баг. Первым делом зафиксируй несоответствие (Bug Report). Затем уточни у разработчика: это "забыли обновить доки" или "изменили логику API". Если изменилась логика — нужно обновлять и тесты, и документацию.

**В: Можно ли использовать Postman вместо Swagger?**
**О:** Да, для быстрого тестирования и интеграции в команду. Но Swagger/OpenAPI лучше подходят для долгосрочного проектирования архитектуры и автоматизации контрактов (Contract Testing), так как они являются машиночитаемыми стандартами.

# 🧠 Шпаргалка: Postman Monitors

**Postman Monitor** — это облачный сервис, который позволяет запускать твои коллекции запросов по расписанию в облаке Postman. Если простыми словами: это твой «автоматический сторож», который периодически обходит API и проверяет, всё ли в порядке (живы ли эндпоинты, не упала ли база, не изменился ли формат ответа).

### 🚀 Основная суть
Вместо того чтобы запускать тесты вручную или через свой CI/CD (как делает Newman), ты делегируешь выполнение задач облаку Postman. Он сам «просыпается» в назначенное время, прогоняет коллекцию и присылает тебе уведомление, если что-то сломалось.

### 🛠 Ключевые компоненты
1.  **Schedule (Расписание):** Настройка частоты проверок (каждый час, раз в день, раз в неделю).
2.  **Regions (Регионы):** Выбор локации, из которой будет идти запрос (США, Европа и т.д.). Это критично для проверки задержек (latency) из разных точек мира.
3.  **Alerting (Уведомления):** Настройка каналов связи (Email, Slack, Webhooks), куда придет «алерт», если тест упал.
4.  **Reports (Отчеты):** Графики аптайма (uptime) и времени ответа (response time). Позволяют увидеть тренды: например, что API стал отвечать на 200мс медленнее за последнюю неделю.

### ⚠️ Нюансы и «подводные камни» (Senior level)
*   **Проблема локальных ресурсов:** Это самый важный момент. Поскольку монитор работает в **облаке Postman**, он не имеет доступа к твоему `localhost` или API, которые спрятаны внутри корпоративного VPN/закрытой сети. Если твой API не виден из интернета — Monitor его не проверит.
    *   *Решение:* Использовать инструменты вроде *ngrok* для проброса локального порта в интернет (но это только для тестов) или деплоить тестовую среду на публичный хостинг.
*   **Стоимость и лимиты:** Каждый запуск монитора расходует твои «Cloud Units» (в рамках тарифного плана). Не ставь проверку каждую минуту, иначе бюджет закончится быстрее, чем ты заметишь.
*   **Environment Variables:** Убедись, что все переменные окружения (BaseURL, Tokens) корректно настроены и доступны в облаке. Если ты используешь `current_value` локально, но не обновил его в облаке — монитор упадет.
*   **Отличие от Newman:** 
    *   *Newman* — это инструмент для **CI/CD** (запуск при пуше кода). Его цель — проверить качество новой сборки.
    *   *Monitor* — это инструмент для **Production/Staging Monitoring**. Его цель — следить за доступностью работающего сервиса.

### 📋 Чек-лист настройки
1. [ ] Создать коллекцию с полноценными тестами (Assertions).
2. [ ] Настроить Environment (убедиться, что URL публичный).
3. [ ] Создать Monitor в Postman.
4. [ ] Выбрать регион (ближайший к твоим пользователям).
5. [ ] Настроить Alerting (Slack/Email).
6. [ ] Проверить первый запуск вручную.

**В: Можно ли с помощью Postman Monitor проводить нагрузочное тестирование?**
**О:** Нет. Его задача — *Health Check* (проверка здоровья). Он делает последовательные запросы по расписанию. Для нагрузки нужны инструменты вроде JMeter или k6, которые умеют генерировать тысячи RPS (запросов в секунду).

# 🚀 Тема: Integration with CI/CD (Continuous Integration / Continuous Deployment)

### 🧠 Суть процесса
Интеграция тестов в CI/CD — это переход от «я нажал кнопку Send в Postman» к «тесты запускаются сами при каждом пуше кода». Твоя цель: сделать так, чтобы после каждого изменения в бэкенде пайплайн (Jenkins, GitLab CI, GitHub Actions) автоматически прогонял твои коллекции и выдавал вердикт: **Pass** (всё ок) или **Fail** (мы что-то сломали).

---

### 🛠 Основные инструменты («Двигатели»)

Чтобы запустить Postman или SoapUI вне графического интерфейса, нам нужны консольные утилиты:

1.  **Newman (для Postman):** Это CLI-раннер. Он умеет читать твою коллекцию и окружение, выполнять запросы и генерировать отчеты. Без него CI/CD невозможен.
    *   *Команда базы:* `newman run my_collection.json -e my_env.json`
2.  **SoapUI TestRunner (для SoapUI):** Аналогичный инструмент для SOAP-сервисов, позволяющий запускать TestSuites через терминал.

---

/### 🏗 Этапы настройки пайплайна

1.  **Экспорт артефактов:** Ты должен выгрузить коллекцию (`.json`) и переменные окружения (`.json`) из Postman и положить их в Git-репозиторий (или скачивать их динамически через API Postman).
2.  **Контейнеризация (Best Practice):** Не устанавливай Node.js или Java прямо на сервер Jenkins. Лучше использовать **Docker-образ**, в котором уже предустановлены `newman` или `SoapUI`. Это гарантирует, что тесты запустятся одинаково и у тебя, и на сервере.
3.  **Триггер:** Настройка события (например, `push` в ветку `develop`), которое запускает выполнение скрипта.
4.  **Выполнение (Execution):** Запуск команды `newman run...` внутри шага пайплайна.
5.  **Reporting & Artifacts:** Сохранение результатов теста (HTML-отчеты, JUnit XML) как **artifacts** в CI-системе, чтобы их можно было скачать и изучить после падения билда.

---

### ⚠️ Нюансы и «подводные камни» (Senior Level)

*   **Secrets Management (Безопасность):** **Никогда** не храни пароли, API-ключи или токены в файлах `.json`, которые лежат в Git! Используй переменные окружения самого CI-сервера (например, *GitLab CI Variables* или *Jenkins Credentials*). В Newman передавай их через флаг `--env-var`.
*   le **Exit Codes (Коды выхода):** Это критично. Если тесты упали, Newman должен вернуть ошибку (exit code $\neq$ 0). Если он вернет 0, CI/CD решит, что всё хорошо, и пропустит сломанный код в продакшн.
*   **Dynamic Environments:** В CI у тебя не может быть «просто dev-окружение». Тесты должны уметь переключаться между `dev`, `staging` и `prod` в зависимости от того, какой пайплайн запущен. Это делается через передачу разных файлов окружений (`-e`).
*   **Flaky Tests (Нестабильные тесты):** В CI часто случаются сетевые лаги. Если тест падает раз в 10 запусков из-за тайм-аута — это «флаки» тест. Нужно внедрять механизмы **retries** (повторных запусков) или более гибкие проверки времени ответа.
*   **JUnit Reporting:** Чтобы Jenkins или GitLab могли отрисовать красивые графики (сколько тестов прошло/упало), используй репортеры в формате **JUnit**. Newman это умеет через плагины (`newman-reporter-junit`).

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что делать, если коллекция Postman слишком большая и её неудобно хранить в Git?**
**О:** Используй **Postman API**. Ты можешь настроить скрипт в CI, который будет автоматически скачивать актуальную версию коллекции по ссылке (через API Key), чтобы не обновлять JSON-файл в репозитории вручную после каждого изменения.

**В: Как передать данные из CSV-файла в Newman при запуске в Jenkins?**
**О:** Используй флаг `-d`. Команда будет выглядеть так: `newman run collection.json -d data.csv`. Главное, чтобы файл `data.csv` был доступен в рабочей директории агента Jenkins.

**В: Как увидеть красивый HTML-отчет прямо в интерфейсе GitLab/Jenkins?**
**О:** Используй плагин `newman-reporter-htmlextra`. После выполнения команды укажи путь к отчету, а в настройках CI (в секции `artifacts`) укажи этот путь. Тогда после завершения билда ты сможешь кликнуть на него и увидеть детальный разбор каждого запроса с цветами и ошибками.

**В: Могу ли я тестировать API, который еще не развернут в облаке?**
**О:** Да, для этого используются **Mock Servers**. В пайплайне ты сначала поднимаешь мок-сервер (через Docker или Postman Mock), прогоняешь тесты против него, а затем переключаешься на реальный сервис.

# 🧠 Шпаргалка: SOAP vs REST

Если коротко: **REST** — это набор рекомендаций (архитектурный стиль), как делать API удобно и легко. **SOAP** — это жесткий протокол с кучей правил, который не прощает ошибок, но гарантирует безопасность и порядок.

### 📊 Сравнительная таблица

| Характеристика | REST (Representational State Transfer) | SOAP (Simple Object Access Protocol) |
| :--- | :--- | :--- |
| **Тип** | Архитектурный стиль (набор принципов). | Протокол (строгий стандарт). |
| **Формат данных** | Любой: JSON (чаще всего), XML, HTML, Plain Text. | **Только XML**. |
	| **Транспорт** | В основном HTTP/HTTPS. | HTTP, SMTP, TCP, FTP и др. |
| **Структура** | Легкая: URL + Метод + Тело (если нужно). | Тяжелая: Envelope $\rightarrow$ Header $\rightarrow$ Body. |
| **Сложность** | Низкая. Легко читать человеку и коду. | Высокая. Требует парсинга сложных XML-схем. |
| **Безопасность** | Использует HTTPS, OAuth2, JWT. | Имеет встроенный стандарт **WS-Security** (очень мощный). |
| **Состояние** | **Stateless** (каждый запрос независим). | Может быть как stateless, так и **stateful**. |
| **Контракт** | Swagger / OpenAPI (необязательно, но принято). | **WSDL** (строго обязателен, это «паспорт» сервиса). |

---

### 🔍 Глубокое погружение (Нюансы от Senior)

#### 1. Про гибкость vs Про надежность
*   **REST** — это про скорость и масштабируемость. Он идеально подходит для мобильных приложений и веб-сервисов, где важен минимальный вес трафика. Если ты строишь микросервисы — твой выбор REST.
*   **SOAP** — это про «тяжелый энтерпрайз». Там, где критически важны транзакции (например, банковские переводы), SOAP выигрывает за счет встроенной поддержки **ACID** (атомарность, согласованность, изолированность, долговечность) и возможности гарантировать доставку сообщения.

#### 2. Контрактное тестирование
*   В **SOAP** у тебя есть файл **WSDL**. Это "священный текст". Если структура ответа хоть на йоту отличается от того, что описано в WSDL — это ошибка. Это делает SOAP очень предсказуемым для автоматизации.
*   В **REST** всё держится на договоренностях (OpenAPI/Swagger). Если разработчик не обновил документацию, ты можешь даже не узнать, что поле `user_id` превратилось в `userId`.

#### 3. Безопасность (Security)
*   В **REST** мы защищаем «трубу» (HTTPS) и используем токены (JWT).
*   В **SOAP** безопасность может быть реализована на уровне самого сообщения (WS-Security). Это значит, что сообщение можно зашифровать так, что оно останется безопасным, даже если его перехватят в промежуточном узле (прокси/шлюзе), так как ключи расшифровки привязаны к содержимому XML.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли использовать JSON в SOAP?**
**О:** Нет. Это технически невозможно по стандарту. SOAP базируется исключительно на XML-структуре (Envelope).

**В: Что такое WSDL простыми словами?**
**О:** Это «инструкция по эксплуатации» вашего сервиса. В ней написано: какие методы можно вызывать, какие параметры передать и что придет в ответ. Без него работать с SOAP практически невозможно.

**В: Почему REST считается более производительным?**
**О:** Из-за отсутствия оверхеда (избыточности). XML-структура SOAP требует много лишних символов (теги, закрывающие теги), что раздувает размер пакета данных. JSON в REST гораздо компактнее и быстрее парсится браузерами и мобильными устройствами.

**В: В каком случае я выберу SOAP, если знаю, что он сложнее?**
**О:** Если проект требует строгих транзакционных гарантий (финансы), работы через нестандартные протоколы (не только HTTP) и глубокой безопасности на уровне сообщения.

# 📜 Шпаргалка: WSDL (Web Services Description Language)

### 💡 Что это такое простыми словами?
Представь, что ты заказываешь мебель в IKEA. Тебе нужна инструкция, чтобы понять: какие детали есть в коробке, как их соединить и какой результат получится. 
**WSDL — это такая «инструкция» для SOAP-сервиса.** Это XML-файл, который говорит клиенту (например, SoapUI): «Я умею выполнять вот такие действия, на вход жду такие-то данные, а на выходе отдам вот такой результат, и искать меня нужно по этому адресу».

Если у тебя есть WSDL, ты можешь автоматически сгенерировать запросы в SoapUI. Без него тебе придется вручную собирать сложный XML-пакет.

---

### 🏗️ Анатомия WSDL (5 главных элементов)
WSDL — это иерархическая структура. Чтобы не запутаться, запомни эти пять слоев от «смысла» к «адресу»:

1.  **`<types>` (Типы данных):** Это словарь. Здесь используются схемы **XSD** (XML Schema Definition). Он описывает, что такое «User» (например: имя — это строка, возраст — число). Без этого мы не поймеsем структуру данных.
2.  **`<message>` (Сообщения):** Описание того, что именно передается. Это «содержимое конверта». Сообщение состоит из набора элементов, описанных в `<types>`.
3.  **`<portType>` (Интерфейс/Операции):** Это список доступных действий (методов). Например: `getUser`, `createUser`, `deleteUser`. Если ты хочешь узнать, какие функции есть у сервиса — смотри сюда.
4.  **`<binding>` (Привязка/Протокол):** Описание того, *как* мы будем передавать данные. Здесь указано, что мы используем протокол **SOAP** и транспорт **HTTP**. Это правила упаковки сообщения в конверт.
5.  **`<service>` (Сервис/Endpoint):** Конечная точка. Это конкретный URL (например, `http://api.example.com/v1/soap`), по которому нужно отправить запрос.

---

### 🔍 Нюансы от Senior-а (На что смотреть при тестировании)

*   **WSDL vs Swagger (OpenAPI):** WSDL — это стандарт для **SOAP** (строгий, тяжелый, XML). Swagger — это стандарт для **REST** (легкий, гибкий, JSON). Если видишь `.wsdl` в конце ссылки — перед тобой SOAP.
*   **Namespace (Пространства имен) — Главная боль:** В WSDL всегда есть атрибуты `xmlns`. Это как фамилии у людей. Если в запросе ты забудешь указать правильный namespace или ошибешься в нем, сервер вернет ошибку, хотя структура XML может быть идеальной.
*   **Версионность:** Изменение WSDL (например, добавление нового обязательного поля) — это **breaking change**. Это ломает всех клиентов. Всегда проверяй, не обновился ли контракт.
*   **XSD Import:** Часто `<types>` ссылается на внешние файлы `.xsd`. Если у тебя нет доступа к этим файлам или сеть закрыта, SoapUI не сможет построить структуру запроса.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Можно ли протестировать SOAP-сервис, если у меня нет ссылки на WSDL?**
**О:** Можно, но это «путь боли». Тебе придется вручную изучать документацию, узнавать структуру XML, заголовки и URL, а затем собирать каждый запрос в Postman или SoapUI с нуля. WSDL экономит 90% времени на подготовку тестов.

**В: В чем разница между WSDL и XSD?**
**О:** Это как «Инструкция по сборке шкафа» (WSDL) и «Список всех винтиков и досок» (XSD). XSD — это часть WSDL, которая отвечает только за форматы данных.

**В: Почему SoapUI пишет "Error parsing WSDL", хотя ссылка открывается в браузере?**
**О:** Три частые причины:
1.  **Сетевой доступ:** Браузер может иметь доступ к прокси, а SoapUI — нет.
2.  **Битые зависимости:** WSDL ссылается на другие файлы (XSD), которые недоступны.
3.  **Ошибка синтаксиса:** В самом XML есть ошибка (например, незакрытый тег), которую браузер «проглатывает», а строгий парсер SoapUI — нет.

**В: Что такое Endpoint в контексте WSDL?**
**О:** Это конкретный адрес (URL) сервера, на который ты отправляешь свой SOAP-запрос. Он описывается в секции `<service>`.

# 🧠 Шпаргалка: Работа с XML и XPath

### 1. Что это такое? (Суть)
*   **XML (eXtensible Markup Language)** — это формат хранения данных в виде древовидной структуры. В нем есть теги, атрибуты и текст. По сути, это "дерево", где каждый узел (node) — это элемент.
*   **XPath (XML Path Language)** — это язык запросов. Представь, что XML — это путь к файлу в Windows (например, `C:\Users\Admin\Docs`), а XPath — это способ быстро найти нужный файл внутри этого пути, не перебирая все папки вручную.

### 2. Анатомия XML
```xml
<bookstore xmlns:fb="http://example.com/fb"> <!-- Корневой элемент + Namespace -->
  <book id="101" category="fiction">        <!-- Атрибут (id, category) -->
    <title lang="en">The Great Gatsby</title> <!-- Элемент с текстом и атрибутом -->
    <author>F. Scott Fitzgerald</author>
  </book>
</bookstore>
```

### 3. Основной синтаксис XPath (Твой инструментарий)

| Символ | Описание | Пример | Что найдет |
| :--- | :--- | :--- | :--- |
| `/` | **Абсолютный путь.** Идет от самого корня. | `/bookstore/book/title` | Только если структура строго такая. |
| `//` | **Относительный путь.** Ищет элемент в любом месте документа. | `//title` | Все теги `<title>`, где бы они ни были. |
  | `.` | **Текущий узел.** | `./author` | Ищет автора внутри текущего элемента. |
| `..` | **Родительский узел.** | `//title/..` | Перейдет от названия книги к самой книге. |
| `@` | **Выбор атрибута.** | `//@id` | Все значения атрибутов `id`. |
| `*` | **Wildcard (звездочка).** Любой элемент или атрибут. | `//book/*` | Все дочерние элементы внутри `<book>`. |
| `[]` | **Предикаты (Фильтры).** Условия поиска. | `//book[1]` | Только первую книгу в списке. |

#### Продвинутые фильтры (Predicates):
*   `//book[@category='fiction']` — найти книги, у которых атрибут `category` равен 'fiction'.
*   `//book[contains(title, 'Great')]` — найти книги, в названии которых есть слово 'Great'.
*   `//book[last()]` — найти последнюю книгу в списке.
*   `//book[position() < 3]` — найти первые две книги.

---

### 4. Senior Nuances (То, на чем валятся джуны)

#### ⚠️ Нюанс №1: Namespaces (Пространства имен) — Главная боль в SoapUI
Если в XML есть `xmlns="http://..."`, твой обычный XPath `//title` может **не работать**. 
*   **Почему?** Потому_что элементы теперь "принадлежат" этому адресу.
*   **Как лечить:** В SoapUI при написании XPath Assertions нужно либо использовать `local-name()`, либо регистрировать префикс (namespace) в настройках теста.
*   **Хак для обхода без регистрации:** `//*[local-name()='title']` — этот запрос проигнорирует namespace и найдет тег по имени.

#### ⚠️ Нюанс №2: Поиск текста vs Поиск узла
*   `//title` — вернет весь узел `<title>en</title>`.
*   `//title/text()` — вернет только строковое значение `en`.
*   *Важно:* Если ты делаешь проверку (Assertion) в SoapUI, выбирай, что именно ты проверяешь: наличие тега или конкретный текст внутри.

#### ⚠️ Нюанс №3: Производительность
Не злоупотребляй `//` на огромных XML-файлах (на сотни мегабайт). Поиск по всему дереву (`//`) заставляет парсер сканировать каждый узел. Если ты знаешь структуру, всегда используй прямой путь `/`.

---

### 5. FAQ (Вопросы на собеседовании)

**В: Чем отличается `/` от `//`?**
**О:** `/` — это строгий путь от корня (как абсолютный путь в файловой системе). `//` — это поиск по всему дереву, независимо от уровня вложенности.

**В: Как проверить, что атрибут `id` у элемента `book` равен '101'?**
**О:** Используй XPath: `//book[@id='101']`.

**В: Что делать, если XPath работает в браузере, но не работает в SoapUI?**
**О:** Скорее всего, дело в **Namespaces**. Проверь наличие атрибута `xmlns` в корневом элементе XML. Используй функцию `local-name()`, чтобы обойти проблему.

**В: Как найти все элементы, у которых нет атрибута `category`?**
**О:** Используй проверку на отсутствие: `//book[not(@category)]`.

# 🧠 Шпаргалка: SoapUI Assertions

**Assertions (Проверки)** — это «судьи» твоего запроса. Без них запрос — это просто отправка данных в пустоту. Assertion проверяет, что ответ сервера соответствует твоим ожиданиям. Если проверка проходит — тест **Green** (Passed), если нет — **Red** (Failed).

В SoapUI проверки можно разделить на три уровня: **Текстовые**, **Структурные** и **Скриптовые**.

---

### 1. Текстовые проверки (Basic Assertions)
*Самые простые, работают с сырой строкой ответа.*

*   **Contains / Not Contains:** Проверяет наличие или отсутствие конкретной строки в теле ответа. 
    *   *Нюанс:* Очень чувствительны к регистру и лишним пробелам.
*   **Empty / Not Empty:** Проверяет, пришел ли ответ вообще или он пустой.
*   **Regex Match:** Использование регулярных выражений. Позволяет проверять сложные паттерны (например, формат даты `\d{4}-\d{2}-\d{2}` или email).
    *   *Senior Tip:* Не пиши слишком сложные Regex, их невозможно поддерживать. Если можно проверить проще — проверяй проще.

### 2. Структурные проверки (Data-Driven Assertions)
*Золотой стандарт для работы с XML (SOAP) и JSON (REST).*

*   **XPath Match (Для SOAP/XML):** Самая важная проверка в SoapUI. Ты указываешь путь к узлу (например, `/Envelope/Body/Response/Status`) и ожидаемое значение.
    *   *Нюанс (Важно!):* **Namespaces (Пространства имен).** Если в XML есть `xmlns`, обычный XPath может не сработать. Нужно либо игнорировать пространства имен, либо правильно их прописывать.
*   **JSONPath Match (Для REST/JSON):** Аналог XPath, но для JSON. Позволяет вытащить конкретное поле из глубоко вложенного объекта и проверить его значение.
*   **Schema Compliance:** «Тяжелая артиллерия». Проверяет не просто значения, а **структуру** всего ответа на соответствие XSD-схеме или WSDL. 
    *   *Зачем:* Это гарантирует, что тип данных (string/int), обязательные поля и порядок элементов не нарушены.

### 3. Протокольные проверки (Protocol Assertions)
*Проверяют метаданные запроса.*

*   **HTTP Status Codes:** Проверка кода ответа (200 OK, 404 Not Found, 500 Error).
    *   *Senior Tip:* Всегда проверяй не только 200, но и то, как система реагирует на ошибки (4xx, 5xx). Это часть негативного тестирования.
*   **Response Time:** Проверка времени ответа (например, `< 500ms`).
    *   *Нюанс:* Не ставь слишком жесткие лимиты, так как время ответа зависит от нагрузки на сеть и сервер в данный момент.

### 4. Скриптовые проверки (Groovy Scripting)
*Уровень «Бог». Когда стандартных кнопок не хватает.*

Если тебе нужно:
1. Взять значение из одного запроса, положить в переменную и проверить в другом.
2. Выполнить сложную математику или логику (if/else).
3. Сходить в базу данных и сравнить ответ API с данными в БД.

Используй **Script Assertion**. Это чистый Groovy (родственник Java).

---

### 💡 Senior Tips: На что смотреть, чтобы не «поплыть»

1.  **Избыточность:** Не проверяй каждое поле в ответе через `Contains`. Если ты проверил структуру через *Schema Compliance*, то проверять наличие каждого поля текстом — это пустая трата времени и ресурсов.
2.  **Динамические данные:** Если в ответе прилетает ID или Timestamp, `Contains` упадет. Используй **Regex Match** или **Groovy Script**, чтобы игнорировать меняющуюся часть.
3.  **Поддерживаемость:** Пиши проверки так, чтобы их было легко поправить. Если завтра разработчики изменят название поля в JSON, ты должен найти и исправить одну строку в Assertions, а не переписывать 10 тестов.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Чем XPath Match отличается от Schema Compliance?**
**О:** `XPath Match` проверяет **конкретное значение** в конкретном месте (например, что `price == 100`). `Schema Compliance` проверяет **правила игры**: что поле `price` вообще существует, что оно является числом и что оно не может быть пустым. Для идеального теста нужны оба.

**В: Почему мой XPath Match не находит узел, хотя я вижу его в ответе?**
**О:** Скорее всего, дело в **Namespaces (xmlns)**. XML-парсер пытается сопоставить префиксы (например, `soapenv:`), и если они не описаны в твоем запросе, он «не видит» узел. Используй функции для игнорирования namespaces или прописывай их корректно.

**В: Можно ли в одном Assertions проверить сразу несколько условий?**
**О:** Да, если ты используешь **Script Assertion**. В Groovy можно написать цикл или цепочку проверок `assert` внутри одного скрипта. Это удобно для сложных бизнес-сценариев.

**В: Что делать, если API возвращает 200 OK, но в теле ошибка (например, `{ "error": "auth failed" }`)?**
**О:** Это классическая ловушка! Твоя проверка `HTTP Status Codes` пройдет, но тест будет ложным. Всегда добавляй проверку тела (через JSONPath или Contains), чтобы убедиться, что бизнес-логика успешна.

# 🛡️ Шпаргалка: Security Testing (SoapUI Pro / ReadyAPI)

**Security Testing** в контексте API — это процесс поиска уязвимостей, которые позволяют злоумышленнику нарушить конфиденциальность, целостность или доступность данных. В SoapUI Pro (теперь часть ReadyAPI) этот процесс автоматизирован через специальный модуль **Security Test Suite**.

## 1. Основные векторы атаки (Что мы проверяем)

Как Senior, я делю все проверки на три уровня:

### А. Аутентификация и Авторизация (AuthN & AuthZ)
*   **Broken Authentication:** Проверяем, можно ли обойти вход. Можно ли использовать старые/протухшие токены? Можно ли подобрать пароль (Brute-force)?
*   **Broken Object Level Authorization (BOLA/IDOR):** Самая частая дыра. Если я меняю в запросе `GET /api/user/123` на `GET /api/user/124`, увижу ли я чужие данные? 
*   **Mass Assignment:** Проверка, можно ли через POST-запрос «подсунуть» лишнее поле. Например, добавить `"role": "admin"` в запрос на регистрацию пользователя.

### Б. Инъекции (Injection) — Классика жанра
*   **SQL Injection (SQLi):** Вставка SQL-комаля в параметры запроса (например, `' OR 1=1 --`), чтобы вытащить данные из БД.
*   **XML External Entity (XXE):** **Критично для SOAP!** Мы пытаемся заставить парсер XML прочитать файл с сервера (например, `/etc/passwd`) через объявление внешних сущностей в теле запроса.
*   **Command Injection:** Попытка выполнить системную команду на сервере через параметры API.

### В. Нарушение целостности и доступности
*   **DoS (Denial of Service):** Отправка огромных XML-файлов (XML Bomb) или слишком большого количества запросов, чтобы «положить» сервис.
*   **Sensitive Data Exposure:** Проверка, не возвращает ли API в ответе лишнего: хеши паролей, персональные данные, технические детали сервера (stack trace).

---

## 2. Инструментарий SoapUI Pro (Security Test Suite)

В отличие от обычного Postman, SoapUI Pro умеет генерировать **Security Test Case** автоматически на основе WSDL или Swagger.

1.  **Automated Scanning:** Ты выбираешь запрос, и инструмент сам подставляет в него «плохие» данные (payloads) из своей базы уязвимостей.
2.  **Fuzzing (Фаззинг-тестирование):** Процесс подачи на вход случайных, невалидных или искаженных данных. Цель — найти точку, где сервис упадет с ошибкой 500.
3.  **Security Test Suite Workflow:**
    *   Создаем `Security Test Case`.
    *   Выбираем тип атаки (например, *SQL Injection* или *XXE*).
    *   Запускаем сканирование.
    *   Анализируем отчет: если статус ответа изменился с `200 OK` на `500 Internal Server Error` или в ответе появился текст ошибки БД — **баг найден**.

## 3. Нюансы и советы от Senior

*   **Не забывай про заголовки:** Security-тестирование — это не только тело (Body) запроса, но и Headers. Проверяй отсутствие `Strict-Transport-Security` или наличие `XSS-Protection`.
*   **Ошибка 500 — это красный флаг:** В идеале API должен возвращать понятные ошибки (4xx), но не раскрывать внутреннюю кухню. Если при инъекции ты видишь `Internal Server Error` с логом базы данных — это уязвимость.
*   **Тестируй "Negative Path":** Security-тест — это всегда про негативные сценарии. Твоя задача — не подтвердить, что всё работает, а доказать, что систему можно сломать.

**В: В чем разница между SQL Injection и XXE?**
**О:** SQLi направлена на манипуляцию базой данных через параметры запроса. XXE направлена на эксплуатацию слабого парсера XML, чтобы заставить сервер прочитать локальные файлы или сделать запрос во внутреннюю сеть.

# 🚀 Cheat Sheet: Load Testing in SoapUI

**Load Testing (Нагрузочное тестирование)** — это процесс проверки того, как система ведет себя под ожидаемой нагрузкой. Наша цель — не просто «нажать кнопку», а найти **bottlenecks** (узкие места): где база данных начинает тормозить, где память течет, и при каком количестве пользователей сервис «ложится».

### 1. Основные понятия (Terminology)
Чтобы говорить на одном языке с разработчиками и DevOps, ты должен знать эти термины:

*   **Virtual Users (VU) / Threads:** Количество виртуальных пользователей, которые одновременно имитируют действия реальных людей.
*   **Ramp-up Period:** Время, за которое все твои VU «просыпаются» и начинают работать. 
    *   *Нюанс:* Нельзя сразу вываливать 1000 пользователей на сервис (это будет Spike Test). Нужно плавно наращивать нагрузку, чтобы увидеть момент деградации производительности.
*   **Throughput (Пропускная способность):** Количество запросов, которые система обрабатывает в единицу времени (обычно RPS — Requests Per Request/Second).
*   **Response Time (Latency):** Время, которое требуется серверу, чтобы обработать запрос и вернуть ответ. Важно смотреть не на среднее значение, а на **percentiles** (90th, 95th, 99th). *Среднее значение — это ложь.*
*   **Error Rate:** Процент запросов, завершившихся с ошибками (4xx, 5xx) относительно общего количества.

### 2. Типы нагрузочных тестов
В SoapUI ты можешь настраивать разные сценарии:
1.  **Load Test:** Проверка работы при ожидаемой (нормальной) нагрузке.
2.  **Stress Test:** Постепенное увеличение нагрузки до тех пор, пока система не начнет выдавать ошибки или не упадет. Ищем «точку разлома».
3.  **Soak / Endurance Test:** Длительный тест (часы или даже сутки) при умеренной нагрузке. Цель — найти **Memory Leaks** (утечки памяти) и переполнение диска логами.
4.  **Spike Test:** Резкое, внезапное увеличение нагрузки (имитация распродажи или хайпа). Проверяем, как система справляется с резким наплывом.

### 3. Алгоритм проведения теста в SoapUI
1.  **Подготовка сценария:** Создаешь обычный `Test Case` с нужными запросами и проверками (Assertions).
2.  **Создание Load Test:** Правой кнопкой по Test Case $\rightarrow$ *New Load Test*.
3.  **Конфигурация параметров:**
    *   Указываешь количество **Threads** (VU).
    *   Указываешь **Ramp-up time**.
    *   Выбираешь тип нагрузки (например, запуск на определенное время или количество итераций).
4.  **Запуск и мониторинг:** Запускаешь тест и следишь за графиками в реальном времени.

### 4. Senior Nuances (На что смотреть, чтобы не облажаться)
*   **Client-side Bottleneck:** Самая частая ошибка новичка — когда тормозит не сервер, а твой компьютер/ноутбук. Если CPU твоего ПК загружен на 100%, результаты теста — мусор. *Решение: запускай тесты с мощных машин или из облака.*
*   **Data Dependency:** Если ты гоняешь 100 пользователей, которые все используют один и тот же `user_id`, ты тестируешь не нагрузку на систему, а блокировки (locks) в базе данных на одну строку. *Решение: используй разные данные для каждого потока (через файлы или динамические переменные).*
*   **Warm-up Period:** Серверу нужно время, чтобы «прогреться» (заполнить кэши, JIT-компиляция). Первые запросы всегда будут медленнее. Всегда игнорируй результаты первых минут теста при анализе стабильности.
*   **Network Latency:** Если ты тестируешь API из другого города/страны, задержка сети может быть больше, чем время обработки запроса сервером.

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем разница между Load и Stress тестом?**
**О:** Load test проверяет работу в пределах нормы (как написано в SLA), а Stress test — где находится предел возможностей системы и как она восстанавливается после падения.

**В: Что важнее: Average Response Time или 95th Percentile?**
**О:** Однозначно 95th (или 99th) percentile. Среднее значение может быть отличным, если 90% запросов прошли за 10мс, а остальные 10% — за 10 секунд. Перцентиль покажет нам реальную картину «плохого» опыта пользователей.

**В: Что делать, если во время теста растет Error Rate?**
**О:** Сначала проверить логи сервера. Если ошибки 5xx — значит, сервис не справляется (перегрузка CPU/RAM или БД). Если ошибки 4xx — возможно, твои данные в тесте некорректны или закончились ресурсы (например, токены).

**В: Можно ли использовать SoapUI для полноценного Performance Testing?**
**О:** Для функционального нагрузочного тестирования API — да. Но для очень высоких нагрузок (десятки тысяч RPS) лучше использовать специализированные инструменты вроде **JMeter** или **Gatling**, так как SoapUI потребляет много ресурсов самого клиента.

# 🧠 Тема: Позитивные и негативные сценарии (Happy Path & Sad Path)

В тестировании API мы делим все проверки на две большие группы. Если ты проверяешь только позитивные — ты просто подтверждаешь, что система работает. Если ты проверяешь негативные — ты проверяешь, насколько система **живучая** и **безопасная**.

---

### 1. Позитивные сценарии (Happy Path)
**Цель:** Проверить, что API выполняет свою основную функцию при идеальных условиях. Мы ожидаем, что всё пройдет по плану, данные сохранятся, а сервер ответит «ОК».

**Что именно проверяем:**
*   **Статус-код успеха:** Ожидаем `200 OK`, `201 Created` или `204 No Content`.
*   **Корректность структуры (Schema):** Все ли поля на месте? Правильные ли типы данных (string, number, boolean)? Не пропал ли массив?
*   **Соответствие бизнес-логике:** Если мы создали пользователя, то в ответе должен быть именно тот ID и те данные, которые мы отправили.
*   **Заголовки (Headers):** Правильный `Content-Type`, наличие необходимых метаданных.

**Пример:** Отправляем POST `/users` с валидным JSON $\rightarrow$ Получаем `201 Created` $\rightarrow$ Проверяем, что в теле ответа пришел созданный объект с нужным `id`.

---

### 2. Негативные сценарии (Sad Path / Edge Cases)
**Цель:** Найти слабые места. Мы намеренно «ломаем» запрос, чтобы убедиться, что API не «падает» с ошибкой 500, не выдает лишних данных и корректно сообщает об ошибке.

**Основные группы негативных тестов:**

#### А. Ошибки входных данных (Input Validation)
*   **Missing Fields (Пропущенные поля):** Удаляем обязательное поле (например, `email`) из JSON. Ожидаем `400 Bad Request`.
*   **Wrong Data Type (Неверный тип):** Вместо числа в поле `age` отправляем строку `"old"`. Ожидаем `400 Bad Request`.
*   **Boundary Values (Граничные значения):** Если поле принимает пароль от 8 до 20 символов, проверяем 7 и 21 символ.
*   **Empty/Null values:** Отправляем пустую строку `""` или `null` там, где это запрещено.
*   **Format Violation:** Невалидный email (без `@`), неверный формат даты (не ISO).

#### Б. Ошибки авторизации и безопасности (Auth & Security)
*   **No Auth:** Запрос без токена/логина. Ожидаем `401 Unauthorized`.
*   **Invalid/Expired Token:** Используем старый или поддельный токен. Ожидаем `401 Unauthorized`.
*   **Insufficient Permissions (RBAC):** Пользователь с ролью `USER` пытается удалить данные через запрос, доступный только `ADMIN`. Ожидаем `403 Forbidden`.

#### В. Ошибки бизнес-логики и ресурсов (Business Logic)
*   **Resource Not Found:** Запрос на несуществующий ID (`GET /users/999999`). Ожидаем `404 Not Found`.
*   **Conflict/Duplicate:** Попытка зарегистрировать пользователя с email, который уже есть в базе. Ожидаем `409 Conflict`.
*   **State Violation:** Попытка отменить заказ, который уже был доставлен.

#### Г. Ошибки протокола и инфраструктуры (Protocol & Server)
*   **Malformed JSON:** Намеренно ломаем синтаксис (забываем кавычку или запятую). Ожидаем `400 Bad Request`.
*   **Wrong Content-Type:** Отправляем XML вместо JSON. Ожидаем `415 Unsupported Media Type`.

---

### 💡 Senior Nuances (Нюансы, о которых забывают джуны)

1.  **Не смотри только на статус-код!** Это самая частая ошибка. Если пришел `400 Bad Request`, обязательно проверь **тело ответа**. Хорошее API должно сказать: *"Ошибка в поле 'email': неверный формат"*, а не просто *"Error"*.
2.  **Проверяй "побочные эффекты".** Если ты сделал негативный запрос (например, создание пользователя с ошибкой), убедись, что в базе данных **не появился** этот кривой пользователь. Негативный тест должен не только вернуть ошибку, но и не испортить состояние системы.
3.  **Idempotency (Идемпотентность).** Проверь, что повторный запрос одного и того же `PUT` или `DELETE` не приводит к непредсказуемым результатам.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что важнее: позитивные или негативные тесты?**
**О:** Они равноценны, но имеют разные цели. Позитивные подтверждают *функциональность*, негативные — *надежность и безопасность*. В реальном проекте 70% времени может уходить на проработку сложных негативных сценариев.

**В: Если я получил 500 Internal Server Error при негативном тесте — это успех или баг?**
**О:** Это **критический баг**. Негативный тест должен возвращать 4xx (ошибку клиента). 500-я ошибка означает, что сервер "упал", не сумел обработать ошибку и "вскрыл кишки" своего кода.

**В: Как понять, какие поля проверять на границы?**
**О:** Смотри в документацию (Swagger/OpenAPI). Если там указаны ограничения (`minLength`, `maximum`), это твои главные цели для тестов. Если ограничений нет — создавай их сам, проверяя экстремально большие и пустые значения.

# 🧠 Шпаргалка: Граничные значения (Boundary Value Analysis — BVA)

**Граничные значения** — это техника тест-дизайна, основанная на предположении, что ошибки чаще всего прячутся не в середине диапазона, а на его «краях». Если программа работает правильно внутри диапазона, то с высокой вероятностью она будет работать и там. Но именно на границах программисты чаще всего ошибаются в условиях (например, используют `<` вместо `<=`).

### 🎯 Суть метода
Вместо того чтобы проверять все возможные числа (что невозможно), мы выбираем только критические точки: **минимум**, **максимум** и значения, которые находятся **сразу за пределами** этих границ.

---

### 🛠 Применение в API (Postman/SoapUI)

Когда ты тестируешь JSON-запрос или параметры URL, ты проверяешь не просто «текст», а конкретные типы данных с их ограничениями.

#### 1. Числовые поля (Integer, Float)
*Пример: поле `age` должно быть от 18 до 99.*
*   **Нижняя граница:** `17` (невалидно), `18` (валидно), `19` (валидно).
*   **Верхняя граница:** `98` (валидно), `99` (валидно), `100` (невалидно).

#### 2. Строковые поля (String length)
*Пример: `username` от 3 до 20 символов.*
*   **Нижняя граница:** 2 символа (ошибка), 3 символа (ок), 4 символа (ок).
*   **Верхняя граница:** 19 символов (ок), 20 символов (ок), 21 символ (ошибка).

#### 3. Массивы и коллекции (Array size)
*Пример: заказ должен содержать от 1 до 5 товаров.*
*   **Тесты:** Пустой массив `[]` (ошибка), массив с 1 элементом (ок), массив с 5 элемента (ок), массив с 6 элементами (ошибка).

#### 4. Даты и время (Date/Time)
*Пример: дата бронирования должна быть не ранее сегодняшнего дня.*
*   **Тесты:** Вчерашняя дата (ошибка), Сегодня (ок), Завтра (ок).

---

### ⚠️ Нюансы от Senior-а (На что смотреть внимательно)

1.  **Метод 3-х точек vs 2-х точек:**
    *   *2-point BVA:* Проверяем только саму границу и значение за ней (например, `18` и `17`).
    *   *3-point BVA (Рекомендую):* Проверяем `boundary - 1`, `boundary`, и `boundary + 1`. Это дает гораздо более полную уверенность.

2.  **Связка с Эквивалентным Разделением (Equivalence Partitioning):**
    BVA никогда не используется в одиночку. Сначала ты делишь все входные данные на группы (классы эквивалентности), а потом внутри каждой группы выбираешь границы. **Не пытайся тестировать только границы, если не проверил хотясь бы одно значение из середины класса.**

3.  **Ошибка "Off-by-one" (Ошибка на единицу):**
    Это классика. Разработчик написал `if (age > 18)` вместо `if (age >= 18)`. В итоге 18-летние пользователи не могут зарегистрироваться. Твоя задача — «поймать» этот баг именно тестом на число `18`.

4.  **Комбинированные границы:**
    Если у тебя есть два поля, зависящих друг от друга (например, `startDate` и `endDate`), граница одного поля становится условием для другого. Тестируй случаи, когда `startDate == endDate`.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между Boundary Value Analysis и Equivalence Partitioning?**
**О:** EP — это процесс разделения данных на группы (классы), где все значения внутри группы считаются одинаковыми для системы. BVA — это техника выбора конкретных значений из этих групп, фокусирующаяся именно на краях.

**В: Что делать, если диапазон бесконечный (например, поле `price` может быть любым положительным числом)?**
**О:** Мы всё равно ищем границы. В данном случае граница — это `0`. Тестируем: `-1` (ошибка), `0` (зависит от требований, обычно ошибка), `0.01` (валидно).

**В: Можно ли использовать BVA для тестирования текстовых полей без ограничения по длине?**
**О:** Если ограничений нет, то BVA не применяется. Но в реальности у любого поля есть предел (размер базы данных, буфер сервера). Senior-подход: найди скрытую границу (например, 255 или 1000 символов) и проверь её.

# 🛡️ Шпаргалка: Тестирование безопасности (Security Testing) API

**Суть:** Мы проверяем не то, *работает* ли функция, а то, как её можно *сломать*, чтобы получить доступ к чужим данным или вывести систему из строя. В API безопасность — это проверка трех столпов: **Аутентификация**, **Авторизация** и **Целостность данных**.

---

### 1. Аутентификация (Authentication) — «Кто ты?»
Проверяем, насколько надежно система узнает пользователя.

*   **Слабые механизмы:** Проверка использования простых методов (Basic Auth без HTTPS) или отсутствие проверки срока действия токена (JWT).
*   **Token Expiration:** Что будет, если использовать старый/протухший токен? (Должен быть `401 Unauthorized`).
*   **Brute Force:** Можно ли бесконечно подбирать пароль/токен? Проверяем наличие блокировки после N неудачных попыток.
*   **Credential Leakage:** Не передаются ли логин/пароль в теле запроса (Body) или URL (Query Params)? *Правило: Только в Header или защищенном Body.*

### 2. Авторизация (Authorization) — «Что тебе можно?»
Самая критическая зона. Даже если я вошел в систему, я не должен видеть чужое.

*   **BOLA / IDOR (Broken Object Level Authorization):** Самая частая дыра. 
    *   *Пример:* Ты запрашиваешь `/api/user/123`. Меняешь `123` на `124`. Если ты видишь данные другого юзера — это критический баг.
*   **BFLA (Broken Function Level Authorization):** Попытка вызвать «админскую» функцию с правами обычного пользователя.
    *   *Пример:* Обычный юзер шлет `DELETE /api/admin/delete-user`. Должен быть `403 Forbidden`.
*   **Privilege Escalation:** Проверка, можно ли через манипуляцию параметрами (например, в JSON: `"role": "user"` $\to$ `"role": "admin"`) повысить свои права.

### ript 3. Валидация входных данных (Injection & Payload)
Проверяем, как API реагирует на «мусор» и вредоносный код.

*   **SQL Injection:** Вставка SQL-команд в параметры запроса (`' OR 1=1 --`). Проверяем, не падает ли база и не выдает ли лишнего.
*   **XXE (XML External Entity):** *Критично для SoapUI/SOAP.* Попытка подсунуть в XML-запрос ссылку на внутренний файл сервера. Если сервер «выплюнет» содержимое файла в ответе — это провал.
*   **Mass Assignment:** Когда ты отправляешь в `POST` запросе лишние поля, которые не должен менять (например, `is_admin: true`), и сервер их принимает.
*   **Command Injection:** Попытка выполнить системную команду ОС через параметры API.

### 4. Утечка информации (Information Disclosure)
Проверяем, не слишком ли много «доброты» проявляет сервер.

*   **Verbose Error Messages:** Ошибки типа `Stack Trace` или `Internal Server Error: Database connection failed at IP 192.168...`. Это подарок для хакера. Должен быть нейтральный `500 Internal Server/Error`.
*   **Sensitive Data in Headers/URL:** Проверка, не светятся ли токены, PII (персональные данные) или ключи в заголовках или логах сервера.
*   **HTTP Headers Security:** Наличие защитных заголовков (`Strict-Transport-Security`, `X-Content-Type-Options`, `Content-Security-Policy`).

### 5. Доступность и лимиты (Availability)
*   **Rate Limiting:** Проверяем, что API ограничивает количество запросов с одного IP/токена. Если нет — можно устроить DoS-атаку (завалить сервис запросами).

---

### 💡 Нюансы от Senior'а (На что обратить внимание)

1.  **Логирование:** Безопасность — это не только API, но и то, что пишет сервер в логи. Если разработчик логирует `Authorization: Bearer <token>` в plain text — это дыра.
2.  **Разница между 401 и 403:** Это классика. **401** — "Я тебя не знаю" (проблема с ID/паролем). **403** — "Я тебя знаю, но тебе сюда нельзя" (проблема с правами). В тестах Postman всегда проверяй правильность этого кода.
3.  **Скрытые методы:** Иногда разработчики забывают закрыть метод `OPTIONS` или `TRACE`, что может помочь злоумышленнику в атаках типа XSS.

### ❓ FAQ (Частые вопросы на интервью)

**В: В чем разница между тестированием безопасности и тестированием функциональности?**
**О:** Функциональное тестирование проверяет, *делает ли API то, что должно*. Тестирование безопасности проверяет, *не делает ли API того, чего делать не должен* (например, выдает чужие данные).

**В: Что такое IDOR и как ты его протестируешь в Postman?**
**О:** Это попытка доступа к ресурсу через подмену ID. В Postman я создам две коллекции/окружения: одно для `User_A`, другое для `User_B`. Я возьму запрос `GET /profile/{id}` от `User_A` и попробую выполнить его, используя токен (Auth Header) от `User_B`, но подставив `id` пользователя `A`.

**В: Как протестировать XXE в SoapUI?**
**О:** Я подготовлю XML-запрос, в котором внутри сущности (`ENTITY`) пропишу путь к чувствительному файлу (например, `/etc/passwd`). Если в ответе на этот запрос я увижу содержимое этого файла — значит, уязвимость присутствует.

**В: Какие заголовки безопасности ты проверяешь в первую очередь?**
**О:** `Strict-Transport-Security` (HSTS) для принудительного HTTPS, `X-Content-Type-Options: nosniff` для предотвращения MIME-sniffing, и `Content-Security-Policy` (CSP).

# 🚀 Тестирование производительности (Performance Testing)

**Суть:** Если функциональное тестирование отвечает на вопрос *"Работает ли фича?"*, то тестирование производительности отвечает на вопросы: *"Как быстро она работает?"*, *"Сколько пользователей она выдержит?"* и *"Когда всё упадет?"*.

### 1. Ключевые метрики (Что мы измеряем)
Нельзя сказать «работает медленно». Нужно оперировать цифрами:
*   **Response Time (Время ответа):** Время с момента отправки запроса до получения последнего байта ответа.
    *   *Latency (Задержка):* Время на "путь" пакета до сервера и обратно.
    *   *TTFB (Time to First Byte):* Время до получения первого байта (важно для понимания скорости обработки сервера).
*   **Throughput (Пропускная способность):** Количество запросов, которые система обрабатывает в единицу времени (обычно **RPS** — Requests Per Second или **TPS** — Transactions Per Second).
*   **Error Rate (Уровень ошибок):** Процент запросов, завершившихся неудачей (4xx, 5xx ошибки) при нагрузке. Если он растет вместе с числом пользователей — вы нашли предел.
*   **Resource Utilization:** Нагрузка на "железо" сервера (CPU, RAM, Disk I/O, Network bandwidth).

### 2. Виды нагрузочного тестирования
Многие путают эти понятия, но для Senior-а разница критична:
1.  **Load Testing (Нагрузочное):** Проверка системы под *ожидаемой* нормальной нагрузкой. Цель — убедиться, что SLA (Service Level Agreement) соблюдается.
2.   **Stress Testing (Стресс-тест):** Постепенное увеличение нагрузки выше нормы до момента, пока система не начнет деградировать или упасть. Цель — найти «точку излома» (breaking point).
3.  **Spike Testing (Тест на скачок):** Резкое, внезапное увеличение нагрузки (например, старт распродажи). Проверяем, насколько быстро система "захлебнется" и сможет ли она восстановиться после спада.
4.  **Soak / Endurance Testing (Тест на выносливость):** Длительная нагрузка в течение долгого времени (часы или дни). Цель — найти **утечки памяти (memory leaks)** или переполнение диска/логов.
5.  **Scalability Testing (Тест масштабируемости):** Проверка того, как добавление ресурсов (CPU/RAM) помогает увеличить пропускную способность.

### 3. Инструментарий
*   **Postman:** Плохо подходит для серьезного нагрузочного тестирования. Можно использовать *Collection Runner* с большим количеством итераций, но это скорее "микро-нагрузка". Позволяет лишь замерить время одного запроса.
*   **SoapUI:** Имеет встроенные возможности для Load Testing (умеет имитировать много пользователей). Хорош для более тяжелых протоколов (SOAP/XML).
/
*   **JMeter / k6 / Gatling:** Индустриальные стандарты. Если проект серьезный — используются они. Они умеют распределять нагрузку с нескольких машин.

### 4. Нюансы и "Подводные камни" (Senior Level)
*   **Warm-up (Прогрев):** Первые запросы всегда медленные (заполнение кэшей, инициализация соединений в пуле БД). **Никогда не включай результаты первых минут теста в отчет!** Сначала нужно "прогреть" систему.
*   **Data Preparation:** Если ты тестируешь один и тот же `GET /user/1` миллион раз, результат будет ложным, так как данные будут лежать в кэше БД или CDN. Нужно использовать разные ID (параметризация).
*   **Test Environment:** Тестировать нагрузку на своей локальной машине — ошибка. Твой ноутбук станет "бутылочным горлышком" раньше, чем сервер. Тесты должны идти из среды, максимально близкой к Prod.
*   **Bottleneck (Узкое место):** Это не всегда сервер. Это может быть медленный запрос в БД, нехватка портов на сетевом оборудовании или лимит соединений в Load Balancer'е.

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между Load и Stress тестированием?**
**О:** Load — проверяем, справляется ли система с *плановой* нагрузкой. Stress — пытаемся её *сломать*, превышая план, чтобы понять запас прочности.

**В: Что делать, если при увеличении нагрузки растет Response Time?**
**О:** Это нормальный процесс (очереди на обработку растут), но важно отследить момент, когда рост становится экспоненциальным. В этот момент нужно смотреть в сторону ресурсов: CPU, RAM или блокировок в базе данных.

**В: Можно ли использовать Postman для нагрузочного тестирования?**
**О:** Для проверки производительности одного конкретного эндпоинта (замерить среднее время) — да. Для имитации 1000 одновременных пользователей — нет, он не предназначен для распределенной генерации нагрузки и быстро исчерпает ресурсы твоего ПК.

**В: Что такое "Memory Leak" и как его найти при тестировании?**
**О:** Это когда приложение забирает память, но не отдает её обратно после завершения задачи. Находится через **Soak Testing**: если в течение 12 часов потребление RAM постоянно растет без плато — у вас утечка.

# 📜 Шпаргалка: Контрактное тестирование (Contract Testing)

### 🧠 Что это такое?
**Контрактное тестирование** — это метод проверки того, что два сервиса (Потребитель и Поставщик) «понимают друг друга». 

Представь, что ты заказываешь пиццу через приложение. 
*   **Твой контракт:** «Я присылаю заказ в формате JSON, где есть `size` и `topping`. В ответ я жду статус `200 OK` и подтверждение заказа». 
*   **Суть теста:** Проверить, что бэкенд (Поставщик) не изменил формат ответа так, что приложение (Потребитель) внезапно перестало понимать, приехала пицца или нет.

### 🏗 Основные участники
1.  **Consumer (Потребитель):** Тот, кто вызывает API (Frontend, Mobile app, другой Microservice). Он диктует правила: «Мне нужно вот это поле в таком-то формате».
2.  **Provider (Поставщик):** Тот, кто отдает данные (Backend/API). Его задача — соответствовать ожиданиям потребителя.
3.  **Contract (Контракт):** Файл (обычно JSON), содержащий описание ожиданий: какие методы вызываются, какие заголовки передаются, какая структура тела ответа и какие значения там должны быть.

### 🔄 Типы контрактного тестирования
*   **Consumer-Driven Contract Testing (CDCT) — Золотой стандарт.** Потребитель сам пишет тесты, которые генерируют контракт. Это самый эффективный подход: бэкенд узнает о том, что он что-то сломал, еще до того, как это попало в прод.
*   **Provider-Driven.** Поставщик говорит: «У меня есть вот такой API». Это менее полезно, так как не учитывает реальные нужды клиентов.

### 🛠 Как проходит процесс (Workflow)
1.  **На стороне Consumer:** Пишем тесты (например, с использованием библиотеки **Pact**). Тест имитирует запрос к API и проверяет ответ. При успешном прохождении генерируется файл-контракт (**Pact file**).
2.  **Публикация:** Контракт отправляется в специальное хранилище — **Pact Broker**.
3.  **На стороне Provider:** Бэкенд подтягивает контракт из Broker, «прогоняет» его через свой реальный код и проверяет: «Могу ли я удовлетворить эти требования?».
4.  **Результат:** Если бэкенд изменил поле `user_id` на `id`, тест на стороне Provider упадет. **Boom!** Мы поймали баг до деплоя.

### ⚖️ Контрактное vs Интеграционное тестирование
| Характеристика | Интеграционное тестирование | Контрактное тестирование |
| :--- | :---ing | :--- |
| **Сложность** | Высокая (нужно поднять все сервисы, БД) | Низкая (сервисы тестируются изолированно) |
| **Скорость** | Медленно (зависит от сети и окружения) | Очень быстро |
| **Стабильность** | Часто «флакают» (flaky tests) из-за сети/БД | Стабильно (тест не зависит от внешних факторов) |
| **Цель** | Проверить бизнес-логику и связи | Проверить совместимость интерфейсов |

### ⚠️ Нюансы и «подводные камни»
*   **Не заменяет интеграционные тесты:** Контрактное тестирование не проверяет, правильно ли работает база данных или логика расчёта скидки. Оно проверяет только **форму** данных.
*   **Слишком строгие контракты:** Если потребитель пропишет в контракте проверку на конкретное значение (например, `name: "Ivan"`), то любое изменение имени в БД сломает тест. Контракт должен провервать **тип** и **структуру**, а не конкретные бизнес-данные.
*   **Управление версиями:** Важно использовать **Pact Broker** и механизм `can-i-deploy`, чтобы автоматически проверять совместимость версий перед деплоем в прод.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Можно ли заменить контрактное тестирование обычным Schema Validation (например, JSON Schema)?**
**О:** Частично — да. Schema Validation проверяет только структуру (есть ли поле `id` и является ли оно числом). Контрактное тестирование (особенно CDCT) идет дальше: оно проверяет именно *взаимодействие* и гарантирует, что потребитель не использует поля, которые поставщик планирует удалить.

**В: Что такое "Breaking Change" в контексте контракта?**
**О:** Это любое изменение, которое ломает текущего потребителя. Примеры: удаление поля, переименование поля, изменение типа данных (был `int`, стал `string`), изменение обязательности поля (было `optional`, стало `required`).

**В: Когда НЕ нужно внедрять контрактное тестирование?**
**О:** Если у вас монолитная архитектура. В монолите изменения сразу видны при компиляции/запуске тестов. Контрактное тестирование раскрывает свою мощь только в **микросервисной архитектуре**, где сервисы живут своей жизнью и деплоятся независимо.

**В: Какие инструменты использовать?**
**О:** Самый популярный и стандарт индустрии — **Pact**. Также есть возможности реализации через Spring Cloud Contract (для Java-стека).

# 📘 Шпаргалка: OpenAPI (Swagger) Specification

### 1. Что это такое? (Суть)
Представь, что ты заказываешь пиццу через приложение. Ты не лезешь на кухню смотреть, как крутят тесто, ты смотришь в **меню**. 
**OpenAPI** — это и есть то самое «меню» для API. Это стандарт описания RESTful API. Он описывает:
* Какие есть эндпоти (URL).
* Какие методы можно использовать (GET, POST и т.д.).
* Что нужно отправить в запросе (параметры, заголовки, тело).
* Что ты получишь в ответ (структуру JSON, коды ответов).

**Важный нюанс (Senior level):** Не путай **OpenAPI** и **Swagger**. 
* **OpenAPI** — это *стандарт/спецификация* (набор правил, как писать описание).
* **Swagger** — это *набор инструментов* для работы с этим стандартом (Swagger UI для визуализации, Swagger Editor для написания, Swagger Codegen для генерации кода).

---

### 2. Анатомия документа (Основные блоки)
Хорошая спецификация состоит из нескольких ключевых разделов:

1.  **`openapi`**: Версия стандарта (например, `3.0.3`). Важно, так как синтаксис меняется от версии к версии.
2.  **`info`**: Метаданные. Название API, версия самого API, описание и контакты разработчиков.
3.  **`servers`**: Список URL-адресов, где живет API (dev, staging, production). 
    * *Нюанс:* Если здесь указан только `localhost`, ты не сможешь протестировать API в облаке или через Postman без правки документации.
4.  **`paths`**: Самая важная часть. Список всех эндпоинтов. Для каждого пути прописаны:
    * **Parameters**: Query, Path, Header или Cookie параметры.
    * **Request Body**: Какого типа данные (JSON/XML) и какая у них структура.
    * **Responses**: Какие статус-коды ожидаются (200, 400, 500) и как выглядит тело ответа.
5.  **`components`**: Секция для переиспользования кода (**DRY — Don't Repeat Yourself**). Здесь описываются `schemas` (модели данных), `securitySchemes` (как авторизоваться) и общие параметры. 
    * *Зачем это QA:* Если ты видишь, что объект `User` описан в `components/schemas`, значит, он используется во многих запросах. Это упрощает проверку структуры.

---

### 3. Зачем это нужно Тестировщику? (QA Value)
Спецификация — это твой **Contract (Контракт)**.

*   **Contract Testing:** Ты проверяешь не просто «пришел ли ответ», а «соответствует ли ответ контракту». Если в Swagger написано, что `age` — это `integer`, а пришла строка `"25"`, — это баг.
*   **Генерация тестов:** На основе OpenAPI можно автоматически генерировать коллекции в Postman или скрипты для проверки типов данных.
*   **Design-First Approach:** Если разработчики сначала пишут Swagger, а потом код, ты можешь начать писать автотесты **до того**, как бэкенд вообще будет готов.

---

### 4. Тонкие моменты и "подводные камни" (Senior Insights)
*   **Documentation Drift (Дрифт документации):** Самая частая проблема. Код изменился (добавили поле), а Swagger не обновили. В этом случае документация становится бесполезной и даже вредной. **Всегда проверяй актуальность.**
*   **Breaking Changes (Ломающие изменения):** Если в спецификации удалили обязательное поле или изменили тип данных — это критический баг, который «положит» всех клиентов (фронтенд, мобилки).
*   **Missing Constraints:** Плохая спецификация — это когда описан тип (`string`), но не указаны ограничения: `minLength`, `maxLength`, `pattern` (regex) или `enum`. Без этих данных ты не сможешь провести полноценное граничное тестирование.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между OpenAPI 2.0 и 3.0?**
**О:** Основные отличия в структуре. В 3.0 появилась более гибкая работа с `requestBody`, разделение параметров на `path` и `query` стало логичнее, и появилась поддержка нескольких серверов (`servers`) вместо одного `host`. Также улучшена работа с переиспользуемыми компонентами.

**В: Что такое "Contract Testing" в контексте Swagger?**
**О:** Это процесс проверки того, что фактический ответ сервера (Response) на 100% совпадает с тем, что описано в файле спецификации (типы данных, обязательные поля, структура). Если несоответствие есть — контракт нарушен.

****В: Как проверить API на соответствие Swagger через Postman?**
**О:** Можно использовать библиотеку `ajv` (JSON Schema Validator) прямо в скриптах тестов Postman. Ты берешь JSON-схему из раздела `components/schemas` твоего Swagger и проверяешь полученный ответ с помощью `pm.expect(response).to.be.valid(schema)`.

**В: Что делать, если в Swagger поле помечено как `required`, но API его не присылает?**
**О:** Это баг реализации (Implementation Bug). С точки зрения контракта, клиент ожидает это поле для работы своей логики. Нужно заводить баг-репорт на несоответствие документации и кода.

# 📑 Шпаргалка: Интеграция Postman/Newman с Jira и TestRail

### 🎯 Зачем это нужно? (The Big Picture)
В тестировании API мало просто «прогнать коллекцию». Результаты должны быть видимы всем: разработчикам, мануальным тестировщикам и менеджерам. 
**Цель интеграции:** Создать **Traceability (Прослеживаемость)**. 
*   `Тест-кейс в TestRail` $\leftrightarrow$ `Автотест в Postman` $\leftrightarrow$ `Баг в Jira`.

---

### 1. Интеграция с Jira: Управление дефектами
Jira сама по себе — это не инструмент тестирования, это трекер задач. Чтобы связать её с Postman, есть два пути:

#### А. Использование специализированных плагинов (Xray / Zephyr) — *Путь Senior*
Если в компании используют **Xray** или **Zephyr**, Jira превращается в мощную систему управления тестами.
*   **Как это работает:** Ты запускаешь коллекцию через **Newman** (CLI версия Postman). Результаты теста (в формате JUnit XML) отправляются через API напрямую в Xray/Zeint.
*   **Результат:** В самой задаче Jira автоматически обновляется статус: «Test Passed» или «Test Failed».

#### Б. Автоматическое создание багов (Custom Scripting) — *Путь Hardcore*
Ты можешь написать скрипт (на Node.js или прямо в Postman через `pm.sendRequest`), который при падении теста в Newman делает `POST` запрос к Jira API.
*   **Нюанс:** Не делай это для каждого упавшего теста! Если у тебя упадет 100 тестов из-за одного сломанного сервера, ты заспамишь Jira 100 багами (это называется *Bug Storm*). Настрой логику так, чтобы создавался только один баг с группировкой.

---

### 2. Интеграция с TestRail: Управление результатами
TestRail — это место, где живут твои тест-кейсы. Тебе нужно, чтобы после прогона коллекции в Postman, статус кейсов в TestRail обновлялся сам.

#### Механика интеграции (Newman $\to$ TestRail API)
Поскольку Postman не умеет «из коробки» стучаться в TestRail, используется промежуточное звено:
1.  **Запуск:** Ты запускаешь коллекцию через **Newman**.
2.  **Генерация отчета:** Newman генерирует отчет (например, в формате JSON или JUnit).
3.  **Скрипт-прослойка:** Небольшой скрипт (на Python или JS) парсит этот отчет и использует **TestRail API** (метод `add_result_for_case`), чтобы отправить результат каждого теста.

**Что передаем:**
*   `test_run_id`: ID текущего прогона в TestRail.
*   `case_id`: ID тест-кейса, который соответствует этому запросу в Postman.
*   `status_id`: Результат (Passed/Failed).
*   `comment`: Текст ошибки из ответа API.

---

### 💡 Нюансы и «Подводные камни» (Senior Tips)

1.  **Hardcoded Data — это грех:** Никогда не храни API-ключи от Jira или TestRail в теле скрипта или в коллекции. Используй **Environment Variables** или секреты твоего CI/CD (Jenkins/GitLab).
2.  **Mapping (Сопоставление):** Самая сложная часть — это связать `ID запроса в Postman` с `ID кейса в TestRail`. 
    *   *Лайфхак:* Используй кастомные переменные в Postman (например, `testrail_id: 1234`). Скрипт при прогоне будет забирать это значение и знать, какой кейс обновить.
3.  **Flaky Tests (Нестабильные тесты):** Если тест упал из-за сетевого лага, а интеграция тут же создала баг в Jira — это плохой процесс. Всегда добавляй этап **Retry** (повторного запуска) перед тем, как отправлять отчет в системы управления.
4.  **Single Source of Truth:** Интеграция должна дополнять, а не дублировать. Если у тебя всё есть в Postman, не заставляй команду вручную копипастить логи в Jira.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Как связать конкретный запрос в Postman с багом в Jira?**
**О:** Через использование уникальных идентификаторов. В запросе можно хранить `issue_key` или использовать теги. При падении теста скрипт берет этот ключ и прикрепляет его к создаваемому тикету.

**В: Что делать, если Newman упал, а интеграция с TestRail не успела отработать?**
**О:** Нужно использовать механизмы `always` (в Postman это блок `test` или обработка завершения процесса в CI/CD). Отчет должен отправляться по завершении *всей* коллекции, а не после каждого запроса.

**В: Можно ли использовать Postman Interceptor для этой задачи?**
**О:** Нет, Interceptor предназначен для перехвата трафика (просмотра того, что летит в браузере). Для интеграции с системами управления тестированием нам нужен **Newman** и работа с **API** этих систем.

**В: В чем разница между автоматизацией багов и автоматизацией результатов?**
**О:** Автоматизация багов — это создание тикета при ошибке (Jira). Автоматизация результатов — это обновление статуса тест-кейса (TestRail/Xray) на "Passed" или "Failed". Это разные задачи.

# 🐳 Шпаргалка: Docker для QA Automation

### 1. Суть простыми словами
Представь, что тебе нужно протестировать API, но для этого требуется база данных, Redis и Mock-сервер. Вместо того чтобы устанавливать всё это на свой компьютер (и мучиться с конфликтами версий), ты берешь **Docker-контейнер**.

*   **Образ (Image)** — это «слепок» или чертеж (как установочный файл `.exe`). В нем записано всё: ОС, установленный Node.js, Newman и твоя коллекция.
*   **Контейнер (Container)** — это запущенный экземпляр образа. Живой процесс, который работает в изоляции.
*   **Dockerfile** — инструкция (рецепт), как собрать образ.
*   **Docker Compose** — инструмент для запуска сразу нескольких контейнеров одной командой (например: API + DB + Newman).

---

### 2. Основные команды (Твой «джентльменский набор»)

#### Работа с контейнерами:
*   `docker ps` — список всех **запущенных** контейнеров.
*   `docker ps -a` — список **всех** контейнеров (даже остановленных). *Важно для поиска упавших тестов.*

*   `docker run <image_name>` — запустить контейнер из образа.
*   `docker stop <container_id>` — остановить контейнер.
*   `docker rm <container_id>` — удалить контейнер (после остановки).
*   `docker logs <container_id>` — **самая важная команда**. Посмотреть, что вывел Newman или твой API внутри контейнера.
*   `docker exec -it <container_id> sh` — «зайти» внутрь работающего контейнера (как через SSH), чтобы проверить файлы или сетевую доступность.

#### Работа с образами:
*   `docker images` — список всех скачанных образов.
*   `docker pull <image_name>` — скачать образ из Docker Hub (например, `node` или `postman/newman`).
*   `docker rmi <image_id>` — удалить образ.

#### Очистка (чтобы не забить диск):
*   `docker system prune` — удалит все остановленные контейнеры и неиспользуемые сети. **Senior-совет:** используй осторожно, это чистит всё лишнее.

---

 la 3. Docker для автоматизации тестов (Newman + Docker)

Когда ты запускаешь Newman в Docker, ты избавляешься от фразы *"У меня на компе тесты проходят, а в Jenkins — нет"*.

**Пример Dockerfile для Newman:**
```dockerfile
# Берем готовый образ с Node.js
FROM node:alpine

# Устанавливаем Newman глобально
RUN npm install -g newman

# Создаем рабочую папку внутри контейнера
WORKDIR /etc/newman

# Копируем твою коллекцию и окружение с твоего компа в контейнер
COPY my_collection.json .
COPY my_environment.json .

# Команда, которая выполнится при запуске контейнера
CMD ["newman", "run", "my_collection.json", "-e", "my_environment.json"]
```

**Как это запустить:**
1. `docker build -t my-tests .` (собираем образ)
2. `docker run my-tests` (запускаем тесты)

---

### 4. Нюансы и «подводные камни» (Senior Insights)

#### ⚠️ Проблема Localhost (Сетевая доступность)
Это самая частая ошибка. Если твой API запущен на твоем компьютере (localhost:8080), а Newman — внутри Docker-контейнера, то для контейнера `localhost` — это **он сам**, а не твой компьютер.
*   **Решение для Windows/Mac:** Используй адрес `host.docker.com` вместо `localhost`.
*   **Решение для Linux:** Используй `--network="host"` при запуске контейнера.

#### 📦 Docker Compose (Оркестрация тестов)
Если тебе нужно поднять окружение "под ключ" (API + Mock-сервер), используй `docker-compose.yml`. Это позволяет одной командой `docker-compose up` развернуть всю инфраструктуру для теста.

#### 📂 Volumes (Проброс папок)
Чтобы не пересобирать образ каждый раз, когда ты изменил один запрос в Postman, используй **Volumes**. Ты "привязываешь" папку со своего компьютера к папке внутри контейнера. Изменил файл — в контейнере он обновился мгновенно.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между Image и Container?**
**О:** Image — это неизменяемый шаблон (чертеж), а Container — это запущенный процесс, созданный на основе этого шаблота (реальный объект).

**В: Как посмотреть логи упавшего теста в Docker?**
**О:** Сначала найти ID контейнера через `docker ps -a`, затем использовать `docker logs <ID>`.

**В: Что делать, если контейнер с тестами не может достучаться до API, который запущен на моей машине?**
**О:** Нужно настроить сетевой мост. Чаще всего — использовать специальный DNS-адрес `host.docker.internal` (для Docker Desktop) или запускать контейнер в режиме `--network="host"`.

**В: Зачем QA использовать Docker, если можно просто запустить Newman через npm?**
**О:** Для обеспечения идентичности сред. Docker гарантирует, что версия Node.js, установленные зависимости и переменные окружения будут **абсолютно одинаковыми** на твоем ноутбуке, у коллеги и на сервере Jenkins/GitLab CI.
