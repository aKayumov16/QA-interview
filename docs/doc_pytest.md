# 🛠 Тема 1: Установка и окружение (Installation & Environment)

### 1. Золотое правило: Изоляция
Никогда, слышишь, **никогда** не устанавливай `pytest` глобально в систему через обычный `pip install pytest`. 

**Почему?** Если ты установишь библиотеку глобально, то при обновлении версии Python или другой библиотеки в системе, твои тесты могут внезапно «отвалиться» из-за конфликта зависимостей.

**Как правильно:** Используй виртуальное окружение (**venv**). Это изолированная папка, где живут только те библиотеки, которые нужны конкретно твоему проекту.

**Команды для старта:**
```bash
# 1. Создаем окружение (называем его .venv)
python -m venv .venv

# 2. Активируем его
# Для Windows:
.venv\Scripts\activate
# Для macOS/Linux:
source .mev/bin/activate

# 3. Теперь устанавливаем pytest внутри этого окружения
pip install pytest
```

### 2. Управление зависимостями
Чтобы твои коллеги (или Jenkins/GitHub Actions) могли запустить тесты, они должны знать, что именно ты установил.
*   **`requirements.txt`**: Классика. Создай его командой `pip freeze > requirements.txt`.
*   **`pyproject.toml`**: Современный стандарт. Если проект серьезный, все настройки (включая pytest) лучше держать здесь.

### 3. Структура проекта и Discovery (Поиск тестов)
PyTest — это «умный» инструмент. Он сам сканирует папки в поисках тестов. Но он ищет по строгому паттерну. Если ты назовешь файл `my_tests.py`, PyTest его **проигнорирует**.

**Правила именования:**
*   **Файлы:** должны начинаться с `test_*.py` или заканчиваться на `*_test.py`.
*   **Функции/Методы:** должны начинаться с `test_`.
*   **Классы:** (если используешь) должны начинаться с `Test` (без слова `TestCase`, это не unittest).

**Рекомендуемая структура:**
```text
my_project/
├── src/                # Исходный код приложения
│   └── app.py
├── tests/              # Папка с тестами
│   ├── __init__.py     # Делает папку пакетом (хороший тон)
│   ├── test_auth.py    # Тесты аутентификации
│   └── test_api.py     # Тесты API
├── .venv/              # Виртуальное окружение
├── requirements.txt    # Список зависимостей
└── pytest.ini          # Конфигурация PyTest (создадим позже)
```

### 4. Запуск тестов: Нюанс с `python -m`
Ты можешь запустить тесты просто командой `pytest`. Но Senior-разработчики часто используют:
```bash
python -m pytest
```
**В чем подвох?** Когда ты запускаешь `pytest`, система ищет исполняемый файл в `PATH`. Если у тебя установлено несколько версий Python, может запуститься не тот pytest. 
Когда ты пишешь `python -m pytest`, ты гарантируешь, что используешь PyTest, который привязан именно к **этому** интерпретатору Python, в котором ты сейчас работаешь. Это избавляет от ошибки `ModuleNotFoundError` при импорте своего кода.

**В: Можно ли использовать разные версии pytest для разных проектов?**

**В: Как быстро проверить, что всё установилось правильно?**
**О:** Выполни команду `pytest --version`. Если выдала версию — ты в деле!

# 🏷️ Тема: Правила именования (Naming Conventions)

В PyTest именование — это не вопрос вкуса или «красоты» кода. Это **техническое требование**. PyTest использует механизм **Discovery** (обнаружение), чтобы найти тесты в твоем проекте. Если ты нарушишь правила, PyTest просто проигнорирует твой код, и ты даже не узнаешь, что тест не запустился.

### 1. Файлы (Test Modules)
Чтобы PyTest понял, что файл содержит тесты, он должен соответствовать одному из шаблонов:
*   `test_*.py` (например, `test_auth.py`) — **Стандарт де-факто**.
*   `*_test.py` (например, `login_test.py`) — Тоже допустимо.

> **Senior Note:** Если ты назовешь файл `my_functions.py`, PyTest его пропустит. Всегда начинай с `test_`.

### 2. Классы (Test Classes)
Если ты группируешь тесты в классы (например, для логической связки), соблюдай правила:
*   Название класса должно начинаться с `Test` (например, `class TestUserRegistration:`).
*   **Важно:** В тестовых классах **не должно быть** метода `__init__`. Если ты добавишь его, PyTest может перестать воспринимать класс как набор тестов.

### 3. Функции и методы (Test Functions/Methods)
Это то, что непосредственно выполняет проверку:
*   Название функции должно начинаться с `test_` (например, `def test_login_success():`).
*   Внутри классов методы также должны называться `test_*`.

---

### 💡 Нюансы и Best Practices (Тонкости)

1.  **Избегай префикса `check_`**: Часто новички пишут `def check_user_is_admin()`. Для PyTest это не тест, а просто вспомогательная функция. Тест **не запустится**.
2.  **Осмысленность вместо краткости**: Не пиши `test_1`, `test_2`. Хорошее имя теста должно отвечать на вопрос: *"Что именно мы проверяем и при каких условиях?"*.
*   ❌ Плохо: `test_login()`
*   ✅ Хорошо: `test_login_with_invalid_password_fails()` (сразу понятно: действие, условие, ожидаемый результат).
3.  **Pattern "Action + Result"**: Старайся придерживаться структуры: `test_[subject]_[condition]_[expected_result]`. Это сэкономит кучу времени при чтении логов после падения тестов в CI/CD.
4.  **Скрытые функции (Helpers)**: Если тебе нужна вспомогательная функция внутри файла с тестами, называй её без префикса `test_` (например, `def create_user():`). Это не запутает PyTest и других разработчиков.

### ❓ FAQ (Частые вопросы)

**В: Я назвал файл `tests.py`, но внутри функции начинаются на `test_`. Почему они не запускаются?**
**О:** Потому что сам файл не прошел проверку Discovery. PyTest ищет файлы по паттерну `test_*.py`. Переименуй в `test_main.py`.

**В: Можно ли использовать `unittest`-стиль (наследование от `unittest.TestCase`)?**
**О:** Можно, PyTest поддерживает его для обратной совместимости. Но в мире PyTest это считается "legacy" подходом. Лучше использовать чистые функции и фикстуры.

**В: Что будет, если я назову класс `TestAuth`, но внутри методы будут называться `check_login`?**
**О:** Тесты внутри класса не будут найдены. Класс будет найден, но он будет воспринят как пустой контейнер, так как в нем нет функций с префиксом `test_`.

**В: Можно ли использовать `pytest.mark.skip` для обхода правил именования?**
**О:** Нет. Маркеры работают только с теми тестами, которые PyTest *уже нашел*. Если имя не соответствует правилам, маркер просто не применится.

# 🚀 Шпаргалка: Запуск тестов (PyTest Execution)

Запуск тестов — это не просто ввод `pytest` в терминале. Это управление процессом: от быстрого локального дебага до эффективного прогона всего регрессионного набора в CI/CD.

### 1. Базовый уровень (Навигация)
*   `pytest` — запустить **все** найденные тесты в текущей директории и поддиректориях.
*   `pytest tests/test_auth.py` — запустить только конкретный файл.
*   `pytest tests/test_auth.py::test_login` — запустить **одну конкретную функцию** (самый частый сценарий при дебаге).
*   `pytest tests/test_auth.py::TestAuthClass::test_login` — запуск конкретного метода внутри класса.

### 2. Фильтрация (Хирургический подход)
Когда тестов тысячи, запускать всё — непозволительная роскошь.
*   `-k "string"` — **Самый мощный инструмент.** Запускает тесты, чьи имена содержат строку.
    *   `pytest -k "login and not logout"` — запустить текс, где есть `login`, но нет `logout`.
    *   `pytest -k "user_id == 5"` — поиск по части имени.
*   `-m "marker"` — запуск тестов, помеченных конкретным маркером (например, `@pytest.mark.smoke`).
    *   `pytest -m smoke` — только дымовые тесты.
    *   `pytest -m "not slow"` — пропустить все медленные тесты.

### 3. Управление выводом (Visibility)
*   `-v` (verbose) — подробный режим. Показывает названия каждого теста (по умолчанию PyTest пишет только точки `.`, `F`, `E`).
*   `-vv` — максимально подробный режим. Полезен, когда нужно увидеть **diff** (разницу) в упавших ассертах (что именно не совпало).
*   `--tb=short` — сокращенный traceback. Если тест упал, тебе не нужны 100 строк логов, достаточно одной строки с ошибкой.
*   `--tb=long` — полный traceback (по умолчанию).
*   `--tb=curve` — «умный» режим: показывает только важные части ошибки.

### 4. Управление жизненным циклом (Efficiency)
*   `-x` или `--exitfirst` — **Stop on failure.** Остановить выполнение сразу после первого упавшего теста. Незаменимо, когда ты правишь баг и не хочешь ждать завершения всей пачки.
*   `-ff` или `--failed-first` — запустить сначала все упавшие тесты (из предыдущего прогона), а потом остальные. Идеально для регрессии.
*   `--maxfail=N` — остановиться после `N` ошибок.
*   `--collect-only` — не запускать тесты, а просто показать список того, что PyTest нашел. Помогает проверить, правильно ли работают пути и сборка (discovery).

### 5. Продвинутые фишки (Pro Level)
*   `-n auto` — **Параллельный запуск** (требуется плагин `pytest-xdist`). Задействует все ядра твоего процессора. Ускоряет тесты в разы.
*   `-W error` — превращает все предупреждения (`Warnings`) в ошибки. Помогает держать код в чистоте и вовремя замечать устаревший (deprecated) функционал.
*   `-c pytest.ini` — запуск с использованием специфического файла конфигурации.

### 💡 Senior Tips (Нюансы)

1.  **Проблема Discovery:** Если ты запустил `pytest`, но твой тест не виден — проверь имя файла и функции. Они **обязаны** начинаться с `test_`. Если файл называется `auth_tests.py` (без префикса), PyTest его проигнорирует.
2.  **Конфликт имен:** Будь осторожен с `-k`. Если ты ищешь `-k "login"`, а у тебя есть тесты `test_login`, `test_logout` и `test_user_login`, то запустятся все три. Используй более специфичные строки.
3.  **Логирование:** По умолчанию PyTest перехватывает логи. Если ты не видишь своих `print()` или `logging.info()`, используй флаг `-s` (отключает перехват вывода), чтобы видеть всё в реальном времени.

# 🚀 Шпаргалка: Простейший Assert в PyTest

### 🧠 Суть концепции
В PyTest тебе **не нужно** учить десятки методов вроде `self.assertEqual`, `self.assertTrue` или `self.assertRaises`, как это было в классическом `unittest`. 

PyTest использует стандартное ключевое слово Python — `assert`. Но здесь происходит магия: PyTest делает **Assertion Rewriting** (перезапись утверждений). Когда тест падает, PyTest "подсматривает" внут-рь твоего `assert` и выводит детальную разницу между тем, что *было*, и тем, что *должно было быть*.

---

### 🛠 Базовый синтаксис
Используй стандартные операторы сравнения Python:
* `==` (равенство), `!=` (неравенство)
* `<`, `>`, `<=`, `>=`
* `is`, `is not` (проверка идентичности объектов в памяти)
* `in`, `not in` (проверка наличия элемента в коллекции)

```python
def test_basic_math():
    assert 2 + 2 == 4
    assert "Pytest" in "Pytest is awesome"
    assert [1, 2] != [1, 3]
```

---

### ✨ Магия детализации (Deep Diff)
Это то, за что мы любим PyTest. Если ты сравниваешь сложные структуры (списки, словари), PyTest покажет **конкретное место**, где данные разошлись.

**Пример падения:**
```python
def test_list_failure():
    expected = [1, 2, 3, 4]
    actual = [1, 2, 9, 4]
    assert actual == expected
```
**Что ты увидишь в консоли:**
PyTest подсветит: `E       - 3` (чего не хватает) и `E       + 9` (что пришло вместо него). Тебе не нужно гадать, какой именно элемент сломался.

---

### 💡 Нюансы и Pro-tips от Senior

#### 1. Кастомные сообщения
Если тест падает в сложном цикле или логике, добавь пояснение через запятую. Это сэкономит время при чтении логов в CI/CD.
```python
def test_with_message():
    user_id = 42
    # Если упадет, ты сразу увидишь: AssertionError: User ID mismatch! Expected 10, got 42
    assert user_id == 10, f"User ID mismatch! Expected 10, got {user_id}"
```

#### 2. Ловушка чисел с плавающей точкой (Floating Point)
**Никогда** не сравнивай `float` напрямую через `==`. Из-за особенностей хранения данных в памяти, `0.1 + 0.2` не будет равно `0.3`.
*   ❌ **Плохо:** `assert 0.1 + 0.2 == 0.3` (упадет)
*   ✅ **Хорошо:** Используй `pytest.approx`

```python
import pytest

def test_float_precision():
    assert 0.1 + 0.2 == pytest.approx(0.3)
```

#### 3. Проверка типов и содержимого
Не ограничивайся только равенством. Часто нужно проверить, что объект *является* списком или словарем.
```python
def test_types():
    data = {"id": 1, "name": "Admin"}
    assert isinstance(data, dict)
    assert "id" in data
```

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Чем `assert` в PyTest лучше, чем в стандартном Python?**
**О:** В обычном Python при падении `assert` ты увидишь только `AssertionError`. PyTest перехватывает этот момент и делает "инспекцию" объектов, выводя подробный Diff (разницу) для списков, словарей и строк.

**В: Что такое `pytest.approx` и зачем он нужен?**
**О:** Это инструмент для безопасного сравнения чисел с плавающей точкой (`float`). Он учитывает небольшую погрешность (epsilon), чтобы избежать ложных падений тестов из-за ошибок округления в двоичной системе.

**В: Можно ли использовать `is` вместо `==` в тестах?**
**О:** С осторожностью. `==` проверяет **значение** (содержимое), а `is` проверяет **адрес в памяти** (идентичность). Для проверки того, что два разных объекта — это один и тот же экземпляр (например, синглтон), используй `is`. Для всего остального — `==`.

**В: Как проверить, что ошибка вообще произошла?**
**О:** Это уже тема следующего уровня (контекстные менеджеры), но помни: для проверки исключений `assert` не используется, используется `with pytest.raises(...)`.

# 🔍 Тема: Discovery (Поиск тестов)

**Discovery** — это автоматический процесс, с помощью которого PyTest сканирует твой проект, находит файлы, классы и функции, которые являются тестами, и строит из них дерево выполнения. Тебе не нужно вручную перечислять каждый тест в консоли; PyTest делает это за тебя по определенным правиму.

### 1. Правила «Золотого стандарта» (Naming Convention)
Чтобы PyTest «увидел» твой код, он должен соответствовать трем уровням именования:

*   **Уровень Файла:** Имя файла должно начинаться с `test_*.py` или заканчиваться на `*_test.py`.
    *   ✅ `test_login.py`, `api_test.py`
    *   ❌ `login_tests.py`, `my_functions.py`
*   **Уровень Класса:** Если ты группируешь тесты в классы, имя класса должно начинаться с `Test`.
    *   ✅ `class TestUserAuth:`
    *   ❌ `class AuthTests:` (PyTest проигнорирует этот класс)
*   **Уровень Функции/Метода:** Самый важный уровень. Имя функции должно начинаться с `test_`.
    *   ✅ `def test_valid_password():`
    *   ❌ `def check_password():`

### 2. Настройка области поиска (Configuration)
В больших проектах у тебя могут быть тысячи файлов (включая `venv`, `node_modules`, `docs`). Если PyTest будет сканировать всё, это будет вечно.

**Как управлять поиском через `pytest.ini` или `pyطject.toml`:**

*   **`testpaths`**: Самый важный параметр. Указывает PyTest, в каких конкретно папках искать тесты. Это ускоряет запуск и исключает лишний шум.
    ```ini
    [pytest]
    testpaths = tests integration_tests
    ```
*   **`norecursedirs`**: Список директорий, которые нужно игнорировать (например, `build`, `dist`, `venv`).
    ```ini
    [pytest]
    norecursedirs = venv .venv docs
    ```
*   **`pythonpath`**: Если твои тесты лежат в папке `tests/`, а код — в `src/`, PyTest может не найти импорты. Этот параметр добавляет папки в `sys.path`.
    ```ini    
    [pytest]
    pythonpath = src
    ```

### 3. Фильтрация во время запуска (CLI Discovery)
Иногда тебе не нужно запускать *все* найденные тесты. Для этого есть мощные флаги:

*   **`-k "keyword"`**: Поиск по ключевому слову. PyTest найдет все тесты, в названии которых есть эта строка. Поддерживает логику `and`, `or`, `not`.
    *   `pytest -k "login and not slow"` — запустит тесты, где есть "login", но нет "slow".
*   **`-a` (do not collect)**: «Грубый» режим. Заставляет PyTest собирать вообще всё, даже то, что не похоже на тест (нарушая правила именования). Используется крайне редко для дебага.
*   **`--collect-only`**: Режим «просмотра». PyTest просто выведет список всех найденных тестов в консоль, но **не будет их запускать**. Незаменимо, когда ты только добавил новые файлы и хочешь проверить, подцепились ли они.

### 💡 Нюансы от Senior-а (Pro Tips)

1.  **Ловушка `__init__.py`**: В современных версиях Python и PyTest тебе **не обязательно** ставить `__init__.py` в папку с тестами, чтобы они работали. Но если ты добавишь его, папка станет «пакетом», что может изменить пути импорта. Будь осторожен.
2.  **Запрет на `__init__` в классах**: Если ты создаешь класс для тестов (`class TestSomething`), **никогда** не добавляй в него метод `def __init__(self)`. PyTest просто пропустит этот класс, так как он ожидает, что классы тестов — это простые контейнеры для методов.
3.  **Конфликты имен**: Если у тебя есть файл `test_utils.py` и внутри него функция `test_login`, а также другой файл `test_auth.py` с функцией `test_login`, PyTest их найдет оба, но в отчетах они могут выгляться запутанно. Всегда старайся делать уникальные префиксы.

# 🛠 Тема: Что такое фикстуры (Fixtures)

### 💡 Суть простыми словами
Представь, что ты снимаешь кино. Перед тем как актер (твой **тест**) выйдет на сцену, декорации должны быть расставлены, свет включен, а реквизит готов (**Setup**). После того как сцена сыграна, нужно убрать мусор и выключить свет (**Teardown**).

**Фикстура** — это и есть тот самый «завхоз», который готовит окружение для теста и очищает его после. В PyTest фикстуры реализуют паттерн **Dependency Injection** (внедрение зависимостей): ты не создаешь объекты внутри теста, ты просто просишь их у PyTest, передавая имя фикстуры в аргументы функции теста.

---

### 🚀 Основные возможности и механика

#### 1. Базовая структура (`return` vs `yield`)
*   **`return`**: Просто подготавливает данные.
*   **`yield`**: Позволяет выполнить код **после** теста (Teardary/Cleanup). Это критически важно для закрытия соединений с БД или удаления временных файлов.

```python
import pytest

@pytest.fixture
def simple_data():
    return {"id": 1, "name": "Test User"}

@pytest.fixture
def database_connection():
    # SETUP: Подключаемся к БД
    db = "Connected to DB"
    yield db  # Здесь тест получает доступ к переменной db
    # TEARDOWN: Закрываем соединение
    print("\nClosing DB connection...")

def test_user_name(simple_data):
    assert simple_data["name"] == "Test User"

def test_db_status(database_connection):
    assert database_connection == "Connected to DB"
```

#### 2. Области видимости (Scopes) — Важнейший нюанс!
Scope определяет, как долго живет фикстура. Если ошибиться со scope, тесты могут начать влиять друг на друга (загрязнение состояния).

| Scope | Описание | Когда использовать |
| :--- | :--- | :---            |
| `function` (default) | Пересоздается для **каждого** теста. | Самый безопасный. Для мелких объектов, файлов. |
| `class` | Один раз на каждый класс тестов. | Когда у тебя группа тестов работает с одним объектом. |
| `module` | Один раз на весь `.py` файл. | Тяжелые операции: загрузка конфига, создание таблицы в БД. |
| `package` | Один раз на всю папку (директорию). | Редко, для настройки окружения целого модуля. |
| `session` | Один раз за **весь запуск** pytest. | Самый тяжелый: инициализация драйвера браузера, старт Docker-контейнера. |

#### 3. Зависимости (Fixture Composition)
Фикстуры могут вызывать другие фикстуры. Это позволяет строить иерархию: `test` -> `api_client` -> `auth_token` -> `db_connection`.

#### 4. Автоматические фикстуры (`autouse=True`)
Иногда нужно, чтобы что-то происходило «в фоне» (например, очистка кэша перед каждым тестом), и ты не хочешь прописывать эту фикстуру в каждый тест вручную.

```python
@pytest.fixture(autouse=True)
def clean_logs():
    # Этот код выполнится перед КАЖДЫМ тестом в этом модуле
    print("\nCleaning logs...")
```

#### 5. Глобальные фикстуры (`conftest.py`)
Если ты создашь фикстуру в файле `conftest.py`, она станет доступна **всем** тестам в этой папке и подпапках без необходимости делать `import`. Это стандарт индустрии для хранения общих Setup-скриптов.

---

### ⚠️ Senior Tips (Нюансы и Антипаттерны)

1.  **Избегай "God Fixtures"**: Не делай одну фикстуру, которая делает *всё* сразу (создает юзера, БД, API и кэш). Дроби их на мелкие, атомарные части. Это позволит тестам быть быстрее и гибче.
2.  **Следи за Side Effects**: Если твоя фикстура с `scope="session"` меняет данные в базе, а тест их удаляет — следующий тест упадет. **Правило: Фикстура должна либо создавать чистый объект, либо гарантировать очистку.**
3.  **Используй `yield` всегда, где есть ресурс**: Если фикстура создает файл или сетевое соединение, всегда используй `yield`, чтобы закрыть его. Иначе ты получишь утечку памяти или дескрипторов файлов.

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Чем фикстура отличается от обычного `setup` метода в `unittest`?**
**О:** Фикстуры гораздо мощнее благодаря **Dependency Injection**. В `unittest` ты полагаешься на состояние класса (`self.db`), а в PyTest ты явно запрашиваешь нужный ресурс как аргумент функции. Это делает зависимости теста прозрачными и упрощает переиспользование.

**В: Что произойдет, если тест упадет внутри фикстуры (до `yield`)?**
**О:** Тест даже не начнется. PyTest пометит это как ошибку настройки (Error), а не провал теста (Fail).

**В: Можно ли передать параметры в фикстуру?**
**О:** Напрямую — нет (аргументы функции теста — это не параметры фикстуры). Но можно использовать **Parametrization** или **Fixture Factories** (когда фикстура возвращает функцию, которая принимает аргументы).

**В: Как сделать так, чтобы фикстура запускалась только если выполнено условие?**
**О:** Используй логику внутри самой фикстуры или комбинируй с маркером `@pytest.mark.skipif`.

# 🧠 Шпаргалка: Использование `yield` в фикстурах PyTest

Если коротко: `yield` — это способ превратить фикстуру из простого «поставщика данных» в полноценный **менеджер жизненного цикла**. Он позволяет реализовать паттерн **Setup $\rightarrow$ Test $\rightarrow$ Teardown** внутри одной функции.

### 1. В чем разница: `return` vs `yield`?
*   **`return`**: Фикстура просто отдает объект и завершает свою работу. Она «забывает» о существовании теста сразу после передачи данных. Очищать ресурсы (закрывать БД, удалять файлы) некому.
*   **`yield`**: Фикстура отдает объект, но **приостанавливает** свое выполнение. После того как тест (или группа тестов) завершится, PyTest «разморозит» фикстуру и выполнит код, который идет *после* `yield`.

### 2. Анатомия фикстуры с `yield`
```python
@pytest.fixture
def db_connection():
    # --- PHASE 1: SETUP (Подготовка) ---
    db = connect_to_database()
    print("\n[Setup] Соединение установлено")

    yield db  # <--- Точка передачи управления тесту

    # --- PHASE 2: TEARDOWN (Очистка) ---
    db.close()
    print("\n[Teardown] Соединение закрыто")
```

### 3. Важные нюансы (Senior Level)

#### ⚠️ Нюанс №1: Ошибки в Setup
Если ошибка произошла **до** строки с `yield` (в фазе Setup), код после `yield` (Teardown) **не выполнится**. 
*   *Последствие:* Если ты создал файл до `yield`, а на этапе создания папки упал — файл останется «мусором» в системе.
*   **Решение:** Используй конструкцию `try...finally`.

```python
@pytest.fixture
def temp_file():
    f = open("test.txt", "w")
    try:
        yield f
    finally:
        # Этот блок выполнится ВСЕГДА, даже если тест упал 
        # или если ошибка случилась в самом тесте
        f.close()
```

#### ⚠️ Нюанс №2: Область видимости (Scope) и время жизни
Поведение `yield` напрямую зависит от `scope`.
*   Если `scope="function"`: Teardown запускается после **каждого** теста.
*   Если `scope="session"`: Teardtdown запустится только тогда, когда **завершится весь прогон тестов**. 
*   *Опасность:* Если ты в `session` scope создаешь тяжелый объект и забываешь его очистить через `yield`, ты можешь «забить» оперативную память или оставить висящие процессы на сервере.

#### ⚠️ Нюанс №3: Тест упал — Teardown все равно работает?
**Да.** PyTest гарантирует, что если выполнение дошло до `yield`, то код после него будет выполнен, даже если тест завершился с ошибкой (`AssertionError`). Это и есть главная сила `yield`.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что произойдет, если в коде после `yield` возникнет ошибка?**
**О:** Тест, который использовал эту фикстуру, пометится как **Error** (не Failed, а именно Error). Это означает, что сам тест прошел, но инфраструктура вокруг него сломалась.

**В: Можно ли использовать `return` и `yield` в одной фикстуре?**
**О:** Технически Python позволит, но это плохой тон и путаница. Если ты используешь `yield`, значит, ты заявляешь о наличии фазы очистки. Не смешивай эти подходы.

**В: Как протестировать именно фазу Teardown?**
**О:** Напрямую — никак (ты не можешь «зайти» внутрь завершенной фикстуры). Но ты можешь проверять побочные эффекты в других тестах или через моки (например, проверить, был ли вызван метод `.close()` у объекта).

**Г: Если я использую `try...finally` внутри фикстуры, нужно ли мне дополнительно использовать `yield`?**
**О:** Да, `yield` — это обязательный механизм передачи данных тесту. `try...finally` лишь гарантирует надежность очистки.

# 🧠 Шпаргалка по PyTest: Области видимости (Scopes)

В PyTest **Scope (область видимости)** определяет «время жизни» фикстуры. Это ответ на вопрос: *«Как часто нам нужно заново создавать этот объект и когда его пора уничтожить?»*

### 🛠 Основные типы Scopes

Всего существует 5 уровней. Мы идем от самого короткого (частого) к самому длинному (редкому).

| Scope | Когда создается? | Когда уничтожается? | Для чего использовать? |
| :---s| :--- | :--- | :--- |
| **`function`** (дефолт) | Перед каждым тестом. | После каждого теста. | Самый безопасный. Идеально для чистых данных, которые не должны влиять на другие тесты. |
| **`class`** | Перед началом первого теста в классе. | После завершения всех тестов в классе. | Если у тебя группа тестов в одном классе использует один и тот же тяжелый объект. |
| **`module`** | Перед первым тестом в `.py` файле. | Когда файл полностью отработал. | Для ресурсов, общих для всего файла (например, инициализация API-клиента). |
| **`package`** | Перед началом тестов в папке (где есть `conftest.py`). | Когда вся папка завершена. | Редко используется. Полезно для интеграционных тестов целого подмодуля. |
| **`session`** | Один раз при запуске команды `pytest`. | В самом конце, когда всё закончилось. | Самый «дорогой» ресурс: запуск браузера (Selenium), создание БД, миграции. |

---

### ⚠️ Senior-советы: Нюансы и Подводные камни

#### 1. Правило Иерархии (Dependency Rule)
Фикстура **высокого уровня** может зависеть от фикстуры **низкого уровня**, но **не наоборот**.
* ✅ `session` фикстура может вызывать `function` фикстуру.
* ❌ `function` фикстура **не может** использовать `session` фикстуру, если та должна менять состояние (потому что `session` живет дольше и не «сбросится» между тестами).

#### 2. Проблема "Загрязнения" (State Leakage)
Это главная ошибка. Если ты используешь `scope='session'` для списка или словаря, и один тест добавил туда элемент — **все последующие тесты увидят этот элемент**.
* **Золотое правило:** Используй `session` только для **read-only** данных или ресурсов, которые умеют «самоочищаться». Если объект мутабельный (изменяемый) — используй `function`.

#### 3. Производительность vs Изоляция
* Чем выше Scope, тем **быстрее** идут тесты (мы не тратим время на пересоздание объекта).
* Чем ниже Scope, тем **надежнее** тесты (каждый тест начинает с чистого листа).
* *Senior-подход:* Всегда стремись к максимальной изоляции (`function`), пока не упрешься в слишком долгое время выполнения тестов.

#### 4. Очистка ресурсов (Teardown)
При использовании широких скоупов (`module`, `session`) использование `yield` становится критически важным. Если ты создал базу данных в `session`, ты **обязан** удалить её в том же `yield`, иначе после завершения тестов у тебя в системе останется «мусор».

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что будет, если я забуду указать scope?**
**О:** PyTest по умолчанию применит `function`. Тесты будут работать правильно и безопасно, но могут идти очень медленно, если создание объекта занимает много времени.

**В: Можно ли использовать `session` scope для управления браузером (WebDriver)?**
**О:** Да, это стандарт индустрии. Запуск браузера — дорогая операция. Но помни: сам браузер будет один, поэтому после каждого теста тебе нужно очищать куки (`driver.delete_all_cookies()`), чтобы тесты не влияли друг на друга.

**В: Как мне понять, какой scope выбрать для новой фикстуры?**
**О:** Задай себе два вопроса:
1. "Может ли этот объект измениться в процессе теста?" (Если да $\rightarrow$ `function`).
2. "Насколько дорого обходится его создание?" (Если очень дорого и он не меняется $\rightarrow$ `session`).

**В: Что такое `autouse=True` и как он связан со scope?**
**О:** `autouse` заставляет фикстуру работать автоматически без прокидывания её в аргументы теста. В сочетании с `session` scope это мощный инструмент для глобальной настройки окружения (например, автоматическое логирование всех тестов).

# 🛠 Автоматические фикстуры (`autouse=True`)

### Что это такое?
Обычно, чтобы использовать фикстуру, ты должен явно передать её имя в аргументы тестовой функции: `def test_example(my_fixture):`. 
**Автоматическая фикстура** — это фикстура, которую **не нужно** прописывать в аргументах. Она запускается сама по себе. Представь её как «фоновый процесс» или «глобальный перехватчик», который работает за кулисами.

### Зачем это нужно? (Use Cases)
Автоматические фикстуры идеальны для задач, которые касаются **инфраструктуры**, а не бизнес-логики:
1.  **Очистка окружения:** Удаление временных файлов или очистка БД после каждого теста.
2.  **Логирование:** Автоматическое создание лог-файла или запись начала/контента теста.
3.  **Настройка среды:** Установка переменных окружения (`env vars`) для всех тестов сразу.
4.  **Мокинг глобальных объектов:** Подмена системного времени или сетевых запросов во всем проекте.

### Пример кода
```python
import pytest

# Эта фикстура будет запускаться ПЕРЕД каждым тестом автоматически
@pytest.fixture(autouse=True)
def setup_environment():
    print("\n[Setup] Подготовка окружения (например, создание папки logs)")
    yield
    print("\n[Teardown] Очистка после теста (удаление временных файлов)")

def test_logic_a():
    print("Выполняем тест A")
    assert True

def test_logic_b():
    print("Выполняем тест B")
    assert 1 == 1
```

### ⚠️ Нюансы и «Подводные камни» (Senior Advice)

**1. Проблема «Магического поведения» (The Magic Trap)**
Это самый важный момент. Если ты используешь слишком много `autouse=True`, новый разработчик (или ты сам через месяц) не сможет понять, почему тест падает или почему данные в БД меняются. 
*   **Правило:** Используй `autouse` только для того, что **не касается бизнес-логики**. Если фикстура готовит пользователя для теста — передавай её явно. Если она чистит кэш браузера — используй `autку`.

**2. Взаимодействие со Scope (Областью видимости)**
`autouse` работает в связке с `scope`. 
*   Если `autouse=True` и `scope='session'`, фикстура запустится **один раз** в самом начале всего прогона.
*   Если `autouse=True` и `scope='function'`, она будет запускаться **перед каждым** тестом.
*   **Нюанс:** Будь осторожен с `autouse` на уровне `session`. Если такая фикстура что-то меняет в глобальном состоянии, это может «отравить» все последующие тесты (эффект загрязнения тестов).

**3. Переопределение**
Ты можешь переопределить автоматическую фикстуру в конкретном модуле или классе, если передашь её явно в аргументы теста. Но это может привести к запуску одной и той же логики дважды.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Можно ли использовать `autouse=True` для подготовки данных пользователя?**
**О:** Не советую. Это делает тест «неявным». Глядя на сигнатуру `def test_login()`, я должен сразу видеть, что мне нужен пользователь. Если он подтягивается магически, я могу забыть про него и написать некорректный тест.

**В: Что будет, если у меня есть две фикстуры с `autouse=True`?**
**О:** PyTest запустит их обе. Порядок запуска будет зависеть от того, какая из них является зависимостью другой (если они связаны) или от порядка их объявления/обнаружения.

**В: Как мне отключить автоматическую фикстуру для одного конкретного теста?**
**О:** Напрямую «выключить» `autouse` нельзя, но ты можешь переопределить её в этом тесте (или в классе этого теста), передав пустую фикстуру с тем же именем. Но лучше просто не использовать `autouse` для вещей, которые можно легко отключить.

**В: Где лучше всего объявлять такие фикстуры?**
**О:** В файле `conftest.py`. Это сделает их доступными во всем проекте, и они будут работать «тихо» и согласованно.

# 🧠 Шпаргалка: Зависимость фикстур (Fixture Dependencies)

### 1. Суть концепции
В PyTest фикстуры — это не изолированные куски кода, а **сеть**. Одна фикстура может запрашивать другую, передавая её в качестве аргумента. Это позволяет строить иерархию: от базовых настроек (конфиг) до высокоуровневых объектов (клиент API с авторизованным пользователем).

**Как это выглядит в коде:**
```python
@pytest.fixture
def db_connection():
    return "Connection to DB"

@pytest.fixture
def user_data(db_connection):  # Зависимость: user_data требует db_connection
    return {"name": "Admin", "db": db_connection}

def test_user_access(user_data):
    assert user_data["name"] == "Admin"
    assert "DB" in user_data["db"]
```

### 2. Граф выполнения (DAG)
PyTest строит **направленный ациклический граф (DAG)**. 
*   **Порядок Setup:** Сначала выполняются «родительские» фикстуры, затем «дочерние».
*   **Порядок Teardown:** В обратном порядке. Сначала очищаются дочерние объекты, потом — родительские.

> **Senior Tip:** Представь это как матрешку. Чтобы собрать самую маленькую куклу (тест), тебе сначала нужно подготовить внешнюю (базовую фикстуру).

### 3. Главное правило: Scope Mismatch (Конфликт областей видимости)
Это самая частая ловушка. **Scope дочерней фикстуры не может быть шире, чем scope её зависимости.**

*   **Можно:** `function`-scope фикстура зависит от `session`-scope фикстуры. (Пользователь создается каждый раз, но база данных живет всё время сессии).
*   **Нельзя:** `session`-scope фикстура зависит от `function`-scope фикстуры. 

**Почему?** Если фикстура живет всю сессию, она не может зависеть от чего-то, что удаляется после каждого теста. PyTest выбросит ошибку: `Scope mismatch`.

### 4. Нюансы и «подводные камни»
*   **Циклические зависимости:** Если `A` требует `B`, а `B` требует `A` — PyTest упадет с ошибкой. Проверяй архитектуру, не делай слишком сложные цепочки.
*   **Скрытые зависимости:** Когда фикстура использует `autouse=True`, она может подмешиваться в дерево незаметно для разработчика. Это удобно, но затрудняет отладку (сложно понять, откуда взялся этот объект).
ary
*   **Переиспользование кода:** Зависимости позволяют соблюдать принцип DRY (Don't Repeat Yourself). Вместо того чтобы в каждом тесте настраивать БД, ты создаешь цепочку: `engine` $\to$ `connection` $\to$ `session` $\to$ `tables`.

### ❓ FAQ (Частые вопросы)

**В: Что будет, если я забуду передать зависимую фикстуру в аргументы функции фикстуры?**
**О:** PyTest не поймет, что их нужно связать. Он либо попытается найти другую фикстуру с таким именем в глобальном контексте, либо (если её нет) выдаст ошибку `FixtureError: Fixture '...' not found`.

**В: Можно ли одной фикстуре передавать сразу несколько зависимостей?**
**О:** Да, без ограничений. Ты можешь написать `def api_client(auth_token, base_url, session):`. Это стандартная практика.

**В: Как понять, какая фикстура вызвала ошибку в длинной цепочке?**
**О:** Используй флаг `-v` при запуске и смотри на Traceback. В PyTest traceback четко показывает путь вызова: от теста через все слои зависимых фикстур до места падения.

**В: Если я использую `yield`, как это влияет на зависимости?**
**О:** Никак. `yield` управляет только моментом очистки (teardown). Логика связей (кто кого вызывает) остается прежней. Главное — помни, что родительская фикстура не завершит свой `yield` до тех пор, пока не отработают все её «дети».

# 🛠 Cheat Sheet: Fixture Factories in PyTest

### 💡 Что это такое?
Обычная фикстура возвращает **объект** (например, пользователя или базу данных).  
**Fixture Factory** — это фикстура, которая возвращает **функцию**. Эта функция принимает аргументы и на их основе создает объект.

### 🚀 Зачем это нужно? (The "Why")
1.  **Избегание «взрыва» фикстур:** Вместо того чтобы плодить `user_admin`, `user_guest`, `user_deleted`, ты создаешь одну фабрику `create_user`.
2.  **Динамика внутри теста:** Тебе нужно создать пользователя с конкретным именем именно в этом тесте, а не полагаться на заранее заготовленный шаблон.
3.  **Гибкость данных:** Ты можешь передавать любые параметры (id, роль, email) прямо в теле теста.

### 🛠 Как это реализовать?
Основной паттерн: фикстура использует `yield`, а перед `yield` определяет внутреннюю функцию, которая и является «заводом».

```python
import pytest

@pytest.fixture
def user_factory(db_connection):
    # Список для отслеживания созданных объектов (для очистки)
    created_users = []

    def _make_user(username, role="guest"):
        user = {"name": username, "role": role, "db": db_connection}
        created_users.append(user) # Регистрируем для удаления
        return user

    yield _make_user  # Возвращаем саму функцию-завод

    # Teardown: Очистка всех созданных пользователей после теста
    for user in created_users:
        print(f"Deleting user: {user['name']}")
        # db_connection.delete(user) 
```

### ⚠️ Нюансы и Senior-советы (The Nuances)

1.  **Проблема Teardown (Очистки):** Это самая важная часть. Если твоя фабрика создает объекты в базе данных, ты **обязан** обеспечить их удаление. Самый надежный способ — хранить список созданных объектов внутри самой фикстуры (как в примере выше) и проходить по нему циклом после `yield`.
2.  **Scope (Область видимости):** Фабрики почти всегда должны иметь scope `function`. Если сделать фабрику `session`-scoped, то все объекты, созданные ею в разных тестах, будут жить до конца всего прогона, что может привести к утечке данных и конфликтам.
3.  **Factory vs Parametrize:** 
    *   Используй `@pytest.mark.parametrize`, если хочешь запустить **один и тот же тест** с разными наборами данных (создастся много тестов).
    *   Используй `Factory`, если тебе нужно создать **разные объекты внутри одного теста** или если логика создания слишком сложная для параметризации.

### 📝 Пример использования

```python
def test_admin_can_delete_user(user_factory):
    # Создаем админа и обычного пользователя прямо в тесте
    admin = user_factory("boss", role="admin")
    victim = user_factory("victim", role="guest")
    
    # Логика теста...
    assert admin["role"] == "admin"
    assert victim["role"] == "guest"

def test_multiple_users_creation(user_factory):
    # В одном тесте можем создать сколько угодно объектов
    u1 = user_factory("user1")
    u2 = user_factory("user2")
    u3 = user_factory("user3")
    assert u1 != u2 != u3
```

# 🧠 Шпаргалка: `conftest.py` — Сердце конфигурации PyTest

### Что это такое?
Если коротко: **`conftest.py` — это файл-контейнер для общих ресурсов.** 
Это специальный файл, который PyTest находит автоматически. Его главная фишка в том, что тебе **не нужно импотировать** то, что в нем написано, чтобы использовать это в тестах. Он работает как «магический» слой конфигурации для папки, в которой лежит, и всех её подпапок.

---

### 🛠 Основные задачи `conftest.py`

#### 1. Общие фикстуры (Shared Fixtures)
Вместо того чтобы копировать одну и ту же фикстуру (например, создание базы данных или авторизацию пользователя) в каждый файл с тестами, ты выносишь её в `conftest.py`. 
*   **Результат:** Тесты становятся чистыми, а фикстура — доступной глобально для данной директории.

#### 2. Настройка Hooks (Перехват жизненного цикла)
`conftest.py` — это место, где ты можешь «вклиниться» в работу PyTest через хуки. Например:
*   Добавить свои аргументы в командную строку (`pytest --my-env=dev`).
*   Изменить логику поиска тестов.
*   Генерировать отчеты или менять порядок выполнения.

#### 3. Иерархическая конфигурация
Ты можешь иметь несколько файлов `conftest.py` в разных папках проекта. PyTest будет собирать их по цепочке снизу вверх: от папки с тестом до корня проекта.

---

### ⚠️ Важные нюансы (Senior Tips)

1.  **Золотое правило: НИКОГДА не импортируй фикстуры из `conftest.py` напрямую.**
    *   ❌ *Плохо:* `from conftest import my_fixture` в файле с тестами.
    *   ✅ *Хорошо:* Просто укажи `my_fixture` как аргумент функции теста. 
    *   *Почему?* Если ты начнешь импорты, ты нарушишь механизм Discovery PyTest, и при рефакторинге (перемещении файлов) всё сломается.

2.  **Принцип локальности (Scope Isolation).**
    Не пихай **всё** в корневой `conftest.py`. Если фикстура нужна только для API-тестов, создай `tests/api/conftest.py`. Это делает архитектуру прозрачной: инженер сразу видит, какие ресурсы доступны конкретному модулю тестов.

3.  **`conftest.py` — это не модуль с логикой.**
    Не пиши в нем сложную бизнес-логику или тяжелые вычисления. В нем должна быть только *настройка* (setup) и *инфраструктура*. Саму логику приложения лучше держать в отдельных утилитах (`utils.py`).

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем `conftest.py` отличается от обычного Python-файла с фикстурами?**

# 🛠 Шпаргалка: `@pytest.mark.parametrize`

### 💡 Суть темы
Если ты ловишь себя на том, что копируешь один и тот же тест, меняя в нем только входные данные — **остановись**. Ты нарушаешь принцип DRY (*Don't Repeat Yourself*). 

`@pytest.mark.parametrize` позволяет превратить одну тестовую функцию в генератор множества тестов. На вход подаются аргументы, на выходе — столько же отдельных тест-кейсов в отчете.

---

### 🚀 Базовый синтаксис
Первый аргумент — это **строка** с именами переменных (через запятую), второй — **список кортежей** (или список списков) с данными.

```python
import pytest

def add(a, b):
    return a + b

@pytest.mark.parametrize("a, b, expected", [
    (1, 2, 3),       # Тест 1
    (5, 5, 10),      # Тест 2
    (0, 0, 0),       # Тест 3
    (-1, 1, 0),      # Тест 4
])
def test_add(a, b, expected):
    assert add(a, b) == expected
```

---

### 💎 Продвинутые фишки (Senior Level)

#### 1. Использование `ids` (Читаемость — это всё)
Когда тестов становится много, в консоли вместо красивых имен ты видишь `test_add[1-2-3]`. Это неудобно дебажить. Используй параметр `ids`, чтобы дать каждому кейсу осмысленное имя.

```python
@pytest.mark.parametrize(
    "a, b, expected",
    [(1, 2, 3), (10, 20, 30)],
    ids=["small_numbers", "large_numbers"] # Теперь в логах будет понятно, что упало
)
def test_add_with_ids(a, b, expected):
    assert add(a, b) == expected
```

#### 2. Indirect Parametrization (Косвенная параметризация)
Это когда ты хочешь передать параметры не напрямую в тест, а **в фикстуру**. Это критически важно для интеграционных тестов (например, подмена URL базы данных или выбор типа браузера).

```python
@pytest.fixture
def api_client(request):
    # request.param — это магия, которая берет данные из параметризации
    url = request.param
    return f"Client connecting to {url}"

@pytests.mark.parametrize("api_client", ["http://dev.api", "http://prod.api"], indirect=True)
def test_api_connection(api_client):
    assert "api" in api_client
```

#### 3. Комбинирование нескольких параметризаций (Cartesian Product)
Если ты вешаешь два декоратора `@pytest.mark.parametrize` на одну функцию, PyTest создаст **декартово произведение**. Если в первом списке 3 значения, а во втором 2 — у тебя будет $3 \times 2 = 6$ тестов.

*Будь осторожен: это может привести к «взрывному» росту количества тестов (Combinatorial Explosion).*

---

### ⚠️ Нюансы и Подводные камни

1.  **Типизация строк:** Имена аргументов в первом параметре декоратора — это **строка**. Если ты напишешь `parametrize(a, b, [...])` вместо `"a, b"`, PyTest выдаст ошибку.
2.  **Сложные объекты:** В список данных можно передавать не только числа, но и словари, списки или даже экземпляры классов. Но старайся не переусложнять, чтобы тест оставался читаемым.
3.  **Порядок аргументов:** Порядок имен в строке `"a, b, expected"` должен **строго соответствовать** порядку элементов в кортежах внутри списка.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Чем `parametrize` отличается от обычного цикла `for` внутри теста?**
**О:** Если тест упадет внутри цикла `for`, выполнение функции прервется, и ты узнаешь только об одной ошибке. При использовании `@pytest.mark.parametrize` каждый набор данных — это **отдельный тест**. Если один упал, остальные продолжат выполняться, и ты получишь полный отчет по всем кейсам.

**В: Можно ли использовать `parametrize` вместе с фикстурами?**
**О:** Да, и это стандарт индустрии. Ты можешь параметризовать саму фикстуру (через аргумент `params` в `@pytest.fixture`) или передавать параметры из теста в фикстуру через `indirect=True`.

**В: Что делать, если параметров слишком много и они создают сотни тестов?**
**О:** Используй фильтрацию по маркерам (`-m`) или разбей тест на несколько разных функций с разными наборами данных. Не пытайся запихнуть всю вселенную в один декоратор.

# 🚀 Параметризация фикстур в PyTest

### Что это такое?
Обычная параметризация (`@pytest.mark.parametrize`) заставляет **тест** запускаться несколько раз с разными данными. 
**Параметризация фикстуры** — это более мощный инструмент. Она заставляет **все тесты, использующие эту фикстуру**, перезапускаться для каждого значения из списка параметров.

Это идеальный способ тестировать один и тот же сценарий в разных средах (разные браузеры, разные БД, разные роли пользователей), не дублируя код в самих тестах.

---

### Базовый синтаксис
Чтобы параметризовать фикстуру, мы используем аргумент `params` в декораторе `@pytest.fixture`. Чтобы достать текущее значение, нам **обязательно** нужен встроенный объект `request`.

```python
import pytest

# Список параметров, по которым будет "крутиться" тест
browsers = ["chrome", "firefox", "safari"]

@pytest.fixture(params=browsers)
def driver(request):
    # request.param — это магия, которая достает текущее значение из списка params
    browser_name = request.param
    print(f"\n[Setup] Запуск браузера: {browser_name}")
    
    yield browser_name  # Передаем значение в тест
    
    print(f"\n[Teardown] Закрытие браузера: {browser_name}")

def test_login_page(driver):
    print(f"Тестируем страницу логина в {driver}")
    assert len(driver) > 0
```

**Что произойдет:** PyTest увидит фикстуру `driver` с 3 параметрами и выполнит `test_login_page` **трижды**.

---

### Продвинутые фишки (Senior Level)

#### 1. Использование `ids` для читаемости
Если параметров много или это сложные объекты, в консоли будет каша из непонятных строк. Используй аргумент `ids`, чтобы дать каждому параметру красивое имя.

```python
@pytest.fixture(params=["admin", "guest", "editor"], ids=["Role: Admin", "Role: Guest", "Role: Editor"])
def user_role(request):
    return request.param
```
*Теперь в отчете вместо `test_user[admin]` ты увиди:: `test_user[Role: Admin]`.*

#### 2. Взаимодействие с Scopes (Области видимости)
Это критический момент. Если ты ставишь `scope="session"`, но при этом параметризуешь фикстуру, PyTest создаст **отдельную сессию для каждого параметра**.
*   Если `scope="function"`: Setup/Teardown выполняется перед каждым тестом для каждого параметра.
*   Если `scope="session"`: Setup выполнится один раз для "chrome", потом один раз для "firefox" и т.д.

#### 3. Параметризация через внешние данные
Не хардкодь списки в коде. Senior-подход — выносить их в `conftest.py` или загружать из JSON/YAML. Это позволяет менять тестовые данные, не трогая логику тестов.

---

### ⚠️ Нюансы и "грабли"

1.  **Зависимость от `request`**: Если ты забудешь прокинуть `request` в аргументы фикстуры, ты не сможешь обратиться к `request.param`, и параметризация превратится в бесполезную трату времени (тест просто выполнится один раз с ошибкой).
2.  **Раздувание количества тестов**: Будь осторожен. Если у тебя 5 параметризованных фикстур, каждая из которых имеет по 5 параметров, количество комбинаций растет экспоненциально ($5 \times 5 \times 5...$). Это может превратить твой запуск теста в бесконечность.
3.  **Сложность отладки**: Когда тест падает внутри параметризованной фикстуры, важно смотреть на `ids`, иначе ты не поймешь, на каком именно значении (например, на "edge case" строке) всё сломалось.

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `@pytest.mark.parametrize` и параметризацией фикстуры?**
**О:** `@pytest.mark.parametrize` меняет входные данные конкретного теста. Параметризация фикстуры меняет "окружение" (environment). Если тебе нужно протестировать логику функции на разных числах — используй маркер. Если тебе нужно проверить один и тот же тест на разных базах данных — используй фикстуру.

**В: Можно ли внутри параметризованной фикстуры использовать другую параметризованную фикстуру?**
**О:** Да, но помни про "взрывной рост" количества тестов (Cartesian product). PyTest создаст все возможные комбинации параметров обеих фикстур.

**В: Как пропустить один конкретный параметр из списка?**
**О:** Напрямую в `params` — нет. Тебе придется либо фильтровать их внутри фикстуры через `if`, либо использовать кастомный маркер для тестов, который будет отсекать ненужные значения во время выполнения.

**В: Что делать, если я хочу передать в фикстуру не просто строку, а сложный объект?**
**О:** Ты можешь передавать в `params` список объектов или словарей. Главное — правильно настроить `ids`, чтобы в логах было понятно, какой именно объект сейчас тестируется.

# 🧠 Шпаргалка: Сложные параметры в PyTest

Когда мы говорим о «сложных параметрах», мы выходим за рамки передачи одиночных `int` или `str`. Мы переходим к передаче структур данных (списки, словари, объекты) и динамическому управлению наборами данных.

### 1. Параметризация через кортежи и словари (`@pytest.mark.parametrize`)
Самый частый кейс: когда входные данные и ожидаемый результат — это не одно значение, а набор связанных данных.

**Senior Tip:** Не плоди отдельные аргументы для каждого поля. Группируй их в кортежи или словари. Это делает сигнатуру теста чистой.

```python
import pytest

# Плохо: много аргументов, трудно масштабировать
@pytest.mark.parametrize("input_val, expected_res, error_msg", [
    (1, 2, None),
    (0, 1, None),
    (-1, 0, "Error") # Представь, если тут будет еще 10 полей...
])
def test_bad_style(input_val, expected_res, error_msg):
    pass

# Хорошо: используем кортежи (структурированный подход)
@pytest.mark.parametrize("payload, expected", [
    ({"id": 1, "name": "Alice"}, 200),
    ({"id": 2, "name": "Bob"}, 201),
    ({}, 400),
])
def test_good_style(payload, expected):
    # payload — это словарь, мы легко можем достать из него любые поля
    assert isinstance(payload, dict)
```

### 2. Параметризация фикстур (Fixture Parametrization)
Иногда нам нужно, чтобы **каждый** тест, использующий определенную фикстуру, запускался несколько раз с разными состояниями этой фикстуры. Это мощнее, чем `parametrize`, так как это меняет уровень подготовки (setup).

**Senior Tip:** Используй это для тестирования разных ролей пользователя, разных браузеров или разных конфигураций БД.

```python
import pytest

@pytest.fixture(params=["admin", "editor", "viewer"])
def user_role(request):
    # request.param — это текущее значение из списка params
    return request.param

def test_access_rights(user_role):
    # Этот тест выполнится 3 раза: один раз для каждого ролей
    print(f"Testing with role: {user_role}")
    assert isinstance(user_role, str)
```

### 3. Динамическая параметризация (`pytest_generate_tests`)
Это «тяжелая артиллерия». Если ты не знаешь заранее, какие параметры будут в тестах (например, они читаются из JSON-файла или базы данных), тебе нужен хук `pytest_generate_tests`.

**Senior Tip:** Это единственный способ сделать тесты по-настоящему Data-Driven, когда набор данных живет отдельно от кода.

```python
# conftest.py или внутри теста
import pytest

def pytest_generate_tests(metafunc):
    # Проверяем, есть ли в аргументах теста параметр 'data_from_file'
    if "data_from_file" in metafunc.fixturenames:
        # Имитируем чтение из внешнего источника (JSON/CSV)
        external_data = [10, 20, 30, 40] 
        metafunc.add_argvalue("data_from_file", external_data)

def test_dynamic_values(data_from_file):
    # Этот тест создастся автоматически на основе списка из хука
    assert data_from_file > 0
```

### 4. Фабрики фикстур (Fixture Factories)
Иногда параметр не может быть просто «значением», ему нужна логика создания. В этом случае фикстура возвращает **функцию**.

**Senior Tip:** Это позволяет передавать параметры прямо в тело теста, сохраняя при этом мощь Setup/Teardown из фикстуры.

```python
import pytest

@pytest.fixture
def user_factory():
    """Фикстура-завод: создает пользователей с разным набором прав."""
    created_users = []

    def _make_user(role, permissions):
        user = {"role": role, "permissions": permissions}
        created_users.append(user) # Для последующей очистки (Teardown)
        return user

    yield _make_user

    # Teardown: удаляем всех созданных пользователей из БД/памяти
    for user in created_users:
        print(f"Cleaning up user: {user['role']}")

def test_user_permissions(user_factory):
    admin = user_factory("admin", ["read", "write", "delete"])
    editor = user_factory("editor", ["read", "write"])
    
    assert "delete" in admin["permissions"]
    assert "delete" not in editor["permissions"]
```

**В: В чем разница между `@pytest.mark.parametrize` и `params` в фикстуре?**

**О:** Используй `scope="session"` или `scope="module"` для базовой части фикстуры, а параметры передавай через под-фикстуру или используй фабрику, которая работает с уже созданным ресурсом.

# 🚀 Динамическая параметризация в PyTest

### Что это такое?
Обычно мы используем `@pytest.mark.parametrize`, когда набор данных нам известен заранее (статичен). Но что, если количество тестов должно зависеть от внешнего мира? Например:
* Количество тестов зависит от списка пользователей в базе данных.
* Тесты должны запускаться для каждого файла в определенной папке.
* Конфигурация прилетает из JSON-файла или API во время выполнения.

**Динамическая параметрирование** — это процесс генерации тестовых случаев «на лету» во время фазы **сбора (collection phase)** тестов, используя специальный хук `pytest_generate_tests`.

---

### Главный инструмент: Хук `pytest_generate_tests`
Этот хук живет **только** в файле `conftest.py`. Он вызывается PyTest для каждого найденного тестового метода или класса.

#### Как это работает (алгоритм):
1. PyTest находит тест.
2. Вызывает `pytest_generate_tests(metafunc)`.
3. Ты внутри хука проверяешь: «А есть ли в этом тесте аргумент, который я хочу параметризовать?»
4. Если есть — подсовываешь ему список значений через `metafunc.parametrize`.

#### Пример кода
Представь, что у нас есть файл `data.json` со списком ID товаров, и мы хотим создать тест для каждого ID.

**`conftest.py`**
```python
import json

def pytest_generate_tests(metafunc):
    # 1. Проверяем, ищем ли мы аргумент 'product_id' в текущем тесте
    if "product_id" in metafunc.fixturenames:
        # 2. Загружаем данные из внешнего источника (имитация)
        try:
            with open("data.json", "s") as f:
                data = json.load(f)
                ids = data["product_ids"]
        except Exception:
            ids = [0]  # Fallback, чтобы тесты не упали при ошибке загрузки

        # 3. Магия: динамически создаем параметры
        # Аргумент 'product_id' получит значения из списка 'ids'
        metafunc.parametrize("product_id", ids, ids=[f"ID_{i}" for i in ids])
```

**`test_products.py`**
```python
def test_product_exists(product_id):
    # Этот тест автоматически запустится столько раз, сколько ID в JSON
    print(f"Testing product: {product_id}")
    assert product_id is not None
```

2.  **Имена аргументов (Fixture Names):** Хук работает через проверку `metafunc.fixturenames`. Если ты опечатаешься в имени аргумента в тесте (например, напишешь `prod_id` вместо `product_id`), параметризация не сработает, и тест просто запустится один раз с ошибкой или как обычный тест.

С хорошими `ids` ты сразу увидишь: `test_product[ID_apple]`.
4.  **Производительность:** Помни, что этот код выполняется на этапе **сбора** (collection). Если ты вставишь туда тяжелый запрос к БД или медленный парсинг огромного XML, PyTest будет «задумчиво» запускаться по 30 секунд. Старайся делать загрузку данных максимально легкой.
5.  **Сложная логика:** Ты можешь использовать `metafunc.config` внутри хука, чтобы проверять флаги командной строки (например, запускать расширенный набор тестов только если передан флаг `--full-scan`).

# 🏷️ Шпаргалка: Встроенные маркеры PyTest

**Маркеры** — это «метки» или «теги», которые мы вешаем на тестовые функции или классы. Они позволяют управлять жизненным циклом теста: пропускать его, помечать как ожидаемый провал или группировать для запуска.

### 1. `@pytest.mark.skip` — Полный пропуск
Используй, когда тест **нельзя** запускать в текущем состоянии (например, функционал еще не написан или удален).

*   **Как работает:** Тест даже не пытается выполниться. В отчете он помечается как `skipped`.
*   **Нюанс:** Всегда пиши аргумент `reason="причина"`. Без причины ты сам запутаешься через неделю, почему этот тест не работает.

```python
import pytest

@pytest.mark.skip(reason="Функционал оплаты еще в разработке")
def test_payment_gateway():
    assert True
```

### 2. `@pytest.mark.skipif` — Условный пропуск
Самый мощный инструмент для кроссплатформенного тестирования. Тест пропускается, только если выполняется определенное **условие**.

*   **Как работает:** Ты передаешь логическое выражение (результат `True` или `False`).
*   **Нюанс:** Условие должно быть валидным Python-выражением. Часто используется для проверки ОС, версии Python или наличия переменной окружения.

```python
import sys
import pytest

# Пропускаем тест, если мы запускаем его на Windows
@pytest.mark.skipif(sys.platform == "win32", reason="Тест работает только на Linux/Mac")
def test_linux_specific_feature():
    assert True
```

### 3. `@pytest.mark.xfail` — Ожидаемый провал (Expected Failure)
Используй, когда ты **знаешь**, что тест упадет (например, зафиксирован баг в Jira, и ты ждешь фикса).

*   **Как работает:** Если тест падает — это считается «успехом» (статус `XFAIL`). Если тест внезапно проходит — это статус `XPASS` (Unexpected Pass), что сигнализирует о том, что баг либо исправлен, либо тест невалиден.
*   **Нюанс:** Это отличный способ держать тесты в репозитории, не «засоряя» общую статистику падениями, но при этом не удаляя их.

```python
@pytest.mark.xfail(reason="Баг №123: API возвращает 500 вместо 200")
def test_api_status_code():
    # Мы ожидаем, что здесь будет ошибка, но если она пройдет — это XPASS
    assert response.status_code == 200 
```

### 4. `@pytest.mark.xfail_strict` — Строгий режим провала
Это модификатор (или параметр внутри `xfail`), который меняет поведение `XPASS`.

*   **Как работает:** Если тест, помеченный как `xfail`, внезапно **проходит**, PyTest пометит его не как `XPASS`, а как **реальную ошибку (FAIL)**.
*   **Зачем это нужно:** Чтобы ты не пропустил момент, когда баг был исправлен. Это заставляет тебя приходить в код и обновлять маркер.

```python
@pytest lapytest.mark.xfail(strict=True, reason="Ждем исправления бага")
def test_critical_bug():
    # Если этот тест пройдет — вся сборка упадет (Fail)
    assert False 
```

### 🛠️ Управление запусками через CLI
Маркеры бесполезны, если ты не умеешь ими пользоваться при запуске. Используй флаг `-m`.

*   `pytest -m "not slow"` — Запустить все тесты, кроме помеченных маркером `slow`.
*   `pytest -m "smoke and api"` — Запустить тесты, у которых есть либо маркер `smoke`, либо `api`.
*   `pytest -m "smoke not regression"` — Запустить только `smoke`, исключив `regression`.

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `skip` и `xfail`?**
**О:** `skip` — это «мы даже не пытаемся проверять». `xfail` — это «мы проверяем, и мы ожидаем увидеть ошибку». Если тест в `skip` пройдет — ты об этом не узнаешь. Если тест в `xfail` пройдет — ты увидишь `XPASS`.

**В: Можно ли вешать несколько маркеров на один тест?**
**О:** Да. Ты можешь написать `@pytest.mark.smoke` и сверху `@pytest.mark.skipif(...)`. PyTest применит их последовательно.

**В: Что будет, если я использую кастомный маркер (например, `@pytest.mark.api`), но не прописал его в `pytest.ini`?**
**О:** PyTest выдаст предупреждение (`PytestUnknownMarkWarning`). В больших проектах это плохой тон. Все свои метки нужно регистрировать в файле конфигурации `pytest.ini` в секции `markers`, чтобы избежать путаницы и предупреждений.

**В: Как пропустить тесты, если в системе не установлена определенная библиотека?**

```python
import importlib.util
has_pandas = importlib.util.find_spec("pandas") is not None

@pytest.mark.skipif(not has_pandas, reason="Нужен pandas для этого теста")
def test_data_processing():
    ...
```

# 🛠 Cheat Sheet: `@pytest.mark.skip`

### 🎯 Суть
`@pytest.mark.skip` — это декоратор, который говорит PyTest: **«Просто забудь про этот тест, даже не пытайся его запускать»**. Тест помечается как `skipped` (статус `s` в консоли) и полностью исключается из процесса выполнения.

### 💻 Синтаксис
```python
import pytest

@pytest.mark.skip(reason="Здесь пишем честную причину, почему мы это пропустили")
def test_broken_feature():
    assert True  # Этот код даже не начнет выполняться
```

### 🚀 Когда использовать (Use Cases)
Как Senior, я советую использовать `skip` только в крайних случаях. Это «красный флаг» для команды.
1. **Известный баг:** Тест упал из-за бага, который уже заведен в Jira/YouTrack. Мы не хотим, чтобы CI (Continuous Integration) падал красным, пока разработчик чинит задачу.
2. **Временная недоступность окружения:** Например, тест требует подключения к стороннему API, который сейчас на техобслуживании.
3. **Незавершенный функционал (WIP):** Фича еще в разработке, и писать на неё полноценный тест рано.

### ⚠️ Важные нюансы (Senior Tips)

1.  **Обязательный `reason`:** Никогда не оставляй пустой `reason`. Через месяц никто не вспомнит, почему этот тест пропущен. Хороший тон: `reason="Bug #123: API returns 500 error"`.
2.  **Skip vs XFail (Критически важно!):** 
    *   `@pytest.mark.skip` — мы **не запускаем** тест вообще. Мы не знаем, пройдет он или упадет.
    *   `@pytest.mark.xfail` — мы **запускаем** тест и **ожидаем**, что он упадет. Если он вдруг пройдет — это будет сигнал (XPassed). 
    *   *Ошибка джуна:* Использовать `skip` там, где нужно использовать `xfail`. Если ты знаешь, что код сломан, используй `xfail`.
3.  **Уровень применения:** Декоратор можно вешать не только на функцию, но и на **класс**. Все тесты внутри этого класса будут пропущены разом.
4.  **Технический долг:** Каждый `@pytest.mark.skip` в твоем репозитории — это технический долг. Если их становится много, значит, процесс тестирования деградирует.

**О:** В консоли он увидит символ `s` (skipped). В HTML-отчетах будет отдельный раздел "Skipped", где благодаря параметру `reason` будет видна причина.

**В: Если я пропустил тест через `@pytest.mark.skip`, выполняются ли фикстуры?**
**О:** Тело теста не выполняется. Однако, если у тебя есть фикстуры с областью видимости `session` или `module`, они всё равно отработают (так как они инициализируются до начала тестов). Но фикстуры с областью `function` для этого конкретного теста запускаться не будут.

```python
@pytest.mark.slow
```

# 🛠 Шпаргалка: `@pytest.mark.skipif`

### 🎯 Суть
`@pytest.mark.skipif` — это декоратор для **условного пропуска** тестов. В отличие от простого `@pytest.mark.skip`, который выключает тест «намертво», `skipif` проверяет логическое условие (True/False) прямо во время выполнения. Если условие истинно — тест пропускается.

### 📝 Синтаксис
```python
import pytest
import sys

@pytest.mark.skipif(condition, reason="Тут пишем, почему мы скипаем")
def test_something():
    pass
```
*   **`condition`**: Любое выражение, которое возвращает `True` или `kom`.
*   **`reason`**: **Обязательный (по хорошему) параметр**. Без него коллега через месяц не поймет, почему тест не запускается.

---

### 🚀 Основные сценарии использования

#### 1. Зависимость от операционной системы
Самый частый кейс. Если фича работает только на Linux или требует специфичного драйвера для Windows.
```python
import sys
import pytest

@pytest.mark.skipif(sys.platform == "win32", reason="Этот тест не работает на Windows")
def test_linux_specific_feature():
    # Тест выполнится только на Linux/Mac
    pass
```

#### 2. Проверка наличия установленной библиотеки
Если ваш тест использует тяжелую библиотеку (например, `pandas` или `tensorflow`), и вы не хотите, чтобы тесты падали с `ImportError` у коллег, у которых её нет.
```python
import pytest
import importlib.util

# Проверяем, установлена ли библиотека pandas
pandas_installed = importlib.util.find_spec("pandas") is not None

@pytests.mark.skipif(not pandas_installed, reason="Pandas не установлен, тест пропускается")
def test_data_processing():
    import pandas as pd
    # ... логика теста
```

#### 3. Проверка переменных окружения (Environment Variables)
Когда нужно запускать тесты только в определенном окружении (например, только на `staging`).
```python
import os
import pytest

@pytest.mark.skipif(os.getenv("ENV") != "staging", reason="Тест доступен только в staging среде")
def test_api_integration():
    pass
```

---

### ⚠️ Нюансы и Senior-советы (Pro Tips)

1.  **Не пишите сложную логику в декораторе.** Декоратор должен быть читаемым. Если условие занимает 5 строк — вынесите его в отдельную переменную или фикстуру перед тестом.
    *   *Плохо:* `@pytest.mark.skipif(os.getenv("A") == "1" and os.getenv("B") == "2" ...)`
    *   *Хорошо:* `is_ready = check_env_conditions(); @pytest.mark.skipif(not is_ready, ...)`

2.  **Scope (Область видимости).** Вы можете вешать `skipif` не только на функции, но и на **классы**. Это позволит пропустить сразу всю группу тестов одним махом.

3.  **Reason — это ваше лицо.** Никогда не оставляйте `reason=""`. В отчетах (например, в Allure или HTML-отчетах) именно этот текст будет единственным объяснением того, почему тест "пропал".

4.  **Связка с `xfail`.** Не путайте `skipif` и `xfail`. 
    *   `skipif` — мы даже не пытаемся запускать код (условие выполнено).
    *   `xfail` — мы запускаем код, но ожидаем, что он упадет.

**В: Что будет, если условие в `skipif` вернет `False`?**
О: Тест запустится в обычном режиме. `skipif` работает как «предохранитель»: срабатывает только когда условие `True`.

**В: Можно ли использовать `skipif` для пропуска тестов на основе результата другого теста?**
О: Напрямую через декоратор — нет. Декораторы вычисляются в момент сбора тестов (collection phase). Для зависимостей между тестами лучше использовать фикстуры или логику внутри теста.

****В: Как это выглядит в консоли при запуске?**
О: PyTest пометит тест как `s` (skipped) и выведет ваш `reason` рядом с названием теста.

**В: Можно ли вешать несколько декораторов `skipif` на один тест?**
О: Да. Если хотя бы один из них вернет `True`, тест будет пропущен. Это удобно для комбинированных условий (например, «пропустить, если Windows И нет переменной ENV»).

# 🛠 Шпаргалка: `@pytest.mark.xfail`

### 💡 Суть темы
**XFAIL** (Expected Failure) — это маркер для тестов, которые **должны упасть**. 

Представь ситуацию: ты нашел баг. Ты завел тест, который воспроизводит этот баг. Тест падает. Но ты не можешь его починить прямо сейчас (например, нужно ждать фикса от другой команды или рефакторинга). Чтобы этот падающий тест не «краснел» в CI/CD и не блокировал сборку, ты помечаешь его как `xfail`. Ты как бы говоришь системе: *"Я знаю, что здесь ошибка, это нормально, не паникуй"*.

---

### ⚙️ Как это работает (Основные режимы)

#### 1. Базовый режим (Default)
Если ты просто напишешь `@pytest.mark.xfail`, PyTest будет считать тест успешным, если он упал с **любой** ошибкой.
*   **Тест упал** $\rightarrow$ Статус `XFAIL` (считается "пройденным" для CI).
*   **Тест прошел** $\rightarrow$ Статус `XPASS` (Unexpected Pass — это плохо, значит баг уже исправлен, но ты об этом не знаешь).

#### 2. Строгий режим (`strict=True`) — **Важно!**
Это то, что отличает Senior от Junior. В промышленной разработке почти всегда нужно использовать `strict=True`. 
При `strict=True`, если тест внезапно **пройдет успешно**, PyTest пометит его как **ошибку (XPASS)**. Это заставит тебя вернуться к тесту и обновить его, так как старый баг уже не воспроизводится.

#### 3. Фильтрация ошибок (`raises`)
Ты можешь указать, что тест считается "ожидаемо упавшим" только если вылетает конкретное исключение. Если вылетит другое — это будет настоящий провал.

---

### 📝 Примеры кода

```python
import pytest

# --- Сценарий 1: Базовый (не рекомендую в проде) ---
@pytest.mark.xfail
def test_known_bug():
    assert 1 == 2  # Тест упадет, но CI будет "зеленым"

# --- Сценарий 2: Строгий режим (Best Practice) ---
@pytest.mark.xfail(strict=True)
def test_critical_bug():
    # Если кто-то починит этот баг, тест станет XPASS и подсветит ошибку
    assert 1 == 3

# --- Сценарий 3: Ожидаем конкретную ошибку ---
@pytest.mark.xfail(raises=ValueError, strict=True)
def test_expected_exception():
    # Тест считается успешным (XFAIL), только если упал с ValueError.
    # Если упадет TypeError — это будет реальный провал теста.
    raise ValueError("Баг все еще здесь")

# --- Сценарий 4: С кастомным сообщением ---
@pytest.mark.xfail(reason="Зависит от обновления API в следующем спринте")
def test_with_reason():
    assert False
```

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Не превращай XFAIL в свалку:** Самая большая ошибка — оставлять `xfail` на старые баги месяцами. Это создает иллюзию стабильности ("зеленого" билда), когда на самом деле проект разваливается. Если баг исправлен — удаляй маркер или переводи тест в обычный режим.
2.  **XPASS — это сигнал к действию:** Если видишь в логах `XPASS`, не игнорируй его. Это значит, что твой "тест на ошибку" прошел успешно. Либо баг починили без тебя, либо ты неправильно написал тест.
3.  **Разница с `@pytest.mark.skip`:** 
    *   `skip` — мы вообще не запускаем код теста (полезно, если фича еще не написана).
    *   `xfail` — мы **запускаем** код и проверяем, что он ломается именно так, как мы ожидаем.

### ❓ FAQ (Частые вопросы)

**В: Чем `xfail` отличается от `skip`?**
**О:** `skip` полностью игнорирует тест. `xfail` выполняет код. Используй `skip`, если кода еще нет, и `xfail`, если код есть, но он работает неправильно (из-за известного бага).

**В: Что такое `XPASS`?**
**О:** Это "Unexpected Pass". Ситуация, когда тест, помеченный как "должен упасть", внезапно прошел успешно. В режиме `strict=True` это считается ошибкой, чтобы ты не забыл обновить тест.

**В: Можно ли использовать `xfail` вместе с параметризацией?**
**О:** Да. Каждая параметризованная итерация будет иметь свой статус. Одна может быть `xfail`, а другая (с другими данными) — обычным `pass`.

**В: Когда стоит использовать параметр `raises` в `xfail`?**
**О:** Когда ты хочешь убедиться, что тест падает именно из-за конкретной ошибки (например, `ValueError`), а не из-за того, что у тебя просто упала база данных или отвалился интернет.

# 🧠 Шпаргалка: `@pytest.mark.xfail_strict`

### Что это такое?
В PyTest есть маркер `xfail` (Expected Failure). Он используется для тестов, которые **должны упасть**. Это ваш способ сказать фреймворку: *"Я знаю, что здесь баг, не паникуй, когда увидишь красный цвет"*.

Однако, по умолчанию поведение `xfail` довольно "мягкое". Маркер `strict=True` делает его "строгим".

---

### 1. Стандартный `@pytest.mark.xfail` (Без strict)
Когда вы используете обычный `xfail`, PyTest отслеживает два сценария:
1. **Тест упал (Expected Failure):** Всё отлично, тест пометился как `XFAIL`. Мы довольны.
2. **Тест прошел (Unexpected Pass):** Опа! Баг исправлен, но мы не ожидали этого. PyTest пометит его как **`XPASS`** (extra pass). 
   * **Нюанс:** Для общей статистики выполнения тестов `XPASS` — это "зеленая" зона. Тест-ран не считается проваленным.

### 2. Строгий `@pytest.mark.xfail_strict`
Этот маркер меняет правила игры. Он превращает "нежданную победу" в полноценную ошибку.
1. **Тест упал (Expected Failure):** Всё отлично, статус `XFAIL`.
2. **Тест прошел (Unexpected Pass):** **ВНИМАНИЕ!** Тест помечается как **`FAILED`**. 

---

### Зачем это нужно Senior-у? (Смысл и стратегия)
Использование `strict=True` — это инструмент контроля жизненного цикла бага.

* **Зачем использовать обычный `xfail`?** Когда вы фиксируете временный баг, который не критичен прямо сейчас, и вам не важно, когда его поправят.
* **Зачем использовать `xfail_strict`?** Когда вы ждете фикса. Вы говорите: *"Я ожидаю, что этот тест падает. Если он вдруг пройдет — значит, в коде произошли изменения, которые я не контролирую (регрессия или случайность), и я должен об этом узнать"*.

**Это способ превратить `XPASS` из "просто уведомления" в "сигнал к действию".**

---

### Код для сравнения

```python
import pytest

def broken_function():
    # Представим, что здесь баг: функция должна возвращать 0, а возвращает 1
    return 1

# --- СЦЕНАРИЙ 1: Мягкий xfail ---
@pytest.mark.xfail
def test_soft_failure():
    assert broken_function() == 0
    # Если баг исправят и функция вернет 0, тест получит статус XPASS (не ошибка)

# --- СЦЕНАРИЙ 2: Строгий xfail ---
@pytest.mark.xfail(strict=True)
def test_strict_failure():
    assert broken_function() == 0
    # Если баг исправят и функция вернет 0, тест получит статус FAILED!
    # Это заставит разработчика или вас пересмотреть этот тест.
```

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем главная разница между `xfail` и `skip`?**
**О:** `skip` — это когда мы вообще не запускаем код теста (например, из-за отсутствия ОС). `xfail` — это когда код **выполняется**, но мы заранее знаем, что результат будет отрицательным.

**В: Что если тест упал с другой ошибкой, которую я не ожидал?**
**О:** Если вы используете `xfail`, любая ошибка (AssertionError или любой Exception) считается "ожидаемой". Но если вы используете `strict=True` и тест прошел — это всегда `FAIL`.

**В: Можно ли использовать `xfail_strict` вместе с `match`?**
**О:** Да. Вы можете ожидать конкретное сообщение об ошибке. Если текст ошибки изменится (даже если тест упадет), это может быть важным сигналом.

**В: Когда мне стоит переключиться с `xfail` на `xfail_strict`?**
**О:** Как только баг переходит из разряда "забытый" в разряд "в работе". Это дисциплинирует команду: нельзя просто исправить баг и забыть обновить тест, если он помечен как `strict`.

# 🔖 Шпаргалка: Кастомные маркеры в PyTest

**Кастомные маркеры** — это «теги» или «метки», которые ты вешаешь на тесты, классы или целые модули. Представь, что это хештеги в Instagram: они не меняют содержание поста, но позволяют мгновенно найти все посты по теме `#food` или `#travel`.

В тестировании маркеры нужны для **фильтрации**: запустить только быстрые тесты, пропустить тяжелые интеграционные или выделить только критически важные (Smoke).

---

### 🛠 1. Как использовать (Синтаксис)

Маркеры вешаются через декоратор `@pytest.mark.<имя_маркера>`.

*   **На отдельный тест:**
    ```python
    @pytest.mark.smoke
    def test_login():
        assert True
    ```
*   **На весь класс (все тесты внутри класса получат этот маркер):**
    ```python
    @pytest.mark.regression
    class TestUserModule:
        def test_create(self): ...
        def test_delete(self): ...
    ```
*   **Несколько маркеров на одном тесте:**
    ```python
    @pytest.mark.smoke
    @pytest.mark.api
    def test_get_user():
        ...
    ```

---

### ⚠️ 2. Главный нюанс: Регистрация маркеров (Senior Tip)

Если ты просто напишешь `@pytest.mark.my_cool_marker`, PyTest запустит тест, но **выдаст предупреждение (Warning)** в консоль:
`PytestUnknownMarkWarning: unknown marker 'my_cool_marker'`.

В больших проектах игнорировать варнинги — плохая практика. Чтобы всё было «по красоте», маркеры нужно зарегистрировать в конфигурационном файле проекта (`pytest.ini` или `pyproject.toml`). Это говорит PyTest: «Я знаю об этих маркерах, это не ошибка».

**Пример для `pytest.ini`:**
```ini
[pytest]
markers =
    smoke: критически важные тесты (проверка основного функционала)
    regression: полная проверка всей системы
    slow: тяжелые тесты, требующие много времени
    api: тесты, работающие через API слой
```

**Пример для `pyproject.toml`:**
```toml
[tool.pytest.ini_options]
markers = [
    "smoke: critical tests",
    "slow: heavy tests"
]
```

---

### 🔍 3. Фильтрация при запуске (CLI)

Самая мощная часть. Используем флаг `-m`.

*   **Запуск по одному маркеру:**
    `pytest -m smoke` — запустятся только тесты с меткой `smoke`.
*   **Логические операторы (`and`, `or`, `not`):**
    `pytest -m "smoke and not slow"` — запустить важные тесты, но исключить те, что идут долго.
    `pytest -m "api or regression"` — запустить либо API тесты, либо регрессионные.
*   **Сложные условия:**
    `pytest -m "not (slow or integration)"` — запустить всё, кроме тяжелых и интеграционных тестов.

---

### 🚀 Резюме для Senior-разработчика

1.  **Маркеры — это метаданные.** Они не меняют логику теста, они управляют его выборкой.
2.  **Всегда регистрируй маркеры в `pytest.ini`.** Это признак чистого кода и отсутствия «мусорных» варнингов в CI/CD логах.
3.  **Используй иерархию.** Маркер на классе — это удобно, чтобы не дублировать код над каждым методом.
4.  **Не злоупотребляй.** Если маркеров становится слишком много (например, 50 штук), их станет невозможно поддерживать. Группируй их по смыслу.

### ❓ FAQ (Частые вопросы)

**В: Можно ли использовать кастомный маркер вместе со встроенным, например `@pytest.mark.skip`?**
О: Да, абсолютно. Ты можешь пометить тест как `@pytest.mark.slow` и одновременно добавить `@pytest.mark.skip(reason="Broken")`. PyTest корректно обработает оба декоратора.

**В: Что будет, если я забуду прописать маркер в `pytest.ini`?**
О: Тест выполнится, но ты получишь `PytestUnknownMarkWarning`. В серьезных проектах это может привести к тому, что CI/CD упадет, если настроена проверка на наличие предупреждений (флаг `-W error`).

**В: Можно ли передавать параметры в кастомный маркер?**
О: Напрямую через декоратор `@pytest.mark.my_marker(param=1)` — нет, это не совсем стандартный путь для маркеров PyTest. Для передачи данных лучше использовать **параметризацию** (`@pytest.mark.parametrize`). Маркеры предназначены для *категоризации*, а не для *передачи данных*.

**В: Как быстро найти все тесты без определенного маркера?**
О: Используй оператор `not`. Команда `pytest -m "not slow"` — твой лучший друг при быстрой проверке кода.

# 🛠 Шпаргалка: Фильтрация тестов через CLI

Когда проект разрастается с 10 до 1000 тестов, запускать их все при каждом изменении — непозволительная роскошь. **Фильтрация** — это твой главный инструмент для экономии времени и изоляции проблем.

В PyTest есть два принципиально разных способа фильтрации: по **маркерам** (`-m`) и по **имени** (`-k`).

---

### 1. Фильтрация по маркерам (`-m`)
Этот способ работает через флаг `-m`. Он использует логику, которую ты заранее заложил в тесты с помощью декораторов `@pytest.mark.name`.

#### Базовый синтаксис:
* `pytest -m smoke` — запустить только тесты, помеченные маркером `smoke`.
* `pytest -m regression` — запустить только тесты с маркером `regression`.

#### Логические операторы (Boolean Logic):
Senior-разработчик всегда использует комбинации, чтобы точечно выбирать нагрузку:
* **AND (`and`)**: Тест должен иметь *оба* маркера.
  `pytest -m smoke and regression` — только тесты, которые и smoke, и regression одновременно.
* **OR (`or`)**: Тест должен иметь *хотя бы один* из маркеров.
  `pytest -m smoke or integration` — запустит всё, что относится к дымовым или интеграционным тестам.
* **NOT (`not`)**: Исключение тестов. Это киллер-фича для ускорения прогонов.
  `pytest -m "not slow"` — запустить все тесты, кроме тех, что помечены как `slow`.

> [!IMPORTANT]
> **Нюанс (Senior Level):** Если ты используешь кастомные маркеры (например, `@pytest.mark.api`), PyTest может выдать предупреждение (`PytestUnknownMarkWarning`). Чтобы этого избежать, всегда регистрируй свои маркеры в файле конфигурации `pytest.ini` или `pyproject.toml` в секции `markers`. Это признак хорошего тона и чистого кода.

---

### 2. Фильтрация по имени (`-k`)
Флаг `-k` работает не с метаданными (маркерами), а с **текстовой строкой** в названии функции или класса. Он использует алгоритм поиска подстроки (похоже на `grep`).

#### Примеры использования:
* `pytest -k "login"` — найдет все тесты, где в названии есть слово "login" (`test_login_success`, `test_user_login_error` и т.д.).
* `pytest -k "user and not admin"` — очень мощная штука: найдет тесты, содержащие "user", но исключит те, где есть "admin".
* `pytest -k "setup or teardown"` — найдет тесты, в названии которых есть либо "setup", либо "teardown".

---

### 3. Сводная таблица: `-m` vs `-k`

| Характеристика | `-m` (Markers) | `-k` (Keyword/Name) |
| :--- | :--- | :--- |
| **Основа** | Декораторы `@pytest.mark...` | Имя функции/класса |
| **Гибкость** | Высокая (можно группировать логически) | Низкая (зависит от нейминга) |
le **Скорость** | Быстрее (PyTest сразу знает, что брать) | Чуть медленнее (нужно сканировать имена) |
| **Когда использовать** | Для создания уровней тестирования (smoke, regression, api) | Когда нужно быстро найти конкретный тест по названию |

---

### 4. Бонус: Полезные флаги для управления запуском
* `--lf` (или `--last-failed`): Запустить только те тесты, которые **упали в прошлый раз**. Незаменимо при отладке!
* `--ff` (или `--failed-first`): Сначала запустить упавшие тесты, а потом все остальные. Позволяет сразу увидеть результат по проблемным зонам.

---

### ❓ FAQ (Частые вопросы)

**В: Что делать, если я забыл, какие маркеры вообще есть в проекте?**
**О:** Просмотри файл `pytest.ini` или `pyproject.toml`. Все «законные» маркеры должны быть там прописаны. Если их нет — значит, они созданы «на лету», и их стоит зафиксировать.

**В: Можно ли комбинировать `-m` и `-k` в одной команде?**
**О:** Да, можно! Например: `pytest -m smoke -k "user"`. PyTest найдет тесты, которые одновременно помечены как `smoke` И содержат слово `user` в названии. Это двойной фильтр.

**В: Почему `-k` иногда работает странно с большими названиями?**
**О:** Помни, что `-k` — это просто поиск подстроки. Если у тебя есть тесты `test_login` и `test_login_admin`, то запрос `-k "login"` выберет **оба**. Для более точного контроля используй маркеры.

**В: Как быстро запустить только один конкретный тест, не зная его маркеров?**
**О:** Используй `-k`. Если ты помнишь хотя бы кусочек названия, например `test_auth_01`, просто пиши `pytest -k "auth"`.

# 🛡️ Тема: Проверка исключений (Exception Testing)

В тестировании важно не только проверить, что код работает правильно, но и убедиться, что он **правильно падает**, когда что-то идет не так. Если твой код должен выкидывать `ValueError` при передаче отрицательного числа, а вместо этого молчит или выкидывает `TypeError`, — это баг.

### 1. Базовый синтаксис: `pytest.raises`
Основной инструмент — контекстный менеджер `with pytest.raises(ErrorType)`. 

**Логика проста:** если внутри блока `with` возникла ошибка `ErrorType`, тест **проходит**. Если ошибки не случилось или возникла другая ошибка — тест **падает**.

```python
import pytest

def divide(a, b):
    if b == 0:
        raise ValueError("Деление на ноль недопустимо!")
    return a / b

def test_divide_by_zero():
    # Мы ожидаем именно ValueError
    with pytest.raises(ValueError):
        divide(10, 0)
```

### 2. Проверка текста ошибки: параметр `match`
Мало знать, что вылетела ошибка `ValueError`. Важно убедиться, что это *та самая* ошибка с *тем самым* сообщением. Для этого используется аргумент `match`.

**Важно:** `match` принимает **регулярное выражение (regex)**.

```python
def test_divide_by_zero_message():
    # Проверяем, что в тексте ошибки есть фраза "ноль"
    with pytest.raises(ValueError, match="ноль"):
        divide(10, 0)
```
*Senior Tip: Не пиши слишком длинный `match`. Если ты привяжешься к каждой запятой в сообщении, тест упадет при малейшем рефакторинге текста ошибки. Используй частичное совпадение.*

### 3. Глубокий анализ: объект `excinfo`
Иногда нужно проверить не только текст, но и специфические атрибуты кастомного исключения (например, код ошибки в API). Для этого мы сохраняем объект исключения через `as excinfo`.

```python
class MyCustomError(Exception):
    def __le(self, error_code):
        self.error_code = error_code

def test_custom_error_attributes():
    with pytest.raises(MyCustomError) as excinfo:
        raise MyCustomError("Ошибка доступа", error_code=403)
    
    # Теперь мы можем изучить объект excinfo
    assert excinfo.type is MyCustomError
    assert excinfo.value.error_code == 403  # Проверяем кастомный атрибут
```

---

### ⚠️ Нюансы и «Подводные камни» (Senior Insights)

1.  **Правило узкого контекста (The Narrow Scope Rule):**
    Это самая частая ошибка джунов. **Никогда не пихай много строк кода внутрь одного `with pytest.raises`.**
    
    *Плохо:*
    ```python
    with pytest.raises(ValueError):
        step_1()  # Ошибка может возникнуть тут
        step_2()  # А может быть тут, и тест все равно пройдет! (Ложноположительный результат)
        step_3()  # Это опасно
    ```
    *Хорошо:* Выделяй в `with` только ту конкретную строку/функцию, которая должна вызвать ошибку.

2.  **Опасность слишком широких исключений:**
    Не используй `pytest.raises(Exception)`. Это «ловушка». Ты поймаешь любую ошибку (даже синтаксическую или системную), и тест пройдет, хотя программа сломана. Всегда указывай максимально конкретный тип ошибки (`ValueError`, `KeyError` и т.д.).

3.  **Регулярные выражения в `match`:**
    Помни, что `.` — это спецсимвол в regex. Если ты хочешь проверить точку в тексте, нужно экранировать её: `match=r"Error\. occurred"`.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что если я хочу проверить, что ошибка НЕ возникла?**
**О:** Для этого не нужен специальный инструмент. Просто напиши код без `pytest.raises`. Если ошибка возникнет — PyTest сам прервет тест и пометит его как `Error`.

**В: Можно ли использовать декоратор `@pytest.mark.xfail` вместо `pytest.raises`?**
**О:** Нет, это разные вещи. 
- `pytest.raises` проверяет, что ошибка возникла **в конкретном месте кода** внутри теста.
- `@pytest.mark.xfail` говорит PyTest: «Я знаю, что этот **весь тест целиком** упадет с ошибкой, не считай это провалом». Это инструмент для работы с недописанным функционалом, а не для проверки логики.

**В: Как проверить, что ошибка содержит несколько разных подстрок?**
**О:** Поскольку `match` — это regex, используй конструкцию «Lookahead»: 
`with pytest.raises(ValueError, match=r"(?=part1)(?=part2)")`. Это проверит наличие обоих фрагментов в любом порядке.

# 🧠 Шпаргалка: Проверка содержимого ошибки в PyTest

### 1. Базовый уровень: `pytest.raises`
Самый простой способ проверить, что конкретный тип ошибки возникает при выполнении кода. Мы используем контекстный менеджер `with`.

```python
import pytest

def divide(a, b):
    if b == 0:
        raise ValueError("Division by zero is not allowed")
    return a / b

def test_divide_by_zero():
    # Тест пройдет, если возникнет ValueError
    with pytest.raises(ValueError):
        divide(10, 0)
```
*   **Нюанс:** Если код внутри `with` **не** выбросит `ValueError`, тест упадет. Если выбросит другой тип ошибки (например, `TypeError`), тест тоже упадет.

---

### 2. Уровень Middle: Проверка текста ошибки (`match`)
Просто проверить тип ошибки часто недостаточно. Нам нужно убедиться, что сообщение об ошибке содержит правильный текст. Для этого у `pytest.raises` есть параметр `match`.

```python
def test_divide_error_message():
    # match принимает регулярное выражение (regex)
    with pytest.raises(ValueError, match="not allowed"):
        divide(10, 0)
```
*   **Как это работает:** PyTest берет строку из `match` и проверяет, есть ли такое совпадение в тексте ошибки.
*   **Нюанс (Senior Tip):** `match` использует **регулярные выражения**. Это значит, что ты можешь использовать `.*` для частичного совпадения или `^` для проверки начала строки. 
    * *Плохо:* `match=".*"` (это слишком размыто, тест пропустит любую ошибку).
    * *Хорошо:* `match="^Division by zero"` (строгое начало строки).

---

### 3. Уровень Senior: Глубокая инспекция через `excinfo`
Иногда текста ошибки мало. Например, если ты тестируешь кастомное исключение, у которого есть дополнительные атрибуты (например, код ошибки или ID транзакции). В этом случае мы перехватываем объект исключения с помощью `as excinfo`.

```python
class MyCustomError(Exception):
    def __int__(self, message, error_code):
        super().__init__(message)
        self.error_code = error_code

def trigger_error():
    raise MyCustomError("Access denied", error_code=403)

def test_custom_error_attributes():
    with pytest.raises(MyCustomError) as excinfo:
        trigger_error()
    
    # Теперь мы можем изучать объект исключения напрямую
    # excinfo.value — это и есть само поднятое исключение
    assert "Access denied" in str(excinfo.value)
    assert excinfo.value.error_code == 403
```
*   **Почему это круто:** Ты можешь проверять любые свойства объекта: `status_code`, `payload`, `user_id` и так далее.

---

### ⚠️ Важные нюансы (Anti-patterns & Best Practices)

1.  **Не делай `match` слишком широким.** Если ты напишешь `match=".*"`, ты можешь случайно пропустить ситуацию, когда ошибка произошла по совершенно другой причине, но текст просто совпал по случайности.
2.  **Избегай проверки всего текста целиком.** Текст ошибок часто меняется (добавили точку в конце или изменили регистр). Лучше проверять ключевое слово: `match="not allowed"`, а не `match="Division by zero is not allowed."`. Это сделает тесты менее «хрупкими» (brittle).
3.  **Соблюдай границы области видимости.** Код внутри `with pytest.raises` должен содержать **только ту строку**, которая должна вызвать ошибку. Если ты засунешь туда лишний код, который тоже может выкинуть `ValueError`, тест пройдет ложно (False Positive).

### ❓ FAQ: Часто задаваемые вопросы

**В: Что если я хочу проверить, что ошибка НЕ возникает?**
О: Для этого не нужно использовать `pytest.raises`. Просто напиши обычный код. Если ошибка возникнет — PyTest сам пометит тест как упавший.

**В: Можно ли в `match` передать просто строку без регулярных выражений?**
О: Да, но помни, что PyTest все равно интерпретирует её как regex. Если в твоем тексте ошибки есть спецсимволы (например, `[ERROR]`), их нужно экранировать `r"\[ERROR\]"`.

**В: Как проверить несколько разных ошибок в одном тесте?**
О: Тебе нужно создать два отдельных блока `with pytest.raises`. Один блок — это один сценарий проверки. Не пытайся запихнуть проверку двух разных исключений в один `with`.

**В: Что такое `excinfo`?**
О: Это объект типа `ExceptionInfo`. Он содержит не только само исключение (`value`), но и информацию о том, где именно (traceback) оно произошло. Но в 99% случаев тебе нужен именно `.value`.

# 💡 Шпаргалка: Детальные сообщения (Assertion Messages)

В PyTest стандартный `assert` — это не просто проверка «правда или ложь». Это мощный инструмент диагностики. Но новички часто используют его либо слишком примитивно, либо избыточно.

### 1. Базовый синтаксис
Python позволяет добавить строку после условия через запятую. Если условие `False`, эта строка выводится в консоль.

```python
def test_simple_message():
    status = "error"
    assert status == "success", f"Ожидали 'success', но получили '{status}'"
```

### 2. Магия PyTest: Assertion Rewriting
**Это самый важный нюанс.** В отличие от стандартного `unittest`, PyTest делает «перезапись» (rewriting) ваших ассертов. Когда тест падает, PyTest автоматически показывает значения всех переменных, участвующих в проверке.

**Плохой пример (избыточность):**
```python
def test_redundant_message():
    x = 5
    y = 10
    # НЕ НУЖНО писать f"x={x}, y={y}", потому что PyTest и так покажет: assert 5 == 10
    assert x == y, f"x было {x}, а y было {y}" 
```

**Хороший пример (контекст):**
Пиши сообщение не о том, *какие* значения пришли, а о том, *почему* это важно или *что именно* проверяется в данном бизнес-кейсе.

```python
def test_contextual_message():
    user_id = 42
    is_active = False
    # Мы добавляем контекст: какой именно пользователь не прошел проверку
    assert is_active, f"Пользователь с ID {user_id} должен быть активен для выполнения операции"
```

### 3. Когда сообщения жизненно необходимы? (Best Practices)

1.  **Сложные условия:** Если у тебя длинный `assert` с несколькими `and/or`, при падении будет непонятно, какое именно звено цепи сломалось. Разбей на несколько ассертов или добавь пояснение.
2.  **Циклы и параметры:** Если ты перебираешь список объектов, всегда добавляй в сообщение уникальный идентификатор (ID, name), чтобы понять, на каком именно элементе упал тест.
    ```python
    for product in products:
        assert product.price > 0, f"Цена товара '{product.name}' (ID: {product.id}) не может быть нулевой"
    ```
3.  **Бизнес-логика:** Когда проверка касается сложного правила (например, "возраст должен быть > 18 и наличие паспорта == True"). Сообщение должно объяснять нарушение правила.

### 4. Антипаттерны (Как делать не надо)

*   ❌ **Дублирование вывода PyTest:** `assert a == b, f"a is {a} and b is {b}"` — это мусор в логах.
*   ❌ **Слишком длинные сообщения:** Если сообщение занимает 5 строк, его никто не будет читать. Краткость — сестра таланта.
*   ❌ **Отсутствие контекста:** `assert result, "Error"` — бесполезно. Что за ошибка? В каком модуле?

---

### ❓ FAQ (Частые вопросы)

**В: Зачем мне вообще писать сообщения, если PyTest и так показывает значения переменных?**
**О:** PyTest показывает *состояние* (что именно упало), но он не знает *намерение* (почему это должно было быть так). Сообщение дает контекст: "Этот юзер должен иметь роль Admin", а не просто "Role is User".

**В: Можно ли использовать `print()` вместо сообщений в `assert`?**
**О:** Нет. `print()` выводится только при запуске с флагом `-s`. Если тест проходит, ты вообще не увидишь свои принты. Сообщения в `assert` видны всегда, когда тест падает.

**В: Что делать, если проверка очень сложная и ассертов слишком много?**
**О:** Если у тебя 10 ассертов в одном тесте — это "тест-спагетти". Лучше разбить один большой тест на несколько маленьких (атомарных). Один тест = одна проверяемая логика.

# 🛠 Шпаргалка: Фикстура `monkeypatch`

**`monkeypatch`** — это встроенная в PyTest фикстура, предназначенная для временного изменения (подмены) атрибутов объектов, переменных окружения и элементов словарей во время выполнения теста.

**Главная суперсила:** Она автоматически делает **teardown** (откат изменений). Как только тест завершается (успешно или с ошибкой), `monkeypatch` возвращает всё в исходное состояние. Тебе не нужно вручную чистить за собой мусор.

---

### 🚀 Основные методы

#### 1. Подмена атрибутов (`setattr`)
Используется, когда нужно заменить метод или значение переменной в объекте или модуле.
```python
def test_example(monkeypatch):
    import my_module
    # Было: my_module.api_url = "https://real-api.com"
    # Стало:
    monkeypatch.setattr(my_module, "api_url", "https://fake-api.com")
    
    assert my_module.api_url == "https://fake-api.com"
```

#### 2. Работа с переменными окружения (`setenv` / `delenv`)
Незаменима, когда код зависит от `os.getenv`.
```python
import os

def test_env_var(monkeypatch):
    # Устанавливаем переменную
    monkeyrentepatch.setenv("DATABASE_URL", "sqlite:///:memory:")
    assert os.getenv("DATABASE_URL") == "sqlite:///:memory:"
    
    # Удаляем переменную (raising=False, чтобы не упасть, если её и так нет)
    monkeypatch.delenv("DATABASE_URL", raising=False)
    assert os.getenv("DATABASE_URL") is None
```

#### 3. Работа со словарями (`setitem` / `delitem`)
Позволяет подменять значения в `dict` или `os.environ` (который по сути тоже словарь).
```python
def test_dict(monkeypatch):
    my_config = {"debug": False, "timeout": 30}
    
    monkeypatch.setitem(my_config, "debug", True)
    assert my_config["debug"] is True
    
    monkeypatch.delitem(my_config, "timeout")
    assert "timeout" not in my_config
```

---

### 🧠 Нюансы от Senior-а (Важно!)

1.  **`monkeypatch` vs `mocker` (`pytest-mock`)**: 
    *   Используй `monkeypatch`, если нужно просто подменить **значение** или **переменную окружения**. Это быстрее и проще.
    *   Используй `mocker` (из плагина `pytest-mock`), если тебе нужно подменить **функцию** так, чтобы она возвращала разные значения (`return_value`), проверяла количество вызовов (`assert_called_once`) или вела себя как `spy`. `monkeypatch` не умеет проверять, сколько раз была вызвана функция.
2.  **Автоматический откат**: Ты можешь быть уверен, что если ты изменил `os.environ` в одном тесте, это **не повлияет** на следующий тест. Это критически важно для изоляции тестов.
3.  **Порядок имеет значение**: Если ты патчишь один и тот же атрибут в разных фикстурах, сработает последняя. Но `monkeypatch` откатит изменения в порядке, обратном их применению (LIFO).
4.  **Область видимости**: `monkeypatch` работает только внутри функции теста или фикстуры, куда она передана. Она не "живет" дольше, чем длится тест.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Что произойдет с изменениями, если тест упадет с ошибкой?**
**О:** Ничего страшного. `monkeypatch` гарантирует откат изменений даже в случае падения теста (Exception). Это предотвращает "эффект домино", когда один сломанный тест портит состояние окружения для всех последующих.

**В: Можно ли использовать `monkeypatch.setattr` для замены функции на другую функцию?**
**О:** Да, абсолютно. Ты можешь передать в качестве значения любую callable-объект (лямбду или другую функцию). Это базовый способ имитации поведения сложной логики.

**В: В чем разница между `monkeypatch.setattr(obj, "attr", val)` и `monkeypatch.setitem(obj, "attr", val)`?**
**О:** 
*   `setattr` используется для объектов (классов, модулей), где доступ идет через точку: `obj.attr`.
*   `setitem` используется для коллекций (словари, списки), где доступ идет через скобки: `obj["attr"]`.

**В: Можно ли с помощью `monkeypatch` подменить `sys.path`?**
**О:** Да, это отличный способ добавить тестовую папку в пути поиска модулей прямо во время теста, чтобы не менять системные переменные навсегда.

# 🛠 Шпаргалка: Библиотека `pytest-mock`

### Что это такое?
`pytest-mock` — это не замена стандартной библиотеке `unittest.mock`, а **обертка (wrapper)** над ней, адаптированная под экосистему PyTest. 

**Главная фишка:** Она предоставляет фикстуру `mocker`. В отличие от классического декоратора `@patch`, фикстура `mocker` автоматически делает **teardown** (откатывает изменения) после завершения теста. Тебе не нужно беспокоиться о том, что подмена в одном тесте сломает другой.

---

### 🚀 Основные инструменты

#### 1. `mocker.patch(target)` — Король мокинга
Заменяет объект или функцию на `MagicMock`.
* **Как использовать:** Передавай строку с полным путем к объекту, который ты хочешь подменить.
* **Пример:** Подмена функции `requests.get`.

```python
def test_api_call(mocker):
    # Мы подменяем requests.get ТАМ, где он используется (в модуле my_service)
    mock_get = mocker.patch('my_service.requests.get')
    mock_get.return_value.status_code = 200
    
    # Теперь при вызове в коде вернется наш мок
    from my_service import fetch_data
    assert fetch_data() == "Success"
```

#### 2. `mocker.spy(target)` — Режим «Шпион»
В отличие от `patch`, шпион **не меняет** поведение функции, но записывает все её вызовы (аргументы, количество вызовов).
* **Зачем:** Когда тебе нужно проверить, что функция была вызвана, но ты не хочешь ломать реальную логику.

```python
def test_spy_example(mocker):
    from my_module import real_function
    spy = mocker.spy(real_function)
    
    # Вызываем код, который внутри использует real_function
    do_something() 
    
    assert spy.call_count == 1
```

#### 3. `mocker.patch.dict(dictionary, values)` — Работа со словарями
Идеально для подмены переменных окружения (`os.environ`) или конфигураций.

```python
def test_env_var(mocker):
    mocker.patch.dict('os.environ', {'API_KEY': 'fake_key'})
    # Теперь в рамках теста API_KEY всегда равен 'fake_key'
```

#### 4. `mocker.stub(target)` — Заглушка (Stub)
Создает объект, который ведет себя как простая замена, но без лишней магии `MagicMock`. Используется редко, в основном для упрощения тестов, где не важна сложная логика.

---

### ⚠️ Золотые правила и нюансы (Senior Tips)

1.  **Правило «Patch where it is USED» (Самое важное!):**
    Это главная ошибка джунов. Не нужно патчить место, где функция *определена*. Нужно патчить место, где она *импортирована*.
    *   *Плохо:* `mocker.patch('utils.get_data')` (если `service.py` делает `from utils import get_data`).
    *   *Хорошо:* `mocker.patch('service.get_data')`.
    *   **Почему?** Потому что когда `service.py` выполняет импорт, он забирает ссылку на оригинальную функцию. Если ты подменишь оригинал в `utils`, в `service` всё равно останется старая ссылка.

2.  **`return_value` vs `side_effect`:**
    *   Используй `.return_value`, когда хочешь, чтобы мок просто возвращал готовый результат (число, строку, объект).
    *   Используй `.side_effect`, когда нужно:
        *   Выбросить исключение: `mock.side_effect = Exception("Boom!")`.
        *   Возвращать разные значения при каждом вызове: `mock.side_effect = [1, 2, 3]`.
        *   Запустить другую функцию.

3.  **Автоматический Cleanup:**
    Никогда не используй `patcher.start()` и `patcher.stop()` вручную внутри тестов с `pytest-mock`. Фикстура `mocker` сама всё очистит. Ручной контроль нужен только в очень специфических интеграционных тестах на уровне сессии.

### ❓ FAQ (Частые вопросы)

**В: Чем `mocker.patch` лучше, чем декоратор `@patch`?**
**О:** В `@patch` ты должен следить за порядком аргументов в функции теста (чем больше патчей, тем сложнее). В `mocker` ты просто вызываешь его внутри тела теста. Плюс — автоматический откат изменений без риска забыть `stop()`.

**В: Как проверить, что функция была вызвана с конкретными аргументами?**
**О:** Используй методы ассертов у мока:
*   `mock.assert_called_with(arg1, arg2)` — проверит именно последний вызов.
*   `mock.assert_called_once_with(...)` — проверит, что был ровно один вызов и с нужными данными.

**В: Что делать, если я хочу подменить метод объекта, а не функцию в модуле?**
**О:** Используй `mocker.patch.object`.
*   Пример: `mocker.patch.object(user_instance, 'save', return_value=True)`. Это чище, чем писать полный путь строкой.

**В: Могу ли я использовать `spy` на встроенных функциях типа `print`?**
**О:** Технически — да, но это плохая практика (антипаттерн). Тесты станут нестабильными и будут зависеть от вывода в консоль. Шпионить лучше за своим кодом.

# 🛠 Шпаргалка: `pytest-mock` и `mocker.patch`

### Что это такое?
`pytest-mock` — это обертка над стандартной библиотекой `unittest.mock`. Она предоставляет фикстуру `mocker`, которая делает жизнь тестировщика проще. 

**Главное преимущество перед стандартным `unittest.mock.patch`:** 
Тебе **не нужно** вручную останавливать патч (не нужен `patcher.stop()` или контекстный менеджер `with`). Фикстура `mocker` сама «откатит» все изменения после завершения теста. Это гарантирует, что один тест не испортит состояние другого.

---

### 🎯 Золотое правило: Куда патчить? (The "Where to Patch" Rule)
Это самая частая ошибка джунов. **Патчить нужно не там, где функция определена, а там, где она ИСПОЛЬЗУЕТСЯ.**

*   **Ситуация А:** В файле `service.py` написано `import utils`. 
    *   *Как патчить:* `mocker.patch("service.utils.some_func")`.
*   **Ситуация Б:** В файле `service.py` написано `from utils import some_func`.
    *   *Как патчить:* `mocker.patch("service.some_func")`. (Потому что в момент импорта ссылка на функцию уже скопирована в `service.py`).

---

### 🛠 Основные приемы

#### 1. Простая подмена значения (`return_value`)
Когда нам нужно, чтобы функция всегда возвращала конкретный результат.
```python
def test_api_success(mocker):
    # Заменяем вызов API на возврат словаря
    mock_get = mocker.patch("app.client.get", return_value={"status": 200})
    
    result = my_function_under_test()
    assert result == {"status": 200}
```

#### 2. Имитация ошибки (`side_effect`)
Используется, когда нужно проверить, как твой код обрабатывает исключения или когда нужно, чтобы функция возвращала разные значения при каждом вызове.
```python
def test_api_error(mocker):
    # Имитируем выброс исключения
    mocker.patch("app.client.get", side_effect=Exception("Connection Timeout"))
    
    # Проверяем, что наш код корректно обрабатывает ошибку (например, логирует её)
    with pytest.raises(Exception):
        my_function_under_test()

def test_multiple_calls(mocker):
    # Имитируем последовательные разные ответы: сначала успех, потом ошибка
    mocker.patch("app.client.get", side_effect=[{"id": 1}, Exception("Error")])
    # Первый вызов вернет словарь, второй — упадет
```

#### 3. Магия `autospec=True` (Senior Tip ⭐)
Если ты просто патчишь функцию, Mock-объект «всеяден». Он позволит вызвать функцию с любыми аргументами, даже если в реальности их там нет. Это создает ложное чувство безопасности.
**Всегда используй `autospec=True`**, чтобы Mock соответствовал сигнатуре (аргументам) оригинальной функции. Если ты изменишь аргументы в коде, но не обновишь тест — `autospec` заставит тест упасть.

```python
# Без autospec: тест пройдет, даже если мы передадим 100 лишних аргументов
mocker.patch("module.func") 

# С autospec: тест упадет, если количество аргументов не совпадает с оригиналом
mocker.patch("module.func", autospec=True)
```

### ⚠️ Нюансы и подвохи

1.  **Patching Classes:** Когда ты патчишь класс, ты подменяешь сам конструктор. Все объекты, созданные через `mocker.patch("path.to.Class")`, будут объектами типа `MagicMock`.
2.  **Order of patches:** Если тебе нужно пропатчить несколько объектов, порядок в коде обычно не важен (так как `mocker` чистит всё сам), но логически лучше идти от общего к частному.
3.  **Don't patch builtins:** Старайся избегать патчинга `builtins.open` или `builtins.print`, если это не критично. Это может сломать работу самого pytest или других плагинов.

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `return_value` и `side_effect`?**

**В: Можно ли использовать `mocker.patch` внутри другого патча?**

**В: Как проверить, что функция была вызвана с правильными аргументами?**
**О:** Используй атрибуты созданного мока: 
`mock_obj.assert_called_once_with(arg1, arg2=True)`.

# 🕵️‍♂️ Шпаргалка: `pytest-mock` — `mocker.spy`

### Что это такое?
Если `mocker.patch` — это **подмена** (мы убираем реальный объект и ставим вместо него «пустышку»), то `mocker.spy` — это **шпионаж**. 

**Суть:** Оригинальный код продолжает работать как положено, но PyTest начинает записывать всё, что происходит с этой функцией: сколько раз её вызвали, с какими аргументами и что она вернула.

### Главное отличие: Patch vs Spy
| Характеристика | `mocker.patch` | `mocker.spy` |
| :--- | :--- | :--- |
| **Логика функции** | Заменяется на заглушку (Mock) | **Остается оригинальной** |
| **Возвращаемое значение** | По умолчанию `None` (или то, что ты укажешь) | **Реальное значение** из функции |
| **Цель** | Изолировать код, убрать тяжелые зависимости (БД, API) | Проверить взаимодействие (был ли вызов), не ломая логику |

---

### Как использовать (Базовый синтаксис)

Представь, что у нас есть сервис, который отправляет уведомления. Мы хотим проверить, что функция отправки вызывается, но нам важно, чтобы само письмо (логически) как бы «ушло».

```python
# code.py
def send_email(email, message):
    print(f"Sending email to {email}")
    return True

def notify_user(email):
    # Мы тестируем эту функцию, но хотим следить за send_email
    return send_email(email, "Welcome!")

# test_code.py
def test_notify_user_spy(mocker):
    import code
    
    # Создаем шпиона на функцию send_email в модуле code
    spy = mocker.spy(code, 'send_email')
    
    # Выполняем тестируемый код
    result = code.notify_user("test@example.com")
    
    # 1. Проверяем, что функция была вызвана
    assert spy.called
    
    # 2. Проверяем аргументы
    spy.assert_called_once_with("test@example.com", "Welcome!")
    
    # 3. Проверяем, что оригинальная логика отработала (результат True)
    assert result is True
```

---

### Ключевые атрибуты шпиона (что мы можем проверить)
После того как `spy` применен, объект `spy` ведет себя как обычный `Mock`:
*   `.called`: `True`, если функцию вызывали хотя бы раз.
*   `.call_count`: количество вызовов (число).
    *   *Пример:* `assert spy.call_count == 1`
*   `.call_args`: содержит аргументы последнего вызова.
    *   *Пример:* `args, kwargs = spy.call_args`
*   `.assert_called_with(...)`: проверяет, что последний вызов был именно с такими параметрами.
*   `.assert_called_once()`: проверка на ровно один вызов.

---

### ⚠️ Нюансы и «грабли» (Senior Tips)

1.  **Куда «шпионить»? (Targeting):** Это самая частая ошибка. Нужно шпионить не там, где функция *определена*, а там, где она *используется*. 
    *   Если `module_a` импортирует `send_email` из `module_b`, то шпионить нужно на `module_a.send_email`.

2.  **Spy не меняет поведение:** Если тебе нужно, чтобы функция вернула `False` вместо `True` (чтобы протестировать ветку ошибки), `spy` тебе не поможет. Для этого используй `patch`. Шпион — это только наблюдатель.

3.  **Side Effects:** Если оригинальная функция вызывает исключение (`raise Error`), шпион **не спасет** тест от падения. Он просто зафиксирует факт вызова, но ошибка всё равно пробросится дальше.

4.  **Область видимости:** `mocker.spy` автоматически очищается после завершения теста (благодаря фикстуре `mocker`). Тебе не нужно вручную «снимать шпиона».

### ❓ FAQ (Частые вопросы)

**В: Зачем мне `spy`, если я могу просто использовать `patch` и вернуть нужный результат?**
**О:** Если твоя функция — это часть сложной цепочки расчетов, и тебе важно, чтобы вся цепочка отработала честно, но ты хочешь лишь убедиться, что "шаг №2" был выполнен. С `patch` ты разрушишь всю цепочку, заменив её заглушкой.

**В: Можно ли шпионить за методом объекта?**
**О:** Да. Если у тебя есть класс `Service`, ты можешь сделать `mocker.spy(service_instance, 'method_name')`. Это очень удобно для проверки взаимодействия между объектами в рамках одного теста.

**В: Что делать, если я хочу и шпионить, и подменить результат?**
**О:** Технически, `spy` не предназначен для этого. Если тебе нужно изменить поведение — используй `patch`. Но если ты хочешь использовать `patch`, но при этом видеть аргументы (как в spy) — `patch` и так это умеет через атрибут `.call_args`. `spy` — это именно про сохранение оригинальной логики.

# 🛠 Шпаргалка: `mocker.stub` в `pytest-mock`

### 💡 Что это такое?
Если `mocker.patch` — это «хирургическая операция» (мы находим существующий объект в коде и заменяем его на подделку), то **`mocker.stub`** — это создание «пустышки» с нуля.

**Stub (Заглушка)** — это объект, который не имеет никакой логики, но имитирует интерфейс нужного тебе класса или функции. Его главная цель: **заменить зависимость, которую ты передаешь в функцию (Dependency Injection).**

### 🔍 Главное отличие: Stub vs Patch
Это самый частый вопрос на собеседованиях.

| Инструмент | Метод работы | Когда использовать |
| :--- | :--- | :--- |
| **`mocker.patch`** | Ищет существующий объект в модуле и подменяет его. | Когда код внутри функции сам импортирует и вызывает зависимость (сложно контролировать). |
| **`mocker.stub`** | Создает новый, чистый объект "из воздуха". | Когда ты сам передаешь объект в функцию через аргументы (Dependency Injection). |

---

### 🛠 Как использовать (Пример)

Представь, что у нас есть сервис, который отправляет уведомления. Мы не хотим реально отправлять Email, мы просто хотим передать «пустую» почтовую службу.

```python
# code.py
class EmailService:
    def send(self, message):
        # Здесь реальная логика отправки (SMTP, API и т.д.)
        print("Отправляем реальное письмо...")
        return True

class NotificationManager:
    def __init__(self, service: EmailService):
        self.service = service  # Мы внедряем зависимость (DI)

    def notify(self, text):
        return self.service.send(text)

# test_code.py
def test_notification_manager_with_stub(mocker):
    # 1. Создаем заглушку (Stub) вместо реального EmailService
    stub_service = mocker.stub()
    
    # 2. Настраиваем поведение (Stub — это по сути Mock, он может возвращать значения)
    # Мы говорим: "Когда вызовут метод send, верни True"
    stub_service.send.return_value = True

    # 3. Передаем заглушку в наш менеджер (Dependency Injection)
    manager = NotificationManager(service=stub_service)

    # 4. Выполняем действие
    result = manager.notify("Привет, мир!")

    # 5. Проверяем результат и то, что метод был вызван
    assert result is True
    stub_service.send.assert_called_once_with("Привет, мир!")
```

### 🧠 Нюансы от Senior-а

1.  **Stub — это не "глупая" заглушка.** В `pytest-mock` (который базируется на `unittest.mock`) объект, созданный через `stub`, обладает всеми возможностями полноценного `Mock`. Ты можешь настраивать `return_value`, `side_effect` (выброс ошибки), проверять количество вызовов и аргументы.
2.  **Идеально для Dependency Injection.** Если твой код написан грамотно, ты передаешь зависимости в конструктор или метод. В этом случае **всегда** используй `stub`. Это делает тесты чистыми, так как тебе не нужно "ловить" импорты внутри модулей через `patch`.
3.  **Проблема "Слишком много свободы".** Поскольку `stub` может всё, есть риск написать тест, который проверяет не логику, а то, как ты настроил заглушку. Старайся проверять только критически важные взаимодействия.

### ❓ FAQ (Частые вопросы)

**В: Если я использую `mocker.stub()`, мне всё равно нужно делать `patch` в файле, где объявлен класс?**
**О:** Нет! В этом и прелесть. Тебе не нужно знать, как называется путь к классу в системе импортов. Ты просто создаешь объект и "втыкаешь" его в тестируемый код.

**В: Чем `stub` отличается от `spy`?**
**О:** 
*   `stub` — это **новый** объект (пустой лист).
*   `spy` — это **существующий** объект, за которым ты просто подсматриваешь (он сохраняет оригинальную логику, но записывает вызовы).

**В: Могу ли я заставить `stub` выбросить ошибку?**
**О:** Да. Используй `side_effect`. 
*Пример:* `stub_service.send.side_effect = ConnectionError("Ошибка сети")`. Это отличный способ протестировать, как твой код обрабатывает сбои внешних систем.

**В: Когда `mocker.stub` бесполезен?**
**О:** Когда ты не можешь контролировать передачу объекта в функцию (например, тестируешь стороннюю библиотеку или легаси-код, где всё захардкожено через импорты). В этом случае твой единственный выбор — `mocker.patch`.

# 🛠 Шпаргалка: Конфигурационные файлы PyTest

В профессиональной разработке никто не запускает тесты длинной строкой аргументов вроде `pytest --addopts "-v --tb=short" ...`. Это неудобно, нельзя зафиксировать в Git и легко ошибиться. **Конфигурационные файлы** решают эту проблему: они позволяют зафиксировать правила игры для всей команды.

### 1. Основные игроки

#### A. `pytest.ini` — Классика
Это стандарт де-факто. Самый простой и понятный способ. Если видишь файл `.ini` в корне проекта — это он.
*   **Плюсы:** Простота, наглядность, поддержка всеми инструментами "из коробки".

#### B. `pyproject.toml` — Современный стандарт (Modern Way)
Сейчас в Python-сообществе принято собирать настройки всех инструментов (`black`, `isort`, `mypy`, `pytest`) в один файл `pyproject.toml`. 
*   **Плюсы:** Один файл на весь проект, меньше мусора в корне.
*   **Нюанс:** Настройки PyTest должны лежать внутри секции `[tool.pytest.ini_options]`.

#### C. `tox.ini` — Инструмент автоматизации (не совсем конфиг PyTest, но важно)
Используется для запуска тестов в разных окружениях (разные версии Python). Он вызывает `pytest`, поэтому может содержать инструкции по запуску, но это уже уровень выше.

---

### 2. Ключевые параметры (Что именно мы настраиваем?)

Независимо от формата, вот список того, что ты будешь конфигурировать в 90% случаев:

*   **`addopts`**: Самый важный параметр. Сюда мы записываем флаги, которые хотим подставлять автоматически при каждом запуске `pytest`.
    *   *Пример:* `addopts = -v --tb=short --durations=10` (подробный вывод, короткий traceback, отчет о самых долгих тестах).
*   **`testpaths`**: Указывает PyTest, в каких директориях искать тесты. Помогает не сканировать весь проект (например, папку `venv` или `data`), ускоряя запуск.
    *   *Пример:* `testpaths = tests integration`.
*   **`python_files`**: Если твои тесты называются не `test_*.py`, а как-то иначе, ты можешь это переопределить.
*   **`markers`**: **Критически важно!** Здесь мы регистрируем все свои кастомные маркеры (например, `slow`, `api`). Если не зарегистрировать маркер здесь, PyTest будет выдавать предупреждение `PytestUnknownMarkWarning`.
    *   *Пример:* `markers = slow: marks tests as slow`.
*   **`filterwarnings`**: Позволяет подавлять ненужные предупреждения (DeprecationWarning и т.д.) или превращать их в ошибки, чтобы код был чистым.

---

### 3. Примеры реализации

#### Вариант 1: `pytest.ini` (Старый добрый)
```ini
[pytest]
# Автоматические флаги при запуске
addopts = -ra -q --durations=5
# Где искать тесты
testpaths = tests/unit tests/integration
# Регистрация маркеров (чтобы не было варнингов)
markers =
    slow: marks tests as slow
    api: marks tests as integration api tests
# Игнорирование конкретных предупреждений
filterwarnings =
    ignore::DeprecationWarning
```

#### Вариант 2: `pyproject.toml` (Современный/Pro)
```toml
[tool.pytest.ini_options]
addopts = "-v --tb=short"
testpaths = ["tests"]
markers = [
    "slow: marks tests as slow",
]
filterwarnings = [
    "ignore::UserWarning",
]
```

---

### 4. Senior Nuances (Нюансы и ловушки)

1.  **Приоритет (Precedence):** Помни правило: **CLI > Config File**. Если ты в конфиге прописал `-v`, но в терминале запустил `pytest -q`, то запустится «тихий» режим. Командная строка всегда главнее.
2.  **Не дублируй `addopts`:** Если ты добавил флаг в конфиг, не пиши его в CI/CD пайплайнах. Это создает путаницу: "Почему я пишу `-v`, а тесты запускаются без него?".
3.  **Опасность `addopts = -x`:** Флаг `-x` (прекратить выполнение при первой ошибке) очень удобен для дебага, но **никогда** не включай его в конфиг или CI/CD. Это "сломает" отчеты: ты увидишь только первый упавший тест, а остальные даже не узнаешь, прошли они или нет.
4.  **`pyproject.toml` и списки:** В TOML-файлах будь внимателен с синтаксисом массивов (списков). Ошибки в запятых — самая частая причина, почему конфиг "не подхватился".

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что будет, если я создам и `pytest.ini`, и `pyproject.toml` с настройками PyTest?**
**О:** Будет конфликт. PyTest найдет первый подходящий конфиг. Обычно он берет тот, что "ближе" или выше по приоритету в логике поиска. **Senior совет:** Оставь только один. В современных проектах выбирай `pyproject.toml`.

**В: Зачем регистрировать маркеры в `markers`, если тесты и так работают без этого?**
**О:** Без регистрации PyTest будет ругаться на `UnknownMarkWarning`. В больших проектах, где логи (logs) забиты мусором, такие варнинги мешают увидеть реальные ошибки. Регистрация — это признак хорошего тона и чистого кода.

**В: Можно ли через конфиг настроить пути к `conftest.py`?**
**О:** Напрямую — нет. PyTest ищет `conftest.py` по дереву директорий, начиная от корня проекта или места запуска. Но ты можешь управлять тем, какие папки сканируются через `testpaths`.

**В: Как быстро добавить флаг в конфиг, если я уже запустил тест с ним в консоли?**
**О:** Это "ленивый" способ, но рабочий: просто скопируй часть строки из терминала и вставь в `addopts`. Но не забудь проверить, нет ли там конфликтующих флагов.

# 🔌 PyTest Plugins: Расширяем возможности фреймворка

**Плагины** — это модули, которые позволяют «допилить» PyTest под конкретные нужды проекта. Сам по себе PyTest — это мощное ядро, но плагины превращают его в полноценный инструмент для CI/CD, анализа покрытия и параллельного запуска.

Все плагины деля, на две категории: **встроенные** (часть экосистемы) и **сторонние** (устанавливаются отдельно).

---

### 🚀 Топ-Must-Have плагинов (Твой стартовый набор)

Если ты работаешь над реальным проектом, эти ребята должны быть в `requirements-dev.txt` по умолчанию:

1.  **`pytest-cov` (Code Coverage)**
    *   **Зачем:** Показывает, какой процент твоего кода покрыт тестами. Без него тестирование — это "стрельба с завязанными глазами".
    *   **Как использовать:** `pytest --cov=my_project_folder`.
    *   **Нюанс:** Он немного замедляет выполнение тестов, так как отслеживает каждую выполненную строку.

2.  **`pytest-xdist` (Parallel Execution)**
    *   **Зачем:** Запускает тесты в несколько потоков/процессов. Если у тебя 1000 тестов, один процесс будет идти вечность, а `xdist` размажет их по всем ядрам твоего процессора.
    *   **Как использовать:** `pytest -n auto` (автоматически использует все доступные ядра).
    *   **Нюанс (Senior Level):** **Осторожно с общими ресурсами!** Если твои тесты пишут в одну и ту же базу данных или используют один файл, параллельный запуск всё сломает (Race Condition). Нужно либо изолировать БД для каждого воркера, либо использовать фикстуры с `scope="session"`.

3.кре **`pytest-html` (Reporting)**
    *   **Зачем:** Генерирует красивый, читаемый HTML-отчет со всеми результатами, логами и ошибками. Это то, что ты скидываешь менеджеру или заливаешь в артефакты CI/CD.
    *   **Как использовать:** `pytest --html=report.html`.

4.  **`pytest-mock` (Better Mocking)**
    *   **Зачем:** Дает удобную фикстуру `mocker`. Это обертка над стандартным `unittest.mock`, которая автоматически делает "cleanup" (откатывает изменения) после завершения теста. Тебе не нужно вручную вызывать `patcher.stop()`.
    *   **Как использовать:** Просто добавь `mocker` в аргументы теста.

---

### ⚙️ Конфигурация плагинов

Не запускай каждый раз длинные команды в терминале. Senior-разработчик всегда настраивает плагины через файл конфигурации (обычно `pytest.ini` или `pyproject.toml`).

**Пример `pytest.ini`:**

### 🧠 Как это работает "под капотом" (Hooks)

Плагины не просто "втыкаются" в код. Они используют **систему хуков (Hooks)**. 
PyTest во время работы вызывает определенные события: *"Я нашел тесты"*, *"Я начинаю тест"*, *"Тест завершился"*. Плагины «подписываются» на эти события.

*   Если ты хочешь написать свой плагин, тебе нужно изучить `pytest_runtest_setup` или `pytest_collection_modifyitems`. Это позволяет менять поведение PyTest прямо в процессе его работы.

---

### ⚠️ Нюансы и подводные камни (Senior Advice)

1.  **Конфликты плагинов:** Иногда два плагина могут пытаться изменить одно и то же событие (hook). Если тесты ведут себя странно — проверь, не конфликтуют ли плагины по части сбора данных.
2.  **Засорение окружения:** Не устанавливай всё подряд. Каждый лишний плагин увеличивает время инициализации PyTest (`collection time`). В больших проектах это заметно.
3.  **Версионность:** Плагины часто обновляются и могут ломать совместимость с новой версией самого PyTest. Всегда фиксируй версии плагинов в `requirements.txt`.

# 🛠 Шпаргалка: pytest-cov

**`pytest-cov`** — это не самостоятельный инструмент, а удобная обертка (wrapper) над мощной библиотекой `coverage.py`. Его единственная задача: запустить тесты так, чтобы в процессе выполнения отследить, какие строчки кода были задействованы, а какие — остались «неприкосновенными».

### 🚀 Быстрый старт
**Установка:**
```bash
pip install pytest-cov
```

**Базовый запуск:**
Чтобы измерить покрытие для папки `src`, используй флаг `--cov`:
```bash
pytest --cov=src
```
*Результат: в консоли появится таблица с процентами покрытия.*

---

### 📊 Отчеты (Reporting)
Просто цифры в консоли — это мало. Для глубокого анализа нужны разные форматы.

1.  **`term-missing` (Стандарт де-факто):** Показывает не только %, но и конкретные номера строк, которые **не** были протестированы.
    ```bash
    pytest --cov=src --cov-report=term-missing
    ```
2.  **HTML-отчет:** Самый наглядный способ. Генерирует папку `htmlcov`, где можно кликнуть на любой файл и увидеть подсвеченные строки (зеленые — ок, красные — пропущено).
    ```bash
    pytest --cov=src --cov-report=html
    ```
3.  **XML (Для CI/CD):** Нужен для интеграции с внешними сервисами вроде **SonarQube** или **Codecov**.
    ```bash
    pytest --cov=src --cov-report=xml
    ```

---

### ⚙️ Конфигурация (Best Practices)
Не забивай длинные команды в терминал. Все настройки нужно выносить в `pyproject.toml` или `.coveragerc`.

**Пример настройки в `pyproject.toml`:**
Это современный стандарт. Мы указываем, что именно считать, и какие файлы игнорировать.

```toml
[tool.pytest.ini_options]
addopts = "--cov=src --cov-report=term-missing --cov-report=html"

[tool.coverage.run]
source = ["src"]
branch = true  # Включает проверку ветвлений (if/else)

[tool.coverage.report]
exclude_lines = [
    "pragma: no cover",  # Игнорировать строки с этим комментарием
    "def __repr__",      # Игнорировать методы repr
    "if __name__ == .__main__.:" # Игнорировать блок запуска скрипта
]
```

---

### 💡 Важные нюансы (Senior Tips)

1.  **Branch Coverage (`--cov-branch`):** По умолчанию проверяется только выполнение строк. Но строка с `if` может выполниться, а вот ветка `else` — нет. Включай `branch = true`, чтобы видеть реальную картину сложности логики.
2.  **`# pragma: no cover`:** Это твой «спасательный круг». Если у тебя есть кусок кода (например, обработка критической ошибки, которую невозможно воспроизвести в тестах), добавь этот комментарий в конце строки, чтобы `coverage` не портил тебе статистику.
3.  **Игнорирование файлов:** Всегда исключай из покрытия тесты (`tests/`), конфигурационные файлы и миграции. Иначе твой процент будет искусственно завышен или занижен.

### ❓ FAQ (Частые вопросы)

**В: Почему у меня покрытие 0%, хотя я запустил pytest?**
**О:** Скорее всего, ты не указал директорию для анализа. `pytest-cov` не знает сам по себе, какой код проверять. Всегда используй `--cov=имя_папки`.

**В: В чем разница между `coverage.py` и `pytest-cov`?**
**О:** `coverage.py` — это «движок», который делает всю грязную работу по замеру строк. `pytest-cov` — это «плагин-переводчик», который позволяет передавать команды этому движку через синтаксис pytest.

**В: Как сделать так, чтобы покрытие не падало при добавлении новых тестов в CI?**
**О:** В CI/CD обычно используют порог (threshold). Можно настроить проверку, чтобы билд падал, если покрытие упало ниже, например, 80%. Это делается через конфиг `coverage.py` или дополнительные скрипты проверки.

**В: Что такое "Missing" в колонке отчета?**
**О:** Это номера строк в твоем исходном коде, которые не были затронуты ни одним из запущенных тестов. Твоя цель как инженера — минимизировать этот список.

# 🚀 Шпаргалка: pytest-xdist (Параллельный запуск тестов)

**`pytest-xdist`** — это плагин, который превращает последовательный запуск тестов в многопоточный/многопроцессный. Его главная цель — **сократить время выполнения Pipeline (CI/CD)**, задействуя все доступные ядра процессора.

### 🛠 Основные команды (CLI)

*   `pytest -n 4` — Запуск тестов в 4 параллельных процессах (воркерах).
*   `pytest -n auto` — **(Best Practice)** Плагин сам определит количество ядер процессора и запустит оптимальное число воркеров.
*   `pytest --dist loadscope` — Группировка тестов по области видимости (module или class). *Важно для избежания конфликтов.*
*   `pytest --dist loadfile` — Запуск тестов так, чтобы все тесты из одного файла попадали в один воркер.

### 🧠 Как это работает (под капотом)
Плагин создает несколько независимых процессов Python. Каждый процесс («воркер») получает свою порцию тестов. Важно понимать: **это не потоки (threads), а процессы**. У каждого воркера своя память, но они могут пытаться одновременно писать в одну и ту же базу данных или файл.

### ⚠️ Главные нюансы и «грабли» (Senior Tips)

1.  **Race Conditions (Состояние гонки):** Это самая частая проблема. Если два теста одновременно пытаются удалить одного и того же пользователя в БД, один упадет.
    *   *Решение:* Изолируйте данные. Используйте уникальные префиксы для имен пользователей/заказов (например, через `uuid`).

2.  **Shared Resources (Общие ресурсы):** Если ваши тесты используют одну и ту же базу данных или папку на диске, параллельный запуск их сломает.
    *   *Решение:* Используйте флаг `--dist loadscope`. Он гарантирует, что все тесты внутри одного класса будут выполняться в одном и том же воркере (последовательно), что предотвращает конфликты внутри одного модуля.

3.  **Фикстуры с `scope="session"`:** Будьте осторожны. Фикстура уровня `session` создается один раз для всего запуска. В `xdist` каждый воркер — это отдельный процесс, поэтому **каждый воркер запустит свою копию сессионной фикстуры**.
    *   *Нюанс:* Если вы создаете БД в `session` фикстуре, у вас будет столько баз данных, сколько воркеров.

4.  **Проблема Coverage:** Стандартный `pytest-cov` может некорректно собирать данные при параллельном запуске.
    *   *Решение:* Используйте специальные настройки или убедитесь, что используете последние версии плагинов, поддерживающих слияние данных.

### 📋 Резюме по стратегиям распределения (`--dist`)

| Стратегия | Что делает | Когда использовать |
| :--- | :--- | :--- |
| `load` (default) | Раскидывает тесты максимально хаотично | Если тесты абсолютно независимы и не трогают общие ресурсы. |
| `loadscope` | Группирует по модулю/классу | **Золотой стандарт.** Когда тесты в одном классе используют одну БД или один файл. |
| `loadfile` | Привязывает тесты к файлам | Когда нужно изолировать группы тестов на уровне файлов. |

### ❓ FAQ (Частые вопросы)

**В: Мои тесты проходят по одному, но падают при запуске с `-n auto`. В чем дело?**
**О:** Скорее всего, у тебя **Race Condition**. Тесты конфликтуют за общий ресурс (база данных, глобальная переменная, файл или порт). Проверь, не используют ли тесты одни и те же ID или пути.

**В: Как мне сделать так, чтобы каждый воркер работал со своей базой данных?**
**О:** В фикстуре настройки БД используй переменную окружения `PYTEST_XDIST_WORKER_ID`. Этот ID уникален для каждого воркера (например, `gw0`, `gw1`). На его основе генерируй имя базы: `db_test_{worker_id}`.

**В: Можно ли использовать `xdist` вместе с `monkeypatch`?**
**О:** Да, но помни, что `monkeypatch` работает только внутри процесса воркера. Он не сможет изменить что-то в другом воркере. Но так как воркеры изолированы, это обычно и есть то, что тебе нужно.

**В: Что делать, если тесты очень быстрые? Стоит ли включать `xdist`?**
**О:** Нет. Накладные расходы на запуск новых процессов (spin-up time) могут превысить выгоду от параллелизма. Если тесты бегут за 5 секунд, `xdist` может даже замедлить процесс. Используй его для тяжелых интеграционных или UI тестов.

# 🛠 Шпаргалка: pytest-html

**`pytest-html`** — это плагин, который превращает сухой текстовый вывод терминала в красивый, интерактивный HTML-отчет. Если ты работаешь в команде, где отчеты должны видеть не только разработчики, но и QA-лиды или менеджеры — этот плагин твой лучший друг.

### 1. Установка и базовый запуск
Устанавливается как любой другой пакет:
```bash
pip install pytest-html
```

Запуск с генерацией отчета:
```bash
pytest --html=report.html --self-contained-html
```
*   `--html=report.html`: путь, куда сохранится файл.
*   `--self-contained-html`: **Важнейший флаг!** Он упаковывает все CSS и картинки внутрь одного файла. Без него отчет будет "разваливаться" без внешних стилей.

### 2. Что внутри отчета?
Стандартный отчет содержит:
*   **Summary:** Общая статистика (сколько прошло, сколько упало, сколько пропущено).
*   **Duration:** Время выполнения каждого теста.
*   **Logs:** Весь `stdout` и `stderr` (то, что ты выводишь через `print()` или логирование) прямо внутри тела теста.
*   **Status:** Цветовая индикация (зеленый/красный/желтый).

### 3. Продвинутый уровень: Кастомизация (через `conftest.py`)
Просто отчет — это скучно. Senior-подход подразумевает добавление метаданных (версия приложения, браузер, окружение) и скриншотов при падении тестов.

#### А) Добавление метаданных (Metadata)
Чтобы в шапке отчета было видно, на какой версии системы шел тест, используй хук `pytest_html_results_as_table`.

```python
# conftest.py
def pytest_html_results_as_table(mainfunc, report):
    # Добавляем кастомную колонку в таблицу результатов
    report.extra = [{'name': 'Browser', 'value': 'Chrome 120'}]
```

#### Б) Автоматические скриншоты при падении (UI Testing)
Это «киллер-фича». Если ты тестируешь Web (Selenium/Playwright), тебе нужно, чтобы скриншот ошибки был вшит прямо в HTML.

```python
# conftest.py
import pytest

@pytest.hookimpl(tryfirst=True, hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()
    
    # Проверяем, что тест упал (failed)
    if report.when == "call" and report.failed:
        # Здесь логика получения скриншота (пример для Selenium)
        # driver = item.funcargs['driver'] 
        # driver.save_screenshot("error.png")
        
        # Прикрепляем скриншот к отчету
        from datetime_utils import get_timestamp # условная функция
        report.extra = [pytest_html.extras.image("error.png")]
```

### 4. Нюансы и "Подводные камни"
1.  **Размер файла:** Если ты прикрепляешь слишком много тяжелых скриншотов или логов, файл `report.html` может раздуться до сотен мегабайт, и браузер будет тормозить при открытии.
2.  **Перезапись:** По умолчанию каждый запуск перезаписывает старый отчет. Если тебе нужна история, используй динамическое имя файла (например, с таймстампом).
3.  **Параллельный запуск (`pytest-xdist`):** При использовании `-n auto` (параллельные тесты) `pytest-html` может вести себя нестабильно при попытке собрать всё в один файл. В сложных CI/CD пайплайнах отчеты часто собирают из нескольких кусков позже.

### ❓ FAQ (Частые вопросы)

**В: Можно ли добавить кастомные колонки в таблицу результатов?**
**О:** Да, через хук `pytest_html_results_table_headers`. Ты можешь добавить колонку "Owner" или "Feature Name", чтобы сразу видеть, какой модуль упал.

**В: Как сделать так, чтобы логи не засоряли отчет, если их слишком много?**
**О:** Используй стандартное логирование (`logging` модуль) и настрой уровень `INFO` или `WARNING`. В отчет попадает всё, что попало в `stdout`. Если ты используешь `print()`, он будет в отчете всегда.

**В: Как прикрепить не только картинку, но и текстовый файл (например, лог сервера)?**
**О:** Используй `pytest_html.extras.text(content="текст")` или `pytest_html.extras.file(path="path/to/log.txt")`. Это позволяет "проваливаться" в детали прямо из браузера.

**В: Можно ли использовать этот отчет в Jenkins/GitLab CI?**
**О:** Да! GitLab и Jenkins умеют парсить HTML-отчеты. Главное — настроить путь к файлу в конфигурации пайплайна (artifacts).

# 🧩 Шпаргалка: pytest-order

**`pytest-order`** — это плагин, который позволяет тебе явно управлять очередностью выполнения тестов. По умолчанию PyTest запускает тесты в произвольном порядке (обычно по алфавиту), и этот плагин дает тебе инструмент, чтобы это изменить.

### 🛠 Установка
```bash
pip install pytest-order
```

### 🚀 Базовое использование
Для управления порядком используется декоратор `@pytest.mark.order(n)`, где `n` — это целое число (чем меньше число, тем раньше выполнится тест).

```python
import pytest

@pytest.mark.order(2)
def test_second():
    print("\nЯ второй!")

@pytest.mark.order(1)
def test_first():
    print("\nЯ первый!")

@pytest.mark.order(3)
def test_third():
    print("\nЯ третий!")
```
*Результат: Сначала выполнится `test_first`, затем `test_second`, затем `test_third`.*

### 🏗 Продвинутые возможности
1.  **Порядок классов:** Ты можешь вешать маркер на целые классы. Все тесты внутри класса будут выполняться в рамках этого порядка.
2.  **Смешанный порядок:** Можно комбинировать маркеры для функций и классов.
    *   *Нюанс:* Если у тебя есть класс с `order(1)` и функция вне его с `order(2)`, сначала отработает класс.

---

### ⚠️ Senior Advice: Важные нюансы (The "Gotchas")

Как твой ментор, я обязан предупредить: **использование `pytest-order` — это почти всегда "code smell" (запах плохого кода).**

1.  **Нарушение изоляции (Главный грех):** Тесты должны быть атомарными и независимыми. Если `test_B` падает, потому что `test_A` не подготовил данные — у тебя проблема с архитектурой. **Решение:** Используй **Fixtures** для подготовки состояния, а не предыдущие тесты.
2.  **Проблема параллелизации (`pytest-xdist`):** Если ты начнешь запускать тесты в несколько потоков/процессов через `pytest-xdist`, плагин `pytest-order` потеряет смысл. Тесты будут распределены по разным воркерам, и порядок выполнения физически невозможно будет гарантировать.
4.  **Хрупкость (Brittleness):** Если ты расставил 100 тестов по порядку от 1 до 100, и тебе нужно вставить новый тест между 5-м и 6-м — тебе придется переписывать индексы у всех последующих тестов. Это кошмар для поддержки.
5.  **Когда это ДОПУСТИМО:** Единственный оправданный случай — тяжелые интеграционные или E2E (End-to-End) тесты, где ты имитируешь реальный пользовательский сценарий (например: *Создать корзину -> Добавить товар -> Оформить заказ*), и переписывать это на фикстуры слишком сложно или дорого по ресурсам.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что будет, если двум тестам присвоить одинаковый `order`?**
**О:** PyTest вернется к своему стандартному алгоритму поиска (обычно это порядок, в котором функции объявлены в файле или их алфавитный порядок). Конфликта не будет, но предсказуемость упадет.

**В: Можно ли использовать отрицательные числа?**
**О:** Да. `@pytest.mark.order(-1)` выполнится раньше, чем `@pytest.mark.order(0)`. Это удобно, если ты хочешь "впихнуть" какой-то критический тест в самое начало, не меняя все остальные индексы.

**В: Поможет ли этот плагин исправить падающие тесты?**
**О:** Нет. Он может *скрыть* симптомы (тест проходит, потому что предыдущий "подчистил" за собой мусор), но он не лечит причину. Если тест зависит от порядка — это баг в дизайне твоих тестов.

**В: Как проверить, в каком порядке реально идут тесты?**
**О:** Запускай с флагом `-v` (verbose). В логах будет видна последовательность выполнения.

# 🛠 Шпаргалка: pytest-django

**`pytest-django`** — это мост между миром PyTest и экосистемой Django. Без него PyTest «не знает» о твоих моделях, настройках (`settings.py`), базе данных и URL-адресах. Этот плагин делает так, чтобы тесты видели твой проект как живое Django-приложение.

### 1. Установка и базовая настройка
Просто установить мало. Нужно «подружить» PyTest с твоими настройками.

**Установка:**
```bash
pip install pytest-django
```

**Конфигурация (`pytest.ini` или `pyطproject.toml`):**
Это самый важный шаг. Ты должен указать, где лежат настройки твоего проекта. Если этого не сделать, получишь ошибку `ImproperlyConfigured`.

*Пример для `pytest.ini`:*
```ini
[pytest]
DJANGO_SETTINGS_MODULE = my_project.settings  # Путь к твоим настройкам
python_files = tests.py test_*.py *_tests.py
```

---

### 2. Главные фикстуры (Твои лучшие друзья)
Плагин «подбрасывает» в тесты готовые объекты, которые экономят кучу кода.

*   **`db`**: Самая важная фикстура. Она дает доступ к базе данных. Если твой тест пишет или читает из БД, ты **обязан** использовать её (или декоратор).
*   **`client`**: Это `django.test.Client`. Позволяет имитировать HTTP-запросы (`GET`, `POST` и т.д.) к твоим View. Идеально для интеграционных тестов.
*   **`rf` (RequestFactory)**: Позволяет создавать объекты запроса вручную. Используй его, если тестируешь конкретную функцию во `views.py`, не запуская весь цикл обработки HTTP-запуска.
*   **`admin_client`**: Тот же `client`, но уже авторизованный под суперпользователем. Удобно для тестов админки.
*   **`settings`**: Позволяет тебе в процессе теста менять настройки Django (например, временно отключить кэш или изменить `DEBUG`).

---

### 3. Работа с базой данных (Нюансы)

**Декоратор `@pytest.mark.django_db`:**
Если ты не используешь фикстуру `db` в аргументах функции, ты можешь повесить этот маркер на тест. Он делает то же самое: разрешает доступ к БД.

**Проблема транзакций (`transaction=True`):**
По умолчанию PyTest оборачивает каждый тест в транзакцию и откатывает её (rollback) после завершения. Это быстро. Но если ты тестируешь код, который сам управляет транзакциями (например, использует `transaction.atomic`), тебе нужно:
```python
@pytest.mark.django_db(transaction=True)
def test_something_with_atomic_blocks(db):
    ...
```

**Флаг `--reuse-db` (Маст-хэв для скорости!):**
Создание и миграция базы данных при каждом запуске — это долго. 
Используй флаг: `pytest --reuse-db`. 
Он будет использовать уже созданную базу, не пересобирая её с нуля. Если ты изменил модели — используй `--run-migrations`.

---

### 4. Продвинутые фишки

*   **Тестирование шаблонов (Templates):** Хотя `pytest-django` фокусируется на логике, для проверки рендеринга HTML всё равно лучше использовать `client.get(...)` и проверять наличие подстроки в `response.content`.
*   **Интеграция с `factory_boy`:** В профессиональной разработке никто не создает объекты через `Model.objects.create()`. Мы используем фабрики. `pytest-django` идеально работает в связке с ними.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему я получаю ошибку `django.core.exceptions.ImproperlyConfigured`?**
**О:** PyTest не знает, какой файл настроек использовать. Проверь свой `pytest.ini` и убедись, что путь в `DJANGO_SETTINGS_MODULE` верный (указывай путь от корня проекта).

**В: Могу ли я тестировать методы моделей без фикстуры `db`?**
**О:** Если метод только читает данные из памяти (не трогает БД), то можно. Но как только появляется запрос к БД (`objects.get`, `filter` и т.д.) — тест упадет с ошиблением доступа к базе, если не будет `db` или `@pytest.mark.django_db`.

**В: В чем разница между `client` и `rf`?**
**О:** 
- `client` — это "настоящий" браузерный запрос. Он проходит через Middleware, URL-conf и полноценный цикл Django. Это медленнее, но ближе к реальности.
- `rf` (RequestFactory) — это просто создание объекта запроса. Он не идет по цепочке Middleware. Это быстрее и подходит для чистого Unit-тестирования логики View.

**В: Как протестировать авторизацию пользователя?**
**О:** Самый простой путь через фикстуру `client`:
```python
def test_profile_page(client, user): # 'user' — это твоя кастомная фикстура или factory
    client.login(username=user.username, password='password')
    response = client.get('/profile/')
    assert response.status_code == 200
```

# 🧩 Шпаргалка: pytest-flask

**`pytest-flask`** — это специализированный плагин, который избавляет тебя от рутины при тестировании Flask-приложений. Вместо того чтобы вручную создавать `app.test_client()` в каждой фикстуре, плагин предоставляет готовые инструменты «из коробку».

### 🚀 Основная суть
Плагин работает по принципу **Dependency Injection**. Он ищет в твоем проекте фикстуру с именем `app`. Если он её находит, то автоматически создает для тебя фикстуры `client` (клиент для запросов) и `app` (само приложение).

### 🛠 Установка
```bash
pip install pytest-flask
```

### 🏗 Базовая настройка (The "Must-Have")
Чтобы плагин заработал, ты **обязан** предоставить ему объект приложения через фикстуру `app`. Без этого `client` не будет знать, к чему подключаться.

```python
import pytest
from my_project import create_app

@pytest.fixture(scope="session")
def app():
    """Создаем экземпляр приложения для тестов."""
    app = create_app(testing=True)  # Важно: используй конфиг для тестирования!
    
    with app.app_context():
        # Здесь можно инициализировать БД или другие ресурсы
        yield app
        # Здесь — очистка (teardown)
```

### 🧪 Использование фикстур

#### 1. Фикстура `client`
Это твой главный инструмент. Она имитирует поведение браузера/пользователя. Ты можешь делать `GET`, `POST`, `PUT`, `DELETE` запросы.

```python
def test_home_page(client):
    # client — это уже готовый FlaskClient
    response = client.get('/')
    assert response.status_code == 200
    assert b"Welcome" in response.data  # Проверка содержимого (в байтах!)

def test_create_user(client):
    payload = {"username": "admin", "email": "admin@test.com"}
    response = client.post('/users', json=payload) # Отправка JSON
    assert response.status_code == 201
```

#### 2. Фикстура `app`
Используется, если тебе нужно проверить настройки приложения (конфигурацию) или использовать контекст приложения.

```python
def test_config_value(app):
    assert app.config['TESTING'] is True
```

### 🔍 Продвинутые нюансы

#### Контекст запроса (`test_request_context`)
Иногда тест не является HTTP-запросом (например, ты тестируешь функцию, которая использует `request.args` или `session`). В этом случае тебе нужно «обернуть» код в контекст запроса.

```python
def test_access_session(client):
    with client.session_transaction() as sess:
        sess['user_id'] = 123
        
    # Теперь внутри этого блока (или в следующем запросе) сессия будет доступна
    response = client.get('/profile')
    assert response.status_code == 200
```

#### Работа с JSON и формами
*   **JSON:** Используй аргумент `json=...` (автоматически установит `content-type: application/json`).
*   **Формы:** Используй `data=...` (как обычный HTML Form).

### ⚠️ Senior Tips (На что наступают новички)

1.  **Scope (Область видимости):** Всегда старайся делать фикстуру `app` с областью `session`, чтобы не пересоздавать тяжелое приложение перед каждым тестом. Но помни: если ты меняешь конфиг приложения в одном тесте, это может «отравиться» на другие тесты.
2.  **Testing Mode:** Всегда устанавливай `app.config['TESTING'] = True`. Это отключает обработку ошибок (чтобы ты видел реальный traceback, а не кастомную страницу 500) и меняет поведение некоторых расширений.
3.  **Database Isolation:** Если используешь SQLAlchemy, фикстура `app` должна отвечать за создание таблиц, а отдельная фикстура (например, `db_session`) — за очистку данных после каждого теста.

# 🛠 Pytest Hooks: Глубокое погружение

**Hooks (хуки)** — это «точки перехвата» жизненного цикла Pytest. Представь, что Pytest — это конвейер на заводе. В определенные моменты (когда заезжает деталь, когда краска сохнет, когда машина выезжает из цеха) конвейер может остановиться или изменить настройки. Хуки позволяют тебе вклиниться в эти моменты и выполнить свой код.

Хуки пишутся либо в `conftest.py`, либо в полноценных плагинах.

### 1. Этап конфигурации (Configuration Hooks)
Здесь мы настраиваем «правила игры» до того, как тесты вообще начали искаться.

*   **`pytest_addoption(parser)`**: Самый важный хук для расширения CLI. Позволяет добавить свои флаги в команду запуска.
    * *Пример:* `--env=staging` или `--browser=chrome`.
    * *Нюанс:* Если ты добавишь аргумент здесь, он станет доступен во всех фикстурах через `request.config.getoption`.
*   **`pytest_configure(config)`**: Вызывается после того, как конфигурация сформирована. Здесь можно программно менять настройки или регистрировать кастомные маркеры (чтобы Pytest не ругался на неизвестные `@pytest.mark.my_marker`).

### 2. Этап сбора тестов (Collection Hooks)
На этом этапе Pytest бегает по папкам и ищет функции `test_*`.

*   **`pytest_collection_modifyitems(items)`**: **Король хуков.** Дает тебе доступ к списку всех найденных тестов (`items`) *перед* их запуском.
    * *Что можно сделать:* Переупорядочить тесты, массово добавить маркеры, или динамически пропустить тесты (skip) на основе условий (например, если база данных недоступна).
    * *Нюанс:* Это гораздо эффективнее, чем делать `skip` внутри самого теста.

### 3. Этап выполнения (Execution Hooks)
Здесь происходит магия запуска каждого конкретного теста.

*   **`pytest_runtest_setup(item)`**: Вызывается **перед** началом теста (но после фикстур с scope `session`, `module`, `class`). Идеально для подготовки глобального окружения.
*   **`pytest_runtest_call(item)`**: Вызывается непосредственно в момент выполнения функции теста. Обычно его не трогают, если только не пишут очень сложные обертки.
*   **`pytest_runtest_teardown(item)`**: Вызывается **после** завершения теста (независимо от того, упал он или прошел). Полезно для логирования финального состояния.
*   **`pytest_runtest_makereport(item, call)`**: Очень мощный хук. Он позволяет перехватить момент создания отчета о тесте.
    * *Кейс из практики:* Именно здесь делают скриншоты при падении Selenium-теста. Ты проверяешь: `if call.excinfo: take_screenshot()`.

### 4. Этап завершения (Reporting Hooks)
Когда все тесты прошли, и нужно подвести итоги.

*   **`pytest_sessionstart(session)`**: Вызывается один раз в самом начале всей сессии. Хорошо для инициализации тяжелых ресурсов (например, поднятия Docker-контейнера).
*   **`pytest_sessionfinish(session)`**: Вызывается в самом конце. Здесь можно закрыть соединения с БД или отправить уведомление в Slack/Telegram.
*   **`pytest_terminal_summary(terminalreporter, exitstatus, config)`**: Позволяет добавить кастомную информацию в финальный отчет в консоли (например, «Всего пройдено тестов: X, Время выполнения: Y»).

---

### 💡 Senior Tips & Nuances (Важные нюансы)

1.  **Где писать?** Если хук нужен только для текущего проекта — пиши в `conftest.py`. Если ты пишешь библиотеку/плагин, которую будут использовать другие команды — делай отдельный пакет и используй `entry_points` в `pyproject.toml`.
2.  **Производительность:** Будь осторожен с `pytest_runtest_setup`. Помни: этот код будет выполняться **перед каждым (!) тестом**. Если там тяжелая логика, твои тесты будут идти вечно. Используй фикстуры с широким scope (`session` или `module`) вместо хуков для тяжелых задач.
3.  **Порядок выполнения:** Помни, что фикстуры и хуки — это разные сущности. Фикстуры работают с *данными*, а хуки — с *процессом*. Не пытайся использовать хуки там, где достаточно простой фикстуры.

### ❓ FAQ (Частые вопросы)

**В: Можно ли через `pytest_addoption` передать путь к файлу с данными?**
**О:** Да, это стандартная практика. Ты добавляешь флаг `--data-file`, а затем в фикстуре читаешь его значение через `request.config.getoption`.

**В: Чем `pytest_runtest_setup` лучше, чем фикстура с `scope="function"`?**
**О:** Фикстура лучше для подготовки данных (объектов, БД). Хук лучше для инфраструктурных вещей, которые не зависят от конкретного теста (например, проверка доступности API перед стартом группы тестов).

**В: Как программно пропустить все тесты с маркером `@pytest.mark.slow` на Windows?**

**В: Где взять скриншот при падении теста?**
**О:** Используй хук `pytest_runtest_makereport`. В нем ты проверяешь статус вызова (`call.excinfo`) и, если есть ошибка, вызываешь метод драйвера для сохранения картинки.

# 🛠 Шпаргалка: Написание собственных CLI-аргументов в PyTest

Когда стандартных флагов `pytest -v` или `-m` становится недостаточно (например, нужно передать URL тестового стенда, логин/пароль или режим «глубокого» тестирования), тебе приходится расширять возможности командной строки.

### 1. Основная концепция
Для добавления своих аргументов используются **хуки (hooks)** PyTest. Весь процесс состоит из двух этапов:
1.  **Регистрация:** Мы говорим PyTest: «Смотри, теперь у нас есть новый флаг». Это делается через хук `pytest_addoption`.
2.  **Использование:** Мы достаем значение этого флага внутри тестов или фикстур.

Всё это пишется в файле **`conftest.py`**.

---

### 2. Реализация (Код)

Вот минимальный рабочий пример. Представь, что мы хотим добавить флаг `--env`, чтобы переключаться между `dev`, `staging` и `prod`.

```python
# conftest.py
import pytest

def pytest_addoption(parser):
    """
    Эта функция вызывается PyTest при инициализации. 
    Здесь мы регистрируем новые аргументы.
    """
    group = parser.addoption(
        "--env", 
        action="store",      # Мы будем передавать значение (например, --env dev)
        default="dev",       # Значение по умолчанию, если флаг не указан
        help="Environment to run tests against (dev, staging, prod)"
    )
    
    # Можно добавить булевый флаг (просто наличие флага включает его)
    parser.addoption(
        "--debug-mode", 
        action="store_true", # Если флаг есть, значение будет True, если нет — False
        help="Enable extra debug logging"
    )

@pytest.fixture(scope="session")
def env_config(request):
    """
    Фикстура, которая вытягивает значение нашего кастомного аргумента.
    """
    # request.config — это объект конфигурации PyTest, где лежат все опции
    return request.config.getoption("--env")

@pytest

def test_environment_check(env_config):
    print(f"\nRunning tests in: {env_config}")
    assert env_config in ["dev", "staging", "prod"]
```

**Как запускать:**
* `pytest` — запустится в `dev` (по дефолту).
* `pytest --env staging` — значение станет `staging`.
* `pytest --debug-mode` — флаг будет `True`.

---

### 3. Нюансы и Senior-советы (Важно!)

1.  **Где писать?** Всегда используй `conftest.py` в корне проекта или в папке с тестами. Если ты напишешь это в файле с тестом, аргумент не будет виден глобально.
2.  **Типизация:** PyTest не знает, что ты передаешь строку или число. Если тебе нужно число, используй `type=int` внутри `addoption`.
3.  **Использование `request.config`:** Чтобы достать значение в фикстуре, тебе **обязательно** нужно прокинуть аргумент `request` в свою фикстуру. Это «магический» объект PyTest, который содержит всё состояние запуска.
4.  **Не перегружай CLI:** Не делай слишком много кастомных аргументов. Если параметров становится больше 5 — лучше вынеси их в `.env` файл или `pytest.ini`. Командная строка должна оставаться читаемой.
5.  **Группировка:** Для больших проектов используй `parser.addgroup("My Project Options")`. Это красиво группирует аргументы в выводе `--help`.

### 4. FAQ (Частые вопросы)

**В: Можно ли использовать кастомный аргумент прямо в `pytest.ini`?**
**О:** Да, но только если ты передаешь его через `addoption`. В самом `.ini` файле ты можешь прописать значение по умолчанию для этого аргумента (через `addopts`), но сама логика регистрации всё равно должна быть в `conкретном conftest.py`.

**В: Что делать, если я хочу выбросить ошибку, если пользователь ввел неверный `--env`?**
**О:** Используй хук `pytest_configure`. В нем можно проверить значение `config.getoption("--env")` и, если оно некорректно, вызвать `pytest.exit("Error: Invalid env!")`. Это остановит запуск тестов еще до начала их выполнения.

**В: Можно ли изменить поведение других плагинов через свои аргументы?**
**О:** Да, это «высший пилотаж». Ты можешь создать флаг `--no-db`, и в фикстуре, отвечающей за базу данных, проверять этот флаг. Если он `True` — не инициализируй БД.

# 🚀 Шпаргалка: Интеграция PyTest с CI/CD

**Суть:** CI/CD превращает локальный запуск тестов в автоматизированный «вратарь» (Gatekeeper). Если тесты упали — код не попадает в мастер. Если прошли — путь открыт.

### 1. Золотое правило: Код должен быть воспроизводим
Главная проблема CI/CD — фраза *"У меня на локалке всё работает"*. Чтобы этого избежать, окружение в CI должно быть идентично твоему (или максимально близко).
*   **Docker — твой лучший друг.** Описывай среду в `Dockerfile`. Запуск тестов внутри контейнера гарантирует, что версия Python и системные зависимости (`libpq-dev` и т.д.) будут одинаковыми везде.
*   **Управление зависимостями.** Используй `requirements.txt`, `poetry.lock` или `Pipfile.lock`. Никаких `pip install pytest` без фиксации версий.

### 2. Жизненный цикл пайплайна (Pipeline Stages)
Типовой процесс запуска тестов в CI выглядит так:
1.  **Checkout:** Клонирование репозитория.
2.  **Setup:** Установка Python, создание venv, установка зависимо/стейджа.
3.  **Linting:** Проверка стиля кода (`flake8`, `black`, `isort`). Если код «грязный», тесты даже не должны начинаться.
4.  **Test Execution:** Запуск `pytest`.
5.  **Post-run (Reporting):** Сбор артефактов (отчетов) и отправка уведомлений.

### 3. Выходные коды (Exit Codes) — это критично!
CI-система понимает, упал пайплайн или нет, только по **exit code** команды `pytest`.
*   `0` — Все тесты прошли успешно. Пайплайн идет дальше.
*   `Non-zero` (1, 2, etc.) — Тесты провалились или произошла ошибка. Пайплайн останавливается.
*   **Нюанс:** Если ты используешь `pytest-xdist` для параллельного запуска, убедись, что он корректно возвращает код ошибки при падении одного из воркеров.

### 4. Артефакты: Как понять, что упало?
В CI у тебя нет доступа к терминалу так же легко, как локально. Тебе нужны **Artifacts**.
*   **HTML Reports:** Используй `pytest-html`. Настрой пайплайн так, чтобы он сохранял `.html` файл после каждого запуска. Его можно скачать прямо из интерфейса GitHub Actions/GitLab CI.
*   **Coverage Reports:** Сохраняй `coverage.xml`. Это позволит строить графики покрытия кода в течение времени (например, в Codecov).

### 5. Продвинутые фишки (Senior Level)
*   **Caching:** Чтобы не скачивать все библиотеки заново при каждом коммите, настрой кэширование папки `.cache/pip` или `venv`. Это экономит минуты и деньги (CI-раннеры стоят денег).
*   **Flaky Tests (Мигающие тесты):** Тесты, которые то проходят, то падают без изменения кода. В CI это яд. Используй `pytest-rerunfailures`, чтобы автоматически перезапустить упавший тест (но не злоупотребляй — это лишь маскировка проблемы).
*   **Secrets Management:** Никогда не клади пароли от БД или API-ключи в репозиторий! Используй **Environment Variables** из настроек CI/CD (GitHub Secrets, GitLab CI Variables). В PyTest доставай их через `os.getenv()`.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему тесты проходят локально, но падают в CI?**
**О:** Самые частые причины: 1) Разные версии библиотек (забыл зафиксировать версию); 2) Отсутствие системных зависимостей в контейнере; 3) Тесты зависят от внешних ресурсов (БД, API), которые недоступны из облака CI.

**В: Как ускорить выполнение тестов в CI?**
**О:** 1) Используй `pytest-xdist` для параллельного запуска на многоядерных раннерах; 2) Разделяй тесты на группы (Smoke, Regression) и запускай только Smoke на каждый PR; 3) Настрой кэширование зависимостей.

**В: Что делать с тестами, которые требуют тяжелую БД?**
**О:** Используй **Service Containers** (в GitHub Actions или GitLab CI). Это позволяет поднять полноценную базу данных (PostgreSQL, Redis) в отдельном контейнере рядом с твоим кодом прямо во время выполнения пайплайна.

**В: Можно ли запускать тесты только для измененных файлов?**
**О:** Да, есть инструменты вроде `pytest-changed`, но это сложно в настройке. Проще использовать стратегию "Smoke tests" — запускать критически важный набор тестов на каждый коммит, а полный регресс — раз в сутки.
