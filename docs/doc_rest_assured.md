# 🧠 Тема 1: Что такое REST Assured?

### 📌 Суть в двух словах
**REST Assured** — это Java-библиотека для автоматизации тестирования RESTful API. Если совсем просто: это «умный» HTTP-клиент, который умеет не только отправлять запросы (как Postman или браузер), но и сразу же проверять ответы на соответствие твоим ожиданиям прямо внутри кода.

### 🛠 Основная концепция: BDD Style
Главная «фишка» библиотеки — использование синтаксиса **BDD (Behavior Driven Development)**. Это делает тесты читаемыми даже для тех, кто не является программистом. Весь запрос строится по паттерну **Given — When — Then**:

1.  **`given()`** (Предпосылки): Здесь мы готовим «входные данные». Заголовки (headers), параметры (params), тело запроса (body), куки (cookies) или авторизация. *Что мы отправляем?*
2.  **`when()`** (Действие): Здесь мы совершаем сам HTTP-вызов. Указываем метод (GET, POST и т.д.) и путь (endpoint). *Что мы делаем?*
3.  **`then()`** (Проверка): Здесь мы проверяем результат. Статус-код, наличие поля в JSON, тип данных, заголовки ответа. *Что мы ожидаем получить?*

### 🚀 Ключевые возможности
*   **Поддержка всех HTTP методов:** GET, POST, PUT, DELETE, PATCH, HEAD, OPTIONS.
*   **Мощная валидация:** Встроенные инструменты для проверки JSON и XML (JsonPath, XmlPath).
le*   **Работа с данными:** Легкая сериализация (превращение Java-объекта в JSON) и десериализация (JSON $\to$ Java-объект/POJO).
*   **Логирование:** Возможность одной командой вывести в консоль весь запрос и ответ для отладки.
*   **Цепочки запросов (Chaining):** Удобное извлечение данных из одного ответа, чтобы использовать их в следующем запросе.

### ⚠️ Нюансы от Senior-а (На что обратить внимание)
1.  **Это не инструмент для нагрузочного тестирования:** REST Assured создан для **функционального** тестирования. Он слишком «тяжелый» для того, чтобы имитировать тысячи пользователей одновременно. Для этого есть JMeter или Gatling.
2.  **Зависимость от парсеров:** Сам REST Assured умеет отправлять запросы, но чтобы он «понимал» JSON внутри тела, тебе **обязательно** нужно добавить в проект библиотеку-десериализатор (обычно это **Jackson** или **Gson**). Без них магии с POJO не случится.
3.  **Под капотом:** Он базируется на стандартных Java-библиотеках для HTTP, поэтому он очень стабилен, но требует правильной настройки Maven/Gradle зависимостей.

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Чем REST Assured лучше, чем обычный Java HttpClient или OkHttp?**
**О:** HttpClient — это низкоуровневый инструмент для отправки запросов. Чтобы проверить статус-код или распарсить JSON через него, тебе придется писать много шаблонного кода (boilerplate). REST Assured же предоставляет высокоуровневый DSL (Domain Specific Language), где проверки встроены в сам синтаксис. Он экономит время и делает тесты читаемыми.

**В: Можно ли использовать REST Assured для тестирования SOAP?**
**О:** Да, библиотека поддерживает XML, поэтому ты можешь отправлять SOAP-запросы и проверять их содержимое. Однако специализированные инструменты могут быть удобнее, так как SOAP — это более строгий протокол.

**В: Что произойдет, если в `then()` не указать проверку?**
**О:** Тест технически пройдет (если сам запрос прошел успешно), но проверка результата не будет выполнена. Это плохая практика, так как тест теряет смысл — мы не узнаем, верны ли данные внутри ответа.

# 🛠 Тема: Настройка окружения (Environment Setup)

Прежде чем писать первый `given().when().then()`, нужно подготовить «лабораторию». Если фундамент кривой (неправильные версии Java или конфликтующие библиотеки), ты будешь тратить 80% времени на борьбу с ошибками в консоли, а не на написание тестов.

### 1. Стек технологий (Core Stack)
Для работы нам необходимы три кита:
1.  **JDK (Java Development Kit):** Сердце проекта. Рекомендую использовать **Java 11 или 17 (LTS версии)**. Забудь про Java 8, если не хочешь проблем с современными библиотеками.
2.  **Build Tool (Maven или Gradle):** Твой менеджер зависимостей и сборщик. В индустрии стандарт — **Maven**. Он берет на себя скачивание всех нужных `.jar` файлов и управление их версиями.
3.  **IDE:** IntelliJ IDEA — это база. Без неё автоматизация превращается в пытку.

### 2. Магический файл: `pom.xml` (для Maven)
Всё управление проектом происходит здесь. Чтобы REST Assured «ожил», тебе нужен набор зависимостей. Я подготовил эталонный конфиг.

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0" ...>
    <properties>
        <!-- Управляем версиями в одном месте — это признак Senior-подхода -->
        <maven.compiler.source>17</maven.compiler.source>
        <maven.compiler.target>17</maven.compiler.target>
        <rest-assured.version>5.4.0</rest-assured.version>
        <jackson.version>2.15.2</jackson.version>
        <testng.version>7.8.0</testng.version>
    </properties>

    <dependencies>
        <!-- 1. Сам REST Assured -->
        <dependency>
            <groupId>io.rest-assured</groupId>
            <artifactId>rest-app</artifactId>
            <version>${rest-assured.version}</version>
            <scope>test</scope>
        </dependency>

        <!-- 2. Jackson Databind: Без него ты не сможешь превращать JSON в Java-объекты (POJO) -->
        <dependency>
            <groupId>com.fasterxml.jackson.core</groupId>
            <artifactId>jackson-databind</artifactId>
            <version>${jackson.version}</version>
            <scope>test</scope>
        </dependency>

        <!-- 3. Тестовый фреймворк (TestNG или JUnit 5) -->
        <dependency>
            <groupId>org.testng</groupId>
            <artifactId>testng</artifactId>
            <version>${testng.version}</version>
            <scope>test</scope>
        </dependency>

        <!-- 4. Allure: Чтобы отчеты были красивыми, а не в консоли -->
        <dependency>
            <groupId>io.qameta.allure</groupId>
            <artifactId>allure-rest-assured</artifactId>
            <version>2.24.0</version>
            <scope>test</scope>
        </dependency>
    </dependencies>
</project>
```

### 3. Нюансы от Senior'а (На что все забивают)

*   **Scope `test`:** Обрати внимание на тег `<scope>test</scope>`. Это значит, что эти библиотеки попадут в проект только во время запуска тестов и не будут «раздувать» финальный артефакт (если ты вдруг решишь упаковать тесты в JAR).
*   **Jackson vs Gson:** Можно использовать и то, и другое. Но **Jackson** — это стандарт де-факто. Он мощнее, быстрее и лучше интегрирован с экосистемой Spring/REST Assured. Если видишь в проекте Gson — не пугайся, но старайся придерживаться Jackson.
*   **Конфликты версий (Dependency Hell):** Всегда используй `<properties>` для версий. Если завтра тебе нужно будет обновить Jackson, ты сделаешь это одной строчкой, а не по всему файлу.
*   **Lombok:** Очень советую добавить библиотеку **Lombok**. Она избавит тебя от написания сотен строк кода (геттеры, сеттеры, конструкторы) для твоих POJO-классов.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Почему мы используем Maven/Gradle, а не просто скачиваем JAR-файлы вручную?**
**О:** Управление транзитивными зависимостями. Если ты скачаешь REST Assured, ему самому нужны еще 10 библиотек. Maven сам поймет это и скачает их. Вручную ты замучаешься выстраивать эту цепочку.

**В: Что такое "Scope" в Maven?**
**О:** Это область видимости библиотеки. `test` — библиотека нужна только для тестов; `compile` — библиотека нужна и при написании кода, и при сборке готового продукта.

**В: Можно ли использовать JUnit 5 вместо TestNG?**
**О:** Конечно. REST Assured абсолютно всё равно, какой движок запуска тестов ты используешь. Но в связке с TestNG часто удобнее работать с параметризованными тестами и сложными зависимостями между методами.

**В: Зачем нам Jackson, если я могу передавать JSON просто как String?**
**О:** Передавать строку — это путь к "спагетти-коду". Как только тебе нужно будет проверить поле внутри глубоко вложенного объекта, работать со строкой станет невозможно. С Jackson ты превращаешь JSON в объект и проверяешь его одной командой `object.getName()`.

# 🧠 Тема: Архитектура запроса (The BDD Structure)

В REST Assured архитектура построена на основе подхода **BDD (Behavior Driven Development)**. Вместо того чтобы просто вызывать методы, мы пишем сценарий, который читается как человеческое предложение. 

В основе лежит концепция трех блоков: **Given — When — Then**.

### 1. `given()` — Предусловия (Preconditions)
Это всё, что нужно «подготовить» перед тем, как отправить запрос. Представь, что ты готовишь почту к отправке: тебе нужен адрес, марка, конверт и содержимое.

**Что сюда входит:**
*   **Headers:** Заголовки (например, `Content-Type: application/json`).
*   **Params:** Параметры запроса (`queryParam` для URL или `pathParam` для пути).
*   **Body:** Тело запроса (JSON, XML, файл или объект POJO).
*   **Auth:** Данные для авторизации (Basic, OAuth2, Bearer Token).
*   **Cookies:** Куки для сессии.
*   **Config/Spec:** Настройки логирования или использование `RequestSpecification` (шаблонов запроса).

### 2. `when()` — Действие (Action)
Это кульминация. Момент, когда запрос фактически «выстреливает» в сторону сервера. Здесь мы указываем HTTP-метод и эндпокеинт.

**Что сюда входит:**
*   **HTTP Methods:** `.get()`, `.post()`, `.put()`, `.delete()`, `.patch()`.
*   **Endpoint:** Путь к ресурсу (например, `"/users/1"`).

### 3. `then()` — Проверка (Assertions)
Это этап валидации. Мы проверяем, что сервер ответил именно так, как мы ожидали. Если проверка не проходит, тест падает здесь.

**Что сюда входит:**
*   **Status Code:** Проверка кода ответа (`statusCode(200)`).
*   **Response Body:** Проверка полей через `JsonPath` или `XmlPath`.
*   **Headers/Cookies:** Проверка заголовков ответа.
*   **Logic:** Проверка типов данных, наличия элементов в массивах и т.д.

---

### 💡 Нюансы от Senior-а (На что важно обратить внимание)

1.  **`extract()` — «Тайный четвертый элемент»:** Иногда нам не нужно просто проверить ответ, а нужно вытащить из него данные (например, `id` созданного пользователя), чтобы использовать их в следующем тесте. Для этого используется метод `.extract()`. Он технически стоит после `when()`, но часто идет в связке с `then()`.
2.  **Разделяй и властвуй:** Не пытайся запихнуть всю логику подготовки данных прямо в `given()`. Если у тебя много параметров, выноси их в переменные или используй `RequestSpecBuilder`. Чистый код — это когда `given()` не занимает 50 строк.
3.  **Fluent Interface:** REST Assured использует "текучий интерфейс". Это значит, что методы возвращают объект того же типа, позволяя строить цепочки (chaining). Но не злоупотребляй этим: слишком длинная цепочка превращается в "спагетти", которое трудно дебажить.

---

### 💻 Пример кода

Представим задачу: Создать пользователя и проверить, что он создался с правильным именем.

```java
given()
    .baseUri("https://api.example.com")
    .contentType(ContentType.JSON) // Header
    .body("{\"name\": \"John\", \"job\": \"QA\"}") // Body
    .log().all() // Нюанс: логируем запрос для отладки
.when()
    .post("/api/users") // Action
.then()
    .statusCode(201) // Assertion
    .body("name", equalTo("John")) // Assertion
    .body("job", notNullValue()) // Assertion
    .log().ifValidationFails() // Нюанс: логируем только если тест упал
.extract()
    .path("id"); // Извлекаем ID для следующих тестов
```

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Можно ли использовать `when()` без `given()`?**
**О:** Технически — да, если тебе не нужны никакие предусловия (например, пустой GET запрос). Но в рамках BDD-структуры это считается плохим тоном. Всегда лучше явно показать, что ты "подготовил" запрос.

**В: Где заканчивается `when()` и начинается `then()`?**
**О:** Граница проходит ровно в момент вызова HTTP-метода (`get`, `post` и т.д.). Метод — это действие, которое отправляет запрос. Всё, что после него — это уже работа с полученным ответом.

**В: Что делать, если мне нужно проверить статус код, но при этом извлечь данные?**
**О:** Ты можешь использовать `.extract().response()`. Это вернет тебе полный объект `Response`, и ты сможешь делать проверки (`assertThat`) отдельно, либо продолжить цепочку через `.then()`, а в конце вызвать `.extract()`.

**В: В чем разница между `queryParam` и `pathParam` внутри `given()`?**
**О:** `pathParam` заменяет переменную прямо в URL (например, `/users/{id}` $\rightarrow$ `/users/1`), а `queryParam` добавляет параметры после знака вопроса (`/users?role=admin`). Это разные части структуры HTTP-запроса.

# 🧠 Шпаргалка: Базовые HTTP методы

В мире REST API каждый метод (или «глагол») сообщает серверу, какое действие нужно совершить над **ресурсом** (данными). Если представить API как работу с файлами, то методы — это команды «прочитать», «создать», «перезаписать».

### 🛠 Основные методы

| Метод | Действие | Тело запроса (Body) | Идемпотентность* | Безопасность** |
| :--- | :--- | :---: | :---: | :---: |
| **GET** | Получение данных | ❌ Нет | ✅ Да | ✅ Да |
| **POST** | Создание нового ресурса | ✅ Да | ❌ Нет | ❌ Нет |
| **PUT** | Полное обновление (замена) | ✅ Да | ✅ Да | ❌ Нет |
| **PATCH** | Частичное обновление | ✅ Да | ❌ Нет/Да*** | ❌ Нет |
| **DELETE** | Удаление ресурса | ❌ Редко | ✅ Да | ❌ Нет |

---

### 🔍 Детальный разбор

#### 1. GET (Read)
Используется только для чтения. Ты запрашиваешь состояние ресурса.
*   **Нюанс:** Все параметры должны быть в URL (`queryParam`). Тело запроса в GET — это плохая практика, многие серверы его просто проигнорируют или выдадут ошибку.
*   **В REST Assured:** `given().get("/users/1").then()...`

#### 2. POST (Create)
Используется для создания нового объекта или выполнения действия (например, «запустить процесс»).
*   **Нюанс:** **Не идемпотентен**. Если ты нажмешь кнопку «Оплатить» (POST) дважды из-за лага интернета, и сервер не имеет защиты от дублей, с тебя спишут деньги два раза. Каждый POST создает новый экземпляр ресурса.
*   **В REST Assured:** `given().body(newUser).post("/users").then()...`

#### 3. PUT (Update/Replace)
Используется для **полной замены** существующего ресурса. Ты отправляешь объект целиком.
*   **Нюанс:** Если ты отправишь в PUT только одно поле (например, `name`), а остальные поля объекта не пришлешь — сервер может затереть остальные поля значениями по умолчанию (`null` или пустые строки). Это **идемпотентный** метод: сколько бы раз ты ни отправлял один и тот же объект, результат на сервере будет одинаковым.
*   **В REST Assured:** `given().body(updatedUser).put("/users/1").then()...`

#### 4. PATCH (Partial Update)
Используется для **частичного** изменения. Ты отправляешь только те поля, которые хочешь изменить.
*   **Нюанс:** В отличие от PUT, ты не переписываешь весь объект. Если нужно сменить только фамилию — шлешь только фамилию. 
*   **В REST Assured:** `given().body(mapOfChanges).patch("/users/1").then()...`

#### 5. DELETE (Delete)
Удаляет ресурс по указанному ID.
*   **Нюанс:** Метод **идемпотентен**. Если ты удалишь пользователя с ID 1, он исчезнет (результат: `204 No Content` или `200 OK`). Если ты попробуешь удалить его еще раз, результат будет таким же — пользователя всё еще нет (хотя статус может измениться на `404 Not Found`, состояние системы «удалено» не изменилось).
*   **В REST Assured:** `given().delete("/users/1").then()...`

---

### 💡 Важные термины для Senior-уровня

*   **\*Идемпотентность (Idempotency):** Свойство метода, при котором повторный запрос с теми же параметрами дает тот же результат на сервере, что и первый запрос. *Важно: это касается состояния сервера, а не статус-кода ответа.*
*   **\*\*Безопасность (Safety):** Метод считается безопасным, если он **не изменяет** состояние ресурса на сервере (только чтение). GET — безопасный, POST — небезопасный.
*   **\*\*\*Нюанс PATCH:** В строгом смысле PATCH не обязан быть идемпотентным (например, если операция — «добавить +1 к счетчику»), но в 90% современных API он используется как идемпотентный.

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем главная разница между PUT и PATCH?**
**О:** PUT — это «замена». Ты присылаешь объект целиком, заменяя старую версию новой. PATCH — это «патч» (заплатка). Ты присылаешь только измененную часть.

**В: Может ли GET-запрос иметь тело (Body)?**
**О:** Технически стандарт HTTP это не запрещает жестко, но на практике — **нет**. Большинство библиотек, прокси-серверов (Nginx) и кэширующих серверов либо отбросят тело, либо выдадут ошибку. Тело в GET — признак плохого дизайна API.

**В: Почему DELETE считается идемпотентным, если второй раз прилетает 404?**
**О:** Потому что состояние ресурса на сервере не изменилось. После первого запроса ресурса нет, после второго его тоже нет. Состояние системы осталась неизменной (ресурс отсутствует).

**В: Что такое POST-запрос, если он не создает ресурс, а просто выполняет действие?**
**О:** В REST всё, что не вписывается в CRUD (Create, Read, Update, Delete) через стандартные методы, часто реализуется через POST. Например, метод `/login` или `/process-payment`. Это «команда», а не манипуляция с сущностью.

# 📌 Шпаргалка: Base Configuration в REST Assured

**Суть темы:** Чтобы не дублировать `https://api.example.com/v1` в каждом тесте, мы выносим общие настройки в глобальную конфигурацию. Это делает тесты чистыми (DRY — Don't Repeat Yourself) и позволяет менять URL всего в одном месте при переключении между Dev/QA/Prod окружениями.

---

### 1. Глобальная настройка (Static Configuration)
Самый простой способ. Мы обращаемся к статическим полям класса `RestAssured`. Эти настройки будут применяться ко **всем** последующим запросам в рамках запуска тестов.

```java
import io.restassured.RestAssured;

// Обычно это делается в методе @BeforeSuite или @BeforeAll
RestAssured.baseURI = "https://api.myapp.com";
RestAssured.basePath = "/api/v1";
RestAssured.port = 8080; // Если API работает на нестандартном порту
```

*   **Плюс:** Очень быстро и просто.
*   **Минус:** Плохо подходит для больших проектов, где нужно тестировать несколько разных сервисов одновременно (все запросы будут "стучаться" по одному адресу).

---

### 2. Продвинутый уровень: RequestSpecification (The Pro Way) 🚀
Как Senior, я настоятельно рекомендую использовать `RequestSpecification`. Вмеме того чтобы менять глобальное состояние, мы создаем «шаблон» запроса и подставляем его в нужные тесты. Это позволяет изолировать настройки разных сервисов.

```java
import io.restassured.builder.RequestSpecBuilder;
import io.restassured.specification.RequestSpecification;
import io.restassured.http.ContentType;

public class SpecFactory {
    public static RequestSpecification getCommonSpec() {
        return new RequestSpecBuilder()
            .setBaseUri("https://api.myapp.com")
            .setBasePath("/api/v1")
            .setContentType(ContentType.JSON)
            .addHeader("Authorization", "Bearer my-token")
            .build();
    }
}

// Использование в тесте:
given()
    .spec(SpecFactory.getCommonSpec()) // Подставляем наш шаблон
    .when()
    .get("/users")
    .then()
    .statusCode(2pect(200));
```

*   **Плюс:** Масштабируемость. Можно создать `userSpec`, `orderSpec`, `authSpec` и использовать их выборочно.
*   **Нюанс:** Это стандарт индустрии для серьезных фреймворков.

---

### 💡 Важные нюансы (Senior Tips)

1.  **Приоритет перекрытия (Overriding):** Если ты установил `baseURI` глобально, но в конкретном тесте написал `.baseUri("https://other-api.com")` внутри блока `given()`, то **локальное значение победит**. Всегда помни: локальный конфиг сильнее глобального.
2.  **Никакого Hardcode!** Никогда не пиши URL прямо в коде. Используй файлы конфигурации (`.properties`, `.yaml`) или переменные окружения. Тест должен уметь запускаться на разных стендах без изменения кода.
3.  **Разделяй BaseURI и PathParam:** `baseURI` — это корень (домен), а `pathParam` — это динамическая часть пути (например, `/users/{id}`). Не смешивай их в одну кучу.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что будет, если я забуду указать `basePath`, но укажу `baseURI`?**
**О:** REST Assured просто отправит запрос на корень домена. Если твой эндпоинт `/users`, а ты не указал путь, запрос уйдет на `https://api.myapp.com/users`. Если API ждет префикс `/v1`, тест упадет с 404.

**В: Можно ли в `RequestSpecification` сразу добавить логирование?**
**О:** Да! Это отличная практика. Добавь `.addFilter(new ResponseLoggingFilter())` прямо в `RequestSpecBuilder`. Тогда все запросы, использующие этот спек, будут автоматически логироваться.

**В: Где лучше всего инициализировать глобальный `baseURI`?**
**О:** В методе с аннотацией `@BeforeSuite` (в TestNG) или `@BeforeAll` (в JUnit 5). Это гарантирует, что настройки применятся до начала выполнения первого теста.

# 🧠 Шпаргалка: Параметры запроса (Query Parameters)

### 📌 Что это такое?
**Query Parameters** — это набор пар «ключ-значение», которые добавляются в конец URL после знака вопроса `?`. Они не меняют сам ресурс (адрес), но управляют тем, *как* сервер должен вернуть данные. 

Используются для:
*   **Фильтрации** (`?type=admin`)
*   **Сортировки** (`?sort=desc`)
*   **Пагинации** (`?page=2&limit=50`)
*   **Поиска** (`?q=rest+assured`)

---

### 🛠 Инструментарий в REST Assured

В REST Assured есть три основных способа работы с ними:

#### 1. Одиночный параметр: `.queryParam()`
Самый простой способ, когда нужно добавить один конкретный ключ.
```java
given()
    .queryParam("role", "admin")
.when()
    .get("/users")
// Итог: /users?role=admin
```

#### 2. Несколько значений для одного ключа: `.queryParams()`
Иногда API требует передать массив значений (например, фильтр по нескольким категориям). REST Assured позволяет перечислить их через запятую.
```java
given()
    .queryParams("category", "books", "electronics", "toys")
.when()
    .get("/products")
// Итог: /products?category=books&category=electronics&category=toys
```

#### 3. Массовое добавление через Map: `.queryParams(Map<String, ?> params)`
Если параметров очень много (например, из конфига или теста), лучше не плодить строки, а использовать `Map`. Это делает код чистым и профессиональным.
```java
Map<String, String> filters = new HashMap<>();
filters.put("status", "active");
filters/put("limit", "10");

given()
    .queryParams(filters)
.when()
    .get("/orders")
// Итог: /orders?status=active&limit=10
```

---

### ⚠️ Нюансы и «подводные камни» (Senior Level)

#### 1. Query Param vs Path Param — Главная ошибка
Это база, на которой валятся все новички.
*   **Path Param** — это часть пути, он определяет **сущность**. `/users/123` (мы обращаемся к конкретному пользователю). Используется `.pathParam()`.
*   **Query Param** — это модификатор запроса. `/users?id=123` (мы ищем пользователя среди всех). Используется `.queryParam()`.

#### 2. URL Encoding
Если в значении параметра есть пробелы или спецсимволы (например, `?name=John Doe`), REST Assured **автоматически** сделает URL-encoding (`?name=John%20Doe`). Тебе не нужно делать это вручную.

#### 3. Порядок имеет значение?
Для HTTP-протокола порядок параметров в Query String обычно не важен. Но для читаемости тестов и удобства отладки (в логах) старайся придерживаться логики: сначала важные фильтры, потом технические (limit, offset).

#### 4. Передача пустых значений
Если ты передашь `.queryParam("key", "")`, в URL будет `?key=`. Убедись, что твой бэкенд умеет обрабатывать пустые строки, иначе получишь `400 Bad Request`.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что использовать, если параметров 20 штук?**
**О:** Только `Map`. Писать 20 строчек `.queryParam()` — это плохой тон и «грязный» код. Собери их в Map или даже вынеси в отдельный JSON-файл/Builder.

**В: Чем `queryParam` отличается от `formParam`?**
**О:** Это принципиальная разница в месте хранения данных. 
*   `queryParam` — данные в **URL** (видимы всем, ограничены длиной строки).
*   `formParam` — данные в **теле запроса** (Body), обычно используются в `POST` запросах с типом `application/x-www-form-urlencoded`.

**В: Можно ли динамически менять параметры на основе ответа предыдущего запроса?**
**О:** Да, это стандартная практика. Ты извлекаешь значение через `.extract().path("...")` и подставляешь его в следующий запрос как аргумент для `.queryParam()`.

# 📑 Шпаргалка: Query Parameters (`queryParam`)

### 1. Что это такое?
**Query Parameters** — это параметры, которые передаются в URL после знака вопроса `?`. Они используются для фильтрации, сортировки или пагинации данных.
*Пример URL:* `https://api.example.com/users?role=admin&status=active`
Здесь `role` и `status` — это query-параметры.

### 2. Базовый синтаксис
В REST Assured мы используем метод `.queryParam(key, value)`.

#### Одиночный параметр:
```java
given()
    .queryParam("id", "123")
.when()
    .get("/users")
.then()
    .statusCode(200);
// Итоговый URL: /users?id=123
```

#### Несколько параметров (Chaining):
Самый читаемый способ в стиле BDD — просто цепочка методов.
```java
given()
    .queryParam("role", "admin")
    .queryParam("status", "active")
.when()
    .get("/users")
.then()
    .statusCode(200);
// Итоговый URL: /users?role=admin&status=active
```

### 3. Продвинутое использование (Senior Level)

#### Работа с коллекциями (Массивы в параметрах)
Иногда API требует передать несколько значений для одного ключа: `?id=1&id=2&id=3`. В REST Assured это делается очень элегантно:
```java
given()
    .queryParam("id", 1, 2, 3) // Передаем через запятую
.when()
    .get("/users")
// Итоговый URL: /users?id=1&id=2&id=3
```

#### Использование Map (Для чистого кода)
Если параметров очень много (например, для сложной фильтрации), цепочка `.queryParam()` превращается в «лапшу». Чтобы не замусоривать тест, выноси параметры в `Map`.

```java
Map<String, String> filters = new HashMap<>();
filters.put("role", "admin");
filters.put("status", "active");
filters.put("sort", "desc");

given()
    .queryParams(filters) // Используем queryParams (во множественном числе)
.when()
    .get("/users")
// Итоговый URL: /users?role=admin&status=active&sort=desc
```

---

### ⚠️ Важные нюансы и «подводные камни»

1.  **`queryParam` vs `pathParam` — Не путай!**
    *   `pathParam` меняет **структуру** пути: `/users/{id}` $\to$ `/users/123`.
    *   `queryParam` добавляет **хвост** к пути: `/users` $\to$ `/users?id=123`.
    *   *Ошибка новичка:* Пытаться передать ID пользователя через `queryParam`, когда API ожидает его в пути.

2.  **URL Encoding (Кодирование символов)**
    REST Assured автоматически кодирует спецсимволы (пробелы, `@`, `&` и т.д.). Если тебе нужно передать пробел, ты пишешь `"John Doe"`, а библиотека сама превратит это в `John%20Doe`. Тебе не нужно делать это вручную.

3.  **Порядок параметров**
    Для большинства современных API порядок query-параметров в URL не имеет значения (`?a=1&b=2` — это то же самое, что `?b=2&a=1`). Но при написании тестов на **сравнение строк (String Comparison)** ломай голову именно об это. Всегда старайся проверять логику ответа, а не строковое совпадение URL.

---

### ❓ FAQ (Частые вопросы)

**В: Что будет, если я передам пустой `queryParam`?**
**О:** Если значение `null`, REST Assured может либо пропустить его, либо выбросить ошибку в зависимости от версии и конфигурации. Лучше всегда явно передавать пустую строку `""`, если логика API это подразумевает.

**В: Можно ли использовать `queryParam` для передачи чувствительных данных (паролей)?**
**О:** **Категорически нет.** Query-параметры сохраняются в логах сервера, в истории браузера и в системных логах прокси-серверов. Все секреты (токены, пароли) должны передаваться только в `Header` или в `Body`.

**В: В чем разница между `.queryParam()` и `.queryParams()`?**
**О:** 
*   `.queryParam(key, value)` — для одного параметра.
*   `.queryParams(map)` — для передачи сразу всей коллекции (Map).

**В: Как проверить, что параметр действительно ушел в запросе?**
**О:** Используй `.log().all()` в блоке `given()`. Это «золотой стандарт» при отладке.
```java
given()
    .queryParam("test", "true")
    .log().all() // Ты увидишь сформированный URL в консоли
...
```

# 📌 Тема: Path Parameters (`pathParam`)

### 💡 Что это такое?
**Path Parameter** — это переменная часть самого пути (URL). Она не является «дополнением» к запросу (как query-параметры), она **является частью ресурса**, к которому ты обращаешься.

Представь адрес: `https://api.shop.com/users/123`.
Здесь `/users/` — это статический путь, а `123` — это **path parameter**. Мы запрашиваем конкретный ресурс (пользователя с ID 123).

В REST Assured мы не пишем ID прямо в строку, а используем «заполнитель» (placeholder) в фигурных скобках: `{id}`.

### 🛠 Как это выглядит в коде
Основной принцип: **Сначала создай шаблон в URL, потом заполни его через `.pathParam()`**.

```java
import io.restassured.RestAssured;
import static io.restassured.RestAssured.*;
import static org.hamcrest.Matchers.*;

public class PathParamExample {
    public void testGetUserInfo() {
        
        given()
            // 1. Определяем заполнитель и значение
            .pathParam("userId", 123) 
            .pathParam("type", "admin")
        .when()
            // 2. Используем заполнители в самом URL через фигурные скобки
            .get("https://api.example.com/users/{userId}/{type}")
        .then()
            .statusCode(200)
            .body("id", equalTo(123));
    }
}
```

### ⚠️ Нюансы и "подводные камни" (Senior Tips)

1.  **Главная ошибка — отсутствие шаблона:** Если ты напишешь `.pathParam("id", 123)`, но в методе `.get()` укажешь просто `"/users/123"` (без `{id}`), то REST Assured **не найдет**, куда подставить это значение. Параметр просто проигнорируется, и магии не случится.
2.  **Разница с QueryParam:** 
    *   `pathParam` — меняет саму суть ресурса (какой именно юзер?).
    *   `queryParam` — фильтрует или сортирует ресурс (`/users?role=admin`). 
    *   *Запомни:* Если ты не можешь убрать этот параметр из URL без потери смысла запроса — это `pathParam`.
3.  **Цепочки (Chaining):** `pathParam` идеально подходит для передачи данных из одного теста в другой. Получил `id` из POST-запроса $\rightarrow$ подставил его в `pathParam` для GET-запроса.
4.  **Типизация:** В `.pathParam("key", value)` значение `value` может быть любым (String, Integer, Long). REST Assured сам приведет его к строке для URL.

---

### ❓ FAQ (Частые вопросы на интервью)

**В: Что будет, если я передам два параметра с одинаковым именем в `.pathParam()`?**
**О:** Последний вызванный метод перетрет предыдущий. В URL подставится последнее значение.

**В: Можно ли передать Map вместо кучи вызовов `.pathParam()`?**
**О:** Да, это отличный способ, если параметров много. Ты можешь создать `Map<String, Object> params = new HashMap<>();` и передать её в запрос (хотя чаще для этого используют `specifications`). Но технически ты можешь использовать циклы или коллекции для динамического формирования запроса.

**В: Как отличить Path Parameter от Query Parameter по URL?**
**О:** Смотри на наличие знака вопроса. 
*   `.../users/123` — это путь (Path).
*   `.../users?id=123` — это параметры запроса (Query).

**В: Обязательно ли использовать фигурные скобки `{}` в методе `.get()`?**
**О:** Да. Без них REST Assured не поймет, что строку в URL нужно искать и заменять на значение из `pathParam`.

# 📑 Шпаргалка: Параметры запроса — `formParam`

### 💡 Суть темы
`formParam` используется для передачи данных в **теле (body)** HTTP-запроса. В отличие от `queryParam`, которые «торчат» в URL, `formParam` прячет данные внутри запроса. Это стандартный способ имитации отправки HTML-форм с веб-сайтов.

Когда ты используешь `.formParam()`, REST Assured автоматически выставляет заголовок `Content-Type: application/x-www-form-urlencoded`.

---

### 🛠 Основные сценарии использования

#### 1. Классическая форма (URL-encoded)
Это самый частый случай. Данные передаются в виде пар `ключ=значение`, разделенных символом `&`.
**Пример:** Логин на сайте.

```java
given()
    .contentType("application/x-www-form-urlencoded") // Явно указываем тип контента
    .formParam("username", "admin")
    .formParam("password", "secret123")
    .formParam("grant_type", "password")
.when()
    .post("/oauth/token")
.then()
    .statusCode(200);
```

#### 2. Отличие от `queryParam` (Важно!)
*   **`queryParam`**: Добавляет параметры в конец URL (`/api/users?id=1`). Видно в логах сервера, в истории браузера, небезопасно для паролей.
*   **`formParam`**: Помещает данные в Body. Это "скрытый" способ передачи.

---

### ⚠️ Нюансы и «Подводные камни» (Senior Level)

1.  **Confusion с Multipart:** 
    Если тебе нужно отправить **файл** (картинку, документ), `formParam` **не подойдет**. Для этого существует метод `.multiPart()`. 
    *   `formParam` $\rightarrow$ `application/x-www-form-urlencoded` (только текст).
    *   `multiPart` $\rightarrow$ `multipart/form-data` (текст + бинарные данные/файлы).

2.  **Автоматическая кодировка:** 
    REST Assured сам заботится об URL-encoding (превращает пробелы в `%20`, спецсимволы в их коды). Тебе не нужно вручную кодировать строку `user@email.com` $\rightarrow$ `user%40email.com`.

3.  **Заголовок Content-Type:** 
    Хотя REST Assured старается угадать тип контента, **всегда** явно прописывай `.contentType("application/x-www-form-urlencoded")`. Это признак хорошего тона и защиты от ошибок в сложных фреймворках.

4.  **Цепочка вызовов:** 
    Ты можешь передавать несколько параметров подряд, вызывая `.formParam()` многократно. Это чище, чем склеивать одну длинную строку.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли использовать `formParam` для передачи JSON?**
**О:** Нет. Для JSON используется метод `.body(object)`. `formParam` предназначен строго для формата `key=value` (URL-encoded). Если ты попытаешься засунуть JSON в `formParam`, сервер получит строку, а не объект.

**В: В чем разница между `formParam` и `multiPart`?**
**О:** Разница в `Content-Type`. `formParam` — это плоский список пар ключ-значение для текста. `multiPart` — это сложная структура, которая позволяет «упаковать» в один запрос и текст, и тяжелый файл (бинарные данные).

**В: Что произойдет, если я передам `queryParam` и `formParam` одновременно?**
**О:** Сервер получит запрос, где часть данных будет в URL, а часть — в теле. Это технически возможно, но крайне плохая практика, которая может запутать логику API.

# 🧠 Шпаргалка: Заголовки (Headers) и Cookies в REST Assured

### 1. HTTP Headers (Заголовки)
**Что это:** Это метаданные запроса или ответа. Представь, что запрос — это посылка. Тело запроса — это сам товар, а заголовки — это наклейки на коробке: «Хрупкое», «Адрес получателя», «Тип содержимого».

#### В части `Given` (Отправка):
Мы используем заголовки, чтобы сказать серверу, как обрабатывать наш запрос.
*   `.header(key, value)` — добавить один заголовок.
*   `.headers(Map<String, String>)` — добавить сразу пачку заголовков из карты.

**Самые важные заголовки:**
*   `Content-Type`: Говорит серверу, в каком формате мы прислали тело (обычно `application/json`).
*   `Accept`: Говорит серверу, какой формат ответа мы хотим получить.
*   `Authorization`: Передача токенов или логина/пароля.
*   `User-Agent`: Информация о том, кто делает запрос (браузер, скрипт и т.д.).

#### В части `Then` (Проверка):
Мы проверяем, что сервер вернул правильные метаданные.
*   `.header("key", "expectedValue")` — точное совпадение.
*   `.header(containsString("part"))` — проверка частичного совпадения (используя Hamcrest).

---

### 2. HTTP Cookies (Куки)
**Что это:** Маленькие кусочки данных, которые сервер просит «запомнить» клиенту. Это способ поддерживать состояние (state) в протоколе HTTP, который сам по себе «забывчив». Обычно используются для сессий и идентификации пользователя.

#### В части `Given` (Отправка):
Если нам нужно имитировать авторизованного пользователя, у которого уже есть сессия:
*   `.cookie(name, value)` — добавить одну куку.
*   `.cookies(Map<String, String>)` — добавить набор кук.

#### В части `Then` (Проверка и Извлечение):
*   **Проверка:** `.cookie("sessionID", "12345")` — проверяем, пришла ли нужная кука в ответе.
*   **Извлечение:** `.extract().cookie("name")` — вытаскиваем значение куки, чтобы использовать его в следующем запросе (самый частый сценарий).

---

### 💻 Практический пример (Code Snippet)

```java
import io.restassured.RestAssured;
import io.restassured.response.Response;
import static io.restassured.RestAssured.*;
import static org.hamcrest.Matchers.*;

public class HeadersAndCookiesTest {

    @Test
    public void complexRequestTest() {
        // 1. Настройка запроса (Given)
        String sessionCookie = "abc-123-xyz";
        
        Response response = given()
            .baseUri("https://api.example.com")
            // Заголовки
            .header("Content-Type", "application/json")
            .header("Custom-Header", "MyValue")
            .headers(java.util.Map.of("Accept", "application/xml", "User-Agent", "QA-Automation"))
            // Куки
            .cookie("sessionId", sessionCookie)
            .cookie("theme", "dark")
        .when()
            .get("/user/profile")
        .then()
            // 2. Проверка (Then)
            .statusCode(200)
            .header("Content-Type", containsString("json")) // Проверка частичного совпадения
            .header("Server", notNullValue())              // Проверка, что заголовок вообще есть
            .cookie("sessionID", sessionCookie)            // Проверяем, вернул ли сервер ту же куку
            .extract().response();

        // 3. Извлечение (Extraction)
        String serverName = response.getHeader("Server");
        String cookieValue = response.getCookie("sessionId");
    }
}
```

### ⚠️ Нюансы от Senior-а (На что смотреть)

1.  **Регистрозависимость:** По спецификации HTTP заголовки **нечувствительны к регистру** (`Content-Type` и `content-type` — это одно и то же). Но в коде Java/Rest Assured лучше придерживаться стандарта, чтобы не путать коллег.
2.  **Перезапись:** Если ты вызовешь `.header("A", "1")`, а потом сразу `.header("A", "2")` в рамках одного `given()`, то в запросе останется только `"A: 2"`. Последний вызванный метод побеждает.
3.  **Content-Type vs Accept:** Не путай их! `Content-Type` — это про то, что ты **отправляешь**. `Accept` — это про то, что ты **хочешь получить**. Ошибка в них — классика новичков.
4.  **Безопасность кук:** В реальных проектах часто приходят куки с флагами `HttpOnly` или `Secure`. REST Assured их прочитает без проблем, но помни, что через JS (в браузере) к ним доступа нет.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли проверить наличие заголовка, не зная его точного значения?**
О: Да, используй Hamcrest matchers. Например, `.header("Server", notNullValue())` или `.header("Cache-Control", containsString("no-cache"))`.

**В: Как передать много заголовков и не превратить код в кашу?**
О: Используй `Map<String, String>` или создай `RequestSpecification`, где все общие заголовки (Content-Type, Auth) уже настроены заранее.

**В: Зачем нам извлекать Cookie из ответа в автоматизации?**
О: Это критически важно для цепочки тестов (Chaining). Например: Тест №1 делает `Login`, извлекает `sessionID` из куки и сохраняет его. Тест №2 использует этот `sessionID`, чтобы проверить профиль пользователя без повторной авторизации.

**В: Что делать, если сервер присылает несколько значений в одном заголовке (например, Set-Cookie)?**
О: REST Assured умеет работать со списками. Ты можешь извлечь их как `List<String>` через `.extract().cookies()`.

# 📌 Шпаргалка: Тело запроса (Request Body) в REST Assured

**Request Body (Payload)** — это полезная нагрузка, которую мы отправляем на сервер (обычно в методах `POST`, `PUT`, `PATCH`). Это «содержимое» нашего сообщения.

В REST Assured есть несколько способов формирования тела, и выбор способа зависит от сложности данных и целей теста.

---

### 1. Способ "Quick & Dirty" (Hardcoded String)
Самый простой вариант: ты просто пишешь JSON как обычную строку.

*   **Когда использовать:** Только для микро-тестов или когда нужно проверить один конкретный символ в теле.
*   **Минусы:** Ужасно неудобно работать с кавычками (`\"`), невозможно масштабировать, код превращается в "кашу".

```java
given()
    .contentType(ContentType.JSON)
    .body("{\"name\": \"John\", \"job\": \"QA\"}") // Мучение с экранированием
.when()
    .post("/api/users");
```

### 2. Способ "Modern Java" (Text Blocks — Java 15+)
Если ты используешь современную Java, забудь про экранирование кавычек. Используй тройные кавычки.

*   **Когда использовать:** Когда нужно быстро набросать небольшой JSON прямо в тесте и не хочется создавать лишние классы.
*   **Плюсы:** Читаемо, чисто, никакой боли с `\"`.

```java
String jsonBody = """
    {
        "name": "John",
        "job": "QA"
    }
    """;

given()
    .contentType(ContentType.JSON)
    .body(jsonBody)
.when()
    .post("/api/users");
```

### 3. Способ "Dynamic" (Maps & Lists)
Мы создаем структуру данных в Java (например, `Map`), а REST Assured сам превращает её в JSON.

*   **Когда использовать:** Когда тебе нужно динамически менять одно-два поля в запросе (например, подставлять случайное имя или ID).
*   **Плюсы:** Очень гибко. Тебе не нужно переписывать всю строку, ты просто меняешь значение в `Map`.
*   **Важно:** Нужна библиотека **Jackson** или **Gson** в проекте, чтобы маппинг сработал.

```java
Map<String, Object> requestBody = new HashMap<>();
requestBody.put("name", "John");
requestBody.put("job", "QA");
requestBody.put("age", 25); // Легко добавить новое поле

given()
    .contentType(ContentType.JSON)
    .body(requestBody)
.when()
    .post("/api/users");
```

### 4. Способ "Professional" (POJO — Serialization)
Это золотой стандарт. Мы создаем Java-класс, который полностью повторяет структуру нашего JSON.

*   **Когда использовать:** Всегда в серьезных проектах. Для сложных, вложенных и больших объектов.
*   **Плюсы:** 
    *   **Type Safety:** Ты не ошибешься в названии поля (компилятор подскажет).
    *   **Reusability:** Один класс можно использовать в десятках тестов.
    *   **Maintainability:** Если поле в API изменилось, ты меняешь его только в одном месте — в классе.

```java
// Класс-модель (POJO)
public class User {
    private String name;
    private String job;
    // Геттеры, сеттеры, конструктор
}

// В тесте
User user = new User("John", "QA");

given()
    .contentType(ContentType.JSON)
    .body(user) // REST Assured сам превратит объект в JSON (десериализация)
.when()
    .post("/api/users");
```

### 5. Способ "External Files" (JSON from Resources)
Загрузка тела запроса из готового `.json` файла, лежащего в `src/test/resources`.

*   **Когда использовать:** Когда у тебя есть огромные JSON-ответы (на сотни строк), которые не хочется держать в коде.
*   **Плюсы:** Тесты остаются короткими и чистыми.

```java
File jsonFile = new File("src/test/resources/payloads/create_user.json");

given()
    .contentType(ContentType.JSON)
    .body(jsonFile)
.when()
    .post("/api/users");
```

### 6. Способ "Multipart/Form-data" (Загрузка файлов)
Используется, когда нужно отправить файл (картинку, документ) или имитировать отправку формы с сайта.

*   **Когда использовать:** Тестирование загрузки аватарок, документов и т.д.

```java
given()
    .multiPart(new File("path/to/image.png")) // Отправка файла
    .formParam("description", "My profile picture") // Дополнительные поля формы
.when()
    .post("/api/upload");
```

---

### 💡 Senior Nuances (На что обратить внимание)

1.  **Content-Type — это критично!** Если ты отправляешь JSON, но забыл `.contentType(ContentType.JSON)`, сервер может получить "кашу" и вернуть `415 Unsupported Media Type` или `400 Bad Request`.
2.  **Зависимости:** Чтобы способы с `Map` и `POJO` работали, в твоем `pom.xml` **обязательно** должен быть `jackson-databind`. Без него REST Assured не поймет, как превратить Java-объект в строку.
3.  **Null values:** Будь осторожен с `null`. При сериализации POJO поля со значением `null` могут либо уходить в JSON как `"field": null`, либо вообще исчезать (зависит от настроек Jackson). Это может сломать контракт API.

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Что лучше использовать для тела запроса: String или POJO?**
**О:** Для простых, разовых проверок — Text Blocks (String). Для полноценной автоматизации — POJO. POJO обеспечивает типизацию и легкость поддержки при изменении API.

**В: Как отправить JSON-файл, в котором нужно заменить одно значение на динамическое?**
**О:** Есть два пути. Плохой: прочитать файл как строку и сделать `.replace()`. Хороший: использовать шаблонизатор (например, FreeMarker) или загрузить данные в POJO, а затем отправить объект.

**В: Что такое сериализация и десериализация в контексте REST Assured?**
**О:** **Сериализация** — это процесс превращения Java-объекта (POJO) в формат JSON для отправки в теле запроса. **Десериализация** — это обратный процесс: превращение JSON-ответа от сервера в Java-объект для удобных проверок в коде.

**В: Может ли тело запроса быть пустым?**
**О:** Да, для некоторых методов (например, `DELETE` или некоторые конфигурации `GET`) тело может отсутствовать. Но если ты отправляешь `Content-Type: application/json`, сервер будет ожидать хотя бы `{}`.

# 📝 Шпаргалка: Тело запроса (Request Body) — Передача строки

### 💡 Суть метода
Передача тела запроса в виде строки (`String`) — это самый примитивный и «ручной» способ отправить данные на сервер. Ты просто берешь готовый текст (JSON, XML или обычный текст) и «впихиваешь» его в запрос.

В REST Assured за это отвечает метод `.body(String body)`.

---

### 🛠 Основные сценарии использования

#### 1. Передача простого текста (Plain Text)
Используется, когда API ожидает не структурированный объект, а просто набор символов.
**Важно:** Обязательно укажи заголовок `Content-Type`.

```java
given()
    .contentType(ContentType.TEXT) // Указываем, что шлем текст
    .body("Hello, this is a simple message") 
.when()
    .post("/endpoint")
.then()
    .statusCode(200);
```

#### 2. Передача JSON как строки (Самый частый случай)
Часто используется в быстрых тестах или когда нужно проверить специфический, «кривой» JSON.

**Проблема:** В Java строки обрамляются двойными кавычками `"`. Если внутри твоей JSON-строки тоже есть кавычки, тебе придется их экранировать (`\"`), что превращает код в нечитаемый ужас.

**Плохой путь (Junior style):**
```java
// Нечитаемо, легко ошибиться в кавычках
String body = "{\"name\": \"John\", \"age\": 30, \"city\": \"New York\"}";
```

**Правильный путь (Senior style) — Использование Java Text Blocks (доступно с Java 15+):**
Тройные кавычки `"""` позволяют писать многострочный текст без всякого экранирования. Это делает тест чистым и понятным.

```java
String body = """
    {
        "name": "John",
        "age": 30,
        "city": "New York"
    }
    """;

given()
    .contentType(ContentType.JSON) // Обязательно! Без этого сервер может не понять формат
    .body(body)
.when()
    .post("/users")
.then()
    .statusCode(201);
```

#### 3. Передача XML
Аналогично JSON, но с XML-разметкой.

```java
String xmlBody = """
    <user>
        <name>John</name>
        <age>30</age>
    </user>
    """;

given()
    .contentType(ContentType.XML)
    .body(xmlBody)
.when()
    .post("/users")
.then()
    .statusCode(201);
```

---

### ⚠️ Нюансы и «подводные камни» (Senior Tips)

1.  **Заголовок `Content-Type` — это критично.** Если ты отправишь JSON-строку, но забудешь `.contentType(ContentType.JSON)`, сервер может вернуть ошибку `415 Unsupported Media Type`. Сервер не «угадывает» тип данных по содержимому, он смотрит на заголовок.
2.  **Проблема кодировки.** Если в твоей строке есть кириллица или спецсимволы (эмодзи, знаки валют), убедись, что твой проект и сервер работают в одной кодировке (обычно UTF-8). В редких случаях может потребоваться явное указание `Charset`.
3.  **Когда НЕЛЬЗЯ использовать строки.** Если JSON большой, сложный или его поля зависят от динамических данных (например, ID из предыдущего шага), **забудь про строки**. Используй **POJO** (объекты) или **Map**. Строки — это только для статических, простых и неизменных кусков текста.
4.  **Лишние пробелы.** При использовании Text Blocks (`"""`) будь внимателен с отступами в начале строк. Хотя JSON прощает лишние пробелы, слишком грязный формат может усложнить отладку логов.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что будет, если я передам JSON-строку, но не укажу `contentType`?**
**О:** Скорее всего, ты получишь ошибку `415 Unsupported Media Type`. Сервер получит данные, но не поймет, как их распарсить (как текст, как XML или как бинарный файл).

**В: Как избежать «ада с кавычками» (`\"`) в старых версиях Java (ниже 15)?**
**О:** Есть три пути:
1. Использовать библиотеку (например, Apache Commons `StringEscapeUtils`).
2. Хранить JSON в отдельном файле в папке `src/test/resources` и читать его через `Files.readString()`.
3. Использовать конкатенацию, но это менее удобно.

**В: Можно ли передать в `.body()` объект, а не строку?**
**О:** Да, REST Assured умеет автоматически превращать Java-объекты (POJO) или `Map` в JSON-строку, если в проекте подключена библиотека Jackson или Gson. Это гораздо более профессиональный подход для сложных структур.

**Г: В чем разница между передачей строки и передачей файла?**
**О:** При передаче строки данные находятся в оперативной памяти. Если файл весит 100 МБ, передача его как строки может «уронить» твой тест или сильно замедлить его. Для больших данных всегда используй передачу через `File`.

# 📂 Тема: Тело запроса (Request Body) — Передача файлов

Когда мы говорим о передаче файлов через API, мы почти всегда выходим за рамки обычного JSON. Здесь в игру вступает формат **Multipart**.

### 1. Главный секрет: Content-Type
Самая частая ошибка новичков — пытаться отправить файл, забыв про правильный заголовок. Для передачи файлов (изображений, документов, архивов) используется тип контента:
`multipart/form-data`.

Именно этот заголовок говорит серверу: *"Внимание! В этом запросе не один кусок данных, а несколько частей (parts), разделенных специальным разделителем (boundary)"*.

### 2. Способ №1: Использование `.multiPart()` (Стандарт)
Это «золотой стандарт» в Rest Assured. Метод `multiPart` сам заботится о создании границ (boundaries) и правильной упаковке файла.

**Синтаксис:**
```java
given()
    .contentType(ContentType.MULTIPART_FORM_DATA) // Обязательно!
    .multiPart("file", new File("src/test/resources/image.png")) // "file" — это имя поля, которое ждет сервер
    .when()
    .post("/upload")
    .then()
    .statusCode(200);
```

### 3. Способ №2: Передача через InputStream (Для продвинутых)
Представь, что файл огромный или он генерируется динамически в памяти теста (например, PDF-отчет). Тебе не хочется создавать физический файл на диске. В этом случае используй `InputStream`.

**Синтаксис:**
```java
given()
    .contentType(ContentType.MULTIPART_FORM_DATA)
    .multiPart("file", 
        getClass().getResourceAsStream("/data/document.pdf"), // Читаем из ресурсов
        "application/pdf" // Можно явно указать тип контента для части файла
    )
    .when()
    .post("/upload")
    .then()
    .statusCode(200);
```

### 4. Нюансы от Senior-а (На что смотреть)

1.  **Boundary (Разделитель):** Когда ты используешь `multipart/form-data`, Rest Assured автоматически генерирует уникальную строку-разделитель (например, `--boundary-12345`). **Никогда** не пытайся прописать этот boundary вручную в заголовках. Просто укажи `ContentType.MULTIPINT_FORM_DATA`, и библиотека сделает всё сама.
2.  **Имя параметра:** Поле `"file"` в методе `.multiPart("file", ...)` — это не название файла, а **ключ (key)**, который ожидает бэкенд. Если разработчик назвал поле `attachment` или `image`, твой тест упадет, если ты напишешь `file`.
3.  **Пути к файлам:** Всегда используй относительные пути (через `src/test/resources`). Использование абсолютных путей (`C:\Users\Admin\...`) — это верный способ сделать так, что тесты сломаются на CI/CD (Jenkins/GitLab).
4.  **Память:** Если ты загружаешь файлы размером в несколько гигабайт через `byte[]` или `String`, ты можешь получить `OutOfMemoryError`. В таких случаях только `InputStream` или прямая передача `File`.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему мой запрос возвращает 400 Bad Request, хотя файл прикрепился?**
**О:** Скорее всего, ты забыл `.contentType(ContentType.MULTIPART_FORM_DATA)`. Без этого заголовка сервер пытается прочитать файл как обычный текст или JSON и «сходит с ума».

**В: Можно ли отправить файл вместе с текстовыми полями в одном запросе?**
**О:** Да! Это и есть суть `multipart`. Ты можешь комбинировать `formParam()` (для текста) и `multiPart()` (для файла):
```java
given()
    .contentType(ContentType.MULTIPART_FORM_DATA)
    .formParam("description", "Это фото котика") // Текстовое поле
    .multiPart("file", new File("cat.jpg"))     // Файл
    .post("/upload");
```

**В: Как проверить, что файл успешно загружен?**
**О:** Обычно API после успешной загрузки возвращает JSON с метаданными файла (id, name, size). Проверяй статус-код `201 Created` и наличие ID в теле ответа через `jsonPath`.

**В: Что делать, если сервер требует специфический Content-Type для самого файла (например, image/jpeg)?**
**О:** Используй перегруженный метод `.multiPart(String name, InputStream stream, String contentType)`. Это позволит тебе явно указать тип контента для конкретной части запроса.

# 🧠 Шпаргалка: Тело запроса (Request Body) в REST Assured

**Request Body (Payload)** — это полезная нагрузка, которую мы отправляем серверу (обычно в методах `POST`, `PUT`, `PATCH`). Это «содержимое» нашего письма. Чтобы сервер понял, что мы ему прислали, критически важно правильно выставить заголовок `Content-Type`.

### 1. Способы передачи данных

У нас есть 4 основных пути: от «грязного» хардкода до профессиональной сериализации.

#### 🟢 Уровень 1: Hardcoded String (Строка в коде)
Самый простой, но самый плохой способ для больших данных. Подходит только для микро-тестов на 2 строки.
*   **Плюсы:** Быстро написать.
*   **Минусы:** Нечитаемо, сложно поддерживать, «засоряет» тест.

```java
String body = "{\"name\": \"John\", \"job\": \"QA\"}";

given()
    .contentType(ContentType.JSON)
    .body(body)
.when()
    .post("/api/users");
```
*💡 **Senior Tip:** Если используешь Java 15+, используй **Text Blocks** (тройные кавычки `"""`). Это избавит тебя от бесконечных `\"`.*

```java
String body = """
    {
        "name": "John",
        "job": "QA"
    }
    """;
```

#### 🟡 Уровень 2: External Files (Внешние файлы)
Мы кладем `.json` или `.xml` файл в папку `src/test/resources`.
*   **Плюсы:** Тест чистый, тело запроса можно редактировать без перекомпиляции кода.
*   **Минусы:** Если нужно динамически поменять одно поле (например, имя), придется либо создавать много файлов, либо использовать костыли.

```java
given()
    .contentType(ContentType.JSON)
    .body(new File("src/test/resources/user_payload.json"))
.when()
    .post("/api/users");
```

#### 🟠 Уровень 3: Map / List (Динамическая сборка)
Мы создаем структуру данных прямо в коде через `Map`. REST Assured сам превратит её в JSON (с помощью Jackson или Gson).
*   **Плюсы:** Идеально для динамических тестов. Легко менять значения «на лету».
*   **Минусы:** При очень сложных, глубоко вложенных структурах код превращается в «кашу» из `put()`.

```java
Map<String, Object> requestBody = new HashMap<>();
requestBody.put("name", "John");
requestBody.put("age", 30);

// Вложенный объект (Address)
Map<String, String> address = new HashMap<>();
address.put("city", "New York");
requestBody.put("address", address);

given()
    .contentType(ContentType.JSON)
    .body(requestBody)
.when()
    .post("/api/users");
```

#### 💎 Уровень Ультра (Senior): POJO (Serialization)
Мы создаем обычный Java-класс, который повторяет структуру JSON. REST Assured берет объект и «сериализует» его в JSON.
*   **Плюсы:** Типизация (ты не опечатаешься в названии поля), автодополнение в IDE, высокая масштабируемость. Это стандарт индустрии.
*   **Минусы:** Нужно сначала написать классы.

```java
// Создаем модель (POJO)
public class User {
    public String name;
    public String job;
    // Конструктор, геттеры, сеттеры...
}

// В тесте:
User user = new User("John", "QA");

given()
    .contentType(ContentType.JSON)
    .body(user) // Передаем объект напрямую
.when()
    .post("/api/users");
```

### 2. Работа с XML
XML работает по тем же принципам, что и JSON, но требует другого `ContentType`.

*   **Заголовок:** `.contentType(ContentType.XML)`
*   **Формат:** Тело должно быть валидным XML-деревом.

```java
String xmlBody = "<user><name>John</name><job>QA</post>";

given()
    .contentType(ContentType.XML)
    .body(xmlBody)
.when()
    .post("/api/users");
```

### ⚠️ Нюансы (На чем валятся джуны)

1.  **Content-Type — это база.** Если ты шлешь JSON, но забыл `.contentType(ContentType.JSON)`, сервер может вернуть `415 Unsupported Media Type`.
2.  **Зависимости.** Чтобы `Map` или `POJO` превратились в JSON, в твоем `pom.xml` **обязательно** должна быть библиотека **Jackson** или **Gson**. Без них REST Assured не поймет, как «разрезать» объект на строки.
3.  **Кодировка.** Если в теле запроса есть кириллица, убедись, что проект настроен на `UTF-8`, иначе получишь «кракозябры».

# 🔐 Шпаргалка: Аутентификация и Авторизация в REST Assured

Прежде всего, разделим эти понятия (это база для любого интервью):
*   **Аутентификация (Authentication/AuthN):** Проверка того, что ты — это ты (проверка паспорта). *Пример: ввод логина и пароля.*
*   **Авторизация (Authorization/AuthZ):** Проверка того, что тебе разрешено делать (наличие визы или пропуска в конкретную зону). *Пример: может ли этот пользователь удалять записи.*

В REST Assured мы автоматизируем передачу «доказательств» твоей личности.

---

### 1. Basic Authentication (Базовая аутентификация)
Самый простой и старый метод. Логин и пароль кодируются в строку `user:password` и переводятся в формат **Base64**.
*⚠️ Нюанс: Base64 — это не шифрование, это просто кодирование. Любой может его декодировать. Используется только поверх HTTPS.*

**Как реализовать:**
```java
given()
    .auth().basic("admin", "password123") // Автоматически создаст заголовок Authorization: Basic ...
.when()
    .get("/secure-endpoint");
```

#### 💡 Нюанс: Preemptive vs Non-preemptive
Это критически важный момент для Senior-тестов.
*   **Non-preemptive (по умолчанию):** REST Assured сначала отправляет запрос *без* данных. Сервер отвечает `401 Unauthorized`. Только после этого клиент отправляет второй запрос уже с данными. Это лишний сетевой круг (latency).
*   **Preemptive:** Клиент сразу отправляет заголовок с логином/паролем. Сервер получает всё с первого раза.

**Как сделать правильно (Preemptive):**
```java
given()
    .auth().preemptive().basic("admin", "password123") 
.when()
    .get("/secure-endpoint");
```

---

### 2. Bearer Token (OAuth2 / JWT)
Самый современный стандарт. Мы не передаем пароль в каждом запросе. Мы один раз логинимся, получаем **Token** (длинную строку) и прикрепляем её к каждому следующему запросу.

**Как реализовать:**
Здесь нет специального метода `.auth().bearer()`, мы просто работаем с заголовками (`headers`).

```java
String token = "eyJhbGciOiJIUzI1Ni..."; // Получен ранее через POST запрос

given()
    .header("Authorization", "Bearer " + token)
.when()
    .get("/api/user/profile");
```

---

### 3. API Keys (Ключи доступа)
Часто используется в сервисах вроде Google Maps или AWS. Ключ может передаваться двумя способами: в заголовке или прямо в URL.

**Способ А: В заголовке (Header)**
```java
given()
    .header("X-API-KEY", "my-secret-key-123")
.when()
    .get("/data");
```

**Способ Б: В параметрах запроса (Query Param)**
```java
given()
    .queryParam("api_key", "my-secret-key-123")
.when()
    .get("/data");
```

---

### 4. Digest Authentication
Чуть более сложная версия Basic Auth. Вметo передачи пароля в открытом (пусть и Base64) виде, используется хеширование (nonce). Встречается реже, но знать нужно.

**Как реализовать:**
```java
given()
    .auth().digest("user", "password")
.when()
    .get("/secure-endpoint");
```

### 🚀 Senior Tips (Профессиональные советы)

1.  **Не хардкодь секреты!** Никогда не пиши пароли и токены прямо в коде теста. Используй переменные окружения (`System.getenv()`), файлы `.properties` или `Vault`.
2.  **Цепочка запросов (Chaining):** В реальных фреймворках ты сначала делаешь запрос на `/login`, вытаскиваешь токен через `.extract().path("token")`, и подкладываешь его в `RequestSpecification` для всех остальных тестов.
3.  **RequestSpecification:** Чтобы не дублировать `.header("Authorization", ...)` в каждом тесте, создай базовый класс или метод, который будет возвращать преднастроенный объект запроса со всеми заголовками авторизации.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Чем отличается `auth().basic()` от `auth().preemptive().basic()`?**
**О:** В первом случае клиент ждет «пинка» от сервера (401 ошибку), чтобы отправить данные. Во втором — отправляет данные сразу. Для тестов всегда лучше использовать `preemptive`, так как это быстрее и имитирует реальное поведение современных приложений.

**В: Что делать, если токен протух (expired) во время выполнения длинного набора тестов?**
**О:** Твой фреймворк должен уметь проверять срок жизни токена или иметь механизм "перелогина". Идеальный подход: перед началом теста (в `@BeforeClass`) делать запрос на авторизацию и обновлять токен.

**В: Как проверить, что авторизация действительно работает?**
**О:** Напиши негативный тест. Сделай запрос к защищенному эндпоинту с заведомо неверным токеном или без него и убедись, что пришел статус `401 Unauthorized` или `403 Forbidden`.

# 🔐 Тема: Аутентификация и Авторизация: Basic Auth

### 💡 Что это такое? (Простыми словами)
**Basic Auth (Базовая аутентификация)** — это самый примитивный способ сказать серверу: «Я тот, за кого себя выдаю, вот мой логин и пароль». 

Работает это так: клиент берет строку `логин:пароль`, кодирует её в формат **Base64** и кладет в заголовок HTTP-запроса под названием `Authorization`.

### ⚙️ Как это работает технически (Нюанс №1)
Важно понимать: **Base64 — это НЕ шифрование**. Это просто способ кодирования текста. Любой, кто перехватит твой запрос, сможет мгновенно декодировать строку и прочитать твой пароль. 
> **Senior Tip:** Поэтому Basic Auth **категорически нельзя** использовать без протокола **HTTPS**. В HTTPS данные шифруются на уровне транспортного уровня, и Base64-строка становится бесполезной для хакера.

---

### 🛠 Реализация в REST Assured

В REST Assured есть два основных способа реализовать Basic Auth.

#### 1. Стандартный способ (Challenge-Response)
По умолчанию REST Assured работает в режиме «ожидания вызова». Сначала клиент делает запрос, сервер отвечает `401 Unauthorized` и говорит: «Эй, пришли мне данные!», и только потом клиент отправляет логин/пароль.

```java
import static io.restassured.RestAssured.*;

given()
    .auth().basic("admin", "superpassword123") // Автоматически соберет заголовок
.when()
    .get("https://api.example.com/user/profile")
.then()
    .statusCode(200);
```

#### 2. Preemptive Auth (Упреждающая аутентификация) — **Важно!**
Иногда сервер настроен так, что он не хочет присылать `401`, а ждет данные сразу. Или ты хочешь сэкономить один сетевой запрос (round-trip). В этом случае мы используем `.preemptive()`. Мы отправляем заголовок `Authorization` **сразу же** в первом запросе.

```java  
given()
    .auth().preemptive().basic("admin", "superpassword123") 
.when()
    .get("https://api.example.com/user/profile")
.then()
    .statusCode(200);
```
*Используй `preemptive()`, если видишь, что без него сервер не принимает запрос с первого раза.*

---

### ⚠️ Нюансы и Best Practices (Senior Level)

1.  **Никакого Hardcode!** Никогда не пиши пароли прямо в коде теста. Это дыра в безопасности. Используй:
    *   Переменные окружения (`System.getenv("API_PASS")`).
    *   Файлы конфигурации (`.properties` или `.yaml`), которые добавлены в `.gitignore`.
2.  **Заголовки вручную:** Если ты хочешь понять, что происходит, ты можешь сам собрать заголовок (но это плохой тон для автотестов):
    ```java
    // Это то же самое, что делает .auth().basic()
    String auth = "Basic " + Base64.getEncoder().encodeToString("admin:password".getBytes());
    given().header("Authorization", auth)...
    ```
3.  **Логирование:** При использовании Basic Auth всегда будь осторожен с `log().all()`. В логах (особенно в Allure или Jenkins) твой пароль может отобразиться в открытом виде. На реальных проектах настраивай маскирование чувствительных данных.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Чем Basic Auth отличается от Bearer Token (OAuth2)?**
**О:** Basic Auth передает логин и пароль (в Base64) в каждом запросе. Это менее безопасно и масштабируемо. Bearer Token — это временный «ключ» (токен), который ты получаешь один раз, а потом просто предъявляешь его. Если токен украдут, он протухнет через час, а если украдут пароль из Basic Auth — у хакера есть полный доступ к аккаунту.

**В: Что такое "Preemptive" в контексте авторизации?**
**О:** Это стратегия, при которой клиент не ждет от сервера ошибки `401 Unauthorized`, а сразу включает данные аутентификации в заголовок первого же запроса. Это экономит время (меньше запросов к серверу).

**В: Безопасно ли использовать Base64 для передачи пароля?**
**О:** Нет, Base64 — это кодирование, а не шифрование. Его можно декодировать одной командой в терминале. Безопасность обеспечивается только использованием TLS/SSL (HTTPS).

# 🧠 Шпаргалка: Digest Authentication (Digest Auth)

### 1. Что это такое? (Суть простыми словами)
Если **Basic Auth** — это когда ты отправляешь свой пароль в открытом виде (просто закодированный в Base64, который легко декодируется), то **Digest Auth** — это «умная» альтернатива. 

В Digest Auth твой реальный пароль **никогда не передается по сети**. Вместо этого клиент и сервер используют сложный математический процесс (хэширование), чтобы доказать, что ты знаешь пароль, не показывая его.

### 2. Как работает механизм (The Handshake)
Digest Auth использует принцип **Challenge-Response** (Вызов — Ответ). Процесс всегда состоит из двух (или более) шагов:

1.  **Запрос (Request):** Клиент отправляет обычный запрос на сервер.
2.  **Вызов (Challenge):** Сервер видит, что авторизации нет, и отвечает кодом `401 Unauthorized`. В заголовке `WWW-Authenticate` он присылает случайную строку — **nonce** (number used once).
3.  **Расчет (Calculation):** Клиент берет свой пароль, смешивает его с этим `nonce`, методом запроса и URI, и прогоняет через хэш-функцию (обычно MD5 или SHA-256).
4.  **Ответ (Response):** Клиент отправляет второй запрос, но уже с готовым хэшем в заголовке `Authorization`.
5.  **Проверка:** Сервер делает то же самое у себя и сравнивает результат. Если совпало — ты внутри.

### 3. Реализация в REST Assured
REST Assured берет всю «грязную» работу по расчету хэшей и обработке `401` ошибки на себя. Тебе нужно только передать логин и пароль.

```java
import static io.restassured.RestAssured.*;
import static org.hamcrest.Matchers.*;

public class DigestAuthTest {
    public void testDigestAuth() {
        given()
            .auth()
            .digest("admin", "super_secret_password") // Магия происходит здесь
        .when()
            .get("https://api.example.com/secure-data")
        .then()
            .statusCode(200)
            .body("status", equalTo("success"));
    }
}
```

### 4. Нюансы и советы профи (Senior Insights)

*   **Автоматизация хэндшейка:** Главная ценность REST Assured здесь в том, что библиотека сама умеет перехватывать `401` от сервера, вытаскивать `nonce` и делать повторный запрос с правильным хэшем. Тебе не нужно писать логику обработки `WWW-Authenticate`.
*   **Безопасность:** Хотя Digest Auth гораздо безопаснее Basic Auth (защищает от перехвата пароля), он всё еще уступает современным методам вроде **OAuth2** или **JWT**, так как подвержен атакам типа *Dictionary Attack* (если хэш будет перехвачен).
*   **Сложность настройки сервера:** Настроить Digest Auth на стороне сервера сложнее, чем Basic, из-за необходимости управления `nonce` и состоянием сессии. Поэтому в современном вебе его встречается реже.
*   **Зависимость от алгоритма:** Если сервер требует специфический алгоритм (например, только SHA-256 вместо MD5) или параметр `qop` (Quality of Protection), стандартный `.digest()` может не сработать без дополнительной настройки фильтров.

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем принципиальная разница между Basic и Digest Auth?**
**О:** В Basic пароль передается в Base64 (это почти открытый текст). В Digest пароль не передается — передается результат его хэширования вместе с уникальным значением `nonce`, что предотвращает повторное использование перехваченных данных (Replay Attack).

**В: Что такое Nonce и зачем он нужен?**
**О:** `Nonce` — это одноразовое случайное число, генерируемое сервером. Оно нужно для того, чтобы хэш каждого запроса был уникальным, даже если пароль не менялся. Это защищает от атак повторного воспроизведения (Replay Attack).

**В: Если я использую `.auth().digest()`, увижу ли я пароль в логах?**
**О:** Если ты включишь логирование запроса `log().all()`, REST Assured покажет заголовок `Authorization`. Там будет виден хэш, но не сам пароль. Однако, всегда будь осторожен с логированием чувствительных данных в CI/CD системах.

**В: Может ли Digest Auth работать без HTTPS?**
**О:** Да, технически может. Но это плохая практика. Без TLS (HTTPS) злоумышленник может подменить `nonce` или попытаться провести атаку на хэш. В современном мире Digest Auth почти всегда идет в связке с SSL/TLS.

# 🔐 Тема: Аутентификация и Авторизация (OAuth2)

### 🧠 Суть простыми словами
Прежде всего, не путай эти понятия:
*   **Аутентификация (Authentication):** Проверка того, *кто ты*. (Ты предъявляешь паспорт/логин).
*   **Авторизация (Authorization):** Проверка того, *что тебе можно*. (У тебя есть право входить в этот кабинет).

**OAuth2** — это протокол **авторизации**. Вместо того чтобы передавать логин и пароль при каждом запросе (что небезопасно), ты один раз обмениваешь их на временный «ключ» — **Access Token**. Дальше ты везде используешь только этот ключ.

---

### 🛠 Реализация в REST Assured

В автоматизации OAuth2 почти всегда состоит из двух этапов:
1.  **Запрос токена:** Отправляем `client_id` и `client_secret` на специальный Auth-сервер.
2.  **Использование токена:** Подставляем полученный токен в заголовок (Header) основного запроса.

#### Шаг 1: Получение токена (The Token Exchange)
Обычно это `POST` запрос с типом контента `application/x-www-form-urlencoded`.

```java
String accessToken = given()
    .auth().preemptive().basic("client_id", "client_secret") // Часто используется Basic Auth для обмена
    .formParam("grant_type", "client_credentials")
    .formParam("scope", "read write")
.when()
    .post("https://auth-server.com/oauth2/token")
.then()
    .statusCode(200)
    .extract()
    .path("access_token"); // Извлекаем сам токен из JSON ответа
```

#### Шаг 2: Использование токена в API запросе
Есть два способа передать полученный `accessToken`.

**Способ А: Через встроенный метод `.auth().oauth2()` (Рекомендуемый)**
REST Assured сам добавит префикс `Bearer `.

```java
given()
    .auth().oauth2(accessToken) // REST Assertured сделает за тебя Header "Authorization: Bearer <token>"
    .get("https://api.myservice.com/user/profile")
.then()
    .statusCode(200);
```

**Способ Б: Через ручное добавление заголовка (Если нужно больше контроля)**
Иногда логика формирования заголовка может быть кастомной.

```java
given()
    .header("Authorization", "Bearer " + accessToken)
    .get("https://api.myservice.com/user/profile")
.then()
    .statusCode(200);
```

---

### ⚠️ Нюансы от Senior (О чем не пишут в учебниках)

1.  **Префикс `Bearer`:** Самая частая ошибка новичков — забыть слово `Bearer` перед токеном при ручном формировании заголовка. Без него сервер тебя не узнает.
2.  **Срок жизни (Expiration):** Токены живут не вечно. Если твои тесты идут долго (например, нагрузочное тестирование), токен может протухнуть прямо посреди прогона. 
    *   *Pro-tip:* Реализуй логику проверки: если пришел `401 Unauthorized`, перед следующим тестом нужно обновить токен.
3.  **Безопасность секретов:** **Никогда** не хардкодь `client_secret` в коде! Используй переменные окружения (`System.getenv()`) или файлы конфигурации (`properties`), которые не попадают в Git.
4.  **Scope (Область доступа):** Если ты получил токен, но получаешь `403 Forbidden`, значит, при запросе токена ты не указал нужный `scope`. Ты "аутентифицирован", но не "авторизован" на это действие.
5.  **Client Credentials vs Password Flow:** В тестах чаще всего используется `client_credentials` (сервер-сервер). Если же тебе нужно имитировать вход пользователя, придется использовать `password` flow, что сложнее, так как требует передачи логина/пароля юзера.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между OAuth2 и Basic Auth?**
**О:** Basic Auth передает логин и пароль в каждом запросе (закодированные в Base64), что небезопачно. OAuth2 использует временный токен, который можно отозвать, не меняя основной пароль пользователя.

**В: Что такое Bearer Token?**
**О:** Это тип токена, который работает по принципу «кто предъявил — тот и владелец». Если злоумышленник украдет твой Bearer токен, он сможет действовать от твоего имени, пока срок действия токена не истечет.

**В: Почему я получил 401, хотя токен верный?**
**О:** Проверь три вещи: 
1. Не забыл ли ты префикс `Bearer `. 
2. Не истек ли `expires_in`. 
3. Правильно ли передана кодировка (иногда лишний пробел в начале заголовка всё ломает).

**В: Что делать, если токен нужно обновлять?**
**О:** В идеале, создай отдельный класс-провайдер (`TokenManager`), который будет проверять срок жизни токена и при необходимости вызывать метод получения нового токена перед выполнением основного запроса.

# 🛡️ Тема: Preemptive Authentication (Упреждающая аутентификация)

### Что это такое? (Простыми словами)
В мире HTTP есть два способа представиться серверу:

1.  **Reactive (Реактивный) подход:** Ты стучишься в дверь (делаешь запрос), сервер говорит: *"Подожди, я тебя не знаю, предъяви паспорт"* (отправляет `401 Unauthorized` с заголовком `WWW-Authenticate`). И только после этого ты присылаешь свои данные. Это лишний «круг» (round-trip) между клиентом и сервером.
2.  **Preemptive (Упреждающий) подход:** Ты не ждешь вопроса от сервера. Ты сразу, в самом первом запросе, прикрепляешь к нему свои "паспортные данные" (заголовки авторизации). Сервер получает запрос, видит credentials и сразу либо пускает тебя, либо отклоняет.

**Preemptive Authentication** — это когда клиент отправляет заголовок `Authorization` **до того**, как сервер запросил его.

---

### Как это работает в REST Assured
В REST Assured по умолчанию многие методы работают в "реактивном" режиме. Чтобы включить "упреждающий" режим, мы используем метод `.preemptive()`.

#### 1. Basic Auth (Самый частый случай)
Basic Auth кодирует логин и пароль в Base64 и кладет в заголовок `Authorization: Basic <base64-string>`.

*   **Реактивно:**
    ```java
    given()
        .auth().basic("user", "password") // Сначала получит 401, потом отправит данные
    .when().get("/secure");
    ```
*   **Preemptive (Как надо делать для скорости):**
    ```java
    given()
        .auth().preemptive().basic("user", "password") // Сразу отправит заголовок Authorization
    .when().get("/secure");
    ```

#### 2. Digest Auth
Чуть более сложный протокол, где сервер присылает "соль" (nonce), а клиент хеширует пароль с этой солью. Здесь превентивный режим использовать сложнее, так как серверу всё равно нужно дать тебе `nonce` из первого ответа, но REST Assured умеет обрабатывать это через `.preemptive().digest()`.

---

### 💡 Нюансы (Senior level)

1.  **Производительность:** Preemptive-подход экономит один сетевой запрос (Round-trip). В высоконагруженных тестах или при огромном количестве запросов это может быть заметно.
2.  **Безопасность:** При использовании `preemptive().basic()` твои учетные данные летят в сеть в первом же пакете. **Никогда не используй это без HTTPS!** Если трафик не зашифрован, любой "прослушиватель" (sniffer) увидит твой логин и пароль в открытом виде (Base64 — это не шифрование, это просто кодировка).
3.  **Когда НЕ использовать:** Если сервер настроен строго на проверку `WWW-Authenticate` и ожидает именно "честный" процесс рукопожатия (handshake), превентивный метод может вызвать ошибку конфигурации или быть проигнорирован. Но в 99% современных REST API используется именно Preemptive Basic Auth.

---

### ❓ FAQ (Частые вопросы на интервью)

**В: В чем принципиальная разница между `.auth().basic()` и `.auth().preemptive().basic()`?**
**О:** Разница в количестве запросов к серверу. `.basic()` сначала отправит запрос без авторизации, получит `401 Unauthorized`, и только потом отправит второй запрос с заголовком `Authorization`. `.preemptive().basic()` отправит всё одним единственным запросом.

**В: Можно ли использовать Preemptive Authentication для OAuth2 (Bearer Token)?**
**О:** Технически, концепция "упреждающего" действия здесь уже заложена в саму суть Bearer-токена (ты просто кладешь `Authorization: Bearer <token>` в заголовок). В REST Assured для этого обычно не используют метод `.preemptive()`, а просто добавляют заголовок через `.header("Authorization", "Bearer " + token)`.

**В: Безопасно ли передавать данные через Preemptive Basic Auth?**
**О:** Только если используется протокол **HTTPS**. В режиме HTTPS содержимое заголовка `Authorization` зашифровано TLS-слоем, и никто не сможет перехватить credentials. В обычном HTTP — это огромная дыра в безопасности.

# 📑 Шпаргалка: SSL-сертификаты в REST Assured

### 💡 Суть проблемы
Когда ты делаешь запрос на `https://`, клиент (REST Assured/Java) проверяет сертификат сервера. Если сертификат выдан доверенным центром (CA), всё ок. Но в **Dev/QA окружениях** часто используют **self-signed certificates** (самоподписанные). Java их не знает, «пугается» и обрывает соединение с ошибкой:
`javax/net/ssl/SSLHandshakeException: PKIX path building failed`.

---

### 🛠 Решение №1: "Ленивый" способ (Relaxed Validation)
Если тебе нужно просто «чтобы работало» и безопасность в тестовом окружении не является приоритетом. Мы говорим REST Assured: *"Забей на проверку, просто доверяй всем"*.

**Как реализовать:**
Используем метод `.relaxedHTTPSValidation()`.

```java
import static io.restassured.RestAssured.*;

public void testWithSelfSignedCert() {
    given()
        .relaxedHTTPSValidation() // Магическая строчка: игнорирует ошибки сертификата
        .baseUri("https://your-qa-env.com")
    .when()
        .get("/api/resource")
    .then()
        .statusCode(200);
}
```

*   **Плюсы:** Максимально быстро, одна строчка кода.
*   **Минусы:** **Небезопасно.** Ты становишься уязвим для атак Man-in-the-Middle (MitM). В реальных проектах это допустимо только на Stage/Dev окружениях.

---

### 🛠 Решение №2: "Профессиональный" способ (Custom TrustStore)
Если ты работаешь в серьезном финтехе или проекте, где безопасность важна даже в тестах. Мы не отключаем проверку, а **добавляем наш сертификат в список доверенных**.

**Алгоритм:**
1. Получаем файл сертификата (например, `my_cert.crt`).
2. Импортируем его в Java TrustStore (файл `.jks` или `.p12`).
3. Указываем REST Assured путь к этому хранилищу.

**Код реализации:**
```java
import io.restassured.config.SSLConfig;
import io.restassured.RestAssured;

public void testWithProperSSL() {
    // Настройка конфигурации SSL
    SSLConfig sslConfig = SSLConfig.sslConfig()
        .trustStore("src/test/resources/my_truststore.jks", "password123");

    RestAssured.config = RestAssured.config().sslConfig(sslConfig);

    given()
        .baseUri("https://secure-qa-env.com")
    .when()
        .get("/api/resource")
    .then()
        .statusCode(200);
}
```

*   **Плюсы:** Максимальная безопасность, имитация реального поведения клиента, проверка того, что сертификат вообще работает.
*   **Минусы:** Сложнее в настройке (нужно управлять файлами хранилищ).

### 🧠 Нюансы от Senior'а (Важно!)

1.  **Разница между KeyStore и TrustStore:**
    *   **TrustStore** — это список тех, *кому ты веришь* (сертификаты серверов). Для тестирования API тебе нужен именно он.
    *   **KeyStore** — это твое «лицо» (твой сертификат), чтобы сервер узнал тебя (используется в Mutual TLS / mTLS).
2.  **Глобальная настройка:** Не пиши `.relaxedHTTPSValidation()` в каждом тесте. Если проект тестовый, настрой это один раз в `BeforeAll` или в базовом классе конфигурации.
3.  **CI/CD Pipeline:** Помни, что если ты используешь решение №2 (TrustStore), этот файл `.jks` должен физически присутствовать на агенте (Jenkins/GitLab Runner), иначе тесты упадут.

**В: Почему `relaxedHTTPSValidation()` не помогает, если ошибка всё равно летит?**
**О:** Проверь, где именно ты вызываешь метод. Если ты настроил `RestAssured.config`, но в конкретном тесте используешь новый экземпляр `RequestSpecBuilder` без этой настройки, проверка включится снова.

**В: Можно ли использовать системную настройку `-Djavax.net.ssl.trustStore`?**

**В: Что делать, если у нас mTLS (двусторонний SSL)?**
**О:** Тебе нужно использовать и `trustStore` (чтобы доверять серверу), и `keyStore` (чтобы предъявить свой сертификат). В REST Assured это настраивается через расширенную конфигурацию `SSLConfig`.

# 📑 Шпаргалка: Проверка статус-кодов (Status Codes)

**Статус-код** — это первое, на что смотрит тестировщик. Это индикатор того, «жив» ли сервер и понял ли он твой запрос. Если код не тот, что ожидался, проверять тело ответа (body) часто нет смысла.

### 1. Базовый синтаксис
В REST Assured проверка идет в блоке `.then()`. Самый простой способ — использование метода `statusCode()`.

```java
given()
    .when()
    .get("/users/1")
    .then()
    .statusCode(200); // Проверяем, что пришел именно 200 OK
```

### 2. Использование Matchers (Гибкость)
Иногда тебе не нужен конкретный код, а нужно проверить условие. Для этого используем библиотеку **Hamcrest** (она идет в комплекте с Rest Assured).

*   **Проверка на любой успешный код (семейство 2xx):**
    Если ты не знаешь точно, будет это `200` или `201`, можно использовать проверку диапазона.
    ```java
    import static org.hamcrest.Matchers.*;

    .then()
    .statusCode(is(not(404))); // Проверяем, что код НЕ 404
    ```

*   **Проверка Status Line:**
    Если нужно проверить не только число, но и текстовое сообщение (редко, но бывает в строгих контрактах).
    ```java
    .then()
    .statusLine("HTTP/1.1 200 OK");
    ```

### 3. Senior-уровень: Нюансы и Best Practices

#### 💡 Нюанс №1: Логирование при ошибке (Must Have!)
Самая большая ошибка новичка — писать тесты, которые падают, но не показывают, *почему*. Если статус-код не совпал, ты должен видеть ответ сервера в консоли.
**Используй `log().ifValidationFails()`**.

```java
given()
    .log().all() // Логируем запрос
.when()
    .get("/users/1")
    .then()
    .log().ifValidationFails() // ЛОГИРУЕМ ОТВЕТ ТОЛЬКО ЕСЛИ ТЕСТ УПАЛ
    .statusCode(200);
```

#### 💡 Нюанс №2: Избегай "Magic Numbers" (Магических чисел)
Не пиши `200`, `201`, `404` по всему проекту. Если завтра логика API изменится, ты замучаешься искать их везде. Создай класс с константами или используй готовые библиотеки (например, Spring `HttpStatus`).

*Плохо:* `.statusCode(201)`
*Хорошо:* `.statusCode(HttpStatus.CREATED.value())`

#### 💡 Нюанс №3: Порядок проверок
Всегда проверяй статус-код **первым**. Если статус `500`, то попытка распарсить JSON из тела ответа может привести к новой ошибке (NullPointerException или JsonPathException), и ты не поймешь, что проблема была в коде сервера.

---

### 🚀 Основные группы кодов для тестов:
*   **2xx (Success):** `200 OK`, `201 Created` (после POST), `204 No Content` (после DELETE).
*   **4xx (Client Error):** `400 Bad Request` (ошибка в твоих данных), `401 Unauthorized` (забыл токен), `403 Forbidden` (нет прав), `404 Not Found` (неверный URL).
*   **5xx (Server Error):** `500 Internal Server Error` (баг на бэкенде).

### ❓ FAQ (Частые вопросы)

**В: Можно ли проверить сразу несколько статус-кодов в одном тесте?**
**О:** Технически — через Hamcrest (`is(oneOf(200, 201))`), но логически — **не стоит**. Тест должен проверять один конкретный сценарий. Если ты проверяешь "либо 200, либо 201", значит, твой тест не знает, что именно он ожидает, и это плохой тест.

**В: Что делать, если я хочу проверить, что статус-код НЕ равен 500?**
**О:** Используй `not()` из Hamcrest: `.then().statusCode(not(500))`. Но помни: проверка "не равен ошибке" — это слабая проверка. Старайся всегда стремиться к конкретике.

**В: Почему мой тест падает с ошибкой, хотя я вижу в логах 200 OK?**
**О:** Проверь, не используешь ли ты `statusLine()`. Если сервер вернул `HTTP/1.1 200 OK`, а ты проверяешь `HTTP/2 200 OK`, тест упадет из-за разницы в версии протокола, хотя код верный. Всегда отдавай приоритет `statusCode()`.

# 🧠 Шпаргалка: Валидация заголовков ответа (Response Headers)

**Заголовки (Headers)** — это метаданные, которые сервер присылает вместе с телом ответа. В автоматизации их проверка критична для подтверждения корректности работы API (например, правильный тип контента, наличие токенов безопасности или заголовков кэширования).

### 1. Основные методы проверки
В REST Assured проверка заголовков чаще всего происходит внутри блока `.then()`.

*   **Проверка конкретного значения:**
    Используем `header(name, value)`. Это самый простой способ для статичных заголовков.
    ```java
    given().get("/users/1")
    .then()
        .header("Content-Type", "application/json; charset=utf-8") // Точное совпадение
        .header("Server", "nginx"); 
    ```

*   **Проверка через Matchers (Гибкий подход):**
    Заголовки часто содержат динамические данные (например, `Date` или `Server: Apache/2.4.41 (Ubuntu)`). Использовать точное совпадение здесь нельзя — тест упадет завтра. Используй **Hamcrest Matchers**.
    ```java
    import static orgkiem.hamcrest.Matchers.*;

    given().get("/users/1")
    .then()
        .header("Content-Type", containsString("application/json")) // Проверка части строки
        .header("Server", startsWith("Apache"))                   // Проверка начала строки
        .header("Cache-Control", notNullValue());                  // Проверка, что заголовок вообще есть
    ```

### 2. Важные нюансы (Senior Tips) 💡

1.  **Проблема `Content-Type`:** 
    Никогда не делай проверку `header("Content-Type", "application/json")` через строгое равенство, если не уверен на 100%, что сервер не пришлет `application/json;charset=UTF-8`. Всегда используй `containsString("application/json")`. Это спасет тебя от «флапающих» (нестабильных) тестов.

2.  **Регистронезависимость:** 
    По стандарту HTTP заголовки регистронезависимы (`Content-Type` и `content-type` — одно и то же). REST Assured умеет обрабатывать это корректно, но для чистоты кода и читаемости тестов придерживайся стандартного написания (Camel-Case).

3.  **Проверка наличия заголовка:**
    Если тебе не важно значение, а важно только наличие (например, заголовок безопасности `X-Content-Type-Options`), используй:
    `header("X-Content-Type-Options", notNullValue())`.

4.  **Работа с `Set-Cookie`:**
    Заголовок `Set-Cookie` может приходить несколько раз. Если тебе нужно проверить конкретную куку, лучше извлечь их через `extract()` и работать с ними как со списком, так как стандартный `.header()` может вернуть только один (первый) найденный заголовок.

### 3. Извлечение заголовков для дальнейшего использования
Иногда значение заголовка (например, `Location` после создания ресурса) нужно сохранить, чтобы использовать в следующем запросе.

```java
String locationHeader = given().post("/users")
    .then()
        .extract()
        .header("Location"); // Извлекаем значение напрямую

// Теперь используем locationHeader в следующем GET запросе
```

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что делать, если я хочу проверить сразу несколько заголовков одним блоком?**
**О:** В REST Assured нет метода `headers(Map<String, String> expectedHeaders)`, поэтому приходится перечислять их цепочкой `.header(...).header(...)`. Это стандартная практика. Если заголовков слишком много, вынеси их в отдельный метод или используй `ResponseSpecBuilder`.

**В: Как проверить, что заголовок отсутствует?**
**О:** Используй Matcher `nullValue()`.
`then().header("X-Custom-Header", nullValue())`.

**В: Можно ли использовать регулярные выражения для проверки заголовков?**
**О:** Да! Через Hamcrest Matcher `matchesPattern`. Это идеально подходит для сложных заголовков, например, когда в `Date` или `Server` есть меняющиеся части.
`then().header("Date", matchesPattern(".*\\d{4}.*"))`.

**В: Почему мой тест падает на проверке Content-Type, хотя я вижу его в Postman?**
**О:** Скорее всего, дело в кодировке (charset). Проверь, нет ли в ответе `;charset=UTF-8`. Если есть — используй `containsString`.

# 🧠 Шпаргалка: Валидация Body (Assertions) в REST Assured

Валидация тела ответа — это «сердце» твоего теста. Мы используем блок `.then()` и библиотеку **Hamcrest Matchers** для проверки того, что пришло в JSON/XML.

### 1. Навигация по JSON (GPath)
Прежде чем проверять значение, нужно до него «достучаться». REST Assured использует синтаксис **GPath** (похож на Groovy):
*   `"user.id"` — доступ к вложенному полю.
*   `"users[0].name"` — доступ к элементу массива по индексу.
*   `"users.name"` — вернет список всех имен из массива `users`.
*   `"users.find { it.id == 1 }.name"` — поиск элемента в массиве по условию (мощнейшая штука!).

### 2. Основные типы проверок (Matchers)

#### А. Проверка точных значений и строк
*   `equalTo(value)` — строгое равенство (самый частый кейс).
*   `not(equalTo(value))` — проверка на неравенство.
*   `containsString("substring")` — проверка, что строка содержит подстроку.
*   `startsWith("prefix")` / `endsWith("suffix")` — проверка начала/конца строки.
*   `emptyString()` / `emptyOrNullValue()` — проверка на пустоту.

#### Б. Проверка чисел и логики
*   `greaterThan(n)` / `lessThan(n)` — границы чисел.
*   `closeTo(value, errorMargin)` — для работы с `float/double`, где важна погрешность (например, при работе с ценами).

#### В. Проверка коллекций (Массивов)
*   `hasSize(n)` — проверка количества элементов в массиве.
*   `hasItem("value")` — проверяет, что такой элемент **есть** в списке.
*   `everyItem(equalTo("value"))` — проверяет, что **все** элементы соответствуют условию.
*   `hasItems("a", "b")` — проверка наличия нескольких элементов сразу.

#### Г. Проверка на существование (Null/Not Null)
*   `notNullValue()` — критически важно для проверки того, что поле вообще пришло в ответе.

### 3. Продвинутый уровень: JSON Schema Validation
Если тебе нужно проверить не одно поле, а **всю структуру** (все типы данных, обязательные поля, форматы), не пиши 50 строк `body(...)`. Используй **JSON Schema**.
*   Ты создаешь `.json` файл со схемой.
*   Используешь: `assertThat(response, matchesJsonSchemaInClasspath("schema.json"))`.
*   **Профит:** Один метод проверяет весь контракт API.

---

### ⚠️ Нюансы от Senior (Don't forget!)

1.  **Не переусердствуй (Over-testing):** Не проверяй каждое поле в ответе, если тест сфокусирован на конкретной фиче. Если ты проверяешь `POST /user`, тебе важно, что `id` создался и `email` верный. Проверять `createdAt` или `updatedAt` не нужно — это делает тесты хрупкими (они упадут при изменении формата даты).
2.  **Типы данных имеют значение:** `equalTo("123")` (строка) **не равно** `equalTo(123)` (число). Всегда следи за типами в JSON.
3.  **Используй Hamcrest для читаемости:** Код `body("id", equalTo(1))` читается как английское предложение. Это стандарт индустрии.

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем разница между `jsonPath().get("path")` и `body("path", matcher)`?**
**О:** `body()` используется внутри цепочки `.then()` для автоматической валидации (Assertion). Если проверка не пройдет, тест упадет сразу. `jsonPath().get()` — это извлечение данных в переменную для последующего использования в других частях теста или других запросах.

**В: Как проверить, что в массиве объектов есть хотя бы один объект с определенным ID?**
**О:** Используй GPath поиск: `.body("users.find { it.id == 5 }", notNullValue())`. Это гораздо эффективнее, чем перебирать массив циклом в Java.

**В: Что делать, если поле может быть либо `null`, либо отсутствовать?**
**О:** Используй `notNullValue()` для проверки наличия, но если логика теста допускает `null`, используй более гибкие проверки или проверяй наличие ключа через `jsonPath().get("path") != null`.

**В: Как проверить, что все элементы в списке соответствуют какому-то паттерну (например, Email)?**
**О:** Используй `everyItem(matchesPattern("regex"))` (требуется интеграция с регулярными выражениями через Hamcrest).

# 🧠 Шпаргалка: Валидация Body через JsonPath

**JsonPath** — это твой «GPS-навигатор» внутри JSON-ответа. Он позволяет перемещаться по древовидной структуре документа, находить нужные узлы и проверять их содержимое. В REST Assured проверка обычно идет в связке с библиотекой **Hamcrest Matchers**.

### 1. Два способа проверки
Есть два подхода к валидации, и важно понимать разницу:

*   **Fluent Style (Внутри `then()`):** Самый чистый и читаемый способ. Мы используем метод `.body(path, matcher)`.
    ```java
    given().when().get("/users/1")
        .then()
        .body("name", equalTo("John")) // Проверка напрямую в цепочке
        .body("address.city", equalTo("New York"));
    ```
*   **Extraction Style (Сначала извлек — потом проверил):** Используется, если логика проверки слишком сложная для одного Matcher или тебе нужно использовать значение для следующего запроса.
    ```java
    String cityName = given().when().get("/users/1")
        .extract().path("address.city"); // Извлек строку
    assertThat(cityName, containsString("York")); // Проверил через JUnit/TestNG
    ```

### 2. Навигация по путям (Syntax)
Чтобы добраться до данных, используй следующие правила:
*   **Dot Notation (Точка):** Для вложенных объектов. `user.address.street`.
*   **Bracket Notation (Скобки):** Если в ключе есть спецсимволы или точки. `['user.name']`.
*   **Array Index (Индексы):** Доступ к элементам массива. `users[0].id` (первый пользователь).
*   **Wildcard (Звездочка):** Обращение ко всем элементам массива. `users[*].name` (вернет список всех имен).

### 3. Основные Matchers (Твои инструменты)
Без Hamcrest `JsonPath` — это просто навигация. Магия происходит здесь:
*   `equalTo(value)` — строгое равенство.
*    `notNullValue()` — проверка, что поле вообще присутствует и не `null`.
*   `hasItem("item")` — проверка, что элемент есть в массиве.
*   `hasItems("a", "b")` — проверка наличия нескольких элементов.
*   `size(n)` или `hasSize(n)` — проверка размера массива/коллекции.
*   `containsString("substring")` — частичное совпадение строки.
*   `instanceOf(Class)` — проверка типа данных (например, `Integer.class`).

### 4. Продвинутый уровень: GPath (Groovy Power)
REST Assured под капотом использует Groovy. Это значит, что ты можешь использовать **фильтрацию** прямо внутри пути. Это «киллер-фича».

*   **Поиск по условию (`find`):** Найти пользователя с ID 5 и проверить его имя.
    `body("users.find { it.id == 5 }.name", equalTo("Alice"))`
*   **Фильтрация списка (`findAll`):** Проверить, что все пользователи старше 18 лет (вернет список имен).
    `body("users.findAll { it.age > 18 }.name", hasItem("Bob"))`
*   **Маппинг (`collect` / `spread`):** Извлечь только массив ID из списка объектов.
    `body("users.id", hasItems(1, 2, 3))`

---

### ⚠️ Нюансы и «грабли» (Senior Tips)

1.  **Типизация данных:** Это самая частая причина падения тестов. `equalTo(1)` **не пройдет**, если в JSON число пришло как строка `"1"`. Всегда проверяй тип: `Integer` vs `String`.
2.  **Пустые массивы vs Null:** Если поле `address` отсутствует, `path("address.city")` выбросит ошибку (NullPointerException). Если массив пуст, `hasSize(1)` упадет. Всегда учитывай состояние данных в тестовой среде.
3.  **Сложные ключи:** Если твой JSON-ключ называется `user.info` (буквально с точкой), обычный путь `user.info` будет искать объект `user` с полем `info`. Используй `['user.info']`.
4.  **Производительность:** Не делай `extract().path()` для огромных JSON-ответов (на несколько мегабайт) в цикле. Это сильно замедляет тесты. Старайся использовать `body(...)` внутри цепочки `then()`.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `hasItem` и `contains`?**
**О:** `hasItem` проверяет, что указанный элемент *присутствует* в массиве (но в массиве могут быть и другие). `contains` требует, чтобы в массиве были *только* эти элементы и в строго определенном порядке.

**В: Как проверить, что массив не пустой?**
**О:** Проще всего использовать `not(empty())` или `hasSize(greaterThan(0))`.

**В: Что делать, если поле в JSON — это динамический UUID, который нельзя предсказать?**
**О:** Не используй `equalTo`. Используй регулярные выражения через Matcher: `body("id", matchesPattern("^[a-f0-9\\-]{36}$"))`.

**В: Можно ли с помощью JsonPath проверить структуру всего JSON сразу?**
**О:** Да, но для этого лучше использовать **JSON Schema Validation**. JsonPath хорош для проверки *значений*, а Schema — для проверки *структуры* (типов, обязательности полей).

# 📑 Шпаргалка: Валидация Body — Проверка наличия поля

Когда мы говорим о проверке «наличия поля», важно различать две разные задачи:
1. **Существование ключа** в JSON-объекте (есть ли такая «ячейка» в структуре).
2. **Наличие значения** (не является ли это поле `null` или пустой строкой).

### 1. Базовые подходы

Для проверок мы используем связку **Rest Assured + Hamcrest Matchers**.

#### А) Проверка, что поле не `null`
Самый частый сценарий. Мы не знаем, какое там значение, но нам важно, чтобы оно пришло.
```java
import static orgs.hamcrest.Matchers.*;

given()
    .get("/user/1")
.then()
    .body("name", notNullValue()) // Поле "name" должно существовать и не быть null
    .body("email", notNullValue());
```

#### Б) Проверка существования ключа (через JsonPath)
Если тебе нужно убедиться, что ключ вообще прописан в JSON, даже если его значение — `null`.
```java
import static org.hamcrest.Matchers.*;

given()
    .get("/user/1")
.then()
    // Проверяем, что в корневом объекте есть ключ "id"
    .body("$", hasKey("id")) 
    // Проверяем наличие ключа во вложенном объекте "address"
    .body("address", hasKey("city"));
```

---

### 2. Продвинутые нюансы (Senior Level)

#### Нюанс №1: Разница между `null` и отсутствующим полем
Это «ловушка» для новичков. 
* Если JSON: `{"name": null}`, то `notNullValue()` **упадет**, а `hasKey("name")` — **пройдет**.
* Если JSON: `{}`, то оба варианта **упадут**.

**Совет:** Если бизнес-логика допускает `null`, используй `hasKey()`. Если поле обязательное по контракту — всегда используй `notNullValue()`.

#### Нюанс №2: Проверка элементов в массивах
Если у тебя есть список (например, `tags: ["java", "rest"]`), и ты хочешь проверить наличие конкретного элемента:
```java
given()
    .get("/products/1")
.then()
    // Проверяем, что в массиве "tags" есть элемент "java"
    .body("tags", hasItem("java")) 
    // Проверяем, что в массиве "tags" НЕТ элемента "python"
    .body("tags", not(hasItem("python")));
```

#### Нюанс №3: Глубокая проверка (Nested Fields)
Не пытайся проверять каждое поле в цепочке, если структура сложная. Если ты проверяешь `user.address.city`, и поля `address` нет — тест упадет с ошибкой на `address`. 
**Senior Tip:** Сначала проверяй наличие родительского объекта, либо используй безопасные пути.

---

### 3. Резюме по Matchers для наличия

| Matcher | Что делает | Когда использовать |
| :--- | :--- | :--- |
| `notNullValue()` | Проверяет, что значение $\neq$ `null` | Когда поле обязательно и должно содержать данные. |
| `hasKey("key")` | Проверяет наличие ключа в объекте | Когда важно само наличие «ячейки» в JSON. |
    | `hasItem("val")` | Проверяет наличие элемента в List | Для проверки содержимого массивов/списков. |
    | `empty()` | Проверяет, что коллекция пуста | Если нужно убедиться, что список пришел, но он без данных. |

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что если я хочу проверить, что поле вообще отсутствует в ответе?**
**О:** Используй `not(hasKey("fieldName"))`. Это полезно для проверки безопасности (например, что поле `password` не утекает в API).
```java
.body("$", not(hasKey("password")))
```

**В: Как проверить наличие поля, если я использую десериализацию в POJO?**
**О:** Если ты уже превратил JSON в Java-объект (POJO), то `hasKey` из Rest Assured не сработает. Тебе нужно использовать обычные JUnit/TestNG ассерты: `assertNotNull(user.getName())`.

**В: Почему мой тест падает, если поле есть, но оно — пустая строка `""`?**
**О:** Потому что `notNullValue()` считает пустую строку валидным значением (она же не `null`). Если тебе нужно, чтобы строка была не просто не `null`, а еще и не пустой, используй:
```java
.body("name", allOf(notNullValue(), not(emptyString())))
```

# 🧠 Шпаргалка: Валидация Body (Assertions)
## Тема: Проверка типов данных и значений

В REST Assured основной инструмент для проверок — это библиотека **Hamcrest Matchers**. Мы не просто пишем `assertEquals`, мы используем "матчеры", которые позволяют строить читаемые предложения в стиле BDD.

### 1. Базовые проверки значений (Exact Matches)
Самый простой уровень: проверяем, что пришло именно то, что мы ждали.

*   **`equalTo(value)`**: Проверка на строгое равенство.
    *   *Нюанс:* Учитывает тип данных. `"1"` (String) $\neq$ `1` (Integer).
*   **`is(value)`**: То же самое, что `equalTo`, но более "человекочитаемо". В 90% случаев используй именно его.
*   **`not(value)`**: Проверка на неравенство.

```java
// Пример
.then()
    .body("id", is(1))               // Проверка Integer
    .body("name", is("John Doe"))    // Проверка String
    .body("isActive", is(true))      // Проверка Boolean
    .body("status", not("Error"));   // Проверка, что статус НЕ Error
```

### 2. Проверка типов данных (Type Validation)
Иногда нам не важно конкретное значение (например, `id` может быть любым), но нам критично, чтобы пришел именно `Integer` или `String`.

*   **`instanceOf(Class)`**: Проверяет, является ли объект экземпляром указанного класса.
*   **`notNullValue()`**: Проверяет, что поле не `null`. Это "золотой стандарт" для проверки обязательных полей.

```java
// Пример
.then()
    .body("id", instanceOf(Integer.class)) 
    .body("email", notNullValue())
    .body("description", instanceOf(String.class));
```

### 3. Проверка чисел и диапазонов (Numeric Assertions)
Когда значение динамическое (например, цена или дата), мы проверяем его границы.

*   **`greaterThan(value)` / `lessThan(value)`**: Проверка границ.
*   **`closeTo(value, errorMargin)`**: **Важнейший метод для Float/Double!** Из-за особенностей вычислений в Java, `0.3333` может не быть равен `0.33`. Используй `closeTo`, чтобы задать допустимую погрешность.

```java
// Пример
.then()
    .body("price", greaterThan(0.0))
    .body("discount", lessThan(100))
    .body("tax", closeTo(5.5, 0.01)); // Проверка: 5.5 +- 0.01
```

### 4. Работа с коллекциями (Lists & Arrays)
Проверка массивов — это то, где новички чаще всего совершают ошибки.

*   **`hasSize(n)`**: Проверяем количество элементов в списке.
*   **`hasItem(value)`**: Проверяем, что в списке есть хотя бы один такой элемент.
*   **`everyItem(matcher)`**: Применяем проверку к **каждому** элементу списка (например, все ID должны быть > 0).
*   **`containsInAnyOrder(val1, val2)`**: Проверяем наличие конкретных элементов, не обращая внимания на их порядок.

```java
// Пример
.then()
    .body("tags", hasSize(3))
    .body("tags", hasItem("premium"))
    .body("users.age", everyItem(greaterThan(18)))
    .body("roles", containsInAnyOrder("ADMIN", "USER"));
```

### 5. Проверка строк (String Pattern Matching)
*   **`containsString("substring")`**: Поиск подстроки.
*   **`matchesPattern(regex)`**: Проверка через Regular Expressions (RegEx). Незаменимо для проверки Email, дат или UUID.

```java
// Пример
.then()
    .body("email", containsString("@"))
    .body("uuid", matchesPattern("^[0-9a-суf]{8}-...")); // Проверка формата UUID
```

---

### ⚠️ Senior Nuances (На что обратить внимание)

1.  **Null vs Missing Field**: `notNullValue()` проверяет, что поле есть и оно не `null`. Но если поля вообще нет в JSON, тест упадет с ошибкой `Path not found`. Если тебе нужно проверить именно *наличие* ключа, используй более сложные подходы или проверку через `jsonPath.get()`.
2.  **Типизация чисел**: Всегда помни, что JSON не различает `int` и `float` (в стандартном JSON это просто `number`). Но Java/Rest Assured — различает. Если в API пришло `10.0`, а ты ждешь `is(10)`, тест может упасть. Используй `closeTo` или проверяй как `Double`.
3.  **Пустые коллекции**: `hasSize(0)` — отличный способ проверить, что поиск не вернул результатов.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `is(equalTo("A"))` и `is("A")`?**
**О:** Технически в Hamcrest они почти идентичны, но `is()` — это "синтаксический сахар". Он делает код похожим на английское предложение. Используй `is()`, чтобы коллеги читали твой тест как текст.

**В: Как проверить, что массив содержит только определенные элементы и ничего больше?**
**О:** Используй `contains(val1, val2)`. В отличие от `containsInAnyOrder`, этот матчер проверяет и наличие, и точный порядок, и отсутствие лишних элементов.

**В: Что делать, если я хочу проверить тип данных, но не знаю точно, какой это класс (например, Number)?**
**О:** Можно использовать проверку через `instanceOf(Number.class)`, так как `Integer`, `Double` и `Float` являются наследниками `Number`.

**В: Почему `hasItem` работает медленно на огромных списках?**
**О:** Потому  что он делает линейный поиск (O(n)). Если в ответе 10 000 элементов, тест будет тормозить. В таких случаях лучше сначала извлечь список и проверить его размер или использовать фильтрацию через `JsonPath`.

# 🧠 Шпаргалка: Работа с JsonPath & XmlPath

Когда ты получаешь ответ от API, тебе редко нужно проверять *весь* JSON целиком. Обычно тебе нужно вытащить конкретное поле (например, `id` пользователя) или проверить, что в списке из 100 элементов есть нужный тебе объект. Для этого существуют **JsonPath** и **XmlPath**.

Это своего рода «GPS-навигатор» внутри твоего JSON/XML документа. В REST Assured под капотом для JsonPath используется мощный движок **Groovy GPath**. Это значит, что ты можешь использовать возможности языка Groovy для фильтрации данных прямо в строке пути.

---

### 1. JsonPath: Навигация и магия Groovy

**Базовый синтаксис:**
*   `$` — корень документа.
*   `.` — переход к дочернему элементу (например, `$.user.name`).
*   `[]` — доступ к элементам массива по индексу или фильтрация.
*   `..` — поиск по всему дереву (deep scan), игнорируя уровни вложенности.

**Примеры использования:**

Представим JSON:
```json
{
  "store": {
    "books": [
      {"id": 1, "title": "Java Guide", "price": 20},
      {"id": 2, "title": "Rest Assured Pro", "price": 50}
    ]
  }
}
```

*   **Простой путь:** `$.store.books[0].title` $\to$ `"Java Guide"`
*   **Поиск по всем книгам (Deep Scan):** `$..price` $\to$ `[20, 50]` (вернет список всех цен).
*   **Фильтрация (GPath Magic):** 
    *   Найти книгу с ценой > 30: `$.store.books.find { it.price > 30 }.title` $\to$ `"Rest Assured Pro"`.
    *   Выбрать все заголовки книг, где цена < 30: `$.store.books.findAll { it.price < 30 }.title` $\to$ `["Java Guide"]`.
    *   *Примечание:* `it` — это текущий объект в итерации (стандарт Groovy).

---

### 2. XmlPath: XPath-style навигация

XmlPath работает по принципу **XPath**. Если ты знаком с XML, тебе будет легко.

**Основные фишки:**
*   `/` — путь от корня.
*   `@` — обращение к атрибуту элемента.
*   `//` — поиск узла в любом месте документа.

**Пример использования:**
```xml
<store>
    <book id="1">
        <title>Java Guide</title>
    </book>
</store>
```

*   **Доступ к тексту:** `store.book.title` $\to$ `"Java Guide"`.
*   **Доступ к атрибуту:** `store.book.@id` $\to$ `"1"`.

---

### 3. Как это реализовать в коде (REST Assured)

Есть два способа: через объект `Response` или напрямую через класс `JsonPath`.

**Способ А: Из ответа (самый частый)**
```java
String title = response.jsonPath().getString("store.books[0].title");
List<String> allTitles = response.jsonPath().getList("store.books.title");
```

**Споs Б: Работа со строкой (если JSON уже в переменной)**
```java
JsonPath jp = new JsonPath(jsonString);
int price = jp.getInt("store.books[1].price");
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Типизация:** Всегда помни, что `jsonPath().get()` возвращает `Object`. Если ты ожидаешь `int`, используй специализированные методы: `.getInt()`, `.getString()`, `.getBoolean()`. Это убережет от `ClassCastException`.
2.  **Null Safety:** Если пути не существует (например, опечатка в имени поля), JsonPath может вернуть `null` или выбросить ошибку в зависимости от метода. Всегда проверяй, что ты не пытаешься вызвать метод на `null`.
3.  **Производительность:** Использование оператора `..` (deep scan) на огромных JSON-файлах (мегабайты текста) может заметно замедлить тесты, так как парсеру приходится обходить всё дерево. Старайся указывать максимально точный путь.
4.  **Массивы vs Объекты:** Если твой путь возвращает список (например, `findAll`), ты не можешь сразу вызвать `.getString()`. Тебе нужно сначала извлечь список, а потом работать с его элементами.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что если я хочу проверить, что в списке есть определенное значение, не доставая его в переменную?**
**О:** Используй `Hamcrest` матчеры прямо в блоке `.then()`.
*Пример:* `response.then().body("store.books.title", hasItem("Java Guide"));`

**В: В чем разница между `find` и `findAll` в JsonPath?**
**О:** `find` возвращает **один** первый подходящий объект (или null). `findAll` возвращает **список** всех объектов, подходящих под условие.

**В: Как мне достать значение из XML, если там есть Namespace (пространство имен)?**
**О:** Это классическая боль. В REST Assured при работе с `XmlPath` нужно учитывать префиксы. Если XML сложный, проще всего использовать `XmlPath` вместе с предварительной очисткой строки от namespace или использовать специализированные библиотеки для парсинга XPath с поддержкой NS.

**В: Что делать, если JSON-ответ содержит вложенные массивы, и мне нужен глубокий поиск?**
**О:** Используй синтаксис `..`. Например, `$..id` найдет все поля `id` на любом уровне вложенности во всем документе. Но помни про совет выше — не злоупотребляй этим в больших файлах.

# 🧠 Шпаргалка: JsonPath & XmlPath (Навигация и фильтрация)

Когда ты получаешь ответ от API, он часто представляет собой огромный «слоеный пирог» из объектов и массивов. **JsonPath** (для JSON) и **XmlPath** (для XML) — это инструменты, которые позволяют тебе не перебирать весь ответ циклами `for`, а мгновенно «выстрелить» точно в нужное поле по его адресу.

В Rest Assured под капотом для JsonPath используется мощный язык **Groovy GPath**. Это значит, что ты можешь использовать возможности Groovy (фильтрацию, поиск, математику) прямо внутри пути.

---

### 1. Основы навигации (Dot & Bracket Notation)

Представь структуру: `$.store.book[0].title`

*   **`$`** — Корень документа (Root). Всегда начинай путь с него.
*   **`.` (Dot notation)** — Переход к дочернему элементу/полю. 
    *   *Пример:* `$.user.name` — заходим в `user`, берем `name`.
*   **`[]` (Bracket notation)** — Работа с индексами массивов или поиск по ключу.
    *   *Пример:* `$.books[0]` — первый элемент массива `books`.
    *   *Пример:* `$.items['id']` — если в ключе есть спецсимволы или пробелы.

---

### 2. Продвинутая навигация (Wildcards & Deep Scan)

Если ты не знаешь точного пути, но знаешь, что поле где-то там есть:

*   **`*` (Wildcard)** — Выбрать все элементы.
    *   *Пример:* `$.store.book[*].author` — вернет список **всех** авторов всех книг в магазине.
*   **`..` (Deep Scan/Recursive Descent)** — Искать поле по всему документу, на какой бы глубине оно ни находилось. Это «киллер-фича».
    *   *Пример:* `$..id` — найдет все поля `id` во всем JSON, независимо от вложенности. **Осторожно:** на огромных JSON это может тормозить тест.

---

### 3. Фильтрация (GPath Expressions) — Самое важное!

Это то, что отличает Junior от Senior. Мы не просто берем данные, мы ищем их по условию. Используется синтаксис `[?(<condition>)]`.

*   **Поиск по значению:**
    *   `$.books[?(@.price < 10)]` — найти все книги, где цена меньше 10.
    *   `@` — это ссылка на **текущий объект**, который мы проверяем в цикле.
*   **Поиск по вхождению строки:**
    *   `$.users[?(@.name =~ /John/)]` — найти пользователя, чье имя содержит "John" (используется Regex).
*   **Проверка наличия элемента в списке:**
    *   `$.orders[?(@.items contains 'apple')]` — найти заказ, в котором есть товар 'apple'.

---

### 4. Нюансы и «Подводные камни» (Senior Tips)

1.  **Типизация при извлечении:** Когда ты делаешь `.extract().path("$.price")`, Rest Assured вернет тип, который он распознал (Float, Integer или String). Если в JSON число `10`, а ты ожидаешь `String`, тест может упасть на этапе сравнения. Всегда проверяй, что именно возвращает путь.
2.  **Пустые результаты:** Если твой фильтр (например, `[?(@.id == 999)]`) не нашел совпадений, JsonPath не выбросит ошибку — он вернет **пустой список** или `null`. Твоя проверка (`assert`) должна учитывать это.
3.  **Fragile Paths (Хрупкие пути):** Избегай слишком длинных путей типа `$.a.b.c.d.e.f[0].g`. Если разработчики добавят новый уровень вложенности, твой тест «умрет». Используй `..` или фильтрацию по уникальным ключам, чтобы сделать путь более устойчивым к изменениям.
4.  **XmlPath vs JsonPath:** В XML всё чуть сложнее из-за атрибутов. Чтобы обратиться к атрибуту, используй символ `@`. 
    *   *Пример:* `$.book.@id` — найдет атрибут `id` у элемента `book`.

**В: Как мне получить список всех ID из массива объектов?**
**О:** Используй `$.items.id`. JsonPath автоматически «пробежится» по всем объектам в массиве `items` и соберет все значения `id` в один плоский список.

**В: В чем разница между `path("$.user.name")` и `get("$.user.name")`?**
**О:** В контексте Rest Assured они работают почти идентично, но `path()` чаще используется для навигации внутри `Response`, а `get()` — это метод из библиотеки JsonPath для получения данных. При использовании в цепочке `then().body(...)` мы всегда используем синтаксис пути.

**В: Что делать, если в JSON поле может быть либо строкой, либо null?**

**В: Можно ли использовать математические операции?**

# 🧠 Шпаргалка: JsonPath & XmlPath (Groovy GPath)

### 1. Суть концепции
Когда ты используешь `jsonPath()` или `xmlPath()` в Rest Assured, под капотом работает язык **Groovy**. Его механизм **GPath** — это не просто путь через точку (`a.b.c`), а мощный язык запросов, похожий на SQL или XPath. 

Вместо того чтобы перебирать списки циклами `for`, ты пишешь **предикат** (условие), и Groovy сам фильтрует данные.

### 2. Базовая навигация (The Basics)
*   `.` — переход к дочернему элементу или полю.
*   `..` — **Deep Scan**. Ищет указанное поле по всему дереву документа, на какой бы глубине оно ни находилось.
*   `[n]` — обращение к элементу списка по индексу (начиная с 0).
*   `[*]` — выбор всех элементов в массиве.

**Пример:** `store.books..author` — найдет всех авторов во всех книгах, независимо от структуры.

### 3. Магия GPath: Фильтрация и Трансформация
Это то, ради чего мы здесь. Главный герой здесь — ключевое слово **`it`**. В Groovy `it` — это текущий элемент, который мы рассматриваем в процессе обхода.

#### А) Поиск элементов (Searching)
*   **`find { it.condition }`** — возвращает **первый** объект, подходящий под условие.
*   **`findAll { it.condition }`** — возвращает **список всех** объектов, подходящих под условие.
*   **`every { it.condition }`** — возвращает `true`, если **все** элементы соответствуют условию.
*   **`any { it.condition }`** — возвращает `true`, если **хотя бы один** элемент соответствует условию.

#### Б) Извлечение данных (Mapping/Collecting)
*   **`collect { it.property }`** — превращает список объектов в список конкретных значений.
    * *Пример:* `books.collect { it.title }` → превратит массив объектов `Book` в массив строк `["Book 1", "Bookten 2"]`.

### 4. Продвинутые приемы (Senior Level)
*   **Сложные условия:** Ты можешь использовать любые операторы сравнения (`>`, `<`, `==`, `!=`) и логические связки (`&&`, `||`).
    * *Пример:* `books.findAll { it.price < 10 && it.category == 'fiction' }`
*   **Работа с типами:** GPath понимает типы данных внутри JSON. Ты можешь сравнивать строки с числами, но будь осторожен (Groovy довольно гибкий, что иногда ведет к ошибкам).
*   **Null-safety:** Если путь может привести к `null`, использование GPath позволяет избежать `NullPointerException` в коде теста, так как ты работаешь внутри строки запроса.

### 5. Нюансы и "Подводные камни" ⚠️
1.  **Пустой результат vs Null:** Если `findAll` не нашел совпадений, он вернет **пустой список `[]`**, а не `null`. Это важно при проверках `assertNotNull`.
2.  **Производительность:** Не используй `..` (Deep Scan) на огромных JSON-ответах (десятки мегабайт). Это заставляет парсер обходить всё дерево, что может замедлить тесты.
3.  **Типизация в Java:** Когда ты делаешь `.extract().path("...")`, Rest Assured возвращает `Object`. Чтобы работать с результатом дальше в Java, не забывай приводить его к нужному типу: `(List<String>) response.path("books.title")`.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `find` и `findAll`?**
**О:** `find` — это "одно значение" (первое попавшееся). `findAll` — это всегда "коллекция" (даже если найден один элемент или ни одного).

**В: Что такое `it` в контексте GPath?**
**О:** Это неявное имя текущего элемента в замыкании (closure). Когда ты пишешь `{ it.price > 5 }`, `it` представляет собой каждый отдельный объект из коллекции, которую ты перебираешь.

**В: Как мне получить только названия всех авторов из списка книг?**
**О:** Используй метод `collect`. Путь будет выглядеть так: `books.author.collect { it }` или проще `books*.author` (синтаксический сахар в Groovy).

**В: Можно ли использовать GPath для XML так же, как для JSON?**
**О:** Да, благодаря тому, что Rest Assured использует одну и ту же логику парсинга через Groovy, синтаксис `XmlPath` практически идентичен `JsonPath`. Единственное отличие — в XML нужно учитывать структуру тегов.

# 📑 Шпаргалка: Валидация JSON Schema в REST Assured

### 💡 Что это такое? (Суть)
Представь, что ты проверяешь посылку. Ты можешь проверить каждый предмет внутри (это **JsonPath**), а можешь просто посмотреть на накладную и убедиться, что коробка соответствует стандарту: размер, вес, наличие маркировки.

**JSON Schema Validation** — это проверка "контракта". Мы не проверяем конкретное значение (например, `id == 1`), мы проверяем **структуру**:
*   Все ли обязательные поля на месте?
*   Правильные ли типы данных (строка, число, массив)?
*   Соответствуют ли строки определенным паттернам (например, email)?
*   Не прилетело ли лишнего мусора в ответе?

Это гораздо эффективнее, чем писать 50 строк `assertThat` на каждое поле.

---

### 🛠 Настройка (Setup)
Для работы тебе понадобится специальная зависимость. Без неё метод `matchesJsonSchemaInClasspath` просто не появится.

**Maven:**
```xml
<dependency>
    <groupId>io.rest-assured</groupId>
    <artifactId>json-schema-validator</artifactId>
    <version>5.x.x</version> <!-- используй ту же версию, что и у rest-assured -->
    <scope>test</scope>
</dependency>
```

---

### 🚀 Реализация

1.  **Создай файл схемы:** Положи его в `src/test/resources/schemas/user-schema.json`.
2.  **Напиши код проверки:**

```java
import static io            io.restassured.module.matchers.JsonSchemaValidator.matchesJsonSchemaInClasspath;

given()
    .when()
        .get("/users/1")
    .then()
        .assertThat()
        // Ищем файл в папке resources
        .body(matchesJsonSchemaInClasspath("schemas/user-schema.json"));
```

---

### 🔍 Что внутри схемы? (Ключевые элементы)
Чтобы схема работала, ты должен использовать ключевые слова JSON Schema:

*   `type`: Тип данных (`string`, `number`, `integer`, `boolean`, `object`, `array`).
*   `properties`: Описание полей объекта.
*   `required`: Список полей, которые **обязательно** должны быть в ответе.
*   `enum`: Список допустимых значений (например, только `"admin"` или `"user"`).
*   `pattern`: Регулярное выражение для строк (проверка формата даты или UUID).
*   `minLength` / `maxLength`: Ограничение длины строки.
*   `items`: Правила для элементов внутри массива.

**Пример маленькой схемы (`user-schema.json`):**
```json
{
  "type": "object",
  "properties": {
    "id": { "type": "integer" },
    "name": { "type": "string" },
    "email": { "type": "string", "pattern": "^(.+)@(.+)$" }
  },
  "required": ["id", "name", "email"]
}
```

### ⚠️ Нюансы и Senior-советы (Don't forget!)

1.  **Разделяй ответственность:** 
    *   Используй **JSON Schema** для проверки *структуры и типов* (контракта).
    *   Имспользуй **JsonPath** для проверки *бизнес-логики* (конкретных значений: `name == "Ivan"`). 
    *   *Ошибка:* Пытаться впихнуть проверку конкретного ID в схему. Если ID изменится, тест упадет, хотя контракт не нарушен.

2.  **Проблема динамических данных:** Если поле может принимать любые значения (например, `timestamp`), используй в схеме тип `string` без жестких ограничений или регулярных выражений.

3.  **Где взять схему?** Не рисуй её из головы. Лучший способ — взять реальный JSON-ответ из Swagger/Postman и прогнать его через [JSON Schema Generator](https://app.quicktype.io/). Это сэкономит кучу времени.

4.  **Локация файлов:** Всегда используй `matchesJsonSchemaInClasspath`. Это позволяет не прописывать абсолютные пути к файлам, что критично при запуске тестов в CI/CD (Jenkins/GitLab).

### ❓ FAQ (Частые вопросы)

**В: Что делать, если тест упал на валидации схемы?**
**О:** REST Assured выдаст подробную ошибку. Ищи в логах фразу `Expected: ... but was: ...`. Там будет указано конкретное поле и причина (например, `expected type: string, but found: integer`).

**В: Можно ли проверить XML таким же способом?**
**О:** Нет. Для XML существует свой стандарт — **XSD (XML Schema Definition)**. В REST Assured механизмы проверки XML отличаются.

**В: Если в ответе придет лишнее поле, которого нет в схеме, тест упадет?**
**О:** По умолчанию — **нет**. JSON Schema по стандарту разрешает наличие дополнительных свойств (`additionalProperties`), если ты явно не запретил их через `"additionalProperties": false`.

**В: Насколько это быстро?**
**О:** Валидация схемы чуть тяжелее, чем обычный `get().path()`, так как парсер проходит по всему дереву JSON. В 99% случаев это незаметно, но на огромных JSON-ответах (мегабайты) имей это в виду.

# 🧠 Тема: Extraction (Извлечение данных)

**Extraction** — это процесс вытаскивания конкретных значений из ответа сервера (JSON/XML), чтобы использовать их в следующих запросах. Без этой темы невозможно построить **Chaining** (цепочку запросов), например: *Создать пользователя $\to$ Взять его `id` $\to$ Удалить пользователя по этому `id`*.

В REST Assured есть два основных пути извлечения данных.

---

### 1. Быстрый путь: `.extract().path("...")`
Используется, когда тебе нужно достать **одно конкретное значение** (строку, число, булево) и ты не планируешь проверять заголовки или статус-код этого же ответа.

*   **Как это работает:** Ты сразу получаешь результат в нужной переменной.
*   **Плюсы:** Максимально лаконично.
*   **Минусы:** Ты "теряешь" объект ответа. Если после извлечения тебе понадобится проверить `statusCode`, ты уже не сможешь это сделать, так как у тебя на руках только строка или число.

**Пример:**
```java
// Извлекаем ID пользователя напрямую в переменную String
String userId = given()
    .when()
        .get("https://api.example.com/users/1")
    .then()
        .extract()
        .path("id"); // Возвращает значение из поля "id"

System.out.println("ID пользователя: " + userId);
```

---

### 2. Профессиональный путь: `.extract().response()`
Это «золотой стандарт». Вместо конкретного значения ты извлекаешь **весь объект ответа** (`Response`).

*   **Как это работает:** Ты сохраняешь весь `Response` в переменную, а затем работаешь с ним как хочешь.
*   **Плюсы:** 
    1.  Можно проверить всё: статус-код, заголовки, тело.
    2.  Можно извлечь несколько разных полей из одного и того же ответа.
    3.  Идеально для сложных тестов.
*   **Минусы:** Чуть больше кода.

**Пример:**
```java
Response response = given()
    .when()
        .get("https://api.example.com/users/1")
    .then()
        .statusCode(200) // Сначала проверяем статус! (Важно!)
        .extract()
        .response(); // Извлекаем весь ответ

// Теперь работаем с объектом response
String name = response.jsonPath().getString("name");
String email = response/jsonPath().getString("email");
String contentType = response.getHeader("Content-Type");
```

---

### 💡 Нюансы и Senior-советы (Тонкости)

1.  **Принцип "Assert First, Extract Later":** Никогда не извлекай данные, пока не проверил статус-код (`statusCode(200)`). Если сервер вернет `500 Error`, а ты попытаешься достать `id` из пустого тела, тест упадет с непонятной ошибкой `NullPointerException`. Сначала убедись, что запрос успешен.
2.  **Типизация:** Будь осторожен с типами данных. Если в JSON число `10`, при использовании `.path("id")` Java может попытаться привести его к типу, который не совпадает с твоей переменной. Всегда явно указывай тип: `.path("id.toString()")` или используй `jsonPath().getInt("id")`.
3.  **Сложные пути (GPath):** Внутри `extract()` ты можешь использовать мощь **Groovy GPath**. Можно не просто достать поле, а найти элемент в списке по условию прямо "на лету".
    *   *Пример:* `String userEmail = response.jsonPath().getString("users.find { it.id == 1 }.email");` (Найти пользователя с id=1 и взять его email).

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `path()` и `jsonPath()`?**
**О:** `path()` — это метод "быстрого доступа" внутри цепочки `.extract()`. Он работает "под капотом", вызывая `jsonPath()`. `jsonPath()` — это отдельный инструмент, который ты используешь, когда у тебя уже есть объект `Response` или строка с JSON.

**В: Что делать, если мне нужно извлечь целый массив объектов?**
**О:** Используй `extract().path("users")` (вернет `List<Map>`) или, что еще лучше, десериализуй ответ в список POJO-классов через `as(UserList.class)`.

**В: Можно ли извлечь данные из массива по индексу?**
**О:** Да, используй синтаксис массивов: `.extract().path("users[0].name")` — это вернет имя первого пользователя в списке.

**В: Могу ли я использовать `extract()` вместе с `then()`?**
**О:** Да, это стандартная практика. Сначала идет `given()`, потом `when()`, затем проверки в `then()`, и только в самом конце — `extract()`. Это логическая цепочка: "Подготовили $\to$ Выполнили $\to$ Проверили $\to$ Забрали результат".

# 🧠 Тема: Сохранение данных в переменные (Data Extraction)

В автоматизации тестирования API мы редко проверяем один изолированный запрос. Чаще всего мы строим **цепочки (Chaining)**: создаем ресурс $\rightarrow$ получаем его ID $\rightarrow$ обновляем его $\rightarrow$ удаляем. Для этого нам нужно «вытащить» данные из ответа одного запроса и передать их в другой.

В REST Assured есть два основных пути извлечения данных.

### 1. Быстрый путь: `extract().path()`
Этот метод идеален, когда тебе нужно достать **одно конкретное значение** (строку, число, булево) прямо «на лету». Ты не сохраняешь весь ответ, а сразу получаешь результат.

*   **Как это работает:** Ты используешь GPath-выражение (похоже на XPath, но для JSON), чтобы указать путь к полю.
*   **Плюс:** Код очень короткий и читаемый.
*   **Минус:** Если тебе понадобятся еще и заголовки (headers) или статус-код этого же ответа, этот метод не поможет — он «забывает» всё, кроме значения поля.

**Пример:**
```java
// Достаем ID созданного пользователя напрямую в переменную типа int
int userId = given()
    .body(userPayload)
    .post("/users")
    .then()
    .statusCode(201)
    .extract()
    .path("id"); // Извлекает значение поля "id" из JSON
```

---

### 2. Путь профессионала: `extract().response()`
Этот метод возвращает **весь объект `Response`**. Это мощный инструмент, который дает тебе полный контроль над ответом.

*   **Как это работает:** Ты сохраняешь весь объект ответа в переменную типа `Response`. После этого ты можешь делать с ним что угодно: проверять статус-код, читать заголовки, извлекать любые поля или даже десериализовать его в POJO.
*   **Плюс:** Максимальная гибкость. Ты можешь сначала сделать все проверки (`then()...`), и только если они прошли, извлечь данные.
*   **Минус:** Чуть больше строк кода.

**Пример:**
```java
// Сохраняем весь объект ответа
Response response = given()
    .get("/users/1")
    .then()
    .statusCode(200)
    .extract()
    .response(); // Теперь у нас есть доступ ко всему ответу

// Извлекаем данные из сохраненного объекта
String name = response.jsonPath().getString("name");
String email = response.jsonPath().getString("contact.email");
String contentType = response.getHeader("Content-Type");
```

---

### 💡 Нюансы и Senior-советы

1.  **Типизация:** Всегда старайся приводить извлеченные данные к конкретному типу (`int`, `String`, `Boolean`). Избегай использования просто `Object`, иначе в тестах будет трудно понять, с чем ты работаешь.
2.  **Сложные пути (GPath):** Если тебе нужно достать значение из массива, используй синтаксис коллекций. Например, `path("users[0].id")` — ID первого пользователя. А если нужно найти ID пользователя с именем "Admin": `path("users.find { it.name == 'Admin' }.id")`.
3.  **Избегай «хрупких» путей:** Не делай слишком глубокую вложенность (например, `a.b.c.d.e.f`). Если структура API изменится, твой тест упадет. Старайся искать уникальные ключи.
4.  **Null Safety:** При извлечении данных всегда помни, что поле может отсутствовать или быть `null`. Если ты сразу пытаешься вызвать `.toString()` на результате, который пришел как `null`, получишь `NullPointerException`.

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `extract().path("id")` и `jsonPath().get("id")`?**
**О:** `extract().path()` — это встроенный метод REST Assured, который позволяет достать значение в одну цепочку с запросом. `jsonPath().get()` — это метод объекта `JsonPath`, который ты применяешь к уже имеющемуся у тебя объекту ответа или строке JSON. По сути, под капотом они делают похожее, но первый удобнее для коротких цепочек.

**В: Как извлечь целый список (List) объектов?**
**О:** Используй `path()` или `jsonPath().getList()`.
*Пример:* `List<String> emails = response.jsonPath().getList("users.email");` — это вернет список всех email-адресов из массива пользователей.

**В: Что делать, если я хочу сохранить не одно поле, а сразу несколько?**
**О:** Если полей много, не используй `extract().path()` для каждого. Используй `extract().response()`, а затем либо десериализуй ответ в **POJO** (это лучший способ), либо создай `JsonPath` и вытаскивай нужные поля из него.

**В: Можно ли извлечь данные, если запрос упал с ошибкой 500?**
**О:** Технически — да, объект `Response` всё равно создается. Но архитектурно — **нельзя**. Если тест упал на этапе `.statusCode(500)`, выполнение прервется, и код извлечения просто не запустится. Это правильно: мы не должны пытаться работать с данными из сломанного ответа.

# 🧠 Шпаргалка: Сложные извлечения (Complex Extractions)

Когда простых проверок `statusCode(200)` недостаточно, и тебе нужно взять `id` из одного ответа, чтобы подставить его в другой запрос — ты вступаешь на территорию **Extraction**.

### 1. Уровни извлечения

#### Уровень 1: Базовый (`path`)
Самый простой способ. Мы используваем метод `.path()`, чтобы достать конкретное значение по пути.
```java
// Извлекаем ID пользователя напрямую
int userId = response.path("id");

// Извлекает имя из вложенного объекта
String cityName = response.path("address.city");
```

#### Уровень 2: Работа с коллекциями (Lists & Maps)
Когда ответ — это массив, нам нужно достать не одно значение, а набор данных.
* **Извлечение списка строк/чисел:**
```java
// Получаем список всех имен пользователей в виде List<String>
List<String> userNames = response.path("users.firstName");

// Получаем список ID (автоматическое приведение типов)
List<Integer> ids = response.path("users.id");
```
* **Извлечение списка объектов (как Map):**
Если ты не хочешь создавать POJO, можно достать элементы как `Map`. Это удобно для быстрых проверок.
```java
// Каждый элемент массива — это Map<String, ?>
List<Map<String, ?>> allUsers = response.path("users");

// Доступ к полю внутри мапы из списка
String firstUserName = allUsers.get(0).get("firstName").toString();
```

#### Уровень 3: Магия Groovy GPath (Твой главный инструмент)
REST Assured использует синтаксис **Groovy GPath**. Это то, что делает извлечение «сложным». Ты можешь фильтровать, искать и трансформировать данные прямо в строке запроса.

* **Поиск по условию (`find`):** Найти пользователя с конкретным именем и достать его email.
```java
// "Найди пользователя, где name == 'John', и возьми его email"
String johnEmail = response.path("users.find { it.name == 'John' }.email");
```
* **Фильтрация коллекции (`findAll`):** Получить все ID пользователей старше 18 лет.
```java
List<Integer> adultIds = response.path("users.findAll { it.age > 18 }.id");
```
* **Итерация и коллекции (`collect`):** Преобразовать список объектов в список их атрибутов.
```java
// Получаем только email-ы всех пользователей (аналог map в JS)
List<String> emails = response.path("users.collect { it.email }");
```

#### Уровень 4: Десериализация (`as`) — "Путь Профи"
Если данных много и структура сложная, забудь про `path()`. Используй **POJO**. Это дает строгую типизацию и защиту от ошибок.
```java
// Превращаем весь JSON в Java-объект
UserResponse userDto = response.as(UserResponse.class);

// Теперь работаем с объектом через стандартный Java API
assertEquals("John", userDto.getUsers().get(0).getName());
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Null Safety:** Если ты используешь `path("users.find { it.id == 5 }.name")` и пользователя с ID 5 не существует, метод вернет `null`. Всегда проверяй на `null`, прежде чем вызывать методы у извлеченного значения, иначе получишь `NullPointerException`.
2.  **Типизация:** `path()` возвращает `Object`. Если ты ожидаешь `Integer`, а пришел `String`, возникнет ошибка каста. При работе с большими проектами всегда используй десериализацию в POJO (`as(Class.class)`).
3.  **Производительность:** Не вытягивай весь массив объектов через `path()`, если тебе нужно только одно поле. Используй GPath фильтрацию (`find`), чтобы уменьшить объем данных, обрабатываемых в памяти.
4.  **Пустые коллекции:** Если `findAll` не найдет совпадений, он вернет пустой список, а не `null`. Это важно учитывать при проверках `isEmpty()`.

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `response.path("...")` и `response.jsonPath().get("...")`?**
**О:** По сути — почти ни в чем. `path()` — это удобная обертка внутри REST Assured, которая внутри себя использует `JsonPath`. Но через `jsonPath()` у тебя остается больше методов для дальнейшей манипуляции объектом (например, можно сохранить `jsonPath` в переменную и использовать его повторно).

**В: Как мне извлечь значение, если я не знаю индекс элемента в массиве?**
**О:** Используй GPath оператор `find`. Например: `users.find { it.email == 'test@test.com' }.id`. Это гораздо надежнее, чем жестко прописывать `users[0]`.

**В: Что делать, если JSON очень глубокий? Можно ли использовать много точек?**
**О:** Да, `path("level1.level2.level3.targetField")` — это стандарт. Главное — следить за тем, чтобы промежуточные узлы существовали, иначе путь "сломается".

**В: Как извлечь файл или бинарные данные?**
**О:** Для этого `path()` не подходит. Тебе нужно получить `Response`, затем `asByteArray()` или `asString()`, в зависимости от контента.

# 🧠 Тема: Понятие POJO (Plain Old Java Object)

Если ты до сих пор формируешь тело запроса через длинные строки `"{ \"name\": \"Ivan\" }"` — остановись. Это путь к ошибкам и боли. Нам нужен **POJO**.

### 1. Что это такое?
**POJO** — это "простой старый Java-объект". Представь себе обычный контейнер для данных. В нем нет никакой сложной логики, нет связи с базой данных или бизнес-правилами. Это просто класс, который содержит поля (данные) и методы для доступа к ним (геттеры и сеттеры).

В контексте REST Assured, POJO — это твой **чертеж** того, как выглядит JSON-запрос или ответ.

### 2. Зачем это нужно? (The "Why")
Использование POJO решает три главные проблемы:
1.  **Type Safety (Типобезопасность):** Ты не ошибешься в названии поля или типе данных (число вместо строки). Компилятор поймает ошибку за тебя.
2.  **Serialization & Deserialization:** 
    *   **Serialization (Сериализация):** Превращение твоего Java-объекта в JSON-строку для отправки в `POST/PUT` запросе.
    *   **Deserialization (Десериализация):** Превращение полученного JSON-ответа обратно в Java-объект, чтобы ты мог писать проверки типа `user.getName().equals("Ivan")`.
3.  **Maintainability (Поддержка):** Если API изменится (например, поле `userName` переименуют в `login`), тебе нужно будет изменить код только в одном месте — в классе POJO, а не во всех 50 тестах.

### 3. Анатомия идеального POJO
Чтобы библиотека (обычно **Jackson** или **Gson**) смогла работать с твоим классом, он должен иметь:
*   **Private поля:** Данные инкапсулированы.
*   **Public Getters/Setters:** Чтобы библиотека могла "прочитать" и "записать" данные.
*   **Конструкторы:** Без параметров (default constructor) — обязательно для десериализации.

### 4. Нюансы и Senior-советы 💡

#### А. Магия Lombok
Писать геттеры, сеттеры и конструкторы вручную — это "boilerplate" (мусорный код). В реальных проектах мы используем библиотеку **Lombok**. С ней твой класс превращается из 50 строк в 5:
```java
@Data // Генерирует геттеры, сеттеры, toString, equals и hashCode
@Builder // Позволяет создавать объекты через удобный Builder pattern
@NoArgsConstructor // Нужен для Jackson
@AllArgsConstructor // Нужен для удобного создания объекта
public class UserPojo {
    private String name;
    private int age;
}
```

#### Б. Несовпадение имен (Mapping)
В JSON поле может называться `first_name` (snake_case), а в Java мы привыкли к `firstName` (camelCase). Чтобы не мучиться, используй аннотацию `@JsonProperty`:
```java
@JsonProperty("first_name")
private String firstName;
```

#### В. Вложенные объекты (Nested POJOs)
Если твой JSON выглядит как матрешка (объект внутри объекта), твои POJO тоже должны быть вложенными. Не пытайся распарсить всё одной плоской структурой — это убьет гибкость.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли использовать `Map<String, Object>` вместо POJO?**
**О:** Можно, и для очень простых, разовых запросов это допустимо. Но как только структура JSON становится сложной или повторяющейся — переходи на POJO. `Map` не дает типизации, и ты легко можешь опечататься в ключе, что приведет к падению теста в рантайме.

**В: Что произойдет, если в JSON есть поле, которого нет в моем POJO?**
**О:** По умолчанию Jackson может выбросить ошибку (`UnrecognizedPropertyException`). Чтобы этого избежать, нужно настроить `ObjectMapper` или добавить аннотацию `@JsonIgnoreProperties(ignoreUnknown = true)` над классом. Это критически важно для стабильности тестов при изменении API.

**В: В чем разница между сериализацией и десериализацией?**
**О:** 
*   **Сериализация:** Java Object $\to$ JSON (подготовка тела запроса).
*   **Десериализация:** JSON $\to$ Java Object (чтение ответа для проверок).

**В: Нужно ли мне писать `equals()` и `hashCode()` в POJO?**
**О:** Если ты планируешь сравнивать два объекта целиком (например, `assertThat(actualUser).isEqualTo(expectedUser)`), то **да**, это обязательно. Без них Java будет сравнивать ссылки на объекты в памяти, а не их содержимое. (Lombok `@Data` делает это за тебя).

# 🧠 Шпаргалка: Сериализация и Десериализация (Jackson/Gson)

В мире REST Assured работа со строками (JSON как текст) — это путь к боли и хрупким тестам. **Jackson** и **Gson** — это «переводчики», которые превращают JSON-строку в Java-объект (**POJO**) и наоборот.

### 1. Основные понятия
*   **Serialization (Сериализация):** Процесс превращения твоего Java-объекта в JSON-строку, чтобы отправить её в теле запроса (`POST`, `PUT`).
*   **Deserialization (Десериализация):** Процесс превращения JSON-ответа от сервера обратно в Java-объект, чтобы ты мог легко проверять поля через геттеры.
*   **POJO (Plain Old Java Object):** Обычный Java-класс, который служит моделью данных для твоего API.

### 2. Зачем это нужно? (Senior View)
| Без библиотек (String/JsonPath) | С библиотеками (POJO) |
| :--- | :--- |
| Ты работаешь с «сырым» текстом или путями `path("user.id")`. | Ты работаешь с типизированным объектом `user.getId()`. |
| Легко опечататься в названии поля. | Ошибку поймает компилятор (Type Safety). |

| Сложно поддерживать большие JSON-структуры. | Структура данных описана в классах, это легко рефакторить. |

### 3. Как это работает в коде

#### **Сериализация (Отправка данных)**
Тебе не нужно формировать JSON вручную. Просто создай объект и передай его в `.body()`.

```java
// Создаем объект
User user = new User("John", "Doe");

given()
    .contentType(ContentType.JSON)
    .body(user) // REST Assured сам вызовет Jackson/Gson и превратит user в JSON
.when()
    .post("/users")
.then()
    .statusCode(201);
```

#### **Десериализация (Получение данных)**
Вместо того чтобы парсить каждый путь, мы «маппим» весь ответ на класс.

```java
User responseUser = given()
.when()
    .get("/users/1")
.then()
    .extract()
    .as(User.class); // Магия: JSON превращается в объект User

// Теперь проверки максимально чистые:
assertEquals(responseUser.getFirstName(), "John");
```

### 4. Нюансы и «Подводные камни» (Тут начинается Senior-уровень)

#### **А) Несоответствие имен полей (Mapping)**
В JSON поле может называться `first_name` (snake_case), а в Java мы хотим использовать `firstName` (camelCase).
*   **Jackson:** Используй `@JsonProperty("first_name")`.
    ```java
    @JsonProperty("first_name")
    private String firstName;
    ```
*   **Gson:** Используй `@SerializedName("first_name")`.

#### **Б) Лишние поля в ответе (Unknown Properties)**
Если API присылает 20 полей, а в твоем POJO только 3, десериализатор может выкинуть ошибку.
*   **Jackson:** Добавь аннотацию над классом: `@JsonIgnoreProperties(ignoreUnknown = true)`. Это критически важно для стабильности тестов!

#### **В) Игнорирование полей**
Если ты не хочешь, чтобы какое-то поле (например, `password`) участвовало в сериализации.
*   **Jackson:** `@JsonIgnore`.
*   **Gson:** `@Expose(serialize = false)`.

#### **Г) Работа со списками**
Если API возвращает массив объектов `[{}, {}]`, десериализировать его напрямую в `List<User>.class` нельзя (из-за Type Erasure в Java).
*   **Решение:** Используй `TypeRef` или десериализуй в массив: `.as(User[].class)`.

### ❓ FAQ (Частые вопросы на интервью/в работе)

**В: Что лучше использовать: Jackson или Gson?**
**О:** В современной индустрии **Jackson** является стандартом де-факто (он встроен в Spring). Он мощнее, быстрее и лучше справляется со сложными структурами. **Gson** проще и легче, хорош для маленьких проектов, но менее гибкий.

**В: Что произойдет, если в JSON придет `null`, а в Java поле имеет примитив `int`?**
**О:** Произойдет ошибка десериализации (`JsonMappingException`), так как `null` нельзя записать в `int`. Всегда используй обертки (`Integer`), если не уверен на 100% в данных.

**В: Как проверить, что поле в JSON вообще присутствует, используя POJO?**
**О:** Если ты используешь десериализацию, проверка наличия поля превращается в проверку на `null` (если тип объекта) или проверку значения по умолчанию. Но если нужно именно *наличие ключа*, лучше использовать `JsonPath`.

**В: Можно ли использовать Jackson/Gson без добавления зависимостей в Maven?**
**О:** REST Assured умеет работать с ними, только если они есть в classpath твоего проекта. Если их нет, тебе придется вручную превращать объекты в String через `ObjectMapper`.

# 🧠 Шпаргалка: Сериализация и Десериализация в REST Assured

Если коротко: это процесс превращения «живого» Java-объекта в строку (JSON) и обратно.

### 1. Что это такое? (Простыми словами)
Представь, что ты отправляешь посылку другу за границу.
*   **Сериализация:** Ты берешь свои вещи (Java Object), упаковываешь их в коробку и заклеиваешь скотчем, чтобы они превратились в стандартную посылку (JSON String), которую поймет почта (API).
*   **Десериализация:** Твой друг получает коробку, открывает её и достает вещи, раскладывая их по своим полкам (создает Java Object из JSON).

### 2. Зачем это нужно в тестах?
Можно писать тесты, передавая тело запроса просто строкой (`String body = "{ \"name\": \"Ivan\" }" `). Но:
1.  **Это ужасно трудно читать**, когда JSON большой.
2.  **Легко ошибиться** в кавычках или запятых (синтаксическая ошибка).
3.  **Сложно поддерживать:** если поле в API изменилось, тебе придется искать и менять строки по всем тестам.

**Решение:** Использовать **POJO** (Plain Old Java Object) — обычные Java-классы.

### 3. Как это работает (Workflow)
Для работы нам нужна библиотека-маппер. Самая популярная — **Jackson**.

**Шаг 1: Создаем POJO класс**
```java
public class User {
    private String name;
    private int age;

    // Геттеры, сетка и конструкторы ОБЯЗАТЕЛЬНЫ
    public User(String name, int age) {
        this.name = name;
        this.age = age;
    }
    // ... getters and setters
}
```

**Шаг 2: Сериализация (Отправка запроса)**
Ты просто передаешь объект в метод `.body()`. REST Assured сам увидит объект и с помощью Jackson превратит его в JSON.
```java
User user = new User("Alex", 25);

given()
    .contentType(ContentType.JSON)
    .body(user) // Вот она, магия сериализации!
.when()
    .post("/users")
.then()
    .statusCode(201);
```

**Шаг 3: Десериализация (Получение ответа)**
Ты превращаешь ответ сервера обратно в объект, чтобы удобно проверять поля.
```java
User responseUser = given()
.when()
    .get("/users/1")
.then()
    .extract()
    .as(User.class); // Превращаем JSON ответа в наш класс User

assertEquals(responseUser.getName(), "Alex");
```

---

### 4. Нюансы и «подводные камни» (Senior Tips) ⚠️

1.  **Аннотации Jackson (`@JsonProperty`):**
    В Java мы пишем `userName` (camelCase), а в JSON может быть `user_name` (snake_case). Чтобы маппинг не сломался, используй аннотацию:
    ```java
    @JsonProperty("user_name")
    private String userName;
    ```

2.  **Игнорирование полей (`@JsonIgnore`):**
    Если в объекте есть поле (например, `password`), которое ты **не хочешь** отправлять в теле запроса, пометь его этой аннотацией.

3.  **Вложенные объекты и Списки:**
    POJO может содержать внутри себя другие POJO или `List<OtherPojo>`. Jackson отлично справляется с глубокой вложенностью, если структура классов совпадает со структурой JSON.

4.  **Проблема типов данных (Date/Time):**
    Самый большой кошмар — форматы дат. Если API присылает дату в формате `yyyy-MM-dd`, а Jackson пытается распарсить её иначе — тест упадет. Всегда настраивай формат через `@JsonFormat(pattern = "yyyy-MM-dd")`.

5.  **Зависимости:**
    Чтобы всё это заработало, в `pom.xml` **обязательно** должен быть `jackson-databind`. Без него REST Assured не поймет, как работать с объектами.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли использовать Gson вместо Jackson?**
**О:** Да, можно. Принцип тот же, но Jackson считается стандартом де-факто в экосистеме Java/Spring и работает чуть мощнее «из коробки» с REST Assured.

**В: Что делать, если JSON ответа слишком огромный и мне нужно проверить только одно поле?**
**О:** Не создавай POJO на весь этот гигантский JSON! Это избыточно (Overkill). Используй `JsonPath` для точечной проверки конкретного поля. Используй POJO только тогда, когда тебе нужно работать со всем объектом или его логической частью.

**В: Что произойдет, если в JSON есть поле, которого нет в моем Java классе?**
**О:** По умолчанию Jackson просто проигнорирует лишнее поле и не выдаст ошибку. Но если ты хочешь жесткого контроля, можно настроить `DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES`.

**В: Почему важно иметь геттеры и сеттеры в POJO?**
**О:** Библиотеки сериализации (Jackson/Gson) используют их для доступа к приватным полям класса. Без них они «не увидят» данные внутри объекта.

# 🧠 Тема: Десериализация (Deserialization)

### Что это такое?
Если **сериализация** — это процесс превращения Java-объекта в JSON (чтобы отправить его в POST-запросе), то **десерелизация** — это обратный процесс. Это когда мы берем «сырой» JSON-ответ от сервера и магическим образом превращаем его в полноценный Java-объект (POJO).

**Зачем это нужно?**
Вместо того чтобы писать бесконечные цепочки `jsonPath().get("user.address.city")`, ты просто делаешь `User user = response.as(User.class)` и работаешь с объектом: `user.getAddress().getCity()`. Это дает **строгую типизацию**, автодополнение в IDE и делает тесты читаемыми.

---

### 🛠 Что нужно для работы (Prerequisites)
Чтобы REST Assured понял, как превратить строку в объект, ему нужен «переводчик» — библиотека-маппер.
1.  **Jackson** (самый стандартный выбор в индустрии) или **Gson**.
2.  **Зависимости:** В `pom.xml` должны быть `rest-assured` и `jackson-databind`.
3.  **POJO классы:** Классы, структура которых зеркально повторяет структуру JSON.

---

### 🚀 Как это выглядит в коде

#### 1. Простой случай (Один объект)
**JSON:** `{"id": 1, "name": "John"}`

```java
// Наш POJO класс
@Data // Используем Lombok, чтобы не писать геттеры/сеттеры вручную
public class User {
    private int id;
    private String name;
}

// Тест
User user = given()
    .when()
    .get("/users/1")
    .then()
    .extract()
    .as(User.class); // Вот она, магия десериализации

assertEquals("John", user.getName());
```

#### 2. Сложный случай (Вложенные объекты и списки)
**JSON:** `{"id": 1, "contacts": [{"type": "email", "value": "a@b.com"}]}`

```java
@Data
public class User {
    private int id;
    private List<Contact> contacts; // Список вложенных объектов
}

@Data
class Contact {
    private String type;
    private String value;
}

// Тест
User user = get("/users/1").as(User.class);
assertEquals("email", user.getContacts().get(0).getType());
```

---

### ⚠️ Нюансы и «подводные камни» (Senior Tips)

1.  **Несоответствие имен полей:** В JSON поле может называться `first_name`, а в Java ты хочешь `firstName`. 
    *   *Решение:* Используй аннотацию `@JsonProperty("first_name")` (для Jackson). Без неё десериализация не поймет, куда класть значение.
2.  **Лишние поля в JSON:** Если сервер присылает 50 полей, а у тебя в POJO только 2 — это нормально. Но если ты используешь строгие настройки, Jackson может выкинуть ошибку `UnrecognizedPropertyException`.
    *   *Решение:* Добавь `@JsonIgnoreProperties(ignoreUnknown = true)` над классом. Это «золотой стандарт» для стабильных тестов.
3.  **Проблема десериализации списков (List):** Ты не можешь просто написать `.as(List<User>.class)` — Java из-за *Type Erasure* (стирания типов) не поймет, что внутри списка.
    *   *Решение:* Используй `TypeRef`.
    ```java
    List<User> users = get("/users").as(new TypeRef<List<User>>() {});
    ```
4.  **Lombok:** Всегда используй `@Data`, `@NoArgsConstructor` и `@AllArgsConstructor`. Jackson обязательно нужен пустой конструктор, чтобы создать объект перед тем, как заполнять его данными.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между JsonPath и Десериализацией?**
**О:** `JsonPath` — это поиск по пути (как XPath в XML). Он быстр для проверки одного поля, но неудобен для сложных структур. Десериализация — это создание полноценной модели данных. Для простых проверок используй JsonPath, для сложной логики и цепочек тестов — десериализацию.

**В: Что произойдет, если в JSON придет `null`, а в Java поле типа `int` (примитив)?**
**О:** Произойдет ошибка (NullPointerException или ошибка маппинга), так как примитив не может хранить `null`. Всегда используй обертки (`Integer`, `Long`, `Boolean`), если не уверен на 100% в данных.

**В: Можно ли десериализовать XML так же, как JSON?**
**О:** Да, REST Assured поддерживает XML, но тебе понадобится библиотека (например, JAXB) и соответствующий подход к созданию POJO. Принцип работы почти идентичен.

# 🧠 Шпаргалка: Работа со сложными структурами в REST Assured

Когда мы говорим о «сложных структурах», мы имеем в виду JSON, где данные не лежат плоским списком, а представляют собой **дерево**: объекты внутри объектов, массивы объектов, списки строк и т.д. 

Для работы с ними у нас есть два пути: **JsonPath** (навигация по пути) и **POJO** (превращение JSON в Java-объекты).

### 1. Навигация через JsonPath (Путь «Быстрый»)
Если тебе нужно просто проверить конкретное поле или вытащить ID, не нужно создавать целые классы. Используй точечную нотацию (`.`).

**Пример структуры:**
```json
{
  "orderId": 123,
  "customer": {
    "name": "Ivan",
    "address": { "city": "Moscow", "zip": "101000" }
  },
  "items": [
    { "productId": 1, "price": 500 },
    { "productId": 2, "price": 1000 }
  ]
}
```

*   **Вложенные объекты:** Используй точку. `customer.address.city` $\to$ `"Moscow"`.
*   **Массивы (индексы):** Используй квадратные скобки. `items[0].price` $\to$ `500`.
*   **Нюанс:** Если в ключе есть спецсимволы или пробелы (редко, но бывает), используй синтаксис `['key name']`.

---

### 2. Магия Groovy GPath (Путь «Профи»)
REST Assured под капотом использует язык **Groovy**. Это значит, что ты можешь не просто переходить по путям, а **фильтровать** данные прямо в строке запроса. Это киллер-фича.

*   **`find`**: Найти первый элемент, подходящий под условие.
    *   `items.find { it.productId == 2 }.price` $\to$ `1000`.
*   **`findAll`**: Найти все элементы, подходящие под условие (вернет список).
    *   `items.findAll { it.price > 600 }.productId` $\to$ `[2]`.
*   **`collect`**: Трансформировать данные (извлечь только одно поле из всех объектов).
    *   `items.collect { it.productId }` $\to$ `[1, 2]`.
*   **`every` / `count`**: Проверка условий на всем массиве.
    *   `items.every { it.price > 0 }` $\to$ `true`.

> **Senior Tip:** Не пытайся вытащить всё через `findAll` и потом циклом в Java. Если можно отфильтровать в JsonPath — делай это там. Это быстрее и код чище.

---

### 3. Десериализация в POJO (Путь «Архитектор»)
Когда структура очень большая, а тебе нужно не просто проверить одно поле, а использовать все данные для логики теста (например, отправить их в другой запрос), JsonPath превращается в ад. Тогда мы используем **POJO**.

1.  Создаешь Java-классы, зеркально отражающие JSON.
2.  Используешь библиотеку (Jackson или Gson).
3.  **Код выглядит так:**
    `OrderResponse order = response.as(OrderResponse.class);`

*   **Плюс:** Полная типизация. Ты работаешь с `order.getCustomer().getName()`, а не со строками. IDE подсказывает методы.
*   **Минус:** Нужно писать много шаблонного кода (Boilerplate).
*   **Нюанс:** Если в JSON есть поля, которых нет в твоем Java-классе, Jackson может упасть с ошибкой. Всегда добавляй `@JsonIgnoreProperties(ignoreUnknown = true)` над классом.

---

### 🚀 Итоговая шпаргалка по синтаксису (Cheat Sheet)

| Задача | Синтаксис JsonPath / GPath | Результат |
| :--- | :--- | :--- |
| Глубокая вложенность | `a.b.c` | Значение поля `c` |
| Элемент массива по индексу | `items[0]` | Первый объект в массиве |
| Поиск по условию | `items.find { it.id == 1 }` | Объект с id=1 |
| Фильтрация списка | `items.findAll { it.price > 100 }` | Список объектов дороже 100 |
| Извлечение списка значений | `items.productId` или `items.collect { it.id }` | `[1, 2, 3]` |
| Проверка наличия в списке | `items.id.hasItem(2)` | `true/false` |

**О:** Это ссылка на текущий элемент, который перебирает Groovy в данный момент. Без `it` ты не сможешь обратиться к свойствам объекта внутри замыкания.

**В: Как проверить, что массив вообще не пустой?**
**О:** Самый простой способ через JsonPath: `items.size().should(Matchers.greaterThan(0))`.

**В: Что выбрать: POJO или JsonPath для больших JSON?**

# 🛠 Шпаргалка: Аннотации Jackson в REST Assured

Когда мы работаем с REST Assured, нам нужно превращать JSON (строку) в Java-объекты (**Deserialization**) и наоборот (**Serialization**). Библиотека **Jackson** — это «переводчик», который делает эту работу. Но JSON часто бывает «неудобным» для Java (например, поля в `snake_case`, а в Java мы используем `camelCase`). 

Аннотации Jackson позволяют нам настроить правила этого перевода.

### 1. `@JsonProperty` — Главный инструмент
Самая важная антновация. Она связывает имя поля в JSON с именем переменной в твоем Java-классе.

*   **Зачем:** Если в JSON поле называется `user_id`, а ты хочешь в Java иметь переменную `userId`.
*   **Пример:**
```java
public class UserResponse {
    @JsonProperty("user_id") // Маппинг: в JSON "user_id", в Java "userId"
    private int userId;

    @JsonProperty("first_name")
    private String firstName;
}
```

### 2. `@JsonIgnoreProperties` — Твой «щит» от падений тестов
**Это самая важная аннотация для автоматизатора.** 

*   **Зачем:** По умолчанию, если в JSON придет новое поле, которого нет в твоем Java-классе, Jackson выбросит ошибку (`UnrecognizedPropertyException`), и твой тест упадет. Чтобы этого не происходило, мы говорим: «Игнорируй всё, что ты не знаешь».
*   **Нюанс:** Всегда ставь `ignoreUnknown = true` в своих DTO (Data Transfer Objects). Это сделает твои тесты устойчивыми к изменениям API.
*   **Пример:**
```java
@JsonIgnoreProperties(ignoreUnknown = true) // Если в ответе появятся новые поля — тест не упадет
public class UserResponse {
    private int userId;
}
```

### 3. `@JsonIgnore` — Скрываем лишнее
*   **Зачем:** Если ты не хочешь, чтобы определенное поле участвовало в процессе (например, ты не хочешь отправлять `password` обратно в запросе или тебе не нужно его десериализовать).
*   **Пример:**
```java
public class UserRequest {
    private String username;
    
    @JsonIgnore // Это поле никогда не попадет в JSON при отправке (Serialization)
    private String internalToken;
}
s
```

### 4. `@JsonFormat` — Магия с датами
Работа с датами — это всегда боль. В JSON дата может быть строкой в любом формате.

*   **Зачем:** Чтобы Jackson понял, как превратить строку `"2023-10-25 14:00:00"` в объект `LocalDateTime`.
*   **Пример:**
```java
public class UserResponse {
    @JsonFormat(shape = JsonFormat.Shape.STRING, pattern = "yyyy-MM-dd HH:mm:ss")
    private LocalDateTime createdAt;
}
```

### 5. `@JsonInclude` — Чистота в запросах
*   **Зачем:** Когда ты создаешь `POST` запрос, тебе часто не нужно отправлять поля со значением `null`. Эта аннотация позволяет исключить пустые поля из итогового JSON-тела.
*   **Пример:**
```java
@JsonInclude(JsonInclude.Include.NON_NULL) // Если поле null — его просто не будет в JSON
public class UserRequest {
    private String name;
    private String email; // Если email == null, в запросе будет только "name"
}
```

---

### 💡 Senior Tips (Нюансы)

1.  **Naming Strategy:** Если у тебя очень много полей в `snake_case`, не нужно вешать `@JsonProperty` на каждое. Можно использовать аннотацию `@JsonNaming(PropertyNamingStrategies.SnakeCaseStrategy.class)` на уровне всего класса. Это сэкономит кучу времени.
2.  **Lombok + Jackson:** Если используешь Lombok (`@Data`, `@Builder`), убедись, что у тебя есть пустой конструктор (или аннотация `@NoArgsConstructor`). Jackson **обязательно** нужен конструктор без параметров, чтобы создать объект перед тем, как заполнять его данными.
3.  **Immutable Objects:** Если ты используешь `final` поля (что круто для безопасности), тебе может понадобиться аннотация `@JsonCreator` над конструктором, чтобы Jackson знал, как передать значения в него.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что произойдет, если в JSON придет поле `age`, а в моем POJO его нет, и я не использовал `@JsonIgnoreProperties`?**
**О:** Тест упадет с ошибкой `UnrecognizedPropertyException`. Это классическая причина "хрупких" автотестов.

**В: В чем разница между `@JsonIgnore` и `@JsonIgnoreProperties(ignoreUnknown = true)`?**
**О:** `@JsonIgnore` применяется к конкретному полю в коде (ты говоришь: «забудь про это поле»). А `ignoreUnknown = true` применяется к классу (ты говоришь: «забудь про всё, что не описано в этом классе»).

**В: Как сделать так, чтобы при создании POST-запроса поля со значением `null` вообще не фигурировали в теле запроса?**
**О:** Используй `@JsonInclude(JsonInclude.Include.NON_NULL)` над классом или полем. Это делает твой JSON компактным и чистым.

**В: Можно ли использовать Jackson аннотации, если я использую Gson?**
**О:** Нет. Эти аннотации принадлежат библиотеке Jackson. Для Gson используются свои (например, `@SerializedName`). Но в мире REST Assured стандарт де-факто — именно Jackson.

# 📝 Шпаргалка: Logging в REST Assured

**Logging (Логирование)** — это твои «глаза» при прохождении тестов. Без логов ты видишь только результат: `Passed` или `Failed`. С логами ты видишь, *почему* именно всё сломалось: какой заголовок улетел, какой статус пришел и что было в теле ответа.

### 1. Уровни логирования (Что именно мы видим)
В REST Assured можно логировать как весь запрос/ответ целиком, так и их отдельные части. Все методы вызываются внутри блоков `given()` (для запроса) или `then()` (для ответа).

**Основные методы:**
* `.log().all()` — «Золотой стандарт». Логирует всё: URI, параметры, заголовки, тело, куки.
* `.log().headers()` — Только заголовки.
* `.log().body()` — Только тело запроса/ответа.
* `.log().params()` — Только Query и Path параметры.
* `.log().uri()` — Только URL.
* `.log().status()` — Только HTTP статус (например, `200 OK`).

**Пример использования:**
```java
// Логируем всё в запросе и только статус в ответе
given()
    .log().all() // Видим всё, что отправляем
    .get("/users/1")
.then()
    .log().status() // Видим только код ответа
    .statusCode(200);
```

---

### 2. Умное логирование (Conditional Logging) — Уровень Senior
Если ты будешь писать `.log().all()` в каждом тесте, твои отчеты в Jenkins/GitLab превратятся в «мусорку» из тысяч строк успешных запросов, которые никто не читает.

**Главный секрет:** Используй метод `.log().ifValidationFails()`.
Он логирует детали **только если тест упал**. Если тест прошел — консоль остается чистой. Это критически важно для чистоты CI/CD логов.

```java
given()
    .log().ifValidationFails() // Логируем запрос, только если Assertions не прошли
    .get("/users/1")
.then()
    .log().ifError() // Логируем ответ, только если случилась ошибка (4xx, 5xx или Assertion Error)
    .statusCode(200);
```

---

### 3. Глобальное логирование через Specifications
Чтобы не дублировать `.log()...` в каждом тесте, Senior-разработчик выносит настройки логирования в `RequestSpecification` и `ResponseSpecification`.

```java
// Создаем шаблон для всех запросов
RequestSpecification requestSpec = new RequestSpecBuilder()
    .addFilter(new ResponseLoggingFilter(LogReason.IF_ERROR)) // Логируем ответ при ошибке
    .addFilter(new RequestLoggingFilter(LogReason.ALL))       // Лог запроса всегда
    .build();

// Используем в тесте
given()
    .spec(requestSpec)
    .get("/users/1")
.then()
    .statusCode(200);
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Безопасность (Security):** **НИКОГДА** не используй `.log().all()` в публичных логах, если в запросе передаются `Authorization` токены, пароли или персональные данные (PII). Это огромная дыра в безопасности. Если нужно логировать заголовки, лучше логируй их выборочно (`.log().headers()`), исключая `Authorization`.
2.  **Производительность и память:** Логирование гигантских JSON-ответов (на несколько мегабайт) через `.all()` может замедлить выполнение тестов и «раздуть» размер лог-файла до критических размеров, что может привести к падению Jenkins-агента.
3.  **Сложность отладки:** Если ты используешь `LogReason.ALL`, но не видишь тела запроса, проверь, не переопределен ли `ContentType`. Иногда некорректный заголовок заставляет логгер думать, что тело пустое.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему мой `.log().all()` в блоке `then()` не показывает тело запроса?**
**О:** Потому что блок `then()` отвечает только за **Response** (ответ). Чтобы увидеть тело **Request** (запроса), метод логирования должен быть вызван внутри блока `given()`.

**В: Можно ли настроить формат лога (например, сделать JSON красивым/Pretty Print)?**
**О:** REST Assured по умолчанию старается форматировать JSON в консоли. Но если ты используешь кастомные фильтры, ты можешь управлять тем, как именно данные выводятся на экран.

**В: Что лучше: `log().ifError()` или `log().ifValidationFails()`?**
**О:** В 90% случаев — `ifValidationFails()`. Он более "всеядный": он сработает и если пришел статус 500 (ошибка сервера), и если пришел статус 200, но не совпало поле в JSON (ошибка валидации).

**В: Как логировать только определенные заголовки, чтобы не светить токен?**
**О:** Вместо `.all()` используй перечисление конкретных нужных тебе параметров или напиши свой `Filter` (это продвинутый уровень, который мы разберем позже).

# 🛠 Тема: Request & Response Specifications

### Что это такое?
Представь, что ты пишешь письма. Вместо того чтобы каждый раз заново писать адрес, тему письма, свой подпись и стандартное приветствие, ты создаешь **шаблон**. 

В REST Assured `RequestSpecification` и `ResponseSpecification` — это те самые шаблоны. Это объекты, которые позволяют вынести общую конфигурацию запроса (заголовки, базовый URL, аутентификация) и ожидаемые параметры ответа (статус-код, тип контента) в отдельные переиспользуемые компоненты.

**Зачем это нужно?**
1. **DRY (Don't Repeat Yourself):** Не дублируй `baseURI`, `contentType` и `headers` в каждом тесте.
2. **Чистый код:** Тесты становятся короткими и читаемыми (только суть теста, а не настройка окружения).
3. **Легкость поддержки:** Если завтра API потребует новый заголовок `X-API-Version`, ты поменяешь его в одном месте (в спецификации), а не в 100 тестах.

---

### 1. RequestSpecification (Шаблон запроса)
Используется для настройки того, **как** мы отправляем запрос.

**Что туда обычно включают:**
* `baseURI` и `basePath`.
* `contentType` (например, `application/json`).
* Общие заголовки (`headers`), например, `Authorization` или `Accept`.
* Параметры запроса (`queryParam`), которые есть всегда.

**Как создавать (через Builder):**
Для создания удобнее всего использовать `RequestSpecBuilder`.

```java
RequestSpecification requestSpec = new RequestSpecBuilder()
    .setBaseUri("https://api.example.com")
    .setBasePath("/v1")
    .setContentType(ContentType.JSON)
    .addHeader("Authorization", "Bearer my-token")
    .build();
```

---

### 2. ResponseSpecification (Шаблон ответа)
Используется для настройки того, **что** мы ожидаем увидеть в ответе. Это набор правил валидации.

**Что туда включают:**
* `statusCode` (например, всегда ждем `200 OK`).
* `contentType` (проверка, что пришел именно JSON).
    
**Как создавать (через Builder):**
Используем `ResponseSpecBuilder`.

```java
ResponseSpecification responseSpec = new ResponseSpecBuilder()
    .expectStatusCode(200)
    .expectContentType(ContentType.JSON)
    .build();
```

---

### 3. Как использовать в тестах
Теперь твой тест превращается из «простыни» настроек в элегантный сценарий.

```java
@Test
void testGetUser() {
    given()
        .spec(requestSpec) // Применяем шаблон запроса
        .pathParam("id", 1)
    .when()
        .get("/users/{id}")
    .then()
        .spec(responseSpec) // Применяем шаблон ответа
        .body("name", equalTo("John")); // Дополнительная проверка конкретного поля
}
```

---

### 💡 Нюансы от Senior-а (На что важно обратить внимание)

1.  **Принцип "Слоистости":** Не пытайся запихнуть *всё* в одну спецификацию. Сделай одну общую (Base Spec) и несколько специфичных для разных модулей API. В тесте ты можешь комбинировать их: `.spec(baseSpec).spec(userModuleSpec)`.
2.  **Опасность статического состояния:** Избегай настройки `RestAssured.baseURI = "..."` напрямую в методах `@BeforeAll`, если планируешь запускать тесты параллельно. Использование объектов `RequestSpecification` гораздо безопаснее для многопоточности.
3.  **Переопределение (Override):** Если ты в спецификации указал заголовок `Content-Type: JSON`, но в самом тесте написал `.contentType(ContentType.XML)`, REST Assured применит то, что было в тесте (последнее значение побеждает). Это позволяет использовать общую базу, но менять детали под конкретный кейс.
4.  **Спецификации и логирование:** В спецификацию можно сразу добавить `.addFilter(new ResponseLoggingFilter())`, чтобы все запросы в проекте автоматически логировались в консоль без лишнего кода в тестах.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли использовать несколько `RequestSpecification` в одном методе `given()`?**
**О:** Да, ты можешь вызывать `.spec(spec1).spec(spec2)`. Они будут объединяться (мерджиться). Но будь осторожен с конфликтующими параметрами.

**В: В чем разница между использованием `RequestSpecBuilder` и просто настройки `RestAssured.baseURI`?**
**О:** `RestAssured.baseURI` — это глобальная статическая переменная. Если ты изменишь её в одном тесте, она изменится для всех. Это "плохой тон" для параллельного запуска. `RequestSpecification` — это локальный объект, он изолирован и безопасен.

**В: Где лучше всего хранить спецификации?**
**О:** В отдельном классе (например, `SpecFactory` или `ApiSpecs`), чтобы они были доступны всем тестовым классам проекта. Это делает архитектуру чистой.

# 🧩 Тема: Filters (Фильтры) в REST Assured

### Что такое Filter?
Если говорить максимально просто: **Filter — это «перехватчик» (Interceptor)**. Представь, что запрос от твоего теста идет к серверу через таможню. Фильтр — это и есть таможенник. Он может:
1.  **Посмотреть** на содержимое (логирование).
2.  **Добавить** что-то в чемодан (добавление заголовков или токенов).
3.  **Изменить** содержимое (подмена тела запроса для тестов).
4.  **Заблокировать** проход (если запрос не соответствует правилам).

В архитектуре это паттерн **Chain of Responsibility** (Цепочка обязанностей).

---

### 1. Встроенные фильтры (Для быстрой отладки)
REST Assured уже имеет готовые инструменты, которые чаще всего используют новички.

*   `RequestLoggingFilter` и `ResponseLoggingFilter`: позволяют выводить в консоль всё, что происходит с запросом и ответом.
*   **Нюанс:** Часто их путают с методом `.log().all()`. 
    *   `.log().all()` — это «разовая» команда внутри конкретного теста.
    *   `Filter` — это глобальная настройка, которую можно внедрить в конфигурацию всего фреймворка.

**Пример использования:**
```java
RestAssured.given()
    .filter(new RequestLoggingFilter()) // Логирует только запрос
    .filter(new ResponseLoggingFilter()) // Логирует только ответ
    .get("/users/1");
```

---

### 2. Custom Filters (Твой уровень: Senior)
Самая мощная фишка — написание своих фильтров. Это позволяет вынести сквозную логику (cross-cutting concerns) из тестов в инфраструктуру.

**Зачем это нужно?**
*   **Автоматическая авторизация:** Чтобы не писать `.header("Authorization", "Bearer ...")` в каждом тесте, фильтр может сам подставлять актуальный токен.
*   **Сложное логирование для Allure/ReportPortal:** Чтобы в отчет попадал красивый, отформатированный JSON, а не «каша» из консоли.
*   **Performance Monitoring:** Фильтр может замерять время выполнения запроса и кидать ошибку (или писать в лог), если API отвечает дольше 2 секунд.

**Как это работает внутри (Код):**
Чтобы создать фильтр, нужно реализовать интерфейс `Filter`. У него всего один метод: `filter(...)`.

```java
public class MyAuthFilter implements Filter {
    @Override
    able to RequestSpecification requestSpec, ResponseSpecification responseSpec, FilterContext ctx) {
        
        // 1. ПЕРЕХВАТ ЗАПРОСА (Pre-processing)
        // Добавляем заголовок ко всем запросам через этот фильтр
        requestSpec.header("X-Custom-Header", "Senior-Power");

        // 2. ВАЖНЫЙ МОМЕНТ: Передача управления дальше по цепочке
        // ctx.next(...) — это вызов следующего фильтра или самого запроса к серверу.
        // Если НЕ вызвать ctx.next, запрос просто умрет на этом месте и не дойдет до сервера!
        ResponseSpecification response = ctx.next(requestSpec, responseSpec);

        // 3. ПЕРЕХВАТ ОТВЕТА (Post-processing)
        System.out.println("Ответ получен со статусом: " + response.getStatusCode());

        return response;
    }
}
```

---

### 💡 Нюансы и «Подводные камни»

1.  **Порядок имеет значение:** Фильтры работают как слои луковицы. Если ты добавил `FilterA` и потом `FilterB`, то запрос сначала пройдет через `A`, затем через `B`, а ответ вернется сначала через `B`, и только потом через `A`.
2.  **Забытый `ctx.next()`:** Это классическая ошибка. Если ты реализовал свой фильтр и забыл вызвать `ctx.next(requestSpec, responseSpec)`, твой тест будет «висеть» или завершится без выполнения сетевого запроса. Ты просто оборвал цепь.
3.  **Производительность:** Не пихай в фильтры тяжелую логику (например, сложные вычисления или запись в базу данных), так как фильтр срабатывает на **каждый** запрос. Это может замедлить прогон тысяч тестов.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Чем `filter(new RequestLoggingFilter())` лучше, чем `.log().all()`?**
**О:** `.log().all()` нужно писать в каждом тесте вручную. Фильтр можно один раз настроить в `RequestSpecification` на уровне всего проекта, и он будет работать «невидимо» для разработчика тестов. Это чистота кода (DRY — Don't Repeat Yourself).

**В: Можно ли с помощью фильтра подменить тело запроса?**
**О:** Да! В блоке Pre-processing ты можешь вызвать `requestSpec.body(newBody)`, и сервер получит уже измененные данные. Это полезно для тестирования негативных сценариев (например, подмены ID пользователя).

**В: Как логировать только ошибки (4xx, 5xx), не засоряя консоль успешными запросами?**
**О:** В кастомном фильтре в блоке Post-processing сделай проверку: `if (response.getStatusCode() >= 400) { // log error }`. Это лучший способ держать логи чистыми.

# 📑 Шпаргалка: Multi-part/form-data в REST Assured

### 💡 Что это такое? (Простыми словами)
Представь, что ты отправляешь посылку через почту. В одной коробке у тебя лежит письмо (текстовые данные), а сверху — фотография (файл). Чтобы почтальон не запутался, где заканчивается письмо и начинается фото, части посылки разделяют специальными разделителями (boundary).

**`multipart/form-data`** — это формат HTTP-запроса, который позволяет «упаковать» в один запрос разные типы данных: текст (строки, числа) и бинарные данные (файлы, картинки, PDF).

### 🛠 Как это реализовать в REST Assured
Для работы с этим форматом мы используем метод `.multiPart()`.

#### 1. Отправка простого файла
Если тебе нужно просто загрузить файл с диска:
```java
given()
    .multiPart("file", new File("path/to/image.png"))
.when()
    .post("/upload")
.then()
    .statusCode(200);
```

#### 2. Отправка файла + текстовых полей (Самый частый кейс)
Обычно API требует не только файл, но и метаданные (например, имя пользователя или описание). Для этого мы комбинируем `multiPart` для файла и `formParam` для текста.
```java
given()
    .contentType("multipart/form-data") // Рекомендуется указывать явно
    .formParam("description", "Это крутое фото") // Текстовое поле
    .multiPart("file", new File("avatar.jpg"))   // Сам файл
.when()
    .post("/user/update-avatar")
.then()
    .statusCode(200);
```

#### 3. Продвинутый уровень: Отправка через InputStream (Для CI/CD)
В реальных проектах на Jenkins/GitLab Runner у тебя нет доступа к локальным путям вроде `C:\Users\Admin\...`. Поэтому лучше загружать файлы из ресурсов проекта (`src/test/resources`).
```java
given()
    .multiPart("file", getClass().getResourceAsStream("/test-data/sample.pdf"))
.when()
    .post("/upload")
...
```

### ⚠️ Нюансы и "подводные камни" (Senior Tips)

1.  **`formParam` vs `multiPart`**: 
    *   Если ты используешь только `formParam`, REST Assured отправит запрос с `Content-Type: application/x-www-form-urlencoded`. Это работает для простых пар ключ-значение, но **не подходит** для файлов.
    *   Как только появляется файл, тип должен быть `multipart/form-data`.
2.  **Имя параметра**: Всегда проверяй документацию (Swagger). Если в Swagger написано `uploadFile`, то в коде должно быть `.multiPart("uploadFile", ...)`, а не `"file"`. Ошибка в ключе — самая частая причина 400 Bad Request.
3.  **Content-Type для каждой части**: Иногда сервер требует, чтобы ты явно указал тип контента для самого файла (например, `image/jpeg`). В REST Assured это можно сделать так:
    ```java
    .multiPart(new RequestSpecBuilder()
        .addHeader("Content-Type", "image/jpeg")
        .build(), "file", new File("img.jpg"))
    ```
4.  **Boundary (Граница)**: Не пытайся формировать `boundary` вручную в заголовках. REST Assured делает это автоматически. Если ты пропишешь заголовок `Content-Type: multipart/form-data` вручную без указания boundary, сервер может не понять, где части запроса заканчиваются.

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем принципиальная разница между `application/x-www-form-urlencoded` и `multipart/form-data`?**
**О:** Первый формат превращает все данные в одну длинную строку типа `key1=value1&key2=value2` (как в URL). Он не умеет передавать бинарные файлы. Второй формат использует "разделители" (boundary), что позволяет разделять тело запроса на независимые блоки с разными типами данных.

**В: Что делать, если файл очень большой и он не помещается в память?**
**О:** Не стоит читать его целиком в `byte[]`. Используй `InputStream` или передавай объект `File`. REST Assured умеет работать с потоками, что позволяет экономить RAM.

**со: Почему мой запрос возвращает 400/415 ошибку при загрузке файла?**
**О:** Проверь три вещи: 
1. Правильно ли указано имя ключа (параметра).
2. Указан ли правильный `Content-Type` для части запроса.
3. Не пытаешься ли ты отправить файл через `formParam` вместо `multiPart`.

# 🧠 Шпаргалка: API Object Model (AOM)

### Что это такое?
**API Object Model (AOM)** — это паттерн проектирования, при котором логика формирования запросов и управления эндпоинтами выносится из тестовых классов в отдельные специализированные классы (Client-классы). 

Если проводить аналогию с UI-автоматизацией: **AOM — это Page Object для API.**

### Зачем это нужно? (Problem vs Solution)
*   **Проблема:** Если ты пишешь `given().get("/users/1").then().statusCode(200)` прямо в тесте, то при изменении пути `/users` на `/v2/users` тебе придется переписывать сотни тестов. Это **Maintenance Nightmare** (кошмар поддержки).
*   Решение: Ты меняешь путь только в одном месте — в классе-клиенте. Тесты остаются нетронутыми.

### Архитектура уровней (Layers)
Правильный AOM строится на трех уровнях:

1.  **Models (POJOs):** Описание структуры данных (Request/Response тела). Используют Jackson/Gson.
2.  **API Clients (Service Layer):** Классы, которые "знают" про эндпоинты, методы (GET, POST) и параметры. Они возвращают либо `Response`, либо десериализованный объект.
3.  **Tests (Test Layer):** Содержат только бизнес-логику и **Assertions** (проверки). Тест не должен знать, какой именно URL вызывается.

---

### Практический пример

#### 1. Model (POJO)
```java
public class UserRequest {
    private String name;
    private String job;
    // Геттеры, сеттеры, конструкторы
}
```

#### 2. API Client (Сердце паттерна)
*Нюанс: Клиент должен отвечать за **действие**, а не за **проверку**.*

```java
public class UserClient {
    private final RequestSpecification spec;

    public UserClient(RequestSpecification spec) {
        this.spec = spec; // Передаем общую спецификацию (baseURI, headers)
    }

    public Response createUser(UserRequest body) {
        return RestAssured.given()
                .spec(spec)
                .body(body)
                .post("/api/users");
    }

    public UserResponse getUser(int id) {
        return RestAssured.given()
                .spec(spec)
                .pathParam("id", id)
                .get("/api/users/{id}")
                .as(UserResponse.class); // Десериализация прямо в клиенте — это удобно
    }
}
```

#### 3. Test Class (Чистый и читаемый)
```java
public class UserTest {
    private UserClient userClient = new UserClient(RequestSpecBuilder.getSpec());

    @Test
    public void shouldCreateUserSuccessfully() {
        UserRequest payload = new UserRequest("John", "QA");

        userCont.createUser(payload)
                .then()
                .statusCode(201)
                .body("name", equalTo("John"));
    }
}
```

---

### 💡 Senior Nuances (Важные нюансы)

1.  **No Assertions in Clients:** Это самая частая ошибка новичков. Не пиши `.statusCode(200)` внутри метода клиента. Клиент должен возвращать `Response` или объект. Проверки — это ответственность теста. Если ты зашьешь проверку в клиент, ты не сможешь протестировать негативный сценарий (например, 400 Bad Request) тем же методом.
2.  **RequestSpecification Reuse:** Всегда используй `RequestSpecBuilder`. Создай один базовый спек с `baseURI`, `contentType` и `auth`, и передавай его в конструктор всех своих клиентов.
3.  **Single Responsibility:** Один клиент — один микросервис/ресурс (например, `UserClient`, `OrderClient`, `AuthClient`). Не делай один "God Client" на всё API.
4.  **Separation of Concerns:** Если эндпоинт требует сложной подготовки данных (например, генерацию токена), логика получения этого токена должна быть скрыта внутри клиента или вспомогательного хелпера.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Что делать, если один запрос зависит от результата другого? (Например, создать юзера и получить его ID)**
**О:** Это называется *Chaining*. В AOM ты вызываешь метод первого клиента, извлекаешь `id` через `.extract().path("id")` и передаешь этот `id` в метод второго клиента. Тест управляет потоком данных, клиент — только выполнением запроса.

**В: Можно ли возвращать из клиента сразу десериализованный объект вместо Response?**
**О:** Да, если тебе нужно просто проверить поля объекта (Data-driven). Но если ты хочешь проверять статус-коды или заголовки, лучше возвращать `Response`. Идеальный вариант — перегрузка методов: один возвращает `Response` (для гибких проверок), другой — `POJO` (для удобства).

**В: Где хранить базовый URL и другие настройки?**
**О:** Никогда не хардкодь их в клиентах. Используй конфигурационные файлы (`properties`, `yaml`) или системные переменные. Клиент должен получать `baseURI` через `RequestSpecification`.

# 🧠 Шпаргалка: Data-Driven Testing (DDT)

**Data-Driven Testing** — это подход, при котором логика теста отделена от тестовых данных. Вместо того чтобы писать 10 разных тестов для проверки 10 разных имен пользователей, ты пишешь **один** тест и «прогоняешь» его через набор данных (массив, файл, таблицу).

### 🎯 Зачем это нужно?
1.  **Масштабируемость:** Нужно проверить еще 50 кейсов? Просто добавь строки в файл, не трогая код.
2.  **Чистота кода (DRY):** Избавляемся от дублирования логики `given-when-then`.
3.  **Покрытие:** Легко тестировать граничные значения (пустые строки, спецсимволы, слишком длинные тексты), просто подсовывая их в поток данных.

---

### 🛠 Основные стратегии реализации

#### 1. Уровень "Junior": Hardcoded Data (Внутри теста)
Данные лежат прямо в коде (в массиве или списке).
*   **Плюсы:** Быстро написать.
*   **Минусы:** Код раздувается, при изменении данных нужно перекомпилировать проект. **В продакшн-фреймворках так не делают.**

#### 2. Уровень "Middle": Тестовые фреймворки (`@DataProvider` или `@ParameterizedTest`)
Использование встроенных механизмов TestNG или JUnit 5.
*   **TestNG (`@DataProvider`):** Метод возвращает `Object[][]`. Каждый элемент массива — это новый запуск теста.
*   **JUnit 5 (`@ParameterizedTest`):** Более современный подход. Можно использовать `@ValueSource` (простые типы), `@CsvSource` (несколько параметров) или `@MethodSource` (сложные объекты).

#### 3. Уровень "Senior": Внешние источники данных (External Data)
Данные живут в файлах, которые лежат в репозитории вместе с кодом.
*   **JSON/XML:** Идеально для REST Assured, так как структура данных совпадает со струкпитурой API. Используем библиотеку **Jackson** для десериализации файла сразу в POJO-классы.
*   **CSV:** Отлично подходит для плоских табличных данных (например, список логинов и паролей).
*   **Excel/Google Sheets:** Удобно для менеджеров, но **плохо для автоматизатора** (сложно делать Code Review, проблемы с Git, тяжелые библиотеки типа Apache POI).

---

### ⚠️ Нюансы и "Подводные камни" (Senior Insights)

1.  **Изоляция тестов:** Каждый набор данных должен запускаться как **отдельный тест**. Если ты используешь обычный цикл `for` внутри одного `@Test`, и на втором элементе произойдет ошибка — весь тест упадет, а остальные данные не проверятся. Используй механизмы фреймворка, чтобы каждый ряд данных был отдельным кейсом в отчете (Allure).
2.  **Data Cleanup (Очистка):** Если твои данные создают реальные объекты в БД/API (например, `POST /users`), убедись, что после прогона теста данные удаляются. Иначе при повторном запуске DDT упадет из-за дубликатов.
3.  **Сложные объекты:** Не пытайся передавать огромные JSON-строки через `@CsvSource`. Это превратит твой код в нечитаемое месиво. Лучше: путь к файлу $\to$ чтение файла $\to$ десериализация в POJO.
4.  **Версионность данных:** Храни данные в том же репозитории, что и код (JSON/CSV). Это позволит при изменении API сразу обновить и тесты, и их данные в одном коммите.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что лучше: CSV или JSON для DDT в REST Assured?**
**О:** Если ты проверяешь простые поля (только `id` и `name`) — **CSV** проще и легче. Если ты проверяешь сложные вложенные структуры (объекты внутри объектов, списки) — только **JSON**, так как его легко превратить в Java-объекты через Jackson.

**В: Как мне увидеть в Allure, какой именно набор данных вызвал падение?**
**О:** Используй аннотацию `@ParameterizedTest` (в JUnit 5) или передавай параметры в имя теста. В связке с Allure можно использовать `Allure.parameter("username", user)`, чтобы в отчете было четко видно: "Failed for user: admin_123".

**В: Можно ли брать данные из базы данных?**
**О:** Можно, но это считается "тяжелым" подходом. Это делает тесты зависимыми от состояния БД. Используй БД только если тебе нужно проверить интеграцию, а для логики DDT лучше использовать статические файлы в репозитории.

**В: Что делать, если данных слишком много (тысячи строк)?**
**О:** Не загружай всё в память сразу. Используй потоковую обработку (Streaming API) или итераторы, чтобы читать файл построчно, не переполняя Heap Size.

# 🚀 Шпаргалка: Управление окружениями (Environment Management)

### 💡 Суть проблемы
Когда ты пишешь тесты, ты работаешь на `dev-окружении`. Но когда тесты запускаются в пайплайне, они должны уметь «переключаться» на `qa`, `staging` или даже `production`. 

**Главное правило Senior-разработчика:** Код тестов должен быть **immutable** (неизменяемым) относительно окружения. Ты не должен менять ни одной строчки кода или конфигурационного файла в репозитории, чтобы сменить URL. Переключение должно происходить через внешние параметры.

---

### ❌ Как делать НЕЛЬЗЯ (Anti-patterns)
1.  **Hardcode:** Прописывать `baseURI = "https://qa-api.example.com"` прямо в коде. Это смерть гибкости.
2.  **Commit change:** Менять URL в конфиг-файле перед пушем в Git. Это приведет к тому, что тесты на Dev будут пытаться ломиться на Prod.
3.  **Multiple config files in Git:** Хранить `dev.properties`, `qa.properties` и т.д., если они содержат секреты (пароли, токены).

---

### ✅ Как делать ПРАВИЛЬНО (Best Practices)

#### 1. Уровень "Junior": Использование `.properties` файлов
Мы создаем базовый конфиг и подменяем его через системную переменную.

**Структура:**
*   `src/test/resources/config-dev.properties`
*   `src/test/resources/config-qa.properties`

**Пример кода (Java):**
```java
// Читаем системную переменную, которую передали при запуске (например, -Denv=qa)
String env = System.getProperty("env", "dev"); // по умолчанию dev
Properties props = new Properties();
FileInputStream fis = new FileInputStream("src/test/resources/config-" + env + ".properties");
props.load(fis);

// Устанавливаем baseURI из файла
RestAssured.baseURI = props.getProperty("base.url");
```

#### 2. Уровень "Middle": Maven Profiles (Стандарт индустрии)
Вместо того чтобы вручную управлять файлами, мы используем возможности Maven. Мы описываем профили в `pom.xml`.

**Пример `pom.xml`:**
```xml
<profiles>
    <profile>
        <id>dev</id>
        <properties>
            <env>dev</env>
        </properties>
    </profile>
    <profile>
        <id>qa</id>
        <properties>
            <env>qa</env>
        </properties>
    </profile>
</profiles>
```

**Запуск в терминале/CI:**
`mvn test -Pqa` — Maven сам подставит нужный профиль, а ты внутри кода сможешь прочитать `-Denv=qa`.

#### 3. Уровень "Senior": Интеграция с CI/CD и Secrets Management
В реальных проектах URL и ключи авторизации не должны лежать в Git.
*   **Environment Variables:** В Jenkins или GitLab CI мы настраиваем переменные окружения (Environment Variables).
*   **Secrets:** Пароли и токены хранятся в *Jenkins Credentials* или *HashiCT Vault*. Тесты просто забирают их из системы через `System.getenv("API_TOKEN")`.

---

### ⚠️ Нюансы, о которых все забывают

1.  **Смена заголовков (Headers):** Разные окружения могут требовать разные `Content-Type` или специфические `Service-ID`. Твой механизм управления окружением должен уметь подтягивать не только `baseURI`, но и набор заголовков.
2.  **SSL Сертификаты:** На `dev` часто стоят самоподписанные сертификаты (self-signed). При переключении на `prod` важно, чтобы тесты не падали из-за проверки SSL. Используй `RestAssured.useRelaxedHTTPClient() = true` только для локальной разработки, но будь осторожен с этим в глобальном конфиге.
3.  **Base Path:** Иногда `baseURI` одинаковый, а меняется только `basePath` (например, `/v1/` на dev и `/v2/` на qa). Учти это в своей логике.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что делать, если мне нужно протестировать API на разных версиях одновременно?**
**О:** Твой механизм управления окружения должен поддерживать передачу параметра версии через System Property (например, `-Dapi.version=v2`). Это позволит запускать один и тот же набор тестов с разными параметрами пути.

**В: Где хранить секретные токены для авторизации?**
**О:** **Никогда не храни их в репозитории.** Используй переменные окружения (Environment Variables) на уровне CI-сервера или специализированные менеджеры секретов (Vault, AWS Secrets Manager). В коде используй `System.getenv()`.

**В: Как убедиться, что тесты не запустились случайно на Production?**
**О:** Это называется "Safety Guard". В методе `@BeforeSuite` добавь проверку: если `baseURI` содержит слово `prod`, а системная переменная `-Denv` явно не установлена в `prod`, то выполнение должно прерываться с ошибкой (`Assert.fail`).

**В: Что лучше: Maven Profiles или просто System Properties?**
**О:** Для простых проектов достаточно System Properties. Но если проект большой, Maven Profiles позволяют управлять целым набором зависимостей и плагинов под конкретное окружение (например, разные репорты для разных сред), что гораздо мощнее.

# 📊 Тема: Интеграция REST Assured с Allure Report

**Allure Report** — это не просто «зеленые галочки». В автоматизации API его главная ценность — **прозрачность**. Если тест упал ночью, ты должен открыть отчет и увидеть тело запроса (Request Body) и ответ (Response Body) без необходимости перезапускать тест локально.

### 1. Настройка окружения (Setup)
Чтобы всё заработало, тебе нужны две вещи: зависимости в `pom.xml` (или `build.gradle`) и плагин для генерации отчета.

**Maven Dependencies:**
```xml
<!-- Allure JUnit5 (или TestNG) -->
<dependency>
    <groupId>io.qameta.allure</groupId>
    <artifactId>allure-junit5</artifactId>
    <version>2.24.0</version>
    <scope>test</scope>
</dependency>

<!-- Магия для автоматического логирования REST Assured -->
<dependency>
    <groupId>io.qameta.allure</groupId>
    <artifactId>allure-rest-assured</artifactId>
    <version>2.24.0</version>
    <scope>test</scope>
</dependency>
```

### 2. Главный инструмент: `AllureRestAssured` Filter
Самая большая ошибка новичков — вручную писать `log().all()` в каждом тесте. Это засоряет консоль и не попадает в отчет красиво. 

**Senior-подход:** Используй встроенный фильтр. Он автоматически перехватывает запрос и ответ и прикрепляет их к шагу теста в Allure как **Attachments**.

```java
import io.qameta.allure.restassured.AllureRestAssured;

public class BaseTest {
    @BeforeEach
    void setup() {
        RestAssured.given()
            .filter(new AllureRestAssured()) // Вот эта магия!
            .baseUri("https://api.example.com");
    }
}
```
*Что ты получишь:* В отчете появится вкладка "Attachments", где будут лежать Request и Response в читаемом виде.

### 3. Структурирование через `@Step`
Не оставляй тесты «голыми». Если у тебя тест состоит из трех запросов (создать, получить, удалить), каждый запрос должен быть обернут в метод с аннотацией `@Step`.

```java
@Step("Создание пользователя: {userName}")
public String createUser(String userName) {
    return given()
        .body(new User(userName))
        .post("/users")
        .then()
        .extract().path("id").toString();
}
```
*Результат:* В Allure вместо кучи кода ты увидишь красивое дерево шагов: 
`Создание пользователя: Ivan` $\rightarrow$ `Получение данных пользователя` $\rightarrow$ `Удаление пользователя`.

### 4. Организация и метаданные
Используй аннотации, чтобы превратить отчет в документацию:
*   `@Feature("User Management")` — группировка по функционалу.
*   `@Story("Create User via API")` — конкретная пользовательская история.
*   `@Owner("YourName")` — кто отвечает за этот тест.
*   `@TmsLink("ID-123")` — ссылка на тест-кейс в TMS (Test IT, TestRail).

### 💡 Нюансы и Senior Tips (О чем не пишут в туториалах)

1.  **⚠️ Безопасность (Security Risk):** `AllureRestAssured` логирует **ВСЁ**, включая заголовки `Authorization` и `Cookie`. Если в логах отчета окажется живой токен или пароль — это дыра в безопасности.
    *   *Решение:* Настрой кастомный фильтр, который маскирует заголовок `Authorization` (заменяет значение на `***`).
2.  **Размер отчетов:** Если у тебя тысячи тестов и каждый запрос весит по 5 МБ (тяжелые JSON), Allure-отчет станет «неподъемным» и будет тормозить при генерации.
    *   *Решение:* Для очень тяжелых ответов лучше логировать только статус-код, а тело записывать в отдельный файл или использовать логирование только при падении теста (`log().ifValidationFails()`).
3.  **Связка с логами:** Всегда старайся, чтобы `Allure.addAttachment` использовался для добавления контекста, который не входит в HTTP-запрос (например, состояние базы данных перед тестом).

### ❓ FAQ (Частые вопросы)

**В: Почему я вижу тесты в консоли, но в Allure Report пусто?**
**О:** Ты забыл запустить генерацию отчета. После прогона тестов у тебя есть папка `allure-results`. Чтобы увидеть отчет, нужно выполнить команду: `allure serve allure-results`.

**В: Можно ли прикрепить скриншот или файл к API тесту?**
**О:** Да. Хотя в API нет «экрана», ты можешь использовать `Allure.addAttachment("Name", "text/plain", content)`. Это полезно для прикрепления логов из БД или JSON-схемы.

**В: Как сделать так, чтобы логировались только упавшие тесты?**
**О:** В стандартном фильтре `AllureRestAssured` это сделать сложно (он пишет всё). Тебе придется написать свой `Filter`, который будет сохранять тело ответа в переменную и прикреплять его к отчету только внутри метода `@AfterEach`, если статус теста `FAILED`.
