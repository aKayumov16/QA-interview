# 🧠 Тема: Что такое Selenide?

### 🎯 Краткое определение
**Selenide** — это не замена Selenium WebDriver, а мощная **надстройка (wrapper)** над ним. Если Selenium — это «голый» двигатель автомобиля, то Selenide — это современный автомобиль с автопилотом, круиз-контролем и датчиками препятствий. 

Он написан на Java и создан для того, чтобы избавить тебя от написания бесконечного шаблонного кода (boilerplate) и решить главную проблему автоматизации: **нестабильность тестов (flakiness)**.

---

### 🚀 Ключевые отличия и «киллер-фичи»

#### 1. Smart Waits (Умные ожидания) — Самое важное
В обычном Selenium, если элемент появился на странице через 500мс после начала поиска, ты получишь `NoSuchElementException`, если не пропишешь `WebDriverWait`. 
**В Selenide всё встроено:** он сам ждет появления элемента (по умолчанию до 4 секунд). Если элемент не найден — он делает скриншот, сохраняет лог и только потом падает с понятной ошибкой.

#### 2. Fluent API (Fluent Interface)
Код на Selenide читается как английское предложение. Тебе не нужно писать сложные конструкции; ты просто выстраиваешь цепочку действий:
`$(#login-button).shouldBe(visible).click();` — это понятно даже менеджеру.

#### 3. Автоматизация инфраструктуры
*   **Управление драйвером:** Тебе не нужно вручную скачивать `chromedriver.exe`. Selenide сам подтянет нужную версию через WebDriverManager (в современных версиях).
*   **Скриншоты и логи:** При падении теста Selenide автоматически делает скриншот страницы и сохраняет HTML-код страницы. Это бесценно при дебаге на CI/CD.

#### 4. Работа с коллекциями и элементами
Selenide предоставляет удобные обертки `$` (для одного элемента) и `$$` (для списка элементов), которые скрывают внутри себя сложную логику поиска и фильтрации.

---

### ⚠️ Нюансы (то, о чем не пишут в рекламных буклетах)

*   **Это всё еще Selenium:** Под капотом Selenide использует те же самые команды WebDriver. Если у тебя плохие локаторы или «кривой» сайт с кучей JS-ошибок, Selenide не починит их магическим образом. Он лишь поможет тебе лучше *дождаться* этих элементов.
*   **Сложность отладки «магии»:** Иногда из-за того, что Selenide слишком много делает за тебя (авто-ожидания, авто-скроллы), бывает трудно понять, в какой именно момент произошел сбой, если ты не привык смотреть логи.
*   **Потребление ресурсов:** Поскольку Selenide постоянно опрашивает состояние элементов (polling), это создает небольшую дополнительную нагрузку на CPU, но в масштабах автотестов это пренебрежимо мало по сравнению с выигрышем в стабильности.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли использовать Selenide, если я уже знаю Selenium?**
**О:** Да, и это лучший способ. Тебе не нужно учить всё заново, тебе просто нужно понять, как Selenide упрощает привычные операции. Ты можешь даже смешивать их в одном проекте (хотя лучше так не делать).

**В: Selenide — это библиотека или фреймворк?**
**О:** Технически это библиотека-обертка над Selenium WebDriver. Она не диктует тебе, как строить архитектуру тестов (как это делает, например, Cucumber), она лишь предоставляет инструменты для взаимодействия с браузером.

** В: Что будет, если элемент появился на странице, но он перекрыт другим элементом (например, лоадером)?**
**О:** Selenide попытается подождать, пока лоадер исчезнет, если ты используешь правильные проверки (`should(disappear)`). Но если ты просто сделаешь `.click()`, и лоадер всё еще на месте, Selende может выдать `ElementClickInterceptedException`. Это классическая ситуация, которую нужно обрабатывать через явные ожидания исчезновения прелоадера.

**В: Чем `$` отличается от `$$`?**
**О:** `$` возвращает `SelenideElement` (один объект). `$$` возвращает `ElementsCollection` (список объектов). Это база синтаксиса Selenide.

# 🛠 Тема: Подключение (Setup & Configuration)

Подключение Selenide — это не только добавление строчки в `pom.xml`. Это настройка фундамента, на котором будут стоять все твои тесты. Если фундамент кривой, тесты будут «флапать» (мигать) и падать без видимых причин.

### 1. Зависимости (Dependencies)
Selenide — это надстройка над Selenium. Тебе не нужно подключать Selenium отдельно, Selenide подтянет всё необходимое сам.

**Для Maven (`pom.xml`):**
```xml
<dependency>
    <groupId>com.codeborne</groupId>
    <artifactId>selenide</artifactId>
    <version>7.0.0</version> <!-- Всегда используй актуальную версию -->
    <scope>test</scope>
</dependency>
```

**Для Gradle (`build.gradle`):**
```gradle
testImplementation 'com.codeborne:selenide:7.0.0'
```

> **Senior Tip:** Не забывай также подключать JUnit 5 или TestNG. Selenide — это библиотека для работы с браузером, но запускать тесты ему всё равно нужно чем-то.

---

### 2. Глобальная конфигурация (`Configuration` class)
В Selenide есть класс `com.codeborne.selenide.Configuration`. Это «пульт управления» твоим браузером. Все настройки лучше всего делать в одном месте — в базовом классе для тестов.

**Основные параметры, которые нужно знать:**
*   `browser`: какой браузер юзаем (`chrome`, `firefox`, `edge`). По умолчанию — `chrome`.
*   `browserSize`: размер окна (например, `"1920x1080"`). **Важно:** Всегда фиксируй размер, иначе тесты на разных машинах будут вести себя по-разному.
*   `headless`: режим «без головы» (`true`/`false`). Используется в CI/CD (Jenkins/GitLab), чтобы браузер не открывал окно на сервере.
*   `timeout`: глобальное ожидание (Smart Wait). По умолчанию 4 секунды. Если твой проект тяжелый, увеличь до 8-10 сек.
*   `holdBrowserOpen`: если `true`, браузер не закроется после теста. Незаменимо при дебаге.

**Как это выглядит в коде (Best Practice):**

```java
public class BaseTest {
    @BeforeAll
    static void setupConfig() {
        Configuration.browser = "chrome";
        Configuration.browserSize = "1920x1080";
        Configuration.headless = Boolean.parseBoolean(System.getProperty("headless", "false"));
        Configuration.timeout = 8000; // 8 секунд
    }
}
```

---

### 3. Управление драйвером (WebDriver Management)
Забудь про ручное скачивание `chromedriver.exe`. Selenide использует внутри себя **WebDriverManager**. Он сам определяет версию твоего браузера, скачивает нужный драйвер и подкладывает его в путь. Тебе вообще не нужно трогать файлы `.exe` или `.dmg`.

---

### 💡 Нюансы от Senior-а (На что все заваливаются)

1.  **Приоритет System Properties:** Всегда настраивай конфиг так, чтобы параметры можно было переопределить через командную строку.
    *   *Плохо:* `Configuration.browser = "chrome";` (захардкодил и всё).
    *   *Хорошо:* `Configuration.browser = System.getProperty("browser", "chrome");`
    *   Это позволит тебе в Jenkins запустить тест на Firefox одной командой: `-Dbrowser=firefox`.

2.  **Где хранить конфиг?** Никогда не пиши настройки внутри самих тестовых классов. Создай `BaseTest`, от которого будут наследоваться все твои тесты. Это обеспечит единую точку входа.

3.  **Проблема Headless режима:** Иногда элементы (например, выпадающие списки) ведут себя иначе в headless режиме из-за разницы в рендеринге. Если тест проходит локально, но падает в CI — первым делом проверяй `headless`.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Нужно ли отдельно подключать Selenium WebDriver и WebDriverManager?**
**О:** Нет. Selenide включает их в себя «под капотом». Достаточно одной зависимости Selenide.

**В: Что произойдет, если я не укажу `browserSize`?**
**О:** Тест запустится с размером окна по умолчанию (обычно это маленькое окно). Это может привести к тому, что элементы «уедут» под футер или спрячутся за бургер-меню, и тест упадет. Всегда фиксируй размер!

**В: Как быстро переключить тесты на Firefox, не меняя код?**
**О:** Через аргумент запуска JVM: `-Dbrowser=firefox`. Благодаря использованию `System.getProperty` в конфиге, Selenide подхватит это значение автоматически.

**В: Зачем нужен параметр `holdBrowserOpen`?**
**О:** Чтобы браузер не закрывался сразу после завершения теста. Это позволяет тебе «зависнуть» в окне и глазами проверить, что там произошло перед тем, как всё исчезнет.

# 🛠 Selenide Configuration: Control Center

Класс `com.codeborne.selenide.Configuration` — это глобальный пульт управления твоим автотестом. Все настройки в нем **статические**. Это значит, что если ты один раз изменил `Configuration.browser = "firefox"`, то все последующие тесты в рамках этого запуска будут пытаться использовать Firefox.

### 🚀 Основные настройки (Must Have)

| Поле | Тип | Описание | Рекомендация Senior |
| :--- | :--- | :--- | :--- |
| `browser` | `String` | Название браузера (`chrome`, `firefox`, `edge`, `safari`). | Всегда явно задавай его в базовом классе. |
| `browserSize` | `String` | Размер окна (например, `"1920x1080"` или `"maximized"`). | Используй стандартный Full HD, чтобы верстка не «поплыла». |
| `headless` | `boolean` | Запуск браузера без графического интерфейса. | `true` для CI/CD (Jenkins/GitLab), `false` при локальной разработке. |
| `timeout` | `Duration` | Глобальное время ожидания для всех `.should()` методов. | По умолчанию 4 сек. В сложных SPA лучше ставить 6-10 сек. |
| `reportsFolder` | `String` | Путь, куда Selenide сохраняет скриншоты и логи. | Настраивай путь так, чтобы CI мог их забрать как артефакты. |

### 🔍 Продвинутые настройки (Pro Level)

*   **`holdBrowserOpen`**: Если `true`, браузер не закроется после завершения теста.
    *   *Зачем:* Идеально для дебага, когда нужно «залипнуть» в окне и посмотреть, что пошло не так.
*   **`proxyEnabled`**: Включает прокси-сервер Selenide.
    *   *Зачем:* Позволяет перехватывать сетевые запросы (Network Interception), подменять ответы API или проверять заголовка. Это киллер-фича для тестирования фронтенда.
*   **`pageLoadStrategy`**: Определяет, когда браузер считает страницу загруженной (`normal`, `eager`, `none`).
    *   *Нюанс:* `eager` может ускорить тесты, так как не ждет загрузки всех картинок, но может привести к нестабильности (flaky tests).

---

### 💡 Важные нюансы (Senior Tips)

1.  **Где инициализировать?**
    Никогда не пиши `Configuration.browser = "chrome"` внутри каждого теста. Это плохой тон. Создай **BaseTest** класс и делай настройку в методе `@BeforeAll` (JUnit 5). Так конфигурация будет единой для всего тестового набора.

2.  **Приоритет System Properties (Магия CI/CD):**
    Selenide умеет читать настройки из системных переменных. Если ты запустишь тест так:
    `mvn test -Dbrowser=firefox`
    ...то значение из командной строки **перебьет** то, что написано в коде. Это критически важно для того, чтобы один и тот же код работал на твоем Mac (Chrome) и на Linux-сервере (Firefox/Headless).

3.  **Опасность статики:**
    Помни, что `Configuration` — это глобальное состояние. Если ты в одном тесте изменишь `timeout` на 60 секунд, он останется таким для всех остальных тестов в этом запуске. Всегда возвращай настройки к дефолтным или используй чистую среду.

### ❓ FAQ (Частые вопросы)

**В: Можно ли использовать `Configuration` вместе с обычным Selenium WebDriver?**
**О:** Да, но только для тех драйверов, которые создает Selenide. Если ты сам инициализировал `new ChromeDriver()`, настройки из `Configuration` на него не подействуют.

**В: Почему мой `timeout` не работает, если я использую `Thread.sleep()`?**
**О:** Потому что `Thread.sleep()` — это «глупое» ожидание, оно не знает про механизмы Selenide. Всегда используй `.shouldBe(visible, Duration.ofSeconds(10))`. Это «умное» ожидание: оно прервется сразу, как только элемент появится, а не будет ждать все 10 секунд.

**В: Как быстро переключиться на Headless режим без правки кода?**
**О:** Через флаг в Maven/Gradle: `-Dselenide.headless=true`. Selenide автоматически подхватит это свойство.

# 🧠 Шпаргалка: Синтаксис `$` и `$$` в Selenide

В Selenium WebDriver ты привык к длинным конструкциям вроде `driver.findElement(By.cssSelector(...))`. В Selenide мы используем "синтаксический сахар", который делает код чистым и читаемым. Это и есть `$` и `$$`.

### 1. Оператор `$` (Поиск одного элемента)
Это сокращение для `findElement`. Он возвращает объект типа **`SelenideElement`**.

*   **Синтаксис:** `$(selector)`
*   **Что делает:** Ищет на странице **один** (первый попавшийся) элемент, соответствующий селектору.
*   **Главный нюанс (Proxy):** Когда ты пишешь `$(".button")`, Selenide **не идет** на страницу искать эту кнопку прямо сейчас. Он создает "прокси-объект". Реальный поиск начнется только в тот момент, когда ты вызовешь какое-либо действие: `.click()`, `.getText()` или `.shouldBe(...)`.

**Примеры:**
```java
// Поиск по CSS
$(".login-button").click(); 

// Поиск по XPath
$("//div[@id='main']").shouldBe(visible);

// Поэтичный поиск по тексту (очень удобно!)
$(withText("Зарегистрироваться")).click();
```

---

### 2. Оператор `$$` (Поиск коллекции элементов)
Это сокращение для `findElements`. Он возвращает объект типа **`ElementsCollection`**.

*   **Синтаксис:** `$$(selector)`
*   **Что делает:** Ищет **все** элементы на странице, подходящие под селектор, и возвращает их списком.
*   **Главный нюанс (Lazy Loading):** Как и в случае с `$`, поиск элементов происходит "лениво". Коллекция обновится только тогда, когда ты начнешь с ней работать (например, проверять размер или перебирать элементы).

**Приamentul:**
```java
// Получить все ссылки в меню
$$(".nav-menu a").shouldHave(size(5));

// Найти конкретный элемент в списке по условию
$$(".user-row").findBy(text("Ivanov")).click();

// Проверить, что список пуст
$$(".error-messages").shouldBe(empty);
```

---

### 💡 Senior Tips: В чем магия?

1.  **Автоматическое ожидание (Smart Wait):** Это самое важное. Если ты используешь `$(...).click()`, и элемента еще нет на странице, Selenide не выкинет ошибку мгновенно. Он будет "стучаться" в браузер до победного (пока не выйдет таймаут), пока элемент не появится и не станет доступен для клика.
2.  **Устойчивость к StaleElementReferenceException:** Поскольку `$` — это прокси, при каждом действии Selenide может заново перепроверить актуальность элемента на странице. Это спасает от классической ошибки "элемент устарел", когда страница обновилась.
3.  **Цепочки (Chaining):** Ты можешь комбинировать поиск. 
    `$(".container").$(".button")` — это валидно. Мы ищем кнопку внутри контейнера.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Если я напишу `SelenideElement el = $(".non-existent");`, упадет ли тест сразу?**
**О:** Нет. Тест не упадет на этой строке. Ошибка произойдет только тогда, когда ты попытаешься что-то сделать с `el` (например, `el.click()`), потому что именно в этот момент Selenide пойдет в браузер и не найдет элемент.

**В: В чем разница между `$(withText("Login"))` и `$(byText("Login"))`?**
**О:** 
*   `byText` — ищет **точное** совпадение текста.
*   `withText` — ищет **частичное** совпадение (содержит данную строку).

**В: Что быстрее: `$$(".item").get(0)` или `$(".item")`?**
**О:** В данном случае результат одинаков, но `$(".item")` семантически правильнее и чище, если тебе нужен только первый элемент. Используй `$$`, когда тебе нужно работать с множеством элементов (фильтровать, считать, проверять размер).

**В: Можно ли использовать `$` для поиска по XPath?**
**О:** Да, Selenide понимает синтаксис XPath внутри `$()`. Если селектор начинается с `//` или `(`, он автоматически поймет, что это XPath. Но лучше придерживаться CSS для скорости и чистоты кода.

# 🎯 Cheat Sheet: Селекторы в Selenide

Селекторы в Selenide — это способы указать программе, какой именно элемент на странице нам нужен. В Selenide мы работаем через два главных инструмента:
*   `$("")` — поиск **одного** элемента (`SelenideElement`).
*   `$$("")` — поиск **коллекции** элементов (`ElementsCollection`).

### 1. CSS Selectors (Твой основной инструмент)
CSS — это стандарт. Он быстрый, читаемый и поддерживается всеми браузерами. В 90% случаев используй именно его.

*   **По тегу:** `$("button")` — найдет первую кнопку.
*   **По ID:** `$("#login-button")` — самый надежный способ (если ID уникален).
*   **По классу:** `$(".submit-btn")` — ищет элемент с этим классом.
*   **По атрибуту:** `$("input[name='email']")` — поиск по любому атрибуту.
*   **Вложенность:** `$(".container .title")` — найдет `.title` внутри `.container`.
*   **Дочерние элементы:** `$("div > p")` — только прямые потомки (p должен быть сразу внутри div).

### 2. XPath (Тяжелая артиллерия)
XPath мощнее CSS, но медленнее и сложнее в чтении. Используй его **только** когда нужно "подняться" вверх по дереву DOM или когда CSS бессилен.

*   **Поиск по тексту (абсолютный):** `//button[text()='Save']` — найдет кнопку с точным текстом.
*   **По частичному тексту:** `//div[contains(text(), 'Welcome')]` — найдет div, где есть слово "Welcome".
*   **Движение вверх (Ancestors):** `//span[@id='child'].../..` — переход к родителю.
*   **Поиск по атрибуту:** `//*[@data-testid='submit-btn']`.

### 3. Selenide-specific Selectors (Удобство и читаемость)
Selenide предоставляет "синтаксический сахар", который делает код похожим на человеческую речь. Это киллер-фича.

*   `byText("Login")` — поиск элемента, текст которого **точно** совпадает с "Login".
    *   *Пример:* `$(byText("Login")).click();`
*   `withText("Welcome")` — поиск элемента, который **содержит** строку "Welcome".
    *   *Пример:* `$(withText("Welcome")).shouldBe(visible);`
*   `byAttribute("name", "user")` — альтернативный способ поиска по атрибуту.

### 4. Связи и фильтрация (Advanced)
Когда элементов много, мы не просто ищем их, а фильтруем.

*   **Поиск внутри элемента:** `$(".menu").$(byText("Settings"))` — сначала находим меню, а потом в нем ищем настройки.
*   **Фильтрация коллекций (`$$`):**
    *   `.filterBy(visible)` — оставить только видимые элементы.
    *   `.findBy(text("Admin"))` — найти один элемент в списке по тексту.
    *   `.filterElements(enabled)` — оставить только активные кнопки/инпуты.

---

### 💡 Senior Tips (Нюансы)

1.  **Забудь про Absolute XPath:** Никогда не используй пути типа `/html/body/div[1]/div[2]/form/input`. Если разработчик добавит один `div` в шапку сайта — твой тест умрет.
2.  **Data-атрибуты — это святое:** Если у тебя есть доступ к разработчикам, проси их добавлять `data-testid="login-button"`. Это самый стабильный селектор, который не зависит от стилей (CSS) и текста (i18n).
3.  **Lazy Loading (Ленивость):** Selenide не ищет элемент в момент написания кода `$(...)`. Он начнет искать его только тогда, когда ты вызовешь действие: `.click()`, `.getText()` или `.shouldBe()`. Это экономит ресурсы.
4.  **Избегай поиска по классам оформления:** Не используй селекторы типа `.btn-red-large-margin`. Завтра дизайнер сделает кнопку синей, и твой тест упадет, хотя функционал не изменился.

### ❓ FAQ (Частые вопросы)

**В: Что лучше использовать: CSS или XPath?**
**О:** Всегда CSS. Если нужно найти родителя элемента или искать по частичному тексту (хотя в Selenide есть `withText`), тогда бери XPath.

**В: Почему мой селектор `byText` не находит элемент, хотя текст на экране есть?**
**О:** Проверь лишние пробелы или переносы строк в HTML. `byText` требует 100% совпадения. Если есть сомнения — используй `withText`.

**В: Можно ли комбинировать селекторы?**
**О:** Да! Это мощная практика. Например: `$$(".user-row").findBy(text("Ivan")).$(".delete-icon").click();` (Найти строку пользователя Ивана, найти в ней иконку удаления и нажать).

**В: Что делать, если элемент находится внутри Iframe?**
**О:** Селектор сам не "прыгнет" внутрь iframe. Тебе нужно сначала переключить контекст: `switchTo().frame("my-iframe");`, а уже потом использовать селекторы.

# 📝 Шпаргалка: Поиск элементов по тексту в Selenide

Когда мы тестируем UI, текст — это самый понятный и "человечный" способ найти элемент. Но дьявол кроется в деталях (пробелы, регистр, переносы строк).

### 1. Основные инструменты

В Selenide есть два главных "кита" для поиска по тексту:

*   **`byText("Текст")`** — **Точное совпадение**. Элемент должен содержать *только* этот текст и ничего больше. Если в кнопке написано `"Войти "` (с пробелом на конце), поиск `byText("Войти")` **не сработает**.
*   **`withText("Текст")`** — **Частичное совпадение**. Ищет подстроку. Если в элементе написано `"Добро пожаловать, Иван!"`, то `withText("Иван")` успешно его найдет.

### 2. Продвинутый поиск: Регулярные выражения (`matchText`)

Если текст динамический (например, "Заказ №12345"), обычные методы не помогут. Тут на сцену выходит `matchText`.

*   **`matchText("регулярка")`** — позволяет использовать мощь Regex.
*   *Пример:* `$(".order-id").shouldHave(text(Pattern.compile("Заказ №\\d+")))` или просто использование строки, если Selenide понимает паттерн.

### 3. Комбинированный подход (CSS + Текст)

Senior-подход — это не искать "просто по тексту" во всем DOM, а ограничивать область поиска. Сначала находим контейнер через быстрый CSS-селектор, а внутри него ищем текст.

```java
// Плохо: ищем по всему документу (медленно и рискованно)
$(byText("Удалить")).click(); 

// Хорошо: ограничиваем область поиска конкретной таблицей или формой
$(".user-card").$(withText("Иван")).shouldBe(visible);
```

### 4. Нюансы и "подводные камни" (Senior Tips) ⚠️

1.  **Проблема лишних пробелов:** Это классика. Разработчики часто добавляют переносы строк или лишние пробелы для красоты кода. 
    *   *Решение:* Всегда предпочитай `withText` вместо `byText`, если тебе не критична стопроцентная точность до символа. Или используй Regex, чтобы игнорировать `\s+`.
2.  **Регистрозависимость:** Selenide чувствителен к регистру. `"Login"` и `"login"` — это разные вещи для `byText`.
3.  **Скрытый текст:** Текст может быть в DOM, но элемент скрыт (`display: none`). Всегда добавляй `.shouldBe(visible)`, чтобы убедиться, что пользователь его видит.
4.  **Текст внутри дочерних элементов:** Если ты ищешь `byText("Кнопка")`, Selenide найдет элемент, даже если текст обернут в `<span>` внутри `<button>`. Он проверяет текстовое содержимое всего узла.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `$(byText("OK"))` и `$(withText("OK"))`, если на кнопке написано "OK"?**
**О:** Если на кнопке ровно "OK" без пробелов — оба сработают. Но если там "OK " (с пробелом), то `byText` упадет, а `withText` — нет.

**В: Что делать, если я не знаю точного текста, но знаю, что он начинается на "Error"?**
**О:** Используй `withText("Error")`. Он найдет и "Error 404", и "Error: Connection lost".

**LA: Как найти элемент, который содержит текст, но при этом игнорируя регистр?**
**О:** Самый надежный способ — использовать `matchText` с флагом `(?i)` (case-insensitive):
`$(byTagName("p")).shouldHave(text(Pattern.compile("(?i)привет")))` — найдет и "ПРИВЕТ", и "привет".

**В: Можно ли искать текст через CSS селектор напрямую, например `$(".class:contains('text')"`?**
**О:** Стандартный CSS не поддерживает `:contains`. Selenide реализует это через свои внутренние механизмы (XPath под капотом), поэтому используй встроенные `byText` или `withText` — это чище и понятнее.

# 🔍 Тема: Поиск по атрибутам (Search by Attributes)

В Selenide поиск по атрибутам — это база. Мы редко ищем элементы просто по тегу `div`. Нам нужны уникальные признаки: `id`, `name`, `class`, а в идеале — специальные тестовые атрибуты вроде `data-testid`.

### 1. Основной инструмент: CSS Селекторы
В Selenide (как и в Selenium) самый эффективный способ поиска по атрибуту — использование синтаксиса CSS. Это быстрее и читабельнее, чем XPath.

*   **Точное совпадение:** `[attribute='value']`
    *   `$("[name='login']")` — найдет элемент, у которого `name` строго равен `login`.
*   **Поиск по началу строки (Prefix):** `[attribute^='value']`
    *   `$("[id^='user_']")` — полезно, если ID динамический (например, `user_123`, `user_456`).
*   **Поиск по окончанию строки (Suffix):** `[attribute$='value']`
    *   `$("[class$='_submit']")` — найдет элемент, класс которого заканчивается на `_submit`.
*   **Поиск по подстроке (Contains):** `[attribute*='value']`
    *   `$("[href*='dashboard']")` — найдет любую ссылку, где в `href` есть слово `dashboard`.

### 2. Проверка атрибутов (Assertions)
Найти элемент — это полдела. Senior-подход подразумевает проверку того, что атрибут находится в правильном состоянии. Для этого используем метод `.shouldHave()`.

*   **Проверка значения конкретного атрибута:**
    ```java
    // Проверяем, что у поля ввода тип именно 'password'
    $("#password-field").shouldHave(attribute("type", "password"));
    ```
*   **Работа с CSS-классами (Специальный метод):**
    Не нужно парсить строку классов вручную. Selenide дает удобный метод:
    ```java
    // Проверяет, что у элемента ЕСТЬ класс 'active', даже если их там десять
    $(".menu-item").shouldHave(cssClass("active")); 

    // Проверяет, что у элемента НЕТ класса 'disabled'
    $(".button").shouldNotHave(cssClass("disabled"));
    ```

### 3. Извлечение значения атрибута
Иногда нам нужно не просто проверить, а забрать значение (например, чтобы сравнить его с переменной из БД).
```java
String link = $("a.profile-link").attr("href"); // Возвращает строку со значением href
```

---

### 💡 Нюансы и Pro-tips (Senior Level)

1.  **Золотой стандарт — `data-testid`:** Если ты имеешь влияние на разработку, всегда проси внедрить атрибуты `data-testid` или `data-cy`. Они не меняются при редизайне (в отличие от классов) и не зависят от логики (в отличие от `id`).
    *   *Плохо:* `$("[class='btn btn-primary active']")` (хрупко).
    *   *Хорошо:* `$("[data-testid='submit-button']")` (стабильно).

2.  **Осторожно с динамическими ID:** Если видишь в DOM `id="ext-gen-1024"`, никогда не используй его целиком. Такие ID генерируются фреймворками (ExtJS, React) при каждой загрузке страницы. Используй только поиск по части строки (`^=` или `*=`).

3.  **Множественные классы:** Когда ты пишешь `$(".btn.active")`, Selenide ищет элемент, у которого есть **оба** этих класса. Это мощный инструмент для уточнения поиска.

4.  **Атрибут существует, но он пустой:** Помни, что `should(exist)` проверит наличие атрибута в DOM, а `shouldHave(attribute("name", ""))` проверит именно пустое значение.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что лучше использовать: XPath или CSS селекторы для поиска по атрибутам?**
**О:** Всегда CSS, если это возможно. Он короче, быстрее работает в браузере и его легче читать. XPath используй только тогда, когда нужно подняться вверх к родителю (в Selenide есть `..`, но CSS этого не умеет).

**В: Как проверить, что атрибут вообще присутствует у элемента, даже если мы не знаем его значение?**
**О:** Используй `should(exist)`. Но если нужно именно наличие атрибута в теге, можно использовать проверку через `attribute`:
`element.should(have(attribute("name")))` (проверяет, что атрибут `name` просто есть в HTML).

**В: Что делать, если класс элемента меняется динамически (например, при наведении)?**
**О:** Не пытайся поймать "состояние" через поиск. Используй `shouldHave(cssClass("..."))`. Selenside будет перепроверять элемент в течение таймаута, пока класс не появится.

**В: Можно ли найти элемент, у которого нет определенного атрибута?**
**О:** Да, через `shouldNotHave(attribute("name"))`. Это полезно для проверки того, что поле очищено или ошибка пропала.

# 🧠 Шпаргалка: Связи между элементами (Element Relationships)

Когда ты работаешь с современными фреймворками (React, Angular, Vue), ты часто сталкиваешься с тем, что у нужного тебе элемента **нет ID** или он **динамический** (меняется при каждой перезагрузке). В этом случае мы используем стратегию **"Якоря"**: находим стабильный элемент (якорь) и от него "отсчитываем" путь к целевому элементу.

### 1. Поиск Вниз (Descendants) — Самое простое
Это поиск дочерних элементов внутри найденного. Мы ограничили область поиска, чтобы не искать по всей странице.

*   **Метод:** `element.find(selector)` или использование `within()`.
*   **CSS селекторы:** 
    *   `div > span` — прямой потомок (только один уровень вниз).
    *   `div span` — любой потомок (на любом уровне вложенности).
*   **Пример:** Найти кнопку внутри конкретной карточки товара.
```java
// Находим карточку по тексту, а внутри неё ищем кнопку "Купить"
$(".product-card").findBy(text("iPhone 15")).find(".buy-button").click();

// Или через scope (область видимости)
within($(".product-card")).find(".buy-button").click();
```

### 2. Поиск Вверх (Ancestors / Parents) — "Поднимаемся по дереву"
Иногда нужно найти контейнер, в котором лежит элемент. Это критично для удаления строк в таблицах или работы с модальными окнами.

*   **Нюанс:** CSS **не умеет** искать вверх (нет селектора "родитель"). Здесь нам на помощь приходит **XPath**.
*   **Методы/Селекторы:**
    *   `parent()` — ближайший родитель.
    *   `ancestor::div` — любой предок (дедушка, прадедушка и т.д.), который является `div`.
*   **Пример:** Найти обертку (row) для конкретной ячейки с текстом "Error".
```java
// Находим ячейку с текстом и поднимаемся к родительской строке таблицы
$x("//td[text()='Error']/ancestor::tr").shouldHave(cssClass("error-row"));

// Или через Selenide parent() (ближайший родитель)
$$("td").findBy(text("Error")).parent().shouldHave(cssClass("active"));
```

### 3. Поиск Вбокво (Siblings) — "Соседи"
Поиск элементов, которые находятся на одном уровне иерархии с твоим "якорем".

*   **CSS селекторы (только вперед):**
    *   `+` (Adjacent Sibling) — следующий за ним элемент (ровно один).
            *   Пример: `label + input` (инпут, который идет сразу после label).
    *   `~` (General Sibling) — все последующие элементы на том же уровне.
*   **XPath (в обе стороны):**
    *   `following-sibling::` — все "соседи" ниже по коду.
    *   `preceding-sibling::` — все "соседи" выше по коду.
*   **Пример:** Найти поле ввода, которое находится рядом с конкретной иконкой.
```java
// XPath: найти input, который является соседом (после) иконки
$x("//i[@class='icon-user']/following-sibling::input").setValue("admin");
```

### 💡 Senior Tips (Нюансы)

1.  **Золотое правило:** Если можешь использовать **CSS** — используй CSS. Он быстрее и читаемее. Используй **XPath** только тогда, когда нужно двигаться **вверх** к родителю или искать по сложному тексту.
2.  **Избегай "Абсолютных путей":** Никогда не пиши `/html/body/div[1]/div[2]/span`. Это "хрупкий" код. Любое изменение в верстке убьет тест. Используй связи через понятные якоря.
3.  **Принцип Scope (Область видимости):** Всегда старайся максимально сузить поиск. Вместо `$$("button").click()` используй `$(".form-container").find("button").click()`. Это защитит тебя от случайного клика по кнопке в футере или хедере.

---

### ❓ FAQ (Частые вопросы)

**В: Можно ли в CSS найти родителя?**
**О:** Нет, стандарт CSS Selectors не поддерживает восходящие связи. Если нужно найти родителя — используй XPath (`/..` или `ancestor::`).

**В: В чем разница между `find()` и `within()`?**
**О:** `element.find(".child")` ищет внутри элемента. `within(".container")` — это способ переключить контекст для всех последующих команд в блоке кода, чтобы не писать `.container` перед каждым элементом. Это делает код чище (Fluent Interface).

**В: Что делать, если элементов-соседей слишком много и `following-sibling` находит лишнее?**
**О:** Добавляй уточнение. Не просто `following-sibling::input`, а `following-sibling::input[type='text']`. Всегда фильтруй результат.

# 🧠 Шпаргалка: Фильтрация элементов в Selenide

Когда мы работаем с коллекциями (`$$`), нам редко нужна вся куча элементов. Чаще всего нам нужно найти "тот самый" элемент среди списка. В Selenide есть три основных способа сделать это: **`filterBy`**, **`findBy`** и **`filter`**.

### 1. `filterBy(Condition... conditions)`
Этот метод используется для **сужения коллекции**. Он не возвращает один элемент, он возвращает **новую коллекцию** (`ElementsCollection`), в которой остались только те элементы, которые соответствуют условиям.

*   **Когда использовать:** Когда тебе нужно проверить группу элементов (например, "все видимые кнопки" или "все элементы с классом `active`").
*   **Пример:**
```java
// Оставляем в коллекции только видимые элементы
$$(".menu-item").filterBy(visible).shouldHave(size(3));

// Оставляем только те, у которых есть текст "Delete"
$$(".btn").filterBy(text("Delete")).shouldBe(enabled);
```

### 2. `findBy(Condition... conditions)`
Этот метод — «хирург». Он ищет **один конкретный элемент** внутри коллекции и возвращает его как `SelenideElement`.

*   **Когда использовать:** Когда тебе нужно совершить действие (кликнуть, ввести текст) с конкретным элементом из списка.
*   **Пример:**
```java
// Находим в списке товаров именно тот, который содержит "iPhone"
$$(".product-card").findBy(text("iPhone")).click();

// Находим элемент, у которого атрибут 'data-id' равен '123'
$$(".row").findBy(attribute("data-id", "123")).shouldBe(visible);
```

### 3. `filter(Predicate predicate)` — Уровень Pro
Это самый мощный инструмент. Он позволяет использовать стандартные Java Lambda-выражения. Если стандартных `Condition` (типа `visible`, `text`) не хватает, ты можешь написать свою логику.

*   **Когда использовать:** Для сложной логики, которую невозможно описать через `Condition` (например, математические сравнения, работа с регулярными выражениями или парсинг текста).
*   **Пример:**
```java
// Фильтруем элементы по цене: оставляем только те, где цена > 1000
$$(".price-tag")
    .filter(el -> Double.parseDouble(el.getText().replace(" руб.", "")) > 1000)
    .shouldHave(sizeGreaterThan(0));

// Фильтруем по сложному регулярному выражению через Java
$$(".user-name").filter(el -> el.getText().matches("^[A-Z].*")); // Начинаются с заглавной
```

### 💡 Senior Tips (Нюансы)

1.  **Разница в возвращаемом типе:** Это самая частая ошибка новичков.
    *   `filterBy` $\rightarrow$ возвращает `ElementsCollection` (список). Ты не можешь вызвать `.click()` сразу, если не уверен, что элемент один. Тебе нужно либо проверить размер, либо добавить `.first()`.
    *   `findBy` $\rightarrow$ возвращает `SelenideElement` (один объект). Здесь можно сразу вызывать `.click()`.

2.  **Порядок имеет значение:** Сначала применяй самые "грубые" фильтры (например, `visible`), чтобы уменьшить размер коллекции, а затем уже сложные `filter(predicate)`. Это ускорит выполнение теста и сделает его стабильнее.

3.  **Опасность `filter(predicate)`:** Помни, что внутри лямбды ты обращаешься к методу `.getText()`. Selenide начнет выполнять поиск и ждать появления текста. Если элементов очень много, это может замедлить тест. Старайся использовать `Condition` везде, где это возможно, так как они оптимизированы под Smart Waits.

4.  **Цепочки (Chaining):** Ты можешь комбинировать методы:
    `$$(".items").filterBy(visible).findBy(text("Target")).click();`
    *(Сначала убрали невидимые $\rightarrow$ нашли нужный по тексту $\rightarrow$ кликнули).*

**О:** `find(Condition)` — это метод класса `SelenideElement` (ищет внутри одного элемента, например, дочерний). `findBy(Condition)` — это метод `ElementsCollection` (ищет среди элементов коллекции).

**В: Как отфильтровать элементы по наличию определенного CSS-класса?**
**О:** Используй `filterBy(cssClass("active"))` или `filterBy(attribute("class", "active"))`.

# 🧠 Тема: Механизм Implicit vs Explicit Waits в контексте Selenide

В автоматизации самая большая проблема — это **асинхронность**. Страница загружается, элементы появляются не сразу, скрипты отрабатывают с задержкой. Если ты попытаешься кликнуть на элемент, которого еще нет, тест упадет. 

Есть три способа решения, и Selenide делает это лучше всех.

### 1. Implicit Wait (Неявное ожидание) — «Глобальный тупняк»
Это настройка уровня WebDriver (Selenium). Ты говоришь драйверу: *«Если не нашел элемент сразу — подожди 10 секунд, перепроверяй DOM постоянно»*.

*   **Как работает:** Применяется ко **всем** поискам элементов в тесте.
*   **Минус №1:** Он проверяет только **наличие элемента в DOM**. Элемент может быть в коде, но скрыт (`display: none`) или перекрыт другим слоем. Тест попытается на него кликнуть и упадет с `ElementClickInterceptedException`.
*   **Минус №2 (Смертельный):** Если смешать Implicit Wait из Selenium и Explicit Wait из Selenide, можно получить непредсказуемое время ожидания (например, вместо 10 секунд тест будет ждать 20 или вообще зависнет).
*   **Вердикт:** В Selenide **забудь про него**. Мы его не используем.

### lem 2. Explicit Wait (Явное ожидание) — «Точечный контроль»
Это когда ты четко говоришь: *«Жди, пока этот конкретный элемент станет видимым/кликабельным/содержимым текста»*. В Selenium это делается через `WebDriverWait`.

*   **Как работает:** Ты создаешь условие и ждешь его выполнения для конкретного объекта.
*   **Плюс:** Очень гибко. Можно ждать появления кнопки, исчезновения лоадера или изменения цвета текста.

### 3. Selenide Smart Waits — «Магия Selenide» (То, что тебе нужно)
Selenide по сути является надстройкой над Explicit Waits, которая автоматизирует всю грязную работу. В Selenide нет понятия "wait" как отдельного объекта, есть понятие **Assertion (Утверждение)**.

Когда ты пишешь `$(...).shouldBe(visible)`, происходит следующее:
1.  **Polling (Опрос):** Selenide начинает многократно (каждые ~500мс) проверять условие `visible`.
2.  **Smart Retry:** Если элемент не найден или не в том состоянии, он не падает сразу, а делает ретрай до тех пор, пока не выйдет глобальный таймаут (`Configuration.timeout`).
3.  **Condition-based:** Ты проверяешь не просто наличие, а **состояние** (текст, атрибут, видимость, кликабельность).

**Ключевая разница в коде:**
*   *Selenium:* `new WebDriverWait(driver, 10).until(ExpectedConditions.visibilityOf(element))` — многословный и тяжелый код.
*   *Selenide:* `$(selector).shouldBe(visible)` — лаконично, понятно и надежно.

### 🛠 Нюансы от Senior-а (На чем все валятся)

1.  **Глобальный таймаут:** По умолчанию в Selenide он **4 секунды**. Если твой фронтенд тяжелый и кнопка появляется через 5 секунд — тест упадет. Всегда проверяй `Configuration.timeout`.
2.  **Кастомный таймаут для конкретного случая:** Не меняй глобальный таймаут ради одного долгого запроса! Используй перегрузку:
    `$(selector).shouldBe(visible, Duration.ofSeconds(15));` — это правильный путь.
3.  **Смертный грех — `Thread.sleep()`:** Никогда не используй его. Он останавливает выполнение потока на фиксированное время. Если ты поставил `sleep(5000)`, а элемент появился через 1 сек, ты впустую потерял 4 секунды. Selenide с `shouldBe` закончит проверку ровно тогда, когда элемент появится.
4.  **Разница между `exist` и `visible`:** 
    *   `exist` — элемент есть в HTML-коде.
    *   `visible` — элемент есть в коде **и** его видит пользователь (у него есть размеры и он не скрыт). Для тестов почти всегда нужно использовать `visible`.

# 🧠 Шпаргалка: Методы `should()` и `shouldNot()`

Это **сердце Selenide**. Если ты не используешь эти методы, ты используешь Selenium, а не Selenide. Вся магия "умных ожиданий" (Smart Waits) сосредоточена именно здесь.

### 1. Суть концепции
В обычном Selenium мы пишем `WebDriverWait`. В Selenide мы пишем `should()`. 
Метод `should()` не просто проверяет условие в текущую миллисекунду. Он **запускает цикл ожидания**:
1. Проверяет условие.
2. Если условие **не** выполнено, он ждет короткое время (polling interval) и пробует снова.
3. Это продолжается до тех пор, пока:
   - Условие не станет истинным (**Success!**).
   - Не выйдет глобальный таймаут (по умолчанию 4 секунды) (**Error!**).

### 2. Два типа проверок
*   **`should(...)`**: Ожидает, что состояние элемента **станет** соответствующим условию.
*   **`shouldNot(...)`**: Ожидает, что состояние элемента **перестанет** быть соответствующим условию (или что элемент исчезнет).

### 3. Синтаксис и вариации
В Selenide есть "синтаксический сахар", который делает код читаемым:
*   `element.should(Condition.visible)` — базовый вариант.

*   `element.shouldBe(Condition.visible)` — использование `be` для состояний (state).
*   `element.shouldHave(Condition.text("Hello"))` — использование `have` для наличия свойств (property/attribute).

**Это одно и то же**, но `shouldBe` и `shouldHave` — это просто удобные обертки, чтобы твой код читался как английское предложение.

### 4. Основные условия (`Condition`)
Чтобы `should` работал, ему нужно передать объект класса `Condition`. Вот топ самых нужных:
*   **Видимость/Наличие:** `visible`, `hidden`, `exist`, `NotExist`.
*   **Текст:** `text("substring")` (содержит), `exactText("full text")` (строгое соответствие), `matchText("regex")` (регулярка).
*   **Состояние:** `enabled` (активен), `disabled` (заблокирован), `clickable` (можно кликнуть).
*   **Атрибуты/CSS:** `cssClass("active")`, `attribute("name", "value")`.

### 5. Нюансы и Senior-tips (Важно!)

⚠️ **Нюанс №1: `exist` vs `visible`**
Это классика.
*   `exist`: Элемент есть в DOM-дереве (даже если он скрыт через `display: none`).
*   `visible`: Элемент есть в DOM **и** пользователь его видит (он не перекрыт, имеет высоту/ширику > 0).
*   *Ошибка новичка:* Проверять `exist`, когда нужно кликнуть. Клик по невидимому элементу упадет.

⚠️ **Нюанс №2: Переопределение таймаута**
Если ты знаешь, что тяжелый отчет грузится 10 секунд, не меняй глобальный конфиг. Сделай локально:
```java
element.shouldBe(visible, Duration.ofSeconds(10));
```

⚠️ **Нюанс №3: Опасность `shouldNot`**
Будь осторожен с `shouldNot(exist)`. Если элемент *уже* исчез из DOM (например, страница обновилась), тест пройдет мгновенно. Это может скрыть баг, когда элемент вообще не успел появиться.

⚠️ **Нюанс №4: Цепочки проверок (Chaining)**
Ты можешь строить цепочки. Selenide будет ждать выполнения каждого звена по очереди:
```java
element.shouldBe(visible).shouldHave(text("Success")); 
// Сначала ждем видимости, и только потом проверяем текст.
```

### ❓ FAQ (Часто задаваемые вопросы)

**В: Чем `should()` лучше, чем обычный `if (element.isDisplayed())`?**
**О:** `if` — это мгновенная проверка. Если элемент появляется через 0.5 сек после загрузки страницы, `if` вернет `false` и тест упадет. `should()` будет ждать этот полсекунды и успешно продолжит тест.

**В: Что произойдет, если условие не выполнится по таймауту?**
**О:** Вылетит `ElementShould` (или `ElementNotFound`) Exception. Но Selenide выдаст шикарную ошибку, где покажет: какой элемент искали, какое условие ожидали и что на самом деле было в этот момент (скриншот и текущий текст/атрибуты).

**В: Можно ли использовать `shouldNot` вместе с `Duration`?**
**О:** Да. Например, `element.shouldNot(exist, Duration.ofSeconds(5))` — мы ждем, пока элемент исчезнет из DOM, и даем на это 5 секунд. Это идеально для проверки удаления данных или завершения процесса загрузки.

**В: Что использовать: `shouldBe(visible)` или `should(visible)`?**
**О:** С точки зрения производительности — разницы нет. С точки зрения чистоты кода (Clean Code) — используй `shouldBe` для состояний и `shouldHave` для атрибутов/текста. Это делает тесты "самодокументированными".

# 🧠 Шпаргалка: Основные условия (Condition) в Selenide

В Selenide `Condition` — это сердце системы **Smart Waits**. Когда ты пишешь `.shouldBe(visible)`, Selenide не просто один раз проверяет элемент, а запускает цикл (polling), который многократно проверяет условие в течение таймаута (по умолчанию 4 секунды).

Все условия делятся на несколько логических групп.

### 1. Видимость и наличие (Visibility & Existence)
Это база. Самая частая причина падения тестов — путаница между "есть в коде" и "вижу на экране".

*   `exist` — элемент присутствует в DOM-дереве (в HTML-коде страницы). Его может быть не видно, но он есть.
*   `NotExist` — элемента нет в DOM-дереве.
*   `visible` — элемент **есть** в DOM и он **виден** пользователю (не скрыт через `display: none`, `visibility: hidden` или нулевой размер).
*   `hidden` — элемент либо отсутствует в DOM, либо скрыт от глаз пользователя.

> **Senior Note:** Никогда не используй `exist` там, где нужно нажать на кнопку. Если кнопка есть в коде, но перекрыта другим слоем (invisible), клик упадет. Всегда стремись к `visible`.

### 2. Работа с текстом (Text Content)
Работа с содержимым элементов.

*   `text("abc")` — **Partial match**. Проверяет, что в элементе *содержится* подстрока "abc". (Например: "Hello abc" — пройдет).
*   `exactText("abc")` — **Exact match**. Текст должен быть идентичен "abc", без лишних пробелов и символов.

*   `matchText("regex")` — **Regex match**. Позволяет использовать регулярные выражения. Идеально для динамических ID или текстов, где меняется только одна цифра.

### 3. Состояние элемента (State)
Проверка интерактивности.

*   `enabled` — элемент активен (можно кликнуть, можно печатать).
*   `disabled` — элемент заблокирован (например, кнопка "Отправить", пока не заполнены поля).
*   `clickable` — элемент виден и доступен для взаимодействия (комбинация видимости и активности).

### 4. Атрибуты и CSS-классы (Attributes & CSS)
Проверка внешнего вида и технических свойств.

*   `cssClass("active")` — проверяет, что у элемента есть класс `active`. Важно: он проверяет *наличие* класса, а не полное совпадение всей строки классов.
*   `attribute("name", "value")` — проверяет конкретный атрибут. Например, `attribute("type", "submit")`.
*   `value("some_text")` — специфичная проверка для полей ввода (`input`). Проверяет текущее значение внутри поля.

### 🛠 Продвинутые фишки (Pro Tips)

**1. Комбинирование условий:**
Ты можешь передавать несколько условий в один метод. Тест пройдет, только если **все** условия соблюдены.
```java
// Элемент должен быть и видимым, и активным
$("button#submit").shouldBe(visible, enabled);
```

**2. Кастомный таймаут для конкретного условия:**
Если ты знаешь, что тяжелый отчет грузится долго, не меняй глобальный конфиг. Измени таймаут только для этого шага.
```java
import static java.time.Duration.*;

// Ждем появления элемента целых 15 секунд вместо стандартных 4
$(".slow-loader").shouldBe(visible, Duration.ofSeconds(15));
```

**3. Отрицание (`shouldNot`):**
Всегда используй `shouldNot`, если хочешь убедиться, что элемент исчез. Это работает быстрее и чище, чем проверка на `hidden`.
```java
$(".spinner").shouldNot(exist); 
```

### ❓ FAQ (Частые вопросы)

**В: В чем разница между `text("user")` и `exactText("user")`?**
**О:** `text` — это поиск подстроки (contains). Если в элементе написано "Welcome, user!", то `text("user")` вернет `true`, а `exactText("user")` — `false`.

**В: Что лучше использовать для проверки исчезновения модального окна: `shouldNot(exist)` или `shouldBe(hidden)`?**
**О:** Если окно удаляется из DOM (как в React/Angular), используй `shouldNot(exist)`. Если окно просто получает CSS `display: none`, используй `shouldBe(hidden)`. Если не уверен — `hidden` покрывает оба случая, но `exist` более точен для архитектуры приложения.

**В: Почему мой тест падает с `ElementNotFound`, хотя я вижу элемент на экране?**
**О:** Скорее всего, элемент перекрыт другим элементом (например, лоадером или всплывающим уведомлением). Проверь условие `clickable` или убедись, что лоадер исчез через `shouldNot(visible)`.

**В: Можно ли использовать `Condition` с регулярными выражениями?**
**О:** Да, через метод `matchText("регулярка")`. Это спасение, когда текст элемента генерируется динамически (например, `"Order #12345"`).

# 📑 Шпаргалка: Condition.visible

### 🎯 Суть
`Condition.visible` — это одно из самых используемых условий в Selenide. Оно проверяет, что элемент не просто «есть в коде», а **виден пользователю на экране**. 

Когда ты пишешь `element.shouldBe(visible)`, Selenide не просто делает проверку один раз. Он включает **Smart Wait** (умное ожидание): Selenary будет опрашивать браузер до тех пор, пока условие не выполнится или не выйдет время таймаута (по умолчанию 4 секунды).

---

### 🛠 Основной синтаксис

```java
// Ждем, пока элемент станет видимым (ожидание включено)
$(".success-message").shouldBe(visible);

// Проверяем, что элемент НЕ виден (может быть в DOM, но скрыт через CSS)
$(".error-popup").shouldNotBe(visible);

// Проверяем, что элемента вообще нет в DOM (полное отсутствие)
$(".loading-spinner").shouldNot(exist); 
```

---

### 🧠 Глубокое понимание: В чем разница между `exist` и `visible`?

Это главный вопрос на собеседованиях. Запомни:

1.  **`exist` (Существование):** Элемент присутствует в HTML-коде страницы (DOM). Ему может быть плевать, какого он размера, прозрачный он или перекрыт другим слоем. Если тег `<div id="test"></div>` есть в коде — он `exists`.
2.  **`visible` (Видимость):** Элемент **существует** И при этом **виден глазу**. 

**Элемент считается НЕ видимым, если:**
*   У него `display: none;` в CSS.
*   У него `visibility: hidden;` в CSS.
*   Его ширина или высота равны **0**.
*   Он перекрыт другим элементом (в некоторых случаях, зависит от реализации драйвера).
*   Его прозрачность (`opacity`) равна `0`.

---

### ⚠️ Нюансы и «подводные камни» (Senior Level)

1.  **Ловушка "Пустого элемента":**
    Если у тебя есть пустой контейнер `<div></div>`, который занимает 0x0 пикселей, `shouldBe(visible)` упадет с ошибкой, хотя элемент в DOM присутствует. Для таких случаев используй `should(exist)`.

2.    **Перекрытие (Overlay):**
    Иногда элемент *виден* (он есть на экране), но его нельзя кликнуть, потому что сверху висит прозрачный лоадер или модальное окно. `visible` пройдет успешно, но следующий шаг `.click()` упадет с `ElementClickInterceptedException`. 
    *Совет:* Если видишь такую проблему, проверяй не только `visible`, но и отсутствие лоадера (`shouldNot(be(visible))`).

3.  **Анимации:**
    Если элемент плавно выезжает (fade-in или slide-in), Selenide может поймать момент, когда элемент уже «существует», но еще не достиг финальной позиции. Благодаря встроенным ожиданиям, `shouldBe(visible)` обычно справляется с этим, но при очень быстрых анимациях иногда полезно добавить небольшую проверку на стабильность.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что будет, если я использую `shouldNotBe(visible)` для элемента, которого вообще нет в DOM?**
**О:** Тест **пройдет успешно**. Если элемента нет в DOM, то он технически не может быть видимым. Это безопасная проверка.

**В: В чем разница между `shouldNot(exist)` и `shouldNotBe(visible)`?**
**О:** 
*   `shouldNot(exist)` — проверяет, что тега вообще нет в HTML.
*   `shouldNotBe(visible)` — проверяет, что тег **есть**, но он скрыт (например, через `display: none`).

**В: Можно ли использовать `visible` вместе с кастомным таймаутом?**
**О:** Да, это лучший способ работы с тяжелыми элементами:
`$(".slow-element").shouldBe(visible, Duration.ofSeconds(10));`

# 🧠 Шпаргалка: Selenide Conditions — Наличие (`exist` и `NotExist`)

В Selenide всё крутится вокруг **Smart Waits** (умных ожиданий). Когда мы используем `Condition`, Selenide не просто один раз проверяет условие, а запускает цикл: *«Проверяю... нет? Подожду еще 500мс... Проверяю...»* до тех пор, пока условие не выполнится или не выйдет таймаут (по умолчанию 4 сек).

### 1. Суть условий
В теме «Наличие» у нас есть два главных игрока:
*   **`Condition.exist`**: Элемент **присутствует в DOM-дереве** (в HTML-коде страницы).
*   **`Condition.NotExist`**: Элемента **нет в DOM-дереве**.

### 2. Главный нюанс (Senior Level) ⚠️
Самая частая ошибка новичков — путать **наличие** (`exist`) и **видимость** (`visible`).

*   **`exist`** — это про HTML-код. Если элемент есть в коде, но у него прописано в CSS `display: none` или `opacity: 0`, то `Condition.exist` вернет **true**. Элемент «существует», но его не видно глазу.
*   **`visible`** — это про глаз пользователя. Элемент должен быть в DOM **И** иметь размеры (ширина/высота > 0), **И** не быть скрытым через CSS.

> **Запоминалка:** `exist` — это «он есть в списке», а `visible` — это «я его вижу на экране».

### 3. Синтаксис и примеры

#### Проверка присутствия:
```java
// Ждем, пока элемент появится в HTML-коде
$(".success-message").should(Condition.exist);

// Можно использовать сокращенную форму (синоним)
$(".success-message").shouldBe(Condition.exist);
```

#### Проверка отсутствия:
Используется, когда мы ждем, что какой-то элемент (например, лоадер или попап) полностью удалится из DOM после завершения операции.
```java
// Ждем, пока элемент исчезнет из HTML-кода совсем
$(".loading-spinner").should(Condition.NotExist);

// Или через отрицание (но NotExist — чище и понятнее)
$(".loading-spinner").shouldNot(Condition.exist); 
```

### 4. Когда что использовать? (Best Practices)

| Сценарий | Что использовать | Почему? |
| :--- | :--- | :--- |
| Проверка, что кнопка появилась и на неё можно нажать | `shouldBe(visible)` | Тебе важно не просто наличие в коде, а возможность взаимодействия. |
| Ожидание исчезновения индикатора загрузки (Spinner) | `should(NotExist)` | Спиннер часто просто скрывается (`display: none`), но если он реально удаляется из DOM — `NotExist` надежнее. |
| Проверка наличия скрытого input (например, для загрузки файла) | `should(exist)` | Его не видно, но он есть в коде, и это важно для работы теста. |

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Что произойдет, если я напишу `$(".item").should(Condition.exist)`, а элемент на странице есть, но он перекрыт другим прозрачным слоем?**
**О:** Тест **пройдет**. Условию `exist` всё равно на перекрытие (z-index) или прозрачность. Он проверяет только наличие тега в дереве HTML. Если тебе нужно проверить кликабельность — используй `visible` или `interactable`.

**В: В чем разница между `.shouldNot(Condition.exist)` и `.should(Condition.NotExist)`?**
**О:** С точки зрения результата — разницы нет. Это синтаксический сахар. Однако `NotExist` читается более естественно («должен не существовать»), что делает код чище.

**В: Может ли `exist` быть true, если элемент имеет размер 0x0 пикселей?**
**О:** Да. Если тег `<div class="box"></div>` есть в коде, но у него нет контента и заданных размеров, `exist` вернет **true**. Для проверки того, что элемент «занимает место», используй `visible`.

**В: Как проверить, что список элементов пуст?**
**О:** Если ты работаешь с коллекцией `$$`, то проверка на отсутствие элементов — это `$$(".item").shouldBe(CollectionCondition.empty)`. Но если мы говорим об одном элементе, то `should(Condition.NotExist)` — твой выбор.

# 🧠 Шпаргалка: Selenide Conditions — Состояние (State)

**Суть темы:** В Selenide `Condition` — это набор правил, по которым мы проверяем элемент. Когда мы используем `.should(Condition.xxx)`, Selenide не просто один раз смотрит на элемент, а **ждет** (smart wait), пока состояние элемента не придет в соответствие с условием.

В этой части мы рассматриваем только **состояние** (status/state) — то, как элемент «чувствует себя» в DOM-дереве и на экране, без учета его текста или значений.

### 1. Наличие в DOM: `exist` vs `visible`
Это база, на которой сыплются новички.

*   **`exist`**: Элемент просто присутствует в HTML-коде страницы. Он может быть скрыт, иметь нулевой размер или прозрачность 0%, но он **есть** в дереве.
*   **`not(exist)`**: Элемента нет в DOM-дереве вообще.
*   **`visible`**: Самое частое. Элемент не только есть в DOM, но и его можно увидеть глазом (он имеет размеры, не перекрыт `display: none` или `visibility: hidden`).
*   **`hidden`**: Элемент либо отсутствует в DOM, либо он есть, но скрыт от пользователя.

> **Senior Tip:** Никогда не используй `exist`, если хочешь проверить, что пользователь увидел кнопку. Используй `visible`. `exist` полезен только для проверки фоновых элементов или мета-тегов.

---

### 2. Интерактивность: `enabled` и `clickable`
Проверяем, можно ли с элементом взаимодействовать.

*   **`enabled`**: Элемент активен. На него можно нажать, в него можно ввести текст (например, кнопка «Отправить» стала активной после заполнения формы).
*   **`disabled`**: Элемент «заблокирован» (атрибут `disabled` в HTML). Клик по нему ничего не даст.
*   **`clickable`**: Продвинутое условие. Элемент должен быть **visible** И **enabled**. Если элемент перекрыт другим прозрачным слоем, `clickable` может упасть — и это правильно.

---

### 3. Стили и атрибуты: `cssClass` и `attribute`
Проверка «внешнего вида» через состояние свойств.

*   **`cssClass("active")`**: Проверяет, есть ли у элемента в списке классов конкретное слово (например, класс `active` или `error`). 
    *   *Нюанс:* Он не удаляет другие классы, он просто проверяет наличие указанного.
*   **`attribute("name", "value")`**: Проверяет состояние атрибута. Например, `$(...).should(attribute("type", "submit"))`.

---

### 🛠 Код-пример (Cheat Sheet Syntax)

```java
// 1. Проверка видимости и наличия
$("#login-button").shouldBe(visible);      // Виден пользователю
$("#hidden-element").shouldNot(exist);    // Его нет в коде страницы
$("#loading-spinner").shouldBe(hidden);   // Он есть, но его не видно (например, opacity: 0)

// 2. Проверка доступности
$("#submit-btn").shouldBe(enabled);       // Кнопка активна
$("#reset-btn").shouldBe(disabled);       // Кнопка серая/неактивная

// 3. Проверка стилей (CSS)
$(".menu-item").shouldHave(cssClass("active")); // Проверяем, что пункт меню выбран
```

### ❓ FAQ: Часто задаваемые вопросы

**В: В чем разница между `shouldNot(exist)` и `shouldBe(hidden)`?**
**О:** Это критический момент. `shouldNot(exist)` проверяет, что элемента **вообще нет в HTML**. `shouldBe(hidden)` допускает, что элемент **есть в HTML**, но он скрыт (например, через CSS `display: none`). Если ты тестируешь удаление пользователя из списка — используй `not(exist)`. Если ты тестируешь закрытие модального окна — используй `hidden`.

**В: Почему мой тест падает на `visible`, хотя я вижу элемент на экране?**
**О:** Скорее всего, элемент перекрыт другим элементом (например, невидимым прелоадером или всплывающим уведомлением). Selenide видит, что физически «нажать» нельзя. Проверь через `clickable`.

**В: Можно ли использовать `not()` с любым условием?**
**О:** Да! Это мощный инструмент. `shouldNot(enabled)` — отличный способ проверить, что кнопка заблокирована до ввода данных.

**В: Что лучше: `shouldBe(visible)` или `shouldBe(exist)` для кнопок?**
**О:** Всегда `visible`. Тест должен имитировать поведение реального пользователя. Пользователь не может взаимодействовать с тем, чего не видит.

# 📜 Шпаргалка: Selenide Conditions — Работа с текстом

В Selenide `Condition` — это не просто проверка, это **умное ожидание**. Когда ты пишешь `.should(text("..."))`, Selenide не просто один раз смотрит на элемент, а ждет (до таймаута), пока текст не появится.

### 🛠 Основные методы

| Метод | Что делает | Описание |
| :--- | :--- | :--- |
| **`text("substring")`** | Проверка на вхождение | Ищет подстроку внутри текста элемента. Самый используемый метод. |
| **`exactText("string")`** | Строгое соответствие | Текст элемента должен *полностью* совпадать с указанным (символ в символ). |
| **`matchText("regex")`** | Регулярные выражения | Позволяет проверять сложные паттерны (email, даты, динамические ID) через RegEx. |

---

### 💡 Нюансы и "Senior" советы

#### 1. `text()` vs `exactText()` — Главная ловушка
*   `text("Login")` вернет `true`, если на кнопке написано `"Login"`, `"Click to Login"` или `"Login Now"`.
*   `exactText("Login")` верят `true` **только** если в элементе нет ничего, кроме `"Login"`. 
*   **Нюанс:** Если в тексте есть невидимые символы (перенос строки `\n`, лишние пробелы или табуляция), `exactText` упадет. В 90% случаев для простых проверок лучше использовать `text()`.

#### 2. Проблема лишних пробелов (Whitespace)
Браузер часто рендерит текст с лишними пробелами или переносами строк, которые не видны глазу в HTML, но есть в DOM.
*   **Совет:** Если `exactText` ведет себя нестабильно, используй `matchText` с регуляркой, которая игнорирует пробелы, либо используй `text()`.

#### 3. Регистрозависимость (Case Sensitivity)
Все стандартные методы `text()` и `exactText()` в Selenide **чувствительны к регистру**.
*   `text("login")` **не найдет** `"Login"`.
*   **Как обойти:** Используй `matchText` с флагом `(?i)` (case-insensitive): 
    `$.should(matchText("(?i)login"))` — это сработает для "LOGIN", "login", "Login".

#### 4. Проверка на пустоту
*   Если нужно проверить, что элемента вообще нет или он пустой:
    *   `.shouldBe(empty)` — элемент есть, но текста внутри нет.
    *   `.shouldNot(exist)` — элемента вообще нет в DOM.

---

### 💻 Примеры кода

```java
// 1. Проверка подстроки (самый безопасный вариант)
$(".submit-button").shouldHave(text("Submit")); 

// 2. Строгая проверка (опасно, если есть лишние пробелы)
$(".header-title").shouldHave(exactText("Welcome to My App"));

// 3. Регулярное выражение (для динамических данных, например, цены)
// Проверяем, что текст начинается на "Price: " и далее идут цифры
$(".price-tag").shouldHave(matchText("Price: \\d+"));

// 4. Игнорирование регистра через Regex
$(".user-name").shouldHave(matchText("(?i)admin")); // найдет "ADMIN", "Admin", "admin"

// 5. Проверка коллекции (все элементы списка должны содержать текст)
$$(".menu-item").shouldHave(sizeGreaterThan(0)).forEach(item -> 
    item.shouldHave(text("Menu"))
);
```

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему мой `exactText` падает, хотя визуально текст совпадает?**
**О:** Скорее всего, в HTML внутри тега есть невидимый символ переноса строки (`\n`) или лишний пробел в конце. Попробуй заменить на `text()` или используй `matchText`.

**В: Можно ли использовать `text()` вместе с `$$` (коллекциями)?**
**О:** Да. Ты можешь проверить, что *каждый* элемент коллекции содержит текст: `$$(".row").shouldHave(size(3)).forEach(el -> el.shouldHave(text("Active")));`.

**В: Как проверить, что текста НЕТ в элементе?**
**О:** Используй отрицание: `.shouldNot(have(text("Error")))` или более коротко `.shouldNotHave(text("Error"))`.

**В: Что использовать для проверки Email-адреса?**
**О:** Только `matchText`. Пример: `$.shouldHave(matchText("[a-z0-9._%+-]+@[a-z0-9.-]+\\.[a-z]{2,6}"))`.

# 🧠 Шпаргалка: Condition — Атрибуты (Attributes)

В Selenide `Condition` — это то, **что** мы ожидаем увидеть у элемента. Работа с атрибутами — это проверка состояния элемента через его HTML-свойства (`id`, `class`, `name`, `disabled`, `src`, `href` и т.д.).

### 1. Основные методы проверки

#### `attribute(String name, String value)`
Самый базовый метод. Проверяет, что у атрибута `name` есть конкретное значение `value`.
*   **Пример:** `element.$(".btn").shouldHave(attribute("type", "submit"));`
*   **Нюанс:** Selenide ждет появления этого значения. Если атрибут есть, но значение другое — будет таймаут.

#### `cssClass(String className)`
Специализированный и «умный» метод для проверки CSS-классов. 
*   **Пример:** `element.$(".item").shouldHave(cssClass("active"));`
*   **Почему это важно (Senior Tip):** В отличие от обычного `attribute("class", "active")`, метод `cssClass` умеет работать с многоклассовыми элементами. Если у тебя `<div class="btn active primary">`, то `cssClass("active")` пройдет, а `attribute("class", "class_name")` — нет, так как он ищет полное совпадение всей строки.

#### `attributeMatches(String name, String regex)`
Когда значение атрибута динамическое (например, `id="user_12345"`), используй регулярные выражения.
*   **Пример:** `element.$("#user-id").shouldHave(attributeMatches("id", "user_\\d+"));`
*   **Нюанс:** Это спасает от написания костылей с подстроками, когда ID меняется при каждой перезагрузке страницы.

---

### 2. Инверсия: `shouldNot`
Любой атрибут можно проверить на **отсутствие**. Это критически важно для проверки того, что кнопка стала неактивной или исчез какой-то флаг.
*   **Пример:** `element.$(".loader").shouldNotHave(attribute("visible", "true"));`
*   **Пример с классом:** `element.$(".menu").shouldNotHave(cssClass("open"));`

---

### 3. Тонкие моменты (Nuances)

1.  **Проверка существования без значения:** Если тебе нужно просто проверить, что атрибут *есть* в теге (неважно, какой там текст), Selenide не имеет метода `attributeExists`. Но ты можешь использовать `attributeMatches` с регуляркой `.*` или проверять через `cssClass` для классов.
2.  **Регистрозависимость:** Помни, что значения атрибутов в HTML чувствительны к регистру. `attribute("type", "Submit")` упадет, если в коде написано `submit`.
3.  **Ожидание (Smart Wait):** Все эти методы — это не просто проверки `assert`, это **ожидания**. Selenide будет переспрашивать DOM-дерево до победного (или до таймаута), пока атрибут не примет нужный вид. Это избавляет от `Thread.sleep()`.

---

### ❓ FAQ: Часто задаваемые вопросы

**В: В чем разница между `shouldHave(cssClass("btn"))` и `shouldHave(attribute("class", "btn"))`?**
**О:** Если у элемента класс `"btn active"`, то первый вариант **пройдет** (он ищет вхождение), а второй — **упадет** (он требует полного совпадения всей строки атрибута). Всегда используй `cssClass` для классов.

**В: Что делать, если атрибут содержит пробелы или лишние символы?**
**О:** Используй `attributeMatches`. Регулярные выражения позволяют игнорировать мусор вокруг нужного тебе значения.

**В: Может ли `shouldNotHave(attribute("disabled", "true"))` упасть, если атрибута `disabled` вообще нет в HTML?**
**О:** Нет, тест пройдет успешно. Если атрибута нет, то и условие «не равен true» выполняется. Это важный момент для проверки очистки состояний.

**В: Как проверить, что атрибут `src` у картинки содержит определенный домен?**
**О:** Используй Regex: `img.$(".logo").shouldHave(attributeMatches("src", ".*google.com/.*"));`

# ⏱️ Тема: Кастомные таймауты в Selenide

### В чем суть?
В Selenium WebDriver мы привыкли к `WebDriverWait` и сложным конструкциям. В Selenide всё проще. По умолчанию у Selenine есть **Global Timeout** (обычно 4 секунды). Это время, которое Selenide будет «опрашивать» (polling) страницу, проверяя, выполнилось ли условие (`Condition`).

**Важный нюанс:** Selenide не "спит" всё это время. Он проверяет элемент каждые 100–500 мс. Если элемент появился через 1 секунду, тест пойдет дальше сразу, не дожидаясь конца таймаута. Это называется **Smart Wait**.

---

### 1. Глобальный таймаут (Global Timeout)
Если ты понимаешь, что всё твое приложение работает медленно (например, тяжелый энтерпрайз), можно увеличить время ожидания для всех проверок сразу.

```java
import com.codeborne.selenide.Configuration;

// Устанавливаем глобальное ожидание в 8 секунд для всех тестов
Configuration.timeout = 8000; // в миллисекундах
// Или более читаемо через Duration (рекомендую)
Configuration.timeout = Duration.ofSeconds(8).toMillis(); 
```
*   **Когда использовать:** Когда сетевые задержки или медленная работа сервера — это норма для всей системы.
*   **Риск:** Слишком большой глобальный таймаут сделает ваши тесты "тупыми" — если что-то реально сломалось, тест будет висеть 30 секунд вместо 4, замедляя CI/CD.

---

### 2. Локальный таймаут (Local Timeout)
Это самый правильный подход. Если у тебя есть один конкретный тяжелый элемент (например, загрузка отчета или генерация PDF), ты расширяешь ожидание **только для него**.

```java
import static com.code-borne.selenide.Selenide.*;
import static com.codeborne.selenide.Condition.*;
import java.time.Duration;

// Ожидаем появления элемента до 15 секунд
$(".heavy-report-status").shouldBe(visible, Duration.ofSeconds(15));

// Проверяем, что текст изменился на "Ready" в течение 20 секунд
$("#status").shouldHave(exactText("Ready"), Duration.ofSeconds(20));
```
*   **Когда использовать:** Для специфических долгих процессов (загрузка файлов, фоновые задачи, ожидание анимации).

---

### 3. Золотые правила Senior-разработчика (Nuances)

1.  **Никогда не используй `Thread.sleep()`!**
    Это главный грех. `Thread.sleep(5000)` остановит выполнение теста на 5 секунд в любом случае. Selenide же продолжит тест сразу, как только условие выполнится. `Thread.sleep` — это "мертвое" ожидание, которое раздувает время прогона тестов.
    
2.  **Не увеличивай глобальный таймаут ради одного элемента.**
    Если ты выставишь `Configuration.timeout = 30000`, и у тебя упадет тест из-за ошибки в коде, ты будешь ждать полминуты перед тем, как увидеть ошибку. Всегда используй `Duration` локально.

3.  **Таймаут для отрицательных проверок (`shouldNot`).**
    Когда ты пишешь `element.shouldNot(visible, Duration.ofSeconds(10))`, Selenide будет ждать **все 10 секунд**, пока элемент не исчезнет. Будь осторожен с этим, чтобы не замедлять тесты намеренно.

4.  **Используй `Duration` вместо чисел.**
    Писать `Duration.ofSeconds(5)` гораздо понятнее и безопаснее, чем `5000`. Это исключает ошибки в количестве нулей.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что произойдет, если элемент появился на 11-й секунде при локальном таймауте в 10 секунд?**
**О:** Тест упадет с ошибкой `ElementShould` (или `ElementShouldNot`). Selenide зафиксирует, что время вышло, а условие так и не достигло нужного состояния.

**В: Можно ли комбинировать глобальный и локальный таймаут?**
**О:** Да. Локальный таймаут всегда **перекрывает** (overrides) глобальный. Если глобально 4с, а локально ты указал 15с — будет работать 15с.

**В: Как проверить, что элемент исчез быстро?**
**О:** Используй `shouldNot(exist)` или `shouldNotBe(visible)`. По умолчанию он использует глобальный таймаут. Если нужно убедиться, что он исчез мгновенно, можно даже уменьшить таймаут локально: `.shouldNot(exist, Duration.ofMillis(500))`.

**В: В чем разница между `should` и `shouldBe` в контексте времени?**
**О:** Разницы нет. Оба метода принимают `Duration`. `should` — это универсальный метод, а `shouldBe` и `shouldHave` — это просто удобные обертки для конкретных типов проверок (состояние vs значение).

# 🛠 Шпаргалка: Базовые действия в Selenide

Базовые действия — это фундамент. В Selenide они максимально упрощены по сравнению с чистым Selenium, так как почти каждый метод уже включает в себя **Smart Wait** (ожидание появления элемента и его кликабельности).

### 1. Работа с текстовыми полями (Inputs)
Это самая частая операция. Здесь важно понимать разницу между тремя методами:

*   **`setValue(String text)`** — **Твой основной инструмент.** 
    *   *Что делает:* Сначала очищает поле (`clear()`), а затем вводит текст.
    *   *Когда использовать:* В 99% случаев при заполнении форм.
*   **`append(String text)`** — Дозапись.
    *   *Что делает:* Не удаляет старый текст, а просто дописывает новый в конец текущего значения.
    *   *Когда использовать:* Если нужно дополнить уже введенный текст (например, в поиске или при работе с динамическими полями).
*   **`clear()`** — Очистка.
    *   *Что делает:* Полностью стирает всё содержимое поля.

> **Senior Note:** Никогда не используй `sendKeys()` из Selenium напрямую, если можно использовать `setValue()`. `setValue()` в Selenide более предсказуем, так как он гарантирует, что поле будет очищено перед вводом, предотвращая "склеивание" старого текста с новым.

---

### 2. Клики (Clicks)
*   **`click()`** — Стандартный клик.
    *   *Нюанс:* Selenide сначала ждет, пока элемент станет `visible` и `enabled`. Если элемент перекрыт другим элементом (например, лоадером или попапом), Selenide будет ждать его исчезновения в течение таймаута.
*   **`doubleClick()`** — Двойной клик.
    *   *Когда использовать:* Для работы с интерфейсами, где элементы открываются по двойному нажатию (например, работа с файловыми структурами).

> **Senior Note:** Если `click()` падает с ошибкой `ElementClickInterceptedException` (элемент перекрыт чем-то другим), и ты уверен, что это не баг, а особенность анимации, которую нельзя побороть ожиданием — можно использовать JavaScript клик. Но в Selenide лучше сначала попробовать настроить ожидания.

---

### 3. Работа с клавиатурой (Keys)
Иногда просто ввести текст мало, нужно имитировать нажатие системных клавиш. Для этого используется класс `Keys`.

*   **Пример использования:**
    ```java
    // Нажать Enter после ввода текста
    `$("#search").setValue("Selenide").pressEnter(); 
    // Или через Keys
    `$("#search").sendKeys(Keys.ENTER);
    ```
*   **Популярные клавиши:** `Keys.ENTER`, `Keys.TAB`, `Keys.ESCAPE`, `Keys.BACK_SPACE`, `Keys.CONTROL + "a"`.

---

### 4. Чекбоксы и Радиокнопки (Checkboxes & Radio Buttons)
Здесь нет специальных методов вроде `check()`. Мы используем стандартный `click()`.

*   **Логика проверки:**
    ```java
    // Проверка, что галочка поставлена
    `$("#checkbox").shouldBe(selected); 
    
    // Проверка, что галочка снята
    `$("#checkbox").shouldNotBe(selected);
    ```

---

### 💡 Нюансы (Pro Tips)

1.  **Проблема "залипшего" текста:** Если ты используешь `append()`, всегда проверяй, в каком состоянии было поле до этого. Если тест упал на середине, в поле может остаться мусор от предыдущего прогона.
2.  **Ожидание завершения действия:** После `click()` или `setValue()` действие часто инициирует асинхронный запрос к серверу (AJAX). Помни: само действие выполнится быстро, но *результат* может появиться с задержкой. Всегда следуй действию проверкой: `.shouldBe(visible)`.
3.  **Интерактивность:** Если элемент `visible` (виден), это не значит, что на него можно кликнуть (он может быть перекрыт прозрачным слоем или быть `disabled`). Selenide сам ждет `clickable`, но если ты пишешь кастомную логику — помни об этом.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `setValue("abc")` и `append("abc")`, если в поле уже написано "123"?**
**О:** `setValue` сделает поле "abc", а `append` сделает его "123abc".

**В: Почему мой `click()` не срабатывает, хотя элемент на странице есть?**
**О:** Скорее всего, элемент перекрыт другим элементом (например, всплывающим баннером или индикатором загрузки). Проверь лог ошибки: если там `ElementClickInterceptedException`, значит, нужно дождаться исчезновения "препятствия".

**В: Можно ли использовать `Keys.CONTROL + 'c'` для копирования текста?**
**О:** Да, через `sendKeys(Keys.CONTROL, "c")`. Но помни, что это имитация работы пользователя на уровне ОС/Браузера, и в Headless режиме (без графического интерфейса) такие сложные комбинации иногда могут вести себя нестабильно.

**В: Как очистить поле, если `clear()` не помогает?**
**О:** Редкий случай, но бывает, что JS-скрипты на сайте перехватывают событие очистки. Тогда можно использовать "хак": `setValue("")` (пустая строка) или выполнить очистку через `executeJavaScript("arguments[0].value = ''", element)`.

# 🛠 Шпаргалка: Работа с Checkboxes и Radio Buttons в Selenide

### 1. Суть задачи
**Checkbox (Чекбокс)** — элемент, который может быть либо включен, либо выключен (toggle). Его можно кликать многократно.
**Radio Button (Радиокнопка)** — элемент выбора из группы. При выборе одной кнопки, предыдущая автоматически снимается.

### 2. Основные действия (Actions)

В Selenide нет магической команды `check()` или `uncheck()`. Мы используем универсальный метод `.click()`, но логика зависит от того, что мы хотим получить.

*   **Выбрать/Переключить:**
    ```java
    $("#checkbox").click(); 
    ```
*   **Проверка состояния (Assertions):**
    Это самое важное. Мы не просто проверяем состояние, мы используем "умные ожидания" (`Smart Waits`).
    ```java
    // Проверить, что галочка СТАВИЛАСЬ
    $("#checkbox").shouldBe(Condition.selected);

    // Проверить, что галочки НЕТ
    $("#checkbox").shouldNotBe(Condition.selected);
    
    // Для радиокнопок (синтаксис такой же)
    $("#radio-option-1").shouldBe(Condition.selected);
    ```

### 3. Нюансы и «Подводные камни» (Senior Level)

#### ⚠️ Проблема №1: "The Hidden Input" (Самая частая ошибка)
В современных UI-фреймворках (React, Angular, Vue) настоящий `<input type="checkbox">` часто скрыт (`opacity: 0` или `display: none`), а визуально мы видим красивый стилизованный `<span>` или `<label>`.

*   **Ошибка:** Если ты попытаешься сделать `$(":checkbox").click()`, Selenide выдаст `ElementNotInteractableException`, потому что элемент невидимым для пользователя.
*   **Решение:** Кликай по связанному с ним **Label** или родительскому контейнеру.
    ```java
    // Плохо: кликаем по скрытому инпуту
    $("input[type='checkbox']").click(); 

    // Хорошо: кликаем по тексту/лейблу, который виден глазу
    $("label[for='checkbox-id']").click();
    ```

#### ⚠️ Проблема №2: Проверка "на всякий случай"
При работе с чекбоксами часто нужно убедиться, что мы именно **включили** его, а не просто кликнули (ведь повторный клик выключит его).
*   **Правильный паттерн:**
    ```java
    public void enableCheckbox() {
        if (!$("#checkbox").is(Condition.selected)) {
            $("#checkbox").click();
        }
    }
    ```

#### ⚠️ Проблема №3: Работа с группами (Radio Buttons)
Когда у тебя много радиокнопок, не пиши для каждой отдельный код. Используй коллекции.
```java
// Выбрать радиокнопку по тексту внутри группы
$$("input[type='radio']").findBy(Condition.text("Option 1")).click();

// Проверить, что в группе выбрана именно нужная кнопка
$$("input[type='radio']").shouldHave(size(3)); // Проверка количества
```

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему `is(Condition.selected)` возвращает `false`, хотя я вижу галочку?**
**О:** Скорее всего, ты пытаешься проверить сам `<input>`, который скрыт стилями, а визуально галочка рисуется на другом элементе (`<i>` или `<span>`). Проверяй состояние того элемента, который реально меняет свой CSS (например, появление класса `.checked`).

**В: Что использовать: `click()` или `press(Keys.SPACE)`?**
**О:** В 99% случаев `click()` достаточно. `Keys.SPACE` — это хак для случаев, когда элемент перекрыт другим слоем, но фокус на нем есть. Но если `click()` не работает из-за перекрытия (Element Click Intercepted), попробуй сначала разобраться с тем, какой элемент реально "виден".

**В: Как быстро проверить, что чекбокс НЕ выбран?**
**О:** Используй самый лаконичный вариант: `$("#checkbox").shouldNotBe(selected);`. Это автоматически добавит ожидание (timeout), если страница еще грузится.

# ⌨️ Шпаргалка: Работа с клавиатурой (`Keys`) в Selenide

В Selenium/Selenide класс `Keys` — это перечисление (Enum), которое представляет собой специальные символы и управляющие клавиши (Enter, Tab, Control и т.д.). Мы используем его, когда обычного `.setValue()` недостаточно.

### 1. Основные методы взаимодействия
Есть два главных способа "нажать" на клавишу:

*   **`element.press(Keys.ENTER)`**: Имитирует одиночное нажатие клавиши. Идеально для кнопок или подтверждения действий. Элемент должен быть в фокусе.
*   **`element.sendKeys(Keys.TAB)`**: Добавляет последовательность символов (включая спецклавиши) в поле ввода. В отличие от `press`, `sendKeys` работает как "печать" на клавиатуре.

### 2. Базовые операции (Quick Reference)
| Действие | Код | Комментарий |
| :--- | :--- | :--- |
| **Перенос строки** | `Keys.ENTER` или `Keys.RETURN` | Завершение ввода, отправка формы. |
| **Переход по полям** | `Keys.TAB` | Перемещение фокуса на следующий элемент. |
| **Удаление** | `Keys.BACK_SPACE` / `Keys.DELETE` | Стирание символов. |
| **Навигация** | `Keys.ARROW_DOWN`, `UP`, `LEFT`, `RIGHT` | Управление в выпадающих списках или кастомных инпутах. |
| **Сброс/Выход** | `Keys.ESCAPE` | Закрытие модальных окон, дропдаунов. |

### 3. Комбинации клавиш (Modifier Keys) — "Магия" Senior-уровня
Самое важное — это использование модификаторов: `CONTROL`, `SHIFT`, `ALT`. Чтобы имитировать комбинацию (например, **Ctrl + A**), нужно передать их последовательно в `sendKeys`.

**Примеры:**
*   `element.sendKeys(Keys.CONTROL, "a");` — Выделить весь текст в поле.
*   `element.sendKeys(Keys.CONTROL, Keys.BACK_SPACE);` — Удалить слово целиком (удаление слова назад).
*   `element.sendKeys(Keys.SHIFT, "abc");` — Ввести текст заглавными буквами.

### 4. ⚠️ Нюансы и "Подводные камни" (Senior Insights)

#### 💎 Разница между `setValue()` и `sendKeys()`
Это классическая ошибка джунов.
*   **`setValue("text")`**: Сначала **очищает** поле, а затем вводит текст. Это "чистая" замена.
*   **`sendKeys("text")`**: Просто **дописывает** текст в конец того, что уже есть в поле. Если ты используешь `sendKeys`, будь готов к тому, что старые данные остану/тся.

#### 💎 Проблема фокуса (Focus Issue)
Клавиши типа `TAB` или `ENTER` работают только тогда, когда элемент **находится в фокусе**. Если ты пытаешься нажать `Keys.ENTER` на элементе, который не был предварительно кликнут, команда может улететь "в пустоту" или сработать на другом активном элементе.
*   **Совет:** Если сомневаешься, делай `.click().sendKeys(Keys.ENTER)`.

#### 💎 Имитация реального пользователя
`Keys.CONTROL + "v"` (вставка из буфера) может не сработать в некоторых браузерах или при специфических настройках безопасности сайта. В таких случаях лучше использовать прямой ввод текста через `setValue()`.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему мой `element.sendKeys(Keys.CONTROL, "a")` не выделяет текст?**
**О:** Скорее всего, элемент не в фокусе. Перед выполнением комбинации убедись, что ты кликнул по полю (`element.click()`). Также проверь, что сайт не блокирует программную эмуляцию буфера обмена.

**В: Что лучше использовать для ввода текста: `setValue` или `sendKeys`?**
**О:** Если твоя цель — заполнить форму с нуля, используй `setValue`. Он гарантирует предсказуемый результат (поле будет чистым). Используй `sendKeys` только если тебе нужно именно *дописать* данные или имитировать посимвольный ввод.

****В: Как нажать Enter, чтобы отправить форму?**
**О:** Самый надежный способ: `element.press(Keys.ENTER)` (если фокус уже на кнопке/поле) или `element.sendKeys(Keys.ENTER)` (если ты в поле ввода).

# 🖱️ Шпаргалка: Мышь и сложные действия (Mouse & Complex Actions)

В Selenide большинство действий (клик, ввод текста) уже "зашиты" в высокоуровневые методы. Но когда интерфейс становится "умным" (выпадающие меню, drag-and-drop, сложные анимации), стандартного `.click()` становится недостаточно. В такие моменты мы спускаемся на уровень ниже — к **Selenium Actions API**, который Selenide позволяет использовать бесшовно.

### 1. Базовые действия (Standard Actions)
Это то, что работает в 90% случаев. Эти методы вызываются прямо у элемента.

*   **`.click()`** — Обычный левый клик.
*   **`.doubleClick()`** — Двойной клик (важно для раскрывающихся элементов или выбора текста).
*   **`.rightClick()`** — Клик правой кнопкой мыши (вызов контекстного меню).
*   **`.hover()`** — Наведение курсора на элемент. **Критически важно** для тестирования выпадающих списков (dropdowns), которые появляются только при наведении.

### 2. Drag and Drop (Перетаскивание)
Есть два пути: простой и "ручной".

*   **Простой путь:**
    `$(source).dragAndDropTo(target);`
    *Используй это, если элементы стандартные и не перегружены сложной JS-логикой.*
*   **Сложный путь (через Actions):**
    Если первый способ не срабатывает (бывает на React/Angular компонентах), используем цепочку действий:
    ```java
    actions().clickAndHold(source).moveToElement(target).release().perform();
    ```
    *Здесь мы буквально имитируем: зажал $\rightarrow$ передвинул $\rightarrow$ отпустил.*

### 3. Продвинутые манипуляции (Advanced Actions)
Когда нужно двигать мышь не "в элемент", а "в точку" или "с отступом". Для этого мы используем `Selenide.actions()`.

*   **Смещение относительно элемента (`moveByOffset`):**
    Иногда нужно кликнуть не в центр кнопки, а, например, в её правый верхний угол.
    ```java
    actions().moveToElement(element).moveByOffset(10, 10).click().perform();
    ```
*   **Движение по цепочке:**
    Можно имитировать рисование или сложные пути: `moveToElement` $\rightarrow$ `moveByOffset` $\rightarrow$ `click`.

---

### 💡 Senior Tips (Нюансы и "подводные камни")

1.  **Проблема перекрытия (Element Click Intercepted):**
    Если при клике ты видишь ошибку `ElementClickInterceptedException`, значит, какой-то лоадер или прозрачный слой закрывает твою кнопку. 
    *   *Решение:* Либо подожди исчезновения лоадера (`should(disappear)`), либо используй `actions().moveToElement(el).click().perform()`. Actions часто умеет "пробивать" препятствия лучше, чем обычный `.click()`.

2.  **Забытый `.perform()`:**
    Это самая частая ошибка новичков. Когда ты используешь `actions()`, ты строишь "план действий". Чтобы этот план **выполнился**, в конце **обязательно** нужно вызвать `.perform()`. Без него ничего не произойдет, и тест пройдет (ложноположительный результат).

3.  **Анимации:**
    Если при `.hover()` выпадает меню с анимацией (плавное появление), Selenium может попытаться кликнуть по пункту меню до того, как он стал доступен. 
    *   *Решение:* Добавляй небольшое ожидание или используй `shouldBe(visible)` для элемента внутри меню перед тем, как выполнять клик.

4.  **Hover и потеря фокуса:**
    При тестировании выпадающих списков помни: если мышь "дернется" в сторону во время выполнения цепочки `actions`, меню может закрыться. Старайся делать цепочку действий максимально короткой.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем разница между `element.click()` и `actions().click(element).perform()`?**
**О:** `element.click()` — это высокоуровневый метод Selenide, который сначала проверяет элемент на видимость и кликабельность. `actions().click()` — это низкоуровневая имитация движения физической мыши. Actions более "сильный" инструмент, способный обходить некоторые препятствия, но он менее стабилен, если элементы быстро меняют положение.

**В: Что делать, если Drag-and-Drop работает нестабильно?**
**О:** Скорее всего, скрипт на сайте ожидает последовательности событий `mousedown` $\rightarrow$ `mousemove` $\rightarrow$ `mouseup`. Попробуй разбить действие на цепочку: `clickAndHold()`, затем пауза (если нужно), затем `moveToElement()` и в конце `release()`.

**В: Можно ли кликнуть по координатам экрана?**
**О:** Напрямую — нет, Selenium работает с DOM-элементами. Но ты можешь найти элемент, переместить мышь к нему через `moveToElement`, а затем использовать `moveByOffset(x, y)`, чтобы попасть в нужную точку относительно этого элемента.

# 📝 Шпаргалка: Работа с формами в Selenide

Работа с формами — это 70% всей автоматизации UI. Основная сложность здесь не в том, чтобы «вписать текст», а в том, чтобы правильно обработать динамические состояния (загрузки, ошибки, маски ввода).

### 1. Текстовые поля (`input`, `textarea`)
Самые базовые элементы. В Selenide есть три кита для работы с ними:

*   `$.setValue("text")` — **Твой основной инструмент.** Он очищает поле и вводит текст. Это безопаснее, чем просто ввод, так как гарантирует отсутствие старых данных.
*   `$.append("text")` — Дописывает текст в конец существующего значения. Полезно для полей с префиксами (например, добавление символа `@` к логину).
*   `$.clear()` — Полная очистка поля.

> **💡 Senior Nuance:** Если поле имеет сложную маску (например, номер телефона `+7 (___) ___`), обычный `setValue` может сработать некорректно из-за того, что скрипты маски перехватывают ввод. В таких случаях иногда приходится использовать цепочку: `.click().sendKeys("...")`.

### 2. Чекбоксы и Радиокнопки (`checkbox`, `radio`)
Здесь важно понимать, на какой именно элемент ты кликаешь.

*   `$.click()` — Стандартный метод.
*   **Проблема «невидимого инпута»:** Часто разработчики скрывают настоящий `<input type='checkbox'>` и рисуют красивый `<span>` или `<label>`. Если ты попытаешься кликнуть на скрытый input, Selenide выдаст `ElementNotInteractableException`.
    *   **Решение:** Всегда старайся находить и кликать по `label`, который связан с этим инпутом.

### 3. Выпадающие списки (`select`)
Тут всё зависит от того, как реализован список.

*   **Native HTML Select (стандартный):**
    *   `$(selector).selectOption("Value")` — выбор по видимому тексту.
    *   `$(selector).selectOptionByValue("value")` — выбор по атрибуту `value`.
*   **Custom Dropdowns (React, Angular, Vue и др.):**
    Это не настоящий `<select>`, а набор `<div>` или `<ul>`.
    *   **Алгоритм:** 1. Кликнуть по выпадающему списку $\to$ 2. Подождать появления элементов списка $\to$ 3. Кликнуть по нужному элементу списка.

### 4. Загрузка файлов (`upload`)
Selenide делает это максимально просто, избавляя нас от мучений с системными диалоговыми окнами Windows/Linux.

*   `$(selector).uploadFile(new File("path/to/file.txt"))`
    *   **Как это работает:** Selenide находит скрытый `input[type='file']` и подставляет путь к файлу напрямую в атрибут. Тебе не нужно взаимодействовать с системным окном "Open File".

### 5. Работа с кнопками и отправкой формы
*   `$.click()` — Нажатие на кнопку Submit.
*   **Эмуляция клавиш:** Иногда форма отправляется только по нажатию `Enter`.
    *   `$(selector).pressEnter()` или `$(selector).pressKey(Keys.ENTER)`.

---

### 🚀 Продвинутые нюансы (Pro Tips)

1.  **Ожидание завершения действия:** После нажатия кнопки "Submit" форма может уходить на сервер (запрос идет 1-2 секунды). **Никогда не используй `Thread.sleep()`!** Вместо этого жди изменения состояния:
    `$(selector).shouldBe(visible)` или `$(errorMessage).shouldNot(exist)`.
2.  **Триггеры событий (Blur/Change):** Современные фреймворки часто не «видят» введенный текст, пока ты не уберешь фокус с поля. Если тест вводит текст, но форма его «не видит», добавь: `$.setValue("text").pressTab()`.
3.  **Валидация ошибок:** Работа с формами — это не только заполнение, но и проверка негативных сценариев.
    `$(errorMessage).shouldHave(text("Поле обязательно для заполнения"))`.

# 📑 Шпаргалка: Итерация по списку элементов (`$$`)

В Selenide работа со списками — это не просто перебор элементов через `for`. Это использование мощного инструмента `ElementsCollection`, который обладает «умным» ожиданием и встроенными методами фильтрации.

### 1. Основа: Что такое `$$`?
Когда ты используешь `$$(".selector")`, ты получаешь объект типа `ElementsCollection`. 
**Важный нюанс:** Это не обычный `List<WebElement>`. Это «ленивая» коллекция. Она не ищет элементы в DOM в момент создания объекта, а делает это только тогда, когда ты начинаешь к ней обращаться (вызывать методы).

### 2. Способы обхода (Iteration)

#### А. Классический цикл `for-each`
Используется, когда нужно выполнить сложные действия с каждым элементом (например, собрать данные в отдельный список или сделать скриншот каждого шага).
```java
$$(".product-item").forEach(element -> {
    System.out-println("Нашел товар: " + element.getText());
});

// Или классика
for (SelenideElement item : $$(".product-item")) {
    item.click();
}
```

#### Б. Использование Java Streams (Для продвинутой обработки)
Если тебе нужно трансформировать список элементов в список строк, чисел или объектов.
```java
List<String> names = $$(".user-name")
    .stream()
    .map(el -> el.getText())
    *   .collect(Collectors.toList());
```

---

### 3. Senior Way: Вместо циклов используй Фильтрацию (Filtering)
**Главное правило:** Если ты пишешь цикл `for` с условием `if` внутри — ты делаешь плохо. В Selenide это решается встроенными методами, которые работают быстрее и стабильнее.

#### А. `filterBy(Condition...)` — Оставить только подходящие
Вместо того чтобы перебирать все элементы и проверять их текст, просто скажи Selenide оставить нужные.
```java
// ПЛОХО (медленно, много кода)
for (SelenideElement el : $$(".row")) {
    if (el.getText().contains("Active")) {
        el.click();
    }
}

// ХОРОШО (быстро, чисто, Selenide сам подождет появления)
$$(".row").filterBy(text("Active")).click();
```

#### Б. `findBy(Condition...)` — Найти первый подходящий
Если тебе нужен один конкретный элемент из списка по критерию.
```java
// Найдем строку, где есть текст "Error" и она видима
$$(".status-message").findBy(visible).findBy(text("Error")).click();
```

#### элементы с кастомной логикой: `filter(Predicate)`
Если стандартных `Condition` (text, visible, etc.) не хватает, можно использовать лямбда-выражение.
```java
$$(".price").filter(el -> Double.parseDouble(el.getText().replace("$", "")) > 100)
             .click();
```

---

### 4. Нюансы и "Подводные камни" ⚠️

1.  **StaleElementReferenceException:** В обычном Selenium при обновлении страницы цикл `for` упадет. **Selenide магическим образом это лечит**: так как коллекция «ленивая», при каждой итерации он может заново перепроверить состояние элементов.
2.  **Производительность:** Не используй `.stream()` на огромных коллекциях (например, 1000 строк таблицы), если можно использовать `.filterBy()`. `filterBy` работает на уровне оптимизированных запросов Selenide к драйверу.
3.  **Порядок элементов:** Помни, что `$$` возвращает элементы в том порядке, в котором они идут в DOM. Если страница динамическая (реактивная), порядок может измениться.

---

### ❓ FAQ (Частые вопросы)

**В: Почему мой цикл `for` работает слишком медленно?**
**О:** Скорее всего, внутри цикла ты вызываешь методы, которые инициируют новые проверки (например, `getText()` или `isDisplayed()`). На каждом элементе Selenide делает микро-проверку. Если элементов 100, это 100 лишних обращений к браузеру. Используй `filterBy` — он оптимизирован.

**В: В чем разница между `$$(".item").filterBy(text("X"))` и `$$(".item").findBy(text("X"))`?**
**О:** `filterBy` возвращает **коллекцию** (все элементы, подходящие под условие). `findBy` возвращает **один единственный элемент** (первый найденный).

**В: Можно ли внутри `forEach` делать клики, которые меняют страницу?**
**О:** Это опасно. Если клик по первому элементу обновит DOM (перезагрузит часть страницы), то при переходе ко второму элементу коллекция может стать невалидной. В таких случаях лучше сначала собрать список нужных элементов в `List<SelenideElement>`, а потом итерироваться по этому списку.

**В: Как проверить, что список пуст?**
**О:** Используй встроенное условие: `$$(".item").shouldBe(empty)`. Не используй `if ($$.size() == 0)`.

# 📑 Шпаргалка: Фильтрация коллекций в Selenide

В Selenide коллекция элементов — это объект типа `ElementsCollection`. Главная фишка здесь в том, что все операции над ней **lazy (ленивые)**. Это значит, что поиск элементов не начнется до тех пор, пока ты не вызовешь какое-то действие (например, `.click()` или `.shouldHave()`).

### 1. Основные инструменты фильтрации

#### А) `.filterBy(Condition...)` — Поиск подмножества
Используется, когда тебе нужно оставить в списке только те элементы, которые соответствуют определенным `Condition`.
*   **Что возвращает:** Новую `ElementsCollection`.
*   **Когда использовать:** Когда нужно отсеять лишнее (например, оставить только видимые элементы или элементы с определенным классом).

```java
// Оставит только те элементы, которые видны на экране
$$(".product-item").filterBy(visible);

// Оставит только элементы, у которых в тексте есть "Apple"
$$(".product-name").filterBy(text("Apple"));

// Комбинирование условий (логическое И)
$$(".product-item").filterBy(visible, cssClass("active"));
```

#### Б) `.findBy(Condition...)` — Поиск одного элемента
Это "хирургический" инструмент. Он ищет первый попавшийся элемент в коллекции, подходящий под условие.
*   **Что возвраходит:** Один `SelenideElement`.
*   **Когда использовать:** Когда ты точно знаешь, что среди списка тебе нужен один конкретный объект по его признаку.

```java
// Найти первый элемент с текстом "Delete" в списке кнопок
$$(".btn").findBy(text("Delete")).click();
```

#### В) `.filter(Predicate<WebElement>)` — Тяжелая артиллерия
Если стандартных `Condition` (типа `visible`, `text`) не хватает, ты можешь написать свою логику на чистом Java.
*   **Что возвращает:** `ElementsCollection`.
*   **Когда использовать:** Когда проверка требует сложной математики или обращения к атрибутам, которых нет в стандартном наборе.

```java
// Оставим только те элементы, у которых цена (атрибут data-price) > 100
$$(".product").filter(element -> {
    String priceStr = element.getAttribute("data-price");
    return Integer.parseInt(priceStr) > 100;
});
```

---

### 2. Нюансы и "Подводные камни" (Senior Tips) 💡

1.  **Разница между `filterBy` и `findBy`:** 
    *   `filterBy` — это **фильтр**. Ты получаешь список (пустой или с элементами).
    *   `findBy` — это **поиск**. Если элемент не найден, Selenide будет ждать его появления (timeout), а если не найдет — выбросит ошибку.
2.  **Производительность:** Не злоупотребляй `.filter(Predicate...)`. Внутри предикта ты пишешь код на Java, который заставляет Selenide обращаться к браузеру за каждым атрибутом. Если в коллекции 1000 элементов, это может сильно замедлить тест. Старайся максимально использовать `filterBy` с готовыми `Condition`.
3.  **Цепочки (Chaining):** Всегда старайся сужать область поиска. Сначала найди контейнер через `$(...)`, а потом уже внутри него ищи коллекцию `$$(...)`. Это делает тесты гораздо стабильнее.
    *   *Плохо:* `$$(".item").filterBy(text("X"))` (ищем по всему DOM).
    *   *Хорошо:* `$(".sidebar").$$(".item").filterBy(text("X"))` (ищем только в сайдбаре).

---

### ❓ FAQ: Часто задаваемые вопросы

**В: Что будет, если `.filterBy()` не найдет ни одного элемента?**
**О:** Ошибки не будет. Ты просто получишь пустую коллекцию. Ошибка возникнет только тогда, когда ты попытаешься совершить действие над этим результатом (например, `.click()`) или применишь проверку `.shouldHave(size(1))`.

**В: В чем разница между `filterBy(text("Apple"))` и `filterBy(exactText("Apple"))`?**
**О:** `text("Apple")` найдет "Green Apple", "Apple Pie" и т.д. (содержит подстроку). `exactText("Apple")` найдет только точное совпадение.

**В: Можно ли использовать `filterBy` вместе с XPath?**
**О:** Да, но `filterBy` работает с `Condition`. Если тебе нужно использовать сложный XPath, лучше сразу применить его в селекторе `$$(".xpath_here")`, а `filterBy` использовать для уточнения состояния (видимость, текст).

**В: Как проверить, что коллекция пустая?**
**О:** Используй `.shouldBe(empty)`. Это самый чистый и читаемый способ.
`$$(".error-message").shouldBe(empty);`

# 📚 Шпаргалка: Проверки коллекций в Selenide (`$$`)

В Selenide работа с группами элементов строится вокруг объекта `ElementsCollection` (возвращается через оператор `$$`). Главное правило Senior-разработчика: **всегда старайся максимально сузить область поиска до коллекции, прежде чем начинать перебор.**

### 1. Базовые проверки размера и состояния
Прежде чем искать что-то внутри, нужно убедиться, что сама коллекция в правильном состоянии.

*   `$$(".item").shouldHave(size(3))` — проверка, что элементов ровно 3.
*   `$$(".item").shouldBe(empty)` — проверка, что список пуст.
/ `$$(".item").shouldHave(sizeGreaterThan(1))` — проверка, что элементов больше одного.
*   `$$(".item").shouldNot(exist)` — проверка, что коллекция вообще не найдена в DOM.

### 2. Поиск внутри коллекции (Filtering)
Это самый мощный инструмент. Вместо того чтобы писать циклы `for`, используй встроенные фильтры.

*   **`findBy(Condition)`**: Ищет **первый** элемент, подходящий под условие.
    ```java
    $$(".user-row").findBy(text("Ivan")).shouldBe(visible);
    ```
*   **`filterBy(Condition)`**: Возвращает **новую коллекцию**, состоящую только из элементов, прошедших фильтр.
    ```java
    $$(".user-row").filterBy(visible).shouldHave(size(5)); // Только видимые пользователи
    ```
*   **`filter(Predicate)`**: Самый гибкий метод. Позволяет использовать чистую Java (лямбды) для сложной логики, которую не покрыть стандартными `Condition`.
    ```java  
    $$(".price").filter(el -> Double.parseDouble(el.getText()) > 100.0); // Фильтр по математическому условию
    ```

### 3. Проверка содержимого (CollectionCondition)
Для коллекций используются не `Condition`, а `CollectionCondition`. Это позволяет проверять сразу всё содержимое.

*   **`texts("A", "B", "C")`**: Проверяет, что элементы в списке содержат именно этот текст и в таком порядке.
*   **`textsInAnyOrder("C", "A", "B")`**: То же самое, но порядок не важен.
*   **`containText("Ivan")`**: Проверяет, что хотя бы один элемент содержит этот текст.
*   **`allMatch(Condition)`**: Проверяет, что **каждый** элемент коллекции соответствует условию (например, все кнопки должны быть `enabled`).

### 4. Нюансы и Senior-советы (⚠️ Важно!)

1.  **Lazy Evaluation (Ленивые вычисления):** Это киллер-фича Selenide. Когда ты пишешь `$$(".item")`, поиск в браузере **не происходит**. Поиск начнется только в момент вызова `.should()` или `.click()`. Поэтому не бойся объявлять коллекции заранее.
2.  **Избегай циклов `for` для проверок:** Если ты пишешь `for (WebElement el : $$(".items")) { assertEquals(...) }`, ты убиваешь магию ожиданий Selenide. Если элемент появится через секунду, твой цикл упадет с ошибкой, а встроенный `shouldHave(texts(...))` подождет его появления.
3.  **Производительность:** Если в списке 1000 элементов, `filter(Predicate)` будет работать медленнее, так как Selenide придется выкачать текст каждого элемента из браузера в Java. Старайся использовать CSS-селекторы внутри `$$(".selector")` для первичной фильтрации на стороне браузера.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `findBy` и `filterBy`?**
**О:** `findBy` возвращает один одиночный элемент (`SelenideElement`). `filterBy` возвращает новую коллекцию (`ElementsCollection`). Если тебе нужно кликнуть — используй `findBy`. Если нужно проверить количество подходящих — `filterBy`.

**В: Что делать, если элементы в коллекции меняются (динамический список)?**
**О:** Используй `CollectionCondition`. Он умеет "перечитывать" коллекцию в течение таймаута. Например, `$$(".item").shouldHave(size(5))` будет ждать, пока количество элементов не станет равным 5.

**В: Можно ли использовать `containsText` для проверки наличия элемента в списке?**
**О:** Да, но помни: `$$(".items").shouldHave(containText("Ivan"))` проверит, что *хотя бы один* элемент из коллекции содержит "Ivan". Это очень удобно и быстро пишется.

**В: Как проверить, что все элементы имеют определенный CSS класс?**
**О:** Используй `allMatch`: 
`$$(".item").should(allMatch("{element} -> {element}.cssClass(\"active\")"));` 
*(Хотя проще и чище через `filterBy(cssClass("active")).shouldHave(size(expectedSize))`)*.

# 🔍 Шпаргалка: Поиск элемента в коллекции по условию

Когда у нас есть список элементов (например, строки таблицы или пункты меню), нам редко нужен «весь список». Нам нужен конкретный элемент, который обладает определенным признаком. В Selenide для этого используются три кита: `findBy`, `filterBy` и `filter`.

### 1. Основные инструменты

#### А) `findBy(Condition...)` — "Найти первого попавшегося"
Это самый быстрый способ. Ты говоришь: «Пробегись по списку и остановись, как только найдеert элемент, подходящий под условие».
*   **Когда использовать:** Когда тебе нужен один конкретный элемент и ты знаешь его уникальный признак (текст, класс, атрибут).
*   **Результат:** Возвращает `SelenideElement`.

```java
// Ищем строку в таблице, где текст равен "Apple"
$$(".product-row").findBy(text("Apple")).click();
```

#### Б) `filterBy(Condition...)` — "Оставить только подходящие"
Этот метод не возвращает один элемент, он возвращает **новую коллекцию**, в которой остались только те элементы, которые прошли фильтр.
*   **Когда использовать:** Когда тебе нужно проверить группу элементов (например, «проверь, что все активные кнопки имеют синий цвет») или когда нужно сузить область поиска перед тем, как применить `findBy`.
*   **Результат:** Возвращает `ElementsCollection`.

```java
// Оставляем только видимые и активные чекбоксы, а потом берем первый
$$("input[type='checkbox']")
    .filterBy(visible, enabled)
    .first()
    .click();
```

#### В) `filter(Predicate)` — "Тяжелая артиллерия" (Custom Logic)
Если стандартных `Condition` (типа `text`, `visible`, `attribute`) не хватает, ты можешь использовать чистую Java-логику (лямбда-выражения).
*   **Когда использовать:** Когда условие слишком сложное для стандартного Selenide (например, нужно проверить регулярное выражение, посчитать длину строки или сравнить два атрибута между собой).
*   **Результат:** Возвращает `ElementsCollection`.

```java
// Ищем элемент, текст которого начинается на "Order_" и содержит число
$$(".order-item")
    .filter(element -> element.getText().matches("Order_\\d+"))
    .first()
    .click();
```

---

### 💡 Нюансы от Senior'а (Важно!)

1.  **`findBy` vs `filterBy`**: 
    *   `findBy` — это поиск **одного**. Если ничего не найдено, Selenide будет ждать (smart wait), пока элемент не появится, и только потом кинет ошибку.
    *   `filterBy` — это фильтрация **всех**. Он не ждет появления элемента, он просто смотрит на то, что *уже есть* в DOM в данный момент. Если список пуст, `filterBy` вернет пустую коллекцию без ошибки.

2.  **Порядок имеет значение**: 
    Всегда старайся сначала максимально сузить поиск через `filterBy`, а потом уже искать конкретный элемент через `findBy`. Это делает тесты быстрее и читаемеку.
    *   *Плохо:* `$$(".item").findBy(text("Delete"))` (ищем по всему DOM).
    *   *Хорошо:* `$$(".modal-content .item").findBy(text("Delete"))` (сначала ограничили область до модального окна).

3.  **Ловушка пустой коллекции**: 
    Если ты используешь `.filterBy(...).click()`, и фильтр не нашел ни одного элемента, ты получишь ошибку `Element not found`. Всегда помни, что цепочка может привести к "пустоте".

### ❓ FAQ (Частые вопросы)

**В: Что будет, если `findBy` найдет два одинаковых элемента?**
**О:** Он вернет **первый** найденный элемент в коллекции. Если тебе нужен второй или последний, используй `.filterBy(...)` и затем метод `.get(index)` или `.last()`.

**В: Можно ли комбинировать `filterBy` и `findBy`?**
**О:** Да, и это лучший паттерн! 
`$$(".rows").filterBy(visible).findBy(text("Target")).click();` — сначала отсекли невидимые строки, потом нашли нужную.

**В: Чем `filter(element -> ...)` хуже, чем `filterBy(Condition)`?**
**О:** `filterBy` использует встроенные механизмы ожидания (Smart Waits) Selenide. Когда ты переходишь на чистую Java-лямбду в `filter()`, ты фактически выходишь из "магии" Selenide и работаешь с текущим состоянием элементов. Если данные подгружаются асинхронно, лямбда может выполниться слишком рано и не найти элемент. **Используй `filterBy` всегда, когда это возможно.**

# 🛠 Работа с Iframe в Selenide

### 💡 Что это такое (простыми словами)
Представь, что веб-страница — это большая картина. **Iframe** — это маленькая дополнительная рамка, приклеенная поверх этой картины. Внутри этой рамки может быть совсем другой «мир» со своими кнопками и текстом.

**Главная проблема:** WebDriver (и Seleniente) по умолчанию «смотрит» только на основную картину. Он физически не видит, что происходит внутри рамки, пока ты явно не скажешь ему: *"Переключи фокус на эту рамку"*.

---

### 🚀 Основной синтаксис

В Selenide переключение происходит через метод `.switchTo().frame()`.

#### 1. Переключение по элементу (Самый надежный способ)
Лучше всего сначала найти сам элемент `iframe`, а затем «войти» в него. Это позволяет использовать все прелести селекторов Selenide.

```java
// Находим iframe и переключаемся в него
$(By.id("iframe_id")).switchTo().frame();

// Теперь мы "внутри". Можем работать с элементами фрейма
$("#button_inside_iframe").click();

// ВАЖНО: После работы нужно вернуться на основную страницу!
switchTo().defaultContent();
```

#### 2. Переключение по ID или Name (Если они статичны)
Если у iframe есть стабильный `id` или `name`, можно передать строку напрямую.

```java
switchTo().frame("iframe_name_or_id");
```

---

### ⚠️ Нюансы и "подводные камни" (Senior Tips)

1.  **Забытый возврат (`defaultContent`)**: Это самая частая причина багов в тестах. Если ты переключился во фрейм, нажал кнопку и **не** вызвал `switchTo().defaultContent()`, твой следующий шаг (например, поиск логотипа сайта) упадет с ошибкой `ElementNotFound`, потому что Selenium всё еще ищет элементы внутри маленького фрейма, а не на главной странице.
    
2.  **Ожидание появления фрейма**: Фреймы часто подгружаются динамически (через JS). Если ты попытаешься переключиться в iframe, который еще не отрисовался, тест упадет. 
    *   *Правильно:* Сначала подожди, пока iframe станет видимым/существующим.
    ```java
    $(By.id("iframe_id")).shouldBe(visible).switchTo().frame();
    ```

3.  **Вложенные фреймы (Nested Iframes)**: Бывает ситуация "матрешки": основной фрейм $\rightarrow$ фрейм внутри него. 
    *   Чтобы попасть во второй, нужно сначала переключиться в первый, а потом из него — во второй.
    *   Чтобы вернуться на главную страницу, всегда используй `switchTo().defaultContent()`, это сбросит все уровни вложенности сразу.

4.  **Поиск элементов внутри фрейма**: Никогда не пытайся искать элементы внутри фрейма, не переключившись в него. Даже если ты видишь их в DevTools, для драйвера их не существует, пока фокус не смещен.

# 🗂 Шпаргалка: Работа с несколькими окнами и вкладками

В Selenium/Selenide браузер рассматривает каждую новую вкладку или всплывающее окно как отдельный **Window Handle** (уникальный идентификатор окна). Когда ты кликаешь по ссылке `target="_blank"`, фокус браузера остается на старой вкладке, а драйвер «не видит» новую, пока ты явно не прикажешь ему переключиться.

### 1. Основные понятия
*   **Window Handle** — это уникальная строка (ID), которую браузер присваивает каждой вкладке.
*   **Driver Context** — текущее состояние драйвера. Команды (`click`, `find`) выполняются только в том контексте (окне), который активен в данный момент.

### 2. Алгоритм переключения (Standard Workflow)

Чтобы не потеряться, всегда используй классический паттерн: **«Запомнил старое $\to$ Переключился на новое $\to$ Сделал дела $\to$ Вернулся»**.

```java
// 1. Запоминаем ID текущего (главного) окна
String mainWindow = WebDriverRunner.driver().getWindowHandle();

// 2. Кликаем по ссылке, которая открывает новую вкладку
$("#open-new-tab-link").click();

// 3. Ждем, пока количество окон станет больше одного (важный нюанс!)
WebDriverRunner.getWebDriver().waitAbout(Duration.ofSeconds(5), () -> 
    WebDriverRunner.driver().getWindowHandles().size() > 1
);

// 4. Получаем список всех открытых ID
Set<String> allWindows = WebDriverRunner.driver().getWindowHandles();

// 5. Переключаемся на новое окно (перебираем все, кроме старого)
for (String windowHandle : allWindows) {
    if (!windowHandle.equals(mainWindow)) {
        WebDriverRunner.driver().switchTo().window(windowHandle);
        break;
    }
}

// 6. Теперь мы в новой вкладке! Работаем...
$(".new-tab-element").shouldBe(visible);

// 7. Закрываем новую вкладку и возвращаемся в главное окно
WebDriverRunner.driver().close(); // Закрывает ТЕКУЩУЮ вкладку
WebDriverRunner.driver().switchTo().window(mainWindow); // Возвращаем фокус
```

### 3. Продвинутый способ: Поиск по заголовку или URL
Если окон много, перебирать их «вслепую» — плохая практика. Лучше искать окно по признаку (Title или URL).

```java
public void switchToWindowByTitle(String expectedTitle) {
    WebDriverRunner.driver().getWindowHandles().forEach(handle -> {
        WebDriverRunner.driver().switchTo().window(handle);
        if (WebDriverRunner.driver().getTitle().contains(expectedTitle)) {
            return; // Нашли!
        }
    });
}
```

### 4. ⚠️ Нюансы и Senior-советы (Тонкие моменты)

1.  **Проблема «Слепого переключения»:** Никогда не переключайся на окно сразу после клика. Новая вкладка может инициализироваться долю секунды. Если драйвер попытается переключиться на ID, которого еще нет в `getWindowHandles()`, ты получишь ошибку или останеся в старом окне. **Всегда используй ожидание количества окон.**
2.  **`close()` vs `quit()`:** 
    *   `driver.close()` — закрывает только текущую вкладку.
    *   `driver.quit()` — убивает весь процесс браузера и все окна. Если после `close()` ты не вернешься в `mainWindow`, твой тест упадет на следующем шаге, так как контекст будет потерян.
3.  **Индексы — это зло:** Не пытайся обращаться к окнам по индексу (например, «второе окно в списке»). Порядок в `getWindowHandles()` может меняться в зависимости от нагрузки или особенностей браузера. Всегда используй сравнение с `mainWindow` или проверку `Title/URL`.
4.  **Z-index и Pop-ups:** Если всплывающее окно — это не новая вкладка, а JS-модалка (слой поверх страницы), то `switchTo().window()` **не поможет**. Для модалок используй обычные `shouldBe(visible)`.

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Что произойдет, если я закрою последнюю открытую вкладку через `driver.close()`?**
**О:** Драйвер перейдет в состояние «зомби». Процесс браузера может остаться висеть, но управлять им нельзя, так как нет активного окна. Следующая команда вызовет `NoSuchSessionException`.

**В: Как понять, что мы действительно переключились на новую вкладку?**
**О:** Самый надежный способ — проверить URL или заголовок страницы (`driver.getCurrentUrl()`) сразу после команды `switchTo().window()`.

**В: Можно ли в Selenide переключаться между окнами без использования `WebDriverRunner`?**
**О:** Напрямую через синтаксис `$` — нет, так как поиск элементов привязан к текущему контексту. Но ты можешь обернуть логику переключения в свой Helper-класс, чтобы в тестах писать красиво: `WindowHelper.switchToTab("Settings")`.

**В: Как обработать ситуацию, когда окно открывается с задержкой (AJAX)?**
**О:** Используй `Wait` (как в моем примере выше). Нужно ждать не просто «секунду», а именно изменения состояния коллекции `getWindowHandles()`.

# 🌑 Shadow DOM: Теневой лес в автоматизации

### Что это такое? (Простыми словами)
Представь, что веб-страница — это обычный HTML-документ. **Shadow DOM** — это «черный ящик» или «изолированный контейнер», спрятанный внутри этого документа. 

Разработчики используют его для создания **Web Components**. Основная идея: инкапсуляция. Все, что находится внутри Shadow DOM (стили, скрипты, элементы), не «протекает» наружу и не портит основную страницу, а внешние стили страницы не могут случайно изменить элементы внутри него.

**Для нас как для автоматизаторов это проблема:** стандартные методы поиска (типа XPath) «упираются в стену» этого контейнера и не видят, что происходит внутри.

---

### Ключевые термины
1.  **Shadow Host** — обычный DOM-элемент, через который мы «входим» в теневую часть. Это наша точка входа.
2.  **Shadow Root** — корень, который находится внутри Host. Именно к нему нам нужно прикрепиться.
3.  **Shadow Tree** — вся иерархия элементов, скрытая внутри Shadow Root.

---

### Главное правило (The Golden Rule) ⚠️
**XPath не работает внутри Shadow DOM.** 
XPath умеет перемещаться только по основному дереву (DOM). Как только он доходит до Shadow Root, он останавливается. Внутри теневого дерева можно использовать **только CSS-селекторы**.

---

### Как с этим работать в Selenide?

С выходом Selenium 4 и обновлений Selenide, работа с Shadow DOM стала значительно проще. Теперь нам не нужно писать сложные JavaScript-костыли для каждого элемента.

#### Способ 1: Использование `getShadowRoot()` (Modern Way)
Если Shadow DOM имеет режим **`mode: 'open'`** (что бывает в 99% случаев), мы можем получить доступ к корню через Selenium API, который Selenide подхватывает.

```java
// 1. Находим Shadow Host (тот самый элемент-вход)
SelenideElement shadowHost = $("#shadow-host-element");

// 2. Получаем Shadow Root
// Внимание: getShadowRoot() возвра럼 WebElement, поэтому оборачиваем обратно в SelenodeElement
WebElement shadowRoot = shadowHost.getWrappedElement().getShadowRoot();

// 3. Ищем элемент ВНУТРИ Shadow Root, используя CSS селектор
SelenideElement innerElement = $(shadowRoot).$(".internal-button");

innerElement.click();
```

#### Способ 2: JavaScript Executor (Old School / Heavy Duty)
Если структура очень сложная или `getShadowRoot()` по какой-то причине не срабатывает (например, в специфических окружениях), используем классику — выполнение JS.

```java
// Выполняем скрипт, который возвращает нужный элемент из тени
WebElement element = executeJavaScript(
    "return document.querySelector('#host').shadowRoot.querySelector('.inner-class')"
);
$(element).click();
```

---

### Нюансы и "подводные камни" 💡

1.  **Nested Shadow DOM (Вложенность):** Бывает, что внутри одного Shadow DOM находится другой. В этом случае тебе нужно «пройти» сквозь них по цепочке: `Host -> Root1 -> Host2 -> Root2`.
2.  **Mode: 'closed':** Если разработчик установил `mode: 'closed'`, то программно достучаться до Shadow Root через стандартный API практически невозможно. Это архитектурная защита. Если видишь такое — иди к разработчикам, это не задача автоматизации.
3.  **Ожидания (Waits):** Элементы внутри Shadow DOM могут появляться с задержкой. Всегда используй `shouldBe(visible)`, так как переход в Shadow Root — это дополнительная операция для браузера.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему мой XPath не находит кнопку, хотя я вижу её в DevTools?**
**О:** Посмотри внимательно в дереве элементов DevTools. Если над кнопкой есть строка `#shadow-root (open)`, значит, кнопка находится в изоляции. Твой XPath «не видит» сквозь эту стену. Переходи на CSS и используй метод `getShadowRoot()`.

**В: Можно ли использовать Selenide-методы `.should()` внутри Shadow DOM?**
**О:** Да! Как только ты получил доступ к элементу (через `$(shadowRoot).$(".element")`), этот объект снова становится полноценным `SelenideElement`. Ты можешь использовать `.shouldBe(visible)`, `.shouldHave(text(...))` и всё остальное.

**В: Что делать, если элементов много и они все в разных Shadow DOM?**
**О:** Не пытайся написать один гигантский селектор. Разбей задачу на шаги: найди Host -> перейди в Root -> найди элемент. Это сделает твой код читаемым и поддерживаемым.

**В: В чем разница между `mode: 'open'` и `mode: 'closed'` для теста?**
**О:** `open` — мы можем протестировать. `closed` — мы не можем (без хаков с переопределением прототипов JS). Если видишь `closed`, это "красный флаг" для автоматизатора.

# 🚨 Topic: Alerts & Pop-ups

Прежде чем мы начнем, **самое важное правило**: в автоматизации нужно четко различать два типа «всплывашек». Если ты их перепутаешь — тест упадет, и ты потратишь час на дебаг.

1.  **JS Alerts (Browser Native):** Это системные окна браузера (`alert()`, `confirm()`, `prompt()`). У них нет HTML-кода, их нельзя найти через `$(selector)`. Они перехватывают фокус у страницы.
2.  **HTML Modals (Web Modals):** Это обычные `<div>`, которые просто красиво наложены поверх сайта. Их можно и нужно искать как обычные элементы через `$(selector)`.

---

### 1. Работа с JS Alerts (Native Browser Pop-ups)

Для работы с ними мы используем метод переключения контекста: `Selenide.switchTo().alert()`.

#### Основные действия:
*   **`accept()`** — Нажать «ОК» (подтвердить действие).
*   **`dismiss()`** — Нажать «Отмена» (закрыть без подтверждения).
*   **`sendKeys("text")`** — Ввести текст в `prompt` (если окно позволяет ввод).

#### Пример кода:
```java
// 1. Окно Alert (только кнопка OK)
open("/alert-page");
alert().accept(); // Нажали OK

// 2. Окно Confirm (OK или Cancel)
open("/confirm-page");
alert().dismiss(); // Нажали Cancel

// 3. Окно Prompt (с полем ввода)
open("/prompt-page");
alert().sendKeys("Hello Senior!"); 
alert().accept();
```

---

### 2. Нюансы и «подводные камни» ⚠️

#### А. Ожидание появления Alert
Alert не появляется мгновенно. Иногда после клика по кнопке браузеру нужно доли секунды, чтобы отрисовать системное окно. Если вызвать `switchTo().alert()` слишком рано, ты получишь `NoAlertPresentException`.

**Как правильно:** Используй явное ожидание (Explicit Wait), хотя Selenide старается помогать, иногда надежнее прописать это явно:
```java
import static org.openqa.selenium.support.ui.ExpectedConditions.alertIsPresent;
import org.openqa.selenium.support.ui.WebDriverWait;

// Ждем, пока alert появится в DOM (в контексте браузера)
new WebDriverWait(WebDriverCompanion.getWebDriver(), Duration.ofSeconds(5))
    .until(alertIsPresent());
```

#### Б. Потеря фокуса (Context Switching)
Когда ты вызываешь `switchTo().alert()`, фокус управления переходит на системное окно. Как только ты сделал `.accept()` или `.dismiss()`, фокус возвращается на основную страницу автоматически. Но если ты попытаешься искать элементы *внутри* процесса работы с алертом — это путь к ошибке.

#### В. HTML Modals (то, что все путают)
Если перед тобой окно, которое можно «проскроллить» или где есть кнопка с классом `.close-button`, — **это не Alert**. Это обычный элемент страницы.
**Правильный подход:**
```java
// Это НЕ alert, это просто div на странице
$(".modal-content").shouldBe(visible);
$(".btn-close").click();
```

### 💡 FAQ (Частые вопросы на собеседованиях)

**В: Можно ли найти текст внутри JS Alert через `$(...)`?**
**О:** Нет. У JS Alert нет DOM-дерева. Ты не можешь использовать CSS или XPath селекторы для поиска текста внутри него. Ты можешь только получить текст всего окна целиком через `alert().getText()`.

**В: Что делать, если `alert().accept()` падает с ошибкой `NoAlertPresentException`?**

---

## 1. Загрузка файлов (File Upload)

В Selenide есть два основных сценария: когда у нас есть стандартный `<input type="file">` и когда мы имеем дело с "красивыми" кастомными компонентами.

### А. Стандартный путь (Happy Path)
Если на странице есть классический элемент `input`, используй метод `.uploadFile()`. Это самый надежный способ.

```java
// Загрузка файла из ресурсов проекта
File file = new File("src/test/resources/test-data/image.png");
$("[data-testid='upload-input']").uploadFile(file);
```

### 🚩 Нюанс: Скрытые инпуты (Hidden Inputs)
В современных фреймворках (React, Angular) реальный `input` часто скрыт (`display: none`), а вместо него рисуют красивую кнопку. Selenide не сможет кликнуть по скрытому элементу напрямую.

**Решение:** Используй `sendKeys()` с путем к файлу. Это имитирует ввод пути в системное окно, минуя клики мышкой.
```java
// Находим скрытый инпут и "вбрасываем" в него путь к файлу
String filePath = new File("src/test/resources/test-data/doc.pdf").getAbsolutePath();
$("[type='file']").sendKeys(filePath);
```

### Б. Сложный путь (Drag & Drop)
Если сайт требует перетаскивания файла в зону (Dropzone), `uploadFile` может не сработать. Тут придется использовать `Actions` (Selenium API), но это нестабильно. 
**Senior Tip:** Если есть возможность, всегда ищи скрытый `input`. Если его нет — используй JavaScript для имитации события drop.

---

## 2. Скачивание файлов (File Download)

Главная проблема скачивания в автотестах — **диалоговое окно сохранения файла**. Мы не можем управлять системным окном Windows/macOS через Selenium.

**Решение:** Перехватить загрузку на уровне браузера, заставив его скачивать всё в конкретную папку проекта.

### Шаг 1: Настройка конфигурации
Нужно указать Selenide, куда именно браузер должен складывать файлы.


# 🛠 Шпаргалка: Selenide + JUnit 5 / TestNG

Когда мы говорим о связке Selenide с тестовым фреймворком, мы говорим не о "нажатии кнопок", а об **управлении жизненным циклом теста**. Selenide — это мотор, но JUnit 5 или TestNG — это водитель и правила дорожного движения.

## 1. Архитектура: Правило BaseTest
**Никогда** не пиши конфигурацию (`Configuration.browser = ...`) внутри самих тестовых классов. Это нарушение принципа DRY (Don't Repeat Yourself).

Создай базовый класс `BaseTest`, от которого будут наследоваться все твои тесты. Здесь происходит вся магия настройки.

```java
// Пример для JUnit 5
public class BaseTest {
    @BeforeAll
    static void setupAll() {
        Configuration.browser = System.getProperty("browser", "chrome"); // Читаем из консоли или дефолт
        Configuration.headless = Boolean.parseBoolean(System.getProperty("headless", "false"));
        Configuration.timeout = 8000; // Увеличиваем глобальный таймаут, если нужно
    }

    @BeforeEach
    void setup() {
        open("https://example.com"); // Открываем страницу перед каждым тестом
    }

    @AfterEach
    void tearDown() {
        // Selenide сам управляет браузером, но здесь можно чистить cookies или localStorage
        Selenide.clearBrowserCookies();
        Selenide.clearBrowserLocalStorage();
    }
}
```

## 2. Жизненный цикл (Lifecycle)
Тебе нужно четко понимать, где и какой метод использовать:

| Действие | JUnit 5 | TestNG | Зачем это нужно? |
| :--- | :--- | :--- | :--- |
| **Один раз перед всеми тестами** | `@BeforeAll` | `@BeforeClass` | Настройка браузера, конфигов, логгеров. |
| **Перед каждым тестом** | `@BeforeEach` | `@BeforeMethod` | Переход на главную страницу, очистка данных. |
| **После каждого теста** | `@AfterEach` | `@AfterMethod` | Снятие скриншота при падении, очистка куки. |
| **Один раз после всех тестов** | `@AfterAll` | `@AfterClass` | Закрытие драйвера (если нужно), генерация отчетов. |

## 3. Параметризация (Data-Driven Testing)
Senior-разработчик не пишет 10 тестов для проверки 10 логинов. Он пишет один тест и прогоняет его через набор данных.

**JUnit 5 (современный стандарт):**
Используем `@ParameterizedTest` и `@CsvSource`.
```java
@ParameterizedTest
@CsvSource({
    "admin, password123",
    "user, qwerty",
    "guest, guest_pass"
})
void loginTest(String login, String password) {
    loginField.setValue(login);
    passwordField.setValue(password);
    button.click();
    // проверки...
}
```

**TestNG (классика):**
Используем `@DataProvider`. Это мощнее, если данные нужно тянуть из Excel или JSON.
```java
@DataProvider(name = "loginData")
public Object[][] getData() {
    return new Object[][] { {"admin", "123"}, {"user", "456"} };
}

@Test(dataProvider = "loginData")
public void loginTest(String user, String pass) { ... }
```

## 4. Параллельный запуск (Parallel Execution)
Это то, что отличает Junior от Senior. Тесты должны летать.

*   **В JUnit 5:** Настраивается через файл `junit-platform.properties` в папке `resources`. Нужно указать `junit.jupiter.execution.parallel.enabled = true`.
*   **В TestNG:** Настраивается через `testng.xml` (атрибут `parallel="methods"`).

> **Нюанс от Senior:** При параллельном запуске будь крайне осторожен с **статическими переменными**. Если ты сохранишь состояние браузера в статическую переменную, один тест может "украсть" сессию у другого. Selenide сам управляет драйвером через `ThreadLocal`, поэтому он безопасен, но твой код — нет.

## 5. Интеграция с Allure (Reporting)
Чтобы отчеты не были бесполезными кусками текста, используй аннотации:
*   `@Step("Описание действия")` — разбивает тест на понятные шаги в отчете.
*   `@Attachment` — прикрепляет скриншоты или логи к шагу.

### ❓ FAQ (Частые вопросы)

**В: Нужно ли вызывать `close()` или `quit()` в `@AfterEach`?**
**О:** В Selenide это делать **не обязательно**. Selenide сам закроет браузер, когда завершится процесс. Но если ты хочешь переиспользовать одну сессию для нескольких тестов (для скорости), используй `Selenide.closeWebDriver()` только в `@AfterAll`.

**В: Как передать настройки из CI/CD (например, Jenkins или GitLab) в тест?**
**О:** Используй системные свойства Java (`System.getProperty`). В коде пишем `Configuration.browser = System.getProperty("browser")`, а в пайплайне запускаем: `mvn test -Dbrowser=firefox`. Это делает твои тесты гибкими.

**В: Что делать, если один тест упал и "засорил" следующий?**
**О:** Всегда используй очистку состояния (`clearBrowserCookies`, `clearBrowserLocalStorage`) в `@AfterEach`. Тесты должны быть **изолированными (atomic)**. Падение одного теста не должно влиять на результат другого.

**В: Чем JUnit 5 лучше TestNG для Selenide?**
**О:** JUnit 5 более современный, у него мощная система расширений (Extensions) вместо старых Listeners, и он лучше интегрирован с современным стеком Java. Но TestNG всё еще незаменим, если тебе нужна сложная логика зависимостей между тестами (`dependsOnMethods`).

# 📊 Allure Report: Ultimate Cheat Sheet

**Allure Report** — это не просто «красивые графики». Это инструмент для создания интерактивных отчетов, которые превращают сырые логи выполнения тестов в понятную историю: что проверяли, как прошли тесты, где именно упали и какие скриншоты это подтверждают.

### 🛠 1. Интеграция (Setup)
Чтобы Allure "подружился" с Selenide и JUnit 5, тебе нужны правильные зависимости в `pom.xml` (Maven) или `build.gradle`.

**Что должно быть в проекте:**
*   `allure-junit5` — адаптер для запуска тестов.
*   `allure-selenide` — **самый важный модуль**. Он автоматически прикрепляет скриншоты и DOM-дерево к отчету при падении теста.

**Магическая строчка кода:**
Чтобы Selenide начал "отдавать" данные в Allure, нужно добавить Listener в класс с базовыми настройками (обычно в `@BeforeAll`):
```java
SelenideLogger.addListener("AllureSelenide", new AllureSelenide()
    .screenshots(true) // Прикреплять скриншоты
    .savePageSource(true)); // Прикреплять исходный код страницы
```

---

### 🏷 2. Аннотации: Структура и Смысл
Без аннотаций твой отчет — это просто список имен методов. Аннотации превращают его в документацию.

#### Группировка (Behavior Driven Development):
*   `@Epic` — высший уровень (например, "Авторизация").
*   `@Feature` — функциональная область ("Вход через Google").
*   `@Story` — конкретный сценарий/кейс ("Ошибка при неверном пароле").

#### Детализация:
*   `@Description("Текст")` — подробное описание того, что делает тест.
*   `@Severity(SeverityLevel.CRITICAL)` — уровень важности (blocker, critical, normal, minor, trivial). Помогает понять, на какие тесты смотреть в первую очередь при падении.
*   `@Owner("Имя")` — кто отвечает за этот тест/функционал.
*   `@TmsLink("ID")` / `@Issue("ID")` — ссылки на Test Management System (например, TestRail) или баг-трекер (Jira). Это связывает автотесты с требованиями и багами.

#### Логирование действий:
*   `@Step("Текст")` — **самая важная анмутация**. Она оборачивает метод в красивый шаг в отчете. Если тест упадет внутри метода, ты увидишь конкретный шаг, на котором это случилось.

---

### 📸 3. Attachments (Вложения)
Помимо автоматических скриншотов от `AllureSelenide`, ты можешь вручную прикреплять что угодно:
```java
// Прикрепить текстовый лог или JSON
Allure.addAttachment("Logs", "text/plain", "Текст твоего лога");

// Прикрепить файл (например, загруженный пользователем)
Allure.addAttachment("Uploaded File", new ByteArrayInputStream(fileBytes));
```

### 🚀 4. Жизненный цикл отчета
1.  **Запуск тестов:** JUnit запускает тесты $\rightarrow$ Allure генерирует файлы в папке `allure-results` (это JSON-файлы).
2.  **Генерация отчета:** Сами по себе JSON-файлы не читаемы. Тебе нужно запустить команду:
    *   `allure serve allure-results` — запускает локальный сервер и сразу открывает красивый HTML в браузере.
    *   `allure generate allure-results --clean` — создает статичную папку `allure-report`, которую можно залить на CI/CD (Jenkins, GitLab).

### 🧠 Senior's Nuances (Нюансы и советы)

1.  **Не злоупотребляй `@Step`:** Не нужно вешать `@Step` на каждый чих (типа `click()`). Вешай его на высокоуровневые действия бизнес-логики: `loginPage.loginAs(user)` или `orderPage.checkout()`. Отчет должен читаться как сценарий, а не как лог нажатий клавиш.
2.  **Чистота данных:** Если ты используешь `@Step` в Page Objects, помни, что параметры метода (например, `username`) автоматически попадут в название шага. Это очень удобно для дебага.
3.  **Скриншоты при падении:** Всегда проверяй, что `AllureSelenide` настроен. Нет ничего хуже, чем упавший тест без скриншота — это заставляет разработчиков переспрашивать "А что именно упало?".

# 📝 Шпаргалка: Логирование в Selenide & Java

**Логирование** — это не просто «печать текста в консоль». В автоматизации это твой единственный след (trace), который позволяет понять, что произошло в момент падения теста на удаленном сервере (Jenkins/GitLab CI), где ты не можешь нажать "Debug".

Мы разделим логирование на 3 уровня: **Selenide Logs**, **Allure/Reporting** и **Application/Test Logs**.

---

### 1. Уровень Selenide: Автоматический лог действий
Selenide — это «умная» обертка. Его главная фишка в том, что он **уже** логирует почти всё за тебя.

*   **Что логирует:** Каждое взаимодействие с элементом (`click`, `setValue`, `shouldBe`). Если тест падает на ожидании, Selenide выведет в консоль: *«Element not found: By.cssSelector(".btn")»*.
*   **Как это работает:** Тебе не нужно ничего настраивать для базовых логов. Он пишет в `System.out`.
*   **Нюанс (Pro Tip):** Если ты видишь в логах кашу, помни: Selenide логирует **состояние**, а не просто нажатие. Он пишет: *"Element should be visible"*. Это критически важно для понимания, на каком именно `Condition` упал тест.

### 2. Уровень Allure: Визуальное логирование (Reporting)
В серьезных проектах никто не смотрит в консоль Jenkins. Все смотрят в **Allure Report**. Здесь логирование превращается в «шаги».

*   **`@Step`**: Самый важный инструмент. Позволяет превратить программный код в человекочитаемый отчет.
    ```java
    @Step("Авторизация пользователя с логином {login}")
    public void login(String login, String password) {
        $(By.id("user")).setValue(login);

        $(By.id("pass")).setValue(password);
        $(By.id("submit")).click();
    }
    ```
*   **Attachments (Вложения)**: Логирование не только текста, но и артефактов.
    *   **Screenshots**: Автоматически при падении (через Selenide + Allure Listener).
    *   **Page Source**: Состояние DOM в момент ошибки.
    *   **Custom Attachments**: Можно логировать JSON-ответы от API или файлы.

### 3. Уровень SLF4J / Logback: Профессиональное логирование кода
Забудь про `System.out.println()`. Это моветон. В промышленной разработке используют фреймворки (SLF4J + Logback/Log4j2).

*   **Почему это важно:** Ты можешь управлять **уровнем детализации** без изменения кода.
    *   `ERROR`: Критические ошибки (тест упал).
    *   `WARN`: Подозрительные моменты (например, элемент нашелся, но через 5 секунд ожидания).
    *   `INFO`: Основные этапы теста (начало сценария, переход на страницу).
    *   `DEBUG`: Детальная информация для разработчиков (содержимое строк, ID элементов).
*   **Пример использования:**
    ```java
    private static final Logger logger = LoggerFactory.getLogger(MyTest.class);

    @Test
    void testExample() {
        logger.info("Начинаем тест регистрации");
        // ... код теста
        logger.debug("Текущий URL: {}", WebDriverRunner.getWebDriver().getCurrentUrl());
s    }
    ```

---

### 💡 Нюансы от Senior'а (на чем валятся джуны)

1.  **Логирование секретов:** **НИКОГДА** не логируй пароли, токены или персональные данные пользователей в `INFO` или `DEBUG`. Если эти логи попадут в систему сбора логов (например, Kibana), это будет дыра в безопасности.
2.  **Log Noise (Шум):** Не делай слишком много `logger.info`. Если у тебя 1000 тестов и каждый пишет по 50 строк — твой отчет станет нечитаемым, а хранилище логов забьется. Логируй только **значимые события**.
3.  **Синхронизация:** Помни, что логи в консоли (System.out) и шаги в Allure — это разные потоки информации. Всегда старайся, чтобы они дополняли друг друга, а не дублировали одно и то же бесполезно.

---

### ❓ FAQ (Частые вопросы)

**В: Почему я не вижу свои `logger.info` в Allure Report?**
**О:** Потому что `SLF4J` пишет в консоль/файл, а Allure читает аннотации `@Step`. Чтобы увидеть логи в Allure, тебе нужно использовать либо `Allure.step()`, либо настроить специальный Listener, который перехватывает логи и прикрепляет их как Attachment.

**В: Можно ли через Selenide логировать ошибки из консоли браузера (Console Logs)?**

**В: Что лучше использовать для логирования шагов: `@Step` или `Allure.step("текст")`?**
**О:** Если шаг — это метод Page Object, используй `@Step`. Это чище и позволяет переиспользовать код. Если шаг — это разовое действие внутри теста (например, проверка конкретного значения), используй лямбда-выражение `Allure.step("Проверка заголовка", () -> { ... });`.

# 🏗️ Page Object Model (POM) — Senior's Guide

**Page Object Model** — это паттерн проектирования, цель которого — разделить **тестовую логику** (что мы проверяем) и **структуру страницы** (как мы находим элементы).

Представь, что тест — это сценарий фильма, а Page Object — это декорации. Если декорации изменятся (кнопка станет синей вместо красной), тебе не нужно переписывать весь сценарий, достаточно поправить один "объект" декораций.

### 🎯 Основные принципы

1.  **Инкапсуляция:** Тест не должен знать про `xpath` или `cssSelector`. Он должен вызывать метод `.login()`, а не `.click("#submit-btn")`.
2.  **Single Responsibility (Принцип единственной ответственности):** Один класс — одна страница (или один крупный компонент).
3.  **No Assertions in Page Objects:** Это золотое правило. **В Page Object не должно быть `should()`, `assertEquals` и прочего.** Страница должна уметь *действовать* и *предоставлять данные*, но решать, "прошел тест или нет" — задача самого теста.
    *   *Исключение для Senior:* Ты можешь использовать `shouldBe(visible)` внутри методов страницы, чтобы убедиться, что действие выполнилось успешно (внутренняя проверка состояния), но финальный результат проверки — в тесте.

### 🛠️ Структура идеального Page Object

Хороший Page Object состоит из трех частей:
1.  **Locators (Поля):** Объявление `SelenideElement`.
2.  **Actions (Методы):** Методы, которые совершают действия (клик, ввод текста).
3.  **Fluent Interface (Цепочки):** Возврат `this` или нового Page Object для написания тестов в одну строку.

#### Пример реализации

```java
// 1. Класс страницы Login Page
public class LoginPage {
    // Locators - скрыты внутри класса
    private final SelenideElement usernameField = $("#username");
    private final SelenideElement passwordField = $("#password");
    private final SelenideElement loginButton = $("#login-submit");

    // Метод открытия страницы
    public LoginPage openPage() {
        Selenide.open("/login");
        return this; // Возвращаем текущий объект для цепочки
    }

    // Action - действие, которое возвращает НОВЫЙ Page Object (Dashboard)
    public DashboardPage login(String user, String pass) {
        usernameField.setValue(user);
        passwordField.setValue(pass);
        loginButton.click();
        return new DashboardPage(); // Переход на другую страницу
    }
}

// 2. Класс страницы Dashboard Page
public class DashboardPage {
    private final SelenideElement welcomeMessage = $(".welcome-text");

    public String getWelcomeText() {
        return welcomeMessage.getText();
    }
}

// 3. Сам Тест (Clean & Readable)
@Test
void successfulLoginTest() {
    new LoginPage()
        .openPage()
  	    .login("admin", "12345") // Мы не знаем, как работает login, мы просто вызываем его
        .getWelcomeText()
        .shouldBe(text("Welcome, admin!")); // Проверка — здесь!
}
```

### 🧩 Продвинутый уровень: Page Components
Когда страница становится огромной (например, Facebook или Jira), создавать один класс на всю страницу — это самоубийство. Используй **Components**.
*   Выноси `Header`, `Sidebar`, `Footer` в отдельные маленькие классы.
*   В основном Page Object просто объявляй их как поля.

### ⚠️ Нюансы и "подводные камни" (Senior Insights)

1.  **Проблема "Too much logic":** Не пиши в методах страниц сложную логику с циклами и условиями. Если метод страницы превращается в алгоритм — выноси его в отдельный Helper или Service.
2.  **Зависимость от порядка:** Метод `login()` должен возвращать объект следующей страницы (`DashboardPage`). Это создает "рельсы", по которым тест едет сам, не давая тебе ошибиться в логике переходов.
3.  **Locators visibility:** Всегда делай поля с локаторами `private`. Если ты сделаешь их `public`, разработчики тестов начнут использовать их напрямую, и смысл POM исчезнет.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Почему нельзя использовать Assertions внутри Page Object?**
**О:** Это нарушает принцип разделения ответственности. Если ты добавишь `assert` в метод `login()`, то при изменении логики проверки тебе придется переписывать не только тесты, но и сами объекты страниц. Тест должен быть "правдой", а Page Object — лишь инструментом для достижения этой правды.

**В: Что такое Fluent Interface в контексте POM?**
**О:** Это практика возврата `this` (текущего объекта) или нового объекта страницы из методов. Это позволяет писать тесты в стиле "череды действий" (`page.open().doSomething().doAnotherThing()`), что делает код максимально читаемым, почти как человеческий язык.

**В: Как быть, если на странице много одинаковых элементов (например, список товаров)?**
**О:** Не делай отдельный Page Object для каждого товара. Создай один класс `ProductComponent`, который описывает один товар, и используй коллекцию `$$(".product-item").map(ProductComponent::new)` в основном Page Object. Это называется паттерном "Component".

# 🧠 Cheat Sheet: Page Elements vs. Page Objects

В автоматизации на Selenide важно понимать разницу между **«Что это?»** (элемент) и **«Что страница умеет делать?»** (объект). Если ты смешаешь их в одну кучу, твои тесты станут хрупкими и нечитаемыми.

### 1. Page Elements (Элементы страницы)
Это низкоуровневые «кирпичики». В Selenide это объекты типа `SelenideElement` или коллекции `ElementsCollection`.

*   **Суть:** Это просто ссылки на локаторы (CSS, XPath). Они не знают о бизнес-логике.
*   **Задача:** Хранить информацию о том, *как найти* кнопку, поле ввода или заголовок.
*   **Пример:** `private SelenideElement loginButton = $("#login");`

### 2. Page Objects (Объекты страниц)
Это высокоуровневые «сценарии». Это классы, которые представляют целую страницу или её логическую часть.

*   **Суть:** Это абстракция над интерфейсом. Вместо того чтобы говорить тесту «кликни по этому ID», ты говоришь «выполни вход».
*   **Задача:** Инкаплосировать (скрыть) детали реализации. Тест не должен знать, какой там CSS-селектор у кнопки. Он должен знать только метод `.login()`.
*   **Пример:** `public void login(String user, String pass) { ... }`

---

### ⚖️ Сравнение: В чем ключевая разница?

| Характеристика | Page Elements (Элементы) | Page Objects (Объекты) |
| :--- | :--- | :--- |
| **Уровень абстракции** | Низкий (Технический) | Высокий (Бизнес-логика) |
| **Что содержит** | Селекторы и `SelenideElement` | Методы действий (`click`, `fill`, `verify`) |
| **Видимость в тестах** | **Скрыты (private)** | **Доступны (public)** |
| **Цель** | Найти элемент на странице | Описать поведение страницы |

---

### 🛠 Senior-подход: Как это проектировать правильно

#### ❌ Плохо (Anti-pattern: "Fat" Page Object / Leakage)
Ты выставляешь элементы наружу. Тест сам вызывает `.click()`. Если селектор изменится, тебе придется переписывать 100 тестов.
```java
// В Page Object
public SelenelleElement loginButton = $("#login"); // ОШИБКА: элемент публичный!

// В Тесте
loginPage.loginButton.click(); // ОШИБКА: тест знает про селектор
```

#### ✅ Хорошо (Encapsulation & Fluent Interface)
Элементы спрятаны внутри класса. Тест взаимодействует только с методами.
```java
public class LoginPage {
    // Элементы скрыты (private)
    private SelenideElement usernameField = $("#user");
    private SelenideElement passwordField = $("#pass");
    private SelenideElement submitButton = $("#submit");

    // Метод описывает действие (Action)
    public void login(String user, String pass) {
        usernameField.setValue(user);
        passwordField.setValue(pass);
        submitButton.click();
    }
}

// В Тесте
loginPage.login("admin", "1234"); // Чисто и понятно
```

### 🚀 Продвинутый уровень: Page Components
Когда проект растет, делать один класс на всю страницу — плохая идея. Используй **Components**.
Если у тебя есть «Шапка сайта» (Header), которая есть на всех страницах, не копируй её элементы в каждый Page Object. Создай отдельный класс `HeaderComponent`.

**Иерархия:**
`LoginPage` $\rightarrow$ содержит $\rightarrow$ `HeaderComponent`, `LoginFormComponent`, `FooterComponent`.

**В: Можно ли использовать `SelenideElement` прямо в коде теста?**
**О:** Технически — можно, Selenide это позволяет. Но архитектурно — **категорически нет**. Это нарушает принцип инкапсуляции. Если селектор изменится, ты "поплывешь" по всему проекту.

**В: Что такое Fluent Interface в контексте Page Objects?**
**О:** Это когда методы Page Object возвращают `this` (текущий объект) или новый объект страницы. Это позволяет строить цепочки:

**В: Должен ли Page Object содержать проверки (assertions)?**

# 🧩 Page Component Pattern (PCP)

### Что это такое?
Если **Page Object Model (POM)** — это когда мы описываем целую страницу как один большой класс, то **Page Component Pattern** — это когда мы разбиваем страницу на маленькие, независимые и переиспользуемые «кирпичики» (компоненты). 

Представь себе конструктор LEGO. Вместо того чтобы каждый раз собирать замок с нуля, у тебя есть готовые детали: «окно», «дверь», «башня». В веб-автоматизации такими деталями выступают **Header**, **Footer**, **Sidebar**, **Table**, **Modal Window** или **Search Bar**.

### Зачем это нужно? (Проблема vs Решение)
*   **Проблема (Pure POM):** У тебя есть 10 страниц, и на каждой есть `Header`. Если разработчики изменят ID кнопки в хедере, тебе придется править 10 классов страниц. Это кошмар поддержки.
*   **Решение (PCP):** Ты создаешь один класс `HeaderComponent`. Меняешь локатор в одном месте — он обновляется везде.

### Основная идея реализации в Selenide
Ключевой секрет Senior-подхода: **Изоляция области поиска (Scope)**. 
Компонент не должен искать элементы по всему `document`. Он должен искать элементы **внутри себя**. В Selenide это реализуется через использование `SelenideElement` в качестве «корня» (root) компонента.

---

### 🛠 Пример реализации

#### 1. Создаем базовый компонент
Каждый компонент должен знать, где его границы.

```java
public class HeaderComponent {
    // Это "корень" нашего компонента — контейнер, в котором лежит весь хедер
    private final SelenideElement root;

    public HeaderComponent(SelenideElement root) {
        this.root = root;
    }

    // Мы ищем элементы НЕ через $, а через root.$
    private final SelenideElement logo = root.$(".logo");
    private final SelenideElement loginButton = root.$(".btn-login");
    private final SelenideElement logoutButton = root.$(".btn-logout");

    public void clickLogin() {
        loginButton.click();
    }

    public boolean isLogoVisible() {
        return logo.isDisplayed();
    }
}
```

#### 2. Используем компонент на странице
Страница теперь не содержит логику хедера, она его **содержит**.

```java
public class LoginPage {
    // Находим контейнер хедера на этой конкретной странице
    private final HeaderComponent header = new HeaderComponent($("header.main-header"));
    
    // Элементы самой страницы
    private final SelenteideElement usernameField = $("#username");
    private final SelenideElement passwordField = $("#password");

    public void login(String user, String pass) {
        usernameField.setValue(user);
        passwordField.setValue(pass);
        // Мы вызываем метод компонента, не зная о его внутренней структуре
        header.clickLogin(); 
    }
}
```

---

### 💡 Нюансы и Senior-советы

1.  **Composition over Inheritance (Композиция вместо наследования):** Не пытайся сделать так, чтобы все страницы наследовались от `BasePage`, который содержит в себе всё. Это приведет к "Божественному объекту" (God Object), который знает слишком много. Используй композицию: страница *содержит* компоненты.
2.  **Scope Isolation:** Всегда используй `root.$` или `root.$$`. Если ты внутри компонента напишешь `$(".button")`, Selenide будет искать кнопку по всей странице, и если на странице две кнопки, тест может упасть или сработать непредсказуемо.
3.  **Граничные условия:** Компонент должен отвечать только за то, что находится внутри его DOM-узла. Если кнопка «Выйти» вылетает в отдельное модальное окно вне хедера — это уже другой компонент (`ModalComponent`).
4.  **Динамические компоненты:** Для компонентов вроде `Table` или `Dropdown`, передавай в конструктор не просто корень, а параметры (например, ID таблицы), чтобы один класс мог обслуживать разные таблицы на сайте.

### ❓ FAQ (Частые вопросы)

**В: Когда мне стоит превращать Page Object в Component?**
**О:** Как только ты поймал себя на том, что копируешь одни и те же локаторы или методы из одного класса страницы в другой. Если элемент повторяется $\ge 2$ раз — это компонент.

**В: Не усложнит ли это структуру проекта?**

**В: Что делать, если компонент "размазан" по DOM? (Например, Header в одном месте, а Logout-меню — в самом низу body)**
**О:** В этом случае создавай два разных компонента. Один — `HeaderComponent` (с логотипом), второй — `UserMenuComponent` (с выпадающим списком). Тест просто будет взаимодействовать с ними по очереди.

**В: Можно ли использовать Page Component Pattern вместе с Selenium Actions?**
**О:** Да, конечно. Внутри методов компонента ты можешь использовать любые сложные взаимодействия (drag-and-drop, hover), скрывая сложность реализации от конечного теста.

# 🧠 Шпаргалка: Fluent Interface (Текучий интерфейс)

### 🎯 Что это такое?
**Fluent Interface** — это паттерн проектирования, при котором методы объекта возвращают сам этот объект (`return this;`) или новый объект. Это позволяет выстраивать **цепочки вызовов** (method chaining), превращая код из набора разрозненных строк в читаемое предложение.

В контексте автотестов это создание своего мини-языка (**DSL — Domain Specific Language**), который описывает шаги пользователя.

---

### 🛠 Как это работает (Механика)
Главный секрет прост: каждый метод, который не должен прерывать цепочку, обязан возвращать `this`.

**Плохо (Imperative Style - "Как делать"):**
Код выглядит как список инструкций. Трудно читать логику процесса.
```java
loginPage.enterUsername("admin");
loginPage.enterPassword("12345");
loginPage.clickLogin();
dashboardPage.checkWelcomeMessage();
```

**Хорошо (Fluent Style - "Что происходит"):**
Код читается как сценарий. Мы фокусируемся на бизнес-логике.
```java
loginPage.loginAs("admin", "12345") // Метод вернул DashboardPage
          .verifyWelcomeMessage("Welcome, Admin!"); 
```

---

### 🚀 Применение в Page Object Model (POM)

Как Senior, я настаиваю: Fluent Interface в Page Objects — это не просто "красиво", это стандарт индустрии. Но есть два уровня реализации:

#### Уровень 1: Возврат текущей страницы (`return this`)
Используется для действий на одной и той же странице (например, заполнение формы).
```java
public class RegistrationPage {
    public RegistrationPage enterEmail(String email) {
        emailField.setValue(email);
        return this; // Важно! Возвращаем текущий объект
    }

    public Registration-Page fillName(String name) {
        nameField.setValue(name);
        return this; 
    }

    public DashboardPage submit() {
        submitButton.click();
        return new DashboardPage(); // Возвращаем НОВУЮ страницу
    }
}
```

#### Уровень 2: Переход между страницами (Page Transitions)
Это "высший пилотаж". Метод, который инициирует переход (клик по кнопке, переход по ссылке), должен возвращать объект **следующей** страницы. Это позволяет тесту "перетекать" из одного состояния в другое.

---

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Проблема "Разрыва цепи":** Если ты забудешь написать `return this;` хотя бы в одном методе, цепочка прервется, и компилятор выдаст ошибку. Твой метод станет `void`, и следующий вызов не сможет прикрепиться к нему.
2.  **Слишком длинные цепочки:** Не пытайся запихнуть весь тест в одну строку на 20 методов. Если цепочка занимает три экрана — это плохой тон. Тест становится невозможно дебажить (сложно понять, на каком именно методе внутри строки всё упало).
3.  **Смешивание логики:** Не смешивай в одной цепочке *действия* (click, setValue) и *проверки* (shouldBe, shouldHave). 
    *   *Правильный подход:* `page.login().verifyDashboard();`
    *   *Плохой подход:* `page.login().checkEmail("admin").clickSubmit().checkSuccess();` (Здесь проверка ломает поток действий).
4.  **Атомарность:** Каждый метод в цепочке должен делать одну логическую вещь.

**В: Помогает ли Fluent Interface в отладке?**
**О:** И да, и нет. **Да**, потому что код понятен. **Нет**, если цепочка слишком огромная — при падении в логах будет указана одна строка, и тебе придется гадать, какой именно метод из десяти внутри этой строки не сработал. *Совет: разбивай длинные цепочки на логические блоки.*

**В: Можно ли использовать Fluent Interface вместе с Selenide?**
**О:** Да, Selenide сам по себе построен на принципах Fluent API. Его методы `shouldBe()`, `shouldHave()` и поиск элементов `$` спроектированы так, чтобы их можно было комбинировать.

**В: Что важнее: возвращать `this` или новый объект страницы?**

**В: Не превратится ли мой код в "спагетти", если я буду постоянно возвращать новые страницы?**
**О:** Если ты правильно спроектировал Page Objects, то наоборот — код станет структурированным. "Спагетти" получается там, где нет четкого разделения на страницы и методы переходов.

# 🔍 Тема: Анализ ошибок (Error Analysis)

В Selenide ошибки делятся на две большие группы: **ошибки твоего ожидания** (когда Selenide честно пытался, но не смог) и **ошибки состояния браузера/драйвера** (когда всё сломалось на более низком уровне).

### 1. Ошибки ожиданий (The `should` failures)
Это самые «красивые» ошибки. Selenide не просто упал, он ждал положенное время (`timeout`) и выдал подробный отчет.

*   **`ElementShould` / `ElementShouldNot`**: 
    *   **Суть:** Ты написал `.shouldBe(visible)`, но элемент так и не появился или исчез слишком быстро.
    *   **Что внутри сообщения:** Selenide пишет: *"Element should be visible; actual: hidden"*. Он четко говорит: «Я ждал видимости, а получил скрытость».
    *   **Нюанс (Senior Tip):** Всегда смотри на **последнее состояние**. Если ошибка `ElementShould` с текстом `expected: text "Login", actual: text "Error"`, значит, проблема не в поиске элемента, а в логике приложения (вместо успеха пришла ошибка).

### 2. Ошибки «Призраков» (Stale Element)
*   **`StaleElementReferenceException`**:
    *   **Суть:** Ты нашел элемент, но перед тем как кликнуть, страница обновилась (DOM перерисован), и старая ссылка на элемент стала невалидной.
    *   **Нюанс:** Selenide — умный фреймворк. Он **автоматически делает ретраи (повторные попытки)** при этой ошибке. Если ты видишь её в логах, но тест проходит — это нормальная работа механизма защиты. Если тест падает — значит, элемент исчезает слишком быстро или страница обновляется слишком агрессивно.

### 3. Ошибки тайм-аутов (TimeoutException)
*   **`TimeoutException`**:
    *   **Суть:** Время ожидания истекло.
    *   **Нюанс:** Не спеши увеличивать `Configuration.timeout`. Если таймаут растет, это симптом «больного» приложения или медленного API. Проверь, не висит ли на странице тяжелый лоадер (spinner), который блокирует выполнение.

### 4. Ошибки инфраструктуры и драйвера
*   **`WebDriverException` / `SessionNotCreatedException`**:
    *   **Суть:** Проблема в «железе» или окружении. Браузер упал, версия ChromeDriver не совпадает с версией Chrome, или Docker-контейнер с браузером перезагрузился.
    *   **Что делать:** Это не ошибка теста, это ошибка настройки CI/CD или инфраструктуры.

---

### 🛠 Инструменты дебага (Твой джентльменский набор)

Когда тест упал, Senior не гадает на кофейной гуще, он смотрит три вещи:

1.  **Screenshot:** Selenide по умолчанию делает скриншот при падении. Это твой главный свидетель. Смотри на него: возможно, перед элементом висит модальное окно или баннер, который ты не учел.
2.  **Page Source:** Если на скриншоте всё ок, но элемент «не найден» — смотри HTML-код. Возможно, текст элемента подгружается динамически через JS и в момент ошибки его еще нет в DOM.
*   **Logs (Selenide + Browser):** Проверяй консоль браузера (через `LogViewer` или настройки драйвера). Часто причина падения теста кроется в ошибке `404` или `500` в сетевых запросах, которые ты не видишь в коде автотеста.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Почему я вижу `NoSuchElementException` вместо Selenide-ошибки?**
**О:** Скорее всего, ты используешь чистый Selenium WebDriver внутри теста или обращаешься к элементу через `driver.findElement()`. Selenide-ошибки возникают только тогда, когда ты используешь его обертки (`$`, `$$`) и методы `.should()`.

**В: Тест падает с ошибкой, что элемент не кликабелен, хотя я его вижу на скриншоте. В чем причина?**

**В: Как быстро понять, что проблема в коде теста, а не в приложении?**
**О:** Если ошибка `ElementShould` показывает правильный текст/состояние, но тест все равно падает — проверь свои селекторы. **В: Поможет ли `Thread.sleep()` исправить ошибку `ElementNotFound`?**
**О:** (Злой взгляд Senior-а) **Нет.** Это плохая практика. Если `Thread.sleep` помогает, значит, ты не используешь механизмы умных ожиданий Selenide или неправильно настроил таймауты. Исправляй селектор или жди правильного `Condition`.

# 📸 Скриншоты и Page Source в Selenide

Когда тест падает (особенно в CI/CD, где нет живого браузера), у тебя есть только два «свидетеля» произошедшего: **картинка** того, что видел браузер, и **HTML-код** того, что было в DOM.

## 1. Скриншоты (Screenshots)

Скриншот — это твой главный инструмент визуальной диагностики.

### 🤖 Автоматические скриншоты
Главная «киллер-фича» Selenide: **он сам делает скриншот при падении теста**. Тебе не нужно писать `try-catch` или дополнительные слушатели (listeners), если ты используешь стандартную конфигурацию.
*   **Где искать:** По умолчанию они сохраняются в папку `build/reports/tests` (для Gradle) или `build/test-results`.

### 🛠 Ручные скриншоты
Иногда нужно сделать скриншот в середине теста для отчетности (например, чтобы подтвердить, что модальное окно открылось).

*   **Весь экран (Viewport):**
    ```java
    import static com.codeborne.selenide.Selenide.*;

    screenshot("my_test_step"); // Создаст файл my_test_step.png
    ```
*   **Скриншот конкретного элемента:**
    Это мега-полезно, когда на странице много элементов и ты хочешь сфокусироваться только на кнопке или карточке товара.
    ```java
    $(".product-card").screenshot("product_card_view");
    ```

### ⚠️ Нюансы (Senior Tips)
1.  **Viewport vs Full Page:** По умолчанию Selenium/Selenide делает скриншот только **видимой области** (viewport). Если элемент находится внизу страницы, ты его не увидишь. Чтобы увидеть всё, нужно сначала проскроллить к элементу (`scrollTo()`).
2.  **Перезапись:** Если ты даешь одинаковые имена скриншотам, старые могут перезаписываться или создаваться файлы с суффиксами. Всегда используй уникальные имена (например, добавляй timestamp или название теста).
3.  **Интеграция с Allure:** В реальных проектах скриншоты прикрепляют к Allure-отчету через `@Attachment`. Без этого скриншоты будут просто лежать в папке `build`, и ты о них забудешь.

## 2. Page Source (Исходный код страницы)

Page Source — это текстовый слепок всего DOM-дерева в момент выполнения команды.

### 🛠 Как получить
Если тебе нужно проверить наличие какого-то скрытого текста или атрибута, который не виден глазу, но есть в коде:

```java
import static com.codeermone.selenide.Selenide.*;

String html = pageSource(); // Получаем весь HTML страницы в виде String
```

### 🔍 Зачем это нужно?
1.  **Проверка скрытого контента:** Например, проверка атрибута `aria-label` или `data-testid`, которые не отображаются на экране.
2.  **Грубый поиск:** Если ты не хочешь искать конкретный элемент через селектор, а хочешь просто проверить, что строка "Error 404" вообще присутствует в коде страницы.
3.  **Дебаг сложных структур:** Когда `$$(".item")` выдает странный результат, можно выгрузить `pageSource()` в файл и изучить его в текстовом редакторе.

### ⚠️ Нюансы (Senior Tips)
1.  **Производительность:** Вызов `pageSource()` на очень тяжелых страницах (с огромным DOM) может замедлить тест. Не делай это в каждом шаге.
2.  **Динамический контент:** Помни, что `pageSource()` возвращает состояние DOM **на текущий момент**. Если после вызова метода прилетел новый кусок данных через AJAX, старый `html` уже не будет актуален.

**В: Что произойдет, если тест упадет на проверке `shouldBe(visible)`, но скриншот не создался?**

**В: В чем разница между `pageSource()` и тем, что мы видим в "View Source" в браузере?**

**В: Как сохранить Page Source в файл для анализа?**
**О:** Самый простой способ — использовать стандартную Java IO:

```java
Files.writeString(Path.of("page_source.html"), pageSource());
```

# 📸 Тема: Использование `Selenide.screenshot()` вручную

### 💡 Суть
По умолчанию Selenide — это «умный» инструмент, который сам делает скриншот **только в случае падения теста**. Но иногда тебе нужно зафиксировать состояние браузера в конкретный момент времени, когда тест **проходит успешно**, или перед выполнением критически важного действия. 

`Selenide.screenshot()` — это твой ручной «затвор» камеры.

### 🛠 Синтаксис и использование

Для удобства всегда используй статический импорт:
```java
import static com.codeborne.selenide.Selenide.*;
```

**1. Базовый вариант (без имени):**
```java
screenshot(); 
// Создаст файл с автоматическим именем (обычно содержит метку времени)
```

**2. С кастомным именем:**
```java
screenshot("step_after_login"); 
// Создаст файл: step_after_login.png
```

### 🔍 Нюансы и "подводные камни" (Senior Tips)

1.  **Куда сохраняются файлы?**
    Все скриншоты падают в папку, указанную в `Configuration.reportsFolder`. По умолчанию это `build/reports/tests`. Если ты хочешь изменить путь, делай это в `@BeforeAll`:
    ```java
    Configuration.reportsFolder = "target/screenshots";
    ```

2.  **Перезапись файлов:**
    Если ты вызываешь `screenshot("my_step")` дважды в одном тесте, Selenide постарается избежать перезаписи, добавляя суффиксы, но полагаться на это не стоит. Лучше давать уникальные имена для каждого важного этапа.

3.  **Скриншот vs Allure:**
    Если ты используешь **Allure Report**, просто вызвать `screenshot()` недостаточно, чтобы картинка красиво отобразилась в отчете внутри шага. Чтобы скриншот «приклеился» к конкретному шагу Allure, нужно использовать аннотацию `@Step` или метод `Allure.addAttachment`. 
    *Однако, `Selenide.screenshot()` создаст физический файл на диске в любом случае.*

4.  **Производительность:**
    Не делай скриншоты внутри циклов (например, при переборе 100 элементов таблицы). Это сильно замедлит выполнение теста из-за операций записи на диск (I/O operations). Используй их только для ключевых контрольных точек.

5.  **Размер области:**
    Скриншот делает именно **viewport** (видимую область браузера). Если элемент находится за пределами видимости, на скриншоте его не будет, даже если он есть в DOM.

### 🚀 Когда это реально нужно? (Use Cases)

*   **Визуальная верификация:** Тест прошел (зеленый), но ты хочешь убедиться, что верстка не «поехала» (например, при проверке сложных графиков или карт).
*   **Отладка сложного флоу:** Когда тест падает на 10-м шаге из-за ошибки в 5-м, и тебе нужно увидеть промежуточное состояние.
*   **Документация:** Использование скриншотов как артефактов выполнения бизнес-сценария.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Зачем мне делать `screenshot()`, если Selenide и так делает его при ошибке?**
**О:** Автоматический скриншот — это «черный ящик» после аварии. Ручной скриншот — это «видеорегистратор», который фиксирует важные моменты *до* того, как всё сломалось. Он полезен для проверки успешных сценариев (Happy Path).

**В: Можно ли сделать скриншот только части страницы?**
**О:** Напрямую через `Selenide.screenshot()` — нет. Selenide делает снимок всего видимого окна браузера. Если нужен конкретный элемент, придется использовать Selenium WebDriver API или дополнительные библиотеки для обрезки (cropping) изображения.

**В: Что делать, если скриншот пустой или черный?**
**О:** Это часто случается при работе в Headless-режиме (`headless = true`), если браузер не успел отрисовать тяжелый JS-контент. Попробуй добавить небольшую паузу `sleep()` перед скриншотом (хотя это и плохая практика, для дебага это оправдано) или используй более жесткое ожидание `shouldBe(visible)`.

**В: Как прикрепить этот скриншот к Allure, чтобы он был внутри шага?**
**О:** Используй связку:
```java
@Step("Проверка заголовка")
public void checkHeader() {
    $(".header").shouldBe(visible);
    // Этот метод добавит скриншот прямо в отчет Allure
    Allure.addAttachment("Header Screenshot", new ByteArrayInputStream(
        Screenshots.takeScreenshot().getBytes() 
    ));
}
```
*(Примечание: `Screenshots.takeScreenshot()` — это вспомогательный метод, который нужно реализовать или использовать из библиотек интеграции).*

# 🧹 Тема: Очистка данных и состояния перед тестом

### 🎯 Главная цель
Обеспечить **изоляцию тестов**. Каждый тест должен быть **идемпотентным** — это значит, что его результат не должен зависеть от того, запускался он один или после десяти других тестов. Если тест упал на середине, следующий за ним не должен упасть из-за «мусора», оставшегося от предыдущего.

---

### 1. Уровни очистки

#### А. Уровень браузера (Client Side)
Самый простой уровень. Мы чистим то, что хранится внутри сессии пользователя.
*   **Cookies:** Удаление кук предотвращает «подкладывание» старой авторизации.
    *   `Selenide.clearBrowserCookies();`
*   **LocalStorage / SessionStorage:** Очистка локального хранилища (важно для современных SPA-приложений).
    *   `Selenide.executeJavaScript("window.localStorage.clear();");`
    *   `Selenide.executeJavaScript("window.sessionStorage.clear();");`
*   **Зачем:** Чтобы избежать ситуации, когда тест «пролетает» авторизацию, потому что в браузере осталась старая сессия, и падает на этапе проверки профиля.

#### Б. Уровень приложения (Application/API Level) — **Best Practice** ⭐️
Чистить данные через UI (нажимать кнопки «Удалить») — это **антипаттерн**. Это медленно и нестабильно.
*   **Как правильно:** Используй API или прямые запросы к БД.
*   **Механизм:** В методе `@BeforeEach` вызывается скрытый (backdoor) API-метод, который удаляет созданного ранее пользователя, заказ или корзину.
*   **Пример:** `RestAssured.given().delete("/api/orders/" + orderId).perform();`

#### В. Уровень файловой системы
Если тесты работают с загрузками (Downloads).
*   **Что делать:** Перед началом теста очищать папку `downloads`.
*   **Зачем:** Чтобы тест не прошел успешно только потому, что файл с таким же именем уже лежал в папке от прошлого запуска.

---

### 2. Стратегии: "Clean Start" vs "Cleanup After"

| Стратегия | Описание | Плюсы | Минусы |
| :--- | :--- | :--- — | :--- |
| **Pre-test Cleanup** (`@BeforeEach`) | Мы чистим состояние **ДО** начала теста. | Самая надежная. Даже если предыдущий тест упал и не успел почистить за собой, новый тест всё равно начнется с чистого листа. | Может немного увеличивать время выполнения (накладные расходы на очистку). |
| **Post-test Cleanup** (`@AfterEach`) | Мы чистим состояние **ПОСЛЕ** теста. | Кажется логичным: "сделал дело — убрал за собой". | **Опасно.** Если тест упадет (Crash), метод `@AfterEach` может не выполниться или не справиться с очисткой, и «мусор» останется для следующего теста. |

**Senior Advice:** Всегда отдавай предпочтение **Pre-test Cleanup**. Твой приоритет — гарантировать чистое состояние *входа*, а не чистоту *выхода*.

---

### 3. Нюансы и ловушки (Senior Insights)

1.  **Проблема "Загрязнения БД":** Если ты создаешь пользователя в тесте, но не удаляешь его — база данных растет. Со временем это может замедлить тесты или привести к конфликтам уникальных полей (например, `email` уже занят).
2.  **Транзакции:** В интеграционных тестах (не UI) можно использовать `@Transactional`, чтобы после каждого теста база сама откатывалась назад. Но в Selenide (E2E) это не работает, так как браузер и БД — это разные процессы. Здесь только API/SQL.
*   **Скорость vs Надежность:** Не пытайся чистить *всё* перед каждым тестом, если это занимает 30 секунд. Чисти только то, что критично для изоляции конкретного сценария.
3.  **Dependency Injection:** Если ты используешь инструменты вроде Spring, старайся управлять состоянием через контекст, но помни: UI-тесты живут "снаружи" приложения, они не знают о транзакциях внутри него.

### ❓ FAQ (Частые вопросы)

**В: Что если я не могу удалить данные из БД (нет доступа к API/SQL)?**
**О:** Используй подход **"Unique Data Generation"**. Вместо того чтобы удалять старых пользователей, генерируй каждого нового с уникальным префиксом или случайным UUID в email. Это не уберет мусор, но предотвратит конфликты.

**В: Можно ли просто перезапускать браузер каждый раз?**
**О:** `Selenide.open()` при новом запуте создает новую сессию, что очищает куки и кэш. Это хороший базовый уровень, но он не решает проблему данных в БД или файлов на диске.

**В: Почему `@AfterEach` — это плохая идея для очистки?**
**О:** Представь: тест упал из-за `TimeoutException`. Сценарий прервался. Если логика удаления была в `@AfterEach`, и она тоже сломалась (например, элемент не нашел), мусор остался. Следующий тест возьмет этот мусор и упадет по другой причине. Ты получишь "эффект домино", где один баг вызывает цепочку ложных падений.

**В: Как быстро очистить папку загрузок в Java?**
**О:** Используй `FileUtils.cleanDirectory(new File("path/to/downloads"))` из библиотеки Apache Commons IO. Это одна строка и максимальная надежность.

# 🚫 Anti-Patterns: Чего НЕ делать в Selenide

В автоматизации самое дорогое — это **время** (время написания, время выполнения и время на исправление упавших тестов). Эти ошибки делают тесты дорогими и бесполезными.

### 1. Использование `Thread.sleep()` — «Смертный грех»
Это самая частая ошибка новичков. Ты просто останавливаешь поток на фиксированное время (например, 5 секунд), надеясь, что элемент успеет появиться.
*   **Почему это плохо:** Если элемент появился за 1 секунду, ты зря ждешь еще 4. Если интернет лаганул и элемент появился через 6 секунд — тест упадет. Тесты становятся медленными и нестабильными (flaky).
*   **Как правильно:** Используй встроенные механизмы Selenide: `shouldBe(visible)`, `shouldHave(text(...))`. Selenide сам будет опрашивать страницу до победного или пока не выйдет таймаут.

### 2. Игнорирование Smart Waits (Ручные ожидания)
Многие пытаются использовать конструкции типа `WebDriverWait` из чистого Selenium внутри Selenide.
*   **Почему это плохо:** Ты дублируешь функционал, который уже заложен в Selenide. Это усложняет код и делает его перегруженным.
*   **Как правильно:** Доверяй `Condition`. Если стандартного таймаута (4 сек) мало, используй: `element.shouldBe(visible, Duration.ofSeconds(10))`.

### 3. Использование «хрупких» селекторов (Абсолютный XPath)
Пример: `/html/body/div[2]/div[1]/div/div[3]/ul/li[5]/a`
*   **Почему это плохо:** Любое минимальное изменение в верстке (добавили лишний `div`) — и твой тест «сломался», хотя функционал работает. Это превращает поддержку тестов в ад.
*   **Как правильно:** Используй CSS-селекторы, ID, или поиск по тексту/атрибутам (`byText`, `withText`). Селектор должен быть привязан к смыслу (например, кнопка «Login»), а не к позиции в дереве DOM.

### 4. Логика теста внутри тестового метода (Spaghetti Code)
Когда в методе `@Test` перемешаны клики, проверки, поиск элементов и сложные вычисления.
*   **Почему это плохо:** Тест невозможно прочитать как сценарий. Если кнопка изменит ID, тебе придется переписывать десятки тестов вместо одного Page Object.
*   **Как правильно:** Используй паттерн **Page Object** или **Page Components**. В тесте должны быть только действия пользователя и проверки: `loginPage.loginAs(user);`.

### 5. «Захардкоженные» данные и селекторы
Написание `$( ".btn-submit-v2" )` прямо в теле теста.
*   **Почему это плохо:** Если разработчики обновят версию кнопки до `v3`, ты пойдешь искать селектор по всем своим тестам.
*   **Как правильно:** Выноси локаторы в классы страниц (Page Objects), а тестовые данные — в конфигурационные файлы или фабрики данных.

### 6. Использование Selenium-style методов там, где есть Selenide-way
Например, использование `driver.findElement(...)` вместо `$`.
*   **Почему это плохо:** Ты теряешь магию Selenide (автоматические ожидания, удобный синтаксис, автоматические скриншоты при ошибках).
*   **Как правильно:** Всегда используй `$` и `$$`. Если тебе нужно что-то очень специфичное из Selenium, делай это через обертку, но не превращай Selenide-тест в чистый Selenium-тест.

### ❓ FAQ: Часто задаваемые вопросы

**В: Мой тест падает с ошибкой `ElementClickInterceptedException`. Значит, мне нужно добавить `Thread.sleep()`?**
**О:** Нет! Это значит, что поверх элемента находится другой элемент (например, лоадер или всплывающее окно). Вместо сна, дождись исчезновения этого преграды: `$(".loader").shouldBe(hidden)`.

**В: Почему я не могу использовать `Assert.assertEquals` для проверки текста в Selenide?**
**О:** Можешь, но это плохая идея. `Assert` проверяет значение *в момент выполнения*. Если текст еще не успел обновиться (анимация), Assert упадет. А `element.shouldHave(text("..."))` будет ждать появления этого текста, что делает тест стабильным.

**В: Что делать, если я всё же вижу, что элементы появляются слишком медленно и стандартных 4 секунд Selenide не хватает?**
**О:** Не увеличивай глобальный таймаут для всего проекта (это замедлит все тесты). Увеличивай таймаут точечно только для этого конкретного тяжелого элемента: `element.shouldBe(visible, Duration.ofSeconds(15))`.

# 🧠 Best Practices: Как писать автотесты, за которые не стыдно

### 1. Главный закон: Забудь про `Thread.sleep()`
Это «смертный грех» автоматизатора. 
*   **Почему нельзя:** `Thread.sleep(5000)` либо сделает тест слишком медленным (если ждать долго), либо тест упадет (если страница не успела загрузиться). Это создает эффект "flaky tests" (нестабильных тестов).
*   **Как правильно:** Используй механизмы **Smart Waits**, встроенные в Selenide. Selenide сам ждет появления элемента в течение таймаута (по умолчанию 4 сек).
*   **Инструмент:** `element.shouldBe(visible)`, `element.shouldHave(text("Done"))`.

### 2. Стратегия локаторов: Ищи «якоря», а не «пути»
*   **Плохо:** Абсолютные XPath (`/html/body/div[2]/div[1]/form/input`). Любое изменение в верстке — и твой тест мертв.
*   **Плохо:** Привязка к хрупким CSS-классам, которые генерируются динамически (например, классы в React/Angular типа `.css-1abcde`).
*   **Хорошо:** Используй уникальные атрибуты, специально добавленные для тестов: `data-testid`, `data-qa`.
*   **Приоритет:** `id` $\to$ `data-testid` $\to$ `name` $\to$ `cssSelector` (по смыслу) $\to$ `byText`.

### 3. Принцип «Атомарности» тестов
*   **Суть:** Один тест — одна проверяемая бизнес-цель. 
*   **Ошибка:** Делать один огромный тест, который проходит через регистрацию, поиск товара, добавление в корзину и оплату. Если он упадет на этапе оплаты, ты не узнаешь, работает ли корзина.
*   **Как правильно:** Разбей процесс на цепочку маленьких тестов. Используй `BeforeEach` для подготовки состояния (например, логина).

### 4. Page Object & Components: Не превращай классы в помойки
*   **Ошибка:** Писать всю логику страницы в одном огромном классе `MainPage`.
*   **Как правильно:** Используй паттерн **Page Component**. Если на странице есть сложная таблица или боковое меню — вынеси их в отдельные классы-компоненты. Это позволит переиспользовать код (например, `HeaderComponent` будет один для всех страниц).

### 5. Fluent Interface (Текучий интерфейс)
*   **Суть:** Пиши тесты так, чтобы они читались как предложения на английском.
*   **Пример:** 
    *   *Плохо:* `loginPage.enterLogin("admin"); loginPage.enterPass("123"); loginPage.clickSubmit();`
    *   *Хорошо:* `loginPage.loginAs("admin", "123");` (внутри метода скрыта вся цепочка действий).

# 🚫 Anti-patterns (Чего делать НЕЛЬЗЯ)

1.  **Hardcoded Data:** Не пиши пароли и логины прямо в коде теста. Используй конфиги или переменные окружения.
2.  **Overuse of `Selenide.executeJavaScript()`:** Если ты используешь JS-скрипты, чтобы «прокликивать» элементы, которые Selenide не может найти — значит, у тебя проблемы с ожиданиями или локаторами. Это маскирует баги.
*   **Logic Leakage:** Не пиши проверки бизнес-логики внутри Page Object. Page Object должен только *находить* элементы и *взаимодействовать* с ними. Проверки (`shouldBe`) должны быть в тестовом классе.

# ❓ FAQ (Частые вопросы на собеседованиях)

**В: Что делать, если стандартного таймаута Selenide (4с) не хватает для долгого процесса?**
**О:** Не увеличивай глобальный `Configuration.timeout` для всех тестов! Это замедлит все упавшие тесты. Используй локальное ожидание только для этого конкретного элемента: 
`element.shouldBe(visible, Duration.ofSeconds(10));`

**В: В чем разница между `click()` и `press(Keys.ENTER)`?**
**О:** `click()` имитирует физический клик мышью по координатам элемента. `press(Keys.ENTER)` отправляет нажатие клавиши в фокусный элемент. Иногда (при работе с кастомными выпадающими списками) `click()` может не срабатывать из-за перекрытия элемента другими слоями, и тогда стоит проверить логику взаимодействия.

**В: Как проверить, что элемент исчез с экрана?**
**О:** Используй отрицательное условие: `element.shouldNot(exist)` или `element.shouldBe(hidden)`. Это гораздо надежнее, чем пытаться поймать исключение в блоке `try-catch`.

**В: Почему `$$(".items").click()` — это плохая идея?**
**О:** Потому что `$$` возвращает коллекцию. Ты не можешь кликнуть на *всю* коллекцию сразу. Тебе нужно либо выбрать индекс `$$(".items").get(0).click()`, либо отфильтровать её: `$$(".items").findBy(text("Apple")).click()`.
