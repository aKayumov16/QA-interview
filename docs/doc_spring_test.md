# 🧠 Шпаргалка: JUnit 5 (Jupiter)

**JUnit 5** — это не просто обновление JUnit 4. Это модульная платформа. Она состоит из **JUnit Platform** (движок для запуска), **JUnit Jupiter** (новый API для написания тестов) и **JUnit Vintage** (поддержка старых тестов JUnit 3/4).

## 1. Жизненный цикл теста (Lifecycle)
Управление состоянием — это самое важное. Тебе нужно знать, когда создается объект теста и когда очищаются данные.

| Аннотация | Когда срабатывает | Нюанс от Senior |
| :--- | :--- | :--- |
| `@Test` | Помечает метод как тест. | База. Без неё метода нет в плане выполнения. |
| `@BeforeEach` | Перед **каждым** тестовым методом. | Идеально для инициализации моков или чистой БД. |
| `@AfterEach` | После **каждого** тестового метода. | Используй для очистки временных файлов или сброса кэша. |
| `@BeforeAll` | Один раз перед **всеми** тестами в классе. | **Важно:** Метод должен быть `static` (по умолчанию). |
| `@AfterAll` | Один раз после **всех** тестов в классе. | Для тяжелых операций: закрытие Docker-контейнеров или БД. |
| `@Disabled` | Пропускает тест. | Не оставляй "закомментированные" тесты, используй эту аннотацию с причиной. |
| `@DisplayName` | Задает понятное имя тесту. | Пиши человеческим языком: `"Должен вернуть 404, если юзер не найден"`. |

## 2. Параметризованные тесты (Parameterized Tests)
Чтобы не писать 10 одинаковых тестов для разных входных данных, используй параметры. Это делает код чистым и покрывает больше кейсов.

*   **`@ParameterizedTest`**: Говорит JUnit, что метод принимает аргументы.
*   **Источники данных (`Sources`):**
    *   `@ValueSource`: Простейший вариант (массив примитивов: `int`, `String`, `double`).
    *   `@CsvSource`: Позволяет передавать несколько аргументов в строку (например, `"input, expected"`).
    *   `@MethodSource`: Самый мощный. Ссылается на метод, который возвращает `Stream`, `Iterable` или `Arguments`. Идеально для сложных объектов.

## 3. Assertions (Проверки)
JUnit предоставляет базовый класс `Assertions`, но в реальной разработке мы часто используем **AssertJ** (он более "текучий" и читаемый).

*   `assertEquals(expected, actual)` — проверка на равенство.
*   `assertNotEquals(unexpected, actual)` — проверка на неравенство.
*   `assertTrue(condition)` / `assertFalse(condition)` — проверка логики.
*   `assertNull(object)` / `assertNotNull(object)` — проверка на наличие объекта.
*   **`assertThrows(Exception.class, () -> { ... })`** — **Must have!** Проверка того, что твой код правильно кидает исключение при ошибке.

## 4. Продвинутые фишки и нюансы (Senior Tips)

### ⚠️ Нюанс №1: Static vs Non-static Lifecycle
По умолчанию JUnit создает **новый экземпляр класса** для каждого метода `@Test`. Это гарантирует изоляцию.
Если ты хочешь использовать `@BeforeAll` без `static`, тебе нужно добавить аннотацию:
`@TestInstance(TestInstance.Lifecycle.PER_CLASS)`. Но будь осторожен: тесты могут начать влиять друг на друга через общие поля.

### ⚠️ Нюанс №2: Assumptions vs Assertions
*   **Assertion** — это проверка бизнес-логики. Если `assert` провалился $\to$ **Тест упал (Fail)**.
*   **Assumption** — это проверка условий окружения (например, "запускать этот тест только если есть доступ к интернету"). Если `assumeTrue` не прошел $\to$ **Тест пропущен (Skipped)**, а не упал.

### ⚠️ Нюанс №3: Порядок выполнения
По умолчанию порядок тестов не гарантирован. Если тебе критично запустить их по порядку (что само по себе считается плохим тоном в Unit-тестах, но иногда нужно в интеграционных), используй:
`@TestMethodOrder(MethodOrderer.OrderAnnotation.class)` и аннотацию `@Order(1)`.

## ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем разница между JUnit 4 и JUnit 5?**
**О:** JUnit 5 — это модульная архитектура (Platform, Jupiter, Vintage). Он поддерживает Java 8+ функции (лямбды), имеет более мощный API для параметризации и расширений (Extensions вместо Rules) и позволяет гибко настраивать жизненный цикл.

**В: Как протестировать метод, который выбрасывает исключение?**
**О:** С помощью `assertThrows(ExpectedException.class, () -> methodCall())`. Это возвращает объект выброшенного исключения, в котором можно проверить даже сообщение внутри него.

**В: Что делать, если тест зависит от состояния другого теста?**
**О:** **Ничего.** Это "антипаттерн". Тесты должны быть атомарными и независимыми. Если один тест падает и тянет за собой остальные — у тебя проблема с дизайном тестов или очисткой данных в `@AfterEach`.

**В: Чем `Assumptions` отличается от `Assertions`?**
**О:** `Assertions` проверяют правильность кода (результат). `Assumptions` проверяют пригодность среды для теста. Ошибка в `Assertion` — это баг в коде. Ошибка в `Assumption` — это не подходящие условия для запуска теста.

# 🛠 Шпаргалка по Mockito

**Mockito** — это фреймворк для создания **заглушек (mocks)**. Его главная цель — изолировать тестируемый класс от его зависимостей. Вместо того чтобы поднимать тяжелую базу данных или реальный HTTP-клиент, мы подсовываем классу «пустышку», которая ведет себя предсказуемо.

---

### 1. Основные сущности (The Big Three)

*   **`@Mock`**: Создает «чистый» макет. У него нет логики. Если ты не прописал поведение, он вернет `null` для объектов, `0` для чисел и `false` для boolean.
*   **`@Spy`**: «Частичный мок». Это реальный объект, обернутый в Mockito. Он вызывает настоящие методы, если ты не переопределил их поведение. Полезно, когда нужно протестировать часть логики реального класса.
*   **`@InjectMocks`**: Твой «герой» (Subject Under Test). Это тот самый класс, который мы тестируем. Mockito автоматически попытается внедрить в него все созданные `@Mock` и `@Spy` объекты (через конструктор или поля).

---

### 2. Stubbing: Учим мок реагировать
*Stubbing — это процесс настройки ответов мока на вызовы методов.*

**Классический способ:**
```java
when(service.getName(anyString())).thenReturn("John Doe");
```

**Для `void` методов (важный нюанс!):**
Ты не можешь использовать `when()` для void-методов, так как метод будет вызван до того, как Mockito успеет его перехватить. Используй синтаксис `do...`:
```java
doNothing().when(service).deleteUser(anyLong()); // Ничего не делать
doThrow(new RuntimeException()).when(service).save(any()); // Выбросить ошибку
```

**Синтаксис `doReturn` vs `when` (Senior Tip):**
Если ты используешь `@Spy`, лучше использовать `doReturn(...).when(...)`. 
*Почему?* Потому что `when(spy.method()).thenReturn(...)` сначала **вызовет реальный метод** (со всеми его побочными эффектами), а потом применит заглушку. `doReturn` просто подменяет ответ, не вызывая реальный код.

---

### 3. Argument Matchers: Гибкость в условиях
Чтобы не прописывать каждое значение вручную, используй матчеры:
*   `any()`, `anyInt()`, `anyString()`, `any(User.class)` — любой аргумент подходящего типа.
*   `eq("value")` — строгое равенство (обязательно, если ты смешиваешь матчеры с реальными значениями).
*   `argThat(argument -> argument.isAdmin())` — кастомная логика проверки аргумента.

⚠️ **Золотое правило:** Если ты используешь хотя бы один матчер в вызове метода, **все** остальные аргументы этого вызова тоже должны быть матчерами. 
❌ `verify(mock).doSomething(anyString(), "fixed_value");` — **Ошибка!**
✅ `verify(mock).doSomething(anyString(), eq("fixed .fixed_value"));` — **Правильно.**

---

### 4. Verification: Проверка взаимодействия
Просто получить ответ от мока мало. Нужно убедиться, что твой код вообще обратился к зависимости.

*   `verify(mock).method();` — метод был вызван (ровно 1 раз по умолчанию).
*   `verify(mock, times(3)).method();` — ровно 3 раза.
*   `verify(mock, never()).method();` — метод **не** должен был вызываться.
*   `verify(mock, atLeastOnce()).method();` — хотя бы один раз.

---

### 5. ArgumentCaptor: Захват аргументов
Иногда нужно не просто проверить, что метод вызван, а «вытащить» объект, который в него передали, чтобы проверить его внутренние поля.

```java
ArgumentCaptor<UserDto> captor = ArgumentCaptor.forClass(UserDto.class);
verify(service).save(captor.capture()); // Захватываем объект

UserDto capturedValue = captor.getValue();
assertEquals("Expected Name", capturedValue.getName());
```

### 🧠 FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `@Mock` и `@Spy`?**
**О:** `@Mock` — это пустая оболочка, методы по умолчанию возвращают `null/0`. `@Spy` — это реальный объект, который делегирует вызовы своим настоящим методам, если не настроен иначе.

**В: Почему при тестировании Spy иногда возникает ошибка или странное поведение?**
**О:** Потому что стандартный синтаксис `when(spy.call()).thenReturn(...)` сначала выполняет реальный метод `spy.call()`. Если в этом методе есть сложная логика или он кидает исключение, тест упадет еще до того, как сработает заглушка. Используй `doReturn(...).when(spy).call()`.

**В: Что такое "Deep Stubs"?**
**О:** Это возможность создать мок, который при вызове цепочки методов возвращает другой мок (например, `when(mock.getA().getB()).thenReturn(value)`). Но Senior-разработчики **не рекомендуют** это использовать, так как это признак плохой архитектуры (нарушение закона Деметры).

**В: Как проверить, что метод не вызывался?**
**О:** Используй `verify(mock, never()).methodName();` или `verifyNoInteractions(mock);`, если хочешь убедиться, что вообще ни один метод этого мока не вызывался.

# 🛠 Mockito: Создание моков (`@Mock`)

### 1. Что такое Mock простыми словами?
Представь, что ты снимаешь кино. Твой главный герой — это **Service**, который нужно протестировать. Но этому герою для работы нужен **Repository** (база данных). Чтобы не строить настоящую огромную декорацию с реальной базой данных, ты берешь «дублера» — актера, который просто имитирует наличие базы. 

**Mock (Мок)** — это и есть этот дублер. Это объект-пустышка, который выглядит как настоящий класс, но не содержит логики. Ты сам решаешь: «Когда тебя спросят имя пользователя, ответь 'Ivan'».

### тесно с `@InjectMocks`
*   **`@Mock`**: Создает «пустышку» (заглушку). Все методы по умолчанию возвращают `null`, `0` или `false`.
*   **`@InjectMocks`**: Это твой **объект под тестированием**. Mockito возьмет все созданные `@Mock` и попытается «впихнуть» их в этот объект (через конструктор или сеттеры).

---

### 2. Как запустить моки (Инициализация)
Аннотации сами по себе не работают. Тесту нужно сказать: «Эй, обработай эти аннотации!».

**Вариант А (Современный, JUnit 5):**
Используем расширение `MockitoExtension`. Это стандарт индустрии.
```java
@ExtendWith(MockitoExtension.lock.class) // Магия инициализации здесь
class UserServiceTest {
    @Mock
    private UserRepository userRepository;

    @InjectMocks
    private UserService userService;
}
```

**Вариант Б (Старый/Ручной):**
Если по какой-то причине ты не используешь расширение, нужно вызвать инициализатор в методе `@BeforeEach`.
```java
@BeforeEach
void setUp() {
    MockitoAnnotations.openMocks(this); 
}
```

---

### 3. Тонкие нюансы (Senior Level)

#### ⚠️ Нюанс №1: Default Values (Значения по умолчанию)
Если ты не настроил поведение мока (`when(...).thenReturn(...)`), Mockito вернет "пустоту":
*   Объекты $\to$ `null`
*   Примитивы (`int`, `long`) $\to$ `0`
*   `boolean` $\to$ `false`
*   Коллекции $\to$ **Пустая коллекция** (это очень удобно, не будет `NullPointerException` при итерации).

#### ⚠️ Нюанс №2: Deep Stubs (Глубокие заглушки)
Иногда бывает так: `user.getAddress().getCity()`. Чтобы не писать три цепочки `when(...)`, можно использовать:
`@Mock(answer = Answers.RETURNS_DEEP_STUBS)`.
*Но будь осторожен:* использование Deep Stubs — это признак плохого дизайна кода (нарушение Закона Деметры). Если тебе это нужно, значит твой код слишком запутан.

#### ⚠️ Нюанс №3: Mock vs Spy
Не путай! 
*   `@Mock` — это полностью фальшивый объект. Его логики не существует.
*   `@Spy` — это "полуправда". Это реальный объект, но ты можешь перехватывать его методы и менять их поведение.

---

### 4. FAQ (Частые вопросы на собеседовании)

**В: Что произойдет, если я забуду `@ExtendWith(MockitoExtension.class)`?**
**О:** Твой `@Mock` будет равен `null`. Тест упадет с `NullPointerException`, как только ты попытаешься вызвать метод у этого мока. Аннотации не инициализируются сами по себе.

**В: Можно ли мокать `final` классы или методы?**
**О:** В старых версиях Mockito — нет. В современных (начиная с 2.x и выше, если подключен `mockito-inline`) — **да**. Но помни: если ты часто мокаешь `final` классы, возможно, архитектура приложения слишком жесткая.

**В: Чем `@Mock` отличается от `@Spy`?**
**О:** `@Mock` создает пустую оболочку (всё возвращает `null`). `@Spy` оборачивает **реальный** объект и вызывает его настоящие методы, пока ты явно не скажешь ему сделать иначе через `doReturn(...)`.

**В: Что такое `@InjectMocks` на самом деле?**
**О:** Это инструмент для автоматизации. Он смотрит на поля в твоем классе (например, `UserService`) и ищет среди созданных `@Mock` подходящие типы, чтобы внедрить их в конструктор или поля этого класса.

# 🕵️ Mockito: Шпионы (`@Spy`)

### Что это такое?
Если **`@Mock`** — это «пустышка» (робот без мозгов, который всегда возвращает `null`, `0` или `false`), то **`@Spy`** — это **частичный мок**. 

Представь, что ты нанял актера. Он выглядит как настоящий человек, ведет себя как настоящий человек, но ты можешь подменить ему только одну реплику в сценарии. Всё остальное он будет делать по-наму, используя реальную логику объекта.

**Суть:** Шпион оборачивает **реальный экземпляр** объекта. Все методы вызывают настоящую логику, пока ты явно не скажешь им: «Стоп, здесь верни вот это».

---

### Главное отличие: Mock vs Spy

| Характеристика | `@Mock` | `@Spy` |
| :--- | :--- | :--- |
| **Основа** | Создается "пустой" класс на лету. | Оборачивает **реальный** объект. |
| **Поведение методов** | По умолчанию ничего не делает (возвращает `null`/`0`). | Выполняет **реальный код** метода. |
| **Когда использовать** | Когда тебе не важна внутренняя логика зависимости. | Когда нужно протестировать реальный метод, но «заглушить» один конкретный вызов внутри него. |

---

### ⚠️ Главная ловушка (The "Senior" Nuance)

Это то, на чем валятся джуны. Есть два способа заглушить метод у шпиона, и они работают **по-разному**.

#### 1. Опасный способ: `when(...).thenReturn(...)`
```java
// ПЛОХО для Spy
when(spyService.doSomething()).thenReturn("Fixed Value");
```
**Почему это плохо?** 
В этой строке Java сначала **выполнит реальный метод** `spyService.doSomething()`, чтобы передать его результат в `when()`. Если этот метод внутри себя делает запрос в БД или выбрасывает ошибку — твой тест упадет еще на этапе настройки (setup), даже не дойдя до проверки.

#### те 2. Безопасный способ: `doReturn(...).when(...)`
```java
// ХОРОШО для Spy
doReturn("Fixed Value").when(spyService).doSomething();
```
**Почему это правильно?**
Синтаксис `doReturn` говорит Mockito: «Не вызывай реальный метод, просто сразу запиши заглушку». Это единственный безопасный способ работы со шпионами.

---

### Когда использовать `@Spy`? (Use Cases)

1.  **Legacy Code (Наследие):** У тебя есть огромный класс с кучей логики, который невозможно разбить на части. Тебе нужно протестировать один метод, но «заткнуть» другой, который лезет в сеть или БД.
2.  **Partial Mocking:** Когда ты тестируешь класс и хочешь проверить его реальную работу, но часть его внутренних методов (которые вызываются внутри того же класса) должны быть подконтрольны.
*Примечание: Если тебе часто приходится использовать `@Spy`, это признак того, что твой класс нарушает Single Responsibility Principle (SRP) — он делает слишком много.*

---

### Пример кода

```java
@ExtendWith(MockitoExtension.class)
class SpyExampleTest {

    @Spy
    private Calculator calculator = new Calculator(); // Создаем реальный объект

    @Test
    void testSpy() {
        // 1. По умолчанию шпион работает как реальный объект
        assertEquals(10, calculator.add(5, 5)); 

        // 2. Подменяем только один метод (используя безопасный doReturn)
        doReturn(100).when(calculator).add(anyInt(), anyInt());

        // Теперь даже 1+1 вернет 100
        assertEquals(100, calculator.add(1, 1));
    }
}

class Calculator {
    public int add(int a, int b) {
        return a + b;
    }
}
```

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли сделать `@Spy` для интерфейса?**
**О:** Нет. Шпиону нужен реальный экземпляр (объект), который можно обернуть. У интерфейса нет реализации, поэтому шпионить не над чем.

**В: Что произойдет, если я использую `when(...).thenReturn(...)` на методе, который выбрасывает Exception?**
**О:** Тест упадет с этим Exception прямо в строке настройки теста. Mockito попытается вызвать метод, чтобы получить аргументы для `when`, и не сможет их получить из-за ошибки.

**В: В чем разница между `spy(new MyService())` и `@Spy MyService service`?**
**О:** С точки зрения результата — почти никакой. Но `@Spy` (аннотация) удобнее в Spring/JUnit, так как Mockito сам управляет жизненным циклом и внедрением зависимостей. Однако при использовании `@Spy` на поле, ты **обязан** инициализировать объект (`= new MyService()`), иначе шпиону нечего будет оборачивать.

**В: Можно ли использовать `verify()` со шпионом?**
**О:** Да! Это одна из главных причин его использования. Ты можешь проверить, был ли вызван реальный метод внутри объекта, даже если ты его заглушил.

# 🧠 Mockito: Stubbing (Заглушки)
**Stubbing** — это процесс программирования поведения мока. Мы говорим моку: *"Когда у тебя вызовут метод `X` с аргументами `Y`, ты должен вернуть результат `Z`"*. Без заглушек моки возвращают только "пустые" значения (null, 0, false).

### 1. Базовый синтаксис
Используется для методов, которые **возвращают значение**.

```java
// Когда вызывается service.getUser(1), верни объект user
when(userService.getUser(1L)).thenReturn(new User("John"));

// Можно вернуть null (если это часть сценария)
when(userService.getUser(99L)).thenReturn(null);
```

### 2. Использование Argument Matchers (Спецификаторы аргументов)
Если тебе не важен конкретный ID, а важно лишь то, что пришел любой `Long`, используй матчеры.

*   `any()` — любой объект данного типа.
*   `anyString()`, `anyInt()`, `anyLong()` — типизированные матчеры.
*   `eq()` — когда нужно смешать конкретное значение и матчер (см. ниже нюанс).

```java
// Вернет пользователя для любого Long
when(userService.getUser(anyLong())).thenReturn(new User("Stranger"));
```

⚠️ **Senior Note (Золотое правило):** 
Если ты используешь хотя бы один матчер (`any()`) в вызове метода, **все остальные аргументы этого метода тоже должны быть матчерами**.
*   ❌ `when(service.update(1L, anyString()))` — **Ошибка!** (смешивание реального значения и матчера).
*   ✅ `when(service.update(eq(1L), anyString()))` — **Правильно.**

### 3. Заглушки для void-методов
Для методов, которые ничего не возвращают (`void`), синтаксис `when(...).thenReturn(...)` **не работает** (код даже не скомпилируется). Здесь используется семейство `do...`.

```java
// Просто ничего не делать (по умолчанию мок и так ничего не делает, но это полезно для ясности)
doNothing().when(userRepository).deleteById(anyLong());

// Выбросить исключение при вызове void метода
doThrow(new RuntimeException("DB Error")).when(userRepository).deleteById(1L);

// Выполнить какое-то действие (например, изменить аргумент)
doAnswer(invocation -> {
    Long id = invocation.getArgument(0);
    System.outprintln("Deleting ID: " + id);
    return null;
}).when(userRepository).deleteById(anyLong());
```

### 4. Последовательные вызовы (Stubbing Consecutive Calls)
Иногда нужно, чтобы при первом вызове вернулся один результат, а при втором — другой (например, для тестирования ретраев или циклов).

```java
// Первый вызов вернет "First", второй - "Second", третий и далее - null
when(mockService.getStatus()).thenReturn("First", "Second", null);
```

### 5. Продвинутый уровень: `thenAnswer()`
Когда `thenReturn` слишком прост, и тебе нужно вычислить ответ на основе входных данных. Это превращает заглушку в мини-логику.

```java
when(userRepository.save(any(User.class))).thenAnswer(invocation -> {
    User user = invocation.getArgument(0); // Берем переданный объект
    user.setId(10L); // Имитируем поведение БД (генерация ID)
    return user;     // Возвращаем измененный объект
});
```

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `when(...).thenReturn(...)` и `doReturn(...).when(...)`?**
**О:** Основное отличие — в работе со **Spy** (шпионами). 
*   `when(...).thenReturn(...)` при вызове на реальном объекте (Spy) **сначала выполнит реальный метод**, а потом переопределит результат. Это может вызвать побочные эффекты или ошибки.
*   `doReturn(...).when(...)` — "тихий" способ. Он не вызывает реальный метод, а сразу подменяет поведение. 
*   *Совет:* Всегда используй `doReturn` для Spy, чтобы избежать лишнего выполнения кода.

**В: Что будет, если я настрою заглушку, но не вызову этот метод в тесте?**
**О:** Тест пройдет успешно. Mockito не проверяет "использование" заглушек сам по себе. Чтобы убедиться, что метод был вызван, нужно использовать `verify(mock).method()`.

**В: Можно ли использовать `any()` для объектов-примитивов (например, `int`)?**
**О:** Да, но лучше использовать специализированные матчеры типа `anyInt()`, чтобы избежать проблем с автобоксингом и сделать код чище.

**В: Что такое "Unnecessary Stubbing Exception"?**
**О:** В новых версиях Mockito (в связке с JUnit 5) включен строгий режим. Если ты написал `when(...).thenReturn(...)`, но этот метод ни разу не был вызван в тесте, Mockito выбросит ошибку. Это сделано для того, чтобы чистить мусорный код из тестов.

# 🧠 Mockito: Проверка взаимодействий (`verify`)

### 🎯 Суть
Если `when(...).thenReturn(...)` — это **Stubbing** (подготовка сценария/заглушка), то `verify(...)` — это **Assertion** (проверка того, что произошло). 

Мы используем `verify`, когда нам важно не только получить результат выполнения метода, но и убедиться, что внутри сервиса произошли определенные действия: был вызван метод сохранения в БД, отправлено уведомление или залогирована ошибка.

---

### 🛠 Основной синтаксис и режимы (Verification Modes)

Базовый синтаксис: `verify(mock).methodName(arguments);`

| Режим | Описание | Когда использовать |
| :--- | :--- | :--- |
| `times(n)` | Метод был вызван ровно `n` раз. | По умолчанию (если не указано иное, Mockito считает, что `times(1)`). |
  | `never()` | Метод **не** должен был быть вызван. | Проверка негативных сценариев (например, при ошибке валидации транзакция не должна сохраниться). |
| `atLeastOnce()` | Вызван хотя бы один раз. | Когда нам не важно точное количество, но важен сам факт вызова. |
| `atLeast(n)` | Минимум `n` раз. | Для проверки стриминга или цикличных процессов. |
| `atMost(n)` | Не более `n` раз. | Редкий случай, для ограничения нагрузки/вызовов. |

---

### 🔍 Работа с аргументами (Argument Matchers)

Это самая «тонкая» часть. Часто нам не нужно проверять *весь* объект, нам нужно проверить только его часть или тип.

1. **`any()`**: Принимает любой объект данного типа.
   * `verify(repo).save(any(User.class));` — нам плевать, какой юзер, главное, что вызов был.
2. **`eq()`**: Явное указание конкретного значения. 
   * **⚠️ Важное правило (Golden Rule):** Если ты используешь хотя бы один `Matcher` (например, `any()`) в методе, то **все** остальные аргументы этого метода тоже должны быть Matchers.
   * ❌ **Ошибка:** `verify(service).doWork(10, anyString());` — упадет с `InvalidUseOfMatchersException`.
   * ✅ **Правильно:** `verify(service).doWork(eq(10), anyString());`
3. **`argThat(predicate)`**: Твой кастомный логический фильтр.
   * `verify(repo).save(argThat(user -> user.getAge() > 18));` — проверка бизнес-логики прямо внутри верификации.

---

### ⛓ Проверка порядка вызовов (`InOrder`)

Иногда важно не только *что* было вызвано, но и в какой *последовательности*. Например: сначала мы создаем лог, а потом отправляем сообщение.

```java
InOrder inOrder = inOrder(loggerMock, emailServiceMock);

// Проверяем строгую последовательность
inOrder.verify(loggerMock).info("Starting process");
instre.verify(emailServiceMock).sendEmail(any());
inOrder.verify(loggerMock).info("Process finished");
```

---

### 🚀 Senior Tips (Нюансы)

1. **Не злоупотребляй `verify`**: Если ты проверяешь каждый чих в методе, твой тест становится "хрупким" (brittle). Любое изменение внутренней реализации (даже если результат тот же) сломает тест. Проверяй только то, что влияет на бизнес-результат или внешние системы.
2. **`verifyNoInteractions(mock)`**: Мощный инструмент для проверки того, что сторонний сервис вообще не трогали. Полезно в тестах безопасности и обработки ошибок.
3. **`verifyNoMoreInteractions(mock)`**: Проверяет, что кроме уже проверенных вызовов, других вызовов к этому моку не было. Используй осторожно — это делает тесты очень жесткими к рефакторингу.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `when(...).thenReturn(...)` и `verify(...)`?**
**О:** `when` — это настройка поведения (Stubbing), мы говорим моку, как отвечать. `verify` — это проверка факта (Verification), мы проверяем, был ли совершен вызов.

**В: Что будет, если я использую `any()` и обычное значение в одном методе?**
**О:** Ты получишь `InvalidUseOfMatchersException`. Mockito не сможет правильно сопоставить аргументы, так как Matchers работают через внутренний стек. Всегда оборачивай обычные значения в `eq()`, если рядом есть `any()`.

**В: Как проверить, что метод был вызван с объектом, у которого определенное поле равно "X"?**
**О:** Используй `argThat(argument -> argument.getField().equals("X"))` или используй `ArgumentCaptor`, чтобы «поймать» объект и затем сделать обычный `assertEquals`.

**В: Можно ли использовать `verify` для методов, которые возвращают `void`?**
**О:** Да, это основной сценарий использования `verify`. Для методов с возвращаемым значением мы чаще используем `when`, но `verify` всё равно полезен, чтобы убедиться, что вызов состоялся.

# 🛠 Mockito: ArgumentCaptor

### Что это такое? (Простыми словами)
Представь, что ты тестируешь курьера. Тебе важно не просто знать, что он *уехал* (вызов метода), а проверить, *какой именно* заказ он взял с собой. 

Часто в методе под тестированием (SUT) создается новый объект «внутри» (например, `new UserDto(...)`). Ты не можешь передать этот объект в тест заранее, потому что его еще не существует. **`ArgumentCaptor`** — это «ловушка», которая позволяет перехватить этот объект в момент вызова метода мока, чтобы ты мог залезть внутрь него и проверить его поля.

---

### Основные способы использования

#### 1. Современный способ (через аннотацию `@Captor`)
Это самый чистый и профессиональный подход. Используй его всегда, если работаешь в рамках JUnit 5.

```java
@ExtendWith(MockitoExtension.class)
class UserServiceTest {

    @Mock
    private UserRepository userRepository;

    @Captor
    private ArgumentCaptor<UserEntity> userCaptor; // Создаем ловушку для UserEntity

    @Test
    void shouldSaveUser() {
        // Arrange
        UserDto inputDto = new UserDto("John", "Doe");
        
        // Act
        userService.register(inputDto); // Внутри метода создается UserEntity

        // Assert
        verify(userRepository).save(userCaptor.capture()); // Перехватываем объект
        
        UserEntity capturedUser = userCaptor.getValue(); // Достаем его
        assertEquals("John", capturedUser.getFirstName()); // Проверяем поля
    }
}
```

#### 2. Классический способ (вручную)
Если по какой-то причине ты не используешь аннотации.

```java
ArgumentCaptor<UserEntity> userCaptor = ArgumentCaptors.forClass(UserEntity.class);
```

---

### Важные нюансы и продвинутые фишки

#### 1. `getValue()` vs `getAllValues()`
*   **`getValue()`**: Возвращает последний перехваченный объект (или единственный, если вызов был один).
*   **`getAllValues()`**: Если метод вызывался несколько раз (например, в цикле), этот метод вернет `List<T>` со всеми объектами, которые попали в ловушку. Это критично для тестирования массовых операций.

#### 2. Когда НЕ нужно использовать ArgumentCaptor
Это главная ошибка джунов. **Не используй захватчик там, где можно обойтись простым `eq()` или `any()`.**
*   ❌ **Плохо:** Перехватывать ID, если ты и так его знаешь. Это усложняет тест.
    `verify(repo).deleteById(userCaptor.capture()); // Зачем?`
*   ✅ **Хорошо:** `verify(repo).deleteById(1L);`
*   **Правило:** Используй `ArgumentCaptor` только тогда, когда тебе нужно проверить **внутреннее состояние** объекта, который был создан *внутри* тестируемого метода.

#### 3. Проблема "Слишком много проверок"
Если ты используешь `ArgumentCaptor`, чтобы проверить 10 разных полей, твой тест становится хрупким (brittle). Если изменится одно поле, тест упадет. Старайся проверять только те поля, которые важны для бизнес-логики данного метода.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем разница между `ArgumentMatcher` (например, `any()`) и `ArgumentCaptor`?**
**О:** `Matcher` используется для **фильтрации** (пропустить любой объект или только подходящий под условие). `ArgumentCaptor` используется для **извлечения** объекта из вызова, чтобы провести над ним глубокие проверки (Asserts) после того, как метод был вызван.

**В: Что будет, если вызвать `getValue()`, когда ни одного вызова метода не было?**
**О:** Ты получишь `MockitoException`. Ловушка пуста, ловить было нечего.

**В: Можно ли использовать `ArgumentCaptor` вместе с `verify(..., times(3))`?**
**О:** Да. Но помни: если ты хочешь проверить все три вызова, тебе нужно будет использовать `getAllValues()`, иначе ты увидишь только последний объект.

**В: Можно ли использовать `ArgumentCaptor` в методе `when(...).thenReturn(...)`?**
**О:** **Категорически нет.** `ArgumentCaptor` предназначен только для фазы **Verification** (проверки того, что *уже произошло*). В фазе `stubbing` (настройка поведения) он не работает и приведет к ошибке. Для настройки поведения используй `any()` или `eq()`.

# 🧠 Cheat Sheet: Assertions (Утверждения)

**Assertions** — это сердце любого теста. Если тест — это детектив, то Assertion — это момент, когда мы говорим: «Улики указывают на то, что подозреваемый виновен». Если утверждение не выполняется, тест проваливается.

В мире Java/Spring мы используем три основных инструмента: **JUnit 5** (база), **AssertJ** (стандарт индустрии) и иногда **Hamcrest**.

---

### 1. JUnit 5 Assertions (Минимальный набор)
Это встроенные инструменты. Они работают, но они «деревянные». Их синтаксис часто неудобен при проверке сложных объектов.

*   `assertEquals(expected, actual)` — проверка на равенство. **Важно:** всегда первым идет ожидаемый результат (`expected`), иначе в логах ошибки будет каша.
*   `assertNotEquals(unexpected, actual)` — проверка на неравенство.
*   `assertTrue(condition)` / `assertFalse(condition)` — проверка логического условия.
*   `assertNull(object)` / `assertNotNull(object)` — проверка на наличие объекта.
*   `assertThrows(Exception.class, executable)` — **критически важно** для проверки того, что твой сервис выбрасывает нужную ошибку при неверных входных данных.

---

### 2. AssertJ (Твой лучший друг)
Если ты видишь в проекте JUnit, но не видишь AssertJ — это плохой знак. AssertJ использует **Fluent Interface** (текучий интерфеймовый стиль), который читается как английское предложение.

**Почему Senior выбирает AssertJ:**
*   **Читаемость:** `assertThat(user.getName()).isEqualTo("Ivan");`
*   **Цепочки (Chaining):** Можно проверять несколько свойств за один раз.
*   **Мощные проверки коллекций:** Проверка содержимого, размера, наличия элементов.

**Примеры использования:**
```java
// Строки
assertThat(name).isNotBlank().startsWith("A").endsWith("z");

// Числа
assertThat(age).isGreaterThan(18).isLessThan(100);

// Коллекции (Магия здесь)
assertThat(userList)
    .hasSize(3)
    .extracting(User::getName) // Вытаскиваем только имена из списка объектов
    .containsExactlyInAnyOrder("Ivan", "Maria", "Petr");

// Объекты (Recursive Comparison)
// Это киллер-фича: сравнивает поля объектов, а не ссылки на них!
assertThat(actualDto)
    .usingRecursiveComparison()
    .isEqualTo(expectedDto);
    
// Исключения
assertThatThrownBy(() -> service.doWork(null))
    .isInstanceOf(IllegalArgumentException.class)
    .hasMessageContaining("ID cannot be null");
```

---

### 3. Senior Nuances (Нюансы и Best Practices)

#### ⚠️ Soft Assertions (Мягкие проверки)
По умолчанию, как только первое `assert` падает, тест останавливается. Если у тебя в тесте 10 проверок, ты увидишь только первую ошибку. Придется исправлять, перезапускать и снова натыкаться на вторую ошибку. Это бесит.
**Решение:** Используй `SoftAssertions`. Он соберет *все* ошибки и вывалит их списком в конце.

```java
SoftAssertions softly = new SoftAssertions();
softly.assertThat(user.getName()).isEqualTo("Ivan");
softly.assertThat(user.getAge()).isEqualTo(25); // Если имя не Ivan, проверка возраста все равно выполнится
softly.assertAll(); // <--- ОБЯЗАТЕЛЬНО! Без этого ошибки не будут выброшены.
```

#### ⚠️ Custom Error Messages
Никогда не оставляй ассерты «голыми». Если тест упадет в CI/CD (Jenkins/GitLab), ты не сможешь посмотреть дебаггер. Добавляй описание.
*   *Плохо:* `assertEquals(200, response.getStatus());`
*   *Хорошо:* `assertEquals(200, response.getStatus(), "HTTP Status should be OK for valid request");`

#### ⚠️ Сравнение объектов: `equals()` vs `Recursive Comparison`
Не полагайся на переопределенный `equals()` в сущностях (Entity), особенно если они связаны с Hibernate/JPA. В тестах лучше использовать `.usingRecursiveComparison()` из AssertJ. Это гарантирует, что ты проверяешь реальные значения полей, а не магию сравнения ссылок или ID.

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем разница между `assertEquals` в JUnit и `assertThat` в AssertJ?**
**О:** `assertEquals` — это классический метод с фиксированным порядком аргументов (`expected`, `actual`). `assertThat` — это Fluent API, который позволяет строить цепочки проверок и предоставляет гораздо более богатый набор методов для сложных типов (коллекции, даты, строки).

**В: Что такое "Soft Assertions" и когда их использовать?**
**О:** Это механизм, который позволяет тесту продолжать выполнение после первого провала. Используй их в интеграционных тестах или при проверке больших DTO, где важно увидеть сразу все несовпадающие поля, а не исправлять их по одному.

**В: Как протестировать, что метод выбрасывает исключение?**
**О:** В JUnit 5 используй `assertThrows(ExpectedException.class, () -> methodCall())`. В AssertJ более красиво через `assertThatThrownBy(() -> methodCall()).isInstanceOf(...)`.

**В: Что делать, если нужно сравнить два объекта, у которых не переопределен `equals`?**
**О:** Используй `assertThat(actual).usingRecursiveComparison().isEqualTo(expected);`. Это проверит все поля объектов рекурсивно.

# 🧠 Шпаргалка: AssertJ (Fluent Assertions)

**AssertJ** — это библиотека для написания "текучих" (fluent) утверждений. В отличие от стандартного JUnit `assertEquals(expected, actual)`, где легко перепутать местами ожидаемое и фактическое значение, AssertJ использует синтаксис, максимально близкий к человеческому языку: `assertThat(actual).isEqualTo(expected)`.

### 🚀 Главные преимущества
1.  **Fluent API:** Цепочки методов (method chaining) позволяют писать длинные проверки в одну строку.
2.  **Читаемость:** Код читается как предложение на английском.
3.  **Информативные ошибки:** Если тест упадет, AssertJ покажет детальную разницу (что именно не совпало в строке или списке).
4.  **Типизация:** IDE подсказывает доступные методы в зависимости от типа объекта (`String`, `List`, `Map` и т.д.).

---

### 🛠 Основные возможности по типам данных

#### 1. Базовые проверки (Object)
Применяются ко всем объектам.
* `assertThat(obj).isNotNull();` — проверка на non-null.
* `assertThat(obj).isInstanceOf(User.class);` — проверка типа.
* `assertThat(obj).isEqualTo(otherObj);` — проверка через `.equals()`.
* `assertThat(obj).isNotSameAs(otherObj);` — проверка, что это разные объекты в памяти (ссылки).

#### 2. Работа со строками (String)
Здесь AssertJ раскрывается на полную.
* `assertThat(str).contains("abc");` — содержит подстроку.
* `assertThat(str).startsWith("Hello");` / `endsWith("World");`
* `assertThat(str).containsIgnoringCase("hello");` — без учета регистра.
* `assertThat(str).isEmpty();` / `isBlank();` (проверка на пустую строку или пробелы).
* `assertThat(str).matches("^[0-9]+$");` — проверка через Regex.

#### 3. Работа с коллекциями (List, Set, Map)
Самая мощная часть для тестирования бизнес-логики.
* `assertThat(list).hasSize(3);` — размер коллекции.
* `assertThat(list).containsExactly("A", "B", "substring");` — проверка строгого порядка и состава.
* `assertThat(list).containsExactlyInAnyOrder("B", "A");` — состав совпадает, порядок не важен.
* `assertThat(list).containsAll(otherList);` — проверка на вхождение всех элементов.
* `assertThat(list).doesNotContainNull();` — проверка, что внутри нет `null`.

**🔥 Pro-level: Магия `extracting` и `filteredOn`**
Тебе не нужно перебирать список циклом, чтобы проверить поле у объектов внутри него.
```java
// Проверяем, что в списке пользователей есть имена "Ivan" и "Maria"
assertThat(users)
    .extracting(User::getName) // Вытаскиваем только имена (теперь мы работаем со списком строк)
    .containsExactlyInAnyOrder("Ivan", "Maria");

// Фильтруем список перед проверкой
assertThat(users)
    .filteredOn(user -> user.getAge() > 18) // Оставляем только совершеннолетних
    .extracting(User::getRole)
    .contains(Role.ADMIN);
```

#### 4. Сравнение объектов (Recursive Comparison)
Это "киллер-фича". Когда у тебя есть два разных объекта (например, из БД и из запроса), и ты хочешь сравнить их поля, не переопределяя `equals()`.
* `assertThat(actualUser).usingRecursiveComparison().isEqualTo(expectedUser);`
  * *Что делает:* Проходит рекурсивно по всем полям объекта и сравнивает их значения. Идеально для DTO и Entity.

---

### ⚠️ Нюансы и Senior-советы

1.  **Используй `.as()` для кастомных сообщений.**
    Если тест падает в сложном цикле или большом списке, стандартная ошибка может быть невнятной.
    `assertThat(user.getEmail()).as("Email of user %s", user.getId()).contains("@");`
    *Если упадет, ты увидишь: `[Email of user 123] expected to contain @ but was...`*

2.  **Soft Assertions (Мягкие проверки).**
    Обычно, если первый `assertThat` падает, выполнение теста прерывается. **Soft Assertions** позволяют выполнить *все* проверки и в конце показать список всех ошибок сразу.
    ```java
    SoftAssertions softly = new SoftAssertions();
    softly.assertThat(user.getName()).isEqualTo("Ivan");
    softly.assertThat(user.getAge()).isEqualTo(25);
    softly.assertAll(); // Без этого вызова ошибки не будут выброшены!
    ```

3.  **Не злоупотребляй `extracting` в слишком длинных цепочках.**
    Слишком длинная цепочка (chain) превращается в "макароны", которые трудно дебажить. Если логика проверки сложнее двух шагов — разбей на два теста.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: В чем разница между `contains` и `containsExactly`?**
**О:** `contains` проверяет, что элементы есть в списке, но не важно, есть ли там что-то еще. `containsExactly` требует, чтобы в списке были *только* эти элементы и именно в таком порядке.

**В: Как проверить, что список не пустой, но при этом не знаю его точный размер?**
**О:** Используй `assertThat(list).isNotEmpty();`.

**В: Что делать, если я хочу сравнить объекты, но игнорировать поле `id` или `createdAt`?**
**О:** В `usingRecursiveComparison()` можно использовать `.ignoringFields("id", "createdAt")`. Это спасает при тестировании объектов, где ID генерируется базой данных.

**В: Почему я использую `assertThat(actual).isEqualTo(expected)`, а не наоборот?**
**О:** Технически AssertJ это проглотит, но по правилам чистого кода и для читаемости "человеческим языком" всегда идет **Subject (что проверяем) $\to$ Verb (действие) $\to$ Object (ожидаемый результат)**.

# 🧠 Шпаргалка: Hamcrest Assertions

**Hamcrest** — это библиотека «матчеров» (matchers). Если JUnit дает тебе возможность сказать: *"Это должно быть равно этому"*, то Hamcrest позволяет сказать: *"Я ожидаю, что этот список содержит три элемента, один из которых — 'Admin', а все строки начинаются с 'User_'"*.

Главная цель Hamcrest — **читаемость (readability)**. Тест должен читаться как предложение на английском языке.

---

### 🛠 Основной синтаксис
В основе всего лежит одна магическая конструкция:
```java
assertThat(actualValue, matcher);
```
*   `actualValue`: то, что мы получили от кода.
*   `matcher`: правило, которому это значение должно соответствовать.

---

### 📂 Основные группы матчеров

#### 1. Проверка равенства и типов (Core Matchers)
Самые базовые вещи, которые используются в 90% случаев.
*   `is(value)` — синтаксический сахар для `equalTo`. Делает код человечным: `assertThat(name, is("John"))`.
*   `equalTo(value)` — классическое равенство через `.equals()`.
*   `instanceOf(Class)` — проверка, что объект является экземпляром конкретного класса.
*   `nullValue()` / `notNullValue()` — проверка на null.

#### 2. Работа со строками (String Matchers)
Здесь Hamcrest раскрывается во всей красе.
*   `containsString("substring")` — содержит подстроку.
*   `startsWith("prefix")` / `endsWith("suffix")` — проверка начала и конца строки.
*   `emptyString()` — строка пустая (`""`).
    *   *Нюанс:* Не путай с `empty()`, который проверяет размер коллекции.
*   `matchesPattern(regex)` — проверка по регулярному выражению.

#### 3. Работа с коллекциями (Collection Matchers)
Самая мощная часть для тестирования списков, сетов и мап.
*   `hasSize(n)` — проверка размера коллекции.
*   `hasItem(element)` — содержит хотя бы один такой элемент.
*   `hasItems(e1, e2)` — содержит указанный набор элементов.
*   `empty()` — коллекция не содержит элементов.
*   `contains(e1, e2)` — **строгая** проверка: элементы должны быть именно в таком порядке и только эти.
*   `containsInAnyOrder(e1, e2)` — те же элементы, но порядок не важен (идеально для Unit-тестов).

#### 4. Числа и логика (Numeric & Logical)
*   `greaterThan(n)` / `lessThan(n)` / `greaterThanOrEqualTo(n)` — сравнение чисел.
*   `closeTo(value, errorMargin)` — **Важно!** Используй для `Double` и `Float`, чтобы избежать проблем с точностью вычислений (проверка в пределах погрешности).
*   `not(matcher)` — логическое отрицание. Можно обернуть любой матчер: `assertThat(name, is(not("Admin")))`.
*   `allOf(m1, m2, ...)` — логическое **AND** (все условия должны совпасть).
*   `anyOf(m1, m2, ...)` — логическое **OR** (хотя бы одно условие должно совпасть).

---

### ⚠️ Senior Nuances (На что обратить внимание)

1.  **`is()` — это не просто декорация.** Хотя `is(equalTo(x))` технически избыточен, в Hamcrest он используется для создания "Fluent Interface". Без него код превращается в сухой набор функций, с ним — в читаемые предложения.
2.  **Смертельная ловушка `contains` vs `containsInAnyOrder`.** Если ты используешь `contains`, и порядок элементов в БД или API изменится (а он может!), твой тест упадет, даже если данные верны. Всегда выбирай `containsInAnyOrder`, если порядок не является частью бизнес-логики.
3.  **Типизация.** Hamcrest очень строг к типам. Если ты сравниваешь `Long` и `Integer`, матчер может выдать ошибку или провалиться, даже если числа одинаковые (1L != 1).

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Чем Hamcrest отличается от AssertJ?**
**О:** Это вопрос вкуса и архитектуры. Hamcrest — это библиотека матчеров, которую можно использовать везде (даже в Mockito). AssertJ — более современная и мощная библиотека с "цепочечным" (fluent) подходом (`assertThat(list).hasSize(3).contains("A")`). В современном Spring-мире AssertJ встречается чаще, но Hamcrest всё еще стандарт де-факты для многих legacy-проектов и встроенных проверок.

**В: Как проверить, что в списке объектов есть объект с определенным полем?**
**О:** Напрямую через базовые матчеры это сложно. Тебе либо придется использовать `hasItem(hasProperty("name", is("John")))` (если объекты — JavaBeans), либо написать свой кастомный `Matcher`.

**В: Что произойдет, если в `allOf` один из матчеров не сработает?**
**О:** Весь `assertThat` упадет. `allOf` работает как логическое "И" в программировании: результат истинен только при выполнении всех условий.

# 🧠 Шпаргалка: JUnit Assertions (JUnit 5)

**Assertions (Утверждения)** — это "вердикты" твоего теста. Если утверждение не выполняется, тест падает. Без ассертов тест — это просто запуск кода, который ничего не проверяет.

### 1. Базовые проверки (The Essentials)
Самые часто используемые методы для простых проверок значений.

*   `assertEquals(expected, actual)` — Проверяет равенство через `.equals()`.
    *   ⚠️ **Senior Tip:** Никогда не путай порядок аргументов! Первый — что мы *ждем*, второй — что *получили*. Если перепутаешь, в логах ошибки будет написано "Ожидалось: 10, а получили: 5", хотя на самом деле наоборот. Это сбивает с толку при дебаге.
*   `assertNotEquals(unexpected, actual)` — Проверяет, что значения *не* равны.
*   `assertTrue(condition)` / `assertFalse(condition)` — Проверка логического условия.
*   `assertNull(object)` / `assertNotNull(object)` — Проверка на наличие или отсутствие объекта.
*   `assertSame(expected, actual)` — Проверяет, что оба объекта указывают на **одну и ту же область памяти** (ссылочная идентичность `==`).
*   `assertNotSame(unexpected, actual)` — Проверяет, что это разные объекты в памяти.

### 2. Работа с типами и массивами
*   `assertInstanceOf(Class<T> type, Object actual)` — Проверяет, является ли объект экземпляром конкретного класса (удобно для полиморфизма).
*   `assertArrayEquals(expectedArray, actualArray)` — Проверяет содержимое массивов (порядок и элементы).

### 3. Продвинутые возможности (Senior Level)

#### 🛡️ Grouped Assertions (`assertAll`)
Это киллер-фича JUnit 5. В обычном тесте, если первое утверждение упало, остальные **не выполняются**. Ты видишь только первую ошибку.
`assertAll` позволяет выполнить **все** проверки в группе, даже если часть из них провалилась. Это дает полную картину того, что именно сломалось в объекте.

```java
// Плохо: если имя не совпадает, мы не узнаем, верный ли email
assertEquals("John", user.getName());
assertEquals("john@example.com", user.getEmail());

// Хорошо: мы увидим все ошибки сразу
assertAll("Проверка данных пользователя",
    () -> assertEquals("John", user.getName()),
    () -> assertEquals("john@example.com", user.getEmail())
);
```

#### 💥 Тестирование исключений (`assertThrows`)
Раньше использовали `@Test(expected = ...)`, но это плохо, так как мы не могли проверить содержимое ошибки. Сейчас используем `assertThrows`.

```java
// Возвращает объект пойманного исключения
Throwable exception = assertThrows(IllegalArgumentException.class, () -> {
    userService.register(null); // Вызываем метод, который должен упасть
});

// Теперь можно проверить сообщение внутри исключения
assertEquals("Username cannot be null", exception.getMessage());
```

#### ⏱️ Тестирование времени (`assertTimeout`)
Иногда нужно убедиться, что алгоритм не "завис".
*   `assertTimeout(Duration, Executable)` — Ждет завершения кода и проверяет, уложились ли мы в лимит. Если код затянется, тест упадет, но только *после* того, как код доработает.
*   `assertTimeoutPreemptively(Duration, Executable)` — **Опасно, но полезно.** Если код не успевает, JUnit прерывает его выполнение принудительно. 
    *   ⚠️ **Нюанс:** Не используй это для кода, который использует `ThreadLocal`, так как прерывание может произойти в другом потоке и нарушить контекст.

### 4. Золотые правила (Best Practices)

1.  **Добавляй сообщения об ошибках:** Почти у каждого метода есть перегрузка с `String message`.
    `assertEquals(expected, actual, "ID пользователя должен быть положительным");`
    В CI/CD логах это сэкономит тебе часы жизни.
2.  **Сравнивай Double осторожно:** Никостью не сравнивай `double` через обычный `assertEquals`. Используй `delta` (погрешность).
    `assertEquals(expected, actual, 0.001); // Проверка с точностью до тысячных`
3.  **Не злоупотребляй AssertJ:** JUnit Assertions — это база. Но если логика проверки становится сложной (проверка списков, вложенных полей), переходи на **AssertJ**. JUnit хорош для простых вещей, AssertJ — для сложных.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Почему мой тест падает, хотя я использую `assertEquals`, а значения выглядят одинаково?**
**О:** Скорее всего, у твоего класса не переопределен метод `.equals()`. `assertEquals` вызывает именно его. Если `.equals()` нет, Java сравнивает ссылки (как `assertSame`).

**В: В чем разница между `assertNotNull` и `assertTrue(obj != null)`?**
**О:** Разницы в результате нет, но `assertNotNull` семантически правильнее и дает более понятную ошибку в логах: *"Expected not null, but was null"*.

**В: Можно ли использовать `assertThrows` для проверки того, что исключение НЕ возникло?**
**О:** Технически нет. Для этого просто не оборачивай код в `assertThrows`. Если исключение вылетит — тест упадет сам.

**В: Что лучше: `assertTimeout` или `assertTimeoutPreemptively`?**
**О:** Если ты тестируешь тяжелый запрос к БД, используй `assertTimeout`. Если ты тестируешь потенциально бесконечный цикл и не хочешь, чтобы билд "завис" на вечность — `assertTimeoutPreemptively`. Но помни про риски с потоками.

# 🧠 Шпаргалка: Pattern AAA (Arrange, Act, Assert)

**AAA** — это стандарт де-факто в написании юнит-тестов. Его цель — сделать структуру теста предсказуемой. Когда любой разработчик открывает твой тест, он должен мгновенно понять: *что мы готовим*, *что мы запускаем* и *что именно проверяем*.

---

### 🏗️ 1. Arrange (Подготовка)
На этом этапе ты создаешь всё необходимое для выполнения теста. Это «декорации» перед началом спектакля.

**Что здесь происходит:**
*   Инициализация объектов под тестируемым кодом (SUT — System Under Test).
*   Создание моков (`@Mock`) и настройка их поведения (`when(...).thenReturn(...)`).
*   Подготовка входных данных (DTO, сущности, параметры).
*   Настройка окружения (если нужно).

**💡 Senior Tip:** Если блок `Arrange` раздулся на 50 строк — это плохой знак. Значит, твой метод делает слишком много или тест слишком сложный. В таких случаях используй **Test Data Builders** или вспомогательные методы (Factory methods), чтобы скрыть детали создания сложных объектов.

---

### 🚀 2. Act (Действие)
Самая короткая часть теста. Здесь ты вызываешь тот самый метод, который тестируешь.

**Что здесь происходит:**
*   Вызов целевого метода.
*   Сохранение результата выполнения в переменную (если метод что-то возвращает).

**💡 Senior Tip:** В идеале блок `Act` должен состоять из **одной строки**. Если у тебя тут целый сценарий с несколькими вызовами — ты пишешь не юнит-тест, а интеграционный или сценарийный тест. Тестируй одну атомарную операцию за раз.

---

### ✅ 3. Assert (Проверка)
Здесь происходит магия: мы проверяем, совпадает ли реальность с нашими ожиданиями.

**Что здесь происходит:**
*   Проверка возвращаемого значения (`assertEquals`, `assertThat`).
*   Проверка состояния объекта (изменилось ли поле внутри сущности).
*   Проверка поведения (был ли вызван метод мока через `verify(...)`).
*   Проверка исключений (`assertThrows`).

**💡 Senior Tip:** Старайся использовать **AssertJ** (`assertThat(...)`). Он делает проверки читаемыми, почти как человеческий язык. И помни: один тест — одна логическая проверка (хотя в одном блоке Assert может быть несколько связанных проверок, например, проверка всех полей одного DTO).

---

### 🛠️ Пример кода (JUnit 5 + Mockito + AssertJ)

```java
@Test
void shouldUpdateUserEmail_WhenEmailIsValid() {
    // 1. Arrange (Подготовка)
    Long userId = 1L;
    String newEmail = "new@example.com";
    User existingUser = new User(userId, "old@example.com"); // Наша сущность
    
    // Настраиваем мок репозитория
    when(userRepository.findById(userId)).thenReturn(Optional.of(existingUser));

    // 2. Act (Действие)
    // Вызываем метод сервиса, который мы тестируем
    User updatedUser = userService.updateEmail(userId, newEmail);

    // 3. Assert (Проверка)
    assertThat(updatedUser.getEmail()).isEqualTo(newEmail); // Проверяем результат
    verify(userRepository).save(any(User.class));           // Проверяем, что репозиторий был вызван
}
```

### ❓ FAQ: Часто задаваемые вопросы

**Q: Можно ли использовать комментарии `// Arrange`, `// Act`, `// Assert` в коде?**
**A:** Да, это отличная практика для обучения и для сложных тестов. В простых тестах они могут быть избыточны, но визуальное разделение пустых строк между блоками — это стандарт.

**Q: Что делать, если в блоке Act происходит несколько действий?**
**A:** Если тебе нужно вызвать `methodA()`, а потом `methodB()`, чтобы проверить результат — ты тестируешь не метод, а *сценарий*. Это допустимо для интеграционных тестов, но в юнит-тестах старайся дробить их так, чтобы `Act` был максимально коротким.

**Q: Можно ли делать Assert перед Act?**
**A:** Технически — можно, но это нарушает логику. Проверка "до" может быть частью этапа `Arrange` (например, проверка, что мок настроен правильно), но сама суть теста — проверить результат *после* действия.

**Q: Как быть, если Arrange слишком сложный из-за множества зависимостей?**
**A:** Используй паттерн **Builder**. Вместо того чтобы в тесте писать 10 строк `user.setName(...)`, `user.setAge(...)` и т.д., напиши `UserBuilder.user().withDefaultData().build()`. Тест должен фокусироваться на тестируемой логике, а не на заполнении полей.

# 🧠 Шпаргалка: `@SpringBootTest`

### 🎯 Суть
`@SpringBootTest` — это «тяжелая артиллерия» для **интеграционного тестирования**. В отличие от Unit-тестов, эта аннотация поднимает **полный ApplicationContext** твоего приложения. Она проверяет не просто логику метода, а то, как все твои бины (Service, Repository, Controller) работают вместе в реальной среде.

### ⚙️ Основные режимы (`webEnvironment`)
Это самый важный параметр. Он определяет, как именно будет поднята веб-среда:

1.  **`WebEnvironment.MOCK` (по умолчанию):**
    *   **Что происходит:** Контекст поднимается, но реальный HTTP-сервер (Tomcat/Netty) **не запускается**.
    *   **Как тестируем:** Используем `MockMvc`. Это имитация запросов внутри контекста.
    *   **Плюс:** Быстрее всего.
2.  **`WebEnvironment.RANDOM_PORT`:**
    *   **Что происходит:** Запускается **реальный сервер** на свободном порту.
    *   **Как тестируем:** Используем `TestRestTemplate` или `WebClient`. Мы делаем настоящие HTTP-вызовы по сети (localhost:port).
    *   **Плюс:** Максимально близко к реальности. Идеально для проверки сетевых настроек, фильтров и сериализации.
3.  **`WebEnvironment.DEFINED_PORT`:**
    *   **Что происходит:** Сервер запускается на порту, указанном в твоих конфигах (например, 8080).
    *   **Минус:** Опасно. Если порт занят другим процессом — тест упадет. В CI/CD это плохая практика.
4.  **`WebEnvironment.NONE`:**
    *   **Что происходит:** Поднимается только контекст (бины), веб-слой вообще не инициализируется. Полезно для тестирования фоновых задач или чисто сервисной логики.

### 🛠️ Управление конфигурацией
Когда ты запускаешь `@SpringBootTest`, тебе часто нужно подменить настройки базы или внешних API:

*   **`properties = "key=value"`:** Переопределяет конкретное свойство прямо в аннотации.
*   **`@ActiveProfiles("test")`:** Подключает профиль `application-test.yml`. Это стандарт де-факто для настройки тестовой БД.
*   **`@TestPropertySource`:** Позволяет указать путь к конкретному `.properties` файлу для теста.

### ⚠️ Нюансы и "Senior" советы (Pitfalls)

1.  **Проблема "Slow Tests":** Поскольку `@SpringBootTest` поднимает весь контекст, тесты становятся медленными. **Золотое правило:** не используй `@SpringBootTest` там, где достаточно `@WebMvcTest` (для контроллеров) или `@DataJpaTest` (для репозиториев).
2.  **Контекстное загрязнение (`@DirtiesContext`):** Если один тест меняет состояние бина (например, перенастраивает `DataSource`), Spring может "испортить" контекст для следующих тестов. Использование `@DirtiesContext` заставляет Spring пересоздать контекст с нуля. 
    *   *Совет:* Избегай этой аннотации как огня. Она убивает производительность. Лучше чисти базу данных вручную или используй транзакции.
3.  **`@MockBean` vs `@SpyBean`:** Внутри `@SpringBootTest` ты можешь заменить реальный бин на мок. Это позволяет тестировать интеграцию, но "отрезать" проблемные части (например, сторонний платежный шлюз).

---

### ❓ FAQ (Подготовка к собеседованию)

**В: Чем `@SpringBootTest` отличается от `@WebMvcTest`?**
**О:** `@SpringBootTest` поднимает **весь** контекст приложения (Full Integration Test). `@WebMvcTest` — это "срез" (Slice Test), он поднимает только веб-слой (контроллеры, фильтры, мапперы) и не трогает репозитории или сервисы.

**В: Что произойдет с базой данных, если я помечу тест аннотацией `@Transactional`?**
**О:** В Spring-тестах `@Transactional` работает магически: после завершения теста транзакция будет **автоматически откачена (rollback)**. Это гарантирует, что тесты не оставляют мусор в БД и не влияют друг на друга.

**В: Как протестировать реальный HTTP-запрос, если я использую `RANDOM_PORT`?**
**О:** Тебе нужно внедрить `TestRestTemplate` или `WebClient`. Spring сам сконфигурирует их так, чтобы они знали, на каком случайном порту сейчас крутится твой сервер.

**В: Когда стоит использовать `@DirtiesContext`?**
**О:** Только в крайнем случае, когда тест настолько сильно меняет состояние бинов (например, через рефлексию или изменение конфигурации), что это невозможно исправить очисткой данных, и последующие тесты гарантированно упадут. Помни: каждый такой вызов — это потеря нескольких секунд/минут времени сборки.

# 🧠 Шпаргалка: Конфигурация тестов в Spring

**Суть темы:** В Spring-тестах главная задача — не просто «запустить код», а **управлять `ApplicationContext`**. Тесты могут быть тяжелыми (поднимать всё приложение) или легкими (поднимать один контроллер). Конфигурация определяет, что именно попадет в этот контекст.

---

### 1. Уровни загрузки контекста

#### А. Полный контекст (`@SpringBootTest`)
Используется для интеграционных тестов. Spring ищет `@SpringBootApplication` и поднимает всё: бины, БД, очереди, сервисы.
*   **Нюанс:** Это самый медленный способ. Если у тебя 100 таких тестов, которые каждый раз создают новый контекст, сборка будет идти вечно.
*   **Параметр `webEnvironment`:** Позволяет указать, нужно ли поднимать реальный веб-сервер (например, Tomcat) или достаточно простого Mock-окружения.

#### Б. Слайс-тесты (Sliced Tests) — «Хирургический подход»
Вместо всего приложения мы берем только нужный слой. Это **золотой стандарт** для быстрых тестов.
*   `@WebMvcTest`: Только контроллеры + фильтры + мапперы. Репозитории и сервисы не грузятся (их надо подсунуть через `@MockBean`).
*   `@DataJpaTest`: Только JPA компоненты, Hibernate, DataSource. Автоматически настраивает базу в памяти (H2).
*   `@JsonTest`: Только сериализация/десериализация JSON.

#### В. Кастомная конфигурация (`@ContextConfiguration`)
Если тебе не нужен `@SpringBootTest`, но ты хочешь вручную указать, какие классы конфигурации или файлы свойств загрузить. Это дает полный контроль и максимальную скорость.

---

### 2. Управление свойствами (Properties)

Тестам часто нужны другие настройки, чем основному приложению (другой URL базы, другой API-ключ).

*   **`@TestPropertySource`**: Самый удобный способ переопределить `application.properties` конкретно для этого теста.
    *   Можно указать путь к файлу: `locations = "classpath:test-config.properties"`.
    *   Можно переопределить конкретное поле: `properties = "server.port=8081"`.
*   **`@ActiveProfiles`**: Переключает профили Spring. 
    *   *Пример:* `@ActiveProfiles("test")` заставит Spring искать `application-test.properties`. Это лучший способ разделять настройки для `dev`, `prod` и `test`.
*   **`@DynamicPropertySource` (Must Have!)**: Используется в паре с **Testcontainers**. Позволяет динамически прокинуть в контекст параметры, которые известны только во время выполнения теста (например, случайный порт поднятого в Docker контейнера с PostgreSQL).

---

### 3. Главная ловушка: Context Caching & Dirty Context

Это то, на чем валятся мидлы. Spring старается **кешировать** контекст. Если два теста используют одинаковую конфигурацию, Spring не создает новый контекст, а берет старый. Это экономит кучу времени.

*   **Проблема:** Если один тест меняет состояние бина (например, через `@MockBean` или меняет данные в БД), следующий тест может получить «испорченный» контекст.
*   **Решение 1: `@DirtyContext`**: Аннотация говорит Spring: «Этот тест испортил контекст, удали его и создай новый для следующего теста».
    *   **⚠️ ВНИМАНИЕ:** Никогда не используй это повсеместно! Это убивает производительность. Используй только в крайнем случае.
*   **Решение 2: Изоляция**: Старайся писать тесты так, чтобы они не меняли состояние общих бинов. Если нужно подменить бин — используй `@MockBean`, Spring умеет грамотно управлять кешем при использовании этого аннотации (хотя и это может привести к пересозданию контекста).

---

### 💡 FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `@SpringBootTest` и `@WebMvcTest`?**
**О:** `@SpringBootTest` поднимает полный контекст приложения со всеми зависимостями. `@WebMvcTest` — это "срез" (slice), он загружает только веб-слой (контроллеры, фильтры). Второй гораздо быстрее.

**В: Что произойдет с производительностью тестов, если я буду использовать `@MockBean` в каждом тестовом классе по-разному?**
**О:** Spring будет вынужден создавать новый `ApplicationContext` для каждого класса, где конфигурация моков отличается от предыдущего. Это приведет к "Context Churn" (постоянной пересборке контекста) и резкому замедлению тестов.

**В: Как протестировать интеграцию с базой данных, если порт базы меняется при каждом запуске Docker-контейнера?**
**О:** Нужно использовать `@DynamicPropertySource`. В этом методе ты берешь динамический порт из контейнера и вызываешь `registry.add("spring.datasource.url", ... )`.

**В: Можно ли использовать `@TestPropertySource` вместе с `@ActiveProfiles`?**
**О:** Да. Сначала применятся настройки профиля (например, `application-test.properties`), а затем значения из `@TestPropertySource` перекроют их. Порядок имеет значение.

# 🧠 Шпаргалка: @ContextConfiguration

### 🎯 Суть в двух словах
`@ContextConfiguration` — это твой пульт управления созданием `ApplicationContext` в тестах. 

Когда ты используешь `@SpringBootTest`, Spring поднимает **весь** контекст приложения (все бины, все настройки). Это круто для интеграционных тестов, но ужасно медленно для разработки. `@ContextConfiguration` позволяет тебе сказать: *"Мне не нужно всё приложение, подними мне только вот эти конкретные классы/конфигурации"*.

**Главная цель:** Изоляция и скорость.

---

### 🛠 Основные способы использования

#### 1. Загрузка через Java-конфигурацию (`classes`)
Самый современный и рекомендуемый способ. Ты указываешь конкретный класс с аннотацией `@Configuration`.
```java
@ExtendWith(SpringExtension.class) // Для JUnit 5
@ContextConfiguration(classes = {MyServiceConfig.class, TestDataConfig.class})
class MyServiceTest {
    @Autowired
    private MyService myService; // Будет поднят только из указанных конфигов
}
```

#### 2. Загрузка через XML (`locations`)
Если ты работаешь с легаси-проектом, где всё на XML.
```java
@ContextConfiguration(locations = "classpath:test-context.xml")
class LegacyTest { ... }
```

#### 3. Использование аннотированных классов (`annotatedClasses`)
Позволяет передать классы, которые сами по себе не являются конфигурациями, но имеют нужные аннотации (например, `@Component`).
```java
@ContextConfiguration(annotatedClasses = {MyComponent.class})
class ComponentTest { ... }
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Проблема Context Caching (Кэширование контекста):**
    Spring очень умный. Если два разных теста используют **одинаковый** набор конфигураций в `@ContextConfiguration`, Spring поднимет контекст один раз и переиспользует его. 
    *   *Нюанс:* Если ты в одном тесте добавишь `@MockBean`, а в другом нет — для Spring это **разные** контексты. Он создаст второй. Если таких тестов будет много, время выполнения тестов взлетит до небес (это называют *Context Dirtying*).

2.  **@SpringBootTest vs @ContextConfiguration:**
    *   `@SpringBootTest` ищет `@SpringBootApplication` и строит дерево зависимостей "снизу вверх" (автоконфигурации, сканирование пакетов). Это **тяжело**.
    *   `@ContextConfiguration` — это "ручное управление". Ты сам определяешь границы. Это **легко**.

3.  **Зависимости внутри конфигураций:**
    Если твой `MyServiceConfig` требует `DatabaseConfig`, а ты не указал его в `@ContextConfiguration`, тест упадет с `NoSuchBeanDefinitionException`. Всегда следи за графом зависимостей своих тестовых конфигов.

4.  **Использование с Sliced Tests:**
    В современных Spring Boot тестах (типа `@WebMvcTest` или `@DataJpaTest`) `@ContextConfiguration` часто используется "под капотом" или дополняется, чтобы подгрузить специфичные бины, не раздувая контекст до уровня всего приложения.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем принципиальная разница между `@SpringBootTest` и `@ContextConfiguration`?**
**О:** `@SpringBootTest` — это автоматика. Он пытается воссоздать реальное приложение, включая все автоконфигурации Spring Boot. `@ContextConfiguration` — это ручной режим. Ты сам выбираешь, какие именно классы конфигурации должны участвовать в создании контекста.

**В: Что произойдет, если я укажу в `classes` класс, который требует бин, не указанный в списке?**
**О:** Тест упадет при старте контекста с ошибкой `BeanCreationException`. Spring не будет искать этот бин по всему проекту (если ты не используешь компонент-сканирование), он будет смотреть только в то, что ты явно разрешил.

**В: Как ускорить тесты, если я вижу, что контекст пересоздается слишком часто?**
**О:** Нужно стремиться к тому, чтобы конфигурация (набор классов в `@ContextConfiguration`) была идентичной во всех тестах. Старайся выносить общую конфигурацию для тестов в отдельный базовый класс (например, `BaseIntegrationTest`), от которого будут наследоваться все остальные.

**В: Можно ли использовать `@ContextConfiguration` вместе с `@MockBean`?**
**О:** Да, и это стандартная практика. Ты создаешь легкий контекст через `@ContextConfiguration`, а затем заменяешь тяжелые внешние зависимости (например, API стороннего сервиса) на моки с помощью `@MockBean`.

# 🚀 Шпаргалка: `@TestPropertySource`

### 💡 Что это такое?
`@TestPropertySource` — это аннотация в Spring Test, которая позволяет тебе переопределить или добавить новые свойства (`properties`) специально для конкретного тестового класса. 

Представь, что у тебя есть `application.properties`, где прописан URL базы данных. Но для одного конкретного теста тебе нужно временно подменить этот URL на другой (например, на H2). Вместо того чтобы менять глобальный конфиг, ты используешь `@TestPropertySource`.

---

### 🛠 Основные способы использования

#### 1. Inline-свойства (прямо в аннотации)
Самый быстрый способ для мелких правок. Подходит, если нужно поменять всего одно значение.
```java
@SpringBootTest
@TestPropertySource(properties = {
    "app.feature.enabled=true",
    "user.role=ADMIN"
})
class FeatureTest { ... }
```

#### 2. Загрузка из внешнего файла
Если настроек много, лучше вынести их в отдельный `.properties` файл в папке `src/test/resources`.
```java
@SpringBootTest
@TestPropertySource(locations = "classpath:test-config.properties")
class ExternalConfigTest { ... }
```

#### 3. Фильтрация свойств (`includeProperties`)
Если ты хочешь загрузить файл, но применить из него **только** определенные ключи, игнорируя остальные.
```java
@TestPropertySource(
    locations = "classpath:full-test-config.properties",
    includeProperties = "app.timeout" // Загрузит только timeout из этого файла
)
```

---

### 🧠 Нюансы и «подводные камни» (Senior Level)

1.  **⚠️ Смертельная ловушка: YAML не поддерживается!**
    `@TestPropertySource` умеет работать **только с `.properties` файлами**. Если ты попытаешься указать `locations = "classpath:test-config.yml"`, Spring выдаст ошибку или просто проигнорирует настройки. Для YAML нужно использовать `@SpringBootTest(properties = ...)` или профили (`@ActiveProfiles`).

2.  **🔝 Приоритет (Precedence):**
    Свойства, указанные в `@TestPropertySource`, имеют **высокий приоритет**. Они перекрывают значения из `application.properties` и `application.yml`. Это именно то, что нужно для изоляции тестов.

3.  **📂 Classpath vs File System:**
    Всегда используй префикс `classpath:`. Если ты укажешь путь без него, Spring будет искать файл в корне файловой системы твоего компьютера/сервера, а не внутри ресурсов проекта.

4.  **🔄 Наслоение (Layering):**
    Ты можешь комбинировать `@TestPropertySource` с `@ActiveProfiles`. Сначала загрузятся настройки профиля, а затем `@TestPropertySource` «наложит» свои значения поверх них.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли использовать `@TestPropertySource` для подмены конфигурации из YAML?**
**О:** Напрямую — нет. Аннотация работает только с форматом `.properties`. Если нужно переопределить YAML, используй `properties` атрибут в `@SpringBootTest` или создай отдельный тестовый профиль.

**В: Что произойдет, если указанный файл не будет найден?**
**О:** Контекст приложения не сможет подняться (`ApplicationContextException`), и тест упадет еще на этапе инициализации.

**В: В чем разница между `properties` и `locations` в этой аннотации?**
**О:** `properties` — это список пар "ключ=значение" прямо в коде. `locations` — это пути к файлам, которые лежат в ресурсах проекта.

**В: Как протестировать поведение системы при включенном/выключенном флаге без создания новых файлов?**
**О:** Используй `properties = "my.feature.flag=true"`. Это самый чистый и быстрый способ для Unit/Integration тестов на один конкретный сценарий.

# 🧠 Шпаргалка: Тестовая конфигурация и `@ActiveProfiles`

### 📌 Суть темы
В Spring профили (`Profiles`) — это способ группировки настроек. В обычном приложении у нас есть `application-dev.yml`, `application-prod.yml` и т.д. 

В тестировании нам часто нужно, чтобы приложение вело себя **иначе**, чем в продакшe: например, вместо реального PostgreSQL использовать H2, или вместо реального API внешнего сервиса использовать заглушку (Mock). Аннотация `@ActiveProfiles` — это инструмент, который говорит Spring: *"При запуске этого теста включи вот эти конкретные профили"*.

---

### 🛠 Основное использование

#### 1. Активация одного профиля
Если тебе нужно, чтобы тест использовал настройки из `application-test.yml`.
```java
@SpringBootTest
@ActiveProfiles("test") // Включает профиль 'test'
class MyIntegrationTest { ... }
```

#### 2. Несколько профилей сразу
Ты можешь комбинировать профили. Например, один для базы данных, другой для настройки безопасности.
```java
@ActiveProfiles({"test", "h2-db", "no-security"})
@SpringBootTest
class MultiProfileTest { ... }
```

#### 3. Как это работает с файлами
Когда ты пишешь `@ActiveProfiles("test")`, Spring ищет файлы в таком порядке (приоритет выше у более специфичных):
1. `application-test.yml` (или `.properties`) — **самый важный для теста**.
2. `application.yml` — базовые настройки.

---

### ⚠️ Нюансы и "подводные камни" (Senior Level)

#### 1. Наслоение профилей (Layering)
`@ActiveProfiles` не заменяет текущий контекст, а **добавляет** новые профили к тем, что уже активны. Если у тебя в системных переменных (`export SPRING_PROFILES_ACTIVE=dev`) уже стоит `dev`, то после `@ActiveProfiles("test")` у тебя будут активны **оба**: `dev` и `test`. 
*   **Совет:** Всегда старайся делать профиль `test` максимально изолированным.

#### 2. Использование вместе с `@TestPropertySource`
Иногда тебе не нужен целый файл `application-test.yml`, а нужно поменять всего одну строчку (например, URL сервиса). Вместо создания нового профиля используй:
```java
@SpringBootTest
@TestPropertySource(properties = "external.api.url=http://localhost:8080")
class SinglePropertyTest { ... }
```
*Это чище, чем плодить десятки мелких файлов конфигурации.*

#### 3. Профили для бинов (`@Profile`)
Ты можешь создавать разные реализации бинов для разных профилей.
```java
@Bean
@Profile("test")
public EmailService mockEmailService() {
    return new MockEmailService(); // Не отправляет реальные письма в тестах
}

@Bean
@Profile("prod")
public EmailService realEmailService() {
    return new RealEmailService(); // Отправляет через SMTP
}
```
`@ActiveProfiles("test")` автоматически подставит `MockEmailService`.

#### 4. Проблема "Тяжелого контекста"
Если один тест использует `@ActiveProfiles("test")`, а другой `@ActiveProfiles("integration")`, Spring **не сможет переиспользовать** контекст. Он будет вынужден остановить старый и запустить новый. Если таких тестов много — сборка станет очень медленной.
*   **Совет:** Старайся держать набор активных профилей в тестах максимально одинаковым.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что произойдет, если я укажу `@ActiveProfiles("test")`, но файла `application-test.yml` не существует?**
**О:** Ошибки не будет. Spring просто проигнорирует этот профиль и будет использовать настройки из базового `application.yml`. Но ты можешь потерять нужную конфигурацию (например, настройки БД), что приведет к падению теста на этапе инициализации бинов.

**В: Можно ли переопределить значения из `@ActiveProfiles` прямо в коде теста?**
**О:** Да, через аннотацию `@TestPropertySource` или через системные свойства. Свойства, заданные явно в коде (через `properties = ...`), имеют более высокий приоритет, чем те, что лежат в файлах профилей.

**В: Как проверить, какой профиль сейчас активен, прямо во время выполнения теста?**
**О:** Ты можешь внедрить объект `Environment` в свой тест и проверить его:
```java
@Autowired
private Environment env;

@Test
void checkProfile() {
    boolean isTest = Arrays.asList(env.getActiveProfiles()).contains("test");
    assertTrue(isTest);
}
```

**В: В чем разница между `@ActiveProfiles` и `@SpringBootTest(properties = "...")`?**
**О:** `@ActiveProfiles` включает целую логику (файлы, бины с `@Profile`), а `properties` в `@SpringBootTest` просто меняет конкретные значения переменных. Для массовой настройки окружения используй профили, для точечной правки одного параметра — `properties`.

# 🧠 Шпаргалка: Управление бинами в тестах (Spring Testing)

Когда мы тестируем Spring-приложение, главная проблема — это **ApplicationContext**. Если мы будем поднимать полный контекст со всеми базами, очередями и сервисами для каждого теста, наши тесты будут идти вечность. Управление бинами позволяет нам «подменять» части системы, чтобы изолировать тестируемый компонент.

### 1. Основные инструменты подмены

#### `@MockBean` — Твой главный инструмент
Это не просто создание мока (как в Mockito), это **замена** существующего бина в контексте Spring на Mockito-мок.
* **Как работает:** Spring находит в контексте бин нужного типа, удаляет его и кладет туда свой `Mock`.
* **Когда использовать:** Когда ты тестируешь слой (например, Controller) и хочешь, чтобы все зависимости (Service, Repository) были заглушками.
* **Нюанс:** `@MockBean` создает новый контекст, если тип или конфигурация меняются.

#### `@SpyBean` — «Полуправда»
Работает как `@MockBean`, но вместо полной заглушки он оборачивает **реальный** бин в `Spy`.
* **Как работает:** Реальные методы бина продолжают работать, если ты их не переопределил (не сделал `doReturn`). Но ты можешь использовать `verify()`, чтобы проверить, вызывался ли метод.
* **Когда использовать:** Когда нужно протестировать сложную логику сервиса, но «подрезать» только один конкретный вызов (например, отправку Email или запрос во внешнюю API).

---

### 2. Управление конфигурацией и импортом

#### `@Import` — Дозаправка контекста
Если ты используешь «срезанное» тестирование (например, `@WebMvcTest`), в контексте нет твоих сервисов.
* **Зачем:** Чтобы подтянуть конкретный класс конфигурации или дополнительный бин, который не попал в текущий slice-тест.

#### `@TestConfiguration` — Спец-настройки для тестов
Это специальный класс, который не попадает в основной код приложения.
* **Как работает:** Ты помечаешь его этой аннотацией, и Spring использует его настройки только во время тестов. В нем можно переопределять бины или добавлять новые «тестовые» версии бинов.

---

### 3. Главная ловушка: Context Dirtying (Загрязнение контекста)

Это то, на чем валятся джуны. Каждый раз, когда ты используешь `@MockBean`, `@SpyBean` или меняешь `@TestPropertySource`, Spring понимает: *"Опа, конфигурация изменилась! Старый контекст мне больше не подходит"*.
* **Результат:** Spring создает **новый** `ApplicationContext`.
* **Последствие:** Если у тебя 100 тестов и в каждом свой `@MockBean`, вместо одного быстрого запуска ты получишь 100 запусков приложения. Тесты станут идти часами.

#### `@DirtiesContext` — «Ядерная кнопка»
Аннотация, которая говорит Spring: *"Этот тест изменил состояние контекста (например, поменял что-то в БД или в бине), после теста этот контекст нужно уничтожить и создать новый"*.
* **Senior Advice:** **Избегай её как огня.** Это самый медленный способ тестирования. Если тебе пришлось использовать `@DirtiesContext`, значит, твои тесты не изолированы и зависят друг от друга.

---

### 🚀 Резюме (Cheat Sheet)

| Аннотация | Что делает с контекстом? | Суть |
| :--- | :--- | :--- |
| **`@MockBean`** | Создает новый контекст (если тип новый) | Заменяет реальный бин на Mockito-мок. |
| **`@SpyBean`** | Создает новый контекму (если тип новый) | Оборачивает реальный бин в Spy (можно подменить методы). |
| **`@Import`** | Расширяет текущий контекст | Добавляет недостающие классы конфигурации. |
| **`@TestConfiguration`** | Добавляет настройки только для тестов | Позволяет создавать кастомные бины для тестов. |
| **`@DirtiesContext`** | Убивает и пересоздает контекст | Самый дорогой (медленный) способ очистки. |

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем разница между `@Mock` (из Mockito) и `@MockBean` (из Spring Boot)?**
**О:** `@Mock` создает объект-заглушку, который живет только внутри одного тестового класса и **не знает про Spring**. `@MockBean` берет бин из `ApplicationContext` и заменяет его на мок, чтобы все остальные компоненты, зависящие от этого бина, начали использовать эту заглушку.

**В: Почему мои тесты стали работать очень медленно после добавления нескольких `@MockBean`?**
**О:** Потому что каждый новый `@MockBean` с новым типом данных заставляет Spring создавать новый `ApplicationContext`. Происходит "Context Churning" (перемешивание контекстов). Нужно стараться группировать тесты так, чтобы они использовали одну и ту же конфигурацию моков.

**В: Можно ли использовать `@SpyBean` на бине, который не был создан в Spring?**
**О:** Нет. Чтобы `@SpyBean` сработал, Spring должен сначала найти этот бин в контексте, чтобы «обернуть» его. Если бина нет — будет ошибка.

**В: Когда стоит использовать `@TestConfiguration` вместо обычного `@Bean` в тестовом классе?**
**О:** Если конфигурация нужна многим тестовым классам (глобальная), используй `@TestConfiguration`. Если она нужна только одному конкретному тесту — можно объявить `@Bean` прямо внутри тестового класса.

# 🧠 Шпаргалка: Управление бинами в тестах — `@MockBean`

### 🎯 Суть в двух словах
`@MockBean` — это инструмент из библиотеки **Spring Boot Test**, который позволяет взять существующий бин в Spring Context и **заменить его на Mockito-мок**. 

Представь, что у тебя есть работающее приложение (контекст), и ты хочешь протестировать один сервис, но «выключить» (подменить) другой сервис или репозиторий, чтобы не ходить в реальную базу или сторонний API. `@MockBean` делает именно это: он находит бин нужного типа в контексте и подсовывает вместо него «пустышку».

---

### 🛠 Как это работает (Механика)
Когда Spring видит `@MockBean`:
1. Он проверяет `ApplicationContext` на наличие бина с таким же типом/именем.
2. **Если бин найден:** Spring удаляет оригинальный бин из контекста и вставляет туда Mockito-мок.
3. **Если бина нет:** Spring создает новый мок и регистрирует его в контексте как полноценный бин.

**Важно:** Все остальные компоненты, которые зависят от этого бина (через `@Autowired`), автоматически начнут получать этот новый мок. Тебе не нужно вручную пересобирать зависимости.

---

### ⚖️ Главное отличие: `@Mock` vs `@MockBean`
Это классический вопрос на собеседовании. Не путай их!

| Характеристика | `@Mock` (Mockito) | `@MockBean` (Spring Boot) |
| :--- | :--- | :--- |
| **Где живет** | Вне Spring Context (внутри JUnit) | **Внутри** Spring ApplicationContext |
| **Для чего** | Для чистых Unit-тестов (где ты сам создаешь объекты через `new`) | Для интеграционных тестов (где поднимается контекст Spring) |
/ **Зависимости** | Не умеет подменять `@Autowired` бины в других классах | Автоматически подменяет все зависимости в контексте |

---

### ⚠️ Нюансы и "Подводные камни" (Senior Level)

#### 1. Проблема "Dirty Context" (Загрязнение контекста) — **Самое важное!**
Каждый раз, когда ты используешь `@MockBean` в одном тестовом классе и другой набор `@MockBean` в другом, Spring может посчитать, что это **разные конфигурации**. 
* **Результат:** Spring будет вынужден останавливать старый контекст и поднимать новый. 
* **Последствие:** Твои тесты начнут выполняться очень медленно (вместо 10 секунд — 2 минуты).
* **Совет:** Старайся группировать тесты так, чтобы они использовали одинаковый набор `@MockBean`.

#### 2. `@MockBean` vs `@SpyBean`
Если тебе не нужно полностью удалять реальный бин, а ты хочешь лишь «подглядывать» за ним или переопределить только один метод, используй `@SpyBean`. Он оставляет реальную логику работающей, но позволяет делать `verify()` или `doReturn()`.

#### 3. Состояние мока
По умолчанию Spring Boot старается сбрасывать состояние моков между тестами, чтобы один тест не влиял на другой (например, через `when(...).thenReturn(...)`). Однако, если ты используешь сложные кастомные настройки, всегда проверяй, что `verify()` не выдает ложноположительных результатов из-за предыдущих тестов.

### ❓ FAQ (Частые вопросы)

**В: Я использую `@WebMvcTest`. Можно ли там использовать `@MockBean`?**
**О:** Да, это стандартный паттерн. `@WebMvcTest` поднимает только слой контроллеров, а сервисы, которые им нужны, ты подменяешь через `@MockBean`, чтобы протестировать только логику HTTP-запросов.

**В: Почему мой тест падает с ошибкой `NoSuchBeanDefinitionException`, хотя я добавил `@MockBean`?**
**О:** Проверь типы данных. Если ты создаешь `@MockBean` для интерфейса, но в контексте есть реализация, которая конфликтует по имени или типам (например, из-за использования Generic-типов), Spring может запутаться. Также убедись, что ты не пытаешься подменить бин, который не был загружен в этот конкретный тестовый профиль.

**В: Можно ли использовать `@MockBean` вместе с `@Autowired`?**
**О:** Да. Ты используешь `@MockBean`, чтобы создать мок в контексте, а затем через `@Autowired` внедряешь этот же мок в свой тестовый класс, чтобы настроить его поведение (`when(...).thenReturn(...)`).

# 🧠 Шпаргалка: `@SpyBean` в Spring Boot

### 1. Суть простыми словами
Представь, что у тебя есть настоящий сотрудник (реальный Bean в контексте Spring). 
*   **`@MockBean`** — это когда ты увольняешь настоящего сотрудника и нанимаешь актера, который просто делает вид, что он на работе. Он ничего не знает о процессах, он просто отвечает «null» или «0», пока ты ему не скажешь иначе.
*   **`@SpyBean`** — это когда настоящий сотрудник остается на месте и выполняет свою работу как обычно, но ты надеваешь на него скрытую камеру (Spy). Ты можешь подсматривать за его действиями (`verify`) или в критический момент «подсказать» ему ложный ответ (`doReturn`), но во всех остальных случаях он будет работать по-настоящему.

**Итог:** `@SpyBean` — это **частичное мокирование** реального объекта из контекста Spring.

---

### 2. Когда использовать?
1.  **Проверка взаимодействия (Verification):** Тебе нужно убедиться, что метод реального сервиса был вызван с правильными параметрами, но ты не хочешь подменять всю логику этого сервиса.
2.  **Partial Mocking:** Тебе нужно, чтобы 90% логики метода работало по-настоящему (например, расчет сложной формулы), а 10% (например, вызов внешнего API внутри этого же класса) — было подменено на заглушку.
3.  **Legacy Code:** Когда класс слишком сложный, чтобы его полностью мокать, и проще «заткнуть» только проблемный метод.

---

### 3. Главные нюансы (Senior Level)

#### ⚠️ Ловушка №1: Синтаксис `when(...)` vs `doReturn(...)`
Это самая частая ошибка. 
*   **Плохо:** `when(spy.method()).thenReturn(value);`
    *   *Почему:* При вызове `spy.method()` внутри `when(...)`, **реальный метод всё равно выполнится один раз!** Если этот метод лезет в базу или удаляет файлы — ты получишь побочные эффекты прямо во время настройки теста.
*   **Хорошо:** `doReturn(value).when(spy).method();`
    *   *Почему:* Этот синтаксис (из Mockito) говорит: «Не вызывай реальный метод, просто сразу подмени результат».

#### ⚠️ Ловушка №2: Pollution of ApplicationContext (Загрязнение контекста)
Использование `@SpyBean` или `@MockBean` модифицирует `ApplicationContext`. Spring кэширует контексты между тестами для скорости. Если в Тесте А ты использовал `@SpyBean`, а в Тесте Б — нет, Spring будет вынужден **пересоздать контекст** (это долго!).
*   *Совет:* Старайся группировать тесты с одинаковыми конфигурациями бинов в одном тестовом классе или использовать общие базовые классы.

#### ⚠️ Ловушка №3: `@SpyBean` vs `@MockBean`
Не используй `@SpyBean` там, где достаточно `@MockBean`. Если тебе не нужна реальная логика объекта — не трать ресурсы на поднятие его тяжелого контекста и выполнение его методов.

---

### 4. Пример кода

Допустим, у нас есть `PaymentService`, который вызывает `EmailService`. Мы хотим проверить, что при оплате вызывается отправка письма, но само письмо отправлять не хотим.

```java  
@SpringBootTest
class PaymentServiceTest {

    @SpyBean // Подменяем только EmailService, оставляя его реальную логику
    private EmailService emailService;

    @Autowired
    private PaymentService paymentService;

    @Test
    void testPaymentTriggersEmail() {
        // Arrange: Настраиваем Spy так, чтобы метод send не выполнял реальный код
        // Используем doReturn, чтобы избежать вызова реального метода!
        doReturn(true).when(emailService).sendEmail(anyString());

        // Act
        paymentService.processPayment(100.0);

        // Assert: Проверяем, что метод был вызван с правильным адресом
        verify(emailService).sendEmail("customer@example.com");
    }
}
```

### 5. FAQ (Частые вопросы на собеседовании)

**В: Чем `@SpyBean` отличается от обычного Mockito `@Spy`?**
**О:** `@Spy` — это чистый Mockito, он не знает про Spring Context. Он создает шпиона над объектом, который ты создал вручную. `@SpyBean` — это часть Spring Boot Test, она ищет существующий Bean в контексте Spring и «оборачивает» его в Spy, заменяя оригинал в контейнере.

**В: Что произойдет, если я использую `when(spy.method()).thenReturn(...)` вместо `doReturn`?**
**О:** Реальный метод выполнится один раз. Если внутри метода есть логика, зависящая от базы данных или других сервисов, тест может упасть с ошибкой (например, `NullPointerException`), даже если ты пытаешься его заглушить.

**В: Можно ли на один и тот же Bean повесить и `@MockBean`, и `@SpyBean`?**
**О:** Технически это приведет к конфликту конфигурации контекста. Spring не поймет, какую версию бина использовать (пустую или реальную с заглушкой), что приведет к непредсказуемому поведению или ошибке при запуске тестов. Выбирай одну стратегию для одного типа бина в рамках одного теста.

# 🧠 Шпаргалка: Управление бинами через `@Import`

### 📌 Суть (The Core)
В Spring Boot при написании интеграционных тестов мы часто используем **"Sliced Tests"** (срезанные тесты), такие как `@WebMvcTest` или `@DataJpaTest`. Эти аннотации поднимают **не весь контекст**, а только его часть (только контроллеры или только репозитории).

Если твоему контроллеру для работы нужен сервис, который не входит в "срез" `@WebMvcTest`, у тебя есть два пути: либо создать мок (`@MockBean`), либо принудительно подтянуть реальный бин/конфигурацию в контекст. **`@Import` — это инструмент для второго пути.**

Он говорит Spring: *"Возьми этот класс конфигурации или этот компонент и добавь его в текущий тестовый контекст"*.

---

### 🛠 Основные сценарии использования

#### 1. Подгрузка конкретной конфигурации
Если у тебя есть `ServiceConfig`, где описаны важные бины (например, мапперы или кастомные сериализаторы), ты используешь `@Import(ServiceConfig.class)`.

#### 2. Дополнение "срезанного" контекста
Когда ты тестируешь слой Web (`@WebMvcTest`), Spring не видит твои `@Service`. Если ты хочешь протестировать контроллер с реальным (не моком), но легким сервисом, ты импортируешь его напрямую.

#### 3. Импорт простых компонентов
Ты можешь импортировать даже обычный класс, помеченный `@Component`, чтобы он стал бином в тесте.

---

### ⚠️ Нюансы и "Подводные камни" (Senior Insights)

1.  **Проблема Dirty Context (Загрязнение контекста):**
    Это самый важный момент. Spring кэширует контексты между тестами. Если `TestA` использует `@Import(Config1.class)`, а `TestB` использует `@Import(Config2.com)`, то для `TestB` Spring будет вынужден **полностью перезапустить контекст**. 
    *   **Совет:** Старайся группировать тесты так, чтобы они использовали одинаковый набор импортов. Иначе твоя сборка будет идти вечно.

2.  **`@Import` vs `@MockBean`:**
    *   Используй `@MockBean`, если тебе нужно изолировать тестируемый класс (контроллер) от его зависимостей (сервисов).
    *   Используй `@Import`, если ты хочешь протестировать реальное взаимодействие между компонентами, не поднимая всё приложение.

3.  **Конфликты бинов:**
    Если в контексте уже есть бин того же типа, что ты пытаешься импортировать, может возникнуть `NoUniqueBeanDefinitionException`. Нужно следить за тем, что именно ты "подмешиваешь".

---

### 💻 Пример кода

Представь, что у нас есть контроллер, которому нужен `HelperService`. Но мы тестируем только Web-слой.

```java
// Реальный сервис, который мы хотим подтянуть
@Component
public class HelperService {
    public String getMagicWord() { return "Spring is Awesome"; }
}

// Контроллер, зависящий от сервиса
@RestController
public class MyController {
    private final HelperService helperService;

    public MyController(HelperService helperService) {
        this.helperService = helperService;
    }

    @GetMapping("/magic")
    public String magic() { return helperService.getMagicWord(); }
}

// ТЕСТ
@WebMvcTest(MyController.class) // Поднимает ТОЛЬКО контроллеры
@Import(HelperService.class)    // Принудительно добавляем HelperService в контекст
class MyControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @Test
    void testMagicEndpoint() throws Exception {
        mockMvc.perform(get("/magic"))
               .andExpect(status().isOk())
               .andExpect(content().string("Spring is Awesome")); // Работает, так как сервис импортирован!
    }
}
```

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем `@Import` отличается от `@ContextConfiguration`?**
**О:** `@ContextConfiguration` — это более мощный инструмент, который определяет *весь* состав контекста с нуля. `@Import` — это "добавка" к уже существующему (или срезанному) контексту.

**В: Что произойдет, если я импортирую класс, который не является конфигурацией или компонентом?**
**О:** Spring попытается обработать его как конфигурацию. Если в нем нет аннотаций `@Configuration` или `@Component`, он просто проигнорирует его (или выдаст ошибку, если не сможет создать бин из него).

**В: Как избежать замедления тестов при использовании `@Import`?**
**О:** Создавай базовый абстрактный класс для тестов со всеми общими `@Import`. Все тесты, наследующие этот класс, будут использовать один и тот же кэшированный контекст, что ускорит выполнение.

# 🧠 Dependency Injection in Tests: The Senior's Guide

Когда мы говорим о DI в тестах, новички часто путают две разные вселенные: **Unit-тесты** (где Spring вообще не участвует) и **Integration-тесты** (где живет Spring Context). Это критически важно понимать.

## 1. Вселенная №1: Unit-тесты (Pure Mockito)
Здесь нет никакого Spring. Нет контекста, нет бинов, нет магии. Есть только твой класс и его зависимости, которые ты создаешь вручную или через Mockito.

**Как мы внедряем зависимости:**
*   **Manual Injection (Constructor):** Самый чистый и надежный способ. Ты просто пишешь `new MyService(mockRepo)`. Это делает тест прозрачным: сразу видно, что куда пришло.
*   **`@InjectMocks`:** Аннотация Mockito. Она пытается сама «засунуть» все твои `@Mock` в объект под аннотацией `@InjectMocks`. 
    *   *Нюанс:* Она использует рефлексию. Если у тебя сложная иерархия или несколько конструкторов, она может сработать не так, как ты ожидаешь.

**Senior Tip:** Всегда старайся использовать **Constructor Injection** в тестах. Это делает твой тест независимым от магии фреймворков и гарантирует, что ты тестируешь именно то, что написал.

---

## 2. Вселенная №2: Integration/Slice Tests (Spring Context)
Здесь Spring запускается (через `@SpringBootTest` или `@WebMvcTest`). Контекст создается, бины сканируются и создаются.

**Как мы внедряем зависимости:**
*   **`@Autowired`:** Ты просишь у Spring уже существующий бин из контекста. Это удобно для интеграционных тестов, когда тебе нужен реальный (или почти реальный) сервис.
*   **`@MockBean`:** **Ключевая фишка.** Эта аннотация не просто создает мок, она **заменяет** настоящий бин в Spring Context на этот мок. 
    *   *Зачем:* Допустим, у тебя есть `OrderService`, который внутри вызывает `PaymentGateway`. Ты хочешь протестировать логику заказов, но не хочешь, чтобы реально шел запрос в платежный шлюз. `@MockBean` подменит реальный шлюз на заглушку прямо внутри контекста Spring.
*   **`@SpyBean`:** То же самое, что и `@MockBean`, но вместо полной замены он берет реальный бин и «оборачивает» его в шпиона. Ты можешь проверять вызовы методов, но при этом реальный код бина будет выполняться.

---

## 3. Главные нюансы (Где все косячат)

### ⚠️ Разница между `@Mock` и `@MockBean`
Это классический вопрос на собеседовании.
*   **`@Mock` (Mockito):** Создает объект-заглушку в памяти. Он **не знает** про Spring. Если ты используешь его в `@SpringBootTest`, он не попадет в контекст приложения.
*   **`@MockBean` (Spring Boot Test):** Создает мок и **кладет его в ApplicationContext**. Все остальные бины, которые зависят от этого компонента, начнут использовать твой мок.

### ⚠️ Проблема "Dirty Context" (`@DirtiesContext`)
Когда ты используешь `@MockBean`, ты меняешь состояние Spring Context (подменяешь бин). Spring старается переиспользовать контекст между тестами для скорости. Если один тест изменил контекст, а второй ожидал чистый — ты получишь непредсказуемые ошибки. 
*   **Решение:** `@DirtiesContext` заставляет Spring пересоздать контекст после теста. 
*   **Senior Warning:** Используй это только в крайнем случае! Пересоздание контекста — самая дорогая операция. Если у тебя 100 тестов с этой аннотацией, твоя сборка будет идти вечность.

---

## ❓ FAQ (Частые вопросы)

**В: Почему мой `@Mock` не работает внутри `@SpringBootTest`, хотя я вижу его в коде?**
**О:** Потому что `@Mock` — это инструмент Mockito, он живет «снаружи» Spring. Чтобы Spring подставил его в свои бины, нужно использовать `@MockBean`.

**В: Что лучше: `@InjectMocks` или ручное создание объекта через `new`?**
**О:** Ручное создание через `new` (Constructor Injection). Это быстрее, надежнее и не скрывает зависимости. `@InjectMocks` — это «магия», которая может подвести в самый неподходящий момент при изменении структуры конструктора.

**В: Можно ли использовать `@Autowired` для моков?**
**О:** Технически можно, если бин уже есть в контексте, но это плохая практика. Если ты хочешь контролировать поведение зависимости в тесте — используй либо `@MockBean`, либо создавай её сам.

**В: Как протестировать метод, который использует `@Value` из `application.properties`?**
**О:** В Unit-тестах (без Spring) тебе придется передать это значение через конструктор вручную. В интеграционных тестах используй `@TestPropertySource(properties = "my.prop=test_value")`.

# 🧠 Шпаргалка: Web Layer Testing (Controller Test)

### 🎯 Суть темы
Тестирование веб-слоя — это **Slice Testing** (тестирование «среза»). Наша цель — проверить не логику бизнеса, а **интерфейс**: правильно ли работает маппинг URL, корректно ли парсится JSON, возвращаются ли нужные HTTP-статусы и срабатывает ли валидация.

Мы **не** поднимаем базу данных и **не** запускаем сервисы. Мы заменяем их «пустышками» (Mocks).

---

### 🛠 Основной инструментарий
1.  **`@WebMvcTest(YourController.class)`**: Главная аннотация. Она говорит Spring: «Подними только веб-инфраструктуру (фильтры, контроллеры, конвертеры), но не трогай остальное».
2.  **`MockMvc`**: Наш главный инструмент для имитации HTTP-запросов (`GET`, `POST`, `PUT`, `DELETE`).
3.  **`@MockBean`**: Создает мок (заглушку) и кладет его в контекст Spring, заменяя реальный сервис.
4.  **`jsonPath`**: Язык запросов к JSON-ответу (позволяет проверить конкретное поле внутри большого JSON).

---

### 💻 Пример: Как делать правильно

Представим контроллер `UserController`, который использует `UserService`.

#### ❌ Плохой подход (Anti-patterns)
*   Использование `@SpringBootTest` для тестов контроллера (слишком медленно, поднимает всё приложение).
*   Проверка бизнес-логики внутри теста контроллера (это задача Unit-теста сервиса).
*   Забывать про `@MockBean` для зависимостей контроллера (контекст просто не поднимется).

#### ✅ Хороший подход (Best Practices)

```java
@WebMvcTest(UserController.class) // Тестируем только этот контроллер
class UserControllerTest {

    @Autowired
    private MockMvc mockMvc; // Инструмент для запросов

    @MockBean
    private UserService userService; // Заменяем реальный сервис заглушкой

    @Autowired
    private ObjectMapper objectMapper; // Для превращения объектов в JSON

    @Test
    @DisplayName("Должен вернуть пользователя по ID и статус 200")
    void getUserById_Success() throws Exception {
        // 1. Arrange (Подготовка)
        UserDTO user = new UserDTO(1L, "John Doe");
        given(userService.findById(1L)).willReturn(user); // Настраиваем поведение мока

        // 2. Act & Assert (Действие и Проверка)
        mockMvc.perform(get("/api/users/1") // Делаем GET запрос
                .contentType(MediaType.APPLICATION_JSON))
                .andExpect(status().isOk()) // Проверяем статус 200
                .andExpect(jsonPath("$.id").value(1)) // Проверяем поле id в JSON
                .andExpect(jsonPath("$.name").value("John Doe")); // Проверяем имя
    }

    @Test
    @DisplayName("Должен вернуть 400, если данные валидации не прошли")
    void createUser_BadRequest() throws Exception {
        UserCreateRequest invalidRequest = new UserCreateRequest(""); // Пустое имя (ошибка)

        mockMvc.perform(post("/api/users")
                .contentType(MediaType.APPLICATION_JSON)
                .content(objectMapper.writeValueAsString(invalidRequest))) // Сериализуем объект в JSON
                .andExpect(status().isBadRequest()); // Проверяем, что сработала валидация @Valid
    }
}
```

1.  **Изоляция**: Если твой контроллер зависит от `UserService`, а тот в свою очередь требует `UserRepository`, то при использовании `@WebMvcTest` тебе **не нужно** мокать репозиторий. Тебе достаточно замолчать только `UserService`.
2.  **Валидация**: Всегда проверяй негативные сценарии (когда приходят пустые поля или неверный формат). Если в контроллере стоит `@Valid`, твой тест должен это подтверждать.
3.  **Content-Type**: Часто новички забывают `.contentType(MediaType.APPLICATION_JSON)`. Без этого Spring может не понять, как парсить тело запроса, и ты получишь `415 Unsupported Media Type`.
4.  **Тестирование ошибок**: Не забудь протестировать сценарии с `404 Not Found` или `403 Forbidden`. Для этого в `@MockBean` нужно настроить выброс исключения: `given(userService.findById(99L)).willThrow(new UserNotFoundException());`.

# 📑 Шпаргалка: Web Layer Testing (`@WebMvcTest`)

## 🎯 Суть темы
`@WebMvcTest` — это **Slice Test** (срез). Вметo того, чтобы поднимать всё приложение целиком (что долго и тяжело), Spring Boot поднимает только "веб-слой". Это делает тесты быстрыми и изолированным.

**Что загружается:**
* Контроллеры (`@Controller`, `@RestController`).
* `ControllerAdvice` (обработчики исключений).
* `Filter`, `WebMvcConfigurer`, `Converter`.
* Spring Security конфигурация.

**Что НЕ загружается:**
* `@Service`, `@Repository`, `@Component` и всё, что связано с базой данных или бизнес-логикой. 
* *Следствие:* Тебе **обязательно** нужно подсунуть моки для всех зависимостей контроллера.

---

## 🛠 Основной инструментарий

1.  **`MockMvc`** — главный инструмент. Это "виртуальный браузер". Он позволяет отправлять HTTP-запросы (GET, POST и т.д.) в контроллер без запуска реального сервера (Tomcat/Netty).
2.  **`@MockBean`** — магия Spring. Она создает Mockito-мок и **автоматически кладет его в ApplicationContext** вместо настоящего бина. Это позволяет контроллеру "думать", что сервис настоящий, хотя это заглушка.
3.  **`jsonPath`** — язык запросов к JSON-ответу. Позволяет проверять конкретные поля внутри пришедшего JSON (например, `$.id` или `$.user.name`).

---

## 🚀 Пример реализации

Представим контроллер, который получает пользователя по ID.

```java
@WebMvcTest(UserController.class) // Указываем конкретный контроллер для скорости
class UserControllerTest {

    @Autowired
    private MockMvc mockMvc; // Наш инструмент для запросов

    @MockBean
    private UserService userService; // Заменяем реальный сервис моком

    @Autowired
    private ObjectMapper objectMapper; // Для превращения объектов в JSON

    @Test
    void shouldReturnUser_WhenUserExists() throws Exception {
        // 1. Arrange (Подготовка)
        User mockUser = new User(1L, "Ivan");
        given(userService.getUserById(1L)).willReturn(mockUser);

        // 2. Act & Assert (Действие и Проверка)
        mockMvc.perform(get("/api/users/1")) // Выполняем GET запрос
                .andExpect(status().isOk())    // Ждем HTTP 200
                .andExpect(jsonPath("$.id").value(1)) // Проверяем поле id в JSON
                .andExpect(jsonPath("$.name").value("Ivan")); // Проверяем имя
    }

    @Test
    void shouldReturn404_WhenUserNotFound() throws Exception {
        // Подготовка: сервис кидает исключение
        given(userService.getUserById(99L)).willThrow(new UserNotFoundException());

        mockMvc.perform(get("/api/users/99"))
                .andExpect(status().isNotFound()); // Проверяем, что ControllerAdvice обработал ошибку
    }
}
```

## 💡 Нюансы и "Senior Tips" (На чем все ловятся)

1.  **Не используй `@SpringBootTest` для контроллеров.** Если ты напишешь `@SpringBootTest`, Spring поднимет всё: БД, Kafka, Redis. Тест будет идти 30 секунд вместо 2 секунд. Используй только `@WebMvcTest`.
2.  **Тестируй `ControllerAdvice`.** Смысл теста контроллера не только в "позитивном сценарии", но и в том, как он обрабатывает ошибки. Если сервис кинул `EntityNotFoundException`, твой контроллер должен вернуть именно `404`, а не `500`.
3.  **Проблема с Security.** Если в проекте есть Spring Security, `@WebMvcTest` попытается его поднять. Ты получишь `401 Unauthorized` или `403 Forbidden` даже на правильные запросы. 
    * *Решение:* Используй аннотацию `@WithMockUser(roles = "USER")`, чтобы имитировать авторизованного пользователя.
4.  **Используй `ObjectMapper`.** Для POST-запросов не собирай JSON строкой вручную (это путь к ошибкам). Создай объект, прогони через `objectMapper.writeValueAsString(obj)` и передай в `.content(...)`.
5.  **Указывай конкретный класс.** Пиши `@WebMvcTest(MyController.class)`, а не просто `@WebMvcTest`. Это заставляет Spring сканировать только один класс, что еще сильнее ускоряет тесты.

## ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем разница между `@Mock` и `@MockBean`?**
**О:** `@Mock` — это чистый Mockito (создает объект в памяти, не знает про Spring). `@MockBean` — это расширение Spring, которое создает мок и **вставляет его в контекст приложения**, чтобы контроллер мог его "увидеть" через `@Autowired`.

**В: Можно ли протестировать логику внутри сервиса с помощью `@WebMvcTest`?**
**О:** Нет. `@WebMvcTest` предназначен только для проверки маппинга (URL), статус-кодов, валидации входящих данных и структуры JSON-ответа. Логика сервиса должна проверяться в `Unit-тестах` (JUnit + Mockito).

**В: Что такое `jsonPath`?**
**О:** Это синтаксис для навигации по JSON-дереву. Символ `$` обозначает корень документа, а точки позволяют переходить вглубты (например, `$.address.city`).

**В: Как протестировать валидацию (например, `@Valid` на поле `@NotNull`)?**
**О:** Нужно отправить запрос с невалидным телом (например, с пустым именем) и ожидать статус `.andExpect(status().isBadRequest())`. Это отличный способ проверить, что твои аннотации валидации действительно работают.

# 🧠 Шпаргалка: Web Layer Testing (MockMvc)

## 🎯 Суть метода
Когда мы тестируем Web Layer, нам **не нужен** запущенный Tomcat или Jetty. Нам не нужно поднимать базу данных или брокеры сообщений. Наша цель — проверить **логику контроллера**:
1. Правильно ли работает маппинг (URL).
2. Верно ли принимаются параметры и JSON-тело.
3. Проходит ли валидация (`@Valid`).
4. Возвращается ли правильный HTTP статус и структура ответа.
5. Вызывается ли нужный метод сервиса с правильными аргументами.

Для этого мы используем **MockMvc** — инструмент, который имитирует HTTP-запрос прямо внутри контекста Spring, не выходя за пределы JVM.

---

## 🛠 Основной инструментарий

### 1. Аннотация `@WebMvcTest`
Это «слайс» (срез) тестирования. Она **не загружает** всё приложение целиком. Она поднимает только веб-слой: контроллеры, фильтры, конфигурации Spring MVC, конвертеры и обработчики исключений.
*   **Важно:** Все твои `@Service`, `@Repository` и прочие компоненты **не будут** найдены в контексте. Их нужно подсунуть вручную через `@MockBean`.

### 2. Объект `MockMvc`
Главный «драйвер» для отправки запросов. Обычно внедряется через `@Autowired`.

---

## 🚀 Практический синтаксис (Fluent API)

Тест строится по цепочке: `perform()` $\to$ `andExpect()` $\to$ `andDo()`.

### Пример базового теста
Предположим, у нас есть `UserController.create(UserDto dto)`.

```java
@WebMvcTest(UserController.class) // Загружаем только этот контроллер
class UserControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @MockBean
    private UserService userService; // Подменяем сервис моком

    @Autowired
    private ObjectMapper objectMapper; // Для превращения объектов в JSON

    @Test
    void shouldCreateUserSuccessfully() throws Exception {
        // 1. Arrange (Подготовка)
        UserDto inputDto = new UserDto("Ivan", "ivan@mail.com");
        UserResponse responseDto = new UserResponse(1L, "Ivan");
        
        // Настраиваем поведение мока
        when(userService.save(any(UserDto.class))).thenReturn(response/dto);

        // 2. Act & Assert (Действие и Проверка)
        mockMvc.perform(post("/api/users") // Тип запроса и URL
                .contentType(MediaType.APPLICATION_JSON) // Заголовок Content-Type
                .content(objectMapper.writeValueAsString(inputDto))) // Тело запроса (JSON)
            
            .andExpect(status().isCreated()) // Проверяем HTTP 201
            .andExpect(jsonPath("$.id").exists()) // Проверяем наличие поля id в JSON
            .andExpect(jsonPath("$.name").value("Ivan")) // Проверяем значение поля
            .andDo(print()); // Печатает детали запроса/ответа в консоль (очень полезно!)
    }
}
```

---

## 🔍 Ключевые инструменты проверки

*   **`status()`**: проверка кодов (`isOk()`, `isBadRequest()`, `isNotFound()`, `isNoContent()`).
*   **`jsonPath("$.path")`**: мощнейший инструмент для навигации по JSON.
    *   `$.name` — поле name в корне.
    *   `$.items[0].id` — id первого элемента в массиве items.
*   **`content()`**: проверка сырого содержимого (строки, байты).
*   **`header()`**: проверка HTTP-заголовков.

## ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Проблема `@MockBean` и контекста:** Каждый раз, когда ты используешь новый `@MockBean` в разных тестовых классах, Spring создает **новый** ApplicationContext. Это замедляет тесты. 
    *   *Совет:* Старайся группировать тесты так, чтобы набор моков был одинаковым.
2.  **Валидация (Bean Validation):** Если ты тестируешь `@Valid`, убедись, что в твоем `UserDto` стоят аннотации (`@NotNull`, `@Size`). `MockMvc` их проверяет, но только если контекст правильно настроен (что `@WebMvcTest` делает по умолчанию).
3.  **Тестирование ошибок:** Не забывай писать негативные тесты! Проверяй, что при невалидном JSON контроллер возвращает `400 Bad Request`, а не `500 Internal Server Error`.
4.  **Security:** Если в проекте есть Spring Security, `@WebMvcTest` попытается его загрузить. Ты можешь получить `401 Unauthorized` вместо ожидаемого результата. 
    *   *Решение:* Используй `@WithMockUser(roles = "USER")` для эмуляции авторизованного пользователя.

# 🧠 Шпаргалка: Web Layer — Тестирование маппинга (JSON $\leftrightarrow$ DTO)

### 🎯 Суть задачи
Когда мы говорим о тестировании маппинга в контроллерах, нас не интересует бизнес-логика. Нас интересует **«граница»** приложения. Мы проверяем, правильно ли Jackson (библиотека сериализации) превращает сырой JSON из HTTP-занка в наш Java-объект (DTO) и наоборот.

Если маппинг сломан — клиент пришлет валидные данные, но приложение их не увидит (или увидит `null`), либо клиент получит пустой ответ вместо ожидаемых данных.

---

### 🛠 Инструментарий
1.  **`@WebMvcTest(MyController.class)`**: Тестирует только веб-слой. Не поднимает базу, не поднимает сервисы. Это быстро.
2.  **`MockMvc`**: Наш главный инструмент для имитации HTTP-запросов (GET, POST и т.д.).
3.  **`ObjectMapper`**: Тот самый Jackson, который превращает Java в JSON. В тестах мы используем его же, что и в приложении.
4.  **`jsonPath`**: Язык запросов к JSON-ответу для проверки конкретных полей внутри тела ответа.

---

### ✅ Что именно нужно проверять (Checklist)

#### 1. Deserialization (JSON $\to$ DTO) — Входящие данные
*   **Типы данных:** Что будет, если прислать строку вместо числа?
*   **Формат дат:** Правильно ли парсится `ISO-86SS` или твой кастомный формат?
*   **Missing fields:** Как ведет себя система, если важного поля нет (оно станет `null` или упадет ошибка)?
*   **Extra fields:** Принимает ли контроллер поля, которых нет в DTO (настройка `FAIL_ON_UNKNOWN_PROPERTIES`)?
*   **Validation integration:** Если поле помечено `@NotNull`, возвращает ли маппинг ошибку 400 Bad Request?

#### 2. Serialization (DTO $\to$ JSON) — Исходящие данные
*   **Имена полей:** Правильно ли работает `@JsonProperty("user_name")`? (Client ждет `snake_case`, а получает `camelCase`).
*   **Видимость/Nulls:** Скрываются ли `null` поля (настройка `@JsonInclude(Include.NON_NULL)`)?
*   **Форматирование дат:** Видит ли клиент дату в нужном ему формате?

---

### 💻 Пример кода

Предположим, у нас есть `UserDTO` с аннотациями Jackson и валидацией.

```java
// DTO
public record UserDTO(
    @JsonProperty("full_name") @NotBlank String name,
    @JsonFormat(pattern = "yyyy-MM-dd") LocalDate birthDate
) {}

// Test
@WebMvcTest(UserController::class)
class UserControllerTest {

    @Autowired
    private MockMvc mockMvc;

    @Autowired
    private ObjectMapper objectMapper; // Используем реальный маппер из контекста

    @MockBean
    private UserService userService // Заглушка, так как мы тестируем только Web Layer

    @Test
    fun `should deserialize valid json to DTO and return 200`() {
        // Arrange: Создаем объект и превращаем его в JSON строку
        val userDto = UserDTO("John Doe", LocalDate.of(1990, 1, 1))
        val jsonContent = objectMapper.writeValueAsString(userDto)

        // Act & Assert
        mockMvc.perform(post("/users")
            .contentType(MediaType.APPLICATION_JSON)
            .content(jsonContent)) // Отправляем JSON
            .andExpect(status().isOk)
            .andExpect(jsonPath("$.full_name").value("John Doe")) // Проверяем маппинг обратно в JSON
    }

    @Test
    fun `should return 400 when name is missing`() {
        // Arrange: JSON без обязательного поля 'full_name'
        val invalidJson = """{"birthDate": "1990-01-01"}"""

        // Act & Assert
        mockMvc.perform(post("/users")
            .contentType(MediaType.APPLICATION_JSON)
            .content(invalidJson))
            .andExpect(status().isBadRequest) // Ожидаем ошибку валидации
    }
}
```

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Используй `objectMapper` из контекста:** Не создавай `ObjectMapper manully = new ObjectMapper()`. В тестах нужно использовать тот же экземпляр, который настроен в Spring, иначе тесты пройдут, а на проде — нет (из-за разных настроек модулей дат или именования).
2.  **Тестируй `jsonPath` на деталях:** Не проверяй просто `$.name`. Проверяй структуру: `$.user.address.city`. Это гарантирует, что вложенные объекты тоже маппятся верно.
3.  **Проблема `@WebMvcTest` и кастомных конфигураций:** Если у тебя есть кастомный `Jackson2ObjectMapperBuilder`, убедись, что он подхватывается в тестах. Иногда приходится явно добавлять `@Import(MyJacksonConfig::class)`.
4.  **Не забывай про `Content-Type`:** Всегда указывай `.contentType(MediaType.APPLICATION_JSON)`, иначе Spring может не понять, как обрабатывать тело запроса.

# 🗄️ Cheat Sheet: Data Layer Testing (Repository Test)

**Суть:** Мы тестируем не бизнес-логику, а **интеграцию с базой данных**. Наша цель — убедиться, что наши Query (JPQL, Native), маппинги (`@OneToMany`, `@Column`), ограничения (`unique`, `nullable`) и кастомные методы репозитория работают именно так, как мы ожидам в реальной БД.

---

### 1. Главный инструмент: `@DataJpaTest`
Это **Sliced Test** (срез). Spring не поднимает всё приложение, а только те бины, которые нужны для работы JPA (Entity Manager, Repositories, DataSource).

*   **Что он делает:** Настраивает Hibernate, находит `@Entity`, конфигурирует `DataSource`.
*   **Транзакционность:** По умолчанию каждый тест помечен `@Transactional`. Это значит, что после завершения теста **данные автоматически откатываются (rollback)**. База остается чистой для следующего теста.
*   **H2/In-memory:** По умолчанию он ищет в classpath драйвер H2 и подменяет реальную БД на неё.

### 2. Стратегии выбора базы данных

| Подход | Плюсы | Минусы | Когда использовать |
| :--- | :--- | :--- | :--- |
| **H2 (In-memory)** | Невероятно быстро, не требует Docker. | Не поддерживает специфичные фичи (JSONB в Postgres, оконные функции). Может «врать» (синтаксис отличается). | Простые CRUD операции, проверка базовых связей. |
| **Testcontainers** | **Реальная база** (Postgres/MySQL) в Docker. 100% уверенность, что тест совпадает с продакшном. | Медленнее, требует наличия Docker на машине/CI. | Сложные Native Queries, проверка триггеров, специфичных типов данных. |

### 3. Важные инструменты внутри теста

*   **`TestEntityManager`**: Это твой «чистый» помощник. Когда ты тестируешь `UserRepository`, тебе нужно создать пользователя в базе *до* вызова метода репозитория. Использовать тот же `UserRepository` для создания данных — плохая практика (ты тестируешь тест). Используй `TestEntityManager.persist(entity)`.
*   **`@Sql`**: Позволяет выполнить `.sql` скрипт перед тестом или после него. Удобно для наполнения базы сложными наборами данных.
*   **`@ActiveProfiles("test")`**: Чтобы подтянуть `application-test.properties` (например, если ты переопределяешь настройки подключения).

### 4. На что смотреть (Checklist Senior-а)

1.  **Constraints (Ограничения):** Проверяй, что база выбрасывает исключение при нарушении `unique` или `nullable`.
2.  **Mappings (Связи):** Проверяй `CascadeType.ALL` и `orphanRemoval`. Если удаляешь родителя — удаляются ли дети?
            *   *Нюанс:* Тестируй `Lazy Loading`. Попробуй обратиться к ленивому полю вне транзакции (если это возможно в твоем сценарии).
3.  **Native Queries:** Если используешь `@Query(nativeQuery = true)`, **только Testcontainers**. H2 часто не понимает специфичный синтаксис Postgres, и ты получишь "зеленый" тест, который упадет на проде.
4.  **Auditing:** Если у тебя есть `@CreatedDate` или `@LastModifiedDate`, убедись, что они заполняются (для этого нужно включить `@EnableJpaAuditing` в тестовой конфигурации).

**О:** Потому что `@DataJpaTest` включает аннотацию `@Transactional`. Каждая тестовая транзакция делает `rollback` в конце метода, обеспечивая изоляцию тестов друг от друга.

**В: Как протестировать, что поле помечено как `unique = true`?**

# 🚀 Cheat Sheet: `@DataJpaTest` (Repository Layer Testing)

### 🎯 Суть темы
`@DataJpaTest` — это так называемый **Slice Test** (срез). Вместо того чтобы поднимать всё приложение целиком (`@SpringBootTest`), Spring Boot поднимает только то, что нужно для работы с базой данных. Это делает тесты быстрыми и изолированed.

### 🛠 Что входит в этот "срез" (What's included)
Когда ты вешаешь `@DataJpaTest`, Spring сканирует и создает в контексте:
1.  **Repositories**: Все твои интерфейсы, наследующие `JpaRepository` или `CrudRepository`.
2.  **Entities**: Все классы, помеченные `@Entity`.
3.  **DataSource & EntityManager**: Настройка подключения к БД и Hibernate.
4.  **TestEntityManager**: Специальный инструмент для управления состоянием базы в тестах (см. ниже).

### ❌ Что НЕ входит (What's NOT included)
*   `@Service`, `@Controller`, `@Component` — их нет в контексте. Если твой репозиторий зависит от какого-то кастомного бина из сервисного слоя, тест упадет. Тебе придется либо использовать `@MockBean`, либо подгрузить этот бин через `@Import`.

---

### 🗝 Главные инструменты

#### 1. `TestEntityManager` — Твой лучший друг
В тестах репозиториев часто возникает проблема: ты сохраняешь объект через `repository.save()`, и он тут же оказывается в кэше первого уровня (L1 Cache) Hibernate. Когда ты делаешь поиск, ты видишь данные не потому, что они реально в БД, а потому что они "застряли" в памяти.
*   **Зачем:** Используй `TestEntityManager` для создания тестовых данных (Setup). Он позволяет явно делать `persist()` и `flush()`, имитируя реальное поведение БД.

#### 2. `@Transactional` (Автоматический откат)
По умолчанию `@DataJpaTest` помечает каждый тест как `@Transactional`.
*   **Нюанс:** После завершения каждого метода `@Test` транзакция **откатывается (rollback)**. Это круто: база остается чистой для следующего теста. Но это опасно, если ты хочешь проверить именно `commit` или работу асинхронных методов.

---

### ⚠️ Senior Nuances (Подводные камни)

#### 1. Проблема H2 vs Real DB
По умолчанию `@DataJpaTest` пытается найти в classpath библиотеку **H2** и заменить твою реальную БД (например, PostgreSQL) на встроенную In-memory БД.
*   **В чем подвох:** Твой SQL-запрос может идеально работать на H2, но упасть на PostgreSQL из-за разницы в диалектах или специфичных функций (например, JSONB или сложные Window Functions).
*   **Решение:** Если используешь **Testcontainers**, добавь аннотацию: 
    `@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)`
    Это скажет Spring: "Не подменяй базу на H2, используй ту, что я настроил (через Docker)".

#### 2. Проблема кэша (L1 Cache)
Если ты сохранил сущность через репозиторий и тут же сделал `findById`, ты получишь объект из кэша. Чтобы проверить, что данные **реально** записаны в таблицу, используй:
```java
entityManager.flush(); // Принудительно отправляем SQL в БД
entityManager.clear(); // Очищаем кэш (L1 Cache), заставляя Hibernate идти в реальную БД
```

#### 3. Тестирование Native Queries
Если у тебя есть `@Query(nativeQuery = true)`, обычные проверки могут не сработать, если ты не настроил правильный `Dialect`. Всегда проверяй такие запросы именно через `Testcontainers` с той же базой, что и в продакшене.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Чем `@DataJpaTest` отличается от `@SpringBootTest`?**
**О:** `@SpringBootTest` поднимает **весь** ApplicationContext (все сервисы, контроллеры, конфигурации). Это медленно. `@DataJpaTest` — это "срез", он поднимает только инфраструктуру для работы с БД. Это быстро и изолированно.

**В: Что произойдет с данными в базе после выполнения теста с `@DataJpaTest`?**
**О:** Данные будут откачены (rollback) благодаря встроенной транзакционности, база останется в исходном состоянии.

**В: Как протестировать репозиторий, если он требует кастомный бин (например, какой-нибудь `AuditService`)?**
**О:** У тебя есть два пути: 
1. Использовать `@MockBean(AuditService.class)`, чтобы создать заглушку.
2. Использовать `@Import(AuditServiceConfig.class)`, чтобы реально подгрузить конфигурацию этого бина в контекст теста.

**В: Зачем использовать `TestEntityManager` вместо обычного `repository.save()` при подготовке данных?**
**О:** Чтобы избежать "лживых" тестов. `TestEntityManager` позволяет более тонко управлять жизненным циклом сущности (persist, flush, detach), что помогает гарантировать, что данные прошли через все этапы Hibernate и реально готовы к поиску в БД.

# 🗄️ Data Layer Testing: In-memory (H2) vs Real DB (Testcontainers)

Когда мы тестируем репозитории (`@DataJpaTest`), наша цель — проверить, что SQL-запросы корректны, маппинг сущностей работает, а ограничения (constraints) соблюдаются. У нас есть два пути: «быстрый и дешевый» (H2) и «медленный, но честный» (Real DB).

### 1. In-memory DB (H2 / HSQLDB) — "Иллюзия реальности"
Это база данных, которая живет только в оперативной памяти во время выполнения теста.

*   **Как это работает:** Ты добавляешь зависимость `h2` в `test` scope, и Spring Boot автоматически подменяет настройки твоей основной БД на H2.
*   **Плюсы:**
    *   🚀 **Скорость:** Запуск мгновенный. Тесты пролетают за секунды.
    *   🛠️ **Zero Setup:** Не нужно иметь установленный Docker или базу на компьютере. Идеально для CI/CD с ограниченными ресурсами.
*   **Минусы (Опасные нюансы):**
    *   ❌ **The "Liar" Effect:** H2 — это не PostgreSQL. Если ты используешь специфичные фичи (JSONB, Window Functions, Array types, PostGIS), H2 их либо не поймет, либо поймет иначе.
    le
    *   ❌ **Dialect Mismatch:** Твой код может работать на H2, но упасть в продакшене из-за разницы в синтаксисе SQL или поведении индексов/ограничений.

### 2. Real DB (Testcontainers) — "Золотой стандарт"
Использование реального экземпляра базы (PostgreSQL, MySQL) внутри Docker-контейнера прямо во время теста.

*   **Как это работает:** Библиотека `Testcontainers` при старте теста дает команду Docker: «Подними мне Postgres». Spring подключается к этому динамическому порту.
*   **Плюсы:**
    *   ✅ **High Fidelity (Высокая точность):** Ты тестируешь ровно то, что будет в продакшене. Если запрос упадет из-за ошибки в синтаксисе Postgres — ты узнаешь об этом до мерджа.
    *   ✅ **Full Feature Support:** Все расширения, типы данных и сложные триггеры работают как надо.
*   **Минусы:**
    *   🐢 **Slow Start:** Поднятие контейнера занимает время (от нескольких секунд до минуты).
    *   🐳 **Infrastructure Dependency:** Нужен установленный Docker и доступ к ресурсам (RAM/CPU) на машине разработчика и в CI.

| Критерий | In-memory (H2) | Real DB (Testcontainers) |
| :--- | :--- | :--- |
| **Скорость** | ⭐⭐⭐⭐⭐ (Очень быстро) | ⭐⭐ (Медленно) |

### 💡 Senior Tips (Нюансы, о которых молчат учебники)

1.  **Стратегия "Пирамида":** Не выбирай что-то одно. Используй **H2 для быстрых проверок** логики маппинга и простых запросов, но **обязательно используй Testcontainers** для интеграционных тестов, где есть сложные `Native Queries` или специфичная логика БД.
2.  **Проблема миграций (Flyway/Liquibase):** Если ты используешь миграции в проде, твои тесты **должны** использовать их и в H2, и в Testcontainers. Если в H2 ты создаешь схему через `ddl-auto: create`, а в проде через Flyway — ты не тестируешь реальную структуру таблиц.
3.  **Dynamic Property Source:** При использовании Testcontainers помни, что порт базы меняется каждый раз. Используй `@DynamicPropertySource`, чтобы прокинуть URL контейнера в Spring контекст.

**В: Как ускорить тесты с Testcontainers?**
**О:** Используй паттерн **Singleton Container**. Вместо того чтобы поднимать новый контейнер для каждого тестового класса, подними один общий контейнер на всю тестовую сессию (через статический блок или базовый класс). Это сэкономит тебе кучу времени.

# 🗂️ Шпаргалка: Data Layer Testing (Custom Queries)

Когда мы тестируем репозитории, наша цель — **не проверить, работает ли Spring Data JPA** (мы это подразумеваем по умолчанию), а проверить, **правильно ли написан наш SQL/JPQL запрос** и корректно ли он маппится на сущности.

### 1. Базовый инструментарий
Для тестов репозиториев мы не используем `@SpringBootTest` (это слишком тяжело). Наш выбор — **`@DataJpaTest`**.

*   **`@DataJpaTest`**: Сканирует только `@Entity` и репозитории. Поднимает минимально необходимый контекст.
*   **Транзакционность**: Каждый тест помечен `@Transactional`. Это значит, что после завершения теста изменения **автоматически откатываются (rollback)**. База остается чистой для следующего теста.
*   **H2 vs Testcontainers**: По умолчанию Spring пытается использовать In-memory БД (H2). 

---

### 2. Сценарии тестирования

#### А. Тестирование JPQL (`@Query`)
JPQL работает с объектами (Entity), а не с таблицами. Здесь важно проверить логику предикатов (WHERE, JOIN).

```java
@DataJpaTest
class UserRepositoryTest {

    @Autowired
    private UserRepository userRepository;

    @Test
    void shouldFindByEmail() {
        // Arrange: Сохраняем юзера
        User user = new User("test@example.com", "John");
        userRepository.save(user);
        
        // Act: Выполняем кастомный JPQL запрос
        Optional<User> found = userRepository.findByEmailCustom("test@example.com");

        // Assert
        assertThat(found).isPresent();
        assertThat(found.get().getName()).isEqualTo("John");
    }
}
```

#### Б. Тестирование Native Queries (Native SQL)
Здесь мы пишем чистый SQL. **Это самое опасное место**, так как здесь можно использовать специфичные функции базы (например, JSONB в Postgres), которые не поймет H2.

*   **Нюанс**: Если твой запрос использует `PostgreSQL-specific` синтаксис, тест на H2 **упадет**.
*   **Решение**: Используй **Testcontainers** (см. раздел ниже).

#### В. Тестирование Pagination & Sorting
Всегда проверяй, что пагинация возвращает именно то количество элементов, которое ты ожидаешь, и что сортировка работает.

```java
@Test
void shouldReturnPagedResults() {
    // Arrange: Создаем 5 пользователей
    for (int i = 1; i <= 5; i++) {
        userRepository.save(new User("user" + i + "@test.com", "Name" + i));
    }

    // Act: Запрашиваем страницу размером 2 с сортировкой по имени
    Pageable pageable = PageRequest.of(0, 2, Sort.by("name").ascending());
    Page<User> page = userRepository.findAll(pageable);

    // Assert
    assertThat(page.getContent()).hasSize(2);
    assertThat(page.getTotalElements()).isEqualTo(5);
}
```

### 3. Senior Nuances (Тонкие моменты)

#### ⚠️ Ловушка Persistence Context (L1 Cache)
Это самая частая причина "глючных" тестов. Hibernate кэширует объекты в `EntityManager`. Если ты сделал `save()`, а потом сразу `find()`, Hibernate может вернуть объект из памяти, **не делая реального SQL запроса к базе**. Ты можешь не заметить ошибку в самом SQL!

**Как лечить:** Используй `entityManager.flush()` и `entityManager.clear()`.
```java
@Autowired
private TestEntityManager entityManager; // Специальный помощник для тестов

@Test
void testQueryWithFlush() {
    User user = new User("test@test.com", "Name");
    userRepository.save(user);
    
    entityManager.flush(); // Принудительно отправляем SQL в БД
    entityManager.clear(); // Очищаем кэш, чтобы заставить Hibernate идти в БД

    // Теперь запрос точно пойдет в базу и проверит реальный SQL
    assertThat(userRepository.findByEmailCustom("test@test.com")).isPresent();
}
```

#### ⚠️ Проблема "H2 vs PostgreSQL" (Testcontainers)
Если ты используешь `@DataJpaTest`, Spring подменит твою реальную БД на H2. Если в Native Query есть `ILIKE` или `JSONB` — тест пройдет на H2, но упадет в продакшене на Postgres.

**Решение:** Используй Testcontainers.
```java
@DataJpaTest
@AutoConfigureTestDatabase(replace = Replace.NONE) // ОТКЛЮЧАЕМ замену на H2
@Testcontainers
class UserRepositoryTest {
    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15");

    // Spring сам подхватит настройки контейнера через @DynamicPropertySource
}
```

**В: Зачем нам `@DataJpaTest`, если можно использовать `@SpringBootTest`?**
**О:** Скорость и изоляция. `@SpringBootTest` поднимает всё приложение (Web, Security, Services). Если у тебя сложный контекст, тесты будут идти вечно. `@DataJpaTest` тестирует только слой данных.

**В: Почему после `repository.save()` я не вижу изменений в БД при проверке через чистый SQL?**
**О:** Потому что транзакция еще не зафиксирована (commit не произошел), а данные находятся в кэше Hibernate. Используй `flush()`.

**В: Что делать, если мой Native Query использует функции, которых нет в H2?**
**О:** Переходи на Testcontainers. Это стандарт индустрии для интеграционных тестов репозиториев. Тестировать SQL-запросы на другой СУБД — это лотерея, а не тестирование.

**В: Нужно ли тестировать простые методы типа `findById`?**
**О:** Нет. Это встроенная функция Spring Data JPA. Трать время только на `@Query`, кастомные реализации и сложные фильтры (Specifications/Querydsl).

# 🛠 Шпаргалка: @EntityScan в Repository Testing

### 💡 Суть простыми словами
Когда ты запускаешь тест с `@DataJpaTest`, Spring пытается настроить всё необходимое для работы с базой данных (EntityManager, DataSource, TransactionManager). Но есть проблема: **Spring ищет JPA-сущности (`@Entity`) только в тех пакетах, которые находятся «внутри» твоего основного тестового класса или главного `@SpringBootApplication` класса.**

Если твои сущности лежат в другом модуле или в пакете, который не является подпакетом текущего теста — Spring их просто «не увидит». Ты получишь ошибку: `Unknown entity: com.example.model.User`. 

**`@EntityScan`** — это команда для Spring: *"Эй, не ограничивайся только этим пакетом, загляни вот в эти конкретные места и найди там мои сущности"*.

---

### 🚀 Когда это становится критичным? (Use Cases)
1.  **Multi-module Projects (Самый частый случай):** У тебя есть модуль `core-domain`, где лежат все `@Entity`, и модуль `infrastructure`, где лежат репозитории. Тест в модуле `infrastructure` не видит сущности из `core-module` без явного указания.
2.  **Custom Package Structure:** Если ты намеренно вынес маппинг сущностей в отдельный пакет, отличный от иерархии твоего `@SpringBootApplication`.

---

### 🛠 Как использовать

```java
@DataJpaTest
@EntityScan(basePackages = {"com.company.project.domain", "com.company.project.shared.entities"})
class UserRepositoryTest {
    // Теперь Spring знает, где искать User, Order и другие сущности
}
```

*   **`basePackages`**: Массив строк с путями к пакетам. Можно указывать несколько.
*   **`basePackageClasses`**: (Более надежный способ) Вме-ка указывать строку, ты передаешь класс, который находится в нужном пакете. Если ты переименуешь пакет, рефакторинг подхватит это автоматически.

```java
@EntityScan(basePackageClasses = {User.class, Order.class})
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Insights)

1.  **Связка с `@EnableJpaRepositories`:** Если ты переносишь репозитории в другой пакет, одного `@EntityScan` мало. Тебе придется добавить и `@EnableJpaRepositories(basePackages = "...")`, иначе Spring не найдет сами интерфейсы репозиториев.
2.  **Производительность:** Не пиши `basePackages = "com.company"`. Это заставит Spring сканировать вообще всё дерево классов проекта. Это замедлит запуск тестов. Будь точен: указывай конкретные пакеты с сущностями.
3.  **Конфликты конфигурации:** Если в проекте несколько `EntityManagerFactory` (редко, но бывает в сложных legacy-системах), `@EntityScan` может вести себя непредсказуемо. В таких случаях нужно более детально настраивать `LocalContainerEntityManagerFactoryBean`.
4.  **Забытый рефакторинг:** Всегда предпочитай `basePackageClasses`. Строковые пути — это "магические строки", которые ломаются при переименовании пакетов и не подсвечиваются IDE как ошибки.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Почему `@DataJpaTest` сам не находит мои сущности?**
**О:** Потомут что `@DataJpaTest` по умолчанию сканирует только те пакеты, которые являются подпакетами того класса, где стоит аннотация (или главного конфигурационного класса). Если твои Entity лежат в другом модуле (другом дереве пакетов), они выпадают из зоны видимости.

**В: Что лучше: `basePackages` или `basePackageClasses`?**
**О:** Однозначно `basePackageClasses`. Это типобезопасно. Если ты переименуешь пакет, IDE автоматически обновит ссылку в тесте. Строка (`basePackages`) останется старой и тест упадет в рантайме.

**В: Если я добавил `@EntityScan`, нужно ли мне добавлять `@EnableJpaRepositories`?**
**О:** Зависит от того, где лежат репозитории. `@EntityScan` отвечает за поиск **сущностей** (классов с `@Entity`), а `@EnableJpaRepositories` — за поиск **интерфейсов** (классов с `@Repository`). Если и сущности, и репозитории в других пакетах — нужно оба.

**В: Можно ли использовать `@EntityScan` вместе с H2 для тестов?**
**О:** Да, это стандартная практика. `@DataJpaTest` сам поднимет H2, а `@EntityScan` просто подскажет ему, какие именно таблицы из твоих сущностей нужно создать в этой временной базе.

# 🧠 Шпаргалка: JSON Layer Testing

### 🎯 Суть темы
Тестирование JSON-слоя — это проверка того, насколько правильно твой Java-объект (POJO) превращается в строку JSON (**сериализация**) и наоборот (**десериализация**). 

Мы не тестируем бизнес-логику здесь. Мы тестируем **контракт**. Если ты переименовал поле в классе, но забыл обновить аннотацию `@JsonProperty`, твой API "сломается" для фронтенда. Тесты JSON-слоя должны поймать это до того, как код попадет в прод.

---

### 🛠 Инструментарий
В Spring Boot основной инструмент — это **`@JsonTest`**.
*   Это "слайс-тест" (slice test). Он не поднимает весь контекст приложения (что быстро), а загружает только инфраструктуру, необходимую для работы с Jackson.
*   Главный герой: **`JacksonTester<T>`**. Это обертка над `ObjectMapper`, которая делает проверки максимально удобными и читаемы/красивыми.

---

### 🚀 Основные сценарии тестирования

#### 1. Сериализация (Object $\to$ JSON)
Проверяем, что поля на месте, названия правильные, а лишнего (например, паролей) нет.
```java
@JsonTest
class UserJsonTest {
    @Autowired
    private JacksonTester<UserDto> json;

    @Test
    void testSerialization() throws Exception {
        UserDto user = new UserDto("John", "admin");

        // Проверяем, что в JSON есть поле "username" (а не "name")
        assertThat(json.write(user)).hasJsonPathStringValue("@.username");
        assertThat(json.write(user)).extractingJsonPathStringValue("@.username")
            .isEqualTo("John");
            
        // Проверяем отсутствие поля, которое мы скрыли через @JsonIgnore
        assertThat(json.write(user)).doesNotHaveJsonPath("@.password");
    }
}
```

#### 2. Десериализация (JSON $\to$ Object)
Проверяем, что если фронтенд пришлет нам JSON, наш Jackson сможет правильно "распаковать" его в объект.
```java
@Test
void testDeserialization() throws Exception {
    String content = "{\"username\":\"John\", \"role\":\"admin\"}";

    // Парсим строку и проверяем результат
    UserDto user = json.parse(content);

    assertThat(user.getUsername()).isEqualTo("John");
    assertThat(user.getRole()).isEqualTo("admin");
}
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Форматы дат (`@JsonFormat`)**: Это самая частая причина падений интеграционных тестов. Если в коде стоит `@JsonFormat(pattern = "yyyy-MM-dd")`, а тест ожидает стандартный ISO формат — тест упадет. Всегда проверяй форматирование `LocalDate`/`LocalDateTime`.
2.  **Case Sensitivity (Регистр)**: По умолчанию Jackson ищет совпадения по именам. Если у тебя в JSON `user_name` (snake_case), а в Java `userName` (camelCase), без аннотации `@JsonProperty("user_name")` десериализация вернет `null`.
3.  **Null-поля (`@JsonInclude`)**: Если ты используешь `@JsonInclude(JsonInclude.Include.NON_NULL)`, то при тестировании сериализации проверяй, что пустые поля **отсутствуют** в итоговой строке. Это важно для экономии трафика.
4.  **Сложные объекты**: Если твой DTO содержит другие DTO, `@JsonTest` подтянет их, но убедись, что все кастомные `Module` (например, для работы с Joda-Time или специфичными типами) зарегистрированы в контексте.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Зачем использовать `@JsonTest`, если можно просто написать обычный Unit-тест с `new ObjectMapper()`?**
**О:** `@JsonTest` — это не просто `ObjectMapper`. Он подтягивает все твои кастомные настройки, которые настроены в приложении (регистрация модулей, настройка `PropertyNamingStrategy`, обработка дат). Тестировать "голым" `ObjectMapper` бесполезно, так как он может вести себя иначе, чем тот, что работает в реальном контроллере.

**В: Что такое `JacksonTester` и почему это круто?**
**О:** Он предоставляет Fluent API (через AssertJ). Вместо того чтобы писать длинные цепочки `assertEquals(obj.getName(), jsonNode.get("name").asText())`, ты пишешь лаконичное `.hasJsonPathStringValue("@.name")`. Это делает тесты читаемыми и устойчивыми к изменениям структуры JSON.

**В: Как протестировать, что поле вообще нельзя передать в JSON?**
**О:** Используй проверку на отсутствие пути: `assertThat(json.write(user)).doesNotHaveJsonPath("@.sensitiveField")`. Это гарантирует, что `@JsonIgnore` работает как надо.

# 🐳 Шпаргалка: Testcontainers

### 🧠 Что это такое (Theory)
**Testcontainers** — это библиотека, которая позволяет запускать реальные экземпляры инфраструктуры (базы данных, брокеры сообщений, Redis и т.д.) внутри Docker-контейнеров прямо во время выполнения тестов.

**Зачем это нужно?**
Раньше мы использовали **H2** (in-memory DB) для тестирования репозиториев. Но H2 — это не PostgreSQL. В H2 нет специфичных функций, JSONB-типов или особенностей работы с транзакциями. Результат: тесты проходят, а на проде всё падает. 
Testcontainers решает проблему **«It works on my machine / It works on H2»**, предоставляя тебе настоящую базу в Docker.

---

### 🛠 Основные компоненты и аннотации
1.  **`@Testcontainers`**: Аннотация уровня класса, которая управляет жизненным циклом контейнеров (запуск/остановка).
2.  **`@Container`**: Указывает, что конкретный экземпляр класса (например, `PostgreSQLContainer`) должен быть управляемым объектом Testcontainers.
3.  **`GenericContainer<T>`**: Базовый класс для запуска любого Docker-образа, у которого нет специального модуля.
4.  **Специализированные модули**: Готовые классы для популярных технологий (`PostgreSQLContainer`, `KafkaContainer`, `RedisContainer`, `RabbitMQContainer`).

---

### 💻 Пример использования (Spring Boot + PostgreSQL)

Самый важный нюанс: контейнер запускается на случайном порту, чтобы избежать конфликтов. Поэтому нам нужно «сообщить» Spring Boot новый порт. Для этого используется `@DynamicPropertySource`.

```java
@SpringBootTest
@Testcontainers // Управляет жизненным-циклом
class IntegrationTest {

    // Определяем контейнер с БД
    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15-alpine")
            .withDatabaseName("testdb")
            .withUsername("user")
            .withPassword("pass");

    // Магия: прокидываем динамический порт и URL в настройки Spring
    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasourceya.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Test
    void testDatabaseConnection() {
        // Твой тест здесь...
    }
}
```

---

### ⚠️ Нюансы и Senior-советы (Pitfalls)

1.  **Проблема скорости (The Speed Trap):** Запуск нового контейнера на каждый тестовый класс — это **очень медленно**. 
    *   *Решение:* Используй паттерн **Singleton Container**. Создай один статический базовый класс для всех тестов, который запускает контейнер один раз на всё прохождение тестов.

2.  **Ryuk (The Reaper):** Testcontainers автоматически запускает контейнер под названием `Ryuk`. Его задача — удалять контейнеры после завершения тестов, чтобы у тебя не засорялся Docker. Не пытайся его отключить, если не знаешь зачем.

3.  **Network (Связь между контейнерами):** Если тебе нужно протестировать взаимодействие двух контейнеров (например, твое приложение и Kafka), их нужно поместить в одну сеть:
    ```java
    Network network = Network.newNetwork();
    KafkaContainer kafka = new KafkaContainer(DockerImageName.parse("confluentinc/cp-kafka:latest"))
            .withNetwork(network);
    ```

4.  **Очистка данных:** Контейнер один, а тестов много. Если первый тест запишет юзера в базу, второй его увидит. 
    *   *Решение:* Используй `@Transactional` (откат транзакции) или делай очистку таблиц (`TRUNCATE`) перед каждым тестом.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем Testcontainers лучше, чем просто запустить Docker Compose заранее?**
**О:** Testcontainers дает полный контроль из кода Java. Тебе не нужно вручную следить за тем, поднята база или нет. Библиотека сама скачает образ, запустит его, дождется готовности (healthcheck) и удалит всё после тестов. Это делает CI/CD пайплайн полностью автономным.

**В: Что делать, если в CI-среде (например, GitLab Runner или Jenkins) нет доступа к Docker?**
**О:** Тебе нужен **Docker-in-Docker (DinD)** или доступ к Docker Socket (`/var/run/docker.sock`). Без возможности запускать контейнеры Testcontainers работать не будет.

**В: Можно ли использовать Testcontainers для тестирования REST API стороннего сервиса?**
**О:** Да! Используй `GenericContainer` с образом, имитирующим сервис (например, **WireMock** в Docker), либо используй библиотеку `WireMock` напрямую, если тебе не нужна именно изоляция контейнера.

**В: Как ускорить тесты, если их сотни?**
**О:** Применяй подход "Singleton Container". Вместо `@Container` (который живет один жизненный цикл класса) создай статический объект в базовом классе, который инициализируется один раз при старте JVM. Это сэкономит минуты времени на поднятии/остановке БД.

# 🐳 Шпаргалка: Testcontainers (Databases)

### 🎯 Суть темы
**Testcontainers** — это библиотека, которая позволяет запускать реальные экземпляры баз данных (PostgreSQL, MySQL, Redis и др.) внутри Docker-контейнеenes прямо из твоего Java-кода во время выполнения тестов.

**Главный девиз Senior-разработчика:** *"Don't test with H2 if you use PostgreSQL in production"*. 
H2 — это круто для Unit-тестов, но он не поддерживает специфичные фичи (JSONB, Window Functions, специфичные типы данных), и ты можешь получить тест, который проходит «зеленым», а в продакшене падает с ошибкой синтаксиса.

---

### 🛠 Основные компоненты
1.  **Container Class:** Объект, описывающий образ (image) и настройки (порты, переменные окружения).
2.  **Ryuk:** Маленький вспомогательный контейнер («чистильщик»), который автоматически удаляет все созданные контейнеры после завершения тестов, чтобы не засорять твой Docker.
3.  **Dynamic Property Source:** Механизм, который «прокидывает» динамический порт (который Docker назначил базе) в настройки Spring (`spring.datasource.url`).

---

### 🚀 Как это реализовать (Modern Way: Spring Boot 3.1+)

Раньше нам приходилось вручную прописывать `@DynamicPropertySource`. Теперь, если ты используешь современный Spring Boot, всё стало намного проще благодаря аннотации `@ServiceConnection`.

**Зависимости (Maven):**
```xml
<dependency>
    <groupId>org/testcontainers</groupId>
    <artifactId>postgresql</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org/springframework/boot</groupId>
    <artifactId>spring-boot-testcontainers</artifactId>
    <scope>test</scope>
</dependency>
```

**Пример идеального интеграционного теста:**

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@Testcontainers // Автоматически управляет жизненным циклом контейнеров
class MyIntegrationTest {

    @Container // Запускает контейнер перед тестом
    @ServiceConnection // МАГИЯ: сама настроит spring.datasource.url, username и password
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15-alpine");

    @Test
    void contextLoads() {
        // Тест будет использовать реальную Postgres в Docker
    }
}
```

---

### 🧠 Нюансы и Senior-советы (Pro Tips)

#### 1. Проблема скорости: Singleton Pattern 🏎️
**Ошибка:** Если ты вешаешь `@Container` на каждый тестовый класс, Spring будет поднимать и останавливать базу для *каждого* класса. Это убьет твой CI/CD.
**Решение:** Создай базовый абстрактный класс с `static` контейнером. Контейнер поднимется один раз за весь прогон тестов.

```java
public abstract class BaseIntegrationTest {
    static final PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15-alpine");

    static {
        postgres.start(); // Запускаем вручную один раз
    }

    @ServiceConnection
    static PostgreSQLContainer<?> container = postgres;
}
```

#### 2. Миграции (Flyway / Liquibase) 📜
Никогда не забудь, что после запуска контейнера твоя база пустая. Если ты используешь Flyway или Liquibase, Spring Boot автоматически запустит их при старте контекста, как только увидит настройки `datasource`. Это гарантирует, что схема базы в тесте идентична продакшену.

#### 3. Проблема "Docker is not running" 🐳
Testcontainers требует запущенного Docker-демона. В CI (GitHub Actions, GitLab CI) нужно убедиться, что у раннера есть доступ к Docker (использование Docker-in-Docker или примонтированный `/var/run/docker.sock`).

#### 4. Использование разных портов
Никогда не хардкодь порт `5432`. Docker перенаправляет внутренний порт контейнера на случайный свободный порт хоста. `@ServiceConnection` или `@DynamicPropertySource` справляются с этим автоматически.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между H2 и Testcontainers?**
**О:** H2 — это In-memory БД, она очень быстрая, но не является полноценной заменой вашей продуктовой БД. Она может не поддерживать специфичные функции (например, сложные типы данных PostgreSQL). Testcontainers запускает реальную БД, что дает 100% уверенность в корректности SQL-запросов.

**В: Как избежать долгого запуска тестов при использовании Testcontainers?**
**О:** Использовать паттерн Singleton для контейнеров (статические поля в базовом классе), чтобы база поднималась один раз на весь тестовый набор, а не на каждый класс.

**В: Что такое Ryuk и зачем он нужен?**
**О:** Это служебный контейнер от авторов Testcontainers. Он следит за тем, чтобы после завершения тестов (даже если они упали с ошибкой) все созданные контейнеры были корректно удалены из системы.

**В: Можно ли тестировать не только БД, но и Kafka или Redis?**
**О:** Да, для них есть отдельные модули: `KafkaContainer`, `GenericContainer` (для чего угодно) и `RedisContainer`. Принцип работы идентичен.

# 🛠 Шпаргалка: Testcontainers (Redis, Kafka, RabbitMQ)

### 1. Что это такое и зачем?
**Testcontainers** — это библиотека, которая позволяет запускать реальные экземпляры инфраструктуры (БД, брокеры сообщений, кэш) в Docker-контейнерах прямо во время выполнения тестов.

**Зачем это Senior-разработчику:**
*   **Прощай, H2/In-memory:** Тестировать Kafka на встроенной памяти невозможно, а Redis через Mockito — значит не проверить реальное поведение команд (например, TTL или сложные типы данных).
*   **Идентичность сред:** Твой тест запускает *тот же самый* образ, который будет работать в Production.
*   **Чистота:** После завершения тестов контейнеры удаляются. Никакого мусора в системе.

---

### 2. Главный нюанс: Динамические порты и `@DynamicPropertySource`
Контейнеры при запуске получают **случайные свободные порты** на твоей хост-машине. Если ты жестко пропишешь в `application-test.yml` порт `6379`, тест упадет, потому что порт уже занят или другой.

**Решение:** Использовать аннотацию `@DynamicPropertySource`, чтобы «прокинуть» порт из контейнера в настройки Spring.

---

### 3. Практика по технологиям

#### 🔴 Redis (Кэширование)
Для Redis чаще всего используют `GenericContainer`, так как он максимально прост.

```java
@Container
static GenericContainer<?> redis = new GenericContainer<>(DockerImageName.parse("redis:7-alpine"))
    .withExposedPorts(6379);

@DynamicPropertySource
static void configureProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.data.redis.host", redis::getHost);
    registry.add("spring.data.redis.port", () -> redis.getMappedPort(6379));
}
```

#### 🟢 Kafka (Стриминг событий)
Для Kafka есть специальный модуль `KafkaContainer`, который берет на себя всю магию настройки bootstrap-серверов.

```java
@Container
static KafkaContainer kafka = new KafkaContainer(DockerImageName.parse("confluentinc/cp-kafka:latest"));

@DynamicPropertySource
static void configureKafkaProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.kafka.bootstrap-servers", kafka::getBootstrapServers);
}
```
*Нюанс:* Kafka — тяжелый зверь. Запуск контейнера может занять 20–40 секунд.

#### 🟡 RabbitMQ (Очереди сообщений)
Используем `RabbitMQContainer`.

```java
@Container
static RabbitMQContainer rabbit = new RabbitMQContainer(DockerImage

Name.parse("rabbitmq:3-management-alpine"));

@DynamicPropertySource
static void configureRabbitProperties(DynamicPropertyRegistry registry) {
    registry.add("spring.rabbitmq.host", rabbit::getHost);
    registry.add("spring.rabbitmq.port", () -> rabbit.getMappedPort(5672));
}
```

### 4. Senior-level Pro-tips (Как не сделать плохо)

#### 🚀 Оптимизация: Singleton Container Pattern
**Проблема:** Если у тебя 100 тестовых классов, и в каждом прописан `@Container`, Docker будет запускать и останавливать контейнеры 100 раз. Это убьет твой CI/CD.
**Решение:** Создай один базовый класс для всех интеграционных тестов и запусти контейнеры как `static` поля. Они запустятся один раз при старте первого теста и умрут только в самом конце.

#### 🛡️ Изоляция данных
Несмотря на то, что контейнер один, данные из одного теста могут «протечь» в другой (например, сообщение осталось в Kafka).
*   **Для Redis/RabbitMQ:** Очищай очереди или ключи в методе `@AfterEach`.
*   **Для Kafka:** Используй уникальные `group-id` для каждого тестового класса.

#### 🏗️ CI/CD (GitLab/GitHub Actions)
Помни: для работы Testcontainers на сервере должен быть установлен **Docker**. В GitHub Actions это работает «из коробки», но в кастомных Jenkins-агентах нужно провервать наличие Docker Socket.

**В: Почему нельзя использовать H2 вместо PostgreSQL/MySQL в тестах?**
**О:** Потомуy что синтаксис SQL и поведение транзакций различаются. Ты можешь написать тест, который проходит на H2, но падает в продакшене из-за специфичной функции Postgres или особенностей работы индексов.

**В: Как ускорить выполнение тестов, если Testcontainers запускает слишком много контейнеров?**
**О:** Используй паттерн Singleton (статические контейнеры) и библиотеку `Reusable Containers` (хотя первый вариант надежнее). Также старайся использовать легковесные образы (на базе `alpine`).

**В: Что делать, если в Docker-контейнере не хватает памяти или он падает при запуске Kafka?**
**О:** Настрой лимиты ресурсов для контейнера через `.withCreateContainerCmdModifier` и убедись, что Docker-демону на машине выделено достаточно RAM.

**О:** Используй **WireMock** (в связке с Testcontainers). Он имитирует HTTP-ответы внешнего сервиса, позволяя тебе тестировать логику обработки ошибок и таймаутов.

# 🛠 Testcontainers: Динамическое управление свойствами (`@DynamicPropertySource`)

### ❓ В чем проблема? (The Pain Point)
Когда ты используешь **Testcontainers**, Docker запускает контейнер (например, PostgreSQL) на **случайном свободном порту**. Это круто, потому что тесты могут идти параллельно и не конфли出一个 с твоей локальной базой.

**Но есть подвох:** Твой `application-test.properties` настроен на порт `5432`. Контейнер запустился на порту `32768`. Spring пытается подключиться к `5432`, не находит базу и падает с ошибкой `Connection Refused`.

**Решение:** Нам нужно «на лету» сказать Spring: *"Эй, забудь про порт 5432, используй вот этот случайный порт, который только что выделил Docker"*. Для этого и нужен `@DynamicPropertySource`.

---

### 🚀 Как это работает (The Implementation)

Аннотация `@DynamicPropertySource` позволяет переопределять свойства `Environment` в Spring Context прямо во время выполнения теста, используя данные из запущенного контейнера.

#### Пример кода (PostgreSQL)

```java
@SpringBootTest
@Testcontainers // Автоматически управляет жизненным циклом контейнеров
class MyIntegrationTest {

    // 1. Объявляем контейнер
    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15-alpine");

    // 2. Магия динамического переопределения свойств
    @DynamicPropertySource
    static void configureProperties(DynamicPropertyRegistry registry) {
        // Передаем URL, который сформировал Testcontainers (включая случайный порт)
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Test
    void contextLoads() {
        // Тест пройдет, так как Spring узнал правильный URL базы
    }
}
```

---

### 🧠 Нюансы от Senior'а (Pro Tips)

1.  **Метод ОБЯЗАТELНО должен быть `static`**: 
    Spring вызывает этот метод еще до того, как будет создан экземпляр твоего тестового класса. Если забудешь `static`, получишь ошибку при запуске.
2.  **Используй `Supplier` (лямбды)**: 
    В методе `registry.add(key, value)` вторым аргументом должен быть не просто `String`, а `Supplier<String>` (например, `postgres::getJdbcUrl`). Это гарантирует, что значение будет взято **после** того, как контейнер реально поднялся и порт зафиксирован.
3.  **Масштабируемость**: 
    Если у тебя много тестовых классов, не дублируй этот код везде. Создай базовый абстрактный класс `BaseIntegrationTest` и опиши `@DynamicPropertySource` там. Все остальные тесты будут наследоваться от него.
4.  **Modern Way (Spring Boot 3.1+) — `@ServiceConnection`**:
    Если ты используешь свежий Spring Boot, забудь про ручной маппинг для стандартных баз (Postgres, Redis, Kafka). Теперь можно просто написать:
    ```java
    @Container
    @ServiceConnection // Автоматически сконфигурирует URL, username и password!
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:15-alpine");
    ```
    *Используй `@DynamicPropertySource` только если тебе нужно настроить что-то кастомное (например, специфичные параметры пула соединений или нестандартные свойства).*

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Почему нельзя просто прописать порт в `application.properties`?**
**О:** Потому-то при запуске тестов на CI/CD (Jenkins, GitHub Actions) порт 5432 может быть занят другим процессом или другим запущенным контейнером. Случайный порт гарантирует изоляцию и отсутствие конфликтов.

**В: Что будет, если передать `postgres.getJdbcUrl()` напрямую как строку, а не через лямбду?**
**О:** Ошибка. На момент инициализации статического поля класса контейнер еще может быть не запущен (не определен порт). Лямбда (`() -> ...`) откладывает вызов метода до момента, когда Spring будет готов наполнять `DynamicPropertyRegistry`.

**В: Можно ли использовать `@DynamicPropertySource` для настройки не только БД, но и кастомных бизнес-свойтей?**
**О:** Да. Ты можешь использовать данные из любого контейнера (например, путь к папке в Volume или URL сервиса) и прокинуть их в свои `@Value("${my.custom.prop}")`.

# 🛠 Шпаргалка: Mocking External APIs

Когда твое приложение общается с внешним миром (платежные шлюзы, сервисы рассылок, API погоды), ты **не можешь** делать реальные запросы в интеграционных тестах. Это медленно, нестабильно и может стоить денег. 

Мы используем **Mocking**, чтобы имитировать поведение внешнего сервера.

## 1. Два уровня подхода
Важно понимать разницу между тем, *что* именно ты мокаешь:

1.  **Unit Level (Mockito):** Ты подменяешь сам Java-клиент (например, `WeatherClient.class`) на мок. 
    *   *Плюс:* Очень быстро.
    *   *Минус:* Ты не проверяешь, правильно ли настроен HTTP-клиент, заголовки и десериализация JSON. Это "тест веры" своему коду.
2.  **Integration Level (WireMock):** Ты запускаешь реальный локальный HTTP-сервер, который имитирует внешний API. Твой код делает настоящий HTTP-запрос на `localhost:8080`.
    *   *Плюс:* Проверяется всё: URL, заголовки, структура JSON, ошибки сети.
    *   *Минус:* Чуть медленнее и требует настройки портов.

**Senior Recommendation:** Для критически важных интеграций (где важен формат данных) всегда используй **WireMock**.

---

## 2. Инструмент №1: WireMock
WireMock — это стандарт индустрии. Он позволяет "заглушить" (stub) конкретные HTTP-эндпоинты.

### Основные операции (Stubbing):
*   **Matching:** Указываем, на какой URL и метод пришел запрос (`get`, `post`, `urlEqualTo`).
*   **Response:** Что вернуть (`status`, `body`, `headers`, `delay`).

### Пример кода (JUnit 5 + WireMock):

```java
@WireMockTest(httpPort = 8888) // Запускает сервер на порту 8888
class ExternalApiIntegrationTest {

    @Test
    void shouldReturnUserSuccess(@WireMockServer server) {
        // 1. Настраиваем заглушку (Stubbing)
        stubFor(get(urlEqualTo("/api/users/1"))
            .willReturn(aResponse()
                .withStatus(200)
                .withHeader("Content-Type", "application/json")
                .withBody("{\"id\": 1, \"name\": \"John Doe\"}")));

        // 2. Вызываем наш сервис (который внутри использует RestTemplate или WebClient на localhost:8888)
        User user = userService.getUserById(1);

        // 3. Проверяем результат
        assertEquals("John Doe", user.getName());
        
        // 4. Верификация (проверка, что запрос вообще был сделан)
        verify(getRequestedFor(urlEqualTo("/api/users/1")));
    }
}
```

---

## 3. Продвинутые сценарии (Нюансы)

### А. Тестирование ошибок (Error Handling)
Ты должен проверить, как твое приложение реагирует на "плохие" ответы:
*   **4xx/5xx ошибки:** `withStatus(500)` — проверяем, что приложение не падает с `NullPointerException`, а корректно обрабатывает ошибку.
*   **Malformed JSON:** Отправь битый JSON (`withBody("{ 'bad': json }")`), чтобы проверить устойчивость парсера.

### Б. Тестирование таймаутов и задержек (Resilience)
Если внешний сервис тормозит, твое приложение не должно "повиснуть".
*   **Simulation of Latency:** Используй `.withFixedDelay(5000)` (задержка 5 секунд). Это идеальный момент, чтобы протестировать настройки `ConnectTimeout` и `ReadTimeout` в твоем `WebClient/RestTemplate`, а также работу паттерна **Circuit Breaker** (Resilience4j).

### В. Динамические порты (Dynamic Property Source)
В CI/CD среде нельзя жестко прописывать порт `8888` (он может быть занят). 
**Senior Tip:** Используй `@DynamicPropertySource`, чтобы подставить реальный порт запущенного WireMock в настройки твоего Spring приложения.

```java
@DynamicPropertySource
static void configureProperties(DynamicPropertyRegistry registry) {
    registry.add("external.api.url", wireMockServer::baseUrl);
}
```

## 4. FAQ (Частые вопросы на собеседовании)

**В: В чем разница между Mockito и WireMock в контексте API?**
**О:** Mockito подменяет Java-объект (интерфейс), игнорируя сетевой слой. WireMock имитирует реальный сетевой уровень (HTTP), проверяя корректность формирования запроса, заголовков и парсинга ответа.

**В: Как протестировать ситуацию, когда внешний сервис отвечает слишком долго?**
**О:** С помощью WireMock функции `.withFixedDelay(ms)` или `.withLogNormalRandomDelay(...)`. Это позволяет проверить настройки таймаутов и механизмы ретраев (retries).

**В: Что делать, если внешний API требует сложную авторизацию (например, OAuth2)?**
**О:** В WireMock можно настроить `RequestMatcher` для проверки наличия конкретного заголовка `Authorization`. Если токен не передан или неверный — возвращаем `401 Unauthorized`.

**В: Можно ли использовать WireMock для записи реальных ответов (Record & Playback)?**
**О:** Да, у WireMock есть режим проксирования. Он может перехватывать реальные запросы к настоящему API и сохранять их в JSON-файлы (fixtures), которые потом можно использовать в тестах как заглушки. Это экономит время на написание маппингов вручную.

# 🛠 Topic: Mocking External APIs with WireMock

### 🧠 Что это такое? (The Essence)
Когда твой микросервис вызывает другой сервис (например, платежный шлюз или API погоды), ты не можешь в интеграционном тесте ходить в реальный интернет. Это медленно, нестабильно и дорого.

**WireMock** — это HTTP-сервер, который "притворяется" внешним сервисом. Ты говоришь ему: *"Если придет GET запрос на `/api/user/1`, ответь кодом 200 и вот таким JSON-ом"*. Твое приложение думает, что общается с реальным миром, но на самом деле общается с WireMock.

---

### 🚀 Основные возможности
*   **Stubbing (Заглушки):** Настройка ответов (Status, Body, Headers).
*   **Request Matching:** Умная фильтрация запросов (по URL, по телу, по заголовкам, по регуляркам или JSONPath).
*   **Verification:** Проверка того, что твой сервис *на самом деле* сделал запрос (с правильными параметрами).
*   **Fault Injection:** Имитация "плохого" поведения (задержки сети, обрыв соединения, ошибки 500).

---

### 🛠 Как использовать (Implementation)

#### 1. Подключение и запуск
В современном Spring Boot лучше всего использовать `WireMockExtension` для JUnit 5. Это автоматически поднимет сервер перед тестами и опустит после.

```java
@SpringBootTest
@WireMockTest(httpPort = 8089) // Запускает WireMock на порту 8s089
class WeatherServiceIntegrationTest {
    // Тесты здесь
}
```

#### 2. Написание заглушки (Stubbing)
Используем DSL-подобный синтаксис:

```java
stubFor(get(urlEqualTo("/api/weather?city=London")) // Что ищем
    .willReturn(aResponse()                        // Что отвечаем
        .withStatus(200)
        .withHeader("Content-Type", "application/json")
        .withBody("{\"temp\": 15, \"condition\": \"Cloudy\"}")
        .withFixedDelay(500))); // Имитация задержки сети в мс
```

#### 3. Проверка вызова (Verification)
Важно убедиться, что твой код не просто получил ответ, но и правильно сформировал запрос.

```java
verify(postRequestedFor(urlEqualTo("/api/logs"))
    .withRequestBody(containing("Error occurred"))); // Проверяем наличие текста в теле
```

### ⚠️ Нюансы и Best Practices (Senior Tips)

1.  **Не путай WireMock и Mockito:**
    *   `Mockito` — для Unit-тестов (замена Java-объектов внутри JVM).
    *   `WireMock` — для Integration-тестов (замена внешнего HTTP-сервиса по сети). Не используй WireMock там, где достаточно Mockito — это слишком тяжело.

2.  **Динамические URL:** 
    Никогда не хардкодь `http://api.weather.com` в коде приложения. Используй `@DynamicPropertySource`, чтобы подменять базовый URL внешнего сервиса на `http://localhost:8089` во время тестов.

3.  **Тестируй негативные сценарии:** 
    Главная сила WireMock — не в возврате "красивых" JSON, а в имитации боли:
    *   `withStatus(500)` — как твой сервис обработает падение соседа?
    *   `withFixedDelay(5000)` — упадет ли твой сервис по таймауту?
    *   `withFault(Fault.CONNECTION_RESET_BY_PEER)` — что будет, если соединение разорвется на середине?

4.  **Используй JSONPath для сложных запросов:** 
    Если нужно проверить наличие поля в огромном JSON-запросе, не пиши `contains("string")`. Используй `equalToJson` или проверку через Matchers.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем WireMock отличается от Mockito?**
**О:** Mockito работает на уровне объектов внутри одного процесса (подменяет методы интерфейсов). WireMock работает на сетевом уровне (поднимает реальный HTTP-сервер, принимающий TCP-соединения).

**В: Как протестировать ретраи (Retry) с помощью WireMock?**
**О:** Можно использовать `Scenarios` (Stateful mocks). Ты создаешь сценарий, где первый запрос возвращает 503 Service Unavailable, а второй — 200 OK. Это позволит проверить, что твой механизм Retry действительно работает.

**В: Что делать, если внешний API отдает очень большой JSON?**
**О:** Храни шаблоны ответов в отдельных `.json` файлах в папке `src/test/resources/mappings`. WireMock умеет подтягивать их автоматически, что не замусоривает код тестов.

**В: Как имитировать задержку (Latency)?**
**О:** С помощью метода `.withFixedDelay(ms)` (фиксированная) или `.withLogNormalDelay(...)` (случайная задержка, максимально приближенная к реальности).

# 🛠 Шпаргалка: Mocking External APIs (RestTemplate)

Когда твой сервис вызывает другой сервис через `RestTemplate`, у тебя есть две стратегии тестирования: **Unit-тестирование** (подмена самого объекта) и **Integration-тестирование** (подмена внешнего сервера).

---

## 1. Стратегия №1: Mockito (Unit Testing)
**Суть:** Мы не запускаем HTTP-сеть вообще. Мы просто говорим объекту `RestTemplate`: «Когда тебя спросят про этот URL, верни вот этот готовый Java-объект».

*   **Для чего:** Проверка бизнес-логики твоего сервиса. Тебе не важно, как работает HTTP, тебе важно, что делать с результатом.
*   **Плюсы:** Молниеносно, не нужно поднимать порты.
*   **Минусы:** Ты **не проверяешь** правильность URL, заголовков (headers) и того, как JSON превращается в твой DTO.

**Пример кода:**
```java
@ExtendWith(MockitoExtension.class)
class MyServiceTest {

    @Mock
    private RestTemplate restTemplate; // Подменяем бин

    @InjectMocks
    private MyService myService; // Внедряем мок в наш сервис

    @Test
    void testGetExternalData() {
        // Arrange (Подготовка)
        String url = "http://api.external.com/data";
        ExternalDto mockResponse = new ExternalDto("Success");
        
        // Говорим: при вызове getForObject верни наш мок
        when(restTemplate.getForObject(eq(url), eq(ExternalDto.class)))
            .thenReturn(mockResponse);

        // Act (Действие)
        String result = myService.fetchData();

        // Assert (Проверка)
        assertEquals("Success", result);
    }
}
```

---

## 2. Стратегия №2: WireMock (Integration Testing) — *The Senior Way*
**Суть:** Мы запускаем настоящий, но крошечный HTTP-сервер прямо внутри теста. Твой `RestTemplate` делает **реальный HTTP-запрос** на `localhost:8080`.

*   **Для чего:** Проверка "сквозного" пути. Ты проверяешь: правильно ли сформирован URL, передаются ли нужные токены в заголовках и не падает ли твой Jackson при парсинге JSON.
*   **Плюсы:** Максимальная уверенность. Тестируется реальный сетевой слой.
*   **Минусы:** Медленнее, чем Mockito, требует управления портами.

**Пример кода:**
```java
@SpringBootTest
@AutoConfigureWireMock(port = 0) // port 0 — найти свободный порт автоматически
class MyServiceIntegrationTest {

    @Autowired
    private MyService myService;

    @Test
    void testExternalApiCall() {
        // Arrange: Настраиваем "заглушку" сервера
        stubFor(get(urlEqualTo("/api/data")) // Слушаем этот путь
            .willReturn(aResponse()
                .withStatus(200)
                .withHeader("Content-Type", "application/json")
                .withBody("{\"status\": \"OK\"}"))); // Возвращаем реальный JSON

        // Act
        String result = myService.fetchData();

        // Assert
        assertEquals("OK", result);
        
        // Проверка: а вообще ли был сделан запрос? (Verification)
        verify(getRequestedFor(urlEqualTo("/api/data")));
    }
}
```

---

## 💡 Нюансы и "подводные камни" (Senior Tips)

1.  **Ошибка десериализации:** Если ты используешь Mockito, ты можешь забыть, что внешнее API прислало поле `user_id` вместо `userId`. Тест на Mockito пройдет (ты же вручную создал объект), а в продакшене всё упадет. **WireMock это поймает.**
2.  **Тестирование ошибок:** Всегда пиши тесты на сценарии `4xx` и `5xx`. 
    *   *В WireMock:* `.withStatus(500)`. Твой сервис должен уметь обрабатывать `HttpServerErrorException`.
3.  **Таймауты:** Если внешний сервис тормозит, твой сервис может "лечь". В WireMock можно имитировать задержку: `.withFixedDelay(2000)` (задержка 2 секунды). Это лучший способ проверить настройки `ConnectTimeout` и `ReadTimeout`.
4.  **ArgumentCaptor:** Если тебе нужно проверить, что твой сервис отправил в `POST`-запросе правильное тело (JSON), используй `ArgumentCaptor` в Mockito или `equalToJson` в WireMock.

## ❓ FAQ (Часто задаваемые вопросы)

**В: Когда использовать Mockito, а когда WireMock?**
**О:** Если ты тестируешь логику расчёта внутри метода — **Mockito**. Если ты тестируешь интеграцию, парсинг JSON или конфигурацию HTTP-клиента — **WireMock**. Не пытайся заменить WireMock-ом все тесты, это сделает сборку слишком медленной.

**В: Как протестировать передачу токена (Authorization header)?**
**О:** В WireMock используй `.withHeader("Authorization", matching("Bearer .*"))`. Это позволит убедиться, что твой сервис не забыл прикрепить токен к запросу.

**В: Что делать, если URL динамический (например, содержит ID)?**
**О:** В WireMock вместо `urlEqualTo` используй `urlPathMatching("/api/users/[0-9]+")`. Это позволит использовать регулярные выражения для гибкости.

**В: RestTemplate считается устаревшим?**
**О:** Да, Spring рекомендует переходить на `WebClient` (для реактивного подхода) или `RestClient` (новый синхронный клиент в Spring 6). Но принципы мокинга (Mockito и WireMock) для них **абсолютно идентичны**.

# 🚀 Шпаргалка: Тестирование WebClient

## 🎯 Основная стратегия
Есть два пути, и один из них — «правильный».

1.  **Unit Test (Mocking the Client):** Использование Mockito для имитации цепочки вызовов `WebClient`. 
    *   *Вердикт:* **Плохо.** Тест становится хрупким: стоит изменить порядок вызова методов в коде, тест упадет, хотя логика верна.
2.  **Integration Test (Mocking the Server):** Использование **WireMock**. Мы поднимаем реальный локальный HTTP-сервер, который отвечает на запросы. `WebClient` думает, что общается с реальным API.
    *   *Вердикт:* **Senior Choice.** Тестируем реальный сетевой протокол, JSON-сериализацию и заголовки.

---

## 🛠 Инструмент №1: WireMock (Золотой стандарт)

WireMock создает «заглушку» сервера. Вы настраиваете правила: *"Если пришел GET на `/users/1`, ответь `200 OK` с таким-то JSON"*.

### Пример реализации
Предположим, у нас есть `UserService`, который вызывает внешнее API.

**Зависимость (Maven):**
```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-contract-wiremock</artifactId>
    <scope>test</scope>
</dependency>
```

**Код теста:**
```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureWireMock(port = 0) // 0 — автоматически подберет свободный порт
class UserServiceTest {

    @Autowired
    private UserService userService; // Наш сервис, использующий WebClient

    @Test
void shouldReturnUserSuccessfully() {
        // 1. Arrange (Настраиваем заглушку)
        stubFor(get(urlEqualTo("/api/users/1"))
            .willReturn(aResponse()
                .withStatus(200)
                .withHeader("Content-Type", "application/json")
                .withBody("{\"id\": 1, \"name\": \"John Doe\"}")));

        // 2. Act (Вызываем наш сервис)
        User result = userService.getUserById(1).block(); // block() только для тестов!

        // 3. Assert (Проверяем результат)
        assertThat(result.getName()).isEqualTo("John Doe");
        
        // Проверка, что запрос вообще дошел до WireMock
        verify(getRequestedFor(urlEqualTo("/api/users/1")));
    }
}
```

### 1. Динамические URL (Самый важный нюанс!)
Ваш `WebClient` не должен иметь захардкоженный URL `https://api.external.com`. В тестах он должен смотреть на `http://localhost:${wiremock.server.port}`.
*   **Как делать:** Используйте `@DynamicPropertySource`, чтобы подменить базовый URL внешнего сервиса на адрес WireMock во время выполнения теста.

### 2. Тестирование ошибок (Error Handling)
Не забудьте проверить, как ваш сервис реагирует на:
*   `404 Not Found` (вернет ли он `Mono.empty()` или кинет исключение?).
*   `500 Internal Server Error`.
*   **Timeout:** Настройте в WireMock задержку `.withFixedDelay(2000)`, чтобы проверить, срабатывает ли ваш механизм ретраев (Retry) или таймаутов.

### 3. Тестирование JSON-маппинга
WireMock позволяет загружать файлы из `src/test/resources`. Вместо того чтобы писать огромные строки с JSON в коде, создайте файл `user.json`. Это делает тесты чистыми.

## ❓ FAQ (Частые вопросы на собеседованиях)

**В: Почему нельзя просто использовать Mockito для WebClient?**
**О:** Потому что `WebClient` использует Fluent API. Чтобы замокать один вызов `.bodyToMono()`, тебе придется создать моки для `RequestHeadersUriSpec`, `RequestHeadersSpec`, `ResponseSpec` и т.д. Тест превратится в написание кода, который имитирует внутренности библиотеки, а не бизнес-логику. Это делает тесты крайне хрупкими.

**В: Как протестировать ситуацию, когда внешний сервис тормозит?**
**О:** В WireMock используй метод `.withFixedDelay(ms)`. Это позволит проверить, правильно ли настроен `timeout` в твоем `WebClient` и не "положит" ли медленный внешний сервис твое приложение.

**В: Что делать, если внешнее API использует OAuth2/Bearer Token?**
**О:** В WireMock можно добавить проверку заголовков через `.withHeader("Authorization", matching("Bearer .*"))`. Это позволит убедиться, что ваш `WebClient` корректно прокидывает токены.

**В: Как избежать конфликтов портов при запуске тестов в CI/CD?**
**О:** Всегда используй порт `0` (random port) для WireMock и `@SpringBootTest(webEnvironment = RANDOM_PORT)`. Это гарантирует, что тесты не упадут, если порт 8080 уже занят другим процессом.

# 🛡️ Шпаргалка: Spring Security Test

**Суть темы:** Тестирование безопасности — это проверка двух вещей: **Authentication** (знаем ли мы, кто этот пользователь?) и **Authorization** (есть ли у него права на это действие?). Мы не тестируем сам фреймворк Spring Security, мы тестируем *наши правила* (фильтры, конфигурацию, маппинг ролей).

---

### 1. Основной инструментарий (Dependencies)
Для работы тебе нужна зависимость:
```xml
<dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-test</artifactId>
    <scope>test</scope>
</dependency>
```

### 2. Главные аннотации (Simulating Users)

Когда мы пишем тесты, нам не нужно создавать реального пользователя в БД. Нам нужно «подложить» объект `Authentication` в `SecurityContextHolder`.

*   **`@WithMockUser`**: Самый быстрый способ. Создает «фейкового» пользователя с заданными ролями и именами.
    *   *Нюанс:* Он не обращается к базе. Это просто пустой объект в памяти.
    *   *Пример:* `@WithMockUser(username = "admin", roles = {"ADMIN", "USER"})`
*   **`@WithUserDetails`**: Более «тяжелый» способ. Spring попытается найти пользователя через твой `UserDetailsService`.
    *   *Когда использовать:* Если твоя логика безопасности зависит от данных из БД (например, проверка статуса `is_active` или `email`).
*   **`@AutoConfigureMockMvc`**: Необходима в интеграционных тестах, чтобы `MockMvc` понимал, что нужно поднять и настроить цепочку фильтров безопасности.

### 3. Тестирование Web-слоя (Controller Level)

Здесь мы проверяем, правильно ли работают наши `SecurityFilterChain`. Используем `MockMvc`.

**Что проверять:**
1.  **401 Unauthorized:** Если пользователь не авторизован.
2.  **403 Forbidden:** Если пользователь авторизован, но у него нет нужной роли.
3.  **CSRF Protection:** Проверка, что POST/PUT запросы без CSRF-токена отклоняются (если он включен).

**Пример с PostProcessors (Senior level trick):**
Иногда нужно имитировать не просто пользователя, а специфические детали запроса (например, JWT или OAuth2). Для этого используются `SecurityMockMvcRequestPostProcessors`.

```java
// Имитация JWT токена в запросе
mockMvc.perform(get("/api/data")
    .with(jwt().claim("scope", "read")) // Добавляем claim прямо в "токен"
    .with(csrf())) // Добавляем CSRF токен, чтобы запрос не упал на фильтре
    .andExpect(status().isOk());
```

### 4. Тестирование Method Security (Service Level)

Если у тебя над методами сервиса стоят аннотации `@PreAuthorize("hasRole('ADMIN')")`, обычный Unit-тест с Mockito их **не увидит**. Чтобы протестировать эти правила, нужен контекст Spring (`@SpringBootTest` или `@DataJpaTest` + доп. конфиг).

### 5. Тонкие моменты (Pitfalls)

1.  **Роли vs Права (Roles vs Authorities):**
    *   В Spring Security `hasRole("ADMIN")` ищет префикс `ROLE_`. То есть он ищет `ROLE_ADMIN`.
    *   Если ты используешь `@WithMockUser(roles = "ADMIN")`, Spring сам добавит `ROLE_`.
    *   Если ты врунишь через `authorities = {"ADMIN"}`, то проверка `hasRole("ADMIN")` **провалится**, так как префикса нет.
2.  **CSRF в тестах:** Забытый `.with(csrf())` — самая частая причина, почему тесты на POST/PUT запросы падают с 403, хотя пользователь «правильный».
3.  **Тестирование OAuth2/OIDC:** Для этого используй специализированный `SecurityMockMvcRequestPostProcessors.oidc()`.

**В: Чем `@WithMockUser` отличается от `@WithUserDetails`?**
**О:** `@WithMockUser` создает простой объект без обращения к базе данных (быстро, для Unit/Web-слоя). `@WithUserDetails` заставляет Spring вызвать твой `UserDetailsService`, чтобы загрузить реальный объект пользователя из БД или кеша (медленнее, для интеграционных тестов).

**В: Почему мой тест с `@WithMockUser(roles = "USER")` получает 403 Forbidden?**

# 🛡️ Spring Security Test: `@WithMockUser`

### 💡 Суть простыми словами
Представь, что тебе нужно протестировать защищенный контроллер (например, `/api/admin/delete`). Чтобы достучаться до него, тебе нужно быть авторизованным. Вместо того чтобы реально имитировать процесс логина (отправлять POST-запрос с паролем, получать JWT и т.д.), ты используешь `@WithMockUser`. 

Эта аннотация — **«магическая заглушка»**. Она говорит Spring: *"Забудь про реальную проверку пароля, просто представь, что в `SecurityContextHolder` уже лежит пользователь с таким-то именем и такими-то ролями"*.

---

### 🛠️ Как это работает (Базовый синтаксис)

Аннотация вешается либо на метод теста, либо на весь класс.

```java
@Test
@WithMockUser(username = "ivan", roles = {"USER", "ADMIN"})
void adminEndpoint_ShouldAllowAccess() throws Exception {
    mockMvc.perform(get("/api/admin/dashboard"))
           .andExpect(status().isOk());

}
```

**Что здесь произошло?**
Spring создаст объект `UsernamePasswordAuthenticationToken`, положит его в контекст безопасности, и твой контроллер "поверит", что пользователь `ivan` с ролями `ROLE_USER` и `ROLE_ADMIN` уже прошел аутентификацию.

---

### ⚠️ Нюансы и «грабли» (Senior Level)

#### 1. Ловушка Roles vs Authorities (Самая частая ошибка!)
В Spring Security есть разница между **Role** и **Authority**.
*   Если ты пишешь `roles = "ADMIN"`, Spring автоматически добавит префикс `ROLE_`. В итоге у пользователя будет право `ROLE_ADMIN`.
*   Если ты используешь `authorities = "READ_PRIVILEGE"`, префикса **не будет**. У пользователя будет ровно `READ_PREVILIEGE`.

**Ошибка:** Ты настроил проверку в контроллере через `.hasAuthority("ADMIN")`, а в тесте написал `@WithMockUser(roles = "ADMIN")`. Тест упадет с `403 Forbidden`, потому что в контексте лежит `ROLE_ADMIN`, а ты ищешь просто `ADMIN`.

#### 2. Проблема Custom UserDetails
`@WithMockUser` создает стандартный объект пользователя (из библиотеки Spring Security). Если твой бизнес-код делает каст:
```java
// В контроллере
CustomUser user = (CustomUser) authentication.getPrincipal();
Long userId = user.getId(); // <--- ТУТ БУДЕТ ClassCastException!
```
...то тест **упадет**. Потому что `@WithMockUser` подсунул стандартный `User`, а не твой `CustomUser`.

**Решение:** Для сложных сценариев используй `@WithUserDetails`. Эта аннотация заставит Spring вызвать твой реальный `UserDetailsService` и загрузить пользователя из базы (или мока базы).

#### 3. Тестирование только авторизации, а не аутентификации
Помни: `@WithMockUser` **пропускает** этап проверки логина/пароля. Ты тестируешь только *права доступа* (Authorization), но не *процесс входа* (Authentication). Если у тебя сложная логика проверки JWT или OAuth2, этот инструмент её не проверит.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что именно делает `@WithMockUser` под капотом?**
**О:** Она заполняет `SecurityContextHolder.getContext().setAuthentication(...)` заранее подготовленным объектом `UsernamePasswordAuthenticationToken`.

**В: Почему мой тест выдает 403, если я указал правильную роль в аннотации?**
**О:** Проверь префикс `ROLE_`. Скорее всего, ты используешь `.hasAuthority("ADMIN")` вместо `.hasRole("ADMIN")`, либо наоборот. Помни: `roles = "USER"` $\to$ `ROLE_USER`.

**В: Как протестировать метод, который использует ID пользователя из сессии/токена?**
**О:** `@WithMockUser` не умеет прокидывать кастомные поля (типа `userId`). Тебе нужно либо использовать `@WithUserDetails`, либо написать свою кастомную аннотацию (через `WithSecurityContextFactory`), которая будет создавать твой `CustomUser`.

**В: Можно ли использовать `@WithMockUser` вместе с `@WebMvcTest`?**
**О:** Да, это идеальная пара. `@WebMvcTest` поднимает только слой контроллеров, а `@WithMockUser` подменяет пользователя, позволяя протестировать логику доступа без поднятия всей базы и сервисов.

# 🛡️ Шпаргалка: Тестирование Method Security (`@PreAuthorize`, `@Secured`)

### 🎯 Суть задачи
Когда мы тестируем методы с аннотациями безопасности, наша цель — проверить не бизнес-логику, а **правильность работы Guard (защитника)**. Мы должны убедиться, что:
1. Пользователь с нужной ролью **проходит**.
2. Пользователь без нужной роли **получает отказ** (`AccessDeniedException` или HTTP 403).
3. Анонимный пользователь **не имеет доступа**.

---

### 🛠️ Основные инструменты

В Spring Security Test всё крутится вокруг подмены `SecurityContextHolder`. Нам не нужно логиниться через форму, нам нужно "подбросить" готовый объект `Authentication` в контекст.

#### 1. `@WithMockUser` — «Быстрый и грязный» способ
Используется, когда тебе плевать на реальную базу данных и `UserDetailsService`. Он просто создает в памяти объект пользователя с заданными ролями.

*   **Когда юзать:** В Unit-тестах или интеграционных тестах контроллеров, где важна только проверка прав (Roles/Authorities).
*   **Пример:**
    ```java
    @Test
    @WithMockUser(roles = "ADMIN") // Создаст пользователя с ROLE_ADMIN
    void adminCanDeleteUser() {
        // Тест пройдет, если метод помечен @PreAuthorize("hasRole('ADMIN')")
    }
    ```

#### 2. `@WithUserDetails` — «Реалистичный» способ
Этот инструмент ищет пользователя в твоем `UserDetailsService`. Он берет `username` из контекста и пытается загрузить его из базы (или мока базы).

*   **Когда юзать:** Если логика безопасности завязана на сложные свойства пользователя (например, `@PreAuthorize("#user.id == authentication.principal.id")`).
*   **Важно:** Тебе нужно иметь в контексте теста бин `UserDetailsService`.

---

### 🚀 Сценарии тестирования

#### Сценарий А: Проверка успешного доступа (Positive Test)
Мы проверяем, что роль совпадает.
```java
@Test
@WithMockUser(authorities = {"READ_PRIVILEGE"})
void testReadAccess() {
    // Метод помечен @PreintAuthorize("hasAuthority('READ_PRIVILEGE')")
    // Тест должен завершиться успешно
}
```

#### Сценарий Б: Проверка отказа в доступе (Negative Test)
Самый важный тест. Мы проверяем, что система "выкидывает" ошибку.
```java
@Test
@WithMockUser(roles = "USER") // У нас только USER, а нужно ADMIN
void testAdminOnlyMethodFails() {
    // Метод помечен @PreAuthorize("hasRole('ADMIN')")
    
    assertThrows(AccessDeniedException.class, () -> {
        service.deleteEverything();
    });
    // Или в MockMvc:
    // mockMvc.perform(delete("/api/admin/data")).andExpect(status().isForbidden());
}
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Level)

1.  **Ловушка префикса `ROLE_`:**
    *   Если ты пишешь `@WithMockUser(roles = "ADMIN")`, Spring автоматически добавит префикс: `ROLE_ADMIN`.
    *   Если ты пишешь `@WithMockUser(authorities = "ADMIN")`, префикса **не будет**.
    *   **Ошибка:** Если в коде `@PreAuthorize("hasRole('ADMIN')")`, а в тесте указал `authorities = "ADMIN"`, тест **упадет**, потому что он ищет `ROLE_ADMIN`.

2.  **Забытый `@EnableMethodSecurity`:**
    *   Если ты пишешь тесты, но аннотации `@PreAuthorize` просто игнорируются (тест проходит даже с неверной ролью) — проверь, включена ли поддержка Method Security в конфигурации приложения (`@EnableMethodSecurity`). Без неё аннотации — это просто пустой текст.

3.  **Тестирование `Principal`:**
    *   Если твой метод использует `Authentication principal` как аргумент, `@WithMockUser` создаст стандартный `User`. Если тебе нужен кастомный объект (например, `MyUserEntity`), используй `@WithUserDetails` и настрой мок для `UserDetailsService`.

4.  **Сложные выражения (SpEL):**
    *   Если в `@PreAuthorize` используется проверка параметров метода (например, `#id == authentication.principal.id`), обычный `@WithMockUser` может не подойти, так как он не знает о твоем кастомном объекте пользователя. Тут спасает только создание своего `@WithMockCustomUser`.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `@WithMockUser` и `@WithUserDetails`?**
**О:** `@WithMockUser` создает "пустышку" в памяти без обращения к базе. `@WithUserDetails` заставляет Spring вызвать `UserDetailsService`, чтобы загрузить реального (или замоканного) пользователя из системы.

**В: Почему мой тест на `@PreAuthorize` проходит, хотя я указал не ту роль?**
**О:** Две основные причины: 1) В конфигурации забыли поставить `@EnableMethodSecurity`. 2) Ты тестируешь сервис в Unit-тесте без поднятия Spring Context (в чистом JUnit моки не знают про аннотации Spring Security).

**В: Как протестировать доступ для анонимного пользователя?**
**О:** Используй `@WithMockUser(roles = "ANONYMOUS")` или вообще не используй аннотацию пользователя, если контекст очищается. Но лучше всего явно проверять отсутствие прав через `mockMvc.perform(...)` без предварительной авторизации.

**В: Что использовать для проверки `hasAuthority('PERMISSION')`?**
**О:** Используй параметр `authorities = {"PERMISSION"}` в `@WithMockUser`. Не используй `roles`, так как `roles` автоматически добавит префикс `ROLE_`, который может сломать проверку конкретной привилегии.

# 🛡️ Шпаргалка: Spring Security Testing
## Тема: Проверка механизмов аутентификации (JWT, OAuth2, Basic Auth)

### 🎯 Главная цель
Мы не тестируем саму библиотеку Spring Security (это работа разработчиков Spring). Мы тестируем **нашу конфигурацию**: правильно ли настроены фильтры, верно ли интерпретируются роли и не забыли ли мы закрыть эндпоинты.

---

### 🛠️ Инструментарий
Для работы тебе нужна зависимость:
```xml
<dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-test</artifactId>
    <scope>test</scope>
</dependency>
```

---

### 1. Базовый уровень: Эмуляция пользователя
Самый простой способ — «подменить» текущего пользователя в контексте, не проходя через весь процесс логина.

*   **`@WithMockUser(username = "admin", roles = {"USER", "ADMIN"})`**
    *   **Что делает:** Создает пустой объект `Authentication` с указанными ролями.
    *   **Нюанс (Senior Tip):** Помни, что в Spring Security роль `ADMIN` превращается в префикс `ROLE_ADMIN`. Если в коде проверка `.hasRole("ADMIN")`, то аннотация должна быть именно такой.
*   **`@WithUserDetails`**
    *   **Что делает:** Ищет пользователя через твой реальный `UserDetailsService`. 
    *   **Когда использовать:** Когда логика прав доступа завязана на данные из БД (например, проверка владельца ресурса по ID).

---

### 2. Тестирование Basic Auth
Здесь мы проверяем, что фильтр `BasicAuthenticationFilter` правильно перехватывает заголовки.

*   **Как тестировать:** Используем `MockMvcRequestPostProcessors.httpBasic`.
```java
mockMvc.perform(get("/api/admin")
    .with(httpBasic("user", "password"))) // Эмуляция заголовка Authorization: Basic ...
    .andExpect(status().isOk());
```

---

### 3. Тестирование JWT (Modern Way)
JWT — это stateless. Мы не можем просто «залогиниться», нам нужно передать валидный токен в заголовке `Authorization`.

*   **Стратегия Senior:** Не пытайся генерировать настоящий подписанный токен в каждом тесте (это медленно и сложно). Вместо этого используй моки для декодирования или эмулируй наличие JWT-токена.
*    **`jwt()` Post-Processor:**
```java
mockMvc.perform(get("/api/data")
    .with(jwt() // Создает Mock Jwt object
        .claims(claims -> claims.claim("user_id", "123"))
        .jwtAuthentication(mockJwtAuthentication))) 
    .andExpect(status().isOk());
```
*   **Нюанс:** Если у тебя кастомный `OncePerRequestFilter` для проверки JWT, тебе нужно убедиться, что твой тест либо прокидывает заголовок `Bearer <token>`, который этот фильтр сможет «распознать» (через мок), либо ты используешь `jwt()` post-processor, чтобы обойти фильтр и сразу положить данные в контекст.

---

### 4. Тестирование OAuth2 / OpenID Connect
Тут мы проверяем, что приложение правильно понимает атрибуты (claims) из провайдера (Google, Okta и т.д.).

*   **`oauth2Login()` Post-Processor:**
```java
mockMvc.perform(get("/user/profile")
    .with(oauth2Login() // Эмуляция успешного входа через OAuth2
        .attributes(attrs -> attrs.put("email", "test@example.com"))
        .authorities(new SimpleGrantedAuthority("SCOPE_read"))))
    .andExpect(status().isOk());
```

---

### ⚠️ Критические нюансы (Pitfalls)

1.  **401 vs 403:** 
    *   Если тест падает с **401 Unauthorized** — ты не прошел аутентификацию (тест не нашел пользователя или токен).
    *   Если тест падает с **403 Forbidden** — пользователь есть, но у него нет нужной роли. Это самая частая ошибка при написании тестов.
2.  **Тестирование «дырок»:** Всегда пиши негативные тесты! Создай тест без аннотации `@WithMockUser` и убедись, что эндпоинт возвращает `401`. Если он вернул `200` — у тебя дыра в безопасности.
3.  **Context Dirtying:** Если ты используешь `@MockBean` для `UserDetailsService`, помни, что это меняет контекст Spring. При большом количестве тестов это может замедлить выполнение.

**О:** `@WithMockUser` создает «пустышку» в памяти, не обращаясь к базе или сервисам. `@WithUserDetails` заставляет Spring вызвать твой `UserDetailsService`, чтобы загрузить реальный объект пользователя (со всеми его связями и правами).

**В: Как протестировать, что пользователь не может удалить чужой пост?**
**О:** Тебе нужно использовать `@WithUserDetails` для двух разных пользователей (или одного, но с разными ID в запросе) и проверить, что `SecurityContext` содержит ID владельца поста, а контроллер возвращает `403 Forbidden`.

**В: Можно ли тестировать JWT без создания реального токена?**
**О:** Да, через `MockMvcRequestPostProcessors.jwt()`. Мы тестируем логику приложения, которая работает *после* того, как токен был проверен. Тестирование самого алгоритма проверки подписи — это уже задача Unit-теста для вашего `JwtFilter`.

**В: Что делать, если я использую кастомный заголовок вместо Bearer?**
**О:** Используй `.header("X-Custom-Auth", "some-value")` в `MockMvc`. Тест должен имитировать реальный HTTP-запрос, который придет на сервер.

# 🧠 Шпаргалка: Testing Asynchronous Code

### 🚀 Суть проблемы
Когда ты тестируешь обычный метод, поток выполнения теста и поток выполнения кода — это одно и то же. В асинхронном коде (`@Async`, `CompletableFuture`, `TaskExecutor`) создается **новый поток**. 

**Главная ловушка:** Тестовый поток доходит до проверки (`assertion`) быстрее, чем фоновый поток успевает завершить работу. Результат: тест падает, хотя код работает правильно. Это называется **Race Condition** (состояние гонки).

---

### ❌ Антипаттерн: `Thread.sleep()`
Самый плохой способ. Ты просто заставляешь тест ждать (например, 2 секунды), надеясь, что код успеет.
*   **Почему это плохо:** 
    1. **Ненадежно:** Если сервер "затупит" на 2.1 сек, тест упадет.
    2. **Медленно:** Если код выполнился за 10мс, ты всё равно заставляешь CI/CD ждать лишние 1.9 сек. На тысяче тестов это превращается в часы ожидания.

---

### ✅ Профессиональный подход: Awaitility
`Awaitility` — это библиотека для **polling** (опроса). Вместо того чтобы "спать", она постоянно и очень быстро проверяет условие, пока оно не выполнится или не выйдет время (timeout).

**Пример использования:**
Представь, что у нас есть сервис, который после обработки заказа обновляет статус в базе через 1 секунду.

```java
@Test
void testAsyncOrderProcessing() {
    // 1. Вызываем асинхронный метод
    orderService.processOrder(orderId);

    // 2. Используем Awaitility для ожидания
    await()
        .atMost(5, TimeUnit.SECONDS) // Максимальное время ожидания
        .pollInterval(100, TimeUnit.MILLISECONDS) // Как часто проверять условие
        .untilAsserted(() -> {
            // 3. Проверяем состояние базы/объекта
            Order updatedOrder = orderRepository.findById(orderId).orElseThrow();
            assertThat(updatedOrder.getStatus()).isEqualTo(OrderStatus.COMPLETED);
        });
}
```

### 🛠 Нюансы, о которых забывают (Senior Level)

#### 1. Потеря контекста (Context Propagation)
Это "смертный грех" в Spring. Когда создается новый поток через `@Async`, **ThreadLocal** данные не копируются автоматически.
*   **Проблема:** `SecurityContextHolder` будет пуст. Если твой асинхронный метод проверяет `@PreAuthorize("hasRole('ADMIN')")`, он упадет с ошибкой доступа, даже если в тесте ты залогинен.
*   **Решение:** Настройка `DelegatingSecurityContextAsyncTaskExecutor`.

#### 2. Невидимые ошибки (Swallowed Exceptions)
Если внутри асинхронного метода произойдет `RuntimeException`, поток завершится, но **тестовый поток об этом не узнает**. Тест просто увидит, что статус не изменился, и упадет по таймауту, вместо того чтобы показать реальную ошибку (например, `NullPointerException`).
*   **Совет:** Всегда проверяй логи или используй специальные обработчики (`AsyncUncaughtExceptionHandler`) в тестах.

#### 3. Видимость изменений (Visibility)
В многопоточности изменения переменной в одном потоке могут быть не видны другому из-за кэширования в ядрах процессора.
*   **Совет:** При тестировании кастомных механизмов убедись, что поля, которые ты проверяешь, помечены как `volatile` или изменения происходят через атомарные типы (`AtomicReference`, `AtomicInteger`).

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что такое "Flaky Test" и как асинхронность на них влияет?**
**О:** Flaky test — это тест, который иногда проходит, а иногда падает без изменения кода. Асинхронный код — главный источник таких тестов из-за непредсказуемой скорости выполнения фоновых задач.

**В: Можно ли использовать `CountDownLatch` для тестирования?**
**О:** Да, это низкоуровневый способ Java. Ты создаешь "защелку" в тесте и в асинхронном коде. Тест ждет `latch.await()`, а асинхронный поток делает `latch.countDown()`. Это надежнее, чем `sleep`, но сложнее в поддержке, чем `Awaitility`.

**В: Как протестировать `@Async` метод, если он вызывает внешний API?**
**О:** Используй связку **Awaitility + WireMock**. WireMock поднимет заглушку API, а Awaitility будет ждать, пока твой сервис обработает ответ от этой заглушки и обновит состояние в базе.

**В: Почему `Thread.sleep()` — это плохая практика для CI/CD?**
**О:** Потомут что это раздувает время сборки (Build Time). В больших проектах суммарное время "пустого" ожидания может составлять десятки минут, что замедляет разработку и увеличивает стоимость инфраструктуры.

# 🗄️ Cheat Sheet: Database State Management in Spring Testing

**Суть проблемы:** Тесты должны быть **изолированными** и **детерминированными**. Если Тест А создал пользователя, а Тест Б упал, потому что ожидал, что база пуста — у тебя проблема с *State Management*.

---

### 1. Стратегия №1: Transactional Rollback (Самый быстрый путь)
В Spring Boot при тестировании слоев (например, `@DataJpaTest`) по умолчанию включена аннотация `@Transactional`.

*   **Как это работает:** Каждый тест запускается внутри транзакции. В конце теста происходит автоматический `rollback`. База остается в том же состоянии, в котором была до теста.
*   **Плюсы:** Невероятно быстро. Никакой очистки вручную.
*   **Нюансы (Senior Alert!):** 
    *   **Не работает с асинхронщиной:** Если твой сервис вызывает `@Async` метод, этот метод запустится в *другой* транзакции/потоке. Он не увидит изменений из теста и не откатит их.
    *   **Не проверяет реальный Commit:** Ты не узнаешь, возникнет ли ошибка при реальной фиксации данных (например, нарушение `Constraint` в БД), так как коммита просто не происходит.

### те 2. Стратегия №2: Script-based Setup (`@Sql`)
Если тебе нужно подготовить специфический набор данных (например, «сложный заказ с 10 позициями»), используй SQL-скрипты.

*   **`@Sql(scripts = "/data/setup.sql")`**: Выполняет скрипт перед тестом.
*   **`executionPhase = ExecutionPhase.AFTER_TEST_METHOD`**: Позволяет очистить базу после теста.
*   **Нюанс:** Всегда следи за порядком. Сначала `DELETE/TRUNCATE`, потом `INSERT`. Если скрипты будут накладываться друг на друга, ты получишь трудноуловимые баги.

### 3. Стратегия №3: Database Cleaning (Очистка «в лоб»)
Если ты используешь **Testcontainers** (реальную БД в Docker) и `@Transactional` не подходит (из-за асинхронности), тебе нужно физически чистить таблицы.

*   **Подход:** Создать `TestExecutionListener` или просто метод с аннотацией `@AfterEach`, который находит все таблицы и делает `TRUNCATE`.
*   **Инструмент:** Можно использовать библиотеку **DbUnit**, но в современном Spring чаще пишут небольшой `DatabaseCleaner` сервис, который через `JdbcTemplate` обходит все таблицы.

### 4. Схема данных: Flyway / Liquibase
Твои тесты **обязаны** использовать ту же схему, что и продакшн.
*   Никогда не создавай таблицы вручную в тестах (`hibernate.ddl-auto=create`).
*   Используй те же миграции (Flyway/Liquibase), что и в основном приложении. Это гарантирует, что если ты забыл добавить колонку в миграцию, тест упадет сразу, а не на проде.

### 5. Инструменты для генерации данных
Чтобы не писать `INSERT INTO users (name) VALUES ('Ivan')` сто раз:
*   **Java Faker / Datafaker:** Генерирует случайные имена, адреса, email. Это делает тесты более «живыми» и помогает найти ошибки с длиной строк или спецсимволами.

---

### 💡 Senior Summary (Золотые правила)

1.  **H2 vs Testcontainers:** Используй H2 только для очень простых Unit-тестов репозиториев. Для всего, что касается сложной логики, связей или специфичных функций (JSONB в Postgres, Window Functions), — **только Testcontainers**.
2.  **Принцип чистого листа:** Каждый тест должен быть способен запуститься первым в списке. Если твой тест зависит от того, что «кто-то уже наполнил базу» — это плохой тест.
3.  **Избегай `ddl-auto: create`:** Это ловушка. Она скрывает ошибки в твоих миграциях.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Почему `@Transactional` в тестах может не работать?**
**О:** Потому что транзакция привязана к потоку. Если код внутри теста запускает новый поток (например, через `@Async` или `CompletableFuture`), этот новый поток не участвует в текущей транзакции теста. Изменения в нем не будут откачены и могут «загрязнить» базу для следующих тестов.

**В: Что лучше: очищать базу перед каждым тестом или после каждого?**
**О:** Безопаснее **перед** каждым тестом (Setup). Если тест упадет на середине выполнения, `After` метод может не сработать, и база останется грязной. А вот `Before` гарантирует чистый старт в любом случае.

**В: Как протестировать миграцию базы данных?**
**О:** Нужно поднять Testcontainers с пустой базой, применить текущие миграции и проверить, что схема соответствует ожидаемой (например, через проверку наличия колонок или использование `SchemaValidator`).

**В: Можно ли использовать `@Sql` вместе с `@Transactional`?**
**О:** Да. Сначала выполнится SQL-скрипт (в рамках той же транзакции), а затем выполнится код теста. В конце всё вместе откатится. Это отличный способ быстро наполнить контекст данными.

# 🧠 Шпаргалка: Database State Management — `@Transactional` в тестах

### 🎯 Суть
В контексте Spring Testing аннотация `@Transactional` используется для того, чтобы **автоматически откатывать (rollback)** все изменения в базе данных после завершения теста. Это гарантирует, что каждый тест запускается в «чистой» среде и не оставляет за собой мусора (записей), который мог бы сломать следующий тест.

### 🛠 Как это работает
Когда ты вешаешь `@Transactional` на тестовый класс или метод:
1. **Start:** Spring начинает транзакцию перед выполнением `@BeforeEach` и самого теста.
2. **Execution:** Тест выполняется, данные пишутся в БД (но они еще не зафиксированы/committed).
3. **Rollback:** После завершения теста Spring принудительно делает `rollback`. База возвращается в состояние, которое было до начала теста.

---

### ⚠️ Нюансы и «Подводные камни» (Senior Level)

#### 1. Проблема асинхронности (`@Async`) — **Самая частая ошибка**
Если твой сервис использует `@Async`, то новый поток создаст **свою собственную транзакцию**. 
* **Проблема:** Твой тестовый метод создал запись в БД, но еще не завершился (транзакция не зафиксирована). Асинхронный поток лезет в базу, а там **пусто**, потому что изменения из основного потока еще «не видны» другим транзакциям.
* **Решение:** Либо избегать `@Transactional` в таких тестах, либо использовать `Testcontainers` с реальной фиксацией данных (но это медленнее), либо тестировать асинхронность через механизмы ожидания (`Awaitility`) и контролируемый коммит.

#### 2. `@DataJpaTest` vs `@SpringBootTest`
* В **`@DataJpaTest`** транзакционность и откат включены **по умолчанию**. Тебе не нужно писать `@Transactional`, если ты тестируешь только репозитории.
* В **`@SpringBootTest`** (интеграционные тесты) транзакционность **не включена** по умолчанию. Если ты хочешь, чтобы тест откатывал изменения, тебе *нужно* явно добавить `@Transactional`.

#### 3. Использование `@Commit` или `@Rollback(false)`
Иногда нужно проверить, что данные действительно сохранились (например, при тестировании логики логов или аудита).
* Ты можешь использовать аннотацию `@Commit`, чтобы заставить тест зафиксировать изменения. 
* **Но будь осторожен:** Если ты сделал `@Commit`, следующий тест увидит эти данные и может упасть из `UniqueConstraintViolation`. В этом случае придется чистить базу вручную или использовать `@DirtiesContext`.

#### 4. Проблема «Dirty Context»
Если тест изменяет состояние не только БД, но и сам Spring Context (например, меняет `@MockBean` или настройки бинов), использование `@Transactional` не поможет очистить контекст. Потребуется `@DirtiesContext`, что сильно замедляет тесты.

---

### 💡 Best Practices
1. **Используй `@Transactional` везде, где это возможно**, чтобы обеспечить изоляцию тестов.
2. **Не полагайся на авто-откат при тестировании асинхронного кода.** Если видишь `@Async` — сразу думай о том, что транзакция теста не видна в новом потоке.
3. **Для интеграционных тестов с реальной БД (Testcontainers)** старайся держать транзакции короткими, но помни про риск загрязнения базы при использовании `@Commit`.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что произойдет, если тест упадет с ошибкой внутри `@Transactional`?**
**О:** Ничего страшного. Spring всё равно выполнит `rollback`. Тест пометится как Failed, но база останется чистой.

**В: Можно ли использовать `@Transactional` вместе с `Testcontainers`?**
**О:** Да. Это стандартная практика. Контейнер запускает реальную БД (например, Postgres), а Spring управляет транзакциями внутри этого контейнера так же, как в обычном приложении.

**В: Почему мой тест видит данные, а другой тест — нет, хотя оба помечены `@Transactional`?**
**О:** Скорее всего, один из тестов использует `@Commit` или ты тестируешь код, который работает в другом потоке (см. пункт про `@Async`). Также проверь, не используешь ли ты разные профили БД для разных тестов.

**В: Как протестировать метод с `@Transactional(propagation = Propagation.REQUIRES_NEW)`?**
**О:** Это сложно. В тесте с `@Transactional` создается внешняя транзакция. Метод с `REQUIRES_NEW` создаст *вторую* (вложенную) транзакцию. Если тест упадет, откатится только внешняя транзакция, а внутренняя может остаться зафиксированной (если она была завершена успешно). Для таких случаев лучше использовать интеграционные тесты без `@Transactional` на уровне тестового класса.

# 🗄️ Database State Management: Flyway & Liquibase в тестах

Когда мы говорим об интеграционных тестах (`@SpringBootTest`, `@DataJpaTest`), главный вопрос: **«В каком состоянии находится наша база данных?»**. Если схема базы не соответствует коду, тесты либо упадут сразу, либо (что хуже) пройдут успешно, но пропустят баг.

### 🎯 Суть процесса
Инструменты миграции (**Flyway** или **Liquibase**) — это "история изменений" твоей БД. В Spring Boot при запуске контекста для тестов эти инструменты автоматически сканируют папку с миграциями и применяют их к целевой базе (будь то H2, PostgreSQL в Docker или локальная база).

**Цель:** Гарантировать, что структура таблиц, индексов и ограничений (constraints) в тестах **идентична** той, что будет на Production.

---

### 🛠️ Как это работает (Workflow)
1.  **Запуск теста:** Spring Boot поднимает `ApplicationContext`.
2.  **Детекция:** Spring видит Flyway/Liquibase в classpath.
3.  **Применение:** Инструмент подключается к БД, проверяет таблицу истории (`flyway_schema_history` или `DATABASECHANGELOG`) и накатывает все недостающие скрипты.
4.  **Готовность:** Только после завершения всех миграций создаются JPA-сущности и репозитории. Тест начинает работу.

---

### ⚠️ Нюансы и "Подводные камни" (Senior Insights)

#### 1. Проблема "Разных диалектов" (H2 vs PostgreSQL)
Это классическая ошибка новичка. Ты пишешь миграцию на специфичном синтаксисе PostgreSQL (например, `JSONB` или `ENUM`), а в тестах используешь **H2**.
*   **Результат:** Тесты падают на этапе миграции, потому что H2 не понимает Postgres-синтаксис.
*   **Решение:** Используй **Testcontainers**. Твои тесты должны запускать реальный PostgreSQL в Docker. Это гарантирует 100% совместимость синтаксиса.

#### 2. Изоляция тестов и `@Transactional`
Многие используют `@Transactional` над тестовым методом, чтобы после теста данные откатились (Rollback).
*   **Нюанс:** `@Transactional` откатывает **DML** (INSERT, UPDATE, DELETE), но он **не откатывает DDL** (CREATE TABLE, ALTER TABLE). 
*   Если один тест создаст таблицу через миграцию (что странно, но бывает в динамических схемах), следующий тест об этом узнает. Всегда старайся держать схему стабильной.

#### 3. Проблема скорости (Migration Overhead)
Накатывать 200 миграций перед каждым тестовым классом — это очень медленно.
*   **Решение:** Spring кэширует контекст. Если ты не меняешь `@MockBean` или конфигурацию, контекст переиспользуется, и миграции не запускаются повторно. Но если ты используешь `@DirtyContext`, Spring пересоздает контекст и заново гоняет Flyway/Liquable. **Избегай `@DirtyContext` как огня.**

#### 4. Seed Data (Наполнение данными)
Миграции должны отвечать за **структуру** (DDL). Наполнение базы базовыми данными (пользователи, справочники) лучше делать отдельно.
*   **Инструменты:** Используй аннотацию `@Sql` в Spring для выполнения конкретных SQL-скриптов перед тестом или библиотеку **DBUnit**. Это позволяет держать миграции чистыми, а тесты — предсказуемыми.

---

### ❓ FAQ (Часто задаваемые вопросы)

**В: Можно ли отключить миграции в тестах для ускорения?**
**О:** Можно (`spring.flyway.enabled=false`), но **крайне не рекомендуется**. Ты рискуешь тестировать код на схеме, которой не существует в реальности. Если тесты проходят "на пустой базе", они бесполезны.

**В: Что делать, если миграция упала во время теста?**
**О:** Проверь таблицу истории (`flyway_schema_history`). Скорее всего, там висит запись со статусом `failed`. Тебе нужно либо почистить базу, либо вручную исправить состояние, иначе Flyway не пустит тебя дальше.

**В: Как тестировать миграции сами по себе?**
**О:** Это отдельный вид тестирования. Нужно создать тест, который запускает Testcontainer с чистой базой, применяет миграции и проверяет, что таблицы создались именно так, как ожидалось (например, через `JdbcTemplate`).

**В: Flyway или Liquibase — что выбрать для тестов?**
**О:** Для тестов — неважно. Главное, чтобы инструмент в тестах был тем же, что и на проде. Если на проде Liquibase, то и в тестах должен быть он. Это обеспечит идентичность поведения.

# 🧠 Шпаргалка: Code Coverage & Quality

Многие новички думают: *"Если у меня покрытие 100%, значит, багов нет"*. Это самая опасная ложь в разработке. **Coverage (покрытие)** — это метрика того, сколько строк кода было *выполнено* во время тестов. Она не говорит о том, насколько *правильно* работают тесты.

### 1. Основные метрики покрытия (Metrics)
Чтобы понимать реальную картину, нужно смотреть не на одну цифру, а на три:

*   **Line Coverage (Instruction Coverage):** Процент строк кода, которые были затронута тестами. Самая простая и "обманчивая" метрика.
*   **Branch Coverage (Decision Coverage):** **Самая важная метрика.** Она проверяет все ветвления (`if`, `switch`, `when`). Если у тебя есть `if (a && b)`, покрытие строк может быть 100%, но если ты не протестировал случай, когда `b` равно `false`, — твой тест бесполезен.
*   **Complexity Coverage:** Насколько покрыты сложные участки кода с высокой цикломатической сложностью.

### 2. Инструментарий (The Toolkit)

#### **JaCoCo (Java Code Coverage)**
Стандарт индустрии для Java/Spring.
*   **Как работает:** Во время выполнения тестов он "внедряется" в байт-код и ставит метки на пройденные инструкции.
*   **Что выдает:** HTML-отчеты, где красным подсвечены непройденные ветки `if/else`.
*   **Senior Tip:** Всегда настраивай исключения (exclusions) для Lombok-геттеров, сеттеров и DTO. Тестировать их — пустая трата ресурсов и "раздувание" покрытия ради красивых цифр.

#### **SonarQube / SonarCloud**
Это не про покрытие, а про **Static Code Analysis**.
*   **Зачем:** Он находит "Code Smells" (плохой дизайн), "Bugs" (ошибки в логике) и "Vulnerabilities" (дыры в безопасности).
*   **Quality Gates:** Это порог, который не дает тебе замержить код. Например: *"Если покрытие упало ниже 80% или появилось новое нарушение правил — билд падает"*.

#### **ArchUnit**
Инструмент для проверки архитектурного качества.
*   **Суть:** Ты пишешь тесты, которые проверяют правила архитектуры.
*   **Пример:** *"Классы из пакета `controller` не должны напрямую обращаться к пакету `repository`, только через `service`"*. Если кто-то нарушит правило — тест упадет.

### 3. Нюансы и "Подводные камни" (Senior Insights)

1.  **The False Sense of Security (Ложное чувство безопасности):** Можно написать тест, который просто вызывает метод, но не проверяет результат (`assert`). Покрытие будет 100%, а баги останутся. **Coverage $\neq$ Correctness.**
2.  **Cyclomatic Complexity (Цикломатическая сложность):** Если в методе слишком много `if`, `else`, `for` и `try-catch`, его сложно покрыть качественно. Если видишь, что метод раздулся — рефактори его, а не пиши еще 50 тестов.
3.  **Focus on Business Logic:** Не стремись к 100% покрытию всего проекта. Стремись к 100% покрытию **Domain/Service слоев**, где живет бизнес-логика. Контроллеры и конфигурации могут иметь меньший процент.

---

### ❓ FAQ (Частые вопросы на интервью)

**В: Что лучше: 100% Line Coverage или 70% Branch Coverage?**
**О:** Однозначно 70% Branch Coverage. Branch coverage заставляет тебя думать о логических путях и граничных условиях, что гораздо ценнее для стабильности системы.

**В: Как бороться с тем, что покрытие падает при добавлении нового кода?**
**О:** Используй **Quality Gates** в CI/CD (например, в GitLab CI или GitHub Actions). Настрой правило: "New Code Coverage must be > 80%". Это заставит разработчиков писать тесты сразу, а не пытаться догнать метрики потом.

**В: Нужно ли тестировать геттеры и сеттеры?**
**О:** Нет. Это "boilerplate" код. Если ты используешь Lombok, настрой JaCoCo так, чтобы он игнорировал сгенерированный код. Тестирование геттеров — это имитация деятельности.

**В: Что такое "Code Smell" в контексте качества?**
**О:** Это признаки того, что код, возможно, работает правильно, но его трудно поддерживать (например, слишком длинный метод, слишком много параметров или слишком глубокая вложенность). Хороший инструмент анализа кода (SonarQube) подсветит их тебе.

# 📊 Code Coverage & Quality: JaCoCo

### Что это вообще такое?
**JaCoCo (Java Code Coverage)** — это инструмент для анализа покрытия кода тестами. 

**Важное уточнение:** JaCoCo **не проверяет**, правильные ли у тебя тесты. Он не ищет баги. Он лишь отвечает на один вопрос: *"Какие строки/ветки твоего кода были затронуты (выполнены) во время прогона тестов, а какие — остались в темноте?"*

Представь, что твои тесты — это фонарик в темной комнате (твой код). JaCoCo показывает карту комнаты: где свет упал, а где всё еще непроверенная зона.

---

### 🛠 Как это работает (Under the hood)
JaCoCo использует **инструментацию байт-кода**. 
Когда ты запускаешь тесты, JaCoCo «подмешивает» в твой скомпилированный `.class` файл специальные инструкции. Эти инструкции работают как счетчики: каждый раз, когда JVM выполняет конкретную инструкцию или переходит по ветке `if`, счетчик инкрементируется. В конце прогона JaCoCo собирает эти данные и рисует отчет.

---

### 📈 Ключевые метрики (На что смотреть)
Не все цифры одинаково полезны. Senior смотрит не на «общую сумму», а на детали:

1.  **Instruction Coverage:** Самый низкий уровень. Сколько конкретных байт-команд было выполнено. Полезно, но слишком мелко для понимания бизнес-логики.
2.  **Line Coverage:** Насколько много строк кода было «затронуто». Это база, на которую все смотрят в первую очередь.
3.  **Branch Coverage (КРИТИЧНО!):** Самая важная метрика. Если у тебя есть `if (a && b)`, то выполнение одной строки может покрыть *линию*, но не покрыть все *ветки* (что `a` было true, а `dt` было false). **Низкий Branch Coverage = скрытые баги.**
4.  **Complexity (Cyclomatic Complexity):** JaCoCo помогает оценить сложность метода. Чем больше ветвлений, тем выше сложность и тем сложнее его протестировать на 100%.

---

### ⚙️ Интеграция в проект

#### Maven

### ⚠️ Нюансы и "Подводные камни" (Senior Insights)

1.  **Ловушка 100% покрытия:** Если ты видишь 100% Line Coverage, это **не значит**, что код работает правильно. Это значит лишь то, что код *выполнился*. Ты мог протестировать метод с `assert true`, и покрытие будет идеальным, а баг останется.
2.  **Тестирование Getter/Setter:** Не трать время на покрытие покрытия геттеров и сеттеров. Это "мусорное" покрытие, которое раздувает проценты, но не несет ценности. Настрой `exclusions` в JaCoCo.
3.  **Branch Coverage vs Line Coverage:** Всегда стремись к высокому **Branch Coverage**. Если у тебя покрыта линия с `if`, но ты не протестировал случай `else`, твой код потенциально сломан.
4.  **Thresholds (Пороги):** В CI/CD (Jenkins, GitLab CI) нужно настраивать **Check Failure**. Например: *"Если покрытие упало ниже 80% — билд падает"*. Это заставляет команду поддерживать качество кода.

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Что делать, если покрытие кода очень низкое?**
**О:** Не нужно писать тесты на каждый геттер. Сначала сосредоточься на **Critical Path** (бизнес-логике) и сложных ветвлениях (`if/else`, `switch`). Используй JaCoCo отчет, чтобы найти "белые пятна" в сложной логике.

**В: Можно ли использовать JaCoCo для поиска багов?**
**О:** Напрямую — нет. Но косвенно — да. Если JaCoCo показывает, что ветка с обработкой ошибки (`catch` блок) не покрыта, значит, ты не знаешь, как поведет себя система при падении базы данных.

**В: В чем разница между JaCoCo и Mutation Testing (например, PITest)?**
**О:** Это разные уровни. JaCoCo проверяет, **дошел** ли тест до строки. Mutation Testing проверяет, **изменит ли тест результат**, если мы специально сломаем код (заменим `>` на `<`). Mutation Testing — это "тесты для тестов".

**В: Как исключить автогенерируемый код (Lombok, MapStruct) из отчета?**
**О:** В конфигурации плагина (Maven/Gradle) нужно указать `excludes`. Для Lombok важно также настроить `lombok.config` с параметром `lombok.addLombokGeneratedAnnotation = true`, чтобы JaCoCo понимал, что этот код не нужно считать.

# 🛡️ Архитектурные тесты: ArchUnit

### Что это такое?
Представь, что ты — архитектор, который нарисовал идеальную схему приложения (слои, зависимости, правила). Но когда в команду приходят другие разработчики, они начинают «срезать углы»: вызывать репозиторий напрямую из контроллера или создавать циклическую зависимость между сервисами.

**ArchUnit** — это библиотека для JUnit, которая позволяет писать тесты на **правила архитектуры**. Это не проверка логики (как в Unit-тестах), это проверка того, что код *структурно* соответствует твоим правилам. Если кто-то нарушит правило — тест упадет, и билд в CI/CD не пройдет.

---

### Основные концепции (Что мы проверяем)

1.  **Layered Architecture (Слои):** Проверка того, что слои не пересекаются не по правилам. Например: *«Контроллеры могут знать о Сервисах, но не могут знать о Репозиториях»*.
2.  **Dependency Rules (Зависимости):** Запрет на использование определенных библиотек или классов в конкретных пакетах.
3.  **Naming Conventions (Именование):** Проверка того, что классы в пакете `service` заканчиваются на суффикс `Service`, а `repository` — на `Repository`.
4.  **Annotation Rules (Аннотации):** Например: *«Все методы в слое Service должны быть помечены `@Transactional`»* или *«Контроллеры должны использовать `@RestController`»*.

---

### Практический пример (Code Snippet)

Для работы тебе нужна зависимость `com.tngtech.archunit:archunit-junit5`.

```java
@AnalyzeClasses(packages = "com.myapp") // Указываем, где искать классы
class ArchitectureTest {

    // 1. Проверка слоев (Layered Architecture)
    @Test
    void layersShouldNotBeViolated() {
        layeredArchitecture()
            .consideringAllDependencies()
            .layer("Controller").definedBy("..controller..")
            .layer("Service").definedBy("..service..")
            .layer("Repository").definedBy("..repository..")
            
            .whereLayer("Controller").mayNotBeAccessedByAnyLayer() // Контроллер - входная точка
            .whereLayer("Service").mayOnlyBeAccessedByLayers("Controller") // Только контроллеры могут звать сервисы
            .whereLayer("Repository").mayOnlyBeAccessedByLayers("Service") // Только сервисы могут звать репозитории
            .check(layeredArchitecture());
    }

    // 2. Проверка именования (Naming Convention)
    @Test
    void servicesShouldHaveCorrectSuffix() {
        classes()
            .that().resideInAPackage("..service..")
            .should().haveSimpleNameEndingWith("Service")
            .check(new ClassFileImporter().withImportOption(ImportOption.DoNotFailOnErrors).importPackages("com.myapp"));
    }

    // 3. Запрет на использование конкретных библиотек (например, запрещаем System.out)
    @Test
    void noSystemOutInCode() {
        noClasses()
            .should().callMethod(System.class, "out")
            .check(new ClassFileImporter().importPackages("com.myapp"));
    }
}
```

---

### 💡 Нюансы от Senior-а (На что обратить внимание)

1.  **Проблема «Legacy» (Freezing ArchRule):** Если ты внедряешь ArchUnit в старый проект, где уже 100 нарушений, тесты упадут сразу. Не пытайся исправить всё разом. Используй `FreezingArchRule`. Она «замораживает» текущие ошибки и позволяет тестам проходить, но **предотвращает появление новых** нарушений.
2.  **Производительность:** ArchUnit сканирует байт-код. Если проект огромный, тесты могут идти долго. Всегда ограничивай область сканирования конкретным базовым пакетом (`packages = "com.myapp"`), а не всем `classpath`.
3.  **Не переборщи с жесткостью:** Слишком строгие правила (например, запрет на использование любого стороннего инструмента в сервисах) могут парализовать разработку. Правила должны помогать, а не мешать.
4.  **Сложность импорта:** При использовании `ClassFileImporter` важно правильно настроить опции импорта, чтобы ArchUnit не спотыкался о внешние библиотеки (Spring, Hibernate), которые он не должен проверять.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Чем ArchUnit отличается от обычных Unit-тестов?**
**О:** Unit-тесты проверяют *поведение* кода (что `sum(2,2)` вернет `4`). ArchUnit проверяет *структуру* кода (что класс `A` не импортирует класс `B`).

**В: Можно ли использовать ArchUnit для проверки циклической зависимости?**
**О:** Да. Это одна из его сильнейших сторон. Правило `slices().matching("..service.(*)..").should().beFreeOfCycles()` автоматически найдет все циклы между пакетами сервисов.

**В: Что делать, если правило архитектуры нарушено в 50 местах?**
**О:** Используй `FreezingArchRule`. Это позволит тебе зафиксировать текущее состояние как «допустимое» и начать контролировать качество кода с этого момента, исправляя старые ошибки постепенно.

**В: Где лучше всего запускать эти тесты?**
**О:** Обязательно в CI/CD пайплайне (Jenkins, GitHub Actions, GitLab CI). Если проверка архитектуры будет только на локальной машине разработчика, она не имеет смысла — её легко проигнорировать.

# 🧠 Шпаргалка: Test Data Management (TDM)

**Test Data Management** — это искусство подготовки, использования и очистки данных для тестов. Плохой TDM приводит к **Flaky Tests** (тестам, которые то проходят, то падают без видимых причин) и "загрязнению" базы данных.

---

### 1. Уровни управления данными

#### А. Unit Level (Изоляция)
Здесь мы не трогаем базу. Наша цель — максимально быстрые тесты.
*   **Manual Creation:** Просто `new User(...)`. Подходит только для очень простых объектов.
*   **Object Mother Pattern:** Создание специальных классов-фабрик, которые возвращают готовые объекты (например, `UserMother.createAdmin()`). Это скрывает сложность инициализации.
*   **Builder Pattern:** Использование Lombok `@Builder` для гибкой настройки только нужных полей в тесте.

#### Б. Integration Level (Реальные данные)
Здесь мы работаем с БД (H2, PostgreSQL через Testcontainers).
*   **`@Sql` Annotation:** Позволяет запускать SQL-скрипты перед или после теста. 
    * *Нюанс:* Не используй огромные `setup.sql`. Если в скрипте 100 строк, а тесту нужна одна запись — это плохой тест.
*   **Flyway/Liquibase:** Всегда запускай миграции при старте тестов. Тесты должны проверять актуальную схему, а не "замороженную" версию из прошлого года.

#### В. Dynamic Generation (Автоматизация)
Чтобы не писать тысячи строк кода для создания объектов.
*   **Java Faker / Datafaker:** Генерация реалистичных имен, адресов, email и т.д. Помогает найти баги с длинными строками или спецсимволами.
*   **Instancio (Must Have!):** Библиотека, которая автоматически заполняет всё дерево объекта случайными данными. Тебе нужно только переопределить то, что важно для теста.

---

### 2. Стратегии очистки (Data Isolation)
Самое важное: **Тест А не должен влиять на Тест Б.**

1.  **`@Transactional` Rollback:** Самый простой способ. Тест запускается в транзакции, которая откатывается в конце. 
    * *Минус:* Не работает, если твой код сам управляет транзакциями (`Propagation.REQUIRES_NEW`) или использует `JdbcTemplate` вне контекста.
2.  **Manual Cleanup:** Использование `@AfterEach` для удаления созданных сущностей. Дорого и сложно поддерживать.
3.  **Database Reset (Testcontainers):** Полная очистка таблиц или перезапуск контейнера. Самый надежный, но медленный способ.

### 3. Senior Insights: Нюансы и "Подводные камни"

*   **Избегай Hardcoded IDs:** Никогда не пиши `assertEquals(1, user.getId())`. Если в базе уже есть данные, ID будет другим. Всегда бери ID из созданного объекта.
*   **Проблема "Магических данных":** Если ты используешь один и тот же `setup.sql` для всех тестов, изменение одного поля в этом скрипте сломает 500 тестов. **Делай данные максимально локальными для конкретного теста.**
*   **Deterministic Randomness:** Если используешь Faker, старайся фиксировать **Seed** (зерно). Это позволит воспроизвести падение теста, если он упал на "неудачном" случайном имени.
*   **Data Pollution:** Если тесты запускаются параллельно, `@Transactional` может не спасти. В этом случае используй уникальные префиксы для данных (например, `username = "user_" + UUID.randomUUID()`).

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что лучше: SQL-скрипты или Object Mother?**
**О:** Зависит от уровня. Для Unit-тестов — только Object Mother/Builder. Для Integration-тестов — SQL для структуры и базовых справочников, а сложные бизнес-объекты лучше создавать через код (Java), чтобы тесты были типизированными и их было легче рефакторить.

**В: Как протестировать метод, который использует `@Transactional(propagation = Propagation.REQUIRES_NEW)`?**
**О:** Аннотация `@Transactional` в самом тесте не поможет, так как новая транзакция создаст отдельную сессию, и изменения не откатятся вместе с тестом. Здесь нужно использовать ручную очистку базы или пересоздавать контейнер.

**В: Почему использование `Instancio` может быть опасным?**
**О:** Если библиотека заполнит поле, которое критично для логики (например, `status = "DELETED"`), тест упадет с непонятной ошибкой. Всегда явно переопределяй ключевые поля в `Instancio`.
