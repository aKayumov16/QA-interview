# 🚀 Тема 1: Что такое TestNG?

### 📖 Простое определение
**TestNG (Test Next Generation)** — это мощный фреймворк для тестирования на языке Java. Если JUnit — это «базовый набор инструментов», то TestNG — это «профессиональная мастерская». 

Он был создан специально, чтобы расширить возможности классических фреймворков (типа JUnit) и дать автоматизатору инструменты для управления сложными сценариями: зависимостями, группами тестов, параллельным запуском и параметризацией.

### 🛠 Ключевые возможности (Core Features)
Чтобы понимать мощь TestNG, нужно знать его «столпы»:

1.  **Аннотации (Annotations):** Это «команды» для движка. С их помощью мы говорим: «этот метод — тест», «этот выполнится перед всеми тестами», «этот — после каждого».
2.  **Группировка (Groups):** Ты можешь пометить тесты метками `@Test(groups = {"smoke", "regression"})`. Это позволяет запускать не всё подряд, а только конкретные наборы.
3.  **Зависимости (Dependencies):** Позволяет выстроить цепочку: «Не запускай Тест Б, если Тест А упал». Это критично для сквозных (E2E) сценариев.
4.  **Data-Driven Testing (DDT):** С помощью `@DataProvider` один и тот же тест можно запустить 100 раз с разными наборами данных (логины, пароли, ссылки) без дублирования кода.
5.  **Параллельное выполнение:** TestNG умеет запускать тесты в разных потоках одновременно через настройки в `testng.xml`, что колоссально экономит время в CI/CD.
6.  **Конфигурация через XML:** Весь процесс (какие классы брать, какие группы включать, сколько потоков использовать) описывается в одном файле `testng.xml`. Это «пульт управления» твоим прогоном.

### 💡 Нюансы от Senior-а
*   **TestNG — это не инструмент для Assert'ов.** Многие новички путают: TestNG управляет *логикой выполнения*, а проверки (прошел тест или нет) делает библиотека **AssertJ** или стандартный **JUnit/TestNG Assert**. Не забивай логику проверок внутри конфигурационных методов.
*   **Зависимости — это палка о двух концах.** Если ты создашь слишком длинную цепочку `dependsOnMethods`, один упавший тест «положит» всю твою тестовую сессию. Это делает тесты хрупкими (brittle). Используй зависимости только там, где без предыдущего шага следующий физически невозможен.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем главное отличие TestNG от JUnit?**
**О:** Основное отличие в гибкости управления. TestNG из коробки поддерживает группы, зависимости между методами и гораздо более продвинутую параметризацию через XML и DataProvider. JUnit 4/5 ближе к классическому Unit-тестированию, а TestNG заточен под интеграционное и UI-тестирование (Selenium/Appium).

**В: Можно ли в TestNG запускать тесты параллельно?**
**О:** Да, это одна из его сильнейших сторон. Это настраивается в файле `testng.xml` через атрибуты `parallel` (может быть `methods`, `tests` или `classes`) и `thread-count`.

**В: Что произойдет с тестом, который зависит от упавшего теста (`dependsOnMethods`)?**
**О:** По умолчанию зависимый тест будет помечен как **SKIPPED** (пропущен). Он даже не начнет выполняться. Это защищает нас от ложных результатов, когда мы пытаемся тестировать функционал, чей фундамент уже разрушен.

**В: Зачем нужен `testng.xml`? Можно ли обойтись без него?**
**О:** Можно запускать тесты по одному через IDE, но в реальной автоматизации `testng.xml` — это стандарт. Он позволяет группировать классы, настраивать параллелизм и управлять параметрами без изменения самого Java-кода. Это разделение конфигурации и кода.

# 🛠 Тема: Настройка окружения (Environment Setup)

Для работы с TestNG недостаточно просто скачать `.jar` файл. Современный стандарт — это управление зависимостями через сборщики (**Maven** или **Gradle**) и правильная структура проекта.

### 1. Фундамент: JDK
TestNG работает на Java. Тебе нужен **JDK (Java Development Kit)**. 
*   **Senior Tip:** Всегда используй LTS-версии (Long Term Support), например, **Java 11** или **Java 17**. Избегай слишком новых версий, если твой проект не требует специфических фич, так как это может вызвать конфликты с плагинами сборщиков.

### 2. Сердце проекта: Maven (рекомендуемый стандарт)
Мы не подключаем библиотеки вручную. Мы используем `pom.xml`. Это позволяет другим разработчикам развернуть проект одной командой.

**Что нужно добавить в `pom.xml`:**

```xml
<dependencies>
    <!-- Сама библиотека TestNG -->
    <dependency>
        <groupId>org.testng</groupId>
        <artifactId>testng</artifactId>
        <version>7.8.0</version> <!-- Всегда проверяй актуальную версию на Maven Central -->
        <scope>test</scope>      <!-- Важный нюанс: scope test означает, что библиотека не попадет в итоговый продукт (JAR/WAR) -->
    </dependency>
</dependencies>

<build>
    <plugins>
        <!-- Плагин для запуска тестов через Maven (обязательно!) -->
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-surefire-plugin</artifactId>
            <version>3.1.2</version>
            <configuration>
                <suiteXmlFiles>
                    <!-- Указываем путь к нашему конфигурационному файлу -->
                    <suiteXmlFile>testng.xml</suiteXmlFile>
                </suiteXmlFiles>
            </configuration>
        </plugin>
    </plugins>
</build>
```

### 3. Структура проекта (Standard Maven Layout)
Никогда не сваливай всё в одну кучу. Соблюдай иерархию, иначе автоматизация в Jenkins/GitLab будет "ломаться":

*   `src/main/java` — основной код приложения (если ты тестируешь API или библиотеку).
*   `src/test/java` — **Здесь живут твои тесты.**
*   `src/test/resources` — Здесь лежат конфиги, `.properties`, `.json`, `testng.xml`.

### 4. Конфигурация запуска: `testng.xml`
Это "пульт управления" твоими тестами. Создай его в корне проекта или в `src/test/resources`. Без него TestNG будет просто запускать все классы подряд, что неудобно для больших проектов.

```xml
<!DOCTYPE suite SYSTEM "https://testng.org/testng-1.0.dtd">
<suite name="Main Suite">
    <test name="Regression Tests">
        <classes>
            <class name="com.example.tests.LoginTest"/>
        </classes>
    </test>
</suite>
```

1.  **Scope `test`**: Всегда ставь `<scope>test</scope>` для TestNG. Зачем тащить тестовый фреймворк в продакшн-сборку приложения? Это раздувает размер артефакта и создает дыры в безопасности.
2.  **Maven Surefire Plugin**: Если ты не настроишь этот плагин в `pom.xml`, команда `mvn test` может просто проигнорировать твой `testng.xml` и запустить всё, что найдет, или вообще ничего не запустить.

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем разница между подключением библиотеки через Maven и скачиванием JAR вручную?**
**О:** Maven управляет транзитивными зависимостями. Если TestNG потребует другую библиотеку для работы, Maven скачает её сам. При ручном подключении тебе придется искать и подключать каждую "под-библиотеку" самостоятельно (Dependency Hell).

**В: Зачем нужен `maven-surefire-plugin`?**
**О:** Это плагин, который отвечает за выполнение тестов во время фазы `test` в жизненном цикле Maven. Именно он умеет читать `testng.xml` и запускать тесты в правильном порядке, а также генерировать отчеты.

**В: Что произойдет, если я не укажу `<scope>test</scope>`?**
**О:** Библиотека TestNG будет включена в classpath основного приложения. Это плохая практика (bad practice), так как тестовый код и зависимости становятся частью рабочего продукта.

# 📝 Шпаргалка: Структура тестового класса в TestNG

Тестовый класс в TestNG — это не просто набор методов с аннотацией `@Test`. Это **управляемая среда**, где каждый элемент имеет свой жизненный цикл и область видимости (scope).

### 1. Анатомия класса (Основные компоненты)

Любой грамотно написанный тестовый класс состоит из четырех слоев:

#### А. Слой конфигурации (Setup/Teardown)
Это методы, которые подготавливают среду перед тестом и очищают её после.
*   **`@Before...`**: Методы инициализации (запуск браузера, создание базы данных, логин).
*   **`@After...`**: Методы очистки (закрытие браузера, удаление созданных пользователей, логгирование результатов).

#### Б. Слой логики (The Tests)
Это методы, помеченные аннотацией **`@Test`**. Они содержат саму проверку: шаги (Steps) и утверждения (Assertions).

#### В. Слой данных (Data Providers/Parameters)
Методы или внешние параметры, которые «впрыскивают» данные в ваши тесты, чтобы один и тот же код мог протестировать разные сценарии.

#### Г. Слой метаданных (Metadata)
Параметры внутри аннотаций: `priority`, `groups`, `description`, `enabled`, `dependsOnMethods`. Они определяют *как* и *когда* будет выполнен тест, не меняя его внутреннюю логику.

---

### 2. Визуальная схема жизненного цикла
Представь это как матрешку. Порядок выполнения (от внешнего к внутреннему):
1.  `@BeforeSuite` (Настройка всего проекта)
2.  `@BeforeTest` (Настройка конкретного `<test>` блока из XML)
*   `@BeforeClass` (Настройка текущего класса)
    *   `@BeforeMethod` (Подготовка перед каждым `@Test`)
        *   **`@Test`** $\leftarrow$ **САМ ТЕСТ**
    *   `@AfterMethod` (Очистка после каждого `@Test`)
*   `@AfterClass` (Завершение текущего класса)
2.  `@AfterTest` ...
1.  `@AfterSuite` ...

---

### 3. Senior-советы: Нюансы и Best Practices

*   **Принцип BaseTest:** Никогда не пиши `WebDriver driver = new ChromeDriver()` прямо в тестовом классе. Создай родительский класс `BaseTest`, вынеси туда `@BeforeMethod` и `@AfterMethod`. Тестовые классы должны быть "тонкими" — только логика тестов.
*   **Атомарность:** Один метод `@Test` = один сценарий проверки. Не пытайся запихнуть регистрацию, поиск и покупку в один метод. Если тест упадет на поиске, ты не узнаешь, работает ли корзина.
*   **Независимость (Statelessness):** Тесты не должны зависеть от данных, оставленных предыдущим тестом. Если Тест №2 требует, чтобы Тест №1 создал пользователя — это плохая структура. Используй `@BeforeMethod` для создания нужного состояния.
*   **Использование `description`:** Всегда пиши понятный `description` в аннотации `@Test`. Когда отчет упадет в Jenkins, ты сразу увидишь суть проблемы, не открывая код.

---

### 4. Пример "Эталонного" класса

```java
import org.testng.annotations.*;
import org.testng.Assert;

public class UserProfileTest extends BaseTest { // Наследуемся от базового класса

    @Test(groups = {"regression", "smoke"}, 
          description = "Проверка корректности отображения имени пользователя",
          priority = 1)
    public void testUserNameDisplay() {
        // Логика теста: только шаги и проверки
        String actualName = "John Doe"; 
        Assert.assertEquals(actualName, "John Doe", "Имя пользователя не совпадает!");
    }

    @Test(groups = {"regression"}, 
          dependsOnMethods = {"testUserNameDisplay"},
          description = "Проверка возможности смены аватара")
    public void testAvatarChange() {
        // Этот тест запустится только если первый прошел успешно
        System.out.println("Меняем аватар...");
    }
}
```

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что будет, если в `@BeforeMethod` произойдет ошибка?**
**О:** Текущий метод `@Test` и все последующие методы в этом классе будут помечены как **SKIPPED** (пропущены). TestNG не будет пытаться запускать тесты, если среда не подготовлена.

**В: Можно ли использовать один и тот же класс для разных групп тестов?**
**О:** Да. Благодаря аннотации `groups`, ты можешь запускать только часть методов из этого класса через `testng.xml`.

**В: В чем разница между `@BeforeClass` и `@BeforeMethod` в плане производительности?**
**О:** Если у тебя 100 тестов, `@BeforeClass` выполнится **1 раз**, а `@BeforeMethod` — **100 раз**. Если внутри `BeforeMethod` тяжелая операция (например, очистка БД), это сильно замедлит твой прогон. Используй `@BeforeClass` для тяжелых, но стабильных операций.

**В: Зачем нужен `dependsOnMethods`, если можно просто поставить высокий `priority`?**
**О:** `priority` — это лишь *желаемый* порядок. Если тест с низким приоритетом упадет, тест с высоким все равно попытается запуститься. `dependsOnMethods` создает жесткую связь: если зависимый тест упал, следующий **автоматически пропустится**.

# 🧠 Шпаргалка: Жизненный цикл аннотаций в TestNG

Жизненный цикл (Lifecycle) — это строгий порядок, в котором TestNG вызывает методы, помеченные аннотациями. Если ты перепутаешь порядок или область видимости, тесты либо не запустятся, либо будут зависеть от «грязного» состояния предыдущих тестов.

### 🏗 Иерархия выполнения (от глобального к локальному)

Представь матрешку: самая большая — `Suite`, самая маленькая — `Method`.

| Аннотация | Уровень (Scope) | Когда вызывается? | Типичный кейс использования |
| :---/---: | :--- | :--- | :--- |
| **`@BeforeSuite`** | **Suite** (Весь XML файл) | Один раз перед началом выполнения всего набора тестов. | Инициализация глобальных отчетов, подключение к БД, настройка логгера. |
| **`@AfterSuite`** | **Suite** | Один раз после завершения всех тестов в Suite. | Закрытие соединений с БД, генерация финального отчета. |
| **`@BeforeTest`** | **Test** (Тег `<test>` в XML) | Перед выполнением блока `<test>` из `testng.xml`. | Настройка конфигурации для конкретной группы тестов (например, выбор браузера). |
| **`@AfterTest`** | **Test** | После завершения блока `<test>`. | Очистка ресурсов, специфичных для этого блока тестов. |
| **`@BeforeClass`** | **Class** | Перед первым методом в текущем классе. | Инициализация WebDriver, создание объекта страницы (Page Object). |
| ** `@AfterClass`** | **Class** | После последнего метода в текущем классе. | `driver.quit()`, очистка кэша браузера. |
| **`@BeforeMethod`**| **Method** | Перед **каждым** методом `@Test`. | Переход на URL, очистка Cookies, логин в систему. |
| **`@AfterMethod`** | **Method** | После **каждого** метода `@Test`. | Снятие скриншота при падении, логгирование результата. |
| **`@Test`** | **Core** | Сама логика теста. | Проверка бизнес-логики (Asserts). |

---

### ⚠️ Senior Nuances (Тонкие моменты)

1.  **Ловушка `@BeforeTest` vs `@BeforeClass`**: Это самая частая ошибка.
    *   `@BeforeTest` относится к тегу `<test>` в твоем `testng.xml`. Если у тебя в XML один блок `<test>`, то этот метод сработает всего один раз.
    *   `@BeforeClass` сработает для каждого класса, который входит в этот `<test>`.
    *   *Запомни:* Если ты инициализируешь драйвер в `@BeforeTest`, а потом запускаешь два разных класса в одном `<test>`, второй класс может упасть, так как драйвер не пересоздастся.

2.  **Принцип "Clean Slate" (Чистый лист)**:
    *   Всегда старайся делать `@BeforeMethod` максимально независимым. Хороший тест — это тест, который можно запустить один в середине прогона, и он не упадет из-за того, что предыдущий тест не удалил корзину или не разлогинился.

3.  **Зависимость от успеха**:
    *   Если `@BeforeMethod` завершился с ошибкой (Exception), сам метод `@Test` **не запустится**. TestNG пометит его как `SKIPPED`. Это защищает нас от бессмысленных тестов на «сломанной» среде.

4.  **Обработка ошибок в Cleanup**:
    *   Всегда пиши `@After...` методы так, чтобы они не падали, если объект (например, `driver`) не был инициализирован. Используй проверки на `null`.

### ❓ FAQ (Часто задаваемые вопросы)

**В: Что будет, если я забуду добавить `@AfterMethod` для очистки данных?**
**О:** Тесты станут "загрязненными" (Flaky). Следующий тест может начать работу с активной сессией или заполненной формой, что приведет к непредсказуемым результатам. Это классический пример "Side Effects".

**В: Можно ли использовать `@BeforeSuite` для инициализации WebDriver?**
**О:** Технически — да, но архитектурно — **плохо**. Если ты создашь один драйвер на всю Suite, тесты нельзя будет запускать параллельно (один поток будет перехватывать управление у другого). Драйвер должен жить на уровне `@BeforeClass` или `@BeforeMethod`.

**В: В каком порядке выполнятся методы, если в классе есть и `@BeforeClass`, и `@BeforeMethod`?**
**О:** Сначала выполнится `@BeforeClass` (один раз), затем по цепочке: `@BeforeMethod` $\to$ `@Test` $\to$ `@AfterMethod`. И так для каждого метода класса.

**В: Если один из методов в `@BeforeSuite` упадет, запустятся ли остальные тесты?**
**О:** Нет. Если критическая настройка на уровне Suite не прошла, TestNG сочтет, что среда не готова, и пропустит (skip) или остановит выполнение всей Suite.

# 📌 Тема: Приоритеты в TestNG (`priority`)

### 💡 Суть простыми словами
По умолчанию TestNG запускает тесты так, как ему удобно (часто это порядок, в котором методы описаны в классе, но полагаться на это — плохая идея). 
**Приоритет** — это способ сказать фреймворку: «Сначала сделай вот это, а потом — вот то». Это числовой параметр внутри аннотации `@Test`.

### 🛠 Как это работает (Правила)
1.  **Чем меньше число, тем выше приоритет.** Тест с `priority = -1` выполнится раньше, чем тест с `test = 0`, а тот — раньше, чем `priority = 1`.
2.  **Значение по умолчанию — 0.** Если ты не указал приоритет, TestNG считает, что он равен `0`.
3.  **Отрицательные числа работают.** Ты можешь использовать `-1`, `-10` и так далее, чтобы вынести критически важные проверки в самое начало.

### 💻 Пример кода

```java
import org.testng.annotations.Test;

public class PriorityExample {

    @Test(priority = 2)
    public void testSecond() {
        System.out.println("Выполняю второй тест (priority = 2)");
    }

    @Test(priority = -1)
    public void testFirst() {
        System.out.println("Выполняю первый тест (самый важный, priority = -1)");
    }

    @Test // По умолчанию priority = 0
    public void testDefault() {
        System.out.println("Выполняю тест с дефолтным приоритетом (priority = 0)");
    }

    @Test(priority = 1)
    public void testThird() {
        System.out.println("Выполняю третий тест (priority = 1)");
    }
}
```

**Порядок вывода в консоль:**
1. `testFirst` (т.к. -1 — самое маленькое число)
2. `testDefault` (т.к. 0 — следующее по величине)
3. `testThird` (т.к. 1)
4. `testSecond` (т.к. 2)

---

### ⚠️ Нюансы и "подводные камни" (Senior Level)

1.  **Ловушка дефолтного значения:** Если ты назначил приоритеты только некоторым тестам, а остальным — нет, все "беспризорные" тесты получат `priority = 0`. Это значит, что они могут перемешаться с твоим важным тестом, у которого тоже `priority = 0`. 
    *   *Совет:* Если начинаешь задавать приоритеты, старайся делать это системно.

2.  **Приоритет vs Зависимости (`dependsOnMethods`):** Это критический момент. Если у тебя есть Тест Б, который зависит от Теста А, но ты явно прописал Тесту Б более высокий приоритет (например, `priority = -1`), **TestNG все равно сначала запустит Тест А**. 
    *   *Правило:* Зависимости (`dependsOn`) всегда имеют высший приоритет над параметром `priority`. Сначала строится граф зависимостей, а потом внутри этого графа выстраивается очередь по приоритетам.

3.  **Не используй приоритеты для бизнес-логики:** Приоритеты — это инструмент управления *порядком выполнения в рамках одного прогона*, а не замена архитектуре тестов. Если один тест не может работать без другого, используй `dependsOnMethods`. Используй `priority` только для того, чтобы ускорить получение фидбека (сначала быстрые и важные проверки).

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что будет, если у двух тестов одинаковый `priority`?**
**О:** TestNG не гарантирует строгий порядок между ними. Они будут запущены в произвольном порядке (обычно в зависимости от того, как JVM загрузила классы или в каком порядке они идут в файле).

**В: Можно ли использовать отрицательные значения для приоритета?**
**О:** Да, и это отличная практика для тестов, которые должны выполняться в самом начале цепочки (например, Smoke-тесты или Setup-проверки).

**В: Что важнее: `priority` или `dependsOnMethods`?**
**О:** `dependsOnMethods`. Если тест зависит от другого, TestNG сначала разрешит зависимость, и только потом будет смотреть на числовое значение приоритета.

# 🧠 Тема: Зависимости в TestNG (`dependsOnMethods` и `dependsOnGroups`)

### 📌 Суть концепции
В автоматизации тесты редко живут в вакууме. Часто выполнение второго теста невозможно, если первый не создал нужные данные (например, нельзя «Добавить товар в корзину», пока не выполнен тест «Авторизация»). 

**Зависимости (Dependencies)** — это механизм, который говорит TestNG: *"Не запускай этот тест, пока не завершится вот этот другой тест. И если тот тест упал — этот тоже не запускай (по умолчанию)"*.

---

### 1. `dependsOnMethods` (Зависимость от методов)
Используется, когда у тебя есть четкая цепочка внутри одного класса.

* **Как работает:** Ты перечисляешь имена методов, от которых зависит текущий тест.
* **Когда использовать:** Для простых сценариев «шаг за шагом» в рамках одной фичи.

**Пример кода:**
```java
public class OrderTest {

    @Test
    public void login() {
        System.out.println("Logging in...");
        // Логика логина
    }

    @Test(dependsOnMethods = {"login"})
    public void addToCart() {
        System.out.println("Adding item to cart...");
        // Этот тест не запустится, если login упадет
    }

    @Test(dependsOnMethods = {"addToCart"})
    public void checkout() {
        System.out.println("Checking out...");
        // Этот тест зависит от цепочки выше
    }
}
```

---

### 2. `dependsOnGroups` (Зависимость от групп)
Более мощный инструмент. Позволяет связать тесты из разных классов через логические группы.

* **Как работает:** Тест ждет завершения всех тестов, входящих в указанную группу.
* **Когда использовать:** Когда у тебя есть глобальные пререквизиты (например, группа `smoke` или `setup`).

**При passage кода:**
```java
public class UserTest {
    @Test(groups = "setup")
    public void createDatabase() {
        System.out.println("DB Created");
    }
}

public class FeatureTest {
    @Test(groups = "feature", dependsOnGroups = {"setup"})
    public void testFeature() {
        System.out.println("Testing feature with ready DB");
    }
}
```

---

### ⚠️ Senior Nuances (То, о чем не пишут в учебниках)

1.  **Эффект домино (Cascading Failure):** Это главная проблема. Если упал самый первый тест в цепочке зависимостей, все последующие тесты получат статус `SKIPPED`. В отчете ты увидишь кучу пропусков. Это может скрыть реальные проблемы в других тестах.
2.  **`alwaysRun = true` — твой спасательный круг:** Если ты хочешь, чтобы тест выполнился **несмотря на то**, что его зависимость упала (например, тест очистки данных), обязательно добавь этот параметр.
    *   `@Test(dependsOnMethods = {"login"}, alwaysRun = true)`
3.  **Зависимости vs Priority:** 
    *   `priority` — это просто **порядок** запуска (как очередь в магазине).
    *   `dependsOn...` — это **логическая связь** (ты не можешь купить хлеб, пока не оплатил его). Если `priority` не сработает, тест всё равно запустится. Если `dependsOn` не сработает — тест будет пропущен.
4.  **Проблема параллелизации:** Использование жестких зависимостей (`dependsOnMethods`) убивает смысл параллельного запуска тестов в разных потоках, так как ты создаешь линейную очередь.

---

### ❓ FAQ (Подготовка к собеседованию)

**В: Что произойдет с тестом, если его зависимый метод завершился со статусом `FAIL`?**
**О:** По умолчанию тест будет помечен как `SKIPPED`. Он даже не начнет выполнение.

**В: В чем разница между `dependsOnMethods` и `dependsOnGroups`?**
**О:** `dependsOnMethods` привязывает тест к конкретным именам методов (узкая связь). `dependsOnGroups` привязывает тест к логическому набору тестов (гибкая связь, позволяет объединять разные классы).

**В: Как запустить тест, даже если его зависимость упала?**
**О:** Нужно использовать атрибут `alwaysRun = true` в аннотации `@Test`.

**В: Почему использование `dependsOnMethods` считается плохой практикой при масштабировании автотестов?**
**О:** Потому de создается "хрупкая" архитектура. Малейшее изменение имени метода или падение одного базового теста вызывает лавинообразный пропуск всех связанных тестов, что затрудняет локализацию реальных багов и мешает параллельному выполнению.

# 📚 Тема: Группировка тестов (Groups) в TestNG

**Группировка** — это механизм "тегирования" ваших тестов. Вместо того чтобы запускать весь огромный набор тестов, вы помечаете их метками (например, `smoke`, `regression`, `api`, `ui`) и управляете запуском через конфигурацию.

### 1. Как объявить группы в коде
Группы назначаются прямо в аннотации `@Test`. Тест может принадлежать одной, нескольким или вообще не иметь групп.

```java
@Test(groups = "smoke")
public void testLogin() { /* ... */ }

@Test(groups = {"regression", "ui"})
public void testCheckout() { /* ... */ }

@Test(groups = "api")
public void testGetUser() { /* ... */ }
```

### 2. Управление запуском через `testng.xml`
Это самый важный этап. Вы не меняете код, вы меняете «пульт управления» (XML-файл).

*   **Include (Включение):** Запускает только те тесты, которые помечены указанной группой.
*   **Exclude (Исключение):** Убирает из запуска тесты с определенной меткой.

```xml
<suite name="MySuite">
    <test name="SmokeTests">
        <groups>
            <run>
                <!-- Запустить только smoke -->
                <include name="smoke" />
                <!-- Но если тест помечен и как smoke, и как slow, исключить его -->
                <exclude name="slow" />
            </run>
        </groups>
        <classes>
            <class name="com.example.Tests" />
        </classes>
    </test>
</suite>
```

### 3. Продвинутые фишки (Senior Level)

#### А) Зависимости между группами (`dependsOnGroups`)
Вы можете сказать TestNG: "Не запускай группу `regression`, пока успешно не пройдет группа `smoke`".
```java
@Test(groups = "regression", dependsOnGroups = "smoke")
public void testCriticalFlow() { ... }
```
*Нюанс:* Если хоть один тест в группе `smoke` упадет, все тесты в `regression` будут помечены как **SKIPPED**.

#### Б) Конфигурация на уровне групп (`@BeforeGroups` / `@AfterGroups`)
Это не то же самое, что `@BeforeMethod`. Эти аннотации выполняются **один раз** перед началом выполнения группы или после завершения.
```java
@BeforeGroups("api")
public void setupApi() {
    System.out.println("Инициализация API клиента для всех API тестов");
}
```

---

### ⚠️ Нюансы и "Подводные камни" (Watch out!)

1.  **Логика OR vs AND:** Когда вы указываете несколько `include` в XML, TestNG работает по логике **OR**. Если тест входит хотя бы в одну из включенных групп — он будет запущен.
2.  **Приоритет Exclude:** Если тест попал под `include`, но одновременно попал и под `exclude`, **Exclude побеждает**. Тест не запустится. Это полезно, чтобы отсекать тяжелые тесты из быстрых прогонов.
    *   *Пример:* Тест в группах `{"smoke", "slow"}`. Если мы включили `smoke`, но исключили `slow` — тест **не запустится**.
3.  **Забытые группы:** Если вы используете `dependsOnGroups`, но забыли добавить саму зависимую группу в список `include` в XML, TestNG может либо пропустить тесты, либо выдать ошибку конфигурации. Всегда проверяйте, что цепочка групп "видна" запускальщику.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `@BeforeMethod` и `@BeforeGroups`?**
**О:** `@BeforeMethod` выполняется перед **каждым** тестом. `@BeforeGroups` выполняется **один раз** перед запуском первого теста, который принадлежит данной группе.

**В: Что произойдет, если тест принадлежит двум группам, одна из которых исключена в XML?**
**О:** Тест будет пропущен (Skipped/Not run). Исключение имеет высший приоритет над включением.

**В: Можно ли группировать не только методы `@Test`, но и классы?**
**О:** В TestNG группы назначаются именно методам `@Test`. Однако, вы можете создать класс, который содержит тесты с определенными группами, и управлять запуском классов через XML, но "тегирование" (группировка) происходит на уровне методов.

**В: Как реализовать запуск только "быстрых" тестов?**
**О:** Пометить все быстрые тесты группой `fast` и в `testng.xml` прописать `<include name="fast" />`. Все остальные тесты (long-running) должны иметь группу `slow` или не иметь групп вовсе, чтобы они не попали под фильтр.

# 🧠 Тема: Управление состоянием в TestNG

В TestNG «управление состоянием» — это контроль над тем, **как**, **в каком порядке** и **при каких условиях** будут выполняться твои тесты. Это инструменты для управления логическими связями между тестами.

### 1. Отключение тестов (`enabled = false`)
Самый простой способ «выключить» тест, не удаляя код.
*   **Как это работает:** Ты добавляешь параметр в аннотацию `@Test(enabled = false)`. Тест просто игнорируется раннером.
*   **Senior Tip:** Используй это только для временного отключения заведомо сломанных тестов (например, пока баг не пофикшен). Не превращай это в свалку забытого кода. Если тест не нужен — удаляй или закомментируй (но лучше через Git).

### 2. Зависимости (`dependsOnMethods` и `dependsOnGroups`)
Это создание цепочек: «Не запускай Тест Б, пока не прошел Тест А».

*   **`dependsOnMethods`**: Привязка одного метода к другому внутри одного класса.
    *   *Пример:* Сначала `login()`, потом `checkProfile()`.
*   **`dependsOnGroups`**: Более мощный инструмент. Привязка теста к результату целой группы тестов.
    *   *Пример:* Тесты в группе `checkout` не запустятся, если упали тесты из группы `auth`.

⚠️ **Главный нюанс (The Senior Warning):** Чрезмерное использование зависимостей делает твою тестовую базу **хрупкой**. Если один базовый тест падает, у тебя «краснеет» (fails) или пропускается (skips) вся цепочка. Это затрудняет локализацию реальных багов. Используй зависимости только там, где без предыдущего шага следующий физически невозможен (например, нельзя купить товар, если не создана сессия).

### 3. Флаг `alwaysRun = true`
Этот флаг — спасательный круг для методов конфигурации (`@AfterMethod`, `@AfterClass` и т.д.).

*   **Суть:** По умолчанию, если метод в цепочке зависимостей упал, все последующие методы (включая `@After...`) могут быть пропущены.
*   **Зачем это нужно:** Если твой тест упал на середине, тебе **обязательно** нужно очистить данные или закрыть браузер. Установка `alwaysRun = true` гарантирует, что метод очистки выполнится в любом случае, даже если основной тест провалился.

### 4. Тайм-ауты (`timeOut`)
Защита от «зависания» тестов.
*   **Как это работает:** `@Test(timeOut = 5000)`. Если метод выполняется дольше 5 секунд, TestNG принудительно прерывает его и помечает как Fail.
*   **Нюанс:** Будь осторожен с `timeOut` в сетевых тестах. Сеть может лагнуть, и ты получишь "flaky test" (нестабильный тест), который падает без реальной причины в коде.

---

### 📊 Итоговая шпаргалка по состояниям

| Параметр | Что делает | Когда использовать |
| :--- | :--- | :--- |
| `enabled = false` | Полностью выключает тест | Временная заглушка для бажных тестов |
| `dependsOnMethods` | Создает жесткую связь между методами | Для линейных сценариев (Step-by-step) |
| `dependsOnGroups` | Запускает тест только после успеха группы | Для архитектурных зависимостей (Auth $\rightarrow$ API) |
| `alwaysRun = true` | Выполняет метод независимо от успеха других | **Обязательно** для методов очистки данных/cleanup |
| `timeOut` | Прерывает тест по истечении времени | Защита от бесконечных циклов и зависаний |

### ❓ FAQ (Часто задаваемые вопросы на собеседовании)

**В: Что произойдет с зависимым тестом, если родительский тест упал?**
**О:** Зависимый тест перейдет в статус **SKIP** (пропущен). Он не будет считаться проваленным (Fail), он просто не будет запущен. Это ключевое отличие от обычного падения.

**В: В чем разница между `dependsOnMethods` и использованием `dependsOnGroups`?**
**О:** `dependsOnMethods` работает на уровне конкретных функций внутри класса, что удобно для простых сценариев. `dependsOnGroups` позволяет управлять высокоуровневой логикой (например, не запускать весь модуль "Payments", если упал модуль "Login"), что гораздо масштабируемее.

**В: Можно ли использовать `alwaysRun = true` в методах `@Before...`?**
**О:** Технически можно, но это редко имеет смысл. Смысл `alwaysRun` — гарантировать выполнение *завершающих* действий (cleanup) после того, как что-то пошло не так. В `@Before` метод и так должен отработать успешно, иначе тест даже не начнется.

**В: Как избежать "эффекта домино" (когда один упавший тест убивает всю Suite)?**
**О:** Не злоупотреблять `dependsOn...`. Старайся проектировать тесты так, чтобы они были **атомарными** и **изолированными**. Каждый тест должен иметь возможность запуститься сам по себе (например, за счет подготовки данных в `@BeforeMethod`).

# 📌 Шпаргалка: Параметризация через `testng.xml`

### 💡 Суть метода
Параметризация через XML — это способ вынести **конфигурационные данные** из Java-кода во внешний файл (`testng.xml`). 

**Главное правило Senior-разработчика:** Используй этот метод только для настроек **окружения** (URL, браузер, таймауты, порты). Никогда не используй его для передачи наборов тестовых данных (для этого есть `@DataProvider`).

---

### 🛠 Как это работает (Механика)

Процесс состоит из двух шагов: объявление в XML и прием в Java.

#### 1. Настройка в `testng.xml`
Мы используем тег `<parameter>`. Его можно разместить на уровне `<suite>` или `<test>`.

```xml
<suite name="MainSuite">
    <!-- Параметр доступен всем тестам в этой Suite -->
    <parameter name="browser" value="chrome" />
    <parameter name="timeout" value="30" />

    <test name="LoginTests">
        <!-- Этот параметр перекроет (override) значение для этого конкретного теста -->
        <parameter name="browser" value="firefox" />
        <classes>
            <class name="com.example.LoginTest" />
        </classes>
    </test>
</suite>
```

#### 2. Прием в Java-коде
Используем аннотацию `@Parameters`. Имена параметров должны **строго** совпадать с именами в XML.

```java
import org.testng.annotations.Parameters;
import org.testng.annotations.*;

public class LoginTest {

    @Parameters({"browser", "timeout"})
    @Test
    public void testLogin(String browserName, int timeout) {
        System.out.println("Запускаем браузер: " + browserName);
        System.out.println("Максимальное ожидание: " + timeout + " сек.");
    }
}
```

---

### 🧠 Важные нюансы (Senior Insights)

1.  **Иерархия и Scope (Область видимости):**
    *   Если параметр объявлен в `<suite>`, он «наследуется» всеми тестами внутри.
    *   Если ты объявляешь параметр с тем же именем в `<test>`, значение из `<test>` **перекрывает** значение из `<suite>`. Это позволяет запускать один и тот же набор тестов на разных браузерах, просто меняя XML.
2.  **Типизация:** 
    *   В XML всё является строкой (`String`). 
    *   Однако TestNG достаточно умен, чтобы автоматически привести тип (cast) к `int`, `boolean`, `double` и т.д., если ты указал соответствующий тип в аргументах метода Java.
3.  **Риск Missing Parameter:** 
    *   Если ты укажешь параметр в аннотации `@Parameters({"api_key"})`, но забудешь прописать его в `testng.xml` — TestNG выбросит `TestNGException` и тест даже не запустится. Это "fail-fast" поведение — оно полезно, так как сразу подсвечивает ошибку конфигурации.
4.  **Различие с @DataProvider:** 
    *   `@Parameters` — это **статичные** значения (одно значение на запуск теста).
    *   `@DataProvider` — это **динамические** данные (цикл из множества значений для одного и того же теста).

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: Что произойдет, если в методе указано 3 параметра, а в XML передано только 2?**
**О:** Тест упадет с ошибкой `TestNGException`. TestNG не может инициализировать метод, так как не хватает аргументов для заполнения сигнатуры метода.

**В: Можно ли передать сложный объект (например, экземпляр класса `User`) через XML?**
**О:** Нет. Через XML можно передавать только примитивы и строки. Для передачи сложных объектов используй `@DataProvider` или создай фабрику/конфигуратор, который прочитает простые параметры из XML и сам соберет объект.

**В: В чем разница между параметром в `<suite>` и в `<test>`?**
**О:** Параметр в `<suite>` — это глобальная настройка (например, `env=production`). Параметр в `<test>` — это локальная настройка для конкретной группы тестов (например, `browser=safari`), которая имеет приоритет над глобальной.

**В: Как сделать параметр необязательным?**
**О:** Напрямую через XML нельзя. Но можно использовать метод `@BeforeMethod` или `@BeforeClass`, чтобы прочитать параметры через `ITestContext` и задать значения по умолчанию, если параметр не найден. (Но лучше просто следить за чистотой своего XML).

# 🧠 Cheat Sheet: @DataProvider в TestNG

### 📌 Что это такое?
Если `@Test` — это сама проверка, то `@DataProvider` — это **фабрика данных**. Вместо того чтобы писать один тест и вручную менять в нем значения, ты создаешь «конвейер», который прогоняет один и тот же тест через разные наборы входных данных.

**Суть:** Один метод `@Test` + много наборов данных = Много итераций теста.

---

### 🛠 Базовый синтаксис
Чтобы магия сработала, нужны две вещи: метод с аннотацией `@DataProvider` и метод `@Test`, который ссылается на него по имени.

```java
public class DataProviderExample {

    // 1. Создаем фабрику данных
    @DataProvider(name = "userLoginData")
    public Object[][] getData() {
        return new Object[][] {
            {"admin", "pass123"}, // Итерация 1
            {"user_test", "qwerty"}, // Итерация 2
            {"guest", "guest_password"} // Итерация 3
        };
    }

    // 2. Используем данные в тесте
    @Test(dataProvider = "userLoginData")
    public void testLogin(String username, String password) {
        System.out.println("Testing login with: " + username + " | " + password);
        // Здесь твоя логика проверки
    }
}
```

---

### 🚀 Продвинутые сценарии (Уровень Senior)

#### 1. Разделение ответственности (Data Provider в другом классе)
В больших проектах нельзя хранить данные внутри тестового класса — это превратит его в «свалку». Мы выносим провайдер в отдельный класс. Для этого используй параметр `dataProviderClass`.

```java
// Класс с данными
public class TestDataFactory {
    @DataProvider(name = ✅ "externalData")
    public Object[][] getExternalData() {
        return new Object[][] { {"Data from another class"} };
    }
}

// Тестовый класс
public class RemoteTest {
    @Test(dataProvider = "externalData", dataProviderClass = TestDataFactory.class)
    public void testWithExternalProvider(String data) {
        System.out.println("Received: " + data);
    }
}
```

#### 2. Оптимизация памяти: `Iterator<Object[]>`
Если данных очень много (например, 10 000 строк из БД), создание огромного массива `Object[][]` сразу забьет всю оперативную память (**OutOfMemoryError**). 
**Senior-совет:** Используй `Iterator`. Он будет подгружать данные по одной строке по мере необходимости.

```java
@DataProvider(name = "largeScaleData")
public Iterator<Object[]> getLargeData() {
    List<Object[]> dataList = new ArrayList<>();
    // Представь, что здесь мы читаем файл или БД
    dataList.add(new Object[]{"row1"});
    dataList.add(new Object[]{"row2"});
    return dataList.iterator(); // Возвращаем итератор вместо массива
}
```

#### 3. Использование сложных объектов (POJO)
Не ограничивайся строками и числами. Ты можешь передавать целые объекты. Это делает тесты очень чистыми.

```java
@Test(dataProvider = "userProvider")
public void testUserPermissions(User user) { // Передаем объект User
    Assert.assertTrue(user.isAdmin());
}
```

---

### ⚠️ Нюансы и «подводные камни» (Pitfalls)

1.  **Соответствие типов:** Количество аргументов в методе `@Test` должно строго соответствовать количеству столбцов в массиве `Object[][]`. Если в массиве 3 элемента, а в методе 2 — тест упадет с ошибкой.
2.  **Имена провайдеров:** Если не указать `name` в `@DataProvider`, TestNG будет использовать имя самого метода. Всегда лучше задавать имя явно, чтобы избежать путаницы при рефакторинге.
3.  **Scope (Область видимости):** Помни, что если ты используешь `dataProviderClass`, этот класс должен быть доступен в classpath (публичный класс).

---

### ❓ FAQ (Часто задаваемые вопросы на собеседовании)

**В: В чем разница между `@Parameter` (из XML) и `@DataProvider`?**
**О:** `@Parameter` передает статичные значения из `testng.xml` один раз на весь запуск теста. `@DataProvider` позволяет запускать один и тот же тест многократно с разными данными в рамках одного прогона.

**В: Можно ли использовать `@DataProvider` для передачи данных из Excel?**
**О:** Да, это классический кейс. Внутри метода с `@DataProvider` ты вызываешь утилиту (например, Apache POI), которая читает Excel и трансформирует строки таблицы в `Object[][]`.

**В: Что произойдет, если один из наборов данных в `@DataProvider` вызовет ошибку?**
**О:** Тест упадет на этой конкретной итерации, но TestNG продолжит выполнение остальных итераций (если не настроены жесткие зависимости `dependsOnMethods`).

**В: Как сделать так, чтобы данные подтягивались динамически из базы данных?**
**О:** Внутри метода `@DataProvider` ты пишешь JDBC-код. Метод выполняет SQL-запрос, перебирает `ResultSet` и наполняет массив (или итератор) объектами для теста.

# 🧠 Шпаргалка: Внешние источники данных (External Data Sources)

### 🎯 Суть концепции
В автоматизации есть золотое правило: **Data-Driven Testing (DDT)**. Мы отделяем **логику теста** (как мы кликаем и проверяем) от **тестовых данных** (логин, пароль, артикул). Это позволяет запускать один и тот же тест с сотней разных комбинаций, не меняя ни строчки кода.

В TestNG "мостом" между внешним файлом и тестом всегда выступает `@DataProvider`. Сам TestNG не умеет читать Excel или JSON — он умеет только работать с массивом объектов `Object[][]`, который ему "скармликает провайдер".

---

### 🛠 Основные инструменты и форматы

#### 1. Properties Files (`.properties`)
*   **Для чего:** Глобальные настройки (URL среды, тайм-ауты, пути к логам).
*   **Плюсы:** Встроены в Java, максимально просто, стандарт индустрии для конфигов.
*   **Минусы:** Только плоские структуры (ключ=значение), нельзя хранить сложные списки или таблицы.

#### 2. CSV / TSV (Comma/Tab Separated Values)
*   **Для чего:** Простые таблицы с однотипными данными.
*   **Плюсы:** Легкость, читаемость, открывается любым редактором.
*   **Минусы:** Нет структуры, сложно передавать вложенные объекты.

#### 3. JSON
*   **Для чего:** Сложные, иерархические данные (например, структура API-запроса или профиль пользователя с адресом, списком заказов и т.д.).
*   **Плюсы:** Идеально для современных веб-приложений, поддерживает вложенность.
*   **Минусы:** Требует библиотек (Jackson или Gson) и парсинга.

#### 4. Excel (XLSX)
*   **Для чего:** Когда данные готовят бизнес-аналитики или мануальные тестировщики.
*   **Плюсы:** Привычно всем, мощный инструмент для подготовки огромных массивов данных.

### 🚀 Senior Tips (Нюансы, о которых молчат в туториалах)

1.  **Не читай файл внутри `@Test`!**
    *   *Ошибка:* Начинать парсинг Excel прямо в методе теста.
    *   *Как надо:* Файл должен читаться один раз в `@DataProvider`. Тест должен получать уже готовый, "чистый" объект или массив строк.

2.  **Используй POJO (Plain Old Java Object).**
    *   Вместо того чтобы передавать в тест `String[]` (где ты по индексу `[0]` — это имя, а `[1]` — возраст), создай класс `User`. Пусть `@DataProvider` возвращает массив объектов `User[]`. Это сделает твой код типобезопасным и понятным.

3.  **Проблема памяти (Memory Leak).**
    *   Если в Excel 10,000 строк, Apache POI может "съесть" всю оперативку. Для гигантских файлов используй потоковое чтение (Streaming API / Event API), а не загрузку всей книги в память.

4.  **Разделяй Environment и Test Data.**
    *   URL базы данных — это *Configuration* (Properties).
    *   Список логинов для проверки — это *Test Data* (JSON/Excel).
    *   Не смешивай их в одном файле.

**В: В чем разница между `@Parameters` и `@DataProvider`?**
**О:** `@Parameters` берет значения из `testng.xml`. Это статичные данные, которые известны до запуска теста (например, браузер). `@DataProvider` — это динамика. Он может генерировать или вычитывать бесконечное количество комбинаций из внешних источников прямо в процессе выполнения.

**В: Что делать, если формат данных в Excel изменился (добавили колонку)?**
**О:** Если ты используешь жесткую привязку по индексам (`row.getCell(3)`), тест упадет. Senior-подход: искать колонку по её **заголовку** (первая строка). Это делает твой фреймворк устойчивым к изменениям.

**В: Как протестировать сценарий, если данных слишком много и они не влезают в память?**
**О:** Нужно использовать стратегию итератора или стриминга. Мы не загружаем весь файл целиком, а читаем его построчно, передавая в `@DataProvider` только текущую порцию данных (batching).

# 📌 Cheat Sheet: Hard Assertions (TestNG)

### 🛠 Что это такое?
**Hard Assertion** (Жесткое утверждение) — это проверка, которая при невыполнении условия **немедленно прерывает** выполнение текущего тестового метода (`@Test`). 

Представь себе сигнализацию в машине: если датчик фиксирует взлом, система не просто «записывает лог», она мгновенно включает сирену и блокирует двери. Всё, что было написано в коде после этой строки, **не будет выполнено**.

### 💻 Как это выглядит в коде
Все методы находятся в классе `org.testng.Assert`.

```java
import org.testng.Assert;
import org.testng.annotations.Test;

public class HardAssertExample {

    @Test
    public void testUserLogin() {
        String expectedRole = "ADMIN";
        String actualRole = "USER";

        // 1. Первая проверка: проходим успешно
        Assert.assertTrue(actualRole.contains("U"), "Ошибка: Роль не содержит букву U");
        System.out.println("Первая проверка пройдена!");

        // 2. Вторая проверка: ПРОВАЛ (Hard Assert)
        // Как только эта строка выполнится, тест упадет и выполнение метода остановится
        Assert.assertEquals(actualRole, expectedRole, "Ошибка: Роль пользователя не совпадает!");

        // 3. Этот код НИКОГДА не выполнится, если вторая проверка выше упала
        System.out.println("Эта строка не напечатается при провале Assert");
    }
}
```

### 🔍 Ключевые нюансы (Senior Level)

1.  **Точка остановки:** Hard Assert — это «прерыватель» потока выполнения внутри одного метода. Он не останавливает весь тестовый набор (Suite), он убивает только текущий `@Test`.
2.  **Жизненный цикл (Cleanup):** Это критически важно! Несмотря на то, что выполнение `@Test` прервано, аннотации **`@AfterMethod`**, **`@AfterClass`** и т.д. **ВСЕГДА выполняются**. Это сделано для того, чтобы ты мог закрыть браузер или базу данных даже при падении теста.
3.  **Использование сообщения (Message):** Всегда передавай третий параметр в `Assert.assertEquals(actual, expected, "Message")`. В логах при падении ты увидишь не просто "Expected ADMIN but found USER", а конкретное описание проблемы, что сэкономит тебе 10 минут на дебаг.
4.  **Когда использовать:** Используй Hard Assert только для критических проверок (Pre-conditions). Если без этой проверки дальнейший тест вообще не имеет смысла (например, если пользователь не залогинился, нет смысла проверять корзину) — используй Hard Assert.

---

### ❓ FAQ (Частые вопросы на собеседованиях)

**В: В чем главное отличие Hard Assert от Soft Assert?**
**О:** Hard Assert прерывает выполнение текущего метода при первой же ошибке. Soft Assert продолжает выполнение теста до самого конца, собирая все ошибки в «корзину», и выдает их только тогда, когда ты явно вызовешь `assertAll()`.

**В: Что произойдет с кодом, написанным сразу после упавшего Hard Assert?**
**О:** Он не будет выполнен. Текущий метод пометится как `FAILED`, и управление передастся в методы очистки (`@AfterMethod`).

**В: Если у меня в одном `@Test` методе 10 проверок через Hard Assert, и первая упала — увижу ли я результаты остальных 9?**
**О:** Нет. Ты узнаешь только о первой ошибке. Остальные 9 проверкам просто не будет дано шанса запуститься. Именно поэтому для проверки множества независимых полей (например, профиля пользователя) лучше использовать Soft Assert.

**В: Поможет ли Hard Assert найти баг в логике, которая идет после него?**
**О:** Нет, он только подтверждает наличие бага в текущей точке. Если тебе нужно проверить цепочку зависимых проверок, ты должен проектировать их так, чтобы критическая проверка (Hard) стояла первой.
</p>

# 🧠 Cheat Sheet: Soft Assertions (в TestNG)

### 📌 Суть в двух словах
**Hard Assertion** (стандартный `Assert`) — это «стоп-кран». Как только проверка не проходит, выполнение теста мгновенно прерывается. Все строки кода ниже этой проверки **не выполняются**.

**Soft Assertion** (`SoftAssert`) — это «режим наблюдателя». Он фиксирует ошибку, но позволяет тесту идти дальше. Тест соберет все ошибки в «корзину» и выдаст их тебе только в самом конце.

---

### 🛠 Как это работает (Алгоритм)
Чтобы Soft Assert работал, ты **обязан** пройти три шага:
1.  **Инициализация:** Создать экземпляр класса `SoftAssert`.
2.  **Проверки:** Использовать методы этого объекта вместо стандартного `Assert`.
3.  **Сборка (Критически важно!):** Вызвать метод `.assertAll()` в конце теста.

### 💻 Пример кода
```java
import org.testng.annotations.Test;
import org.testng.asserts.SoftAssert;

public class SoftAssertExample {

    @Test
    public void userProfileTest() {
        SoftAssert softAssert = new SoftAssert();

        // Представим, что мы проверяем данные пользователя на странице
        String expectedName = "Ivan";
        String actualName = "John"; // Ошибка здесь
        
        String expectedEmail = "ivan@mail.com";
        String actualEmail = "ivan@mail.com"; // Тут всё ок

        // 1. Проверка имени (Провалится, но тест пойдет дальше)
        softAssert.assertEquals(actualName, expectedName, "Имя пользователя не совпадает!");

        // 2. Проверка email (Пройдет успешно)
        softAssert.assertEquals(actualEmail, expectedEmail, "Email не совпадает!");

        // 3. Золотое правило: без этой строки тест всегда будет PASS, даже если проверки провалились!
        softAssert.assertAll(); 
    }
}
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Level)

1.  **Ловушка `assertAll()`**: Это самая частая ошибка джунов. Если ты забудешь вызвать `.assertAll()`, TestNG посмотрит на все ошибки, соберет их внутри объекта, но не "выбросит" их в отчет. В итоге тест завершится со статусом **PASSED**, хотя проверки провалились. Это создает иллюзию стабильности там, где её нет.
2.  **Когда использовать Hard Assert?** Если следующая проверка физически невозможна без успешной предыдущей. 
    *   *Пример:* Ты проверяешь наличие кнопки "Купить". Если кнопки нет (Hard Assert failed), нет смысла проверять её цвет или размер. Смысла в Soft Assert здесь ноль.
3.  **Когда использовать Soft Assert?** Когда ты проверяешь набор независимых атрибутов одного объекта. 
    *   *Пример:* Проверка полей профиля, проверка заголовков API-ответа, проверка нескольких элементов в списке.
4.  **Потокобезопасность (Thread Safety)**: **Никогда** не делай `SoftAssert` статическим или общим для всех потоков при параллельном запуске тестов. Если два теста будут писать ошибки в один и тот же объект `softAssert`, отчет превратится в кашу, где ошибки одного теста приписываются другому. Один тест = один экземпляр `SoftAssert`.

### ❓ FAQ (Вопросы на собеседовании)

**В: Что произойдет, если я вызову `softAssert.assertEquals(...)` после того, как уже вызвал `softAssert.assertAll()`?**
**О:** Тест упадет. После вызова `assertAll()` объект переходит в состояние "завершен", и новые проверки к нему добавлять нельзя — это нарушит логику отчета.

**В: Можно ли смешивать Hard и Soft Assert в одном методе?**
**О:** Да, можно. Но помни: если Hard Assert упадет, выполнение метода прервется, и твой `softAssert.assertAll()` просто не будет достигнут. Все накопленные "мягкие" ошибки не будут выведены.

**В: Как увидеть все ошибки сразу, а не исправлять их по одной?**
**О:** Именно для этого и нужен Soft Assert. Он позволяет за один прогон увидеть полный список несоответствий (например: имя не то, email не тот, телефон не тот), что экономит время на перезапуск тестов.

# 📌 Шпаргалка: Assertions в TestNG

**Assertion (Утверждение)** — это сердце любого теста. Это точка, в которой мы решаем: тест пройден (Pass) или провален (Fail). Если утверждение не выполняется, TestNG помечает тест как Failed и (в зависимости от типа) может остановить выполнение.

---

### 1. Hard Assert vs Soft Assert (Главное различие)

Это база. Ошибка в выборе между ними — самая частая причина «мусорных» логов в отчетах.

#### **Hard Assert (Жесткое утверждение)**
*   **Как работает:** Как только условие не выполняется, выполнение текущего `@Test` метода **немедленно прерывается**. Весь код, идущий ниже упавшего `Assert`, не будет выполнен.
*   **Когда использовать:** Когда дальнейшие шаги теста не имеют смысла, если этот шаг провалился (например: если мы не смогли залогиниться, нет смысла проверять наличие кнопки «Профиль»).

#### **Soft Assert (Мягкое утверждение)**
*   **Как работает:** Если условие не выполняется, тест **не останавливается**. Ошибки накапливаются в памяти. Чтобы увидеть результат, нужно обязательно вызвать метод `assertAll()`.
*   **Когда использовать:** Когда нужно проверить сразу много независимых параметров (например: проверка всех полей в профиле пользователя — имя, фамилия, email, телефон). Мы хотим увидеть *все* ошибки за один прогон, а не исправлять их по одной.
*   **⚠️ Нюанс (Senior Tip):** Если ты забудешь вызвать `softAssert.assertAll()`, тест всегда будет считаться **пройденным**, даже если все проверки внутри него провалились. Это классическая ловушка.

---

### 2. Основные методы класса `org.testng.Assert`

Все стандартные методы TestNG работают по принципу: `actual` (что получили) и `expected` (что ожидали).

*   **`assertEquals(actual, expected)`**: Самый частый гость. Сравнивает объекты или примитивы на равенство.
*   **`assertNotEquals(actual, expected)`**: Проверяет, что значения *разные*.
*   **`assertTrue(condition)` / `assertFalse(condition)`**: Проверка логического выражения (boolean).
*   **`assertNull(object)` / `assertNotNull(object)`**: Проверка на наличие или отсутствие объекта (проверка на `null`).

---

### 3. Тонкие моменты и нюансы (Edge Cases)

#### **A. Сравнение чисел с плавающей точкой (`double`, `float`)**
Никогда не сравнивай `double` напрямую через `assertEquals(actual, expected)`. Из-за особенностей двоичной системы компьютер может выдать `0.30000000000000004` вместо `0.3`.
*   **Решение:** Используй метод с параметром **delta** (допустимая погрешность).
*   **Пример:** `Assert.assertEquals(actual, expected, 0.001);` (Если разница меньше 0.001 — тест пройден).

#### **B. Сравнение строк (Strings)**
Помни про невидимые символы: пробелы в начале/конце или переносы строк (`\n`).
*   **Совет:** При сравнении строк часто полезно использовать `.trim()` к `actual`, чтобы избежать ложных провалов из-за лишнего пробела.

#### **C. Списки и коллекции**
`assertEquals` для списков (`List`) проверяет не только наличие элементов, но и их **порядок**. Если элементы те же, но порядок другой — тест упадет.

#### **D. Проверка исключений (Expected Exceptions)**
Иногда цель теста — проверить, что система *правильно выдает ошибку*.
*   **Как делать:** Используй параметр в аннотации: `@Test(expectedExceptions = NullPointerException.class)`.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что будет, если в методе с Hard Assert после упавшего утверждения стоит `System.out.println("Hello")`?**
**О:** Текст "Hello" не будет напечатан. Выполнение метода прерывается сразу на строке с `Assert`.

**В: Я использую SoftAssert, проверяю 5 полей, но тест проходит (Green), хотя в логах вижу ошибки. В чем проблема?**
**О:** Ты забыл вызвать `softAssert.assertAll();` в конце метода. Без этого вызова TestNG не «поднимает» накопленные ошибки.

**В: Можно ли использовать `assertTrue(actual.equals(expected))` вместо `assertEquals(actual, expected)`?**
**О:** Технически можно, но **не делай так**. В `assertEquals` TestNG при падении напишет в лог: *"Expected: [A], but found: [B]"*. А в `assertTrue` ты увидишь просто: *"Expected true, but found false"*, и не поймешь, какое именно значение пришло. Это усложняет отладку.

**В: Как проверить, что список содержит определенный элемент, не проверяя весь список целиком?**
**О:** Используй `assertTrue(list.contains(element))`. Но помни, что это не проверит лишние элементы в списке.

# 📑 Шпаргалка: Структура `testng.xml`

`testng.xml` — это «пульт управления» твоим автотестированием. Если аннотации в коде говорят, *что* делать, то XML-файл говорит, *как*, *в каком порядке* и *с какими параметрами* запускать эти тесты. 

Без этого файла ты ограничен запуском одного класса или метода через IDE. С ним — ты создаешь полноценные тестовые наборы (Suites) для CI/CD.

### 🏗 Иерархия элементов (от корня к веткам)

Структура строго вложенная:
`Suite` $\rightarrow$ `Test` $\rightarrow$ `Classes/Packages` $\rightarrow$ `Class` $\rightarrow$ `Methods`.

#### 1. `<suite>` — Корень всего
Это самый верхний уровень. Один XML-файл = одна Suite.
*   **Атрибуты:**
    *   `name`: Название твоего тестового набора (важно для отчетов).
    *   `parallel`: Режим параллелизма (`methods`, `tests`, `classes` или `none`). **Senior tip:** выбирай уровень параллелизма осторожно, чтобы не "положить" окружение и не вызвать Race Condition.
    *   `thread-count`: Количество потоков, которые будут работать одновременно.

#### 2. `<test>` — Логическая группа
Внутри одной Suite может быть много `<test>`. Это не один тест, а **группа тестов**, объединенных общей логикой (например, "Smoke Tests", "Regression", "API Tests").
*   **Атрибуты:**
    *   `name`: Имя конкретного набора внутри Suite.
    *   `preserve-order`: Если `true`, TestNG будет запускать `<test>` в том порядке, в котором они написаны в XML.

#### 3. `<groups>` — Фильтрация (Твой главный инструмент)
Позволяет сказать: «Запусти только те методы, которые помечены группой `smoke`».
*   **Вложенные элементы:**
    *   `<include name="group_name"/>`: Включаем группу.
    *   `<exclude name="group_name"/>`: Исключаем группу (например, исключаем `flaky` тесты).

#### 4. `<parameter>` — Инъекция данных
Позволяет передавать значения прямо из XML в код теста через аннотацию `@Parameters`.
*   **Пример:** Передача URL браузера или логина/пароля. Это позволяет использовать один и тот же код для разных окружений (Dev, QA, Prod), просто меняя XML.

#### 5. `<classes>` / `<package>` — Указатели на код
Здесь ты указываешь, где именно лежат твои тесты.
*   `<packages>`: Сканирует все классы в указанном пакете (удобно для больших проектов).
*   `<classes>`: Ты явно перечисляешь конкретные классы.
*   `<class name="com.example.MyTest"/>`: Путь к конкретному классу.

---

### 💻 Пример "Эталонного" XML

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE suite SYSTEM "https://testng.org/testng-1.0.dtd">

<!-- Настройка всей Suite: параллельный запуск на уровне классов -->
<suite name="Main Regression Suite" parallel="classes" thread-count="3">

    <!-- Первый блок тестов: Smoke -->
    <test name="Smoke Tests">
        <!-- Передаем глобальный параметр для всех тестов внутри этого <test> -->
        <parameter name="browser" value="chrome"/>
        
        <groups>
            <run>
                <include name="smoke"/>
    </groups>

        <classes>
            <class name="tests.LoginTest"/>
            <class name="tests.HeaderTest"/>
        </classes>
    </test>

    <!-- Второй блок тестов: Регрессия -->
    <test name="Regression Tests">
        <parameter name="browser" value="firefox"/>
        
        <groups>
            <run>
                <exclude name="flaky"/> <!-- Игнорируем нестабильные тесты -->
            </run>
        </groups>

        <packages>
            <package name="tests.api.*"/> 
        </packages>
    </test>

</suite>
```

### 🧠 FAQ (Частые вопросы на собеседовании)

**В: В чем разница между `<test>` и `<class>` в XML?**
**О:** `<test>` — это логическая сущность (сценарий или набор проверок), у которого есть свои настройки (параметры, группы). `<class>` — это физический Java-класс с кодом. Один `<test>` может содержать десятки `<class>`.

**В: Как запустить тесты параллельно на уровне методов, но чтобы внутри одного класса они шли по порядку?**
**О:** Тебе нужно установить `parallel="methods"` в теге `<suite>`, но для конкретных классов или групп использовать настройки зависимостей (`dependsOnMethods`) в коде. Однако, если ты хочешь именно "чистый" XML-подход, то управление порядком внутри методов через XML сильно ограничено — лучше полагаться на `priority` в аннотациях.

**В: Где лучше объявлять `<parameter>`: в `<suite>` или в `<test>`?**
**О:** Если параметр нужен всем тестам (например, `baseUrl`), объявляй в `<suite>`. Если параметр специфичен только для одного набора (например, `timeout` для API), объявляй внутри конкретного `<test>`.

**В: Что произойдет, если я укажу класс, которого не существует?**
**О:** TestNG выбросит ошибку при парсинге XML и выполнение Suite прервется. Всегда проверяй пути (Full Qualified Name) после рефакторинга.

# 🚀 Тема: Параллельное выполнение в TestNG (Parallel Execution)

### 1. Суть и уровни параллелизма
Параллелизм в TestNG настраивается через файл `testng.xml`. Мы не пишем код для создания потоков, мы просто говориlam TestNG, **что** именно мы хотим запускать одновременно.

Главный атрибут — `parallel`, который принимает три значения:

*   `parallel="methods"` — **Максимальный хаос.** Каждый метод `@Test` запускается в отдельном потоке. Самый быстрый, но самый опасный вариант.
*   `parallel="classes"` — **Золотая середина.** Тесты внутри одного класса идут друг за другом (последовательно), но разные классы запускаются параллельно. Это безопаснее, если у тебя есть состояние внутри класса.
*   `parallel="tests"` — **Групповой подход.** Параллелятся блоки `<test>` внутри XML. Удобно, когда ты хочешь разделить тесты на "Smoke" и "Regression", и запускать их одновременно в разных потоках.

**Атрибут `thread-count`**: Это количество "рабочих рук" (потоков). Если ты поставишь `methods` и `thread-count="10"`, TestNG попытается запустить 10 методов сразу.

### 2. Пример конфигурации (`testng.xml`)

```xml
<suite name="Parallel Suite" parallel="classes" thread-count="3">
    <test name="Login Tests">
        <classes>
            <class name="com.tests.LoginTest"/>
            <class name="com.tests.RegistrationTest"/>
        </classes>
    </test>
    <test name="Checkout Tests">
        <classes>
            <class name="com.tests.PaymentTest"/>
        </classes>
    </test>
</suite>
```
*В этом примере: классы `LoginTest` и `RegistrationTest` могут лететь параллельно, если они в разных `<test>` блоках или если настроен `parallel="classes"`.*

---

### 3. ⚠️ Главные нюансы (Senior Tips)

#### А. Проблема Thread Safety (Потокобезопасность)
Это самая частая причина падения тестов. Если ты используешь одну и ту же переменную `WebDriver driver` во всех тестах, то второй поток перепишет драйвер первого. В итоге: первый тест пытается кликнуть на кнопку, но браузер уже закрыт или открыт другой URL.

**Решение:** Используй **`ThreadLocal<WebDriver>`**. Это специальный контейнер, который создает отдельную копию объекта для каждого потока.
```java
public class DriverManager {
    private static ThreadLocal<WebDriver> driver = new Threadтеlocal<>();

    public static void setDriver(WebDriver driverInstance) {
        driver.set(driverInstance);
    }

    public static WebDriver getDriver() {
        return driver.get();
    }
}
```

#### Б. Состояние данных (Data Dependency)
Если тест №1 создает пользователя, а тест №2 его удаляет — в параллельном режиме тест №2 может сработать раньше теста №1. 
*   **Правило:** Каждый тест должен быть атомарным и не зависеть от состояния базы данных, измененного другим тестом.

#### В. Ресурсы системы
Запуск 50 потоков браузера Chrome "съест" всю оперативную память твоего агента в Jenkins. Всегда подбирай `thread-count` исходя из возможностей железа.

---

### 4. FAQ (Часто задаваемые вопросы)

**В: Что делать, если один тест упал, а остальные должны продолжать выполняться параллельно?**
**О:** В TestNG это поведение по умолчанию. Если ты не используешь `dependsOnMethods`, падение одного метода в потоке не остановит другие потоки. Но если есть зависимости — используй `alwaysRun = true` в аннотации `@BeforeMethod`.

**В: Как запустить только определенные тесты параллельно, а остальные — последовательно?**
**О:** Это делается через разделение на разные `<test>` блоки в `testng.xml` и настройку уровней параллелизма именно для тех блоков, которые требуют скорости. Либо через использование разных XML файлов.

**В: Можно ли использовать `parallel="methods"` для API тестов?**
**О:** Да, и это идеально! API тесты не потребляют много ресурсов (в отличие от браузеров), поэтому ты можешь выставить очень высокий `thread-count` (например, 20-50) и прогнать тысячи запросов за считанные минуты.

**В: В чем разница между `parallel="classes"` и `parallel="tests"`?**
**О:** 
- `classes`: Тесты внутри одного `<test>` блока будут запускаться в разных потоках, но разделены по классам.
- `tests`: Параллелятся сами блоки `<test>`. Если в одном блоке `<test>` у тебя 10 классов — они будут выполняться последовательно (в рамках этого блока), пока работают другие блоки `<test>`.

# 🧠 Шпаргалка по TestNG: Использование фильтров (Groups & XML)

### 🎯 Суть темы
Фильтрация в TestNG — это механизм управления запуском тестов. Вместо того чтобы запускать *всё подряд* (что долго и дорого), мы выбираем только нужные части: «только Smoke», «только регресс» или «все, кроме сломанных».

Основной инструмент фильтрации — **Группы (Groups)**.

---

### 🛠 1. Уровень кода: Аннотация `@Test`
Ты помечаешь тест определенным тегом. Один тест может принадлежать сразу нескольким группам.

```java
@Test(groups = {"smoke", "regression"})
public void testLogin() { ... }

@Test(groups = {"regression", "slow"})
public void testHeavyDataProcessing() { ... }
```
*   **Нюанс:** Если ты не указал группу, тест попадает в группу «по умолчанию» (unassigned). При использовании фильтров по группам такие тесты часто игнорируются.

---

### ⚙️ 2. Уровень конфигурации: `testng.xml`
Это "пульт управления". Именно здесь происходит магия включения и исключения.

#### А) Только включение (`<include>`)
Запускаем только то, что перечислили. Все остальные тесты будут проигнорированы.
```xml
<groups>
    <run>
        <include name="smoke" />
    </run>
</groups>
```

#### Б) Исключение (`<exclude>`)
Запускаем всё, **кроме** указанных групп. Полезно, когда нужно запустить полный регресс, но вырезать "хрупкие" или слишком долгие тесты.
```xml
<groups>
    <run>
        <exclude name="slow" />
    </run>
</groups>
```

#### В) Сложная логика (Комбинации)
Ты можешь комбинировать `include` и `exclude`.
*Пример: Запустить группу `regression`, но убери из неё тесты с пометкой `flaky`.*
```xml
<groups>
    <run>
        <include name="regression" />
        <exclude name="flaky" />
    </run>
</groups>
```

---

### ⚠️ Важные нюансы (Senior Insights)

1.  **Приоритет Exclude:** Если тест попадает и в `include`, и в `exclude` одновременно — **Exclude побеждает**. Тест будет пропущен. Это критически важно помнить при написании сложных XML-конфигов.
2.  **Зависимости (Dependencies) + Фильтры:** Если твой тест `Test_B` зависит от `Test_A` (`dependsOnMethods`), а ты отфильтровал `Test_A` (исключил его), то `Test_B` автоматически перейдет в статус **SKIPPED**. Это может "повалить" весь отчет, хотя сам код теста исправен.
*   *Совет:* Всегда проверяй, не вырезаешь ли ты "фундамент" для своих зависимых тестов.
3.  **Фильтрация через Maven/Gradle:** Ты можешь передавать группы прямо в командной строке, переопределяя XML:
    `mvn test -Dgroups="smoke"`
    Это позволяет использовать один и тот же `testng.xml` для разных задач в CI/CD.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что произойдет, если я укажу `<include name="smoke">`, но в коде у теста нет группы "smoke"?**
**О:** Тест не будет запущен. Фильтр `include` работает как строгий белый список.

**В: Можно ли фильтровать тесты по именам классов или методов, а не по группам?**
**О:** Да, через теги `<classes>` и `<methods>` в `testng.xml`. Но это "грязный" путь. Группы — это стандарт индустрии, так как они позволяют менять состав тестов, не переписывая XML под каждый класс.

**В: Как запустить все тесты, кроме группы "broken"?**
**О:** Используй тег `<exclude name="broken" />` внутри блока `<groups><run>`.

**В: Если я использую `dependsOnGroups`, и группа, от которой я завишу, исключена фильтром, что будет с моим тестом?**
**О:** Твой тест будет пропущен (Skipped), так как его зависимость не была выполнена в текущем запуске.

# 🎧 Тема: Listeners (Слушатели) в TestNG

### Что это такое?
Если говорить совсем просто: **Listener — это «шпион» или «наблюдатель»**. 

Представь, что ты проводишь эксперимент. Ты можешь просто смотреть на результат, а можешь поставить скрытую камеру, которая будет автоматически записывать каждый твой шаг, делать скриншот, если что-то разбилось, и звонить начальнику, если всё пошло не по плану. В TestNG **Listeners** — это и есть эта камера и система оповещения.

Технически, это классы, которые реализуют специальные интерфейсы TestNG и «подписываются» на события жизненного цикла теста (начало, успех, провал, завершение).

---

### 🛠 Основные интерфейсы (Твой арсенал)

#### 1. `ITestListener` — Самый важный
Следит за отдельными методами `@Test`. 
*   **Когда использовать:** Снятие скриншотов при падении, логирование шагов, отправка уведомлений в Slack/Telegram, запись результатов в Allure/ExtentReports.
*   **Ключевые методы:**
    *   `onTestStart`: Вызывается перед началом теста.
    *   `onTestSuccess`: Вызывается, когда тест прошел успешно.
    *   `onTestFailure`: **Критически важен.** Сюда мы вешаем логику создания скриншотов.
    *   `onTestSkipped`: Если тест был пропущен (например, из-за зависимости).

#### 2. `ISuiteListener` — Уровень всей «свиты»
Следит за всем запуском целиком (`<suite>` в XML).
*   **Когда использовать:** Глобальная подготовка (например, очистка базы данных перед началом всех тестов или генерация финального PDF-отчета после завершения всего прогона).
*   **Ключевые методы:** `onStart` и `onFinish`.

#### 3. `IAnnotationTransformer` — «Хакерский» уровень (Advanced)
Позволяет изменять параметры аннотаций прямо во время выполнения.
*   **Когда использовать:** Если тебе нужно динамически отключать тесты (`enabled = false`) или менять их приоритет в зависимости от условий (например, если база данных недоступна). Это магия, которая меняет правила игры на лету.

#### 4. `IRetryAnalyzer` — Борец с «флакующими» (Flaky) тестами
Хотя это часто выделяют отдельно, по сути это механизм перехвата ошибки для повторного запуска.
*   **Когда использовать:** Чтобы автоматически перезапустить упавший тест еще раз, прежде чем признать его проваленным.

---

### 🚀 Как подключить Listener?

Есть два пути, и как Senior, я советую выбирать их осознанно:

1.  **Через аннотацию `@Listeners` над классом:**
    ```java
    @Listeners(MyCustomListener.class)
    public class MyTests { ... }
    ```
    *Плюс:* Видно сразу в коде. 
    *Минус:* Приходится прописывать в каждом классе (плохо для масштабируемости).

2.  **Через `testng.xml` (Best Practice):**
    ```xml
    <suite name="MySuite">
        <listeners>
            <listener class-name="com.example.MyCustomListener" />
        </listeners>
        <test name="MyTest"> ... </test>
    </suite>
    ```
    *Плюс:* Глобально, чисто, удобно управлять конфигурацией без изменения кода.

---

### ⚠️ Нюансы и «Подводные камни» (Senior Tips)

1.  **Thread Safety (Потокобезопасность):** Если ты запускаешь тесты в параллели (`parallel="methods"`), твой Listener **обязан** быть потокобезопасным. Используй `ThreadLocal` для хранения данных (например, для хранения экземпляра драйвера), иначе результаты разных тестов перемешаются.
2.  **Не перегружай логику:** Не пиши тяжелые запросы к БД или сложные вычисления прямо внутри `onTestFailure`. Это замедлит выполнение всего набора тестов. Listener должен быть максимально легким.
3.  **Зависимости:** Никогда не делай Listener зависимым от логики самого теста. Если Listener упадет с ошибкой, он может «положить» весь отчет или вообще остановить выполнение тестов.

**О:** `ITestListener` работает на уровне конкретного метода `@Test` (старт/финиш теста), а `ISuiteListener` — на уровне всего файла `testng.xml` (старт/финиш всей сессии).

**В: Как сделать скриншот только при падении теста?**
**О:** Нужно реализовать интерфейс `ITestListener` и переопределить метод `onTestFailure`. Внутри этого метода вызвать метод драйвера `getScreenshotAs(...)`.

**В: Что произойдет, если в Listener возникнет Exception?**
**О:** Это может привести к непредсказуемому поведению. Тест может пометить как `Error` вместо `Failure`, или отчет может не сформироваться корректно. Всегда оборачивай код внутри методов Listener в `try-catch`.

**В: Можно ли использовать несколько Listeners одновременно?**
**О:** Да, ты можешь подключить сколько угодно слушателей через XML или аннотацию. Они будут выполняться последовательно.

# 🎧 Тема: TestNG Listeners (`ITestListener`)

### Что это такое? (Простыми словами)
Представь, что ты — режиссер на съемочной площадке. Твои тесты — это актеры, которые выполняют сцены. **Listener (Слушатель)** — это твой ассистент, который стоит с блокнотом. Он не участвует в игре, но он *слышит* каждое действие: когда актер вышел на сцену, когда он забыл текст (тест упал) и когда сцена успешно завершена.

В техническом смысле `ITestListener` — это интерфейс, который позволяет тебе «подписаться» на события жизненного цикла теста и выполнять свой код в ответ на эти события.

---

### Основные методы (Что мы ловим?)
Интерфейс `ITestListener` содержит несколько ключевых методов. Тебе не обязательно переопределять все, но вот самые важные:

1.  **`onStart(ISuite suite)`**: Вызывается один раз в самом начале, когда запускается весь Suite (набор тестов). Идеально для инициализации общих ресурсов или логгеров.
2.  **`onTestStart(ITestResult result)`**: Вызывается прямо перед началом каждого конкретного `@Test`. Здесь удобно логировать: «Начинаю тест: [Имя теста]».
3.  **`onTestSuccess(ITestResult result)`**: Вызывается, когда тест прошел успешно.
4.  **`onTestFailure(ITestResult result)`**: **Самый важный метод.** Вызывается, если тест упал (AssertionError или любая Exception). Именно здесь мы делаем скриншоты в Selenium.
5.  **`onTestSkipped(ITestResult result)`**: Вызывается, если тест был пропущен (например, из-за того, что упала зависимая ему проверка `dependsOnMethods`).
6.  **`onFinish(ISuite suite)`**: Вызывается в самом конце, когда весь Suite завершен. Здесь мы закрываем соединения с БД или генерируем финальный отчет.

---

### Как подключить Listener к проекту?
Есть два пути, и Senior-разработчик выберет правильный в зависимости от ситуации.

**Способ 1: Через аннотацию `@Listeners` (Локально)**
Ты просто вешаешь аннотацию над своим тестовым классому.
```java

public class MyTests {

}
```
*Плюс: Быстро и удобно при разработке.*

**Способ 2: Через `testng.xml` (Для CI/CD)**
Ты прописываешь слушателя в конфигурационном файле.
```xml
<suite name="MySuite">
    <listeners>
        <listener class="com.example.MyCustomListener" />
    </listeners>
    <test name="MyTest">
        <!-- ... -->
    </test>
</suite>
```
*Плюс: Это "золотой стандарт". Ты можешь управлять слушателями, не меняя Java-код. Это удобно для Jenkins/GitLab.*

### 💡 Нюансы и "Подводные камни" (Senior Insights)

1.  **Объект `ITestResult` — это твой супергерой.** Все методы (start, success, failure) принимают этот объект. В нем хранится всё: имя метода, класс, параметры теста и даже само исключение (`Throwable`), которое привело к падению.
2.  **Скриншоты на провале:** Если ты пишешь автотесты на Selenium, `onTestFailure` — единственное место, где нужно вызывать `driver.takeScreenshot()`. Но помни: если драйвер уже "умер" (Session ID is null), скриншот не сделается.
3.  **Потокобезопасность (Thread Safety):** Если ты запускаешь тесты **параллельно** (`parallel="methods"`), твой Listener должен быть готов к тому, что несколько методов `onTestStart` могут вызываться одновременно из разных потоков. Не храни данные в обычных переменных класса Listener — используй `ThreadLocal`.

# 🧠 Шпаргалка: TestNG Listeners — `ISuiteListener`

### 📌 Что это такое?
Если `ITestListener` — это «надзиратель» за каждым отдельным тестом, то **`ISuiteListener`** — это «менеджер всей фабрики». Его область видимости — не конкретный метод или класс, а весь запуск (Suite), описанный в твоем `testng. XML`.

Он реагирует на события глобального масштаба: начало и конец выполнения всего тестового набора.

### 🛠 Основные методы
Интерфейс очень простой, в нем всего два метода:

1.  **`onStart(ISuite suite)`** — вызывается **один раз** в самом начале, когда TestNG прочитал `testng.xml` и готов запустить первый тест.
2.  **`onFinish(ISuite suite)`** — вызывается **один раз** в самом конце, когда все тесты в рамках этой Suite завершены (неважно, прошли они или упали).

---

### 🚀 Зачем это нужно в реальном проекте? (Use Cases)
Senior-разработчик использует `ISuiteListener` для глобальных вещей, которые не должны зависеть от конкретных тестов:

*   **Глобальная инициализация:** Подключение к базе данных, создание пустой папки для логов или запуск Docker-контейнера перед началом всех тестов.
*   **Глобальный Cleanup:** Закрытие соединений с БД, очистка временных файлов или удаление созданных тестовых пользователей после завершения всего прогона.
*   **Reporting Setup/Teardown:** Инициализация тяжелых отчетов (например, Allure или ExtentReports) и их финальная «сборка» (закрытие стримов, генерация итогового HTML).
*   **Сбор статистики:** Запись времени начала и окончания всего прогона для мониторинга производительности CI/CD пайплайна.

---

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **Не путай уровни ответственности:** Никогда не пиши логику проверки статуса теста (`passed`/`failed`) внутри `ISuiteListener`. Для этого есть `ITestListener`. Если ты попытаешься анализировать результаты тестов в `onStart`, ты ничего не найдешь, потому что они еще не запустились.
2.  **Регистрация:** Мало просто написать класс. Чтобы TestNG его «услышал», его нужно прописать в `testng.xml` внутри тега `<listeners>`.
3.  **Ошибка в `onStart` — фатальна:** Если твой код упадет с исключением внутри `onStart`, TestNG может вообще не запустить тесты. Это критическая точка входа.
4.  **Потокобезопасность:** Хотя `onStart` и `onFinish` вызываются один раз, помни, что если ты используешь параллельный запуск нескольких *Suite* (редко, но бывает), твои глобальные переменные могут пересекаться.

# 🧠 Шпаргалка: IAnnotationTransformer (TestNG)

### Что это такое?
Представь, что у тебя есть сотни тестов. Тебе нужно внезапно отключить все тесты с определенным приоритетом или изменить их группы, но ты **не хочешь** лезть в каждый класс и менять код вручную. 

`IAnnotationTransformer` — это "хирург" для твоих аннотаций. Это специальный Listener, который перехватывает аннотации (например, `@Test`) прямо в момент запуска и позволяет тебе **динамически изменить их параметры** (priority, groups, enabled, timeOut и т.д.) программным путем, не меняя исходный код тестов.

### Как это работает (Механизм)
Когда TestNG сканирует классы перед запуском, он натыкается на аннотацию `@Test`. В этот момент вызывается метод `transform` нашего слушателя. Мы получаем объект `ITestAnnotation`, который является "пультом управления" этой конкретной аннотацией. Мы можем нажать на любые кнопки: выключить тест, изменить его группу или приоритет.

### Реализация (Код)

```java
import org.testng.IAnnotationTransformer;
import org.testng.annotations.ITestAnnotation;
import java.lang.reflect.Constructor;
import java.lang.reflect.Method;

public class MyAnnotationTransformer implements IAnnotationTransformer {

    @Override
    public void transform(ITestAnnotation annotation, 
                          Class testClass, 
                          Constructor testConstructor, 
                          Method testMethod, 
                          Object[] testClassInstance) {

        // Пример 1: Отключаем все тесты, в названии которых есть "Flaky"
        if (testMethod.getName().contains("Flaky")) {
            annotation.setEnabled(false);
            System.out.println("🛠 Transformer: Тест " + testMethod.getName() + " был отключен.");
        }

        // Пример 2: Динамически меняем приоритет для конкретного метода
        if (testMethod.getName().equals("criticalTest")) {
            annotation.setPriority(1); // Делаем его супер-приоритетным
        }

        // Пример 3: Добавляем группу всем тестам этого класса
        if (testClass.getSimpleName().contains("Regression")) {
            annotation.setGroups(new String[]{"regression", "smoke"});
        }
    }
}
```

### Как подключить?
Есть два пути, но Senior всегда выберет **первый** (через XML), чтобы не засорять код аннотациями `@Listeners`.

1.  **В `testng.xml` (Рекомендуемый):**
    ```xml
    <listeners>
        <listener class-name="com.example.MyAnnotationTransformer" />
    </listeners>
    ```
2.  **Над тестовым классом:**
    ```java
    @Listeners(com.example.MyAnnotationTransformer.class)
    public class MyTests { ... }
    ```

### Когда это использовать (Use Cases)
*   **Environment-based execution:** Отключать тяжелые UI-тесты, если запуск идет в "быстрой" среде (например, на Pull Request).
*   **Fixing Flaky tests:** Если тест начал падать без причины, можно программно его отключить через Transformer, не удаляя из репозитория.
*   **Dynamic Grouping:** Автоматически добавлять тесты в группу `smoke` на основе их названия или метаданных класса.

### ⚠️ Нюансы и "Подводные камни"
1.  **Только метаданные:** Ты можешь менять **параметры аннотации** (priority, groups, enabled), но ты **не можешь** изменить само тело метода (логику внутри `{ ... }`).
2.  **Производительность:** Метод `transform` вызывается для **каждого** найденного метода с `@Test`. Не питай тяжелую логику (запросы к БД или сложные вычисления) внутри него, иначе запуск тестов станет мучительно долгим.
3.  **Порядок имеет значение:** Если у тебя несколько трансформеров, они будут применяться по очереди. Последний изменит то, что изменил предыдущий.

### ❓ FAQ (Частые вопросы на собеседовании)

**В: В какой момент вызывается `IAnnotationTransformer`?**
**О:** Во время фазы сканирования аннотаций перед началом выполнения тестов. Он работает с метаданными еще до того, как созданы экземпляры классов тестов.

**В: Можно ли с помощью него изменить `dataProvider`?**
**О:** Да, через метод `annotation.setDataProvider("name")`. Это позволяет подменять источники данных на лету.

**В: Чем `IAnnotationTransformer` отличается от `ITestListener`?**
**О:** `IAnnotationTransformer` меняет **настройки** (аннотации) *до* запуска. `ITestListener` следит за **результатом** (start, success, failure) *во время* выполнения.

**В: Что будет, если в `transform` вызвать `annotation.setEnabled(false)` для всех тестов?**
**О:** Тесты не упадут, они просто будут помечены как `Skipped`, и TestNG их даже не попытается запустить.

# 🧠 Cheat Sheet: Retry Logic in TestNG

### 🎯 Суть проблемы
В автоматизации есть понятие **Flaky Tests** (нестабильные тесты). Это тесты, которые падают не из-за багов в приложении, а из-за внешних факторов: лаг сети, медленная загрузка элемента, микро-задержка в БД. 

**Retry Logic** — это механизм автоматического перезапуска упавшего теста. Если тест упал, TestNG запускает его снова (N раз). Если со второй или третьей попытки он прошел — мы считаем тест успешным (но с пометкой, что была попытка).

---

### 🛠 Реализация: Шаг за шагом

#### 1. Создание Анализатора (`IRetryAnalyzer`)
Тебе нужно реализовать интерфейс `IRetryAnalyzer`. Его единственный метод `retry` возвращает `true`, если мы хотим перезапустить тест, и `false`, если попытки исчерпаedны.

```java
import org.testng.RetryAnalyzer;
import org.testng.ITestResult;

public class RetryAnalyzer implements RetryAnalyzer {
    private int count = 0;
    private static final int maxRetryCount = 3; // Максимум 3 перезапуска

    @Override
    public boolean retry(ITestResult result) {
        if (count < maxRetryCount) {
            count++;
            System.out.println("⚠️ Test failed. Retrying... Attempt: " + count);
            return true; // Да, запускай еще раз
        }
        return false; // Нет, попыток больше не будет
    }
}
```

#### 2. Применение (Два пути)

**Путь А: "Джуновский" (Ручной)**
Ты прописываешь путь к анализатору в каждой аннотации `@Test`. Это ужасно, потому что если у тебя 1000 тестов, ты сойдешь с ума их обновлять.
```java
@Test(retryAnalyzer = RetryAnalyzer.class)
public void myTest() {
    // ...
}
```

**Путь Б: "Senior" (Глобальный через Listener)**
Мы используем `IAnnotationTransformer`. Этот слушатель перехватывает аннотации во время выполнения и **автоматически** подставляет наш `RetryAnalyzer` во все тесты.

```java
import org.testng.IAnnotationTransformer;
import org.testng.annotations.ITestAnnotation;
import java.lang.reflect.Method;

public class RetryListener implements IAnnotationTransformer {
    @Override
    public void transform(ITestAnnotation annotation, Method method) {
        // Автоматически вешаем RetryAnalyzer на каждый @Test
        annotation.setRetryAnalyzer(RetryAnalyzer.class);
    }
}
```

**Не забудь зарегистрировать Listener в `testng.xml`:**
```xml
<listeners>
    <listener class-name="comlem.package.RetryListener" />
</listeners>
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Insights)

1.  **Загрязнение состояния (State Pollution):** Это самая частая ошибка. Если твой тест упал на середине, он мог оставить за собой "мусор": созданную запись в БД, открытую сессию или не закрытое окно браузера. При перезапуске этот мусор может сломать *следующую* попытку.
    *   *Решение:* Всегда используй `@AfterMethod` для очистки окружения (удаление данных, сброс кэша).
2.  **Скрытие реальных багов:** Если ты поставишь слишком много ретраев (например, 10), ты можешь не заметить, что тест стабильно падает из-за бага, но "проскакивает" только на 9-й попытке из-за удачного стечения обстоятельств. Это создает иллюзию стабильности.
    *   *Решение:* Лимит ретраев должен быть маленьким (1–3).
3.  **Ложные отчеты:** В стандартном отчете TestNG тест может отобразиться как `PASSED`, хотя он упал 2 раза. Это опасно.
    *   *Решение:* Используй кастомные Listeners или Allure, чтобы логировать факт ретрая. Команда должна видеть: "Тест прошел, но был Flaky".

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Что такое Flaky Test и помогает ли Retry Logic его исправить?**
**О:** Flaky test — это тест с нестабильным результатом. Retry Logic не *исправляет* причину (сеть или код), он лишь *нивелирует последствия*, позволяя пайплайну в CI/CD не останавливаться из-за временных сбоев.

**В: Можно ли использовать Retry Logic для всех тестов без разбора?**
**О:** Нет. Только для тех, которые зависят от внешних факторов (интеграционные тесты). Юнит-тесты должны быть детерминированными. Если юнит-тест требует ретрая — значит, в нем ошибка или он не является юнит-тестом.

**В: Как сделать так, чтобы RetryAnalyzer работал глобально?**
**О:** Через реализацию интерфейса `IAnnotationTransformer` и регистрацию его в `testng.xml` или через `Listeners`.

**В: Что произойдет, если тест упал из-за Assert.fail(), а ретрай включен?**
**О:** TestNG воспримет это как обычный провал теста и запустит его заново согласно логике твоего `RetryAnalyzer`.

# 🧠 Тема: Custom Annotations (Пользовательские аннотации)

### 💡 Что это такое?
Если коротко: **Аннотация — это "наклейка" или "тег" на твоем коде.** Сама по себе аннотация ничего не делает. Она просто хранит метаданные. Чтобы эта "наклейка" начала работать, нужен "читатель" — специальный механизм (обычно **Listener**), который увидит этот тег и выполнит определенную логику.

В TestNG мы создаем свои аннотации, чтобы:
1.  **Маркировать тесты** (например, `@Feature("Login")` или `@Smoke`).
2.  **Передавать параметры** в Listeners (например, `@RetryCount(3)`).
*Это позволяет избежать "захардкоженных" значений в коде и делает фреймворк гибким.*

---

### 🛠 Как это устроено (Анатомия)

Чтобы создать рабочую аннотацию, тебе нужны три компонента:
1.  **`@interface`**: Объявление самой аннотации.
2.  **Retention Policy**: Указание, как долго "живет" аннотация (нам нужно `RUNTIME`, чтобы мы могли прочитать её во время выполнения тестов).
3.  **Target**: Указание, куда можно вешать аннотацию (на метод, на класс и т.д.).

---

### 🚀 Практический пример: Аннотация `@Feature`

Представь, что мы хотим, чтобы в логах при запуске теста было видно, к какой функциональной области он относится.

#### Шаг 1: Создаем аннотацию
```java
import java.lang.annotation.ElementType;
import javaint.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

// RetentionPolicy.RUNTIME — КРИТИЧЕСКИ ВАЖНО! Без этого Listener не увидит аннотацию.
@Retention(RetentionPolicy.RUNTIME) 
// Target.METHOD — значит, мы будем вешать её на методы @Test
@Target(ElementType.METHOD) 
public @interface Feature {
    String value(); // Поле, куда мы запишем название фичи
}
```

#### Шаг 2: Создаем "Мозг" (Listener), который читает аннотацию
```java
import orgary.testng.ITestListener;
import orgary.testng.ITestResult;
import java.lang.reflect.Method;

public class FeatureListener implements ITestListener {

    @Override
    public void onTestStart(ITestResult result) {
        // Получаем метод, который сейчас запускается
        Method method = result.getMethod().getTestMethod();

        // Проверяем, есть ли на этом методе наша аннотация @Feature
        if (method.isAnnotationPresent(Feature.class)) {
            // Извлекаем значение из аннотации
            Feature feature = method.getAnnotation(Feature.class);
            System.out.println("🚀 [LOG] Starting test for Feature: " + feature.value());
        } else {
            System.out.println("🚀 [LOG] Starting a generic test (No feature defined)");
        }
    }
}
```

#### Шаг 3: Используем в тестах
```java
import org.testng.annotations.Listeners;
import org.testng.annotations.Test;

@Listeners(FeatureListener.class) // Подключаем наш "мозг"
public class LoginTests {

    @Test
    @Feature("User Authentication") // Применяем нашу аннотацию
    public void testSuccessfulLogin() {
        System.out.println("Executing login test...");
    }

    @Test
    public void testGenericFunction() {
        System.out.println("Executing a simple test...");
    }
}
```

---

### ⚠️ Нюансы и "Подводные камни" (Senior Tips)

1.  **`RetentionPolicy.RUNTIME` — это база.** Если ты забудешь поставить `RUNTIME`, аннотация будет видна только в исходном коде, но когда Java запустит байт-код, она "исчезнет", и твой Listener вернет `null`.
2.  **Reflection API.** Чтение аннотаций происходит через Reflection (рефлексию). Это мощно, но помни: рефлексия — медленная операция. В масштабах одного теста это незаметно, но если у тебя 10 000 тестов и ты делаешь тяжелые вычисления внутри Listener на основе аннотаций, это может замедлить прогон.
3.  **Не переусложняй.** Не нужно создавать аннотацию для всего подряд. Используй их только тогда, когда тебе действительно нужно передать метаданные, которые меняются от теста к тесту.

---

### ❓ FAQ (Частые вопросы на собеседовании)

**В: Можно ли передавать параметры в кастомную аннотацию?**
**О:** Да. Ты просто объявляешь поля внутри `@interface`. Например: `int retry() default 1;`. Это позволит тебе писать `@Retry(retry = 3)`.

**В: Чем отличается `@Target(ElementType.METHOD)` от `@Target(ElementType.TYPE)`?**
**О:** `METHOD` позволяет вешать аннотацию на конкретный тест. `TYPE` позволяет весить её на весь класс целиком. Если ты хочешь, чтобы вся группа тестов в классе имела одну фичу, используй `TYPE`.

**В: Что будет, если Listener не найдет аннотацию?**
**О:** Если ты правильно написал код (с проверкой `isAnnotationPresent`), то ничего страшного не случится. Программа просто пойдет по ветке `else`. Но если ты попытаешься вызвать `.value()` у аннотации, которой нет — получишь `NullPointerException`. **Всегда делай проверку на наличие!**

# 📊 Тема: Стандартные отчеты TestNG

Когда ты запускаешь тесты через TestNG (через IDE или Maven), фреймворк автоматически генерирует результаты в папку `test-output` (по умолчанию). Эти отчеты — твой первый инструмент диагностики после прогона.

### 1. Виды стандартных отчетов

В стандартном наборе есть три ключевых файла, которые тебе нужно знать:

*   **`index.html` (Главный дашборд):**
    Это интерактивная HTML-страница. Она содержит иерархию: `Suite` $\rightarrow$ `Test` $\rightarrow$ `Class` $\rightarrow$ `Method`. 
    *   *Зачем нужен:* Для детального разбора упавших тестов прямо на локальной машине. Можно кликнуть на упавший метод и сразу увидеть **Stacktrace** (ошибку).
*   **`emailable-report.html` (Портативный отчет):**
    Это "облегченная" версия. В отличие от `index.html`, который тянет за собой кучу CSS и JS файлов из папки, этот файл — **один единственный HTML-файл**, в котором всё вшито внутрь.
    *   *Зачем нужен:* Это твой лучший друг для быстрой отправки результатов коллегам через Slack, Telegram или Email. Его можно просто переслать, и он откроется у любого человека без потери форматирования.
*   **`testng-results.xml` (Машиночитаемый отчет):**
    Это XML-файл со всей структурой прогона. В нем нет "красоты", но есть сухие данные: сколько тестов прошло, сколько упало, время выполнения и ошибки.
    *   *Зачем нужен:* Это **критически важный файл для CI/CD (Jenkins, GitLab CI)**. Именно этот файл парсят плагины в Jenkins, чтобы отрисовать красивые графики (Trend Graph) и построить историю запусков.

### 2. Что внутри (Ключевые метрики)
При анализе любого из этих отчетов Senior смотрит на:
1.  **Status:** `PASS`, `FAIL`, `SKIP` (пропущен), `SKIP` (из-за зависимости).
2.  **Duration:** Время выполнения каждого метода. Помогает найти "тормозящие" тесты.
3.  **Error Message & Stacktrace:** Текст ошибки и путь в коде, где всё сломалось.

### 3. Senior Nuances (Нюансы и подводные камни)

*   **Проблема "Грязной папки":** Если ты не очищаешь папку `test-output` перед новым запуском, старые результаты могут перемешаться с новыми или просто запутать тебя. **Всегда делай `mvn clean` перед запуском.**
*   **Ограниченность:** Стандартные отчеты TestNG — это "база". Они не умеют прикреплять скриншоты, логи или видео. Если тебе нужно показать отчет менеджеру или клиенту, стандартный отчет выглядит слишком "технически" и бедно. Для этого мы используем **Allure** или **ExtentReports**.
*   **Связь с Listeners:** Стандартные отчеты наполняются данными благодаря встроенным слушателям (Listeners). Если ты пишешь свой кастомный Listener, ты можешь влиять на то, что попадет в эти отчеты.

**В: Можно ли использовать стандартный `index.html` для анализа тестов в Jenkins?**

# 🚀 Шпаргалка: Интеграция TestNG с внешними фреймворками

Когда мы говорим об интеграции, мы имеем в виду, как сделать так, чтобы результаты тестов были понятны бизнесу (Reporting), как запускать их автоматически (CI/CD) и как управлять ими через код (Build Tools).

## 1. Reporting Frameworks (Отчетность)
TestNG сам по себе выдает довольно сухой `index.html`. Для серьезных проектов этого мало. Нам нужны визуальные отчеты с шагами, скриншотами и историей.

### **Allure Report (Золотой стандарт)**
Это не просто «красивые картинки», это мощный инструмент анализа.
*   **Как работает:** TestNG выполняет тесты $\to$ Allure Listener перехватывает события $\to$ Генерирует JSON-атрибуты $\to$ Allure Command Line превращает их в HTML.
*   **Ключевые фишки для интеграции:**
    *   `@Step("Текст шага")`: Разбивает тест на логические части. Без этого отчет — просто кусок текста.
    *   `@Attachment`: Позволяет «приклеивать» скриншоты, логи или файлы прямо к тесту.
    *   `@Feature` / `@Story`: Связывает автотесты с требованиями (BDD-подход).
*   **Нюанс:** Чтобы Allure «увидел» тесты, в `pom.xml` обязательно должен быть прописан `allure-testng` адаптер.

### **ExtentReports**
Более классический вариант, часто используется в энтерпрайз-проектах для создания очень красивых, статичных HTML-отчетов.
*   **Как интегрировать:** Через создание своего `ITestListener`. Ты пишешь код, который при событии `onTestSuccess` или `onTestFailure` записывает данные в объект отчета Extent.

## 2. Build Tools (Maven / Gradle) — Двигатель тестов
TestNG не живет в вакууме. Его запускает сборщик.

*   **Maven Surefire Plugin:** Это «мост» между Maven и TestNG. Именно этот плагин отвечает за то, какой `testng.xml` будет запущен.
    *   **Нюанс (Передача параметров):** Самая частая задача — передать значение из командной строки в тест.
        *   *Команда:* `mvn test -Dbrowser=chrome`
        *   *В коде:* Ты читаешь это через `System.getProperty("browser")`.
*   **Управление зависимостями:** Все библиотеки (Allure, Selenium, Log4j) управляются здесь. Если ты забудешь про `scope: test`, твои тесты могут не найти нужные классы при запуске в CI.

## 3. CI/CD Pipelines (Jenkins, GitLab CI, GitHub Actions)
Здесь TestNG превращается из «скрипта на моем компе» в часть процесса разработки.

*   **Headless Mode:** В CI нет монитора. Интеграция подразумевает настройку браузера (Selenium/Playwright) так, чтобы он работал в режиме `headless`.
*   **Artifacts (Артефакты):** Главная задача интеграции с Jenkins — настроить сохранение отчетов (Allure/Extent) как «артефакты» сборки. Если ты не настроил это, после завершения работы джоба все твои красивые отчеты удалятся вместе с рабочим пространством.
*   **Exit Codes:** TestNG должен возвращать `0`, если тесты прошли, и `1` (или другой ненулевой), если упали. Именно по этому коду CI понимает: «Блочить деплой или нет?».

## 4. Logging Frameworks (Log4j2 / SLF4J)
Тесты без логов — это слепое тестирование.
*   **Зачем:** Когда тест падает в Jenkins, ты не можешь подойти к нему и посмотреть консоль. Тебе нужен файл `.log`, где записана хронология: *«Нажал кнопку -> Ждал 5 секунд -> Получил ошибку»*.
*   креативная интеграция: Настройка логгера так, чтобы при падении теста (через `ITestListener`) лог автоматически прикреплялся к Allure-отчету.

# 📊 Allure Report: Интеграция и использование

### 1. Суть интеграции
Важно понимать: Allure — это **не** библиотека для тестирования. Это инструмент генерации отчетов. Чтобы они заработали, нам нужен «переводчик» (Adapter), который будет слушать TestNG и записывать результаты в JSON-файлы.

**Процесс выглядит так:**
`TestNG выполнение` $\rightarrow$ `Allure TestNG Adapter` $\rightarrow$ `Папка allure-results (JSON)` $\rightarrow$ `Allure Command Line` $\rightarrow$ `Красивый HTML отчет`.

### 2. Настройка (Maven)
Чтобы всё закрутилось, тебе нужны две вещи в `pom.xml`: сам адаптер и плагин для запуска тестов.

```xml
<dependencies>
    <!-- Адаптер, который превращает результаты TestNG в формат Allure -->
    <dependency>
        <groupId>io.qameta.allure</groupId>
        <artifactId>allure-testng</artifactId>
        <version>2.24.0</version> <!-- Используй актуальную версию -->
    </dependency>
</dependencies>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-surefire-plugin</artifactId>
            <version>3.1.2</version>
            <configuration>
                <!-- Важно: указываем, где искать тесты и как их запускать -->
            </configuration>
        </plugin>
    </plugins>
</top>
```

### 3. Обогащение отчета (Аннотации)
Просто запустить тесты — мало. Чтобы отчет был полезен, нужно наполнить его метаданными.

*   **`@Step("Текст шага")`**: Самая важная аннотация. Разбивает тест на понятные человеческие этаги. Если тест упал, ты сразу увидишь, на каком именно шаге (например, "Login" или "Add to cart").
*   **`@Description("Описание")`**: Подробное текстовое описание того, что проверяет этот тест.
*   **`@Severity(SeverityLevel.CRITICAL)`**: Уровень серьезности. Помогает при анализе: если упал `BLOCKER`, бросаем всё и чиним; если `MINOR` — можем подождать.
*   **`@Owner("Имя")`**: Кто отвечает за этот тест/функционал.
*   **`@TmsLink("ID")` / `@Issue("ID")`**: Ссылки на задачи в Jira или TMS (Test Management System). Это связывает автотесты с ручными тестами и требованиями.

### 4. Добавление артефактов (Скриншоты, Логи)
Senior-подход: отчет должен "говорить" сам за себя. Если тест упал, в отчете **обязательно** должен быть скриншот.

Используем статический метод `Allure.addAttachment`:

```java
import io.qameta.allure.Allure;
import java.io.ByteArrayInputStream;

public void takeScreenshot(byte[] screenshot) {
    Allure.addAttachment("Screenshot to Page", new ByteArrayInputStream(screenshot));
}
```
*Совет: Лучше всего это делать внутри `TestListener`, чтобы скриншот прикреплялся автоматически при любом падении.*

---

### 💡 Нюансы и "Подводные камни" (Senior Tips)

1.  **Разделение Results и Report**: Помни, что после запуска тестов у тебя появляется папка `allure-results` с кучей JSON. Это «сырье». Чтобы увидеть отчет, нужно выполнить команду `allure serve allure-results`. Не пытайся открывать JSON файлы напрямую.
2.  **Грязные результаты**: Если ты запускаешь тесты повторно, старые JSON в папке `allure-results` могут смешаться с новыми. **Всегда очищай папку `allure-results` перед новым запуском** (через Maven clean).
3.  **Атомарность шагов**: Не делай один гигантский `@Step` на весь тест. Если шаг слишком большой, ты не поймешь, где именно внутри него произошла ошибка. Дроби логику.
4.  **Environment Info**: Чтобы в отчете было видно, на каком стенде (Dev/Staging) и какой версией билда проходили тесты, создай файл `allure-results/environment.properties` и запиши туда нужные параметры.

**В: В чем разница между Allure Adapter и Allure Report?**
**О:** Адаптер — это библиотека в твоем проекте, которая "подслушивает" TestNG и создает JSON-файлы. Allure Report — это отдельный инструмент (CLI), который берет эти JSON и рисует из них интерактивный сайт.

**О:** Проверь использование `@Step`. Возможно, ты вешаешь аннотацию на слишком низкоуровневые методы (например, на каждый клик по элементу). Оставляй шаги только для значимых бизнес-действий.

**В: Можно ли использовать Allure с другими фреймворками, кроме TestNG?**
**О:** Да, существуют адаптеры для JUnit, Pytest, Cucumber и других. Принцип работы (Adapter $\rightarrow$ JSON $\rightarrow$ Report) остается идентичным.

# 🚀 Шпаргалка: Запуск тестов через Maven и Gradle

Когда мы говорим о запуске тестов, важно разделять: **TestNG** управляет *логикой* (что и в каком порядке запускать), а **Maven/Gradle** управляют *процессом* (как собрать проект, подтянуть зависимости и запустить выполнение в среде CI/CD).

В реальной работе никто не нажимает "Run" в IntelliJ IDEA. Все тесты запускаются через терминал или Jenkins/GitLab Runner с помощью команд сборки.

---

## 1. Maven: Король Surefire
Основной инструмент для запуска тестов в Maven — это плагин **`maven-surefire-plugin`**. Именно он отвечает за поиск классов, заканчивающихся на `*Test`, и их выполнение.

### Основные конфигурации в `pom.xml`:
Чтобы управлять тестами, мы настраиваем этот плагин:

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-surefire-plugin</artifactId>
    <version>3.2.5</version> <!-- Всегда используй свежую версию -->
    <configuration>
        <!-- Указываем, какой XML файл TestNG использовать -->
        <suiteXmlFiles>
            <suiteXmlFile>testng.xml</suiteXmlFile>
        </suiteXmlFiles>
        
        <!-- Передача системных свойств (например, браузер) -->
        <systemPropertyVariables>
            <browser>${browser}</browser>
        </systemPropertyVariables>

        <!-- Исключение определенных групп тестов -->
        <groups>regression</groups> 
        <excludedGroups>flaky</excludedGroups>
    </configuration>
</plugin>
```

### Запуск из терминала (CLI):
*   **Стандартный запуск:** `mvn test`
*   **Пропуск тестов (только сборка):** `mvn install -DskipTests`
*   **Запуск конкретного класса/метода через параметры:**
    `mvn test -Dtest=MyTestClass#myTestMethod`
*    el **Передача динамического параметра (самое важное!):**
    `mvn test -Dbrowser=firefox` — *это значение подставится в `systemPropertyVariables`, и твой код внутри Java сможет его прочитать через `System.getProperty("browser")`.*

---

## 2. Gradle: Гибкость и Скорость
Gradle использует задачу (task) `test`. В отличие от Maven, конфигурация здесь пишется на языке Groovy или Kotlin, что дает больше гибкости.

### Конфигурация в `build.gradle`:
```groovy
test {
    // Указываем, какой XML использовать
    systemProperty 'testng.xml', 'testng.xml'

    // Прокидываем системные свойства из командной строки в Java-код
    systemProperty 'browser', System.getProperty('browser')

    // Фильтрация тестов по группам (через проброс параметров)
    if (project.hasProperty('group')) {
        useTestNG {
            groups = [project.property('group')]
        }
    }

    // Настройка параллелизма на уровне Gradle (не путать с TestNG!)
    maxParallelForks = Runtime.runtime.availableProcessors() / 2
}
```

### Запуск из терминала (CLI):
*   **Стандартный запуск:** `./gradlew test`
*   **Запуск конкретной группы:** `./gradlew test -Pgroup=regression`
*   **Передача системного свойства:** `./gradlew test -Dbrowser=chrome`

## 💡 Senior Nuances (Нюансы, о которых молчат)

1.  **Разница между `systemProperty` и `argLine`**: 
    В Maven, если ты хочешь передать параметры JVM (например, настройки памяти `-Xmx512m`), тебе нужно использовать `<argLine>`. А если ты хочешь передать данные в свой код (`browser=chrome`), используй `<systemPropertyVariables>`. Новички часто путают их.
    
2.  **Проблема "Забытого XML"**: 
    Если ты настроил `suiteXmlFile` в `pom.xml`, но запускаешь тесты через `mvn test -Dtest=MyTest`, Maven может проигнорировать твой `testng.xml` и попытаться запустить класс "как есть". Всегда проверяй, как твои команды взаимодействуют с конфигурацией плагина.

3.  **Параллелизм: Уровни управления**:
    *   **Уровень Gradle/Maven:** Создает несколько процессов JVM (тяжело, но изолированно).
    *   **Уровень TestNG:** Внутри одного процесса запускает много потоков (легко, быстро, но требует `ThreadLocal` для драйвера). 
    *   *Senior tip:* Всегда используй параллелизм на уровне **TestNG**, если только тебе не нужно тестировать разные версии Java или специфичные настройки окружения.

4.  **CI/CD Pipeline**: В Jenkins/GitLab мы никогда не пишем `mvn test`. Мы пишем скрипт, который может принимать аргументы. Твой проект должен быть "заточен" под то, чтобы параметры (браузер, среда, уровень тестов) приходили извне через `-D` или `-P`.

## ❓ FAQ (Подготовка к интервью)

**В: Как запустить только один метод в TestNG через Maven?**
**О:** Можно использовать параметр `-Dtest=ClassName#methodName`, но при этом важно, чтобы `maven-surefire-plugin` не перекрывал этот запрос своим жестко прописанным `suiteXmlFile`. Лучший способ — настроить фильтрацию групп в самом XML.

**В: Что произойдет, если я передам `-Dbrowser=chrome`, но не пропишу его в `pom.xml` в секции `systemPropertyVariables`?**
**О:** Тест запустится, но твой Java-код (через `System.getProperty("browser")`) получит `null`. Параметр попадет в процесс Maven, но не "пробросится" внутрь работающего теста.

**В: В чем разница между `mvn install` и `mvn test`?**
**О:** `mvn test` только компилирует и запускает тесты. `mvn install` проходит через все стадии (compile, test, package, verify) и сохраняет готовый JAR-файл в твой локальный репозиторий (`.m2`), чтобы другие проекты могли его использовать как зависимость.

**В: Как в Gradle передать переменную из командной строки так, чтобы она стала доступна в Java?**
**О:** Нужно сделать два шага: 1) Принять её в `build.gradle` через `System.getProperty`, 2) Прокинуть её в блок `test { systemProperty ... }`. Само по себе `-D` в Gradle не магически не появляется внутри тестов.
